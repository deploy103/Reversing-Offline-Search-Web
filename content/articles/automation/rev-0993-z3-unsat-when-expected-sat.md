## 한 줄 요약
`s.check()`가 `unsat`을 반환하는 것은 "Z3가 못 풀어서" 나는 결과가 아니라 "지금 입력한 제약조건들을 동시에 만족하는 값이 수학적으로 존재하지 않는다"는 확정적 결론이며, 실제 검증 로직을 그대로 옮겼다면 거의 항상 부호(signed/unsigned) 처리 실수, 비트 폭 불일치, 또는 원래 로직 자체를 잘못 옮긴 번역 오류가 원인이다.

## 언제 검색해야 하나
- 리버싱한 검증 함수를 손으로 확인했을 때는 분명히 만족 가능한 조건인데 Z3가 `unsat`을 반환할 때
- `s.add()`로 조건을 하나씩 추가하다가 특정 시점부터 갑자기 `unsat`으로 바뀌어서 원인 조건을 못 찾겠을 때
- 부호 있는 비교(`<`, `>`)를 썼는데 Z3의 기본 비교 연산자가 부호 없는 비교라는 사실을 몰라서 결과가 이상할 때
- CTF 라이트업 코드를 그대로 따라 쳤는데 자신의 바이너리에서는 `unsat`이 나서 코드가 틀렸는지 로직 파악이 틀렸는지 구분이 안 될 때

## 핵심 개념
Z3의 `s.check()`는 세 가지 결과만 반환한다. `sat`(만족하는 값이 존재), `unsat`(만족하는 값이 절대 존재하지 않음), `unknown`(제한 시간/자원 안에 결론을 못 냄). 여기서 반드시 이해해야 할 점은, `unsat`은 Z3의 능력 부족이 아니라 **논리적으로 확정된 답**이라는 것이다. 즉 지금 `s.add()`로 넣은 조건들 중 최소 두 개 이상이 서로 모순되어, 어떤 값을 넣어도 전부를 동시에 만족시킬 수 없다는 뜻이다.

리버싱 자동화에서 `unsat`이 뜨는 원인은 거의 항상 다음 중 하나다.

1. **부호(signed/unsigned) 불일치** — Z3 `BitVec`의 기본 비교 연산자(`<`, `>`, `<=`, `>=`)는 **부호 없는(unsigned) 비교**다. C 코드가 `int`(부호 있는 타입)를 비교하는데 이를 그대로 `x > y`로 옮기면, 음수가 관여하는 순간 실제 C의 의미와 다르게 해석되어 모순이 생길 수 있다. 부호 있는 비교가 필요하면 별도의 signed 비교 연산자를 써야 한다.
2. **비트 폭 불일치** — C에서는 `char`(8비트)였는데 Z3에서 `BitVec('x', 32)`로 선언하면, 값이 잘리는(truncate) 지점이 달라져서 원래는 성립하던 오버플로우 조건이 성립하지 않게 된다.
3. **로직 번역 실수** — 조건문의 방향을 반대로 옮기거나(`==`를 `!=`로), 비트 연산 우선순위를 파이썬 연산자 우선순위와 착각해서 괄호를 빠뜨리는 경우.
4. **도달 불가능한 분기 로직** — 원래 C 코드에 애초에 실행되지 않는 죽은 코드(dead code)나 상수로 인해 항상 거짓인 분기가 있는 경우, 그 분기의 조건까지 그대로 `s.add()`에 옮기면 처음부터 `unsat`이 되는 것이 오히려 정상이다.

## 화면/코드에서 보이는 징후
```python
>>> s.check()
unsat
>>> s.model()
Traceback (most recent call last):
  ...
z3.z3types.Z3Exception: model is not available
```
`unsat` 뒤에 `s.model()`을 호출하면 예외가 난다. 이것 자체는 정상 동작이다(만족하는 모델이 없으니 당연히 꺼낼 모델도 없다). 문제는 "왜 unsat인지"를 못 찾는 것이다.

## 가장 먼저 할 것
`s.add()` 호출을 전부 주석 처리하고, 한 줄씩 다시 살려가며 `s.check()`를 반복 실행한다. 어느 조건을 추가하는 순간 `sat`에서 `unsat`으로 바뀌는지 찾으면 그 조건(또는 그 조건과 바로 이전 조건의 조합)이 원인이다.

## 단계별 절차

**1) 조건 이분 탐색으로 원인 좁히기**
```python
from z3 import *

x = BitVec('x', 32)
s = Solver()
s.add(x * 3 - 7 == 0x50)   # 조건 A
print('A만:', s.check())    # sat인지 먼저 확인

s.add(x < 0)                 # 조건 B 추가
print('A+B:', s.check())     # 여기서 unsat이면 B가 의심
```
조건을 하나씩 추가할 때마다 `s.check()`를 찍어 어느 시점부터 `unsat`으로 바뀌는지 확인한다.

**2) 부호 비교인지 확인하기**
C 코드가 `if (x < 0)`처럼 부호 있는 비교를 한다면, Z3 기본 연산자 대신 부호 있는 비교를 명시적으로 써야 한다.
```python
from z3 import *
x = BitVec('x', 32)
s = Solver()

# 잘못된 예: 기본 <, > 는 unsigned 비교라서 "음수"라는 개념 자체가 다르게 취급된다
s.add(x < 0)          # unsigned 기준으로는 절대 참이 될 수 없어 항상 unsat 유발 가능
print(s.check())       # unsat

s2 = Solver()
s2.add(x < BitVecVal(0, 32))  # 여전히 unsigned 비교이므로 동일하게 unsat
print(s2.check())
```
부호 있는 음수 조건을 표현하려면 signed 비교 연산자를 쓰거나, 조건을 `x > 0x7fffffff`(32비트 unsigned 표현에서 최상위 비트가 1인 범위)처럼 unsigned 관점으로 다시 써야 한다.

**3) 비트 폭 재확인**
원래 C 변수 타입을 다시 확인한다. `char`는 8비트, `short`는 16비트, `int`는 32비트, `long`(리눅스 x64)은 64비트다. `BitVec` 선언에 잘못된 폭을 쓰지 않았는지 각 변수마다 다시 점검한다.

**4) 최소 재현으로 축소**
전체 검증 로직이 아니라, 의심되는 조건 한두 개만 남긴 아주 작은 스크립트를 새로 짜서 그 부분만 따로 `sat`/`unsat`을 확인한다. 전체 스크립트에서 디버깅하는 것보다 훨씬 빠르게 원인을 좁힐 수 있다.

## 명령어/단축키
- `s.check()` : `sat`/`unsat`/`unknown` 반환
- `s.assertions()` : 현재 솔버에 들어있는 모든 제약조건 목록 출력(무엇이 들어갔는지 재확인용)
- `s.push()` / `s.pop()` : 현재 조건 상태를 저장하고, 나중에 그 시점으로 되돌리기(조건을 하나씩 실험할 때 유용)
- `Solver().check(extra_condition)` : 기존 조건에 추가로 임시 조건 하나만 넣어서 즉석 테스트

## 출력 해석
- `unsat` — 지금 들어있는 조건들이 동시에 성립할 수 없다는 확정적 결론. "조건을 잘못 옮겼거나, 원래 로직에 도달 불가능한 분기가 있다"고 해석해야 한다.
- `s.assertions()` 출력 — 지금까지 `s.add()`로 누적된 조건이 정확히 무엇인지 그대로 보여준다. 눈으로 다시 읽어보면 괄호 누락이나 연산자 실수를 바로 찾는 경우가 많다.
- 조건을 하나씩 껐다 켰다 하면서 `sat`으로 바뀌는 지점을 찾았다면, 그 조건이 원래 C 로직과 정확히 같은 의미인지(부호, 비트 폭, 연산 순서) 다시 대조해야 한다.

## 흔한 실수
- Z3 `BitVec`의 기본 비교 연산자가 unsigned라는 사실을 모르고 부호 있는 C `int` 비교를 그대로 옮기는 것.
- 원래 변수가 8비트/16비트인데 습관적으로 32비트 `BitVec`을 선언해서 잘림(truncate) 지점이 달라지는 것.
- `unsat`이 뜨자마자 "Z3가 이 문제를 못 푼다"고 오해하고 다른 도구로 갈아타는 것 — 대부분은 도구 문제가 아니라 조건 번역 실수다.
- 여러 `Solver()` 인스턴스를 헷갈려서, 조건을 추가한 솔버가 아니라 새로 만든 빈 솔버에 `check()`를 호출하는 것.

## 막혔을 때 다음 체크
- 비트 폭 관련 실수가 의심되면 → REV-0994 Z3 비트 폭 불일치 오류.
- 문자/문자열 단위 조건에서 unsat이 계속 나면 → REV-0269 Z3로 문자 조건 풀기.
- 8비트/32비트 오버플로우가 섞인 로직이면 → REV-0270 Z3에서 8비트 32비트 Overflow 다루기.
- 조건 자체가 너무 복잡해 손으로 옮기기 어렵다면 → REV-0271 angr 심볼릭 실행 기초로 넘어가 바이너리 실행 자체를 심볼릭하게 시뮬레이션하는 것을 고려한다.

## 미니 예제
```python
from z3 import *

x = BitVec('x', 8)  # 원래 C 코드에서 unsigned char x 라고 가정
s = Solver()

s.add(x + 10 == 5)   # 8비트 unsigned 관점에서는 x = 251 (0xfb) 일 때 251+10=261 -> 8비트로 잘려 5가 됨
print(s.check())       # sat
print(s.model())       # [x = 251]
```
같은 조건을 32비트로 잘못 선언하면 오버플로우 지점이 달라져 결과가 완전히 달라진다.
```python
x2 = BitVec('x', 32)
s2 = Solver()
s2.add(x2 + 10 == 5)
print(s2.check())      # sat이지만 model 값이 8비트일 때와 전혀 다름(음수 wraparound 지점이 다름)
```
이처럼 비트 폭 하나만 달라져도 `sat`/`unsat` 여부와 모델 값이 통째로 바뀔 수 있으므로, 원래 C 타입을 정확히 확인하는 것이 `unsat` 디버깅의 출발점이다.

## 관련 글
- REV-0994 — Z3 제약조건 작성 시 비트 폭이 안 맞아서 오류가 날 때
- REV-0268 — Z3 BitVec 기초
- REV-0269 — Z3로 문자 조건 풀기
- REV-0270 — Z3에서 8비트 32비트 Overflow 다루기

## 출처/검증
- `s.check()`가 `sat`/`unsat`/`unknown` 세 가지만 반환한다는 점과 `BitVec` 비교 연산자의 기본 동작(unsigned)은 Z3 공식 GitHub(Z3Prover/z3) 및 Z3py 튜토리얼 문서를 기준으로 정리했다(2026-09-09 검증).
- 코드 예제는 `pip install z3-solver` 환경의 표준 CPython 3에서 그대로 재현 가능하다.
