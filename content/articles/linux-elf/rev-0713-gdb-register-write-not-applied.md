## 한 줄 요약
GDB에서 `set $rax = 값`으로 레지스터를 바꿨는데도 반영이 안 되는 것처럼 보이는 경우는 대부분 진짜로 안 바뀐 게 아니라, 현재 몇 번째 프레임(`frame N`)을 보고 있는지, 어느 스레드를 보고 있는지, 아직 한 스텝도 실행하지 않아 값이 그대로인지, 또는 화면(TUI/display)이 갱신되지 않은 것인지를 착각한 경우다.

## 언제 검색해야 하나
- `set $rax = 5`를 했는데 바로 `print $rax`를 해도 여전히 이전 값이 나올 때
- 콜스택 위쪽 프레임(`frame 1` 등)에서 레지스터를 바꿨는데 실제 프로그램 동작에는 아무 영향이 없을 때
- 멀티스레드 프로그램에서 레지스터를 바꿨는데 계속 이상하게 동작할 때
- TUI(`layout regs`) 창에 보이는 레지스터 값이 명령을 쳐도 그대로 멈춰있는 것처럼 보일 때

## 핵심 개념

### 레지스터 쓰기는 "현재 선택된 프레임"이 아니라 실제로는 프레임 0(가장 안쪽)에서만 의미가 있다
GDB의 `bt`/`frame N`으로 콜스택 중 바깥쪽 프레임(호출자)을 선택하고 그 상태에서 `print $rax` 같은 걸 하면, GDB는 그 프레임의 레지스터 값을 스택 언와인딩(unwinding) 정보로 **재구성해서 보여준다**. 이 값은 실제 CPU 레지스터가 아니라 "그 프레임이 실행되던 시점에 저장되어 있었을 값"의 추정치다. 이 상태에서 `set $rax = 값`을 해도 GDB는 경고 없이 받아주는 것처럼 보이지만, 실제 CPU 레지스터(프레임 0의 값)에는 반영되지 않는 경우가 있어 "분명 명령어를 쳤는데 실행에 아무 영향이 없다"고 느끼게 된다. 레지스터를 실제로 바꿔서 실행 흐름에 영향을 주려면 반드시 `frame 0`(가장 안쪽, 현재 실행 중인 프레임)으로 돌아온 상태에서 수정해야 한다.

### 아직 한 스텝도 실행하지 않아서 "그대로"인 것
`set $rax = 5`는 그 순간 레지스터 값 자체는 바로 바뀐다. 하지만 프로그램은 `next`/`step`/`continue`로 실행을 진전시키기 전까지는 그 어떤 동작도 하지 않으므로, "레지스터를 바꿨는데 프로그램 출력/분기 결과가 그대로"라고 느끼는 건 아직 그 값을 사용하는 명령어까지 실행이 안 갔기 때문일 수 있다. `print $rax`로 레지스터 값 자체는 이미 바뀌어 있는지 먼저 확인하는 습관이 필요하다.

### 서브레지스터 크기 혼동
`$eax`를 `0x1234`로 설정하면 x86-64에서는 상위 32비트(`$rax`의 상위 절반)가 자동으로 0으로 클리어된다(제로 확장). 반대로 `$al`(하위 8비트)만 바꾸면 나머지 상위 바이트는 그대로 남는다. 어떤 폭의 레지스터를 바꿨는지와 어떤 폭으로 확인하는지가 다르면 "값이 이상하게 반영됐다/안 됐다"고 오해하기 쉽다.

### 멀티스레드에서 다른 스레드를 보고 있는 경우
`info threads`로 스레드 목록을 확인하지 않고 레지스터를 수정하면, 현재 GDB가 포커스하고 있는 스레드가 아니라 다른 스레드의 실행에는 아무 영향이 없다. 각 스레드는 자신만의 레지스터 세트를 가지므로 `thread N`으로 대상 스레드를 명확히 선택한 뒤 수정해야 한다.

### TUI/display 갱신 타이밍
`layout regs`로 레지스터 창을 띄운 상태에서 `set $rax = 값`만 치면, 화면이 다음 정지 이벤트(`step`/`next`/`continue` 후 재정지) 전까지 갱신되지 않는 것처럼 보일 수 있다. 실제 값은 바뀌었지만 화면 갱신 타이밍 때문에 착시가 생기는 것으로, `print $rax`로 직접 확인하면 이미 바뀌어 있는 경우가 많다.

## 화면/코드에서 보이는 징후
```gdb
(gdb) frame 1
(gdb) set $rax = 0
(gdb) frame 0
(gdb) print $rax
$1 = 32          # frame 1에서 바꾼 값이 반영되지 않음
```

## 가장 먼저 할 것
`bt`로 지금 몇 번째 프레임을 보고 있는지 확인하고, 실제 실행에 영향을 주고 싶다면 반드시 `frame 0`으로 이동한 뒤 레지스터를 수정한다. 멀티스레드라면 `info threads`로 대상 스레드도 함께 확인한다.

## 단계별 절차
1. `bt`로 현재 프레임 번호 확인
2. `frame 0`(가장 안쪽 프레임)으로 이동
3. `info threads`로 대상 스레드가 맞는지 확인, 필요하면 `thread N`으로 전환
4. `set $rax = 값` (또는 `set var 변수명 = 값`) 실행
5. 바로 `print $rax`로 값이 실제로 바뀌었는지 재확인
6. 서브레지스터(`$eax`, `$ax`, `$al`)를 썼다면 폭에 맞는 이름으로 다시 확인해 제로 확장/부분 갱신 여부 점검
7. 그래도 실행 흐름이 안 바뀐다면 `x/i $pc`로 다음에 실행될 명령어가 실제로 그 레지스터를 사용하는지 확인 — 애초에 그 레지스터를 안 쓰는 지점이면 값을 바꿔도 결과가 그대로인 게 정상

## 명령어/단축키
```gdb
bt
frame 0
frame N
info threads
thread N
set $rax = 값
set var VAR = 값
print $rax
print/x $eax
x/i $pc
layout regs
```

## 출력 해석
`frame 0`에서 `set $rax = ...` 후 `print $rax`가 즉시 새 값을 보여주면 정상적으로 반영된 것이다. `frame 1` 이상에서 수정한 뒤 `frame 0`으로 돌아왔을 때 값이 바뀌지 않았다면, 그것이 바로 "바깥 프레임 레지스터 쓰기가 실제 실행에는 반영되지 않는다"는 신호다.

## 흔한 실수
- 콜스택을 살펴보다가 `frame 1`, `frame 2`에 머문 채로 레지스터를 수정하고 `frame 0`으로 안 돌아온 것을 잊는 것.
- `set $eax`로 바꿨는데 `print $rax`(64비트 전체)로 확인하면서 "왜 상위 비트가 이상하지"라고 헷갈리는 것 — 제로 확장은 정상 동작이다.
- 멀티스레드 프로그램에서 `thread`를 확인하지 않고 엉뚱한 스레드의 레지스터만 계속 바꾸는 것.
- 레지스터는 이미 바뀌었는데 TUI 화면 갱신이 늦어서 "안 바뀐 줄" 알고 같은 명령을 반복 입력하는 것.

## 막혔을 때 다음 체크
- 브레이크포인트/워치포인트가 예상 시점과 다르게 걸리는 문제라면 → REV-0708 GDB에서 tbreak/watch가 예상과 다른 시점에 걸릴 때.
- 함수 반환값을 확인하는 절차가 헷갈리면 → REV-0657 GDB에서 함수 반환값을 finish로 확인하는 법.
- GDB 심화 브레이크포인트/워치포인트 명령 전반이 궁금하면 → REV-0642 GDB 명령어 심화 치트시트(watch/catch/tbreak).

## 미니 예제
```gdb
(gdb) bt
#0  check (x=10) at chall.c:15
#1  0x0000000000401290 in main () at chall.c:20
(gdb) frame 1
#1  0x0000000000401290 in main () at chall.c:20
(gdb) set $rax = 0
(gdb) frame 0
#0  check (x=10) at chall.c:15
(gdb) print $rax
$1 = 140737488346624
```
`frame 1`에서 바꾼 값이 `frame 0`으로 돌아오자 그대로 사라진 것을 볼 수 있다. 실행에 영향을 주려면 처음부터 `frame 0` 상태에서 수정했어야 한다.

## 관련 글

- REV-0657 — GDB에서 함수 반환값을 finish로 확인하는 법
- REV-0642 — GDB 명령어 심화 치트시트(watch/catch/tbreak)

## 출처/검증
- GDB의 프레임 선택과 언와인딩된 레지스터 값이 실제 CPU 레지스터와 다르게 취급되는 동작, `set $reg`/`set var` 명령: GDB 공식 매뉴얼("Debugging with GDB") "Selecting a Frame"/"Registers" 챕터 기준 (2026-09-09 검증).
- x86-64에서 32비트 레지스터 쓰기 시 상위 32비트가 자동으로 제로 확장되는 동작: Intel 64 and IA-32 Architectures Software Developer's Manual 기준.
- GDB의 스레드별 레지스터 컨텍스트와 `thread`/`info threads` 명령: GDB 공식 매뉴얼 "Threads" 챕터 기준.
