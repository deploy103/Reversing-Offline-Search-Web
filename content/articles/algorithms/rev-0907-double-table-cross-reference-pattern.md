## 한 줄 요약
이중 테이블 패턴은 서로 다른 두 개의 룩업 테이블(순방향 테이블과 역방향 테이블, 또는 두 개의 독립적인 치환 테이블)을 함께 사용해서 한 테이블의 출력을 다른 테이블의 입력 인덱스로 다시 넣는 구조이며, REV-0215(단일 룩업 테이블)의 확장판으로 두 테이블 모두를 원본 그대로 덤프하고 어느 것이 순방향/역방향인지부터 구분하면 그대로 역산할 수 있다.

## 언제 검색해야 하나
- `.rodata`나 전역 변수 영역에 크기가 같거나 비슷한 배열 두 개가 붙어서 선언되어 있을 때
- 코드에서 `table_a[input[i]]`의 결과를 다시 `table_b[...]`의 인덱스로 넣는 이중 인덱싱이 보일 때
- 디컴파일에서 배열 이름이 `sbox`/`inv_sbox`, `enc_table`/`dec_table`처럼 짝을 이루는 느낌일 때
- REV-0215 단일 테이블 패턴을 적용해봤는데 결과가 안 맞아서, 사실은 테이블이 하나가 아니라 두 개가 얽혀 있는 게 아닌지 의심될 때

## 핵심 개념

### 왜 테이블을 두 개 쓰는가
단일 치환 테이블(REV-0215)은 `output = table[input]` 형태로 끝나지만, 실전 알고리즘에서는 다음과 같은 이유로 테이블 두 개를 함께 쓰는 경우가 많다.

1. **암호화/복호화 대칭성**: AES의 S-box와 Inverse S-box처럼, 정방향 변환에 쓰는 테이블과 그 역변환에 쓰는 테이블을 각각 따로 저장해두면 암호화 코드와 복호화 코드가 대칭적으로 단순해진다. 복호화 쪽 코드만 보면 "역방향 테이블"이 별도로 존재하는 이유를 알 수 있다.
2. **2단 치환(2-stage substitution)**: 입력을 테이블 A로 한 번 치환한 뒤, 그 결과를 다시 테이블 B로 치환하는 이중 치환. 이 경우 두 테이블을 합성한 효과(`table_b[table_a[x]]`)는 사실 하나의 256엔트리 테이블로 미리 합쳐서 표현할 수 있지만, 원본 바이너리는 두 단계로 나눠서 구현했을 뿐이다.
3. **테이블 기반 순열(permutation) + 값 치환의 결합**: 테이블 A는 인덱스를 재배열하는 용도(REV-0216 배열 셔플과 유사)이고, 테이블 B는 그 재배열된 위치에서 값 자체를 바꾸는 용도로 역할이 분리된 경우.

### 순방향/역방향 구분법
두 테이블이 서로 역함수 관계라면, 다음 성질이 반드시 성립한다.

```
모든 x에 대해 table_b[table_a[x]] == x
```

이 성질을 파이썬으로 두 테이블을 각각 덤프한 뒤 바로 검증할 수 있다. 성립하면 순방향/역방향 쌍이 확실하고, 성립하지 않으면 2단 치환처럼 역할이 다른 두 테이블이라는 뜻이다.

### 합성 테이블로 단순화하기
2단 치환이든 역함수 쌍이든, 리버싱 목적에서는 두 테이블을 파이썬에서 미리 합성해 하나의 매핑으로 만들어두면 이후 계산이 훨씬 쉬워진다.

```python
composed = [table_b[table_a[x]] for x in range(256)]
```

이렇게 만든 `composed` 테이블 하나만 있으면, 원본 코드가 두 단계로 나눠 처리하던 것을 한 번의 인덱싱(`composed[input[i]]`)으로 재현할 수 있다. 이 합성 테이블이 항등함수(`composed[x] == x`)로 나온다면 두 테이블이 서로의 완전한 역함수라는 뜻이고, 항등함수가 아니라면 실제 정보를 담은 유효 변환이라는 뜻이다.

## 화면/코드에서 보이는 징후
- `.rodata`에 256바이트(또는 16, 64 등) 크기 배열 두 개가 이름 없이 나란히 붙어 있음(`unk_402100`, `unk_402200` 등)
- 디컴파일 코드에서 `b = table1[a]; c = table2[b];` 형태로 두 테이블을 연쇄적으로 인덱싱
- 암호화 함수와 복호화 함수가 각각 다른 테이블을 참조하는데 두 함수의 구조가 대칭적으로 닮아 있음
- 한 테이블만 갖고 REV-0215 방식으로 계산했을 때 결과가 항상 어긋남

## 가장 먼저 할 것
두 배열의 시작 주소와 크기를 각각 확정하고, IDA/Ghidra의 Hex View(`Alt+B`)로 각 배열의 바이트를 전부 덤프한다. 그다음 코드에서 어떤 순서로(`table_a` 먼저인지 `table_b` 먼저인지) 인덱싱되는지 정확히 옮겨 적는다.

## 단계별 절차
1. `.rodata` 영역에서 두 테이블의 시작 주소, 크기, 원소 타입(1바이트/4바이트 등)을 확정한다.
2. IDA에서 각 배열 위에 커서를 놓고 `Array`(`*`) 또는 `D`로 배열 범위를 지정한 뒤 `Alt+B`로 raw 바이트를 그대로 읽어 파이썬 리스트로 옮긴다.
3. 코드에서 두 테이블이 참조되는 순서(어떤 변수가 먼저 어떤 테이블의 인덱스로 쓰이는지)를 의사코드로 정확히 옮긴다.
4. 파이썬에서 `table_b[table_a[x]] == x`가 모든 `x`에 대해 성립하는지 검사해 순방향/역방향 쌍인지 확인한다.
5. 역함수 쌍이 아니라면 `composed[x] = table_b[table_a[x]]`로 합성 테이블을 만들어 REV-0215 방식으로 단일 테이블처럼 다룬다.
6. 재구현한 파이썬 코드가 실제 바이너리와 같은 출력을 내는지 알려진 입력 몇 개로 교차 검증한다(REV-0919).

## 명령어/단축키
```python
def dump_table_from_hex(hex_str: str) -> list[int]:
    raw = bytes.fromhex(hex_str)
    return list(raw)

table_a = dump_table_from_hex("637C777BF26B6FC5...")  # IDA Hex View에서 복사한 바이트
table_b = dump_table_from_hex("52096AD53036A538...")

# 역함수 쌍인지 검증
is_inverse_pair = all(table_b[table_a[x]] == x for x in range(len(table_a)))
print(is_inverse_pair)

# 2단 치환이면 합성 테이블 생성
composed = [table_b[table_a[x]] for x in range(len(table_a))]
```
IDA: 테이블 시작 주소에서 `*`(Array) 후 개수 입력 → 배열 전체 선택 → `Edit > Export data`로 바이트 내보내기, 또는 Hex View에서 드래그 후 복사.

## 출력 해석
- `is_inverse_pair`가 `True`면 두 테이블은 순방향/역방향 쌍이다 — 이 경우 암호화 코드를 볼 때 `table_a`만, 복호화 코드를 볼 때 `table_b`만 신경 쓰면 되고, 서로를 역산할 필요 없이 이미 역함수가 주어져 있는 것이다.
- `False`가 나오면 두 테이블은 독립적인 역할(순열+치환 분리 등)을 하므로, `composed` 테이블을 직접 계산해서 그 자체를 REV-0215의 단일 룩업 테이블처럼 취급해야 한다.
- `composed`가 항등함수(`composed[x] == x` for all x)로 나오면, 실질적으로 이 두 테이블 단계는 아무 정보도 추가하지 않는 장식적 코드(난독화 목적)일 가능성이 있다 — 이 경우 이 단계를 건너뛰고 다음 변환에 집중해도 된다.

## 흔한 실수
- 두 테이블 중 하나만 덤프하고 나머지는 "비슷하겠지"라고 추측하는 것 — 두 테이블의 바이트가 완전히 다른 경우가 대부분이므로 반드시 둘 다 정확히 덤프해야 한다.
- 인덱싱 순서(`table_a[table_b[x]]`인지 `table_b[table_a[x]]`인지)를 반대로 재구현하는 것 — 순서가 바뀌면 합성 결과가 완전히 달라진다. 디컴파일 코드의 변수 흐름을 줄 단위로 따라가며 확인해야 한다.
- 두 테이블이 역함수 쌍인지 검증하지 않고 무작정 둘 다 순방향으로 취급해서 역산 로직을 잘못 세우는 것.
- 테이블 크기를 실제보다 작게 잘라서 덤프하는 것 — 256엔트리 테이블인데 앞의 16바이트만 보고 패턴을 추측하면 나머지 240바이트에서 어긋난다. 전체 크기를 반드시 확인한다.

## 막혔을 때 다음 체크
- 테이블이 하나뿐인 단순 치환이라면 → REV-0215 Lookup Table 기반 변환
- 테이블 결과가 인덱스 재배열(순열)에 쓰인다면 → REV-0216 배열 인덱스 재배열 Shuffle 검증
- 재구현한 합성 로직이 실제 바이너리와 맞는지 확실히 검증하고 싶다면 → REV-0919
- 이 변환이 AES S-box처럼 표준 암호의 일부인지 궁금하면 → REV-0211 AES 테이블 또는 AES API 흔적 찾기

## 미니 예제
간단한 예제로 두 개의 4엔트리 테이블이 있다고 하자.

```python
table_a = [2, 0, 3, 1]   # 순열 역할
table_b = [10, 20, 30, 40]  # 값 치환 역할

def transform(x: int) -> int:
    return table_b[table_a[x]]

for x in range(4):
    print(x, transform(x))
# 0 -> table_a[0]=2 -> table_b[2]=30
# 1 -> table_a[1]=0 -> table_b[0]=10
# 2 -> table_a[2]=3 -> table_b[3]=40
# 3 -> table_a[3]=1 -> table_b[1]=20
```

이 결과를 합성 테이블로 미리 계산해두면 이후 입력 4개짜리 배열 전체를 한 번에 변환할 수 있다.

```python
composed = [table_b[table_a[x]] for x in range(4)]
print(composed)  # [30, 10, 40, 20]

def check(input_bytes: list[int]) -> list[int]:
    return [composed[b] for b in input_bytes]

print(check([0, 1, 2, 3]))  # [30, 10, 40, 20]
```
실제 CTF 문제에서는 테이블 크기가 16이나 256이고 값도 훨씬 불규칙하지만, 원리는 이 예제와 똑같다 — 두 테이블을 정확히 덤프하고 인덱싱 순서만 지키면 파이썬으로 그대로 재현된다.

## 관련 글
- REV-0215 — Lookup Table 기반 변환
- REV-0216 — 배열 인덱스 재배열 Shuffle 검증
- REV-0211 — AES 테이블 또는 AES API 흔적 찾기
- REV-0919 — 알고리즘 복원 결과를 원본과 바이트 단위로 비교 검증하기

## 출처/검증
- AES S-box/Inverse S-box가 서로 역함수 관계로 설계된 표준 구조: FIPS 197 (Advanced Encryption Standard) 공식 명세 기준.
- 2단 치환(순열+값 치환)이 하나의 합성 테이블로 환원 가능하다는 성질: 함수 합성의 기본 수학적 정의(치환 함수는 합성해도 여전히 치환 함수) 기준 (2026-09-09 검증).
