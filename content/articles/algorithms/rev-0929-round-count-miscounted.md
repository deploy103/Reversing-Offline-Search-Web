## 한 줄 요약
블록 암호나 해시의 라운드(반복) 구조를 재구현했는데 값이 안 맞는다면, 자료마다 "라운드"를 세는 방식이 다르거나(같은 루프를 어떤 문서는 32번, 어떤 문서는 64번이라고 부름) 마지막 라운드가 다른 라운드와 다르게 동작하는 예외 규칙을 놓쳤을 가능성이 크므로, **문서의 "N라운드"라는 말을 믿지 말고 디스어셈블리의 루프 종료 조건을 직접 세어서 확인**해야 한다.

## 언제 검색해야 하나
- TEA/XTEA, AES 같은 라운드 기반 알고리즘을 재구현했는데 값이 절반만 맞거나 정확히 두 배/절반 어긋날 때
- 참고 자료(위키, 블로그)에 나온 "N라운드"라는 설명과 실제 바이너리의 루프 횟수가 다르게 느껴질 때
- 결과가 대부분의 라운드에서는 맞다가 마지막 한 단계에서만 틀릴 때
- CTF 문제가 표준 알고리즘의 라운드 수를 의도적으로 줄이거나 늘린 변형일 때

## 핵심 개념
"라운드"라는 단어의 정의 자체가 문헌마다 다르게 쓰이는 경우가 있다. 예를 들어 TEA는 원 논문 기준 **`for` 루프가 32번 반복**되며, 매 반복마다 `v0`와 `v1`을 한 번씩 갱신한다. 그런데 일부 자료는 이를 "각 워드 갱신을 개별 라운드로 세어 64라운드"라고 설명하기도 한다. 둘 다 "같은 코드"를 가리키지만 부르는 숫자가 다르므로, 이 용어만 믿고 루프를 32번 대신 64번(또는 그 반대) 돌리면 완전히 다른 결과가 나온다. **결론적으로 "N라운드"라는 설명은 참고만 하고, 실제 반복 횟수는 항상 디스어셈블리의 루프 카운터 초기값과 종료 조건(`cmp`, `jl`/`jle` 등)을 직접 세어서 확정해야 한다.**

또 다른 흔한 함정은 **마지막 라운드가 다른 라운드와 다르게 동작하는 경우**다. 예를 들어 AES는 키 크기에 따라 `Nr`(10/12/14)라운드를 도는데, 표준 라운드는 `SubBytes → ShiftRows → MixColumns → AddRoundKey` 네 단계를 거치지만, **마지막 라운드만 `MixColumns` 단계가 빠진다.** 이 예외를 모르고 모든 라운드에 동일한 함수를 그대로 적용하면, 처음 `Nr-1`개 라운드는 맞다가 정확히 마지막 라운드에서만 결과가 틀리게 된다.

루프 반복 횟수의 단순한 off-by-one도 흔하다. `for (i = 0; i <= n; i++)`(n+1번 반복, 흔치 않지만 존재)와 `for (i = 0; i < n; i++)`(n번 반복)를 헷갈리거나, 반복 종료 조건이 `jle`(이하일 때 분기, 즉 크거나 같을 때 종료)인지 `jl`(미만일 때 분기)인지 착각하면 반복 횟수가 하나씩 어긋난다.

## 화면/코드에서 보이는 징후
```asm
        xor   ecx, ecx        ; i = 0
.loop:
        ...
        inc   ecx
        cmp   ecx, 0Ah        ; 10과 비교
        jl    .loop            ; ecx < 10이면 반복 -> 총 10번 반복(0..9)
```
- 위처럼 `jl`(미만)과 `jle`(이하)의 차이, 비교 상수가 정확히 몇인지에 따라 반복 횟수가 9번/10번/11번으로 갈릴 수 있음
- 라운드 함수 내부에서 마지막 반복만 호출하는 하위 함수 개수가 다른 반복보다 하나 적은 패턴(마지막 라운드 예외 처리)

## 가장 먼저 할 것
디스어셈블리에서 루프 카운터의 **초기값, 증가 방식, 종료 비교 상수, 분기 조건(jl/jle/jge 등)** 네 가지를 표로 적어 정확한 반복 횟수를 계산한다. 참고 문서의 "N라운드"라는 설명은 이 표와 대조만 하고, 최종 판단은 반드시 디스어셈블리 기준으로 한다.

## 단계별 절차

**1) 루프 반복 횟수 직접 계산**

`cmp ecx, 0Ah` + `jl .loop`이고 `ecx`가 0부터 시작해 매 반복 `inc`된다면, `ecx`가 `0,1,...,9`일 때 조건(`ecx < 10`)이 참이라 반복하고, `ecx == 10`이 되는 순간 조건이 거짓이 되어 루프를 빠져나온다. 따라서 **총 10번 반복**(마지막 반복 시작 시 `ecx == 9`)이다.

**2) 마지막 반복이 특별 취급되는지 확인**

루프 본문 코드를 반복문 안에서 보지 말고, 루프를 벗어난 직후에 별도로 실행되는 코드가 있는지 확인한다. AES처럼 "마지막 라운드는 한 단계 생략"하는 패턴이 있다면, 코드가 루프 밖에서 마지막 라운드 전용 코드를 따로 두거나, 루프 안에 `if (i == Nr - 1) skip_mixcolumns();` 형태의 조건 분기가 있을 것이다.

**3) 파이썬 재구현에 정확히 반영**
```python
def aes_like_rounds(state, round_keys, Nr):
    for r in range(1, Nr):
        state = sub_bytes(state)
        state = shift_rows(state)
        state = mix_columns(state)          # 마지막 라운드 전까지만 적용
        state = add_round_key(state, round_keys[r])
    # 마지막 라운드: MixColumns 없음
    state = sub_bytes(state)
    state = shift_rows(state)
    state = add_round_key(state, round_keys[Nr])
    return state
```

**4) TEA류 "라운드 vs 사이클" 용어 혼동 방지**

TEA를 재구현할 때는 **메인 `for` 루프 자체를 32번** 돈다. `sum`의 최종값이 `delta * 32 mod 2^32 == 0xC6EF3720`이 되는지 직접 검산해서, 루프 횟수를 다른 자료의 "64"라는 표현에 이끌려 두 배로 늘리지 않았는지 재확인한다.
```python
delta = 0x9E3779B9
print(hex((delta * 32) & 0xFFFFFFFF))   # 0xc6ef3720 -> 32회가 맞다는 산술적 증거
print(hex((delta * 64) & 0xFFFFFFFF))   # 다른 값 -> 64회로 잘못 돌리면 sum 최종값부터 어긋남
```

## 명령어/단축키
```asm
cmp reg, N / jl LOOP    ; reg < N 동안 반복 -> 총 N번(0..N-1)
cmp reg, N / jle LOOP   ; reg <= N 동안 반복 -> 총 N+1번(0..N)
```
```python
for r in range(1, Nr):      # 1부터 Nr-1까지, 즉 (Nr-1)번 -> "중간 라운드"
    ...
# 마지막(Nr번째) 라운드는 루프 밖에서 별도 처리
```

## 출력 해석
- 재구현한 `sum`(TEA류) 또는 라운드 카운터 최종값을 알려진 상수(`0xC6EF3720` 등)와 대조해서, 값이 다르면 반복 횟수 자체가 틀렸다는 확실한 증거다.
- 결과가 "거의 다 맞는데 마지막 한 단계만 틀림"이라면 마지막 라운드 예외 처리(AES의 MixColumns 생략 등)를 놓쳤을 가능성이 매우 크다.
- 결과가 "정확히 절반만 맞는" 것처럼 보이면 라운드 수를 정확히 2배 또는 절반으로 잘못 설정했을 가능성을 의심한다.

## 흔한 실수
- 문서나 위키의 "N라운드"라는 설명을 검증 없이 그대로 루프 횟수로 사용하는 것 — 같은 알고리즘이라도 "라운드"를 세는 관례가 자료마다 다를 수 있다.
- 표준 알고리즘(AES 등)의 마지막 라운드 예외(MixColumns 생략 등)를 몰라서 모든 라운드에 동일한 로직을 적용하는 것.
- `jl`과 `jle`, `<`와 `<=`를 혼동해서 반복 횟수를 하나 더 돌리거나 덜 도는 것 — 항상 루프 카운터의 시작값·종료 비교·분기 종류 세 가지를 표로 정리해서 눈으로 확인한다.
- CTF 문제가 표준 알고리즘의 라운드 수를 의도적으로 바꾼 변형이라는 걸 모르고 표준 라운드 수(예: AES 10라운드)를 그대로 가정하는 것 — 반드시 디스어셈블리에서 실제 반복 횟수를 다시 센다.

## 막혔을 때 다음 체크
- TEA/XTEA의 표준 라운드 수와 상수 관계가 헷갈린다면 → REV-0210 TEA와 XTEA 상수 패턴
- AES의 라운드 구조나 테이블 기반 여부가 헷갈린다면 → REV-0211 AES 테이블 또는 AES API 흔적 찾기
- 라운드 수는 맞는데 여전히 값이 안 맞는다면 오버플로우/엔디안 문제일 수 있다 → REV-0926 정수 오버플로를 빼먹어서 계산이 계속 안 맞을 때
- 여전히 어느 지점에서 갈라지는지 못 찾겠다면 → REV-0921 알고리즘을 복원했는데 출력이 원본과 안 맞을 때

## 미니 예제
어떤 CTF 바이너리가 TEA 변형을 쓰는데, 문제 설명 파일에는 "64 rounds"라고 적혀 있었다고 하자. 디스어셈블리를 직접 세어보니:
```asm
        xor   ecx, ecx
.loop:
        ...
        inc   ecx
        cmp   ecx, 20h        ; 0x20 = 32
        jl    .loop
```
루프가 정확히 32번(`ecx`가 0~31일 때 반복) 돈다. 문제 설명의 "64 rounds"는 "각 워드 갱신을 라운드 1개로 세면 64"라는 다른 세는 방식이었을 뿐, 실제 메인 루프 반복 횟수는 32다. 이를 확인하기 위해 `sum`의 최종값을 계산해본다.
```python
delta = 0x9E3779B9
print(hex((delta * 32) & 0xFFFFFFFF))   # 0xc6ef3720
```
바이너리의 복호화 함수가 `sum`을 `0xC6EF3720`으로 초기화하고 있다면, 이는 32회 반복이 맞다는 산술적 증거이며, "64 rounds"라는 설명 문구를 무시하고 32회로 재구현해야 한다.

- TEA의 32회 메인 루프 반복과 `sum` 최종값(`delta * 32 mod 2^32 = 0xC6EF3720`) 관계: David Wheeler, Roger Needham, "TEA, a Tiny Encryption Algorithm"(1994) 기준 (2026-09-09 검증).
