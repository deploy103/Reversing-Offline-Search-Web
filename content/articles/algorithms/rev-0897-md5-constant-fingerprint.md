## 한 줄 요약
바이너리 안에서 32비트 정수 4개가 `0x67452301`, `0xefcdab89`, `0x98badcfe`, `0x10325476` 순서로만 초기화되고(다섯 번째 값이 없음) 최종 결과가 16바이트(128비트)로 나온다면 이는 MD5이며, 초기값이 정확히 4개뿐이라는 점과 사인 함수에서 유도된 64개짜리 T 테이블이 SHA-1(REV-0896)과 구분되는 핵심 지문이다.

## 언제 검색해야 하나
- 함수 진입부에서 32비트 지역 변수 4개가 특정 16진수 상수로 초기화되는 걸 봤는데, SHA-1(REV-0896)에서 배운 다섯 번째 상수 `0xC3D2E1F0`가 안 보일 때
- 64개짜리 32비트 상수 테이블이 코드나 데이터 영역에 있고, 각 값이 얼핏 무작위처럼 보일 때(사인 함수 기반이라 규칙성이 육안으로는 안 보임)
- 최종 비교 대상 버퍼가 정확히 16바이트(32자리 hex 문자열)일 때
- Import 목록에 `CryptCreateHash`+`CALG_MD5`, 또는 OpenSSL `MD5_Init`/`MD5`, `EVP_md5` 같은 함수/문자열이 있을 때

## 핵심 개념

### MD5가 무엇이고 왜 여전히 CTF에 나오는가
MD5(Message Digest Algorithm 5)는 Ron Rivest가 설계하고 1992년 RFC 1321로 표준화한 128비트 암호학적 해시 함수다. 충돌 공격이 이미 오래전부터 실용화되어 보안 용도로는 완전히 폐기되었지만, 파일 무결성 체크섬이나 레거시 프로토콜, 그리고 CTF의 "해시 알고리즘 알아맞히기/재구현" 문제에서 매우 자주 등장한다. SHA-1과 설계 계보가 같아서(둘 다 MD4의 후예) 코드 구조가 비슷하지만, 상태 크기와 초기값 개수, 라운드 상수 생성 방식이 다르다.

### 4개의 32비트 초기 버퍼값 — SHA-1과 겹치는 부분
MD5는 내부 상태로 4개의 32비트 버퍼(A, B, C, D)를 쓰고, 다음 고정값으로 초기화한다(RFC 1321, `MD5Init` 함수 기준):
```
A = 0x67452301
B = 0xefcdab89
C = 0x98badcfe
D = 0x10325476
```
**주의할 점**: 이 네 값은 SHA-1(REV-0896)의 초기값 H0~H3과 정확히 동일하다. 두 알고리즘이 같은 MD4 계보에서 나왔기 때문이다. 따라서 이 네 개만 발견했다고 MD5로 단정하면 안 되고, **바로 뒤에 SHA-1의 다섯 번째 초기값인 `0xC3D2E1F0`가 이어지는지 확인**해야 한다. `0xC3D2E1F0`가 없고 초기화가 정확히 4개에서 끝나면 MD5, 다섯 번째가 있으면 SHA-1이다.

### 64개짜리 T 테이블 — MD5 고유의 강력한 지문
MD5는 SHA-1과 달리 라운드 상수를 4개가 아니라 **64개** 쓰는데, 이 값들은 사인(sine) 함수에서 기계적으로 유도된다(RFC 1321 정의):
```
T[i] = floor(abs(sin(i)) * 2^32),  (i = 1 ~ 64, 라디안 단위)
```
이 공식을 실제로 계산하면 첫 몇 개 값은 다음과 같다:
```
T[1]  = 0xd76aa478
T[2]  = 0xe8c7b756
T[3]  = 0x242070db
T[4]  = 0xc1bdceee
```
이 64개짜리 테이블(총 256바이트)은 SHA-1의 4개 라운드 상수(REV-0896)와 개수부터 다르므로, "라운드 상수가 4개면 SHA-1류, 64개면 MD5"라는 규칙만으로도 소스 없이 구분할 수 있다. `T[1] = 0xd76aa478`이 데이터 영역이나 코드 상수로 그대로 보이면 MD5로 사실상 확정이다.

### 64단계 = 16단계 × 4라운드, 그리고 4개의 비선형 함수
MD5는 512비트 블록마다 64단계(SHA-1은 80단계)를 돌며, 16단계씩 4개 라운드로 나뉘고 라운드마다 다른 비선형 함수를 쓴다:
```c
F(B,C,D) = (B & C) | ((~B) & D)   // 라운드 1
G(B,C,D) = (B & D) | (C & (~D))   // 라운드 2
H(B,C,D) = B ^ C ^ D              // 라운드 3
I(B,C,D) = C ^ (B | (~D))         // 라운드 4
```
각 단계는 덧셈(T 테이블 값 + 메시지 워드) 후 라운드별로 정해진 비트 수만큼 왼쪽 순환(rotate left)한다. 회전량은 라운드마다 `{7,12,17,22}`, `{5,9,14,20}`, `{4,11,16,23}`, `{6,10,15,21}`처럼 4가지 값이 반복되는데, 이 4종류 회전량 세트도 MD5 특유의 지문이다.

### 출력 크기와 개수 요약
| 알고리즘 | 초기값 개수 | 라운드 상수 개수 | 출력 크기 |
|---|---|---|---|
| MD5 | 4개 (32비트) | 64개(사인 유도) | 16바이트 |
| SHA-1 | 5개 (32비트) | 4개 | 20바이트 |
| SHA-256 | 8개 (32비트) | 64개(세제곱근 유도) | 32바이트 |

MD5와 SHA-256은 둘 다 "라운드 상수 64개"라서 개수만으로는 구분이 안 되니, 반드시 **초기값 개수(4개 vs 8개)** 와 **출력 크기(16바이트 vs 32바이트)** 를 함께 확인해야 한다.

### 문자열/API 지문
- **Windows CryptoAPI**: `CryptCreateHash` + `CALG_MD5` 상수(`0x00008003`)
- **Windows CNG**: `BCryptOpenAlgorithmProvider`에 와이드 문자열 `L"MD5"` 전달
- **OpenSSL**: `MD5_Init`/`MD5_Update`/`MD5_Final` 저수준 API, 또는 `EVP_md5()`
- **Python 대조 표준**: `hashlib.md5()`

## 화면/코드에서 보이는 징후
- 함수 초기화부에서 정확히 4개의 32비트 변수가 `0x67452301`, `0xefcdab89`, `0x98badcfe`, `0x10325476` 순서로 설정되고, 그 다음에 다섯 번째 초기값이 이어지지 않음
- `.rodata`에 64개(256바이트)짜리 32비트 상수 테이블, 첫 값이 `0xD76AA478`
- 512비트(64바이트) 블록 처리 루프 안에 64회(80회가 아님) 도는 내부 루프
- 최종 결과 버퍼가 정확히 16바이트
- Import에 `CryptCreateHash`+`CALG_MD5`, 또는 문자열 `"MD5"`/`"md5"`

## 가장 먼저 할 것
`0x67452301`을 IDA `Alt+B` 또는 `objdump -s`로 찾은 뒤, 그 직후에 `0xC3D2E1F0`(SHA-1의 다섯 번째 초기값)가 이어지는지 확인한다. 없으면 MD5, 있으면 SHA-1(REV-0896)이다. 애매하면 T 테이블의 첫 값 `0xD76AA478`을 대신 검색해 MD5 여부를 재확인한다.

## 단계별 절차
1. `strings ./binary | grep -i md5` 및 Import 목록에서 `CryptCreateHash`, `MD5_Init`, `EVP_md5` 검색으로 라이브러리 호출 여부 먼저 확인
2. 없으면 IDA/Ghidra에서 `67452301`을 16진수 상수로 검색
3. 초기값이 4개에서 끝나고 `C3D2E1F0`가 없는지 확인 — 있으면 SHA-1이므로 REV-0896으로 이동
4. `.rodata`/코드에서 64개짜리 32비트 상수 테이블 탐색, 첫 값이 `D76AA478`인지 확인
5. 512비트 블록 처리 루프 안에 64회 도는 내부 루프(80회면 SHA-1) 존재 확인
6. Python `hashlib.md5()`로 알고 있는 입력을 넣어 바이너리가 기대하는 출력값과 일치하는지 대조

## 명령어/단축키
```bash
strings ./binary | grep -iE "md5"
objdump -s -j .rodata ./binary | grep -A1 "6745 2301"
python3 -c "import hashlib; print(hashlib.md5(b'').hexdigest())"
```
IDA: `Alt+B`에 `01 23 45 67`(리틀엔디안 `0x67452301`) 입력. Ghidra: `Search → Memory`에서 Hex `01234567` 검색.

## 출력 해석
- Python `hashlib.md5(b"").hexdigest()` 결과는 `d41d8cd98f00b204e9800998ecf8427e` (빈 문자열의 MD5) — 이 값으로 자신이 짠 재현 코드가 표준과 일치하는지 항상 검증한다.
- 초기값 4개는 찾았는데 다섯 번째 상수(`C3D2E1F0`)까지 이어진다면 이건 MD5가 아니라 SHA-1이므로 REV-0896 절차로 넘어간다.
- 결과 버퍼가 16바이트가 아니라 8바이트 등으로 잘려 있다면, MD5 다이제스트 중 일부만 잘라 쓰는 커스텀 검증 로직일 수 있다.

## 흔한 실수
- 초기값 4개(`67452301`, `efcdab89`, `98badcfe`, `10325476`)만 보고 SHA-1인지 MD5인지 구분하지 않은 채 넘어가는 것 — 반드시 다섯 번째 값의 유무를 확인해야 한다.
- 라운드 상수 개수를 확인하지 않고 "64개짜리 테이블이 있으니 SHA-256"이라 오판하는 것 — MD5도 64개짜리 테이블을 쓰므로 초기값 개수(4개 vs 8개)와 출력 크기(16바이트 vs 32바이트)를 반드시 함께 봐야 한다.
- MD5가 이미 충돌 공격에 취약하다는 걸 몰라서, "해시가 같으면 원문도 같다"고 무비판적으로 신뢰하는 것 — CTF에서는 의도적으로 충돌쌍을 만들어 검증을 우회시키는 문제도 존재한다.
- T 테이블 값을 직접 계산 없이 하드코딩된 상수만 믿고 검증 안 하는 것 — `int(abs(sin(i)) * 2**32)` 공식으로 직접 재생성해서 바이너리 값과 대조하면 오타나 변형 여부를 확실히 잡아낼 수 있다.

## 막혔을 때 다음 체크
- 다섯 번째 초기값(`C3D2E1F0`)이 존재한다면 → REV-0896 SHA-1 흔적을 상수로 알아보는 법
- 초기값이 8개이고 라운드 상수도 64개면 SHA-256 → REV-0895 SHA-256 흔적을 상수로 알아보는 법 (예정)
- MD5 해시 결과가 다시 키와 결합되어 쓰인다면 → REV-0898 HMAC 패턴 알아보기(이중 해시 구조) (예정)
- 해시가 역산 가능한지 헷갈리면 → [rev-0221-is-it-invertible.md](./rev-0221-is-it-invertible.md)
- 찾은 로직을 파이썬으로 재현하는 일반적 방법이 필요하면 → [rev-0222-reimplement-in-python.md](./rev-0222-reimplement-in-python.md)

## 미니 예제
IDA 디컴파일 결과에서 다음 초기화를 발견했다:
```c
a = 0x67452301;
b = 0xefcdab89;
c = 0x98badcfe;
d = 0x10325476;
// 다섯 번째 변수 초기화 없음
```
바로 아래 함수 본체에서 64개짜리 상수 테이블을 참조하는데, 그 배열의 첫 값을 확인하니:
```c
T[0] = 0xd76aa478;  // RFC 1321의 T[1]과 일치 (인덱스는 구현마다 0-base/1-base 차이 있음)
```
초기값이 4개뿐이고 T 테이블 첫 값이 `0xd76aa478`이므로 이 함수는 MD5로 확정된다. Python으로 검증:
```python
import hashlib
print(hashlib.md5(b"").hexdigest())
# d41d8cd98f00b204e9800998ecf8427e
```

- MD5 초기 버퍼값(A~D) 및 T[i] 사인 함수 정의: IETF RFC 1321, "The MD5 Message-Digest Algorithm" 원문 기준 (2026-09-09 검증).
