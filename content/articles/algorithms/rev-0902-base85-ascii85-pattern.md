## 한 줄 요약
입력 바이트를 4바이트(32비트) 단위로 묶어 하나의 큰 정수로 본 뒤 85진법으로 변환해서 5개의 문자로 늘리고, 그 문자가 `!`(33)부터 `u`(117)까지의 ASCII 범위에 들어가며 32비트가 모두 0인 그룹을 `z` 한 글자로 압축하는 특수 규칙이 보이면 이는 Base85(Ascii85/btoa 계열) 인코딩이며, Base64(3바이트→4글자)보다 압축 효율이 좋다는 점에서 구분된다.

## 언제 검색해야 하나
- 인코딩 결과 문자열 길이가 원본 데이터 길이보다 정확히 5/4배(4바이트→5글자)로 늘어날 때 — Base64(REV-0212)의 4/3배와는 다른 비율
- `.rodata`나 문자열 뷰에서 `!`부터 시작해서 `u` 근처까지 이어지는(또는 순서가 다른 커스텀) 85자짜리 문자 집합이 보일 때
- 인코딩된 결과 문자열이 `<~`로 시작하고 `~>`로 끝날 때(Adobe PostScript/PDF 스타일 구분자)
- 특정 4바이트 그룹이 모두 0일 때만 예외적으로 한 글자(`z`)로 처리되는 조건 분기가 보일 때
- 나눗셈과 거듭제곱(85, 85², 85³, 85⁴) 연산이 반복되는 인코딩 루프를 발견했을 때

## 핵심 개념

### Base85가 Base64보다 나은 점 — 압축 효율
Base64(REV-0212)는 3바이트(24비트)를 6비트씩 4조각으로 잘라 4글자로 표현하므로 원본 대비 4/3배(약 33% 증가)로 늘어난다. Base85는 대신 **4바이트(32비트)를 큰 정수 하나로 보고 85진법(base-85)으로 변환해 5자리로 표현**한다. `85^5 = 4,437,053,125`로 `2^32(4,294,967,296)`보다 크기 때문에, 4바이트 정수는 항상 5자리 85진법 숫자로 정확히 표현 가능하다. 늘어나는 비율은 5/4배(25% 증가)로 Base64보다 인쇄 가능 문자를 이용한 인코딩치고는 상당히 효율적이다.

### 인코딩 원리 — 32비트 정수를 85진법으로
4바이트를 빅엔디안 32비트 정수 N으로 합친 뒤, 85로 반복해서 나눈 나머지를 구해 5개의 자릿수(0~84)를 뽑는다:
```c
uint32_t n = (b0 << 24) | (b1 << 16) | (b2 << 8) | b3;
char c[5];
for (i = 4; i >= 0; i--) {
    c[i] = n % 85;
    n /= 85;
}
```
이렇게 얻은 0~84 값에 각각 알파벳 오프셋을 더해 인쇄 가능한 ASCII 문자로 바꾼다. Adobe의 표준 Ascii85(PostScript/PDF에서 쓰는 방식)는 **ASCII 33(`!`)부터 117(`u`)까지**를 그대로 순서대로 사용한다. 즉 0은 `!`, 84는 `u`에 대응한다. 이 범위(`!`~`u`)가 코드나 데이터에서 순서대로 나타나면 표준 Adobe Ascii85로 확정할 수 있다.

### `z` 특수 압축 — Ascii85만의 독특한 규칙
Adobe Ascii85는 인코딩 효율을 조금 더 높이기 위해, **4바이트가 모두 0(0x00000000)인 그룹**은 정식 5글자(`!!!!!`) 대신 **`z` 한 글자**로 압축해서 표현하는 특수 규칙을 둔다. 디코딩 시에는 `z`를 만나면 곧바로 4바이트의 0으로 되돌린다. 이 "특정 값(전부 0)일 때만 예외적으로 한 글자 처리"라는 조건 분기가 코드에 있으면 표준 Base64/Base32에는 없는 Ascii85 고유의 지문이다.

### Adobe 구분자 — `<~`와 `~>`
Adobe PostScript/PDF 환경에서는 Ascii85로 인코딩된 데이터임을 표시하기 위해 앞에 `<~`, 뒤에 `~>`를 붙이는 관례가 있다. 이 구분자가 문자열에 그대로 보이면 Adobe 스타일 Ascii85임을 바로 알 수 있다. 반대로 Git의 binary patch에서 쓰는 Base85나 RFC 1924(IPv6 주소 압축용), ZeroMQ의 Z85는 **같은 85진법 아이디어를 쓰지만 알파벳 순서와 특수 규칙이 완전히 다르므로**, `!`~`u` 순서가 아니라 다른 문자 집합이 보이면 어느 변형인지 알파벳 자체를 다시 대조해야 한다.

### 패딩 처리
입력 길이가 4바이트의 배수가 아니면, 마지막 그룹은 최대 3바이트의 0으로 채운 뒤 인코딩하고, 인코딩 후 패딩으로 추가됐던 만큼의 문자를 결과 끝에서 제거한다(Base64의 `=` 패딩 문자와 달리 Ascii85는 별도 패딩 문자 없이 길이 자체를 줄인다).

### 다른 인코딩과의 구분 요약
| 인코딩 | 알파벳 크기 | 입력:출력 비율 | 특수 규칙 |
|---|---|---|---|
| Base64(REV-0212) | 64자 | 3:4 | `=` 패딩 |
| Base85(Ascii85) | 85자 | 4:5 | `z`=전부 0, `<~`~`~>` |
| Hex(REV-0213) | 16자 | 1:2 | 없음 |

## 화면/코드에서 보이는 징후
- `.rodata`/`.rdata`에 `!`부터 순서대로 `u`까지(또는 다른 순서의) 85자짜리 문자 배열
- 4바이트를 32비트 정수로 합친 뒤 85로 5번 나누는 루프(`% 85`, `/ 85` 반복)
- 결과 버퍼가 입력보다 정확히 5/4배 커짐
- 특정 4바이트가 0일 때만 별도 분기로 처리되는 조건문(`z` 압축)
- 문자열 앞뒤에 `<~`, `~>` 구분자

## 가장 먼저 할 것
결과 문자열 길이와 원본 길이의 비율을 먼저 계산한다. 정확히 5/4배(4바이트→5글자)면 Base85 계열을 의심하고, `.rodata`에서 `!`(0x21)로 시작하는 85자 문자 집합을 찾는다. `<~`/`~>` 구분자가 문자열에 보이면 Adobe Ascii85로 즉시 확정.

## 단계별 절차
1. 인코딩 결과 길이와 원본 길이의 비율 계산 — 5/4배면 Base85 후보(4/3배면 Base64, REV-0212로 이동)
2. `.rodata`에서 85자 문자 집합 탐색, `!`(33)로 시작하는지 확인
3. 인코딩 루프에서 32비트 정수를 85로 나누는 연산(`%85`, `/85`)이 5번 반복되는지 확인
4. `z` 한 글자로 4바이트 0 그룹을 압축하는 특수 분기가 있는지 확인
5. 문자열 앞뒤에 `<~`/`~>` 구분자가 있는지 확인(Adobe 스타일 여부 판단)
6. Python `base64.a85encode`/`a85decode`로 직접 대조 검증

## 명령어/단축키
```bash
strings ./binary | grep -E "<~.*~>"
python3 -c "
import base64
print(base64.a85encode(b'hello world'))
print(base64.a85decode(b'BOu!rD]j7BEbo7'))
"
```
IDA: `Shift+F12`(문자열 창)에서 85자 내외 필터링, 또는 `<~` 텍스트 검색(`Alt+T`).

## 출력 해석
- Python `base64.a85encode(b"hello world")`는 `b'BOu!rD]j7BEbo7'`를 반환한다 — 이 값으로 재현 로직이 표준과 일치하는지 검증한다.
- 디코딩 결과가 깨진다면 `z` 특수 규칙 처리를 빠뜨렸거나(0인 그룹을 5글자로 잘못 처리), 패딩 바이트 제거 로직이 다를 수 있다.
- 알파벳이 `!`~`u`가 아니라 다른 순서/범위(`0`~`z` 등)라면 RFC 1924나 Z85 같은 다른 Base85 변형이므로 표준 `a85encode`가 아니라 해당 변형에 맞는 별도 테이블을 써야 한다.

## 흔한 실수
- Base85를 Base64(REV-0212)와 혼동해서 입력:출력 비율을 3:4로 잘못 가정하는 것 — Base85는 4:5다.
- `z` 특수 압축 규칙을 놓치고 모든 그룹을 5글자로만 처리하려다 디코딩이 깨지는 것.
- Adobe Ascii85와 RFC 1924/Z85를 같은 것으로 착각하는 것 — 셋 다 "85진법"이라는 아이디어는 같지만 알파벳 순서와 구분자 규칙이 전혀 다르므로 반드시 알파벳 자체를 비교해야 한다.
- `<~`/`~>` 구분자를 인코딩된 데이터의 일부로 착각해서 그대로 디코딩에 포함시켜 실패하는 것 — 이 구분자는 인코딩 대상이 아니라 래퍼(wrapper)이므로 제거하고 디코딩해야 한다.

## 미니 예제
`.rodata`에서 다음 문자열을 발견했다:
```
<~BOu!rD]j7BEbo7~>
```
Adobe 구분자 `<~`, `~>`가 붙어 있으므로 Ascii85로 확정하고 안쪽 데이터만 디코딩한다:
```python
import base64
print(base64.a85decode(b"BOu!rD]j7BEbo7"))
# b'hello world'
```
결과가 `b'hello world'`로 사람이 읽을 수 있는 문자열이 나오므로 Ascii85 디코딩이 정확함을 확인할 수 있다. 만약 원본에 `z`가 하나 섞여 있었다면(예: `<~z~>`) 이는 4바이트 `00 00 00 00`을 압축한 것이므로 디코딩 시 곧바로 4개의 0바이트로 복원해야 한다.

## 출처/검증
- Ascii85/Base85 알파벳 범위(`!`~`u`, ASCII 33~117), `z` 특수 압축 규칙, `<~`/`~>` Adobe 구분자: Adobe PostScript Language Reference 및 널리 알려진 Ascii85 명세 설명 기준 (2026-09-09 검증).
- Base85가 4바이트→5글자로 인코딩되는 수학적 근거(`85^5 > 2^32`): 표준 Base85/Ascii85 인코딩 원리 설명 기준 (2026-09-09 확인).
- RFC 1924/Z85와 Adobe Ascii85가 서로 다른 알파벳을 쓰는 별개 변형이라는 점: 각 사양(RFC 1924 IPv6 표현, ZeroMQ Z85 사양) 비교 기준 (2026-09-09).
- Python `base64.a85encode`/`a85decode` 동작: Python 공식 `base64` 모듈 문서 기준 (2026-09-09).
