## 한 줄 요약
Polynomial Hash(다항식 해시)는 문자열의 각 문자를 `hash = hash * base + c[i]` 형태로 누적해서 임의 길이 입력을 고정 크기 정수 하나로 압축하는 패턴이며, `base`가 흔한 상수(31, 131, 65599 등)이고 결과가 32비트/64비트로 랩어라운드된다는 두 가지 특징만 알아도 디스어셈블리에서 즉시 알아볼 수 있다.

## 언제 검색해야 하나
- 디컴파일 결과에 `for` 루프 안에서 정수 변수 하나가 `v = v * 상수 + 문자` 형태로 계속 갱신되는 코드가 보일 때
- 곱셈에 쓰이는 상수가 31, 33, 37, 131, 1000003, 65599처럼 익숙한 소수/홀수일 때
- 최종 비교 대상이 8글자 hex 하나(예: `0xC1D2E3F4`)처럼 짧은 고정폭 정수라서, 원문 복원이 원리적으로 불가능해 보일 때
- FNV류(REV-0207, REV-0208)인 줄 알았는데 XOR이 안 보이고 곱셈+덧셈만 보여서 뭔지 헷갈릴 때

## 핵심 개념

### 다항식 해시의 수학적 정의
다항식 해시는 문자열 `s = s[0], s[1], ..., s[n-1]`을 다음 식으로 정수 하나에 매핑한다.

```
hash = s[0]*base^(n-1) + s[1]*base^(n-2) + ... + s[n-1]*base^0   (mod M)
```

이 식을 처음부터 끝까지 매번 거듭제곱을 계산하면 느리므로, 실제 구현(그리고 디스어셈블리에서 보게 될 코드)은 항상 아래처럼 호너의 방법(Horner's method)으로 누적한다.

```c
unsigned int hash = 0;
for (int i = 0; i < n; i++) {
    hash = hash * BASE + (unsigned char)s[i];
}
```

이 루프 한 줄이 다항식 해시의 정의 그 자체다. `hash`를 한 번 곱하고 한 번 더할 때마다 `base`의 거듭제곱이 자동으로 누적되기 때문이다.

### 어디서나 나오는 이유 — Java hashCode, 컴파일러 문자열 스위치
가장 유명한 예는 자바의 `String.hashCode()`다.

```java
// java.lang.String.hashCode()의 정의
h = 31*h + s[i]
```

`base=31`을 쓰는 이유는 곱셈을 `(h << 5) - h`로 최적화할 수 있어서 예전 컴파일러들이 선호했기 때문이다. 그 외에도 다음과 같은 상수가 흔하다.

| base | 주로 쓰이는 곳 |
|---|---|
| 31 | Java `String.hashCode`, 다수의 CTF 커스텀 해시 |
| 33 | djb2 해시(원래는 `hash*33 + c`, 초기값 5381) |
| 37, 131 | 경쟁 프로그래밍/교재의 문자열 해시 예제 |
| 65599 | PHP 초기 해시 구현체에서 유래, 여러 교재에서 재사용 |
| 1000003 | Python 구버전 튜플 해시 등에서 쓰인 큰 소수 |

C/C++ 컴파일러가 `switch(str)` 같은 문자열 스위치문을 생성할 때도 내부적으로 문자열을 정수 해시로 바꿔 비교하는 코드를 만드는데, 이때도 다항식 해시 형태가 자주 보인다. 따라서 다항식 해시를 봤다고 항상 "이건 커스텀 인증 로직이다"라고 단정하면 안 되고, 컴파일러가 자동 생성한 코드일 가능성도 열어둬야 한다(뒤 흔한 실수 참고).

### 자연 오버플로가 곧 `mod M`
정수 변수 타입(`unsigned int`=32비트, `unsigned long long`=64비트)이 곧 모듈러스 역할을 한다. C에서 `unsigned int` 연산은 `2^32`로 자동 랩어라운드되므로, 위 코드의 실제 의미는 `mod 2^32`가 명시적으로 적혀 있지 않아도 이미 적용되고 있는 것이다. 리버싱할 때는 디스어셈블리에서 `imul eax, eax, 1Fh`(31) 같은 32비트 곱셈 명령과 뒤이은 `add eax, ecx`(문자 덧셈)만 봐도 이 패턴을 확신할 수 있다.

### 왜 원문 복원이 원리적으로 불가능한가
다항식 해시는 단방향(one-way) 압축이다. 임의 길이 `n`의 입력을 고정폭(32비트 또는 64비트) 정수 하나로 뭉개기 때문에 `n`이 조금만 커도 서로 다른 무수히 많은 입력이 같은 해시값을 만들 수 있다(비둘기집 원리). 즉 목표 해시값 하나만 놓고 "원래 입력이 정확히 무엇이었는지"를 유일하게 복원하는 것은 수학적으로 불가능하다. 리버싱에서 실제로 할 수 있는 것은 (1) 같은 해시를 만드는 아무 문자열이나 찾는 역상 찾기(preimage search, 사실상 브루트포스나 알려진 사전 대입), (2) 이미 알고 있는 후보 문자열이 있다면 같은 해시 함수를 직접 재구현해서 검증하는 것 두 가지뿐이다.

## 화면/코드에서 보이는 징후
- 디컴파일에 `v2 = v2 * 31 + *p;` 또는 `hash = 31 * hash + c;` 형태의 한 줄짜리 반복 갱신
- 어셈블리에서 `imul` 뒤에 즉시 `add`가 오는 짧은 루프, 곱셈 피연산자가 리터럴 상수
- 루프 종료 후 32비트 또는 64비트 레지스터 하나만 비교 대상으로 쓰임(배열 전체가 아니라 스칼라 값 하나)
- 초기값이 0이 아니라 5381 같은 특정 상수로 시작하면 djb2 계열일 가능성

## 가장 먼저 할 것
루프 본문에서 곱해지는 상수(`base`)와 결과 변수의 비트폭(32비트인지 64비트인지)부터 정확히 적어둔다. 그다음 초기값이 0인지 5381 같은 특정 값인지 확인한다. 이 세 가지(초기값, base, 비트폭)만 알면 파이썬으로 즉시 동일하게 재구현할 수 있다.

## 단계별 절차
1. IDA/Ghidra 디컴파일에서 해시 누적 루프를 찾고, 곱셈 상수·덧셈 대상(문자 하나인지 다른 값인지)·초기값·결과 변수 타입을 표로 정리한다.
2. 결과 변수가 `unsigned int`면 `mod 2**32`, `unsigned long long`이면 `mod 2**64`를 적용해야 함을 기록한다.
3. Python으로 동일한 루프를 그대로 옮겨 재구현한다.
4. 알고 있는 임의의 테스트 문자열(예: 프로그램 자체의 다른 문자열 리터럴)로 재구현 결과와 실제 바이너리 동작(GDB로 함수 실행 후 반환값 확인, REV-0919 방식)을 비교해서 재구현이 정확한지 검증한다.
5. 목표가 "정확히 원문을 복원"이 아니라 "같은 해시를 만드는 아무 입력 찾기"라면 REV-0219 방식으로 브루트포스 가능성을 계산하거나, 자릿수가 감당되면 사전 파일을 통째로 넣어 일치하는 항목을 찾는다.

## 명령어/단축키
```python
def poly_hash(s: bytes, base: int, mod: int, init: int = 0) -> int:
    h = init
    for c in s:
        h = (h * base + c) % mod
    return h

# Java String.hashCode() 재현
print(poly_hash(b"hello", base=31, mod=2**32))

# djb2 재현 (초기값 5381, base 33)
print(poly_hash(b"hello", base=33, mod=2**32, init=5381))
```
IDA: 루프 안 곱셈 명령 위에서 `imul` 피연산자를 확인 → 상수면 그 자리에서 `M`(즉시 오퍼랜드를 상수로 표시)으로 값 확정. Ghidra: 디컴파일 창에서 곱셈 상수에 커서를 놓고 `L`로 이름을 붙여 `BASE`처럼 표시해두면 가독성이 좋아진다.

## 출력 해석
- 재구현한 `poly_hash()`가 바이너리와 동일한 출력을 내면 base/mod/init이 모두 정확하다는 뜻이다.
- 결과가 부호 있는 정수(`int`)로 출력되고 음수로 보인다면 REV-0206(음수 상수를 Unsigned Hex로 다시 읽기)을 먼저 적용해서 부호 없는 값으로 변환한 뒤 비교해야 한다.
- 32비트 결과인데 64비트로 계산하면 상위 비트가 남아 값이 절대 안 맞는다 — 변수 타입을 반드시 어셈블리 레지스터 폭(`eax` vs `rax`)으로 재확인한다.

## 흔한 실수
- 다항식 해시를 보자마자 "커스텀 인증 로직"이라 단정하는 것 — 문자열 스위치문 컴파일 결과처럼 컴파일러가 자동 생성한 경우도 흔하다. 그 해시값이 실제로 사용자 입력 검증에 쓰이는지, 아니면 단순 내부 분기 최적화인지 먼저 xref로 확인해야 한다.
- `base`를 정확히 읽지 않고 "31 근처겠지"라고 추측하는 것 — 31과 33처럼 비슷해 보이는 값도 결과가 완전히 달라진다.
- `mod` 연산을 명시적 코드로만 찾으려는 것 — 대부분은 정수 타입의 자연 오버플로가 곧 `mod`이므로 소스에 `%` 연산자가 안 보이는 게 정상이다.
- 다항식 해시가 단방향이라는 걸 잊고 "역산해서 원문을 구하겠다"고 시간을 쓰는 것 — 원리적으로 유일한 원문 복원은 불가능하며, 가능한 건 프리이미지 탐색뿐이다(REV-0913 참고).

## 막혔을 때 다음 체크
- XOR이 섞여 있어서 순수 다항식 해시가 아닌 것 같다면 → REV-0207 FNV-1과 FNV-1a 해시 패턴, REV-0208 16777619 상수가 보일 때 FNV 의심하기
- 목표 해시를 만드는 입력을 찾아야 하는데 브루트포스가 가능한 크기인지 궁금하면 → REV-0219 Brute Force가 가능한 입력 공간 계산, REV-0920
- 해시가 단방향인지 대칭 암호처럼 가역인지 헷갈리면 → REV-0221 역연산 가능한 알고리즘 판단법, REV-0913
- 음수로 보이는 상수 비교값을 부호 없는 값으로 바꾸는 법이 기억 안 나면 → REV-0206 음수 상수를 Unsigned Hex로 다시 읽기

## 미니 예제
어떤 크랙미가 사용자 입력을 받아 다음과 같은 디컴파일 결과를 보여준다고 하자.

```c
unsigned int check(const char *s) {
    unsigned int h = 0;
    for (int i = 0; s[i]; i++) {
        h = h * 31 + (unsigned char)s[i];
    }
    return h == 0x7C6D9A2E;
}
```

파이썬으로 즉시 검증할 수 있다.

```python
def poly_hash(s: bytes, base=31, mod=2**32) -> int:
    h = 0
    for c in s:
        h = (h * base + c) % mod
    return h

target = 0x7C6D9A2E
print(poly_hash(b"hello"))       # 예: 다른 값 -> 불일치
print(poly_hash(b"testcase"))    # target과 비교

# 짧은 사전으로 프리이미지 탐색
candidates = [b"admin", b"letmein", b"testcase", b"flagflag"]
for c in candidates:
    if poly_hash(c) == target:
        print("match:", c)
```
길이가 짧고(4~8바이트) 문자셋이 좁다면(REV-0219 방식으로 계산) 이렇게 후보를 늘려 브루트포스로 프리이미지를 찾는 것이 현실적인 해법이다. 길이가 길면 애초에 유일한 원문 복원은 불가능하므로 다른 취약점(길이 검증 우회, 별도 백도어 문자열 등)을 찾아야 한다.

### 심화 예제 — itertools로 전체 탐색해서 실제로 프리이미지를 찾아내기
사전 단어 몇 개만 시도하는 대신, 문자셋과 길이를 고정하고 모든 조합을 실제로 다 돌려서 목표 해시를 만드는 입력을 끝까지 찾아내는 완전 탐색(exhaustive search) 스크립트다. 짧은 길이에서 브루트포스가 실제로 몇 번째 시도에 성공하는지까지 눈으로 확인할 수 있다.
```python
import itertools   # 문자셋의 모든 조합(product)을 순서대로 만들어주는 표준 모듈

def poly_hash(s: bytes, base=31, mod=2**32) -> int:
    """호너의 방법으로 다항식 해시를 계산 (Java String.hashCode()와 동일한 base=31)."""
    h = 0
    for c in s:
        h = (h * base + c) % mod   # 한 문자씩 곱하고 더하는 것을 반복(자연 오버플로가 곧 mod)
    return h

# 목표 해시값을 미리 알고 있는 짧은 문자열로부터 만들어본다 (실전에서는 바이너리가 이 값을 알려줌)
secret = b"ab12"                       # 리버서는 이 값을 모른다고 가정
target = poly_hash(secret)             # 크랙미가 요구하는 목표 해시값이라고 가정
print("목표 해시값:", hex(target))

# 4글자, 소문자+숫자로 이루어진 모든 조합을 순서대로 만들어서 하나씩 대입해본다
charset = "abcdefghijklmnopqrstuvwxyz0123456789"   # 문자 종류 36개
found = None
count = 0
for combo in itertools.product(charset, repeat=4):  # 36^4 = 1,679,616가지 조합을 전부 생성
    count += 1
    candidate = "".join(combo).encode()
    if poly_hash(candidate) == target:               # 목표 해시와 같은 값이 나오면 즉시 발견
        found = candidate
        break

print(f"{count}번째 시도에서 발견:", found)
assert found == secret, "브루트포스로 찾은 값이 원래 비밀값과 다름"
print("전체 탐색으로 목표 해시를 만드는 입력을 실제로 찾아냄")
```
실제로 실행하면 다음과 같이 나온다(실행 확인함):
```text
목표 해시값: 0x2d8e02
2297번째 시도에서 발견: b'ab12'
전체 탐색으로 목표 해시를 만드는 입력을 실제로 찾아냄
```
길이 4, 문자셋 36개인 이 예제는 최악의 경우에도 168만 번 정도면 끝나서 순식간에 풀린다. 문자셋이나 길이가 커지면 REV-0219/REV-0920의 방식으로 먼저 전체 조합 수를 계산해, 이 방식이 몇 초 안에 끝날지 며칠이 걸릴지 미리 가늠하는 것이 중요하다.

## 관련 글
