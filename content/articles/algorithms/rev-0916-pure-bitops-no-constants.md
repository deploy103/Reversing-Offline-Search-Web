## 한 줄 요약
알려진 매직 넘버도, S-box 테이블도 전혀 없이 SHL/SHR/ROL/ROR/XOR/AND/OR만 반복되는 커스텀 알고리즘은 REV-0915의 상수 매칭 전략이 원천적으로 통하지 않으므로, 정적 분석 대신 동적 실행으로 라운드 함수 하나를 정확히 추출한 뒤 그 라운드 함수만 파이썬으로 정밀 재현하고 전체 반복 횟수를 맞추는 방식으로 접근해야 한다.

## 언제 검색해야 하나
- REV-0915에서 소개한 지문 상수(AES S-box, TEA delta, FNV prime 등)를 전부 대조해봤는데 하나도 일치하지 않을 때
- 코드에 데이터 테이블이 전혀 없고 오직 산술/논리 명령(`shl`, `shr`, `rol`, `ror`, `xor`, `and`, `or`, `add`, `sub`)만 반복되는 루프가 있을 때
- 출제자가 "이 문제는 완전히 새로 설계한 알고리즘"이라고 명시했거나, 알려진 알고리즘의 어떤 구조와도 안 맞아 보일 때
- 라운드 함수 하나가 짧고 단순한데, 전체 라운드 수가 몇 번인지, 라운드마다 무엇이 바뀌는지(라운드 키, 라운드 인덱스) 파악이 안 될 때

## 핵심 개념

### 지문이 없다는 것의 의미
REV-0915에서 다룬 상수 매칭 전략은 "이미 세상에 알려진 알고리즘을 그대로 또는 살짝 변형해서 썼다"는 전제에 의존한다. 하지만 순수 비트 연산만으로 이루어진 커스텀 알고리즘은 애초에 참고할 표준 명세가 없다 — 출제자가 그 자리에서 새로 설계했기 때문이다. 이 경우 "이 알고리즘의 이름이 무엇인지" 알아내려는 시도 자체가 무의미하며, 목표를 "이름 식별"에서 "정확한 동작 재현"으로 전환해야 한다.

### ARX(Add-Rotate-XOR) 계열이라는 것만은 참고할 수 있다
상수는 없어도, 연산 종류(덧셈, 회전, XOR)만으로 이루어진 구조라면 REV-0915에서 언급한 ARX 계열의 일반적인 성질은 참고할 수 있다. ARX 계열 알고리즘은 보통 다음 골격을 갖는다.

```c
uint32_t a, b, c, d;  // 상태 변수(레지스터 몇 개)
for (int round = 0; round < N; round++) {
    a = (a + b) ;
    a = rol(a, K1);       // K1: 고정된 회전량 (상수지만 "지문"으로 알려진 값은 아님)
    a ^= c;
    c = (c + d);
    c = rol(c, K2);
    c ^= a;
    // ... 상태 변수들끼리 계속 뒤섞임
}
```

여기서 회전량 `K1`, `K2` 등은 분명 상수지만 FNV prime이나 AES S-box처럼 "공개적으로 알려진 지문"이 아니라 출제자가 임의로 고른 값이다. 따라서 이 값들을 인터넷에서 검색해봐야 소용없고, 코드에서 직접 정확한 값을 뽑아내는 수밖에 없다.

### 정적 분석의 한계와 동적 분석으로의 전환
순수 비트 연산 코드는 컴파일러 최적화가 심하게 걸리면(레지스터 재할당, 명령어 재배열, 루프 언롤링) 정적 디스어셈블리만으로 라운드 경계를 알아보기 어려울 수 있다. 이런 경우 다음 동적 분석 전략이 훨씬 효율적이다.

1. **라운드 함수 시작/끝에 브레이크포인트**: 루프가 도는 지점(주소가 반복되는 지점)을 GDB `x/i $pc`로 확인하고, 그 주소에 브레이크포인트를 걸어 몇 번 반복되는지(`ignore` 명령으로 카운트하거나 단순히 몇 번 걸리는지 세어) 확인한다.
2. **매 반복마다 상태 변수 덤프**: 라운드가 끝나는 지점마다 관련 레지스터/메모리 값을 출력해서, 한 라운드가 정확히 상태를 어떻게 바꾸는지 데이터로 확보한다.
3. **Unicorn/Capstone으로 라운드 함수만 떼어내 에뮬레이션**: 라운드 함수의 시작/끝 주소만 알면, 전체 프로그램을 실행하지 않고도 Unicorn 엔진으로 그 함수만 독립적으로 실행하며 임의의 입력에 대한 출력을 빠르게 관찰할 수 있다(REV-0273).

### 라운드 함수를 블랙박스로 취급해 입출력만으로 역설계하기
디스어셈블리를 한 줄씩 해석하는 게 너무 어렵다면, 라운드 함수를 아예 "블랙박스"로 놓고 입출력 관계만으로 동작을 추정하는 방법도 있다. 예를 들어 입력 상태에서 한 비트만 바꿔가며 출력이 어떻게 바뀌는지 관찰하면(REV-0913의 눈사태 효과 테스트와 같은 원리), 어떤 입력 비트가 어떤 출력 비트에 영향을 주는지(비트 의존성 그래프)를 실험적으로 추론할 수 있다. 이 방법은 완벽하지 않지만, 디스어셈블리 해석이 막힐 때 실마리를 제공한다.

```python
def bit_dependency_map(black_box, input_bits=32, output_bits=32):
    base = black_box(0)
    deps = {}
    for i in range(input_bits):
        flipped = black_box(1 << i)
        diff = base ^ flipped
        affected = [b for b in range(output_bits) if (diff >> b) & 1]
        deps[i] = affected
    return deps
```

## 화면/코드에서 보이는 징후
- 코드에 데이터 테이블(배열)이 전혀 없고 오직 레지스터 연산만 반복됨
- `rol`/`ror`(또는 `shl`+`or`+`shr` 조합으로 표현된 회전) 명령이 고정된 시프트량으로 반복됨
- REV-0915의 지문 상수 스캔이 전부 실패함(어떤 알려진 매직 넘버도 안 나옴)
- 함수 이름이나 문제 설명에 "custom", "homemade", "우리만의 알고리즘" 같은 표현이 있음

## 가장 먼저 할 것
루프의 반복 횟수(라운드 수)와 한 반복 안에서 실행되는 명령어 개수(라운드 함수의 크기)를 먼저 확정한다. 그다음 GDB로 실제 실행하며 한 라운드 전후의 상태 변수 값을 직접 기록해 "라운드 함수가 정확히 무엇을 하는지"에 대한 실측 데이터를 확보한다.

## 단계별 절차
1. 루프의 시작/끝 주소와 반복 횟수를 확정한다(정적으로 안 보이면 GDB로 실제 실행 횟수를 센다).
2. 라운드 함수 안의 모든 상수(회전량, 상태 변수 개수)를 명령어 단위로 정확히 옮겨 적는다 — 레지스터 이름과 실제 변수 역할을 대응시킨다.
3. GDB로 라운드 경계마다 상태 변수를 덤프해, 정적으로 옮긴 로직이 실제 값 변화와 일치하는지 최소 2~3라운드 분량 검증한다.
4. 파이썬으로 라운드 함수 하나를 정확히 재구현하고, 전체 라운드 수만큼 반복 적용하는 전체 함수를 완성한다.
5. 알려진 입력에 대해 파이썬 재구현과 실제 바이너리 실행 결과가 매 라운드마다 일치하는지 교차 검증한다(REV-0912, REV-0919).
6. 정확히 재구현되면, 이후 이 알고리즘이 가역인지(REV-0221), known-plaintext 없이도 판단 가능한지(REV-0913) 다음 단계로 넘어간다.

## 출력 해석
- GDB로 관찰한 실제 상태 변화가 정적으로 옮긴 파이썬 로직과 라운드마다 정확히 일치하면 재구현이 정확하다는 뜻이다.
- 특정 라운드에서만 값이 어긋난다면, 회전량이나 XOR 순서를 잘못 옮겼을 가능성이 크다 — 그 라운드의 명령어를 다시 한 줄씩 대조한다.
- 비트 의존성 맵(`bit_dependency_map`)에서 특정 입력 비트가 출력의 극히 일부 비트에만 영향을 준다면 약한 확산(디퓨전)을 가진 알고리즘이라는 뜻이고, 이는 부분적인 역산이나 분할 정복 전략의 실마리가 될 수 있다.

## 흔한 실수
- 지문 매칭이 실패했다고 "이 알고리즘은 분석 불가능하다"고 포기하는 것 — 지문이 없을 뿐, 정적+동적 분석을 정확히 병행하면 어떤 커스텀 알고리즘이든 재현 가능하다.
- 회전 연산이 `rol`/`ror` 명령이 아니라 `(x << k) | (x >> (32-k))` 형태로 풀어져 있는 것을 못 알아보고 별개의 시프트 연산 두 개로 착각하는 것 — 이 패턴은 회전(rotate)의 전형적인 컴파일 결과이므로 항상 하나의 회전 연산으로 묶어 해석해야 한다.
- 라운드 수를 정적으로만 추측하고 실제 실행 횟수를 세어보지 않는 것 — 루프 언롤링이 있으면 정적으로 보이는 코드 블록 수와 실제 논리적 라운드 수가 다를 수 있다.
- 재구현을 라운드 1개만 검증하고 전체가 맞다고 확신하는 것 — 라운드마다 라운드 인덱스나 라운드 키가 달라지는 경우가 흔하므로 최소 몇 라운드는 반드시 교차 검증해야 한다.

## 막혔을 때 다음 체크
- 표준 암호의 변형일 가능성도 다시 확인하고 싶다면 → REV-0915 라이브러리 호출 없이 손으로 구현된 암호를 알아채는 단서
- 재구현 후 이 알고리즘이 역산 가능한지 판단하려면 → REV-0221 역연산 가능한 알고리즘 판단법, REV-0913 Known-plaintext 없이 알고리즘 성질만으로 역산 가능성 판단하기
- 손으로 다 못 풀겠어서 자동화 도구로 넘기고 싶다면 → REV-0271 angr 심볼릭 실행 기초, REV-0273 Unicorn으로 작은 검증 함수 에뮬레이션
- 재구현 결과를 체계적으로 검증하는 절차가 궁금하면 → REV-0912 알고리즘 복원 결과를 유닛 테스트로 검증하는 법

## 미니 예제
다음과 같은 라운드 함수가 GDB 관찰로 확인됐다고 하자(상수는 모두 임의로 고른 값이라 검색해도 안 나온다).

```c
void round_func(uint32_t *a, uint32_t *b) {
    *a += *b;
    *a = (*a << 7) | (*a >> 25);   // rol(a, 7)
    *a ^= *b;
    *b += *a;
    *b = (*b << 3) | (*b >> 29);   // rol(b, 3)
}
```

GDB로 4라운드 반복이 확인됐다면, 파이썬으로 그대로 옮긴다.

```python
def rol32(x, k):
    x &= 0xFFFFFFFF
    return ((x << k) | (x >> (32 - k))) & 0xFFFFFFFF

def round_func(a, b):
    a = (a + b) & 0xFFFFFFFF
    a = rol32(a, 7)
    a ^= b
    b = (b + a) & 0xFFFFFFFF
    b = rol32(b, 3)
    return a, b

def encrypt(a, b, rounds=4):
    for _ in range(rounds):
        a, b = round_func(a, b)
    return a, b

print(encrypt(0x11111111, 0x22222222))
```

이 결과를 실제 바이너리를 GDB로 같은 초기값을 넣어 실행한 결과와 라운드마다 비교하면, 재구현이 정확한지 확실히 검증할 수 있다.

## 출처/검증
- ARX(Add-Rotate-XOR) 구조와 이를 이용한 라운드 함수 설계 일반론: ChaCha/Salsa20 등 ARX 계열 스트림 암호의 공개 설계 문서(Daniel J. Bernstein) 기준.
- 회전(rotate) 연산이 시프트+OR 조합으로 컴파일되는 전형적인 패턴: 컴파일러가 회전 연산을 위한 전용 명령(`rol`/`ror`)을 못 쓰는 고수준 언어 표현을 시프트 두 개로 대체하는 일반적인 코드 생성 관행 기준 (2026-09-09 검증).
