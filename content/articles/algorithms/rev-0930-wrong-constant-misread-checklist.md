## 한 줄 요약
알고리즘 로직 전체를 정확히 옮겼는데도 결과가 안 맞는다면, 의외로 원인은 로직이 아니라 **상수 하나를 눈으로 잘못 옮겨 적은 것**인 경우가 매우 많다 — 16진수/10진수 혼동, 자릿수 누락, 부호 있는 표시로 인한 오독, 64비트 값을 32비트로 잘라 읽는 실수가 대표적이며, 이 글은 그런 실수들과 함께 `algorithms` 카테고리 전체를 마무리하는 디버깅 체크리스트를 겸한다.

## 언제 검색해야 하나
- 로직, 오버플로우 마스킹, 엔디안, 패딩, 라운드 수까지 다 확인했는데도 결과가 안 맞을 때
- 디컴파일 창에 보이는 상수와 디스어셈블리의 상수가 다르게 표시될 때
- 상수를 옮겨 적을 때 손으로 타이핑하다가 자릿수를 빼먹었을 가능성이 있을 때
- `algorithms` 카테고리의 다른 글로 원인을 다 좁혀봤는데도 여전히 안 맞을 때, 마지막으로 상수 자체를 재검증하고 싶을 때

## 핵심 개념
상수 오독은 크게 네 가지 형태로 나타난다.

**1) signed/unsigned 표시로 인한 오독**: 디컴파일러가 32비트 unsigned 상수를 signed로 표시해서 `-1520786223`처럼 낯선 음수로 보여주는 경우. 이 값을 그대로 옮기면 부호만 다른 게 아니라 완전히 다른 비트 패턴으로 착각하기 쉽다.

**2) 64비트 값을 32비트로 잘라 읽는 실수**: `mov eax, imm32` 같은 명령은 32비트 즉시값만 가지지만, 64비트 레지스터 전체(`rax`)에 값을 넣는 `movabs rax, imm64` 계열 명령은 8바이트 전체가 상수다. 디스어셈블리 뷰나 IDA의 특정 표시 모드에서 이 둘을 혼동하면, 64비트 상수의 상위 32비트를 통째로 놓치고 하위 32비트만 옮겨 적는 실수가 생긴다.

**3) 16진수/10진수 혼동**: 소스나 라이트업에 `0x10`이라고 적힌 걸 10으로 옮기거나, 반대로 디컴파일러가 보여주는 순수 10진수 상수(`803406689`)를 16진수 자릿수처럼 착각해서 앞에 `0x`를 붙여버리는 실수. 상수를 옮길 때는 항상 진법 표시(`0x` 유무)를 소스와 정확히 대조해야 한다.

**4) 손으로 옮겨 적다가 생기는 단순 오타**: 자릿수 하나를 빠뜨리거나(`0x1A2B3C4D`를 `0x1A2B3C4`로), 비슷하게 생긴 문자를 바꿔 쓰는(`0`과 `O`, `1`과 `l`) 것처럼 순수한 타이핑 실수. 상수가 길수록 확률이 높아진다.

이 네 가지는 전부 "값 자체는 완전히 틀렸지만 로직은 완벽하게 맞는" 상황을 만들기 때문에, 로직만 아무리 재확인해도 못 찾는다. **상수는 항상 복사(copy)로 옮기고, 손으로 타이핑하지 않는 것**이 가장 확실한 예방책이다.

## 화면/코드에서 보이는 징후
- 파이썬 코드의 상수 리터럴과 IDA/Ghidra 화면에 표시된 상수를 나란히 놓고 봤을 때 자릿수나 부호가 다름
- `cmp` 명령의 오퍼랜드(어셈블리, hex)와 디컴파일 창의 비교 상수(C 코드, 종종 signed 10진수)가 겉보기에 다른 표기로 보임
- 64비트 레지스터에 대입되는 명령(`movabs`, `mov reg64, imm64`)인데 상수를 8바이트가 아니라 4바이트로 옮겨 적음

## 가장 먼저 할 것
로직을 다른 REV 문서들의 체크리스트로 다 확인했는데도 안 맞는다면, 코드에 쓰인 **모든 상수를 하나하나 디스어셈블리와 다시 대조**한다. 이때 절대 눈으로 보고 타이핑하지 말고, IDA/Ghidra에서 값을 직접 복사해서 붙여넣는다.

## 단계별 절차

**1) 상수 목록 뽑기**

재구현 코드에 등장하는 모든 리터럴 상수(초기값, 곱셈/시프트 상수, 목표 비교값)를 리스트로 뽑는다.

**2) 원본 디스어셈블리에서 같은 상수를 복사로 재확인**

IDA/Ghidra에서 해당 상수 위에 커서를 놓고 값을 복사(`Ctrl+C` 또는 우클릭 → Copy)해서, 재구현 코드의 값과 문자열 그대로 비교한다.

**3) signed로 표시된 상수는 unsigned로 변환해서 대조**
```python
def to_u32(n: int) -> int:
    return n & 0xFFFFFFFF

# 디컴파일러가 -1520786223으로 보여준 상수
print(hex(to_u32(-1520786223)))
```

**4) 64비트 상수는 명령어 종류부터 확인**

`mov eax, imm32`인지 `movabs rax, imm64`(또는 `mov rax, imm64`)인지 옵코드/피연산자 크기를 먼저 확인하고, 64비트라면 8바이트 전체를 옮긴다.

**5) 진법 표시를 소스와 한 글자씩 대조**

`0x` 접두어 유무, 자릿수 개수를 원본과 정확히 맞춘다.

## 명령어/단축키
```python
hex(n & 0xFFFFFFFF)              # signed로 보이는 값 -> unsigned 32비트로 환원
hex(n & 0xFFFFFFFFFFFFFFFF)      # signed로 보이는 값 -> unsigned 64비트로 환원
assert my_constant == 0x1A2B3C4D # 상수 하나하나에 assert를 걸어 오타를 조기에 잡기
```
IDA: 상수 위 우클릭 → `Copy` 또는 `Yank`로 값을 직접 복사(손 타이핑 대신).

## 출력 해석
- 상수를 하나씩 `assert`로 걸어두면, 재구현 코드를 실행하는 순간 어떤 상수가 틀렸는지 그 줄 번호로 바로 알 수 있다.
- 모든 상수가 assert를 통과했는데도 결과가 안 맞으면, 상수 문제가 아니라 로직/순서 문제이므로 이진 탐색 절차로 되돌아간다.

## 흔한 실수
- 상수를 눈으로 보고 손으로 타이핑하는 것 — 8자리, 16자리 hex 상수는 반드시 복사-붙여넣기로 옮긴다.
- signed로 표시된 상수를 "이 프로그램은 원래 음수를 쓰나보다"라고 그대로 믿고 옮기는 것 — 항상 unsigned 여부를 먼저 확인한다.
- 여러 상수 중 하나만 확인하고 나머지는 "맞겠지"라고 넘어가는 것 — 상수가 여러 개라면 전부 assert로 걸어서 한 번에 검증한다.
- 상수 오독을 의심하지 않고 로직만 계속 다시 짜는 것 — 로직 재작성은 이미 맞는 부분에 새 버그를 심을 위험이 있으므로, 상수부터 먼저 배제하는 게 안전하다.

## 막혔을 때 다음 체크
아래는 `algorithms` 카테고리를 마무리하는 디버깅 체크리스트다. 알고리즘 복원 결과가 원본과 안 맞을 때는 이 순서로 하나씩 배제해나가는 것이 가장 효율적이다.

1. 오라클(체크 함수) 자체가 맞는지 알려진 입력으로 교차검증했는가? → REV-0924 브루트포스를 돌렸는데 답이 안 나올 때
2. 모든 곱셈/덧셈/시프트 뒤에 원본 비트폭에 맞는 마스킹을 걸었는가? → REV-0926 정수 오버플로를 빼먹어서 계산이 계속 안 맞을 때
3. 여러 바이트를 하나의 워드로 합치는 지점의 바이트 순서(엔디안)를 확인했는가? → REV-0927 엔디안을 잘못 적용해서 해시 값이 안 맞을 때
4. 데이터에 필요한 패딩(PKCS7, 길이-강화 패딩 등)을 정확히 적용했는가? → REV-0928 패딩(Padding) 처리를 빼먹어서 결과가 어긋날 때
5. 루프 반복 횟수와 마지막 라운드의 예외 처리를 디스어셈블리로 직접 세어 확인했는가? → REV-0929 라운드 수나 반복 횟수를 잘못 세어서 결과가 다를 때
6. 모든 상수를 손 타이핑이 아니라 복사로 옮겼고, signed/unsigned 표시를 확인했는가? → 이 글(REV-0930)
7. XOR 키처럼 부분적으로만 복구된 값이 있다면 주기적 오류 패턴을 확인했는가? → REV-0922 XOR 키를 구했는데 일부만 맞을 때
8. Z3를 쓴다면 unsat/틀린 해가 나올 때 unsat_core와 부호 비교부터 재확인했는가? → REV-0925 Z3에게 조건을 걸었는데 unsat이 뜰 때
9. 여전히 원인을 못 찾겠다면, 최종 출력이 아니라 중간값을 단계별로 비교하는 이진 탐색으로 되돌아갔는가? → REV-0921 알고리즘을 복원했는데 출력이 원본과 안 맞을 때

이 아홉 단계를 순서대로 배제하면, 대부분의 "로직은 맞는 것 같은데 결과가 안 맞는" 상황의 원인을 찾아낼 수 있다.

## 미니 예제
어떤 검증 함수의 목표 상수를 디컴파일 창에서 다음과 같이 봤다고 하자.
```c
if (hash == -1640531527) return SUCCESS;
```
이 값을 그대로 파이썬에 `-1640531527`로 옮겨서 비교했더니 절대 통과하지 못했다. unsigned로 변환해본다.
```python
print(hex(-1640531527 & 0xFFFFFFFF))   # 0x9e3779b9
```
`0x9E3779B9`는 TEA의 델타 상수(REV-0210)다. `hash`는 애초에 `unsigned int`로 선언된 변수인데 디컴파일러가 signed 10진수로 보여준 것뿐이었고, 이를 그대로(signed 그대로) 옮긴 것이 원인이었다. `hash == 0x9E3779B9`로 고치자 검증 로직이 원본과 정확히 일치했다.

## 출처/검증
- x86/x64의 `mov reg32, imm32`와 `movabs`/`mov reg64, imm64` 명령어의 즉시값 크기 차이: Intel 64 and IA-32 Architectures Software Developer's Manual, Volume 2(MOV 명령어 정의) 기준 (2026-09-09 검증).
- signed/unsigned 상수 표시 문제의 근본 원리는 REV-0206 문서와 동일한 2의 보수 표현 규칙에 기반한다.
