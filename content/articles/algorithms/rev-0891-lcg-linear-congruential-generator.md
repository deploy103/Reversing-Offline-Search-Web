## 한 줄 요약
난수 하나를 만드는 데 상태값 하나에 대해 `state = (state * A + C) mod M`이라는 곱셈-덧셈-나머지 연산 한 줄이면 충분하고, 그 상태값에서 바로 출력을 뽑아낸다면 그건 선형 합동 생성기(LCG)이며, 이전 출력 하나 또는 몇 개만 알면 그 이후 전체 수열을 그대로 예측할 수 있는 암호학적으로 취약한 PRNG다.

## 언제 검색해야 하나
- 난수 생성 함수가 복잡한 상태 배열 없이 **정수 변수 하나**만 유지하면서, 매 호출마다 그 값에 곱셈, 덧셈, 나머지(또는 오른쪽 시프트/AND 마스킹)를 적용해 다음 값을 만들 때
- `1103515245`, `12345`, `214013`, `2531011`, `0x5DEECE66D`, `0xB` 같은 상수가 곱셈/덧셈 자리에 등장할 때
- CTF 문제에서 "다음에 나올 난수를 예측하라", "이전 시드를 복원하라" 같은 요구가 있고, 바이너리의 난수 생성 로직이 짧고 단순할 때
- `srand(seed)` 이후 `rand()`를 여러 번 호출해서 나온 값들로 게임의 승패나 검증 로직이 결정되는 구조를 봤을 때

## 핵심 개념

### LCG의 정의
LCG는 가장 오래되고 가장 단순한 의사난수 생성기 알고리즘이다. 내부 상태(state, 흔히 `X`로 표기)를 하나만 유지하고, 다음 상태를 아래 점화식으로 계산한다.

```
X_(n+1) = (A * X_n + C) mod M
```
여기서 `A`(승수, multiplier), `C`(증분, increment), `M`(모듈러스, modulus)은 알고리즘마다 고정된 상수다. 출력값은 보통 이 상태값 자체이거나, 상태값의 특정 비트 구간을 잘라낸 값이다. 알고리즘 전체가 곱셈 한 번, 덧셈 한 번, 나머지(혹은 비트마스킹) 한 번으로 끝나기 때문에 컴파일된 코드에서 극도로 짧고 단순한 형태로 나타난다.

```c
// LCG의 전형적인 형태 — 상태 하나, 연산 한 줄
static uint32_t lcg_state;

uint32_t lcg_next(void) {
    lcg_state = lcg_state * 1103515245u + 12345u;   // A, C가 그대로 리터럴로 박혀있음
    return (lcg_state >> 16) & 0x7fff;               // 상위 비트만 잘라 반환하는 경우가 흔함
}
```
모듈러스 `M`은 코드에 명시적인 나머지 연산으로 나타나지 않는 경우가 많다 — 상태 변수가 정확히 32비트(`uint32_t`) 또는 64비트 정수라면, **정수 오버플로 자체가 `mod 2^32`(또는 `2^64`) 나머지 연산을 대신**해준다. 그래서 겉보기엔 그냥 평범한 곱셈-덧셈으로 보이지만 실제로는 모듈러 연산이 자동으로 걸려 있는 것이다.

### 잘 알려진 LCG 상수들 — 어떤 런타임인지 특정하기
같은 LCG 구조라도 상수(`A`, `C`, `M`)가 다르면 완전히 다른 라이브러리/언어의 구현이다. 상수만 보고도 어떤 런타임에서 나온 코드인지 짐작할 수 있다.

| 출처 | A(승수) | C(증분) | 비고 |
|---|---|---|---|
| ANSI C 예제 / 구형·임베디드 libc, musl의 내부 `lcg31`/`rand_r` 보조 함수 | `1103515245` | `12345` | `mod 2^31`, 교과서에 실린 원조 LCG. musl의 `rand_r.c`에도 이 상수를 쓰는 `lcg31` 헬퍼가 존재 |
| Microsoft Visual C++ `rand()`(구 CRT, VC6 계열) | `214013` | `2531011` | `mod 2^32`(32비트 오버플로), 결과는 `(x >> 16) & 0x7fff`로 15비트만 반환 |
| Java `java.util.Random` | `0x5DEECE66D`(25214903917) | `0xB`(11) | `mod 2^48`, 시드 설정 시 `seed ^ 0x5DEECE66D`로 한 번 더 XOR |
| musl `lcg64`(64비트 보조 LCG) | `6364136223846793005` | `1` | `mod 2^64`, PCG 계열에서도 재사용되는 유명한 64비트 승수 |

**주의**: glibc(리눅스 표준 C 라이브러리)의 실제 `rand()`/`random()`은 이런 단순 LCG가 **아니다**. glibc는 기본적으로 상태 테이블 31개짜리 지연 피보나치형 덧셈 생성기(`r[i] = (r[i-3] + r[i-31]) mod 2^32`, 이후 한 비트를 버려 출력)를 쓴다. 겉보기엔 "상태 하나짜리 단순 연산"이 아니라 "배열 하나를 순환 참조하며 두 항을 더하는" 형태로 나타나므로, 상태가 배열인지 스칼라 변수인지만 봐도 glibc 스타일과 순수 LCG를 구분할 수 있다. 이 차이는 REV-0893에서 더 자세히 다룬다.

### LCG가 암호학적으로 취약한 이유 — 예측과 역추적
LCG는 상수 `A`, `C`, `M`을 알고 있고 출력값을 하나(또는 상위 비트만 잘려 나온다면 몇 개) 확보하면, 다음 출력값을 그대로 계산할 수 있다. 더 나아가 **역방향 계산도 가능**하다 — `A`가 `M`에 대해 모듈러 역원(REV-0887)을 가지면, `X_n = (X_(n+1) - C) * A^-1 mod M` 공식으로 이전 상태를 거꾸로 복원할 수 있다. 즉 LCG는 "다음 값 예측"과 "이전 값 역추적"이 모두 대수적으로 간단히 풀리는, 암호학적 용도로는 절대 쓰면 안 되는 생성기다.

```python
def lcg_next(x, a, c, m):
    return (a * x + c) % m

def lcg_prev(x, a, c, m):
    a_inv = pow(a, -1, m)          # REV-0887의 모듈러 역원
    return ((x - c) * a_inv) % m
```

### 출력에서 상위 비트만 잘라내는 이유
표에서 보듯 MSVC의 `rand()`는 상태값의 하위 16비트를 버리고 그 위의 15비트만 반환한다. LCG는 **하위 비트일수록 주기가 짧고 통계적 편향이 심하다**는 알려진 약점이 있어서, 실무 구현들은 상대적으로 더 무작위에 가까운 상위 비트만 골라 쓴다. 이 사실은 리버싱 중 "출력값만으로 전체 32/64비트 상태를 복원할 수 있는가"를 판단할 때 중요하다 — 상위 비트만 보인다면 하위 비트 정보가 손실되어 있으므로, 여러 개의 연속 출력을 모아 하위 비트를 브루트포스로 채워 넣어야 정확한 상태 복원이 가능하다.

## 화면/코드에서 보이는 징후
- 전역/정적 변수 하나(배열이 아님)가 상태로 쓰이고, 함수 호출마다 `state = state * CONST_A + CONST_B` 형태로 갱신됨
- 표에 나온 상수(`1103515245`, `12345`, `214013`, `2531011`, `0x5DEECE66D`, `0xB`, `6364136223846793005`)가 그대로 리터럴로 등장
- 나머지 연산이 명시적으로 없지만 상태 변수 타입이 고정 비트 폭 정수(`uint32_t`, `uint64_t`)라 오버플로로 모듈러 연산이 암묵적으로 처리됨
- 반환값이 상태값 그 자체가 아니라 시프트/마스킹으로 일부 비트만 잘라낸 형태(`>> 16`, `& 0x7fff`)

## 가장 먼저 할 것
곱셈에 쓰이는 상수를 확인해 위 표와 대조한다. 일치하는 게 있으면 해당 런타임의 표준 구현으로 확정하고 공개된 상수/모듈러스를 그대로 가져다 쓴다. 표에 없는 낯선 상수라면 커스텀 LCG일 수 있으니, 상태 변수의 비트 폭으로 모듈러스 `M`부터 추정한다.

## 단계별 절차
1. 난수 생성 함수에서 상태가 배열인지 스칼라 변수인지 확인 — 스칼라면 LCG 계열, 배열이면 glibc식 지연 피보나치나 Mersenne Twister(REV-0892)일 가능성
2. 곱셈/덧셈 상수를 표와 대조해 어떤 런타임인지 특정
3. 상태 변수의 타입 크기(32/48/64비트)로 모듈러스 `M`을 확정
4. 출력이 상태 전체인지, 상위/하위 일부 비트만 잘린 것인지 확인
5. 시드 하나(또는 출력 하나)를 확보했다면 파이썬으로 동일 점화식을 재현해 이후 수열 전체를 예측
6. 이전 상태를 복원해야 한다면 모듈러 역원(REV-0887)으로 역방향 점화식을 세워 계산
7. 출력이 일부 비트만 잘린 경우, 연속된 여러 출력값과 상태 갱신 규칙을 연립해 손실된 비트를 좁혀나감(제약이 부족하면 남은 비트 폭만큼만 브루트포스)

## 명령어/단축키
```python
# 상수 대조 스니펫 — 코드에서 뽑은 상수를 아래 표와 비교
KNOWN_LCG = {
    "ansi_c":  (1103515245, 12345, 2**31),
    "msvcrt":  (214013, 2531011, 2**32),
    "java":    (0x5DEECE66D, 0xB, 2**48),
    "musl64":  (6364136223846793005, 1, 2**64),
}

def identify(a, c):
    for name, (A, C, M) in KNOWN_LCG.items():
        if a == A and c == C:
            return name, M
    return None, None
```
IDA/Ghidra: 곱셈 명령어(`imul`) 피연산자 위에서 상수를 확인하고 `Alt+B`로 같은 상수가 다른 함수에도 나오는지 교차 검색.

## 출력 해석
- 표의 상수와 정확히 일치하면 모듈러스와 출력 비트 자르기 방식까지 이미 공개된 정보이므로, 별도 분석 없이 표준 구현을 그대로 파이썬으로 재현하면 된다.
- 상수가 표에 없다면 커스텀 LCG이니, 상태 변수의 선언 타입으로 모듈러스를 추정하고 직접 점화식을 재구성해야 한다.
- 출력이 상태의 일부 비트만 잘라낸 것이라면, 시드 하나만으로는 다음 값을 100% 확정할 수 없고 잘려나간 비트 폭만큼의 후보가 남는다는 점을 감안해야 한다.

## 흔한 실수
- glibc `rand()`도 단순 LCG일 거라고 가정하고 표의 ANSI C 상수를 그대로 적용하는 것 — glibc의 기본 `random()`/`rand()`는 배열 기반 지연 피보나치 생성기이지 단일 상태 LCG가 아니다(REV-0893 참고).
- 모듈러스를 잘못 잡아서(예: 32비트인데 31비트로 가정) 예측값이 미묘하게 어긋나는 것.
- 출력에서 잘려나간 하위 비트를 무시하고 상태값과 출력값이 동일하다고 가정해 이전 상태 복원 공식이 어긋나는 것.
- 상수가 우연히 비슷해 보인다고(예: 자릿수가 비슷) 실제로 대조하지 않고 런타임을 잘못 단정하는 것 — 반드시 정확한 숫자 일치를 확인해야 한다.

## 막혔을 때 다음 체크
- 상태가 배열 기반이고 인덱스가 순환한다면 glibc 스타일이거나 Mersenne Twister일 가능성이 크므로 → REV-0892 Mersenne Twister 흔적 알아보기
- 실제 `rand()`/`srand()` 문제에 어떻게 접근할지 구체적 전략이 필요하면 → REV-0893 rand()/srand() 시드 기반 문제 접근법
- 상태 역추적에 필요한 모듈러 역원 계산법이 기억나지 않으면 → REV-0887 모듈러 역원(Modular Inverse)이 코드에 나타나는 패턴
- 시드값 자체가 시간(`time()`)에서 온다면 → REV-0894 시간 기반 시드(seed = time())를 역산하는 접근

## 미니 예제
어떤 게임 바이너리를 IDA로 열었더니 다음과 같은 디컴파일 결과가 나왔다고 하자.

```c
unsigned int g_state;

int next_roll(void) {
    g_state = g_state * 214013 + 2531011;
    return (g_state >> 16) & 0x7fff;
}
```
곱셈 상수 `214013`과 덧셈 상수 `2531011`이 표의 MSVC `rand()` 계열과 정확히 일치한다. 시드(`g_state`의 초기값)만 알아내면 이후 모든 "주사위 굴림" 결과를 그대로 예측할 수 있다.

```python
def msvc_rand(seed, n):
    state = seed
    outs = []
    for _ in range(n):
        state = (state * 214013 + 2531011) & 0xFFFFFFFF
        outs.append((state >> 16) & 0x7fff)
    return outs

# 예: 프로그램이 화면에 표시한 시드값이 12345였다면
print(msvc_rand(12345, 5))
```
이렇게 재현한 수열이 실제 프로그램의 출력과 일치하는지 확인하면, 이후의 "다음 값"을 미리 알고 문제를 풀 수 있다.

## 관련 글
- REV-0892 — Mersenne Twister 흔적 알아보기
- REV-0893 — rand()/srand() 시드 기반 문제 접근법
- REV-0894 — 시간 기반 시드(seed = time())를 역산하는 접근
- REV-0887 — 모듈러 역원(Modular Inverse)이 코드에 나타나는 패턴
- REV-0883 — 흔한 시드 기반 PRNG 상수 빠른 참조(LCG 계수 등)

## 출처/검증
- ANSI C 예제 LCG 상수(`1103515245`, `12345`)와 musl `rand_r.c`의 `lcg31`/`lcg64` 헬퍼 구현: musl libc 공식 저장소 `src/prng/rand_r.c` 소스 기준 (2026-09-09 검증).
- Microsoft Visual C++ 구형 CRT `rand()` 구현(`214013`, `2531011`, 상위 15비트 반환): Microsoft Visual C++ 6.0 CRT 소스 및 이를 재현한 다수의 기술 문서/게임 개발 참고자료(Vintage RNG 분석) 기준 (2026-09-09 검증).
- Java `java.util.Random`의 LCG 상수(`0x5DEECE66D`, `0xB`, 48비트 모듈러스): OpenJDK `java.util.Random` 공식 소스 및 Java SE 공식 API 문서 기준 (2026-09-09 검증).
