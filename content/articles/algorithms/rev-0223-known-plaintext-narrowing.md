## 한 줄 요약
CTF 플래그는 거의 항상 `flag{`처럼 정해진 형식으로 시작하며, 이 알려진 평문(known plaintext)과 바이너리 안의 비교 대상(사실상의 암호문)을 XOR하면 브루트포스 없이 키를 직접 계산해낼 수 있다 — 형식만으로 문자셋을 좁히는 것보다 훨씬 강력한 지름길이다.

## 언제 검색해야 하나
- 체크 함수가 입력을 어떤 방식으로 변환한 뒤 고정된 배열과 비교하는데, 그 변환이 XOR 계열로 보일 때
- "플래그 형식이 `flag{...}`인 걸 아는데 이걸로 뭘 할 수 있지?"라는 생각이 들 때
- 브루트포스 공간이 너무 커서(REV-0219 계산 결과 비현실적) 다른 지름길이 필요할 때
- 이미 REV-0221에서 이 변환이 XOR처럼 가역이라고 판단했는데, 정작 키 값 자체를 모를 때

## 핵심 개념
고전 암호학의 "기지평문 공격(known-plaintext attack)"은 공격자가 평문 일부와 그에 대응하는 암호문 일부를 동시에 알고 있을 때 성립한다. CTF 리버싱에서는 이 조건이 거의 공짜로 주어진다: 플래그가 `flag{`로 시작한다는 건 문제 설명에서 이미 알려주고, 그 `flag{`가 변환된 결과(비교 대상 상수 배열)는 바이너리의 `.rodata`에서 직접 뽑아낼 수 있기 때문이다.

변환이 `ciphertext = plaintext XOR key`(키를 평문 길이에 맞춰 반복 적용) 형태라면, 알고 있는 평문 바이트와 대응 암호문 바이트를 XOR하기만 하면 키 바이트가 바로 나온다: `key_byte[i] = plaintext_byte[i] ^ ciphertext_byte[i]`. 브루트포스가 전혀 필요 없고, 알려진 길이만큼만 계산하면 끝난다(O(알려진 길이)).

이 접근은 REV-0218(길이 역추적)·REV-0219(브루트포스 가능성 계산)이 "탐색 공간을 줄이는" 접근인 것과 달리, **탐색 자체를 없애버리는** 접근이다. 다만 이 지름길은 변환이 바이트 단위로 독립적인 XOR류일 때만 통한다 — 여러 바이트가 뒤섞이는 해시나 블록암호에는 적용할 수 없다(뒤에서 설명).

## 화면/코드에서 보이는 징후
- 루프 안에서 `input[i] ^ key[i % key_len]` 형태의 바이트별 독립 XOR
- 비교 대상 배열이 `.rodata`에 하드코딩되어 있고, 길이가 예상 플래그 길이와 비슷함
- 문제 설명이나 템플릿에 `flag{` 또는 `FLAG{`, `dreamhack{`처럼 대회별 고정 접두사가 명시됨

## 가장 먼저 할 것
IDA/Ghidra에서 비교 대상 배열(정답 암호문)의 원본 바이트를 정확히 덤프한다. 그다음 문제에서 알려진 접두사(`flag{` 등)의 아스키 바이트와 나란히 놓고 XOR해서 키 후보를 뽑는다.

## 단계별 절차

**1) 비교 대상 배열 덤프**

IDA에서 비교 대상 배열을 더블클릭해 `.rodata`로 이동한 뒤, 배열 시작 주소에서 `Alt+B`(hex view)로 바이트를 그대로 읽는다. 예를 들어 앞 5바이트가 `43 5C 8E 8B DB`라고 하자.

**2) 알려진 평문 바이트 확보**

플래그가 `flag{`로 시작한다고 알려져 있으면, 아스키 값은 `f=0x66, l=0x6C, a=0x61, g=0x67, {=0x7B`이다.

**3) 바이트별 XOR로 키 계산**

```
0x43 ^ 0x66 = 0x25
0x5C ^ 0x6C = 0x30
0x8E ^ 0x61 = 0xEF
0x8B ^ 0x67 = 0xEC
0xDB ^ 0x7B = 0xA0
```
키 후보는 `[0x25, 0x30, 0xEF, 0xEC, 0xA0]`이다.

**4) 키 길이 확인**

이 5바이트가 정말 반복 키인지 확인하려면, 암호문의 6번째, 7번째... 바이트를 같은 5바이트 키로 계속 XOR해서 나온 결과가 출력 가능한 문자(아스키 32~126)로 이어지는지 본다. 사람이 읽을 수 있는 문자열이 계속 나오면 키 길이 5가 맞다고 확신할 수 있다.

알려진 평문이 짧아서(예: `flag{`가 5바이트뿐) 키 길이가 5보다 긴지 확신이 안 서는 경우에는, 고전 암호학의 **카시스키 테스트(Kasiski examination)**와 같은 원리를 이용할 수 있다: 반복 키 XOR 암호문에서는 "같은 평문 조각이 같은 키 위치에서 다시 나타나는 지점" 사이의 거리가 키 길이의 배수가 되는 경향이 있다. 실전에서는 이렇게까지 정교하게 할 필요 없이, 후보 키 길이를 5, 8, 10, 16처럼 몇 가지로 좁혀서(대개 flag의 알려진 총 길이의 약수이거나, 함수 안에 보이는 다른 상수 배열의 크기와 일치하는 값들) 각각 시도해보고 결과가 사람이 읽을 수 있는 문자열로 나오는 후보를 고르는 **가설 검증(trial decryption)** 방식이 CTF 환경에서는 더 빠르고 실용적이다. 아래 파이썬 코드처럼 여러 후보 길이를 한 번에 시도하는 헬퍼를 만들어두면 편하다:
```python
def guess_key_len(ciphertext: bytes, known_pt: bytes, candidate_lens):
    for klen in candidate_lens:
        if klen < len(known_pt):
            continue  # 알려진 평문보다 짧은 키는 이 방법으로 검증 불가
        key = bytes(c ^ p for c, p in zip(ciphertext[:len(known_pt)], known_pt))
        # klen이 known_pt보다 길면 나머지 키 바이트는 아직 모름 -> 앞부분만으로 부분 검증
        print(klen, key)
```

**5) 전체 복호화**

키가 확정되면 브루트포스 없이 전체 암호문에 키를 반복 적용해서 바로 평문 전체를 얻는다.

```python
known_pt = b"flag{"
ciphertext = bytes.fromhex("435C8E8BDB...")  # 실제로는 전체 비교 대상 바이트
key = bytes(c ^ p for c, p in zip(ciphertext[:len(known_pt)], known_pt))
print(key.hex())   # 2530efeca0

# 키가 반복된다고 확인되면 전체 복호화
full_pt = bytes(c ^ key[i % len(key)] for i, c in enumerate(ciphertext))
print(full_pt)
```

## 명령어/단축키
```python
# 빠른 수동 확인
print(hex(0x43 ^ 0x66))  # 0x25
```
IDA: `.rodata` 배열 위에서 `Alt+B`(Hex View 이동), `D`(데이터로 변환), 배열 크기가 명확하지 않으면 `Array`(`*`) 명령으로 전체 범위를 지정해 한 번에 바이트를 확인한다.

## 출력 해석
- 복호화 결과 앞부분이 정확히 `flag{`로 나오면 키 계산이 맞다는 뜻이고, 그 뒤로 이어지는 바이트들이 사람이 읽을 수 있는 문자로 보이면 반복 키 길이도 맞다는 신호다.
- 뒷부분이 깨진 문자로 나오면 키 길이가 5가 아니라 다른 값(예: 8, 16)일 가능성이 크므로, 더 긴 길이로 다시 XOR을 시도해봐야 한다.

## 흔한 실수
- 모든 문제가 정확히 소문자 `flag{`로 시작한다고 가정하는 것 — 실제로는 `FLAG{`, `flag_`, 또는 `dreamhack{`, `ctf{`처럼 대회마다 고유한 접두사를 쓴다. 반드시 문제 설명이나 바이너리의 비교 대상 상수(REV-0215의 룩업 테이블/상수 추출 기법 참고)에서 정확한 접두사 바이트를 확인해야 한다 — 대소문자 하나만 틀려도 복구한 키 전체가 무의미해진다.
- 변환이 바이트별 독립 XOR이 아닌데도 이 기법을 억지로 적용하려는 것 — 해시, 블록암호, REV-0217의 행렬/중첩루프 변환처럼 출력 바이트 하나가 입력 여러 바이트에 동시에 의존하는 구조에서는 "암호문 바이트 하나 XOR 평문 바이트 하나"로 키를 분리해낼 수 없다. 이런 경우 알려진 접두사/접미사는 여전히 유용하지만(문자셋·길이를 좁히거나, 브루트포스 도중 첫 바이트가 틀리면 바로 가지치기하는 용도), 대수적으로 키를 바로 뽑아내는 건 불가능하다.
- 문자셋을 좁히는 이득을 과소평가하는 것 — 아래 예제 2에서 보듯 형식을 아는 것만으로 브루트포스 시간이 몇 자릿수씩 줄어든다.

## 막혔을 때 다음 체크
- 변환이 XOR이 아니라 다른 연산(덧셈, 곱셈, 룩업테이블)일 수 있다면 → rev-0221-is-it-invertible.md에서 연산 종류부터 다시 분류.
- 형식은 알지만 길이를 모른다면 → rev-0218-length-check-backtrace.md에서 길이 검증 코드를 먼저 역추적.
- 형식 힌트로 좁힌 뒤에도 브루트포스가 필요하다면 → rev-0219-bruteforce-feasibility.md에서 정확히 몇 초/몇 분이 걸리는지 계산.

## 미니 예제

**예제 1 — 알려진 접두사로 XOR 키 직접 계산 (위 절차 그대로)**

암호문 `43 5C 8E 8B DB`와 평문 `flag{`를 XOR하면 키는 `25 30 EF EC A0`이다. 계산을 다시 검산해보면: `0x43=01000011`, `0x66=01100110`, XOR하면 `00100101=0x25` — 맞다. 나머지 네 바이트도 같은 방식으로 `0x30, 0xEF, 0xEC, 0xA0`이 나온다. 이 5바이트가 반복 키라면 브루트포스 0회로 전체 플래그를 복원할 수 있다.

**예제 2 — 형식만으로 문자셋을 좁혔을 때의 효과**

플래그 형식이 `flag{` + 16진수 문자 8개(`0-9a-f`) + `}`로 확인됐다고 하자. 미지수는 문자셋 16, 길이 8이므로 `16^8`을 계산한다. `16^4 = 65536`이고 `16^8 = 65536^2 = 4,294,967,296`이다(이 값은 정확히 `2^32`와 같다 — `16=2^4`이고 `4×8=32`이기 때문이다). 초당 10^8회를 시도하는 최적화된 브루트포스라면 `4,294,967,296 / 100,000,000 ≈ 42.9`초로 사실상 즉시 끝난다. 순수 파이썬 10^6회/초 기준이라도 `4,294,967,296 / 1,000,000 ≈ 4,295`초, 약 71.6분으로 CTF 시간 안에 충분히 시도해볼 만하다.

같은 길이 8을 형식 힌트 없이 인쇄 가능 문자 95종으로 브루트포스했다면 어땠을지 비교해보자. `95^8`을 계산하면 `95^2=9025`, `95^4=9025^2=81,450,625`, `95^8=81,450,625^2=6,634,204,312,890,625`(약 6.63×10^15)이다. 이 경우는 초당 10^8회여도 `6.63×10^15/10^8 ≈ 6.63×10^7`초, 약 2.1년이 걸려 사실상 불가능하다. 문자셋을 95에서 16으로 좁힌 것만으로 소요 시간이 약 11자릿수(10^11배 이상) 줄어든 것이다 — 형식 힌트 하나가 이 정도의 차이를 만든다.

**예제 3 — 두 기법을 합치는 최선의 경우**

플래그 전체 길이가 20바이트로 확인됐고(REV-0218), 형식은 `flag{` + 알 수 없는 내용 14바이트 + `}`(5+14+1=20)라고 하자. 예제 1의 방식으로 앞 5바이트 `flag{`에서 반복 키 5바이트를 이미 복구했다면, 그 키를 나머지 14바이트에도 그대로 XOR 적용하면 된다 — 이 14바이트에 대해서는 브루트포스가 전혀 필요 없다. 이것이 기지평문 공격의 이상적인 결과다: 형식 힌트가 탐색 공간을 줄이는 데 그치지 않고, 변환이 바이트별 독립 연산이라면 탐색 자체를 완전히 제거해버린다.

## 출처/검증
- 기지평문 공격(known-plaintext attack)의 고전적 정의와 반복 키 XOR(스트림 암호류)에서의 적용: 고전 암호학 교재 수준의 표준 개념, Vigenère/스트림 암호 키 복구 기법과 동일한 원리 (2026-09-08 검증).
- CTF 플래그 형식 관례(`flag{...}`, 대회별 접두사): 다수 CTF 대회 운영 관례 기준 일반 지식.
