## 한 줄 요약
파이썬으로 재구현한 알고리즘이 "몇 개 입력을 넣어보니 맞더라"는 감으로 끝나면 나중에 엣지 케이스(빈 문자열, 최대 길이, 특수 바이트)에서 조용히 틀린 채로 넘어가기 쉬우므로, 실제 바이너리에서 뽑아낸 입출력 쌍을 `pytest` 테스트 케이스로 고정해두고 경계값·회귀 테스트까지 갖추는 습관이 재구현 신뢰도를 실질적으로 높인다.

## 언제 검색해야 하나
- 재구현한 파이썬 함수가 "이번 입력은 맞는데 저번 입력은 틀렸다"처럼 일관성 없는 결과를 낼 때
- REV-0911(다단계 파이프라인)처럼 여러 단계를 합친 재구현에서 어느 단계가 문제인지 빠르게 좁히고 싶을 때
- 재구현 코드를 수정한 뒤 "이전에 맞았던 케이스가 여전히 맞는지"를 매번 손으로 재확인하기 귀찮을 때
- 빈 입력, 길이 1, 최대 길이, non-ASCII 바이트 같은 경계 상황에서 재구현이 실제 바이너리와 같은 동작을 하는지 확신이 없을 때

## 핵심 개념

### 왜 "한 번 맞으면 끝"이 위험한가
알고리즘 재구현에서 가장 흔한 실패 패턴은 평범한 입력(짧은 영문 소문자 문자열 등) 하나로만 검증하고 "재구현 완료"라고 결론짓는 것이다. 하지만 많은 버그가 다음과 같은 경계 조건에서만 드러난다.

- 빈 문자열(`b""`) — 루프가 0번 도는 경우 초기값 처리가 맞는지
- 길이 1인 입력 — 인덱스 `i-1`, `i+1`을 참조하는 코드에서 경계 밖 접근이 발생하는지
- 최대 길이 근처 — 버퍼 크기, 오버플로 처리 로직이 맞는지
- non-ASCII 바이트(0x80 이상) — 부호 있는 `char`로 처리되어 음수로 확장되는 경우(REV-0206)를 재구현에서 놓쳤는지
- 알고리즘의 "특수 상수"에 해당하는 입력(예: 다항식 해시에서 곱셈 결과가 정확히 오버플로 경계에 걸리는 값)

이런 경계 조건은 우연히 고른 테스트 문자열 하나로는 절대 드러나지 않는다. 유닛 테스트로 이런 케이스를 명시적으로 나열해두면 재구현의 숨은 결함을 훨씬 빨리 찾을 수 있다.

### 테스트 케이스는 어디서 얻는가 — 실제 바이너리가 정답 오라클
재구현이 맞는지 판단하는 기준(oracle)은 항상 실제 바이너리 자신이다. GDB에서 검증 함수에 브레이크포인트를 걸고, 여러 입력에 대해 함수를 직접 호출(`call`) 하거나 자연스럽게 실행되도록 유도해 반환값을 기록하면, 이것이 곧 "정답이 확실한" 테스트 케이스가 된다. `gdb`의 `call` 명령이나 pwntools로 프로세스를 실행해 stdout을 캡처하는 방법 모두 가능하다.

```
(gdb) call (int)check("hello", 5)
$1 = 0
(gdb) call (int)check("flag{test}", 10)
$2 = 1
```

이렇게 얻은 (입력, 예상 출력) 쌍을 pytest 테스트 함수로 고정해두면, 재구현 코드를 아무리 리팩터링해도 이 쌍들이 깨지지 않는 한 안전하다고 믿을 수 있다.

### pytest로 구조화하기
파이썬 표준 테스트 프레임워크인 `pytest`(또는 표준 라이브러리 `unittest`)를 쓰면 여러 케이스를 짧고 명확하게 관리할 수 있다. CTF 리버싱처럼 일회성 스크립트가 많은 상황에서도, 재구현 함수 하나가 여러 단계로 복잡해지면 이 정도의 구조화는 시간을 절약해준다.

```python
import pytest
from solve import check  # 재구현한 함수

CASES = [
    (b"", False),                     # 빈 입력 경계값
    (b"a", False),                    # 길이 1 경계값
    (b"flag{test}", True),            # 실제 바이너리에서 확인한 정상 케이스
    (b"\xff\xfe\x00", False),         # non-ASCII / 널 바이트 포함
]

@pytest.mark.parametrize("data,expected", CASES)
def test_check(data, expected):
    assert check(data) == expected
```

`pytest.mark.parametrize`를 쓰면 케이스 하나를 추가할 때마다 함수를 새로 안 써도 되고, 실패한 케이스만 명확히 리포트되어 어떤 입력에서 재구현이 틀렸는지 즉시 알 수 있다.

### 회귀 테스트로서의 가치
다단계 파이프라인(REV-0911)을 분석하다 보면 코드를 계속 수정하게 된다 — 처음엔 XOR인 줄 알았는데 나중에 룩업 테이블이었다는 걸 알게 되어 로직을 바꾸는 식이다. 이때 이미 확보해둔 테스트 케이스들을 다시 실행하기만 하면, 수정한 코드가 이전에 맞았던 케이스를 실수로 깨뜨렸는지(회귀, regression) 즉시 알 수 있다. 손으로 매번 재확인하는 것보다 훨씬 빠르고 안전하다.

## 화면/코드에서 보이는 징후
- 재구현 코드를 손으로 몇 번 테스트했는데 실행할 때마다 다른 결과가 나오거나, 코드를 수정할 때마다 이전에 맞았던 게 확실한지 불안한 상태
- 검증 함수가 여러 단계(REV-0911)로 이루어져 있어 어느 단계에서 결함이 생겼는지 특정하기 어려움
- 실제 바이너리를 GDB로 여러 번 실행해서 입출력을 얻었지만 이 결과들을 어디에도 기록해두지 않고 매번 다시 실행해서 눈으로 비교하는 중

## 가장 먼저 할 것
GDB로 실제 검증 함수를 최소 5~10개의 서로 다른 입력(정상 케이스 몇 개, 경계값 몇 개)에 대해 실행해 (입력, 출력) 쌍을 확보한다. 이 쌍들을 파이썬 리스트나 pytest 파라미터 목록으로 즉시 코드에 옮겨 적는다.

## 단계별 절차
1. 재구현 대상 함수의 입력 형태(바이트 문자열, 정수, 구조체 등)와 출력 형태(bool, 정수 반환값 등)를 확정한다.
2. GDB `call` 명령이나 pwntools 자동화로 실제 바이너리에서 최소 5개 이상의 (입력, 출력) 쌍을 수집한다 — 정상 케이스뿐 아니라 빈 입력, 길이 1, 최대 길이, non-ASCII 바이트를 반드시 포함한다.
3. 수집한 쌍을 `pytest.mark.parametrize` 목록으로 코드에 고정한다.
4. 재구현 함수를 작성하고 `pytest -v`로 전체 테스트를 실행해 몇 개가 실패하는지 확인한다.
5. 실패한 케이스가 있으면 그 입력만 따로 GDB로 다시 스텝 실행하며 재구현과 실제 동작이 어디서 갈라지는지 비교한다.
6. 모든 테스트가 통과하면, 이후 코드를 리팩터링하거나 REV-0911처럼 파이프라인을 합칠 때도 같은 테스트 스위트를 반복 실행해 회귀를 방지한다.

## 명령어/단축키
```bash
pip install pytest
pytest -v test_solve.py
pytest -v test_solve.py -k "boundary"   # 이름에 boundary가 들어간 케이스만 실행
```
```
# GDB에서 실제 검증 함수를 직접 호출해 정답 오라클 확보
(gdb) break *0x<check함수주소>
(gdb) run
(gdb) call (int)check("candidate_string", 16)
```

## 출력 해석
- `pytest -v` 실행 결과 모든 케이스에 `PASSED`가 뜨면 재구현이 최소한 수집한 테스트 케이스 범위 안에서는 정확하다는 뜻이다.
- 특정 케이스만 `FAILED`가 뜨면 pytest가 자동으로 `assert` 좌우 값을 출력해주므로, 재구현 결과와 기대값이 정확히 어떻게 다른지 바로 확인할 수 있다.
- 경계값 케이스(빈 입력, 길이 1)에서만 실패한다면 루프 초기화나 인덱스 처리 부분에 결함이 있을 가능성이 크고, 정상 케이스에서도 실패한다면 핵심 변환 로직 자체(상수, 연산 순서)를 다시 봐야 한다.

## 흔한 실수
- 테스트 케이스를 정상적인 입력 한두 개로만 구성하고 "충분하다"고 판단하는 것 — 경계값을 포함하지 않으면 숨은 버그를 놓친다.
- 테스트 케이스의 기대값을 실제 바이너리가 아니라 재구현 코드 자신의 출력으로 채우는 것 — 이러면 재구현이 처음부터 틀렸어도 테스트가 항상 통과하는 무의미한 테스트가 된다. 기대값은 반드시 실제 바이너리 실행 결과에서 얻어야 한다.
- 테스트를 한 번 통과시켜 놓고 이후 코드를 수정할 때 테스트를 다시 안 돌려서 회귀를 놓치는 것.
- 모든 로직을 한 개의 거대한 `test_all()` 함수에 넣어 하나라도 실패하면 전체가 실패로 뭉뚱그려지는 것 — `parametrize`로 케이스별로 분리해야 어디가 실패했는지 바로 보인다.

## 막혔을 때 다음 체크
- 재구현이 여러 단계로 나뉘어 있어 어느 단계 테스트부터 시작해야 할지 모르겠다면 → REV-0911 여러 알고리즘이 순차적으로 합성된 문제 풀어내기
- 테스트를 다 통과했는데도 최종적으로 원본과 완전히 동일한지 더 엄격하게 검증하고 싶다면 → REV-0919 알고리즘 복원 결과를 원본과 바이트 단위로 비교 검증하기
- GDB에서 함수를 직접 호출하는 방법 자체가 익숙하지 않다면 → REV-0657 gdb finish로 반환값 확인하기, REV-0656 gdb python 스크립팅 기초
- 부호 있는 문자 확장 때문에 경계값에서 결과가 갈리는 것 같다면 → REV-0206 음수 상수를 Unsigned Hex로 다시 읽기

## 미니 예제
REV-0906의 다항식 해시 재구현을 유닛 테스트로 감싸보자.

```python
# solve.py
def poly_hash(s: bytes, base=31, mod=2**32, init=0) -> int:
    h = init
    for c in s:
        h = (h * base + c) % mod
    return h
```

```python
# test_solve.py
import pytest
from solve import poly_hash

# GDB로 실제 바이너리에서 확보한 (입력, 기대 해시값) 쌍이라고 가정
CASES = [
    (b"", 0),                      # 빈 입력 -> 초기값 그대로
    (b"a", 97),                    # 길이 1 -> h = 0*31+97 = 97
    (b"ab", 3105),                 # 97*31+98 = 3007+98 = 3105
    (b"hello", 99162322),          # 정상 케이스
]

@pytest.mark.parametrize("data,expected", CASES)
def test_poly_hash(data, expected):
    assert poly_hash(data) == expected
```

이렇게 구성해두면 `poly_hash` 구현을 나중에 최적화하거나 다른 파이프라인 단계와 합치더라도, `pytest test_solve.py`를 실행하는 것만으로 이전에 확인했던 모든 케이스가 여전히 맞는지 몇 초 안에 확인할 수 있다.

## 관련 글

- REV-0919 — 알고리즘 복원 결과를 원본과 바이트 단위로 비교 검증하기
- REV-0657 — GDB에서 함수 반환값을 finish로 확인하는 법

- REV-0206 — 음수 상수를 Unsigned Hex로 다시 읽기

## 출처/검증
- `pytest.mark.parametrize`를 이용한 테스트 케이스 관리와 경계값 테스트(boundary value testing) 원칙: pytest 공식 문서 및 소프트웨어 테스팅의 표준 경계값 분석 기법 기준.
- GDB `call` 명령으로 실행 중인 프로세스의 함수를 직접 호출해 결과를 얻는 방법: GDB 공식 문서(Calling Program Functions) 기준 (2026-09-09 검증).
