## 한 줄 요약
실전 크랙미는 길이 제약, 문자셋 제약, known-plaintext, 구조적 힌트(체크섬, 접두사/접미사) 같은 여러 게이트(gate) 조건이 동시에 걸려 있는 경우가 많으며, 이 조건들을 하나씩 순서대로(가장 싸고 강력한 조건부터) 적용해 탐색 공간을 곱셈적으로 줄여나가는 절차 자체가 하나의 재사용 가능한 워크플로우다.

## 언제 검색해야 하나
- REV-0218(길이), REV-0223(known-plaintext) 등 개별 narrowing 기법은 알고 있는데, 여러 조건이 동시에 걸린 실전 문제에서 이들을 어떤 순서로 어떻게 조합해야 할지 막막할 때
- 조건을 하나 적용했는데도 탐색 공간이 여전히 브루트포스하기엔 너무 클 때, 다른 조건을 더 찾아내야 하는지 판단이 안 설 때
- 여러 조건을 조합하는 과정에서 실수로 조건 일부를 놓치거나 중복 적용해서 답이 하나도 안 나오거나(제약이 모순) 너무 많이 나오는(제약이 부족한) 상황일 때

## 핵심 개념

### narrowing은 집합의 교집합이다
입력 공간 좁히기는 결국 집합론이다. 전체 가능한 입력의 집합을 `U`라 하면, 각 조건(게이트) `G1, G2, ..., Gn`은 각각 `U`의 부분집합을 정의하고, 최종적으로 남는 답의 집합은 이 모든 부분집합의 교집합이다.

```
Answer ⊆ G1 ∩ G2 ∩ ... ∩ Gn
```

교집합의 크기는 부분집합 중 어느 하나보다도 절대 크지 않으므로, 조건을 하나씩 더 찾아 추가할 때마다 탐색 공간은 줄어들거나 그대로 유지될 뿐 절대 늘어나지 않는다. 이 성질 때문에 "일단 찾을 수 있는 조건은 다 찾아서 교집합을 구하는 것"이 항상 이득이 되는 전략이다.

### 실전 게이트의 종류와 비용 순서
게이트는 종류에 따라 "적용 비용"(분석에 드는 시간)과 "좁히는 힘"(탐색 공간을 얼마나 줄여주는지)이 다르다. 다음 순서로 적용하는 것이 효율적이다.

1. **길이 제약(REV-0218)**: 가장 싸다. 버퍼 크기, 길이 비교 코드 한 곳만 찾으면 되고, 지수 `n`을 확정 짓기 때문에 좁히는 힘도 크다.
2. **문자셋 제약**: 입력 문자마다 `isalpha`, `isdigit`, 특정 범위 체크가 있는지 확인. 있다면 밑(charset_size)을 95에서 26이나 16으로 줄여준다(REV-0219 예제와 동일한 효과).
3. **known-plaintext(REV-0223)**: 있다면 가장 강력하다 — 대수적으로 가역인 단계라면 해당 구간의 탐색을 아예 제거해버린다.
4. **체크섬/검증합 조건**: 예를 들어 "전체 바이트의 합이 특정 값이어야 한다", "짝수 인덱스 바이트의 XOR이 0이어야 한다" 같은 부가 조건. 이런 조건은 개별 문자를 독립적으로 결정짓지는 못하지만, 전체 조합 중 일부를 즉시 제외시켜준다(브루트포스 루프 안에서 이런 조건을 먼저 검사하면 조기 종료로 실질 속도가 빨라진다).
5. **구조적 힌트(접두사/접미사 고정)**: `flag{`, `}` 같은 고정된 부분은 아예 미지수에서 빼버릴 수 있다 — 이것도 known-plaintext의 일종이지만 형식만으로도(내용을 몰라도) 적용 가능한 경우가 있다.

### 조건을 순서대로 적용하는 실전 절차
게이트를 하나씩 적용할 때마다 남은 탐색 공간을 REV-0219 공식으로 즉시 재계산하고, 이 값을 계속 추적하는 것이 핵심이다.

```python
def track_narrowing(charset_size, length, rate=1e8, budget=3600):
    keyspace = charset_size ** length
    seconds = keyspace / rate
    print(f"charset={charset_size}, length={length}, "
          f"keyspace={keyspace:.3e}, est_sec={seconds:.1f}, "
          f"feasible={seconds <= budget}")
    return keyspace, seconds

# 1단계: 아무 조건도 없을 때
track_narrowing(95, 20)
# 2단계: 길이가 20 -> 8로 확정(REV-0218)
track_narrowing(95, 8)
# 3단계: 문자셋이 hex로 확정(REV-0913/코드 관찰)
track_narrowing(16, 8)
# 4단계: known-plaintext로 앞 4바이트가 이미 확정(REV-0223) -> 미지 길이 4로 축소
track_narrowing(16, 4)
```

이렇게 각 단계마다 수치를 눈으로 확인하면서 진행하면, "이제 브루트포스가 가능한 크기에 도달했다"는 시점을 정확히 판단할 수 있고, 어떤 조건이 가장 크게 기여했는지도 한눈에 파악된다.

### 조건들이 서로 모순되거나 중복되는지 검증하기
여러 조건을 코드에서 따로따로 뽑아내다 보면, 실수로 서로 모순되는 조건(예: 길이가 8이라고 뽑았는데 다른 곳에서는 길이가 6이라는 조건이 나옴)을 둘 다 채택하는 경우가 생긴다. 이 경우 교집합이 공집합이 되어 답이 하나도 안 나온다. 조건을 추가할 때마다 실제로 그 조건을 만족하는 예시가 최소 하나는 존재하는지(공집합이 아닌지) 작은 스크립트로 즉시 확인하는 습관이 중요하다.

## 화면/코드에서 보이는 징후
- 검증 함수 안에 길이 체크, 문자 범위 체크, 별도의 합계/체크섬 비교, 그리고 최종 해시 비교가 순서대로 나열되어 있음
- 한 조건만 적용해서는 REV-0219 계산 결과 여전히 며칠 이상 걸리는 규모로 나옴
- 여러 REV 문서(REV-0218, REV-0223 등)에서 각각 조건을 뽑았지만 이를 하나로 합치는 절차가 없어 무엇부터 브루트포스에 넣어야 할지 헷갈림

## 가장 먼저 할 것
검증 함수를 위에서 아래로 훑으며 "이것도 조건이다" 싶은 모든 체크(길이, 문자 범위, 합계, known-plaintext 가능 여부)를 빠짐없이 목록으로 뽑는다. 그 다음 각 조건을 비용이 싼 순서(길이 → 문자셋 → known-plaintext → 체크섬)로 정렬한다.

## 단계별 절차
1. 검증 함수 전체를 훑으며 모든 게이트 조건을 표로 나열한다(조건 종류, 어떤 변수/바이트에 적용되는지, 어디서 확인했는지).
2. 각 조건을 비용이 싼 순서로 정렬한다.
3. `track_narrowing()` 같은 헬퍼로 조건을 하나씩 적용하며 탐색 공간이 줄어드는 과정을 수치로 기록한다.
4. 각 조건이 서로 모순되지 않는지, 실제로 만족 가능한 예시가 있는지 작은 스크립트로 검증한다.
5. 남은 탐색 공간이 REV-0219/REV-0920 기준으로 실현 가능한 크기가 되면 브루트포스나 Z3(REV-0917로 축소한 뒤)로 넘긴다.
6. 실현 가능한 크기에 아직 못 미치면, 검증 함수를 다시 훑어 놓친 조건이 없는지(특히 체크섬처럼 눈에 잘 안 띄는 부가 조건) 재확인한다.

## 명령어/단축키
```python
def track_narrowing(charset_size, length, rate=1e8, budget=3600):
    keyspace = charset_size ** length
    seconds = keyspace / rate
    print(f"charset={charset_size}, length={length}, "
          f"keyspace={keyspace:.3e}, est_sec={seconds:.1f}, "
          f"feasible={seconds <= budget}")
    return keyspace, seconds

def check_satisfiable(constraints, sample_space):
    # 조건들이 모순되지 않는지 작은 후보군으로 사전 검증
    for candidate in sample_space:
        if all(c(candidate) for c in constraints):
            return candidate
    return None
```

## 출력 해석
- `track_narrowing()`을 단계별로 호출한 로그에서 `est_sec`이 급격히 줄어드는 지점이 있다면, 그 조건이 이번 문제에서 가장 강력한 게이트였다는 뜻이다 — 비슷한 유형의 문제를 다시 만나면 그 종류의 조건부터 먼저 찾는 게 효율적이다.
- `feasible=True`로 전환되는 시점이 곧 "이제 브루트포스로 넘어갈 타이밍"이다.
- `check_satisfiable()`이 `None`을 반환하면 조건들 중 일부가 서로 모순되거나, 조건 자체를 잘못 뽑았다는 뜻이므로 원본 코드를 재확인해야 한다.

## 흔한 실수
- 조건을 발견하는 순서 그대로(비용을 고려하지 않고) 적용해서, 비싼 분석(예: known-plaintext 확인)을 먼저 하고 싼 분석(길이 체크)을 나중에 하는 비효율.
- 체크섬처럼 "문자 하나하나를 결정짓지는 못하지만 조합 전체를 걸러내는" 조건의 가치를 과소평가해서 아예 안 찾아보는 것 — 이런 조건도 브루트포스 루프 안에서 조기 종료 조건으로 쓰면 상당한 속도 향상을 준다.
- 여러 조건을 합칠 때 모순 여부를 확인하지 않고 브루트포스를 몇 시간 돌렸다가 답이 하나도 안 나오는 것을 뒤늦게 알아채는 것.
- narrowing이 아직 부족한데도 "이 정도면 됐겠지"라고 성급하게 브루트포스에 들어가 몇 시간을 낭비하는 것 — 진행 전 반드시 REV-0219/REV-0920 계산으로 예상 시간을 확인해야 한다.

## 막혔을 때 다음 체크
- 길이 조건 뽑는 법이 기억 안 나면 → REV-0218 길이 검증부터 역추적하는 법
- known-plaintext 적용법이 기억 안 나면 → REV-0223 Known plaintext와 Flag 형식으로 조건 줄이기
- known-plaintext가 아예 없는 상황이라면 → REV-0913 Known-plaintext 없이 알고리즘 성질만으로 역산 가능성 판단하기
- narrowing 후에도 Z3로 넘겨야 한다면 → REV-0917 Z3로 풀기 전에 손으로 먼저 검증 로직 축소하기
- 최종적으로 브루트포스 가능 여부를 정확히 판단하려면 → REV-0219 Brute Force가 가능한 입력 공간 계산, REV-0920 시간 복잡도로 브루트포스 가능 여부 판단하는 실전 기준

## 미니 예제
어떤 크랙미의 검증 함수를 분석해 다음 조건들을 순서대로 발견했다고 하자.

```python
# 발견한 게이트 조건 목록 (비용 오름차순으로 이미 정렬)
# 1) 길이는 정확히 12바이트 (REV-0218)
# 2) 모든 문자는 소문자 또는 숫자 (charset=36)
# 3) 앞 5바이트는 known-plaintext로 이미 "flag{" 확정 (REV-0223)
# 4) 마지막 바이트는 반드시 "}" (구조적 힌트로 확정)

track_narrowing(95, 12)   # 아무 조건 없을 때: 도저히 불가능한 크기
track_narrowing(36, 12)   # 문자셋만 좁혔을 때
track_narrowing(36, 12 - 5 - 1)  # known-plaintext + 접미사 확정 후 미지 길이 6
```

각 단계 출력(예시 수치, 10^8/s 가정):
```
charset=95, length=12, keyspace=5.404e+23, est_sec=5.404e+15, feasible=False
charset=36, length=12, keyspace=4.739e+18, est_sec=4.739e+10, feasible=False
charset=36, length=6,  keyspace=2.176e+09, est_sec=21.8,      feasible=True
```

문자셋 축소만으로는 여전히 불가능한 규모였지만, known-plaintext와 구조적 힌트로 미지 길이를 12에서 6으로 줄이자 21.8초로 완전히 실현 가능한 규모가 되었다. 이처럼 여러 조건의 교집합 효과는 개별 조건 하나의 효과를 단순히 더한 것이 아니라 곱셈적으로 누적된다는 것이 실전에서 가장 중요하게 체감되는 지점이다.

## 관련 글
- REV-0218 — 길이 검증부터 역추적하는 법
- REV-0223 — Known plaintext와 Flag 형식으로 조건 줄이기
- REV-0219 — Brute Force가 가능한 입력 공간 계산
- REV-0913 — Known-plaintext 없이 알고리즘 성질만으로 역산 가능성 판단하기
- REV-0917 — Z3로 풀기 전에 손으로 먼저 검증 로직 축소하기
- REV-0920 — 시간 복잡도로 브루트포스 가능 여부 판단하는 실전 기준

## 출처/검증
- 여러 제약 조건의 교집합이 개별 조건보다 항상 작거나 같다는 성질: 집합론의 기본 정리(교집합은 부분집합 관계) 기준.
- 게이트 조건을 비용 순서로 정렬해 적용하는 것이 탐색 효율을 높인다는 원칙: 제약 만족 문제(Constraint Satisfaction Problem)에서 저렴한 제약을 먼저 적용해 탐색 공간을 조기에 줄이는 일반적인 알고리즘 설계 관행(제약 전파, constraint propagation) 기준 (2026-09-09 검증).
