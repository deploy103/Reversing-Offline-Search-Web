## 한 줄 요약
실전 CTF 크랙미는 XOR 하나, 해시 하나처럼 단일 기법으로 끝나는 경우보다 여러 알고리즘이 파이프라인처럼 순서대로 이어지는 경우가 더 흔하며, 이런 문제는 "한 방에" 역산하려 하지 말고 각 단계의 경계(중간 결과가 다음 함수로 넘어가는 지점)를 먼저 찾아 단계별로 분리한 다음, 마지막 단계부터 거꾸로 하나씩 역산해 올라가는 것이 핵심 전략이다.

## 언제 검색해야 하나
- 메인 검증 함수 안에서 서로 성격이 다른 변환 함수(예: XOR 루프 함수 하나, 테이블 치환 함수 하나, 해시 함수 하나)가 순서대로 호출되고, 앞 함수의 반환값/출력 버퍼가 다음 함수의 입력으로 그대로 들어갈 때
- REV-0199(XOR 역산)나 REV-0215(테이블 역산) 같은 단일 기법으로 역산을 시도했는데 결과가 사람이 읽을 수 있는 문자열로 나오지 않을 때
- 함수 호출 그래프(Ghidra의 Function Call Graph, IDA의 Xrefs)를 보면 검증 로직이 한 함수가 아니라 3~5개 함수가 체인처럼 연결된 형태로 보일 때
- "이 문제는 여러 암호 기법을 조합했다"는 문제 설명이나 태그가 있을 때

## 핵심 개념

### 합성 함수로 보기
다단계 검증은 수학적으로 함수 합성(function composition)이다. 입력 `x`가 있을 때, 검증은 다음과 같이 진행된다.

```
stage1_out = f1(x)
stage2_out = f2(stage1_out)
stage3_out = f3(stage2_out)
result = (stage3_out == TARGET)
```

역산의 핵심 원리는 간단하다 — **합성의 역은 순서를 뒤집은 역함수들의 합성이다.**

```
x = f1^-1( f2^-1( f3^-1( TARGET ) ) )
```

즉 각 단계의 역함수 `f1^-1`, `f2^-1`, `f3^-1`을 개별적으로 구할 수만 있다면, `TARGET`에서 시작해 마지막 단계부터 거꾸로 하나씩 역함수를 적용하며 올라가면 원래 입력 `x`를 복원할 수 있다. 이것이 단일 알고리즘 역산(REV-0199, REV-0215 등)과 다단계 문제의 근본적인 차이다 — 다단계 문제는 "역산 기법 하나를 완벽히 아는 것"보다 "단계를 정확히 나누고 순서를 관리하는 것"이 더 중요하다.

### 모든 단계가 가역인 것은 아니다
파이프라인 중 한 단계라도 비가역(다항식 해시, FNV 같은 단방향 해시)이면, 그 지점부터 위쪽으로는 대수적 역산이 불가능해진다. 이 경우 전략이 바뀐다.

- 비가역 단계가 파이프라인의 **마지막**에 있다면(예: XOR으로 변환 → 그 결과를 해시로 압축 → 해시값 비교): 최종 비교는 해시값이므로, 해시 앞 단계(XOR)의 결과 자체가 무한히 많은 후보를 가질 수 있어 유일한 원문 복원이 불가능할 수 있다. 이 경우 REV-0219(브루트포스 가능성 계산)로 남은 탐색 공간이 감당 가능한지부터 확인한다.
- 비가역 단계가 파이프라인의 **중간**에 있다면(예: 입력 → 해시로 압축 → 그 해시값을 다시 XOR로 변환 → 비교): 마지막 XOR은 쉽게 역산되어 해시값을 복원할 수 있지만, 그 해시값에서 원래 입력을 되돌리는 건 여전히 불가능하다. 이때는 REV-0913처럼 known-plaintext나 알고리즘 성질을 이용한 우회가 필요하다.

### 단계 경계를 찾는 실전 방법 — 중간값을 직접 관찰
정적 분석만으로 단계 경계를 나누기 애매하면, GDB/x64dbg로 각 함수의 반환 직후 버퍼 상태를 덤프해서 눈으로 확인하는 게 가장 빠르고 확실하다. 함수 A가 끝나는 지점에 브레이크포인트를 걸고 출력 버퍼를 `x/20xb $rdi` 같은 명령으로 찍어보면, "이 지점까지는 사람이 읽을 수 있는 문자열이었는데 다음 함수를 지나니 난수처럼 바뀌었다"는 식으로 단계 경계가 명확히 드러난다.

### 각 단계를 독립적으로 검증한 뒤 합치기
다단계 문제를 풀 때 흔히 저지르는 실수는 전체 파이프라인을 한 번에 재구현하고 한 번에 테스트하는 것이다. 대신 각 단계(`f1`, `f2`, `f3`)를 개별 파이썬 함수로 만들고, 각 함수를 실제 바이너리의 중간값과 개별적으로 비교해 정확성을 검증한 다음에 전체를 합치는 것이 디버깅하기 훨씬 쉽다. 한 단계씩 검증하면 어디서 틀렸는지 즉시 알 수 있지만, 전체를 한 번에 합쳐서 틀리면 어느 단계가 문제인지 찾기 위해 다시 각 단계를 분리해야 하는 이중 작업이 발생한다.

## 화면/코드에서 보이는 징후
- 메인 검증 함수의 디스어셈블리/디컴파일에 성격이 다른 이름 없는 서브함수(`sub_401200`, `sub_401350`, `sub_4014A0`)가 순서대로 호출됨
- 한 함수의 리턴값 레지스터(`eax`/`rax`)나 출력 버퍼 포인터가 다음 함수의 첫 인자로 그대로 전달됨
- Ghidra의 Function Call Graph에서 검증 함수 아래로 체인 형태(가지치기 없이 일렬로 이어지는 모양)의 호출 구조가 보임
- 단일 역산 기법을 적용했는데 결과 바이트가 아스키 범위를 벗어나거나 무작위처럼 보임

## 가장 먼저 할 것
메인 검증 함수의 호출 그래프를 그려서(Ghidra Function Call Graph, IDA에서 Xrefs 따라가며 수동 스케치) 몇 개의 서브함수가 몇 번 호출되는지, 어떤 순서로 데이터가 흘러가는지부터 확정한다. 이 지도 없이 바로 역산에 들어가면 중간에 길을 잃기 쉽다.

## 단계별 절차
1. 메인 검증 함수를 읽고 서브함수 호출 순서를 `f1 -> f2 -> f3 -> compare` 형태로 도식화한다.
2. 각 서브함수 경계에서 GDB로 중간 버퍼 값을 실제로 덤프해 몇 바이트가 어떻게 변하는지 확인한다.
3. 각 서브함수를 개별적으로 분석해 REV-0196~0217 등 이미 알려진 패턴 중 어디에 해당하는지 분류한다.
4. 각 서브함수를 독립적인 파이썬 함수로 재구현하고, 2단계에서 얻은 실제 중간값과 개별 비교해 정확성을 검증한다.
5. 검증된 파이썬 함수들을 순서대로 이어붙여 전체 파이프라인을 완성한다.
6. 마지막 단계부터 거꾸로 역함수를 적용할 수 있는지 확인하고, 안 되는 단계가 있으면 REV-0913/REV-0219 전략으로 전환한다.

## 명령어/단축키
```python
def f1(x: bytes) -> bytes:
    return bytes(b ^ 0x5A for b in x)          # 예: 첫 단계는 상수 XOR

def f2(x: bytes) -> bytes:
    table = [0x63, 0x7C, 0x77, 0x7B]            # 예: 두 번째 단계는 룩업 테이블(REV-0215)
    return bytes(table[b % len(table)] for b in x)

def f3(x: bytes) -> int:
    h = 0
    for c in x:
        h = (h * 31 + c) & 0xFFFFFFFF           # 예: 세 번째 단계는 다항식 해시(REV-0906, 비가역)
    return h

def pipeline(x: bytes) -> int:
    return f3(f2(f1(x)))

print(hex(pipeline(b"testcase")))
```
GDB로 단계 경계 관찰:
```
break *0x<f1_ret_addr>
break *0x<f2_ret_addr>
run
x/16xb $rdi     # 각 지점에서 중간 버퍼 확인
```

## 출력 해석
- 각 단계의 파이썬 재구현 결과가 GDB로 관찰한 실제 중간값과 정확히 일치하면 그 단계는 확정된 것이다.
- 마지막 단계가 다항식 해시처럼 비가역이면, `pipeline()` 전체를 거꾸로 풀 수는 없고 `f1`, `f2`의 역함수만 알아둔 채 REV-0219처럼 남은 탐색 공간(f1, f2를 거친 뒤에도 남는 문자셋과 길이)을 계산해 브루트포스 여부를 판단해야 한다.
- 한 단계라도 재구현 결과가 안 맞으면, 그 단계 서브함수를 다시 REV-0196~0223 패턴 목록과 대조해 분류를 잘못하지 않았는지 재확인한다.

## 흔한 실수
- 전체 파이프라인을 한 번에 통째로 역산하려다 어디서 틀렸는지 못 찾고 포기하는 것 — 반드시 단계별로 쪼개서 개별 검증해야 한다.
- 중간값을 GDB로 확인하지 않고 정적 분석 추측만으로 각 단계 경계를 나누는 것 — 특히 컴파일러가 함수를 인라인(inline)해버리면 정적으로는 단계 구분이 흐릿해질 수 있으므로 동적 관찰이 더 믿을 만하다.
- 파이프라인 중 하나의 단계가 비가역이라는 걸 확인하지 않고 "역산이 안 되네, 뭔가 잘못했나보다"라며 이미 맞게 구현한 다른 단계까지 의심하고 다시 뒤엎는 것.
- 단계 순서를 반대로 이어붙이는 것 — `f2(f1(x))`와 `f1(f2(x))`는 일반적으로 완전히 다른 결과를 낸다. 반드시 실제 호출 순서를 그대로 지켜야 한다.

## 막혔을 때 다음 체크
- 개별 단계가 어떤 패턴인지 분류가 안 될 때 → REV-0196~REV-0217 (strcmp/memcmp/XOR/테이블/셔플 등 개별 패턴 목록)
- 마지막 단계가 비가역인데 known-plaintext도 없다면 → REV-0913 Known-plaintext 없이 알고리즘 성질만으로 역산 가능성 판단하기
- 역산 후 남은 탐색 공간이 브루트포스로 감당되는지 궁금하면 → REV-0219 Brute Force가 가능한 입력 공간 계산, REV-0920
- 재구성한 전체 파이프라인이 실제 바이너리와 정확히 일치하는지 최종 검증하는 법이 궁금하면 → REV-0919, REV-0912

## 미니 예제
위 예제의 `pipeline()`이 실제로 `TARGET = 0x9F3A21B4`와 비교한다고 하자. `f3`(다항식 해시)이 비가역이므로, `f1`, `f2`를 거친 뒤의 값(`f2(f1(x))`)을 유일하게 복원할 수는 없다. 대신 `f1`, `f2`가 각각 정확히 재구현되었다는 전제 하에, 원래 입력 길이와 문자셋이 이미 알려져 있다면(REV-0218) 그 좁혀진 공간 안에서 `pipeline(candidate) == TARGET`을 만족하는 후보를 브루트포스로 찾는다.

```python
import itertools

TARGET = 0x9F3A21B4
charset = b"abcdefghijklmnopqrstuvwxyz"
length = 6

for combo in itertools.product(charset, repeat=length):
    candidate = bytes(combo)
    if pipeline(candidate) == TARGET:
        print("found:", candidate)
        break
```
길이 6, 문자셋 26이면 `26^6 ≈ 3.09×10^8`으로 REV-0219 기준 최적화된 환경에서 수 초~수십 초면 충분히 실현 가능한 크기다. 이렇게 "역산 가능한 단계는 역산하고, 안 되는 마지막 단계는 좁혀진 공간에서 브루트포스"하는 것이 다단계 문제의 현실적인 최종 전략이다.

### 완전한 예제 스크립트 — 파이프라인을 끝까지 실행하고 브루트포스로 검증까지
아래 스크립트는 앞서 나온 `f1`(XOR), `f2`(테이블 치환), `f3`(다항식 해시)을 다시 처음부터 정의하고, 실제로 `TARGET` 값을 계산한 뒤 브루트포스로 원문을 되찾는 과정을 전부 담고 있다. 파이썬 초보자도 그대로 복사해서 실행할 수 있다.

```python
import itertools  # 문자 조합을 순서대로 만들어주는 표준 라이브러리


def f1(x: bytes) -> bytes:
    # 1단계: 모든 바이트에 0x5A를 XOR한다 (REV-0199 참고)
    return bytes(b ^ 0x5A for b in x)


def f2(x: bytes) -> bytes:
    # 2단계: 각 바이트를 4칸짜리 테이블에서 치환한다 (REV-0215 참고)
    # 주의: 테이블 크기가 4뿐이라서 원래 256가지였던 값이 4가지로 줄어든다 -> 정보가 크게 손실된다
    table = [0x63, 0x7C, 0x77, 0x7B]
    return bytes(table[b % len(table)] for b in x)


def f3(x: bytes) -> int:
    # 3단계: 다항식 해시로 전체를 하나의 32비트 정수로 압축한다 (REV-0906 참고, 비가역)
    h = 0
    for c in x:
        h = (h * 31 + c) & 0xFFFFFFFF
    return h


def pipeline(x: bytes) -> int:
    # 실제 검증 함수와 동일한 순서로 세 단계를 이어붙인다: f1 -> f2 -> f3
    return f3(f2(f1(x)))


# 1) 원래 비밀 문자열이 있었다고 가정하고, 그 문자열의 pipeline() 결과를 TARGET으로 삼는다
#    (실전에서는 이 값을 어셈블리의 cmp 명령 상수에서 직접 읽어온다)
secret = b"ctf"
TARGET = pipeline(secret)
print("원래 비밀 문자열:", secret)
print("TARGET (실제로는 바이너리에 박혀 있는 값):", hex(TARGET))

# 2) TARGET만 안다고 가정하고, 길이 3짜리 소문자 조합을 전부 시도해서 pipeline(candidate) == TARGET을
#    만족하는 문자열을 찾는다. 문자셋과 길이는 REV-0218 방식으로 이미 좁혀뒀다고 가정한다.
charset = b"abcdefghijklmnopqrstuvwxyz"
length = 3
found = None
for combo in itertools.product(charset, repeat=length):  # 26 x 26 x 26 = 17,576가지 조합을 전부 만든다
    candidate = bytes(combo)          # combo는 정수 튜플이므로 바이트 문자열로 바꾼다
    if pipeline(candidate) == TARGET: # 파이프라인 결과가 TARGET과 같으면 정답 후보를 찾은 것
        found = candidate
        break                          # 하나 찾았으니 더 찾을 필요 없이 반복을 멈춘다

print("브루트포스로 찾은 문자열:", found)
print("원래 비밀 문자열과 같은가?:", found == secret)
```

실제로 실행하면 다음과 같이 출력된다.
```
원래 비밀 문자열: b'ctf'
TARGET (실제로는 바이너리에 박혀 있는 값): 0x1e048
브루트포스로 찾은 문자열: b'cdb'
원래 비밀 문자열과 같은가?: False
```

여기서 아주 중요한 교훈이 드러난다 — 브루트포스로 찾은 문자열 `b'cdb'`가 원래 비밀 문자열 `b'ctf'`와 **다르다**는 점이다. 원인은 `f2` 단계가 256가지 바이트를 4가지 값으로만 치환하는 손실 변환이기 때문이다 — 서로 다른 여러 입력이 `f2`를 거치면 같은 값이 되어버려서, 최종 `TARGET`도 여러 개의 서로 다른 입력에서 나올 수 있다. 즉 이 파이프라인은 앞서 배운 "출력이 입력보다 작아지는 단계가 있으면 유일한 원문 복원이 불가능하다"(REV-0913)는 원칙이 그대로 적용된 실제 사례다. CTF 정답 제출 시에는 브루트포스로 찾은 후보가 실제로 사람이 읽을 수 있는 의미 있는 문자열인지(예: `flag{...}` 형식에 맞는지) 추가로 확인해서 진짜 정답을 골라내야 한다.
