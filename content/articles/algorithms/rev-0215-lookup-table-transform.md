## 한 줄 요약
디스어셈블리에서 "입력값(또는 입력에서 파생된 값)을 인덱스로 삼아 고정 주소의 배열에서 값을 그대로 읽어오는" 코드가 보이면 **Lookup Table(LUT) 기반 변환**이며, 먼저 이 테이블이 CRC 같은 잘 알려진 알고리즘에서 자동 생성되는 것인지, 아니면 문제 제작자가 임의로 만든 것인지부터 구분해야 한다.

## 언제 검색해야 하나
- `movzx eax, byte [rax+off_140003000]`처럼 레지스터 값을 인덱스로 써서 고정 주소를 참조하는 명령어를 만났을 때
- Ghidra 디컴파일에서 `DAT_140003000[input[i]]` 같은 표현을 봤을 때
- `.rodata` 섹션에 256개(또는 그 배수) 크기의 정적 배열이 있고, 그 배열을 참조하는 함수가 검증/체크섬 루틴 근처에 있을 때
- REV-0214(커스텀 알파벳 치환)나 REV-0211(AES 흔적)을 읽었는데 좀 더 일반적인 "테이블을 봤을 때 뭘 해야 하나"가 궁금할 때

## 핵심 개념
Lookup Table 기반 변환은 "계산을 미리 해서 배열에 저장해두고, 실행 시점에는 계산 대신 배열 참조만 한다"는 아주 흔한 최적화/난독화 기법이다. 이 카테고리 안에는 성격이 매우 다른 두 종류가 섞여 있고, 이를 구분하는 것이 리버싱 시간을 크게 좌우한다.

**1) 알고리즘적으로 재생성 가능한 테이블 (다시 계산할 필요 없음)**

대표적인 예가 CRC32 테이블이다. CRC32는 다항식 나눗셈을 매 바이트마다 반복하면 느리기 때문에, 실무 구현체는 256개의 결과를 미리 계산해 테이블로 저장해두고 XOR과 시프트만으로 빠르게 처리한다. 이 테이블은 **CRC 다항식 하나로 완전히 결정**되므로, 바이너리에서 값을 일일이 뽑을 필요 없이 파이썬 표준 라이브러리로 대체할 수 있다.

표준 CRC-32(reflected, 다항식 `0xEDB88320`) 테이블의 앞부분은 다음과 같은 값으로 시작한다:
```
table[0] = 0x00000000
table[1] = 0x77073096
table[2] = 0xEE0E612C
table[3] = 0x990951BA
```
바이너리의 `.rodata`에서 리틀엔디언으로 `96 30 07 77 2C 61 0E EE ...` 같은 바이트열이 보인다면(이는 `0x77073096`, `0xEE0E612C`를 리틀엔디언으로 표기한 것) 이건 CRC32 테이블일 확률이 매우 높다. 이 경우 테이블을 뽑아 저장하는 대신 바로 `zlib.crc32()`를 쓰면 된다.

**2) 임의/불투명 테이블 (반드시 바이트 그대로 추출해야 함)**

문제 제작자가 직접 설계한 S-box나 셔플 키, 챌린지 전용 상수 테이블은 규칙이 없다. 이런 테이블은 지름길이 없고, **바이너리에서 바이트 하나하나를 그대로 뽑아내는 것 외에는 방법이 없다**. REV-0214(커스텀 알파벳 치환)가 바로 이 카테고리의 대표 사례이고, AES의 S-box([REV-0211](./rev-0211-aes-fingerprints.md))도 사실은 "잘 알려진 상수를 가진 불투명 테이블"이라는 점에서 이 카테고리에 속한다 — 다만 AES S-box는 워낙 유명해서 시작 바이트(`63 7C 77 7B ...`)만 보고도 바로 알아볼 수 있다는 차이가 있다.

## 화면/코드에서 보이는 징후
- 어떤 값도 더하거나 곱하지 않고, 그냥 `base + index * element_size` 형태의 주소 계산만으로 메모리를 읽는 명령어
  - 1바이트 원소: `movzx eax, byte [rcx+rax]`
  - 4바이트 원소(주로 CRC32 등): `mov eax, [rcx+rax*4]`
- IDA에서 그 주소로 이동하면 이름 없는 `unk_...`, `byte_...`, `dword_...` 레이블이 붙은 정적 배열이 있음
- 루프 안에서 테이블 참조 결과가 다시 다음 루프의 입력(누적 XOR 등)으로 쓰이는 경우 — CRC류 알고리즘의 전형적 패턴
- 테이블 참조가 두 번 연속 이어지는 경우(`output = TBL2[TBL1[input]]`) — 아래 "이중 LUT" 항목 참고

## 가장 먼저 할 것
테이블 참조 명령어를 발견하면, 가장 먼저 **테이블 크기와 원소 크기**를 확인한다(1바이트 원소 256개인지, 4바이트 원소 256개=1024바이트인지). 그다음 테이블의 시작 몇 개 값을 16진수로 적어두고, 아래 절차대로 "이거 CRC 같은 유명 알고리즘 아닌가?"부터 확인한다. 유명 알고리즘이면 표준 라이브러리로 바로 끝나고, 아니면 REV-0214와 같은 방식으로 전체를 추출해야 한다.

## 단계별 절차

**1) 테이블 원소 크기 확인**

인덱싱에 쓰인 곱셈 배수(`*1`, `*4`, `*8`)를 보고 원소가 1/4/8바이트인지 확정한다. IDA 디스어셈블리에서 `movzx`면 1바이트, 일반 `mov eax, [...]`면 4바이트일 가능성이 크다.

**2) 잘 알려진 상수인지 대조**

테이블 시작 4~8바이트를 16진수로 뽑아 알려진 알고리즘의 테이블과 비교한다. CRC32라면 위에 적은 `0x77073096, 0xEE0E612C, 0x990951BA` 순서와 대조한다. 일치하면 3번으로, 안 맞으면 5번(불투명 테이블 추출)으로 간다.

**3) CRC로 확인되면 표준 라이브러리로 검증**

```python
import zlib
print(hex(zlib.crc32(b"test")))
```
바이너리를 실제로 실행해서 같은 입력(`"test"`)에 대한 결과값을 뽑아보고, 위 파이썬 결과와 일치하는지 대조한다. 일치하면 테이블을 추출할 필요가 전혀 없이 `zlib.crc32()` 한 줄로 전체 알고리즘을 대체할 수 있다.

**4) CRC가 아니지만 다른 유명 다항식일 수도 있음**

CRC 계열은 다항식에 따라 여러 변형(CRC-16, CRC-32C 등)이 있다. 테이블 시작값이 표준 CRC32와 다르다면, `binascii.crc_hqx`(CRC-16-CCITT) 등 다른 표준 함수와도 대조해본다. 그래도 안 맞으면 5번으로.

**5) 불투명 테이블 추출**

- **IDA**: 테이블 시작 주소로 이동 → `Edit → Export data...`로 필요한 범위를 내보내거나, IDAPython 콘솔(`View → Open subviews → Output window`)에 직접 입력:
  ```python
  print([hex(Byte(0x140003000+i)) for i in range(256)])
  ```
- **Ghidra**: Listing에서 바이트 범위 드래그 선택 → 우클릭 → `Copy Special → Python List`
- 추출한 값을 파이썬 리스트나 `bytes.fromhex(...)`로 솔브 스크립트에 붙여넣는다.

## 명령어/단축키
```python
import zlib
zlib.crc32(b"data")           # CRC32 표준 구현 (다항식 0xEDB88320 기준)
```
IDA: `Edit → Export data...`, `View → Open subviews → Output window`(IDAPython 콘솔)
Ghidra: `Copy Special → Python List`

## 출력 해석
- `zlib.crc32()` 결과가 바이너리의 실행 결과와 정확히 일치하면 CRC32로 확정, 더 이상 테이블을 신경 쓸 필요 없음.
- 값이 반대(비트 반전, `~crc`)로 나온다면, 많은 CRC32 구현체가 최종 단계에서 `crc ^ 0xFFFFFFFF`를 적용한다는 점을 의심하고 XOR을 추가/제거해서 다시 비교.
- 불투명 테이블을 추출했는데 크기가 예상과 다르면(예: 256개를 기대했는데 128개만 의미 있는 값이고 나머지가 0이면), 실제 인덱스로 쓰이는 값의 범위가 0~127뿐일 수 있으니 인덱싱에 쓰인 마스크(`and eax, 7Fh` 등)를 다시 확인.

## 흔한 실수
- 테이블 앞부분 몇 바이트만 보고 성급하게 "이건 그냥 랜덤 상수"라고 판단해 전체를 억지로 손으로 옮겨 적다가 실수하는 경우 — 항상 CRC 등 표준 알고리즘과의 대조를 먼저 시도한다.
- CRC32를 재현할 때 초기값(`0xFFFFFFFF`)이나 최종 XOR(`0xFFFFFFFF`)을 빼먹고 "표준과 다르다"고 오판하는 경우 — CRC 변형마다 초기값/최종XOR/반사(reflect) 여부가 다르므로, 값이 하나라도 안 맞으면 이 세 가지 파라미터부터 의심한다.
- 원소 크기(1바이트 vs 4바이트)를 착각해서 엉뚱한 범위를 덤프하는 경우 — 곱셈 배수(`*1`, `*4`)를 디스어셈블리에서 다시 확인.
- 이중 LUT 구조(`output[i] = SBOX[PERM[i]]`처럼 순서 재배열 테이블과 값 치환 테이블이 함께 쓰이는 경우)를 하나의 테이블로 착각하고 뒤섞어 처리하는 경우 — xref를 따라가면 서로 다른 두 개의 별도 배열 주소가 나오는지 반드시 확인한다. 순서 재배열 부분은 [REV-0216](./rev-0216-array-shuffle-check.md), 값 치환 부분은 [REV-0214](./rev-0214-custom-alphabet-substitution.md)를 각각 참고해서 단계를 나눠 처리한다.

## 미니 예제

**예제 1 — CRC 테이블 인식으로 작업을 생략한 경우**

IDA에서 `.rodata`에 다음 바이트가 리틀엔디언 dword로 나열된 것을 발견했다:
```
77 07 30 96  EE 0E 61 2C  99 09 51 BA  ...
```
이걸 dword로 읽으면 `0x96300777`가 아니라(리틀엔디언이므로 바이트 순서를 뒤집어야 함) `0x77073096`, `0xEE0E612C`, `0x990951BA`가 된다. 이는 정확히 표준 CRC32 테이블의 앞 3개 값과 일치한다. 확인:
```python
import zlib
data = b"test"
print(hex(zlib.crc32(data)))   # 0xd87f7e0c
```
바이너리를 실행해 같은 입력 `"test"`를 넣었을 때 나오는 값과 `0xd87f7e0c`가 일치하면, 테이블을 단 한 바이트도 뽑을 필요 없이 이 알고리즘 전체를 `zlib.crc32()`로 대체할 수 있다.

**예제 2 — 불투명 테이블을 그대로 추출한 경우**

주소 `0x140005000`에 8개짜리 바이트 리맵 테이블이 있고, 인덱스로 쓰이는 값은 0~7 범위(즉 3비트 값)만 나온다고 하자. IDA Hex View에서 다음 8바이트를 확인했다:
```
A3 5C 91 0E F7 22 6B D8
```
```python
TBL = bytes.fromhex("A35C910EF7226BD8")

def transform(b):
    return TBL[b]

print(transform(0))  # 0xA3
print(transform(7))  # 0xD8
```
테이블 크기가 8개뿐이라는 사실 자체가 "이 값은 바이트 전체가 아니라 0~7 범위의 작은 값(니블의 절반, enum, 3비트 필드 등)에 적용된다"는 중요한 단서다. 인덱스 범위를 테이블 크기와 대조하는 습관이 데이터의 성격을 파악하는 데 큰 도움이 된다.
