## 한 줄 요약
문자를 고정된 칸수만큼 밀되, 알파벳(또는 출력 가능 ASCII 전체) 범위를 벗어나면 반대쪽 끝으로 다시 돌아오는 `mod 26`(또는 `mod 95` 등) 연산이 보인다면, 이건 룩업 테이블 없이 산술식 하나로 완결되는 시저 암호(Caesar cipher) 계열이다.

## 언제 검색해야 하나
- 문자 변환식이 `(c - 'A' + N) % 26 + 'A'` 형태로, 룩업 테이블 없이 덧셈과 나머지 연산만으로 끝날 때
- 문자열에 `ROT13`, `ROT47`, `Caesar` 같은 이름이 그대로 남아있거나(strip 안 된 바이너리), 출력물이 알파벳 순서는 유지하되 알파벳이 아닌 것처럼 보일 때
- 대문자와 소문자를 각각 다른 상수(`'A'`, `'a'`)를 기준으로 별도 처리하는 두 개의 분기가 있을 때
- ADD/SUB 상수 변환(REV-0200)처럼 보이는데, 단순 `+N`이 아니라 **범위를 벗어나면 되돌아오는 나머지 연산**이 추가로 붙어있을 때

## 핵심 개념

### 시저 암호는 "가장 단순한 치환 암호"
시저 암호는 로마의 율리우스 카이사르가 썼다고 전해지는, 역사상 가장 오래된 암호 방식 중 하나다. 원리는 극단적으로 단순하다 — 알파벳을 고정된 칸수(시프트값 `N`) 만큼 밀어서 다른 문자로 바꾼다. `N=3`이면 `A→D`, `B→E`, ..., `X→A`, `Y→B`, `Z→C`처럼 끝에 도달하면 다시 처음으로 돌아온다(순환, wraparound). 치환 암호(REV-0888)의 관점에서 보면 시저 암호는 "26가지 매핑 중에서도 특별히 **모든 문자를 똑같은 칸수만큼 미는** 규칙적인 매핑"에 해당하는 특수 케이스다.

```c
// 표준 시저 암호 — 대소문자 분리 처리
char caesar_shift(char c, int n) {
    if (c >= 'A' && c <= 'Z') {
        return 'A' + ((c - 'A' + n) % 26 + 26) % 26;   // 음수 시프트 대비 이중 mod
    }
    if (c >= 'a' && c <= 'z') {
        return 'a' + ((c - 'a' + n) % 26 + 26) % 26;
    }
    return c;   // 알파벳이 아니면 그대로
}
```
`% 26 + 26) % 26`처럼 나머지 연산을 두 번 겹쳐 쓰는 이유는 `n`이 음수(왼쪽으로 밀기, 즉 복호화)일 때 C의 `%` 연산자가 음수를 반환할 수 있기 때문이다. 이 이중 mod 패턴 자체가 시저류 암호의 특징적인 코드 냄새다.

### ADD/SUB 상수 변환(REV-0200)과의 결정적 차이
REV-0200에서 다루는 일반적인 ADD/SUB 상수 변환은 바이트 전체 범위(`mod 256`)에서 동작하며 알파벳 여부를 신경 쓰지 않는다. 반면 시저 암호는 **알파벳 범위(`mod 26`)로 한정해서 순환**하고, 알파벳이 아닌 문자(숫자, 기호, 공백)는 건드리지 않고 그대로 통과시키는 조건 분기가 반드시 따라온다. 즉 "덧셈 후 나머지 연산"이라는 겉모습은 같지만, **모듈러스가 26이냐 256이냐, 그리고 알파벳 여부를 검사하는 조건문이 있느냐**로 두 패턴을 구분할 수 있다.

### ROT13과 ROT47 — 유명한 특수 케이스
- **ROT13**: 시프트값이 정확히 13인 시저 암호. 알파벳 26개의 정확히 절반이기 때문에, 같은 함수를 암호화와 복호화에 그대로 재사용할 수 있는 재미있는 성질이 있다(`ROT13(ROT13(x)) == x`). 유즈넷 시절부터 스포일러를 가리는 용도로 널리 쓰였고, CTF에서도 "진짜 암호"라기보다 워밍업 문제로 자주 등장한다.
- **ROT47**: 알파벳 26개가 아니라 출력 가능한 ASCII 문자 94개(`!`부터 `~`까지, 코드 33~126) 전체를 대상으로 47칸(94의 절반) 밀어서 순환시킨다. 숫자와 기호까지 함께 뒤섞이므로 ROT13보다 더 광범위하게 적용된다.

```c
// ROT47 구현 예시
char rot47(char c) {
    if (c >= '!' && c <= '~') {
        return '!' + (c - '!' + 47) % 94;
    }
    return c;
}
```
ROT13/ROT47은 시프트값이 알파벳(또는 문자 범위) 크기의 정확히 절반이라는 특수성 때문에 **암호화 함수와 복호화 함수가 완전히 동일한 코드**로 나타난다는 것이 리버싱 관점의 핵심 단서다. 함수를 두 번 연속 호출해도 원래 값으로 돌아오는지 확인해보면 바로 알 수 있다.

### 시프트값을 모를 때 — 26가지(또는 94가지) 전수조사
시저 암호는 키 공간이 극도로 작다(알파벳 기준 최대 25가지, ROT47 기준 최대 93가지). 시프트값을 몰라도 모든 경우의 수를 다 시도해서 사람이 읽을 수 있는 결과가 나오는 것을 찾으면 그만이다. 이건 브루트포스가 정당화되는 대표적인 경우다(REV-0219 참고 — 키 공간이 100 미만이면 사실상 즉시 계산 가능).

```python
def caesar_bruteforce(ciphertext):
    for n in range(26):
        result = "".join(
            chr((ord(c) - ord('A') + n) % 26 + ord('A')) if c.isupper() else
            chr((ord(c) - ord('a') + n) % 26 + ord('a')) if c.islower() else c
            for c in ciphertext
        )
        print(f"shift={n:2d}: {result}")
```
26줄을 눈으로 훑어서 의미가 통하는 줄을 고르기만 하면 되므로, 별도의 통계 분석 없이도 순식간에 풀린다.

## 화면/코드에서 보이는 징후
- `(c - 'A' + N) % 26 + 'A'` 형태의 산술식, 룩업 테이블이 전혀 없음
- 음수 시프트를 대비한 이중 나머지 연산(`% 26 + 26) % 26`)
- 대문자/소문자를 각각 `'A'`, `'a'` 기준으로 나눠 처리하는 두 개의 유사한 분기
- 시프트값이 정확히 13(ROT13)이거나 47(ROT47)이라 암호화/복호화 코드가 완전히 동일
- 알파벳이 아닌 문자는 조건문에서 그대로 통과(`else return c`)

## 가장 먼저 할 것
변환식이 룩업 테이블을 참조하는지, 아니면 산술식만으로 끝나는지부터 확인한다. 산술식만 있고 모듈러스가 26(또는 94)이면 시저류로 확정. 그 다음 시프트값 상수를 코드에서 바로 읽거나, 못 찾으면 26가지 전수조사로 바로 풀어버린다.

## 단계별 절차
1. 문자 변환이 룩업 테이블 없이 산술식(`+N`, `% 26`)만으로 되어 있는지 확인
2. 모듈러스가 26(알파벳 전용)인지 94/95(전체 출력 가능 문자)인지 확인해 ROT13/ROT47 계열 여부 판단
3. 시프트값 상수 `N`을 디스어셈블리에서 직접 확인 — 상수가 없다면 사용자 입력이나 다른 계산에서 유도되는지 추적
4. 시프트값을 알아냈다면 그대로 반대 방향(`-N`)으로 적용해 복호화
5. 시프트값을 못 찾았거나 난독화되어 있다면 26가지(또는 94가지) 전수조사로 사람이 읽을 수 있는 결과를 탐색
6. 대소문자, 숫자, 기호가 각각 어떻게 처리되는지 확인해 전수조사 스크립트의 범위를 정확히 맞춤

## 명령어/단축키
```python
def caesar_decrypt(ciphertext: str, n: int) -> str:
    out = []
    for c in ciphertext:
        if c.isupper():
            out.append(chr((ord(c) - ord('A') - n) % 26 + ord('A')))
        elif c.islower():
            out.append(chr((ord(c) - ord('a') - n) % 26 + ord('a')))
        else:
            out.append(c)
    return "".join(out)

# 시프트값을 모를 때: 26가지 전수조사는 본문의 caesar_bruteforce() 참고
```
IDA: 상수 `13`, `26`, `47`, `94` 근처를 `Alt+B`(상수 검색)나 크로스레퍼런스로 확인. Ghidra: 디컴파일 뷰에서 `% 0x1a`(26) 또는 `% 0x5e`(94) 패턴 검색.

## 출력 해석
- 26가지 전수조사 결과 중 정확히 하나만 의미가 통하는 영어 단어/플래그 형식이 나오면 그게 정답 시프트값이다.
- 두 개 이상의 결과가 그럴듯해 보인다면 알파벳이 아닌 다른 요소(치환 암호, REV-0888)가 섞여 있을 가능성이 있으니 변환식 전체를 재검토한다.
- ROT13/ROT47처럼 암호화·복호화 함수가 똑같다면, 그 함수를 암호문에 한 번 더 적용하는 것만으로 평문이 나온다.

## 흔한 실수
- 시프트값이 큰 상수(예: 300)로 보여서 다른 알고리즘으로 오인하는 것 — `% 26`을 거치면 300도 결국 `300 % 26 = 14`로 작은 값이 되므로, 코드에 나오는 원본 상수가 커도 실질 시프트값은 항상 0~25 사이임을 기억해야 한다.
- 알파벳이 아닌 문자(공백, 구두점)까지 시프트 대상으로 착각해서 전수조사 스크립트가 깨지는 것.
- ADD/SUB 상수 변환(REV-0200, `mod 256`)과 혼동해서 26이 아니라 256으로 나머지 연산을 하는 것.
- 음수 시프트에서 이중 `mod` 처리를 빠뜨려 파이썬에서 음수 인덱스로 엉뚱한 문자가 나오는 것(파이썬의 `%`는 C와 달리 항상 양수를 반환하므로 이 문제는 파이썬에서는 드물지만, C 코드를 그대로 옮겨적을 때 실수하기 쉽다).

## 막혔을 때 다음 체크
- 시프트값이 위치마다 달라지는(반복 키를 쓰는) 경우라면 → REV-0889 Vigenere류 반복 키 암호 알아보기
- 매핑이 규칙적인 시프트가 아니라 완전히 무작위 순열이라면 → REV-0888 간단한 치환 암호(substitution cipher) 알아보기
- 알파벳 전용이 아니라 바이트 전체(mod 256)에서 동작하는 단순 상수 변환이라면 → REV-0200 ADD SUB 상수 기반 문자 변환
- 키 공간이 작아서 전수조사가 정당한지 다시 확인하려면 → REV-0219 Brute Force가 가능한 입력 공간 계산

## 미니 예제
어떤 CTF 바이너리를 objdump로 확인했더니 다음과 비슷한 의사코드가 나왔다고 하자.

```c
void transform(char *s) {
    for (int i = 0; s[i]; i++) {
        if (s[i] >= 'a' && s[i] <= 'z') {
            s[i] = 'a' + (s[i] - 'a' + 13) % 26;
        }
    }
}
```
시프트값이 정확히 13이고 소문자만 처리하므로 ROT13이다. ROT13은 자기 자신이 역함수이므로, 이 함수를 암호문에 한 번 더 통과시키면 바로 평문이 나온다.

```python
import codecs

ciphertext = "synt{guvf_vf_rnfl}"
print(codecs.decode(ciphertext, "rot13"))
# 출력: flag{this_is_easy}
```
만약 시프트값이 13이 아니라 알 수 없는 값이었다면, 앞서 소개한 `caesar_bruteforce()`로 26가지를 모두 출력해 `flag{`로 시작하는 줄을 눈으로 찾으면 된다.

## 관련 글
- REV-0888 — 간단한 치환 암호(substitution cipher) 알아보기
- REV-0889 — Vigenere류 반복 키 암호 알아보기
- REV-0200 — ADD SUB 상수 기반 문자 변환
- REV-0219 — Brute Force가 가능한 입력 공간 계산
- REV-0221 — 역연산 가능한 알고리즘 판단법

## 출처/검증
- 시저 암호의 정의(고정 시프트, 알파벳 26개 기준 순환)와 역사적 배경: David Kahn, *The Codebreakers* 및 표준 암호학 입문 교재(고전 암호 챕터) 기준 (2026-09-09 검증).
- ROT13이 시프트 13(알파벳 크기의 절반)이라 자기 자신의 역함수가 되는 성질과, ROT47이 ASCII 33~126(94개 문자) 범위에서 47칸 이동하는 정의: ROT13/ROT47 관련 표준 기술 문서 및 위키백과 "ROT13" 항목 기준 (2026-09-09 검증).
