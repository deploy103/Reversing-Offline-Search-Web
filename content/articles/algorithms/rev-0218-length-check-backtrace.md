## 한 줄 요약
CTF flag 검증 바이너리를 처음 열었을 때 가장 먼저 찾아야 할 것은 복잡한 암호/해시 알고리즘이 아니라 **`strlen(input) == N` 형태의 길이 검증**이다. 이건 함수 전체에서 가장 읽기 쉬운 비교문이면서, 진짜 알고리즘이 다루는 "미지의 바이트 수"를 알고리즘을 읽기도 전에 알려주는 최고의 시작점이다.

## 언제 검색해야 하나
- 디컴파일된 `check()` 함수가 너무 길고 복잡해서 어디서부터 읽어야 할지 막막할 때
- flag의 정확한 길이를 모르는 상태에서 브루트포스(REV-0219) 여부를 판단해야 할 때
- "Correct!"/"Wrong flag" 같은 성공/실패 메시지는 찾았는데, 그 메시지로 이어지는 진짜 검증 로직이 어디서 시작하는지 못 찾았을 때
- 알고리즘 전체를 다 이해하지 않고도 문제의 "진짜 크기"(미지 바이트 수)를 먼저 가늠하고 싶을 때

## 핵심 개념
거의 모든 CTF 체크 함수는 다음 순서로 구성된다:

1. **길이 게이트** — `strlen(input) != N` 이면 즉시 실패
2. **접두사/접미사 게이트** — `flag{`로 시작하는지, `}`로 끝나는지 확인
3. **문자셋 게이트** (있을 수도 없을 수도 있음) — 각 문자가 특정 범위(숫자만, hex만 등)인지 확인
4. **진짜 알고리즘** — 나머지 미지 바이트에 대해 XOR/치환/해시/암호화 등을 수행하고 결과를 비교

1~3번 게이트는 전형적으로 한 줄짜리 비교문이라서 디스어셈블리만 봐도 5분 안에 파악된다. 반면 4번은 문제의 핵심이라 이해하는 데 오래 걸린다. **순서를 바꿔서, 쉬운 게이트부터 전부 찾아낸 다음 어려운 부분에 시간을 투자하는 것**이 효율적인 리버싱 전략이다. 이걸 "게이트 인벤토리(gate inventory)"라고 부르자.

길이 게이트가 중요한 이유는 단순히 "빨리 찾아서"가 아니다. 길이 N, 접두사 길이 P, 접미사 길이 S를 알아내면 **진짜 미지 바이트 수는 `N - P - S`** 로 확정된다. 이 숫자 하나가 REV-0219(브루트포스 가능성 계산)의 지수(exponent)를 결정하고, 문제가 몇 시간짜리인지 며칠짜리인지를 가른다.

## 화면/코드에서 보이는 징후
- 함수 맨 앞부분에서 `call strlen` 직후 `cmp eax, imm` / `jnz`
- `if ( strlen(s) != 24 )` 같은 디컴파일 결과가 함수 최상단에 위치
- `memcmp(input, "flag{", 5)` 처럼 고정 문자열과 비교하는 짧은 `memcmp`/`strncmp` 호출
- `input[len-1] != '}'` 처럼 배열의 마지막 인덱스만 비교하는 단일 조건문
- 성공 메시지로 가는 경로 바로 앞에 있는 거대한 `for`/`while` 루프 (이게 4번 "진짜 알고리즘")

## 가장 먼저 할 것
IDA에서 `Shift+F12`(Strings 창)를 열어 `Correct`, `Wrong`, `Access granted`, `flag` 같은 키워드로 필터링해서 성공/실패 메시지 문자열을 찾는다. Ghidra라면 `Window → Defined Strings` 메뉴에서 같은 작업을 한다. 문자열을 찾으면 그 문자열 위에서 IDA는 `Ctrl+X`(Ghidra는 우클릭 → `Show References To`)를 눌러서 그 문자열을 사용하는 함수로 바로 이동한다. 이제 이 함수가 체크 로직이 있는 함수다.

## 단계별 절차

**1) 체크 함수 진입점 찾기**

위에서 설명한 대로 문자열 xref를 따라가면 `printf("Correct!\n")` 같은 호출이 있는 위치에 도착한다. 이 호출 직전의 분기(`jnz`/`jz`)가 "최종 통과/실패 플래그"를 결정한 조건이다. 하지만 이건 대개 여러 게이트를 통과한 최종 결과이지, 길이 검증 자체는 아니다.

**2) 함수 최상단으로 거슬러 올라가기**

체크 함수의 시작 부분(IDA에서 함수 이름 더블클릭 후 맨 위로 스크롤, 또는 그래프 뷰에서 진입 노드 확인)을 본다. 대부분의 구현에서 **가장 먼저 실행되는 검증이 길이 체크**다. 다음과 같은 패턴을 찾는다:

```asm
mov     rcx, [rbp+input]
call    strlen
cmp     eax, 18h        ; 0x18 = 24 decimal
jnz     fail_label
```

여기서 `18h`는 16진수이므로 `1*16 + 8 = 24`, 즉 flag 전체 길이가 24바이트라는 뜻이다. IDA에서 이 즉시값(`18h`)을 클릭하고 `H` 키를 누르면 10진수/16진수 표기가 토글되어 암산 없이 바로 확인할 수 있다.

주의할 점 하나: 최적화가 걸린 바이너리에서는 컴파일러가 `call strlen`을 아예 생략하고 널 바이트를 찾는 짧은 루프(`cmp byte [rax+rcx], 0` / `jne` 반복)로 직접 풀어써버리는 경우가 있다. 이 경우 "strlen 호출"이라는 눈에 보이는 단서 자체가 없으므로, 함수 맨 앞부분에 있는 아주 짧고 단순한 바이트 스캔 루프도 길이 계산의 일부일 수 있다는 걸 염두에 두고 살펴봐야 한다. 또한 `strlen`은 널 종료 문자를 세지 않는다는 점도 기억해야 한다 — 만약 검증 로직이 `strlen` 대신 고정 크기 버퍼(`char input[25]`처럼 널 바이트 자리까지 포함한 크기)를 기준으로 길이를 비교한다면, 실제 flag 길이는 버퍼 크기보다 1 작을 수 있으니 어느 쪽 기준인지 반드시 구분해야 한다.

**3) 접두사/접미사 게이트 찾기**

길이 체크 바로 다음 블록들을 확인한다. `memcmp`/`strncmp`로 고정 문자열과 비교하거나, 배열의 특정 인덱스 하나만 리터럴과 비교하는 짧은 조건문이 있다면 그게 접두사/접미사 게이트다.

**4) 모든 fail 경로 나열하기(게이트 인벤토리)**

`fail_label`로 점프하는 모든 `jnz`/`jz`를 IDA 그래프 뷰에서 확인한다(`Esc`로 이전 위치로 돌아가고, 분기 화살표를 눈으로 따라가거나 `Ctrl+Enter`로 커서 아래 주소로 점프). 각 분기 조건을 표로 정리하면, "쉬운 게이트"와 "진짜 알고리즘 게이트"가 명확히 분리된다.

**5) 미지 바이트 수 확정**

`전체 길이 N - 접두사 길이 P - 접미사 길이 S = 미지 바이트 수`를 계산한다. 이 숫자가 다음 단계(브루트포스 판단, 알고리즘 역산 등)의 기준이 된다.

## 명령어/단축키
- IDA: `Shift+F12` (Strings 창), `Ctrl+X` (커서 위치 xref 목록), `H` (숫자 진법 토글), `Esc`/`Ctrl+Enter` (이동 히스토리 전/후)
- Ghidra: `Window → Defined Strings`, 우클릭 `Show References To`, `Window → Decompiler`
- Python으로 16진수 즉시값 빠르게 변환: `print(int("18", 16))` → `24`

## 출력 해석
- `strlen` 호출 뒤 비교값이 `N`이면 flag 전체 길이는 정확히 N바이트다. `jle`/`jge` 등 부등호 비교라면 "최소/최대 길이"만 제한하는 것이므로 정확한 길이가 아직 미정임에 주의한다.
- `memcmp(input, "flag{", 5)`가 있으면 앞 5바이트는 완전히 고정되어 있으므로 브루트포스/알고리즘 분석 대상에서 제외해도 된다.
- 마지막 바이트 하나만 검사하는 `input[N-1] == '}'`는 접미사 게이트로, 보통 1바이트만 줄여준다.
- 길이 게이트가 하나가 아니라 **여러 개**(예: `if (len < 10) return 0; ... if (len > 40) return 0;`)로 나뉘어 있는 경우도 있다. 이때는 두 범위의 교집합이 실제 허용 길이 범위이며, 그 안에서 다시 정확히 하나의 값만 통과시키는 `==` 비교가 별도로 더 있는지 반드시 확인해야 한다 — 범위 체크만 보고 "길이가 10~40 사이 아무 값이나 된다"고 성급히 결론 내리면 뒤에 숨어 있는 진짜 길이 게이트를 놓치게 된다.

## 흔한 실수
- `main()`부터 위에서 아래로 순서대로 읽으면서 진짜 알고리즘의 복잡한 루프에 먼저 빠져드는 것 — 5~10분만 투자해서 게이트 인벤토리부터 만들면 전체 그림이 먼저 보인다.
- 길이 게이트를 찾고 바로 만족해서 접두사/접미사 게이트를 놓치는 것 — 접두사/접미사가 있으면 미지 바이트 수가 실제로는 훨씬 작아서 브루트포스 난이도가 크게 달라진다.
- `cmp eax, 18h`를 10진수 18로 착각하는 것 — 어셈블리 리터럴은 기본적으로 16진수 표기이므로 반드시 `H` 키나 계산기로 변환해서 확인한다.
- 부등호 비교(`jle`, `jge`)를 등호 비교로 착각해서 길이를 확정으로 잘못 판단하는 것.

## 미니 예제
IDA에서 다음과 같은 디컴파일 결과를 봤다고 하자:

```c
int check(char *input) {
    if (strlen(input) != 24) return 0;             // 길이 게이트: 24바이트
    if (memcmp(input, "flag{", 5) != 0) return 0;  // 접두사 게이트: 5바이트 고정
    if (input[23] != '}') return 0;                // 접미사 게이트: 1바이트 고정
    // ... 이하 200줄짜리 진짜 알고리즘이 input[5..22]에만 작동 ...
}
```

여기서 게이트 인벤토리를 정리하면:
- 전체 길이: 24바이트
- 알려진 바이트: 접두사 5 + 접미사 1 = 6바이트
- **진짜 미지 바이트 수: 24 - 6 = 18바이트**

이 18이라는 숫자를 200줄짜리 알고리즘을 단 한 줄도 읽지 않고 얻어냈다는 게 핵심이다. 이 차이가 얼마나 큰지 감을 잡으려면, 인쇄 가능 아스키 문자셋(95종)을 가정했을 때:
- 24바이트 전체를 브루트포스: 95^24 ≈ 2.92×10^47
- 18바이트만 브루트포스: 95^18 ≈ 3.97×10^35

95^24 ÷ 95^18 = 95^6 ≈ 7.35×10^11배 차이다. 즉 접두사/접미사 게이트를 찾아내는 것만으로 브루트포스 난이도를 **7,350억 배** 줄인 셈이다(구체적인 실현 가능성 판단은 [rev-0219-bruteforce-feasibility.md](./rev-0219-bruteforce-feasibility.md)에서 이어서 다룬다). 물론 18바이트도 여전히 브루트포스로는 불가능한 수준이므로, 다음 단계는 진짜 알고리즘이 역산 가능한지(REV-0221) 판단하는 것이다.
