## 한 줄 요약
브루트포스가 문자셋/길이 계산대로 다 돌았는데도 정답을 못 찾았다면, 탐색 범위가 부족한 게 아니라 **거의 항상 오라클(체크 함수) 자체에 버그가 있어서 진짜 정답을 넣어도 `True`를 반환하지 못하는 상태**이므로, 탐색 공간을 더 늘리기 전에 오라클부터 별도로 검증해야 한다.

## 언제 검색해야 하나
- REV-0219(브루트포스 가능한 입력 공간 계산)로 확인한 시간 안에 브루트포스를 다 돌렸는데 정답이 하나도 안 나올 때
- 체크 함수(오라클)를 REV-0222 방식으로 재구현한 뒤 브루트포스에 연결했는데 아무 입력도 `True`를 안 만들 때
- 문자셋이나 길이를 늘려서 다시 돌려도 여전히 답이 안 나올 때(문자셋/길이 문제가 아니라는 신호)

## 핵심 개념
브루트포스가 "탐색 공간을 다 돌았는데 답이 없다"는 결과 자체가 이상 신호다. CTF 문제는 설계상 반드시 답이 존재하므로, 탐색 범위 안에 답이 있는데 못 찾았다는 것은 논리적으로 다음 중 하나다.

1. **오라클(체크 함수)이 실제 바이너리와 다르게 동작한다** — 재구현 과정에서 마스킹 누락, 엔디안 실수, 회전/시프트 방향 반전, 비교 연산자 반전(`!=`를 `==`로 잘못 옮김) 등으로 진짜 정답을 넣어도 `False`가 나오는 상태.
2. **목표 상수(비교 대상 값) 자체를 잘못 옮겨 적었다** — 오라클 로직은 맞는데 비교 기준값이 틀리면 어떤 입력을 넣어도 절대 통과할 수 없다.
3. **문자셋/길이 가정이 실제보다 좁다** — 예상 문자셋에 특수문자나 대문자가 빠졌거나, 길이 범위(`range(1, 7)`처럼 상한을 놓침)가 실제 정답 길이를 포함하지 못함.
4. **자료형/인코딩 불일치** — 오라클이 `str`을 기대하는데 `bytes`를 넣거나 그 반대, 혹은 대소문자를 구분해야 하는데 무시하는 등.

이 중 압도적으로 흔한 것은 1번과 2번이다. 탐색 공간을 넓히기 전에, **오라클이 스스로 일관성이 있는지**부터 확인하는 게 훨씬 빠르다 — 즉 오라클로 암호화(순방향) 함수를 만들 수 있다면, 아무 입력이나 넣어 순방향으로 계산한 결과를 다시 오라클(검증 함수)에 넣었을 때 반드시 `True`가 나와야 한다. 이게 안 되면 오라클 자체가 바이너리와 다르게 동작한다는 뜻이다.

## 화면/코드에서 보이는 징후
- 브루트포스 루프가 끝까지(진행률 100%) 돌았는데 `FOUND` 로그가 한 번도 안 찍힘
- 오라클 함수에 알려진 값(있다면 다른 난이도의 동일 문제, 혹은 자체 제작한 테스트 벡터)을 넣어도 기대한 결과가 안 나옴
- 오라클을 아무리 다른 입력으로 돌려도 항상 `False`만 반환하고, 단 한 번도 `True`가 안 나옴(정답이 존재하는지조차 의심스러운 상태)

## 가장 먼저 할 것
브루트포스 루프를 더 돌리기 전에 멈추고, **오라클 함수 자체를 실제 바이너리와 한 개의 알려진 입력으로 직접 대조**한다. 가장 확실한 방법은 디버거로 바이너리를 실행해 임의의 입력(꼭 정답이 아니어도 됨, 예: `"AAAA"`)을 넣고 검증 함수의 최종 반환값(레지스터 `eax`/`rax` 등)을 직접 읽은 뒤, 파이썬 오라클에 같은 입력을 넣어 같은 값이 나오는지 비교하는 것이다.

## 단계별 절차

**1) 오라클을 디버거로 교차검증**
```gdb
break check_func
run
# "AAAA" 입력 후
finish
print $eax        # 실제 바이너리가 계산한 최종값
```
```python
print(hex(check_raw("AAAA".encode())))  # 오라클이 계산한 값, 위와 정확히 같아야 함
```
`check_raw`는 `True`/`False`만 반환하는 게 아니라 **비교 직전의 중간 계산값**을 반환하도록 임시로 수정한 버전이다. 이 값이 디버거로 읽은 `eax`와 다르면 오라클 자체가 틀린 것이다.

**2) 순방향-역방향 왕복 테스트(가능한 경우)**

가역 연산이라면, 오라클과 반대 방향인 순방향 함수를 만들어서 임의 입력 → 순방향 계산 → 역방향(오라클) 검증이 항상 성립하는지 확인한다.
```python
test_input = b"randomtest"
encoded = forward(test_input)
assert oracle_returns_true_for(encoded)  # 오라클이 자기 자신의 순방향 결과를 못 알아보면 버그 확정
```

**3) 목표 상수 재대조**

오라클 안의 비교 대상 값(`target`)을 디스어셈블리의 `cmp` 오퍼랜드와 한 글자도 빠짐없이 다시 대조한다. 특히 엔디안, signed/unsigned 표시 문제로 상수 자체가 잘못 옮겨졌을 가능성을 확인한다.

**4) 오라클이 확실히 맞다고 검증되면 그제서야 탐색 범위 재점검**

문자셋을 넓히거나(대문자/특수문자 포함), 길이 상한을 늘려서 다시 돌린다.

## 명령어/단축키
```python
def sanity_check(oracle, known_good_input=None):
    if known_good_input is not None:
        assert oracle(known_good_input), "오라클이 알려진 정답에도 False를 반환함 - 오라클 버그"
    # 정답을 모른다면 최소한 오라클이 항상 False만 반환하지 않는지 확인
```

## 출력 해석
- 디버거로 읽은 중간값과 파이썬 오라클의 중간값이 다르면 → 오라클 재구현 버그. REV-0921의 이진 탐색 절차로 정확한 위치를 좁힌다.
- 두 값이 같은데도 브루트포스가 답을 못 찾으면 → 목표 상수 자체가 틀렸거나, 탐색 범위가 실제로 부족한 것.
- 순방향-역방향 왕복 테스트가 실패하면 → 오라클 구현이 원본 연산의 역함수가 아니라 전혀 다른 연산이라는 뜻이므로 어셈블리를 처음부터 다시 대조해야 한다.

## 흔한 실수
- 오라클을 검증하지 않고 탐색 공간(문자셋, 길이)만 계속 넓혀가며 시간을 낭비하는 것 — 오라클에 버그가 있으면 아무리 넓혀도 답이 안 나온다.
- 비교 연산자 방향을 반대로 옮기는 것(`if h == target: return False` 처럼 `True`/`False`를 바꿔 씀) — 이 경우 오히려 오답이 `True`로 나오고 정답이 `False`로 나오는 정반대 상황이 생길 수 있다.
- 대소문자, 공백, 인코딩(`str` vs `bytes`, UTF-8 vs ASCII) 차이를 신경 안 쓰고 오라클에 넣는 것.
- 브루트포스 진행률만 보고 "돌고 있으니 언젠가는 찾겠지"라며 오라클 검증을 미루는 것 — 오라클이 틀렸다면 몇 시간을 돌려도 결과는 똑같다.

## 막혔을 때 다음 체크
- 오라클 재구현 자체의 특정 버그 유형(오버플로, 엔디안, 회전 방향)을 좁히고 싶다면 → REV-0921 알고리즘을 복원했는데 출력이 원본과 안 맞을 때
- 목표 상수가 의심된다면 → REV-0930 상수 하나를 잘못 읽어서 전체 알고리즘이 안 맞을 때
- 탐색 공간 자체가 정말 부족한지 다시 계산하고 싶다면 → REV-0219 Brute Force가 가능한 입력 공간 계산
- 문자셋/길이를 더 정확히 좁히는 방법이 필요하다면 → REV-0218 길이 검증부터 역추적하는 법

## 미니 예제
어떤 문제에서 파이썬 오라클을 다음과 같이 재구현했다고 하자.
```python
def check(s: bytes) -> bool:
    h = 0
    for b in s:
        h = (h * 31 + b) & 0xFFFFFFFF
    return h != 0x1A2B3C4D   # 버그: 원본은 je(같으면 성공)인데 !=로 잘못 옮김
```
이 오라클은 `h`가 목표값과 **다를 때** `True`를 반환하므로, 실제 정답(즉 `h == 0x1A2B3C4D`를 만드는 입력)을 브루트포스로 넣어도 오라클은 계속 `False`를 반환해 절대 찾을 수 없다. 디스어셈블리를 다시 보니 `cmp eax, 1A2B3C4Dh` 다음 `je correct`였으므로, "같으면 성공"이 맞는 논리다. `!=`를 `==`로 고치자 정답이 즉시 발견됐다 — 오라클 자체의 부호 반전이 원인이었던 전형적인 사례다.

### 추가 예제 — sanity_check로 오라클 버그를 브루트포스보다 먼저 잡기
아래는 실제로 실행 가능한 전체 스크립트로, "오라클을 먼저 검증하지 않고 브루트포스만 끝까지 돌리면 답이 안 나온다"는 것을 직접 보여준다. 목표 문자열은 `"AB"`(길이 2, 문자셋 `"AB"`)이고, 해시 함수는 `h = (h*31 + byte) & 0xFFFFFFFF`이다. 이 해시로 `"AB"`를 계산하면 `0x821`이 나온다는 것을 GDB로 미리 확인했다고 가정한다.

```python
import itertools  # 문자셋 조합을 전부 만들어내기 위한 표준 라이브러리


def h(s: bytes) -> int:
    # 아주 단순한 곱셈 기반 누산 해시 (실습용으로 축소한 모델)
    v = 0
    for b in s:               # 바이트를 하나씩 순회
        v = (v * 31 + b) & 0xFFFFFFFF   # 32비트로 마스킹(REV-0926 참고)하며 누적
    return v


# GDB로 바이너리에 "AB"를 직접 입력해서 확인한 "알려진 정답 쌍"
KNOWN_INPUT = b"AB"
KNOWN_HASH = 0x821


def oracle_buggy(s: bytes) -> bool:
    # [틀린 코드] 디스어셈블리의 cmp 상수를 옮겨 적다가 자릿수를 바꿔 적음(0x821 -> 0x281)
    WRONG_TARGET = 0x281
    return h(s) == WRONG_TARGET


def oracle_fixed(s: bytes) -> bool:
    # [고친 코드] 상수를 정확히 옮긴 올바른 오라클
    TARGET = 0x821
    return h(s) == TARGET


def sanity_check(oracle, known_good_input=None) -> None:
    # 브루트포스를 돌리기 전에 오라클 자체가 알려진 정답에 True를 주는지 먼저 확인
    if known_good_input is not None:
        assert oracle(known_good_input), "오라클이 알려진 정답에도 False를 반환함 - 오라클 버그"


# 1) 버그가 있는 오라클을 sanity_check로 먼저 점검 -> 브루트포스를 돌리기도 전에 바로 걸린다
try:
    sanity_check(oracle_buggy, KNOWN_INPUT)
    print("오라클 정상")
except AssertionError as e:
    print("[틀린 오라클] 사전 점검에서 이미 실패:", e)

# 2) 그래도 모르고 문자셋 "AB", 길이 2 전체(AA, AB, BA, BB)를 브루트포스로 끝까지 돌렸다고 가정
found = None
for combo in itertools.product("AB", repeat=2):
    candidate = "".join(combo).encode()
    if oracle_buggy(candidate):     # 버그 있는 오라클로 검사
        found = candidate
        break
print("[틀린 오라클] 브루트포스 결과:", found)
# 출력: [틀린 오라클] 브루트포스 결과: None
# -> 탐색 공간(4가지 조합)을 전부 돌았는데도 단 하나도 True가 안 나옴

# 3) 오라클을 고친 뒤 sanity_check와 브루트포스를 다시 수행
sanity_check(oracle_fixed, KNOWN_INPUT)   # 이번엔 조용히 통과(에러 없음)
found_fixed = None
for combo in itertools.product("AB", repeat=2):
    candidate = "".join(combo).encode()
    if oracle_fixed(candidate):     # 고친 오라클로 검사
        found_fixed = candidate
        break
print("[고친 오라클] 브루트포스 결과:", found_fixed)
# 출력: [고친 오라클] 브루트포스 결과: b'AB'
```
`sanity_check`는 브루트포스 루프를 단 한 번도 돌리지 않고도 "이 오라클은 버그가 있다"는 사실을 즉시 알려준다. 실제로 상수 하나(`0x821` -> `0x281`)만 틀려도 4개뿐인 아주 작은 탐색 공간조차 전부 실패로 끝나며, 상수를 고치는 순간 첫 조합 검사에서 곧바로 `b'AB'`를 찾아낸다.
