## 한 줄 요약
암호학적 해시(SHA-1/MD5, REV-0896/0897)나 CRC(REV-0209)만큼 복잡하지 않고, 데이터를 단순히 더하거나(합산 체크섬), 두 개의 누적 합을 조합하거나(Adler-32, Fletcher), 자릿수에 가중치를 곱해 더하는(Luhn 등) 방식으로 "우연한 오류"만 잡아내는 가벼운 검증 로직이 보이면 이는 Checksum이며, 목적이 "보안"이 아니라 "실수/전송 오류 검출"이라는 점을 이해하는 것이 핵심이다.

## 언제 검색해야 하나
- 해시치고는 계산이 너무 단순한(루프 안에 덧셈/누적만 있고 라운드 함수, S-box, 회전 연산이 없는) 검증 함수를 발견했을 때
- 결과가 16비트나 32비트인데, 초기값·상수 개수가 SHA-1(REV-0896)이나 MD5(REV-0897)의 지문과 전혀 안 맞을 때
- `65521`이라는 특정 상수(또는 `0xFFF1`)로 나눗셈/나머지 연산을 하는 코드를 봤을 때 — Adler-32의 강력한 지문
- 두 개의 별도 누적 변수(`s1`, `s2` 같은 이름)가 함께 갱신되며, 마지막에 하나를 16비트 왼쪽 시프트해서 합치는 코드를 봤을 때
- 신용카드 번호, 시리얼 번호, 학번 같은 "형식은 맞는데 진짜인지 확인하는" 짧은 검증 로직을 마주쳤을 때(Luhn 알고리즘 후보)

## 핵심 개념

### Checksum과 암호학적 해시의 근본적 차이
SHA-1(REV-0896), MD5(REV-0897) 같은 암호학적 해시는 "공격자가 의도적으로 같은 해시를 만드는 입력(충돌)을 찾기 어렵게" 설계된다. 반면 Checksum은 그런 보안 목표가 전혀 없고, 오직 **전송 오류, 저장 오류, 우연한 비트 손상**을 빠르고 값싸게 검출하기 위해 만들어진다. 그래서 계산이 극도로 단순하고(곱셈조차 없는 경우가 많음), 의도적인 위조에는 쉽게 뚫린다. CTF에서 이런 체크섬을 만나면 "이건 보안 장치가 아니라 단순 무결성 확인용이니, 값을 알면 원하는 대로 맞출 수 있다"는 전제로 접근해야 한다.

### 가장 단순한 형태 — 단순 합산/XOR 체크섬
```c
uint8_t checksum = 0;
for (i = 0; i < len; i++)
    checksum += data[i];       // 또는 checksum ^= data[i];
```
바이트를 그냥 다 더하거나(오버플로는 무시하고 wrap), 전부 XOR한 값을 검증에 쓰는 방식이다. 구현이 가장 단순한 만큼 오류 검출력도 가장 약하다 — 예를 들어 순수 덧셈 체크섬은 두 바이트의 순서를 바꿔도(예: `AB`↔`BA`) 같은 합이 나오므로 순서 오류를 못 잡는다.

### Adler-32 — 두 개의 16비트 합을 조합
zlib에서 CRC-32(REV-0209)보다 빠른 대안으로 쓰는 Adler-32는 두 개의 16비트 누적값을 유지한다:
```c
uint32_t s1 = 1, s2 = 0;
for (i = 0; i < len; i++) {
    s1 = (s1 + data[i]) % 65521;
    s2 = (s2 + s1) % 65521;
}
uint32_t adler32 = (s2 << 16) | s1;
```
`s1`은 모든 바이트의 누적 합이고(초기값 1에서 시작), `s2`는 매 단계마다의 `s1` 값을 다시 누적한 합이다(초기값 0에서 시작). 둘 다 **65521**로 나눈 나머지를 취하는데, 이 값은 65536(2^16)보다 작은 가장 큰 소수다 — 소수를 쓰는 이유는 특정 패턴의 2바이트 오류가 체크섬을 그대로 통과하는 걸 방지하기 위함이다(RFC 1950 zlib 명세). **`65521`이라는 상수가 코드에 그대로 보이면 Adler-32로 사실상 확정**할 수 있는 강력한 지문이다. 참고로 rsync는 이 소수 대신 단순히 65536으로 나머지를 취하는 변형을 쓰므로, 상수가 `65536`이면 Adler-32의 변형(rsync rolling checksum)임을 의심할 수 있다.

### Fletcher 체크섬 — Adler-32의 원조
Adler-32는 Fletcher 체크섬을 개량한 것으로, 원조 Fletcher는 모듈러스로 소수가 아닌 `255`나 `65535` 같은 2^n-1 값을 쓴다. 구조(`s1`/`s2` 두 누적값 유지, 마지막에 이어붙임)는 Adler-32와 거의 같으므로, **모듈러스 상수가 65521(소수)이면 Adler-32, 255나 65535 같은 값이면 Fletcher**로 구분하면 된다.

### Luhn 알고리즘 — 자릿수 검증(신용카드/일련번호)
Luhn 알고리즘은 숫자로만 이루어진 코드(신용카드 번호, 일부 일련번호/학번 체계)의 오타를 검출하기 위한 체크 숫자 계산법이다:
```python
def luhn_checksum(digits: list[int]) -> int:
    total = 0
    for i, d in enumerate(reversed(digits)):
        if i % 2 == 1:      # 뒤에서부터 짝수 번째 자리(0-base로는 홀수 인덱스)
            d *= 2
            if d > 9:
                d -= 9
        total += d
    return total % 10
```
뒤에서부터 세어 한 자리씩 건너뛰며 2배로 곱하고, 두 자릿수가 되면 9를 빼는(자릿수 합과 동일한 효과) 특유의 처리가 지문이다. 최종 합이 10으로 나누어떨어지면 유효한 번호로 간주한다. "짝수/홀수 번째 자리만 2배" + "9를 넘으면 9를 뺀다"는 조합이 코드에 보이면 Luhn으로 확정할 수 있다.

### CRC와의 구분 — 왜 굳이 다른 방식을 쓰는가
CRC(REV-0209)는 다항식 나눗셈 기반이라 오류 검출력이 체크섬류보다 훨씬 강력하지만 계산이 상대적으로 무겁다(테이블 조회 또는 8회 비트 루프 필요). 반면 Adler-32/Fletcher/단순 합산은 덧셈만으로 계산되어 CPU 부담이 적다. 그래서 대용량 데이터의 빠른 무결성 확인(zlib 압축 스트림 등)에는 Adler-32를, 강한 오류 검출이 필요한 곳(이더넷, ZIP)에는 CRC-32를 쓰는 식으로 용도가 나뉜다.

### 요약 비교표
| 방식 | 계산 방식 | 대표 상수/지문 | 대표 용례 |
|---|---|---|---|
| 단순 합산/XOR | 바이트 누적 덧셈/XOR | 없음(너무 단순) | 임베디드, 간단 파일 포맷 |
| Adler-32 | 이중 누적 + 모듈러 | `65521` | zlib 스트림 |
| Fletcher | 이중 누적 + 모듈러 | `255`, `65535` | 원조 Fletcher(TCP 옵션 등) |
| Luhn | 자릿수 가중合 | 짝수자리 2배, 9 초과시 -9 | 신용카드, 일련번호 |
| CRC(REV-0209) | 다항식 나눗셈 | `0xEDB88320` 등 | ZIP, 이더넷, PNG |

## 화면/코드에서 보이는 징후
- 단순 `for` 루프 안에서 `sum += data[i]` 또는 `xor ^= data[i]`만 반복
- 코드 어딘가에 `65521` 또는 `0xFFF1` 상수로 나머지 연산
- `s1`, `s2`(또는 유사한 이름)의 두 누적 변수가 함께 갱신되고 마지막에 `(s2 << 16) | s1`으로 합쳐짐
- 숫자 자릿수를 뒤에서부터 순회하며 한 자리 건너 2배로 곱하고 9를 넘으면 9를 빼는 로직
- 검증 실패 시 "checksum mismatch", "corrupted", "invalid CRC/checksum" 류의 문자열 출력

## 가장 먼저 할 것
검증 함수의 복잡도부터 가늠한다. 라운드 함수, S-box, 회전 연산이 전혀 없고 단순 덧셈/나머지 연산만 있다면 암호학적 해시가 아니라 체크섬이다. `65521` 상수가 있으면 Adler-32로 즉시 확정, 없으면 단순 합산이나 Luhn 여부를 코드 구조로 판별한다.

## 단계별 절차
1. 검증 로직에 곱셈/회전/S-box가 없고 덧셈/나머지 연산만 있는지 확인(있으면 CRC나 해시 계열이므로 REV-0209/0896/0897로 이동)
2. `65521`, `0xFFF1`, `65535`, `255` 같은 모듈러스 상수를 코드에서 검색
3. 누적 변수가 1개인지 2개인지 확인 — 2개면 Adler-32/Fletcher류, 1개면 단순 합산/XOR
4. 숫자 자릿수를 다루는 도메인(카드번호, 일련번호)이라면 Luhn 여부를 자릿수 가중치 패턴으로 확인
5. Python으로 후보 알고리즘을 재현해서 알고 있는 입력에 대한 결과를 바이너리 값과 대조
6. 일치하면 이 체크섬 값을 원하는 대로 만드는 입력을 역으로 구성(단순 합산이면 마지막 바이트 하나를 조정하는 식으로 손쉽게 원하는 체크섬 값을 맞출 수 있음)

## 명령어/단축키
```bash
strings ./binary | grep -iE "checksum|corrupt|invalid crc"
objdump -d ./binary | grep -B2 -A2 "65521\|0xfff1"
python3 -c "
import zlib
print(zlib.adler32(b'Wikipedia'))   # 표준 zlib Adler-32
"
```
IDA: 상수 `65521`(`0xFFF1`) 위에서 `H` 토글로 진법 확인, Xref(`X`)로 어느 함수에서 쓰이는지 추적.

## 출력 해석
- `zlib.adler32(b"Wikipedia")`는 `300286872`(hex로 `0x11E60438`)가 나온다 — 재현 로직 검증에 활용할 수 있는 잘 알려진 참조값이다.
- 재현 결과가 바이너리 값과 안 맞으면, 초기값(`s1=1, s2=0`이 표준이지만 커스텀 구현은 둘 다 0으로 시작하는 경우도 있음)이나 처리 순서(빅엔디안/리틀엔디안으로 최종 값을 합치는 순서)를 다시 확인한다.
- 단순 합산 체크섬은 오버플로 처리(8비트로 랩어라운드하는지, 32비트 그대로 두는지)에 따라 결과가 달라지므로 자료형 크기를 정확히 맞춰야 한다.

## 흔한 실수
- 체크섬을 암호학적 해시와 동일한 보안 강도로 착각해서 "역산이 불가능하다"고 포기하는 것 — 체크섬은 애초에 위조 방지가 목적이 아니라서, 원하는 체크섬 값을 만드는 입력을 구성하기가 오히려 훨씬 쉽다(예: 단순 합산이면 마지막 1바이트만 조정해서 원하는 합을 맞출 수 있음).
- Adler-32와 CRC-32(REV-0209)를 결과 크기(둘 다 32비트)만 보고 혼동하는 것 — 계산 방식(다항식 나눗셈 vs 이중 누적합)과 지문 상수(`0xEDB88320` vs `65521`)로 반드시 구분해야 한다.
- Luhn 알고리즘에서 "뒤에서부터 짝수 번째"의 기준을 헷갈려 2배 곱하는 자리를 반대로 적용하는 것 — 반드시 실제 코드의 루프 방향과 인덱스 기준을 그대로 따라가며 검증해야 한다.
- 체크섬 불일치를 "심각한 보안 실패"로 오해하는 것 — 대부분은 그냥 전송/파싱 과정에서 데이터가 하나라도 바뀌면 걸러내려는 가벼운 안전장치일 뿐이다.

## 미니 예제
디컴파일 코드에서 다음 함수를 발견했다:
```c
unsigned int calc(unsigned char *data, int len) {
    unsigned int s1 = 1, s2 = 0;
    for (int i = 0; i < len; i++) {
        s1 = (s1 + data[i]) % 65521;
        s2 = (s2 + s1) % 65521;
    }
    return (s2 << 16) | s1;
}
```
모듈러스 `65521`이 정확히 두 번 등장하고 두 누적 변수가 함께 갱신되므로 Adler-32로 확정된다. Python으로 검증:
```python
import zlib
print(zlib.adler32(b"Wikipedia"))
# 300286872
```
바이너리에서 같은 입력에 대해 계산한 값이 `300286872`와 일치하면 Adler-32 사용이 최종 확정된다.

## 출처/검증
- Adler-32 알고리즘 정의와 모듈러스 `65521`(2^16보다 작은 최대 소수)이 소수여야 하는 이유: IETF RFC 1950("ZLIB Compressed Data Format Specification") 및 zlib 공식 소스코드(`adler32.c`) 기준 (2026-09-09 검증).
- Adler-32 표준 예시값(`"Wikipedia"` → `300286872`): 공개적으로 널리 알려진 zlib Adler-32 참조 예제 기준 (2026-09-09 확인).
- Fletcher 체크섬과 Adler-32의 관계 및 rsync의 65536 변형: 일반적으로 알려진 체크섬 알고리즘 비교 문헌 기준 (2026-09-09).
- Luhn 알고리즘(자릿수 2배/9 차감 규칙): ISO/IEC 7812-1에서 채택된 Luhn 알고리즘의 표준 정의 기준 (2026-09-09).
