## 한 줄 요약
파이썬으로 옮긴 해시/체크섬 루프가 **짧은 입력에서는 맞다가 입력이 길어지면(또는 반복 횟수가 늘면) 갑자기 틀리기 시작**한다면, 십중팔구 원본이 32비트(또는 8/16/64비트) 레지스터에서 자동으로 일어나는 오버플로우 랩어라운드를 파이썬의 무한정밀도 정수가 흉내내지 못해서 생기는 문제이며, 매 연산 직후 `& 0xFFFFFFFF`(또는 해당 비트폭 마스크)를 걸어주면 해결된다.

## 언제 검색해야 하나
- 짧은 테스트 문자열(`"AB"`, `"test"`)로는 재구현 결과가 원본과 맞는데, 실제 목표 길이의 긴 입력에서는 틀릴 때
- 누산 변수(해시값, 체크섬, 카운터)가 루프를 돌면서 계속 커지기만 하는 구조일 때
- 곱셈이나 왼쪽 시프트가 반복적으로 들어가는 루프를 파이썬으로 옮겼을 때
- 원본 C/어셈블리 코드에 `unsigned int`, `uint32_t`, `DWORD`처럼 크기가 고정된 타입이 쓰였을 때

## 핵심 개념
C의 `unsigned int`(보통 32비트)나 어셈블리의 32비트 레지스터(`eax`, `ecx` 등)는 연산 결과가 표현 가능한 범위(`0 ~ 0xFFFFFFFF`)를 넘으면 **자동으로 초과분을 버리고 나머지만 남기는(모듈러 연산, 랩어라운드) 동작**을 CPU 차원에서 수행한다. 이건 버그가 아니라 정의된 정상 동작이다.

반면 파이썬의 `int`는 **임의 정밀도(arbitrary precision)**를 지원해서, 아무리 곱하고 더해도 절대 자동으로 잘리지 않는다. 그래서 원본 로직을 파이썬으로 그대로 옮기면서 매 연산 뒤에 `& 0xFFFFFFFF`를 걸어주지 않으면, 값이 32비트를 넘어서는 순간부터 두 계산이 완전히 다른 길을 가게 된다.

**언제 이 문제가 드러나는가가 핵심이다.** 누산값이 32비트를 넘기 전까지는 파이썬 값과 원본 레지스터 값이 우연히 정확히 일치한다(마스킹을 안 해도 아직 잘릴 게 없으므로). 그래서 짧은 입력이나 초반 몇 반복에서는 "맞는 것처럼" 보이다가, 누산값이 `0xFFFFFFFF`를 넘어서는 시점부터 갑자기 완전히 다른 값이 나온다. 이 "처음엔 맞다가 어느 순간부터 틀림"이라는 패턴 자체가 오버플로우 마스킹 누락의 강력한 증거다.

**구체적 숫자로 확인**: 초기값 `5381`에서 시작해 매 바이트마다 `h = h * 33 + byte`를 반복하는 djb2류 해시에 `b"AAAAAAAAAA"`(0x41이 10개)를 넣어보자.

| i | 마스킹 없음(파이썬 기본) | `& 0xFFFFFFFF` 적용 | 32비트 초과 여부 |
|---|---|---|---|
| 0 | `0x2b5e6` | `0x2b5e6` | 아니오 |
| 1 | `0x5972e7` | `0x5972e7` | 아니오 |
| 2 | `0xb87d008` | `0xb87d008` | 아니오 |
| 3 | `0x17c81d149` | `0x7c81d149` | **예 (여기서부터 갈라짐)** |
| 4 | `0x310cbbfaaa` | `0xcbbfaaa` | 예 |

`i=0`부터 `i=2`까지는 마스킹 여부와 무관하게 값이 완전히 같다 — 아직 32비트(`0xFFFFFFFF`, 약 42억)를 넘지 않았기 때문이다. `i=3`에서 마스킹 없는 값(`0x17c81d149`, 약 640억)이 32비트를 넘어서면서 두 계산이 완전히 갈라진다. 실제 CPU의 `imul`/`add`는 항상 32비트 레지스터에만 결과를 담으므로 `& 0xFFFFFFFF` 쪽이 진짜 동작과 일치한다.

## 화면/코드에서 보이는 징후
```python
h = 5381
for b in data:
    h = h * 33 + b     # 마스킹 없음 -> 파이썬 정수가 무한정 커짐
```
- 위처럼 곱셈/덧셈/시프트 뒤에 `& 0xFFFFFFFF`(또는 `0xFF`, `0xFFFF`, `2**64-1` 등 다른 비트폭 마스크)가 전혀 없는 코드
- `print(h)`로 중간값을 찍어보면 값이 10자리, 20자리로 한없이 길어짐(32비트 레지스터라면 최대 10자리 십진수, `4294967295`를 넘을 수 없어야 정상)

## 가장 먼저 할 것
누산 변수가 선언된 원본 타입(`unsigned int` 32비트인지, `unsigned char` 8비트인지, `unsigned long long` 64비트인지)을 다시 확인하고, 파이썬 코드에서 그 변수가 갱신되는 모든 줄 뒤에 해당 비트폭 마스크가 걸려 있는지 하나하나 점검한다.

## 단계별 절차

**1) 원본 변수 비트폭 확인**

디스어셈블리에서 누산 변수가 쓰이는 레지스터 크기(`al`=8비트, `ax`=16비트, `eax`=32비트, `rax`=64비트)를 확인한다.

**2) 파이썬 코드의 모든 갱신 지점에 마스킹 추가**
```python
MASK32 = 0xFFFFFFFF

def check(data: bytes) -> int:
    h = 5381
    for b in data:
        h = (h * 33 + b) & MASK32   # 매 반복 직후 즉시 마스킹
    return h
```

**3) 짧은 입력과 긴 입력 둘 다로 재검증**

짧은 입력에서만 테스트하고 끝내지 말고, 실제 목표 길이(또는 그보다 긴 입력)로도 반드시 재검증한다. 오버플로우 버그는 짧은 테스트에서는 절대 드러나지 않는다.

**4) 중간 임시 변수도 놓치지 않기**

`(a * b + c) * d`처럼 한 줄에 연산이 여러 개 섞여 있으면, 파이썬은 이를 한 번에 계산해서 최종 결과만 마스킹하기 쉽지만, 원본 CPU는 `a*b`의 결과부터 이미 32비트로 잘렸을 수 있다. 원본 어셈블리가 실제로 몇 단계로 나눠 계산하는지 확인하고, 그 단계마다 마스킹 위치를 맞춰야 한다.

## 명령어/단축키
```python
MASK8, MASK16, MASK32, MASK64 = 0xFF, 0xFFFF, 0xFFFFFFFF, 0xFFFFFFFFFFFFFFFF
x = (x + y) & MASK32
x = (x * y) & MASK32
x = (x << n) & MASK32     # 왼쪽 시프트는 특히 마스킹을 빼먹기 쉬움
```

## 출력 해석
- 마스킹 전/후 값을 나란히 출력해서, 두 값이 갈라지는 정확한 반복 인덱스를 확인한다(위 표처럼). 그 인덱스에서 누산값이 처음으로 32비트를 넘는다는 뜻이다.
- 마스킹을 추가한 뒤에도 여전히 안 맞으면, 비트폭 자체를 잘못 잡았을 가능성이 있다(8비트인데 32비트로 마스킹했다든가) — 원본 타입을 재확인한다.

## 흔한 실수
- 최종 반환값에만 마스킹을 걸고 루프 중간의 임시 계산에는 마스킹을 빼먹는 것 — 중간에 이미 오버플로우가 나면 최종 마스킹으로는 되돌릴 수 없다.
- 짧은 문자열 하나로만 테스트하고 "맞았다"고 결론짓는 것 — 위 표에서 보듯 초반 몇 반복은 마스킹 여부와 무관하게 우연히 같은 값이 나온다.
- 시프트 연산(`<<`) 뒤에 마스킹을 빼먹는 것 — 왼쪽 시프트는 곱셈보다도 더 빨리 비트 수가 늘어나서 오버플로우가 훨씬 일찍 발생한다.
- 8비트/32비트가 섞인 식에서 전부 32비트로 통일해서 마스킹하는 것 — 중간에 8비트로 잘려야 하는 지점이 있다면 그 지점만 `& 0xFF`를 따로 걸어야 한다.

## 막혔을 때 다음 체크
- 마스킹을 다 걸었는데도 여전히 특정 인덱스부터 틀린다면 → REV-0921 알고리즘을 복원했는데 출력이 원본과 안 맞을 때(이진 탐색으로 재확인)
- 회전/시프트 자체를 파이썬으로 옮기는 표준 방법이 필요하다면 → REV-0222 검증 루틴을 Python으로 그대로 재현하기
- Z3로 이 로직을 풀어야 한다면 비트폭 처리를 Z3 쪽에서도 동일하게 신경 써야 한다 → REV-0270 Z3에서 8비트 32비트 Overflow 다루기
- 오버플로우 자체가 검증 로직의 트릭으로 의도적으로 쓰인 경우라면 → REV-0205 Modulo와 오버플로를 이용한 검증

## 미니 예제
초기값 `5381`, 곱셈 상수 `33`인 djb2류 해시에 10바이트(`b"AAAAAAAAAA"`)를 넣었을 때:
```python
MASK32 = 0xFFFFFFFF

def check_wrong(data: bytes) -> int:
    h = 5381
    for b in data:
        h = h * 33 + b        # 마스킹 없음
    return h

def check_right(data: bytes) -> int:
    h = 5381
    for b in data:
        h = (h * 33 + b) & MASK32
    return h

data = b"AAAAAAAAAA"
print(hex(check_wrong(data)))  # 0x726a7b35f4922f6f (32비트를 한참 넘음)
print(hex(check_right(data)))  # 0xf4922f6f (실제 32비트 레지스터가 갖는 값)
```
`check_right`가 반환하는 `0xf4922f6f`만이 실제 바이너리의 `eax` 레지스터 값과 일치한다.

## 관련 글
- REV-0921 — 알고리즘을 복원했는데 출력이 원본과 안 맞을 때
- REV-0205 — Modulo와 오버플로를 이용한 검증
- REV-0222 — 검증 루틴을 Python으로 그대로 재현하기
- REV-0270 — Z3에서 8비트 32비트 Overflow 다루기

## 출처/검증
- C 언어에서 부호 없는 정수 타입의 오버플로우는 undefined behavior가 아니라 모듈러(2^n) 연산으로 정의된 well-defined 동작이라는 규정 및 x86 32비트 레지스터의 연산 동작: Intel 64 and IA-32 Architectures Software Developer's Manual, Volume 1 기준 (2026-09-09 검증).
- 파이썬 `int`가 임의 정밀도 정수라는 사양: Python 공식 문서(내장 타입 `int`) 기준.
- 본문의 djb2류 해시 계산 수치는 Python으로 직접 실행해 검산됨.
