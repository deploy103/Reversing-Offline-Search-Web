## 한 줄 요약
하나의 정수(주로 32비트 또는 64비트) 안에 여러 개의 독립적인 값이나 플래그가 서로 다른 비트 구간에 나뉘어 저장되어 있고, 이를 꺼낼 때 `시프트(shift) 후 마스크(AND)`를, 넣을 때 `시프트 후 OR`를 쓰는 패턴이 보이면 이는 Bit Packing이며, 압축/직렬화 목적이든 단순 플래그 저장 목적이든 "왜 이렇게 쪼갰는가"를 알아내는 것이 핵심이다.

## 언제 검색해야 하나
- 디컴파일 코드에서 한 변수(`flags`, `packed`, `state` 등으로 명명된 경우가 많음)에 대해 `>> n & mask` 형태의 접근이 여러 번, 서로 다른 `n`과 `mask`로 반복될 때
- 반대로 여러 개의 작은 값(예: 4비트, 8비트씩)을 `<< n | value`로 하나의 정수에 합치는 코드를 봤을 때
- 값의 유효 범위가 이상하게 좁을 때(예: 특정 변수가 항상 0~15 사이인데 자료형은 32비트 int) — 실제로는 4비트만 쓰는 필드일 가능성
- 구조체 정의(디컴파일러가 재구성한 것 포함)에 `: 3`, `: 5` 같은 비트필드(bitfield) 문법이 보일 때
- 네트워크 프로토콜 헤더나 파일 포맷 헤더를 파싱하는데 필드 하나가 바이트 경계와 안 맞게 끊겨 있을 때

## 핵심 개념

### Bit Packing이란 무엇이고 왜 쓰는가
Bit Packing은 여러 개의 작은 값(플래그, 좁은 범위의 숫자, 열거형 등)을 각각 별도의 변수나 바이트로 저장하는 대신, **하나의 정수 안에 비트 구간(bit field)을 나눠 욱여넣는** 기법이다. 목적은 크게 세 가지다:
1. **메모리/저장 공간 절약** — 예를 들어 0~15 범위의 값 8개를 저장한다면, 각각 int(4바이트)로 저장하면 32바이트가 필요하지만 4비트씩 압축하면 4바이트(32비트)면 충분하다.
2. **네트워크/파일 포맷 명세 준수** — TCP 헤더의 플래그 비트들, PE/ELF 파일 헤더의 속성 비트들처럼 표준 포맷 자체가 특정 비트 레이아웃을 강제하는 경우.
3. **CTF에서의 의도적 난독화** — 여러 검증 조건을 하나의 정수 비교로 위장해서, 디스어셈블리만 봐서는 무엇을 검사하는지 바로 알기 어렵게 만드는 경우.

### 값을 꺼내는 패턴 — Shift and Mask
비트 구간에서 값을 읽어내는 전형적인 코드는 다음과 같다:
```c
field_a = (packed >> 0)  & 0x0F;   // 하위 4비트
field_b = (packed >> 4)  & 0xFF;   // 그다음 8비트
field_c = (packed >> 12) & 0x07;   // 그다음 3비트
field_d = (packed >> 15) & 0x1FFFF; // 나머지 상위 비트들
```
핵심은 **오른쪽으로 밀어서(`>>`) 원하는 필드를 최하위 비트로 가져온 뒤, AND 마스크로 그 필드보다 상위 비트를 모두 0으로 지우는** 두 단계다. 마스크 값이 `2^n - 1`(예: `0x0F`=4비트, `0xFF`=8비트, `0x07`=3비트, `0x1F`=5비트, `0x3FF`=10비트)인지 확인하면 그 필드가 몇 비트짜리인지 즉시 알 수 있다.

### 값을 채워 넣는 패턴 — Shift and OR
반대로 여러 값을 하나로 합치는 코드는 다음과 같다:
```c
packed = (field_a & 0x0F)
       | ((field_b & 0xFF) << 4)
       | ((field_c & 0x07) << 12)
       | ((field_d & 0x1FFFF) << 15);
```
각 값을 먼저 자신의 마스크로 범위를 제한(clamp)한 뒤, 지정된 비트 위치로 왼쪽 시프트하고, 전체를 OR로 합친다. 이 패턴에서 시프트량들을 순서대로 나열하면(`0, 4, 12, 15, ...`) 각 필드의 시작 비트 위치와 폭(다음 시프트량과의 차이)을 계산해서 전체 레이아웃을 재구성할 수 있다.

### 필드 폭과 마스크 값 대응표
| 필드 폭(비트) | 마스크(hex) | 표현 가능 범위 |
|---|---|---|
| 1 | `0x1` | 0~1 (단일 플래그) |
| 2 | `0x3` | 0~3 |
| 3 | `0x7` | 0~7 |
| 4 | `0xF` | 0~15 |
| 5 | `0x1F` | 0~31 |
| 6 | `0x3F` | 0~63 |
| 8 | `0xFF` | 0~255 |
| 16 | `0xFFFF` | 0~65535 |

마스크 값이 이 표에 딱 맞아떨어지면 필드 폭을 바로 역산할 수 있다. 딱 맞아떨어지지 않는 애매한 마스크(예: `0x35`)라면 단순 비트필드가 아니라 다른 목적의 비트 연산(예: 특정 비트만 검사하는 플래그 체크)일 수 있으니 구분해야 한다.

### 단일 비트 플래그와의 구분
Bit Packing의 특수한 경우로, 폭이 1비트씩인 여러 개의 독립적인 on/off 플래그를 한 정수에 모아두는 경우도 매우 흔하다:
```c
bool is_admin  = (flags >> 0) & 1;
bool is_active = (flags >> 1) & 1;
bool is_banned = (flags >> 2) & 1;
```
이 경우 `& 1`이 반복되고 시프트량이 1씩 증가하는 패턴이 특징적이다. 반대로 설정할 때는 `flags |= (1 << n)`(비트 켜기), `flags &= ~(1 << n)`(비트 끄기), `flags ^= (1 << n)`(비트 토글) 형태로 나타난다.

### 프로토콜/파일 포맷에서의 실전 예 — 표준을 강제로 지키는 경우
IPv4 헤더의 첫 바이트는 상위 4비트가 버전(Version), 하위 4비트가 헤더 길이(IHL)로 정의되어 있다. TCP 헤더의 플래그 바이트는 URG/ACK/PSH/RST/SYN/FIN 각각이 1비트씩이다. 이런 표준 포맷을 파싱하는 코드를 만나면, 알고 있는 표준 스펙과 시프트/마스크 값을 대조해서 어떤 필드인지 즉시 특정할 수 있다.

## 화면/코드에서 보이는 징후
- 한 변수에 대해 서로 다른 시프트량과 마스크로 여러 번 `>> n & mask` 접근
- 시프트량 없이 마스크만 다른 여러 `& constant` 연산이 반복(폭이 겹치지 않는 여러 필드를 순서대로 검사)
- `<< n | value` 조합이 여러 개 이어져 하나의 결과로 합쳐짐
- 디컴파일러가 재구성한 구조체에 `unsigned int field : 4;` 같은 비트필드 문법
- 값 하나의 실제 사용 범위가 자료형 전체 범위보다 훨씬 좁음(예: `int`인데 항상 0~7 사이)

## 가장 먼저 할 것
의심되는 정수 변수에 대해 접근하는 모든 코드 위치를 Xref(`X` 단축키)로 모은 뒤, 각 접근의 시프트량과 마스크 값을 표로 정리한다. 시프트량을 오름차순으로 정렬하면 전체 비트 레이아웃(어느 비트부터 어느 비트까지가 어떤 필드인지)이 드러난다.

## 단계별 절차
1. 의심되는 정수 변수의 모든 읽기/쓰기 위치를 Xref로 수집
2. 각 위치에서 시프트량(`n`)과 마스크 값을 기록
3. 마스크를 이진수로 바꿔 연속된 1비트 개수(필드 폭)를 확인 — 위 대응표와 비교
4. 시프트량 순서대로 정렬해 비트 0부터 상위 비트까지 필드 경계를 그려본다(그림으로 그리면 이해가 빠르다)
5. 잘 알려진 프로토콜/파일 포맷 헤더라면 표준 스펙 문서와 시프트/마스크 값을 대조해 필드 이름을 특정
6. Python으로 동일한 shift/mask 로직을 재현해서, 알고 있는 입력값에 대해 바이너리와 같은 결과가 나오는지 검증

## 명령어/단축키
- IDA: 의심 변수에서 `X`(Xref to)로 모든 참조 위치 나열, `Alt+M`으로 구조체 구성원(비트필드 포함) 확인
- Ghidra: `Data Type Manager`에서 구조체를 만들고 필드마다 비트 크기를 직접 지정해 재구성
```python
def unpack(v: int):
    field_a = (v >> 0)  & 0x0F
    field_b = (v >> 4)  & 0xFF
    field_c = (v >> 12) & 0x07
    field_d = (v >> 15) & 0x1FFFF
    return field_a, field_b, field_c, field_d

def pack(a: int, b: int, c: int, d: int) -> int:
    return (a & 0x0F) | ((b & 0xFF) << 4) | ((c & 0x07) << 12) | ((d & 0x1FFFF) << 15)

v = 0x12345678
print(unpack(v))
assert pack(*unpack(v)) == v
```

## 출력 해석
- `pack(*unpack(v)) == v`가 참이면 필드 경계를 정확히 재구성한 것이다 — 재구성한 shift/mask로 다시 조립했을 때 원본과 완전히 같아야 한다.
- 재조립 결과가 원본과 다르면, 필드 사이에 예약된(사용하지 않는) 비트 구간을 놓쳤거나 마스크 폭을 잘못 계산한 것이니 시프트량 표를 다시 검토한다.
- 필드 하나의 값이 검증 로직에서 특정 상수와 비교된다면, 그 필드가 바로 CTF 문제의 조건 중 하나(예: "이 4비트 필드가 반드시 5여야 한다")일 가능성이 크다.

## 흔한 실수
- 시프트량만 보고 마스크를 확인하지 않아 필드 폭을 잘못 계산하는 것 — 반드시 마스크 값도 함께 대조해야 한다.
- 필드 사이의 예약/패딩 비트를 하나의 필드로 착각해 전체 레이아웃을 어긋나게 재구성하는 것.
- 부호 있는(signed) 필드를 부호 없는 것처럼 다뤄서, 필드의 최상위 비트가 부호 비트인 경우를 놓치는 것 — 필드 폭 그대로 값이 음수로 해석돼야 하는 경우 별도의 부호 확장(REV-0206 참고)이 필요하다.
- Bit Packing을 단순 XOR 인코딩(REV-0199)이나 룩업 테이블 변환(REV-0215)과 혼동하는 것 — Bit Packing은 값 자체를 바꾸는 게 아니라 여러 값의 "위치"만 한 정수 안에서 재배열하는 것이라는 점이 다르다.

## 미니 예제
IDA 디컴파일 결과에서 다음과 같은 검증 함수를 발견했다:
```c
int check(unsigned int packed) {
    int version = (packed >> 28) & 0xF;
    int len     = (packed >> 24) & 0xF;
    int flags   = (packed >> 16) & 0xFF;
    int payload = packed & 0xFFFF;
    return version == 4 && len == 5 && (flags & 0x01) && payload == 0x1337;
}
```
시프트량(`28, 24, 16, 0`)과 마스크(`0xF, 0xF, 0xFF, 0xFFFF`)를 정리하면 32비트가 `버전(4비트) | 길이(4비트) | 플래그(8비트) | 페이로드(16비트)`로 나뉘어 있음을 알 수 있다. 조건을 만족하는 값을 파이썬으로 직접 조립해본다:
```python
version, length, flags, payload = 4, 5, 0x01, 0x1337
packed = (version << 28) | (length << 24) | (flags << 16) | payload
print(hex(packed))  # 0x45011337
```
이 값을 프로그램에 입력하면 `check()` 함수를 통과한다는 것을 시프트/마스크 분석만으로 미리 알 수 있다.
