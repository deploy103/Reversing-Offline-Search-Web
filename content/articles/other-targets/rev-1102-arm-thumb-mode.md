## 한 줄 요약
Thumb은 ARM 프로세서가 지원하는 압축된 16비트 명령어 집합으로, 같은 CPU가 32비트 ARM 명령어와 16비트 Thumb 명령어 사이를 오가며 실행할 수 있고, 함수 포인터/심볼 주소의 최하위 비트(LSB)가 1이면 "이 주소는 Thumb 모드로 진입해야 한다"는 표시라서 실제 명령어 주소는 짝수인데도 심볼 테이블에는 홀수 주소로 나타나는 경우가 흔하다.

## 언제 검색해야 하나
- Ghidra/IDA가 ARM 바이너리를 열었는데 디스어셈블 결과가 전혀 말이 안 되거나 명령어 크기가 이상하게 다 어긋날 때
- `nm`/`readelf -s` 결과에서 함수 심볼 주소가 홀수(예: `0x8135`)로 끝나서 당황할 때
- 디스어셈블 도구가 "이 명령어는 4바이트"라고 하는데 실제로는 2바이트씩 잘려야 정상으로 보일 때
- 안드로이드 네이티브 라이브러리(`.so`)나 임베디드 펌웨어 리버싱에서 "ARM"과 "Thumb"이 섞여 있다는 말을 들었을 때

## 핵심 개념

### Thumb은 왜 존재하는가
ARM은 원래 모든 명령어가 32비트 고정 길이인 RISC 아키텍처다. 이는 디코딩이 단순하고 빠르다는 장점이 있지만, 코드 크기가 커진다는 단점이 있다. Thumb은 이 문제를 해결하기 위해 도입된 16비트 명령어 집합으로, 자주 쓰는 32비트 ARM 명령어의 부분집합을 절반 크기로 인코딩한다. 임베디드 기기처럼 메모리가 제한적인 환경, 그리고 모바일(Android 네이티브 라이브러리) 환경에서 코드 크기를 줄이기 위해 널리 쓰인다. Thumb-2 확장부터는 16비트와 32비트 명령어를 섞어 쓸 수 있게 되어 코드 밀도와 성능을 동시에 개선했다.

### 프로세서는 어떻게 두 모드를 구분하는가
CPU 내부에는 현재 상태가 ARM인지 Thumb인지를 나타내는 상태 비트(T bit, CPSR/APSR의 일부)가 있다. 이 비트를 어셈블리 코드가 직접 덮어쓰는 것은 안전하지 않다(예측 불가능한 동작) — 반드시 전용 분기 명령을 통해서만 전환해야 한다.

- `BX Rn` (Branch and Exchange): 레지스터 `Rn`에 담긴 주소로 분기하면서, 그 주소의 최하위 비트(LSB)가 1이면 Thumb 모드로, 0이면 ARM 모드로 전환한다.
- `BLX` (Branch with Link and Exchange, ARMv5 이상): `BX`와 동일하게 모드를 전환하며 분기하되, 복귀 주소를 `LR`에 저장(link)한다 — 함수 호출에 쓰인다.

### "홀수 주소"의 정체
실제 명령어는 항상 2바이트(Thumb) 또는 4바이트(ARM) 정렬된 주소에 있으므로 최하위 비트가 진짜 주소 일부로 쓰이는 일은 없다. 그래서 컴파일러/링커는 이 여분의 비트 하나를 "이 함수는 Thumb 코드다"라는 표시로 재활용한다. 심볼 테이블이나 함수 포인터에 저장된 주소의 LSB가 1이면 Thumb 함수라는 뜻이고, 실제로 그 주소로 점프할 때는 LSB를 무시하고 짝수 주소부터 명령어를 읽는다. 이것이 "함수 심볼 주소가 홀수로 끝나 있다"는 현상의 원인이다.

### 인터워킹(interworking)이란
ARM 코드로 작성된 함수가 Thumb 코드로 작성된 함수를 호출하거나 그 반대인 경우를 인터워킹이라 부른다. 링커는 Thumb 함수의 심볼 주소에 LSB를 1로 설정해두고, 호출하는 쪽이 `BX`/`BLX`로 그 값을 그대로 사용하면 CPU가 자동으로 올바른 모드로 전환된다. 이 메커니즘 덕분에 하나의 실행 파일 안에 ARM 코드와 Thumb 코드가 자유롭게 섞여도 정상 동작한다.

### 리버싱 도구가 실수하는 지점
디스어셈블러가 어떤 영역을 ARM으로 볼지 Thumb으로 볼지는 정적 분석만으로 100% 정확히 알기 어렵다(특히 strip된 바이너리, 점프 테이블, 함수 포인터 배열 등). 잘못 판단하면 명령어 경계가 어긋나 완전히 의미 없는 디스어셈블리가 나온다 — Ghidra/IDA에서 "코드가 이상하다"고 느껴질 때 가장 먼저 의심해야 할 것이 바로 ARM/Thumb 모드 오판이다(REV-1104에서 수동 교정법을 다룬다).

## 화면/코드에서 보이는 징후
- 함수 심볼 주소가 홀수(`0x8135`처럼 끝자리가 홀수)
- 디스어셈블 결과가 알아볼 수 없는 명령어의 나열이거나 즉시 `invalid instruction`이 반복됨
- 같은 바이너리인데 어떤 구간은 자연스러운 코드, 어떤 구간은 깨진 것처럼 보임(모드 경계 오판)
- `BX`/`BLX` 명령의 대상이 레지스터이고, 그 레지스터 값을 추적하면 LSB가 1로 설정되어 있음

## 가장 먼저 할 것
디스어셈블리가 이상해 보이면 먼저 그 주소가 원래 ARM 모드로 열렸는지 Thumb 모드로 열렸는지 확인하고, 심볼 테이블의 원래 함수 주소 LSB(홀수/짝수)를 대조해 올바른 모드로 다시 디스어셈블한다.

## 단계별 절차
1. `readelf -s ./chall.so` 또는 Ghidra Symbol Table에서 의심되는 함수의 원래 주소값을 확인
2. 주소가 홀수면 Thumb 함수, 짝수면 ARM 함수라고 잠정 판단
3. Ghidra/IDA에서 해당 주소(짝수로 정렬한 실제 주소)부터 Thumb 모드로 강제 재해석(REV-1104의 방법 사용)
4. 재해석 후 명령어 경계가 자연스러운 함수 프롤로그(`PUSH`류)로 정렬되는지 확인
5. `BX`/`BLX Rn` 호출부에서 `Rn`에 들어가는 값을 역추적해, 호출 대상이 Thumb인지 ARM인지 미리 예측해두면 다음 분석이 빨라짐

## 명령어/단축키
```bash
# 심볼 주소의 홀짝(Thumb 여부) 확인
readelf -s ./libnative.so | grep -i FUNC

# objdump로 Thumb 강제 디스어셈블 (32비트 ARM ELF, binutils)
objdump -d --disassembler-options=force-thumb ./libnative.so

# GDB에서 현재 명령어 세트 확인
(gdb) show arm force-mode
(gdb) info registers cpsr
```

## 출력 해석
- `readelf -s`에서 함수 주소가 `00008135`처럼 나오면 실제 코드는 `0x8134`부터 시작하는 Thumb 코드다(마지막 비트 1은 Thumb 표시일 뿐 실제 주소가 아님).
- `objdump -d`에서 같은 파일을 ARM 모드로 디스어셈블했을 때 `.text`의 특정 구간이 전부 `.byte 0x.., 0x..`처럼 "알 수 없는 데이터"로만 나온다면, 그 구간이 사실 Thumb 코드인데 ARM으로 잘못 해석되고 있다는 신호다.

## 흔한 실수
- 심볼 주소의 LSB를 그대로 실제 코드 시작 주소로 착각해서 홀수 주소에서부터 바이트를 읽으려는 것 — 실제 코드는 그 주소에서 1을 뺀 짝수 위치부터다.
- Thumb 모드에서 일반 데이터 처리 명령이 조건 플래그를 잘 안 바꾼다는 점(Thumb-1 기준)을 잊고 x86/ARM 습관대로 플래그 갱신을 가정하는 것.
- 전체 바이너리를 한 가지 모드로만 강제 디스어셈블하고, 일부 함수만 다른 모드라는 것을 놓치는 것 — 하나의 파일 안에서도 함수별로 모드가 다를 수 있다(인터워킹).
- Thumb-2가 32비트 명령어도 섞어 쓸 수 있다는 것을 모르고 "Thumb=항상 16비트"라고 단정하는 것.

## 막혔을 때 다음 체크
- ARM/ARM64 레지스터와 호출 규약 자체가 헷갈리면 → REV-1101 ARM/ARM64 레지스터와 호출 규약 기초
- Ghidra/IDA에서 실제로 아키텍처/모드를 지정하는 구체적 메뉴 조작법 → REV-1104 Ghidra/IDA에서 ARM 바이너리 아키텍처 설정하기
- 조건부 명령 접미사(`EQ`, `NE` 등)가 Thumb의 `IT` 블록과 함께 나와서 헷갈리면 → REV-1103 ARM에서 조건부 실행(비트) 읽는 법

## 미니 예제
```
$ readelf -s libnative.so | grep check
    45: 00008d31   120 FUNC    GLOBAL DEFAULT   12 check_password
```
주소가 `00008d31`로 끝자리가 1(홀수)이므로 `check_password`는 Thumb 함수다. 실제 코드는 `0x8d30`부터 시작하며, 이 함수를 호출하는 쪽 코드에는 다음과 같은 패턴이 나타난다.
```asm
LDR  R3, =check_password   ; R3 = 0x00008d31 (LSB=1, 링커가 자동 설정)
BLX  R3                    ; R3의 LSB가 1이므로 Thumb 모드로 전환하며 호출
```

## 출처/검증
- Thumb 명령어 집합이 32비트 ARM 명령어 부분집합을 16비트로 압축 인코딩한 것이라는 설명 및 Thumb-2의 16/32비트 혼합 지원: 다수의 ARM 공식/준공식 아키텍처 개요 자료(Embedded.com "Introduction to ARM/Thumb" 등) 교차 확인(2026-09-10).
- `BX`/`BLX`가 대상 주소의 LSB(비트 0)를 검사해 1이면 Thumb, 0이면 ARM 모드로 전환하며, T bit를 직접 쓰는 것은 예측 불가능한 동작이라는 규칙: ARM 아키텍처 참조 매뉴얼 기반 다수 자료(SoC "Using BX and BLX Instructions Correctly in Thumb Code" 등) 및 링커가 Thumb 함수 주소의 LSB를 1로 설정하는 관례 확인.
- 인터워킹(ARM↔Thumb 혼합 호출) 개념: 위와 동일 출처 기준.
