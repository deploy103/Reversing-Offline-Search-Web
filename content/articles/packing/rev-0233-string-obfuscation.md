## 한 줄 요약
IDA의 Strings 창(`Shift+F12`)이나 `strings` 명령어로 봤을 때 `"Enter password"`, `"Correct!"` 같은 사람이 읽을 수 있는 문자열이 하나도 안 보인다면, 그 문자열들은 삭제된 게 아니라 **바이너리 안에 암호화/인코딩된 바이트로 저장되어 있다가 실행 중(런타임)에 원래 값으로 복원**되는 경우가 대부분이며, 이 복원 루프를 찾아 읽거나 직접 실행시켜서 원문을 얻는 것이 핵심 대응법이다.

## 언제 검색해야 하나
- IDA/Ghidra의 Strings 창을 열었는데 결과가 거의 없거나 의미 없는 랜덤 문자열뿐일 때
- Linux 바이너리에 `strings ./chall`을 돌렸는데 플래그나 비교 문구가 하나도 안 나올 때
- 디컴파일된 코드에 `for` 루프 안에서 `byte[i] ^= key` 같은 패턴이 보이는데 왜 있는지 모를 때
- 함수 안에서 `mov byte ptr [rbp-1], 'H'`, `mov byte ptr [rbp-2], 'e'`처럼 문자를 한 글자씩 스택에 쓰는 코드가 반복될 때
- 정답 비교 로직 근처에 이상하게 큰 바이트 배열 상수가 있는데 문자열처럼 안 보일 때

## 핵심 개념
문자열 난독화는 패커/프로텍터 수준의 복잡한 기법이 아니라, CTF 크랙미 제작자가 "그냥 Strings 창 한 번 보고 답을 찾는 것"을 막기 위해 흔히 넣는 가장 저비용 방어책이다. 근본 원리는 항상 같다: **원래 문자열을 어떤 규칙으로 변형해서 바이너리(.rodata/.data 섹션)에 저장해 두고, 프로그램이 그 문자열을 실제로 써야 하는 시점 직전에 원래대로 되돌리는 코드를 실행한다.** 그 변형 규칙이 바로 분석가가 찾아야 할 "복호화 로직"이다.

### 자주 보는 패턴 네 가지

**1) 단순 XOR 인코딩**
가장 흔한 방식이다. 컴파일 시점에 원본 문자열의 각 바이트에 고정된 키(1바이트 또는 여러 바이트 반복)를 XOR 해서 저장해 두고, 실행 시 같은 키로 다시 XOR하면 원본이 복원된다(XOR은 자기 자신의 역연산이라 `A ^ K ^ K = A`). 디컴파일 코드에서는 대략 이런 모습이다.
```c
for (i = 0; i < len; i++)
    buf[i] = enc[i] ^ key[i % keylen];
```
키가 한 바이트 상수(`^ 0x37` 등)면 IDA/Ghidra에서 상수를 바로 확인할 수 있고, 여러 바이트짜리 키 배열이면 그 배열 자체도 데이터 섹션에서 찾을 수 있다.

**2) 스택 문자열 (stack string)**
문자열을 아예 데이터 섹션에 상수로 두지 않고, 함수 진입 시 로컬 변수(스택) 위에 한 바이트씩 `mov` 명령으로 채워 넣는 방식이다. 컴파일러가 짧은 문자열을 최적화하면서 자연스럽게 이런 코드를 만들기도 하지만, 난독화 목적으로 일부러 이렇게 작성하는 경우도 많다. 이 경우 데이터 섹션에는 완성된 문자열이 아예 존재하지 않으므로 Strings 창에서 절대 안 보인다. 어셈블리를 직접 읽으면서 `mov byte ptr [rbp-0x10], 'p'`, `mov byte ptr [rbp-0xf], 'a'`, `mov byte ptr [rbp-0xe], 's'` ... 순서를 이어 붙이면 원문이 나온다.

**3) Base64/커스텀 인코딩**
`"UGFzc3dvcmQxMjM="`처럼 그 자체로는 읽을 수 있지만 원문이 아닌 인코딩된 문자열이 보이는 경우다. Strings 창에는 뜨지만 사람이 읽어도 의미를 알 수 없다. 코드 안에 base64 디코드 함수(문자 매핑 테이블, `>> 6`/`& 0x3F` 같은 비트 연산)가 있는지 확인하면 된다.

**4) 조각내서 런타임에 이어 붙이기**
`"pass"`, `"word"`처럼 짧은 조각들을 따로따로 저장해 뒀다가 `strcat`/`sprintf`로 실행 중에 하나로 합치는 방식. 각 조각은 Strings 창에 다 보이지만, 완성된 전체 문자열은 안 보이기 때문에 처음 보면 당황하기 쉽다.

## 화면/코드에서 보이는 징후
- IDA Strings 창(`Shift+F12`)에 실행 파일 크기에 비해 문자열 개수가 비정상적으로 적다.
- `.rodata`/`.data` 섹션에 사람이 못 읽는 랜덤 바이트 배열이 있는데, 크기가 딱 "비밀번호 길이 + 몇 바이트" 정도로 의심스럽다.
- 함수 안에 반복문이 있고, 루프 카운터로 배열을 순회하며 XOR/ADD/SUB/ROL 같은 연산을 바이트 단위로 적용한다.
- 디컴파일 결과에 `sub_401230(enc_buf, 16, 0x5A)`처럼 "버퍼, 길이, 키로 추정되는 상수" 세 인자를 받는 함수 호출이 정답 비교 직전에 있다.
- 문자열 비교(`strcmp`, `memcmp`) 직전에 위와 같은 복호화 함수 호출이 항상 선행된다.

## 가장 먼저 할 것
1. Strings 창/명령어로 "정말 아무것도 없는지" 먼저 확인한다. 완전히 없다면 스택 문자열이나 XOR 인코딩을 의심한다.
2. 랜덤해 보이는 바이트 배열이 있다면 그 배열을 참조(xref)하는 함수를 찾는다. IDA에서 데이터 위에 커서를 놓고 `X`를 누르면 그 데이터를 사용하는 코드 위치로 바로 이동할 수 있다.
3. 그 함수 안에서 반복문과 바이트 단위 연산(`xor`, `add`, `sub`, `rol`, `ror`)을 찾는다. 이것이 복호화 루틴이다.
4. 정적으로 키와 알고리즘을 파악하기 어렵다면, **굳이 손으로 풀지 말고 디버거로 그 함수 실행이 끝난 직후 지점에 브레이크포인트를 걸어 복호화된 결과를 메모리에서 직접 읽는다.** 이 방식이 실전에서 가장 빠르고 실수가 적다.

## 단계별 절차
1. IDA Strings 창 또는 `strings -a ./binary`로 문자열 존재 여부를 확인한다.
2. 문자열이 없다면 `.rodata`/`.data` 섹션을 직접 훑어보며 의심스러운 바이트 배열을 찾는다(Hex View, `x64dbg`의 Dump 창, 또는 `objdump -s -j .rodata ./binary`).
3. 그 배열을 사용하는 함수를 xref로 찾아 디컴파일한다.
4. 복호화 루프의 키와 연산을 코드에서 읽어낸다. 여러 바이트 키면 배열 시작 주소도 같이 적어둔다.
5. 정적으로 직접 계산하기 번거로우면, 그 함수의 리턴 직후(또는 복호화 루프가 끝나는 지점)에 브레이크포인트를 걸고 프로그램을 실제로 실행한다.
6. 브레이크포인트에서 멈추면 복호화된 문자열이 저장된 버퍼 주소를 찾아 메모리 뷰에서 문자열로 읽는다(x64dbg는 Dump 창에서 주소 우클릭 → "Follow in Dump", GDB는 `x/s 0x주소`).
7. Base64로 의심되면 파이썬 등으로 직접 디코딩해서 확인한다(`python3 -c "import base64; print(base64.b64decode('...'))"`).

## 명령어/단축키
- IDA: `Shift+F12`(Strings 창), `X`(Xrefs to로 데이터 사용처 찾기), `A`(바이트 배열을 문자열로 재해석), `F5`(디컴파일)
- x64dbg: 복호화 루프 끝 주소에 `F2`로 브레이크포인트, `F9` 실행, Dump 창에서 결과 버퍼 주소 우클릭 → "Follow in Dump" → 문자열로 표시
- GDB/Pwndbg: `break *0x주소`, `run`, `x/s $rax`(또는 결과가 담긴 레지스터/메모리 주소), `x/32xb 0x주소`(바이트 단위로 직접 확인)
- Linux: `strings -a -n 4 ./binary`(최소 길이 4바이트 이상 문자열만), `objdump -s -j .rodata ./binary`(섹션 raw 덤프)

## 출력 해석
- `x/s` 결과가 `0x...: "flag{...}"`처럼 정상적인 ASCII로 보이면 복호화가 성공적으로 끝난 시점을 잘 잡은 것이다.
- 여전히 랜덤 바이트로 보인다면 브레이크포인트 위치가 복호화 루프보다 앞선 시점일 수 있으니, 루프를 한 단계(Step Over, `F8`/`next`)씩 지나가며 다시 확인한다.
- base64 디코드 결과가 여전히 이상하면 URL-safe 변형(`+`/`/` 대신 `-`/`_`)이거나 패딩(`=`)이 빠진 커스텀 알파벳일 수 있다. 코드에서 사용하는 문자 매핑 테이블을 다시 확인한다.

## 흔한 실수
- Strings 창에 안 보인다고 "문자열이 아예 없는 프로그램"이라고 단정하고 분석을 포기하는 것.
- XOR 키를 한 바이트로 가정하고 계산했는데 실제로는 여러 바이트가 반복되는 키였던 경우 — 키 배열의 실제 길이를 코드에서 다시 확인해야 한다.
- 복호화 루프를 손으로 계산하려다 오프바이원(off-by-one) 실수를 하는 것 — 가능하면 디버거로 직접 결과를 읽는 편이 훨씬 안전하다.
- 조각내서 이어 붙이는 방식인 줄 모르고 짧은 문자열 하나만 보고 "이게 답인가?" 오판하는 것.

## 막혔을 때 다음 체크
- 복호화 함수를 찾았는데 어디서 호출되는지 모르겠다면 → 그 함수 시작 주소에서 `X`(Xrefs to)로 호출자를 역추적한다.
- 브레이크포인트를 걸 위치를 못 정하겠다면 → 정답 비교(`strcmp`/`memcmp`) 함수를 먼저 찾고, 그 직전 인자로 들어가는 버퍼가 어디서 채워지는지 거슬러 올라간다.
- 여러 함수에 걸쳐 문자열이 조각조각 흩어져 있다면 → 각 조각의 xref를 모두 모아 실행 순서대로 정리한 뒤 이어 붙인다.
- 도무지 정적으로 이해가 안 되면 → 일단 실행해서 관찰하는 동적 분석으로 전환한다(`REV-0241` 참고).

## 미니 예제
**예제 1 — 1바이트 XOR 디코딩**
```c
// 디컴파일 결과 예시
char enc[9] = {0x1D, 0x08, 0x01, 0x08, 0x0D, 0x02, 0x0C, 0x0A, 0x00};
for (int i = 0; i < 8; i++)
    enc[i] ^= 0x6D;
// 이제 enc에는 "password" 가 들어있음
```

**예제 2 — 스택 문자열 조립**
```asm
mov     byte ptr [rbp-8], 'f'
mov     byte ptr [rbp-7], 'l'
mov     byte ptr [rbp-6], 'a'
mov     byte ptr [rbp-5], 'g'
mov     byte ptr [rbp-4], '{'
```
이런 코드를 순서대로 읽으면 `"flag{"`가 스택 위에서 조립되고 있음을 알 수 있다.

**예제 3 — 디버거로 결과만 확인 (GDB)**
```text
pwndbg> break *0x401234
pwndbg> run
pwndbg> x/s $rax
0x7ffee...:  "flag{stack_str1ng_1s_ez}"
```
