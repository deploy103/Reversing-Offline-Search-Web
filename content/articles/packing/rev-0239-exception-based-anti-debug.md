## 한 줄 요약
예외(exception)를 발생시키고 그 예외가 "디버거에게 먼저 가로채지는지, 아니면 프로그램 자신의 핸들러가 먼저 받는지"를 이용해 디버거의 존재를 판단하는 기법으로, 대표적으로 `int3`(소프트웨어 브레이크포인트) 자가 삽입과 Windows SEH(Structured Exception Handling) 트릭 두 갈래가 있다.

## 언제 검색해야 하나
- 디버거로 프로그램을 실행하면 정상 실행과 다르게 예외 메시지가 뜨거나 프로그램이 종료될 때
- 코드 중간에 `int3`(바이트 `0xCC`) 명령이 함수 로직 안에 삽입되어 있는데 왜 있는지 이해가 안 될 때
- Windows 프로그램에서 `__try`/`__except` 블록이나 `SetUnhandledExceptionFilter` 호출이 안티디버깅 목적처럼 이상하게 쓰인 걸 볼 때
- 디버거의 "Pass exception to program"(예외를 프로그램에 전달) 옵션 설정에 따라 프로그램 동작이 달라지는 것을 경험할 때

## 핵심 개념

### 예외 처리의 기본 원리와 디버거의 위치
프로그램 실행 중 `int3`, 0으로 나누기, 잘못된 메모리 접근 같은 예외가 발생하면, 운영체제는 그 예외를 처리할 핸들러를 찾는다. **디버거가 프로세스에 붙어 있으면, 예외는 먼저 디버거에게 전달된다.** 디버거가 "이건 내가 처리할 예외가 아니다"라고 판단해 프로그램에 넘겨주면(Windows에서는 `DBG_EXCEPTION_NOT_HANDLED`로 계속 진행), 그제서야 프로그램 자체의 예외 핸들러(SEH 체인 등)가 실행된다. **디버거가 없으면 예외는 곧바로 프로그램의 핸들러(또는 OS의 기본 처리기)로 간다.** 이 "디버거가 먼저 볼 수 있다"는 구조 자체를 역이용하는 것이 예외 기반 안티디버깅의 핵심이다.

### 1) int3 자가 삽입 (소프트웨어 브레이크포인트 자가 탐지)
`int3`(기계어 바이트 `0xCC`)는 디버거가 소프트웨어 브레이크포인트를 걸 때 실제로 대상 명령의 첫 바이트를 `0xCC`로 바꿔치기하는 방식으로 구현된다(원래 명령 바이트는 디버거가 따로 저장해둔다). 이 원리를 뒤집어서, 크랙미가 코드 안에 **자기 스스로 `int3`을 미리 심어두고**, 그 예외가 발생했을 때 어떤 핸들러가 이를 처리하는지로 디버거 존재 여부를 판단한다.
```asm
int3                 ; 스스로 발생시키는 소프트웨어 예외
; 디버거가 없으면: 프로그램 자체의 예외 핸들러(SEH 등)로 바로 감
; 디버거가 있으면: 디버거가 먼저 이 예외를 가로채서 화면에 "브레이크포인트"로 표시하고 멈춤
```
좀 더 정교한 변형은 **코드 자체를 스캔해서 `0xCC` 바이트가 원래 있으면 안 되는 위치에 있는지 검사**하는 것이다. 이는 "디버거가 소프트웨어 브레이크포인트를 심어놨는지"를 직접 찾아내는 방식으로, 코드 섹션을 통째로 읽어 각 바이트를 검사하는 루프로 나타난다.
```c
for (int i = 0; i < code_len; i++) {
    if (code[i] == 0xCC) {
        // 누군가 브레이크포인트를 심어놨다 -> 디버거 의심
    }
}
```

### 2) SEH(Structured Exception Handling) 트릭 (Windows)
Windows는 `__try`/`__except` 블록으로 구조화된 예외 처리를 지원한다. 안티디버깅 코드는 이 구조를 다음과 같이 악용한다.
```c
__try {
    // 일부러 예외를 발생시키는 코드 (예: 0으로 나누기, 잘못된 포인터 접근)
    int x = 1 / zero;
} __except (EXCEPTION_EXECUTE_HANDLER) {
    // 디버거가 없으면 여기로 정상적으로 넘어와서 진짜 로직 실행
    real_logic();
}
```
디버거가 붙어 있으면 예외 발생 시점에 디버거가 먼저 멈춰버리기 때문에(디버거 설정에 따라 다르지만 기본적으로 첫 기회 예외에서 멈추는 경우가 많다), `__except` 블록으로 자연스럽게 넘어가지 못하고 분석가가 수동으로 "계속 실행"(Pass exception)을 눌러야 하는 상황이 벌어진다. 정교한 크랙미는 아예 `__except` 블록 안에 실제 핵심 로직(정답 문자열 복호화 등)을 넣어두어서, 디버거로 예외를 제대로 통과시키지 않으면 그 로직 자체가 실행되지 않도록 만들기도 한다.

또 다른 변형은 `SetUnhandledExceptionFilter()`로 커스텀 예외 필터를 등록해두고, 디버거가 붙어 있으면 이 필터가 아예 호출되지 않는다는 점(디버거가 예외를 가로채므로)을 이용해 "필터가 호출됐는지 여부"로 디버거 유무를 판단하는 것이다.

### 3) Trap Flag / 하드웨어 브레이크포인트 관련 변형
EFLAGS의 Trap Flag(TF) 비트를 직접 세팅해서 강제로 싱글스텝 예외(`EXCEPTION_SINGLE_STEP`)를 스스로 발생시키고, 그 예외가 어떻게 처리되는지로 디버거를 감지하는 기법도 있다. 또한 디버그 레지스터(`DR0`~`DR3`, `DR7`)를 직접 읽어서 값이 0이 아니면 "하드웨어 브레이크포인트가 걸려 있다"고 판단하는 방식도 예외 기반 기법과 같은 계열로 묶인다(디버그 레지스터를 읽으려면 커널 지원이 필요하므로 보통 `GetThreadContext()` API를 통해 접근한다).

## 화면/코드에서 보이는 징후
- 디스어셈블리 중간에 함수 로직과 무관해 보이는 `int3`(`CC`) 바이트가 단독으로 있다.
- `__try`/`__except` 블록이 있는데, 그 안에서 일부러 예외를 유발하는 코드(널 포인터 역참조, 0 나눗셈)가 보인다.
- `SetUnhandledExceptionFilter` 호출이 있는데 등록하는 필터 함수 안에 핵심 로직이 들어있다.
- 디버거의 예외 처리 옵션(x64dbg의 "Ignore following exceptions" 등)을 바꿨더니 프로그램 동작이 달라진다.
- IDA에서 코드 섹션 전체를 바이트 단위로 훑는 루프가 있고, 비교 대상이 `0xCC`다.

## 가장 먼저 할 것
1. 프로그램이 예외로 멈추면, 디버거 화면에 표시되는 예외 종류(Access Violation, Breakpoint, Single Step 등)를 먼저 확인한다.
2. 그 예외가 발생한 주소 근처에 `int3`나 의도적인 오류 유발 코드가 있는지 디스어셈블리를 확인한다.
3. `__except`/`SetUnhandledExceptionFilter` 관련 코드가 있는지 함수 구조를 살펴본다.

## 단계별 절차
1. 디버거에서 예외가 발생하면 우선 "예외를 프로그램에 전달"(Pass to application, x64dbg는 Shift+F9, GDB는 시그널 전달 옵션)해서 정상적으로 SEH/시그널 핸들러까지 흘러가도록 해본다.
2. 예외 발생 주소를 기록하고, IDA에서 같은 주소를 찾아 코드 문맥을 확인한다.
3. `int3` 자가 삽입이라면, 그 명령이 정말 예외를 "이용"하는 것인지(디버거 유무로 분기가 달라지는지) 아니면 단순한 안티-디스어셈블리 트릭(디스어셈블러를 혼란시키기 위한 쓰레기 바이트)인지 구분한다.
4. SEH 트릭이라면 `__except` 블록의 시작 주소를 찾아 그 안의 로직을 디컴파일해서, 디버거 없이 실행됐을 때만 도달 가능한 진짜 코드가 무엇인지 파악한다.
5. 우회 실습(자신의 크랙미에 한함)은 대개 "예외를 항상 프로그램에 정상 전달"하도록 디버거 옵션을 맞추거나, 예외 유발 코드를 건너뛰고 `__except` 블록으로 직접 실행 흐름을 옮기는 방식으로 진행한다.

## 명령어/단축키
- x64dbg: 메뉴 Options → Preferences → Exceptions에서 특정 예외를 애플리케이션에 자동으로 전달하도록 설정, `Shift+F9`(예외를 프로그램에 전달하며 실행)
- IDA: `Alt+T`(텍스트 검색으로 `CC` 바이트 패턴이나 `int3` 확인), `F5`(디컴파일로 `__try`/`__except` 구조 확인)
- GDB/Pwndbg: `handle SIGTRAP nostop pass`(SIGTRAP을 프로그램에 전달), `catch signal SIGSEGV` 등으로 시그널 발생 시점 관찰

## 출력 해석
- 예외를 프로그램에 전달했을 때 정상 동작(진짜 로직 실행)으로 이어진다면, 그 예외가 "정상 흐름의 일부"로 설계되었다는 뜻이다.
- 예외를 전달하지 않고 디버거가 계속 잡고 있으면 프로그램이 멈춰 있거나 다른 경로로 빠진다면, 이것이 디버거 탐지 트릭이 작동한 결과다.

## 흔한 실수
- 디버거가 예외에서 멈췄을 때 "버그가 났다"고 오해하고 그냥 재시작하는 것 — 실제로는 의도된 안티디버깅 트릭일 수 있다.
- 예외를 무조건 무시(Pass)하기만 하고 그 예외가 어떤 코드 경로로 이어지는지 확인하지 않는 것.
- `int3` 자가 삽입과 디버거가 심어놓은 브레이크포인트를 혼동하는 것 — 원래 코드에 있던 `0xCC`인지, 자신이 건 브레이크포인트인지 구분해야 한다.
- SEH 구조 자체를 모르는 상태로 `__except` 블록을 그냥 지나치는 것 — Windows 예외 처리 메커니즘에 대한 기본 이해가 필요하다.

## 막혔을 때 다음 체크
- 예외가 왜 발생하는지 모르겠다면 → 발생 주소의 직전 명령을 확인해 의도적인 오류 유발 코드(0 나눗셈, 잘못된 포인터)인지 본다.
- 예외를 전달했는데도 진짜 로직에 도달하지 못한다면 → SEH 체인이 여러 겹일 수 있으니 `__except` 블록 안에 또 다른 예외 유발 코드가 있는지 확인한다.
- 소프트웨어 브레이크포인트 자체가 문제라면 → 하드웨어 브레이크포인트(디버그 레지스터 기반)로 바꿔서 코드 바이트를 건드리지 않고 관찰하는 방법도 있다.
- 리눅스 환경이라면 SEH 대신 시그널(`SIGTRAP`, `SIGSEGV`)과 시그널 핸들러(`sigaction`) 기반의 유사한 트릭이 쓰이므로, `handle` 명령으로 시그널 전달 여부를 조정하며 관찰한다.

## 미니 예제
**예제 1 — SEH 트릭으로 진짜 로직 숨기기**
```c
__try {
    int* p = NULL;
    *p = 1; // 의도적으로 access violation 발생
} __except (EXCEPTION_EXECUTE_HANDLER) {
    // 디버거 없이 실행돼야 여기 도달
    reveal_flag();
}
```

**예제 2 — int3 자가 스캔**
```c
BOOL has_software_breakpoint(BYTE* code, size_t len) {
    for (size_t i = 0; i < len; i++) {
        if (code[i] == 0xCC) return TRUE;
    }
    return FALSE;
}
```
