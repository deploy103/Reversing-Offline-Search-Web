## 한 줄 요약
패킹된 것으로 의심되는 바이너리를 받았을 때 "확인 → 식별 → 자동 시도 → 수동/동적 전환 판단"의 순서로 체크리스트를 따라가면, 이미 packing 카테고리에 흩어진 개별 문서(REV-0224~0241)를 어떤 순서로 봐야 할지 헤매지 않고 빠르게 다음 행동을 정할 수 있다.

## 언제 검색해야 하나
- 패킹된 것 같은 파일을 처음 받았는데 어디서부터 손대야 할지 막막할 때
- REV-0224~0241 문서를 하나씩 읽긴 했는데, 실제 순서대로 어떻게 적용해야 할지 흐름이 잘 안 잡힐 때
- CTF 시간 제한 안에서 "언패킹에 얼마나 시간을 쓸지" 판단 기준이 필요할 때
- 이미 언패킹을 시도하다 막혔는데, 지금까지 뭘 확인했고 다음에 뭘 확인해야 하는지 체크리스트로 되짚고 싶을 때

## 핵심 개념
언패킹은 "무조건 완전히 풀어야 하는 작업"이 아니라, 목표(정적 분석용 완전 복원 vs 특정 로직만 확인)에 따라 중간에 멈춰도 되는 작업이다. 아래 체크리스트는 이 판단을 매 단계마다 명시적으로 포함시켜, 불필요하게 시간을 쓰지 않도록 설계했다.

| 단계 | 체크 항목 | 참고 문서 |
|---|---|---|
| 1 | 패킹 의심 징후(엔트로피, import 개수, 섹션 이름)를 확인했는가 | REV-0224 |
| 2 | UPX 여부를 확정했는가(`strings`, DIE, `upx -l`) | REV-0225 |
| 3 | UPX가 아니라면 다른 알려진 패커 시그니처와 대조했는가 | REV-0931 |
| 4 | 자동 언패커(`upx -d` 등)로 풀리는가 | REV-0226 |
| 5 | 자동 언패커가 없다면, 완전 언패킹이 정말 필요한 목표인지 재확인했는가 | REV-0227, REV-0935 |
| 6 | 완전 언패킹이 필요 없다면 동적 분석으로 전환했는가 | REV-0241 |
| 7 | 완전 언패킹이 필요하다면 OEP 탐색 → 메모리 덤프 → IAT 복구 순서로 진행했는가 | REV-0227 |
| 8 | 진행 중 안티디버깅에 막히지 않았는가 | REV-0932 |

## 화면/코드에서 보이는 징후
이 문서는 GUI/코드 화면이 아니라 작업 순서 자체를 다룬다. 체크리스트 각 항목에서 "예/아니오"로 답하며 다음 항목으로 넘어가면 된다.

## 가장 먼저 할 것
1번(REV-0224 패킹 의심 징후 확인)부터 시작한다. 이미 패킹이 확실하다고 알고 있는 상태라면 2번(UPX 여부 확정)부터 시작해도 된다.

## 단계별 절차
**1) 패킹 의심 확인**: DIE로 파일을 열어 엔트로피와 패커/프로텍터 이름을 확인한다(REV-0224, REV-0933).
**2) UPX 확정 시도**: `strings`/`upx -l`로 UPX 여부를 확인한다(REV-0225).
**3) UPX면 자동 언패킹**: `upx -d`로 바로 푼다(REV-0226). 성공하면 체크리스트 종료.
**4) UPX가 아니면 시그니처 재대조**: REV-0931 표에서 다른 알려진 패커인지 확인하고, 해당 패커의 공식 언패커가 있는지 찾는다.
**5) 자동 도구가 없으면 목표 재확인**: "완전한 정적 분석용 파일이 꼭 필요한가?"를 자문한다. 아니라면 6번, 맞다면 7번으로 간다.
**6) 동적 분석 전환**: REV-0241 절차대로 디버거에서 직접 실행하며 필요한 로직만 확인한다. 체크리스트 종료.
**7) 완전 언패킹 진행**: REV-0227의 OEP 탐색 → 메모리 덤프 → IAT 복구 순서를 따른다. 이 과정에서 안티디버깅에 막히면 8번을 확인한다.
**8) 안티디버깅 대응**: REV-0932 분류표로 어떤 종류인지 확인하고 해당 세부 문서(REV-0234~0240, REV-0529)로 이동한 뒤 7번으로 복귀한다.

## 명령어/단축키
```bash
strings sample | grep -i upx
upx -l sample
upx -d sample
```
- DIE: 파일 드래그 → 결과란/엔트로피 확인
- x64dbg: OEP 탐색 시 `F9`(Run), 메모리 쓰기 브레이크포인트, Scylla 플러그인(덤프/IAT 복구)

## 출력 해석
- 3번 단계(`upx -d`)가 `Unpacked 1 file.`을 출력하면 체크리스트가 그대로 종료된다 — 더 진행할 필요가 없다.
- 5번 단계에서 "동적 분석만으로 충분하다"는 결론이 나오는 경우가 CTF에서는 오히려 다수다. 이 경우 7번/8번(완전 언패킹)으로 넘어가지 않아도 된다는 것 자체가 이 체크리스트의 핵심 절약 포인트다.

## 흔한 실수
- 목표 재확인(5번) 단계를 건너뛰고 무조건 완전 언패킹을 시도하다가 시간을 다 쓰는 것.
- UPX 확정(2번) 없이 곧바로 수동 언패킹(7번)으로 뛰어드는 것 — 대부분의 UPX는 몇 초 안에 자동으로 풀린다.
- 안티디버깅(8번)에 막혔을 때 원인 분류 없이 무작정 여러 방법을 시도하는 것 — REV-0932로 먼저 분류하면 시간이 절약된다.

## 막혔을 때 다음 체크
- 1~2단계에서 막히면(패킹 여부/UPX 여부 판단 자체가 어려우면) → REV-0224, REV-0933을 다시 확인한다.
- 4단계에서 시그니처는 찾았는데 자동 도구가 없다면 → REV-0935에서 상용 프로텍터인지 먼저 확인한다.
- 7단계 OEP 탐색이 막히면 → REV-0937 패커별 OEP 특징 빠른 참조를 확인한다.

## 미니 예제
```text
[받은 파일] chall.exe

1. DIE 확인 -> Entropy 7.9, Packer: Unknown
2. strings 확인 -> "UPX!" 발견 -> UPX 확정
3. upx -d chall.exe -> Unpacked 1 file. -> 체크리스트 종료, 바로 IDA로 정적 분석 진행
```

## 관련 글
- REV-0224 — 패킹된 바이너리인지 의심하는 기준
- REV-0225 — UPX인지 확인하는 법
- REV-0226 — UPX 기본 언패킹
- REV-0227 — 수동 언패킹 개념 OEP와 Dump
- REV-0241 — 패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환
- REV-0931 — 흔한 패커 시그니처 빠른 참조표(UPX/ASPack/PECompact 등)
- REV-0932 — 안티디버깅 기법 종류 빠른 참조표(정리본)
- REV-0935 — VMProtect/Themida 등 상용 프로텍터 존재만 알아두는 참조표
- REV-0937 — 패커별 OEP 특징 빠른 참조 (예정)

## 출처/검증
- 체크리스트 순서와 "목표 재확인" 단계의 실용적 접근은 다수의 공개 CTF writeup 및 리버싱 교육 자료에서 공통적으로 강조하는 "완전 언패킹보다 목적에 맞는 최소 분석" 원칙을 정리한 것이다(2026-09-09 검증).
- 개별 도구/명령의 정확한 동작은 각 하위 문서(REV-0224~0227, REV-0241)에서 별도로 검증되어 있다.
