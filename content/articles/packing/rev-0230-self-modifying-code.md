## 한 줄 요약
Self-modifying code(자기 수정 코드, SMC)는 프로그램이 실행되는 도중 자기 자신의 코드 바이트를 직접 읽고 다시 써서(예: XOR 복호화) 바꾸는 기법으로, 디스크에 저장된 상태의 코드는 진짜 실행될 명령과 다르기 때문에 IDA 같은 정적 디스어셈블러를 무력화하는 데 널리 쓰인다.

## 언제 검색해야 하나
- IDA에서 디스어셈블한 코드가 말이 안 되는 명령(잘못된 opcode, 이상한 오퍼랜드)으로 계속 깨져 보일 때
- 코드 섹션에 `VirtualProtect`나 `mprotect` 같은 함수가 호출된 뒤 그 영역에 직접 쓰기(write)가 일어나는 패턴을 발견했을 때
- 디버거로 실행하면서 본 코드와 IDA에서 정적으로 본 코드가 서로 다를 때
- REV-0227에서 말한 압축 해제 스텁의 동작 원리를 더 구체적으로 이해하고 싶을 때 (사실 대부분의 패커 스텁 자체도 self-modifying code의 한 형태다)

## 핵심 개념
일반적으로 실행 파일의 코드 섹션(`.text`)은 "읽기+실행"만 가능하고 "쓰기"는 불가능하게 설정되어 있다(메모리 보호 속성). 이는 실수로 코드를 덮어써서 프로그램이 오동작하는 것을 막기 위한 정상적인 설계다. **Self-modifying code**는 이 관례를 의도적으로 깨는 코드다. 프로그램은 실행 도중 다음과 같은 순서를 밟는다.

1. 코드 섹션의 메모리 보호 속성을 "쓰기 가능"으로 바꾼다(Windows의 `VirtualProtect`, Linux의 `mprotect` API 호출).
2. 자기 자신의 코드 바이트 일부를 계산(주로 XOR, ADD, ROL 같은 단순 연산 반복)해서 원래와 다른 바이트로 덮어쓴다.
3. (선택) 다시 메모리 보호 속성을 "쓰기 불가"로 되돌린다(디버거의 메모리 쓰기 감시를 회피하거나, 정상적인 실행처럼 보이기 위해).
4. 방금 덮어쓴 바로 그 코드 영역을 실행한다.

핵심은 **디스크에 저장된 바이트와 실제로 CPU가 실행하는 바이트가 다르다**는 점이다. IDA나 Ghidra 같은 정적 분석 도구는 디스크 파일(또는 그 파일을 그대로 읽은 메모리 스냅샷)의 바이트만 보고 디스어셈블하므로, self-modifying code 구간은 실제 실행될 명령이 아니라 "수정되기 전의 원본 바이트"를 잘못 디스어셈블하게 된다. 그 결과 화면에는 의미 없는 명령어 나열이나, 심지어 명령어 경계 자체가 어긋난 깨진 디스어셈블리가 나타난다.

이 기법은 패커의 압축 해제 스텁(REV-0226, REV-0227)에서 가장 흔하게 볼 수 있는 형태이지만, 패킹이 아니더라도 특정 함수 하나만 실행 직전에 복호화하는 방식(코드 가상화, 안티 디버깅과 결합된 보호 기법)으로도 널리 쓰인다.

## 화면/코드에서 보이는 징후
- IDA 디스어셈블리에서 특정 구간이 빨간색이나 회색으로 "데이터"처럼 표시되거나, 억지로 코드로 지정(C 키)해도 opcode가 이상하게 잘려서 다음 명령과 경계가 안 맞음
- 코드 안에 `VirtualProtect(addr, size, PAGE_EXECUTE_READWRITE, &oldProtect)` 같은 호출이 있고, 그 직후 반복문에서 `[addr + ecx], al` 같은 형태로 메모리에 직접 쓰기가 일어남
- 같은 주소를 반복적으로 `XOR`, `ADD`, `SUB`, `ROL`/`ROR` 연산으로 갱신하는 짧은 루프가 보이는데, 그 루프가 다루는 메모리 범위가 바로 그 함수 자신이 위치한 코드 영역과 겹침
- x64dbg 같은 디버거로 브레이크포인트를 걸어보면, 같은 주소에서 첫 실행 때와 두 번째 실행 때 디스어셈블리 결과가 서로 다르게 보임
- 메모리 쓰기 브레이크포인트(`Set Memory Breakpoint on Write`)를 코드 섹션에 걸어두면, 실행 중 예상치 못한 시점에 브레이크포인트가 반복적으로 걸림

## 가장 먼저 할 것
정적 디스어셈블리가 이상하게 깨져 보이면, 그 구간을 억지로 계속 재해석하려 하지 말고 **동적으로 실제 실행되는 바이트를 확인**하는 방향으로 전환한다. x64dbg로 그 지점까지 실행한 뒤 실제 메모리 내용을 다시 디스어셈블(Follow in Disassembler)해보면, 복호화가 끝난 뒤의 진짜 코드를 볼 수 있다.

## 단계별 절차

**1) 이상한 디스어셈블리 구간 식별**

IDA에서 코드가 깨져 보이거나 데이터로 잘못 인식된 구간을 찾는다. 그 구간을 가리키는 코드에서 `VirtualProtect`/`mprotect` 호출과 반복적인 메모리 쓰기 루프가 있는지 위아래를 살펴본다.

**2) 디버거로 해당 함수까지 실행**

x64dbg(Windows)나 GDB/Pwndbg(Linux)로 프로그램을 실행하고, 문제의 코드가 호출되기 직전까지 브레이크포인트로 진행시킨다.

**3) 복호화 루프를 한 단계씩 실행하며 관찰**

`F8`(Step Over) 또는 `F7`(Step Into)로 복호화 루프를 통과시킨다. 루프가 끝난 시점에 해당 메모리 영역을 다시 디스어셈블하면 원래 IDA에서 이상하게 보이던 바이트가 정상적인 명령으로 바뀌어 있는 것을 확인할 수 있다.

**4) 복호화된 코드를 IDA로 옮기기(선택)**

디버거에서 복호화가 끝난 시점의 메모리 값을 그대로 복사(덤프)해서, IDA의 해당 주소 바이트를 수동으로 패치(Edit → Patch Program → Change byte)하면, 정적 분석 도구에서도 올바르게 디스어셈블된 코드를 볼 수 있게 된다.

**5) 메모리 쓰기 브레이크포인트로 자동화**

매번 수동으로 스텝하기 번거롭다면, 코드 섹션 전체에 "쓰기 시 중단" 브레이크포인트를 걸어두고 실행하면, self-modifying code가 코드를 바꾸는 정확한 순간마다 자동으로 멈추게 할 수 있다.

## 명령어/단축키
- x64dbg `F7`(Step Into) / `F8`(Step Over) : 복호화 루프를 한 단계씩 실행
- x64dbg 메모리 맵에서 섹션 우클릭 → `Set Memory Breakpoint on Write` : 코드 섹션에 쓰기가 일어나는 순간 자동 중단
- x64dbg에서 주소 우클릭 → `Follow in Disassembler` : 현재 메모리 상태 그대로 다시 디스어셈블해서 보기
- IDA `Edit → Patch Program → Change Byte...` (또는 Hex View에서 직접 편집) : 복호화된 바이트로 정적 데이터베이스를 갱신
- IDA 코드 재해석: 문제 구간에서 `C` 키(코드로 지정), `U` 키(정의 취소 후 재분석)

## 출력 해석
- 복호화 루프 실행 전후로 같은 주소의 바이트 값이 달라졌다면 → self-modifying code가 확실히 동작한 것이다.
- `VirtualProtect`의 세 번째 인자가 `PAGE_EXECUTE_READWRITE`(0x40)라면 → 이후 그 영역에 쓰기와 실행이 모두 가능해졌다는 뜻이므로, 바로 다음에 코드 수정이 일어날 가능성이 매우 높다는 신호다.
- 메모리 쓰기 브레이크포인트가 짧은 루프 동안 수백~수천 번 반복해서 걸린다면 → 바이트 단위로 한 개씩 복호화하는 전형적인 XOR 루프 패턴이다.
- 복호화 후 코드가 다시 원래대로(암호화 상태로) 돌아가는 것이 관찰된다면 → 함수 실행이 끝난 뒤 다시 암호화해서 정적 분석과 메모리 덤프 모두를 방해하려는 의도적인 안티 리버싱 기법이다.

## 흔한 실수
- 정적 디스어셈블리가 깨져 보이는 것을 IDA의 버그나 오류로 오해하고 억지로 수동 재정의만 반복하는 것. 실제로는 해당 바이트가 실행 시점 전까지는 "진짜 코드가 아니기" 때문에 정상적으로 디스어셈블될 수 없는 것이 당연하다.
- 복호화가 끝난 시점을 못 찾고 무작정 스텝 실행만 반복하다가 루프 안에서 지치는 것. `VirtualProtect` 호출과 그 직후의 쓰기 루프의 끝(보통 루프 카운터가 특정 값에 도달하며 빠져나가는 조건 분기)을 먼저 찾아두면 훨씬 빠르다.
- 디버거에서 확인한 복호화된 코드를 IDA에 반영하지 않고 매번 디버거 화면만 보며 분석하는 것. 규모가 큰 함수라면 한 번 복호화된 바이트를 IDA에 패치해두는 것이 이후 분석 속도를 크게 높여준다.
- self-modifying code가 안티 디버깅과 결합되어 있을 수 있다는 점을 간과하는 것. 디버거가 붙어 있는지 감지해서 일부러 잘못된 방식으로 복호화하거나 크래시를 유도하는 경우도 있으므로, 복호화 후 코드가 말이 되는지 반드시 사람이 눈으로 검증해야 한다.

## 막혔을 때 다음 체크
- 복호화 루프를 찾았는데도 결과가 여전히 이상하다면 → 안티 디버깅 체크가 복호화 알고리즘 자체에 영향을 주고 있을 수 있으니, 디버거 탐지 우회를 먼저 시도한다.
- 코드 전체가 아니라 특정 함수 하나만 이런 패턴이라면 → 그 함수가 특별히 중요한 로직(예: 플래그 검증)일 가능성이 높으므로 집중 분석 대상으로 표시해둔다.
- self-modifying code가 아니라 Control Flow Flattening처럼 보인다면(코드는 그대로인데 흐름만 복잡함) → REV-0231을 참고한다.
- 여러 겹의 self-modifying + 가상화가 겹쳐 있어 손으로 따라가기 너무 복잡하다면 → 동적 분석 위주로 전환해서 최종 결과 값(예: 비교되는 플래그 문자열)만 확인하는 실용적 접근을 고려한다.

## 미니 예제
디스어셈블리에서 다음과 같은 코드를 봤다고 하자(x86, 의사코드에 가깝게 정리).

```asm
; VirtualProtect(addr=decode_start, size=0x20, PAGE_EXECUTE_READWRITE, &old)
push offset old_protect
push 0x40              ; PAGE_EXECUTE_READWRITE
push 0x20               ; size
push offset decode_start
call VirtualProtect

mov ecx, 0x20            ; 루프 카운터 = 32바이트
mov esi, offset decode_start
decode_loop:
    xor byte ptr [esi], 0x5A   ; 자기 자신의 코드 바이트를 XOR로 복호화
    inc esi
    loop decode_loop

jmp decode_start          ; 방금 복호화한 코드로 점프해서 실행
```

`decode_start`부터 32바이트가 원래 IDA에서는 의미 없는 opcode로 보였을 것이다. 하지만 이 루프를 실제로 실행해보면 각 바이트가 `0x5A`와 XOR되어 다른 값으로 바뀌고, 그 결과가 진짜 실행될 명령이다. x64dbg에서 `loop decode_loop`를 다 통과한 직후 `decode_start` 주소를 다시 디스어셈블하면, 예를 들어 원래 `db 0xAA, 0x12, ...`처럼 보이던 것이 `push ebp; mov ebp, esp; ...`처럼 정상적인 함수 시작 코드로 바뀌어 있는 것을 확인할 수 있다.

## 관련 글
- REV-0227 — 수동 언패킹 개념 OEP와 Dump
- REV-0231 — Control Flow Flattening 기초
- REV-0232 — Opaque Predicate 기초

## 출처/검증
- Self-modifying code의 동작 원리(메모리 보호 속성 변경 후 코드 바이트 직접 수정)와 이것이 정적 디스어셈블러를 무력화하는 이유는 x86/x64 메모리 보호 모델(Windows `VirtualProtect`, POSIX `mprotect`)의 공식 문서(learn.microsoft.com, man7.org)를 기준으로 정리했다(2026-09-08 검증).
- 패커 스텁이 self-modifying code의 대표적 실사례라는 점, 그리고 안티 디버깅과 결합되는 경향은 다수의 공개 리버싱/악성코드 분석 교육 자료에서 공통적으로 다루는 내용을 요약했다.
- 실제 opcode/레지스터 사용은 컴파일러와 패커 구현에 따라 크게 달라지므로, 예제는 개념 설명을 위한 단순화된 형태이며 실제 샘플에서는 훨씬 복잡할 수 있다.
