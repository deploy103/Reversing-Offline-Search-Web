## 한 줄 요약
REV-0233(문자열 난독화)에서 다룬 개념을 실전에서 자동화하려면, 암호화된 각 문자열 사용 직전에 반복적으로 호출되는 복호화 함수를 하나 찾아 그 알고리즘을 파악한 뒤, 같은 로직을 Python으로 재구현해서 바이너리 안의 모든 암호화된 문자열을 한 번에 복호화하는 스크립트를 만드는 것이 목표다.

## 언제 검색해야 하나
- `strings packed.exe`를 돌려도 의미 있는 문자열이 거의 안 나오는데, 실제로 실행하면 메시지박스나 콘솔에 평문 메시지가 뜰 때
- IDA에서 문자열 참조 부분이 `"Enter password:"` 같은 텍스트가 아니라 바이트 배열(`db 5A, 3F, 12, ...`)로만 보일 때
- 여러 함수 앞에서 똑같이 생긴 함수 하나가 반복적으로 호출되는 패턴을 발견했을 때(문자열 복호화 함수일 가능성)
- 문자열이 수백 개라서 하나씩 디버거로 실행해서 확인하기엔 너무 비효율적이라고 느껴질 때

## 핵심 개념

### 왜 문자열을 암호화하는가
바이너리 안의 평문 문자열은 리버서에게 가장 쉬운 단서다. `"Correct password!"`, `"http://malicious-c2.example"` 같은 문자열 하나만 찾아도 코드의 의도를 짐작할 수 있다. 그래서 malware나 CTF 문제 제작자는 이런 "쉬운 단서"를 없애기 위해 문자열을 컴파일 시점에 암호화해서 저장하고, 실행 중 그 문자열이 필요한 순간에만 복호화해서 스택이나 힙에 잠깐 풀어놓는다.

### 복호화 함수를 찾는 두 가지 경로
1. **Xref(교차 참조)로 찾기**: IDA/Ghidra에서 암호화된 것으로 보이는 바이트 배열을 하나 클릭하고 `Xref to`(단축키 `X`)를 눌러 그 데이터를 참조하는 코드 위치를 찾는다. 그 코드가 바로 복호화 함수(또는 복호화 함수를 호출하는 지점)일 가능성이 높다.
2. **반복 호출 패턴으로 찾기**: 서로 다른 여러 함수의 시작 부분에서 매번 똑같은 함수 하나가 호출되고, 그 함수가 항상 (포인터, 길이) 또는 (포인터, 키) 형태의 인자를 받는다면 이는 전형적인 "문자열 복호화 헬퍼 함수" 패턴이다.

### 복호화 알고리즘 파악하기
복호화 함수를 찾았다면 그 내부를 읽어 알고리즘을 특정한다. CTF/malware에서 가장 흔한 것은 다음 순서로 시도해볼 가치가 있다.
- **단순 XOR(고정 키)**: `byte[i] ^= key` 형태. 가장 흔하다.
- **XOR with rolling key**: 키가 인덱스에 따라 바뀌거나(`key = base_key + i`), 이전 바이트 값에 의존하는 경우.
- **RC4**: 키 스케줄링 단계(`S-box` 256바이트 배열 초기화)가 눈에 띄면 RC4일 가능성이 높다.
- **Base64 + XOR 조합**: 디코딩 후 다시 XOR하는 2단계 구조.
- **간단한 치환/회전(ROL/ROR)**: `rol al, 3` 같은 명령이 반복되면 비트 회전 기반이다.

### 자동 복호화 스크립트 만들기
알고리즘과 키를 특정했다면, IDA에서 확인한 암호화된 바이트 배열들을 전부 뽑아(`Export data` 또는 직접 파일 오프셋 읽기) Python으로 동일한 로직을 재구현해 한 번에 복호화한다. IDAPython을 쓰면 IDA 안에서 직접 각 문자열의 실제 주소에 복호화 결과를 코멘트로 붙여 넣을 수도 있어, 재분석 없이 바로 읽을 수 있는 형태로 만들 수 있다.

## 화면/코드에서 보이는 징후
- IDA Strings 창(`Shift+F12`)에 의미 있는 문자열이 거의 없음
- 특정 함수 진입 직후 항상 `call sub_4011A0`처럼 같은 서브루틴이 호출되고, 그 서브루틴의 파라미터가 데이터 섹션의 바이트 배열 주소인 경우
- 그 서브루틴 내부에 `xor`, `rol`/`ror`, 또는 256바이트 배열 초기화 루프(RC4 S-box)가 보임
- x64dbg로 그 함수 반환 직후 반환된 포인터를 Dump 창에서 보면 평문 문자열이 나타남

## 가장 먼저 할 것
암호화된 것으로 의심되는 데이터를 하나 클릭하고 `X`(Xref to)로 참조하는 코드부터 찾는다. 그 코드가 곧 복호화 함수이거나, 복호화 함수를 호출하는 지점이다. 함수를 찾았으면 x64dbg로 실제 실행시켜 반환값(복호화된 문자열 포인터)이 무엇을 가리키는지부터 확인해 알고리즘 파악의 방향을 잡는다.

## 단계별 절차
1. IDA Strings 창이 비어있음을 확인, 대신 데이터 섹션에서 의심스러운 바이트 배열 위치 확인
2. 바이트 배열에 `X`(Xref to)로 참조 함수 찾기
3. 그 함수(복호화 함수로 추정)를 x64dbg에서 브레이크포인트 걸고 실행
4. 함수 진입 시 인자(포인터, 길이, 키 등)와 반환 시 결과(복호화된 문자열)를 Dump 창에서 비교 관찰
5. 함수 내부 디스어셈블리를 읽고 알고리즘 종류 특정(XOR/RC4/치환 등)
6. 같은 로직을 Python으로 재구현
7. 바이너리에서 암호화된 모든 문자열 데이터를 추출(오프셋/길이 목록 확보)
8. Python 스크립트로 일괄 복호화, 결과를 텍스트 파일 또는 IDA 코멘트로 반영

## 명령어/단축키
- IDA: `X`(Xref to), `Shift+F12`(Strings 창), `Alt+T`(Text search)
- x64dbg: 함수 진입/반환에 브레이크포인트, `Ctrl+G`(Dump로 이동), Watch 창으로 반환 레지스터(`eax`/`rax`) 추적
- IDAPython 콘솔(`Shift+F2` 또는 하단 Output 창의 Python 프롬프트): `idc.get_bytes(addr, length)`로 원시 바이트 추출

## 출력 해석
- 함수 반환 후 `eax`(또는 `rax`)가 가리키는 메모리에서 사람이 읽을 수 있는 ASCII/UTF-16 문자열이 보이면, 그 함수는 확실히 문자열 복호화 함수다.
- 복호화 함수 내부에 정확히 256번 반복되는 초기화 루프와 그 뒤에 이어지는 스왑(swap) 연산이 보이면 RC4의 KSA(Key Scheduling Algorithm) 단계로 거의 확정할 수 있다.
- 같은 키가 여러 문자열에서 반복 사용되는지, 아니면 문자열마다 다른 키를 쓰는지 확인하면 스크립트의 일괄 처리 방식이 달라진다.

## 흔한 실수
- 문자열마다 디버거로 일일이 실행해서 확인하는 것 — 문자열이 수십~수백 개면 비효율적이다. 알고리즘만 파악하면 정적으로 전부 복호화하는 것이 훨씬 빠르다.
- 복호화 함수를 찾았는데 인자 순서(포인터가 먼저인지 길이가 먼저인지, 호출 규약이 `cdecl`인지 `fastcall`인지)를 잘못 파악해서 Python 재구현이 틀리는 것.
- XOR 키를 한 문자열에서만 확인하고 다른 문자열에도 무조건 같은 키를 적용했다가 틀리는 것 — 키가 문자열별로 다르게 파생되는 경우가 있다.
- 복호화된 결과에 UTF-16(2바이트 문자) 인코딩을 고려하지 않아 깨진 문자로 보이는 것을 "복호화 실패"로 오판하는 것.

## 막혔을 때 다음 체크
- 복호화 함수 자체를 못 찾겠다면 → REV-0233 문자열 난독화가 보일 때(기초 개념)로 돌아가 패턴부터 재확인
- 함수 단위로 통째로 암호화되어 있어 문자열 복호화 이상의 문제라면 → REV-0949 함수 단위 암호화(Function Encryption) 개념 소개
- 이 복호화 로직 자체가 커스텀 패커의 일부였다면 → REV-0943 커스텀 패커 알아보는 단서
- 시간이 오래 걸린다면 CTF 목표가 정말 이 문자열인지부터 재확인 → REV-0953 5분 판단 절차

## 미니 예제
```python
# 복호화 함수 분석 결과: XOR with rolling key (key = (base_key + i) & 0xFF)
def decrypt(data: bytes, base_key: int) -> bytes:
    return bytes((b ^ ((base_key + i) & 0xFF)) for i, b in enumerate(data))

# IDA에서 추출한 암호화 문자열 목록 (오프셋, 길이, base_key)
encrypted_strings = [
    (0x00405000, 18, 0x5A),
    (0x00405020, 24, 0x5A),
]

with open("packed.exe", "rb") as f:
    raw = f.read()

for offset, length, key in encrypted_strings:
    # 파일 오프셋 계산은 실제로는 RVA -> 파일 오프셋 변환이 필요함(섹션 정보 참고)
    chunk = raw[offset:offset+length]
    print(decrypt(chunk, key))
```
이 스크립트를 확장해 바이너리 전체에서 암호화된 문자열 후보를 자동으로 찾아 순회하면, 디버거를 켤 필요 없이 모든 문자열을 한 번에 복원할 수 있다.

## 관련 글
- REV-0233 — 문자열 난독화가 보일 때
- REV-0949 — 함수 단위 암호화(Function Encryption) 개념 소개
- REV-0943 — 커스텀 패커(자체 제작 패커) 알아보는 단서
- REV-0953 — 패킹/난독화 여부를 실전에서 5분 안에 판단하는 절차

## 출처/검증
- 문자열 암호화에 흔히 쓰이는 XOR/RC4/치환 알고리즘 패턴은 다수의 공개 malware 분석 리포트와 CTF 라이트업에서 반복적으로 관찰되는 사례를 기준으로 정리했다.
- RC4의 KSA(256바이트 초기화 루프) 식별 방법은 RC4 알고리즘의 공개 명세(원 설계 및 다수의 암호학 교재)를 기준으로 확인했다.
- IDAPython을 이용한 바이트 추출/코멘트 자동화는 Hex-Rays IDA 공식 문서(IDAPython API)를 참고했다(2026-09-09 검증).
