## 한 줄 요약
DIE/PE-bear 화면에 뜬 엔트로피 숫자 하나를 봤을 때, 그 값이 "정상 코드/데이터"인지 "압축·암호화 의심"인지 즉시 판단할 수 있도록 구간별 기준값만 압축해서 정리한 표다.

## 언제 검색해야 하나
- 엔트로피 개념 자체(왜 압축/암호화 데이터가 높게 나오는지)는 이미 알고 있고, "지금 이 숫자가 정상 범위인지"만 빠르게 확인하고 싶을 때
- DIE 화면에 여러 섹션의 엔트로피 숫자가 쭉 나열되어 있는데, 어느 것부터 의심해야 할지 우선순위를 정하고 싶을 때
- 리포트/writeup에 "entropy 7.2"처럼 숫자만 적혀 있어서 이게 높은 건지 낮은 건지 바로 감이 안 잡힐 때

## 핵심 개념
엔트로피는 0~8 bits/byte 범위의 숫자이며, 8에 가까울수록 바이트 분포가 무작위에 가깝다(압축/암호화 데이터의 전형적 특징). 아래 표는 REV-0228에서 설명한 원리를 바탕으로 "숫자만 보고 바로 참조"할 수 있게 구간별 판단 기준만 정리한 것이다. 원리와 근거가 더 필요하면 REV-0228을 먼저 읽는 것을 권장한다.

## 화면/코드에서 보이는 징후
| 엔트로피 구간 | 일반적 해석 | 흔한 예 |
|---|---|---|
| 0.0 ~ 1.0 | 대부분 동일 값(0x00 등)으로 채워짐 | 미사용 예약 공간, 패딩, `.bss` |
| 1.0 ~ 3.0 | 매우 단순/반복적인 패턴 | 짧은 초기화 데이터, 정렬용 채움 |
| 3.0 ~ 5.5 | 구조화된 데이터, 문자열 위주 | `.rdata`, `.rodata`, 리소스 문자열 테이블 |
| 5.5 ~ 6.5 | 정상적인 컴파일된 기계어 코드 | `.text` (전형적인 범위) |
| 6.5 ~ 7.0 | 다소 높은 편, 즉시 의심하기보단 다른 징후와 교차 확인 | 코드+데이터 혼재, 약한 인코딩 |
| 7.0 ~ 7.5 | 주의 구간 | 이미 압축된 리소스(PNG/JPEG/ZIP), 일부 인코딩 |
| 7.5 ~ 7.8 | 압축/암호화 강한 의심 | 패커 스텁이 압축한 섹션 초입부 |
| 7.8 ~ 8.0 | 압축 또는 암호화 거의 확정 | UPX `UPX1` 섹션, AES/RC4 암호화 블록, XOR 인코딩 셸코드 |

## 가장 먼저 할 것
DIE/PE-bear에서 섹션별 엔트로피를 확인할 때, 이름이 `.text`인 섹션이 6.5를 넘는지부터 본다. `.text`가 6.5를 넘으면 코드 섹션 이름만 정상이고 실제 내용은 압축/암호화되어 있을 가능성을 최우선으로 의심한다.

## 단계별 절차
**1) 섹션 이름과 엔트로피를 나란히 놓고 본다.**
**2) 위 표에서 해당 구간의 해석을 확인한다.**
**3) `.text`/`.code` 계열 섹션이 6.5를 넘으면 REV-0225(UPX)나 REV-0931(다른 패커 시그니처)로 즉시 이동한다.**
**4) 리소스/데이터 섹션만 유독 높으면 정상 압축 리소스(이미지, 폰트)일 가능성도 함께 고려한다(REV-0228 흔한 실수 참고).**
**5) 파일 전체 평균이 7.9 이상이면 패킹을 강하게 의심하고 REV-0224 체크리스트로 이동한다.**

## 명령어/단축키
- DIE: 파일 드래그 → Entropy 탭
- PE-bear: Section Headers 탭의 Entropy 열
- ELF는 GUI 엔트로피 도구가 흔치 않으므로, 필요하면 `objdump -s`로 섹션을 덤프한 뒤 Python 스크립트로 직접 Shannon 엔트로피를 계산한다.

## 출력 해석
- 표의 경계값(6.5, 7.5, 7.8 등)은 절대적 규칙이 아니라 실무에서 널리 쓰이는 경험적 기준이다. 파일/컴파일러/최적화 옵션에 따라 정상 `.text`도 6.5를 살짝 넘는 경우가 있으므로, 항상 "같은 파일 안 다른 섹션과의 상대 비교"를 함께 본다.
- 여러 섹션이 고르게 7~8 사이라면 파일 전체가 패킹되었을 가능성이, 특정 섹션 하나만 튄다면 그 섹션에만 별도 페이로드가 숨겨져 있을 가능성이 높다.

## 흔한 실수
- 경계값을 넘었다고 무조건 "패킹 확정"으로 결론짓는 것 — 표는 우선순위를 정하기 위한 참고 기준이며, 최종 판단은 섹션 이름/시그니처/entry point 코드와 함께 내려야 한다.
- 리소스 섹션의 높은 엔트로피(이미 압축된 이미지/폰트 때문)를 코드 패킹과 혼동하는 것.
- 파일 전체 평균만 보고 섹션별 편차를 확인하지 않는 것.

## 막혔을 때 다음 체크
- 엔트로피 원리와 왜 이런 구간이 나오는지 근거가 더 필요하면 → REV-0228 Entropy가 높은 Section의 의미.
- `.text` 엔트로피가 높은데 패커 이름이 안 잡히면 → REV-0931 흔한 패커 시그니처 빠른 참조표.
- 엔트로피는 정상인데 다른 패킹 징후(import 부족 등)가 있으면 → REV-0229 Import가 거의 없는 PE를 봤을 때, REV-0938 난독화 기법 종류 빠른 참조표.

## 미니 예제
```text
.text   entropy=7.91   -> 표 기준 "압축 또는 암호화 거의 확정" 구간, 즉시 REV-0225로 이동
.rsrc   entropy=4.30   -> 표 기준 "구조화된 데이터" 구간, 정상 범위
```

## 관련 글
- REV-0228 — Entropy가 높은 Section의 의미
- REV-0224 — 패킹된 바이너리인지 의심하는 기준
- REV-0225 — UPX인지 확인하는 법
- REV-0931 — 흔한 패커 시그니처 빠른 참조표(UPX/ASPack/PECompact 등)

## 출처/검증
- 구간별 경험적 기준값은 REV-0228에서 정리한 Shannon 엔트로피 이론(Claude Shannon, "A Mathematical Theory of Communication", 1948)과 Detect It Easy/PE-bear가 실무에서 사용하는 표시 방식을 종합한 것이다(2026-09-09 검증).
- 정확한 임계값은 컴파일러/최적화 옵션/파일 종류에 따라 달라질 수 있어, 특정 샘플 판단 시에는 같은 파일 내 다른 섹션과의 상대 비교를 권장한다.
