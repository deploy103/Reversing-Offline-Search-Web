## 한 줄 요약
"이게 패킹된 건지 아닌지" 판단에 계속 시간을 쓰고 있다면, 한 가지 지표(엔트로피, 시그니처, 함수 개수 중 하나)만 보지 말고 **여러 지표를 함께 조합한 5분짜리 체크리스트**로 빠르게 결론을 내리고, 애매한 경우에는 "언패킹이 필요한가"보다 "정적 분석이 지금 통하는가"를 기준으로 실용적으로 판단하는 것이 시간을 아끼는 방법이다.

## 언제 검색해야 하나
- Detect It Easy에서는 패커가 안 잡히는데, IDA에서 함수 개수가 적거나 디컴파일 결과가 이상해서 패킹인지 아닌지 몇 시간째 고민하고 있을 때
- 엔트로피는 높은데 패커 시그니처는 없고, "혹시 커스텀 패커인가?"라는 생각에 계속 매달리게 될 때
- 컴파일러 최적화(인라인 함수, 함수 병합)와 패킹으로 인한 함수 감소를 구분하지 못해서 헷갈릴 때
- 패킹 여부 판단에만 시간을 다 쓰고 정작 문제 풀이(플래그 찾기 등) 진도를 못 나가고 있다고 느낄 때

## 핵심 개념

### 단일 지표로 판단하면 안 되는 이유
REV-0959에서 다뤘듯 엔트로피 하나만으로는 패킹을 단정할 수 없고, 시그니처 스캐너도 만능이 아니다(변형된 패커, 알려지지 않은 커스텀 패커는 시그니처 DB에 없으면 못 잡는다). 함수 개수가 적은 것도 패킹 때문일 수 있지만, 컴파일러가 최적화 단계에서 함수를 인라인 처리했거나, 프로그램 자체가 정말 단순해서 함수가 몇 개 안 되는 정상적인 경우일 수도 있다. **하나의 신호만으로 결론 내리면 오판 가능성이 크므로, 여러 신호를 동시에 확인하는 체크리스트 접근이 필요하다.**

### 5분 판단 체크리스트
아래 항목을 순서대로 확인하고, 몇 개나 "패킹 의심" 쪽으로 나오는지 센다.

| 항목 | 확인 방법 | 패킹 의심 신호 |
|---|---|---|
| 패커 시그니처 | Detect It Easy Deep scan | 알려진 패커/프로텍터 이름이 나옴 |
| 섹션 엔트로피 | PE-bear 섹션별 엔트로피 | `.text` 섹션까지 7.0 이상으로 높음 |
| Import 개수 | IDA Imports 탭 | 정상 프로그램 규모에 비해 극단적으로 적음(5개 미만) |
| 섹션 이름 | PE-bear Section Headers | `UPX0`, `UPX1` 등 비표준 이름 |
| Entry Point 코드 | IDA에서 EP로 이동해 코드 확인 | 컴파일러 스텁(`push ebp` 등)이 아니라 낯선 반복 코드 |
| Strings 풍부함 | IDA Strings 창(`Shift+F12`) | 프로그램 규모 대비 문자열이 거의 없음 |

이 중 **3개 이상**이 "패킹 의심" 쪽으로 나오면 실제로 패킹일 가능성이 높다고 보고 언패킹 절차(REV-0227, REV-0241)로 넘어간다. **1개 이하**라면 패킹이 아닐 가능성이 높으므로, 다른 원인(컴파일러 최적화, 정상적인 압축 리소스 등)을 REV-0959 방식으로 확인한다. **2개 정도로 애매하다면**, 아래 "실용적 판단 기준"을 적용한다.

### 애매할 때의 실용적 판단 기준
이론적으로 100% 확신하기 어려운 경우, "패킹인가 아닌가"라는 질문 자체를 잠시 내려놓고 **"지금 정적 분석이 실제로 통하는가"**로 질문을 바꾼다. IDA의 디컴파일 결과(F5)를 실제 목표 함수(예: 정답 비교 로직)에 대해 시도해보고, 그 결과가 이해 가능한 C 코드처럼 보인다면 패킹 여부와 무관하게 그냥 정적 분석을 계속하면 된다. 반대로 디컴파일 결과가 봐도 이해할 수 없는 형태라면, 원인이 패킹이든 난독화든 상관없이 동적 분석으로 전환하는 것이 맞는 선택이다. 즉 "정확한 원인 진단"보다 "다음에 뭘 해야 하는가"를 먼저 정하고 움직이는 것이 실전에서는 더 빠르다.

## 화면/코드에서 보이는 징후
- Detect It Easy와 PE-bear를 왔다 갔다 하며 같은 파일을 몇 번이고 재확인하고 있다.
- IDA 디컴파일 결과를 두고 "이게 패킹 때문에 이런 건지, 그냥 최적화 때문인지" 판단을 반복해서 미루고 있다.
- 다른 사람의 라이트업이나 힌트를 찾아보며 "패킹이 맞는지" 확인하는 데 시간을 쓰고 있다.

## 가장 먼저 할 것
지금 바로 위 체크리스트 6개 항목을 하나씩 5분 안에 확인한다. 완벽한 확신을 얻으려 하지 말고, 개수를 세어 다수결로 판단한다.

## 단계별 절차
1. Detect It Easy Deep scan을 1회 실행한다.
2. PE-bear로 섹션별 엔트로피를 확인한다(`.text` 포함).
3. IDA Imports 탭에서 함수 개수를 센다.
4. PE-bear로 섹션 이름을 확인한다.
5. IDA에서 Entry Point로 이동해 코드 모양을 본다.
6. IDA Strings 창을 연다.
7. 위 6개 중 패킹 의심 쪽으로 나온 개수를 센다. 3개 이상이면 언패킹 절차로, 1개 이하면 다른 원인 확인으로, 2개면 "목표 함수의 디컴파일이 실제로 읽을 만한가"를 기준으로 다음 행동을 정한다.

## 명령어/단축키
- Detect It Easy: Deep scan 옵션 체크 후 재스캔
- PE-bear: `Section Headers` 뷰에서 엔트로피/이름/크기 한눈에 확인
- IDA: `Shift+F12`(Strings), Imports 탭, `Ctrl+E`(Entry Point 목록으로 이동)

## 출력 해석
- 6개 항목 중 다수가 "정상" 쪽이면, 함수 개수가 적은 것은 최적화 때문이거나 원래 프로그램이 단순한 것이라고 봐도 무방하다.
- 다수가 "패킹 의심" 쪽이면 시그니처가 안 잡히더라도 알려지지 않은 커스텀 패커일 가능성을 염두에 두고 REV-0241 절차로 넘어간다.
- 정확히 반반으로 갈리는 애매한 경우, "목표 함수 디컴파일 결과가 읽을 만한가"라는 실용적 질문이 최종 결정권을 갖는다.

## 흔한 실수
- 시그니처 스캐너 결과 하나만 믿고 "패커가 안 잡혔으니 패킹이 아니다"라고 단정하는 것 — 커스텀/변형 패커는 시그니처 DB에 없을 수 있다.
- 함수 개수가 적다는 이유만으로 패킹이라고 단정하고 곧바로 언패킹 도구부터 시도하는 것 — 최적화 때문일 수도 있으므로 다른 지표도 함께 봐야 한다.
- 완벽한 확신을 얻을 때까지 판단을 미루며 시간을 계속 쓰는 것 — 체크리스트로 다수결 판단을 내리고 일단 다음 단계로 진행한 뒤, 틀렸다면 그때 되돌아가는 것이 전체적으로 더 빠르다.
- 애매한 상황에서 "정적 분석이 통하는가"라는 실용적 질문으로 전환하지 않고 계속 "패킹이 맞나?"라는 원래 질문에만 매달리는 것.

## 막혔을 때 다음 체크
- 엔트로피만 높고 나머지가 정상이라면 → REV-0959(Entropy는 높은데 패킹이 아닌 것으로 판명될 때)를 참고한다.
- 다수결로 패킹이 맞다고 판단되면 → REV-0227(수동 언패킹 개념 OEP와 Dump)과 REV-0241(정적/동적 전환)로 넘어간다.
- 이미 언패킹을 시작했는데 결과가 이상하다면 → REV-0955, REV-0956, REV-0960 등 관련 문서를 확인한다.

## 미니 예제
```text
체크리스트 적용 예:
- 패커 시그니처: 없음 (정상)
- .text 엔트로피: 6.3 (정상)
- Import 개수: 3개 (의심)
- 섹션 이름: .text, .rdata, .data (정상, 표준 이름)
- Entry Point 코드: push ebp; mov ebp, esp; CRT 초기화 API 호출 (정상)
- Strings: 문자열 120개 이상 (정상)

=> 6개 중 1개만 의심(Import 3개) -> 다수결로 "패킹 아님"
=> Import가 적은 이유는 정적 링크(static linking)일 가능성으로 재확인
   -> file 명령/PE-bear로 확인해보니 실제로 정적 링크된 라이브러리 다수 포함
   => 패킹이 아니라 정적 링크 때문에 외부 import가 적은 정상 케이스로 결론
```

## 관련 글
- REV-0959 — Entropy는 높은데 패킹이 아닌 것으로 판명될 때
- REV-0241 — 패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환
- REV-0227 — 수동 언패킹 개념 OEP와 Dump

## 출처/검증
- 패킹 여부를 판단할 때 단일 지표(엔트로피, 시그니처, 함수 개수)만으로는 오판이 발생할 수 있다는 점과, 여러 지표를 함께 확인하는 접근 방식은 다수의 공개 리버싱 교육 자료와 실무 분석 가이드에서 공통적으로 권장하는 방법을 정리한 것이다(2026-09-09 검증).
- Detect It Easy/PE-bear의 각 지표 확인 방법: 두 도구의 공식 문서 및 GitHub 저장소 설명 기준.
