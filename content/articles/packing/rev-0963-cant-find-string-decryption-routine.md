## 한 줄 요약
IDA의 Strings 창에 의미 있는 문자열이 거의 안 보이고 대신 바이트 배열이나 XOR된 데이터만 보인다면, 문자열이 난독화되어 있는 것이며 복호화 루틴을 정적으로 못 찾겠을 때는 "문자열이 실제로 쓰이는 지점"부터 거꾸로 추적하거나, 아예 정적 분석을 잠시 접고 동적으로 복호화 직후 시점을 붙잡는 것이 훨씬 빠르다.

## 언제 검색해야 하나
- IDA의 `Shift+F12`(Strings 창)를 열어봤는데 프로그램 크기에 비해 문자열이 너무 적거나, "Enter password" 같은 UI 텍스트가 하나도 안 보일 때
- 디스어셈블리에서 `.data` 섹션에 의미를 알 수 없는 바이트 배열(`db 0x1A, 0x3F, 0x02, ...`)이 여러 개 있는데, 이게 문자열이라는 확신은 있지만 어떻게 풀리는지 모를 때
- x64dbg로 실행하면서 메시지박스나 콘솔 출력에는 정상적인 텍스트가 뜨는데, 정적으로는 그 텍스트가 어디에도 평문으로 안 보일 때
- REV-0233(문자열 난독화가 보일 때)을 읽고 난독화라는 것은 이해했는데, 정작 "복호화 함수가 어디 있는지" 코드에서 찾지 못할 때

## 핵심 개념

### 정방향 탐색이 어려운 이유
"바이트 배열을 보고 그걸 누가 복호화하는지" 찾으려는 시도(정방향 탐색)는 생각보다 어렵다. 왜냐하면 컴파일러 최적화나 코드 구조에 따라 그 바이트 배열을 참조하는 코드가 함수 여러 개에 걸쳐 흩어져 있거나, 레지스터 인덱싱으로 간접 참조되어 IDA의 자동 교차 참조(xref)가 제대로 안 잡히는 경우가 많기 때문이다. 배열 하나를 보고 "이걸 처리하는 함수가 어디지?"라고 역추적하는 것보다, 반대 방향이 훨씬 효율적이다.

### 역방향 탐색: "쓰이는 지점"에서 거꾸로 올라가기
문자열은 결국 어딘가에서 반드시 **사용**된다 — 화면에 출력되거나(`printf`, `MessageBoxA`), 비교되거나(`strcmp`), 파일 경로/레지스트리 키로 쓰인다. 이런 "문자열을 인자로 받는 API"는 이름이 잘 알려져 있으므로, 그 API의 호출 지점부터 거꾸로 추적하면 복호화 루틴을 훨씬 쉽게 찾을 수 있다.

1. IDA Imports 탭에서 `MessageBoxA/W`, `printf` 계열, `strcmp`, `lstrcmpA`, `SetWindowTextA` 등 문자열을 인자로 받는 API를 찾는다.
2. 그 API에 대한 교차 참조(`X` 단축키)를 열어 호출 지점들을 나열한다.
3. 각 호출 직전의 코드를 거슬러 올라가며, 인자로 넘겨지는 값(레지스터/스택)이 어디서 만들어지는지 추적한다.
4. 그 값이 어떤 함수의 반환값이라면, 그 함수가 바로 복호화 루틴일 가능성이 높다.

### 동적 탐색: 복호화 "직후" 시점을 붙잡기
정적으로 xref를 따라가는 것도 복잡한 코드에서는 시간이 오래 걸릴 수 있다. 이럴 때는 x64dbg로 실제 실행시키면서, 문자열을 쓰는 API(`MessageBoxA`, `printf` 등)에 브레이크포인트를 걸고, 그 호출 시점에 인자로 들어오는 메모리 주소의 내용을 직접 확인하는 방법이 훨씬 빠르다. API가 호출되는 순간에는 이미 복호화가 끝난 평문이 메모리에 있을 수밖에 없기 때문이다.

## 화면/코드에서 보이는 징후
- IDA Strings 창의 항목 수가 프로그램 규모에 비해 비정상적으로 적다(정상 프로그램이라면 수십~수백 개 있어야 할 UI 텍스트가 몇 개뿐).
- `.data`/`.rdata` 섹션에 `db` 지시어로 나열된 바이트 배열이 여러 개 있는데 ASCII로 해석되지 않는다.
- 특정 함수가 배열 하나를 순회하면서 각 바이트에 XOR, ADD, ROL 같은 연산을 반복하는 루프 형태를 갖고 있다(전형적인 단순 복호화 루틴의 모양).
- x64dbg로 실행 중 콘솔/메시지박스에는 정상 텍스트가 뜨는데, 그 시점 이전 메모리를 봐도 평문이 안 보인다(복호화가 그 직전 순간에 일어났다는 뜻).

## 가장 먼저 할 것
정적으로 배열부터 추적하려 하지 말고, 먼저 IDA Imports 탭에서 문자열을 다루는 표준 API 목록(`MessageBoxA/W`, `printf`류, `strcmp`류, `SetWindowTextA`)이 무엇이 있는지 확인한다.

## 단계별 절차
1. IDA Imports 탭에서 문자열을 인자로 받는 API를 확인하고, 그 중 프로그램 로직상 반드시 호출될 법한 것(예: 정답 확인 시 뜨는 메시지박스라면 `MessageBoxA`)을 우선 선택한다.
2. 해당 API 이름을 더블클릭해서 이동한 뒤, `X`(Cross-references to) 단축키로 호출 지점 목록을 연다.
3. 각 호출 지점의 직전 코드를 확인해서, 문자열 인자로 쓰이는 값이 상수 주소인지, 아니면 어떤 함수 호출의 반환값인지 구분한다. 함수 호출 반환값이라면 그 함수 내부로 들어가 확인한다.
4. 그 함수 내부에 반복 루프와 XOR/ADD/ROL 같은 바이트 단위 연산이 보이면, 이것이 복호화 루틴이다(REV-0233에서 다룬 패턴 참고).
5. 정적 추적이 막히거나 너무 오래 걸리면, x64dbg로 전환해서 그 API(`MessageBoxA` 등)에 브레이크포인트를 걸고 실행한다. 브레이크포인트에 걸리는 순간 인자로 들어온 문자열 포인터를 덤프 창에서 확인하면 복호화된 평문이 바로 보인다.
6. 평문을 확인한 후, 그 포인터가 가리키는 메모리 주소에 대해 "언제 이 값이 마지막으로 쓰였는가"를 알고 싶다면 메모리 쓰기 브레이크포인트를 걸어 복호화 루틴이 실행되는 순간을 정확히 잡을 수 있다.

## 명령어/단축키
- IDA: `Shift+F12`(Strings 창), `X`(선택한 함수/변수의 교차 참조 보기), `Ctrl+F`(Imports 이름 검색)
- x64dbg: 특정 API 이름으로 브레이크포인트(`Symbols` 탭에서 함수 검색 후 우클릭 → `Set Breakpoint`, 또는 `bp MessageBoxA` 명령어 창 입력)
- x64dbg 인자 확인: 브레이크포인트 히트 시 x86은 스택(`ESP+4` 등), x64는 `RCX`/`RDX` 레지스터에서 문자열 포인터 확인 후 덤프 창에서 `Follow in Dump`
- x64dbg 메모리 쓰기 브레이크포인트: 해당 문자열 버퍼 주소 우클릭 → `Set Memory Breakpoint on Write`(복호화가 그 주소에 쓰는 순간을 잡음)

## 출력 해석
- API 호출 지점에서 확인한 문자열 포인터가 가리키는 덤프 내용이 평문(ASCII로 읽히는 텍스트)이면, 그 시점 이전 어딘가에서 복호화가 이미 끝난 것이다.
- 메모리 쓰기 브레이크포인트가 반복적으로(루프처럼) 여러 번 히트된다면, 한 바이트씩 순차적으로 복호화하는 루틴을 정확히 잡은 것이다.
- 복호화 루틴 내부에서 XOR 대상 키 값이 상수라면 정적으로 직접 복호화 스크립트를 작성해서 모든 문자열을 한 번에 풀어낼 수도 있다(파이썬 등으로).

## 흔한 실수
- 배열 하나하나를 처음부터 끝까지 정적으로 눈으로 추적하려다 시간을 다 쓰는 것 — 역방향(API 호출 지점에서 거슬러 올라가기)이 훨씬 빠른 경우가 대부분이다.
- IDA의 xref가 자동으로 안 잡히는 것을 보고 "찾을 수 없다"고 포기하는 것 — 간접 참조(레지스터 기반 인덱싱)는 IDA가 자동으로 못 잡는 경우가 흔하며, 이럴 때 동적 분석이 필요한 이유이기도 하다.
- x64dbg로 API에 브레이크포인트를 걸 때, 콜 컨벤션에 따른 인자 위치(x86 스택 vs x64 레지스터)를 헷갈려서 엉뚱한 값을 문자열 포인터로 착각하는 것.
- 문자열 하나만 확인하고 나머지도 같은 방식이라고 가정했는데, 실제로는 문자열마다 다른 키/알고리즘을 쓰는 경우를 놓치는 것.

## 막혔을 때 다음 체크
- 문자열 난독화의 기본 패턴 자체가 낯설다면 → REV-0233(문자열 난독화가 보일 때)을 먼저 읽는다.
- 이 문제가 패킹 전체와 얽혀 있다면 → REV-0241(패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환)을 참고한다.
- 문자열은 찾았는데 이후 로직 전체가 난독화되어 있다면 → 제어 흐름 평탄화 관련 REV-0231을 참고한다.

## 미니 예제
```text
1) IDA Strings 창 -> 항목 4개뿐, 전부 DLL 이름 문자열
2) Imports 탭에서 MessageBoxA 확인, X로 xref 확인 -> sub_401500에서 1회 호출
3) sub_401500 진입 직전 코드 확인
   -> lea rdx, [rbp-0x40]   ; 지역 버퍼 주소
   -> call sub_401200       ; 이 함수 호출 후 rdx 버퍼에 값이 채워짐
   -> call MessageBoxA
4) sub_401200 내부 확인
   -> for 루프, byte_403000[i] ^ 0x5A 를 [rbp-0x40+i]에 저장하는 패턴 발견
5) byte_403000 배열을 파이썬으로 0x5A와 XOR -> "Access Granted!" 평문 확인
```
```python
data = bytes.fromhex("0d0a0a3e30303c33203b32332120")  # 예시 바이트 배열
key = 0x5A
print(bytes(b ^ key for b in data))
```

## 관련 글
- REV-0233 — 문자열 난독화가 보일 때
- REV-0241 — 패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환
- REV-0231 — Control Flow Flattening 기초

## 출처/검증
- 문자열 난독화 탐지를 위한 API 호출 지점 역추적 방식과 XOR 기반 단순 복호화 루틴 패턴: 다수의 공개 리버싱 교육 자료 및 CTF 문자열 복호화 문제 풀이에서 공통적으로 사용하는 절차를 정리한 것이다(2026-09-09 검증).
- x64dbg에서의 API 브레이크포인트와 콜 컨벤션별 인자 위치(x86 stack, x64 RCX/RDX): x64dbg 공식 문서 및 Microsoft x64 호출 규약 문서 기준.
