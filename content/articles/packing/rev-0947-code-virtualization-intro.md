## 한 줄 요약
코드 가상화는 원본 x86/x64 명령어를 프로텍터가 자체 설계한 바이트코드로 변환하고, 그 바이트코드를 해석 실행하는 작은 가상 머신(VM)을 실행 파일 안에 심어 넣는 기법으로, 디스어셈블러에는 "원본 로직"이 아니라 "핸들러를 반복 호출하는 인터프리터 루프"만 보이게 되어 정적 분석을 사실상 무력화한다.

## 언제 검색해야 하나
- IDA/Ghidra에서 특정 함수를 열었더니 정상적인 함수 구조가 아니라 거대한 `switch`문 하나와 그 안의 수십~수백 개 case로만 이루어져 있을 때
- REV-0942에서 상용 프로텍터(VMProtect/Themida)를 다루다가 "코드 가상화가 정확히 뭘 하는지" 더 알고 싶을 때
- 디스어셈블리에서 같은 몇 개의 레지스터만 계속 참조하며 반복되는 연산 패턴(`VM Context` 구조체처럼 보이는 큰 구조체 포인터가 계속 등장)을 발견했을 때
- "가상화된 코드는 왜 원본 명령어가 안 보이는가"를 개념적으로 이해하고 싶을 때

## 핵심 개념

### 일반적인 프로그램 실행 vs 가상화된 실행
일반적인 x86/x64 프로그램은 CPU가 직접 실행하는 기계어 명령(`mov`, `add`, `cmp`, `jmp` 등)으로 이루어져 있다. 리버서는 디스어셈블러로 이 명령들을 그대로 읽으면 로직을 파악할 수 있다.

코드 가상화는 이 전제를 깨뜨린다. 프로텍터의 컴파일 시점(또는 사전 처리 단계) 도구가 보호하고 싶은 함수를 골라, 그 함수의 x86/x64 명령어들을 **자체 정의한 가상 명령어(바이트코드)**로 변환한다. 그리고 실행 파일 안에는:

1. 변환된 바이트코드 데이터
2. 이 바이트코드를 한 줄씩 읽어 해석하고 실행하는 **VM 인터프리터(디스패처)** 코드

가 대신 들어간다. 프로그램이 실행되면 CPU는 이제 원본 명령어가 아니라 "VM 인터프리터"라는 하나의 고정된 코드만 반복 실행하고, 실제 로직은 데이터(바이트코드)로 존재한다.

### VM 인터프리터의 전형적인 구조
1. **VM Context**: 가상 레지스터들의 값을 담는 구조체(메모리 영역). 실제 CPU 레지스터 몇 개(주로 하나의 포인터 레지스터)만 이 구조체를 가리키는 데 쓰이고, 나머지 "가상 레지스터"는 전부 이 구조체 안의 필드다.
2. **가상 명령어 포인터(vIP)**: 다음에 실행할 바이트코드의 위치를 가리키는 값. VM Context 안에 저장된다.
3. **디스패치 루프(dispatcher)**: vIP가 가리키는 바이트코드 1바이트(오퍼레이터 코드, opcode)를 읽고, 그 값에 따라 핸들러 테이블에서 해당 핸들러로 점프한다.
4. **핸들러들**: 각 가상 opcode에 대응하는 실제 동작(가상 add, 가상 mov, 가상 jmp 등)을 수행하는 코드 블록. 동작을 마치면 다시 디스패치 루프로 돌아간다.

이 구조 때문에 디스어셈블리에서는 "핸들러 A 실행 → 디스패처로 복귀 → 핸들러 B 실행 → 디스패처로 복귀 → ..."가 반복되는 모양으로 보인다. 실제 로직(원래 `if (password == "abc")` 같은 비교)은 핸들러들이 어떤 순서로 호출되는지, 그리고 바이트코드 데이터 자체에 인코딩되어 있어서 x86 명령어 수준의 디스어셈블리만으로는 알아볼 수 없다.

### 왜 강력한 보호 기법인가
- 정적 디스어셈블러(IDA/Ghidra)는 x86/x64 명령어 집합을 기준으로 분석하므로, VM 바이트코드 자체는 그냥 "데이터"로 보일 뿐 의미를 해석해주지 못한다.
- 같은 원본 로직이라도 프로텍터마다(심지어 컴파일할 때마다) 다른 가상 명령어 집합, 다른 핸들러 순서로 변환될 수 있어 "패턴 매칭으로 자동 복호화"가 어렵다.
- 완전히 이해하려면 리버서가 그 VM의 opcode 집합과 각 핸들러의 의미를 직접 분석("VM 역공학")해야 하는데, 이는 별도의 전문 분야로 취급될 만큼 시간이 오래 걸린다.

### 현실적인 접근
개인/CTF 수준에서 코드 가상화를 완전히 풀어내는 것은 REV-0942에서 다룬 것처럼 매우 시간이 많이 드는 작업이다. 실전에서는:
- 가상화된 함수가 정말 분석에 필요한 부분인지 먼저 판단한다(대부분의 프로그램은 일부 핵심 함수만 가상화하고 나머지는 일반 코드로 둔다).
- 가상화되지 않은 주변 코드(가상화된 함수를 호출하는 지점, 반환값을 사용하는 지점)를 통해 "이 함수가 대략 무엇을 하는지"를 간접적으로 추론하는 것이 더 실용적인 경우가 많다.
- 동적 분석(가상화된 함수 호출 전후의 레지스터/메모리 상태 비교)으로 입출력 관계만 파악해도 충분한 경우가 있다.

## 화면/코드에서 보이는 징후
- IDA Graph view에서 특정 함수가 하나의 거대한 순환 구조(디스패치 루프)로만 이루어져 있고, 그 안에 매우 많은 분기(case)가 몰려 있음
- 코드 전반에 걸쳐 특정 하나의 레지스터(예: `esi` 또는 `rbx`)가 구조체 포인터처럼 계속 `[reg+offset]` 형태로 참조됨
- 함수 크기가 원본 로직에 비해 비정상적으로 큼(실제로는 몇 줄짜리 비교 로직인데 디스어셈블리는 수천 줄)
- 문자열/상수 참조가 거의 안 보이고 대신 반복적인 산술 연산 패턴만 보임

## 가장 먼저 할 것
가상화가 의심되는 함수를 발견하면, 먼저 그 함수의 "호출 이전"과 "반환 이후" 코드부터 확인한다. 무엇을 인자로 넘기고 반환값을 어떻게 쓰는지 알면, 내부 구현을 몰라도 함수의 역할(예: "문자열 비교 함수인 듯하다")을 추정할 수 있는 경우가 많다.

## 단계별 절차
1. 의심되는 함수를 IDA Graph view로 열어 구조가 "디스패치 루프 + 다수 case"인지 확인
2. 함수 호출 전후 코드에서 인자/반환값 사용 패턴 확인
3. 동적으로 실행하며(x64dbg) 함수 진입 시점과 반환 시점의 레지스터/메모리 스냅샷 비교
4. 여러 입력값(예: 비밀번호 후보)으로 반복 실행해 반환값이 어떻게 달라지는지 패턴 관찰
5. 완전한 VM 역공학이 필요한지, 아니면 입출력 관계 파악만으로 충분한지 판단
6. 필요하다면 REV-0942의 우선순위 전략(동적 분석 우선)을 다시 참고

## 명령어/단축키
- IDA: Graph view 전환(스페이스바), 함수 크기/노드 수 확인
- x64dbg: 함수 진입/반환 지점에 브레이크포인트, `F9`로 여러 번 실행하며 레지스터 변화 비교
- x64dbg Watch 창: 특정 구조체 포인터(VM Context로 추정되는 레지스터)의 필드 값 실시간 관찰

## 출력 해석
- 반복 실행 시 같은 함수라도 매번 다른 순서로 case가 실행되는 것처럼 보이면, 이는 입력값에 따라 VM이 다른 바이트코드 경로를 타기 때문일 수 있다(예: 비교 결과에 따라 분기).
- 함수 반환 직후 특정 플래그(ZF 등)나 반환값이 0/1처럼 단순한 값이면, 내부가 아무리 복잡해도 "성공/실패 판정 함수" 정도로 단순화해서 이해해도 충분한 경우가 많다.

## 흔한 실수
- 가상화된 함수를 발견하자마자 "이 프로그램 전체가 가상화되어 있다"고 오판하는 것 — 보통 핵심 로직 일부만 가상화되고 나머지는 일반 코드다.
- VM 핸들러 하나하나를 전부 손으로 분석하려고 시도하다가 시간을 지나치게 소모하는 것 — 입출력 관계 파악만으로 충분한지 먼저 따져봐야 한다.
- 정적 분석만으로 가상화 로직을 이해하려는 것 — 동적으로 실제 값 변화를 관찰하는 편이 훨씬 효율적이다.

## 막혔을 때 다음 체크
- 이 함수가 상용 프로텍터(VMProtect 등)의 산출물이라 확신된다면 → REV-0942 상용 프로텍터를 만났을 때 현실적인 대응
- 함수 단위로 암호화되어 있을 뿐 VM은 아닌 것 같다면 → REV-0949 함수 단위 암호화(Function Encryption) 개념 소개
- 전체적으로 시간 대비 효율을 다시 따지고 싶다면 → REV-0953 패킹/난독화 여부를 실전에서 5분 안에 판단하는 절차

## 미니 예제
```text
; VM 디스패치 루프 (개념적 예시, esi = VM Context 포인터)
dispatch_loop:
  movzx eax, byte ptr [esi+vIP]     ; 현재 가상 명령어(opcode) 읽기
  inc dword ptr [esi+vIP]           ; vIP 증가
  jmp dword ptr [handler_table+eax*4]  ; opcode에 해당하는 핸들러로 점프

handler_add:                        ; 가상 ADD 명령어 처리
  mov eax, [esi+vReg0]
  add eax, [esi+vReg1]
  mov [esi+vReg0], eax
  jmp dispatch_loop                 ; 처리 후 다시 디스패치 루프로 복귀

handler_jz:                         ; 가상 조건 분기 처리
  cmp dword ptr [esi+vFlagZero], 0
  jne dispatch_loop
  mov eax, [esi+vJumpTarget]
  mov [esi+vIP], eax
  jmp dispatch_loop
```
이런 구조에서는 `handler_add`, `handler_jz`가 각각 진짜 `add`, `jz`에 대응하지만, 디스어셈블리만 봐서는 이들이 원래 프로그램의 어느 부분에 해당하는지 알 수 없다 — 바이트코드 데이터(`[esi+vIP]`가 가리키는 값들의 나열)를 함께 해석해야 원본 로직이 드러난다.

## 관련 글
- REV-0942 — 상용 프로텍터(VMProtect/Themida)를 만났을 때 현실적인 대응
- REV-0949 — 함수 단위 암호화(Function Encryption) 개념 소개
- REV-0953 — 패킹/난독화 여부를 실전에서 5분 안에 판단하는 절차
- REV-0231 — Control Flow Flattening 기초
- REV-0232 — Opaque Predicate 기초

## 출처/검증
- 코드 가상화의 VM Context/디스패치 루프/핸들러 구조는 VMProtect 등 상용 가상화 프로텍터를 다룬 다수의 공개 리버싱 컨퍼런스 발표 자료 및 블로그 분석 글에서 공통적으로 설명하는 일반 구조를 기준으로 정리했다.
- 이 문서는 특정 제품의 정확한 opcode 표나 내부 구현을 재현한 것이 아니라, 코드 가상화라는 기법 자체의 일반적 개념을 소개하는 것을 목적으로 한다(2026-09-09 검증).
