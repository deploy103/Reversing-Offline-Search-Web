## 한 줄 요약
Detect It Easy 같은 시그니처 스캐너는 패커 이름을 정확히 알아냈는데, 정작 그 패커 전용 언패킹 도구(`upx -d` 등)를 실행하면 오류가 나거나 아무 변화 없이 실패한다면, **파일이 해당 패커로 패킹되긴 했지만 표준 방식과 다르게 변형(수정된 헤더, 다른 버전, 커스텀 스텁 삽입)되어 있어서 도구가 내부 구조를 표준으로 인식하지 못하기 때문**이다.

## 언제 검색해야 하나
- Detect It Easy 결과 창에 "UPX 3.96" 처럼 구체적인 버전까지 나오는데, `upx -d`를 실행하면 "NotPackedException" 또는 "CantUnpackException" 같은 오류가 뜰 때
- 시그니처 스캐너가 패커 이름을 확신에 찬 것처럼 표시하는데도, 그 패커의 공식/서드파티 자동 언패킹 도구가 전부 실패할 때
- `upx -l`(정보만 조회)은 되는데 `upx -d`(실제 언패킹)만 실패할 때
- 다른 사람의 CTF 풀이에서는 같은 도구로 잘 됐다는데, 내 환경/파일에서만 실패할 때

## 핵심 개념

### 시그니처 탐지와 언패킹은 서로 다른 작업이다
Detect It Easy 같은 도구는 파일 안의 **특정 바이트 패턴(시그니처)**을 찾아서 "이 파일은 UPX로 패킹된 것 같다"고 알려줄 뿐이다. 이는 단순 패턴 매칭이라 몇 바이트만 일치해도 인식될 수 있다. 반면 `upx -d` 같은 실제 언패킹 도구는 그 패턴을 넘어서 **파일의 정확한 내부 구조(헤더 필드 값, 체크섬, 오프셋 테이블)를 표준 스펙대로 해석**해야 동작한다. 따라서 "시그니처는 맞지만 구조가 조금이라도 다르면" 탐지는 성공하고 실제 언패킹은 실패하는 상황이 얼마든지 생길 수 있다.

### 흔한 원인들
1. **패커 버전 불일치**: UPX 3.x로 패킹된 파일을 UPX 4.x로 언패킹하려 하면(또는 반대), 내부 포맷이 버전 간에 조금씩 달라 실패할 수 있다.
2. **헤더 필드 수동 조작**: 일부 CTF 문제나 방어 기법은 UPX로 정상 패킹한 뒤, 파일의 특정 필드(체크섬, 매직 넘버 근처의 예약 필드)를 일부러 손상시켜서 `upx -d`가 "이 파일은 UPX가 아니다" 또는 "손상됨"으로 판단해 거부하도록 만든다. 이때 프로그램 자체는 정상 실행되므로(로더는 그 필드를 검사하지 않으므로), 실행에는 문제가 없지만 자동 언패킹만 막히는 것이다.
3. **패커 자체가 변형(fork)된 버전**: UPX 소스를 조금 수정해서 만든 커스텀 빌드(스텁 코드는 UPX와 비슷하지만 완전히 같지는 않음)로 패킹된 경우, 시그니처는 유사해서 잡히지만 표준 `upx -d`와 100% 호환되지 않는다.
4. **다중 실행 파일이 하나로 합쳐진 경우**: 인스톨러/self-extracting 아카이브 안에 UPX로 패킹된 실행 파일이 포함되어 있으면, 시그니처 스캐너는 내부의 UPX 흔적을 찾아내지만 언패킹 도구는 전체 파일 구조(인스톨러 래퍼)를 이해하지 못해 실패한다.

## 화면/코드에서 보이는 징후
- `upx -d packed.exe` 실행 시 `packed.exe: NotPackedException: file is not packed` 또는 `CantUnpackException: header corrupted` 같은 메시지가 뜬다.
- Detect It Easy는 "UPX(Markus Oberhumer & Laszlo Molnar & John Reiser)"처럼 구체적인 제작자 정보까지 표시하지만, 도구 실행은 실패한다.
- 파일을 HxD로 열어 UPX 매직 문자열(`UPX!`)을 검색하면 실제로 존재한다 — 즉 시그니처 자체는 진짜다.
- 다른 버전의 UPX(웹에서 여러 버전을 받아 시도)로 시도하면 그 중 하나에서만 성공하는 경우가 있다.

## 가장 먼저 할 것
`upx -V`로 현재 버전을 확인하고, 공식 GitHub 릴리스 페이지에서 다른 버전(특히 더 오래된 버전들)을 몇 개 받아 각각 시도해본다. 버전 문제인지 아닌지가 가장 빠르게 갈리는 지점이다.

## 단계별 절차
1. `upx -V`로 현재 버전을 확인한다.
2. UPX 공식 GitHub 릴리스 페이지에서 여러 버전(예: 3.94, 3.96, 4.0.x, 4.2.x)을 받아 각각 `upx -d`를 시도한다.
3. 모든 버전에서 실패한다면, HxD로 파일을 열어 UPX 매직 문자열(`UPX!`) 주변 바이트를 직접 살펴본다. 정상적인 UPX 파일이라면 이 근처에 특정 구조(체크섬, 압축 크기 필드)가 있는데, 이 값이 명백히 이상하면(예: 전부 0이거나 파일 크기를 초과하는 값) 의도적으로 손상되었을 가능성이 있다.
4. 자동 도구로 안 되는 것이 확인되면, 미련 없이 REV-0227의 수동 언패킹 절차(x64dbg로 OEP 탐색 → 덤프 → IAT 복구)로 전환한다. 자동 도구가 못 하는 것을 수동으로 하는 것이지, 패킹 자체가 못 푸는 것이 아니다.
5. 인스톨러/self-extracting 구조가 의심되면, 먼저 그 래퍼를 정상적으로 실행/추출해서 내부의 진짜 대상 파일을 꺼낸 뒤, 그 파일에 대해서만 다시 처음부터 판별 절차를 반복한다.
6. CTF 문제라면, 문제 설명이나 힌트에 "표준 도구로는 안 풀린다"는 암시가 있는지 다시 확인한다 — 의도적으로 자동 언패킹을 막아둔 문제일 수 있다.

## 명령어/단축키
```text
upx -V                       # 버전 확인
upx -d -f packed.exe          # 강제 모드로 재시도
upx --version                 # 위와 동일, 버전 상세 정보
```
- HxD: `Ctrl+F`로 `UPX!` 문자열 검색, 주변 바이트 hex 값 직접 확인
- Detect It Easy: 결과에 표시된 정확한 패커 버전 문자열 기록해두기(어느 버전을 우선 시도할지 힌트가 됨)

## 출력 해석
- `NotPackedException`은 UPX가 "이 파일은 애초에 UPX로 패킹된 게 아니다"라고 판단했다는 뜻 — 시그니처는 있지만 구조 검증에서 걸린 것이다.
- `CantUnpackException: header corrupted` 계열 메시지는 UPX 헤더 구조까지는 인식했지만 세부 필드 값이 기대와 다르다는 뜻 — 의도적 손상 가능성이 있다.
- 특정 버전에서만 성공한다면, 그 버전이 원본을 패킹할 때 쓰인 실제 버전과 가장 가깝다는 뜻이다.

## 흔한 실수
- 딱 한 가지 버전의 UPX만 설치되어 있다고 가정하고 그것만 반복 시도하는 것 — 여러 버전을 받아 시도해보는 것이 의외로 빠른 해결책이다.
- 도구가 실패하는 것을 "이 파일은 언패킹이 불가능하다"고 확대 해석해서 아예 포기하는 것 — 자동 도구의 한계일 뿐, 수동 절차로는 대부분 가능하다.
- 인스톨러/self-extracting 파일의 바깥 껍질과 안쪽 진짜 대상 파일을 구분하지 않고, 바깥 껍질에 계속 언패킹 도구를 돌리는 것.
- HxD로 헤더를 직접 확인하지 않고 도구 오류 메시지만 보고 원인을 추측하는 것 — 실제 바이트를 봐야 손상/변형 여부를 확신할 수 있다.

## 막혔을 때 다음 체크
- 수동 언패킹으로 넘어가야 한다면 → REV-0227(수동 언패킹 개념 OEP와 Dump)을 참고한다.
- 벗겨낸 후에도 또 다른 패커 시그니처가 나온다면 → REV-0960(여러 겹으로 패킹된 바이너리를 만났을 때)을 참고한다.
- 애초에 UPX가 맞는지부터 다시 의심된다면 → REV-0225(UPX인지 확인하는 법)로 돌아가 확인한다.

## 미니 예제
```text
$ upx -V
upx 4.2.2

$ upx -d packed.exe
packed.exe: CantUnpackException: header corrupted

$ upx -d -f packed.exe
packed.exe: CantUnpackException: header corrupted

(다른 버전의 UPX 3.96을 별도로 받아서 재시도)
$ ./upx-3.96 -d packed.exe
                       Ultimate Packer for eXecutables
Unpacked 1 file.

=> UPX 3.96으로 패킹된 파일을 최신 4.2.2로 풀려다 실패한 버전 불일치 사례
```

## 관련 글
- REV-0227 — 수동 언패킹 개념 OEP와 Dump
- REV-0960 — 여러 겹으로 패킹된(Multi-layer) 바이너리를 만났을 때
- REV-0956 — OEP를 찾았는데 실행이 이상하게 될 때

## 출처/검증
- UPX의 버전별 내부 포맷 차이와 `NotPackedException`/`CantUnpackException` 오류 메시지: UPX 공식 저장소(github.com/upx/upx) 소스 코드 및 이슈 트래커에서 확인되는 동작 기준(2026-09-09 검증).
- 헤더 필드를 의도적으로 손상시켜 자동 언패킹만 막는 기법은 다수의 공개 CTF 리버싱 문제 풀이에서 보고되는 일반적인 패턴을 정리한 것이다.
