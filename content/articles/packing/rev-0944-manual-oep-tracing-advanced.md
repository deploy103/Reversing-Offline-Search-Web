## 한 줄 요약
REV-0227이 OEP 개념을 소개했다면, 이 글은 x64dbg에서 실제로 손을 움직여 OEP를 찾는 세 가지 구체적 기법 — ESP 트릭, 메모리 쓰기 브레이크포인트, 조건부 자동 트레이스 — 를 순서대로 시도하는 실전 절차를 다룬다.

## 언제 검색해야 하나
- REV-0227에서 OEP 개념은 이해했는데 "구체적으로 x64dbg에서 뭘 누르면 되는지" 모를 때
- ASPack/PECompact/MPRESS(REV-0939~0941) 같은 압축 패커를 만나 pushad/popad는 찾았는데 그 다음이 막막할 때
- "ESP 트릭"이라는 용어를 들었는데 정확히 어떤 원리인지 모를 때
- 메모리 쓰기 브레이크포인트를 걸었는데 너무 자주 걸려서 OEP까지 못 가는 상황일 때

## 핵심 개념

### 기법 1 — ESP 트릭 (Stack Pointer 기법)
`pushad`가 실행되면 8개의 32비트 레지스터(x86 기준)가 스택에 쌓이면서 ESP(스택 포인터)가 그만큼 감소한다. 스텁 코드는 나중에 `popad`로 이 값들을 복원하는데, `popad`가 실행되는 순간 ESP는 `pushad` 직후의 값으로 되돌아온다. 즉:

1. entry point에서 `pushad` 실행 직후 ESP 값을 확인한다(예: `0x0019FF00`).
2. 이 ESP 주소에 **하드웨어 브레이크포인트(Access 또는 Write 타입)**를 건다.
3. 실행(`F9`)하면, 압축 해제 스텁이 아무리 복잡해도 결국 `popad`가 그 스택 위치를 다시 "읽는" 순간 브레이크포인트가 걸린다.
4. `popad` 직후 몇 줄만 더 따라가면 `jmp OEP` 또는 `call OEP`가 바로 보인다.

이 기법이 통하는 이유는, 스텁이 내부적으로 무슨 짓을 하든 결국 `pushad`로 저장한 레지스터를 원래대로 되돌리려면 그 스택 주소를 다시 읽어야 하기 때문이다. UPX, ASPack처럼 `pushad`/`popad` 쌍을 쓰는 패커에 특히 잘 통한다.

### 기법 2 — 메모리 쓰기 브레이크포인트 (섹션 전체)
압축 해제는 결국 원본 코드/데이터를 특정 메모리 영역(보통 원래 `.text`가 있어야 할 가상 주소)에 "쓰는" 작업이다.

1. 압축 해제가 끝나면 더 이상 그 영역에 쓰기가 일어나지 않고, 대신 그 영역의 코드가 "실행"되기 시작한다.
2. 원본 코드 영역 전체(또는 의심되는 섹션)에 **Write 타입 메모리 브레이크포인트**를 건다.
3. 실행하면 압축 해제 루프가 그 영역에 바이트를 쓸 때마다 브레이크포인트가 계속 걸린다 — 이건 정상이다. `F9`로 계속 넘긴다.
4. 어느 순간 이 영역에 대한 **쓰기가 아니라 실행(Execute)** 시도로 브레이크포인트가 걸리는 시점이 온다. 이때가 바로 압축 해제가 끝나고 OEP로 진입한 순간이다.

이 방법은 스텁 구조를 몰라도(pushad/popad가 없는 변형이라도) 적용 가능하다는 장점이 있다. 단점은 쓰기 브레이크포인트가 너무 자주 걸려서(수백~수천 번) 매번 `F9`를 눌러야 할 수 있다는 점인데, x64dbg는 조건부 브레이크포인트로 이를 줄일 수 있다.

### 기법 3 — 조건부 자동 트레이스
반복 걸림을 자동화하려면 x64dbg의 브레이크포인트 조건식이나 스크립트 기능을 쓴다. 브레이크포인트 우클릭 → `Edit breakpoint`에서 조건을 걸어, 예를 들어 "쓰기 주소가 특정 함수 프롤로그 바이트 패턴(`55 8B EC`, `48 89 5C 24`)과 일치할 때만 멈추기"처럼 설정하면 반복 수동 클릭을 줄일 수 있다. 또는 `Trace into/over` 기능(조건부 트레이스, `Ctrl+F11`/`Ctrl+F7` 계열)으로 "실행 주소가 특정 범위를 벗어나면 멈춤"같은 규칙을 걸어 자동으로 스텁을 빠르게 통과시킬 수 있다.

### 여러 OEP 후보가 나올 때
상용 프로텍터가 아닌 일반 압축 패커에서도 간혹 여러 번 `jmp`가 연쇄적으로 이어지는 경우가 있다(스텁 내부에서 단계별로 여러 섹션을 순서대로 복원하기 때문). 이 경우 "코드 스타일이 확실히 바뀌는 지점"을 최종 판단 기준으로 삼는다 — 함수 프롤로그(`push ebp; mov ebp, esp` 또는 x64 `sub rsp, imm`)와 함께, 원본 프로그램이 실제로 쓸 법한 API(`GetStdHandle`, `printf`, 커스텀 함수 호출)가 처음 등장하는 지점이 진짜 OEP다.

## 화면/코드에서 보이는 징후
- ESP 트릭 적용 후 몇 초 안에 `popad` 근처에서 멈추면 기법이 잘 통한 것
- 메모리 쓰기 브레이크포인트가 처음에는 계속 걸리다가, 어느 순간부터 "Execute" 사유로 멈추면 그 지점이 OEP
- OEP 후보 코드가 함수 프롤로그로 시작하고 그 아래로 익숙한 API 호출이 이어짐

## 가장 먼저 할 것
`pushad`가 있는 스텁이라면 ESP 트릭을 가장 먼저 시도한다. 성공률이 높고 빠르다. `pushad`가 없거나 ESP 트릭이 통하지 않는 변형이라면 메모리 쓰기 브레이크포인트로 전환한다.

## 단계별 절차
1. entry point에서 `pushad`(또는 x64의 개별 push들) 직후 ESP 값을 Registers 창에서 확인
2. Dump 창에서 해당 ESP 주소로 이동(`Ctrl+G`), 우클릭 → `Breakpoint → Hardware, Access` (또는 Write)
3. `F9`로 실행 — `popad` 근처에서 멈추는지 확인
4. 멈췄다면 `F8`로 몇 줄 진행해 `jmp`/`call` 대상 주소 확인 → OEP 후보
5. ESP 트릭이 실패하면 원본 이미지의 코드 섹션 가상 주소 범위를 확인(PE-bear로 `.text` VA/크기 확인)
6. 그 범위 전체에 메모리 쓰기 브레이크포인트, `F9` 반복 실행하며 "Execute" 사유로 멈출 때까지 진행
7. OEP 후보에서 코드 스타일 확인(함수 프롤로그 + 익숙한 API)
8. 확정되면 Scylla 등으로 덤프(REV-0945)

## 명령어/단축키
- x64dbg Dump 창 이동: `Ctrl+G`
- 하드웨어 브레이크포인트: Dump 창에서 우클릭 → `Breakpoint → Hardware, Access/Write`
- 메모리 브레이크포인트: Memory Map 탭에서 섹션 우클릭 → `Set Memory Breakpoint on Write/Execution`
- 실행/추적: `F9`(Run), `F8`(Step Over), `F7`(Step Into), `Ctrl+F7`(Trace Into), `Ctrl+F8`(Trace Over)

## 출력 해석
- 하드웨어 브레이크포인트가 걸린 시점의 명령이 `popad`라면 ESP 트릭 성공, 그 다음 줄의 `jmp`가 OEP 후보다.
- 메모리 브레이크포인트의 "Break reason"이 `Execute`로 표시되면 그 주소가 실행되려 한 시점이며, 이는 곧 압축 해제가 끝났다는 뜻이다. `Write`로 계속 걸리는 동안은 아직 압축 해제 진행 중이다.
- OEP 후보 코드에 `int3`(0xCC)가 섞여 있다면 안티 디버깅용 트랩일 수 있으니 진짜 OEP가 아닐 가능성을 의심해야 한다.

## 흔한 실수
- ESP 트릭에서 하드웨어 브레이크포인트가 아니라 일반(소프트웨어) 브레이크포인트를 스택 주소에 걸려고 시도하는 것 — 스택 데이터 영역에는 소프트웨어 브레이크포인트(`0xCC` 삽입)가 적용되지 않으므로 반드시 하드웨어 브레이크포인트를 써야 한다.
- 메모리 쓰기 브레이크포인트가 수백 번 걸리는 것을 보고 "잘못된 방법"이라 판단하고 포기하는 것 — 이는 정상이며 계속 `F9`를 누르거나 조건부 설정으로 자동화하면 된다.
- 첫 번째 `jmp`를 무조건 OEP로 확정하는 것 — 다단계 스텁에서는 중간 경유지일 수 있으므로 코드 스타일까지 확인해야 한다.
- x64에서 `pushad`가 없다고 ESP 트릭 자체를 포기하는 것 — 개별 레지스터 push 시퀀스도 원리는 동일하게 적용된다(첫 push 직후 ESP/RSP 값 기준으로 브레이크포인트를 걸면 된다).

## 막혔을 때 다음 체크
- OEP까지는 찾았는데 덤프한 파일이 실행 안 된다면 → REV-0945 IAT 복구 개념
- 안티 디버깅 때문에 애초에 디버거 부착이 막힌다면 → REV-0230/REV-0235/REV-0236/REV-0239 안티 디버깅 관련 문서
- 스텁이 유난히 복잡하고 VM 인터프리터처럼 보인다면 → 상용 프로텍터일 가능성, REV-0942 상용 프로텍터를 만났을 때 현실적인 대응
- 어떤 패커인지부터 다시 확인하고 싶다면 → REV-0939~0941 개별 패커 기초 문서

## 미니 예제
```text
[entry point]
pushad                  ; ESP: 0x0019FF00 -> 0x0019FEDC (예시)
; ... 압축 해제 스텁, 수백 줄 ...
popad                   ; 이 시점에 ESP가 다시 0x0019FF00 근처를 읽음
jmp 0x00401320          ; <- OEP 후보

[0x00401320]
push ebp
mov ebp, esp
sub esp, 0x40
call ds:[GetStdHandle]  ; 원본 프로그램의 정상 API 호출 시작
```
Dump 창에서 `0x0019FEDC`(pushad 직후 ESP)에 Hardware Access 브레이크포인트를 걸고 `F9`를 누르면, 스텁이 아무리 길어도 `popad` 시점에 정확히 멈춘다.

## 출처/검증
- ESP 트릭과 메모리 쓰기 브레이크포인트를 이용한 OEP 탐색 기법은 x64dbg 공식 문서(help.x64dbg.com)의 브레이크포인트 관련 설명과, 다수의 공개 수동 언패킹 튜토리얼에서 공통적으로 다루는 절차를 기준으로 정리했다(2026-09-09 검증).
- 실제 성공 여부는 패커 종류/버전에 따라 달라질 수 있으므로 특정 샘플에 적용할 때는 여러 기법을 함께 시도하는 것이 권장된다.
