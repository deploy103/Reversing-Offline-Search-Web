## 한 줄 요약
OEP에서 메모리를 덤프했는데도 결과 파일의 코드 섹션이 의미 없는 값(전부 0, 또는 원본과 다른 명령어)으로 채워져 있다면, 패커가 **덤프 시점 자체를 감지하거나, 코드를 실행 직전에만 잠깐 복원했다가 곧바로 다시 지워버리는 안티덤프(anti-dump) 기법**을 쓰고 있을 가능성이 크다.

## 언제 검색해야 하나
- Scylla나 다른 도구로 OEP에서 덤프를 떴는데, 그 결과 파일을 IDA로 열었을 때 코드 섹션 대부분이 `00 00 00 00`(NULL 바이트) 또는 `CC CC CC CC`(INT3로 채워진 것)로만 보일 때
- x64dbg 안에서 실시간으로 보면 코드가 정상인데, 그 순간 덤프한 파일에는 다른 내용이 들어 있을 때
- 같은 OEP 지점을 여러 번 덤프했는데 매번 내용이 조금씩 다르게 나올 때
- 프로그램이 실행되는 동안 특정 함수가 호출되기 직전에만 코드가 나타났다가, 호출이 끝나면 다시 사라지는 것처럼 관찰될 때

## 핵심 개념

### 안티덤프가 노리는 지점
안티덤프 기법은 "언패킹된 코드가 메모리에 완전한 형태로 오래 머물지 않도록" 만드는 것이 핵심이다. 몇 가지 대표적인 방식이 있다.

1. **덤프 도구 자체를 탐지**: Scylla 같은 도구가 메모리를 읽기 위해 `ReadProcessMemory`를 호출하는데, 일부 패커는 자신의 프로세스에 대해 이 API가 호출되는 것 자체를 감시하거나(디버거가 붙어 있다는 신호로 해석), 페이지 보호 속성을 조작해서 특정 메모리 영역을 읽으려는 시도가 있으면 그 내용을 즉시 지워버리는 콜백을 걸어둔다.
2. **On-demand 복호화(실행 직전 복원, 실행 직후 재암호화)**: 함수 단위로 코드를 암호화해두고, 그 함수가 호출되기 직전에만 복호화해서 실행한 뒤, 실행이 끝나자마자 다시 암호화(또는 0으로 덮어씀)하는 방식이다. 이 경우 "완전히 언패킹된 상태"라는 것이 애초에 존재하지 않는다 — 항상 일부 함수만 복호화되어 있고 나머지는 암호화된 채로 유지되기 때문에, 어느 시점에 덤프해도 전체 코드가 한꺼번에 보이지 않는다.
3. **가드 페이지(guard page)를 이용한 트리거**: 코드 섹션의 메모리 페이지에 `PAGE_GUARD` 속성을 걸어두고, 누군가(디버거의 메모리 읽기 포함) 그 페이지에 접근하면 예외가 발생하도록 만든 뒤, 그 예외 핸들러 안에서 "지금 읽으려는 게 정상 실행 흐름인지 외부 도구인지" 판단해서 다르게 반응한다.

### 왜 "한 번의 완전한 덤프"가 근본적으로 어려운가
전통적인 수동 언패킹은 "스텁이 원본 코드를 전부 복원한 뒤 딱 한 번 OEP로 점프한다"는 전제를 깔고 있다. 하지만 on-demand 복호화 방식의 패커는 이 전제 자체가 성립하지 않는다 — 코드가 "한꺼번에 전부" 복원되는 순간이 존재하지 않고, 항상 필요한 부분만 부분적으로 복원되었다가 다시 사라진다. 이런 경우 REV-0227식 "OEP 찾고 한 번에 덤프" 접근법은 원리적으로 한계가 있으며, 여러 시점의 덤프를 겹쳐서 합치거나(스티칭), 함수 호출 시점마다 개별적으로 코드를 캡처하는 방식이 필요하다.

## 화면/코드에서 보이는 징후
- 덤프 파일을 IDA로 열었을 때 코드 섹션의 상당 부분이 `NULL` 바이트로 채워져 있고, 일부만 정상적인 명령어로 보인다.
- 같은 지점을 여러 번 덤프했을 때 매번 다른 함수만 정상으로 보이고 나머지가 비어 있다(어느 함수가 최근에 호출되었는지에 따라 달라짐을 시사).
- x64dbg의 메모리 맵에서 코드 섹션의 페이지 보호 속성이 `PAGE_GUARD` 또는 예상과 다른 값으로 표시된다.
- 덤프 시도 직후 프로세스가 곧바로 종료되거나, 디버거 자체가 응답 없음 상태에 빠진다.

## 가장 먼저 할 것
지금 겪고 있는 것이 "한 번에 다 안 보이는" 현상인지, "덤프 자체가 트리거되어 프로세스가 죽는" 현상인지부터 구분한다. 전자는 on-demand 복호화, 후자는 덤프 탐지형 안티덤프일 가능성이 높다.

## 단계별 절차
1. 같은 OEP 후보 지점에서 여러 번 반복적으로 덤프해보고, 매번 결과가 똑같은지 다른지 비교한다. 다르다면 on-demand 방식을 의심한다.
2. on-demand 방식이 의심되면, 프로그램을 실제로 끝까지 실행하면서(가능한 모든 기능/메뉴를 조작하며) 각 시점마다 덤프를 여러 번 떠서, 서로 다른 덤프에서 정상으로 보이는 코드 영역들을 모아 하나로 합치는 방식을 시도한다. 이는 시간이 오래 걸리므로, 목표가 "완전한 정적 분석 파일 재구성"이 아니라 "특정 함수 하나의 로직 확인"이라면 그 함수가 호출되는 순간에만 집중해서 덤프하는 것이 더 효율적이다.
3. 덤프 시도 자체가 프로세스를 죽이거나 응답 없음을 유발한다면, x64dbg의 메모리 맵에서 코드 페이지의 보호 속성을 먼저 확인한다. `PAGE_GUARD`나 `PAGE_NOACCESS`로 표시된 페이지가 있다면, 그 속성을 정상값(`PAGE_EXECUTE_READ` 등)으로 먼저 바꾼 뒤 덤프를 재시도한다.
4. 위 방법이 안 통하면, 메모리를 통째로 읽는 대신 함수 호출 직전에 브레이크포인트를 걸어 "그 함수의 코드만" 작은 단위로 하나씩 복사해서 모으는 수동 방식으로 전환한다.
5. CTF 맥락이라면, 완전한 정적 분석 파일을 포기하고 x64dbg 안에서 직접 함수 로직을 스텝 단위로 읽어가며 필요한 정보(비교값, 알고리즘)만 확인하는 편이 훨씬 실용적인 경우가 많다.

## 명령어/단축키
- x64dbg 메모리 맵: `View → Memory Map`에서 각 페이지의 `Protection` 컬럼 확인
- 페이지 보호 속성 변경: 메모리 맵에서 해당 영역 우클릭 → `Set Page Memory Rights`
- 반복 덤프 비교: Scylla로 같은 지점을 여러 번 덤프해 별도 파일로 저장 후 HxD의 비교 기능이나 `fc`/`diff`로 바이트 차이 확인

## 출력 해석
- 여러 번의 덤프 결과를 비교(`diff` 등)했을 때 매번 다른 영역이 정상으로 보인다면, 이는 on-demand 복호화의 강력한 증거다.
- 특정 페이지의 `Protection`이 `PAGE_NOACCESS`나 `PAGE_GUARD`로 표시된다면, 정상적인 코드 페이지가 아니라 의도적으로 접근을 막아둔 트랩임을 시사한다.
- 덤프 직후 프로세스가 매번 정확히 같은 지점에서 죽는다면, 그 지점 근처에 덤프 탐지 코드가 있다는 뜻이므로 그 코드를 우회하거나 무력화해야 한다.

## 흔한 실수
- 코드 섹션이 부분적으로 비어 있는 것을 보고 "OEP를 잘못 찾았다"고 단정해서 REV-0956 절차만 반복하는 것 — 실제로는 OEP는 맞았고 안티덤프가 원인인 경우가 많다.
- 완전한 한 번의 덤프로 전체 코드를 복원하려는 시도를 계속 반복하며 시간을 쓰는 것 — on-demand 방식에서는 애초에 그런 순간이 존재하지 않을 수 있다.
- 페이지 보호 속성을 확인하지 않고 바로 덤프 도구만 반복 실행하는 것.
- 목표를 "완전한 정적 분석 파일 재구성"으로 고정해두고, 실제로 필요한 것은 특정 함수 하나의 로직뿐이라는 점을 간과하는 것.

## 막혔을 때 다음 체크
- 덤프한 파일이 크래시가 나는 다른 이유(IAT 미복구 등)와 헷갈린다면 → REV-0955(언패킹한 덤프가 크래시가 날 때)를 먼저 확인해 원인을 구분한다.
- OEP 자체를 다시 검토해야 한다면 → REV-0956(OEP를 찾았는데 실행이 이상하게 될 때)을 참고한다.
- 완전한 언패킹을 포기하고 동적 분석으로 전환하는 판단 기준이 필요하다면 → REV-0241(패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환)을 참고한다.

## 미니 예제
```text
1) OEP(0x00401230)에서 Scylla로 덤프 -> dump1.exe
2) 같은 지점에서 다시 덤프 -> dump2.exe
3) HxD 비교 기능으로 두 파일 비교
   -> 0x1200~0x1400 영역이 dump1은 NULL, dump2는 정상 명령어
   -> 0x2000~0x2200 영역은 반대로 dump1만 정상
4) On-demand 복호화 방식으로 판단
5) 목표가 "패스워드 비교 로직 확인"이었으므로, 완전한 덤프 대신
   x64dbg에서 비교 함수 호출 직전에 브레이크포인트를 걸어
   해당 함수 코드만 개별적으로 복사해 분석 완료
```

## 관련 글
- REV-0955 — 언패킹한 덤프가 크래시가 날 때
- REV-0956 — OEP를 찾았는데 실행이 이상하게 될 때
- REV-0241 — 패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환

## 출처/검증
- 안티덤프 기법(덤프 도구 탐지, 가드 페이지, on-demand 코드 복호화)은 다수의 공개 멀웨어/프로텍터 분석 자료 및 리버싱 교육 자료에서 공통적으로 다루는 일반적 기법을 정리한 것이다(2026-09-09 검증).
- Windows 메모리 페이지 보호 속성(`PAGE_GUARD`, `PAGE_NOACCESS` 등)의 동작: Microsoft 공식 문서(Win32 API `VirtualProtect` 관련 문서) 기준.
