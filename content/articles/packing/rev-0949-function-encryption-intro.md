## 한 줄 요약
함수 단위 암호화는 프로그램 전체가 아니라 보호하고 싶은 개별 함수의 코드 바이트만 암호화해서 저장해두고, 그 함수가 호출되기 직전에 메모리에서 복호화하고 실행이 끝나면 다시 암호화(또는 즉시 해제)하는 기법으로, 코드 가상화(REV-0947)보다는 약하지만 REV-0230 Self-modifying Code의 "함수 단위 특화 버전"이라고 볼 수 있다.

## 언제 검색해야 하나
- IDA/Ghidra에서 특정 함수 하나만 디스어셈블리가 정상적인 명령어로 해석되지 않고 의미 없는 바이트 나열로 나올 때
- 그 함수를 호출하기 직전에 항상 다른 함수 하나가 먼저 호출되는 패턴이 반복적으로 보일 때(복호화 함수로 추정)
- x64dbg로 실행하다가 특정 코드 영역에 대해 "Write" 브레이크포인트가 함수 호출 직전에만 걸리는 것을 발견했을 때
- REV-0230(Self-modifying Code)의 개념은 이해했는데, "프로그램 전체가 아니라 특정 함수만" 이런 식으로 동작하는 이유가 궁금할 때

## 핵심 개념

### 전체 언패킹 vs 함수 단위 암호화
REV-0227/REV-0944에서 다룬 "패킹"은 보통 프로그램 전체(또는 대부분의 코드 섹션)를 한 번 압축/암호화해두고, 실행 시작과 동시에 딱 한 번 통째로 풀어서 OEP로 넘어가는 방식이다. 이 경우 OEP만 찾으면 이후에는 코드가 계속 평문 상태로 유지된다.

함수 단위 암호화는 이와 다르다. 프로그램은 이미 정상적으로 시작되어 대부분의 코드가 평문 상태로 실행되지만, **보호하고 싶은 특정 함수(라이선스 검증, 핵심 알고리즘, 안티치트 로직 등) 몇 개만** 암호화된 채로 남아 있다가, 그 함수가 호출될 때마다 그때그때(on-demand) 복호화된다. 실행이 끝나면 다시 암호화하거나(방어를 극대화하는 경우) 그냥 평문 상태로 남겨두기도 한다(성능을 위한 절충).

### 왜 이렇게 하는가
프로그램 전체를 패킹하면 REV-0944의 OEP 추적 기법으로 한 번에 전체가 노출된다. 하지만 핵심 로직 몇 개만 함수 단위로 암호화해두면:
- OEP를 찾아 전체를 덤프해도 그 특정 함수들의 코드는 여전히 암호화된 채로 파일에 남는다.
- 리버서가 "전체 언패킹은 끝났다"고 착각하고 분석을 진행하다가, 정작 중요한 함수에서 의미 없는 바이트만 보고 막히게 된다.
- 매번 호출 시점에만 복호화되므로, 정적 분석에서는 항상 암호화된 형태로만 보인다.

### 전형적인 구현 패턴
1. 보호할 함수의 코드가 원래 위치에 암호화된 채로 저장되어 있다.
2. 그 함수를 호출하는 지점 직전에 `call decrypt_function(addr, size, key)` 형태의 헬퍼 호출이 삽입되어 있다.
3. `decrypt_function`은 `VirtualProtect`로 해당 코드 페이지를 쓰기 가능하게 바꾸고(코드 페이지는 기본적으로 실행 전용이라 직접 쓰려면 권한 변경이 필요하다), XOR 등으로 복호화한 뒤 원래 위치에 덮어쓴다.
4. 복호화가 끝나면 실제 함수를 호출한다.
5. 함수 실행이 끝나면(옵션) 같은 페이지를 다시 암호화하고 원래 권한(실행 전용)으로 되돌린다.

### REV-0230/REV-0947과의 관계
- REV-0230(Self-modifying Code)이 "코드가 실행 중 스스로를 고쳐 쓴다"는 일반적인 개념이라면, 함수 단위 암호화는 그 개념을 "보호 목적으로, 함수 경계 단위로 체계적으로" 적용한 특수 사례다.
- REV-0947(코드 가상화)이 명령어 하나하나를 다른 형태(바이트코드)로 바꿔서 실행 자체의 의미를 숨긴다면, 함수 단위 암호화는 명령어 형태는 그대로 x86/x64로 유지하되 "언제 평문으로 볼 수 있는가"를 통제해서 정적 분석 타이밍을 방해하는 방식이다. 즉 코드 가상화보다 구현이 단순하지만, "정적으로 봤을 때 이 함수가 뭘 하는지 전혀 알 수 없다"는 효과는 비슷하게 낸다.

## 화면/코드에서 보이는 징후
- IDA에서 특정 함수 주소로 이동하면 `Failed to create function` 또는 의미 없는 opcode 나열(`db` 바이트만 표시)이 나옴
- 그 함수를 호출하는 지점 바로 앞에 항상 동일한 서브루틴 호출이 반복됨(인자로 함수 주소, 크기가 넘어감)
- x64dbg의 메모리 쓰기 브레이크포인트를 코드 섹션에 걸어두면, 함수가 호출되기 직전마다 짧게 쓰기가 발생했다가 멈춤
- Memory Map에서 해당 코드 페이지의 보호 속성이 실행 중간에 `PAGE_EXECUTE_READ`에서 `PAGE_EXECUTE_READWRITE`로 바뀌었다가 다시 돌아오는 것이 관찰됨(`VirtualProtect` 호출 전후)

## 가장 먼저 할 것
IDA/Ghidra에서 "함수로 인식이 안 되는" 코드 영역을 발견하면, 그 영역이 호출되는 지점(Xref)부터 먼저 확인한다. 호출 직전에 반복되는 헬퍼 함수가 있다면 그것이 복호화 루틴이다. x64dbg로 그 헬퍼 함수 실행 전후 해당 코드 영역의 바이트를 Dump 창에서 비교하면 복호화 여부를 바로 확인할 수 있다.

## 단계별 절차
1. IDA에서 함수로 인식되지 않는(또는 이상한 opcode로 보이는) 코드 영역 확인
2. 그 영역을 가리키는 호출 지점(Xref) 확인, 직전에 반복 호출되는 헬퍼 함수 특정
3. x64dbg로 헬퍼 함수 진입 전 코드 영역 바이트를 Dump 창에서 기록
4. 헬퍼 함수 실행 후(다음 명령으로 진행 후) 같은 영역 바이트를 다시 확인 — 바뀌었다면 복호화 확인
5. 헬퍼 함수 내부를 읽어 알고리즘 특정(REV-0948과 동일한 XOR/RC4 류가 흔함)
6. 함수 실행이 끝난 뒤 재암호화가 일어나는지 확인(다시 바뀌는지 관찰)
7. 알고리즘을 알아냈다면 REV-0948처럼 Python으로 재구현, 파일 내 암호화된 함수 코드를 일괄 복호화해서 정적 분석 가능한 형태로 재구성

## 명령어/단축키
- x64dbg: 코드 섹션 메모리 쓰기 브레이크포인트(`Memory Map` 우클릭 → `Set Memory Breakpoint on Write`)
- x64dbg Memory Map: 페이지 보호 속성(`Protection` 열) 실시간 확인
- IDA: `Xref to`(`X`)로 호출 지점 추적, `Edit → Undefine`/`Create function`으로 복호화 후 재분석

## 출력 해석
- 헬퍼 함수 호출 전후로 코드 바이트가 바뀌고, 바뀐 뒤의 바이트가 정상적인 x86/x64 명령어 패턴(`55 8B EC` 함수 프롤로그 등)으로 보이면 복호화가 확인된 것이다.
- Memory Map의 Protection 열이 `ERW`(Execute-Read-Write)로 잠깐 바뀌었다가 다시 `ER`(Execute-Read)로 돌아온다면 `VirtualProtect` 호출을 통한 임시 권한 변경이 이루어진 것이다.

## 흔한 실수
- 함수 하나가 이상하게 보인다고 전체 프로그램이 패킹된 것으로 오판하고 REV-0944의 전체 OEP 탐색 절차를 처음부터 다시 시도하는 것 — 이미 OEP를 지난 정상 실행 상태에서 특정 함수만 암호화된 경우와 구분해야 한다.
- 복호화가 끝난 직후의 코드만 덤프하고, 함수 실행이 끝난 뒤 다시 재암호화되는 것을 놓쳐서 "한 번 봤으니 끝났다"고 착각하는 것 — 재호출 시 다시 암호화된 상태일 수 있다.
- `VirtualProtect` 호출 자체를 놓치고 "코드가 어떻게 쓰기 가능해졌는지" 원리를 이해하지 못한 채 결과만 관찰하는 것.

## 막혔을 때 다음 체크
- 이 패턴이 문자열이 아니라 코드 자체에 적용된 것이 확실하다면 이 문서가 맞는 방향이지만, 문자열만 암호화된 것이라면 → REV-0948 문자열 암호화/복호화 루틴
- 복호화된 코드조차 정상 x86이 아니라 여전히 이상한 바이트코드처럼 보인다면 → REV-0947 코드 가상화 개념 소개(더 강한 보호일 가능성)
- Self-modifying code의 기초 개념부터 다시 보고 싶다면 → REV-0230 Self-modifying Code 기초
- 이런 함수가 덤프/분석을 방해하려는 목적이 강하다면 → REV-0950 Anti-Dump 기법 개념 소개

## 미니 예제
```text
call_site:
  push offset target_func   ; 인자: 암호화된 함수 주소
  push 0x200                ; 인자: 크기
  push 0x77                 ; 인자: key
  call decrypt_helper        ; VirtualProtect + XOR 복호화 수행
  call target_func           ; 이제 평문이 된 함수 호출
  ; (옵션) 실행 후 재암호화 호출이 이어질 수 있음

decrypt_helper:
  push ebp
  mov ebp, esp
  ; VirtualProtect(addr, size, PAGE_EXECUTE_READWRITE, &old)
  call ds:VirtualProtect
  ; XOR 복호화 루프
decrypt_loop:
  xor byte ptr [esi], key
  inc esi
  loop decrypt_loop
  ret
```
`call target_func` 직전에 이 헬퍼가 항상 먼저 실행되는 패턴을 발견하면, 함수 단위 암호화가 적용된 것으로 확신할 수 있다.

## 관련 글
- REV-0230 — Self-modifying Code 기초
- REV-0947 — 코드 가상화(Code Virtualization) 개념 소개
- REV-0948 — 문자열 암호화/복호화 루틴 알아보고 자동 복호화하기
- REV-0950 — Anti-Dump 기법(덤프 방지) 개념 소개

## 출처/검증
- 함수 단위 온디맨드 복호화(call 직전 decrypt, 실행 후 재암호화) 패턴은 다수의 공개 malware 분석 리포트 및 리버싱 교육 자료에서 공통적으로 설명하는 구조를 기준으로 정리했다.
- `VirtualProtect`를 이용한 코드 페이지 임시 쓰기 권한 부여는 Microsoft 공식 Win32 API 문서(`VirtualProtect` 함수 설명)를 기준으로 확인했다(2026-09-09 검증).
