## 한 줄 요약
패킹된 파일을 x64dbg로 열거나 attach했을 때 정상 실행과 다르게 곧바로 종료되거나 멈춰버린다면, 원인은 대부분 **패커 스텁 자체에 포함된 안티디버깅 체크**이며, 이는 프로그램 로직의 안티디버깅과는 별개로 패커가 자기 자신을 보호하기 위해 심어 둔 것이다.

## 언제 검색해야 하나
- `./chall.exe`를 직접 더블클릭하면 잘 실행되는데, x64dbg로 열어서 `F9`를 누르면 스텁 코드 초반부에서 바로 종료될 때
- x64dbg로 이미 실행 중인 패킹된 프로세스에 attach하려고 하면 프로세스가 곧바로 종료될 때
- 소프트웨어 브레이크포인트(`F2`)를 스텁 코드 어딘가에 걸었더니, 그 지점에 도달하기도 전에 프로그램이 이상 종료될 때
- Detect It Easy로 확인했을 때 UPX가 아니라 안티디버깅 기능이 포함된 상용 패커(Themida, VMProtect, Enigma Protector 등)로 나올 때

## 핵심 개념

### 패커 자체의 안티디버깅과 프로그램 로직의 안티디버깅은 다르다
REV-0234~0240에서 다룬 안티디버깅은 주로 **프로그램 개발자가 직접 코드에 심어 둔** 체크(`IsDebuggerPresent`, `ptrace` 등)였다. 반면 상용 패커/프로텍터는 **패커 제작사가 스텁 코드 안에 미리 넣어 둔** 별도의 안티디버깅 로직을 갖고 있는 경우가 많다. 이는 압축 해제 과정 자체를 디버거로 들여다보지 못하게 막기 위한 것으로, 원본 프로그램 개발자의 의도와 무관하게 패커를 쓰기만 해도 자동으로 따라붙는다.

### 패커 스텁이 흔히 쓰는 자체 보호 기법
- **코드 무결성 체크(체크섬)**: 디버거가 소프트웨어 브레이크포인트를 걸면 해당 위치의 바이트가 `0xCC`(INT3)로 바뀐다. 패커 스텁이 실행 중 자기 코드의 체크섬을 계산해서 원본과 다르면 종료하도록 되어 있으면, 브레이크포인트를 하나만 걸어도 감지된다.
- **타이밍 체크**: 압축 해제 루프 사이사이에 `RDTSC`/`GetTickCount` 등으로 경과 시간을 재서, 디버거로 인해 실행이 비정상적으로 느려진 것을 감지한다.
- **`OutputDebugString`/`NtQueryInformationProcess` 등 디버거 존재 확인 API**: `IsDebuggerPresent`보다 덜 알려진 API를 사용해 PEB의 `NtGlobalFlag`, `ProcessDebugPort` 등을 조회한다.
- **하드웨어 브레이크포인트 탐지**: 디버그 레지스터(`DR0`~`DR7`)를 직접 조회해서, 소프트웨어 브레이크포인트뿐 아니라 하드웨어 브레이크포인트가 걸려 있는지도 확인한다.
- **자기 자신에 대한 자가 attach(anti-attach)**: 스텁이 시작하자마자 스스로 디버거 역할을 해서 자신에게 attach를 시도하고, 실패하면(이미 다른 디버거가 붙어 있다는 뜻이므로) 종료한다.

## 화면/코드에서 보이는 징후
- 직접 실행 시에는 정상 동작하지만, x64dbg로 실행/attach하면 스텁 코드가 몇 명령 진행되다가 갑자기 종료된다.
- x64dbg 하단 상태 표시줄에 프로세스 종료 메시지만 뜨고, 별다른 예외 메시지 없이 조용히 끝나는 경우가 많다(체크섬/무결성 실패는 예외를 던지지 않고 그냥 `ExitProcess`를 호출하는 경우가 흔함).
- attach 방식으로 시도했을 때, attach 자체는 성공한 것처럼 보이지만 그 직후 프로세스 목록에서 프로세스가 사라진다.

## 가장 먼저 할 것
가장 먼저 x64dbg의 예외/브레이크포인트 설정을 바꿔본다. 소프트웨어 브레이크포인트를 하나도 걸지 않은 "순수 실행"(`F9`만 누르고 아무 것도 건드리지 않은 상태)에서도 종료되는지, 아니면 브레이크포인트를 건 직후에만 종료되는지를 먼저 구분해야 한다.

## 단계별 절차
1. 소프트웨어 브레이크포인트를 하나도 걸지 않은 상태로 `F9`만 눌러 실행해본다. 이 상태에서도 종료된다면 코드 무결성 체크가 아니라 타이밍/attach 탐지 계열이다.
2. 브레이크포인트를 걸었을 때만 종료된다면, 모든 브레이크포인트를 하드웨어 방식(주소 우클릭 → `Breakpoint` → `Hardware, on Execution`)으로 바꿔서 다시 시도한다 — 소프트웨어 브레이크포인트는 코드 바이트를 직접 수정하므로 체크섬 검사에 걸리기 쉽다.
3. x64dbg의 `Options → Preferences → Exceptions`에서 예외를 프로그램에 자동으로 전달하지 않고 디버거가 먼저 처리하도록 설정을 확인하고, 필요하면 반대로 "모든 예외를 프로그램에 전달"(`Shift+F9`로 개별 전달)해서 패커가 예외 기반으로 자기 상태를 판단하는지도 시험해본다.
4. x64dbg의 안티안티디버깅 플러그인(ScyllaHide 등)을 활성화해서, `IsDebuggerPresent`류 API와 PEB 플래그를 자동으로 위장한 상태에서 재시도한다.
5. 그래도 종료된다면, 스텁 코드를 조금씩 단계별로(`F7`/`F8`) 실행하면서 종료 직전 마지막으로 실행된 명령을 기록한다. `rdtsc`, `int 2Dh`, `cpuid` 근처였다면 타이밍/VM 탐지 계열, `NtQueryInformationProcess` 호출 근처였다면 API 기반 계열로 원인을 좁힌다.
6. 상용 프로텍터(Themida, VMProtect 등)로 확인되고 여러 겹의 방어가 겹쳐 있다면, 완전한 정적 언패킹을 고집하기보다 REV-0241 방식대로 필요한 최소한의 동적 관찰(목표 로직 근처에서만 조심스럽게 브레이크)로 목적을 좁히는 것이 시간을 아낀다.

## 명령어/단축키
- x64dbg 하드웨어 브레이크포인트: 주소 우클릭 → `Breakpoint` → `Hardware, on Execution`
- x64dbg 예외 전달: `Shift+F9`(현재 예외를 프로그램에 전달하고 계속 실행)
- x64dbg 옵션: `Options → Preferences → Exceptions`(예외 처리 방식 설정)
- ScyllaHide: `Plugins → ScyllaHide → Options`에서 원하는 우회 항목(PEB, API 후킹 등) 체크 후 적용
- Detect It Easy: 패커/프로텍터 이름 확인(자체 안티디버깅 존재 여부를 미리 짐작하는 데 도움)

## 출력 해석
- 브레이크포인트 유무와 관계없이 매번 같은 지점 근처에서 종료된다면 결정론적 체크(체크섬, API 기반)일 가능성이 높다.
- 하드웨어 브레이크포인트로 바꿨더니 종료되지 않는다면, 소프트웨어 브레이크포인트가 심은 `0xCC` 바이트를 체크섬 검사가 잡아냈다는 강력한 증거다.
- ScyllaHide 적용 후에도 여전히 종료된다면, PEB/API 기반이 아니라 타이밍이나 자체 무결성 체크일 가능성이 크므로 방향을 바꿔야 한다.

## 흔한 실수
- 프로그램 자체의 안티디버깅(REV-0234~0240)만 떠올리고, 패커 스텁 고유의 방어 로직이 별도로 존재할 수 있다는 점을 간과하는 것.
- 소프트웨어 브레이크포인트만 계속 쓰면서 "디버거가 이상하다"고 오해하는 것 — 하드웨어 브레이크포인트로 바꾸는 것만으로 해결되는 경우가 상당히 많다.
- ScyllaHide 같은 안티안티디버깅 플러그인의 존재를 모른 채 모든 체크를 수동으로 하나씩 찾아 패치하려 드는 것 — 우선 플러그인으로 일반적인 탐지를 자동 우회해보는 것이 훨씬 빠르다.
- 상용 프로텍터를 상대로 완벽한 우회를 목표로 시간을 무한정 쓰는 것 — CTF 맥락에서는 목표 로직만 확인하면 충분한 경우가 많다.

## 막혔을 때 다음 체크
- 프로그램 로직 자체의 안티디버깅까지 함께 의심된다면 → REV-0240(디버거에서 갑자기 종료될 때 체크리스트)을 참고한다.
- 이 단계를 넘겨서 이제 OEP를 찾는 단계로 넘어간다면 → REV-0956(OEP를 찾았는데 실행이 이상하게 될 때)을 참고한다.
- 패커 시그니처는 확인했는데 자동 언패킹 도구가 안 통한다면 → REV-0961(패커 시그니처는 잡히는데 도구가 자동 언패킹을 실패할 때)을 참고한다.

## 미니 예제
```text
1) chall_packed.exe 더블클릭 -> 정상적으로 "Enter password:" 창 뜸
2) x64dbg로 chall_packed.exe 열고 F9 -> 아무 브레이크포인트 없이도 곧바로 프로세스 종료
3) ScyllaHide 활성화(PEB 패치, NtQueryInformationProcess 후킹) 후 재시도
   -> 여전히 종료됨
4) 스텁 코드를 F8로 한 줄씩 진행하며 관찰
   -> rdtsc 호출 직후 비교 명령(cmp eax, 임계값) 발견
5) 타이밍 기반 체크로 판단, REV-0237 방식 참고해 임계값 비교 분기를 패치하거나
   조건부 브레이크포인트로 그 분기만 강제로 통과시킴
6) 이후 정상적으로 스텁 진행, OEP 탐색 재개
```

## 관련 글
- REV-0240 — 디버거에서 갑자기 종료될 때 체크리스트
- REV-0241 — 패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환
- REV-0956 — OEP를 찾았는데 실행이 이상하게 될 때
- REV-0961 — 패커 시그니처는 잡히는데 도구가 자동 언패킹을 실패할 때

## 출처/검증
- 패커 스텁의 코드 무결성 체크, 타이밍 체크, 자가 attach 방지 기법: 다수의 공개 리버싱 교육 자료와 상용 프로텍터(Themida, VMProtect) 분석 사례에서 공통적으로 설명하는 일반적 패턴을 정리한 것이다(2026-09-09 검증).
- ScyllaHide의 기능과 사용법: ScyllaHide 공식 저장소(github.com/x64dbg/ScyllaHide) 문서 기준.
- x64dbg의 하드웨어 브레이크포인트, 예외 전달 옵션: x64dbg 공식 문서(help.x64dbg.com) 기준.
