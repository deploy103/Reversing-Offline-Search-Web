## 한 줄 요약
엔트로피(entropy)는 데이터가 얼마나 "무작위처럼 보이는지"를 0~8 bits/byte 사이 숫자로 나타낸 값이며, 정상적인 `.text` 코드 섹션은 보통 5.5~6.5 정도인 반면 압축되거나 암호화된 섹션은 7.5~8.0에 가까워지므로, 섹션 엔트로피가 8.0에 근접하면 패킹/암호화를 강하게 의심해야 한다.

## 언제 검색해야 하나
- Detect It Easy나 PE-bear 화면에 "Entropy" 값이 나오는데 그 숫자가 정확히 뭘 의미하는지 모를 때
- REV-0224 패킹 체크리스트에서 "엔트로피가 높다"는 항목을 봤는데 구체적인 기준값이 궁금할 때
- 어떤 섹션이 압축된 것인지 암호화된 것인지 구분하고 싶을 때
- CTF 문제에서 "이 데이터 블록이 XOR로 인코딩된 것 같다"는 감을 수치로 확인하고 싶을 때

## 핵심 개념

### Shannon 엔트로피란 (직관적 설명)
정보이론에서 말하는 **Shannon 엔트로피**는 "이 데이터의 각 바이트 값이 얼마나 골고루, 예측 불가능하게 분포되어 있는가"를 수치로 나타낸 것이다. 공식은 다음과 같다.

```text
H = - Σ p(x) * log2(p(x))     (x는 0~255의 각 바이트 값, p(x)는 그 값이 나타날 확률)
```

이 공식을 몰라도 결론만 알면 충분하다. 한 바이트는 0~255까지 256가지 값을 가질 수 있고, 이 256가지 값이 **완전히 균등하게, 무작위로** 나타날 때 엔트로피가 최댓값인 **8 bits/byte**가 된다(2^8 = 256이므로). 반대로 파일의 모든 바이트가 똑같은 값 하나(예: 전부 0x00)라면 엔트로피는 0이다. 즉 엔트로피는 "이 데이터를 보고 다음 바이트 값을 얼마나 예측하기 어려운가"의 척도이며, 예측하기 쉬울수록(패턴이 있을수록) 값이 낮고, 예측하기 어려울수록(무작위에 가까울수록) 값이 8에 가까워진다.

### 왜 압축/암호화 데이터는 엔트로피가 높은가
- **압축(compression)**: zlib, LZMA, UPX가 쓰는 NRV/LZMA 계열 압축 알고리즘은 원본 데이터의 "반복되는 패턴"을 최대한 짧은 표현으로 바꾼다. 압축이 잘 되었다는 것은 결과 데이터에 더 이상 "짧게 표현할 수 있는 패턴"이 남아 있지 않다는 뜻이고, 이는 곧 바이트 값 분포가 균일하고 무작위처럼 보인다는 뜻이다. 그래서 잘 압축된 데이터는 엔트로피가 7.9~8.0 가까이 나온다.
- **암호화(encryption)**: AES, RC4 같은 암호화 알고리즘의 목표 자체가 "출력을 통계적으로 무작위와 구분할 수 없게 만드는 것"이다. 그래서 암호화된 데이터도 압축된 데이터와 마찬가지로 엔트로피가 매우 높게 나온다. (참고로 이 때문에 엔트로피 측정만으로는 "압축된 것"과 "암호화된 것"을 구분할 수 없다 — 둘 다 높게 나온다. 구분하려면 다른 단서, 예를 들어 알려진 압축 알고리즘의 매직 바이트나 헤더 구조를 봐야 한다.)

### 왜 정상 코드 섹션은 엔트로피가 낮은가
컴파일러가 생성한 x86/x64 기계어 코드는 실제로는 상당히 "패턴이 있는" 데이터다. 자주 쓰이는 명령(`mov`, `push`, `call`, `jmp` 등)의 opcode 바이트가 반복적으로 나타나고, 레지스터 번호도 몇 가지로 제한되며, 상대 주소 오프셋도 특정 범위에 몰려 있다. 따라서 일반적인 `.text` 섹션의 엔트로피는 보통 **5.5~6.5 bits/byte** 정도에 그친다(파일마다 다르지만 8에 훨씬 못 미친다). 문자열이 많은 `.rdata`/`.rodata` 섹션은 ASCII 문자 범위(대부분 0x20~0x7E)만 쓰기 때문에 오히려 더 낮게 나오는 경우도 흔하다.

## 화면/코드에서 보이는 징후
- **Detect It Easy(DIE)의 Entropy 탭**: 파일을 드래그한 뒤 우측 하단(또는 별도 버튼)의 "Entropy" 기능을 열면 섹션별로 막대 그래프와 함께 숫자(0.00~8.00)가 표시된다. 색상으로도 표시되는 경우가 많아, 엔트로피가 높은 섹션은 빨간색/주황색 계열로 눈에 띄게 강조된다.
- **PE-bear의 Section Headers / Entropy 뷰**: 섹션 목록에 엔트로피 열이 함께 표시되며, 8.0에 가까운 섹션이 시각적으로 구분된다.
- 정상적인 `.text` 섹션: 대략 5.5~6.5
- 정상적인 `.rdata`/`.data` 섹션: 문자열/상수 위주라 더 낮거나 중간 정도(3~6 사이, 데이터 성격에 따라 편차가 큼)
- UPX의 `UPX1` 섹션(압축된 코드+데이터가 들어있는 섹션): 7.8~8.0에 근접
- 암호화된 셸코드나 XOR 인코딩된 페이로드가 들어있는 데이터 블록: 7.5~8.0

## 가장 먼저 할 것
DIE에 파일을 드래그한 뒤 Entropy 탭(또는 화면 하단 관련 버튼)을 눌러 섹션별 수치를 눈으로 확인한다. `.text`라는 이름을 가진 섹션인데도 엔트로피가 7.5 이상이면, 이름만 `.text`로 위장했을 뿐 실제로는 압축/암호화된 데이터가 들어있다는 강한 신호다. DIE 사용법은 REV-0126(../windows-pe/rev-0126-die-basics.md)을 참고한다.

## 단계별 절차

**1) DIE로 파일 전체 엔트로피 확인**

DIE에 파일을 드래그하면 상단 결과란 근처에 파일 전체 엔트로피가 함께 표시되는 경우가 많다. 7.9 이상이면 파일 전체가 압축/암호화되어 있다는 뜻이다(패킹된 실행 파일에서 흔함).

**2) 섹션별 엔트로피 세부 확인**

Entropy 탭에서 섹션마다 개별 수치를 확인한다. 어떤 섹션은 낮고(예: 헤더, 심볼 테이블) 어떤 섹션은 매우 높은(코드/리소스가 압축된 섹션) 식으로 편차가 크게 나타나는 것이 패킹된 파일의 전형적인 모습이다.

**3) 섹션 이름과 엔트로피를 함께 판단**

이름이 `.text`인데 엔트로피가 8에 가깝다면 패킹 스텁이 원본 섹션 이름을 그대로 흉내 낸 것일 수 있다(REV-0224의 "섹션 이름 위장" 참고). 이름이 `UPX0`/`UPX1`처럼 이미 낯설다면 REV-0225로 바로 넘어가도 된다.

**4) PE-bear로 교차 검증(선택)**

DIE와 PE-bear는 서로 다른 구현이므로, 애매한 경우 두 도구의 수치를 비교해 일관성을 확인하면 신뢰도가 올라간다.

**5) 리소스/특정 데이터 블록 단위로도 확인**

전체 섹션이 아니라 특정 리소스(REV-0141, ../windows-pe/rev-0141-resource-section.md 참고)나 데이터 블록 하나만 유독 엔트로피가 높다면, 그 부분에만 별도로 암호화된 페이로드(예: 2차 페이로드, 설정 파일, 임베디드 실행 파일)가 숨겨져 있을 가능성을 의심해야 한다.

## 명령어/단축키
- Detect It Easy: 파일 드래그 → 하단/우측 "Entropy" 버튼 클릭 → 섹션별 그래프 확인
- PE-bear: 파일 열기 → Section Headers 탭에서 Entropy 열 확인
- (참고) Python으로 직접 계산하고 싶다면 `scipy.stats.entropy`나 간단한 반복문으로 바이트 빈도를 세어 위 공식을 그대로 구현할 수 있다(오프라인 커스텀 스크립트 작성 시).

## 출력 해석
- 섹션 엔트로피 **0~1**: 대부분 같은 값(0x00 등)으로 채워진 영역. 미사용 예약 공간, 패딩(padding) 등일 가능성이 높다.
- **3~5**: 문자열/구조화된 데이터 위주. `.rdata`, 리소스 문자열 테이블 등에서 흔하다.
- **5.5~6.5**: 일반적인 컴파일된 기계어 코드(`.text`)의 전형적인 범위.
- **7.0~7.5**: 다소 높은 편. 압축이 약하게 걸렸거나, 코드/데이터가 섞여 있거나, 일부 인코딩이 적용된 리소스(예: JPEG, PNG 같은 이미 압축된 이미지 리소스도 이 범위가 나올 수 있음 — 반드시 패킹만을 의미하진 않는다).
- **7.8~8.0**: 매우 높음. 압축(UPX 등) 또는 암호화된 데이터일 가능성이 매우 크다.
- 파일 전체 평균 엔트로피가 7.9 이상이면 → 파일 전체가 패킹되었을 가능성이 매우 높다(REV-0224/REV-0225로 이동).

## 흔한 실수
- 엔트로피가 높다고 무조건 "패킹됨"으로 단정하는 것. 이미 압축된 리소스(JPEG, PNG, ZIP으로 묶인 리소스, 폰트 파일 등)를 포함한 정상 프로그램도 해당 리소스 섹션만 엔트로피가 높게 나올 수 있다. 섹션 이름, 위치(리소스 섹션인지 코드 섹션인지), 다른 징후와 함께 판단해야 한다.
- 압축과 암호화를 엔트로피만으로 구분하려는 것. 엔트로피 수치 자체로는 압축인지 암호화인지 알 수 없으며, 매직 바이트나 알려진 알고리즘의 헤더 구조를 별도로 확인해야 구분된다.
- 파일 전체 평균 엔트로피만 보고 섹션별 편차를 확인하지 않는 것. 예를 들어 코드 섹션은 낮은데 특정 리소스 하나만 매우 높다면, 그건 전체 패킹이 아니라 그 리소스 안에 숨겨진 페이로드일 수 있다(REV-0141 관련).
- 엔트로피 수치의 절대적 임계값(예: "7.5 이상이면 무조건 패킹")을 기계적으로 적용하는 것. 도구/알고리즘에 따라 오차가 있으므로 "높다/낮다"의 상대적 경향을 다른 증거와 함께 참고하는 용도로 쓰는 것이 안전하다.

## 막혔을 때 다음 체크
- 엔트로피는 높은데 어떤 패커인지 시그니처가 안 잡힌다면 → REV-0224로 돌아가 entry point 코드와 import 개수를 함께 재확인한다.
- 특정 섹션만 유독 높다면 → 그 섹션이 리소스 섹션(REV-0141)인지, 코드 섹션인지 먼저 구분한다. 리소스라면 정상적인 압축 이미지/폰트일 수 있다.
- 파일 전체가 다 높게 나온다면 → REV-0225로 이동해 UPX 여부부터 확인한다.
- 엔트로피는 정상 범위인데 다른 패킹 징후(import 부족, 함수 부족)가 있다면 → 패커가 압축이 아니라 코드 난독화(REV-0230~0232) 위주로 동작했을 가능성을 고려한다. 난독화는 반드시 엔트로피를 크게 높이지는 않는다.

## 미니 예제
DIE로 `sample.exe`를 열었더니 다음과 같은 섹션별 엔트로피가 나왔다고 하자.

```text
.text    raw=0x200   entropy=7.92
.rdata   raw=0x100   entropy=7.85
.data    raw=0x050   entropy=2.10
.rsrc    raw=0x080   entropy=4.30
```

`.text`와 `.rdata`가 이름은 정상적인데 엔트로피가 7.9에 가깝다. 정상적인 컴파일된 코드라면 5.5~6.5 정도여야 하므로, 이 섹션들은 이름만 표준을 흉내 냈을 뿐 실제로는 압축된 데이터가 들어있는 것으로 강하게 의심된다. `.data`는 2.10으로 낮아 정상적인 초기화된 변수 영역으로 보이고, `.rsrc`는 4.30 정도로 아이콘/문자열 리소스가 섞인 전형적인 범위다. 이 경우 다음 단계는 REV-0225로 가서 UPX 여부(섹션 이름과 무관하게 매직 바이트 확인)를 검사하는 것이다.

## 출처/검증
- Shannon 엔트로피의 정의와 압축/암호화 데이터가 최대 엔트로피(8 bits/byte)에 가까워지는 이유는 정보이론의 표준적인 설명(Claude Shannon, "A Mathematical Theory of Communication", 1948)에 기반한 일반 상식 수준의 내용이다.
- 정상 코드 섹션과 압축/암호화 섹션의 대략적인 엔트로피 범위(5.5~6.5 대 7.8~8.0)는 Detect It Easy, PE-bear 등 도구가 실무에서 패킹 탐지 지표로 사용하는 방식과 다수의 공개 리버싱/포렌식 교육 자료에서 공통적으로 제시하는 경험적 범위를 정리한 것이다(2026-09-08 검증).
- 정확한 임계값은 파일/컴파일러/컴파일 옵션에 따라 달라질 수 있으므로, 특정 샘플 판단 시에는 여러 섹션을 상대 비교하는 방식으로 사용하는 것을 권장한다.
