## 한 줄 요약
UPX처럼 공식 자동 복원 도구가 없는 패커(VMProtect, Themida, 커스텀 패커 등)를 풀려면, 프로그램을 디버거로 실행해서 압축 해제가 끝나고 원본 코드로 넘어가는 순간(OEP, Original Entry Point)을 찾은 뒤, 그 시점의 메모리 내용을 파일로 떠서(dump) 분석 가능한 실행 파일로 재구성해야 한다 — 이것이 "수동 언패킹"의 핵심 개념이다.

## 언제 검색해야 하나
- REV-0225/REV-0226 절차로 확인했더니 UPX가 아니거나, `upx -d`가 통하지 않는 패커를 만났을 때
- "OEP"라는 용어를 리버싱 글이나 툴 화면에서 봤는데 무슨 뜻인지 모를 때
- "메모리에서 덤프한다"는 표현이 정확히 무엇을 하는 것인지 궁금할 때
- x64dbg의 "Scylla" 플러그인이나 IDA의 dump 관련 기능을 언제/왜 쓰는지 감이 안 잡힐 때
- 상용 패커(VMProtect, Themida, Enigma)로 패킹된 바이너리를 만나서 "직접 풀어야 하나?"라는 생각이 들 때

## 핵심 개념

### OEP(Original Entry Point)란
모든 실행 파일은 PE 헤더/ELF 헤더에 "프로그램 실행이 시작되는 주소"(entry point)가 적혀 있다. 패킹되지 않은 정상 파일이라면 이 주소는 컴파일러가 생성한 초기화 코드(`__libc_start_main` 호출 준비 코드, CRT 초기화 등)를 가리킨다. 그런데 패킹된 파일은 이 entry point 값이 **패커의 압축 해제 스텁(unpacking stub) 코드**를 가리키도록 바뀌어 있다. 즉 파일 헤더에 적힌 entry point는 진짜 프로그램의 시작점이 아니라 "압축을 풀고 나서 진짜 시작점으로 점프하는 코드"의 시작점일 뿐이다.

**Original Entry Point(OEP)**는 바로 그 "진짜 프로그램이 원래 시작했어야 할 주소"를 가리키는 용어다. 압축 해제 스텁은 실행되는 동안 압축된 원본 코드/데이터를 메모리에 그대로 복원해놓은 뒤, 마지막에 딱 한 번 `JMP OEP` 같은 명령으로 원본 코드로 넘어간다. 이 점프가 일어나는 순간이 바로 "언패킹이 완료된 시점"이며, 리버서가 찾아야 할 목표 지점이다.

### 왜 메모리 덤프가 필요한가
OEP를 찾았다고 해서 끝이 아니다. 디스크에 있는 파일 자체는 여전히 압축된 상태 그대로다(패커가 파일을 수정하는 것이 아니라, 실행 중에만 메모리에서 압축을 풀기 때문). 따라서 "메모리 안에서는 이미 다 풀려 있는 원본 코드"를 **파일로 다시 떠내는(dump)** 작업이 필요하다. 이것이 "프로세스 덤프" 또는 "메모리 덤프"라고 부르는 작업이다.

개념적으로는 다음과 같은 순서다.

1. 디버거로 패킹된 프로그램을 실행한다.
2. 압축 해제가 끝나고 OEP로 점프하기 직전(또는 직후)에 실행을 멈춘다(브레이크포인트).
3. 이 순간 프로세스의 메모리 전체(또는 필요한 영역)를 그대로 파일로 복사해서 저장한다.
4. 저장된 파일은 메모리에서 실행되던 상태 그대로이므로, 디스크 실행 파일 포맷과 몇 가지가 다르다(특히 import table). 이를 실행 가능한 형태로 다시 맞춰주는 후처리가 필요하다.

### 왜 import table을 다시 고쳐야 하는가
정상 실행 파일은 IAT(Import Address Table)에 "이 프로그램이 어떤 DLL의 어떤 함수를 쓰는지"가 정리되어 있고, 로더가 실행 시 그 함수들의 실제 주소를 채워 넣는다. 그런데 패킹된 프로그램은 원본 IAT 정보를 감춘 채, 실행 중에 스텁이 직접 `LoadLibraryA`/`GetProcAddress`로 필요한 함수 주소를 알아내서 자기만의 방식으로 채워 넣는 경우가 많다(REV-0229 참고). 그래서 메모리를 덤프한 시점에는 "함수 주소는 메모리에 이미 다 채워져 있지만, 그 주소가 어느 DLL의 어느 함수였는지"를 알려주는 정상적인 IAT 구조가 없을 수 있다. 이를 실제 함수 이름과 다시 연결해주는 작업을 **IAT 복구(import table 재구성)**라고 부르며, x64dbg의 Scylla 플러그인이나 별도 도구인 ImpREC(Import REConstructor) 같은 것이 이 작업을 도와준다.

## 화면/코드에서 보이는 징후
- REV-0225/0226에서 `upx -l`, `upx -d`가 모두 실패한다.
- Detect It Easy가 UPX가 아닌 다른 패커 이름(`VMProtect`, `Themida`, `Enigma Protector`, `ASPack` 등)을 표시하거나, 시그니처를 아예 못 찾고 "Unknown"이라고만 뜬다.
- entry point 코드가 UPX의 짧고 규칙적인 패턴이 아니라, 훨씬 길고 복잡한 코드(가상 머신 인터프리터 같은 반복 구조, 다량의 자체 수정 코드)로 되어 있다.
- x64dbg로 프로그램을 실행하면 처음에는 잘 모르는 주소들만 계속 실행되다가, 어느 순간 갑자기 코드 성격이 바뀌면서(예: 익숙한 함수 호출 패턴, 알아볼 수 있는 문자열 참조 시작) 원본 코드 영역으로 넘어간 듯한 느낌을 준다 — 이 지점이 OEP일 가능성이 높다.

## 가장 먼저 할 것
UPX가 아니라는 것이 확인되면, 먼저 "정말 수동 언패킹이 필요한가"부터 재검토한다. 많은 CTF 문제는 패킹 자체보다 그 안의 로직이 목표이므로, 굳이 완벽하게 언패킹된 실행 파일을 만들지 않고도 **디버거로 그냥 실행하면서 동적 분석만으로 문제를 풀 수 있는 경우**가 많다. 예를 들어 비밀번호 비교 로직이 궁금하다면, OEP를 정확히 찾아 파일로 덤프하는 대신 그냥 x64dbg에서 실행하다가 `strcmp` 계열 함수에 브레이크포인트를 걸어 확인하는 편이 더 빠를 수 있다. 완전한 정적 분석용 언패킹 파일이 꼭 필요한 상황(예: IDA에서 오래 붙잡고 분석해야 하는 큰 프로그램)일 때만 이 문서의 개념을 실제로 적용해볼 가치가 있다.

## 단계별 절차 (개념 수준)
이 문서는 실전 수동 언패킹의 세부 클릭 절차까지 다루지는 않는다(패커마다 방식이 크게 다르고, 난이도가 높은 별도 주제이기 때문이다). 대신 전체 흐름의 개념을 정리한다.

**1) OEP 추정 위치 찾기**

디버거(x64dbg)로 실행하면서 "메모리 쓰기가 많이 일어나는 구간이 끝나는 지점", "스택 포인터가 처음 push된 이후 다시 원래 레벨로 돌아오는 지점(ESP/RSP 트릭)", 또는 "그 동안 안 보이던 API 호출 패턴이 갑자기 정상적으로 시작되는 지점"을 단서로 삼아 OEP 후보를 좁혀간다.

**2) OEP에서 실행 정지**

후보 주소에 브레이크포인트를 걸고 그 지점에서 실행을 멈춘다. 이 시점의 코드가 정상적인 컴파일러 스타일 코드(예: 함수 프롤로그 `push ebp` / `mov ebp, esp`, 익숙한 CRT 초기화 패턴)로 보이면 OEP를 맞게 찾은 것이다.

**3) 메모리 덤프**

이 시점에서 프로세스 메모리를 파일로 떠낸다. x64dbg + Scylla 조합에서는 Scylla 플러그인이 "Dump" 버튼으로 현재 메모리 상태를 실행 파일 형태로 저장해준다.

**4) IAT(Import table) 복구**

Scylla의 "IAT Autosearch" 기능으로 메모리에서 IAT로 추정되는 영역을 찾고, "Get Imports"로 각 주소가 어떤 DLL의 어떤 함수인지 알아낸 뒤, "Fix Dump"로 방금 만든 덤프 파일의 import table을 정상적인 구조로 다시 써준다.

**5) 검증**

복구된 파일을 IDA에 열어 함수/문자열/import가 정상적으로 보이는지, 그리고 실제로 실행했을 때 원본과 동일하게 동작하는지 확인한다.

## 명령어/단축키
- x64dbg에서 실행/일시정지: `F9`(Run), `F7`(Step Into), `F8`(Step Over)
- x64dbg 메모리 쓰기 브레이크포인트: 메모리 맵에서 섹션 우클릭 → `Set Memory Breakpoint on Write` (압축 해제가 끝나는 지점을 잡을 때 사용하는 대표적인 방법 중 하나)
- Scylla 플러그인: x64dbg의 `Plugins → Scylla` 메뉴에서 실행
- Scylla의 `IAT Autosearch` / `Get Imports` / `Fix Dump` 버튼: IAT 복구 3단계

## 출력 해석
- OEP 후보 지점에서 코드가 여전히 짧고 반복적이며 이상한 API만 호출한다면 → 아직 언패킹 스텁 내부이므로 더 진행해야 한다.
- OEP 후보 지점에서 함수 프롤로그(`push ebp; mov ebp, esp` 또는 x64의 `sub rsp, ...`)와 함께 원본이 쓸 법한 API(`GetStdHandle`, `printf` 계열 등) 호출이 바로 보이면 → OEP를 제대로 찾았을 가능성이 높다.
- Scylla의 `Get Imports` 결과에 "invalid" 또는 물음표로 표시되는 항목이 많다면 → OEP를 잘못 찾았거나(너무 이르게 멈춤), IAT 위치를 잘못 지정한 것이다. OEP를 다시 찾아야 한다.

## 흔한 실수
- OEP를 "그냥 대충 그럴듯해 보이는 지점"으로 넘겨짚고 덤프해서, IAT 복구가 계속 실패하는데 원인을 못 찾는 것. OEP가 조금만 어긋나도 이후 단계가 전부 틀어진다.
- 상용 패커(VMProtect, Themida 등)를 UPX와 같은 방식으로 몇 분 만에 풀릴 것이라 기대하는 것. 이런 패커는 코드 가상화, 안티 디버깅이 겹겹이 있어서 숙련자도 수동 언패킹에 오랜 시간이 걸리며, CTF 맥락에서는 언패킹 자체보다 동적 분석으로 우회하는 것이 더 실용적인 경우가 많다.
- 덤프한 파일의 import table을 복구하지 않고 바로 실행해서 크래시가 나는 것을 "언패킹 실패"로 오해하는 것. 메모리 덤프 직후에는 IAT가 깨져 있는 것이 정상이며, Fix Dump 단계를 거쳐야 실행 가능해진다.
- 안티 디버깅 루틴(REV-0230 관련) 때문에 애초에 디버거로 실행하는 것 자체가 막혀서 OEP를 찾기도 전에 프로그램이 종료되는 것. 이 경우 안티 디버깅 우회가 선행되어야 한다.

## 막혔을 때 다음 체크
- OEP를 아무리 찾아도 안 보인다면 → 애초에 자동 언패킹 도구(패커 이름 + "unpacker"로 검색)가 이미 존재하는 유명 패커일 수 있으니 먼저 찾아본다.
- 프로그램이 디버거 안에서 아예 이상하게 동작하거나 바로 종료된다면 → 안티 디버깅 체크(`IsDebuggerPresent`, `ptrace` 등)가 있을 가능성이 높으니 동적 분석 카테고리의 안티 디버깅 우회 문서를 먼저 확인한다.
- 코드가 실행할 때마다 스스로를 계속 다시 쓰는 것처럼 보인다면 → REV-0230(Self-modifying Code 기초)을 참고해 그 패턴부터 이해한다.
- 시간이 너무 오래 걸린다면 → CTF 맥락에서는 완전한 언패킹 대신 동적 분석만으로 목표(플래그, 비교 로직)를 확인하는 것이 더 실용적인 선택일 수 있다.

## 미니 예제
개념을 코드 수준 의사코드로 요약하면 다음과 같다.

```text
[패킹된 파일 entry point]
stub_start:
    pushad
    ; 압축된 데이터를 원본 위치에 풀어놓는 루프 (수백~수천 번 반복)
    decompress_loop:
        ...
    ; IAT를 스텁이 직접 채워 넣음
    resolve_imports:
        call LoadLibraryA
        call GetProcAddress
        ...
    popad
    jmp OEP        ; <-- 바로 이 지점이 "원래 프로그램이 시작했어야 할 곳"

[OEP, 원본 프로그램 시작]
OEP:
    push ebp
    mov ebp, esp
    sub esp, 0x40
    call GetStdHandle   ; 원본이 실제로 쓰는 정상적인 API 호출 시작
    ...
```

`jmp OEP` 직전이나 직후에 브레이크포인트를 걸어 멈추면, 그 시점의 메모리에는 이미 압축이 다 풀린 원본 코드가 올라와 있다. 그 메모리 상태를 그대로 파일로 떠내고 IAT를 복구하면, 디스크에서는 압축되어 있던 원본 프로그램과 사실상 동일한 실행 파일을 얻을 수 있다.

## 출처/검증
- OEP의 정의와 압축 해제 스텁이 원본 코드로 점프하는 구조, IAT 복구가 필요한 이유는 x64dbg 공식 문서(help.x64dbg.com) 및 Scylla 플러그인(github.com/NtQuery/Scylla) 공식 설명을 기준으로 정리했다(2026-09-08 검증).
- OEP 탐색에 흔히 쓰이는 메모리 쓰기 브레이크포인트, ESP 트릭 등의 기법은 다수의 공개 리버싱 교육 자료에서 공통적으로 설명하는 일반적인 접근법을 요약한 것이며, 실제 성공 여부는 패커 종류와 버전에 크게 좌우되므로 특정 샘플에 적용할 때는 별도 검증이 필요하다.
