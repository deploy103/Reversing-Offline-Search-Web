## 한 줄 요약
디버거로 실행/attach했을 때만 프로그램이 갑자기 죽거나 다르게 동작한다면, 십중팔구 이 시리즈(REV-0233~0239)에서 다룬 안티디버깅/안티VM 체크 중 하나에 걸린 것이다 — 아래 체크리스트를 위에서부터 순서대로 확인하면 대부분의 경우 원인을 빠르게 좁힐 수 있다.

## 언제 검색해야 하나
- `./chall`로 직접 실행하면 멀쩡한데 `gdb ./chall` → `run`으로 실행하면 프로그램이 이상하게 종료될 때
- x64dbg로 프로그램을 열고 `F9`를 눌렀는데 정상 실행 때와 다른 메시지가 뜨거나 그냥 꺼질 때
- attach만 했는데(브레이크포인트를 하나도 안 걸었는데도) 프로그램이 종료될 때
- 어디서부터 원인을 찾아야 할지 막막할 때, 순서대로 훑어볼 체크리스트가 필요할 때

## 핵심 개념
안티디버깅 기법은 종류가 다양해도 결국 "디버거 유무를 판단하는 신호 하나를 확인하고, 참이면 종료/오동작으로 분기"한다는 공통 구조를 가진다. 따라서 원인을 찾을 때는 **"어떤 신호를 확인하는가"** 기준으로 후보를 좁혀나가는 것이 효율적이다. 아래 체크리스트는 실제로 자주 만나는 순서대로 정리한 것이다.

디버거가 없을 때는 멀쩡히 동작하던 프로그램이 디버거를 붙이는 순간 달라진다는 것은, 프로그램 코드 어딘가에 "디버거의 존재 여부"를 관찰 가능한 신호(API 반환값, 메모리 상의 플래그, 실행 시간, 예외 처리 방식, 시스템 콜 성공/실패)로 바꿔서 확인하는 로직이 반드시 있다는 뜻이다. 이 신호는 운영체제/커널이 "지금 이 프로세스를 누군가 디버깅하고 있다"는 사실을 어떤 형태로든 노출하기 때문에 생기며, 완전히 숨기는 것은 사실상 불가능하다 — 다만 그 신호를 어떤 API/명령으로 조회하느냐에 따라 발견 난이도가 달라질 뿐이다. 체크리스트를 순서대로 훑는 이유는, 실전에서 가장 자주 쓰이는(따라서 가장 먼저 의심해볼 만한) 순서로 신호의 종류를 나열해두었기 때문이다.

## 화면/코드에서 보이는 징후
- 정상 실행과 디버거 실행의 출력/종료 코드가 다르다.
- 특정 지점(항상 같은 주소)에서 종료되거나 예외가 발생한다.
- attach 시점, 브레이크포인트 도달 시점, Step 실행 중 등 "언제" 죽는지가 매번 비슷하다.

## 가장 먼저 할 것
디버거를 닫고 그냥 실행했을 때와, 디버거로 실행했을 때의 차이를 정확히 기록한다 — 어느 시점(시작 직후/특정 입력 이후/특정 주소)에 갈라지는지가 원인 후보를 좁히는 가장 중요한 단서다.

## 단계별 절차 (체크리스트)

**1. Windows API 기반 체크 확인 — `IsDebuggerPresent`/`CheckRemoteDebuggerPresent`**
IDA Imports 탭에서 이 두 이름을 검색한다. 있다면 REV-0235를 참고해 호출 위치와 분기를 확인한다.

**2. PEB 직접 접근 확인 — `fs:[30h]`/`gs:[60h]`**
Import 목록에 아무것도 없다면, 어셈블리에서 세그먼트 레지스터 접근(`gs:`, `fs:`)을 텍스트 검색한다. REV-0236을 참고한다.

**3. Linux: ptrace 자가 트레이싱 확인**
`strace -f ./chall`로 초반에 `ptrace(PTRACE_TRACEME, ...)` 호출과 그 반환값을 확인한다. `-1`(EPERM)이면 REV-0234의 패턴이다.

**4. 타이밍 체크 확인 — RDTSC/GetTickCount/QueryPerformanceCounter**
`rdtsc` 텍스트 검색 또는 관련 API import를 확인한다. 발견되면 REV-0237을 참고해 임계값과 비교 위치를 찾는다. 특히 **Step 실행 중에만 죽는다면** 이 체크가 가장 유력한 후보다 — 사람이 한 줄씩 밟는 것 자체가 시간을 많이 소비하기 때문이다.

**5. CPUID 기반 VM 탐지 확인**
디버거를 VM 안에서 쓰고 있다면, `cpuid` 사용처와 벤더 문자열 비교(REV-0238)를 확인한다. 물리 PC에서는 재현이 안 되는데 VM에서만 재현된다면 이 경로가 유력하다.

**6. 예외 기반 체크 확인 — int3/SEH**
`__try`/`__except` 블록, `SetUnhandledExceptionFilter`, 코드 중간의 이질적인 `0xCC` 바이트를 확인한다(REV-0239). 특히 **디버거가 예외 메시지를 보여주며 멈췄다면** 이 경로일 가능성이 매우 높다. 이 경우 디버거의 "예외를 프로그램에 전달"(x64dbg `Shift+F9`, GDB `handle SIGTRAP nostop pass`) 옵션부터 시도해본다.

**7. 문자열 난독화로 인한 오판 확인**
안티디버깅이 아니라, 복호화되지 않은 문자열/데이터를 정상 데이터로 착각해서 이후 로직이 깨지는 경우도 있다(REV-0233). "죽는다"기보다 "이상하게 동작한다"는 증상이면 이쪽도 함께 의심한다.

**8. 위 어디에도 해당 없으면 — 패커/프로텍터 자체의 무결성 체크**
UPX 이상의 상용 패커(VMProtect, Themida 등)는 자체 코드 무결성 체크(체크섬)를 갖고 있어서, 디버거가 임시로 코드에 `0xCC`를 심는 것 자체(소프트웨어 브레이크포인트)만으로도 체크섬이 깨져 종료될 수 있다. 이 경우 하드웨어 브레이크포인트(디버그 레지스터 기반, 코드 바이트를 건드리지 않음)로 바꿔서 다시 시도한다.

## 명령어/단축키
- IDA: `Ctrl+F`(Imports 검색), `Alt+T`(텍스트 검색), `Shift+F12`(Strings 창)
- x64dbg: Options → Preferences → Exceptions(예외 자동 전달 설정), 브레이크포인트를 하드웨어 방식으로 걸기(주소 우클릭 → Breakpoint → Hardware, on Execution)
- GDB: `strace -f ./chall`(별도 터미널에서 먼저 관찰), `handle SIGTRAP nostop pass`, `catch syscall ptrace`
- 공통: 정상 실행 로그와 디버거 실행 로그를 나란히 비교(`diff`)

## 출력 해석
- 종료 시점이 실행할 때마다 같은 주소/같은 타이밍이면 결정론적 체크(API 기반, PEB 기반)일 가능성이 높다.
- 종료 시점이 매번 조금씩 다르면(사람이 조작하는 속도에 따라 달라짐) 타이밍 기반 체크일 가능성이 높다.
- VM에서만 재현되면 CPUID/VM 흔적 기반, 물리 PC에서도 재현되면 API/PEB/예외 기반일 가능성이 높다.

## 흔한 실수
- 체크리스트를 순서 없이 이것저것 시도하다가 이미 확인한 항목을 반복하는 것 — 위에서부터 순서대로, 확인한 항목은 표시해가며 진행한다.
- 하나의 체크를 우회했다고 바로 안심하는 것 — 실제로는 여러 겹의 체크가 동시에 존재하는 경우가 흔하다.
- 디버거 설정(예외 전달 옵션, 하드웨어 브레이크포인트 사용 여부) 자체가 원인일 수 있다는 걸 간과하고 바이너리만 계속 들여다보는 것.
- attach 방식과 실행 방식(디버거로 처음부터 실행 vs 이미 실행 중인 프로세스에 attach)의 차이를 구분하지 않는 것 — 일부 체크는 attach 시점에만, 일부는 시작 시점에만 반응하므로 두 가지 방식을 모두 시도해봐야 한다.
- 재현이 간헐적으로만 될 때 "운이 나쁘다"고 넘기는 것 — 타이밍 기반 체크는 분석 속도(사람이 얼마나 빨리 F8을 누르는지)에 따라 통과하거나 걸리거나 하므로, 재현이 불안정하다는 것 자체가 타이밍 체크(REV-0237)의 강한 단서다.

## 막혔을 때 다음 체크
- 체크리스트를 다 훑었는데도 원인을 못 찾았다면 → 정적 분석을 잠시 멈추고 완전히 동적인 접근(REV-0241)으로 전환해, 정상 실행과 디버거 실행을 나란히 스텝하며 정확히 어느 명령에서 갈라지는지 이진 탐색하듯 좁혀나간다.
- 패커/프로텍터가 의심되면 → Detect It Easy(DIE)로 먼저 패커 시그니처를 확인하고, 언패킹이 먼저 필요한지 판단한다.
- 여전히 막히면 → 종료 직전 마지막 API 호출이나 마지막으로 실행된 명령 주소를 기록해두고, 그 주소 근처 코드를 REV-0233~0239 각 글의 "화면/코드에서 보이는 징후" 절과 하나씩 대조한다.

## 미니 예제
**정상 실행 vs 디버거 실행 비교 절차 예시**
```text
1) 터미널1: ./chall 직접 실행 → "Correct!" 출력, 정상 종료(exit 0)
2) 터미널2: gdb ./chall → run → "Segmentation fault" 로 비정상 종료
3) 두 실행의 차이가 "gdb로 실행했는가"뿐이므로 안티디버깅 의심
4) strace -f ./chall 로 관찰 → ptrace(PTRACE_TRACEME, ...) = 0 확인
5) gdb에서 동일 지점 관찰 → ptrace(PTRACE_TRACEME, ...) = -1 EPERM 확인
6) REV-0234의 우회 절차 적용
```

## 체크리스트를 습관으로 만들기
이 체크리스트를 매번 처음부터 새로 떠올리기보다는, 새 크랙미를 받을 때마다 위 8단계를 순서대로 5분 안에 훑어보는 루틴으로 만들어두면 좋다. 대부분의 CTF 문제는 이 여덟 가지 범주 중 한두 개만 사용하며, 여러 개를 동시에 정교하게 조합하는 경우는 실제 상용 프로텍터가 아닌 이상 드물다. 따라서 체크리스트 초반(1~3번)에서 원인이 발견되는 경우가 실전에서는 압도적으로 많다는 점을 기억해두면, 막연히 전체 바이너리를 처음부터 읽어 내려가는 것보다 훨씬 빠르게 문제를 좁힐 수 있다.

## 관련 글
- REV-0233 — 문자열 난독화가 보일 때
- REV-0234 — ptrace PTRACE_TRACEME 안티디버깅
- REV-0235 — IsDebuggerPresent 우회 개념
- REV-0236 — PEB BeingDebugged 검사 우회 개념
- REV-0237 — RDTSC Time Check 안티디버깅
- REV-0238 — CPUID 기반 VM 탐지 기초
- REV-0239 — Exception 기반 안티디버깅 기초
- REV-0241 — 패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환

## 출처/검증
- 체크리스트 구성은 REV-0233~0239 각 글에서 정리한 개별 안티디버깅/안티VM 기법을 실전 진단 순서로 재구성한 것이며, 근거는 각 개별 글의 출처를 따른다(2026-09-08 검증).
