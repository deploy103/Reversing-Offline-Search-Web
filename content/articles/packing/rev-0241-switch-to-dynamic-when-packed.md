## 한 줄 요약
IDA/Ghidra의 정적 디컴파일 결과가 함수도 거의 없고 문자열도 안 보이고 코드가 뭉개진 것처럼 보인다면, 패킹이나 강한 난독화 때문에 **정적으로 보이는 바이트가 실제 실행되는 코드와 다르기 때문**일 가능성이 높으며, 이럴 때는 정적 분석을 붙잡고 있기보다 실제로 실행시켜서 관찰하는 동적 분석으로 전환하는 것이 훨씬 빠르다.

## 언제 검색해야 하나
- IDA로 파일을 열었는데 함수 개수가 비정상적으로 적고(`Functions` 창에 몇 개뿐), 대부분 코드가 이상한 바이트 나열처럼 보일 때
- Strings 창에 의미 있는 문자열이 거의 없을 때(REV-0233과 함께 의심)
- Detect It Easy(DIE)로 확인했더니 UPX, ASPack, Themida, VMProtect 같은 패커/프로텍터 시그니처가 나올 때
- 파일 섹션의 엔트로피(entropy)가 비정상적으로 높다는 분석 결과(7.5~8.0에 가까움)를 봤을 때
- "이 프로그램은 패킹되어서 정적 분석이 의미 없다"는 이야기를 들었는데 구체적으로 뭘 해야 하는지 모를 때

## 핵심 개념

### 왜 정적 분석이 "틀리게" 보이는가
패커(packer)는 원본 실행 파일을 압축하거나 암호화한 뒤, 그 압축/암호화된 데이터와 함께 "압축을 푸는 코드(스텁, stub)"만 실행 파일에 넣어둔다. 실행 시:
1. OS가 프로세스를 로드하면 엔트리 포인트는 원본 프로그램이 아니라 **패커의 스텁 코드**를 가리킨다.
2. 스텁 코드가 실행되면서 압축/암호화된 원본 데이터를 메모리 상에서 풀어(압축 해제/복호화) 원래 코드로 복원한다.
3. 복원이 끝나면 스텁이 원본 프로그램의 진짜 시작 지점(**OEP, Original Entry Point**)으로 점프한다.

IDA/Ghidra 같은 정적 분석 도구는 **파일에 저장된 바이트를 그대로 읽고 해석**하기 때문에, 이 파일을 열었을 때 보이는 것은 "압축된/암호화된 데이터"와 "그것을 푸는 스텁 코드"뿐이다. 진짜 프로그램 로직은 파일 안에 평문으로 존재하지 않으므로, 아무리 디컴파일해봐야 의미 있는 결과가 나올 수 없다 — **이것이 "디컴파일이 틀렸다"고 느껴지는 근본 원인**이다. 도구가 고장 난 게 아니라, 분석 대상 자체가 정적 분석에 적합하지 않은 상태인 것이다.

난독화(obfuscation)도 비슷한 효과를 낸다. 코드 자체는 파일에 그대로 있지만, 제어 흐름 평탄화(control flow flattening), 불필요한 분기 삽입, 가상 머신 기반 난독화(VM-based obfuscation, 커스텀 바이트코드 인터프리터) 같은 기법이 적용되면 디컴파일러가 원래 의도된 로직을 정확히 복원하지 못하고 뒤죽박죽인 `goto`/`switch` 덩어리로 보여준다.

### 정적 분석이 통하는 범위와 안 통하는 범위
| 상황 | 정적 분석(IDA F5 등)으로 충분한가 |
|---|---|
| 패킹되지 않은 일반 바이너리 | 대체로 충분 |
| UPX 등 단순 압축 패커 | 언패킹(수동 또는 도구)만 하면 이후 정적 분석 가능 |
| 안티디버깅/안티VM 체크(REV-0233~0239) | 정적으로 위치는 찾을 수 있으나, 실제 값/타이밍은 동적으로 확인해야 확실함 |
| 강한 코드 난독화, 가상화 기반 프로텍터(VMProtect 등) | 정적 분석만으로는 사실상 한계, 동적 분석/트레이싱이 필수 |

### 언제 정적에서 동적으로 전환해야 하는가
다음 신호가 하나라도 보이면 정적 분석을 오래 붙잡지 말고 동적 분석으로 넘어가는 것이 시간을 아낀다.
- 함수 개수가 파일 크기에 비해 비정상적으로 적다.
- 엔트로피가 높은 섹션이 있다(압축/암호화된 데이터의 특징).
- Strings 창이 거의 비어 있다.
- DIE(Detect It Easy)가 패커/프로텍터를 시그니처로 인식했다.
- 디컴파일 결과에 의미를 알 수 없는 큰 `switch` 문이나 반복적인 `goto`가 가득하다.

## 화면/코드에서 보이는 징후
- IDA `Functions` 창에 함수가 몇 개(예: 5개 미만)뿐이고, 이름도 `sub_401000` 같은 자동 생성 이름만 있다.
- 코드 섹션 대부분이 회색/빨간색으로 "데이터"처럼 표시되고 명령어로 인식되지 않는다.
- Detect It Easy로 열었을 때 "Packer" 또는 "Protector" 항목에 UPX, ASPack, PECompact, Themida, VMProtect 등의 이름이 나온다.
- 섹션 헤더 정보(IDA의 Segments 창, `readelf -S`/`objdump -h`)에서 `.text` 섹션 크기가 실제 파일 크기에 비해 이상하게 작거나, 이름이 표준과 다른 섹션(`UPX0`, `UPX1` 등)이 있다.

## 가장 먼저 할 것
1. Detect It Easy(DIE)로 파일을 열어 패커/컴파일러 시그니처를 먼저 확인한다 — 이것만으로 "패킹됨"을 몇 초 안에 확증할 수 있다.
2. 패킹이 확인되면, 정적 디컴파일 결과를 신뢰하지 않고 동적 분석(디버거로 직접 실행)으로 넘어갈 준비를 한다.
3. UPX처럼 잘 알려진 단순 패커라면 전용 언패킹 도구(`upx -d`)를 먼저 시도한다 — 성공하면 이후는 다시 일반적인 정적 분석으로 돌아갈 수 있다.

## 단계별 절차
1. Detect It Easy(DIE)로 패커 시그니처를 확인한다. UPX 등 표준 패커로 나오면 `upx -d packed.exe`(또는 대상 파일)로 언패킹을 먼저 시도한다.
2. 언패킹 도구가 실패하거나(커스텀/변형 패커, 상용 프로텍터) 시그니처가 안 잡히면, 디버거로 프로그램을 직접 실행해 관찰하는 동적 분석으로 전환한다.
3. 디버거에서 엔트리 포인트부터 실행하며, 스텁 코드가 반복적으로 메모리에 데이터를 쓰는 루프(압축 해제/복호화 루프)를 관찰한다.
4. 스텁이 끝나고 진짜 프로그램(OEP)으로 점프하는 지점을 찾는다. 흔한 단서는 스텁의 마지막 부분에 있는 큰 폭의 `jmp`(간접 점프 포함)이다.
5. OEP에 도달하면 그 지점에서 메모리 덤프를 뜬다(x64dbg의 Scylla 플러그인 등으로 프로세스 메모리를 파일로 저장) — 이렇게 뜬 덤프는 압축이 풀린 상태의 코드를 담고 있어 IDA로 다시 열면 훨씬 정상적인 정적 분석이 가능해진다.
6. 안티디버깅 체크(REV-0233~0239)가 이 과정을 방해한다면, 각 글의 대응법을 순서대로 적용한다.
7. 언패킹/덤프까지 가지 않고도 될 경우, 굳이 정적 복원을 시도하지 말고 그냥 "관심 있는 동작(정답 비교, 문자열 복호화 등)이 일어나는 지점"에 브레이크포인트를 걸어 필요한 정보만 동적으로 뽑아내는 실용적인 접근도 충분히 유효하다 — CTF에서는 완벽한 언패킹보다 이 방식이 더 빠를 때가 많다.

## 명령어/단축키
- Detect It Easy: 파일 드래그 앤 드롭 후 좌측 하단 결과 확인, 스캔 심화 옵션으로 여러 시그니처 DB 동시 적용
- Linux: `upx -d ./packed`(UPX 언패킹 시도), `readelf -S ./packed`(섹션 이름/크기로 UPX 흔적 확인)
- x64dbg: 엔트리 포인트에서 시작 후 `F9`로 실행하며 스텁 루프를 관찰, ESP(스택 포인터) 값이 급격히 바뀌는 지점을 "ESP 상의 하드웨어 브레이크포인트"로 잡아 OEP 근처를 빠르게 찾는 기법("ESP 트릭")도 있음
- x64dbg 플러그인: Scylla(OEP 도달 후 메모리 덤프 + IAT 복구)
- IDA: 덤프된 파일을 다시 열어 `Shift+F12`(Strings), `F5`(디컴파일)로 정상적인 정적 분석 재시도

## 출력 해석
- 언패킹 후 Strings 창에 의미 있는 문자열이 갑자기 많이 나타난다면 언패킹이 성공했다는 좋은 신호다.
- 덤프한 파일을 IDA로 열었을 때 함수 개수가 크게 늘어나고 이름이 원래 컴파일러가 남긴 심볼(라이브러리 함수 등)로 인식되기 시작하면 정상적인 정적 분석 단계로 돌아온 것이다.

## 흔한 실수
- 패킹된 파일을 그대로 붙잡고 몇 시간씩 디컴파일 결과를 해석하려고 애쓰는 것 — DIE로 30초만 확인해도 패킹 여부를 바로 알 수 있다.
- UPX처럼 쉬운 경우에도 수동 언패킹을 시도하며 시간을 낭비하는 것 — 표준 패커는 먼저 전용 도구를 시도하는 게 훨씬 빠르다.
- OEP를 찾았다고 착각하고 너무 이른 지점에서 덤프를 떠서, 여전히 스텁 코드 일부만 담긴 불완전한 덤프로 분석을 이어가는 것.
- 동적 분석으로 필요한 정보(예: 복호화된 문자열 하나)만 얻으면 되는 상황에서도 굳이 완전한 언패킹/덤프를 고집하는 것 — CTF에서는 목적에 맞게 최소한의 동적 관찰로 끝내는 것이 효율적이다.

## 막혔을 때 다음 체크
- DIE가 패커를 못 잡아낸다면 → 섹션 엔트로피를 직접 확인하거나(대부분의 PE 분석 도구가 제공), 파일 크기 대비 코드 섹션 크기가 비정상적으로 작은지 본다.
- OEP를 못 찾겠다면 → "ESP 트릭"이나 스택이 급격히 정리되는 지점(함수 프롤로그 패턴이 다시 정상적으로 나타나는 지점)을 찾는다.
- 덤프한 파일이 IDA에서 여전히 이상하게 보인다면 → Import Address Table(IAT)이 아직 복구되지 않아서일 수 있다. Scylla 같은 도구로 IAT 복구까지 함께 진행한다.
- 안티디버깅 때문에 언패킹 과정 자체가 방해받는다면 → REV-0240 체크리스트로 돌아가 원인을 먼저 제거한다.

## 미니 예제
**판단 흐름 예시**
```text
1) IDA로 파일 열기 -> Functions 창에 함수 3개뿐, 코드 대부분 회색
2) Detect It Easy로 확인 -> "UPX 3.96" 시그니처 확인
3) upx -d ./chall 시도 -> 성공, 파일 크기가 커짐
4) 다시 IDA로 열기 -> 함수 200개 이상, Strings 창에 "Enter password" 등 정상 문자열 확인
5) 이제부터 REV-0233~0239 기준으로 안티디버깅 체크 유무를 정적으로 다시 확인
```

## 관련 글
- REV-0233 — 문자열 난독화가 보일 때
- REV-0240 — 디버거에서 갑자기 종료될 때 체크리스트

## 출처/검증
- 패커의 스텁/OEP 구조 및 언패킹 일반 절차(ESP 트릭, Scylla를 이용한 덤프/IAT 복구): 공개된 리버싱 교육 자료 및 UPX/Scylla 공식 문서에서 다루는 표준 절차를 정리함(2026-09-08 검증).
- Detect It Easy(DIE)의 패커/컴파일러 시그니처 탐지 기능: DIE 공식 프로젝트 문서 기준.
