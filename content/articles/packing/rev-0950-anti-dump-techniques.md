## 한 줄 요약
Anti-Dump는 프로텍터가 OEP를 정확히 찾아도 메모리 덤프 자체가 정상적으로 되지 않도록 방해하는 기법군으로, PE 헤더 값을 실행 중에 의도적으로 훼손하거나, IAT/코드 섹션 크기를 실제와 다르게 위조하거나, 덤프 시도(예: 특정 메모리 접근 패턴)를 탐지해서 프로세스를 종료하는 방식으로 REV-0944~0946의 절차를 실패하게 만든다.

## 언제 검색해야 하나
- OEP는 정확히 찾은 것 같은데 Scylla의 Dump 버튼을 눌러도 결과 파일이 손상되어 있거나 실행이 안 될 때
- 덤프한 파일 크기가 원본 프로세스 메모리 사용량에 비해 비정상적으로 작을 때
- 덤프를 시도하는 순간 프로세스가 갑자기 종료되거나 디버거가 응답 없음 상태가 될 때
- "안티덤프"라는 용어를 들었는데 안티 디버깅과 뭐가 다른지 헷갈릴 때

## 핵심 개념

### 안티 디버깅과의 차이
안티 디버깅(REV-0234~0240)은 "디버거가 붙어있는지 자체를 탐지해서 실행을 막거나 방해하는" 기법이다. 반면 안티 덤프는 디버거가 붙어있는 것은 허용하더라도(또는 이미 우회되었다는 전제 하에), "메모리를 파일로 떠내는 행위" 자체를 방해하거나, 떠낸 결과물이 쓸모없게 만드는 기법이다. 즉 목표하는 방해 시점이 다르다 — 안티 디버깅은 "관찰 자체"를, 안티 덤프는 "관찰 결과를 파일로 가져가는 것"을 막는다.

### 대표적인 안티 덤프 기법
1. **PE 헤더 값 훼손**: 프로세스가 실행되는 동안 메모리 상의 PE 헤더(예: `SizeOfImage`, 섹션 헤더의 `VirtualSize`/`SizeOfRawData`)를 정상 값과 다르게 바꿔놓는다. Scylla 같은 덤프 도구는 이 헤더 값을 참고해서 "얼마만큼의 메모리를 파일로 떠낼지" 계산하는데, 값이 위조되어 있으면 필요한 코드/데이터의 일부만 떠내거나 엉뚱한 범위를 떠내게 된다.
2. **섹션 크기/개수 위조**: 실제로는 5개의 섹션이 있는데 헤더에는 3개만 있다고 기록해두면, 덤프 도구가 나머지 2개 섹션(중요한 코드가 들어있을 수 있는)을 아예 인식하지 못하고 건너뛴다.
3. **덤프 시도 탐지**: 일부 프로텍터는 자신의 메모리 영역을 다른 프로세스(디버거)가 `ReadProcessMemory`로 읽어가려는 시도 자체를 감지해서(스레드로 주기적으로 자기 자신의 메모리 상태를 감시하거나, 특정 API 후킹으로) 그 순간 프로세스를 종료하거나 예외를 발생시킨다.
4. **코드 섹션 재암호화 타이밍 조작**: REV-0949(함수 단위 암호화)와 결합해서, "지금 이 순간만 평문"인 코드 구간을 아주 짧게 유지하고 나머지 시간에는 항상 암호화 상태로 되돌려놓아, 덤프를 시도하는 그 짧은 순간을 노리기 어렵게 만든다.
5. **가짜 OEP 유도**: 여러 개의 그럴듯한 `jmp` 지점을 만들어 리버서가 진짜 OEP가 아닌 곳에서 덤프를 시도하게 유도한다(REV-0944에서 언급한 "여러 OEP 후보" 문제의 악의적 버전).

### 대응 전략
- **헤더 값을 신뢰하지 말고 직접 검증한다.** Scylla가 자동으로 계산한 덤프 크기를 그대로 믿지 말고, Memory Map에서 실제 커밋된(committed) 메모리 영역의 크기를 직접 확인해서 비교한다.
- **덤프 도구의 수동 옵션을 활용한다.** Scylla는 "Dump" 시 이미지 크기를 수동으로 지정하는 옵션을 제공한다. 자동 계산값이 의심스럽다면 Memory Map에서 확인한 실제 크기로 직접 입력한다.
- **여러 시점에서 덤프를 시도해본다.** 한 번의 덤프가 손상되었다면, 재암호화 타이밍을 피해 살짝 다른 시점(같은 OEP 근처의 몇 명령 전/후)에서 다시 시도한다.
- **덤프 탐지가 의심되면 우선 안티 디버깅 우회부터 강화한다.** `ReadProcessMemory` 후킹 기반 탐지라면, 이는 사실상 프로세스 내부 API 후킹이므로 x64dbg의 API 브레이크포인트로 해당 후킹 지점을 먼저 무력화해야 할 수 있다.

## 화면/코드에서 보이는 징후
- Scylla로 덤프한 파일을 PE-bear로 열면 섹션 헤더의 `VirtualSize`가 비정상적으로 작거나 0으로 표시됨
- 덤프 파일을 IDA에 열면 일부 섹션의 내용이 전부 0으로 채워져 있음(NULL 패딩)
- 덤프 시도 직후 프로세스가 곧바로 종료되거나 x64dbg가 "process terminated" 메시지를 표시
- 같은 OEP에서 여러 번 덤프를 시도했는데 매번 결과 파일 크기나 내용이 다르게 나옴

## 가장 먼저 할 것
덤프가 실패했다고 판단되면, 먼저 Memory Map에서 프로세스의 실제 커밋된 메모리 영역과 각 섹션에 해당하는 크기를 직접 확인한다. Scylla가 계산한 덤프 크기와 실제 Memory Map 크기를 비교해서 차이가 있는지부터 확인하는 것이 우선이다.

## 단계별 절차
1. OEP에서 정지한 상태에서 `Alt+M`(Memory Map)으로 이동
2. 대상 프로세스의 각 메모리 영역(코드/데이터 섹션에 해당하는 영역)의 실제 크기 확인
3. Scylla의 Dump 옵션에서 자동 계산된 이미지 크기와 비교
4. 차이가 있다면 Scylla의 수동 크기 입력 옵션으로 실제 크기를 직접 지정해 재덤프
5. 덤프 결과 파일을 PE-bear로 열어 섹션별 `VirtualSize`/`SizeOfRawData`가 합리적인지 검증
6. 여전히 손상된다면 OEP 근처의 다른 시점(몇 명령 전/후)에서 재시도
7. 덤프 시도 자체가 프로세스 종료를 유발한다면 API 후킹 기반 탐지 여부를 REV-0239/REV-0240 개념으로 재확인

## 명령어/단축키
- x64dbg: `Alt+M`(Memory Map), 각 영역 우클릭 → `Dump Memory to File`(Scylla 없이 특정 영역만 수동으로 떠내는 대안)
- Scylla: Dump 옵션 창의 이미지 크기 수동 입력 필드
- PE-bear: 섹션 헤더 탭에서 `VirtualSize`, `SizeOfRawData` 값 확인

## 출력 해석
- Memory Map에서 확인한 실제 크기가 Scylla 자동 계산값보다 크다면, 자동 계산이 위조된 헤더 값을 그대로 신뢰해서 일부를 누락시킨 것이다 — 수동으로 큰 값을 입력해 재시도한다.
- 덤프 파일의 특정 섹션이 전부 0으로 채워져 있다면, 그 섹션이 애초에 그 시점에 메모리에 올라와 있지 않았거나(다른 타이밍에 로드됨), 프로텍터가 의도적으로 그 구간만 비워둔 것이다.

## 흔한 실수
- Scylla가 자동으로 계산해준 값을 무조건 신뢰하고, 결과 파일이 깨져도 원인을 다른 곳(IAT 문제 등)에서만 찾는 것.
- 덤프 실패를 IAT 문제로 오해하고 REV-0945/REV-0946의 IAT 복구만 반복 시도하는 것 — 애초에 덤프된 코드/데이터 자체가 불완전하면 IAT를 아무리 잘 복구해도 실행이 안 된다.
- 한 번 덤프가 실패했다고 완전히 포기하는 것 — 같은 OEP 근처의 조금 다른 시점에서 재시도하면 성공하는 경우가 흔하다.
- 안티 덤프와 안티 디버깅을 같은 것으로 혼동해서 잘못된 우회 기법을 적용하려는 것.

## 막혔을 때 다음 체크
- IAT 자체 복구가 문제라면 → REV-0945/REV-0946
- 덤프 시도 자체가 프로세스 종료를 유발한다면 → REV-0239 예외 기반 Anti-Debug, REV-0240 디버거 갑작스런 종료 체크리스트
- 함수 단위 재암호화 타이밍이 문제라면 → REV-0949 함수 단위 암호화 개념
- 이 정도 방어가 결합된 수준이면 상용 프로텍터일 가능성이 높다 → REV-0942 상용 프로텍터를 만났을 때 현실적인 대응

## 미니 예제
```text
정상 섹션 헤더(PE-bear로 확인해야 할 값):
  .text   VirtualSize=0x00012000  SizeOfRawData=0x00012000

위조된 섹션 헤더(프로텍터가 메모리 상에서 바꿔놓은 값):
  .text   VirtualSize=0x00001000  SizeOfRawData=0x00001000  <- 실제보다 훨씬 작게 위조

Memory Map에서 직접 확인한 실제 커밋 크기: 0x00012000
```
Scylla 자동 계산은 위조된 `VirtualSize`(0x1000)만 믿고 그만큼만 떠내려 하지만, Memory Map에서 확인한 실제 크기(0x12000)로 수동 지정하면 나머지 코드까지 온전히 덤프할 수 있다.

## 관련 글
- REV-0944 — 패킹된 바이너리에서 OEP를 수동으로 추적하는 절차 심화
- REV-0945 — 언패킹 후 IAT를 복구하는 개념(Import Reconstruction)
- REV-0949 — 함수 단위 암호화(Function Encryption) 개념 소개
- REV-0942 — 상용 프로텍터(VMProtect/Themida)를 만났을 때 현실적인 대응
- REV-0240 — 디버거에서 갑자기 종료될 때 체크리스트

## 출처/검증
- PE 헤더 값 위조를 통한 안티 덤프 기법(SizeOfImage, VirtualSize 조작)은 다수의 공개 언패킹 튜토리얼 및 malware 분석 자료에서 공통적으로 설명하는 방식을 기준으로 정리했다.
- Scylla의 자동 이미지 크기 계산 및 수동 크기 지정 옵션은 Scylla 공식 저장소(github.com/NtQuery/Scylla) 문서를 기준으로 확인했다(2026-09-09 검증).
