## 한 줄 요약
"OEP를 찾은 것 같다"고 판단하고 그 지점에서 실행/덤프를 진행했는데 프로그램이 이상하게 동작한다면, 그 지점이 진짜 OEP가 아니라 **패커가 일부러 만들어 둔 가짜 OEP(false OEP, 함정)이거나, 아직 압축 해제가 완전히 끝나기 전 단계**였을 가능성이 높다.

## 언제 검색해야 하나
- `jmp OEP`처럼 보이는 명령을 따라갔는데, 도착한 지점의 코드가 여전히 짧고 반복적이거나 다시 스텁 비슷한 코드로 이어질 때
- OEP라고 판단한 지점에서 실행을 계속했더니 프로그램이 원래 예상한 동작(입력 대기, 메시지 출력 등)을 하지 않고 곧바로 종료되거나 무한 루프에 빠질 때
- 하나의 바이너리에서 `jmp` 명령이 여러 번 나오는데, 어느 것이 진짜 OEP로 가는 점프인지 헷갈릴 때
- ESP 트릭이나 메모리 쓰기 브레이크포인트로 멈춘 지점이 매번 다르게 나와서 확신이 안 설 때

## 핵심 개념

### 가짜 OEP(false OEP)란
일부 패커, 특히 안티리버싱 기능이 강화된 패커는 진짜 OEP로 점프하기 전에 **의도적으로 비슷하게 생긴 가짜 점프 지점을 하나 이상 심어 둔다.** 리버서가 ESP 트릭이나 메모리 쓰기 브레이크포인트로 "그럴듯한" 지점에서 멈추면, 실제로는 아직 스텁 코드의 일부(예: 두 번째 언패킹 레이어, 안티디버깅 체크 루틴)일 뿐인데 그것을 OEP로 착각하게 만드는 것이다. 이 함정 지점에서 덤프를 뜨면 겉보기엔 그럴듯한 코드가 나오지만, 실제로 실행해보면 원본 프로그램과 다르게 동작하거나 아예 크래시가 난다.

### 압축 해제가 여러 단계로 나뉘는 경우
UPX처럼 단일 스텁-단일 점프 구조가 아니라, 상용 패커나 커스텀 패커는 **압축 해제를 여러 단계로 나눠서 수행**하는 경우가 흔하다. 1단계 스텁이 2단계 스텁을 풀어놓고 거기로 점프하고, 2단계 스텁이 다시 원본 코드를 풀어놓고 그제서야 진짜 OEP로 점프하는 식이다. 이 경우 첫 번째 `jmp`만 보고 "찾았다"고 판단하면, 아직 완전히 풀리지 않은 중간 단계에 도착하게 된다.

### 판단 기준: "진짜 OEP처럼 보이는" 코드의 특징
진짜 OEP는 컴파일러가 생성한 정상적인 프로그램 시작 코드이므로 다음과 같은 특징을 보인다.
- 함수 프롤로그가 명확하다(`push ebp; mov ebp, esp` 또는 x64의 스택 정렬용 `sub rsp, ...`).
- CRT 초기화 패턴(`__scrt_common_main`, `GetModuleHandleA`, `GetCommandLineA` 등 잘 알려진 API 호출)이 바로 이어진다.
- 코드가 반복적이지 않고, 여러 함수로 자연스럽게 갈라지는 정상적인 흐름을 보인다.
- 원본 프로그램이 실제로 사용할 법한 문자열(예: "Enter password", 원본 UI 텍스트)에 대한 참조가 근처에서 보이기 시작한다.

반대로 가짜 OEP/중간 단계 코드는 여전히 루프가 많고, 이름 없는 API 호출(`LoadLibraryA`, `GetProcAddress`)이 반복되며, 프로그램 고유의 문자열이 보이지 않는다.

## 화면/코드에서 보이는 징후
- OEP라고 생각한 지점에서 `F8`(Step Over)로 몇 번 진행했을 때, 다시 처음 봤던 스텁과 비슷한 압축 해제 루프 패턴이 나타난다.
- 그 지점에서 Strings 참조를 봤을 때 원본 프로그램의 UI 문자열이 전혀 안 보이고, 여전히 DLL 이름/API 이름 문자열만 보인다.
- 덤프해서 IDA로 열었더니 함수가 여전히 몇 개(1~5개) 뿐이다.
- 실행을 계속했을 때 원래 프로그램이 하지 않을 행동(예상보다 이른 종료, 이상한 메시지 박스)이 나타난다.

## 가장 먼저 할 것
지금 멈춘 지점이 진짜 OEP인지 판단하기 전에, 먼저 그 지점에서 `F8`(Step Over)로 10~20개 명령 정도만 더 진행해 본다. 여전히 반복적인 압축 해제 패턴이거나 API 이름 resolve 코드가 계속된다면 아직 OEP가 아니다.

## 단계별 절차
1. 현재 멈춘 지점의 코드를 x64dbg의 디스어셈블리 창에서 위아래로 살펴보고, 함수 프롤로그와 CRT 초기화 패턴이 있는지 확인한다.
2. 확신이 안 서면 그 지점에서 몇 개 명령을 더 실행(`F8`)해보고, 다시 반복 루프나 `LoadLibraryA`/`GetProcAddress` 호출 패턴이 나오는지 관찰한다. 나온다면 아직 다음 단계 스텁이 남아있는 것이다.
3. Strings 창(x64dbg의 `Memory Map` → 문자열 검색, 또는 덤프 후 IDA `Shift+F12`)에서 원본 프로그램이 실제로 쓸 법한 문자열이 보이는지 확인한다. API 이름/DLL 이름 문자열만 보인다면 아직 이르다.
4. 다단계 패커가 의심되면, 방금 도달한 지점을 "1차 OEP 후보"로 기록해두고, 거기서부터 다시 ESP 트릭이나 메모리 쓰기 브레이크포인트를 새로 걸어 "2차 점프"를 찾는다.
5. 여러 번 반복해서 더 이상 새로운 점프/압축 해제 루프가 안 나오고, 함수 프롤로그와 원본 문자열 참조가 자연스럽게 보이는 지점에 도달하면 그곳을 최종 OEP로 확정한다.
6. 확정 후 덤프를 뜨고(REV-0227), IAT 복구 후 실행해서 원본과 동일하게 동작하는지 반드시 검증한다.

## 명령어/단축키
- x64dbg: `F8`(Step Over, 함수 내부로 들어가지 않고 다음 줄로), `F7`(Step Into), `Ctrl+F9`(Execute till return, 현재 함수 리턴까지 실행)
- x64dbg 문자열 검색: 우클릭 → `Search for` → `String references`(현재 모듈 내 문자열 참조 스캔)
- 메모리 쓰기 브레이크포인트: 메모리 맵에서 섹션 우클릭 → `Set Memory Breakpoint on Write`(다음 단계 스텁이 어디를 다시 쓰는지 잡을 때)

## 출력 해석
- Step Over를 반복했을 때 명령 주소가 계속 낮은 범위 안에서 왔다 갔다 하면(루프) 아직 압축 해제 중이다.
- String references 결과가 `kernel32.dll`, `GetProcAddress` 같은 이름 위주라면 아직 이르다. `Enter the password`, `Correct!` 같은 프로그램 고유 문자열이 보이면 원본 코드 근처에 온 것이다.
- Step Over 중 갑자기 주소 범위가 완전히 새로운 섹션(원본 `.text`에 해당하는 위치)으로 넘어가고, 그 뒤로 다시 이전 스텁 주소로 돌아오지 않으면 최종 단계에 도달한 것으로 볼 수 있다.

## 흔한 실수
- 첫 번째로 만난 그럴듯한 `jmp`를 곧바로 OEP로 확정하고 덤프부터 떠서, 나중에 실행이 이상한 이유를 엉뚱한 곳(IAT, 안티디버깅)에서만 찾는 것.
- 다단계 패커의 존재를 모른 채 "OEP를 한 번 찾으면 끝"이라고 가정하는 것 — 상용 패커일수록 단계가 여러 겹인 경우가 흔하다.
- 함수 프롤로그 패턴만 보고 판단하고 Strings 확인을 생략하는 것 — 일부 가짜 OEP는 프롤로그처럼 보이는 코드를 일부러 흉내 내기도 한다.
- 매번 처음부터 다시 실행하지 않고, 이전 시도에서 걸어둔 브레이크포인트가 남아있는 상태로 계속 진행해서 어느 시점 관찰인지 헷갈리는 것.

## 막혔을 때 다음 체크
- 진짜 OEP를 확정했는데도 덤프가 여전히 이상하다면 → REV-0955(언패킹한 덤프가 크래시가 날 때)를 참고한다.
- 여러 겹 패킹이 확실하다면 → REV-0960(여러 겹으로 패킹된 바이너리를 만났을 때)을 참고한다.
- 애초에 자동 언패킹 도구가 실패해서 수동으로 여기까지 왔다면 → REV-0961(패커 시그니처는 잡히는데 도구가 자동 언패킹을 실패할 때)을 참고한다.
- OEP 탐색 자체의 개념이 헷갈린다면 → REV-0227(수동 언패킹 개념 OEP와 Dump)로 돌아가 기초를 다시 확인한다.

## 미니 예제
```text
1) ESP 트릭으로 0x00405A10에서 멈춤 -> jmp 0x00401000 발견
2) 0x00401000으로 이동, F8로 10줄 진행 -> 다시 LoadLibraryA/GetProcAddress 반복 호출 관찰
   => 아직 OEP 아님, 2단계 스텁으로 판단
3) 이 지점에서 새로 메모리 쓰기 브레이크포인트 설정 후 계속 진행
4) 0x00401A40에서 다시 멈춤 -> jmp 0x004012C0 발견
5) 0x004012C0 이동, String references 확인
   -> "Enter password: ", "Correct!" 등 원본 문자열 참조 다수 발견
   => 이 지점을 최종 OEP로 확정
```

## 관련 글
- REV-0227 — 수동 언패킹 개념 OEP와 Dump
- REV-0955 — 언패킹한 덤프가 크래시가 날 때
- REV-0960 — 여러 겹으로 패킹된(Multi-layer) 바이너리를 만났을 때
- REV-0965 — 언패킹 후 원래 Entry Point로 못 돌아갈 때

## 출처/검증
- 가짜 OEP(false OEP)와 다단계 언패킹 스텁 구조는 다수의 공개 리버싱 교육 자료 및 상용 패커(Themida, VMProtect 등) 분석 사례에서 공통적으로 다루는 안티리버싱 기법을 일반화한 것이다(2026-09-09 검증).
- ESP 트릭, String references 기반 OEP 판별 방식: x64dbg 공식 문서(help.x64dbg.com) 및 일반적인 수동 언패킹 튜토리얼 기준.
