## 한 줄 요약
값이 "갑자기" 음수로 보이는 현상은 십중팔구 값 자체가 바뀐 게 아니라, 그 값을 **어디선가 signed 타입으로 재해석**하기 시작했기 때문이므로, 문제가 생긴 그 지점에서 "이 값의 실제 타입이 int인가 unsigned int인가"부터 되짚어야 한다.

## 언제 검색해야 하나
- 반복문 안에서 카운터나 크기 값을 잘 쓰고 있었는데 특정 시점부터 디컴파일러가 그 값을 음수로 표시하기 시작할 때
- 함수 리턴값이 `-1`, `-13` 같은 음수인데 이게 "에러 코드"인지 "진짜 계산된 음수"인지 구분이 안 될 때
- 어떤 변수는 코드 앞부분에서 `unsigned int`로 보이다가 뒷부분에서 `int`로 바뀌어 보여서 값 해석이 헷갈릴 때
- 파일 크기나 오프셋처럼 논리적으로 절대 음수가 될 수 없는 값이 화면에는 음수로 찍혀 있을 때

## 핵심 개념
CPU 레지스터나 메모리에는 "이 값은 양수다/음수다"라는 표식이 붙어 있지 않다. 값이 음수로 "보이는" 건 순전히 **그 값을 signed로 해석하는 코드(비교, 출력, 디컴파일러의 타입 추론)를 통과했기 때문**이다. 그래서 "값이 갑자기 음수가 됐다"는 현상을 만나면 먼저 확인할 것은 값 자체의 변화가 아니라 **"어느 지점부터 signed 해석이 끼어들었는가"**다.

**흔한 세 가지 원인**:
1. **디컴파일러의 타입 추론 실수**: IDA/Ghidra는 변수의 실제 C 타입을 항상 정확히 추론하지 못한다. 원래 `unsigned int`인데 `int`로 잘못 추론하면, `0xFFFFFFF0`처럼 큰 값이 `-16`으로 표시된다. 이건 값이 바뀐 게 아니라 **표시 방식만 잘못된 것**이다.
2. **함수 리턴값의 signed 캐스팅**: `read()`, `recv()` 같은 함수는 실패 시 `-1`을 반환하는데, 리턴 타입이 `size_t`(unsigned)를 쓰는 API와 섞여 있으면 "리턴값이 아주 큰 unsigned 값으로 보였다가 갑자기 `-1`(즉 `0xFFFFFFFF`)로 보이는" 것처럼 헷갈릴 수 있다.
3. **실제로 값이 오버플로/언더플로된 경우**: 이건 표시 문제가 아니라 진짜 계산 결과가 바뀐 것이며, REV-0376에서 다루는 오버플로 문제로 이어진다.

**구체적 숫자로 구분해보기**: 어떤 변수가 `0xFFFFFFF3`이라는 비트 패턴을 갖고 있다고 하자.
- signed 32비트로 해석: `-13`
- unsigned 32비트로 해석: `4294967283`

이 값 자체는 프로그램 실행 중 단 한 번도 바뀌지 않았을 수 있다. 그런데 어떤 코드 경로(또는 디컴파일러의 어떤 뷰)는 이걸 `int`로, 다른 경로는 `unsigned int`로 취급해서 보여주는 바람에 "갑자기 음수가 됐다"는 착시가 생긴다. 진짜 조사해야 할 것은 "이 변수가 소스 코드에서 원래 어떤 타입으로 선언됐는가"다.

## 화면/코드에서 보이는 징후
- 같은 레지스터(예: `eax`)를 GDB에서 `p $eax`로 보면 큰 양수인데, 프로그램이 출력한 값은 음수 — 이건 프로그램 내부의 `printf("%d", ...)`처럼 signed 포맷 지정자를 썼기 때문일 수 있다
- IDA 디컴파일에서 어떤 줄은 `v4`를 `int`로, 몇 줄 아래에서는 같은 변수를 캐스팅해서 `(unsigned int)v4`로 쓰는 경우
- 조건문 `if (result < 0)`이 있는데 `result`가 실제로는 파일 크기나 배열 길이처럼 절대 음수일 수 없는 값

## 가장 먼저 할 것
문제의 값을 **헥스(비트 패턴) 그대로** 확인한다. GDB라면 `p/x`, IDA라면 숫자 위에서 `H`. 헥스값의 최상위 비트가 1인지부터 본다(32비트라면 `0x80000000` 이상인지). 그다음 그 변수가 소스/디컴파일에서 어떤 C 타입으로 선언됐는지 찾는다.

## 단계별 절차

**1) 값의 헥스 표현부터 고정**
음수로 보이는 표시(`-13` 등)를 먼저 헥스로 바꿔 실제 비트 패턴을 확정한다.
```python
>>> hex(-13 & 0xFFFFFFFF)
'0xfffffff3'
```

**2) 그 값이 만들어진 지점(정의)까지 역추적**
IDA에서 변수 위에 커서를 놓고 `Ctrl+X`(cross-reference, 어디서 쓰였는지) 또는 그 변수가 대입되는 지점을 찾아 올라간다. 값이 어디서 마지막으로 대입됐는지 찾으면, 그 대입 소스(함수 리턴값, 산술 연산 결과, 메모리에서 읽은 값)가 무엇인지 알 수 있다.

**3) 그 지점의 원래 타입 확인**
함수 리턴값이라면 그 함수의 시그니처(원형)를 확인한다. `int read(...)`처럼 signed 리턴이면 `-1`이 진짜 실패 코드일 수 있고, `size_t`(unsigned) 리턴인데 `int`로 잘못 대입받았다면 그건 디컴파일러/코드의 타입 불일치다.

**4) IDA/Ghidra에서 타입을 강제로 바꿔 비교**
IDA에서 변수 선택 후 `Y`(Set type)로 `int` ↔ `unsigned int`를 바꿔보고, 어느 쪽이 코드 흐름과 논리적으로 더 말이 되는지 비교한다. "이 값이 파일 크기다" 같은 문맥이 있다면 unsigned 해석이 맞을 가능성이 높다.

**5) 어셈블리 레벨에서 실제 비교 명령어 확인**
그 값을 비교하는 조건 점프가 `jl`/`jg`(signed)인지 `jb`/`ja`(unsigned)인지 확인한다. 이건 디컴파일러의 추측이 아니라 컴파일러가 실제로 생성한 명령어이므로 가장 신뢰할 수 있는 증거다.

## 명령어/단축키
```text
GDB:    p/x $eax        # 헥스(비트 패턴) 그대로 보기
GDB:    p/d $eax        # signed 10진수로 보기
GDB:    p/u $eax        # unsigned 10진수로 보기
IDA:    숫자 위 H         # 10진/16진 전환
IDA:    변수 선택 후 Y     # 타입 변경(int ↔ unsigned int)
IDA:    변수 위 Ctrl+X    # 이 값이 쓰인/대입된 위치 목록
x64dbg: 레지스터 우클릭 → "부호 있는 10진수로 표시" 토글
```

## 출력 해석
- `p/x`와 `p/d`를 같은 레지스터에 실행해서 값이 다르게 나온다면 정상이다 — 비트 패턴은 하나인데 해석만 다른 것이다.
- 디컴파일러가 보여주는 `int`/`unsigned int` 타입은 어디까지나 추론이므로, 실제 조건 점프 명령어(`jl` vs `jb`)와 다르면 어셈블리 쪽을 더 신뢰한다.

## 흔한 실수
- 화면에 보이는 음수 숫자를 그대로 "버그"나 "이상 동작"으로 단정하고 넘어가는 것 — 실제로는 타입 재해석 문제일 뿐 값 자체는 정상일 수 있다.
- 함수 리턴값의 관례적 실패 코드(`-1`)와 실제 산술적으로 계산된 음수를 구분하지 않는 것.
- 디컴파일러가 보여주는 타입을 검증 없이 신뢰하고 그 위에서만 추론을 계속 쌓아가는 것.
- 값이 바뀐 시점을 찾지 않고 "왜 음수인지" 화면만 계속 바라보는 것 — 항상 그 값이 마지막으로 대입된 지점까지 거슬러 올라가야 한다.

## 막혔을 때 다음 체크
- 2의 보수 표현 자체가 헷갈리면 REV-0024 문서로 이동.
- signed/unsigned 비교와 조건 점프(`jl` vs `jb`) 구분법이 필요하면 REV-0025 문서로 이동.
- 값이 표시 문제가 아니라 실제로 계산이 잘못돼서 튄 것 같으면 REV-0376 문서(오버플로 의심)로 이동.

## 미니 예제
IDA 디컴파일에서 다음 코드를 봤다고 하자.
```c
int len = get_remaining_size();
if ( len < 0 )
    printf("error: negative length %d\n", len);
```
그런데 `get_remaining_size()`의 실제 원형을 찾아보니 `unsigned int get_remaining_size(void)`였다. 즉 이 함수는 절대 음수를 반환할 수 없는데, 디컴파일러가 리턴값을 받는 지역변수 `len`을 `int`로 잘못 추론해서 큰 unsigned 값(예: `0xFFFFFFF0` = 4294967280)을 `-16`으로 표시한 것이다. `len`의 타입을 `unsigned int`로 바꿔서 다시 보면 `if (len < 0)`은 항상 거짓인 죽은 코드였음이 드러나고, 실제로 신경 써야 할 조건은 `len`이 특정 큰 값을 넘는지 여부였다는 게 명확해진다.
