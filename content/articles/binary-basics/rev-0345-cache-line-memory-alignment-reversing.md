## 한 줄 요약
현대 x86/x64 CPU는 메모리를 보통 64바이트 단위(캐시 라인)로 캐시에 올리고, 일부 SIMD 명령어(`MOVAPS`, `MOVDQA` 등)는 16바이트 정렬을 하드웨어 레벨에서 강제하기 때문에, 디스어셈블리에 나타나는 정렬 관련 코드(NOP 패딩, `align 16` 표시, 구조체 안의 이상한 `pad` 필드, false sharing 방지 코드)는 대부분 버그가 아니라 "성능을 위해 의도적으로 넣은 코드"이며, 이걸 알아두면 코드를 읽다가 헷갈리지 않고 곧바로 다음 실제 로직으로 넘어갈 수 있다.

## 언제 검색해야 하나
- `movaps`/`movdqa` 명령어에서 크래시(`#GP`, General Protection Fault)가 발생한 이유가 정렬 문제일 수 있다는 말을 들었을 때
- 함수의 시작 주소가 항상 16(`0x10`)의 배수로 정렬되어 있는 걸 발견하고 이유가 궁금할 때
- 구조체 정의에 이름 없는 `pad[N]`, `reserved[N]` 같은 필드가 있어서 왜 있는지 모를 때
- 멀티스레드/성능 최적화 코드에서 변수 하나 크기에 비해 과도하게 큰 정렬 지시어(`alignas(64)` 등)가 붙어있는 걸 봤을 때
- AES 등 암호화 구현을 리버싱하는데 캐시 타이밍 공격이라는 용어가 왜 나오는지 궁금할 때

## 핵심 개념

### 캐시 라인이란
CPU는 메모리에서 데이터를 가져올 때 한 바이트씩이 아니라 **캐시 라인(cache line)** 이라는 고정 크기 블록 단위로 가져온다. 대부분의 현대 x86/x64 CPU는 캐시 라인 크기가 **64바이트**다. 즉 주소 0x1000의 1바이트만 읽어도, CPU는 실제로는 0x1000~0x103F(64바이트) 전체를 L1 캐시에 올린다. 이 개념은 REV-0030(메모리 레이아웃 기초)에서 다룬 "메모리 영역"과는 다른 축의 이야기로, "메모리 안의 데이터가 어떻게 CPU 캐시로 오가는가"에 대한 것이다.

### 정렬(alignment)이 필요한 이유 — 하드웨어가 강제하는 경우
대부분의 x86/x64 정수 연산 명령어는 정렬되지 않은 주소를 접근해도 문제없이 동작한다(속도만 약간 느려질 수 있음). 하지만 일부 SIMD(벡터) 명령어는 **정렬이 하드웨어 레벨에서 강제**된다.

```asm
movaps  xmm0, [rax]      ; rax가 16의 배수가 아니면 #GP(General Protection Fault) 발생!
movups  xmm0, [rax]      ; 정렬 안 돼도 항상 동작 (Unaligned, 다만 약간 더 느릴 수 있음)
```
`MOVAPS`(Aligned), `MOVAPD`, `MOVDQA`(Aligned) 계열은 **A**(Aligned)가 이름에 들어간 대로 16바이트 정렬을 요구하고, 정렬이 안 된 주소로 호출하면 예외가 발생한다. 반면 `MOVUPS`, `MOVDQU`(**U**nAligned) 계열은 정렬 여부와 무관하게 항상 동작한다. 디스어셈블리에서 `movaps`가 보인다면, 컴파일러가 "이 메모리 주소는 반드시 16바이트 정렬되어 있다"고 확신하고 생성한 코드라는 뜻이다 — 보통 스택 정렬 규약(x64 호출 규약은 `call` 시점에 RSP가 16바이트 정렬되어 있어야 함)이나 `_aligned_malloc`/`posix_memalign`처럼 정렬을 보장하는 할당 함수를 쓴 결과다.

### 함수/루프의 시작 주소가 정렬되는 이유
컴파일러는 함수의 시작 주소나 자주 반복되는 루프의 시작 주소를 종종 16바이트(또는 32바이트) 경계에 맞춰 배치한다. 이는 명령어 페치(instruction fetch) 및 명령어 캐시(I-cache) 효율을 높이기 위한 성능 최적화다. 이 정렬을 맞추기 위해 실제 코드가 없는 빈 공간에 `NOP`(아무 동작도 안 하는 명령어)를 채워 넣는데, 이를 정렬용 NOP 패딩이라 부른다(자세한 내용은 REV-0473 참고). 디스어셈블리에서 함수와 함수 사이에 의미 없어 보이는 `nop` 여러 개가 이어진다면, 이는 실제 로직이 아니라 다음 함수를 정렬 경계에 놓기 위한 채움재이므로 분석 대상에서 제외하면 된다.

### 구조체에 등장하는 정체불명의 pad 필드
REV-0344(정렬과 패딩이 구조체에 미치는 영향)에서 다룬 **자연 정렬 패딩**은 컴파일러가 자동으로 삽입하는 "보이지 않는" 빈 공간이었다. 반면 성능에 민감한 코드(멀티스레드, 게임 엔진, 커널 등)에서는 프로그래머가 **직접 명시적으로** `char pad[40];`처럼 이름 있는 패딩 필드를 구조체에 선언해 넣는 경우가 있다. 이건 실수가 아니라 다음 절에서 설명할 false sharing을 막기 위한 의도적 설계다.

### False sharing — 캐시 라인이 성능에 영향을 주는 대표 사례
여러 스레드가 각각 다른 변수를 다루더라도, 그 변수들이 **같은 캐시 라인(64바이트) 안에 물리적으로 붙어있다면**, 한 스레드가 자기 변수를 수정할 때마다 그 캐시 라인 전체가 다른 CPU 코어의 캐시에서 무효화(invalidate)된다. 논리적으로는 서로 다른 데이터를 다루는데도 캐시 라인을 "공유"하는 것처럼 성능이 떨어지는 현상이라 **false sharing**(거짓 공유)이라 부른다.

```c
struct Counters {
    long counter_a;   // 스레드 A가 계속 갱신
    long counter_b;   // 스레드 B가 계속 갱신 — counter_a와 같은 캐시 라인(64바이트)에 들어감!
};

// false sharing을 피하기 위한 패딩 처리
struct CountersPadded {
    long counter_a;
    char pad[56];       // 64바이트 캐시 라인을 채워서 counter_b를 다음 라인으로 밀어냄
    long counter_b;
};
```
리버싱 중 이런 `pad[56]`, `_reserved[N]`처럼 크기가 애매하게 큰 필드를 만난다면, 자연 정렬 패딩(REV-0344, 보통 몇 바이트 이내)과 구분해서 "멀티스레드 성능 최적화를 위한 의도적 캐시 라인 분리"일 가능성을 의심해볼 수 있다. C++11 이상에서는 `alignas(64)`처럼 정렬 지시어를 직접 써서 같은 효과를 내기도 한다.

### 캐시 타이밍과 리버싱/보안의 접점
캐시가 데이터를 얼마나 빨리 돌려주는지(캐시 히트 vs 캐시 미스)는 **관찰 가능한 시간 차이**를 만들어낸다. 이 특성은 두 가지 방향으로 리버싱과 연결된다.

1. **안티 디버깅/시간 기반 탐지**: `RDTSC` 명령어로 실행 시간을 측정해서 디버거가 붙어있는지 탐지하는 기법(REV-0237)이 캐시/파이프라인 타이밍 차이를 이용하는 대표 사례다.
2. **암호 알고리즘의 캐시 타이밍 사이드채널**: 초창기 AES 소프트웨어 구현 중 일부는 룩업 테이블(T-table)을 참조하는 방식으로 동작했는데, 이 테이블 접근 패턴이 입력 키에 따라 서로 다른 캐시 라인을 건드리면서 **접근 시간 차이가 키 정보를 유출**하는 사이드채널 공격(cache-timing attack)의 대상이 된 적이 있다. 이런 배경 때문에 최신 CPU는 AES 전용 하드웨어 명령어(`AESENC` 등)를 제공해서 테이블 조회 자체를 없애 이 문제를 회피한다. CTF 리버싱에서 "왜 이 구현은 상수 시간(constant-time) 비교를 쓰는가" 같은 질문이 나온다면 이 캐시 타이밍 배경을 알아두면 이해가 빠르다.

### LOCK 프리픽스와 캐시 라인
멀티코어 환경에서 원자적(atomic) 연산을 보장하는 `LOCK` 프리픽스(REV-0432 참고)는 내부적으로 해당 메모리 주소가 속한 캐시 라인을 다른 코어가 손대지 못하게 잠그는 방식으로 동작한다(최신 CPU에서는 버스 전체가 아니라 캐시 라인 단위로 잠금). 그래서 `lock` 접두사가 붙은 명령어가 자주 반복되는 코드는, 여러 코어가 같은 캐시 라인을 두고 경쟁하면서 성능이 떨어질 수 있고, 이 역시 false sharing과 근본적으로 같은 하드웨어 메커니즘(캐시 라인 단위 처리)에서 비롯된다.

## 화면/코드에서 보이는 징후
- `movaps`/`movdqa` 명령어 실행 시점 근처에서 크래시가 나는데, 그 직전에 스택 포인터나 힙 포인터를 조정하는 코드가 있다면 정렬이 깨졌을 가능성을 의심(예: 스택을 16바이트 정렬 없이 임의로 조정한 셸코드나 수제 어셈블리).
- 함수와 함수 사이에 `nop` 여러 개가 연달아 있고, 그 다음 함수 시작 주소가 항상 `0x10`(16)이나 `0x20`(32)의 배수 — 정렬용 패딩(REV-0473).
- 구조체 안에 이름이 `pad`, `reserved`, `_unused` 등이고 크기가 애매하게 큰(예: 56, 40, 60바이트) 필드 — false sharing 방지용일 가능성.
- 소스에 `alignas(64)`나 `__attribute__((aligned(64)))`가 붙어있는 변수/구조체 선언(디컴파일러가 인식하면 주석/속성으로 표시되기도 함).
- 암호화 관련 코드에서 룩업 테이블 접근 패턴이 입력값에 따라 달라지는 것이 아니라, 모든 가능한 값에 대해 항상 같은 패턴으로 메모리를 훑는(constant-time) 코드가 보임.

## 가장 먼저 할 것
정렬 관련 코드를 만났을 때 가장 먼저 할 일은 "이게 로직의 일부인지, 아니면 성능/안전을 위한 부수적 장치인지" 구분하는 것이다. `nop` 패딩과 `pad` 필드는 대개 실제 로직과 무관하므로, 이를 로직으로 착각해서 분석 시간을 낭비하지 않도록 먼저 걸러내고 넘어간다.

## 단계별 절차

**1) 정렬용 NOP과 실제 코드 구분**
```asm
    ret
    nop
    nop
    nop                      ; 여기까지는 이전 함수의 여백(정렬용)
next_func:                   ; 0x10의 배수 주소에서 시작
    endbr64
    push    rbp
    ...
```
`ret` 직후 여러 개의 `nop`이 이어지다가 정렬된 주소에서 새 함수가 시작된다면 그 `nop`들은 무시하고 넘어간다.

**2) movaps 크래시 시 정렬 확인**
```
(gdb) x/i $rip              # 크래시 난 명령어 확인 (movaps 등)
(gdb) p $rax                # 피연산자 레지스터 값 확인
(gdb) p $rax & 0xf           # 0이 아니면 16바이트 정렬이 깨진 것 -> #GP 원인 확정
```

**3) 구조체의 pad 필드가 false sharing 방지용인지 판단**
```c
struct Counters {
    long counter_a;
    char pad[56];     // 8(counter_a) + 56 = 64 -> 정확히 캐시 라인 크기와 일치!
    long counter_b;
};
```
패딩 크기를 더했을 때 정확히 64(또는 32, 128 등 흔한 캐시 라인 배수)가 되는지 계산해보면 의도를 확인할 수 있다.

**4) 캐시 타이밍에 민감한 암호 코드인지 확인**
비교/조회 연산이 입력값과 무관하게 항상 같은 횟수·같은 패턴으로 메모리에 접근하는지(constant-time), 아니면 입력값에 따라 조회 위치나 조기 종료 시점이 달라지는지(non-constant-time) 비교해본다. 후자는 캐시/시간 사이드채널에 취약할 수 있는 구현이다.

## 명령어/단축키
```
(gdb) x/i $rip
(gdb) p $rax & 0xf         # 16바이트 정렬 여부 빠르게 확인
(gdb) p $rax & 0x3f        # 64바이트(캐시 라인) 정렬 여부 확인
```
```c
_Alignof(struct Counters)          // C11: 실제 정렬 요구값 확인
alignas(64) long counter;           // C11/C++11: 정렬 강제 지시어
```
IDA/Ghidra: 함수 리스트에서 함수 시작 주소를 몇 개 훑어 16의 배수인지 육안으로 확인하면 컴파일러의 정렬 정책을 짐작할 수 있다.

## 출력 해석
- `p $rax & 0xf`(마지막 4비트)가 0이면 16바이트 정렬 상태 — `movaps` 사용이 안전하다.
- `p $rax & 0x3f`(마지막 6비트)가 0이면 64바이트(캐시 라인) 정렬 상태 — 캐시 라인 관련 최적화 코드의 전제 조건을 만족한다.
- 구조체의 패딩 크기가 "캐시 라인 크기 - 앞선 필드 크기"와 정확히 일치한다면 그 구조체는 의도적으로 false sharing을 피하도록 설계된 것으로 해석해도 무방하다.

## 흔한 실수
- 함수 사이의 정렬용 `nop`들을 실제 실행되는 로직으로 착각해서 의미를 부여하려는 것.
- 구조체의 `pad`/`reserved` 필드를 단순 실수나 미사용 공간으로만 보고, false sharing 방지 같은 의도적 설계 가능성을 고려하지 않는 것.
- `movaps` 크래시를 만났을 때 "명령어 자체가 잘못됐다"고 판단하고, 정작 원인인 이전 단계의 스택/힙 정렬 붕괴를 못 찾는 것.
- REV-0344(구조체 자연 정렬 패딩, 보통 몇 바이트)와 이 문서의 false sharing 방지 패딩(보통 수십 바이트, 캐시 라인 크기 단위)을 같은 현상으로 혼동하는 것 — 전자는 컴파일러 자동 삽입, 후자는 프로그래머가 명시적으로 선언한다는 차이가 있다.
- 캐시 라인 크기가 모든 CPU에서 항상 64바이트라고 하드코딩해서 가정하는 것 — 대부분의 x86/x64는 64바이트가 맞지만, 정확한 값은 `CPUID` 명령어로 조회하는 것이 원칙적으로 정확하다.

## 막혔을 때 다음 체크
- 정렬용 NOP 패딩과 실제 코드를 구분하는 구체적 방법이 더 궁금하면 → REV-0473(정렬용 NOP 패딩과 실제 코드 구분하는 법)으로 이동.
- 구조체 자연 정렬/패딩의 기본 규칙이 궁금하면 → REV-0344(정렬과 패딩이 구조체에 미치는 영향)로 이동.
- `LOCK` 프리픽스와 원자적 연산의 기본 개념이 궁금하면 → REV-0432(LOCK 프리픽스와 원자적 연산 개념)로 이동.
- `MOVAPS`/`MOVDQA` 명령어 자체의 세부 동작이 궁금하면 → REV-0386(MOVAPS), REV-0389(MOVDQA와 MOVDQU)로 이동.
- 시간 측정 기반 안티디버깅 기법이 궁금하면 → REV-0237(RDTSC Time Check 안티디버깅)으로 이동.

## 미니 예제
정렬이 깨진 상태에서 `movaps`를 호출했을 때의 크래시를 GDB로 재현/진단하는 흐름을 보자.

```c
#include <emmintrin.h>
#include <stdio.h>

int main(void) {
    char buf[32];
    float *p = (float *)(buf + 1);   // 일부러 1바이트 어긋나게 정렬
    __m128 v = _mm_load_ps(p);        // 내부적으로 movaps 사용 -> 정렬 깨짐
    printf("%f\n", ((float *)&v)[0]);
    return 0;
}
```
```
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x0000000000401156 in main ()
(gdb) x/i $rip
=> 0x401156 <main+34>: movaps xmm0,XMMWORD PTR [rax]
(gdb) p $rax & 0xf
$1 = 1
```
`$rax & 0xf`가 0이 아닌 1로 나와서, `movaps`가 요구하는 16바이트 정렬이 깨져 있었다는 것이 바로 확인된다. 이 경우 `_mm_load_ps` 대신 정렬을 요구하지 않는 `_mm_loadu_ps`(내부적으로 `movups` 사용)를 썼다면 크래시 없이 정상 동작했을 것이다.

## 관련 글
- REV-0344 — 정렬(Alignment)과 패딩이 구조체에 미치는 영향
- REV-0473 — 정렬용 NOP 패딩과 실제 코드 구분하는 법
- REV-0432 — LOCK 프리픽스와 원자적 연산 개념
- REV-0386 — MOVAPS: 정렬된 XMM 레지스터 이동
- REV-0389 — MOVDQA와 MOVDQU: 정수 XMM 이동
- REV-0237 — RDTSC Time Check 안티디버깅

## 출처/검증
- 캐시 라인 크기(대부분의 x86/x64 CPU에서 64바이트)와 캐시 계층 구조: Intel 64 and IA-32 Architectures Optimization Reference Manual, "Cache and Memory Subsystem" 챕터 기준.
- `MOVAPS`/`MOVDQA`(정렬 요구, #GP 발생)와 `MOVUPS`/`MOVDQU`(비정렬 허용) 차이: Intel 64 and IA-32 Architectures Software Developer's Manual, Volume 2, 각 명령어 설명 섹션 기준.
- False sharing과 캐시 라인 정렬을 이용한 회피 기법(`alignas`, 패딩): C++ 표준(C++11 이상) `alignas` 명세 및 일반적인 멀티스레드 성능 최적화 문헌(Intel Optimization Reference Manual, "Avoiding False Sharing" 관련 설명) 기준.
- `LOCK` 프리픽스가 캐시 라인 단위로 메모리 잠금을 처리하는 방식(캐시 코히런시 프로토콜 기반): Intel SDM Volume 3, "Locked Atomic Operations" 섹션 기준.
- AES T-table 구현의 캐시 타이밍 사이드채널 취약점과 하드웨어 AES 명령어(AES-NI) 도입 배경: Intel의 AES-NI 백서(White Paper) 및 관련 암호학 사이드채널 연구 일반 설명 기준 (2026-09-09 확인).
