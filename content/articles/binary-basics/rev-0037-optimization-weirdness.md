## 한 줄 요약
컴파일러 최적화는 프로그램의 **최종 결과**는 그대로 유지하면서 실행 속도/크기를 위해 코드의 **구조**를 크게 바꿔버리기 때문에, 최적화된 바이너리의 디컴파일 결과는 원본 소스 코드와 함수 경계, 변수 개수, 실행 순서가 다르게 보일 수 있다 — 이것은 버그가 아니라 정상적인 동작이다.

## 언제 검색해야 하나
- 디스어셈블리에서 분명히 소스에 있었을 법한 함수 호출이 안 보이고 코드가 통째로 다른 함수 안에 섞여 있을 때(인라이닝)
- 반복문 하나가 어셈블리에서 똑같은 코드가 여러 번 반복돼서 나올 때(루프 언롤링)
- 지역 변수가 스택 어디에도 없고 계속 레지스터에만 머물러 있어서 `[rbp-N]` 패턴을 못 찾을 때
- `if`/`else`가 있어야 할 자리에 `cmovXX`나 `setXX` 명령어만 있고 분기(`jXX`)가 안 보일 때
- 함수 안에서 코드 순서가 원본 C 코드와 다르게 재배치된 것처럼 보일 때

## 핵심 개념
컴파일러는 사람이 짠 소스 코드를 "**입력과 출력이 같다면 내부 구현은 마음대로 바꿔도 된다**"는 원칙(as-if rule) 아래 최적화한다. `-O0`(최적화 없음)으로 컴파일하면 소스 코드 한 줄 한 줄이 거의 그대로 어셈블리 한 블록으로 대응되어 읽기 쉽지만, `-O2`, `-O3`, `/O2`(MSVC) 같은 최적화 옵션을 켜면 코드가 사람이 짠 순서·구조와 상당히 달라진다. 리버싱 대상(특히 상용 소프트웨어, CTF 배포 바이너리)은 대부분 최적화가 켜진 릴리즈 빌드이므로, 이 차이를 이해하는 것이 필수다. 자주 만나는 최적화 패턴은 다음과 같다.

**1) 인라이닝(Inlining)** — 작은 함수는 `call`로 호출하지 않고 그 함수의 코드를 호출 지점에 통째로 복사해 넣는다. 그래서 원본 소스에 있던 함수가 디스어셈블리에서 독립된 함수로 존재하지 않고, 다른 함수 안에 흡수되어 사라진 것처럼 보인다.
```c
static int square(int x) { return x * x; }
int compute(int a) { return square(a) + 1; }
```
```asm
; -O0: call square 가 실제로 존재
; -O2: square가 인라인되어 compute 안에 곱셈만 남음
compute:
    mov     eax, edi
    imul    eax, edi     ; square(a)가 그대로 imul 한 줄로 흡수됨
    add     eax, 1
    ret
```

**2) 레지스터 할당(Register allocation) — 스택을 거치지 않는 지역 변수** — 최적화 없는 빌드는 거의 모든 지역 변수를 매번 스택(`[rbp-N]`)에 저장했다가 다시 읽어오지만, 최적화된 빌드는 변수를 계속 레지스터에만 두고 스택에 아예 안 쓰기도 한다. REV-0031에서 다룬 "RBP 없는 함수"도 이 최적화의 한 형태다. 이런 코드는 지역 변수의 "위치"가 고정 주소가 아니라 특정 구간 동안의 레지스터이므로, 추적하려면 그 레지스터가 언제부터 언제까지 쓰이는지 범위를 봐야 한다.

**3) 루프 언롤링(Loop unrolling)** — 반복 횟수가 적거나 예측 가능한 루프는 조건 분기와 점프 오버헤드를 줄이기 위해 같은 코드를 여러 번 복사해서 펼쳐놓는다.
```c
for (int i = 0; i < 4; i++) arr[i] = 0;
```
```asm
; 최적화 시 (개념적으로)
mov     dword [rdi], 0
mov     dword [rdi+4], 0
mov     dword [rdi+8], 0
mov     dword [rdi+0xC], 0
; 실제 루프(cmp/jmp)가 아예 사라지고 대입 4개만 남음
```

**4) 분기 제거 — CMOVcc/SETcc로 대체** — 짧은 `if`/`else`는 분기 예측 실패 비용을 피하기 위해 조건부 이동 명령어(`CMOVcc`)나 조건부 설정 명령어(`SETcc`)로 바뀌어, 실제 점프(`je`, `jne` 등) 없이 값을 계산해버린다.
```c
int max(int a, int b) { return a > b ? a : b; }
```
```asm
; 최적화 시
cmp     edi, esi
mov     eax, edi
cmovle  eax, esi     ; a <= b 이면 eax = b, 아니면 eax = a (분기 없이 처리)
ret
```
이런 코드는 디스어셈블리만 봐서는 `if`가 있었는지조차 알아채기 어렵다.

**5) 명령어 재배치/스케줄링** — 결과에 영향이 없는 한, 컴파일러는 명령어 순서를 CPU 파이프라인에 유리하게 재배치한다. 그래서 원본 C 코드에서 A문장이 B문장보다 먼저 있었어도, 어셈블리에서는 B에 해당하는 코드가 먼저 나올 수 있다.

**6) 죽은 코드 제거(Dead code elimination) 및 상수 폴딩(Constant folding)** — 결과에 전혀 영향을 주지 않는 코드나, 컴파일 시점에 이미 값이 확정되는 계산은 통째로 사라지고 상수 하나로 대체된다.
```c
int f(void) { int x = 2 + 3; return x; }
```
```asm
; 최적화 시 덧셈 자체가 사라짐
mov     eax, 5
ret
```

이런 변형들 때문에 IDA/Ghidra의 디컴파일 결과도 원본 소스와 다르게 보일 수밖에 없다. 디컴파일러는 최적화된 어셈블리에서 원래 구조를 **추정**해서 재구성하는 것이지, 원본 소스를 그대로 복원하는 것이 아니다. 그래서 최적화 수준이 높을수록 디컴파일 결과의 변수 이름은 의미 없는 `a1`, `v3` 같은 형태로 나오고, 함수 경계도 흐릿해지며, 반복문이 이상하게 펼쳐진 형태로 남는다.

## 화면/코드에서 보이는 징후
- 소스에서 예상했던 함수 호출(`call`)이 없고, 그 함수의 로직이 호출자 함수 안에 그대로 펼쳐져 있다.
- 짧은 반복문이 여러 번 동일하거나 유사한 코드 블록으로 복제되어 나타난다.
- `[rbp-N]` 참조가 거의 없고, 함수 전체가 레지스터(`eax`, `ecx`, `edx` 등)만으로 계산을 끝낸다.
- `jXX`(조건 분기) 대신 `cmovXX`, `setXX` 명령어가 나온다.
- IDA 디컴파일 결과의 변수 이름이 `v3`, `a1`, `result` 등 자동 생성된 이름뿐이고, 원본 변수명과 매칭되는 게 거의 없다(디버그 심볼이 없는 릴리즈 빌드에서는 원래도 그렇지만, 최적화가 겹치면 더 심해진다).
- 동일한 소스 파일을 여러 최적화 옵션으로 컴파일해서 비교하면(가능한 경우) 구조가 크게 다르게 나온다.

## 가장 먼저 할 것
낯설게 보이는 최적화된 코드를 만나면, 개별 명령어를 하나하나 원본 소스 줄과 매칭하려 하지 말고 **"이 코드 블록이 전체적으로 무엇을 계산해서 어디에 저장하는가"** 를 먼저 파악한다. 최적화된 코드는 줄 단위 대응이 깨지는 대신, 입력과 출력의 관계는 반드시 원본과 동일하다는 점을 활용하는 것이다.

## 단계별 절차

**1) 인라인된 코드 식별**

호출 없이 곱셈/덧셈 몇 개로 끝나는 짧은 블록을 보면 "이게 원래는 별도 함수였을 수 있다"고 의심하고, 그 계산 패턴(예: `x*x`, `x+1`)이 어떤 유틸리티 함수의 전형적인 형태인지 유추한다.

**2) 레지스터 전용 변수는 사용 구간(live range)으로 추적**

`[rbp-N]`이 없다면, 특정 레지스터(예: `ebx`)가 함수 진입부터 끝까지 계속 같은 값을 들고 다니는지, 아니면 중간에 다른 값으로 재사용(overwrite)되는지를 명령어 순서대로 눈으로 따라간다. IDA는 이런 레지스터에도 종종 자동 변수 이름을 붙여준다.

**3) 언롤링된 루프는 반복 패턴으로 되돌려 생각**

똑같은 형태의 명령어 블록(오프셋만 4, 8, 12씩 다른)이 연속되면, "이건 사실 `for` 루프였다"고 재구성해서 이해한다.

**4) CMOV/SETcc는 삼항 연산자나 단순 if로 되돌려 읽기**

`cmp` 다음에 `cmovXX`가 오면 "`cmp`의 조건이 참이면 값을 바꾸는 삼항 연산자(`? :`)"라고 해석한다.

**5) 디버거로 실제 입출력 값을 관찰해서 검증**

구조가 헷갈릴 때는 정적으로 완벽히 이해하려 애쓰기보다, 디버거로 함수 진입 시 인자 값과 리턴 시 RAX 값을 여러 입력에 대해 관찰해서 "이 함수가 결국 무엇을 계산하는가"를 실험적으로 확인하는 것이 빠를 때가 많다.

**6) 가능하면 최적화 옵션을 낮춰 재현**

만약 소스 코드나 유사한 재현 코드를 손에 넣을 수 있다면, `-O0`으로 컴파일해서 최적화 없는 버전과 나란히 비교하면 최적화된 버전의 각 블록이 무엇에 대응하는지 훨씬 빠르게 파악할 수 있다.

## 명령어/단축키
```bash
gcc -O0 -S -o out_O0.s src.c      # 최적화 없이 어셈블리 생성(비교용)
gcc -O2 -S -o out_O2.s src.c      # 최적화 켜서 어셈블리 생성
diff out_O0.s out_O2.s             # 두 결과를 비교하며 최적화 효과 관찰
```
IDA/Ghidra: 함수 위에서 `F5`(Ghidra) 또는 자동 디컴파일 뷰(IDA) — 반복적으로 리네임하며 이해한 내용을 주석/변수명으로 남겨두면 다음에 다시 볼 때 훨씬 빠르다.

## 출력 해석
- `imul`/`add`만으로 끝나는 짧은 함수는 인라인된 헬퍼 함수의 흔적일 수 있다.
- `cmovXX`/`setXX`가 있다는 것은 원본에 조건문이 있었지만 분기 없이 계산됐다는 뜻이지, 조건 자체가 없었다는 뜻이 아니다.
- 함수 하나의 크기가 예상보다 훨씬 크면(수백 줄) 여러 작은 함수가 인라이닝되어 하나로 합쳐졌을 가능성이 높다.
- 디컴파일된 변수 이름이 원본과 다르다고 해서 로직 자체가 틀렸다는 뜻은 아니다 — 이름은 디컴파일러의 추정일 뿐, 계산 결과가 같다면 최적화 전후의 동작은 100% 동일해야 한다.

## 흔한 실수
- 최적화된 코드가 원본 소스와 줄 단위로 대응된다고 가정하고 억지로 맞추려는 것 — 최적화는 구조를 재배치할 뿐 결과만 보존하므로, 줄 대응이 아니라 "입출력 동작"을 기준으로 이해해야 한다.
- 인라인된 함수를 "이 함수는 원래 없었다"고 결론짓는 것 — 소스 레벨에서는 분명 존재했지만 바이너리 레벨에서 흡수된 것뿐이다.
- CMOV/SETcc 코드에 분기가 없다고 해서 "조건 분기 우회로 안티디버깅을 하고 있다"처럼 과잉 해석하는 것 — 단순한 컴파일러 최적화인 경우가 훨씬 많다.
- 디버그 심볼이 있는 빌드와 없는(stripped) 릴리즈 빌드를 혼동해서, 최적화 문제와 심볼 부재 문제를 같은 원인으로 착각하는 것 — 이 둘은 별개의 이슈다(심볼 문제는 REV-0038 참고).

## 막혔을 때 다음 체크
- RBP 없는 함수, 스택 프레임 자체가 생략된 것처럼 보이는 경우가 궁금하면 → REV-0031(스택 프레임이 무엇인지)로 이동.
- 인라인/최적화된 코드에서 함수 인자가 어디 있는지 헷갈리면 → REV-0032(함수 인자와 반환값이 어디에 있는지)로 이동.
- 함수/변수 이름이 아예 안 보이는 상황(디버그 심볼 부재)이 겹쳐 있다면 → REV-0038(심볼이 있는 바이너리와 Stripped 바이너리 차이)로 이동.

## 미니 예제
다음 함수가 최적화 여부에 따라 어떻게 달라지는지 비교해보자.

```c
int clamp(int x, int lo, int hi) {
    if (x < lo) return lo;
    if (x > hi) return hi;
    return x;
}
```

**`-O0` (최적화 없음)** — 소스와 거의 1:1 대응, 분기 3개:
```asm
clamp:
    push    rbp
    mov     rbp, rsp
    mov     [rbp-4], edi     ; x
    mov     [rbp-8], esi     ; lo
    mov     [rbp-0xC], edx   ; hi
    mov     eax, [rbp-4]
    cmp     eax, [rbp-8]
    jge     check_hi
    mov     eax, [rbp-8]
    jmp     done
check_hi:
    mov     eax, [rbp-4]
    cmp     eax, [rbp-0xC]
    jle     done
    mov     eax, [rbp-0xC]
done:
    pop     rbp
    ret
```

**`-O2` (최적화)** — 분기 없이 CMOV 두 번으로 압축:
```asm
clamp:
    cmp     edi, esi
    mov     eax, edi
    cmovl   eax, esi         ; x < lo 면 eax = lo
    cmp     eax, edx
    cmovg   eax, edx         ; (eax) > hi 면 eax = hi
    ret
```

`-O0` 버전은 `if`문 3개가 그대로 `cmp`/`jXX` 조합으로 남아 소스와 쉽게 대응되지만, `-O2` 버전은 스택 프레임도 없고(RBP 미사용), 분기도 전혀 없이 `cmovl`/`cmovg` 두 개로 끝나버린다. 두 코드 모두 같은 입력에 대해 항상 같은 결과를 내지만, 코드의 겉모습은 완전히 다르다 — 이것이 바로 "컴파일러 최적화가 디컴파일 결과를 이상하게 만드는" 핵심 이유다.
