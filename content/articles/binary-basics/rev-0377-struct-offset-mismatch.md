## 한 줄 요약
구조체 멤버 오프셋이 "필드 크기를 그냥 순서대로 더한 값"과 다르게 나온다면, 그건 계산 실수가 아니라 컴파일러가 각 필드를 **CPU가 효율적으로 접근할 수 있는 경계에 맞추기 위해 자동으로 넣은 패딩(padding)** 때문일 가능성이 매우 높다.

## 언제 검색해야 하나
- IDA/Ghidra에서 구조체를 만들어 넣었는데 `[rax+0x10]` 같은 오프셋이 손으로 계산한 값과 안 맞을 때
- `sizeof(struct)` 결과가 멤버 크기를 다 더한 값보다 더 크게 나올 때
- 구조체 멤버 순서만 바꿨는데 전체 크기가 달라지는 이유가 궁금할 때
- 네트워크 패킷 구조체나 파일 포맷 구조체를 리버싱하는데 필드 사이에 알 수 없는 빈 바이트가 보일 때

## 핵심 개념
컴파일러는 구조체의 각 멤버를 메모리에 배치할 때, 그 멤버 타입의 크기에 맞는 **정렬 경계(alignment boundary)**에 시작 주소를 맞추려 한다. 예를 들어 `int`(4바이트)는 보통 4의 배수 주소에서 시작해야 하고, `double`(8바이트)은 8의 배수 주소에서 시작해야 한다. 이 규칙을 지키기 위해 컴파일러는 필드 사이에 보이지 않는 **패딩 바이트**를 끼워 넣는다.

**구체적인 예시**: 다음 구조체를 x64에서 컴파일한다고 하자.
```c
struct Example {
    char  a;   // 1바이트
    int   b;   // 4바이트
    char  c;   // 1바이트
    double d;  // 8바이트
};
```
필드 크기만 단순히 더하면 `1 + 4 + 1 + 8 = 14`바이트가 될 것 같지만, 실제 오프셋은 다음과 같다.
- `a`: 오프셋 `0x00` (1바이트)
- **패딩 3바이트** (`b`를 4바이트 경계인 `0x04`에 맞추기 위해)
- `b`: 오프셋 `0x04` (4바이트)
- `c`: 오프셋 `0x08` (1바이트)
- **패딩 7바이트** (`d`를 8바이트 경계인 `0x10`에 맞추기 위해)
- `d`: 오프셋 `0x10` (8바이트)

전체 크기는 `0x18`(24바이트)이다. 손으로 계산한 14바이트와 실제 24바이트 사이의 10바이트 차이가 전부 패딩이다. 심지어 구조체의 **끝**에도 "가장 큰 멤버의 정렬 요구사항"에 맞추기 위한 꼬리 패딩(tail padding)이 붙을 수 있다 — 이 구조체 배열을 만들 때 두 번째 원소의 `a`도 8바이트 경계에서 시작해야 하기 때문이다.

**필드 순서를 바꾸면 크기가 줄어들 수 있다**: 같은 필드들을 크기가 큰 순서대로(`double d`, `int b`, `char a`, `char c`) 재배치하면 패딩이 거의 사라져 `8 + 4 + 1 + 1 = 14`바이트에 가깝게(정렬 때문에 16바이트) 줄어든다. 이건 실제로 C/C++ 코드를 최적화할 때 쓰는 기법이기도 하고, 리버싱 중에는 "왜 이 두 구조체가 필드는 똑같은데 크기가 다른가"를 설명해주는 단서이기도 하다.

## 화면/코드에서 보이는 징후
- IDA/Ghidra 구조체 뷰에서 필드 사이에 회색으로 `gap_XX` 또는 `field_XX`처럼 이름 없는 바이트 뭉치가 자동으로 생기는 경우
- 두 구조체가 논리적으로 같은 필드 구성인데 멤버 순서만 다르고, 전체 크기(`sizeof`)가 서로 다른 경우
- 네트워크 패킷을 구조체로 캐스팅해서 파싱하는 코드에서, 실제 프로토콜 명세와 어긋나는 오프셋에 필드를 읽어서 버그가 나는 경우(이런 이유로 실제 프로토콜 구조체는 보통 `#pragma pack(1)`을 쓴다)

## 가장 먼저 할 것
문제의 오프셋이 어긋난 그 구조체에서, 어긋나기 시작한 필드 **바로 앞** 필드의 타입 크기를 확인한다. 앞 필드가 1바이트/2바이트인데 다음 필드가 4바이트/8바이트라면 패딩이 들어갔을 가능성이 매우 높다.

## 단계별 절차

**1) 실제 오프셋을 어셈블리에서 그대로 읽기**
`mov eax, [rdi+0x10]` 같은 명령어에서 오프셋(`0x10`)을 있는 그대로 신뢰한다. 손으로 계산한 값과 다르다면 손 계산 쪽을 의심한다.

**2) 정렬 규칙 적용해서 손으로 재계산**
각 필드 앞에서 "다음 필드 크기의 배수가 되도록 현재 오프셋을 올림(round up)"하는 규칙을 적용해 다시 계산한다. 예: 현재 오프셋이 `0x08`이고 다음 필드가 8바이트 `double`이면 이미 8의 배수이므로 패딩 없이 바로 배치. 현재 오프셋이 `0x09`인데 다음 필드가 4바이트 `int`이면 `0x0C`까지 3바이트 패딩 후 배치.

**3) IDA/Ghidra의 구조체 정의 기능으로 검증**
IDA는 `Local Types` 또는 `Structures` 창에서 직접 구조체를 정의하면 패딩을 포함한 정확한 오프셋과 전체 크기를 자동 계산해서 보여준다. Ghidra는 Data Type Manager에서 구조체를 만들면 동일하게 정렬을 반영한다.

**4) 컴파일러별/pragma별 차이 고려**
`#pragma pack(1)`이나 `__attribute__((packed))`가 적용된 구조체는 패딩을 전혀 넣지 않는다. 네트워크 프로토콜이나 파일 포맷 구조체처럼 바이트 단위로 정확히 맞아야 하는 경우 이 옵션이 흔히 쓰이므로, 오프셋이 "패딩 없이" 딱 필드 크기 합과 일치한다면 packed 구조체일 가능성을 고려한다.

## 명령어/단축키
```text
IDA:    Local Types 창 (Shift+F1) → 구조체 정의, 자동 오프셋/크기 계산
IDA:    변수 위 우클릭 → Create struct / Change type
Ghidra: Data Type Manager → New → Structure
C:      offsetof(struct Example, d)   // 특정 필드의 정확한 오프셋 확인(표준 매크로)
C:      sizeof(struct Example)        // 패딩 포함 전체 크기 확인
```

## 출력 해석
- IDA의 구조체 뷰에서 이름 없는 `gap`/`byte`가 필드 사이에 자동 생성된다면 이는 도구가 임의로 만든 오류가 아니라, 실제 컴파일 결과에 존재하는 패딩을 정확히 반영한 것이다.
- `sizeof(struct)` 결과가 가장 큰 멤버 크기의 배수라면(예: `double`이 있는데 전체 크기가 8의 배수), 이는 정렬 규칙이 정상적으로 적용됐다는 신호다.

## 흔한 실수
- 구조체 크기를 필드 크기의 단순 합으로 암산하고 어셈블리 오프셋이 "틀렸다"고 오해하는 것.
- 패딩 바이트를 실제 데이터로 착각해서 그 위치에 의미 있는 값을 억지로 끼워 맞추려 하는 것.
- packed 구조체와 일반 구조체를 구분하지 않고 항상 정렬 규칙이 적용된다고 가정하는 것 — 네트워크/파일 포맷 구조체는 packed인 경우가 많다.
- 필드 순서를 바꿔서 만든 커스텀 구조체 정의를 IDA에 입력할 때, 원본 컴파일러와 다른 정렬 기준(4바이트 vs 8바이트)을 적용해서 새로운 오프셋 오류를 만드는 것.

## 막혔을 때 다음 체크
- 구조체 접근이 애초에 어셈블리로 어떻게 변환되는지(`[reg+offset]` 패턴 자체)가 궁금하면 REV-0035 문서로 이동.
- 오프셋 계산에 포인터/역참조 개념이 헷갈리면 REV-0033 문서로 이동.
- 배열 인덱스 계산에서 비슷한 혼동이 있다면 REV-0378 문서로 이동.

## 미니 예제
어셈블리에서 다음과 같은 코드를 봤다고 하자.
```asm
mov     eax, [rdi]        ; a  (char, offset 0x00)
mov     [rdi+4], ecx      ; b  (int,  offset 0x04, 패딩 3바이트 건너뜀)
mov     dl, [rdi+8]       ; c  (char, offset 0x08)
movsd   xmm0, [rdi+0x10]  ; d  (double, offset 0x10, 패딩 7바이트 건너뜀)
```
필드 크기만 보고 `b`는 `0x01`, `c`는 `0x05`, `d`는 `0x06`에 있을 거라 예상했다면 완전히 틀린다. 실제로는 `int`가 4바이트 경계, `double`이 8바이트 경계에 맞춰지느라 오프셋 `0x04`, `0x08`, `0x10`에 배치된 것이며, 이 계산은 앞서 설명한 `struct Example`과 정확히 일치한다.

## 출처/검증
- 구조체 멤버 정렬과 패딩 규칙: ISO/IEC 9899(C 표준) 6.7.2.1 "Structure and union specifiers" 및 각 컴파일러(MSVC, GCC/Clang)의 기본 정렬(alignment) 규칙 문서 기준 (2026-09-09 검증).
- `#pragma pack`/`__attribute__((packed))` 동작: Microsoft Learn(`pack` pragma) 및 GCC 공식 문서(Type Attributes, `packed`) 기준.
