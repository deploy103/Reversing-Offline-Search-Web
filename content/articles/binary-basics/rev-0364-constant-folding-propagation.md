## 한 줄 요약
상수 폴딩(constant folding)은 컴파일 타임에 계산 가능한 산술식을 미리 계산해 결과 리터럴로 치환하는 최적화이고, 상수 전파(constant propagation)는 어떤 변수가 항상 같은 상수 값을 갖는다는 사실을 알아내 그 변수 사용처를 전부 그 상수로 바꿔버리는 최적화다 — 두 최적화가 겹치면 소스코드에 분명히 있던 계산식이나 변수가 디스어셈블리/디컴파일 결과에서 통째로 사라진다.

## 언제 검색해야 하나
- 소스코드(또는 원본 문제 설명)에 `BUF_SIZE * 2` 같은 계산식이 있는데, 디스어셈블리에는 곱셈 명령어 없이 그냥 `256` 같은 숫자 하나만 바로 보일 때
- `#define KEY 0x41` 같은 매크로 상수를 어셈블리에서 찾으려 했는데, 매크로 이름은 당연히 없고 그 값이 여러 곳에 그냥 리터럴로 흩뿌려져 있어서 "이 숫자가 그 상수인지" 확신이 안 설 때
- 디컴파일된 함수 호출에서 인자가 `func(local_var)`가 아니라 `func(0x1000)`처럼 이미 계산이 끝난 리터럴로 나와서, 원래 변수가 어떤 로직으로 그 값이 됐는지 역추적이 막막할 때
- `if (a == b)`처럼 비교였을 소스 코드가 디컴파일 결과에서 아예 `if (1)` 또는 조건문 자체가 사라진 것처럼 보일 때

## 핵심 개념

### 상수 폴딩 — 컴파일 타임 계산
상수 폴딩은 컴파일러가 **런타임까지 기다릴 필요가 없는 계산을 컴파일 시점에 미리 끝내버리는** 최적화다. 예를 들어 소스코드에 `int size = 4 * 64;`가 있으면, 컴파일러는 이 곱셈이 두 리터럴(`4`, `64`) 사이의 연산이고 프로그램 실행 중에 값이 바뀔 여지가 전혀 없다는 걸 알기 때문에, 굳이 실행 파일에 "4와 64를 곱하는 명령어"를 넣지 않는다. 대신 컴파일 타임에 `4 * 64 = 256`을 계산해서 결과값 `256`을 바로 넣어버린다. 그래서 디스어셈블리를 보면 `imul` 같은 곱셈 명령어는 흔적도 없고 `mov eax, 100h`(256의 16진수)처럼 이미 계산이 끝난 리터럴만 보인다.

이건 버그가 아니라 정상적인 최적화다. `-O0`(최적화 없음)으로 컴파일해도 상수 폴딩만은 거의 모든 컴파일러가 기본으로 적용한다 — 어차피 결과가 항상 같은 계산을 실행할 때마다 반복하는 건 명백한 낭비이기 때문이다.

### 상수 전파 — 변수의 상수화
상수 전파는 조금 더 나아간 개념이다. 어떤 변수에 항상 같은 상수 값이 대입된다는 것을 컴파일러가 데이터 흐름 분석으로 알아내면, 그 변수를 쓰는 모든 자리를 그 상수 값으로 직접 바꿔치기한다.

```c
int key = 0x41;
int result = data ^ key;   // 소스에는 변수 key가 있음
```

이 코드가 최적화되면, `key`가 프로그램 어디서도 다른 값으로 바뀌지 않는다는 것을 컴파일러가 확인한 뒤 `key`라는 변수 자체를 아예 없애고 `data ^ 0x41`로 직접 치환해버린다. 디스어셈블리에는 `key`라는 이름의 스택 슬롯이나 레지스터가 아예 존재하지 않고, `xor eax, 41h`처럼 상수가 명령어에 바로 인코딩되어 나온다.

### 두 최적화가 겹칠 때 — 연쇄 반응
상수 폴딩과 상수 전파는 서로를 강화한다. 상수 전파로 변수 하나가 리터럴로 바뀌면, 그 변수가 들어있던 계산식 전체가 이제 "리터럴들끼리의 계산"이 되어 상수 폴딩 대상이 된다. 이 과정이 반복되면 원래 여러 줄에 걸쳐 있던 계산 로직 전체가 결과값 하나로 뭉개져서 사라지는 경우도 흔하다.

```c
#define BASE 0x1000
#define SIZE 0x100
int limit = BASE + SIZE * 2;
if (addr < limit) { ... }
```

이 코드는 최적화 컴파일 후 `limit`이라는 변수도, `BASE + SIZE * 2`라는 계산도 전혀 남지 않고 그냥 `cmp eax, 1200h` 한 줄로 끝나버릴 수 있다. 소스코드나 문제 설명서에서 본 매크로/공식을 디스어셈블리에서 그대로 찾으려 하면 실패할 수밖에 없다 — 이미 컴파일 타임에 계산이 끝나 리터럴로 녹아있기 때문이다.

### 조건문과 분기까지 사라지는 극단적인 경우
상수 전파가 조건문의 비교 대상까지 상수로 만들어버리면, 컴파일러는 그 조건이 항상 참인지 거짓인지도 컴파일 타임에 알 수 있게 된다. 이 경우 컴파일러는 조건 분기 명령어 자체를 아예 제거하고, 항상 실행되는 쪽 코드만 남기는 데드 코드 제거(dead code elimination)까지 함께 적용한다. 그래서 소스에 분명히 `if`문이 있었는데 디스어셈블리에는 `cmp`/`jz` 같은 비교·분기 명령어가 전혀 없이 한쪽 코드만 쭉 이어져 있는 경우도 나온다.

## 화면/코드에서 보이는 징후
- 디스어셈블리에 곱셈(`imul`, `mul`)이나 나눗셈(`idiv`, `div`) 명령어 없이 계산이 끝난 리터럴 값만 `mov`로 바로 들어가는 경우
- IDA/Ghidra 디컴파일 결과에서 함수 인자나 비교 대상이 지역 변수 이름 대신 처음부터 리터럴 숫자로 표시되는 경우
- 소스/문제 설명에 있던 매크로 상수 이름이 바이너리 어디에도 문자열로 남아있지 않고, 그 값만 리터럴로 여러 곳에 흩어져 있는 경우
- 소스에 `if`문이 있었는데 디스어셈블리에는 조건 분기 없이 한쪽 흐름만 존재하는 경우

## 가장 먼저 할 것
디스어셈블리에서 리터럴 값을 보면 "이 값이 런타임 계산 결과가 아니라 컴파일 타임에 이미 확정된 상수일 수 있다"는 가능성을 항상 열어둔다. 특히 문제 설명서나 소스코드에 있던 매크로/공식의 결과값이 무엇인지 직접 계산기(파이썬 등)로 미리 구해보고, 그 값을 디스어셈블리에서 검색하는 방식으로 접근하면 확인이 빠르다.

## 단계별 절차
1. 원본 소스(있다면)나 문제 설명에 등장하는 매크로/상수식을 전부 나열한다.
2. 파이썬 등으로 각 식의 실제 결과값을 미리 계산해 둔다.
3. IDA/Ghidra에서 해당 값을 리터럴로 직접 검색한다(IDA: Search → Immediate Value, `Alt+I`).
4. 검색된 위치에서 그 리터럴이 어떤 연산(비교, XOR, 덧셈 등)에 쓰이는지 확인해, 원래 소스의 어느 계산식에 대응하는지 역으로 매핑한다.
5. 여러 매크로 값이 조합된 것 같으면(예: `BASE + SIZE*2`), 후보 조합을 다시 계산해 리터럴과 일치하는지 대조한다.
6. 조건문이 사라진 것 같으면, 최적화로 인해 분기 자체가 제거됐을 가능성을 염두에 두고 남은 코드가 원래 어느 분기(참/거짓)에 해당하는지 문맥으로 추정한다.

## 명령어/단축키
- IDA: `Alt+I` (Immediate Value 검색) — 특정 리터럴 값이 코드 어디에 나오는지 전체 검색
- IDA: `Alt+B` (Binary/Byte 검색) — 리터럴을 리틀 엔디안 바이트 시퀀스로 찾을 때
- Ghidra: `Search → For Scalars` — 특정 상수값이 사용된 모든 위치 검색
- 파이썬: `hex(BASE + SIZE * 2)`처럼 후보 계산식을 즉석에서 검증

## 출력 해석
- 리터럴 검색으로 정확히 일치하는 위치를 찾았다면, 그 위치가 원래 소스의 어느 계산식이었는지 100% 확정된 것은 아니다 — 우연히 같은 숫자가 다른 목적으로 쓰였을 수도 있으므로 주변 문맥(비교 대상, XOR 대상 등)까지 함께 봐야 한다.
- 같은 상수가 여러 함수에 반복해서 나온다면, 원래 하나의 전역 상수/매크로였을 가능성이 높다 — 이름을 붙여(`make_const` 또는 IDA의 `N` 단축키로 상수 이름 지정) 가독성을 높이는 것이 좋다.

## 흔한 실수
- 디스어셈블리에 계산식이 안 보인다고 "이 값은 계산되는 게 아니라 원래부터 하드코딩된 상수였다"고 잘못 결론 내리는 것 — 최적화로 계산이 사라졌을 뿐 원래는 계산식이었을 수 있다.
- 소스코드의 매크로 이름을 디스어셈블리/디컴파일 결과에서 문자열로 찾으려고 헛수고하는 것 — 매크로는 전처리 단계에서 이미 사라지고, 상수 폴딩까지 겹치면 그 결과 리터럴만 남는다.
- `-O0`이면 상수 폴딩도 전혀 없을 거라 가정하는 것 — 최적화 레벨이 꺼져 있어도 컴파일러는 대부분 리터럴끼리의 계산만큼은 여전히 접어버린다(REV-0037 참고).

## 막혔을 때 다음 체크
- 최적화 전반이 코드 구조를 어떻게 바꾸는지 더 넓게 알고 싶다면 → REV-0037 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 이유
- 정수 계산 자체의 오버플로/랩어라운드가 궁금하면 → REV-0027 정수 Overflow와 Wraparound
- 리터럴을 헥스로 읽을 때 바이트 순서가 헷갈리면 → REV-0023 Little Endian과 Big Endian
- 상수와 AND/XOR 연산 조합을 해석해야 하면 → REV-0026 8비트 16비트 24비트 32비트 64비트 마스크

## 미니 예제
```c
#define ROUNDS 4
#define STEP   0x11
int total = ROUNDS * STEP;   // 소스: 곱셈식
if (input == total) { puts("OK"); }
```
최적화 컴파일 후 디스어셈블리는 대략 다음과 같이 나온다:
```asm
cmp     dword ptr [input], 44h    ; ROUNDS*STEP = 4*0x11 = 0x44, 이미 계산 끝남
jnz     short loc_fail
```
`imul` 명령어도, `total`이라는 변수도 흔적이 없다. `0x44`라는 리터럴만 보고 원래 `ROUNDS * STEP`이었다는 걸 알아내려면, 문제 설명에 있는 매크로 후보들을 미리 계산해보고 일치하는 값을 찾는 접근이 필요하다.

## 관련 글

- REV-0027 — 정수 Overflow와 Wraparound
- REV-0026 — 8비트 16비트 24비트 32비트 64비트 마스크
- REV-0368 — 비트 연산 우선순위를 어셈블리 순서로 확인하는 법

## 출처/검증
- 상수 폴딩(constant folding)과 상수 전파(constant propagation)의 정의 및 동작: 컴파일러 최적화 표준 개념(Aho, Lam, Sethi, Ullman, *Compilers: Principles, Techniques, and Tools*) 기준 (2026-09-09 검증).
