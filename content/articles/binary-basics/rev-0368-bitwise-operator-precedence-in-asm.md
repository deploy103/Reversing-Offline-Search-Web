## 한 줄 요약
C의 비트 연산자(`&`, `^`, `|`)는 비교 연산자(`==`, `<` 등)보다 우선순위가 낮아서 괄호 없이 섞어 쓰면 사람이 기대한 것과 다르게 묶이는 경우가 흔한데, 디스어셈블리를 보면 **컴파일러가 실제로 어떤 순서로 연산을 실행했는지**가 명령어 나열 순서 그대로 드러나므로 우선순위 규칙이 헷갈릴 때는 소스보다 어셈블리 순서를 신뢰하는 것이 더 정확하다.

## 언제 검색해야 하나
- 소스코드에 `if (a & b == c)`처럼 괄호 없이 비트 연산과 비교 연산이 섞여 있는데, 이게 `(a & b) == c`인지 `a & (b == c)`인지 헷갈릴 때
- 디컴파일된 C 코드에서 `x & y ^ z` 같은 식이 나왔는데 실제 연산 순서가 소스의 왼쪽부터 순서와 같은지 확신이 안 설 때
- CTF 크랙미의 검증 로직이 여러 비트 연산자를 한 줄에 섞어 써서, 손으로 재현하려는데 순서를 잘못 짜서 결과가 안 맞을 때
- IDA/Ghidra 디컴파일러가 자동으로 괄호를 쳐주긴 하는데, 그 괄호가 왜 그 자리에 있는지 원리가 궁금할 때

## 핵심 개념

### C 비트 연산자 우선순위 표 (헷갈리는 구간만)
C 연산자 우선순위는 전체가 매우 길지만, 리버싱에서 실제로 자주 함정이 되는 부분은 "비교 연산자가 비트 연산자보다 우선순위가 높다"는 사실 하나다. 우선순위가 높은 순서대로(위가 먼저 계산됨):

| 우선순위(높음→낮음) | 연산자 | 비고 |
|---|---|---|
| 높음 | `==`, `!=` | 동등 비교 |
| ↑ | `<`, `>`, `<=`, `>=` | 관계 비교 |
| ↑ | `&` | 비트 AND |
| ↑ | `^` | 비트 XOR |
| 낮음 | `\|` | 비트 OR |

이 순서를 외우는 것보다 훨씬 중요한 건 **"비교 연산자(`==`, `<` 등)가 비트 연산자(`&`, `^`, `\|`)보다 항상 먼저 계산된다"**는 한 가지 규칙이다. 이것 때문에 `a & b == c`는 사람의 직관("AND 결과와 c를 비교하고 싶다")과 반대로 `a & (b == c)`로 묶인다 — 즉 `b == c`를 먼저 계산해서 `0` 또는 `1`을 만든 다음, 그 결과와 `a`를 AND 하는 것이다. 이는 C 언어를 오래 써본 사람도 실수하는 유명한 함정이라, 좋은 코드 스타일 가이드는 이런 조합에 항상 괄호를 강제한다. 하지만 CTF 크랙미나 난독화된 코드는 일부러(또는 관습적으로) 괄호를 생략해서 헷갈리게 만드는 경우가 있다.

### 디스어셈블리는 우선순위 논쟁을 무의미하게 만든다
컴파일이 끝나면 우선순위라는 개념 자체가 사라진다. 우선순위는 "소스코드 텍스트를 어떻게 파싱할 것인가"에 대한 규칙일 뿐이고, 컴파일러는 파싱이 끝나는 순간 이미 트리 구조(AST)로 명확한 연산 순서를 확정해버린다. 그 확정된 순서가 그대로 어셈블리 명령어의 나열 순서로 나타난다. 즉 **어셈블리를 보면 우선순위 규칙을 몰라도 실제 연산 순서를 그냥 위에서 아래로 읽으면 된다.**

```c
if (a & b == c) { ... }
```
이 코드는 `b == c`가 먼저 계산되므로, 어셈블리도 그 순서 그대로 나온다.
```asm
mov     eax, [b]
cmp     eax, [c]
sete    al           ; b == c 결과(0 또는 1)를 al에 저장
movzx   eax, al
and     eax, [a]     ; 그 결과와 a를 AND — b==c가 먼저 계산됐다는 증거
test    eax, eax
jz      short loc_false
```
`sete`/`cmp`가 `and`보다 먼저 나온다는 사실 자체가 "비교가 먼저 계산됐다"는 것을 그대로 보여준다. 우선순위 표를 외울 필요 없이, 이 나열 순서를 위에서 아래로 읽기만 하면 실제 계산 순서를 100% 정확하게 알 수 있다.

### 디컴파일러가 자동으로 쳐주는 괄호를 신뢰하라
IDA Hex-Rays나 Ghidra의 디컴파일러는 내부적으로 확정된 연산 순서(AST)를 다시 C 텍스트로 출력할 때, 원래 소스에 괄호가 없었더라도 **모호함이 없도록 필요한 곳에 괄호를 자동으로 추가**한다. 예를 들어 위 예시는 디컴파일러 출력에서 `if (a & (b == c))`처럼 괄호가 명시적으로 붙어 나오는 경우가 많다. 이 괄호는 원본 소스에 실제로 있었을 수도, 없었을 수도 있지만 어느 쪽이든 **디컴파일러가 보여주는 괄호는 실제 실행 순서를 정확히 반영한다** — 그러니 우선순위를 암기하는 대신 디컴파일러가 쳐준 괄호를 그대로 신뢰하고 읽는 것이 실전에서 가장 빠르고 안전하다.

### 여러 비트 연산자가 섞였을 때(`&`, `^`, `|`)
비트 연산자끼리도 우선순위 차이가 있다(`&` > `^` > `|`). `a & b ^ c | d`는 `((a & b) ^ c) | d`로 묶인다. 이것도 마찬가지로 손으로 외우기보다, 디스어셈블리에서 `and`가 먼저, 그 다음 `xor`, 마지막에 `or`가 나오는 순서를 그대로 읽으면 확인이 끝난다.

## 화면/코드에서 보이는 징후
- 소스나 디컴파일 결과에 괄호 없는 `& == | ^` 조합이 뒤섞여 있는 경우
- 디스어셈블리에서 `cmp`/`sete`/`setne` 같은 비교 계열 명령어가 `and`/`or`/`xor` 비트 연산 명령어보다 먼저 나오는 순서
- IDA/Ghidra 디컴파일 결과에 원본에는 없었을 법한 괄호가 자동으로 추가되어 있는 경우

## 가장 먼저 할 것
괄호 없는 비트/비교 연산 혼합식을 만나면, 손으로 우선순위 표를 떠올리기보다 먼저 어셈블리(또는 디컴파일러가 이미 쳐준 괄호)를 확인해서 실제 순서를 있는 그대로 읽는다.

## 단계별 절차
1. 문제의 혼합식이 포함된 함수를 디스어셈블리 뷰로 연다.
2. 비교 명령어(`cmp`, `test`)와 그 결과를 저장하는 `sete`/`setne`/`setg` 등, 그리고 비트 연산 명령어(`and`, `or`, `xor`)가 나오는 순서를 위에서 아래로 그대로 따라간다.
3. 먼저 실행되는 연산이 최종 결과에 먼저 들어가는(더 안쪽으로 묶이는) 연산이다.
4. IDA/Ghidra 디컴파일러를 함께 켜서, 디컴파일러가 이미 자동으로 친 괄호와 자신이 어셈블리로 읽은 순서가 일치하는지 교차검증한다.
5. 여러 조건이 섞인 복잡한 식이면, 직접 파이썬으로 두 가지 해석(우선순위대로 묶은 것 vs 왼쪽부터 순서대로 묶은 것) 결과를 비교해 실제 로직과 어느 쪽이 맞는지 검증한다.

## 명령어/단축키
- IDA: 디스어셈블리 뷰(`Space`로 전환)와 Hex-Rays 디컴파일 뷰(`F5`)를 나란히 열어 명령어 순서와 괄호를 동시에 비교
- Ghidra: Listing(디스어셈블리)과 Decompile 패널을 나란히 두고 같은 방식으로 비교
```python
# 두 가지 해석을 파이썬으로 직접 비교해보기
a, b, c = 5, 3, 3
print((a & b) == c)   # 사람이 기대했을 법한 해석
print(a & (b == c))   # 실제 C 우선순위 규칙에 따른 해석
```

## 출력 해석
- 어셈블리에서 `cmp`/`sete` 계열이 `and`/`or`/`xor`보다 먼저 나온다면, 그 비교 연산이 비트 연산보다 먼저 계산되어 안쪽으로 묶인 것이다.
- 디컴파일러가 보여주는 괄호 구조는 원본 소스의 괄호 유무와 무관하게 항상 실제 실행 순서와 정확히 일치한다 — 디컴파일러 출력의 괄호를 최종 근거로 삼아도 된다.

## 흔한 실수
- `a & b == c`를 `(a & b) == c`로 직관적으로 읽어버리는 것 — C 우선순위 규칙상 실제로는 `a & (b == c)`다.
- 우선순위 표 전체를 억지로 암기하려는 것 — 실전에서는 디스어셈블리/디컴파일러 괄호를 읽는 게 훨씬 빠르고 실수가 없다.
- 비트 연산자끼리의 우선순위(`&` > `^` > `\|`)를 비교 연산자와의 관계와 혼동하는 것 — 두 그룹은 서로 다른 규칙이다.
- 어셈블리 순서를 볼 때 조건 분기(`jz`, `jnz`) 명령어 위치만 보고 전체 로직을 판단해, 그 앞에 있는 비교/비트 연산의 실제 계산 순서를 놓치는 것.

## 막혔을 때 다음 체크
- AND/OR/XOR 각 연산 자체의 의미(마스킹, 토글 등)가 헷갈리면 → REV-0026 8비트 16비트 24비트 32비트 64비트 마스크
- 상수 계산이 아예 다 접혀서 어셈블리에 계산 흔적조차 안 남았다면 → REV-0364 상수 폴딩과 상수 전파가 디컴파일에 미치는 영향
- 조건 분기와 비교 결과(ZF, SF 등 플래그) 해석이 헷갈리면 → 어셈블리 딕셔너리의 CMP/Jcc 관련 항목 참고
- 컴파일러 최적화로 연산 순서 자체가 재배열된 것 같다면 → REV-0037 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 이유

## 미니 예제
크랙미 검증 함수에서 흔히 보이는 패턴을 보자.
```c
// 디컴파일러가 자동으로 괄호를 쳐서 보여준 결과
if ( (input_len & (checksum == 0x1A)) != 0 )
{
    puts("Correct!");
}
```
이 코드를 손으로 재현하려는 사람이 우선순위를 착각해서 `(input_len & checksum) == 0x1A`로 짜면 완전히 다른(그리고 항상 거짓에 가까운) 조건이 되어버린다. 실제로는 `checksum == 0x1A`를 먼저 계산해 `0` 또는 `1`을 얻고, 그 값을 `input_len`과 AND한 결과가 0이 아닌지를 검사하는 것이다 — 즉 `checksum`이 정확히 `0x1A`이면서 동시에 `input_len`의 최하위 비트가 `1`(홀수)일 때만 참이 되는, 사람이 처음 봤을 때 직관과 전혀 다른 조건이다. 디컴파일러의 괄호를 그대로 신뢰했다면 이 함정을 바로 피할 수 있었다.

## 관련 글
- REV-0026 — 8비트 16비트 24비트 32비트 64비트 마스크
- REV-0364 — 상수 폴딩과 상수 전파가 디컴파일에 미치는 영향
- REV-0037 — 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 이유

## 출처/검증
- C 연산자 우선순위 표(비교 연산자가 비트 연산자보다 높은 우선순위를 가짐): ISO/IEC 9899(C 표준) 부속서 및 The C Programming Language(Kernighan & Ritchie) 연산자 우선순위 표 기준 (2026-09-09 검증).
- 컴파일러가 AST를 통해 연산 순서를 확정하고 디컴파일러가 이를 괄호로 명시적으로 표현하는 방식: IDA Hex-Rays 및 Ghidra 디컴파일러 공식 문서 기준 일반 원리.
