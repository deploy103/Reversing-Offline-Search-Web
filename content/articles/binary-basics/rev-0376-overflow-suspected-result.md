## 한 줄 요약
계산 결과가 상식적으로 말이 안 될 만큼 크거나 작다면, 그 값이 담긴 레지스터/변수의 **비트폭을 넘어서는 계산**을 했기 때문일 가능성이 높으며, 초과분은 그냥 버려지고 남은 비트만 결과로 남는 "랩어라운드(wraparound)"가 일어난 것이다.

## 언제 검색해야 하나
- 두 값을 더했는데 결과가 오히려 원래 값보다 작아졌을 때
- 곱셈 결과가 자료형이 담을 수 있는 범위를 훌쩍 넘어서, 전혀 다른(때로는 음수인) 값으로 나올 때
- 반복문 카운터가 특정 큰 값 근처에서 갑자기 0이나 아주 작은 값으로 튈 때
- CTF 문제에서 "정수 오버플로를 유발해서 체크를 우회하라"는 힌트가 있을 때

## 핵심 개념
CPU의 레지스터는 정해진 비트 수(8/16/32/64비트)만 저장할 수 있다. 계산 결과가 그 비트 수로 표현 가능한 범위를 넘어서면, 넘친 비트는 그냥 사라지고 **남은 하위 비트만 결과로 남는다**. 이걸 오버플로(overflow, signed 관점) 또는 랩어라운드/wraparound(unsigned 관점)라고 부른다.

**32비트 unsigned 덧셈 예시**: `0xFFFFFFFF + 1`을 계산하면 수학적으로는 `0x100000000`이지만, 32비트 레지스터는 33번째 비트를 저장할 공간이 없다. 그래서 결과는 하위 32비트만 남은 `0x00000000` = `0`이 된다. "큰 값 두 개를 더했는데 결과가 0이 나왔다"는 현상은 대부분 이 패턴이다.

**32비트 signed 곱셈 예시**: `50000 * 50000 = 2,500,000,000`인데, 32비트 signed `int`가 표현 가능한 최댓값은 `2,147,483,647`(`0x7FFFFFFF`)이다. `2,500,000,000`은 이 범위를 넘으므로 32비트 결과 레지스터에는 하위 32비트 `0x9502F900`만 남고, 이걸 signed로 해석하면 `2,500,000,000 - 4,294,967,296 = -1,794,967,296`이라는, 애초에 두 양수를 곱했는데 음수가 나오는 결과가 된다.

**FNV 해시류 상수에서도 자주 등장**: 예를 들어 FNV-1a 32비트 해시의 곱셈 상수 `16777619`(`0x01000193`)를 반복 곱셈하면서 32비트로 계속 잘라내는 것도 의도된 오버플로 활용이다. 즉 오버플로가 항상 "버그"인 것은 아니고, 해시 함수나 체크섬처럼 **의도적으로 랩어라운드를 이용하는 정상 로직**일 수도 있다는 점을 함께 기억해야 한다.

**CPU가 오버플로를 감지하는 방법**: x86/x64는 산술 연산 뒤에 두 개의 플래그로 오버플로를 알려준다.
- **CF(Carry Flag)**: unsigned 관점에서 "자리올림/자리내림이 발생했다"는 표시. `add`/`sub` 뒤에 `jc`/`jnc`(또는 `jb`/`jae`)로 확인 가능.
- **OF(Overflow Flag)**: signed 관점에서 "부호 있는 값의 범위를 벗어났다"는 표시. `jo`/`jno`로 확인 가능.
같은 연산이라도 CF와 OF는 서로 다른 조건에서 세팅되므로, 어떤 플래그를 검사하는 분기인지에 따라 "unsigned 오버플로를 체크하는 코드"인지 "signed 오버플로를 체크하는 코드"인지 구분할 수 있다.

## 화면/코드에서 보이는 징후
- `add`/`imul`/`shl` 직후에 `jo`, `jno`, `jc`, `jnb` 같은 플래그 분기 명령어가 붙어 있는 경우 — 컴파일러나 개발자가 오버플로를 의식적으로 체크하고 있다는 신호
- 디컴파일 결과에서 곱셈/덧셈 결과 변수가 나중에 원래 값보다 훨씬 작아 보이는 경우
- 반복문 카운터를 `unsigned char`나 `unsigned short` 같은 작은 타입으로 선언해서, 255나 65535를 넘으면 다시 0으로 돌아가는 경우

## 가장 먼저 할 것
결과가 이상한 그 연산의 **피연산자 크기(비트폭)와 결과를 담는 변수의 크기**부터 확인한다. 특히 두 개의 32비트 값을 곱하는데 결과를 32비트에 담고 있다면 오버플로 가능성을 최우선으로 의심한다.

## 단계별 절차

**1) 계산을 비트폭 그대로 재현**
결과가 이상한 연산을 파이썬으로 실제 비트폭에 맞춰 재현해본다.
```python
>>> a, b = 50000, 50000
>>> (a * b) & 0xFFFFFFFF          # 32비트로 잘라낸 실제 결과(unsigned 해석)
1500000000
>>> v = (a * b) & 0xFFFFFFFF
>>> v - 0x100000000 if v & 0x80000000 else v   # signed로 재해석
```
* 참고: 위 예시는 계산 편의를 위한 것이며, 실제 값은 곱셈 규모에 따라 달라지므로 항상 실제 피연산자로 다시 계산해야 한다.

**2) 어셈블리에서 결과를 받는 레지스터 크기 확인**
`imul eax, ebx`처럼 32비트 레지스터끼리 곱해서 32비트 레지스터(`eax`)에만 결과를 담는지, 아니면 `imul`의 확장 형태로 64비트(`edx:eax`)까지 결과를 받는지 확인한다. 32비트만 받는다면 상위 비트는 그냥 버려진다.

**3) 오버플로 체크 플래그 분기 여부 확인**
연산 직후 `jo`/`jno`(signed) 또는 `jc`/`jnc`(unsigned) 분기가 있는지 본다. 있다면 원래 코드가 오버플로를 이미 감지해서 처리하고 있다는 뜻이고, 없다면 오버플로가 체크되지 않은 채로 흘러간다는 뜻이라 취약점 후보가 된다.

**4) 의도된 랩어라운드인지 버그인지 문맥으로 판단**
해시/체크섬/난수 생성 로직이라면 랩어라운드가 정상 설계일 수 있다. 반면 "입력 길이 합산" "잔액 계산" 같은 로직에서 체크 없이 오버플로가 발생한다면 이는 버그 또는 의도적으로 파고들 수 있는 취약점이다.

## 명령어/단축키
```text
GDB:    p/x $eax                # 오버플로 후 실제 남은 비트 확인
GDB:    p $eflags                # 플래그 레지스터 전체 확인(OF/CF 포함)
어셈블리: jo / jno               # signed 오버플로 분기
어셈블리: jc / jnc (jb/jae)      # unsigned 캐리(오버플로) 분기
Python: (a * b) & 0xFFFFFFFF     # 32비트 unsigned 랩어라운드 재현
Python: (a * b) & 0xFFFFFFFFFFFFFFFF  # 64비트 랩어라운드 재현
```

## 출력 해석
- `p $eflags`에서 `OF`가 세팅돼 있으면 마지막 signed 연산이 표현 범위를 넘었다는 뜻이다.
- 파이썬으로 재현한 마스킹 결과(`& 0xFFFFFFFF` 등)가 프로그램이 실제로 보여준 값과 일치한다면, 그 연산이 정확히 그 비트폭에서 랩어라운드된 것이 확인된 것이다.

## 흔한 실수
- 오버플로를 "버그"로만 생각하고 해시/체크섬 로직에서도 무조건 문제로 지적하는 것 — 의도된 설계일 수 있다.
- 파이썬으로 재현할 때 비트 마스크(`& 0xFFFFFFFF`)를 빼먹어서, 파이썬의 임의 정밀도 정수 때문에 실제 프로그램과 다른 결과를 얻는 것.
- CF와 OF를 혼동해서 signed 코드에서 unsigned 오버플로 체크(`jc`)만 찾거나 그 반대로 찾는 것.
- 곱셈 결과가 원래 피연산자보다 훨씬 커야 정상인 상황에서, 오버플로로 오히려 작아진 결과를 "정상적으로 계산됐다"고 그냥 받아들이는 것.

## 막혔을 때 다음 체크
- 애초에 값이 왜 음수로 보이는지부터 헷갈리면 REV-0375 문서로 이동.
- 오버플로/wraparound의 원리 자체(수학적 정의, 비트별 마스크)를 더 깊이 보고 싶으면 REV-0027 문서로 이동.
- 컴파일러가 나눗셈이나 나머지 연산을 곱셈+시프트로 바꾸는 최적화 패턴 때문에 상수가 이상해 보이면 REV-0385 문서로 이동.

## 미니 예제
다음 C 코드가 있다고 하자.
```c
unsigned int total_size(unsigned char count, unsigned int item_size)
{
    return count * item_size;   // count는 최대 255, item_size는 큰 값일 수 있음
}
```
`count = 255`, `item_size = 20000000`이면 수학적으로는 `5,100,000,000`이지만 `unsigned int`(32비트)에 담기면 `5,100,000,000 & 0xFFFFFFFF = 805,032,704`가 남는다. 만약 이 함수의 리턴값을 `malloc`의 크기 인자로 넘긴다면, 개발자가 기대한 것보다 훨씬 작은 버퍼가 할당되는데도 호출하는 쪽은 `count`개의 `item_size` 크기 블록을 다 쓸 수 있다고 착각해서 힙 오버플로가 발생하는, 전형적인 "정수 오버플로 → 버퍼 오버플로" 연쇄 취약점 패턴이 된다.

## 관련 글
- REV-0027 — 정수 Overflow와 Wraparound
- REV-0375 — 값이 갑자기 음수로 보일 때 부호 확인하는 법
- REV-0385 — 같은 소스인데 컴파일러마다 상수 값이 다르게 보일 때

## 출처/검증
- CF/OF 플래그 세팅 조건과 오버플로 감지 명령어(`JO`, `JC` 등): Intel 64 and IA-32 Architectures Software Developer's Manual, Vol.1, "RFLAGS" 및 Vol.2 "Jcc" 섹션 기준 (2026-09-09 검증).
- 정수 오버플로가 버퍼 오버플로로 이어지는 패턴: CWE-190(Integer Overflow or Wraparound) 및 CWE-680(Integer Overflow to Buffer Overflow) 공식 설명 기준.
