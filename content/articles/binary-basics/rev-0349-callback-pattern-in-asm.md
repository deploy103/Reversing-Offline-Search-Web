## 한 줄 요약
콜백(callback)은 "내 함수의 주소를 다른 함수에게 인자로 넘겨서, 그 다른 함수가 나중에 필요한 시점에 대신 호출해달라"는 패턴이며, 어셈블리에서는 REV-0348에서 다룬 간접 호출(`call reg`)이 **호출자가 아니라 호출받는 라이브러리/프레임워크 함수 내부에서** 일어나기 때문에 "내가 만든 함수가 어디서도 호출되지 않는 것처럼" 보이는 게 특징이다.

## 언제 검색해야 하나
- `qsort(arr, n, size, cmp_func)`처럼 함수 포인터를 인자로 받는 라이브러리 API를 만났는데 `cmp_func`가 실제로 언제 어떻게 실행되는지 감이 안 잡힐 때
- 내가 분석 중인 함수(예: 비교 함수, 이벤트 핸들러)가 IDA에서 "Xrefs to"가 하나도 없는데 실행 중에는 분명히 실행되고 있을 때
- `signal()`, `pthread_create()`, GUI 이벤트 핸들러 등록처럼 "함수를 등록해두면 나중에 시스템/라이브러리가 대신 불러준다"는 API 패턴을 분석해야 할 때
- 라이브러리 함수(`qsort`, `bsearch` 등) 내부를 스텝인(Step Into)했더니 갑자기 내가 만든 코드로 점프해서 당황스러울 때

## 핵심 개념

### 콜백 = "나중에 불러달라"고 주소를 맡기는 것
일반적인 함수 호출은 A가 B를 직접 부른다(`B()`). 콜백 패턴은 방향이 뒤집힌다. A(예: 내가 만든 `main`)가 B(예: 라이브러리의 `qsort`)를 부르면서, "네가 필요할 때 이 함수(`cmp`)를 대신 불러줘"라며 **함수의 주소**를 인자로 넘긴다. 그러면 B 내부 어딘가에서 그 주소로 간접 호출(REV-0348)이 일어난다. 즉 콜백 함수의 몸체는 내가 작성했지만, **그 함수를 실제로 호출하는 코드(call 명령어)는 내 코드가 아니라 라이브러리 코드 안에 있다**는 것이 핵심이다.

```c
int cmp(const void *a, const void *b) {
    return *(int*)a - *(int*)b;
}

int main(void) {
    int arr[5] = {5,3,1,4,2};
    qsort(arr, 5, sizeof(int), cmp);   // cmp의 "주소"를 인자로 전달
    return 0;
}
```

`main`이 하는 일은 딱 두 가지다: (1) `cmp` 함수의 시작 주소를 계산(`lea`)하고, (2) 그 주소를 4번째 인자 레지스터(SysV x64는 `rcx`)에 담아 `qsort`를 호출하는 것. `cmp`를 직접 `call`하는 코드는 `main` 어디에도 없다.

```asm
main:
    ...
    lea     rcx, [cmp]              ; cmp 함수의 주소 계산 (call이 아니라 lea!)
    mov     rdx, 4                  ; sizeof(int)
    mov     rsi, 5                  ; n
    lea     rdi, [rbp-0x20]         ; arr
    call    qsort                    ; qsort 호출, cmp는 인자로만 전달됨
    ...
```

### 라이브러리 내부에서 실제 호출이 일어난다
`qsort`(libc 내부, 우리가 소스를 직접 볼 수 없는 경우가 많음)는 정렬 알고리즘을 수행하다가 두 원소를 비교해야 할 때마다, 인자로 받아둔 함수 포인터를 통해 간접 호출한다.
```asm
; qsort 내부(개념적 의사코드, 실제 glibc 구현은 더 복잡함)
qsort_internal:
    ...
    mov     rdi, [원소1 주소]
    mov     rsi, [원소2 주소]
    call    r12                      ; r12에 저장해둔 cmp 함수 포인터로 간접 호출
    cmp     eax, 0
    jg      swap_needed
    ...
```
IDA로 `main`만 봐서는 `cmp`가 호출되는 지점을 절대 찾을 수 없다 — 그 `call`은 `qsort`(때로는 정적으로 링크되어 있어도 별도 함수로 분리된) 내부에 있기 때문이다. 이것이 REV-0348에서 설명한 "간접 호출은 정적 xref로 안 잡힌다"는 문제의 가장 흔한 실전 사례다.

### 콜백을 찾는 실전 전략
1. **인자 전달 지점에서 역추적**: 콜백을 등록/전달하는 호출(`qsort(..., cmp)`, `signal(SIGINT, handler)`, `pthread_create(&t, NULL, worker, arg)`)을 먼저 찾는다. 이 호출 직전에 `lea reg, [함수주소]` 또는 `mov reg, 함수주소` 형태로 함수 시작 주소를 레지스터에 담는 코드가 반드시 있다.
2. **디버거로 실제 실행 흐름 추적**: 콜백 함수의 시작 주소에 브레이크포인트를 걸어두면, 정적 분석으로 호출 지점을 못 찾아도 실행 중 언제 어디서 불리는지 곧바로 확인할 수 있다.
3. **레지스터/스택에서 함수 포인터 값 검색**: 디버거에서 "이 함수의 주소를 담고 있는 메모리/레지스터가 어디 있는가"를 역방향으로 찾는다(예: x64dbg의 메모리 검색으로 특정 주소값 검색).

### 흔한 콜백 API 예시
- **`qsort`/`bsearch`(libc)**: 비교 함수를 인자로 받음.
- **`signal`(libc)**: 시그널 핸들러 함수 포인터를 등록, 커널이 시그널 발생 시 호출.
- **`pthread_create`(pthread)**: 스레드 시작 함수를 인자로 받음, 새 스레드에서 그 함수가 실행됨.
- **Windows API의 콜백 계열**(`EnumWindows`, `SetTimer`, `CreateThread`): 함수 포인터를 등록해두면 시스템이 필요할 때 호출.
- **GUI 프레임워크의 이벤트 핸들러 등록**: 버튼 클릭 등 이벤트 발생 시 등록해둔 함수가 호출됨.

이들의 공통점은 "등록은 내 코드에서, 실제 호출은 프레임워크/커널/라이브러리 코드에서" 일어난다는 것이다.

### 콜백과 REV-0348 함수 포인터 배열의 차이
REV-0348에서 다룬 함수 포인터 배열(디스패치 테이블, vtable)은 **내 코드 안에서** 인덱스로 골라 직접 호출하는 패턴이다. 반면 콜백은 함수 포인터를 **외부(라이브러리/커널/프레임워크)에게 넘겨주고**, 그 외부 코드 안에서 호출이 일어난다는 점이 다르다. 둘 다 "함수 주소를 값으로 다룬다"는 원리는 같지만, 호출이 일어나는 위치(내 코드 vs 남의 코드)가 다르므로 분석 전략도 달라진다 — 배열이면 그 배열이 정의된 데이터 영역을 뒤지면 되지만, 콜백이면 등록 지점에서 시작해 라이브러리 내부까지 따라 들어가거나 디버거로 실행을 추적해야 한다.

## 화면/코드에서 보이는 징후
- `lea reg, [함수이름]` 또는 `mov reg, offset 함수이름` 형태로 함수 주소를 레지스터에 담은 직후, `call`이 아니라 **다른 함수 호출의 인자로 그 레지스터가 쓰인다**.
- 내가 정의한 함수 위에서 IDA "Xrefs to"를 봤을 때 아무 결과도 없다(직접 호출하는 곳이 없음).
- `qsort`, `signal`, `pthread_create` 같은 잘 알려진 라이브러리 함수 호출 직전에 함수 주소로 보이는 값이 인자로 전달된다.
- 라이브러리 함수를 스텝인(Step Into)하다가 갑자기 프로그램 자신의 코드(`.text`의 낮은 주소 등, 라이브러리 코드와 다른 영역)로 실행 흐름이 튄다.

## 가장 먼저 할 것
분석 대상 함수가 "아무도 호출하지 않는 것 같다"면, 먼저 그 함수의 **시작 주소값 자체**가 다른 어딘가에서 데이터/인자로 쓰이고 있는지부터 찾는다. IDA에서 함수 이름 위에 커서를 놓고 Xrefs를 보면 코드상의 호출(call)뿐 아니라 주소 값으로 참조되는 지점("Data" 타입 xref)도 함께 나열되므로, 그 목록에서 "이 주소를 인자로 넘기는 코드"를 찾는 것이 출발점이다.

## 단계별 절차
1. 콜백으로 의심되는 함수의 Xrefs를 확인한다 — 코드 xref는 없어도 데이터 xref(주소값 참조)가 있을 수 있다.
2. 그 데이터 xref 지점 근처에서 어떤 라이브러리/API 함수 호출에 인자로 쓰였는지 확인한다.
3. 그 API가 잘 알려진 콜백 API(`qsort`, `signal`, `pthread_create` 등)인지 문서에서 시그니처를 확인해 몇 번째 인자가 함수 포인터인지, 언제 호출되는지 파악한다.
4. 콜백 함수 시작 주소에 브레이크포인트를 걸어 실제 호출 시점과 호출자(콜스택)를 디버거로 확인한다.
5. 콜스택(`bt`/`Alt+K`)을 확인해 실제로 어떤 라이브러리 함수 내부에서 호출되었는지 검증한다.

## 명령어/단축키
```
(gdb) break cmp                 # 콜백 함수 이름/주소에 직접 브레이크
(gdb) run
(gdb) bt                         # 콜스택 확인 → qsort 내부에서 호출되었는지 바로 보임
```
```
(gdb) info symbol *0x401120      # 어떤 함수 주소인지 심볼로 확인
```
IDA: 함수 이름 위 `X` 단축키(Xrefs to)로 코드 xref와 데이터 xref를 함께 확인. x64dbg: 콜백 함수 시작 주소에 브레이크포인트(`F2`) 후 실행, 걸리면 Call Stack 창에서 호출 경로 확인.

## 출력 해석
- `bt`(backtrace) 결과에 `cmp` 함수 위에 `qsort` 관련 프레임(`msort_with_tmp`, `__qsort_r` 등 glibc 내부 함수명)이 여러 겹 보이면, 라이브러리 내부에서 콜백이 호출되고 있다는 확실한 증거다.
- 콜백 함수가 여러 번(정렬 대상 개수에 비례해서) 반복 호출된다면 비교/순회 계열 콜백(정렬, 순회)일 가능성이 높고, 딱 한 번만 호출된다면 초기화/이벤트성 콜백일 가능성이 높다.

## 흔한 실수
- 콜백 함수에 대한 코드 Xref가 없다고 "죽은 코드(dead code)"라고 오판하고 분석에서 제외하는 것 — 실행에는 실제로 관여하는 경우가 매우 흔하다.
- 콜백 등록 API 호출(`qsort(..., cmp)`)만 보고 "cmp가 바로 이 시점에 실행된다"고 착각하는 것 — 실제 실행은 `qsort` 내부 로직이 진행되는 동안 여러 차례에 걸쳐 나중에 일어난다.
- REV-0348의 함수 포인터 배열(디스패치 테이블)과 콜백을 같은 것으로 취급해서, 콜백 함수를 찾을 때도 데이터 영역만 뒤지고 라이브러리 내부 호출 경로를 확인하지 않는 것.
- 콜백 함수의 매개변수 타입/개수를 API 문서 없이 임의로 추측하는 것 — `qsort` 비교 함수는 `int (*)(const void*, const void*)`처럼 정해진 시그니처를 반드시 따라야 하므로, 실제 호출 규약을 API 문서에서 확인해야 한다.

## 막혔을 때 다음 체크
- 함수 포인터가 메모리/레지스터에서 어떻게 표현되고 간접 호출이 어떻게 생겼는지 기본 개념이 헷갈리면 → REV-0348 함수 포인터가 메모리에서 어떻게 보이는지
- 함수 인자가 어느 레지스터로 전달되는지 호출 규약 자체가 헷갈리면 → REV-0032 함수 인자와 반환값이 어디에 있는지
- 스택 프레임과 콜스택 구조 자체가 헷갈리면 → REV-0031 스택 프레임이 무엇인지

## 미니 예제
```c
#include <stdlib.h>

int cmp(const void *a, const void *b) {
    return *(const int*)a - *(const int*)b;
}

void sort_array(int *arr, int n) {
    qsort(arr, n, sizeof(int), cmp);
}
```

x64 SysV 어셈블리(개념 설명용, `sort_array`만 발췌):
```asm
sort_array:
    ; rdi=arr, esi=n
    mov     ecx, esi
    mov     rsi, rdi          ; qsort 인자 순서에 맞춰 재배치 시작
    ...
    lea     rcx, [cmp]        ; 4번째 인자(cmp)에 함수 주소를 로드 — call이 아니라 lea!
    mov     r8d, 4            ; sizeof(int) (Windows x64 예시 레지스터 배치, 개념 설명용)
    call    qsort               ; cmp는 여기서 호출되지 않고 인자로만 전달됨
    ret
```

디버거에서 `qsort` 안으로 Step Into해 들어가면, 정렬 알고리즘이 진행되는 도중 어느 시점에 `call rcx`(또는 그에 준하는 레지스터) 형태로 `cmp` 함수가 실제로 호출되는 지점을 만나게 된다. `sort_array` 함수 자체의 코드만 아무리 들여다봐도 `call cmp`라는 줄은 존재하지 않으며, 이것이 콜백 패턴의 핵심 특징이다.

## 관련 글
- REV-0348 — 함수 포인터가 메모리에서 어떻게 보이는지
- REV-0032 — 함수 인자와 반환값이 어디에 있는지
- REV-0031 — 스택 프레임이 무엇인지

## 출처/검증
- `qsort`/`bsearch` 비교 함수 콜백 시그니처와 호출 규약: ISO C 표준(C11) 7.22.5 Searching and sorting utilities 섹션 및 POSIX/glibc `qsort(3)` 매뉴얼 기준.
- 간접 호출을 통한 콜백 실행과 정적 xref 한계: Intel 64 and IA-32 Architectures Software Developer's Manual, Vol.2(`CALL` 명령어) 및 IDA Pro 공식 문서(Xrefs 동작 방식) 기준 (2026-09-09 확인).
