## 한 줄 요약
C 문자열은 메모리에서 문자 코드가 연속으로 나열되고 끝에 값 `0`(널 바이트)이 붙는 형태(**null-terminated**)로 저장되며, 어떤 인코딩(ASCII/UTF-8/UTF-16)을 쓰느냐에 따라 문자 하나당 바이트 수와 바이트 배열 패턴이 달라진다.

## 언제 검색해야 하나
- IDA/Ghidra의 문자열 목록(Strings 창)에서 어떤 문자열은 정상으로 보이는데 어떤 문자열은 글자 사이에 `00`이 껴서 이상하게 보일 때
- Windows API 함수 이름 끝에 `A`와 `W`가 붙어 있는 이유가 궁금할 때(`MessageBoxA` vs `MessageBoxW`)
- 헥스 덤프에서 문자열처럼 보이는 바이트 나열을 발견했는데 어떤 인코딩인지 판단해야 할 때
- 한글/이모지 등 비ASCII 문자가 포함된 문자열이 여러 바이트로 쪼개져 저장된 걸 보고 당황했을 때

## 핵심 개념
컴퓨터는 문자를 그 자체로 저장하지 않고, 문자마다 정해진 숫자(코드 포인트)를 매핑한 뒤 그 숫자를 특정 바이트 형식으로 인코딩해서 저장한다. 리버싱에서 자주 만나는 세 가지 인코딩은 다음과 같다.

**ASCII (1바이트 고정)**: 영문 대소문자, 숫자, 기본 기호만 표현하며 문자 하나가 정확히 1바이트(0~127)를 차지한다. `"Hi"`는 메모리에 `48 69`(H=0x48, i=0x69) 두 바이트로 저장된다.

**UTF-8 (가변 길이, 1~4바이트)**: ASCII와 완전히 호환되도록 설계되어, 영문/숫자는 ASCII와 똑같이 1바이트로 저장되지만 한글·한자·이모지 같은 비ASCII 문자는 2~4바이트로 늘어난다. 리눅스/웹/현대 크로스플랫폼 소프트웨어의 기본 인코딩이다. 예를 들어 한글 `"가"`는 UTF-8에서 `EA B0 80` 3바이트로 저장된다.

**UTF-16 (가변 길이, 보통 2바이트 단위, "와이드 문자열")**: 대부분의 문자를 2바이트(코드 유닛) 하나로 표현하고, 극히 일부 확장 문자(이모지 등)만 2바이트짜리 두 개(서로게이트 쌍)를 쓴다. Windows API의 내부 문자열 처리(특히 `wchar_t`, `WCHAR`)가 기본적으로 UTF-16을 쓴다. 영문자를 UTF-16으로 저장하면 각 문자 뒤에 `00` 한 바이트가 따라붙는 것처럼 보인다 — 예를 들어 `"Hi"`는 `48 00 69 00`으로 저장된다(리틀 엔디안 기준). 이것이 바로 "글자 사이에 00이 껴있는" 문자열의 정체다.

**Null terminator(널 종료 문자)**: C 스타일 문자열은 별도로 길이를 저장하지 않는 대신, 문자열의 끝을 알리는 값 `0`을 마지막에 붙인다. ASCII/UTF-8 문자열은 `00` 한 바이트로 끝나고, UTF-16(와이드) 문자열은 2바이트짜리 `0x0000`으로 끝난다. 문자열을 처리하는 함수(`strlen`, `strcpy` 등)는 이 널 바이트를 만날 때까지 계속 읽어나가는 방식으로 동작한다 — 이 널 바이트가 없으면 함수가 메모리를 계속 읽어나가다가 크래시를 일으키거나(버퍼 오버리드), 반대로 널 바이트를 공격자가 의도적으로 조작해 문자열을 자르는 취약점(문자열 절단)의 원인이 되기도 한다.

**Windows API의 `A`/`W` 접미사**는 바로 이 인코딩 선택을 반영한다. `MessageBoxA`는 ANSI(대략 1바이트 계열, 로케일에 따라 멀티바이트일 수 있음) 버전, `MessageBoxW`는 UTF-16 와이드(Wide) 버전이다. 최신 Windows 프로그램 대부분은 내부적으로 `W` 버전을 쓰고, `A` 버전은 호출 시 내부적으로 UTF-16으로 변환한 뒤 `W` 버전을 호출하는 래퍼인 경우가 많다.

정리하면:

| 인코딩 | 문자당 바이트 | 종료 표시 | 주 사용처 |
|---|---|---|---|
| ASCII | 1바이트 고정 | `00` (1바이트) | 초창기 C, 영문 전용 |
| UTF-8 | 1~4바이트 가변 | `00` (1바이트) | Linux, 웹, 크로스플랫폼 |
| UTF-16 | 2바이트(±서로게이트) | `00 00` (2바이트) | Windows API 내부(`wchar_t`) |

## 화면/코드에서 보이는 징후
- IDA/Ghidra의 문자열 창에서 타입이 `C`(char, ASCII/UTF-8 추정)와 `Unicode`(UTF-16 추정)로 구분되어 표시된다.
- 헥스 덤프에서 `48 00 65 00 6C 00 6C 00 6F 00`처럼 알파벳과 `00`이 번갈아 나오면 UTF-16 리틀 엔디안 문자열이다.
- 함수 이름 뒤에 `A`/`W`가 붙은 Windows API 임포트가 보인다(`CreateFileA`/`CreateFileW`, `lstrlenA`/`lstrlenW` 등).
- 디컴파일된 코드에서 `wchar_t*`, `LPWSTR`, `WCHAR[]` 타입이 등장하면 UTF-16을 다루는 코드다.
- 한글이 포함된 문자열을 IDA가 잘못된 인코딩으로 추정해서 깨진 문자로 보여주는 경우가 있다 — 이럴 때는 헥스값을 직접 보고 UTF-8/EUC-KR 등을 수동으로 판단해야 한다.

## 가장 먼저 할 것
문자열처럼 보이는 바이트 나열을 만나면, 먼저 **바이트 사이에 `00`이 규칙적으로 섞여 있는지**를 확인한다. 매 문자 뒤에 `00`이 하나씩 있으면 UTF-16(와이드) 가능성이 높고, `00`이 전혀 없다가 끝에만 하나 있으면 ASCII/UTF-8 가능성이 높다.

## 단계별 절차

**1) 헥스 덤프로 바이트 패턴 확인**

x64dbg나 GDB의 메모리 덤프 창에서 문자열 주소를 열어 바이트를 직접 본다.
```
(gdb) x/20xb 0x0000555555556004
0x555555556004: 0x48 0x00 0x65 0x00 0x6c 0x00 0x6c 0x00
0x55555555600c: 0x6f 0x00 0x00 0x00
```
`48 00 65 00 6c 00 6c 00 6f 00 00 00` → `H`,`e`,`l`,`l`,`o` 각 글자 뒤에 `00`이 붙고 끝에 `00 00`으로 종료 → UTF-16 `"Hello"`.

**2) 디버거의 문자열 뷰 기능 활용**

GDB는 문자열 타입을 지정해서 바로 해석할 수 있다.
```
(gdb) x/s 0x0000555555556010          # 일반 char* (ASCII/UTF-8) 해석
(gdb) x/wc 0x0000555555556010          # 유니코드는 수동으로 2바이트씩 확인 필요
```
x64dbg는 메모리 덤프 창에서 우클릭 → "Text" 표시 방식을 `ASCII`/`UNICODE`로 전환해서 바로 읽을 수 있다.

**3) IDA/Ghidra에서 타입 강제 지정**

문자열이 잘못된 타입(예: char로 인식됐는데 실제로는 UTF-16)으로 보이면, 해당 데이터 위에서 우클릭 → 문자열 타입을 `Unicode`(UTF-16)로 바꿔서 다시 렌더링한다.

**4) UTF-8 다중 바이트 문자 판별**

UTF-8에서 바이트의 상위 비트 패턴으로 그 바이트가 몇 바이트짜리 문자의 일부인지 알 수 있다.
```
0xxxxxxx           -> 1바이트 문자(ASCII와 동일)
110xxxxx 10xxxxxx  -> 2바이트 문자
1110xxxx 10xxxxxx 10xxxxxx          -> 3바이트 문자(한글 대부분 포함)
11110xxx 10xxxxxx 10xxxxxx 10xxxxxx -> 4바이트 문자(이모지 등)
```
예를 들어 `EA B0 80`을 보면 첫 바이트가 `1110....` 패턴이므로 3바이트짜리 UTF-8 문자(한글 한 글자)로 판단할 수 있다.

## 명령어/단축키
```
(gdb) x/s addr          # C 문자열(ASCII/UTF-8, null 종료)로 해석해서 출력
(gdb) x/20xb addr        # 원시 바이트 20개를 헥스로 확인 (인코딩 직접 판단용)
strings -e l target.exe  # UTF-16 리틀 엔디안 문자열만 추출 (binutils strings 도구)
strings target.exe       # 기본 ASCII 문자열 추출
```
IDA: Strings 창(`Shift+F12`)에서 인코딩별 필터링 및 검색 가능. 문자열 데이터 위에서 우클릭 → 타입 변경으로 ASCII ↔ Unicode 전환.

## 출력 해석
- `strings` 명령의 기본 옵션은 ASCII/UTF-8 계열만 잡아낸다. Windows 바이너리에서 UTF-16 문자열이 안 보인다면 `strings -e l`(리틀 엔디안 16비트) 옵션을 추가해야 한다.
- IDA Strings 창에서 `Unicode`로 분류된 항목은 대부분 UTF-16이며, 실제 표시되는 글자 수는 바이트 수의 절반(영문 기준) 정도다.
- 문자열 끝에 널 바이트가 없다면 그 데이터가 완전한 문자열이 아니거나, 길이를 별도로 저장하는 문자열 타입(예: C++ `std::string`, Pascal 스타일 문자열)일 가능성이 있다.

## 흔한 실수
- UTF-16 문자열을 ASCII로 착각해서 "이상하게 글자 사이에 널바이트가 낀 깨진 문자열"이라고 오해하는 것 — 실제로는 정상적인 와이드 문자열이다.
- `strings` 명령이 UTF-16 문자열을 찾아주지 못하는데 "이 바이너리에는 이 문자열이 없다"고 단정하는 것 — 인코딩 옵션을 바꿔가며 다시 시도해야 한다.
- 문자열 길이를 바이트 수로 계산할 때 UTF-16이나 UTF-8 멀티바이트 문자를 고려하지 않고 "글자 수 = 바이트 수"로 가정하는 것.
- Null terminator가 없는(길이 기반) 문자열 구조체를 만났을 때 억지로 `00`을 찾으려다가 엉뚱한 곳까지 문자열이라고 오판하는 것.
- IDA/Ghidra가 인코딩을 잘못 추정해서 한글이 깨져 보이는데도 그 결과를 그대로 믿는 것 — 이럴 때는 원본 바이트를 헥스 에디터(HxD, ImHex)로 직접 열어서 UTF-8 3바이트 패턴(`EA`, `EB`, `EC`로 시작하는 경우가 한글 영역에서 흔함)이 맞는지 대조하는 것이 가장 확실하다.

## 막혔을 때 다음 체크
- 문자열이 저장된 위치(코드/데이터/스택/힙)가 궁금하면 → REV-0030(Code Data BSS Stack Heap 기초)으로 이동.
- 문자열 포인터를 함수 인자로 넘기는 코드의 형태가 궁금하면 → REV-0032(함수 인자와 반환값이 어디에 있는지), REV-0033(포인터와 역참조)으로 이동.
- 문자열 비교/복사 명령어(`REP MOVSB`, `SCASB`)의 구체적 동작이 궁금하면 AGENTS.md에 정의된 Assembly Dictionary의 `MOVS`, `SCAS`, `REP` 관련 항목을 검색해서 이동.

## 미니 예제
다음 C 코드가 두 가지 인코딩을 어떻게 메모리에 저장하는지 비교해보자.

```c
#include <stdio.h>
#include <wchar.h>

int main(void) {
    char    ascii_str[] = "Hi";
    wchar_t wide_str[]  = L"Hi";   // Windows에서 UTF-16으로 저장됨
    printf("%s\n", ascii_str);
    return 0;
}
```

메모리에 저장되는 실제 바이트:
```
ascii_str: 48 69 00              ; 'H' 'i' NUL   (3바이트)
wide_str : 48 00 69 00 00 00     ; 'H'.. 'i'.. NUL(2바이트)  (6바이트)
```

디스어셈블리에서 이 두 문자열을 다루는 코드는 대략 이렇게 보인다.
```asm
lea     rax, [ascii_str]
mov     rdi, rax
call    strlen          ; ASCII/UTF-8 문자열 길이 계산, 1바이트씩 세며 00을 찾음

lea     rax, [wide_str]
mov     rcx, rax
call    wcslen           ; 와이드 문자열 길이 계산, 2바이트씩 세며 0x0000을 찾음
```
`strlen`과 `wcslen`(Windows에서는 `lstrlenW` 등)처럼 **함수 이름 자체가 다르다**는 점도 어떤 인코딩을 다루는 코드인지 짐작하는 유용한 단서다.

## 관련 글
- REV-0030 — Code Data BSS Stack Heap 기초
- REV-0032 — 함수 인자와 반환값이 어디에 있는지
- REV-0033 — 포인터와 역참조를 어셈블리에서 읽는 법

## 출처/검증
- UTF-8 바이트 패턴 및 가변 길이 인코딩 규칙: Unicode Standard 공식 스펙(UTF-8, RFC 3629) 기준 (2026-09-08 검증).
- UTF-16 및 서로게이트 쌍: Unicode Standard의 UTF-16 인코딩 형식(RFC 2781 등) 기준.
- Windows API의 `A`/`W` 함수 접미사와 ANSI/Wide 처리 방식: Microsoft 공식 문서 "Unicode and Character Sets" 기준.
