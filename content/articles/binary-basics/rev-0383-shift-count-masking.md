## 한 줄 요약
x86/x64에서 시프트(`SHL`/`SHR`/`SAR`/`ROL`/`ROR`) 연산의 시프트량(count)은 레지스터 크기를 넘는 값을 그대로 쓰지 않고, **레지스터 폭에 맞춰 자동으로 마스킹(잘라내기)**된다 — 32비트 연산이면 시프트량을 `& 0x1F`(0~31로 제한), 64비트 연산이면 `& 0x3F`(0~63으로 제한)한 값만 실제로 적용된다.

## 언제 검색해야 하나
- `x << 32`처럼 시프트량이 레지스터 비트 수와 같거나 더 큰데, 결과가 예상한 `0`이 아니라 원본 값 그대로 나올 때
- 시프트량을 변수로 받는 함수에서, 변수 값이 크면 예상치 못한 시프트가 일어날 때
- 32비트 연산과 64비트 연산에서 같은 시프트량을 썼는데 결과가 다르게 나올 때(마스킹 범위가 다르기 때문)
- CTF 문제에서 "시프트량 정수 오버플로/언더플로"를 이용해 검증 로직을 우회해야 할 때

## 핵심 개념
수학적으로 32비트 값을 32번 왼쪽으로 시프트하면 모든 비트가 밀려나가서 결과는 `0`이어야 할 것 같다. 하지만 실제 x86/x64 CPU는 그렇게 동작하지 않는다.

**하드웨어 규칙**: x86/x64의 시프트/회전 명령어는 시프트량 오퍼랜드를 그대로 쓰지 않고, 먼저 대상 오퍼랜드의 비트폭에 맞춰 **모듈로(mod) 연산**을 적용한다.
- 8/16/32비트 오퍼랜드: 시프트량을 **5비트**만 사용(즉 `count & 0x1F`, 0~31 범위로 제한)
- 64비트 오퍼랜드: 시프트량을 **6비트**만 사용(즉 `count & 0x3F`, 0~63 범위로 제한)

**구체적 예시**: `eax`(32비트)를 32번 왼쪽 시프트하려고 `shl eax, 32`를 실행하면, CPU는 먼저 `32 & 0x1F = 0`을 계산한다. 즉 **실제로는 0번 시프트**, 다시 말해 **아무 일도 일어나지 않고 `eax`는 원래 값 그대로 남는다.** "32번 밀었으니 0이 되겠지"라는 기대와 정반대의 결과다.

`shl eax, 33`이라면 `33 & 0x1F = 1`이므로 실제로는 1번만 시프트된다. `shl eax, 40`이면 `40 & 0x1F = 8`이므로 8번 시프트된 것과 동일하다.

64비트에서는 기준이 다르다. `shl rax, 32`는 `32 & 0x3F = 32`이므로 **실제로 32번 시프트가 그대로 적용**되어, 이 경우는 결과가 예상대로 상위 32비트만 남고 하위 32비트는 0이 된다. 즉 **같은 "32"라는 시프트량도 32비트 연산이냐 64비트 연산이냐에 따라 전혀 다른 결과**를 낸다.

**C 표준에서도 이건 사실 "정의되지 않은 동작(UB)"이다**: C 언어 표준은 시프트량이 피연산자의 비트 수 이상이면 결과를 정의하지 않는다(undefined behavior). 즉 `int x; x << 32;`는 C 표준상 어떤 결과가 나와도 이상하지 않지만, 실제로 x86 CPU에서 컴파일된 바이너리를 돌리면 하드웨어의 마스킹 규칙(`& 0x1F`)을 그대로 따르는 결과가 나온다. 이건 "C 표준이 보장하는 동작"이 아니라 "이 CPU와 이 컴파일러 조합에서 실제로 관찰되는 동작"이라는 점을 구분해야 한다.

## 화면/코드에서 보이는 징후
- 소스 코드나 디컴파일 결과에서 시프트량이 변수인데, 그 변수의 실제 범위를 확인하지 않고 "32 이상이면 안전하게 0이 되겠지"라고 가정한 방어 코드가 있는 경우
- `shl`/`shr`/`sar` 명령어의 시프트량 오퍼랜드가 즉시값 32 이상인데도 프로그램이 크래시 없이 그대로 동작하는 경우
- 32비트 시프트와 64비트 시프트가 섞인 코드에서 같은 상수 시프트량인데 결과 폭이 다른 경우

## 가장 먼저 할 것
문제의 시프트가 몇 비트 폭 연산인지(`shl eax` 32비트, `shl rax` 64비트, `shl al` 8비트 등) 먼저 확인하고, 그 폭에 맞는 마스크(32비트=`0x1F`, 64비트=`0x3F`)로 시프트량을 직접 계산해본다.

## 단계별 절차

**1) 대상 레지스터/오퍼랜드의 비트폭 확인**
`shl eax, N`(32비트) vs `shl rax, N`(64비트)을 구분한다.

**2) 시프트량에 알맞은 마스크 적용**
```python
def effective_shift(count, width):
    mask = 0x1F if width <= 32 else 0x3F
    return count & mask

print(effective_shift(32, 32))   # 0  → shl eax, 32 는 아무 효과 없음
print(effective_shift(32, 64))   # 32 → shl rax, 32 는 그대로 32비트 시프트
```

**3) 시프트량이 변수라면 그 변수가 마스킹 이후에도 위험한 값이 될 수 있는지 검토**
예를 들어 사용자 입력으로 시프트량을 받는 함수가 있는데, `if (count >= 32) return;` 같은 방어 코드가 없다면, `count = 40`을 넣어도 마스킹으로 인해 실제로는 `count = 8`처럼 동작해서 방어 로직을 그대로 우회할 수 있다.

**4) 디버거로 실측**
GDB에서 레지스터에 원하는 값을 넣고 `shl`/`shr` 명령을 한 스텝 실행해서 실제 마스킹 규칙을 직접 확인한다.

## 명령어/단축키
```asm
shl  eax, 32   ; 32 & 0x1F = 0  → 효과 없음(eax 그대로)
shl  eax, 33   ; 33 & 0x1F = 1  → 1비트만 시프트
shl  rax, 32   ; 32 & 0x3F = 32 → 그대로 32비트 시프트
shr  ax,  16   ; 8/16비트 대상도 마스크는 0x1F 기준(운영체제/모드에 따라 세부 인코딩 차이 있음)
```
```gdb
set $eax = 0xDEADBEEF
stepi
p/x $eax
```

## 출력 해석
- `shl eax, 32` 실행 후 `eax`가 실행 전과 완전히 동일하다면, 이는 오작동이 아니라 `32 & 0x1F = 0` 마스킹 규칙이 정확히 적용된 정상 결과다.
- 32비트와 64비트 버전의 같은 상수 시프트량이 다른 결과를 낸다면, 각 폭에 맞는 마스크(`0x1F` vs `0x3F`)를 적용해서 재계산하면 정확히 일치해야 한다.

## 흔한 실수
- "시프트량이 비트 수 이상이면 결과는 0이다"라고 수학적으로만 생각하고, 실제 CPU의 마스킹 규칙을 확인하지 않는 것.
- 32비트 연산과 64비트 연산의 마스크 범위(`0x1F` vs `0x3F`)가 다르다는 것을 모르고 한쪽 규칙을 다른 쪽에도 그대로 적용하는 것.
- 시프트량을 사용자 입력으로 받는 코드에서 상한 검사만 하고, 그 상한이 실제 비트폭 마스킹을 우회할 수 있는 값(32, 64, 96 등)인지 확인하지 않는 것.
- C 표준상 정의되지 않은 동작(UB)이라는 이유로 "이 코드는 아무 의미도 없다"고 넘겨버리는 것 — 실제 바이너리는 특정 컴파일러/CPU 조합에서 결정론적으로 동작하므로 리버싱 관점에서는 그 실제 동작을 정확히 알아야 한다.

## 막혔을 때 다음 체크
- SHL/SAL, SAR 명령어 자체의 기본 동작(플래그 변화 포함)이 궁금하면 assembly 카테고리의 SHL/SAL, SAR 문서로 이동.
- 시프트 결과가 오버플로처럼 보이는 다른 상황이 궁금하면 REV-0376 문서로 이동.
- 32비트/64비트 레지스터 관계 자체가 헷갈리면 REV-0022 문서로 이동.

## 미니 예제
다음 C 코드가 있다고 하자.
```c
unsigned int mask_bits(unsigned int value, unsigned int n) {
    if (n >= 32)
        return 0;          // 개발자는 "32 이상이면 안전하게 0" 이라고 의도
    return value << n;
}
```
겉보기엔 안전해 보이지만, 만약 이 검사가 실수로 빠지거나 다른 경로(예: 인라인된 별도 함수)에서 `n` 검사 없이 `value << n`이 직접 컴파일된다면 어셈블리는 다음과 같다.
```asm
mov     eax, edi        ; value
mov     ecx, esi        ; n
shl     eax, cl         ; cl(시프트량)도 실제로는 & 0x1F 적용됨
ret
```
`n = 32`을 넣으면 `cl & 0x1F = 0`이 되어 `shl eax, 0`, 즉 `value`가 시프트 없이 그대로 반환된다. 개발자가 "n이 32 이상이면 0을 리턴하게 만들었으니 안전하다"고 믿고 있던 별도 코드 경로가 있다면, 이 하드웨어 마스킹 동작 때문에 그 가정이 깨지는 지점을 찾는 것이 이런 유형의 문제를 푸는 핵심이다.

## 관련 글
- REV-0022 — 32비트와 64비트 레지스터 차이
- REV-0376 — 계산 결과가 예상보다 훨씬 크거나 작을 때(오버플로 의심)
- REV-0063 — SAR: 산술 오른쪽 시프트

## 출처/검증
- 시프트/회전 명령어의 카운트 마스킹 규칙(32비트: 5비트, 64비트: 6비트): Intel 64 and IA-32 Architectures Software Developer's Manual, Vol.2, "SHL/SAL/SHR—Shift Instruction" 및 "SAR—Shift Arithmetic Right" 명령어 레퍼런스의 "Operation" 의사코드(`COUNT := COUNT MOD 32` 또는 `MOD 64`) 기준 (2026-09-09 검증).
- C 언어에서 시프트량이 비트폭 이상일 때 정의되지 않은 동작(UB)이라는 규정: ISO/IEC 9899(C 표준) 6.5.7 "Bitwise shift operators" 조항 기준.
