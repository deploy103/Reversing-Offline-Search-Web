## 한 줄 요약
비트필드(`unsigned int flag : 1;`)는 여러 개의 작은 값을 **바이트 하나(또는 정수 하나) 안에 비트 단위로 쪼개 담는** 문법이며, 어셈블리에서는 REV-0026에서 다룬 비트 마스크(AND/OR/XOR)와 시프트(SHL/SHR) 명령어의 조합으로 컴파일되어, 일반 구조체 필드 접근(`[reg+오프셋]` 한 줄)과 달리 **읽기/쓰기마다 시프트+마스크 연산이 따라붙는다**는 점이 결정적으로 다르다.

## 언제 검색해야 하나
- C 구조체 정의에 `unsigned int a : 1; unsigned int b : 3;`처럼 필드 이름 뒤에 콜론과 숫자가 붙은 문법을 봤을 때
- 어셈블리에서 하나의 값을 읽어온 뒤 `shr`(오른쪽 시프트)과 `and`(마스크)를 연달아 적용해서 아주 작은 값(0~1, 0~7 등)만 뽑아내는 패턴이 반복될 때
- 구조체 `sizeof`가 필드 개수에 비해 작게 나와서 필드들이 한 정수 안에 압축되어 있다고 의심될 때
- 플래그/상태값 여러 개가 한 바이트/워드 안에 몰려 있는 것으로 보이는 코드(파일 포맷 헤더, 네트워크 프로토콜, 게임 상태값 등)를 분석할 때

## 핵심 개념

### 비트필드는 "한 정수 안의 작은 구획들"
일반 구조체 필드는 각자 최소 1바이트 이상의 독립된 공간을 갖는다(REV-0035). 비트필드는 그보다 더 잘게, **비트 단위**로 공간을 나눠 쓴다.

```c
struct Flags {
    unsigned int is_active   : 1;   // 1비트
    unsigned int level       : 3;   // 3비트 (0~7)
    unsigned int type        : 4;   // 4비트 (0~15)
    unsigned int reserved    : 24;  // 나머지 24비트(사용 안 함)
};
// sizeof(struct Flags) == 4   (전부 합쳐 32비트 = int 하나에 들어감)
```
이 구조체는 메모리에 4바이트(`int` 하나)만 차지하며, 그 4바이트 안에서 최하위 비트부터(대부분의 x86/x64 컴파일러 관례) `is_active`(1비트), `level`(3비트), `type`(4비트) 순서로 채워진다. 정확한 비트 순서와 패딩 규칙은 컴파일러/플랫폼에 따라 구현 정의(implementation-defined)라는 점은 알아두되, 실전에서는 리틀엔디안 x86/x64에서 GCC/MSVC 모두 최하위 비트부터 채우는 것이 일반적이다.

### 읽기 — 시프트로 위치를 맞추고 마스크로 잘라낸다
```c
int get_level(struct Flags *f) {
    return f->level;
}
```
```asm
mov     eax, [rdi]        ; 4바이트 전체를 읽음 (is_active, level, type, reserved가 전부 섞여 있음)
shr     eax, 1              ; is_active(1비트)만큼 오른쪽으로 밀어서 level을 최하위로 이동
and     eax, 7               ; 하위 3비트만 남김 (level은 3비트이므로 마스크 0b111 = 7)
ret
```
`shr eax, 1`으로 `is_active`가 차지하던 1비트를 밀어내 `level`을 맨 오른쪽으로 가져온 다음, `and eax, 7`(이진수 `111`)로 3비트만 남기고 나머지 상위 비트를 전부 지운다. 이 "시프트 후 마스크" 두 줄 조합이 비트필드 읽기의 전형적인 시그니처다.

### 쓰기 — 기존 값을 지우고 새 값을 그 자리에 끼워 넣는다
비트필드에 값을 쓰는 것은 더 복잡하다. 같은 정수 안의 **다른 비트필드 값은 그대로 보존**해야 하기 때문에, 해당 비트 위치만 0으로 지운 뒤 새 값을 시프트해서 OR로 끼워 넣는 절차가 필요하다.

```c
void set_level(struct Flags *f, int lv) {
    f->level = lv;
}
```
```asm
mov     eax, [rdi]           ; 기존 4바이트 전체 값 읽기
and     eax, 0xFFFFFFF1       ; level이 차지하는 비트(1~3번 비트, 마스크 0b1110)만 0으로 지움
mov     ecx, esi               ; lv
and     ecx, 7                  ; lv 값도 3비트로 잘라냄(혹시 더 큰 값이 들어와도 안전하게)
shl     ecx, 1                  ; level 위치(1번 비트부터)로 밀어올림
or      eax, ecx                ; 지워둔 자리에 새 값을 끼워 넣음
mov     [rdi], eax             ; 결과를 다시 저장 (다른 필드는 그대로 보존됨)
```
이 "읽기 → AND로 해당 비트 지우기 → 새 값 시프트 → OR로 합치기 → 다시 쓰기"의 5단계 패턴이 비트필드 쓰기의 전형적인 시그니처다. 일반 구조체 필드 쓰기(`mov [rdi+N], value` 한 줄)와 비교하면 훨씬 복잡해 보이지만, 이 패턴 자체가 "비트필드에 값을 대입하고 있다"는 확실한 단서가 된다.

### 왜 비트필드를 쓰는가 — 메모리 절약과 프로토콜 명세 준수
비트필드는 크게 두 가지 이유로 쓰인다. 첫째, 여러 플래그/작은 값을 한 정수에 몰아넣어 **메모리를 절약**한다(임베디드 환경, 대량의 상태값 배열 등). 둘째, 파일 포맷이나 네트워크 프로토콜, CPU 레지스터처럼 **비트 단위로 명세가 고정된 데이터**(예: TCP 헤더의 플래그 비트, PE/ELF 헤더의 특정 필드)를 그대로 표현하기 위해 쓴다. CTF에서는 커스텀 파일 포맷 파서나 패킹된 상태값 구조체 분석에서 자주 만나게 된다.

### 이미 REV-0026에서 배운 마스크/시프트가 여기서 재사용된다
비트필드 접근은 새로운 명령어가 아니라, REV-0026에서 다룬 "특정 비트만 뽑아내는 마스크(AND)"와 "값을 원하는 위치로 옮기는 시프트(SHL/SHR)" 기법을 **구조체 필드 접근**이라는 맥락에 적용한 것뿐이다. 다른 점은, 일반적인 플래그 조작은 코드 흐름 어디서나 한 번씩 등장하지만, 비트필드는 **같은 베이스 주소에 대해 서로 다른 시프트량/마스크값 조합이 반복적으로 나타난다**는 것이다.

## 화면/코드에서 보이는 징후
- 같은 오프셋(`[reg]`, `[reg+N]`)에서 값을 읽은 뒤 `shr`(또는 `shl`)과 `and`가 바로 이어지는 패턴이 반복되고, 매번 시프트량과 마스크 상수만 다르다.
- 마스크 상수가 `1`, `3`, `7`, `0xF`, `0x1F`처럼 `2^n - 1` 형태(비트 n개를 뽑아내는 마스크)로 자주 등장한다.
- 쓰기 코드에서 `and`(비트 지우기) → `shl`(새 값 정렬) → `or`(합치기) → 저장의 4~5단계 조합이 나타난다.
- 구조체 정의(디버그 정보나 헤더 파일이 남아있는 경우) 필드 뒤에 `: 숫자` 콜론 문법이 보인다.

## 가장 먼저 할 것
`shr`/`shl` 다음에 `and`가 바로 붙은 패턴을 발견하면, 시프트량과 마스크 값을 한 쌍으로 기록해둔다. 시프트량이 그 필드가 시작하는 비트 위치, 마스크에서 세트된 비트 개수(`0x7`이면 3비트, `0xF`이면 4비트)가 그 필드의 비트 폭이다. 같은 베이스 주소에서 이런 쌍을 여러 개 모으면 전체 비트필드 레이아웃을 복원할 수 있다.

## 단계별 절차
1. 같은 베이스 주소에 대한 `shr`/`and`(또는 `shl`/`and`/`or`) 조합을 전부 모은다.
2. 각 조합에서 시프트량(비트 시작 위치)과 마스크(비트 폭)를 기록한다.
3. 시프트량을 오름차순으로 정렬해 필드 순서를, 마스크로 각 필드의 비트 폭을 확정해 전체 레이아웃 표를 만든다.
4. 쓰기 코드에서 등장하는 "보존 마스크"(`and eax, 0xFFFFFFF1` 같은, 특정 비트만 0으로 지우는 상수)를 비트 반전(`~마스크`)해서 그 필드의 위치/폭을 교차 검증한다.
5. 필요하면 IDA에서 구조체를 만들고 비트필드 멤버로 정의해 디컴파일 결과를 정리한다.

## 명령어/단축키
```
(gdb) print/t *(unsigned int*)&flags   # /t 포맷으로 32비트 전체를 2진수로 출력해 비트 배치 한눈에 확인
(gdb) print flags.level                  # 디버그 정보가 있으면 비트필드 필드명으로 바로 접근 가능
```
```python
# 마스크/시프트 값으로 비트필드 레이아웃을 손으로 계산할 때
value = 0b00010110
level = (value >> 1) & 0b111      # 1번 비트부터 3비트 추출
```

## 출력 해석
- `print/t`로 출력된 2진수 문자열을 오른쪽(최하위 비트)부터 왼쪽으로 읽으면서, 앞서 기록한 시프트량/폭 목록과 대조하면 각 구간이 어떤 필드인지 바로 확인할 수 있다.
- 마스크 상수를 2진수로 변환했을 때 연속된 `1`의 개수가 그 필드의 비트 폭과 정확히 일치해야 한다. 안 맞으면 필드 경계를 잘못 짚었을 가능성이 있다.
- 쓰기 코드의 "보존 마스크"(예: `0xFFFFFFF1`)를 반전하면 `0x0000000E`(이진수 `1110`)가 되는데, 이는 "1~3번 비트가 이 필드의 위치"라는 뜻과 일치해야 한다.

## 흔한 실수
- 비트필드 읽기(`shr`+`and`)를 그냥 "값을 나누고 마스킹하는 이상한 계산"으로 오해하고 구조체 필드라는 것을 놓치는 것.
- 시프트량과 마스크 폭을 혼동해서(예: 시프트량 3을 "3비트 폭"으로 착각) 비트 위치 복원을 잘못하는 것.
- 비트필드의 정확한 비트 순서(최하위부터 채우는지, 최상위부터 채우는지)가 컴파일러/플랫폼에 따라 다를 수 있다는 것을 무시하고 한 가지 규칙만 맹신하는 것 — 실제 바이너리에서 관찰된 시프트량으로 검증하는 것이 항상 더 안전하다.
- 쓰기 코드에서 "보존 마스크"가 있다는 것을 놓치고, 그 명령어가 단순히 값을 지우는 것처럼 보고 다른 필드가 함께 훼손된다고 착각하는 것 — 실제로는 다른 필드를 보존하기 위한 정상적인 절차다.

## 막혔을 때 다음 체크
- 비트 마스크/시프트의 기본 원리 자체가 헷갈리면 → REV-0026 8비트 16비트 24비트 32비트 64비트 마스크
- 일반 구조체 필드의 고정 오프셋 접근 방식과 비교하고 싶다면 → REV-0035 구조체 접근이 어셈블리로 변하는 방식
- 여러 값이 한 정수 안에서 오프셋 0을 공유하는 다른 패턴(union)과 헷갈리면 → REV-0351 Union이 메모리에서 어떻게 겹치는지

## 미니 예제
```c
struct Flags {
    unsigned int is_active : 1;   // bit 0
    unsigned int level     : 3;   // bit 1~3
    unsigned int type      : 4;   // bit 4~7
};

int get_level(struct Flags *f) {
    return f->level;
}

void set_level(struct Flags *f, int lv) {
    f->level = lv;
}
```

x64 SysV 어셈블리(개념 설명용):
```asm
get_level:
    mov     eax, [rdi]     ; 4바이트 전체 로드
    shr     eax, 1           ; is_active(1비트) 만큼 밀어 level을 최하위로
    and     eax, 7            ; 3비트만 남김 (0b111)
    ret

set_level:
    mov     eax, [rdi]        ; 기존 값 로드
    and     eax, 0xFFFFFFF1    ; level 위치(비트 1~3, 0b1110)만 0으로 지움
    mov     ecx, esi            ; lv
    and     ecx, 7                ; 3비트로 제한
    shl     ecx, 1                ; level 위치로 이동
    or      eax, ecx              ; 합치기
    mov     [rdi], eax           ; 저장
    ret
```

IDA/Ghidra가 비트필드 구조체를 인식했다면 다음처럼 자연스럽게 복원한다.

```c
int get_level(struct Flags *f)
{
  return f->level;
}

void set_level(struct Flags *f, int lv)
{
  f->level = lv;
}
```

`shr eax, 1` + `and eax, 7`이 읽기(`f->level`), `and eax, 0xFFFFFFF1` + `shl ecx, 1` + `or eax, ecx`가 쓰기(`f->level = lv`)에 정확히 대응한다. 마스크 `0xFFFFFFF1`을 비트 반전하면 `0x0E`(이진수 `1110`)가 되어, "1번 비트부터 3비트가 level의 자리"라는 사실과 정확히 일치하는 것을 확인할 수 있다.

## 관련 글
- REV-0026 — 8비트 16비트 24비트 32비트 64비트 마스크
- REV-0035 — 구조체 접근이 어셈블리로 변하는 방식
- REV-0351 — Union이 메모리에서 어떻게 겹치는지

## 출처/검증
- 비트필드(bit-field)의 정의, 크기/정렬 및 구현 정의(implementation-defined) 비트 순서 규칙: ISO C 표준(C11) 6.7.2.1 Structure and union specifiers 섹션 기준.
- 비트필드 읽기/쓰기가 시프트(`SHL`/`SHR`)와 마스크(`AND`/`OR`) 명령어 조합으로 컴파일되는 패턴: Intel 64 and IA-32 Architectures Software Developer's Manual, Vol.2 및 실제 GCC/Clang x86-64 컴파일 결과 기준 (2026-09-09 확인).
