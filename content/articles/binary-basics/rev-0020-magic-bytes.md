## 한 줄 요약
거의 모든 파일 형식은 **파일의 맨 앞 몇 바이트("매직 바이트")에 고정된 식별용 값**을 넣어두며, 이 값을 확인하면 확장자가 없거나 거짓이어도 실제 파일 종류를 알아낼 수 있다 — 예를 들어 PE는 `4D 5A`("MZ"), ELF는 `7F 45 4C 46`으로 시작한다.

## 언제 검색해야 하나
- CTF 문제 파일에 확장자가 없거나(`chall`, `flag.bin`처럼) `.txt`, `.jpg` 등으로 위장되어 있어서 진짜 형식을 모를 때
- `file` 명령어를 돌렸는데 `data`라고만 나와서 아무 정보도 못 얻었을 때
- 헥스에디터로 파일을 열었더니 앞부분이 `4D 5A`나 `7F 45 4C 46`이 아니라서 "이거 헤더가 깨진 건가?" 싶을 때
- 실행 파일인데 더블클릭해도 안 열리고, 디버거/디스어셈블러에서 "알 수 없는 형식"이라고 뜰 때

## 핵심 개념
운영체제 로더나 각종 파서 프로그램은 파일을 열 때 확장자만 믿지 않는다. 확장자는 사용자 편의를 위한 문자열일 뿐이고, 실제로 "이 파일이 PE인지, PNG인지, ZIP인지"를 판단하는 근거는 **파일 내용의 맨 앞부분에 박혀 있는 고정된 바이트 값**이다. 이를 **매직 바이트(magic bytes)** 또는 **파일 시그니처(file signature)**라고 부른다.

핵심 원리는 단순하다: 파일 형식을 설계할 때 "이 형식이면 파일의 offset 0(맨 첫 바이트)부터 반드시 이 값이 와야 한다"고 정해둔다. 파서는 파일을 열자마자 이 몇 바이트만 읽어서 형식을 즉시 구분할 수 있고, 잘못된 형식의 파일을 실수로 로드해서 크래시가 나는 일을 막을 수 있다.

**대부분의 매직 바이트는 파일 offset 0에 있다.** 이것이 원칙이다. 단, PE는 예외적으로 **두 번째 시그니처를 간접 참조(indirect)로 찾는 특이한 구조**를 가지고 있는데, 이 부분이 리버싱 초보가 꼭 알아야 할 포인트다(아래 "PE" 항목에서 자세히 설명).

### 각 형식의 정확한 매직 바이트

**PE (Windows 실행 파일, .exe/.dll/.sys)**
- offset `0x00`: `4D 5A` — ASCII로 "MZ". DOS 헤더(`IMAGE_DOS_HEADER`)의 시작을 나타내는 시그니처이며, MS-DOS용 실행 파일 로더 개발자 Mark Zbikowski의 이니셜에서 따온 것으로 알려져 있다.
- offset `0x3C`: 4바이트 리틀엔디안 정수 `e_lfanew` 필드. 이 값이 **실제 PE 헤더가 시작하는 파일 offset**을 가리킨다.
- `e_lfanew`가 가리키는 위치: `50 45 00 00` — ASCII로 "PE\0\0". 이 4바이트 뒤에 COFF 헤더(`IMAGE_FILE_HEADER`)가 이어진다.

즉 PE는 "offset 0에 MZ가 있고, offset 0x3C에 적힌 값만큼 뒤로 가면 PE\0\0이 있다"는 **2단계 검증 구조**다. 왜 이렇게 만들었을까? MS-DOS 시절의 하위 호환 때문이다. 옛날 DOS는 PE라는 개념을 몰랐고, MZ 헤더 뒤에는 보통 "이 프로그램은 DOS 모드에서 실행할 수 없습니다" 같은 문구를 출력하는 작은 DOS 스텁 프로그램이 있었다. Windows는 이 DOS 헤더 구조를 그대로 유지하면서, `e_lfanew`라는 필드 하나로 "진짜 헤더는 이만큼 뒤에 있다"고 가리키는 방식으로 PE 포맷을 얹었다. 그래서 MZ와 PE\0\0 사이의 거리는 파일마다 다를 수 있다(대개 링커가 정한 값, 흔히 `0x80`, `0xF0` 등).

**ELF (Linux 실행 파일)**
- offset `0x00`~`0x03`: `7F 45 4C 46` — `0x7F` 뒤에 ASCII "ELF".
- offset `0x04` (`EI_CLASS`): `01`이면 32비트, `02`이면 64비트.
- offset `0x05` (`EI_DATA`): `01`이면 리틀엔디안, `02`이면 빅엔디안.

이 두 필드는 architecture 판별(x86 vs x64)의 첫 단서다. 자세한 구분법은 [REV-0021](./rev-0021-x86-vs-x64.md)(x86 vs x64 구분법)에서 다룬다.

**PNG**
- `89 50 4E 47 0D 0A 1A 0A` (8바이트 고정). `50 4E 47`은 "PNG"이고, 앞뒤로 `0x89`, `0D 0A`, `1A 0A`가 붙는데 이건 우연이 아니라 의도적으로 설계된 값이다 — 텍스트 모드로 잘못 전송되거나(개행 변환), 7비트 전송 경로에서 상위 비트가 잘리는 문제를 미리 감지하기 위한 "보호용" 바이트들이다.

**JPEG**
- 항상 `FF D8 FF`로 시작. 그 다음 바이트로 세부 종류가 갈린다: `FF D8 FF E0`(JFIF 표준), `FF D8 FF E1`(Exif, 카메라 촬영 메타데이터 포함).

**GIF**
- `47 49 46 38 39 61`("GIF89a") 또는 `47 49 46 38 37 61`("GIF87a"). 뒤 2바이트가 버전을 나타내며, 89a가 최신(애니메이션 GIF 등 확장 지원).

**ZIP 계열 (ZIP, APK, JAR, DOCX, XLSX 등)**
- `50 4B 03 04`("PK\x03\x04"). PK는 ZIP 포맷을 만든 Phil Katz의 이니셜이다.
- 빈 압축 파일(엔트리가 하나도 없는 경우)은 `50 4B 05 06`(End Of Central Directory만 존재)으로 시작한다.
- **APK, JAR, DOCX, XLSX, PPTX, ODT, JPK 등은 전부 내부적으로 ZIP 컨테이너다.** 그래서 이 파일들도 시작 바이트가 똑같이 `50 4B 03 04`다. 확장자만으로 "이건 워드 파일" 식으로 안심하면 안 되고, 실제로는 압축된 XML/클래스 파일 묶음이라는 것을 기억해야 한다. 실제로 `.docx` 파일을 `.zip`으로 바꿔서 압축 해제 프로그램으로 열면 내부 XML 구조가 그대로 보인다.

**RAR**
- RAR4: `52 61 72 21 1A 07 00`(7바이트, "Rar!"+제어 바이트)
- RAR5: `52 61 72 21 1A 07 01 00`(8바이트, 끝에 `01 00`이 추가됨)

**7-Zip**
- `37 7A BC AF 27 1C`(6바이트)

**gzip**
- `1F 8B`(2바이트만). 뒤에 압축 방식(`08`=deflate가 보통)과 플래그 바이트가 이어진다.

**PDF**
- `25 50 44 46 2D`("%PDF-"), 뒤에 버전 문자열(예: "1.7")이 이어진다.

**Java .class**
- `CA FE BA BE`("CAFEBABE"). Java 클래스 파일임을 나타낸다.

**Mach-O (macOS 실행 파일)**
- 32비트: `FE ED FA CE`
- 64비트: `FE ED FA CF`
- 유니버설/팻 바이너리(여러 아키텍처를 한 파일에 묶은 것): `CA FE BA BE`

여기서 중요한 함정 하나: **Mach-O 팻 바이너리의 매직 바이트가 Java .class 파일과 완전히 같은 `CA FE BA BE`다.** 두 형식을 구분하는 방법은 매직 바이트 자체가 아니라 **그 다음에 오는 필드와 파일 전체 구조**다.
- Java .class는 `CA FE BA BE` 뒤에 마이너 버전(2바이트), 메이저 버전(2바이트)이 오고 파일 크기가 보통 수 KB~수백 KB 수준이며 이후 상수 풀(constant pool) 구조가 이어진다.
- Mach-O 팻 바이너리는 `CA FE BA BE` 뒤에 아키텍처 개수(4바이트, `fat_header.nfat_arch`)가 오고, 그 뒤로 각 아키텍처별 서브 헤더(CPU 타입, 오프셋, 크기)가 반복된다. 파일 크기도 실행 파일 특성상 훨씬 크고 여러 아키텍처의 실제 코드가 이어 붙어 있다.
- 또한 Mach-O 팻 헤더는 **빅엔디안으로 기록**된다는 점도 특이하다(일반 Mach-O 32/64비트 헤더는 실행되는 CPU에 맞춰 리틀/빅엔디안이 달라질 수 있지만, 팻 헤더 자체는 항상 빅엔디안). 반면 Java .class 파일의 매직 뒤 버전 필드는 항상 빅엔디안(Java 클래스 포맷 자체가 빅엔디안 고정)이라 이 자체로는 구분이 안 되고, 결국 **다음 필드의 값 범위와 파일 크기·확장자·주변 문맥**을 같이 보고 판단해야 한다. 즉 "매직 바이트가 같다고 형식이 같다는 보장은 없다"는 걸 보여주는 대표 사례다.

**BMP**
- `42 4D`("BM", 2바이트).

**SQLite**
- `53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33 00` — ASCII로 "SQLite format 3\0"(16바이트, null 종료 포함). 이렇게 길고 사람이 읽을 수 있는 문자열을 통째로 매직 바이트로 쓰는 경우도 있다.

### `file` 명령어는 어떻게 동작하는가
Linux/WSL의 `file` 명령어(그리고 Windows용 포팅 버전)는 내부적으로 **libmagic**이라는 라이브러리를 사용한다. libmagic은 `/usr/share/file/magic` 또는 컴파일된 매직 데이터베이스 파일에 "offset X에 이 바이트 패턴이 있으면 이 형식이다"라는 규칙 수천 개를 등록해두고, 파일을 열 때 이 규칙들을 순서대로 대조해서 일치하는 첫 규칙의 설명을 출력한다. 즉 `file`이 하는 일은 우리가 손으로 헥스에디터를 보며 매직 바이트를 확인하는 것을 자동화한 것뿐이다 — 원리를 알면 `file`이 왜 특정 결과를 내는지, 왜 가끔 `data`(어떤 규칙과도 안 맞음)라고만 나오는지 이해할 수 있다.

## 화면/코드에서 보이는 징후
- 헥스에디터로 파일을 열었는데 맨 앞이 `4D 5A`도 `7F 45 4C 46`도 아니고 알 수 없는 바이트로 시작함 — 헤더가 잘렸거나 의도적으로 손상되었을 가능성
- `file chall`을 실행했더니 `data`라고만 출력됨 — 알려진 시그니처와 일치하지 않는다는 뜻
- IDA/Ghidra/x64dbg에 파일을 로드하려 했더니 "Unknown format" 또는 "지원하지 않는 파일 형식" 오류가 뜸
- 파일 확장자를 바꿔서 열었는데도(`.txt` → `.exe`) 여전히 실행이 안 됨
- ZIP으로 알고 있던 파일을 압축 해제 프로그램에서 열었더니 "손상된 파일"이라고 나옴

## 가장 먼저 할 것
파일을 받으면 분석 도구에 넣기 전에 **`file` 명령어부터 돌리고, 결과가 애매하면 곧바로 헥스에디터로 첫 16~32바이트를 직접 확인**한다. 이 한 단계로 "어떤 도구로 열어야 하는지"가 대부분 결정된다.

## 단계별 절차

**1) `file` 명령어로 1차 판별**
```bash
file chall
# chall: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV) ...
```
결과가 명확하면 여기서 끝. `ELF`, `PE32`, `PE32+`, `Zip archive`, `PNG image data` 등으로 바로 나온다.

**2) `file`이 `data`라고만 답하면 헥스에디터로 직접 확인**

Windows에서는 HxD나 ImHex로 파일을 열고, Linux/WSL에서는 `xxd` 또는 `hexdump -C`로 첫 32바이트를 본다.
```bash
xxd -l 32 chall
```
출력된 첫 몇 바이트를 위의 표(MZ, ELF, PNG, ZIP 등)와 대조한다.

**3) 매직 바이트가 알려진 값과 다르면 "위장" 또는 "손상"을 의심**

CTF에서 흔한 트릭은 파일의 첫 몇 바이트를 일부러 지우거나 다른 값으로 덮어써서 `file`이나 로더가 형식을 인식하지 못하게 만드는 것이다. 이때는:
- 파일 뒷부분 구조(예: ELF라면 섹션 이름 문자열, PE라면 임포트 테이블의 API 이름 문자열)를 `strings` 명령어로 훑어서 어떤 형식의 흔적이 남아있는지 추정한다.
```bash
strings chall | head -30
```
- 흔적을 발견했다면(예: `.dynsym`, `GLIBC_2.2.5` 같은 ELF 특유의 문자열), 올바른 매직 바이트를 헥스에디터에서 직접 써 넣어 헤더를 복구해본다. 예를 들어 ELF로 추정되면 offset 0에 `7F 45 4C 46`을 채워 넣고, `file`로 다시 확인한다.
- 이 작업은 "손상된 헤더를 정상 상태로 복원해서 분석 도구가 파일을 인식하게 만드는 것"이 목적이며, CTF/포렌식에서 매우 흔한 초반 단계다. 헤더 하나만 고쳐도 IDA나 `readelf`가 파일 전체를 정상적으로 파싱하기 시작하는 경우가 많다.

**4) 형식이 확인되면 그에 맞는 전용 도구로 넘어간다**

- PE라면 PE-bear, Detect It Easy, IDA로.
- ELF라면 `readelf -h`, `objdump`, IDA/Ghidra로.
- ZIP 계열(APK/JAR/DOCX 등)이라면 `unzip -l`이나 압축 해제 후 내부 파일 구조 확인, APK라면 apktool/JADX로.

## 명령어/단축키
```bash
file <파일>                    # libmagic 기반 형식 판별
xxd -l 32 <파일>                # 첫 32바이트를 헥스로 출력
hexdump -C <파일> | head -2     # 위와 동일한 목적, 다른 도구
strings <파일> | head -30       # 형식을 짐작할 문자열 흔적 찾기
readelf -h <파일>               # ELF라면 헤더 상세 확인(EI_CLASS, EI_DATA 포함)
```
HxD(Windows): 파일을 열면 기본으로 맨 앞 offset `00000000`부터 보여준다. ImHex도 마찬가지이며, 우측 하단에서 원하는 offset으로 바로 이동(Ctrl+G류 Goto) 가능하다.

## 출력 해석
- `xxd -l 32 chall` 결과 첫 줄이 `7f45 4c46 0201 0100 ...`라면: offset 0에 `7F 45 4C 46`(ELF 매직) → offset 4에 `02`(64비트) → offset 5에 `01`(리틀엔디안)까지 한 줄에서 다 읽을 수 있다.
- `file`이 `PE32+ executable (console) x86-64`라고 답하면 → 64비트 PE, 콘솔 애플리케이션. `PE32`(플러스 없음)이면 32비트 PE.
- `file`이 `Zip archive data`라고만 답하고 `Microsoft Word`처럼 세부 종류를 못 맞히면 → ZIP이긴 한데 내부 구조(`[Content_Types].xml` 등)까지는 못 읽었다는 뜻이므로, 압축을 풀어서 내부를 직접 봐야 한다.
- 매직 바이트는 정상인데 그 뒤 필드 값이 터무니없이 크거나 이상하면(예: PE의 `e_lfanew`가 파일 크기보다 큰 값) → 헤더 일부가 의도적으로 조작된 것일 수 있으니 전체 구조를 더 의심해서 봐야 한다.

## 흔한 실수
- **확장자만 보고 형식을 단정하는 것.** `.jpg`로 되어 있어도 실제 내용은 ZIP일 수 있다(파일 안에 파일을 숨기는 스테가노그래피/폴리글랏 기법에서 흔함). 항상 매직 바이트로 재확인한다.
- **PE의 두 번째 시그니처 위치를 고정된 오프셋으로 착각하는 것.** `e_lfanew`는 파일마다 다른 값을 가질 수 있으므로, 항상 offset `0x3C`의 값을 먼저 읽고 그 위치로 이동해야 한다. "PE 시그니처는 항상 offset 0x80에 있다"처럼 외워서 적용하면 링커나 컴파일러가 다른 파일에서 틀릴 수 있다.
- **`CA FE BA BE`를 보고 무조건 Java .class라고 단정하는 것.** 위에서 설명했듯 Mach-O 팻 바이너리도 같은 매직을 쓴다. 다음 필드와 파일 전체 크기·구조를 반드시 같이 확인해야 한다.
- **매직 바이트 몇 개만 보고 형식 전체가 정상이라고 안심하는 것.** 매직 바이트는 "이 형식으로 시도해볼 가치가 있다"는 1차 신호일 뿐, 파일 전체가 손상 없이 올바르다는 보장은 아니다. 특히 CTF에서는 매직 바이트만 정상으로 고쳐두고 뒤쪽 구조를 일부러 망가뜨린 문제도 있다.
- **`file` 결과를 100% 신뢰하는 것.** libmagic의 규칙에 없는 커스텀/변형 포맷이거나, 매직 바이트가 의도적으로 위조된 경우 `file`도 틀린 답을 낼 수 있다. 의심스러우면 항상 헥스에디터로 직접 검증한다.

## 막혔을 때 다음 체크
- ELF의 EI_CLASS/EI_DATA까지는 확인했는데 정확히 x86인지 x64인지, 어떤 계산 규칙으로 구분하는지 헷갈리면 → [REV-0021](./rev-0021-x86-vs-x64.md)(x86 vs x64 구분법)로 이동.
- 매직 바이트 확인 후 헤더 전체 구조(섹션 vs 세그먼트, 헤더 뒤에 무엇이 오는지)가 궁금하면 → [REV-0029](./rev-0029-section-vs-segment.md)(섹션과 세그먼트)로 이동.
- 파일 형식 자체보다 "바이너리와 실행 파일이 전체적으로 어떻게 구성되는지"부터 다시 잡고 싶다면 → [REV-0019](./rev-0019-binary-basics.md)(바이너리와 실행 파일의 기본 구조)로 이동.
- 매직 바이트는 정상인데 그 다음부터 파싱이 실패한다면, 헤더의 다른 필드(예: PE의 `e_lfanew`, ELF의 `e_shoff`)가 조작되었을 가능성을 의심하고 해당 필드 전용 문서를 검색.

## 미니 예제
CTF에서 확장자가 없는 파일 `mystery`를 받았다고 하자.

```bash
$ file mystery
mystery: data
```
`file`이 아무것도 못 알아냈다. 헥스에디터 대신 커맨드라인으로 첫 16바이트를 본다.
```bash
$ xxd -l 16 mystery
00000000: 4d 5a 90 00 03 00 00 00  04 00 00 00 ff ff 0000  MZ..............
```
`4D 5A`로 시작한다 — DOS 헤더 시그니처("MZ")다. 그런데 `file`이 `data`라고만 답한 이유는, 아마 뒤쪽 PE 헤더 부분이 손상되었거나 `file`이 참조하는 매직 데이터베이스가 이 변형을 못 잡았기 때문일 수 있다. `e_lfanew`(offset `0x3C`)를 확인해보자.
```bash
$ xxd -s 0x3C -l 4 mystery
0000003c: 8000 0000                                       ....
```
리틀엔디안이므로 값은 `0x00000080`, 즉 offset `0x80`에 PE 시그니처가 있어야 한다.
```bash
$ xxd -s 0x80 -l 4 mystery
00000080: 0000 0000                                       ....
```
`50 45 00 00`이어야 할 자리가 전부 `00`으로 뭉개져 있다. **PE 시그니처가 의도적으로 지워진 것**이다. 이 4바이트를 헥스에디터(HxD)에서 `50 45 00 00`으로 되돌려 쓰면:
```bash
$ xxd -s 0x80 -l 4 mystery
00000080: 5045 0000                                       PE..
```
```bash
$ file mystery
mystery: PE32 executable (GUI) Intel 80386, for MS Windows
```
이제 `file`도, IDA도, PE-bear도 정상적으로 파일을 인식한다. 이렇게 **매직 바이트/시그니처 하나를 복구하는 것만으로 분석 도구 전체가 파일을 정상적으로 열게 되는 경우가 CTF에서 매우 흔하다.**

## 출처/검증
- PE 포맷의 `MZ`/`e_lfanew`/`PE\0\0` 구조: Microsoft PE Format 공식 문서(`IMAGE_DOS_HEADER`, `IMAGE_NT_HEADERS`) 기준 개념 설명 (2026-09-08 검증).
- ELF 매직 바이트 및 `EI_CLASS`/`EI_DATA` 필드: System V ABI / ELF 스펙(`e_ident` 배열 정의) 기준.
- PNG/JPEG/GIF/ZIP/gzip/PDF 등 각 포맷의 시그니처 값: 각 포맷 공식 스펙(PNG: ISO/IEC 15948, ZIP: PKWARE APPNOTE, gzip: RFC 1952) 및 `file`/libmagic 매직 데이터베이스 기준.
- Mach-O 매직 바이트 및 팻 바이너리 구조: Apple 공식 `<mach-o/loader.h>`, `<mach-o/fat.h>` 헤더 정의 기준.
