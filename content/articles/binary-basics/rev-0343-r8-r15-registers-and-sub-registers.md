## 한 줄 요약
`R8`~`R15`는 AMD64(x64)에서 새로 추가된 8개의 범용 레지스터로, x86 시절 3비트짜리 레지스터 필드로는 8개(0~7)까지만 지정할 수 있었던 인코딩 한계를 REX 프리픽스의 확장 비트(`REX.B`/`REX.X`/`REX.R`)로 넘어서서 만들어졌으며, 그래서 R8~R15는 32비트 크기로 접근할 때조차 반드시 REX 프리픽스가 붙는다는 점이 `EAX` 같은 기존 레지스터와의 결정적 차이다.

## 언제 검색해야 하나
- x64 디스어셈블리에서 `R8`, `R9`, ..., `R15`가 처음 등장했을 때 이 레지스터들의 정체와 유래가 궁금할 때
- `R8D`, `R9W`, `R12B`처럼 접미사가 붙은 이름이 왜 `EAX`/`AX`/`AL`과 다른 규칙을 따르는지 궁금할 때
- Windows x64(`RCX`/`RDX`/`R8`/`R9`)나 SysV x64(`RDI`/`RSI`/`RDX`/`RCX`/`R8`/`R9`) 호출 규약에서 왜 하필 `R8`/`R9`까지만 인자 레지스터로 쓰이는지 궁금할 때
- `syscall` 명령어 실행 후에 `RCX`, `R11` 값이 왜 바뀌어 있는지 이해하고 싶을 때
- 함수 프롤로그에서 `push r12`, `push r13`처럼 R8~R15 계열이 콜리 세이브로 백업되는 이유가 궁금할 때

## 핵심 개념

### 왜 새 레지스터가 필요했는가
x86(32비트)은 범용 레지스터가 8개(`EAX`~`EDI`)뿐이었다. 컴파일러는 함수 안의 여러 변수를 최대한 레지스터에 담아두고 싶어하는데, 8개로는 복잡한 함수에서 금방 부족해져서 지역 변수를 스택에 자꾸 내렸다 올렸다(spill/reload)하는 코드가 많아진다. AMD64를 설계할 때 레지스터 개수를 16개로 두 배 늘려서 이런 스필/리로드를 줄이고 성능을 높이는 것이 주요 목표 중 하나였다. 그렇게 새로 추가된 8개가 `R8`~`R15`다.

### 인코딩 문제 — 3비트로는 8개까지만 지정 가능
x86 명령어 인코딩에서 레지스터를 지정하는 필드(오피코드 안의 `reg` 필드, 또는 ModRM 바이트의 `reg`/`rm` 필드)는 **3비트**다. 3비트로 표현 가능한 값은 0~7, 즉 정확히 8개까지다. 그래서 8086부터 80386까지 범용 레지스터가 항상 8개(`AX`~`DI`, `EAX`~`EDI`)였던 것은 우연이 아니라 이 3비트 필드의 한계 때문이었다.

AMD64는 레지스터를 16개로 늘리면서 이 3비트 필드 자체를 건드리지 않고, 대신 **REX 프리픽스에 추가 비트를 하나씩 더 두어 3비트 필드를 4비트로 확장**하는 방식을 택했다. 즉 기존 명령어 인코딩과의 호환성을 유지하면서 주소 공간(레지스터 지정 공간)만 넓힌 것이다.

### REX 프리픽스 구조
REX 프리픽스는 명령어 맨 앞에 붙는 1바이트로, 상위 4비트는 항상 `0100`(이 패턴 자체가 "이건 REX 프리픽스다"라는 표시), 하위 4비트가 `W`, `R`, `X`, `B` 네 개의 플래그다.

```
0100 W R X B   (1바이트, 0x40~0x4F 범위)
```

- **W(Width)**: 1이면 오퍜랜드 크기를 64비트로 지정(`REX.W`가 켜진 경우가 흔히 보는 `0x48` 계열). 0이면 기본 32비트(또는 오퍼랜드 크기 접두사에 따라 16비트).
- **R(Reg extension)**: ModRM의 `reg` 필드(3비트)에 이 비트를 최상위 비트로 덧붙여 4비트로 확장. 목적지/소스 중 `reg` 필드로 지정되는 레지스터가 R8~R15 범위에 있을 때 1이 된다.
- **X(Index extension)**: SIB 바이트의 `index` 필드를 확장. 배열 인덱싱에 R8~R15를 인덱스 레지스터로 쓸 때 필요.
- **B(Base extension)**: ModRM의 `rm` 필드나 SIB의 `base` 필드, 또는 오피코드에 직접 포함된 레지스터 지정을 확장. 베이스 레지스터나 목적지 레지스터가 R8~R15일 때 1이 된다.

정리하면, 명령어 하나에서 최대 3개까지 레지스터 피연산자(reg, base, index)가 등장할 수 있는데, 그 각각이 R8~R15 범위인지 여부를 `R`/`B`/`X` 세 비트가 따로따로 표시하는 구조다.

### 왜 R8~R15는 32비트 접근에도 항상 REX가 필요한가
`EAX` 같은 기존 레지스터는 3비트 필드만으로 완전히 표현 가능하므로(`EAX`=000), REX 프리픽스 없이도 인코딩할 수 있다. 반면 `R8D`(R8의 32비트 서브 레지스터)는 애초에 3비트 필드로는 표현 불가능한 레지스터(8번, 4비트로는 1000)이므로, 32비트 연산이라 해도 반드시 `REX.R` 또는 `REX.B`(또는 `REX.X`) 비트가 세팅된 REX 프리픽스가 함께 와야 한다. 즉 "R8~R15는 항상 REX 프리픽스를 동반한다"는 규칙은 인코딩 공간의 근본적인 한계에서 나온 것이다.

### 서브 레지스터 이름 규칙 — 접미사만 사용
R8~R15는 8086 시절의 유산이 없는 완전히 새로운 레지스터이므로, 서브 레지스터 이름도 레거시 규칙(`AH`/`AL`처럼 접두사 없이 별도 이름)을 따르지 않고 REV-0342에서 정리한 것처럼 **번호 뒤에 접미사만 붙이는 규칙적인 방식**을 쓴다.

| 64비트 | 32비트 | 16비트 | 8비트 |
|---|---|---|---|
| R8  | R8D  | R8W  | R8B  |
| R9  | R9D  | R9W  | R9B  |
| R10 | R10D | R10W | R10B |
| R11 | R11D | R11W | R11B |
| R12 | R12D | R12W | R12B |
| R13 | R13D | R13W | R13B |
| R14 | R14D | R14W | R14B |
| R15 | R15D | R15W | R15B |

접미사 없음(64비트), `D`(Doubleword, 32비트), `W`(Word, 16비트), `B`(Byte, 8비트)가 전부이며, **상위 바이트를 가리키는 이름은 아예 존재하지 않는다**(`R8H` 같은 이름은 없다). 8비트 접근은 항상 하위 바이트 하나뿐이다.

### 호출 규약에서 R8~R15의 역할
- **정수 인자 전달**: SysV x64(Linux/macOS)는 정수/포인터 인자를 `RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9` 순서로 최대 6개까지 레지스터로 전달한다. Windows x64는 `RCX`, `RDX`, `R8`, `R9` 순서로 최대 4개까지 전달한다. 두 규약 모두 정확히 **여덟 번째(R8)와 아홉 번째(R9) 레지스터**에서 인자 전달이 끝난다는 점이 흥미로운 우연이다 — 인자 개수가 이보다 많으면 스택으로 넘어간다.
- **RAX 다음으로 소모되는 반환 관련 레지스터**: 함수가 128비트 값을 리턴할 때 `RAX`:`RDX` 조합을 쓰는 관례가 있지만, R8~R15가 리턴값 전달에 직접 관여하는 경우는 표준 정수 호출 규약에서는 없다.
- **`syscall` 명령어와 R11/RCX**: x64 리눅스에서 `syscall` 명령어를 실행하면, CPU가 하드웨어 레벨에서 현재 `RIP`(다음 명령어 주소)를 `RCX`에, `RFLAGS`를 `R11`에 자동으로 저장한 뒤 커널 모드로 진입한다. 그래서 시스템콜 직후 `RCX`와 `R11`은 **호출 전의 값이 보존되지 않는(clobbered) 레지스터**로 취급해야 한다. `syscall`의 인자 전달 자체는 `RDI`, `RSI`, `RDX`, `R10`, `R8`, `R9` 순서를 쓰는데(SysV 함수 호출 규약과 세 번째 인자부터 다르게 `RCX` 대신 `R10`을 쓰는 점에 주의 — `RCX`가 리턴 주소 저장에 쓰이기 때문이다), 이 부분은 REV-0077(SYSCALL)에서 더 자세히 다룬다.
- **콜리 세이브(callee-saved) 레지스터**: `R12`, `R13`, `R14`, `R15`는 SysV x64/Windows x64 모두 콜리 세이브로 지정되어 있다. 즉 이 레지스터들을 함수 안에서 실제로 사용한다면, 함수는 프롤로그에서 원래 값을 `push`로 백업하고 에필로그에서 `pop`으로 복원해야 한다(REV-0341 변형 3 참고). 반면 `R8`~`R11`은 콜러 세이브(caller-saved)로, 호출된 함수가 자유롭게 값을 덮어써도 되고 호출자가 필요하면 호출 전에 알아서 백업해야 한다.

## 화면/코드에서 보이는 징후
- 디스어셈블리 바이트 앞에 `4X` 계열(REX 프리픽스, `0x40`~`0x4F`)이 붙어 있고 오퍼랜드에 `R8`~`R15` 계열 이름이 등장 — x64 코드에서 신규 레지스터를 사용 중이라는 신호.
- 함수 프롤로그에 `push r12`, `push r13`처럼 R12~R15가 저장되는 코드 — 그 함수가 이 레지스터들을 실제로 사용하며 콜리 세이브 규약을 지키고 있다는 뜻(REV-0341 참고).
- 함수 진입부에서 4개 이상의 인자를 받는 코드에서 5번째, 6번째 인자가 `R8`, `R9`(SysV) 또는 3, 4번째 인자가 `R8`, `R9`(Windows)로 전달되는 패턴.
- `syscall` 명령어 직후 코드가 `R11`이나 `RCX`를 다시 설정하거나, 이 레지스터들을 값이 살아있다고 가정하지 않고 다시 로드하는 패턴.

## 가장 먼저 할 것
디스어셈블리에서 `R8`~`R15` 계열 이름을 만나면, 우선 그 레지스터가 **함수 인자로 쓰였는지(4~6번째 인자), 콜리 세이브 백업 대상인지(R12~R15가 프롤로그에서 push됨), 아니면 syscall 관련 특수 레지스터인지(R11)**부터 구분한다. 이 세 갈래로 나누면 대부분의 등장 맥락이 설명된다.

## 단계별 절차

**1) REX 프리픽스 존재로 x64 코드임을 먼저 확인**
```
바이트 열: 4D 89 C4       ; 4D = REX(W=1,R=1,X=0,B=1) 프리픽스
디스어셈블리: mov r12, r8   ; R8, R12 모두 R8~R15 범위라서 REX.R, REX.B 모두 필요
```

**2) 함수 인자 위치인지 확인 (SysV x64 기준)**
```asm
; void log_event(int a, int b, int c, int d, int e, int f)
mov     [rbp-4],  edi   ; a  (1번째, RDI)
mov     [rbp-8],  esi   ; b  (2번째, RSI)
mov     [rbp-0xc], edx  ; c  (3번째, RDX)
mov     [rbp-0x10], ecx ; d  (4번째, RCX)
mov     [rbp-0x14], r8d ; e  (5번째, R8D!)
mov     [rbp-0x18], r9d ; f  (6번째, R9D!)
```
5번째, 6번째 인자에서 `R8D`/`R9D`가 등장하면 SysV x64 함수 인자 전달 패턴이 맞다.

**3) 콜리 세이브 백업 패턴 확인**
```asm
push    r12          ; 프롤로그에서 백업
push    r13
...
pop     r13           ; 에필로그에서 역순 복원
pop     r12
```

**4) syscall 전후 R11/RCX 취급 확인**
```asm
mov     rax, 1          ; syscall 번호(write)
mov     rdi, 1
lea     rsi, [buf]
mov     rdx, len
syscall                  ; 이 시점에 RCX <- 리턴주소, R11 <- RFLAGS (하드웨어가 자동 설정)
; syscall 직후 코드에서 RCX, R11을 이전 값 그대로라고 가정하면 안 됨
```

## 명령어/단축키
```
(gdb) info registers          # x64면 rax~r15까지 16개 모두 표시
(gdb) p $r8
(gdb) p $r8d                  # gdb가 서브 레지스터 이름을 인식
```
IDA/Ghidra: 오퍼랜드의 `R8`~`R15` 위에서 우클릭 → 관련 교차 참조(cross-reference)로 그 레지스터가 함수 내에서 인자/백업/임시값 중 어느 용도로 쓰였는지 흐름을 따라갈 수 있다.

## 출력 해석
- 함수 진입 직후 `R8D`/`R9D`가 즉시 스택으로 spill되는 코드가 보이면, 이 함수는 5개 이상의 인자를 받는 함수라는 뜻이다(SysV 기준).
- 프롤로그에서 `push r12`가 있는데 에필로그에서 대응하는 `pop r12`가 없다면, 함수 경계 설정을 잘못 잡았거나 조기 리턴 경로(REV-0341 변형 7)에서 다른 방식으로 복원되고 있을 가능성을 의심해야 한다.
- `syscall` 명령어 실행 직후의 `R11` 값이 실행 전 값과 다르게 나온다면 정상이다. 이건 버그가 아니라 CPU가 `RFLAGS`를 자동 저장한 결과다.

## 흔한 실수
- `R8`~`R15`를 x86(32비트) 디스어셈블리에서 봤다고 착각하는 것 — 이 레지스터들은 x64에서만 존재하므로, 실제로 보인다면 아키텍처 판단 자체를 다시 점검해야 한다.
- `R8H` 같은 상위 바이트 이름이 존재할 거라 가정하는 것 — R8~R15에는 상위 바이트 이름이 없다.
- `R8`~`R11`(콜러 세이브)과 `R12`~`R15`(콜리 세이브)를 구분하지 않고 전부 "값이 함수 호출 후에도 보존된다"고 가정하는 것 — 실제로 보존되는 것은 `R12`~`R15`뿐이다.
- `syscall` 직후에도 `RCX`/`R11`이 이전 값 그대로일 거라 가정하고 디버깅하다가 값이 바뀐 이유를 못 찾아 헤매는 것.
- REX 프리픽스가 항상 64비트 연산(`REX.W=1`)을 의미한다고 착각하는 것 — REX 프리픽스는 R8~R15 사용만으로도 필요할 수 있으며, 이 경우 `REX.W`는 0일 수 있다(32비트 연산이지만 R8~R15를 참조).

## 막혔을 때 다음 체크
- `EAX`/`AX`/`AL`/`AH` 계열의 이름 규칙과 역사가 궁금하면 → REV-0342(레지스터 이름 규칙 EAX AX AL AH 관계)로 이동.
- 부분 쓰기 시 제로 익스텐션 등 실제 동작 규칙이 궁금하면 → REV-0022(32비트와 64비트 레지스터 차이)로 이동.
- 콜리 세이브 레지스터가 프롤로그/에필로그에서 어떻게 백업/복원되는지 더 자세히 보려면 → REV-0341(함수 프롤로그와 에필로그 자세히 읽기)로 이동.
- `syscall` 명령어 자체의 동작과 인자 전달 규약이 궁금하면 → REV-0077(SYSCALL)로 이동.

## 미니 예제
SysV x64에서 6개 인자를 받는 함수의 프롤로그를 보자.

```c
long compute(long a, long b, long c, long d, long e, long f) {
    return a + b + c + d + e + f;
}
```

```asm
compute:
    mov     [rsp-0x8],  rdi   ; a
    mov     [rsp-0x10], rsi   ; b
    mov     [rsp-0x18], rdx   ; c
    mov     [rsp-0x20], rcx   ; d
    mov     [rsp-0x28], r8    ; e  <- R8 등장
    mov     [rsp-0x30], r9    ; f  <- R9 등장
    mov     rax, [rsp-0x8]
    add     rax, [rsp-0x10]
    add     rax, [rsp-0x18]
    add     rax, [rsp-0x20]
    add     rax, [rsp-0x28]
    add     rax, [rsp-0x30]
    ret
```

인자가 4개까지였다면 `RDI`/`RSI`/`RDX`/`RCX`만으로 끝났겠지만, 5번째와 6번째 인자가 등장하면서 `R8`, `R9`가 나타났다. 이 코드에서 `mov [rsp-0x28], r8` 한 줄만 보고도 "이 함수는 인자가 최소 5개 이상이다"라는 사실을 바로 추론할 수 있다.

## 관련 글
- REV-0342 — 레지스터 이름 규칙 EAX AX AL AH 관계
- REV-0022 — 32비트와 64비트 레지스터 차이
- REV-0341 — 함수 프롤로그와 에필로그 자세히 읽기

## 출처/검증
- REX 프리픽스 구조(`W`/`R`/`X`/`B` 비트)와 R8~R15 인코딩 확장 방식: Intel 64 and IA-32 Architectures Software Developer's Manual, Volume 2, "REX Prefixes" 섹션 기준.
- R8~R15 신규 레지스터 도입 배경 및 성능 목표: AMD64 Architecture Programmer's Manual, Volume 1, "General-Purpose Registers" 섹션 기준.
- SysV x64 함수 인자 전달 순서(RDI/RSI/RDX/RCX/R8/R9) 및 콜러/콜리 세이브 레지스터 구분: System V AMD64 ABI 공식 스펙, "Parameter Passing" 및 "Register Usage" 섹션 기준.
- Windows x64 호출 규약(RCX/RDX/R8/R9): Microsoft x64 Calling Convention 공식 문서 기준.
- `syscall` 명령어가 RCX/R11을 자동으로 사용하는 동작 및 syscall 인자에서 R10을 쓰는 이유: Intel SDM Volume 2 "SYSCALL" 명령어 설명 및 Linux 커널 `x86-64 syscall` 관례(man 2 syscall, arch/x86 진입점 문서) 기준 (2026-09-09 검증).
