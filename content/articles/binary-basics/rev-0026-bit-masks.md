## 한 줄 요약
`AND` 연산에 `0xFF`, `0xFFFF`, `0xFFFFFF`, `0xFFFFFFFF` 같은 값을 쓰면 **원하는 하위 N비트만 남기고 나머지는 0으로 지우는 "마스크"** 역할을 하며, 각각 8/16/24/32비트에 대응한다.

## 언제 검색해야 하나
- 코드에 `and eax, 0FFh` 또는 `x & 0xFF` 같은 연산이 나오는데 왜 하는지 모를 때
- FNV 해시, 체크섬, 커스텀 인코딩 알고리즘에서 `& 0xFFFFFF`(24비트 마스크)처럼 낯선 크기의 마스크가 나올 때
- 특정 바이트만 뽑아내거나, 특정 크기로 값을 "잘라내는" 코드를 이해해야 할 때

## 핵심 개념
`AND` 연산은 두 비트가 모두 1일 때만 1이 되고, 하나라도 0이면 0이 된다. 이 성질을 이용하면 **특정 비트를 그대로 두고(마스크 비트=1), 나머지는 강제로 0으로 만드는(마스크 비트=0)** 필터를 만들 수 있다.

`x & 0xFF`를 예로 들면, `0xFF`는 이진수로 `1111 1111`(하위 8비트가 전부 1)이다. 이 값과 AND하면:
- 하위 8비트는 원래 값이 그대로 유지된다 (1 AND 아무값 = 아무값)
- 그 위의 비트들은 전부 0이 된다 (0 AND 아무값 = 0)

결과적으로 `x & 0xFF`는 "x의 최하위 1바이트만 남기고 나머지는 버려라"는 뜻이 된다. 이건 실제로 **정수를 특정 비트폭으로 자르는 연산**과 동일하다 — C에서 `(uint8_t)x`로 캐스팅하는 것과 결과가 같다.

**자주 쓰이는 마스크 표**:

| 마스크 | 이진수 | 의미 | 대응 타입 |
|---|---|---|---|
| `0xFF` | 8비트 전부 1 | 하위 1바이트만 남김 | `uint8_t` / `unsigned char` |
| `0xFFFF` | 16비트 전부 1 | 하위 2바이트만 남김 | `uint16_t` / `unsigned short` |
| `0xFFFFFF` | 24비트 전부 1 | 하위 3바이트만 남김 | 24비트 값 (RGB 색상, 일부 해시 등에서 사용) |
| `0xFFFFFFFF` | 32비트 전부 1 | 하위 4바이트만 남김 | `uint32_t` / `unsigned int` |
| `0xFFFFFFFFFFFFFFFF` | 64비트 전부 1 | 하위 8바이트만 남김 | `uint64_t` / `unsigned long long` |

패턴은 간단하다: **N비트 마스크는 16진수로 `F`가 N/4개 연속된 값**이다 (F 하나가 4비트를 나타내므로).

## 화면/코드에서 보이는 징후
- 어셈블리에서 `and eax, 0FFh` 또는 `movzx eax, al` (al만 쓰고 상위 비트는 자동으로 0이 됨, 결과적으로 마스크와 유사한 효과)
- 디컴파일된 C 코드에서 `x & 0xFF`, `x & 0xFFFFFF`, `(uint8_t)x` 같은 캐스팅
- FNV-1a 해시처럼 `hash & 0xFFFFFFFF`로 32비트로 값을 유지하는 루프

## 가장 먼저 할 것
마스크 값을 보면 먼저 **16진수 F의 개수를 세서 몇 비트를 남기는지 파악**한다. `0xFFFFFF`라면 F가 6개이므로 24비트(3바이트)를 남긴다는 뜻이다.

## 단계별 절차

**1) 마스크의 비트폭 확인**
```python
>>> mask = 0xFFFFFF
>>> bin(mask)
'0b111111111111111111111111'   # 1이 24개 = 24비트 마스크
>>> mask.bit_length()
24
```

**2) 실제로 어떤 값이 살아남는지 계산**
```python
>>> x = 0x12345678
>>> x & 0xFF          # 하위 1바이트
0x78
>>> x & 0xFFFF         # 하위 2바이트
0x5678
>>> x & 0xFFFFFF       # 하위 3바이트
0x345678
>>> x & 0xFFFFFFFF     # 하위 4바이트(변화 없음, 이미 32비트라서)
0x12345678
```
이 예시로 마스크의 동작 원리가 명확해진다: 항상 **오른쪽(하위, LSB 방향)부터** 비트를 유지한다.

**3) IDA/Ghidra 디스어셈블리에서 발견 시 대응**

`and eax, 0FFFFFFh`처럼 보이면, "이 연산 이후 값은 항상 0~16777215(0xFFFFFF) 범위 안에 있다"고 해석하면 된다. 이후 이 값이 어떤 조건과 비교되는지, 반복문에서 어떻게 쓰이는지를 보면 알고리즘의 성격(체크섬, 해시, 색상값 등)을 짐작할 수 있다.

**4) 24비트 마스크를 봤을 때 특히 주의**

24비트(`0xFFFFFF`)는 흔한 정수 타입(8/16/32/64)이 아니라서 등장하면 특별한 의미가 있는 경우가 많다: RGB 색상(빨강8+초록8+파랑8), 또는 FNV류 해시에서 곱셈 후 특정 비트만 남기는 커스텀 로직. 이 값을 보면 "표준 정수 타입이 아니라 의도적으로 3바이트만 쓰는 알고리즘이구나"라고 생각하고 주변 상수(예: `16777619` = FNV prime)를 함께 확인한다.

## 명령어/단축키
```python
# 파이썬에서 N비트 마스크 만들기
def mask(bits):
    return (1 << bits) - 1

mask(8)   # 0xFF
mask(16)  # 0xFFFF
mask(24)  # 0xFFFFFF
mask(32)  # 0xFFFFFFFF
```

## 출력 해석
- `x & 0xFF`의 결과는 항상 0~255 범위다.
- `x & 0xFFFF`의 결과는 항상 0~65535 범위다.
- 마스크 연산 뒤에 오는 값의 최댓값을 보면 "이 변수는 몇 비트짜리로 취급되고 있는가"를 바로 알 수 있다 — 이는 오버플로/랩어라운드를 의도적으로 구현한 코드에서 특히 중요하다.

## 흔한 실수
- 마스크를 "그냥 어떤 상수와 AND하는 이상한 연산"으로 넘겨버리고 그 의미(비트폭 제한)를 놓치는 것
- `0xFFFFFF`를 32비트 마스크로 착각하는 것 — F가 6개면 24비트, 8개여야 32비트다. 항상 세어봐야 한다.
- 마스크와 비교값을 혼동하는 것 — `x & 0xFF == 0x41`은 "x의 하위 1바이트가 0x41('A')인가"를 묻는 것이지, x 전체가 0x41이라는 뜻이 아니다.

## 막혔을 때 다음 체크
- 마스크를 건 뒤 값이 여전히 이상하게 크거나 음수로 보인다면 → REV-0024(2의 보수)로 돌아가서 signed/unsigned 해석을 다시 확인.
- `16777619`같은 특정 상수와 함께 24비트/32비트 마스크가 반복 등장한다면 → REV-0208(FNV 상수 의심)로 이동.
- 마스크가 루프 안에서 매 반복 적용된다면 → 오버플로를 의도적으로 재현하는 알고리즘(체크섬/해시)일 가능성이 높다.

## 미니 예제
FNV-1a 해시의 전형적인 파이썬 구현에서 마스크가 어떻게 쓰이는지 보자:
```python
def fnv1a_32(data: bytes) -> int:
    h = 0x811C9DC5                  # FNV offset basis
    for b in data:
        h ^= b
        h = (h * 0x01000193) & 0xFFFFFFFF   # <- 32비트 마스크로 오버플로 재현
    return h
```
파이썬 정수는 자동으로 커지기 때문에, C의 `uint32_t` 곱셈에서 자연스럽게 일어나는 오버플로(상위 비트 버림)를 흉내 내려면 매 연산 후 `& 0xFFFFFFFF`를 명시적으로 걸어야 한다. 이것이 마스크가 리버싱/CTF 스크립트에서 가장 자주 쓰이는 이유다.
