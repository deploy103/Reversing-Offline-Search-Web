## 한 줄 요약
배열 접근 어셈블리에서 인덱스 계산이 예상과 다르게 보인다면, 대부분 **원소 크기를 곱하는 스케일(scale) 값**을 빼먹고 계산했거나, 인덱스 변수가 signed라서 **음수 인덱스가 그대로 허용**되는 경우이며, 두 원인 모두 인덱스 변수의 실제 타입과 배열 원소 크기를 정확히 확인하면 해결된다.

## 언제 검색해야 하나
- 배열 접근 어셈블리에서 인덱스에 왜 4, 8, 12, 16 같은 숫자가 곱해지는지 헷갈릴 때
- `[rax + rcx*4 + 0x10]` 같은 SIB(Scale-Index-Base) 형태 주소 계산이 손으로 한 계산과 안 맞을 때
- 배열 인덱스에 음수를 넣었는데도 프로그램이 크래시하지 않고 이상한 메모리를 읽어서 계속 동작할 때
- `movsxd`/`movsx`/`movzx`가 인덱스 레지스터 앞에 왜 붙어 있는지 궁금할 때

## 핵심 개념
`array[i]`라는 C 코드는 어셈블리에서 절대 `array + i`로 바로 계산되지 않는다. 배열의 각 원소가 차지하는 바이트 크기(원소 크기, element size)만큼 인덱스에 **곱셈**을 해야 올바른 주소가 나온다.

**기본 공식**: `주소 = 배열_시작주소 + i * sizeof(원소타입)`

**구체적 예시**: `int arr[10]`이 있고 `arr[3]`에 접근한다고 하자. `int`는 4바이트이므로 실제 주소는 `배열_시작 + 3 * 4 = 배열_시작 + 12`다. 어셈블리에서는 다음처럼 나타난다.
```asm
mov     eax, [rdi + rcx*4]   ; rcx = 인덱스(i), 4 = sizeof(int)
```
여기서 `rcx*4`가 바로 "인덱스 곱하기 원소 크기"이며, x86/x64의 SIB(Scale-Index-Base) 주소 지정 방식은 스케일 값으로 **1, 2, 4, 8만** 지원한다. 만약 원소 크기가 그 외의 값(예: 구조체 배열처럼 24바이트)이라면, CPU가 한 번에 곱할 수 없으므로 컴파일러는 별도의 `imul`이나 `lea` 조합으로 곱셈을 미리 계산한 뒤 더한다.
```asm
imul    rcx, rcx, 24      ; i * 24 (구조체 크기)
add     rax, rcx          ; 배열_시작 + i*24
```

**인덱스의 부호 확장 문제**: 인덱스 변수가 32비트(`int i`)이고 배열 접근 주소 계산은 64비트로 이뤄지는 x64 환경에서는, 컴파일러가 인덱스를 64비트로 확장하는 명령어를 반드시 끼워 넣는다.
- 인덱스가 `int`(signed)면 `movsxd rcx, ecx`(부호 확장) — 인덱스가 음수면 상위 32비트도 전부 1로 채워져서, 곱셈 후에도 "배열보다 앞쪽의 메모리"를 가리키는 매우 큰(또는 음수인) 오프셋이 그대로 유지된다.
- 인덱스가 `unsigned int`나 `size_t`면 `mov ecx, ecx`(상위 32비트를 0으로 자동 클리어, x64의 특성) — 음수라는 개념 자체가 없으므로 어떤 값을 넣어도 항상 "배열 뒤쪽의 아주 먼 메모리"를 가리키는 큰 양수 오프셋이 된다.

**왜 음수 인덱스가 위험한가**: `int i = -1`을 32비트 인덱스로 쓰면 `arr[-1]`은 배열 시작 바로 앞의 4바이트(다른 변수나 메타데이터일 수 있음)를 가리킨다. 경계 검사가 `if (i >= 0 && i < len)`처럼 제대로 돼 있으면 막히지만, `if (i < len)`처럼 하한 검사가 빠져 있으면 음수 인덱스로 배열 앞쪽 메모리를 임의로 읽거나 쓸 수 있는 취약점이 된다.

## 화면/코드에서 보이는 징후
- 디스어셈블리에서 `imul reg, reg, N`(N이 4, 8, 12, 16, 24 등) 직후 배열 베이스 주소에 더하는 패턴
- `[base + index*scale + disp]` 형태의 SIB 주소 지정에서 `scale`이 1/2/4/8 중 하나
- 인덱스 레지스터 앞에 `movsxd`(signed 확장) 또는 단순 32비트 대입(unsigned, 상위 비트 자동 클리어)이 붙어 있는 경우
- 경계 검사 코드에 `if (idx < len)`만 있고 `idx >= 0` 체크가 없는 경우

## 가장 먼저 할 것
문제의 배열 접근에서 곱해지는 스케일 값(4, 8, 24 등)이 그 배열 원소 타입의 실제 `sizeof`와 일치하는지부터 확인한다. 그다음 인덱스 변수가 signed인지 unsigned인지, 그리고 확장 명령어가 `movsxd`인지 단순 클리어인지 확인한다.

## 단계별 절차

**1) 스케일 값으로 원소 크기 역산**
`rcx*4`가 보이면 원소는 4바이트(`int`, `float`, 포인터가 아닌 32비트 계열), `rcx*8`이면 8바이트(`double`, 64비트 포인터, `long`)다. 스케일 없이 `imul reg, reg, N`이 별도로 있다면 N이 곧 구조체/배열 원소의 전체 크기(`sizeof`)다.

**2) 인덱스 확장 명령어로 signed/unsigned 판단**
`movsxd rcx, ecx`가 보이면 인덱스는 signed(`int`)로 선언된 것이고 음수 인덱스가 이론적으로 가능하다. 단순히 32비트 레지스터에만 값을 넣고 그대로 64비트 연산에 쓰는 경우(x64에서 32비트 결과는 자동으로 상위를 0으로 채움)라면 unsigned로 다뤄지고 있다는 뜻이다.

**3) 경계 검사 코드 앞뒤로 하한/상한 둘 다 확인**
인덱스를 쓰는 지점 앞에 있는 조건문을 찾아서 상한(`idx < len`)만 있는지, 하한(`idx >= 0`)도 있는지 확인한다. signed 인덱스인데 하한 검사가 없다면 음수 인덱스 취약점 후보다.

**4) 실제 주소를 손으로 재계산해서 검증**
배열 시작 주소, 인덱스 값, 원소 크기를 직접 대입해 `배열_시작 + i * size`를 계산하고, 디버거에서 그 주소의 값을 확인해 어셈블리 결과와 일치하는지 검증한다.

## 명령어/단축키
```text
어셈블리: [base + index*scale + disp]   ; scale은 1/2/4/8만 가능
어셈블리: imul reg, reg, N               ; scale 4/8로 표현 불가능한 원소 크기(N)일 때
어셈블리: movsxd reg64, reg32            ; signed 32비트 인덱스를 64비트로 부호 확장
GDB:    x/4xg (addr)                    ; 계산된 주소 주변 메모리를 8바이트씩 확인
IDA:    배열 변수 위 Ctrl+X               ; 이 배열이 접근되는 모든 위치 확인
```

## 출력 해석
- `imul rcx, rcx, 24` 다음에 배열 베이스와 더해진다면, 이 배열의 원소는 24바이트(예: 8+4+4바이트 필드를 가진 구조체에 4바이트 패딩이 더해진 형태 등)라는 뜻이다. REV-0377에서 다룬 구조체 패딩과 함께 보면 왜 24바이트가 나왔는지 설명된다.
- `movsxd`가 보이는데 실제로 이 인덱스에 음수가 들어갈 수 있는 경로가 있다면, 그건 설계 실수이거나 의도적으로 파고들 수 있는 취약점이다.

## 흔한 실수
- SIB 주소의 스케일이 항상 1이라고 가정하고 `index*4`, `index*8`을 그냥 "index에 이상한 숫자가 곱해졌다"고 오해하는 것.
- 구조체 배열처럼 원소 크기가 4/8이 아닌 경우, 스케일만 찾다가 별도로 존재하는 `imul` 명령어를 놓치는 것.
- 인덱스가 signed인지 unsigned인지 확인하지 않고 "인덱스는 항상 0 이상"이라고 가정해서 하한 검사 누락을 놓치는 것.
- x64에서 32비트 레지스터에 값을 쓰면 상위 32비트가 자동으로 0이 된다는 규칙(REV-0381 참고)을 모르고 unsigned 인덱스 확장 과정을 혼란스러워하는 것.

## 막혔을 때 다음 체크
- 배열 접근이 어셈블리로 변환되는 기본 패턴 자체가 더 필요하면 REV-0034 문서로 이동.
- 인덱스 변수의 부호 확장/제로 확장 규칙이 헷갈리면 REV-0025 문서로 이동.
- 32비트 레지스터 연산 후 64비트 상위 비트가 어떻게 되는지 궁금하면 REV-0381 문서로 이동.
- 구조체 원소 크기(패딩 포함)가 왜 그렇게 계산됐는지 궁금하면 REV-0377 문서로 이동.

## 미니 예제
다음 C 코드와 어셈블리를 비교해보자.
```c
int get_item(int *arr, int idx) {
    return arr[idx];
}
```
```asm
movsxd  rax, esi          ; idx(esi, 32비트 signed)를 64비트로 부호 확장
mov     eax, [rdi+rax*4]  ; arr + idx*4 (int는 4바이트)
ret
```
`idx = -1`을 넣으면 `movsxd`가 `rax = 0xFFFFFFFFFFFFFFFF`(64비트 -1)로 만들고, `rax*4 = 0xFFFFFFFFFFFFFFFC`(64비트 -4)가 되어 결과 주소는 `arr - 4`, 즉 배열 바로 앞의 4바이트를 읽는다. 호출하는 쪽에서 `idx >= 0`을 검사하지 않았다면 이 함수는 배열 앞쪽 임의 메모리를 읽어주는 통로가 된다.
