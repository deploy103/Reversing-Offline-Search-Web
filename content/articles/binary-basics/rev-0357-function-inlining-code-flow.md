## 한 줄 요약
함수 인라이닝(inlining)은 컴파일러가 `CALL`/`RET` 오버헤드를 없애기 위해 짧은 함수의 본문 코드를 호출 지점에 그대로 복사해 넣는 최적화로, 그 결과 원본 소스에는 분명히 존재하던 함수가 디스어셈블리에서는 독립된 함수로 보이지 않고 여러 호출자 함수 안에 흩어져 반복된 코드 조각으로만 남는다.

## 언제 검색해야 하나
- 소스 코드나 헤더 파일에 분명히 선언된 함수인데, IDA/Ghidra의 Functions 창이나 Xref 목록에서 그 함수를 호출하는 `call`을 하나도 찾을 수 없을 때
- 짧고 단순한 계산(곱셈, 비교, getter/setter류)이 여러 함수 안에 똑같이 반복되어 나타날 때
- 헤더 파일에서 `static inline`, `__forceinline`, `__attribute__((always_inline))`으로 선언된 함수를 찾다가, 그 함수가 실제 바이너리에는 독립적으로 존재하지 않는 것을 발견했을 때
- 디버거로 특정 함수 이름에 브레이크포인트를 걸려고 했는데 심볼이 아예 없거나 그 함수에 걸리지 않을 때(인라인되어 사라졌기 때문일 수 있음)
- 바이너리 크기가 소스 코드의 함수 개수에 비해 함수 개수(심볼 테이블 기준)가 훨씬 적어 보일 때

## 핵심 개념

### 인라이닝이 하는 일
일반적인 함수 호출은 `CALL`(리턴 주소 push + 점프), 함수 프롤로그/에필로그(REV-0031), `RET`(리턴 주소 pop + 점프)까지 여러 단계의 오버헤드가 있다. 함수 본문이 아주 짧다면(예: 한두 줄짜리 계산), 이 오버헤드가 실제 계산보다 더 클 수도 있다. 그래서 컴파일러는 컴파일 시점에 해당 함수의 **본문 코드를 호출 지점에 그대로 복사해서 붙여넣고, `CALL` 자체를 아예 없애버린다.** 이를 인라인 확장(inline expansion)이라 부른다.

```c
static int square(int x) { return x * x; }

int compute(int a, int b) {
    return square(a) + square(b);
}
```

`-O0`(최적화 없음)으로 컴파일하면 `square`가 독립 함수로 남아 두 번 `call`된다.
```asm
; -O0
compute:
    push    rbp
    mov     rbp, rsp
    mov     edi, [rbp+arg_a]
    call    square           ; square(a)
    mov     [rbp-4], eax
    mov     edi, [rbp+arg_b]
    call    square           ; square(b)
    add     eax, [rbp-4]
    pop     rbp
    ret

square:
    push    rbp
    mov     rbp, rsp
    mov     eax, [rbp+arg_x]
    imul    eax, eax
    pop     rbp
    ret
```

`-O2`로 컴파일하면 `square`는 바이너리 어디에도 독립 함수로 존재하지 않고, `compute` 안에 두 번의 `imul`로 흡수된다.
```asm
; -O2
compute:
    mov     eax, edi
    imul    eax, edi         ; square(a)가 통째로 여기 흡수됨
    mov     ecx, esi
    imul    ecx, esi          ; square(b)도 마찬가지
    add     eax, ecx
    ret
```

`square`를 다른 어떤 함수도 별도로 호출하지 않는다면, 링커는 이 함수의 코드 자체를 최종 바이너리에서 완전히 제거해버릴 수도 있다(`square`의 심볼조차 남지 않음).

### 코드 흐름에 미치는 실질적 영향
1. **함수 경계가 사라진다** — 원본 소스의 함수 단위가 바이너리 레벨에서는 더 이상 명확한 경계로 존재하지 않는다. `compute` 하나를 분석해도 그 안에 `square`의 로직이 두 벌 섞여 있다는 사실을 스스로 알아채야 한다.
2. **같은 코드가 여러 번 복제된다** — `square`가 100개의 호출 지점에서 인라인되면, 사실상 같은 로직이 100군데에 복사되어 바이너리 크기가 커진다(코드 크기와 실행 속도의 트레이드오프).
3. **콜스택 깊이가 줄어든다** — 디버거로 `bt`(backtrace)를 봤을 때 원래대로라면 `compute → square`로 두 단계였을 콜스택이, 인라이닝 후에는 `compute` 한 단계로만 보인다. 크래시 지점을 추적할 때 "이 함수가 이 로직을 직접 갖고 있다"고 착각하기 쉽다.
4. **디버깅 브레이크포인트가 걸리지 않는다** — 디버그 심볼이 있어도 인라인된 함수 이름으로 브레이크포인트를 걸면 실제로 그 코드가 실행되는 시점에 멈추지 않을 수 있다(컴파일러/디버거 조합에 따라 디버그 정보에 인라인 위치가 기록되어 있어 걸리는 경우도 있다).

### 인라이닝을 유도/강제하는 소스 코드 신호
- C99/C11: `static inline` — 컴파일러에게 인라이닝을 "제안"하지만 강제하지는 않는다. 컴파일러가 함수가 너무 크거나 재귀적이면 무시할 수 있다.
- MSVC: `__forceinline` — 컴파일러에게 인라이닝을 강하게 요구한다(그래도 절대적 보장은 아니다).
- GCC/Clang: `__attribute__((always_inline))` — 마찬가지로 강한 요청.
- 최적화 옵션(`-O2`, `-O3`, `/O2`)이 켜지면, `inline` 키워드가 없는 일반 `static` 함수도 컴파일러 판단에 따라 자동으로 인라인될 수 있다. 이것이 바로 리버싱 대상에서 인라이닝이 흔한 이유다 — 소스에 `inline`이라는 단어가 전혀 없어도, 짧고 호출 빈도가 높은 `static` 함수는 최적화러가 알아서 인라인해버린다.

### 인라이닝과 함수 크기의 관계 — 반대 방향(Outlining)도 있다
매우 큰 함수를 여러 번 호출하는 대신, 컴파일러가 오히려 반복되는 코드 조각을 별도 함수로 "밖으로 빼내는(outlining)" 최적화도 존재한다(공통 부분식 추출, ICF 등). 이 경우 소스에는 없던 `sub_XXXXXX` 같은 함수가 바이너리에만 새로 생기기도 한다. 인라이닝의 정반대 현상이지만 같은 최적화 파이프라인의 일부로 이해하면 된다.

## 화면/코드에서 보이는 징후
- IDA/Ghidra Functions 창에 소스에 있었을 법한 함수 이름이 없거나, 있어도 그 함수를 부르는 `call`이 Xref에 전혀 없음
- 매우 짧고 유사한 계산 블록(`imul`, `cmp`+`setcc`, 필드 접근 등)이 여러 함수 안에서 거의 동일하게 반복
- 디컴파일러(IDA F5, Ghidra Decompile)의 결과에 헬퍼 함수 호출이 안 보이고, 그 계산이 호출자 함수의 리턴 표현식에 직접 펼쳐져 있음
- 디버거에서 함수 이름으로 브레이크포인트를 걸었는데 실행이 멈추지 않거나, 걸리더라도 콜스택 깊이가 예상보다 한 단계 얕음
- 헤더 파일에 `static inline`/`__forceinline`으로 선언된 함수가 정의되어 있지만 바이너리의 심볼 테이블에는 없음

## 가장 먼저 할 것
소스나 헤더에서 찾던 함수가 바이너리에 안 보이면, 먼저 그 함수를 호출했을 만한 인근 함수(호출자로 추정되는 함수)를 열어 비슷한 계산 패턴이 그 안에 그대로 섞여 있는지 확인한다. 짧은 산술/비교/필드 접근 몇 줄이 함수 시작이나 리턴 직전에 몰려 있다면 인라인된 흔적일 가능성이 높다.

## 단계별 절차

**1) 사라진 함수의 예상 동작(계산 패턴) 정리**

소스나 헤더에서 그 함수의 로직(예: `x*x`, `a>b?a:b`)을 확인하고, 이 로직이 어셈블리로 어떻게 나타날지 미리 예상한다(REV-0037의 최적화 패턴 참고).

**2) 예상 호출자 후보 함수들을 열어 패턴 검색**

그 함수를 호출했을 만한 상위 함수를 열어, 예상한 계산 패턴과 일치하는 짧은 명령어 블록이 있는지 눈으로 훑거나, IDA 텍스트 검색(`Alt+T`)으로 특징적인 명령어 시퀀스를 찾는다.

**3) 여러 호출 지점에서 같은 패턴이 반복되는지 확인**

동일한 계산 블록이 서로 다른 함수 여러 곳에서 발견되면, 이는 하나의 공통 함수가 여러 곳에 인라인된 강력한 증거다.

**4) 함수에 이름을 붙여 문서화**

인라인된 것으로 확인되면, IDA/Ghidra에서 그 코드 블록에 주석을 남기거나 "가상 함수 이름"으로 라벨을 달아 다음에 다시 볼 때 빠르게 알아볼 수 있게 한다(실제로 함수로 분리되지는 않지만, 분석 기록으로서 유용하다).

**5) 디버거로 계산 결과를 검증**

여러 입력값에 대해 그 코드 블록 직후의 레지스터 값을 관찰해서, 예상한 로직(예: 제곱, min/max)과 실제 동작이 일치하는지 실험적으로 확인한다.

## 명령어/단축키
```bash
gcc -O0 -S -o out_O0.s src.c    # 인라인 안 된 버전(비교 기준)
gcc -O2 -S -o out_O2.s src.c    # 인라인 최적화가 적용된 버전
diff out_O0.s out_O2.s           # 어떤 함수가 사라지고 어디로 흡수됐는지 비교
```
IDA: `Ctrl+X`(Xref to)로 특정 함수를 호출하는 곳이 정말 없는지 확인. Ghidra: Decompile 창에서 함수 크기가 비정상적으로 커 보이면 인라이닝 의심.

## 출력 해석
- Xref to 결과가 완전히 비어 있는 함수는 (1) 인라인되어 모든 호출이 흡수됐거나, (2) 아예 죽은 코드(사용되지 않아 제거됨)이거나, (3) 익스포트되어 외부에서만 호출되는 함수일 수 있다 — 심볼 테이블과 export 목록도 함께 확인해야 정확히 구분된다.
- 여러 함수에서 완전히 동일한 명령어 시퀀스가 반복된다면 인라이닝일 가능성이 매우 높지만, 우연히 비슷한 로직을 각 함수가 독립적으로 작성했을 가능성도 이론적으로는 있다 — 소스 코드가 있다면 대조하는 것이 가장 확실하다.
- 디버그 정보(DWARF, PDB)가 남아있는 빌드는 인라인된 함수의 원래 위치/이름을 `.debug_line`이나 PDB의 inline site 정보로 추적할 수 있는 경우가 있다(모든 빌드가 이 정보를 보존하지는 않는다).

## 흔한 실수
- 함수가 안 보인다고 "컴파일이 잘못됐다"거나 "함수가 삭제된 버그"로 오해하는 것 — 대부분은 정상적인 인라이닝이다.
- 인라인된 코드 조각을 처음부터 새로운 로직으로 오해해서 중복 분석하는 것 — 같은 패턴이 반복되면 먼저 "이미 분석한 다른 함수의 인라인 흔적 아닌가"를 의심하면 시간을 아낄 수 있다.
- `static inline` 키워드가 소스에 있다고 해서 반드시 인라인된다고 단정하는 것, 반대로 키워드가 없다고 인라인이 절대 안 됐을 거라 단정하는 것 — 둘 다 컴파일러의 최종 판단(함수 크기, 호출 빈도, 최적화 레벨)에 달려 있어 키워드는 힌트일 뿐이다.
- 재귀 함수나 매우 큰 함수도 인라인될 수 있다고 착각하는 것 — 재귀 함수는 일반적으로 인라인되지 않으며(무한 확장 위험), 함수 크기가 크면 컴파일러가 코드 크기 증가를 우려해 인라인을 포기하는 경우가 많다.

## 막혔을 때 다음 체크
- 인라이닝 외에 컴파일러 최적화가 만드는 다른 이상한 패턴(루프 언롤링, CMOV 등)이 궁금하면 → REV-0037 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 이유
- `CALL`이 진짜 하나도 없는 함수를 만나 당황스럽다면 → REV-0495 인라인된 함수 때문에 CALL이 하나도 없는 함수를 만났을 때
- 비슷한 코드가 여러 함수에서 반복되는데 인라이닝이 아니라 다른 이유(함수 복제, 템플릿 특수화 등)인지 궁금하면 → REV-0466 함수가 여러 번 복제된 것처럼 보이는 이유(Function Cloning)
- Debug 빌드와 Release 빌드에서 인라이닝 여부 자체가 다른 이유가 궁금하면 → REV-0361 Debug 빌드와 Release 빌드의 어셈블리 차이
- 함수 호출/리턴의 기본 스택 동작이 헷갈리면 → REV-0031 스택 프레임이 무엇인지

## 미니 예제
경계값 처리를 하는 작은 헬퍼 함수가 여러 곳에서 쓰이는 경우를 보자.

```c
static inline int clamp01(int x) {
    if (x < 0) return 0;
    if (x > 1) return 1;
    return x;
}

int normalize(int a, int b) {
    return clamp01(a) + clamp01(b);
}
```

`-O0` 빌드에서는 `clamp01`이 독립 함수로 두 번 호출된다.
```asm
normalize:
    mov     edi, [a]
    call    clamp01
    mov     [tmp], eax
    mov     edi, [b]
    call    clamp01
    add     eax, [tmp]
    ret
```

`-O2` 빌드에서는 `clamp01`의 두 `if`가 인라인되어 `normalize` 안에서 CMOV 체인으로 압축된다.
```asm
normalize:
    xor     eax, eax
    cmp     edi, 1
    mov     ecx, 1
    cmovle  ecx, edi
    cmovs   ecx, eax          ; clamp01(a)의 결과가 ecx에
    cmp     esi, 1
    mov     edx, 1
    cmovle  edx, esi
    cmovs   edx, eax           ; clamp01(b)의 결과가 edx에
    lea     eax, [ecx+edx]
    ret
```

이 `-O2` 결과만 보면 `clamp01`이라는 함수가 존재했다는 사실을 전혀 알 수 없다 — `cmp`/`cmovle`/`cmovs` 조합이 두 번 반복되는 패턴을 보고 "같은 헬퍼 함수가 두 번 인라인된 것 같다"고 추론해야 한다. 소스 코드나 헤더가 있다면 이 추론을 즉시 확인할 수 있지만, 블랙박스 바이너리만 있다면 패턴 반복과 계산 결과 관찰(디버거)로 검증해야 한다.
