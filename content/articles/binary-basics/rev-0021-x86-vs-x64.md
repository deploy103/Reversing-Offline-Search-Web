## 한 줄 요약
파일이 x86(32비트)인지 x64(64비트)인지는 추측하지 말고, PE는 COFF 헤더의 `Machine` 필드(`0x14C`=x86, `0x8664`=x64)를, ELF는 `e_ident[EI_CLASS]`(1=32비트, 2=64비트)와 `e_machine`(3=x86, 0x3E=x64)을 직접 읽어서 확인한다.

## 언제 검색해야 하나
- IDA나 Ghidra에 파일을 로드하기 전에, 혹은 로드했는데 디스어셈블리가 전부 쓰레기값처럼 나올 때
- `file` 명령어나 헥스 에디터로 받은 바이너리인데 32비트/64비트 여부를 빨리 확인하고 싶을 때
- 어셈블리 코드에 `RAX`, `R8`, `R13` 같은 레지스터가 보이는데 이게 무슨 뜻인지 헷갈릴 때
- x64dbg를 열었는데 x32dbg를 썼어야 했다는 걸 뒤늦게 깨달았을 때

## 핵심 개념
x86과 x64는 같은 인텔/AMD 계열 CPU 명령어 집합(ISA)의 32비트 버전과 64비트 버전을 가리키는 말이다. 겉모습(파일 확장자 `.exe`, `.dll`, ELF 실행 파일)만 봐서는 절대 구분할 수 없고, 반드시 **파일 헤더 안의 특정 필드 값**을 읽어야 한다. 이 구분을 틀리면 디스어셈블러가 명령어 길이와 레지스터를 완전히 잘못 해석해서 전부 의미 없는 코드로 보이게 되므로, 리버싱을 시작하기 전 가장 먼저 확인해야 하는 항목이다.

**PE(Windows .exe/.dll) 구조**
1. 파일 오프셋 `0x00`에 `MZ`(DOS 시그니처)로 시작한다.
2. 파일 오프셋 `0x3C`(60진수)에 4바이트 필드 `e_lfanew`가 있는데, 이 값이 실제 PE 헤더가 시작하는 파일 오프셋을 가리킨다.
3. `e_lfanew`가 가리키는 위치에 `PE\0\0`(4바이트 시그니처)가 있다.
4. 그 바로 뒤가 **COFF 파일 헤더**이고, COFF 헤더의 첫 번째 필드가 2바이트 `Machine`이다.
   - `0x014C` = `IMAGE_FILE_MACHINE_I386` → x86(32비트)
   - `0x8664` = `IMAGE_FILE_MACHINE_AMD64` → x64(64비트)
5. 독립적으로 재확인할 수 있는 필드가 하나 더 있다. COFF 헤더 뒤에 이어지는 **Optional Header**의 첫 2바이트 `Magic` 필드다.
   - `0x10B` = PE32 (32비트, 이 경우 `ImageBase` 필드가 4바이트)
   - `0x20B` = PE32+ (64비트, 이 경우 `ImageBase` 필드가 8바이트로 늘어남)

`Machine`과 `Magic` 두 필드는 원칙적으로 항상 일치해야 한다(정상적으로 빌드된 파일이라면). 둘 다 확인하면 헤더가 조작되었거나 손상된 파일인지도 짐작할 수 있다. PE32/PE32+ 차이가 왜 생기는지, ImageBase가 왜 커지는지는 [rev-0028-va-rva-offset.md](./rev-0028-va-rva-offset.md)에서 더 자세히 다룬다.

**ELF(Linux 실행 파일) 구조**
ELF는 헤더 시작 부분에 `e_ident`라는 16바이트 식별 배열이 있고, 그 뒤로 나머지 헤더 필드가 이어진다.
1. 파일 오프셋 `0x00`~`0x03`: `7F 45 4C 46` (`\x7fELF` 매직 바이트)
2. 파일 오프셋 `0x04`(`EI_CLASS` 인덱스): 클래스(비트수)를 나타낸다.
   - `1` = `ELFCLASS32` → 32비트(x86 등)
   - `2` = `ELFCLASS64` → 64비트(x64 등)
3. 파일 오프셋 `0x05`(`EI_DATA`): 엔디언(1=리틀, 2=빅). 대부분의 x86/x64 리눅스 바이너리는 리틀엔디언(`1`)이다.
4. 파일 오프셋 `0x12`(18진수, 2바이트) `e_machine`: CPU 아키텍처 종류.
   - `3` = `EM_386` → x86
   - `0x3E`(62) = `EM_X86_64` → x64

ELF에서도 `EI_CLASS`(32/64비트 여부)와 `e_machine`(구체적 CPU 종류)이 서로 다른 축의 정보라는 점이 중요하다. 이론적으로는 `EI_CLASS=1`인데 `e_machine`이 x86이 아닌 다른 32비트 CPU(ARM 등)를 가리킬 수도 있으므로, "32비트/64비트 여부"와 "x86 계열인지 여부"는 항상 같이 확인해야 한다.

**레지스터 이름으로 판단하는 보조 방법**: 디스어셈블리 코드 자체를 보고도 짐작할 수 있다. `EAX`, `EBX`, `ECX`, `EDX`, `ESP`, `EBP`처럼 `E`로 시작하는 32비트 레지스터만 보이고 함수 인자가 스택에 `push`되어 전달된다면 x86 문맥이다. 반대로 `RAX`, `RDI`, `RSI`, 그리고 x86에는 없는 `R8`~`R15` 레지스터가 보이거나 명령어 앞에 REX 프리픽스(`48`, `4C` 등으로 시작하는 옵코드 바이트)가 붙어 있으면 x64 코드라는 확실한 증거다. 레지스터 폭에 대한 자세한 이름 체계는 [rev-0022-register-widths.md](./rev-0022-register-widths.md)를 참고한다.

**호출 규약(calling convention)도 아키텍처에 따라 달라진다**(자세한 내용은 rev-0022에서 다룸): x86은 대부분 인자를 스택에 쌓아 전달하는 방식(`cdecl`, `stdcall` 등)을 쓰고, x64는 처음 몇 개 인자를 레지스터로 전달한다 — Windows x64는 `RCX, RDX, R8, R9` 순서, 리눅스 System V x64는 `RDI, RSI, RDX, RCX, R8, R9` 순서를 쓴다. 디스어셈블리에서 함수 호출 직전에 `push` 명령이 여러 번 나오면 x86식, `mov rcx, ...` / `mov rdx, ...`처럼 레지스터에 바로 값을 채우면 x64식일 가능성이 높다 — 다만 이건 참고용 정황 증거일 뿐, 확정 증거는 항상 헤더 필드다.

## 화면/코드에서 보이는 징후
- IDA/Ghidra에서 잘못된 비트수로 파일을 열면 명령어 경계가 어긋나서 `db`, `dw` 같은 알 수 없는 데이터 바이트 나열이나 존재하지 않는 옵코드 오류가 대량으로 나타난다.
- x64dbg로 32비트 실행 파일을 열려고 하면 "이 파일은 32비트 실행 파일입니다. x32dbg를 사용하세요" 같은 경고가 뜬다(반대의 경우도 마찬가지).
- `file` 명령 결과에 "ELF 64-bit LSB executable, x86-64" 또는 "ELF 32-bit LSB executable, Intel 80386" 같은 문구가 그대로 나온다.
- 디스어셈블리에 `R8`, `R9`, `R13`, `RAX`, `RIP` 같은 이름이 하나라도 보이면 그 순간 100% x64로 확정할 수 있다(x86 명령어 집합에는 이 레지스터들이 존재하지 않는다).

## 가장 먼저 할 것
IDA/Ghidra/x64dbg 등 무거운 도구를 열기 전에, 먼저 `file` 명령이나 헥스 에디터로 **10초 안에 비트수부터 확정**한다. 잘못된 비트수로 도구를 여는 순간 시간을 낭비하고, 심하면 "이 바이너리는 이상하다"고 잘못 판단하게 된다.

## 단계별 절차

**1) 터미널에서 가장 빠르게 확인 (리눅스/WSL)**
```bash
file ./target.exe
file ./target_elf
```
출력 예시:
```
target.exe: PE32+ executable (console) x86-64, for MS Windows
target_elf: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, ...
```
`PE32+`와 `x86-64`, 또는 `ELF 64-bit`와 `x86-64`라는 문구가 곧 결론이다. 32비트라면 각각 `PE32 executable`, `ELF 32-bit ... Intel 80386`으로 나온다.

**2) ELF는 readelf로 헤더 필드를 직접 확인**
```bash
readelf -h ./target_elf
```
출력에서 `Class:`와 `Machine:` 줄을 본다.
```
  Class:                             ELF64
  Data:                              2's complement, little endian
  Machine:                           Advanced Micro Devices X86-64
```
`Class: ELF64`가 곧 `EI_CLASS=2`, `Machine: Advanced Micro Devices X86-64`가 곧 `e_machine=0x3E`를 사람이 읽기 좋게 풀어 쓴 것이다.

**3) PE는 PE-bear/CFF Explorer 같은 GUI 도구로 확인**
PE-bear로 파일을 열면 좌측 트리에서 `File Header`를 클릭했을 때 `Machine` 필드가 `0x14C (x86)` 또는 `0x8664 (x64)`로 바로 표시된다. `Optional Header`를 클릭하면 `Magic` 필드도 같이 확인할 수 있다.

**4) 헥스 에디터로 손수 확인 (도구가 없을 때 최후 수단)**
HxD 같은 헥스 에디터로 파일을 열고:
- PE: 오프셋 `0x3C`에서 4바이트를 읽어 `e_lfanew` 값을 얻는다(예: `D8 00 00 00` → 리틀엔디언이므로 `0x000000D8`). 그 오프셋(`0xD8`)으로 이동하면 `50 45 00 00`(`PE\0\0`)이 보이고, 그 바로 뒤 2바이트가 Machine 필드다. `4C 01`(리틀엔디언 → `0x014C`)이면 x86, `64 86`(리틀엔디언 → `0x8664`)이면 x64.
- ELF: 오프셋 `0x04` 한 바이트만 보면 된다. `01`이면 32비트, `02`이면 64비트. 확신을 더하려면 오프셋 `0x12`(2바이트, 리틀엔디언)도 확인: `03 00`이면 x86, `3E 00`이면 x64.

**5) IDA/Ghidra 로드 시점에 확인**
IDA는 파일을 열 때 "Load file as" 대화상자에 이미 감지된 파일 타입과 프로세서(예: "Portable executable for AMD64 (PE) [pe64.dll]", "Portable executable for 80386 (PE) [pe.dll]")를 보여준다. 이 문구를 그대로 신뢰하면 되지만, 만약 원본 파일에 헤더 조작이 의심된다면 위 1~4단계로 직접 재검증한다. Ghidra는 Import 시 "Language" 선택 화면에서 `x86:LE:64:default` 인지 `x86:LE:32:default`인지 직접 골라야 하므로, 여기서 잘못 고르면 처음부터 다시 임포트해야 한다 — 반드시 사전에 비트수를 확인한 뒤 임포트하는 습관을 들인다.

## 명령어/단축키
```bash
# 리눅스/WSL
file ./binary
readelf -h ./binary | grep -E "Class|Machine"
objdump -f ./binary | grep architecture

# 파이썬으로 직접 파싱 (도구 없이 빠르게 스크립트로 확인)
python3 -c "
import struct
with open('target.exe','rb') as f:
    data = f.read(0x200)
e_lfanew = struct.unpack_from('<I', data, 0x3C)[0]
machine = struct.unpack_from('<H', data, e_lfanew + 4)[0]
print(hex(machine))   # 0x14c=x86, 0x8664=x64
"

python3 -c "
with open('target_elf','rb') as f:
    data = f.read(0x20)
print('class:', data[4])          # 1=32bit, 2=64bit
print('machine:', hex(data[0x12] | (data[0x13]<<8)))  # 3=x86, 0x3e=x64
"
```
x64dbg/x32dbg는 각각 별도 실행 파일(`x64dbg.exe` / `x32dbg.exe`)이며, 잘못된 쪽으로 32비트/64비트 파일을 열면 자동으로 올바른 쪽으로 다시 열도록 안내하는 경우가 많다(버전에 따라 다름).

## 출력 해석
- `file` 결과에 `PE32 executable`만 있고 `+`가 없다 → x86(32비트).
- `file` 결과에 `PE32+ executable`이다 → x64(64비트). `+`가 붙었는지 여부가 핵심이다.
- `readelf -h`의 `Class: ELF32` → x86 계열 32비트. `Class: ELF64` → 64비트.
- Machine 필드 `0x014C` → x86, `0x8664` → x64. 이 값 이외의 값(`0x1C0`=ARM, `0xAA64`=ARM64 등)이 나오면 x86 계열이 아닌 다른 아키텍처이므로 이 글의 범위를 벗어난다.
- ELF `e_machine` `3` → x86, `62`(`0x3E`) → x64. 다른 값(`40`=ARM, `183`=AArch64 등)이면 마찬가지로 x86 계열이 아니다.

## 흔한 실수
- 파일 확장자나 "요즘 나온 프로그램이니까 당연히 64비트겠지"라는 추측만으로 판단하는 것 — 실제로 CTF/구형 소프트웨어에서는 32비트 바이너리가 매우 흔하다.
- PE에서 `Machine` 필드만 보고 `Magic` 필드(Optional Header)를 확인하지 않는 것 — 헤더가 손상되었거나 의도적으로 조작된 파일에서는 둘이 불일치할 수 있으므로, 특히 이상한 파일을 다룰 때는 두 값을 모두 확인하는 습관이 안전하다.
- ELF에서 `EI_CLASS`(비트수)와 `e_machine`(CPU 종류)을 같은 것으로 혼동하는 것 — 32비트인데 x86이 아닌 경우(예: 32비트 ARM)도 있으므로 둘 다 확인해야 한다.
- IDA/Ghidra에서 아키텍처를 잘못 고른 채로 몇 분씩 "왜 코드가 이상하지"라며 붙잡고 있는 것 — 디스어셈블리가 이상하면 가장 먼저 의심할 것은 로직이 아니라 아키텍처 선택 자체다.
- x64 코드인데 함수 인자가 스택 `push`로 전달되지 않는다고 해서 "이 함수는 인자가 없다"고 오해하는 것 — x64는 처음 몇 개 인자가 레지스터(`RCX/RDX/R8/R9` 또는 `RDI/RSI/RDX/RCX/R8/R9`)로 전달되므로 `push` 명령이 없는 게 정상이다.

- 비트수를 정확히 맞췄는데도 IDA/Ghidra 디스어셈블리가 여전히 이상하다면, 패킹/난독화(엔트로피가 비정상적으로 높음)를 의심하고 Detect It Easy로 재확인한다.

## 미니 예제
32비트 PE 파일과 64비트 PE 파일의 헤더 앞부분을 헥스 에디터로 나란히 비교했다고 하자.

**x86 PE (32비트)**
```
offset 0x3C: D8 00 00 00        -> e_lfanew = 0x000000D8
offset 0xD8: 50 45 00 00        -> "PE\0\0"
offset 0xDC: 4C 01              -> Machine = 0x014C (IMAGE_FILE_MACHINE_I386, x86)
```

**x64 PE (64비트)**
```
offset 0x3C: D8 00 00 00        -> e_lfanew = 0x000000D8
offset 0xD8: 50 45 00 00        -> "PE\0\0"
offset 0xDC: 64 86              -> Machine = 0x8664 (IMAGE_FILE_MACHINE_AMD64, x64)
```
`e_lfanew`가 가리키는 위치와 `PE\0\0` 시그니처는 두 파일이 동일하지만, 그 바로 뒤 2바이트만 다르다는 점에 주목한다. 이 2바이트만 정확히 읽으면 무거운 도구를 열지 않고도 비트수를 확정할 수 있다.

같은 원리를 ELF로 파이썬 스크립트에서 확인하면:
```python
>>> with open('a.out', 'rb') as f:
...     header = f.read(20)
>>> header[:4]
b'\x7fELF'
>>> header[4]          # EI_CLASS
2                        # -> ELFCLASS64, 64비트
>>> header[0x12] | (header[0x13] << 8)   # e_machine, 리틀엔디언 2바이트
62                       # -> 0x3E, EM_X86_64, x64
```
이 결과만으로 "이 ELF는 x86-64용 64비트 실행 파일이다"라고 확정할 수 있다. IDA/Ghidra를 열기 전에 이 스크립트를 한 번 돌려보는 습관을 들이면 잘못된 아키텍처로 임포트해서 시간을 낭비하는 일을 막을 수 있다.

- PE 파일 형식(DOS 헤더, `e_lfanew`, COFF `Machine` 필드, Optional Header `Magic` 값 `0x10B`/`0x20B`): Microsoft PE Format 공식 문서(`docs.microsoft.com/windows/win32/debug/pe-format`) 기준 (2026-09-08 검증).

- `file`/`readelf` 출력 형식: GNU binutils 및 `file` 유틸리티(magic 데이터베이스) 실제 동작 기준.
