## 한 줄 요약
구조체 각 필드는 자신의 타입 크기에 맞는 배수 위치(정렬, alignment)에만 놓일 수 있어서 컴파일러가 필드 사이/구조체 끝에 빈 바이트(패딩)를 자동으로 끼워 넣으며, 이 규칙 때문에 `sizeof(struct)`가 단순히 필드 크기의 합과 다르고, 같은 필드를 다른 순서로 선언하면 구조체 전체 크기가 달라질 수 있으며, 32비트/64비트 빌드처럼 포인터 크기가 다른 환경 사이에서는 같은 구조체라도 오프셋 자체가 달라질 수 있다.

## 언제 검색해야 하나
- REV-0035(구조체 접근이 어셈블리로 변하는 방식)에서 오프셋 사이 "구멍"을 봤는데, 왜 컴파일러가 굳이 그 자리에 빈 공간을 남기는지 근본 규칙이 궁금할 때
- 구조체 필드 순서만 바꿨더니 `sizeof` 결과가 달라져서 당황했을 때
- `#pragma pack(1)`, `__attribute__((packed))` 같은 지시어가 코드/디스어셈블리 근처 주석에 보이는데 이게 무슨 효과인지 궁금할 때
- 같은 프로그램의 32비트 빌드와 64비트 빌드에서 구조체 필드 오프셋이 다르게 나와서 struct 정의를 이식(포팅)하기 어려울 때
- 바이너리 diff(패치 전후 비교)에서 구조체 크기 하나가 미묘하게 몇 바이트 달라진 이유를 알아내야 할 때

## 핵심 개념

### 이 문서와 REV-0035의 관계
REV-0035는 구조체 필드 접근이 `[reg+offset]` 형태로 어셈블리에 나타나는 방식과, 그 오프셋 사이에 패딩으로 인한 "구멍"이 생길 수 있다는 것을 간단히 언급했다. 이 문서는 그 패딩이 **정확히 어떤 규칙으로 결정되는지**, 그리고 그 규칙이 리버싱 실무(특히 서로 다른 빌드/아키텍처 간 구조체 비교)에 어떻게 영향을 주는지를 자세히 다룬다.

### 1) 자연 정렬(natural alignment) 규칙
대부분의 컴파일러(x86/x64 대상 GCC/Clang/MSVC)는 각 기본 타입에 대해 "그 타입의 크기만큼의 배수 주소에만 놓는다"는 규칙을 기본으로 따른다.

| 타입 | 크기 | 정렬 요구(보통) |
|---|---|---|
| `char` | 1 | 1바이트 배수 아무 곳 |
| `short` | 2 | 2바이트 배수 위치 |
| `int`, `float` | 4 | 4바이트 배수 위치 |
| `long`(64비트 빌드), `double`, 포인터(64비트) | 8 | 8바이트 배수 위치 |
| 포인터(32비트 빌드) | 4 | 4바이트 배수 위치 |

**구조체 필드는 구조체 시작 주소로부터의 오프셋이 자신의 정렬 요구값의 배수가 되어야 한다.** 예를 들어 `int` 필드는 구조체 시작으로부터 0, 4, 8, 12... 위치에만 올 수 있다. 만약 이전 필드 때문에 그 위치가 배수가 아니게 됐다면, 컴파일러는 배수가 맞을 때까지 빈 바이트(패딩)를 끼워 넣은 뒤 그 필드를 배치한다.

### 2) 필드 순서가 구조체 크기에 미치는 영향
같은 필드를 다른 순서로 선언하면 패딩의 양이 달라져서 전체 크기가 달라질 수 있다.

```c
struct Bad {
    char  a;     // offset 0                (1바이트)
    // 패딩 3바이트 (offset 1~3) — int는 4의 배수여야 함
    int   b;     // offset 4                (4바이트)
    char  c;     // offset 8                (1바이트)
    // 패딩 7바이트 (offset 9~15) — double은 8의 배수여야 함
    double d;    // offset 16               (8바이트)
};              // 전체 크기 24바이트 (8의 배수로 맞춤, tail padding 없음)
```
```c
struct Good {
    double d;    // offset 0    (8바이트)
    int    b;    // offset 8    (4바이트)
    char   a;    // offset 12   (1바이트)
    char   c;    // offset 13   (1바이트)
    // 패딩 2바이트 (offset 14~15) — 구조체 전체 크기를 8의 배수로 맞추기 위한 tail padding
};              // 전체 크기 16바이트
```
필드 내용은 완전히 동일한데(`char` 2개, `int` 1개, `double` 1개), 큰 타입을 먼저 선언한 `Good`은 16바이트, 작은 타입을 앞세운 `Bad`는 24바이트가 된다. **이것이 흔히 말하는 "구조체 필드는 큰 타입부터 작은 타입 순으로 선언하면 패딩을 줄일 수 있다"는 최적화 기법의 근거**다.

### 3) 구조체 전체의 정렬 요구값과 tail padding
구조체 자체도 정렬 요구값을 갖는데, 이는 **구조체 내부에서 가장 정렬 요구값이 큰 필드의 정렬값과 같다.** 그리고 구조체의 전체 크기는 반드시 이 정렬값의 배수여야 한다. 그래야 그 구조체를 배열로 선언했을 때(`struct Good arr[10];`) 두 번째, 세 번째 원소도 항상 올바른 정렬 위치에 자동으로 놓이기 때문이다. 이렇게 구조체 끝에 붙는 패딩을 **tail padding**이라 부른다. `Good` 예시에서 `char a`, `char c` 다음에 남는 2바이트가 바로 이것이다.

### 4) 강제로 패딩을 없애는 방법 — `#pragma pack` / `packed` 속성
프로토콜 헤더, 파일 포맷, 네트워크 패킷처럼 "메모리에 정확히 이 바이트 순서 그대로" 있어야 하는 구조체는 정렬 규칙을 무시하고 패딩 없이 다닥다닥 붙여야 할 때가 있다. 이때 사용하는 것이 컴파일러 확장 지시어다.

```c
#pragma pack(push, 1)
struct PacketHeader {
    char  type;      // offset 0
    int   length;    // offset 1  (패딩 없이 바로 붙음! 4바이트 정렬 위반)
    short checksum;  // offset 5
};                    // 전체 크기 7바이트 (패딩 없음)
#pragma pack(pop)
```
GCC/Clang에서는 `__attribute__((packed))`로 동일한 효과를 낸다. 이렇게 만들어진 구조체는 `int length` 필드가 4바이트 정렬 위치가 아닌 홀수 오프셋(1)에 걸쳐 있으므로, CPU가 이 필드를 읽을 때 **정렬되지 않은 메모리 접근(unaligned access)** 이 발생한다. x86/x64는 대부분의 명령어에서 정렬되지 않은 접근을 허용하지만(속도는 약간 느려질 수 있음), ARM 등 일부 아키텍처/모드에서는 예외(fault)가 발생할 수 있다.

### 5) 리버싱에서 이게 왜 중요한가 — 구조체 오프셋 이식과 바이너리 비교
- **32비트 vs 64비트 빌드 간 오프셋 불일치**: 포인터 크기가 32비트에서는 4바이트, 64비트에서는 8바이트로 바뀌면서, 구조체 안에 포인터 필드가 있다면 그 필드의 정렬 요구값 자체가 달라진다. 그 결과 32비트 빌드에서 확인한 구조체 오프셋을 그대로 64비트 빌드 리버싱에 재사용하면 틀린다 — 반드시 해당 아키텍처 기준으로 오프셋을 다시 확인해야 한다.
- **패치/버전 비교(bindiff)에서 구조체 크기 변화 해석**: 두 버전의 바이너리를 비교할 때 구조체 크기가 몇 바이트 늘어났다면, 실제로 필드가 추가된 것일 수도 있지만, 단순히 필드 순서가 바뀌어 패딩 양만 달라진 것일 수도 있다. 오프셋 목록을 오름차순으로 정렬해서(REV-0035에서 다룬 방법) 실제 "구멍"이 생긴 위치를 확인하면 패딩 변화와 필드 추가를 구분할 수 있다.
- **컴파일러가 필드 순서를 재배치하지 않는다는 점**: C 표준은 구조체 멤버가 선언된 순서대로 메모리에 배치되어야 한다고 규정한다(패딩 삽입은 허용하지만 순서 재배열은 금지). 따라서 디스어셈블리에서 오프셋이 오름차순으로 나타난다면 그 순서가 곧 소스 코드의 선언 순서라고 신뢰할 수 있다 — 이는 구조체를 역공학으로 복원할 때 중요한 전제다.
- **패킹된 구조체를 알아보는 법**: 오프셋 사이에 "구멍"이 전혀 없이 1바이트 단위로 빽빽하게 필드가 이어진다면(예: `char`, `int`가 연달아 offset 0, 1로 붙음), 자연 정렬을 따르지 않는 packed 구조체이거나 애초에 전부 `char` 배열/바이트 파싱 코드일 가능성이 있다. 파일 포맷 파서, 네트워크 패킷 파서 코드에서 이런 패턴이 흔히 보인다.

## 화면/코드에서 보이는 징후
- `[rdi]`, `[rdi+4]`, `[rdi+8]`, `[rdi+0x10]`처럼 오프셋이 4/8의 배수로만 나타나고 사이 값(1, 2, 3, 5, 6, 7 등)은 전혀 안 쓰이는 패턴 — 자연 정렬을 따르는 일반 구조체.
- `[rdi]`, `[rdi+1]`, `[rdi+5]`처럼 홀수 오프셋이 자주 등장하고 정렬 규칙과 무관하게 필드가 붙어있는 패턴 — packed 구조체이거나 바이트 단위 파서.
- 같은 로직을 처리하는 함수인데 32비트 빌드와 64비트 빌드에서 구조체 관련 오프셋 상수가 다르게 나타남 — 포인터 크기 변화로 인한 정렬 차이.
- 구조체 크기(예: `sub rsp, N`에서 유추한 지역 구조체 크기)가 필드 개수×평균 크기로 계산한 값보다 항상 조금 더 큼 — tail padding 존재 가능성.

## 가장 먼저 할 것
구조체로 추정되는 베이스 레지스터의 모든 오프셋을 오름차순으로 나열하고, 오프셋 사이 간격이 4/8의 배수로 깔끔하게 떨어지는지, 아니면 불규칙하게 촘촘한지부터 본다. 깔끔하면 일반 정렬 구조체이므로 정렬 규칙으로 필드 타입 크기를 역산할 수 있고, 촘촘하면 packed 구조체나 원시 바이트 파싱 코드로 접근 방식을 바꿔야 한다.

## 단계별 절차

**1) 오프셋 목록 수집 및 간격 분석 (REV-0035 방식 재사용)**
```asm
mov     eax, [rdi]        ; offset 0
mov     [rdi+4], ecx       ; offset 4
mov     dl, [rdi+8]        ; offset 8
mov     rax, [rdi+0x10]    ; offset 0x10 (16)
```
오프셋: 0, 4, 8, 0x10 → 8과 0x10 사이에 8바이트 간격인데 offset 8에서 1바이트만 읽었으므로(`dl`), 그 사이 7바이트는 패딩일 가능성이 높다(다음 필드가 8바이트 정렬을 요구하는 타입이기 때문).

**2) 정렬 규칙으로 패딩 위치와 크기 역산**
```
offset 8  : char (1바이트 읽기)
offset 16 : 8바이트 읽기 (long/포인터/double)
```
8바이트짜리 필드가 오프셋 16(8의 배수)에 있으려면, offset 8의 char 뒤 offset 9~15(7바이트)가 패딩이어야 한다는 계산이 나온다.

**3) IDA/Ghidra에서 구조체 재정의 시 정렬 옵션 확인**
IDA Structures 창에서 새 구조체를 만들 때, 기본적으로 자동 정렬(alignment)이 적용된다. 만약 실제 바이너리가 packed 구조체를 쓰고 있다면 구조체 속성에서 정렬을 1로 강제 지정해야 오프셋이 올바르게 맞물린다.

**4) 32비트/64비트 빌드 비교 시 포인터 필드부터 재확인**
```c
struct Node {
    int   value;   // 32비트: offset 0(4B) / 64비트: offset 0(4B) 동일
    Node *next;    // 32비트: offset 4(4B 정렬) / 64비트: offset 8(8B 정렬, 4바이트 패딩 추가!)
};
```
포인터 필드가 있는 구조체는 32비트→64비트 이식 시 반드시 오프셋을 다시 계산해야 한다.

## 명령어/단축키
```c
#include <stddef.h>
printf("%zu\n", sizeof(struct Mixed));       // 실제 컴파일러가 계산한 전체 크기 확인
printf("%zu\n", offsetof(struct Mixed, d));  // 특정 필드의 실제 오프셋 확인 (소스가 있을 때)
```
```
(gdb) ptype struct Mixed      # 디버그 정보가 있을 때 컴파일러가 실제로 배치한 레이아웃 확인
(gdb) print sizeof(struct Mixed)
```
IDA: `Shift+F9`(Structures 창) → 구조체 속성에서 정렬(Alignment) 값을 1(packed)로 변경 가능.

## 출력 해석
- 오프셋 간격이 규칙적으로 4/8의 배수라면 일반 정렬 구조체이므로, 간격 크기로 필드 타입을 추정할 수 있다(4바이트 간격이면 그 사이는 `int`/`float` 등 4바이트 필드, 8바이트 간격이면 `double`/포인터/`long` 등 8바이트 필드).
- `sizeof` 결과가 필드 크기의 단순 합보다 크다면 그 차이만큼 패딩(필드 사이 + tail padding)이 존재한다는 뜻이다.
- packed 구조체(`#pragma pack(1)`)로 선언된 것이 확실하면, 정렬 배수 규칙 자체를 적용하지 말고 소스/스펙 문서(프로토콜 명세 등)에 정의된 바이트 순서를 그대로 신뢰해야 한다.

## 흔한 실수
- `sizeof(struct)`가 각 필드 크기의 합과 같을 거라 무조건 가정하는 것 — 패딩 때문에 항상 그렇지는 않다.
- 필드 순서를 바꾸면 컴파일러가 자동으로 최적 순서로 재배치해줄 거라 착각하는 것 — C 표준은 선언 순서를 그대로 유지하도록 강제하며, 패딩 최소화는 프로그래머가 직접 순서를 조정해야 하는 일이다.
- 32비트 빌드에서 확인한 구조체 오프셋을 검증 없이 64비트 빌드 리버싱에 그대로 사용하는 것 — 포인터 필드가 하나라도 있으면 오프셋이 달라질 수 있다.
- packed 구조체와 일반 정렬 구조체를 구분하지 않고 똑같이 "4/8의 배수 오프셋"을 기대하는 것 — packed 구조체는 이 규칙을 따르지 않는다.
- 패딩 바이트에 우연히 남아있는 이전 메모리 쓰레기값을 실제 데이터 필드로 착각해서 분석하는 것 — 패딩 영역은 초기화되지 않는 경우가 많아 예측 불가능한 값이 들어있을 수 있다.

## 막혔을 때 다음 체크
- 구조체 필드 접근이 어셈블리에서 어떤 형태로 나타나는지 기초부터 다시 보려면 → REV-0035(구조체 접근이 어셈블리로 변하는 방식)로 이동.
- 구조체 배열의 인덱스 계산과 필드 오프셋이 함께 나오는 경우가 궁금하면 → REV-0034(배열 접근이 어셈블리로 변하는 방식)로 이동.
- 정렬이 CPU 캐시/성능 관점에서 왜 중요한지, 리버싱에서 어떤 신호로 쓰이는지 더 알고 싶으면 → REV-0345(캐시 라인과 메모리 정렬 개념이 리버싱에 미치는 영향)로 이동.

## 미니 예제
같은 필드 구성의 구조체를 선언 순서만 바꿔서 크기 차이를 직접 확인한다.

```c
#include <stdio.h>
#include <stddef.h>

struct Bad {
    char  a;
    int   b;
    char  c;
    double d;
};

struct Good {
    double d;
    int    b;
    char   a;
    char   c;
};

int main(void) {
    printf("Bad:  %zu bytes\n", sizeof(struct Bad));   // 24
    printf("Good: %zu bytes\n", sizeof(struct Good));  // 16
    printf("Bad.d offset:  %zu\n", offsetof(struct Bad, d));   // 16
    printf("Good.d offset: %zu\n", offsetof(struct Good, d));  // 0
    return 0;
}
```

디스어셈블리에서 `struct Bad`를 다루는 함수는 `d` 필드 접근이 `[rdi+0x10]`(16)으로 나타나고, `struct Good`을 다루는 함수는 같은 필드가 `[rdi]`(0)로 나타난다. 필드 내용은 완전히 동일해도 선언 순서가 다르면 오프셋과 전체 크기가 이렇게 달라진다는 것을, 오프셋 목록만 보고도 눈치챌 수 있어야 한다.

## 관련 글
- REV-0035 — 구조체 접근이 어셈블리로 변하는 방식
- REV-0034 — 배열 접근이 어셈블리로 변하는 방식
- REV-0345 — 캐시 라인과 메모리 정렬 개념이 리버싱에 미치는 영향

## 출처/검증
- 구조체 멤버 정렬(natural alignment), tail padding, 멤버 선언 순서 유지 규칙: C11 표준(ISO/IEC 9899:2011) 6.7.2.1 "Structure and union specifiers" 및 System V AMD64 ABI "Aggregates and Unions" 섹션 기준.
- `#pragma pack`/`__attribute__((packed))` 동작: GCC 공식 문서("Structure-Packing Pragmas", "Common Type Attributes") 및 Microsoft C++ 문서(`#pragma pack`) 기준 (2026-09-09 검증).
- 정렬되지 않은 메모리 접근(unaligned access)에 대한 x86/x64의 허용 및 성능 특성: Intel 64 and IA-32 Architectures Software Developer's Manual, Volume 3, "Alignment Checking" 섹션 기준.
