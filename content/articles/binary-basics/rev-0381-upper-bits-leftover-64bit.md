## 한 줄 요약
x64에서 **32비트 레지스터(예: `eax`)에 값을 쓰면 상위 32비트가 자동으로 0으로 클리어**되지만, **8비트(`al`)나 16비트(`ax`) 레지스터에만 값을 쓰면 나머지 상위 비트는 그대로 남아 있는다** — 이 두 규칙을 헷갈리면 "분명히 값을 썼는데 전체 레지스터를 보면 쓰레기가 섞여 있다"는 혼란이 생긴다.

## 언제 검색해야 하나
- `mov eax, ...`로 값을 넣었는데 `rax` 전체를 보면 상위 32비트에 값이 남아있어서 이상하다고 느낄 때
- `mov al, ...`나 `mov ax, ...`처럼 작은 폭 레지스터에만 값을 쓴 다음, `eax`나 `rax` 전체를 확인했더니 예상 밖의 값이 섞여 있을 때
- 32비트 함수 리턴값을 64비트 포인터 계산에 바로 썼는데 계산이 이상하게 틀어질 때
- IDA/Ghidra 디컴파일에서 `(unsigned __int64)`로 강제 캐스팅이 왜 들어가 있는지 이해가 안 갈 때

## 핵심 개념
x86/x64 레지스터는 "겹쳐서" 존재한다. 예를 들어 `rax`(64비트) 안에 `eax`(하위 32비트), 그 안에 `ax`(하위 16비트), 그 안에 `al`(하위 8비트)이 들어있는 구조다. 그런데 이 부분 레지스터에 값을 쓸 때 **상위 비트를 어떻게 처리하는지가 폭에 따라 다르다는 것**이 핵심 함정이다.

**규칙 1: 32비트(`eXX`) 레지스터에 쓰면 상위 32비트가 자동으로 0이 된다 (x64 고유 규칙)**
```asm
mov rax, 0xFFFFFFFFFFFFFFFF   ; rax 전체를 모두 1로 채움
mov eax, 0x00000001           ; eax(하위 32비트)에 1을 씀
; 결과: rax = 0x0000000000000001  (상위 32비트가 자동으로 0으로 클리어됨!)
```
이건 x64 아키텍처가 명시적으로 정한 특별 규칙이다. 32비트 명령어의 결과는 항상 64비트 레지스터의 상위 절반을 0으로 만든다. 그래서 컴파일러가 32비트 값을 다루다가 갑자기 64비트 연산(포인터 계산 등)에 그대로 써도 안전한 경우가 많다.

**규칙 2: 8비트(`al`/`ah`)나 16비트(`ax`) 레지스터에 쓰면 나머지 상위 비트는 그대로 남는다 (구식 규칙, 하위 호환)**
```asm
mov rax, 0xFFFFFFFFFFFFFFFF   ; rax 전체를 모두 1로 채움
mov al, 0x01                   ; al(최하위 1바이트)에만 1을 씀
; 결과: rax = 0xFFFFFFFFFFFFFF01  (상위 56비트가 그대로 남아있음!)
```
```asm
mov rax, 0xFFFFFFFFFFFFFFFF
mov ax, 0x0001
; 결과: rax = 0xFFFFFFFFFFFF0001  (상위 48비트가 그대로 남아있음!)
```
이 차이는 8086 시절부터 이어진 하위 호환성 때문이다. 원래 16비트/8비트 레지스터 연산은 "나머지 부분은 건드리지 않는다"는 규칙으로 설계됐고, 이후 32비트(IA-32)로 확장되면서 32비트 연산만 예외적으로 "상위를 클리어한다"는 새 규칙이 추가됐다. 그리고 64비트(x64)로 확장될 때 이 32비트 규칙이 계승되어 오늘의 형태가 됐다.

**왜 이게 문제가 되는가**: 함수가 32비트 값을 리턴하고(`eax`에 결과), 호출하는 쪽이 이 리턴값을 곧바로 64비트 포인터 연산에 쓴다고 하자. `mov eax, ...`로 세팅됐다면 `rax`의 상위 32비트는 이미 0이 보장되므로 안전하다. 하지만 어떤 이유로 `al`이나 `ax`만 세팅된 상태에서 `rax` 전체를 포인터로 쓴다면, 이전에 그 레지스터에 남아있던 상위 비트 쓰레기값이 섞여서 완전히 엉뚱한 주소를 가리키게 된다.

## 화면/코드에서 보이는 징후
- 디스어셈블리에서 함수 진입 직후 `xor eax, eax`(또는 `xor rax, rax`)로 레지스터를 먼저 0으로 밀어버린 다음 `mov al, ...`을 쓰는 패턴 — 상위 바이트가 쓰레기로 남는 문제를 사전에 방지하기 위한 관용구
- 32비트 리턴값을 64비트로 확장할 때 `movzx`/`movsx`가 명시적으로 붙어 있는 코드(리턴값이 8/16비트인 경우) vs 그냥 `mov eax, ...`만으로 충분한 코드(32비트인 경우)
- 디버거에서 `al`만 바꿨는데 `rax` 전체 값이 상위 바이트가 그대로인 채로 하위 1바이트만 바뀌는 경우

## 가장 먼저 할 것
문제가 된 레지스터 연산이 몇 비트 폭(8/16/32/64)의 명령어였는지부터 확인한다. 32비트 명령어(`eXX` 레지스터 대상)라면 상위 32비트는 항상 0이 되므로 걱정할 필요가 없다. 8비트/16비트 명령어라면 상위 비트가 남아있을 수 있으므로 그 레지스터의 이전 값을 반드시 추적해야 한다.

## 단계별 절차

**1) 명령어의 대상 레지스터 폭 확인**
`mov eax, ...`(32비트) vs `mov al, ...`(8비트) vs `mov ax, ...`(16비트)를 정확히 구분한다.

**2) 32비트 명령어라면 상위 클리어를 신뢰**
x64에서 `eXX` 레지스터를 대상으로 하는 산술/이동 명령어는 결과적으로 `rXX`의 상위 32비트를 항상 0으로 만든다는 것을 규칙으로 받아들인다(예외: 일부 벡터/SIMD 명령어나 특수 상황은 별도 문서 확인 필요).

**3) 8비트/16비트 명령어라면 그 레지스터의 직전 값을 역추적**
그 명령어 실행 직전에 전체 64비트 레지스터에 어떤 값이 있었는지(예: 함수 진입 시점에 아무 초기화 없이 이전 호출의 레지스터 값이 남아있었는지) 확인한다. 초기화(`xor rax, rax` 등)가 앞에 있다면 상위 비트는 0이라고 안전하게 가정할 수 있다.

**4) 디버거에서 직접 값 대입해서 재현**
GDB나 x64dbg에서 레지스터에 임의 값을 채운 뒤, 원하는 명령어를 한 스텝 실행하고 전체 레지스터를 다시 확인해 규칙을 눈으로 검증한다.

## 명령어/단축키
```gdb
set $rax = 0xFFFFFFFFFFFFFFFF
stepi                # 다음 명령어 1개 실행
p/x $rax             # 결과 확인
p/x $eax             # 하위 32비트만 별도 확인
```
```asm
mov  eax, 1     ; rax 상위 32비트 자동 클리어됨
mov  al, 1      ; rax 상위 56비트는 그대로 남음
mov  ax, 1      ; rax 상위 48비트는 그대로 남음
xor  eax, eax   ; rax 전체를 0으로 만드는 흔한 관용구(32비트 xor라 상위도 클리어)
```

## 출력 해석
- `mov eax, N` 실행 직후 `p/x $rax`가 `N`과 정확히 일치한다면(상위 비트가 전부 0), 이는 오류가 아니라 x64의 정상 규칙이다.
- `mov al, N` 실행 직후 `p/x $rax`의 상위 56비트가 실행 전과 동일하다면, 이 역시 정상이다 — 8비트 연산은 원래 나머지를 건드리지 않기 때문이다.

## 흔한 실수
- 8비트/16비트 레지스터 연산도 32비트처럼 상위 비트를 자동으로 클리어해줄 거라고 착각하는 것.
- `xor eax, eax`(32비트 xor)와 `xor al, al`(8비트 xor)의 효과가 다르다는 것을 모르고 아무거나 써서 레지스터를 "완전히 0으로 만들었다"고 착각하는 것 — `xor al, al`은 상위 56비트를 그대로 남긴다.
- 함수 리턴값을 다루는 캘링 컨벤션에서, 리턴 타입이 실제로 몇 비트인지 확인하지 않고 무조건 전체 64비트 레지스터를 신뢰하는 것.
- 디컴파일러가 보여주는 `(unsigned __int64)` 캐스팅을 의미 없는 잡음으로 여기고 무시하는 것 — 이는 정확히 이 상위 비트 규칙 때문에 컴파일러/디컴파일러가 명시한 것일 수 있다.

## 막혔을 때 다음 체크
- 32비트/64비트 레지스터의 이름 구조(`rax`/`eax`/`ax`/`al`) 자체가 헷갈리면 REV-0022 문서로 이동.
- 배열 인덱스 계산에서 32비트 인덱스를 64비트로 확장하는 과정이 궁금하면 REV-0378 문서로 이동.
- signed/unsigned 값 읽기(`movsx`/`movzx`)와의 관계가 궁금하면 REV-0025 문서로 이동.

## 미니 예제
다음 어셈블리를 보자.
```asm
mov     rax, 0x1122334455667788
mov     eax, 0x9              ; 32비트 연산 → rax 상위 32비트 자동 클리어
; rax = 0x0000000000000009
mov     al, 0xAA               ; 8비트 연산 → 상위 56비트는 그대로 유지
; rax = 0x00000000000000AA     (직전 eax 연산으로 이미 상위가 0이었으므로 결과적으로 깨끗함)
```
만약 두 번째 줄(`mov eax, 0x9`)이 없었다면, `mov al, 0xAA`만 실행한 결과는 `rax = 0x11223344556677AA`처럼 원래 있던 쓰레기 상위 비트가 그대로 남았을 것이다. 이 예제는 "직전에 32비트 연산으로 상위를 클리어해뒀는가"가 최종 결과를 완전히 바꾼다는 것을 보여준다.

## 관련 글
- REV-0022 — 32비트와 64비트 레지스터 차이
- REV-0025 — Signed와 Unsigned 해석
- REV-0378 — 배열 인덱스 계산이 이상하게 나올 때

## 출처/검증
- x64에서 32비트 연산 결과가 64비트 레지스터 상위를 자동으로 0으로 만드는 규칙: Intel 64 and IA-32 Architectures Software Developer's Manual, Vol.1, "General-Purpose Registers in 64-Bit Mode" 섹션 기준 (2026-09-09 검증).
- 8비트/16비트 부분 레지스터 연산이 나머지 비트를 보존하는 하위 호환 규칙: 동 매뉴얼 Vol.1, "Operand Size and Address Size in 64-Bit Mode" 및 8086 이후 x86 레지스터 확장 역사에 대한 아키텍처 개요 섹션 기준.
