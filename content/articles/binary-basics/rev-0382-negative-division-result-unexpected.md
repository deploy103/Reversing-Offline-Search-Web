## 한 줄 요약
C/C++와 x86/x64의 `IDIV`는 음수 나눗셈에서 몫을 **0을 향해 잘라내는(truncation toward zero)** 방식을 쓰기 때문에, 수학의 floor 나눗셈(더 작은 쪽으로 내림)이나 파이썬의 기본 `//` 연산과 결과가 다를 수 있으며, 이 차이는 나머지 연산자 `%`의 부호에도 그대로 이어진다.

## 언제 검색해야 하나
- `-7 / 2` 같은 음수 나눗셈 결과가 예상(예: `-4`)과 다르게 `-3`으로 나올 때
- `%` 나머지 연산 결과가 음수로 나와서 배열 인덱스나 해시 버킷 계산이 이상해질 때
- 어셈블리에서 `idiv` 직전에 `cdq`/`cqo` 같은 부호 확장 명령어가 왜 붙는지 궁금할 때
- 파이썬으로 같은 계산을 재현했는데 C 프로그램의 결과와 값이 다를 때

## 핵심 개념
정수 나눗셈에서 나머지가 남을 때, "몫을 어느 쪽으로 반올림할 것인가"에는 여러 관례가 있다. C 언어(C99 이후)와 x86/x64의 `IDIV` 명령어는 **0을 향해 자르는(truncate toward zero)** 방식을 쓴다. 이는 수학적으로 흔히 쓰는 **floor(더 작은 정수 쪽으로 내림)** 방식과 음수가 하나라도 끼면 결과가 달라진다.

**구체적 예시**: `-7 / 2`를 계산해보자.
- 수학적으로 정확한 값은 `-3.5`
- **C/x86 IDIV (truncate toward zero)**: `-3.5`에서 소수부를 그냥 버리고 0 쪽으로 자름 → **`-3`**
- **파이썬 `//` (floor, 더 작은 정수로 내림)**: `-3.5`보다 작은 정수 중 가장 큰 것 → **`-4`**

같은 수학 문제인데 C는 `-3`, 파이썬 기본 연산자는 `-4`를 낸다. 이 차이를 모르고 파이썬으로 대상 프로그램의 계산을 재현하면 값이 안 맞아서 혼란스러울 수 있다.

**나머지(`%`)의 부호도 몫의 반올림 방향을 따라간다**: C 표준은 `(a/b)*b + a%b == a`가 항상 성립하도록 정의한다. `-7 / 2 = -3`(truncate)이므로 `-7 % 2 = -7 - (-3*2) = -7 + 6 = -1`이다. 즉 **C에서 나머지의 부호는 피제수(나누어지는 값, 여기서는 `-7`)의 부호를 따른다.** 반면 파이썬은 `-7 // 2 = -4`이므로 `-7 % 2 = -7 - (-4*2) = -7 + 8 = 1`이 되어 **나누는 값(제수, 여기서는 `2`)의 부호를 따르는 결과**가 나온다. 같은 `-7 % 2`인데 C는 `-1`, 파이썬은 `1`이라는 정반대 부호가 나오는 것이다.

**어셈블리에서 부호 확장이 필요한 이유**: x86의 `IDIV` 명령어는 나뉘는 값(피제수)을 항상 **2배 크기의 레지스터 쌍**으로 받는다(예: 32비트 나눗셈이면 `edx:eax` 64비트를 피제수로, `eax`에 몫, `edx`에 나머지를 남김). 만약 원래 값이 음수인 32비트 정수라면, 이걸 64비트 피제수로 확장할 때 단순히 상위 32비트를 0으로 채우면(제로 확장) 안 되고, 부호를 유지하도록 상위 32비트를 전부 부호 비트로 채워야(부호 확장) 한다. 이 작업을 해주는 명령어가 `CDQ`(32비트: `eax` → `edx:eax`)와 `CQO`(64비트: `rax` → `rdx:rax`)다. `CDQ`는 `eax`의 최상위 비트가 0이면 `edx`를 전부 0으로, 1이면 `edx`를 전부 `0xFFFFFFFF`로 채운다.

**unsigned 나눗셈은 다른 명령어를 쓴다**: signed 나눗셈은 `IDIV`(+`CDQ`/`CQO`로 부호 확장), unsigned 나눗셈은 `DIV`(+상위 레지스터를 그냥 0으로 클리어)를 쓴다. 어느 명령어가 쓰였는지만 봐도 그 값이 signed로 다뤄졌는지 unsigned로 다뤄졌는지 알 수 있다.

## 화면/코드에서 보이는 징후
- `idiv` 명령어 바로 앞에 `cdq`(32비트) 또는 `cqo`(64비트)가 붙어 있는 코드 — signed 나눗셈이라는 확실한 신호
- `div` 명령어 앞에 상위 레지스터(`edx`, `rdx`)를 `xor edx, edx`로 명시적으로 0을 채우는 코드 — unsigned 나눗셈 신호
- 음수를 다루는 해시/버킷 인덱스 계산에서 `%` 결과가 음수가 나와서 배열 인덱스로 바로 쓰면 크래시하거나 이상한 위치를 가리키는 경우

## 가장 먼저 할 것
문제가 된 나눗셈/나머지 연산이 `idiv`(signed)인지 `div`(unsigned)인지부터 확인한다. `idiv`라면 그 앞에 `cdq`/`cqo`가 있는지, 그리고 피제수가 음수일 가능성이 있는지 확인한다.

## 단계별 절차

**1) 명령어로 signed/unsigned 구분**
`idiv`(부호 있는 나눗셈) vs `div`(부호 없는 나눗셈). 이것만으로도 컴파일러가 이 값을 어떤 타입으로 다뤘는지 알 수 있다.

**2) truncate 방식으로 몫/나머지를 손으로 재계산**
파이썬의 `//`, `%`를 그대로 쓰지 않고, C/x86 방식(0을 향해 자름)으로 직접 계산한다.
```python
import math
def c_div(a, b):
    q = a / b
    return math.trunc(q)          # 0을 향해 잘라내는 truncation

def c_mod(a, b):
    return a - c_div(a, b) * b

print(c_div(-7, 2), c_mod(-7, 2))   # -3, -1  (C/x86과 동일)
```

**3) 어셈블리에서 부호 확장 명령어 유무 확인**
`cdq`/`cqo`가 있다면 피제수가 signed로 확장된 것이므로, 그 값이 음수일 수 있는 상황이라면 반드시 truncate 규칙을 적용해서 계산해야 한다.

**4) 결과를 실제 디버거 값과 대조**
GDB나 x64dbg로 `idiv` 실행 직후 `eax`(몫)와 `edx`(나머지)를 직접 확인해서 손 계산과 일치하는지 검증한다.

## 명령어/단축키
```asm
cdq                  ; eax(32비트, signed)를 edx:eax(64비트)로 부호 확장
cqo                  ; rax(64비트, signed)를 rdx:rax(128비트)로 부호 확장
idiv    ebx          ; edx:eax를 ebx로 signed 나눗셈, 몫→eax, 나머지→edx
xor     edx, edx     ; unsigned 나눗셈 전 상위 레지스터 클리어
div     ebx          ; edx:eax를 ebx로 unsigned 나눗셈, 몫→eax, 나머지→edx
```
```gdb
p/d $eax     # idiv 직후 몫(signed) 확인
p/d $edx     # idiv 직후 나머지(signed) 확인
```

## 출력 해석
- `idiv` 직후 `edx`(나머지)의 부호가 원래 피제수(`eax`, 나눗셈 전 값)의 부호와 같다면 이는 정상이다 — C/x86의 truncate 규칙이 그렇게 정의되어 있다.
- 파이썬으로 검증할 때 `//`, `%`를 그냥 쓰면 C/어셈블리 결과와 다를 수 있으므로, 반드시 `math.trunc` 기반 함수로 재구현해서 비교해야 한다.

## 흔한 실수
- 파이썬 `//` 연산자가 C의 정수 나눗셈과 항상 같은 결과를 낸다고 가정하고 그대로 스크립트에 옮기는 것 — 음수가 개입하면 다를 수 있다.
- `cdq`/`cqo` 없이 바로 `idiv`가 나온다고 착각하는 것 — signed 나눗셈에서 이 부호 확장 명령어는 사실상 항상 필요하므로, 없다면 그건 `div`(unsigned)이거나 피제수가 이미 64비트로 준비된 특수한 경우다.
- 나머지 연산 결과의 부호를 무조건 양수로 가정하고 그 값을 그대로 배열 인덱스에 사용해 음수 인덱스 버그를 만드는 것.
- C99 이전 표준(구현 정의였던 시절)과 C99 이후(0을 향한 truncation으로 명확히 정의됨) 규칙을 혼동하는 것 — 현대 컴파일러는 모두 C99 이후 규칙을 따른다.

## 막혔을 때 다음 체크
- signed/unsigned 값 해석과 조건 점프 차이가 헷갈리면 REV-0025 문서로 이동.
- 나눗셈이 곱셈+시프트로 최적화되는 매직 넘버 패턴이 궁금하면 assembly 카테고리의 나눗셈 최적화 패턴 글로 이동.
- 나머지 연산 자체의 최적화 패턴이 궁금하면 assembly 카테고리의 나머지 연산 최적화 패턴 글로 이동.

## 미니 예제
다음 C 코드와 어셈블리를 비교해보자.
```c
int f(int x) {
    return x % 3;
}
```
```asm
mov     eax, edi
cdq                    ; edi가 음수일 수 있으므로 edx:eax로 부호 확장
mov     ecx, 3
idiv    ecx
mov     eax, edx       ; 나머지(edx)를 리턴값으로 사용
ret
```
`x = -8`을 넣으면 `-8 / 3`은 truncate 방식으로 `-2`(수학적으로는 `-2.666...`이지만 0쪽으로 자름), 나머지는 `-8 - (-2*3) = -8 + 6 = -2`가 되어 함수는 `-2`를 반환한다. 파이썬에서 그냥 `-8 % 3`을 실행하면 `1`이 나와서 완전히 다른 값이 되므로, 이 프로그램을 파이썬으로 재현하려면 반드시 truncate 기반 나머지 계산 함수를 따로 만들어야 한다.
