## 한 줄 요약
`EAX`/`AX`/`AL`/`AH`처럼 같은 레지스터를 부르는 이름이 여러 개인 이유는 x86 계열 CPU가 하위 호환성을 지키기 위해 각 세대(8086 → 80386 → AMD64)마다 이전 레지스터를 그대로 두고 그 위에 더 넓은 이름을 덧씌워왔기 때문이며, 이 역사를 알면 "왜 A/B/C/D 레지스터만 상위 바이트(`AH` 등) 이름이 따로 있고 `SI`/`DI`/`BP`/`SP`는 없는지" 같은 불규칙함까지 자연스럽게 이해된다.

## 언제 검색해야 하나
- `EAX`, `AX`, `AL`, `AH`라는 이름이 왜 이렇게 여러 개인지, 그리고 왜 규칙이 딱 떨어지지 않는지 궁금할 때
- `AH`, `BH`, `CH`, `DH`(상위 바이트) 같은 이름이 `SI`, `DI`, `BP`, `SP`에는 왜 없는지 궁금할 때
- 레지스터 이름의 접두사(`E`, `R`)와 접미사(`D`, `W`, `B`, `L`, `H`)가 각각 무엇을 의미하는지 한 번에 정리하고 싶을 때
- 디스어셈블리에서 낯선 레지스터 이름을 봤을 때 이름만 보고 폭(width)과 계열을 즉시 판별하는 감을 잡고 싶을 때

## 핵심 개념

### 이 문서와 REV-0022의 관계
REV-0022(32비트와 64비트 레지스터 차이)에서 `AL⊂AX⊂EAX⊂RAX`의 포함 관계와, x64에서 32비트 서브 레지스터에 쓰면 상위 비트가 제로 익스텐션되는 규칙을 이미 다뤘다. 이 문서는 그 내용을 반복하지 않고, **왜 이름 규칙 자체가 지금과 같은 모양이 되었는지 그 역사와 명명 규칙 자체**에 집중한다. 부분 쓰기(partial write)의 정확한 동작이 궁금하면 REV-0022를 먼저 참고한다.

### 1) 8086 이전 — 8080의 8비트 레지스터
x86 계열의 조상인 인텔 8080(1974)은 8비트 레지스터 `A`(Accumulator, 누산기), `B`, `C`, `D`, `E`, `H`, `L`을 가지고 있었다. 이 중 `B`+`C`, `D`+`E`, `H`+`L`은 프로그램에서 종종 한 쌍으로 묶여 16비트 값처럼 취급되기도 했다(`BC`, `DE`, `HL`).

### 2) 8086(1978) — 16비트로 확장하며 하위 호환 이름을 남김
인텔 8086은 레지스터를 16비트로 확장하면서, 이전 8080 코드와의 호환성 및 어셈블리 프로그래머의 학습 부담을 줄이기 위해 다음과 같이 이름을 지었다.

- `AX`(Accumulator), `BX`(Base), `CX`(Counter), `DX`(Data) — 이 네 개는 8080 시절 `A`/`BC`/`HL` 계열과 마찬가지로 **16비트 레지스터 안에서도 상위 바이트(`AH`)와 하위 바이트(`AL`)를 따로 부를 수 있게** 설계되었다. 즉 `AX`라는 16비트 레지스터 하나를 `AH`(High, bit15~8)와 `AL`(Low, bit7~0)로 쪼개 접근할 수 있다.
- `SI`(Source Index), `DI`(Destination Index), `BP`(Base Pointer), `SP`(Stack Pointer) — 이 넷은 문자열 연산(`MOVS`, `STOS` 등, REV-0081/0082 참고)이나 스택/베이스 주소 계산처럼 **애초부터 16비트 "주소/포인터" 용도로 새로 도입된 레지스터**라서, 8비트로 쪼개 쓸 이유 자체가 없었다. 그래서 이 네 레지스터에는 상위/하위 바이트를 따로 부르는 이름이 처음부터 존재하지 않는다.

이 차이가 "왜 `AH`/`BH`/`CH`/`DH`는 있는데 `SIH`/`DIH`류는 없는가"의 정확한 답이다 — 원래 8비트 시절부터 쪼개 쓰던 레지스터(`A`/`B`/`C`/`D` 계열)와, 16비트 시대에 새로 태어난 레지스터(`SI`/`DI`/`BP`/`SP`)의 태생 차이다.

### 3) 80386(1985) — 32비트로 확장, `E` 접두사 등장
80386은 레지스터를 32비트로 확장하면서 기존 16비트 이름 앞에 `E`(Extended)를 붙였다. `AX` → `EAX`, `SI` → `ESI`, `BP` → `EBP`처럼 **모든 레지스터에 예외 없이 규칙적으로** `E`를 붙인 것이 특징이다. 8비트/16비트 시절의 불규칙함(`AH`/`AL`이 있고 없고)과 달리, 32비트 확장은 처음부터 일관된 접두사 규칙으로 설계됐다.

### 4) AMD64/x64(2003) — `R` 접두사와 완전히 새로운 이름 규칙(R8~R15)
AMD64는 두 가지를 동시에 했다.
- 기존 32비트 이름 앞에 `R`을 붙여 64비트로 확장: `EAX` → `RAX`, `ESI` → `RSI`.
- 완전히 새로운 8개의 범용 레지스터 `R8`~`R15`를 추가.

`R8`~`R15`는 역사적 이름(`A`/`B`/`C`/`D`, `SI`/`DI`)을 계승하지 않고 그냥 번호를 매겼기 때문에, 서브 레지스터를 부르는 방식도 완전히 새로운 규칙(`D`=32비트, `W`=16비트, `B`=8비트 접미사)을 따른다. 이 R8~R15의 세부 인코딩과 계산 규약상의 역할은 REV-0343에서 자세히 다룬다.

### 5) 전체 이름 규칙을 정리하면
| 세대 | 접두사/접미사 규칙 | 예시 |
|---|---|---|
| 8080 계열 8비트 (`A`/`B`/`C`/`D`) | 접두사 없음, 상위(`H`)/하위(`L`) 별도 이름 | `AH`, `AL` |
| 8086 16비트 | 접두사 없음, `A`/`B`/`C`/`D`만 8비트 분할 가능 | `AX`, `SI` |
| 80386 32비트 | `E` 접두사(Extended) | `EAX`, `ESI` |
| AMD64 64비트(레거시 계열) | `R` 접두사 | `RAX`, `RSI` |
| AMD64 신규 레지스터(R8~R15) | 접미사만 사용(`D`/`W`/`B`), 접두사 없음, 상위 바이트 이름 없음 | `R8D`, `R8W`, `R8B` |

이 표를 외우기보다, **"레거시 4형제(A/B/C/D)만 상위/하위 바이트를 따로 부르는 이름이 있고, 그 이유는 역사적으로 8비트 시절부터 그렇게 설계됐기 때문"** 이라는 한 문장과, **"E는 32비트, R은 64비트, 새 레지스터(R8~)는 번호+접미사"** 라는 규칙 두 가지만 기억하면 어떤 레지스터 이름을 봐도 계열과 폭을 즉시 추론할 수 있다.

### 6) 왜 이 역사를 알아야 리버싱에 도움이 되는가
디스어셈블리에서 레지스터 이름을 볼 때, 이름 자체가 "이 레지스터가 원래 무슨 용도로 설계됐는가"에 대한 힌트를 준다.
- `ECX`/`CX`/`CL`(Counter)이 반복문의 카운터나 `REP` 계열 명령어(REV-0080~0084)와 함께 자주 등장하는 것은 우연이 아니라 이름 그대로의 설계 의도다.
- `ESI`/`EDI`(Source/Destination Index)가 `MOVSB`/`MOVSD` 같은 문자열 복사 명령어의 암묵적 피연산자로 고정되어 있는 것도 이름에서 유래한 역할이다.
- `EBP`/`RBP`(Base Pointer)가 스택 프레임의 기준으로 쓰이는 관례(REV-0031)도 이름에서 그대로 드러난다.
- `ESP`/`RSP`(Stack Pointer)는 이름 그대로 항상 스택 최상단을 가리키는 특별한 레지스터로 취급되어, 범용 레지스터처럼 자유롭게 재활용되는 경우가 드물다(단, x64에서 최적화 시 예외적으로 스택 상대 주소 계산의 기준으로 재활용되는 경우는 있음 — REV-0341 변형 2 참고).

즉 이름 규칙을 역사적으로 이해하면 "이 레지스터가 왜 하필 이 위치에서 이 용도로 쓰이는가"를 추측하는 데 실질적으로 도움이 된다.

## 화면/코드에서 보이는 징후
- IDA/Ghidra 디스어셈블리에서 `AL`/`AH`처럼 상위/하위 바이트로 쪼개 쓰는 코드는 거의 항상 `A`/`B`/`C`/`D` 계열 레지스터에서만 보이고, `SIL`/`DIL`(x64 전용, REX 프리픽스 필요)은 있어도 `SIH`/`DIH` 같은 이름은 애초에 존재하지 않는다.
- 반복문 카운터가 `ECX`/`RCX`에 자주 배정되는 패턴, 문자열/배열 복사에 `ESI`/`EDI`가 소스/목적지로 자주 쓰이는 패턴이 관찰된다(단, 컴파일러 레지스터 할당은 항상 이렇게 되는 건 아니며 경향일 뿐이다).
- 코드 안에서 `EBP`가 스택 프레임 기준이 아니라 일반 계산에 재활용되고 있다면, 프레임 포인터 생략(FPO) 최적화가 적용된 것으로 의심할 신호다.

## 가장 먼저 할 것
낯선 레지스터 이름을 만나면 접두사(`E`/`R`/없음)로 폭을 먼저 확정하고, 접미사나 이름 형태(`H`/`L`/`X` 등)로 8/16/32/64비트 중 어디에 해당하는지 이어서 판별한다. 그 다음 레지스터 알파벳(`A`/`B`/`C`/`D`/`SI`/`DI`/`BP`/`SP`)의 원래 이름(Accumulator/Base/Counter/Data/Source Index/Destination Index/Base Pointer/Stack Pointer)을 떠올리면 그 레지스터가 코드에서 맡고 있을 법한 역할을 짐작하는 데 도움이 된다.

## 단계별 절차

**1) 접두사로 큰 분류 확정**
```
E 로 시작       -> 32비트 (EAX, ESI, EBP)
R 로 시작       -> 64비트 (RAX, RSI, RBP) 또는 R8~R15 계열
접두사 없음      -> 16비트(AX, SI) 또는 8비트(AL, AH)
```

**2) A/B/C/D 계열이면 8비트 분할 가능 여부 확인**
```
AL, AH  -> AX의 하위/상위 바이트 (8086부터 존재)
BL, BH  -> BX의 하위/상위 바이트
CL, CH  -> CX의 하위/상위 바이트
DL, DH  -> DX의 하위/상위 바이트
SIL, DIL, BPL, SPL -> x64에서만 존재(REX 프리픽스 필요), 전부 "하위 바이트"이며 상위 바이트 이름은 없음
```

**3) 원래 이름으로 용도 짐작**
```
A -> Accumulator (연산 결과, 반환값)
B -> Base (기준 주소)
C -> Counter (반복 횟수)
D -> Data (보조 데이터)
SI -> Source Index (복사/비교의 출발지)
DI -> Destination Index (복사/비교의 목적지)
BP -> Base Pointer (스택 프레임 기준)
SP -> Stack Pointer (스택 최상단)
```

## 명령어/단축키
```
(gdb) info registers      # 현재 아키텍처에서 지원하는 전체 레지스터 이름 목록 확인
(gdb) p $al                # 8비트 서브 레지스터 직접 조회가 안 되면 p $rax & 0xff 로 대체
```
IDA/Ghidra: 레지스터 이름에 마우스 오버 시 관련된 다른 폭의 이름이 함께 하이라이트되어, 포함 관계를 시각적으로 바로 확인할 수 있다.

## 출력 해석
- 디스어셈블리에 `AL`만 보이고 `AH`는 안 보이는 함수라면, 그 함수는 8비트 값(예: `char`, `bool`) 하나만 다루고 있을 가능성이 높다.
- `BH`, `CH`, `DH` 같은 레거시 상위 바이트 레지스터는 최신 컴파일러가 생성하는 코드에서는 드물게 나타난다(레지스터 인코딩상 REX 프리픽스와 충돌 문제가 있어 x64에서는 사실상 기피됨) — 등장한다면 오래된 코드나 손으로 작성된 어셈블리, 또는 아주 특수한 최적화 패턴일 가능성이 있다.
- `SIL`/`DIL`/`BPL`/`SPL`가 보인다면 반드시 x64 코드다(REX 프리픽스 필요) — x86(32비트) 코드에는 이 이름들이 존재하지 않는다.

## 흔한 실수
- `AH`/`BH`/`CH`/`DH` 같은 상위 바이트 이름이 모든 레지스터에 공통으로 있을 거라 착각하는 것 — `SI`/`DI`/`BP`/`SP`/`R8`~`R15` 계열에는 상위 바이트 이름이 아예 없다.
- 레지스터 이름의 원래 의미(Accumulator, Counter 등)를 "반드시 그 용도로만 쓰인다"는 절대 규칙으로 오해하는 것 — 실제로는 컴파일러가 상황에 따라 자유롭게 재배정하는 경향(convention)일 뿐, 하드웨어가 강제하는 규칙은 아니다(단, `RCX`/`RDX`/`R8`/`R9`가 함수 인자 전달에, `RSP`가 스택 포인터로 쓰이는 것처럼 호출 규약이나 명령어 인코딩상 실제로 고정된 역할도 있다).
- `E`/`R` 접두사 규칙과 R8~R15의 `D`/`W`/`B` 접미사 규칙을 같은 규칙으로 착각해서 `R8E`, `ER8` 같은 존재하지 않는 이름을 떠올리는 것.

## 막혔을 때 다음 체크
- 부분 쓰기 시 상위 비트가 지워지는지 여부(제로 익스텐션) 등 실제 동작 규칙이 궁금하면 → REV-0022(32비트와 64비트 레지스터 차이)로 이동.
- `R8`~`R15`가 왜 추가됐고 인코딩상 어떻게 다른지 궁금하면 → REV-0343(x64에서 R8~R15 레지스터와 서브 레지스터)으로 이동.
- 스택 프레임에서 `RBP`/`RSP`가 실제로 어떻게 쓰이는지 궁금하면 → REV-0031(스택 프레임이 무엇인지)로 이동.

## 미니 예제
아래는 레지스터 이름만 보고 세대와 폭을 판별하는 연습이다.

```
DL      -> D 계열, 접두사 없음+하위바이트 이름 -> 8비트 (DX의 하위 바이트)
ESI     -> E 접두사 -> 32비트 (Source Index)
R13     -> R 접두사+숫자, 접미사 없음 -> 64비트 신규 레지스터
R13D    -> R+숫자+D 접미사 -> 32비트 (R13의 하위 32비트)
BPL     -> BP 계열 + L 접미사 -> 8비트, x64 전용(REX 필요), 상위바이트 이름 없음
CH      -> C 계열 + H -> 8비트 상위 바이트 (CX의 상위 바이트, 8086 시절부터 존재)
```
이 여섯 개 이름만으로도 "접두사(`E`/`R`/없음)로 세대와 폭을 먼저 보고, 계열(A/B/C/D인지 SI/DI/BP/SP/R8~15인지)로 상위 바이트 이름의 존재 여부를 판단한다"는 규칙이 실전에서 어떻게 적용되는지 확인할 수 있다.
