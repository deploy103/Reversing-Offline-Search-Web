## 한 줄 요약
엔디안이 헷갈릴 때는 "바이트 나열을 통째로 뒤집는다"고 생각하지 말고, **바이트 하나하나의 순서만 뒤집고 각 바이트 내부(니블 두 개)는 절대 뒤집지 않는다**는 규칙 하나만 정확히 기억하면, x86/x64에서 리틀 엔디안 값을 손으로도 실수 없이 검증할 수 있다.

## 언제 검색해야 하나
- REV-0023(엔디안 개념)은 이해했는데, 실제 헥스에디터에서 4바이트/8바이트 값을 보고 직접 손으로 계산하다가 자꾸 틀릴 때
- 파이썬 없이 그 자리에서 급하게 헥스덤프를 눈으로 읽어야 하는데 순서를 헷갈릴 때
- 계산 결과가 예상한 상수와 미묘하게 다르게 나와서(예: 자릿수는 맞는데 순서가 이상함) 어디서 실수했는지 찾아야 할 때
- CTF 문제 풀이 중 종이/화이트보드에 헥스값을 옮겨 적으며 검증해야 하는 상황일 때

## 핵심 개념

### 핵심 규칙 한 줄: "바이트 단위로만 뒤집는다"
가장 흔한 실수는 헥스 문자열 전체를 글자 단위로 거꾸로 읽는 것이다. 예를 들어 `12 34 56 78`을 보고 "그냥 전체를 뒤집으면 되니까 `87 65 43 21`"이라고 생각하면 완전히 틀린다. **엔디안 변환은 항상 "바이트(2개 헥스 문자로 이루어진 한 덩어리)"를 최소 단위로 삼아서, 그 덩어리들의 순서만 바꾸는 것**이지, 각 바이트 내부의 두 니블(4비트씩)까지 뒤집는 게 아니다.

```
원래 바이트 나열(파일/메모리 순서, 낮은 주소→높은 주소):  78 56 34 12
                                                          ^^ ^^ ^^ ^^
                                                          이 4개 덩어리(바이트)의 순서만 뒤집는다
사람이 읽는 순서로 재배열:                                12 34 56 78
```

`78`이라는 바이트 안에서 `7`과 `8`의 위치가 서로 바뀌는 일은 절대 없다. 항상 "두 글자짜리 덩어리"를 원자 단위로 취급해서 그 덩어리들의 배열 순서만 뒤집는다.

### 손으로 검증하는 3단계 절차
1. **바이트 단위로 쪼갠다**: 헥스 문자열을 2글자씩 끊어서 나열한다. 예: `78563412` → `78`, `56`, `34`, `12`
2. **순서를 거꾸로 나열한다**: 마지막 바이트를 맨 앞으로, 첫 바이트를 맨 뒤로. 예: `12`, `34`, `56`, `78`
3. **붙여 쓴다**: `12345678`

이 3단계는 리틀 엔디안 바이트열을 사람이 읽는 값(빅 엔디안처럼 보이는 표기)으로 바꿀 때나, 반대로 사람이 아는 상수값을 리틀 엔디안 바이트열로 바꿀 때나 똑같이 적용된다 — 방향만 다를 뿐 "바이트 단위로 쪼개고 순서를 뒤집는다"는 절차는 동일하다.

### 자주 틀리는 함정 — 홀수 자리 헥스
바이트 개수가 딱 맞아떨어지지 않는(헥스 자릿수가 홀수인) 값을 다룰 때 특히 실수가 잦다. 예를 들어 2바이트 값 `0x1F90`(8080)을 리틀 엔디안으로 저장하면 어떻게 될까?

1. `0x1F90`을 바이트 단위로 쪼갠다: 이 값은 2바이트이므로 `1F`, `90`
2. 순서를 뒤집는다: `90`, `1F`
3. 파일/메모리에 저장된 실제 바이트열: `90 1F`

만약 여기서 실수로 니블 단위까지 뒤집어 `09 F1`이라고 계산하면 틀린다. `1F90`을 쪼갤 때 반드시 "왼쪽부터 2글자씩" 끊어야 하며, 상위 바이트는 `1F`, 하위 바이트는 `90`이다.

### 길이(바이트 개수)를 먼저 확정하는 것이 실수를 줄이는 핵심
엔디안 변환에서 가장 흔한 실수는 "이 값이 몇 바이트짜리인지"를 먼저 정하지 않고 계산을 시작하는 것이다. 상위 비트가 `0`이라 생략된 값(`0x50` vs `0x0050`)은 바이트 개수를 헷갈리기 쉽다. 예를 들어 포트 번호 80은 흔히 `0x50`이라고만 쓰지만, TCP 헤더의 포트 필드는 **항상 2바이트 고정 크기**이므로 실제로는 `0x0050`으로 취급해야 한다. 이걸 1바이트로 착각하고 엔디안 변환을 건너뛰면 안 되고, 2바이트로 확정한 뒤 `00`, `50` 두 바이트의 순서(빅 엔디안 네트워크 바이트 오더이므로 그대로 `00 50`)를 검증해야 한다.

### 검증 습관: 알고 있는 매직 넘버로 자가 점검
계산 결과를 스스로 검증하는 가장 쉬운 방법은, 이미 확실히 알고 있는 매직 넘버(REV-0020)로 먼저 손 계산 절차를 연습해보는 것이다. 예를 들어 PE 파일은 항상 `4D 5A`(`MZ`)로 시작한다는 걸 알고 있으므로, 이 값을 2바이트 정수로 읽으면 리틀 엔디안 기준 `0x5A4D`가 되어야 한다는 걸 미리 검증해볼 수 있다.
```
파일 바이트: 4D 5A
바이트 단위로 순서 뒤집기: 5A 4D
결과: 0x5A4D  (IMAGE_DOS_SIGNATURE 상수와 일치)
```
이렇게 답을 이미 아는 값으로 절차를 검증해두면, 실전에서 낯선 값을 계산할 때도 같은 절차를 믿고 적용할 수 있다.

## 화면/코드에서 보이는 징후
- 헥스에디터에서 4바이트/8바이트 필드를 읽어야 하는데 어느 방향으로 읽을지 확신이 안 서는 상황
- 손으로 계산한 값이 예상 상수와 자릿수는 맞는데 순서가 뒤바뀐 것처럼 보이는 결과가 나올 때(니블까지 뒤집는 실수를 의심)
- 종이/화이트보드 CTF 풀이에서 파이썬 없이 즉석으로 헥스값을 재구성해야 하는 상황

## 가장 먼저 할 것
계산을 시작하기 전에 "이 값이 정확히 몇 바이트인가"부터 확정한다(1/2/4/8바이트). 그 다음 헥스 문자열을 왼쪽부터 2글자씩 끊어 바이트 단위 블록으로 나누고, 그 블록들의 순서만 뒤집는다는 원칙을 지킨다.

## 단계별 절차
1. 값의 바이트 폭을 확정한다(예: PE Machine 필드는 2바이트, ELF `e_type`은 2바이트, 일반 `int`는 4바이트).
2. 헥스 문자열을 2글자씩(=1바이트씩) 끊어 나열한다.
3. 나열된 바이트 블록들의 순서를 통째로 뒤집는다(각 블록 내부 두 글자는 순서 유지).
4. 뒤집힌 순서대로 다시 이어붙인다.
5. 알고 있는 매직 넘버나 상수(REV-0020)로 같은 절차를 미리 검산해 절차 자체가 맞는지 확인한다.
6. 확신이 안 서면 파이썬 한 줄로 즉시 교차검증한다(`int.from_bytes(bytes.fromhex("xxxx"), "little")`).

## 명령어/단축키
```python
# 손 계산 결과를 즉시 교차검증
bytes.fromhex("78563412")
int.from_bytes(bytes.fromhex("78563412"), "little")   # 사람이 읽는 값으로
hex(0x12345678).replace("0x","").zfill(8)               # 사람이 아는 값 -> 헥스 문자열
```
```python
# 사람이 아는 값을 리틀 엔디안 바이트열로 (역방향 검산)
(0x12345678).to_bytes(4, "little").hex()   # '78563412'
```

## 출력 해석
- 손 계산 결과와 `int.from_bytes(..., "little")` 결과가 일치하면 절차가 정확했다는 뜻이다.
- 불일치한다면 십중팔구 "바이트 폭을 잘못 잡았거나(예: 2바이트인데 4바이트로 착각)" "니블까지 뒤집는 실수"를 의심한다.
- 상위 바이트가 `00`인 값(`00 50` 같은)은 사람이 쓰는 표기에서 자릿수가 생략되기 쉬우므로, 항상 고정 바이트 폭 기준으로 앞자리 `0`을 살려서 계산하는 습관이 실수를 줄인다.

## 흔한 실수
- 바이트 블록이 아니라 헥스 문자열 전체를 글자 단위로 거꾸로 읽어서 니블까지 뒤집어버리는 것 — 이 문서에서 가장 강조하는 함정이다.
- 값의 바이트 폭을 확정하지 않고 계산을 시작해, `0x50`(1바이트로 착각)과 `0x0050`(실제로는 2바이트 필드) 사이에서 혼란을 겪는 것.
- 네트워크 바이트 오더(빅 엔디안) 필드에도 무조건 리틀 엔디안 뒤집기를 적용해버리는 것(REV-0023의 네트워크 바이트 오더 섹션 참고).
- 손 계산 결과를 검산 없이 그대로 신뢰하는 것 — 특히 CTF처럼 정답이 명확한 상황에서는 파이썬 한 줄로 교차검증하는 습관을 들이는 편이 훨씬 안전하다.

## 막혔을 때 다음 체크
- 엔디안 개념 자체(리틀/빅, 왜 x86/x64가 항상 리틀 엔디안인지)부터 다시 정리하고 싶으면 → REV-0023 Little Endian과 Big Endian
- 매직 넘버/파일 시그니처로 손 계산을 검산하는 기준값이 더 필요하면 → REV-0020 Magic Byte와 파일 시그니처
- 계산한 값이 음수처럼 보여서 혼란스럽다면 엔디안이 아니라 부호 해석 문제일 수 있음 → REV-0024 2의 보수와 음수 표현, REV-0025 Signed와 Unsigned 해석
- 특정 비트폭만 남기는 마스크 연산과 헷갈린다면 → REV-0026 8비트 16비트 24비트 32비트 64비트 마스크

## 미니 예제
ELF 헤더의 `e_type` 필드(2바이트, 오프셋 0x10)를 헥스에디터에서 봤다고 하자.
```
오프셋 0x10에서 읽은 바이트: 02 00
```
손으로 검증하는 절차:
1. 바이트 폭 확정: `e_type`은 2바이트 필드다.
2. 바이트 단위로 쪼개기: `02`, `00`
3. 순서 뒤집기: `00`, `02`
4. 이어붙이기: `0x0002`

`0x0002`는 `ET_EXEC`(실행 파일)에 해당하는 상수다. 만약 니블까지 뒤집는 실수를 했다면 `02 00` → `00 20`처럼 완전히 다른(그리고 존재하지 않는) 값을 만들어냈을 것이다. 바이트 블록 단위로만 뒤집는다는 규칙을 지켰기 때문에 정확한 상수를 얻을 수 있었다.
