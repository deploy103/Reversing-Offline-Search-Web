## 한 줄 요약
엔디안(endianness)은 **여러 바이트로 이루어진 값을 메모리/파일에 저장할 때 바이트를 어느 순서로 배치하는가**를 뜻하며, x86/x64는 항상 **리틀 엔디안**(최하위 바이트가 낮은 주소에 먼저 옴)을 쓴다.

## 언제 검색해야 하나
- 헥스에디터(HxD, ImHex)로 PE/ELF 헤더를 열었는데, 알고 있는 상수값(예: `0x8664`)이 파일에는 `64 86`처럼 순서가 뒤집혀 보일 때
- 4바이트나 8바이트짜리 값을 손으로 읽으려는데 어느 방향으로 읽어야 할지 헷갈릴 때
- 네트워크 패킷을 리버싱하는데 포트 번호나 IP 주소 필드가 예상과 다른 값으로 보일 때
- `struct.pack`/`struct.unpack`에서 `<`나 `>` 포맷 문자의 의미를 모를 때
- ELF 헤더의 `EI_DATA` 바이트가 뭘 의미하는지 궁금할 때

## 핵심 개념
CPU는 1바이트(8비트)보다 큰 값 — 16비트(2바이트), 32비트(4바이트), 64비트(8바이트) — 을 메모리나 파일에 저장할 때, 그 값을 구성하는 여러 바이트를 **어떤 순서로 늘어놓을지** 정해야 한다. 이 저장 순서 규칙을 **엔디안(endianness, 바이트 순서)**이라 부른다.

크게 두 가지 방식이 있다.

- **리틀 엔디안(Little Endian, LE)**: 최하위 바이트(LSB, Least Significant Byte)를 가장 낮은 주소에 먼저 저장한다. "작은(little) 자리가 앞에 온다"고 외우면 된다.
- **빅 엔디안(Big Endian, BE)**: 최상위 바이트(MSB, Most Significant Byte)를 가장 낮은 주소에 먼저 저장한다. "큰(big) 자리가 앞에 온다."

**왜 이게 중요한가**: 사람이 손으로 쓰는 16진수 표기(`0x12345678`)는 항상 "왼쪽이 상위 자리"인 수학적 표기다. 하지만 그 값이 실제로 메모리나 파일 바이트로 저장될 때는 CPU/파일 포맷이 정한 엔디안 규칙을 따른다. 이 둘을 혼동하는 것이 리버싱 초보자가 헥스에디터를 볼 때 가장 자주 겪는 함정이다.

### 32비트 값 `0x12345678`을 예로 든 헥스 덤프

이 값을 4바이트로 쪼개면 `12`, `34`, `56`, `78`이다(각각 상위→하위 자리). 이 값이 주소 `0x1000`부터 저장된다고 하자.

**리틀 엔디안으로 저장된 경우** (x86, x64에서 실제로 이렇게 저장됨):

| 주소 | 0x1000 | 0x1001 | 0x1002 | 0x1003 |
|---|---|---|---|---|
| 바이트 | `78` | `56` | `34` | `12` |

주소가 증가하는 방향으로 바이트를 나열하면 `78 56 34 12` — 원래 값과 "거꾸로" 보인다. 최하위 바이트(`78`)가 가장 먼저(가장 낮은 주소에) 온다.

**빅 엔디안으로 저장된 경우** (네트워크 프로토콜, 일부 임베디드/구형 아키텍처):

| 주소 | 0x1000 | 0x1001 | 0x1002 | 0x1003 |
|---|---|---|---|---|
| 바이트 | `12` | `34` | `56` | `78` |

이쪽은 사람이 쓰는 표기와 순서가 같다 — 최상위 바이트(`12`)가 가장 먼저 온다. "빅 엔디안은 읽는 순서 그대로"라고 기억하면 쉽다.

### x86과 x64는 항상 리틀 엔디안이다

이것이 이 글에서 가장 중요한 결론이다: **x86과 x64(AMD64/Intel 64) 아키텍처는 예외 없이 항상 리틀 엔디안이다.** Windows PE 실행 파일이든 Linux ELF 실행 파일이든, x86/x64 CPU에서 실행되는 한 메모리에 올라간 모든 다바이트 정수(`int`, `DWORD`, `QWORD`, 포인터, 주소 등)는 리틀 엔디안으로 저장된다. 이 글의 나머지 내용 대부분은 결국 이 한 문장에서 파생된다.

### ELF 헤더의 EI_DATA 바이트

ELF 포맷은 이론적으로 리틀/빅 엔디안을 모두 지원하도록 설계되어 있다. ELF 헤더(`e_ident` 배열)의 **오프셋 5번 바이트**가 이를 나타내는 `EI_DATA` 필드다.

- `01` = `ELFDATA2LSB` → 리틀 엔디안
- `02` = `ELFDATA2MSB` → 빅 엔디안

x86/x64 리눅스 실행 파일을 헥스에디터로 열어서 파일 맨 앞을 보면, `7F 45 4C 46`(매직 넘버 `\x7fELF`, [rev-0021-x86-vs-x64.md](./rev-0021-x86-vs-x64.md)에서 다룬 필드) 다음 바이트들 중 오프셋 5에서 거의 항상 `01`을 보게 된다. MIPS나 SPARC 같은 다른 아키텍처용 ELF에서는 `02`가 나올 수도 있지만, 이 위키가 다루는 x86/x64 대상 실전 리버싱에서는 사실상 항상 `01`(리틀 엔디안)이라고 봐도 된다.

### PE COFF 헤더의 Machine 필드 — 가장 흔한 착각 지점

Windows PE 파일의 COFF 헤더에는 `Machine` 필드가 있고, 이 값이 AMD64(x64)면 `0x8664`로 알려져 있다(사람이 읽는 표준 표기). 하지만 이 값이 파일 안에 실제로 어떻게 저장되어 있는지 헥스에디터로 확인하면, 다음과 같은 순서로 보인다.

```
오프셋      바이트
+0x00       64
+0x01       86
```

즉 `0x8664`라는 값을 찾으려고 헥스에디터에서 `86 64`를 검색하면 **못 찾는다.** 실제 파일에는 `64 86` 순서로 들어 있기 때문이다. 이건 앞서 설명한 리틀 엔디안 규칙 그대로다 — `0x8664`를 2바이트로 쪼개면 상위 바이트 `86`, 하위 바이트 `64`이고, 리틀 엔디안은 하위 바이트를 먼저 저장하므로 `64 86` 순서가 된다.

**이것이 리버싱 초보자가 가장 흔히 겪는 혼동이다**: 문서나 툴에서 "Machine 값은 `0x8664`"라고 배웠는데, 정작 파일을 열어서 눈으로 보면 그 숫자가 안 보이고 순서가 뒤집힌 `64 86`만 보이니 "내가 잘못 찾았나?", "이 파일이 이상한가?"라고 착각하게 된다. 답은 간단하다 — 파일이 이상한 게 아니라, 리틀 엔디안이 정상 동작한 것뿐이다.

### ARM은 어떨까

ARM CPU는 기술적으로 "바이 엔디안(bi-endian)"이다. 즉 부팅 시 설정에 따라 리틀 엔디안 모드로도, 빅 엔디안 모드로도 동작할 수 있게 설계되어 있다. 하지만 실전 리버싱에서 실제로 마주치는 ARM 바이너리 — 안드로이드 APK 안의 네이티브 라이브러리(`.so`), iOS 앱 — 는 거의 전부 리틀 엔디안(`EI_DATA` = `01`, 또는 Mach-O의 경우 리틀 엔디안 CPU 타입)이다. "ARM이니까 빅 엔디안일 수도 있다"고 과도하게 걱정할 필요는 없지만, 이론적으로 다를 수 있다는 사실 자체는 알아두는 게 좋다.

### 네트워크 바이트 오더는 빅 엔디안이다

TCP/IP 프로토콜 스택은 역사적으로 **빅 엔디안을 "네트워크 바이트 오더(network byte order)"**로 표준화했다. TCP/UDP 헤더의 포트 번호, IP 헤더의 여러 필드 등은 모두 빅 엔디안으로 전송된다. C 표준 라이브러리의 `htons()`/`htonl()`(host to network short/long)과 `ntohs()`/`ntohl()`(network to host)이 바로 이 변환을 위한 함수다 — x86/x64 호스트(리틀 엔디안)와 네트워크(빅 엔디안) 사이를 오갈 때 반드시 거쳐야 하는 함수라서, 패킷 파서나 네트워크 클라이언트/서버 바이너리를 리버싱할 때 이 함수 호출이 자주 등장한다.

예를 들어 TCP 포트 80(HTTP)을 캡처한 패킷에서 그대로 헥스로 보면 `00 50`으로 나타난다. `0x50` = 80이고, 빅 엔디안이므로 상위 바이트(`00`)가 먼저, 하위 바이트(`50`)가 나중에 온다 — 사람이 쓰는 표기(`0x0050`)와 순서가 같다. 만약 이걸 리틀 엔디안이라고 잘못 가정하고 읽으면 `50 00` = `0x0050`... 이 경우는 상위 바이트가 `00`이라 우연히 같은 결과가 나오지만, 두 바이트가 모두 의미 있는 값(예: 포트 `0x1F90` = 8080)일 때 리틀 엔디안으로 잘못 읽으면 `90 1F` = `0x1F90`이 아니라 `0x901F`(36895)처럼 완전히 다른, 말도 안 되는 포트 번호로 오독하게 된다. 패킷 덤프를 볼 때는 "이건 네트워크 필드이므로 빅 엔디안"이라는 걸 항상 의식해야 한다.

## 화면/코드에서 보이는 징후
- 헥스에디터에서 알고 있는 상수(`0x8664`, `0x00905A4D`, 매직 넘버 등)를 검색했는데 안 나오고, 바이트 순서가 뒤집힌 값만 보이는 경우
- IDA/Ghidra에서 `dd`(define dword)로 표시된 값이 파일 오프셋상의 바이트 나열과 반대 순서로 보이는 경우
- Wireshark나 raw 소켓 덤프에서 포트 번호, 길이 필드가 이상하게 큰 값이나 작은 값으로 읽히는 경우 (엔디안을 잘못 가정)
- `struct.pack`/`struct.unpack` 코드에서 `<`(리틀 엔디안), `>`(빅 엔디안), `!`(네트워크=빅 엔디안), `=`(네이티브) 접두사가 헷갈리는 경우

## 가장 먼저 할 것
헥스에디터로 다바이트 필드(2/4/8바이트)를 읽을 때는, **그 필드가 "일반 x86/x64 메모리·파일 필드"인지 "네트워크 프로토콜 필드"인지부터 구분한다.** PE/ELF 헤더나 x86/x64 메모리상의 값이면 리틀 엔디안(바이트를 거꾸로 읽는다), TCP/IP/UDP 헤더 같은 네트워크 필드면 빅 엔디안(바이트를 그대로 읽는다)이라고 가정하고 시작한다.

## 단계별 절차

**1) 헥스에디터에서 값을 눈으로 뒤집어 읽기**

HxD나 ImHex에서 4바이트 `64 86 00 00`을 봤다면, 이걸 사람이 읽는 순서로 재배열하려면 뒤에서부터 앞으로 읽는다: `00 00 86 64` → `0x00008664`. 상위 0바이트는 보통 생략하고 `0x8664`로 쓴다.

**2) ImHex의 "해석 패널" 활용하기**

손으로 뒤집는 게 번거롭거나 실수하기 쉬우면, ImHex에서 해당 바이트 범위를 드래그로 선택한 뒤 하단/우측의 **Inspector(값 해석) 패널**에서 `u32 (little endian)` / `u32 (big endian)` 항목을 동시에 확인한다. HxD는 우측 하단에 선택 영역의 크기만 표시되므로, 정확한 정수 해석이 필요하면 ImHex나 파이썬 스크립트를 쓰는 편이 안전하다.

**3) 파이썬으로 변환 (가장 빠르고 실수 없는 방법)**

```python
import struct

# 정수 -> 바이트 (엔디안 지정)
struct.pack('<I', 0x12345678)   # b'\x78\x56\x34\x12'  (리틀 엔디안)
struct.pack('>I', 0x12345678)   # b'\x12\x34\x56\x78'  (빅 엔디안)

# 바이트 -> 정수 (반대 방향)
int.from_bytes(b'\x78\x56\x34\x12', 'little')  # 0x12345678
int.from_bytes(b'\x12\x34\x56\x78', 'big')     # 0x12345678
```

`struct` 포맷 문자열의 첫 글자가 엔디안을 결정한다: `<`는 리틀, `>`는 빅, `!`는 네트워크(빅 엔디안과 동일), `=`는 네이티브(실행 중인 머신 기준, x86/x64에서는 결국 리틀 엔디안).

**4) PE Machine 필드를 직접 확인해보기**

```python
with open("sample.exe", "rb") as f:
    data = f.read()

e_lfanew = int.from_bytes(data[0x3C:0x40], "little")   # PE 헤더 시작 오프셋
machine_off = e_lfanew + 4                               # "PE\0\0" 다음이 Machine 필드
machine = int.from_bytes(data[machine_off:machine_off+2], "little")
print(hex(machine))   # 0x8664 이면 AMD64(x64)
```

파일 바이트는 `64 86` 순서로 들어 있지만, `int.from_bytes(..., "little")`을 쓰면 파이썬이 알아서 순서를 뒤집어 사람이 아는 `0x8664`로 재구성해준다.

**5) ELF EI_DATA 바이트 확인**

```python
with open("sample.elf", "rb") as f:
    ei_data = f.read(16)[5]
print("LE" if ei_data == 1 else "BE" if ei_data == 2 else "unknown")
```

## 명령어/단축키
```python
# 자주 쓰는 struct 포맷 정리
'<B' # 1바이트 unsigned  (엔디안 무관, 1바이트는 순서가 없음)
'<H' # 2바이트 unsigned little-endian  (>H 는 big-endian)
'<I' # 4바이트 unsigned little-endian  (>I 는 big-endian)
'<Q' # 8바이트 unsigned little-endian  (>Q 는 big-endian)
'!H' # network byte order 2바이트 (= big-endian, 소켓 프로그래밍에서 흔히 사용)
```
- ImHex: 바이트 선택 후 Inspector 패널에서 엔디안별 해석값 동시 확인
- HxD: 우클릭 → "선택 영역을 다른 이름으로 저장"으로 잘라내서 별도로 파이썬 분석하는 것도 실전에서 유용

## 출력 해석
- 파일/메모리에서 `78 56 34 12` (증가하는 주소 순)를 봤다면 → 리틀 엔디안 기준 값은 `0x12345678`
- 파일/메모리에서 `12 34 56 78`을 봤다면 → 빅 엔디안 기준 값이거나, 리틀 엔디안이라면 실제 값은 `0x78563412`이므로 두 해석이 완전히 다른 숫자를 만든다 — 반드시 어느 엔디안인지 먼저 확정한 뒤 읽어야 한다.
- PE 파일 오프셋에서 `64 86`을 봤다면 → x64 바이너리의 Machine 필드(`0x8664`)일 가능성이 매우 높다.
- 패킷 덤프에서 `00 50`을 봤다면 → 빅 엔디안 기준 포트 80(HTTP). 같은 바이트를 리틀 엔디안으로 잘못 읽으면 `0x5000`(20480번 포트)이 되어 완전히 틀린 해석이 된다.

## 흔한 실수
- 헥스에디터에서 상수를 그대로(사람이 쓰는 순서로) 검색해서 "파일이 이상하다"고 오해하는 것 — x86/x64 파일 안의 다바이트 값은 항상 뒤집혀 저장되어 있다는 걸 잊는 것.
- 모든 바이너리 필드를 무조건 리틀 엔디안이라고 가정하고, 네트워크 프로토콜 필드(포트, IP, 패킷 길이 등)까지 리틀 엔디안으로 읽어서 값이 완전히 틀리는 것 — 네트워크 바이트 오더는 빅 엔디안이다.
- `struct.pack`/`unpack`에서 포맷 문자를 빼먹어 네이티브(`=` 취급)로 동작시키고, 이게 어떤 엔디안인지 신경 쓰지 않다가 다른 아키텍처/플랫폼에서 결과가 달라지는 것.
- 1바이트(8비트) 값에는 엔디안 개념이 적용되지 않는다는 걸 잊고, 1바이트짜리 필드에도 "순서"를 고민하며 시간을 낭비하는 것 — 바이트가 하나뿐이면 뒤집을 순서 자체가 없다.
- 엔디안(바이트 순서)과 [REV-0024](./rev-0024-twos-complement.md)에서 다룬 2의 보수(부호 해석)를 혼동하는 것 — 엔디안은 "바이트를 어떤 순서로 배치하느냐"이고, 2의 보수는 "그렇게 조합된 값을 양수/음수 중 어떻게 해석하느냐"로 서로 별개의 개념이다.

## 막혔을 때 다음 체크

## 미니 예제
IDA나 헥스에디터로 x64 PE 파일을 열었는데, 파일 오프셋 어딘가에서 다음 6바이트를 봤다고 하자.

```
오프셋      바이트열
0x00F8      50 45 00 00 64 86
```

`50 45 00 00`은 ASCII로 `PE\0\0` — PE 시그니처다. 바로 다음에 오는 `64 86`이 COFF 헤더의 `Machine` 필드(2바이트)다. 이 2바이트를 리틀 엔디안으로 재조합하면:

1. 파일에 저장된 순서: `64`, `86` (낮은 오프셋 → 높은 오프셋)
2. 사람이 읽는 순서로 뒤집기: `86`, `64`
3. 합치면: `0x8664`

`0x8664`는 `IMAGE_FILE_MACHINE_AMD64` 상수이므로, 이 파일은 x64용 PE 실행 파일이라는 뜻이다. 파이썬으로 같은 결과를 확인하면:

```python
>>> raw = bytes.fromhex("6486")
>>> hex(int.from_bytes(raw, "little"))
'0x8664'
```

만약 실수로 빅 엔디안으로 해석했다면 어떻게 될까:

```python
>>> hex(int.from_bytes(raw, "big"))
'0x6486'
```

`0x6486`은 알려진 `Machine` 상수 목록에 없는 값이라 "이 파일이 이상하게 손상됐나?"라고 잘못된 결론을 내리기 쉽다. 실제로는 파일이 손상된 게 아니라, x86/x64 PE 파일은 항상 리틀 엔디안이라는 전제를 놓친 것뿐이다. 이 한 가지 원칙 — **x86/x64에서는 무조건 리틀 엔디안, 예외 없음** — 만 확실히 기억해도 이 글에서 다룬 혼동의 대부분을 피할 수 있다.
