## 한 줄 요약
`union`은 구조체(`struct`)와 문법이 비슷해 보이지만, 각 필드가 **서로 다른 오프셋을 갖는 대신 전부 오프셋 0을 공유**하며 전체 크기도 필드 합이 아니라 **가장 큰 필드의 크기 하나뿐**이므로, 어셈블리에서는 서로 다른 필드에 접근하는 코드가 전부 `[base]`, `[base+0]`처럼 동일한(또는 그 안에 포함되는) 주소를 가리키는 것으로 나타난다.

## 언제 검색해야 하나
- C 코드에 `union`이 등장하는데 구조체와 뭐가 다른지, 메모리를 실제로 어떻게 쓰는지 궁금할 때
- 어셈블리에서 같은 베이스 주소(`[rdi]`, `[rdi+0]`)를 두고 어떤 곳에서는 4바이트로, 어떤 곳에서는 1바이트씩 읽는 등 서로 다른 크기/방식으로 반복 접근하는 코드를 만났을 때
- `sizeof(구조체)`가 예상(필드 크기의 합)보다 훨씬 작게 나와서 이게 구조체가 아니라 union이 아닐까 의심될 때
- 네트워크 패킷 파싱, 타입 펀닝(type punning, 예: `float`를 그 비트 그대로 `int`로 재해석)처럼 "같은 메모리를 다른 타입으로 보는" 코드를 분석할 때

## 핵심 개념

### struct는 "그리고(and)", union은 "또는(or)"
`struct`의 필드들은 동시에 전부 존재하며 각자 다른 메모리 위치(오프셋)를 차지한다(REV-0035). `union`의 필드들은 **동시에 존재하지 않는다** — 정확히는, 메모리 공간을 공유하기 때문에 한 시점에는 그 중 하나의 해석만 "의미가 있다"고 프로그래머가 약속하는 것이다. `union`의 모든 필드는 오프셋 0부터 시작하며, `union`의 전체 크기는 필드들의 크기 합이 아니라 **가장 큰 필드 하나의 크기**(정렬 요건 포함)로 결정된다.

```c
union Value {
    int    i;      // offset 0, 4바이트
    float  f;      // offset 0, 4바이트
    char   b[4];   // offset 0, 4바이트
};
// sizeof(union Value) == 4  (가장 큰 필드가 4바이트이므로)
```

```c
struct SameFields {
    int    i;      // offset 0
    float  f;      // offset 4
    char   b[4];   // offset 8
};
// sizeof(struct SameFields) == 12  (필드마다 별도 공간)
```
구조체 버전은 `i`, `f`, `b`가 서로 다른 주소(`[rdi]`, `[rdi+4]`, `[rdi+8]`)를 갖지만, union 버전은 셋 다 **똑같이 `[rdi]`(오프셋 0)** 를 가리킨다. 어셈블리만 봐서는 "이 함수가 union의 `i`를 쓰는지 `f`를 쓰는지 `b`를 쓰는지" 구분할 수 없고, 오직 **몇 바이트를 어떤 명령어(정수 `mov` vs `movss`)로 읽는지**를 보고 그 시점에 어떤 필드로 "취급"하고 있는지만 추측할 수 있다.

### 타입 펀닝(Type Punning) — union의 가장 흔한 실전 용도
union은 "같은 비트 패턴을 다른 타입으로 재해석"하는 용도로 자주 쓰인다. 대표적으로 부동소수점 값의 비트 패턴을 정수로 직접 들여다보는 경우다.

```c
union FloatBits {
    float f;
    unsigned int u;
};

unsigned int float_to_bits(float val) {
    union FloatBits fb;
    fb.f = val;
    return fb.u;      // val의 비트 패턴을 정수로 재해석해서 반환
}
```
```asm
float_to_bits:
    movss   [rbp-4], xmm0    ; fb.f = val   (오프셋 0에 float로 씀, xmm 레지스터 이용)
    mov     eax, [rbp-4]      ; fb.u 읽기    (같은 오프셋 0을 정수로 씀)
    ret
```
`movss`로 쓴 자리를 바로 `mov eax, [...]`(정수 읽기)로 다시 읽는 패턴이 보이면, "부동소수점 값을 정수 비트 패턴으로 재해석하고 있구나"(REV-0346 IEEE 754 비트 구조 참고)라고 확신할 수 있다. C 표준에서는 이런 식의 타입 펀닝이 엄밀히는 구현 정의(implementation-defined) 동작이지만, 실전 리버싱 대상 바이너리에서는 매우 흔하게 나타난다.

### 네트워크 패킷/바이트 단위 접근 — 배열과 정수를 겹쳐 보기
```c
union Packet {
    unsigned int raw;
    unsigned char bytes[4];
};
```
이 패턴은 4바이트 정수를 한 번에 다루고 싶을 때는 `raw`로, 바이트 단위로 하나씩 조작(엔디안 변환, 체크섬 계산 등)하고 싶을 때는 `bytes[0]`~`bytes[3]`로 접근하는 용도로 쓰인다. 어셈블리에서는 오프셋 0에 대한 4바이트 읽기(`mov eax, [rdi]`)와 오프셋 0/1/2/3에 대한 1바이트 읽기(`mov al, [rdi]`, `mov al, [rdi+1]` ...)가 같은 함수 안에 섞여서 나타나면 이 패턴을 의심한다.

### union 안에 구조체가 들어있는 경우 — 태그드 유니온(Tagged Union)
실전 코드에서는 union 자체만 단독으로 쓰기보다, "지금 이 union이 어떤 필드로 쓰이고 있는지"를 나타내는 별도의 정수 필드(태그, tag)와 묶어서 구조체 안에 함께 두는 패턴이 흔하다.

```c
struct TaggedValue {
    int type;        // offset 0: 0=int, 1=float, 2=string
    union {
        int    i;    // offset 4
        float  f;    // offset 4
        char  *s;    // offset 4 (또는 8, 정렬에 따라 다름)
    } value;
};
```
어셈블리에서는 `type` 필드(오프셋 0)를 먼저 읽어 `cmp`/`switch`로 분기한 뒤, 각 분기마다 같은 오프셋(예: 4)을 서로 다른 크기/명령어로 접근하는 코드가 나타난다. 이런 "분기 후 같은 오프셋을 다르게 해석"하는 패턴을 보면 태그드 유니온 구조를 의심하고, 분기 조건에 쓰인 태그 값들을 모아 `enum`을 역으로 복원할 수 있다.

## 화면/코드에서 보이는 징후
- 같은 베이스 레지스터/오프셋(`[rdi]`, `[rdi+0]`)을 서로 다른 위치에서 서로 다른 명령어(정수 `mov` vs `movss`/`movsd`)나 다른 크기(1/2/4/8바이트)로 반복 접근한다.
- 구조체처럼 보이는데 필드별 오프셋이 전부 0으로 겹치거나, 오프셋 목록을 모아보니 "겹치는 구간"이 있다.
- `sizeof`로 추정한 전체 크기가 필드 개수에 비해 훨씬 작다(필드 합이 아니라 최대값과 일치).
- 정수 값을 계산한 직후 그 값을 바로 `float`/`double` 관점으로 재해석하는(또는 그 반대) 코드가 붙어 있다.

## 가장 먼저 할 것
같은 오프셋을 서로 다른 방식으로 접근하는 코드를 발견하면, 먼저 그 시점에 어떤 명령어(정수용 `mov`인지 SSE용 `movss`/`movsd`인지)가 쓰였는지로 "지금 이 순간에는 어떤 타입으로 취급 중인지"를 판단한다. 그 다음 함수 전체에서 그 오프셋에 대한 접근이 몇 가지 다른 방식으로 나타나는지 모아보면 union의 필드 목록을 역으로 복원할 수 있다.

## 단계별 절차
1. 동일 오프셋에 대한 서로 다른 접근 패턴(명령어 종류, 읽는 크기)을 전부 수집한다.
2. 각 접근 방식이 어떤 C 타입에 대응하는지 추정한다(정수 `mov` + 4바이트 → `int`/`float`처럼 크기만으로는 구분 안 되는 경우 앞뒤 문맥으로 판단, SSE 명령어 사용 시 확실히 `float`/`double`).
3. 접근 방식이 조건 분기(태그 값)에 따라 달라지는지 확인해 태그드 유니온 여부를 판단한다.
4. IDA에서 해당 변수/필드를 union 타입으로 직접 정의(Structures 창에서 union 추가)해 디컴파일 결과를 정리한다.
5. 디버거로 실제 값을 여러 타입으로 동시에 재해석해 보며 의도한 사용 방식을 검증한다.

## 명령어/단축키
```
(gdb) print val.i          # union 변수를 int 필드로 해석해서 출력 (디버그 정보 있을 때)
(gdb) print val.f           # 같은 메모리를 float 필드로 해석해서 출력
(gdb) x/4xb &val             # union의 raw 바이트 4개를 헥스로 직접 확인
(gdb) print/x *(int*)&val   # 디버그 정보 없이도 강제로 int로 재해석해서 확인
(gdb) print *(float*)&val   # 같은 자리를 float로 재해석
```
IDA: Structures 창(`Shift+F9`)에서 `Insert` 후 union 타입(멤버들의 오프셋을 전부 0으로) 정의 가능.

## 출력 해석
- 같은 메모리 주소를 `int`로 출력했을 때와 `float`로 출력했을 때 전혀 다른 숫자가 나오는 것은 정상이다 — 같은 비트 패턴을 다른 규칙(2의 보수 vs IEEE 754)으로 해석했기 때문이다(REV-0346 참고).
- 오프셋 목록을 모았을 때 서로 "겹치는" 구간이 있다면 구조체가 아니라 union(또는 struct 안에 중첩된 union)이라는 강한 증거다.
- 태그 값에 따라 분기하는 코드에서, 각 분기 안의 접근 방식이 서로 다르면 그 분기 조건이 곧 union의 "현재 활성 필드"를 나타낸다.

## 흔한 실수
- union의 필드들이 서로 다른 오프셋을 가진다고 착각해서(구조체처럼) 오프셋 계산을 잘못 복원하는 것.
- 타입 펀닝 코드를 보고 "버그"라고 오해하는 것 — `union`을 이용한 의도적인 비트 재해석은 임베디드/네트워크/게임 코드에서 흔히 쓰이는 정상적인 기법이다.
- 태그드 유니온에서 태그 필드를 확인하지 않고 무조건 특정 필드로만 해석해서, 실제로는 다른 타입으로 쓰이고 있는 값을 잘못 판독하는 것.
- `union` 크기를 필드 합으로 계산해서 스택 프레임 크기나 구조체 전체 크기 추정을 틀리는 것 — 반드시 "가장 큰 필드 하나"만큼만 차지한다는 점을 기억해야 한다.

## 막혔을 때 다음 체크
- 구조체 필드 오프셋의 기본 개념과 패딩이 헷갈리면 → REV-0035 구조체 접근이 어셈블리로 변하는 방식
- 부동소수점 비트 구조 자체가 헷갈려서 타입 펀닝 결과를 이해하기 어렵다면 → REV-0346 부동소수점 표현 IEEE 754 기초
- XMM 레지스터로 float/double이 어떻게 로드/저장되는지 헷갈리면 → REV-0347 부동소수점이 어셈블리(XMM)로 보일 때 읽는 법

## 미니 예제
```c
union FloatBits {
    float f;
    unsigned int u;
};

unsigned int get_sign_bit(float val) {
    union FloatBits fb;
    fb.f = val;
    return (fb.u >> 31) & 1;   // 부호 비트만 추출
}
```

x64 SysV 어셈블리(개념 설명용):
```asm
get_sign_bit:
    movss   [rbp-4], xmm0     ; fb.f = val   (오프셋 0에 float로 저장, xmm0에서 옮김)
    mov     eax, [rbp-4]       ; fb.u 읽기    (같은 오프셋 0을 정수로 재해석)
    shr     eax, 31             ; 31비트 오른쪽으로 밀어서 부호 비트만 남김
    and     eax, 1              ; 혹시 모를 상위 비트 제거
    ret
```

IDA/Ghidra는 union 타입을 인식했다면 다음과 같이 복원한다.

```c
unsigned int get_sign_bit(float val)
{
  union FloatBits fb;

  fb.f = val;
  return (fb.u >> 31) & 1;
}
```

`movss`로 오프셋 0에 float를 쓰고, 바로 다음 줄에서 같은 오프셋 0을 정수 `mov`로 읽는 이 조합이 union 타입 펀닝의 전형적인 시그니처다. 구조체였다면 `f`와 `u`가 서로 다른 오프셋(예: 0과 4)을 가졌겠지만, union이므로 완전히 같은 주소를 공유한다.

## 관련 글
- REV-0035 — 구조체 접근이 어셈블리로 변하는 방식
- REV-0346 — 부동소수점 표현 IEEE 754 기초
- REV-0347 — 부동소수점이 어셈블리(XMM)로 보일 때 읽는 법

## 출처/검증
- `union`의 오프셋 공유 및 크기 결정 규칙(가장 큰 멤버 기준): ISO C 표준(C11) 6.7.2.1 Structure and union specifiers 섹션 기준.
- 타입 펀닝(비트 패턴 재해석)의 구현 정의 동작 및 실전 사용 패턴: ISO C 표준(C11) 6.5.2.3 Structure and union members 및 실제 GCC/Clang 컴파일 결과 기준 (2026-09-09 확인).
