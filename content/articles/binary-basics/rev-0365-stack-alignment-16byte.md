## 한 줄 요약
x64 호출 규약(Windows·SysV 공통)은 `call` 명령이 실행되는 시점에 스택 포인터(`RSP`)가 항상 16바이트 배수 주소를 가리키도록 요구하며, 이는 `movaps`/`movdqa` 같은 정렬된 SIMD 명령어가 정렬되지 않은 주소에서 실행되면 크래시나는 것을 막기 위한 규약이다.

## 언제 검색해야 하나
- 함수 프롤로그의 `sub rsp, 0x28`, `sub rsp, 0x38`처럼 스택을 내리는 크기가 8의 배수가 아니라 이상하게 애매한 숫자로 보일 때
- `call` 직전에 `and rsp, 0FFFFFFFFFFFFFFF0h`처럼 스택 포인터를 강제로 특정 배수로 맞추는 코드가 보일 때
- 리버싱한 함수를 직접 호출하는 스크립트/셸코드를 만들었는데 `movaps` 명령에서 세그폴트가 날 때
- IDA/Ghidra 스택 프레임 레이아웃에서 로컬 변수 크기 합과 `sub rsp` 크기가 딱 안 맞고 패딩이 껴 있는 것처럼 보일 때

## 핵심 개념

### 정렬이 필요한 이유 — SIMD 명령어의 하드웨어 제약
현대 CPU는 SSE/AVX 같은 SIMD(Single Instruction Multiple Data) 명령어로 16바이트(SSE, `XMM` 레지스터) 또는 32바이트(AVX, `YMM` 레지스터) 단위 데이터를 한 번에 처리한다. 이 중 `movaps`, `movapd`, `movdqa` 같은 "정렬된(aligned) 이동" 명령어는 **피연산자 메모리 주소가 반드시 16바이트 배수여야 한다**는 하드웨어 제약이 있다. 주소가 16의 배수가 아닌 상태에서 이 명령어를 실행하면 CPU가 `#GP`(General Protection Fault) 예외를 발생시키고, 이는 프로그램 크래시(세그폴트)로 이어진다. (정렬 요구가 없는 `movups`, `movupd`, `movdqu` 같은 "정렬 안 된(unaligned)" 버전도 있지만 대체로 약간 느리다.)

컴파일러는 지역 배열/구조체를 스택에 SIMD로 빠르게 초기화하거나 복사하는 코드를 자주 생성하는데, 이때 스택에 있는 그 데이터의 주소가 16바이트 배수라는 것을 컴파일러가 보장할 수 있어야 정렬된 명령어를 안전하게 쓸 수 있다. 그래서 x64 호출 규약 자체가 "함수 호출 시점의 스택 정렬"을 표준으로 못 박아버렸다.

### x64 호출 규약의 정렬 규칙
Windows x64(Microsoft x64 calling convention)와 Linux SysV x64(System V AMD64 ABI) 모두 동일한 규칙을 정의한다: **`call` 명령이 실행되는 순간, `RSP`는 16바이트 배수여야 한다.** 여기서 미묘한 부분은, `call`은 실행되면서 8바이트짜리 반환 주소를 스택에 `push`하므로, `call` 실행 직후(피호출 함수 진입 시점)에는 `RSP`가 항상 `16의 배수 - 8`, 즉 `RSP % 16 == 8`인 상태가 된다는 점이다.

이 규칙은 함수 진입 시 자동으로 성립하는 게 아니라, **모든 함수가 이 규칙을 지키도록 스스로 스택을 관리해야** 유지된다. 함수 프롤로그에서 로컬 변수 공간을 확보하려고 `sub rsp, N`을 실행할 때, 컴파일러는 이 함수가 끝나고 자신이 호출하는 다른 함수를 `call`하는 시점에 다시 16바이트 정렬이 맞아떨어지도록 `N` 값을 계산한다.

### sub rsp 크기가 8의 배수인데 16의 배수가 아닌 이유
함수 진입 시점에 `RSP % 16 == 8`(반환 주소 push 때문)이므로, 그 상태에서 로컬 변수를 위해 `sub rsp, N`을 하고 나면 최종 `RSP`가 다시 16의 배수가 되려면 **`N`도 8의 배수이면서 동시에 `(N + 8) % 16 == 0`, 즉 `N % 16 == 8`**이어야 한다. 그래서 함수 프롤로그에 `sub rsp, 0x28`(0x28 = 40 = 16*2+8), `sub rsp, 0x38`(56 = 16*3+8)처럼 "16으로 나누면 8이 남는" 애매해 보이는 숫자가 자주 나오는 것이다. 필요한 로컬 변수 크기가 이 조건에 딱 맞지 않으면, 컴파일러는 남는 공간을 패딩으로 채워서라도 정렬 조건을 맞춘다.

### Windows x64의 섀도우 스페이스와 함께 고려
Windows x64는 함수를 호출할 때 인자를 레지스터(`RCX`/`RDX`/`R8`/`R9`)로 넘기더라도, 피호출 함수가 이 값을 스택에 저장할 수 있도록 최소 32바이트(0x20)의 "섀도우 스페이스(shadow space)"를 호출자가 미리 확보해야 한다. 이 32바이트도 16의 배수이므로 정렬 계산에 자연스럽게 들어맞고, 그 결과 Windows x64 함수 프롤로그에서 `sub rsp, 0x28`(섀도우 스페이스 0x20 + 정렬 유지용 8) 같은 패턴이 매우 흔하게 보인다.

### 정렬이 깨졌을 때 컴파일러가 직접 고치는 코드
함수 안에서 `alloca()`처럼 런타임에 크기가 결정되는 가변 크기 스택 할당을 쓰면, 컴파일러는 컴파일 타임에 정확한 오프셋을 계산할 수 없다. 이런 경우 런타임에 직접 스택 포인터를 강제로 정렬시키는 코드를 넣는다.

```asm
and rsp, 0FFFFFFFFFFFFFFF0h   ; RSP를 16의 배수로 강제로 내림(하위 4비트 클리어)
```

`0xF0` 마스크(하위 4비트를 0으로)로 `AND`하면 `RSP`가 반드시 16의 배수 주소로 내려간다(REV-0026 마스크 개념과 동일한 원리). 이런 코드를 보면 "이 함수는 SIMD 정렬이 필요한 지역 변수가 있거나, 가변 크기 스택 할당을 쓴다"고 해석할 수 있다.

## 화면/코드에서 보이는 징후
- 함수 프롤로그에 `sub rsp, 0x28`, `sub rsp, 0x38`, `sub rsp, 0x48`처럼 16으로 나누면 나머지가 8인 값이 반복됨
- `call` 직전에 `and rsp, ...F0h`로 스택 포인터를 강제 정렬하는 코드
- `movaps xmm0, [rsp+20h]` 같은 정렬 SIMD 명령어가 스택 접근에 쓰이는 함수
- 리버싱한 코드를 직접 호출하는 셸코드/후킹 코드를 짤 때, `call` 전 스택 정렬을 맞추지 않아 특정 함수에서만 크래시가 남

## 가장 먼저 할 것
크래시가 `movaps`/`movdqa` 명령어(정렬 SIMD)에서 발생했다면, 가장 먼저 그 시점의 `RSP`(또는 접근 대상 주소)가 16의 배수인지 계산기로 확인한다. GDB/x64dbg에서 `RSP` 값을 16진수로 보고 마지막 자리가 `0`으로 끝나는지(16의 배수는 항상 16진수 마지막 자리가 0) 확인하면 빠르다.

## 단계별 절차
1. 크래시 지점의 명령어가 `movaps`/`movdqa` 등 정렬 요구 명령어인지 확인한다.
2. 그 명령어가 접근하는 메모리 주소를 계산한다(레지스터 + 오프셋).
3. GDB에서 `p/x $rsp` 또는 x64dbg에서 레지스터 창으로 실제 주소값을 확인하고, 16진수 마지막 자리가 0인지 본다(0이 아니면 정렬 안 됨).
4. 직접 함수를 호출하는 코드(셸코드, 후킹, 수동 `call`)를 작성했다면 `call` 직전 `RSP`가 16의 배수인지 확인하고, 필요하면 `push`로 8바이트를 더 넣거나 `and rsp, -0x10`으로 강제 정렬한다.
5. 함수 프롤로그의 `sub rsp, N` 크기를 보고 `N % 16 == 8`인지 검산해, 정상적인 x64 정렬 규약을 따르는 함수인지 확인한다.

## 명령어/단축키
```
(gdb) p/x $rsp                 # 현재 RSP를 16진수로 확인
(gdb) p $rsp % 16               # 16으로 나눈 나머지 확인 (0이어야 call 가능 시점)
(gdb) x/4xg $rsp                # RSP 주변 8바이트씩 4개 확인
```
```python
# 파이썬으로 정렬 여부 빠르게 검산
rsp = 0x7fffffffe4a8
print(rsp % 16)   # 0이면 16바이트 정렬됨
```
x64dbg: 레지스터 패널에서 RSP 값 우클릭 → Follow in Dump으로 실제 메모리 상태 확인.

## 출력 해석
- `RSP % 16 == 0`이면 그 시점에서 `call`을 실행해도 안전하다(정렬 유지).
- `RSP % 16 == 8`이면 방금 `call`이 실행되어 반환 주소가 push된 직후 상태(함수 진입 시점)로, 정상이다.
- 그 외의 나머지 값(1~7, 9~15)이 나온다면 어딘가에서 정렬 규약을 어긴 것 — 직접 작성한 셸코드/후킹 코드에서 `push`/`sub rsp` 개수를 잘못 맞췄을 가능성이 크다.

## 흔한 실수
- 모든 `sub rsp` 크기가 16의 배수여야 한다고 착각하는 것 — 정확히는 함수 진입 시점의 오프셋(-8)까지 감안해 "16으로 나누면 8이 남는" 크기가 정상이다.
- 직접 어셈블리로 함수를 호출하는 코드를 짤 때 정렬을 신경 쓰지 않고 아무 때나 `call`을 실행해서, 특정 SIMD 명령어를 쓰는 라이브러리 함수(`printf`의 부동소수점 처리 경로 등)에서만 간헐적으로 크래시가 나는 것을 디버깅하지 못하는 것.
- `and rsp, 0xF0` 계열 코드를 보고 "이건 마스킹으로 값을 필터링하는 암호화 로직"이라고 오해하는 것 — 실제로는 스택 정렬을 위한 관용구다.
- x86(32비트)도 x64와 같은 16바이트 정렬 규약을 강제한다고 착각하는 것 — x86 cdecl/stdcall은 이런 엄격한 16바이트 정렬 요구가 없다(SSE를 쓰는 일부 함수에서만 별도로 신경 쓴다). 16바이트 정렬 요구는 x64 호출 규약의 특징이다.

## 막혔을 때 다음 체크
- 애초에 함수 프롤로그의 `sub rsp` 크기가 스택 프레임 전체에서 어떤 역할인지 헷갈리면 → REV-0031 스택 프레임이 무엇인지
- AND로 하위 비트를 지우는 마스킹 원리 자체가 헷갈리면 → REV-0026 8비트 16비트 24비트 32비트 64비트 마스크
- Windows x64와 SysV x64의 인자 전달 레지스터 차이가 궁금하면 → REV-0032 함수 인자와 반환값이 어디에 있는지
- 셸코드/직접 호출 코드에서 계속 크래시가 난다면 GDB로 크래시 순간의 `RSP`와 명령어를 함께 확인하는 절차부터 다시 밟는다.

## 미니 예제
Windows x64에서 흔히 보이는 프롤로그를 보자.
```asm
; void __fastcall Func(int a1, int a2)
sub     rsp, 28h        ; 0x28 = 40 = 16*2 + 8, 진입시 RSP%16==8과 맞물려 call 시점엔 다시 16배수
mov     [rsp+30h], ecx  ; a1을 섀도우 스페이스에 저장
mov     [rsp+38h], edx  ; a2를 섀도우 스페이스에 저장
call    SomeOtherFunc   ; 이 시점에 RSP는 반드시 16의 배수
add     rsp, 28h
retn
```
`sub rsp, 28h`는 섀도우 스페이스 `0x20`과 정렬 유지용 `8`을 합친 크기다. 만약 이 함수를 리버싱해서 직접 호출하는 파이썬/pwntools 셸코드를 짠다면, 자신의 `call SomeOtherFunc` 이전에 스택이 16의 배수가 되도록 호출자 쪽에서도 정렬을 맞춰야 한다는 뜻이다.

## 관련 글
- REV-0031 — 스택 프레임이 무엇인지
- REV-0032 — 함수 인자와 반환값이 어디에 있는지
- REV-0026 — 8비트 16비트 24비트 32비트 64비트 마스크
- REV-0037 — 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 이유
