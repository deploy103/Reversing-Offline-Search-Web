## 한 줄 요약
문자열이 깨져 보이는 건 대부분 문자열 자체가 손상된 게 아니라, **바이트를 잘못된 인코딩(문자 집합)으로 해석**했기 때문이며, 특히 각 문자 사이에 `00` 바이트가 하나씩 끼어 있다면 그건 깨진 게 아니라 UTF-16(wide char) 문자열을 8비트 텍스트로 착각해서 보고 있는 것이다.

## 언제 검색해야 하나
- `strings` 명령이나 IDA의 문자열 뷰(View > Open subviews > Strings)에서 한글/특수문자가 물음표(`?`)나 네모(``)로 보일 때
- 문자열 바이트를 헥스로 봤더니 `48 00 65 00 6C 00 6C 00 6F 00`처럼 문자마다 `00`이 하나씩 끼어 있을 때
- 리소스 섹션이나 `.rdata`에서 뽑은 한글 문자열이 UTF-8로 열어도 텍스트 에디터에서 깨질 때
- 같은 프로그램인데 Windows용 문자열과 Linux용 문자열이 바이트 배열은 비슷한데 해석 결과가 다를 때

## 핵심 개념
문자열은 결국 바이트의 나열일 뿐이고, 그 바이트를 "어떤 문자로 읽을지"를 정하는 규칙이 인코딩이다. 같은 바이트 시퀀스라도 인코딩을 잘못 고르면 완전히 다른(또는 깨진) 글자가 나온다.

**대표적인 인코딩과 특징**:
- **ASCII**: 1바이트당 1글자, 영문/숫자/기호만(0x00~0x7F). 한글은 표현 불가.
- **UTF-8**: 가변 길이(1~4바이트). 영문은 ASCII와 동일한 1바이트, 한글은 보통 3바이트(예: `한` = `EC 95 88`). 리눅스/웹에서 사실상 표준.
- **UTF-16(LE)**: 고정 2바이트(또는 서로게이트 쌍이면 4바이트) 단위. Windows API(`WCHAR`, `wchar_t`)의 기본 문자열 형식. 영문 `H`도 `48 00`처럼 항상 2바이트로 저장되기 때문에, 이걸 그냥 ASCII 텍스트 뷰어로 열면 **글자 사이마다 `00`이 낀 것처럼 보이거나, 짝수 바이트만 읽는 도구는 `H`, `e`, `l`, `l`, `o`를 제대로 뽑아내지만 홀수 바이트를 기준으로 읽는 도구는 완전히 다른 글자를 뽑아낸다.**
- **EUC-KR / CP949(MS949)**: 옛 Windows 한글 프로그램에서 흔히 쓰던 완성형 한글 인코딩. 2바이트로 한글 한 글자를 표현하지만 UTF-8과는 바이트 값 자체가 다르다.

**구체적 숫자 예시**: 한글 `"안녕"`을 세 가지 인코딩으로 저장하면 완전히 다른 바이트가 나온다.
- UTF-8: `EC 95 88 EB 85 95` (6바이트)
- UTF-16LE: `48 C5 55 B1` (4바이트, 문자당 2바이트)
- CP949(EUC-KR): `BE C8 B3 E7` (4바이트, 문자당 2바이트지만 UTF-16과 값이 다름)

이 셋은 전혀 다른 바이트 나열이다. 그러니 리소스에서 뽑은 바이트가 `BE C8 B3 E7`인데 이걸 UTF-8로 디코딩하려 하면 당연히 깨진다 — 애초에 UTF-8로 인코딩된 바이트가 아니기 때문이다. **문자열이 깨졌다는 건 바이트가 손상됐다는 뜻이 아니라, 디코더가 원본 인코딩을 잘못 추측했다는 뜻**인 경우가 압도적으로 많다.

## 화면/코드에서 보이는 징후
- `strings` 기본 옵션으로는 UTF-16 문자열이 거의 안 잡히거나, 영문 부분만 한 글자씩 끊겨서 나옴
- IDA가 문자열을 `C string`으로 인식했는데 실제로는 wide string이라 뒤에 이상한 문자가 덧붙어 보임
- 한글이 포함된 리소스 문자열을 UTF-8 텍스트 에디터로 열면 한글 자리에 깨진 특수문자(예: `占쏙옙`)가 나타남 — 이건 CP949 바이트를 UTF-8로 잘못 디코딩했을 때 나오는 전형적인 패턴이다
- 헥스 덤프에서 문자 사이마다 `00`이 규칙적으로 반복됨(UTF-16LE 신호)

## 가장 먼저 할 것
문자열 바이트를 헥스로 먼저 확인한다. 문자 사이에 `00`이 규칙적으로 끼어 있으면 UTF-16이다. 그게 아니고 한글처럼 보이는 2바이트 조합이 반복되면 UTF-8인지 CP949인지 구분해야 한다.

## 단계별 절차

**1) 헥스 패턴으로 인코딩 후보 좁히기**
`00`이 문자마다 하나씩 끼어 있으면 UTF-16LE(리틀 엔디안이므로 낮은 바이트가 먼저 나옴), 안 끼어 있으면 ASCII/UTF-8/CP949 계열이다.

**2) IDA/Ghidra에서 문자열 타입 강제 지정**
IDA에서 데이터 위에 커서를 놓고 `Alt+A`(또는 우클릭 > Data > Strings)로 문자열 타입을 바꿔본다. `C-style ASCII string`으로 안 보이면 `Unicode string(UTF-16)`로 바꿔서 다시 확인한다. Ghidra는 데이터 위에서 우클릭 > Data > TerminatedCString / TerminatedUnicodeString(변환 후 재분석)으로 전환한다.

**3) 도구로 강제 디코딩해서 비교**
```bash
# UTF-16LE로 뽑기
strings -e l target.bin
# 그냥 ASCII로 뽑기 (비교용)
strings target.bin
```

**4) Python으로 여러 인코딩을 직접 시도**
```python
data = bytes.fromhex("bec8b3e7")
for enc in ["utf-8", "utf-16le", "cp949", "euc-kr"]:
    try:
        print(enc, "->", data.decode(enc))
    except UnicodeDecodeError:
        print(enc, "-> 디코딩 실패")
```
CP949로 시도했을 때만 예외 없이 깔끔한 한글이 나오면 원본 인코딩이 CP949였다는 뜻이다.

## 명령어/단축키
```text
strings -e l file       # 리틀 엔디안 UTF-16 문자열 추출
strings -e b file       # 빅 엔디안 UTF-16 문자열 추출
IDA: 데이터 위에서 Alt+A  # 문자열 타입(ASCII/Unicode) 전환
Ghidra: 우클릭 > Data > TerminatedUnicodeString
Python: data.decode("cp949"), data.decode("utf-16le")
HxD: 하단 상태바에서 "코드 페이지" 변경하여 즉시 미리보기
```

## 출력 해석
- Python `decode()`가 `UnicodeDecodeError` 없이 성공했다고 해서 무조건 정답은 아니다 — 우연히 다른 인코딩으로도 유효한 바이트 시퀀스가 될 수 있으므로, 나온 텍스트가 실제로 말이 되는 한글/문맥인지 눈으로 확인해야 한다.
- CP949 바이트를 UTF-8로 잘못 디코딩하면 특정 특수문자가 반복되는 패턴(예: 물음표 다이아몬드)이 나오는데, 이는 "디코더가 원본 인코딩을 잘못 짚었다"는 강한 신호다.

## 흔한 실수
- Windows API(`MessageBoxW`, `lstrlenW` 등 `W` 접미사 함수) 근처의 문자열을 무조건 ASCII로 보고 넘어가는 것 — `W` 계열 API는 UTF-16 문자열을 기대한다.
- 문자열이 안 보인다고 바로 "패킹/암호화됐다"고 단정하는 것 — 실제로는 단순히 wide string이라 기본 `strings`에 안 잡히는 경우가 많다.
- CP949와 UTF-8을 혼동해서 옛날 한국 Windows 프로그램의 리소스를 UTF-8 전용 도구로만 열어보고 "깨졌다"고 결론 내리는 것.
- 문자열 끝의 널 종료(`\x00`)를 UTF-16에서는 2바이트(`00 00`)로 확인해야 하는데 1바이트만 보고 문자열 길이를 잘못 계산하는 것.

## 막혔을 때 다음 체크
- 문자열이 애초에 메모리/파일에 어떻게 저장되는지 원리부터 다시 보고 싶으면 REV-0036 문서로 이동.
- 엔디안 개념 자체가 헷갈리면 REV-0023 문서로 이동.
- 인코딩 문제가 아니라 진짜 암호화/난독화가 의심되면 정적 분석 카테고리의 문자열 암호화 관련 글을 검색.

## 미니 예제
IDA에서 다음과 같은 바이트가 보였다고 하자.
```
DB 08: 61 00 64 00 6D 00 69 00 6E 00 00 00
```
문자 사이마다 `00`이 껴 있으므로 UTF-16LE로 의심하고 2바이트씩 묶어 읽는다: `61 00`=`a`, `64 00`=`d`, `6D 00`=`m`, `69 00`=`i`, `6E 00`=`n`, `00 00`=문자열 종료. 합치면 `"admin"`이라는 wide string이다. 만약 이 바이트를 그냥 ASCII로 읽었다면 `a`, `\0`, `d`, `\0`, ... 처럼 문자마다 널 문자가 끼어 있는 것처럼 보여 도구에 따라 첫 글자 `a`만 뽑히고 나머지는 잘려나갔을 것이다.
