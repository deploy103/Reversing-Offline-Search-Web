## 한 줄 요약
x86 계열 CPU는 같은 물리적 레지스터를 8/16/32/64비트 폭으로 쪼개 부르는 이름이 따로 있고(예: `AL`⊂`AX`⊂`EAX`⊂`RAX`), x64에서는 32비트 하위 레지스터에 값을 쓰면 상위 32비트가 자동으로 0으로 지워지지만 16비트·8비트에 쓰면 상위 비트가 그대로 남는다는 것이 가장 중요한 함정이다.

## 언제 검색해야 하나
- 디스어셈블리에 `EAX`, `RAX`, `AX`, `AL`처럼 이름이 다른데 왜 같은 레지스터를 가리키는 것 같은지 헷갈릴 때
- `mov eax, 0`은 상위 비트까지 지우는 것 같은데 `mov al, 0`은 왜 그렇지 않은지 궁금할 때
- `R8D`, `R9W`, `R12B`처럼 처음 보는 레지스터 이름이 나왔을 때
- 바이트 스트림에 `0x48`, `0x49` 같은 낯선 접두 바이트(REX 프리픽스)가 계속 붙어있는 이유가 궁금할 때
- x86 코드와 x64 코드에서 함수 인자를 넘기는 방식이 왜 다른지 확인해야 할 때

## 핵심 개념

### 1) 하나의 레지스터, 여러 개의 이름
x86/x64 CPU는 물리적으로 64비트(x64 기준) 저장 공간을 가진 범용 레지스터(General Purpose Register, GPR)를 여러 개 갖고 있다. 이 저장 공간의 **일부만 잘라서 접근**할 수 있도록 폭마다 다른 이름을 붙여 놓았다. 즉 `EAX`와 `RAX`는 "다른 레지스터"가 아니라 "같은 물리적 저장 공간을 얼마나 넓게 보느냐"의 차이다.

레지스터 하나(`A` 계열, 즉 RAX/EAX/AX/AH/AL)를 기준으로 포함 관계를 그려보면:

```
RAX  (64비트, bit63 ~ bit0)                x64 전용
 └─ EAX (하위 32비트, bit31 ~ bit0)         x86/x64 공통
     └─ AX  (하위 16비트, bit15 ~ bit0)     x86/x64 공통
         ├─ AH (bit15 ~ bit8, 상위 바이트)  x86/x64 공통 (레거시)
         └─ AL (bit7 ~ bit0, 하위 바이트)   x86/x64 공통
```

`RAX`의 하위 32비트를 떼어낸 것이 `EAX`이고, `EAX`의 하위 16비트를 떼어낸 것이 `AX`이며, `AX`는 다시 `AH`(상위 바이트)와 `AL`(하위 바이트)로 나뉜다. 이 네 이름은 전부 **같은 물리적 비트를 공유**한다. `AL`에 값을 쓰면 `AX`, `EAX`, `RAX`의 하위 8비트도 함께 바뀐 것이다.

### 2) 전체 레지스터 이름표 (x86 8개 + x64에서 추가되는 R8~R15)

x86(32비트)에서 쓰던 범용 레지스터는 8개(`A`, `B`, `C`, `D`, `SI`, `DI`, `BP`, `SP` 계열)이고, x64에서는 여기에 `R8`~`R15`가 새로 8개 더 생겨서 총 16개가 된다.

| 64비트 (x64 전용) | 32비트 | 16비트 | 8비트(하위) | 8비트(상위, 레거시) |
|---|---|---|---|---|
| RAX | EAX | AX | AL | AH |
| RBX | EBX | BX | BL | BH |
| RCX | ECX | CX | CL | CH |
| RDX | EDX | DX | DL | DH |
| RSI | ESI | SI | SIL | (없음) |
| RDI | EDI | DI | DIL | (없음) |
| RBP | EBP | BP | BPL | (없음) |
| RSP | ESP | SP | SPL | (없음) |
| R8  | R8D | R8W | R8B | (없음) |
| R9  | R9D | R9W | R9B | (없음) |
| R10 | R10D | R10W | R10B | (없음) |
| R11 | R11D | R11W | R11B | (없음) |
| R12 | R12D | R12W | R12B | (없음) |
| R13 | R13D | R13W | R13B | (없음) |
| R14 | R14D | R14W | R14B | (없음) |
| R15 | R15D | R15W | R15B | (없음) |

**읽는 규칙**: `R8`~`R15`는 새 레지스터라서 접미사로 폭을 구분한다 — `D`(Doubleword, 32비트), `W`(Word, 16비트), `B`(Byte, 8비트), 접미사 없음(64비트). 반면 `A`/`B`/`C`/`D` 계열은 8086 시절부터 내려온 레거시 이름이라 접미사 규칙이 다르고(`E` 접두사=32비트, `R` 접두사=64비트), `AH`처럼 상위 바이트를 따로 부르는 이름은 원래 8개 레지스터 중 `AX`/`BX`/`CX`/`DX` 4개에만 존재한다. `SI`/`DI`/`BP`/`SP`와 `R8`~`R15`는 **8비트 접근 시 항상 하위 바이트만 있고, "상위 바이트" 별명은 아예 없다.** (`SIL`, `R8B` 등은 전부 하위 바이트다.)

### 3) x86과 x64의 근본적 차이
- x86(32비트 모드)에는 `EAX`까지만 존재한다. `RAX`, `R8`~`R15`는 x64(64비트 모드)에서만 존재하며, 32비트 모드의 어셈블러/디스어셈블러는 이 이름들을 아예 인식하지 못한다.
- x64는 x86의 상위 호환이다. 즉 x64 CPU에서도 `EAX`, `AX`, `AL` 같은 32/16/8비트 이름은 그대로 쓸 수 있다. 다만 **그 레지스터가 물리적으로는 64비트 RAX의 일부**라는 점이 x86 시절과 다르다.

## 화면/코드에서 보이는 징후
- IDA/Ghidra에서 x64 바이너리인데 `mov eax, [rbp-4]`처럼 32비트 레지스터와 64비트 레지스터가 한 함수 안에 섞여 나오는 경우 — 정상이다. 정수 연산은 대개 32비트(`int`)로, 포인터 연산은 64비트(`long`/포인터)로 하기 때문이다.
- x64dbg/GDB 레지스터 창에 `RAX`, `RBX`, ... `R8`, `R9`, ... `R15`까지 16개가 보이는데, x32dbg나 32비트 GDB에서는 `EAX`부터 `EDI`까지 8개만 보이는 경우
- 디스어셈블리 바이트 열에 `48 89 E5`, `40 8A C1`처럼 `4X` 계열 바이트가 명령어 앞에 자주 붙어있는 경우 (REX 프리픽스, x64 코드라는 신호)
- `lea rax, [rip+0x2ee5]`처럼 `rip`을 직접 피연산자로 쓰는 명령어가 보이는 경우 — x64 전용 주소 지정 방식
- 함수 진입부에서 `RCX`/`RDX`/`R8`/`R9`(Windows) 또는 `RDI`/`RSI`/`RDX`/`RCX`/`R8`/`R9`(Linux)가 스택으로 옮겨지는(spill) 코드가 반복되는 경우

## 가장 먼저 할 것
바이너리를 열었을 때 IDA/Ghidra의 아키텍처 표시나 `file` 명령 출력을 확인해서 **x86인지 x64인지부터 확정**한다. x86이면 `RAX`, `R8`~`R15`, `RIP` 상대 주소 지정, REX 프리픽스 자체가 존재하지 않으므로 애초에 헷갈릴 이유가 없다. x64라면 지금 보고 있는 레지스터가 32비트 하위 이름(`EAX`)인지 64비트 전체 이름(`RAX`)인지를 먼저 구분하고, 값을 쓰는 명령이면 "이 write가 상위 32비트를 지우는가"를 항상 함께 확인한다.

## 단계별 절차

**1) 레지스터 이름만 보고 폭을 즉시 판별하기**

- `R`로 시작하고 접미사가 없으면(`RAX`, `R12`) → 64비트
- `E`로 시작하거나 `D`로 끝나면(`EAX`, `R12D`) → 32비트
- 접미사가 `W`이거나 레거시 2글자 이름이면(`R12W`, `AX`, `CX`) → 16비트
- 접미사가 `B`, `L`이거나 `H`로 끝나면(`R12B`, `AL`, `SIL`, `AH`) → 8비트

**2) x64에서 부분 쓰기(partial write)가 상위 비트에 미치는 영향을 확인하기**

이것이 x64 리버싱에서 가장 자주 나오는 함정이다.

```asm
; RAX = 0x1122334455667788 인 상태에서 시작

mov eax, 0        ; 32비트 쓰기 -> RAX 전체가 0x0000000000000000 이 된다
                   ; (제로 익스텐션: 상위 32비트도 함께 0으로 지워짐)

mov ax,  0         ; 16비트 쓰기 -> RAX = 0x1122334455660000
                   ; (상위 48비트는 건드리지 않고 그대로 남음)

mov al,  0         ; 8비트 쓰기 -> RAX = 0x1122334455667700
                   ; (상위 56비트는 건드리지 않고 그대로 남음)
```

즉 규칙은 다음과 같다:
- **32비트 서브 레지스터(`EAX` 등)에 쓰면 x64에서는 항상 상위 32비트가 0으로 초기화(제로 익스텐션)된다.** 이건 x64 아키텍처가 정의한 특수 규칙이다.
- **16비트/8비트 서브 레지스터(`AX`, `AL`, `AH` 등)에 쓰면 상위 비트는 전혀 건드리지 않는다.** 이전에 그 레지스터에 어떤 값이 있었든 그대로 남는다.

이 차이 때문에 `mov eax, 0`을 보고 "RAX 전체가 0이 됐다"고 판단하는 건 **맞고**, `mov al, 0`을 보고 같은 식으로 "RAX 전체가 0이 됐다"고 판단하면 **틀린다.** `al`만 0이 되고 나머지 56비트는 직전 값이 그대로 남아있는 "쓰레기값 포함 레지스터"가 된다. 함수 반환값을 `al`로만 설정하고 `eax`/`rax`는 건드리지 않는 컴파일러 출력(예: bool 반환 함수)을 볼 때 이 규칙을 모르면 반환값 전체를 잘못 해석하기 쉽다.

**3) REX 프리픽스 인식하기**

x64 명령어에서 `R8`~`R15`를 쓰거나, 64비트 연산 크기를 지정하거나, `SIL`/`DIL`/`BPL`/`SPL` 같은 새 8비트 하위 레지스터를 쓰려면 명령어 앞에 **REX 프리픽스**(1바이트, `0x40`~`0x4F` 범위)가 붙어야 한다. REX 바이트의 `W` 비트(REX.W, 값이 1이면 `0x48`/`0x49`/`0x4C`/`0x4D` 등)가 켜져 있으면 오퍼랜드 크기가 64비트라는 뜻이다. 바이트 덤프에서 이 범위의 바이트가 명령어 시작 부분에 자주 보인다면 그 자체로 "이건 x64 코드"라는 신호로 읽을 수 있다. x86(32비트) 코드에는 REX 프리픽스가 아예 존재하지 않는다.

**4) RIP 상대 주소 지정 인식하기**

x64에서만 가능한 주소 지정 방식으로, 현재 명령어 포인터(`RIP`)를 기준으로 상대 오프셋을 더해 메모리를 가리킨다.

```asm
lea rax, [rip+0x2ee5]   ; RAX = 현재 명령어의 다음 주소 + 0x2ee5
```

x86(32비트)에는 `EIP`를 직접 피연산자로 쓰는 주소 지정 모드가 없다. 그래서 32비트 위치독립코드(PIE/PIC)는 `call` 직후 `pop`으로 스택에 쌓인 반환 주소(=다음 명령어 주소=EIP 값)를 레지스터로 꺼내는 우회 트릭을 써야 했다. x64는 이 트릭 없이 `lea reg, [rip+offset]` 한 줄로 끝난다. PIE로 빌드된 ELF나 ASLR이 걸린 실행 파일을 리버싱할 때 문자열/전역변수 참조가 대부분 이 형태로 나타난다.

## 명령어/단축키

**x64dbg**
- 레지스터 창(오른쪽 패널)에서 `RAX` 더블클릭 → 값을 직접 수정. 우클릭 → `Zero`로 0으로 초기화, `Change value` → 16진수 입력.
- 상태표시줄에서 현재 프로세스가 32비트(x32dbg)인지 64비트(x64dbg)인지 확인 — 실행 파일 자체에 따라 자동으로 결정된다.

**GDB / Pwndbg**
```
(gdb) info registers          # 전체 레지스터 확인 (x64면 rax~r15, x86이면 eax~edi까지만)
(gdb) p $rax                  # 64비트 값
(gdb) p $eax                  # 하위 32비트만 (gdb가 자동으로 서브 레지스터 이름 인식)
(gdb) p/x $al                 # gdb는 al 같은 8비트 서브 레지스터를 직접 지원하지 않을 수 있음
                               # 이 경우 p $rax & 0xff 로 계산
```

**IDA / Ghidra**
- 디스어셈블리 창에서 레지스터 이름 위에 마우스를 올리면 같은 함수 내에서 그 레지스터가 다시 쓰이는 다른 줄이 하이라이트된다. 서브 레지스터(`AL`)와 전체 레지스터(`RAX`)가 같이 하이라이트되는지 확인하면 포함 관계를 눈으로 검증할 수 있다.
- IDA의 Hex-Rays 디컴파일러는 부분 쓰기를 `LOBYTE(v1) = 0;`, `(unsigned int)v1 = 0;` 같은 캐스트 표현으로 보여줄 때가 있다. 이 캐스트가 바로 "몇 비트짜리 쓰기였는가"를 알려주는 단서다.

## 출력 해석
- 디스어셈블리에 `EAX`만 나오고 `RAX`는 전혀 안 나오는 함수 조각이라도, 물리적으로는 여전히 64비트 `RAX`의 일부를 쓰고 있는 것이다. `EAX`에 값을 쓴 순간 `RAX` 상위 32비트는 0으로 정리된다.
- `movzx eax, al` 같은 코드는 "AL의 값을 EAX 전체로 제로 확장하라"는 뜻이다. 이렇게 하면 32비트 쓰기 규칙 덕분에 결과적으로 RAX 전체가 AL 값 하나로 깨끗하게 정리된다. 부분 쓰기의 "쓰레기 상위 비트" 문제를 컴파일러가 회피할 때 자주 쓰는 패턴이다.
- 함수 프롤로그에서 `sub rsp, 0x20`처럼 32(0x20)의 배수로 스택을 내리는 코드가 보이면, x64 호출 규약에서 요구하는 스택 정렬(16바이트 정렬) 및 Windows의 섀도우 스페이스 확보와 관련된 것으로 해석한다.

## 흔한 실수
- `mov al, 0`을 보고 "이 레지스터(RAX) 전체가 0이 됐다"고 오해하는 것. 8비트/16비트 쓰기는 상위 비트를 지우지 않는다. 오직 32비트 쓰기만 상위 32비트를 제로 익스텐션한다.
- `R8`, `R9` 같은 x64 전용 레지스터를 x86(32비트) 바이너리 디스어셈블리에서 봤다고 착각하는 것. x86 모드에는 애초에 존재하지 않으므로, 만약 실제로 보인다면 아키텍처 판단 자체가 잘못됐을 가능성을 먼저 의심한다.
- `AH`, `BH`, `CH`, `DH`(상위 바이트 레거시 이름)를 `R8B`~`R15B` 같은 새 8비트 레지스터에도 있을 거라 착각하는 것. `R8`~`R15` 계열과 `SI`/`DI`/`BP`/`SP` 계열은 상위 바이트 별명이 없다.
- EFLAGS와 RFLAGS를 완전히 다른 것으로 오해하는 것. x64에서 플래그 레지스터가 64비트(`RFLAGS`)로 넓어지긴 했지만, 실제로 의미 있게 쓰이는 비트(ZF, CF, SF, OF, PF, AF 등 조건 분기에 쓰이는 플래그들)는 여전히 하위 32비트 안에 있고 상위 비트는 예약(reserved)되어 사실상 쓰이지 않는다. 조건 점프(`JZ`, `JNZ` 등) 해석 방식 자체는 x86과 x64가 동일하다.
- 32비트/64비트 함수 인자 전달 방식을 x86 cdecl 감각으로 x64에 그대로 적용하는 것. x64에서는 첫 몇 개 정수/포인터 인자가 레지스터로 전달되므로, 스택만 보고 인자를 찾으려 하면 놓친다.

- `and eax, 0FFh`처럼 마스크로 하위 비트만 남기는 코드와, 그것이 어떤 하위 레지스터 이름(`AL`)에 대응하는지 정리가 필요하면 → [rev-0026-bit-masks.md](./rev-0026-bit-masks.md)로 이동.

## 미니 예제
Windows x64에서 흔히 보이는 bool 반환 함수의 디스어셈블리를 예로 보자.

```asm
; int __fastcall CheckFlag(int a1)
mov     eax, 1          ; EAX = 1 (상위 32비트도 함께 0으로 정리됨, RAX = 0x0000000000000001)
cmp     ecx, 10          ; 인자(a1, RCX로 전달됨)와 10 비교
jge     short loc_return
mov     al, 0            ; AL만 0으로 설정! RAX 상위 56비트는 위에서 남은 값이 그대로 유지됨
loc_return:
retn
```

이 코드에서 `mov eax, 1`은 `RAX` 전체를 `0x1`로 깨끗하게 만들지만, 그 이후 조건이 성립해 `mov al, 0`이 실행되면 `RAX`는 `0x0000000000000000`이 아니라 **`AL`만 0이 되고 나머지 비트는 직전의 `0x1`에서 온 상위 비트(이 경우는 이미 0이라 눈에 안 띄지만, 만약 RAX에 다른 쓰레기 값이 있었다면 그대로 남는다)**가 된다. 호출자가 `int` 반환값 전체를 32비트로 읽는 관례에 의존한다면, 이런 부분 쓰기 뒤에 상위 바이트가 정리되지 않은 채로 남아 있을 경우가 실제 버그의 원인이 될 수도 있다 — 그래서 컴파일러는 보통 `mov al, 0` 대신 `xor eax, eax`처럼 32비트 단위로 레지스터를 정리하는 코드를 선호한다. `xor eax, eax`는 자기 자신과 XOR해서 0을 만드는 관용구이면서, 동시에 32비트 쓰기이므로 `RAX` 상위 비트까지 깔끔하게 0으로 만든다는 점도 함께 기억해두면 좋다.
