## 한 줄 요약
레지스터나 메모리에 든 큰 16진수 값을 무작정 "숫자 데이터"로 해석하다 계산이 안 맞으면, 그 값이 사실은 **주소(포인터)**이고, 포인터 산술은 일반 정수 덧셈과 달리 **가리키는 타입의 크기만큼 곱해서 이동한다**는 규칙을 놓쳤을 가능성이 높다.

## 언제 검색해야 하나
- 레지스터 값이 `0x00007FFE...`, `0x0000560A...`처럼 특정 패턴으로 시작해서 이게 데이터인지 주소인지 구분이 안 될 때
- 실행할 때마다(디버거를 다시 붙일 때마다) 같은 변수의 값이 계속 달라져서 "상수인 줄 알았는데 아니다"라고 헷갈릴 때
- `ptr + 1`을 했는데 실제 주소가 1이 아니라 4나 8만큼 늘어나서 당황할 때
- 디컴파일 결과에서 `int` 타입으로 보이는 변수인데 실제로는 명백히 주소로 쓰이고 있는 경우

## 핵심 개념
포인터도 결국 레지스터/메모리에 저장된 하나의 숫자(주소값)일 뿐이라서, 겉모습만 보면 일반 정수 데이터와 구분이 안 될 수 있다. 하지만 몇 가지 단서로 "이건 주소다"라고 판단할 수 있고, 포인터라는 걸 알고 나면 그 값에 대한 산술 규칙도 완전히 달라진다.

**주소로 의심할 수 있는 값의 패턴**:
- Linux x64 사용자 공간 스택/힙 주소는 흔히 `0x00007F...`나 `0x0000560...`처럼 상위 절반이 `0x0000`으로 시작한다(x64는 실제로 48비트 정도의 가상 주소 공간만 쓰기 때문).
- Windows도 유사하게 x64 사용자 모드 주소는 특정 범위(`0x00000000...`~`0x00007FFF...`) 안에 들어온다.
- 실행할 때마다 값이 바뀐다면 ASLR(Address Space Layout Randomization)이 적용된 주소일 가능성이 크다. 반대로 실행마다 항상 같은 값이면 ASLR이 없는 고정 베이스이거나, 애초에 진짜 데이터 상수일 수 있다.
- 그 값으로 메모리를 읽었을 때(`x/10x` 등) 의미 있는 데이터가 나온다면 그건 확실히 주소다.

**포인터 산술의 스케일링 규칙**: C에서 `T *p`에 대해 `p + 1`은 "1바이트 뒤"가 아니라 **`sizeof(T)`바이트 뒤**를 의미한다.
- `int *p`에서 `p + 1` → 실제 주소는 `p + 4`(4바이트 뒤)
- `double *p`에서 `p + 1` → 실제 주소는 `p + 8`(8바이트 뒤)
- `struct Foo *p`(예: 24바이트 구조체)에서 `p + 1` → 실제 주소는 `p + 24`

이건 REV-0378에서 다룬 배열 인덱스 계산과 원리가 완전히 같다 — 사실 `p[i]`와 `*(p + i)`는 C에서 동일한 의미이기 때문이다. 어셈블리에서는 이 스케일링이 `imul`이나 SIB 주소의 `scale` 필드로 드러난다.

**포인터를 정수로 착각했을 때 생기는 전형적인 혼란**: 어떤 값에 `+1`을 했는데 실제 메모리 상 이동량이 1이 아니라 4나 8이라면, 그 변수가 `int`나 `char`가 아니라 포인터 타입으로 선언되어 있다는 강력한 증거다. 반대로, 정수인 줄 알았던 값이 `+1`할 때마다 정확히 1씩만 늘어난다면 그건 포인터가 아니라 `char *`(1바이트 단위)이거나 진짜 정수다.

## 화면/코드에서 보이는 징후
- IDA/Ghidra 디컴파일에서 변수 타입이 `int` 또는 `_DWORD`로 보이는데, 그 변수에 `[reg]`처럼 역참조(`*`)가 붙어서 실제로는 메모리를 가리키는 용도로 쓰이는 경우
- GDB에서 `p $rax`로 본 값이 `0x0000...`으로 시작하고, `x/s $rax` 또는 `x/10x $rax`로 확인했더니 실제로 유효한 데이터가 나오는 경우
- 같은 변수를 두 번 실행해서 확인했는데 값이 매번 다르게 나오는 경우(ASLR)
- 정수 덧셈처럼 보였던 연산이 실제로는 특정 배수(4, 8, 구조체 크기)로 스케일링되어 있는 경우(REV-0378 참고)

## 가장 먼저 할 것
헷갈리는 값을 디버거에서 그 주소로 직접 메모리를 읽어본다(`x/10x 값` 또는 `x/s 값`). 의미 있는 데이터/문자열이 나오면 포인터이고, 접근 자체가 안 되거나(`Cannot access memory`) 말이 안 되는 쓰레기 값이 나오면 그냥 정수 데이터일 가능성이 높다.

## 단계별 절차

**1) 값의 형태로 1차 판단**
64비트 환경에서 상위 절반이 `0x0000...`으로 시작하는 값은 사용자 공간 주소일 가능성이 높다. 완전히 랜덤해 보이는 32비트 값이거나 작은 값(예: `0x1A`, `100`)이라면 일반 데이터일 가능성이 높다.

**2) 디버거로 그 값 자체를 주소 삼아 메모리 확인**
```gdb
x/10xg 0x00005600aabbcc00
x/s   0x00005600aabbcc00
```
읽기가 성공하고 그 안에 의미 있는 값/텍스트가 있다면 포인터로 확정한다.

**3) 여러 번 재실행해서 값의 변동 여부 확인**
같은 지점에서 값이 실행마다 바뀐다면 ASLR이 걸린 주소다. `checksec` 또는 바이너리의 PIE(Position Independent Executable) 여부를 확인해서 ASLR 적용 대상인지 교차 검증한다.

**4) 포인터로 확정됐다면 산술 연산의 스케일 재확인**
그 포인터에 대한 연산(`+1`, 배열 인덱싱)이 몇 바이트 단위로 이동하는지 어셈블리에서 확인하고, 이를 통해 가리키는 타입의 크기(`sizeof`)를 역산한다.

## 명령어/단축키
```gdb
p $rax                  ; 레지스터 값 그대로 확인
x/10xg $rax              ; $rax를 주소로 보고 8바이트씩 10개 덤프
x/s $rax                 ; $rax를 주소로 보고 문자열로 해석
info proc mappings       ; 현재 프로세스의 메모리 매핑(어느 영역인지) 확인
```
```bash
checksec --file=binary   # PIE(ASLR 대상) 여부 등 확인
```

## 출력 해석
- `x/10xg`가 `Cannot access memory at address ...`를 출력하면 그 값은 유효한 주소가 아니라는 뜻이므로 포인터가 아니라 일반 데이터일 가능성이 높아진다.
- `info proc mappings`에서 그 주소가 속한 영역이 `[heap]`, `[stack]`, 또는 특정 `.so`/실행 파일 매핑 범위 안이라면 그 값이 포인터라는 확실한 증거다.

## 흔한 실수
- 큰 16진수 값을 보자마자 "이건 그냥 이상한 상수겠지"라고 단정하고 메모리로 확인해보지 않는 것.
- 포인터 산술을 일반 정수 덧셈처럼 생각해서 `+1`, `+N`의 실제 이동 바이트 수를 계산에서 빼먹는 것(REV-0378 참고).
- ASLR 때문에 매번 바뀌는 주소값을 "고정된 매직 넘버"로 착각하고 패치/하드코딩하려는 것 — 오프셋(베이스 주소로부터의 상대 거리)을 써야 재현 가능하다.
- void 포인터(`void *`)에 대한 산술은 표준 C에서 정의되지 않는데도 특정 컴파일러 확장(1바이트 단위로 취급)을 표준 동작으로 오해하는 것.

## 막혔을 때 다음 체크
- 포인터와 역참조가 어셈블리로 어떻게 표현되는지 기초부터 다시 보고 싶으면 REV-0033 문서로 이동.
- VA/RVA/파일 오프셋 개념이 헷갈리면 REV-0028 문서로 이동.
- 포인터 산술의 스케일링과 배열 인덱스 계산이 헷갈리면 REV-0378 문서로 이동.

## 미니 예제
GDB에서 다음과 같은 상황을 봤다고 하자.
```gdb
(gdb) p $rdi
$1 = 94823983732768
(gdb) p/x $rdi
$2 = 0x5638a1a032e0
(gdb) x/s $rdi
0x5638a1a032e0: "flag{...}"
```
`$rdi`를 그냥 `p`로 출력하면 거대한 10진수라서 "이상한 정수 데이터"처럼 보이지만, `p/x`로 헥스 변환하면 `0x0000...` 패턴의 전형적인 힙/코드 주소 형태이고, 실제로 `x/s`로 그 주소를 문자열로 읽어보면 의미 있는 텍스트가 나온다. 이 세 단계(10진수로 헷갈림 → 헥스로 패턴 확인 → 메모리로 실제 검증)가 "숫자인 줄 알았던 값이 사실은 포인터였다"를 확인하는 표준 절차다.

## 관련 글
- REV-0033 — 포인터와 역참조를 어셈블리에서 읽는 법
- REV-0028 — 주소 VA RVA File Offset 차이
- REV-0378 — 배열 인덱스 계산이 이상하게 나올 때

## 출처/검증
- x64 사용자 공간 가상 주소 범위와 표준 형태: Intel 64 and IA-32 Architectures Software Developer's Manual, Vol.1, "Canonical Addressing"(정규 주소, 상위 비트 제약) 섹션 기준 (2026-09-09 검증).
- 포인터 산술과 배열 인덱싱의 동등성(`p[i]` == `*(p+i)`), 타입 크기에 따른 스케일링: ISO/IEC 9899(C 표준) 6.5.6 "Additive operators" 조항 기준.
- ASLR(Position Independent Executable)과 실행마다 달라지는 주소 개념: GNU/Linux `checksec` 및 glibc/커널 ASLR 관련 공식 문서 기준 개념 설명.
