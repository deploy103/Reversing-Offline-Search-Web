## 한 줄 요약
함수 포인터는 "함수가 시작하는 메모리 주소를 담은 변수"일 뿐이며, 어셈블리에서는 `call 0x401234`처럼 **주소가 고정된 직접 호출(direct call)** 이 아니라 `call rax`, `call [rdi+8]`처럼 **레지스터/메모리에 담긴 값으로 호출하는 간접 호출(indirect call)** 로 나타나기 때문에, IDA의 정적 xref 분석만으로는 호출 대상을 바로 알아낼 수 없다는 것이 가장 큰 특징이다.

## 언제 검색해야 하나
- 어셈블리에 `call rax`, `call [rbx+0x10]`, `call qword ptr [rdi+8]`처럼 대상이 특정 함수 이름이 아니라 레지스터/메모리 참조로 되어 있을 때
- IDA에서 어떤 함수를 봤는데 "Xrefs to"가 텅 비어 있어서 대체 이 함수가 어디서 호출되는지 알 수 없을 때(간접 호출로만 불리는 함수는 정적 xref에 안 잡힐 수 있음)
- C 코드에 `void (*handler)(int);`, `int (*ops[4])(void);`처럼 함수 포인터 변수/배열이 있는데 이게 메모리에서 어떻게 표현되는지 알고 싶을 때
- vtable, 콜백 테이블, syscall 핸들러 테이블처럼 "함수 주소들의 배열"을 분석해야 할 때

## 핵심 개념

### 함수 포인터는 그냥 주소값이다
C에서 함수 이름은 그 함수의 시작 주소를 가리키는 값으로 취급된다. `void (*fp)(int) = my_func;`는 "fp라는 변수에 my_func 함수가 시작하는 메모리 주소를 저장하라"는 뜻이다. 이 주소는 보통 코드 영역(`.text`)에 있는 값이며, 크기는 일반 포인터와 같다(x64에서 8바이트, x86에서 4바이트). 즉 함수 포인터는 "가리키는 곳이 데이터가 아니라 실행 가능한 코드"라는 점만 다를 뿐, 저장 방식 자체는 다른 포인터와 완전히 동일하다(REV-0033 포인터 개념 참고).

### 직접 호출 vs 간접 호출
컴파일 시점에 호출 대상이 확정되는 일반 함수 호출은 **직접 호출(direct call)** 이다.
```asm
call    0x401234        ; 항상 같은 주소의 함수를 호출 (IDA가 정적으로 xref 표시 가능)
```
반면 함수 포인터를 통한 호출은 런타임에 레지스터나 메모리에 들어있는 값을 목적지로 삼는 **간접 호출(indirect call)** 이다.
```asm
mov     rax, [rbp-8]     ; rax = fp (저장해둔 함수 포인터 값)
call    rax               ; rax에 들어있는 주소로 점프 + 리턴 주소 push
```
```asm
call    qword ptr [rdi+8]  ; rdi+8 위치(메모리)에 저장된 함수 포인터로 바로 호출
```
직접 호출은 `call` 뒤에 상수 주소가 오지만, 간접 호출은 `call` 뒤에 레지스터 이름 또는 `[ ]`로 감싼 메모리 참조가 온다는 것이 눈으로 구분하는 핵심이다.

### 정적 분석의 한계 — xref가 끊긴다
IDA/Ghidra는 `call 0x401234`처럼 대상이 고정된 호출은 자동으로 "이 함수는 여기서 호출된다(Xref)"를 표시해준다. 하지만 `call rax`는 `rax`에 실제로 어떤 값이 들어올지 정적으로는 알 수 없으므로(런타임에 조건에 따라 다른 함수가 들어올 수도 있다), IDA는 이 호출의 대상을 특정 함수와 자동으로 연결하지 못한다. 그래서 콜백/vtable 기반 코드에서 특정 함수가 "아무 데서도 호출되지 않는 것처럼" 보이는 경우가 흔하다 — 실제로는 함수 포인터를 통해 호출되고 있을 뿐이다. 이럴 때는 그 함수의 주소가 **데이터로서 어디에 저장되는지**(`.data`, `.rodata`에 그 주소 상수가 박혀 있는 곳)를 거꾸로 찾아야 한다. IDA에서는 함수 시작 주소 위에서 우클릭 → "Xrefs to"를 봐도 안 잡히면, 그 주소 리터럴 자체를 데이터 영역에서 검색(`Search → Immediate Value`로 그 주소값 검색)하는 방법이 유효하다.

### 함수 포인터 배열 — 콜백 테이블/디스패치 테이블
함수 포인터는 배열로 묶여서 "핸들러 테이블", "디스패치 테이블", "vtable"의 형태로 자주 등장한다.
```c
int op_add(int a, int b) { return a + b; }
int op_sub(int a, int b) { return a - b; }

int (*ops[2])(int, int) = { op_add, op_sub };

int calc(int idx, int a, int b) {
    return ops[idx](a, b);
}
```
`ops` 배열은 메모리에 함수 시작 주소값들이 8바이트(x64)씩 연속으로 나열된 형태로 저장된다.
```
.rodata:
  ops[0] = 0x0000000000401120   ; op_add의 주소
  ops[1] = 0x0000000000401140   ; op_sub의 주소
```
이를 호출하는 어셈블리는 배열 인덱싱(REV-0034)과 간접 호출이 결합된 형태다.
```asm
mov     rax, [rip+ops]           ; ops 배열의 시작 주소(또는 그 배열 자체 로드)
mov     rax, [rax + rdi*8]       ; ops[idx] 값(함수 주소) 로드
call    rax                       ; 그 주소로 호출
```
이 패턴이 보이면 "인덱스에 따라 다른 함수가 실행되는 디스패치 테이블"이라고 확신할 수 있고, `.rodata`/`.data`에서 그 배열 위치를 찾아 각 슬롯에 어떤 함수 주소가 들어있는지 하나씩 확인하면 전체 핸들러 목록을 복원할 수 있다.

### C++ vtable도 결국 함수 포인터 배열
C++ 가상 함수 호출(virtual function call)도 내부적으로는 객체 시작 부분에 숨겨진 vtable 포인터가 있고, 그 vtable이 곧 함수 포인터들의 배열이다. `obj->virtualMethod()`는 결국 `obj`가 가리키는 vtable에서 해당 슬롯의 함수 주소를 읽어 간접 호출하는 코드로 컴파일된다. 원리는 위의 `ops[idx]()`와 완전히 동일하며, 다만 인덱스 대신 클래스가 정의한 고정된 슬롯 순서를 쓴다는 점만 다르다.

## 화면/코드에서 보이는 징후
- `call` 명령의 대상이 상수 주소가 아니라 레지스터(`call rax`, `call rbx`) 또는 메모리 참조(`call [rdi+8]`, `call qword ptr [rax+rcx*8]`)다.
- `.rodata`/`.data`에 코드 영역(`.text`) 안의 주소로 보이는 8바이트(x64)/4바이트(x86) 값들이 연속으로 나열되어 있다.
- 함수 하나가 정의는 되어 있는데 IDA "Xrefs to"에는 아무것도 없다.
- 함수 시작 부분에서 첫 번째 필드가 다른 함수 주소들의 배열을 가리키는 포인터(vtable 포인터)로 보인다.

## 가장 먼저 할 것
`call` 뒤에 상수가 아니라 레지스터/메모리 참조가 보이면 간접 호출임을 먼저 인지한다. 그 다음 그 레지스터/메모리에 값이 어디서 채워졌는지(직전 코드에서 `mov`로 어디서 로드했는지) 거슬러 올라가, 최종적으로 어떤 데이터 영역 주소에서 함수 포인터 값을 읽어왔는지 찾는다.

## 단계별 절차
1. `call reg` 또는 `call [mem]` 형태의 간접 호출을 발견한다.
2. 호출 직전 코드를 거슬러 올라가 그 레지스터/메모리 값이 어디서 로드됐는지 추적한다.
3. 값의 출처가 고정된 데이터 영역 주소라면, 그 주소를 IDA에서 직접 열어 실제로 저장된 값(함수 주소로 추정되는 상수)을 확인한다.
4. 그 상수 주소가 `.text` 영역 안에 있으면 그 주소를 함수로 변환(IDA에서 `C` 또는 `P` 단축키로 코드/함수로 재정의)해 어떤 함수인지 확인한다.
5. 배열 형태라면 배열의 각 슬롯을 인덱스 0부터 순서대로 조사해 전체 핸들러 목록을 만든다.
6. 정적으로 특정이 어려우면 디버거에서 `call` 직전에 브레이크포인트를 걸어 실제 실행 중 레지스터 값을 확인한다.

## 명령어/단축키
```
(gdb) break *0x0000555555555160     # call reg 직전 주소에 브레이크
(gdb) run
(gdb) info registers rax             # rax에 실제로 어떤 함수 주소가 들어있는지 확인
(gdb) x/i $rax                        # 그 주소의 첫 명령어를 디스어셈블해서 진짜 함수인지 확인
(gdb) info symbol $rax                # 심볼 정보가 있다면 함수 이름 바로 확인
```
IDA: 데이터 영역의 주소 리터럴 위에서 `Search → Immediate Value`로 특정 함수 주소를 검색하면 그 값을 참조하는 모든 위치(함수 포인터 테이블 등)를 찾을 수 있다. 함수처럼 보이는 데이터 위치에서는 `P`(Create function)로 강제로 함수를 정의할 수 있다.

## 출력 해석
- `call rax`에서 GDB로 `x/i $rax`를 했을 때 정상적인 함수 프롤로그(`push rbp` 등)가 보이면 실제 함수 시작점이 맞다는 뜻이다.
- 함수 포인터 배열의 슬롯 값이 전부 `.text` 범위 안의 그럴듯한 주소라면 디스패치 테이블/vtable로 확신할 수 있다.
- 값이 `0x0`(NULL 함수 포인터)이면 그 슬롯은 호출되지 않거나 호출 시 크래시(NULL 포인터 역참조 후 `call`)를 일으키는 경로다.

## 흔한 실수
- 간접 호출을 보고 "이 코드는 정적 분석이 불가능하다"고 포기하는 것 — 값의 출처를 한 단계씩 역추적하면 대부분 특정 가능하다.
- 함수 포인터 변수와 그 변수가 가리키는 함수 자체를 혼동하는 것 — `fp`는 주소를 담은 변수고, `fp()`(호출)는 그 주소로 점프하는 별개의 동작이다.
- vtable/디스패치 테이블의 슬롯 순서를 실제 소스 코드의 함수 선언 순서와 다르게 가정하는 것 — 반드시 데이터 영역에서 실제 저장된 순서를 확인해야 한다.
- 조건부로 다른 함수 포인터가 대입되는 코드(런타임 분기)에서 하나의 값만 보고 "이 콜백은 항상 이 함수다"라고 단정하는 것.

## 막혔을 때 다음 체크
- 콜백이 함수 인자로 전달되어 호출되는 구체적인 패턴이 궁금하면 → REV-0349 콜백 함수 패턴을 어셈블리에서 알아보는 법
- 포인터 역참조와 대괄호 표기 자체가 헷갈리면 → REV-0033 포인터와 역참조를 어셈블리에서 읽는 법
- 배열 인덱싱이 어셈블리로 어떻게 변하는지 헷갈리면 → REV-0034 배열 접근이 어셈블리로 변하는 방식

## 미니 예제
```c
int op_add(int a, int b) { return a + b; }
int op_sub(int a, int b) { return a - b; }

int (*ops[2])(int, int) = { op_add, op_sub };

int calc(int idx, int a, int b) {
    return ops[idx](a, b);
}
```

x64 SysV 어셈블리(개념 설명용):
```asm
calc:
    ; edi=idx, esi=a, edx=b
    movsxd  rax, edi                 ; idx를 64비트로 부호 확장
    lea     rcx, [rip+ops]            ; ops 배열의 주소
    mov     rax, [rcx + rax*8]        ; rax = ops[idx]  (함수 포인터 로드)
    ; 인자 재배치: (a,b) -> (edi, esi) 순서로 다시 세팅
    mov     edi, esi                  ; a
    mov     esi, edx                  ; b
    call    rax                        ; ops[idx](a, b)  — 간접 호출
    ret
```

IDA/Ghidra는 이를 다음처럼 복원한다(타입 정보를 정확히 잡았을 경우).

```c
int calc(int idx, int a, int b)
{
  return ops[idx](a, b);
}
```

`call rax`가 `ops[idx](a, b)`에 대응하고, `.rodata`에서 `ops` 배열을 열어보면 `op_add`, `op_sub` 함수의 실제 시작 주소가 순서대로 들어있는 것을 확인할 수 있다. IDA의 "Xrefs to op_add"에는 이 호출이 자동으로 잡히지 않을 수 있으므로, `ops` 배열 자체를 데이터 영역에서 직접 확인하는 것이 확실한 검증 방법이다.

## 관련 글
- REV-0349 — 콜백 함수 패턴을 어셈블리에서 알아보는 법
- REV-0033 — 포인터와 역참조를 어셈블리에서 읽는 법
- REV-0034 — 배열 접근이 어셈블리로 변하는 방식

## 출처/검증
- 간접 호출(`call reg`/`call [mem]`) 인코딩과 직접 호출의 차이: Intel 64 and IA-32 Architectures Software Developer's Manual, Vol.2, `CALL` 명령어 레퍼런스 기준.
- vtable/함수 포인터 테이블을 통한 가상 호출 구현 방식: Itanium C++ ABI(vtable 레이아웃 관례) 및 실제 GCC/Clang 컴파일 결과 기준 (2026-09-09 확인).
