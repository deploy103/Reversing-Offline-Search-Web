## 한 줄 요약
x86/x64는 리틀 엔디안(little-endian)이라 다중 바이트 값을 메모리/파일에 저장할 때 **낮은 자릿수 바이트가 먼저(더 낮은 주소에)** 온다 — 이 순서를 반대로 읽고 "문서에 나온 상수랑 안 맞는다"고 착각하는 경우가 매우 흔하며, 특히 파일 포맷 시그니처나 네트워크 프로토콜(빅 엔디안인 경우가 많음)을 다룰 때 이 착각이 자주 발생한다.

## 언제 검색해야 하나
- 헥스 덤프에서 뽑은 4바이트/8바이트 값을 알려진 매직 넘버나 상수와 비교했는데 바이트 순서가 반대로 보일 때
- 파일 포맷 명세 문서(RFC, 스펙 문서)에 나온 상수를 코드에 그대로 복사했는데 실제 파일과 안 맞을 때
- 네트워크 패킷을 파싱하는데 필드 값이 예상보다 훨씬 크거나 이상한 값으로 보일 때(네트워크 바이트 순서는 보통 빅 엔디안)
- CRC/체크섬 상수를 리버싱해서 코드에 옮겼는데 계산 결과가 문서와 다를 때

## 핵심 개념
"리틀 엔디안"이란 다중 바이트 정수를 메모리에 저장할 때 **최하위 바이트(LSB)가 가장 낮은 주소에 저장**되는 방식이다. 반대로 "빅 엔디안"은 **최상위 바이트(MSB)가 가장 낮은 주소**에 저장된다. x86/x64는 리틀 엔디안을 쓰지만, 네트워크 프로토콜(TCP/IP 헤더 등)이나 일부 파일 포맷, 자바 가상머신 등은 빅 엔디안을 쓴다.

**구체적 숫자 예시**: 32비트 값 `0x12345678`을 메모리에 저장한다고 하자.
- **리틀 엔디안(x86/x64)**: 주소가 낮은 순서대로 `78 56 34 12`
- **빅 엔디안**: 주소가 낮은 순서대로 `12 34 56 78`

헥스 에디터로 파일을 열어서 `78 56 34 12`라는 4바이트를 봤다면, 이걸 "그대로 순서대로" `0x78563412`라고 읽으면 안 되고, **바이트 순서를 뒤집어서** `0x12345678`로 읽어야 리틀 엔디안 값의 실제 의미가 나온다.

**매직 넘버가 안 맞는 전형적인 상황**: PNG 파일의 시그니처는 문서에 `89 50 4E 47 0D 0A 1A 0A`로 정의돼 있다. 이건 **바이트 시퀀스 자체를 순서대로 명시한 것**이라 엔디안과 무관하게 그대로 매칭하면 된다. 하지만 만약 어떤 포맷 문서가 "매직 넘버는 `0x1A0A0D47`이다"처럼 **하나의 정수 값**으로 표기했다면, 이 정수를 리틀 엔디안 파일에서 찾으려면 실제 파일에는 `47 0D 0A 1A`(바이트 순서 반전) 형태로 저장돼 있다는 것을 알아야 한다. 이 둘(바이트 시퀀스로 정의된 시그니처 vs 정수 값으로 정의된 매직 넘버)을 혼동하면 "분명히 맞는 값인데 검색이 안 된다"는 상황이 생긴다.

**네트워크 바이트 순서는 보통 빅 엔디안**: 소켓 프로그래밍에서 `htons()`, `htonl()`, `ntohs()`, `ntohl()` 같은 함수가 존재하는 이유가 바로 이것이다. 호스트(x86/x64, 리틀 엔디안)와 네트워크(관례상 빅 엔디안, "network byte order")의 바이트 순서가 다르기 때문에 명시적으로 변환해줘야 한다. 이런 함수 호출이 코드에 보인다면 그 값은 십중팔구 포트 번호나 IP 주소처럼 네트워크로 전송되는 필드다.

## 화면/코드에서 보이는 징후
- 파일 헥스 덤프의 특정 4/8바이트 구간이 알려진 상수의 "역순"으로 보이는 경우
- `htons`/`htonl`/`ntohs`/`ntohl` 호출이 코드에 있는 경우 — 엔디안 변환이 명시적으로 일어나는 지점
- 구조체를 통째로 파일에서 읽어들인 뒤(`fread` 등) 특정 필드만 값이 이상하게 크거나 이상해 보이는 경우
- CRC-32, Adler-32 같은 체크섬 알고리즘의 상수/결과값을 리틀 엔디안으로 저장할지 빅 엔디안으로 저장할지에 대한 명세가 실제 구현과 안 맞는 경우

## 가장 먼저 할 것
문제의 값이 파일/네트워크에서 "바이트 시퀀스"로 정의된 것인지, 아니면 "정수 값"으로 정의된 것인지부터 구분한다. 바이트 시퀀스라면 순서 그대로 비교하면 되고, 정수 값이라면 그 정수를 대상 아키텍처의 엔디안에 맞게 바이트로 풀어서 비교해야 한다.

## 단계별 절차

**1) 문제의 헥스 바이트를 그대로 옮겨 적기**
파일/메모리에서 본 순서 그대로(`78 56 34 12`처럼) 먼저 기록한다.

**2) 리틀 엔디안으로 해석해서 정수값 도출**
```python
data = bytes.fromhex("78563412")
import struct
value = struct.unpack("<I", data)[0]   # '<' = 리틀 엔디안, I = 4바이트 unsigned
print(hex(value))    # 0x12345678
```

**3) 반대로 빅 엔디안으로도 해석해서 비교**
```python
value_be = struct.unpack(">I", data)[0]  # '>' = 빅 엔디안
print(hex(value_be))   # 0x78563412
```
두 결과 중 어느 쪽이 알려진 문서/상수와 일치하는지 비교해서 이 파일/프로토콜이 어떤 엔디안을 쓰는지 확정한다.

**4) 소스에서 엔디안 변환 함수 호출 여부 확인**
`htonl`/`ntohl` 등이 보이면 그 값은 네트워크(빅 엔디안)와 호스트(리틀 엔디안) 사이를 오가는 값이라는 확실한 증거다.

## 명령어/단축키
```python
import struct
struct.unpack("<I", data)[0]   # 리틀 엔디안 4바이트 → 정수
struct.unpack(">I", data)[0]   # 빅 엔디안 4바이트 → 정수
struct.pack("<I", 0x12345678)  # 정수 → 리틀 엔디안 4바이트
int.from_bytes(data, "little") # 파이썬 내장(struct 없이도 가능)
int.from_bytes(data, "big")
```
```asm
bswap   eax        ; 32비트 레지스터의 바이트 순서를 반전(엔디안 변환에 자주 쓰임)
```

## 출력 해석
- `struct.unpack("<I", ...)`와 `struct.unpack(">I", ...)`의 결과가 서로 바이트 순서만 반전된 관계라면(예: `0x12345678` vs `0x78563412`), 이는 계산 오류가 아니라 엔디안 해석 차이를 정확히 보여준 것이다.
- 알려진 매직 넘버/체크섬 상수와 둘 중 하나만 정확히 일치한다면, 그 값을 통해 이 파일/프로토콜의 엔디안을 확정할 수 있다.

## 흔한 실수
- 헥스 덤프에 보이는 바이트를 항상 "왼쪽에서 오른쪽으로 그대로 읽으면 된다"고 가정하고 리틀 엔디안 반전을 빼먹는 것.
- 파일 포맷 시그니처처럼 애초에 "바이트 시퀀스"로 정의된 값에 불필요하게 엔디안 반전을 적용해서 오히려 안 맞게 만드는 것 — 매직 바이트(예: `4D 5A`, `PE`용 PE 헤더)는 대부분 시퀀스 자체로 정의되므로 반전하면 안 된다.
- 네트워크 프로토콜 코드에서 `htonl`/`ntohl` 호출을 못 보고 그냥 호스트 엔디안 그대로 값을 해석해서 IP나 포트 번호가 이상하게 큰 값으로 보이는 것.
- 파이썬 `struct` 포맷 문자에서 `<`(리틀)와 `>`(빅) 지정을 빠뜨려서 시스템 기본 엔디안(`@`, 보통 리틀)에 의존하다가 다른 환경에서 결과가 달라지는 것.

## 막혔을 때 다음 체크
- 엔디안 개념 자체(어느 쪽이 리틀/빅인지, 왜 그런 방식을 쓰는지)가 헷갈리면 REV-0023 문서로 이동.
- 바이트 순서를 반전하는 `BSWAP` 명령어 자체가 궁금하면 assembly 카테고리의 BSWAP 문서로 이동.
- 문자열이 아니라 값 자체의 인코딩(문자 인코딩)이 헷갈린다면 REV-0374 문서로 이동.

## 미니 예제
어떤 파일 포맷 문서에 "버전 필드는 오프셋 0x04에 있고, 값은 리틀 엔디안 32비트 정수로 `2`여야 정상 파일이다"라고 나와 있다고 하자. 실제 파일을 헥스 에디터로 열어 오프셋 0x04를 보니 다음과 같았다.
```
offset 0x04: 02 00 00 00
```
이 4바이트를 리틀 엔디안으로 해석하면 `struct.unpack("<I", b'\x02\x00\x00\x00')` = `2`로 문서와 정확히 일치한다. 만약 여기서 실수로 빅 엔디안으로 해석했다면 `struct.unpack(">I", b'\x02\x00\x00\x00')` = `0x02000000` = `33554432`라는 전혀 다른 값이 나와서 "버전이 이상하게 크다"거나 "이 파일은 손상됐다"고 잘못 결론 내릴 뻔했을 것이다.
