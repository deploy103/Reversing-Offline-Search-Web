## 한 줄 요약
`INT 0x80`은 "소프트웨어 인터럽트를 발생시켜 커널에게 시스템 콜을 요청하는" 32비트 리눅스의 옛날 방식이다. `EAX`에 시스템 콜 번호를, `EBX/ECX/EDX/ESI/EDI/EBP`에 인자를 담아 실행하면 커널 코드로 제어가 넘어간다.

## 언제 검색해야 하나
- 32비트 CTF pwn 바이너리나 쉘코드에서 `int 0x80` 이 보이는데 `syscall` 명령어와 뭐가 다른지 모를 때
- `mov eax, 4` / `int 0x80` 같은 코드를 보고 4번이 무슨 시스템 콜인지 모를 때 (i386 시스템 콜 번호표가 x86-64와 다르다는 걸 모를 때)
- 디버거에서 `int 0x80` 실행 직후 프로그램이 커널로 "사라졌다가" 돌아오는 게 이해 안 될 때
- x64 바이너리인데 왜인지 `int 0x80`이 등장해서 당황스러울 때 (32비트 compat 모드 syscall)

## 핵심 개념

### INT 명령어 자체의 동작
`INT imm8`은 범용 소프트웨어 인터럽트 명령이다. 오퍼랜드는 0~255 사이의 **인터럽트 벡터 번호**이며, 이 번호는 **IDT(Interrupt Descriptor Table)**의 인덱스로 쓰인다.

`INT n` 실행 시 CPU가 하는 일:
1. 현재 `EFLAGS`, `CS`, `EIP`(x64에서는 확장된 형태)를 커널 스택에 PUSH한다.
2. IDT에서 n번 엔트리를 찾아 그 안에 등록된 핸들러 주소로 점프한다.
3. 이 과정에서 CPU 권한 수준이 사용자 모드(Ring 3)에서 커널 모드(Ring 0)로 바뀐다.
4. 핸들러가 끝나면 `IRET` 명령으로 저장해뒀던 `EFLAGS/CS/EIP`를 복원해서 인터럽트가 발생한 바로 다음 명령으로 돌아온다.

즉 `INT`는 "CALL과 비슷하지만 목적지가 커널이 미리 등록해둔 IDT 테이블을 거치고, 권한 레벨까지 바뀌는" 특수한 CALL이라고 이해하면 된다. `CALL`/`RET` 관계는 REV-0071 참고, `INT`/`IRET`가 그 커널 버전이다.

`INT`는 시스템 콜 전용이 아니다. 예를 들어 `INT3`(오퍼랜드 없이 1바이트 `0xCC`)는 디버거 브레이크포인트에 쓰이는 별도 벡터이고, 옛날 DOS에서는 `INT 21h`가 DOS 서비스 호출에 쓰였다. **리눅스에서 `INT 0x80` 벡터만 커널 부팅 시 "시스템 콜 게이트"로 등록**되어 있어서, 이 벡터로 인터럽트를 걸면 커널의 시스템 콜 디스패처(`system_call` 핸들러)로 들어가게 되는 것이다.

### INT 0x80: 32비트 리눅스 시스템 콜 규약
`INT 0x80`을 시스템 콜로 쓸 때 레지스터 규약은 다음과 같다 (i386, 즉 32비트 ABI):

```
EAX = 시스템 콜 번호
EBX = 1번째 인자
ECX = 2번째 인자
EDX = 3번째 인자
ESI = 4번째 인자
EDI = 5번째 인자
EBP = 6번째 인자
```

실행 후 반환값도 **EAX**에 담겨 돌아온다. `RDI/RSI/RDX/RCX/R8/R9`를 쓰는 SysV x64 함수 호출 규약(REV-0071 참고)과 이름이 겹치는 레지스터가 있어도 **완전히 다른 규약**이니 혼동하지 않는다.

### SYSCALL과의 결정적 차이
64비트 리눅스에서는 시스템 콜을 걸 때 보통 `SYSCALL` 명령어(REV-0077 참고)를 쓴다. `INT 0x80`과 비교하면:

| 구분 | `INT 0x80` | `SYSCALL` |
|---|---|---|
| 대상 | 32비트(i386) 리눅스, 또는 64비트 커널의 32비트 호환 모드 | 64비트(x86-64) 네이티브 |
| 메커니즘 | 소프트웨어 인터럽트 (IDT 조회 + 권한 전환, 상대적으로 느림) | 전용 명령어, MSR(`STAR`/`LSTAR`)에 미리 등록된 핸들러로 즉시 진입 (빠름) |
| 시스템 콜 번호 규약 | `EAX`, **i386 시스템 콜 테이블** 사용 (예: `write` = 4) | `RAX`, **x86-64 시스템 콜 테이블** 사용 (예: `write` = 1) |
| 인자 레지스터 | `EBX,ECX,EDX,ESI,EDI,EBP` | `RDI,RSI,RDX,R10,R8,R9` |
| 반환 | `EAX` | `RAX` |

**가장 흔한 초보자 실수**가 바로 이 표의 "시스템 콜 번호 규약" 줄이다. i386 테이블과 x86-64 테이블은 같은 이름의 시스템 콜이라도 번호가 다르다(`write`가 i386에서는 4번, x86-64에서는 1번). `int 0x80` 코드를 분석하면서 x86-64용 시스템 콜 번호표를 찾아보면 완전히 엉뚱한 답이 나온다 — 반드시 **32비트(i386) 시스템 콜 번호표**를 봐야 한다.

64비트 커널도 하위 호환을 위해 `int 0x80` 벡터를 여전히 지원하며, 이때는 i386 시스템 콜 번호표와 32비트 레지스터(`EAX/EBX/...`, 상위 32비트는 무시)가 그대로 적용된다. 그래서 64비트 프로세스 안에서도 `int 0x80`을 쓴 32비트 호환 셸코드를 종종 볼 수 있다.

### 플래그, 스택, RIP
- **플래그**: `INT` 실행 자체는 `EFLAGS`를 스택에 PUSH해서 커널이 보게 하지만, 사용자 코드 입장에서 CF/ZF/SF/OF 같은 산술 플래그를 직접 바꾸지는 않는다. (일부 게이트 타입에서 `IF` 플래그가 클리어될 수 있으나 이는 커널 내부 동작이다.)
- **스택**: 사용자 스택(`ESP`/`RSP`)은 `INT 0x80` 실행으로 직접 변하지 않는다 — 컨텍스트 저장은 **커널 스택**에서 일어난다. `IRET`로 복귀하면 사용자 스택은 그대로다.
- **RIP/EIP**: `INT 0x80` 다음 명령의 주소가 저장되고, 커널 처리가 끝나면 정확히 그 다음 명령으로 실행이 이어진다. `CALL`처럼 "돌아온다"는 점은 같지만 돌아오는 경로가 `RET`이 아니라 `IRET`이라는 차이가 있다.

## 화면/코드에서 보이는 징후
- `mov eax, 4` / `mov ebx, 1` / ... / `int 0x80` 형태의 블록 — i386 write 시스템 콜 패턴
- `mov eax, 1` / `int 0x80` — i386 exit 시스템 콜 (번호 1)
- `int $0x80` (AT&T 문법, GDB/objdump 출력에서 자주 보임) — Intel 문법의 `int 0x80`과 동일
- 32비트 ELF(`file` 명령으로 `ELF 32-bit`) 안에서 반복적으로 등장
- 64비트 ELF인데 `int 0x80`이 나오면 32비트 호환 셸코드이거나 의도적으로 삽입된 레거시 코드

## 가장 먼저 할 것
1. 바이너리/코드 조각이 32비트인지 64비트인지 먼저 확인한다(`file` 명령 또는 IDA 상단 아키텍처 표시).
2. `int 0x80` 직전 `EAX`에 들어간 값을 확인한다.
3. 그 값을 **i386 시스템 콜 번호표**(예: 1=exit, 3=read, 4=write, 5=open, 11=execve 등)에서 찾는다. x86-64 번호표와 절대 혼동하지 않는다.
4. `EBX/ECX/EDX/ESI/EDI/EBP` 순서로 인자를 읽는다.

## 단계별 절차

**1) 시스템 콜 번호 확인**
```asm
mov eax, 4        ; sys_write (i386)
mov ebx, 1        ; fd = 1 (stdout)
mov ecx, msg       ; buf 주소
mov edx, 13        ; count
int 0x80
```
→ `write(1, msg, 13)`로 해석.

**2) exit 패턴 확인**
```asm
mov eax, 1         ; sys_exit (i386)
xor ebx, ebx       ; status = 0
int 0x80
```
→ `exit(0)`로 해석. `int 0x80`을 실행하면 이 프로세스는 여기서 종료되므로 이 지점 이후 코드는 실행되지 않는다.

**3) GDB/Pwndbg에서 실제로 확인**
`int 0x80` 명령 주소에 브레이크포인트(`b *addr`)를 걸고 `i r eax ebx ecx edx esi edi ebp`로 레지스터를 직접 확인한다. `si`(stepi)로 한 명령씩 진행하며 커널로 넘어갔다가 돌아오는 것도 관찰 가능하다(사용자 모드 디버거에서는 커널 내부는 안 보이고 명령 실행 전후 상태만 비교 가능).

**4) SYSCALL 코드와 구분해서 읽기**
같은 바이너리 안에 `int 0x80`과 `syscall`이 섞여 있다면 어느 쪽이 어느 아키텍처/모드용인지 우선 구분한다. 뒤섞여 있는 경우는 드물지만, 32/64비트 셸코드를 함께 넣어둔 "universal shellcode"에서 볼 수 있다.

## 명령어/단축키
- GDB/Pwndbg: `b *0xADDR`(브레이크포인트), `i r`(레지스터 확인), `si`(1개 명령어 step), `catch syscall`(시스템 콜 진입 시 자동 중단, gdb 7.x 이상)
- IDA: 시스템 콜 번호 상수 위에서 우클릭 → 필요 시 자동 열거형(enum)으로 표시 가능하지만 기본적으로는 자동 인식 안 됨 — i386 syscall 번호표를 따로 참고해야 함
- objdump/GDB에서 AT&T 문법으로 보일 때 `int $0x80`으로 표시되는데 Intel 문법의 `int 0x80`과 완전히 같은 명령이다.

## 출력 해석
- `int 0x80` 실행 직후 `EAX`에 새 값이 들어와 있다면 그것이 시스템 콜의 반환값이다. 음수(예: `0xFFFFFFxx`)면 대부분 `-errno` 형태의 에러를 뜻한다(리눅스 시스템 콜의 공통 관례).
- 디버거로 `int 0x80` 전후 스택 포인터를 비교하면 변화가 없어야 정상이다 — 사용자 스택은 시스템 콜로 인해 불균형해지지 않는다.

## 흔한 실수
- x86-64 시스템 콜 번호표를 `int 0x80` 코드에 그대로 적용하는 것 — i386과 x86-64는 번호 체계가 다르다. 반드시 i386용 표를 찾는다.
- 인자 레지스터를 `RDI/RSI/RDX/...`(SYSCALL/함수 호출 규약)로 착각하는 것 — `int 0x80`은 `EBX/ECX/EDX/ESI/EDI/EBP` 순서다.
- `int 0x80`과 `int3`(`0xCC`, 디버거 브레이크포인트)을 혼동하는 것 — 오퍼랜드 유무와 값이 다르다(`int3`은 전용 1바이트 인코딩, `int 0x80`은 `CD 80` 2바이트).
- 64비트 바이너리에 `int 0x80`이 있는 걸 보고 "이 바이너리는 32비트다"라고 단정하는 것 — 64비트 프로세스 안에서도 32비트 호환 셸코드로 의도적으로 삽입될 수 있다.

## 막혔을 때 다음 체크
- 시스템 콜 번호를 찾았는데 동작이 이해 안 되면 → i386 `unistd_32.h` 계열 번호표(예: 리눅스 커널 소스의 `arch/x86/entry/syscalls/syscall_32.tbl` 오프라인 사본)를 확보해서 대조한다.
- `syscall`과 `int 0x80`이 같은 파일에 섞여 있어 헷갈리면 → 각 블록이 32비트 코드 세그먼트인지 64비트 코드 세그먼트인지(주변 레지스터가 `E`로 시작하는지 `R`로 시작하는지) 먼저 구분한다.
- 반환값(`EAX`)이 음수인데 무슨 에러인지 모르겠다면 → 절댓값을 `errno` 번호표에서 찾는다.

## 미니 예제

**예제 1 — 고전 "Hello" 쉘코드 (32비트 i386)**
```asm
section .text
global _start
_start:
    mov eax, 4          ; sys_write
    mov ebx, 1           ; fd = stdout
    mov ecx, msg
    mov edx, msg_len
    int 0x80

    mov eax, 1           ; sys_exit
    xor ebx, ebx
    int 0x80
```

**예제 2 — execve 쉘코드 (`/bin/sh` 실행, i386)**
```asm
; eax = 11 (sys_execve)
; ebx = "/bin/sh" 문자열 주소
; ecx = argv 배열 주소 (또는 0)
; edx = envp 배열 주소 (또는 0)
mov eax, 11
int 0x80
```
C로 대응하면 `execve("/bin/sh", NULL, NULL)`.

**예제 3 — 64비트 바이너리 안의 32비트 호환 int 0x80 (드문 케이스)**
```asm
; 64비트 프로세스지만 32비트 레지스터로 int 0x80 호출
mov eax, 4         ; 여전히 i386 write 번호 사용, RAX 아님
mov ebx, 1
mov ecx, esi
mov edx, 10
int 0x80
```
64비트 컨텍스트라도 `int 0x80` 벡터로 들어가는 순간 커널은 i386 시스템 콜 테이블/레지스터 규약으로 처리한다.

**예제 4 — SYSCALL과 나란히 비교**
```asm
; --- 32비트: int 0x80 ---
mov eax, 1          ; sys_exit (i386 번호)
xor ebx, ebx
int 0x80

; --- 64비트: syscall ---
mov rax, 60          ; sys_exit (x86-64 번호, 60번!)
xor rdi, rdi
syscall
```
같은 "exit(0)"인데 번호(1 vs 60)와 인자 레지스터(EBX vs RDI)가 완전히 다르다는 점이 이 명령어의 핵심 함정이다.

- `INT`/`IRET` 명령어 동작: Intel 64 and IA-32 Architectures Software Developer's Manual, Volume 2A, "INT n/INTO/INT3/INT1—Call to Interrupt Procedure" 섹션 기준 (2026-09-08 검증).
- 리눅스 `int 0x80` 시스템 콜 게이트, i386 레지스터 규약(EAX/EBX/ECX/EDX/ESI/EDI/EBP): 리눅스 커널 문서 및 `man 2 syscall` (Linux man-pages) 기준.
- i386 vs x86-64 시스템 콜 번호 차이(예: write=4 vs 1, exit=1 vs 60): 리눅스 커널 소스 `syscall_32.tbl` / `syscall_64.tbl` 기준.
