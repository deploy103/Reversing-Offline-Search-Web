## 한 줄 요약
`NOP`(No Operation)은 레지스터/메모리/플래그를 전혀 건드리지 않고 `RIP`(다음 명령 주소)만 자기 길이만큼 전진시키는 "아무것도 안 하는" 명령어다. 오퍼랜드 없이 단독으로 쓰이며, 기계어로는 `0x90` 한 바이트다.

## 언제 검색해야 하나
- 디스어셈블리에 `nop`이 여러 줄 연속으로 나오거나, 헥스 덤프에 `90 90 90 90`처럼 0x90이 반복될 때
- 함수 시작 주소 앞에 왜 `nop`이 몇 개 끼어있는지 궁금할 때
- 크랙미(crackme)에서 "실패" 분기나 검증 함수 호출을 무력화하고 싶을 때
- x64dbg/IDA에서 명령어를 NOP으로 덮어써서 패치하는 방법을 알고 싶을 때
- `0F 1F 44 00 00` 같은 낯선 바이트열이 실제로는 NOP이라는 걸 확인하고 싶을 때

## 핵심 개념

### NOP이 실제로 하는 일
`NOP`은 오퍼랜드가 없다. 실행해도:
- 레지스터 값 변화 없음
- 메모리 변화 없음
- 플래그(CF/ZF/SF/OF/AF/PF 전부) 변화 없음
- 스택(RSP) 변화 없음

유일한 효과는 `RIP`(또는 32비트에서 `EIP`)가 이 명령어의 바이트 길이만큼 증가해서 다음 명령으로 넘어가는 것뿐이다. 가장 흔한 단일 바이트 형태(`0x90`)는 역사적으로 `XCHG EAX, EAX`(자기 자신과 교환 = 아무 효과 없음)와 같은 인코딩이지만, 현대 CPU는 이를 진짜 "아무 일도 안 하는" 전용 명령으로 인식해서 실행한다.

### 멀티바이트 NOP
컴파일러/어셈블러는 1바이트 `0x90`을 여러 개 나열하는 대신, **한 개의 명령어로 여러 바이트를 채우는 멀티바이트 NOP 인코딩**(`0F 1F /0` 계열, 예: `0F 1F 44 00 00` = `nop dword ptr [rax+rax*1+0x0]`)을 자주 사용한다. 이유는 CPU 입장에서 짧은 명령어 여러 개를 디코딩하는 것보다 긴 명령어 하나를 디코딩하는 게 더 효율적이기 때문이다. IDA/Ghidra에서 `nop dword ptr [...]`나 `nop word ptr [...]` 형태로 보이면 전부 이 멀티바이트 NOP이다 — 오퍼랜드처럼 보이는 메모리 표현이 있지만 실제로는 아무 메모리 접근도 일어나지 않는다.

### 리버싱에서 NOP을 보면 반드시 구분해야 할 두 가지 의미
디스어셈블리에서 `0x90`이 연속으로 나오면, 아래 두 상황 중 어느 쪽인지 반드시 구분해야 한다.

**1) 정렬용 패딩 (정상, 무해함)**
함수의 시작 주소나 루프의 맨 위를 16바이트(또는 특정) 경계에 맞추기 위해 컴파일러/링커가 넣는 padding이다. 판별 기준:
- NOP들이 끝난 직후 주소가 "딱 떨어지는" 정렬된 주소인가 (예: 16진수로 끝자리가 `0x0`이나 `0x10` 등)
- NOP들이 서로 관계없는 두 코드 블록(예: 함수 A의 끝과 함수 B의 시작) 사이에 끼어 있는가, 즉 어떤 함수의 본문 "중간"이 아닌가

이 경우는 완전히 정상이며 아무 의심할 필요가 없다.

**2) 패치로 무력화된 코드 ("NOP 슬레드", "체크 무력화")**
원래 있던 명령어(아주 흔하게는 검증 함수를 부르는 `CALL`, 또는 "틀렸습니다" 분기로 가는 조건부 점프 `JE`/`JNZ` 등)를 크래커(또는 학습 목적의 리버서 본인)가 정확히 같은 바이트 수만큼 `0x90`으로 덮어써서 그 명령어를 무력화한 것이다. 판별 기준:
- NOP들이 함수 본문 **중간**, 즉 정상적인 실행 흐름 한복판에 있는가
- 길이가 짧은 조건부 점프(2바이트, `Jcc rel8`) 또는 `CALL rel32`(5바이트)와 정확히 일치하는 개수인가 (전형적으로 2바이트 또는 5바이트 단위)
- 같은 바이너리의 원본/미패치 사본이 있다면 그 자리에 실제 명령어가 있는지 바이트 단위로 비교(diff)해서 확인 가능

### 리버서가 직접 NOP 패치를 적용하는 법
이 프로젝트의 범위는 CTF/워게임/교육 목적이다 — 아래 절차는 **크랙미 연습용으로 "가짜 플래그 실패" 분기를 무력화**하는 예시로만 사용하고, 상용 소프트웨어 라이선스 우회 목적으로 쓰지 않는다.

- **x64dbg**: 디스어셈블리(CPU) 창에서 무력화할 명령어(들)를 드래그해서 선택 → 우클릭 → `Binary` → `Fill with NOPs`. 또는 명령어 한 줄을 선택하고 스페이스바를 눌러 어셈블 다이얼로그를 연 뒤 직접 `nop`을 입력해서 덮어쓸 수도 있다.
- **IDA**: 무력화할 명령어 위에 커서를 놓고 `Edit` → `Patch Program` → `Assemble...`로 그 자리에 `nop`을 어셈블하거나, Hex View에서 직접 `90` 바이트로 덮어쓴다. 메모리상의 패치는 디스크 파일에 반영되지 않으므로, 실제 실행 파일(.exe)을 바꾸려면 `Edit` → `Patch Program` → `Apply patches to input file`을 눌러야 한다.

### IDA/Ghidra 디컴파일 표현
NOP은 프로그램 로직에 아무 영향이 없으므로 디컴파일러(F5)는 이를 아예 결과 C 코드에 표시하지 않는다 — 디스어셈블리 화면에서만 보인다.

### 리버싱에서의 의미
- 함수 진입점 바로 앞의 짧은 NOP 뭉치는 그냥 넘겨도 된다(정렬 패딩).
- 함수 본문 중간에 뜬금없이 낀 NOP 뭉치, 특히 정확히 2바이트나 5바이트짜리는 "여기 원래 뭔가 있었다"는 강한 신호다 — 조건부 점프나 CALL이 무력화됐을 가능성이 매우 높다. 이런 지점은 크랙미 풀이나 안티치트 우회 흔적을 분석할 때 최우선으로 살펴봐야 할 위치다.

## 화면/코드에서 보이는 징후
- `nop` (디스어셈블리 한 줄, 바이트 `90`)
- `90 90 90 90 90 90` (헥스 덤프에서 연속된 0x90)
- `nop word ptr [rax+rax*1+0x0]`, `nop dword ptr [rax+rax*1+0x0]` — 멀티바이트 NOP (바이트 `0F 1F ...`)
- 함수 시작 주소 직전에 1~15바이트 정도의 짧은 NOP 구간 — 정렬 패딩
- 함수 본문 중간, 정확히 2바이트 또는 5바이트짜리 NOP 구간 — 패치로 무력화된 Jcc 또는 CALL 의심

## 가장 먼저 할 것
NOP 구간을 만나면:
1. 이 구간이 함수/루프 경계(코드 블록 사이)에 있는가, 아니면 정상 실행 흐름 한복판에 있는가?
2. NOP 구간 직후 주소가 정렬된 주소(16바이트 배수 등)인가?
3. NOP 구간의 정확한 바이트 길이가 몇인가 (2바이트면 짧은 Jcc, 5바이트면 CALL rel32/JMP rel32를 의심)?

## 단계별 절차

**1) 정렬 패딩인지 확인**
```
; sub_401230의 끝
...
ret
90 90 90 90 90 90          ; 패딩
sub_401240:                 ; 다음 함수 시작 (0x401240, 16바이트 정렬)
    push rbp
```
→ 정상. 무시하고 넘어간다.

**2) 무력화된 조건부 점프 의심**
원본(가정):
```asm
cmp     eax, 0
je      wrong_flag      ; 74 05  (2바이트, JE rel8)
```
패치 후:
```asm
cmp     eax, 0
nop                       ; 90
nop                       ; 90
```
→ 정확히 2바이트가 NOP으로 바뀌었다. `je`가 원래 있던 자리라고 강하게 의심할 수 있다.

**3) 무력화된 CALL 의심**
원본(가정):
```asm
call    check_password   ; e8 xx xx xx xx  (5바이트, CALL rel32)
test    eax, eax
jz      wrong_flag
```
패치 후:
```asm
nop                        ; 90
nop                        ; 90
nop                        ; 90
nop                        ; 90
nop                        ; 90
test    eax, eax           ; eax는 이전에 남아있던 쓰레기 값 (CALL이 실행 안 됐으므로 "진짜" 반환값이 아님)
jz      wrong_flag
```
→ 5바이트가 NOP으로 바뀌었다. 주의: `call`을 단순히 NOP으로만 지우면 `eax`가 실제로 계산된 값이 아니라 그 이전 명령이 남긴 쓰레기 값이 되어, 뒤따르는 `test eax, eax` / `jz wrong_flag`의 동작이 예측 불가능해질 수 있다. 그래서 제대로 된 패치는 보통 CALL만 지우는 게 아니라, 뒤따르는 비교/분기까지 함께 손봐서 항상 "성공" 경로로 가도록 만든다 — 단순히 "CALL을 NOP으로 지우면 끝"이라고 생각하면 안 된다.

**4) 직접 패치해보기 (x64dbg, 연습용)**
CPU 창에서 무력화할 명령어를 선택 → 우클릭 → `Binary` → `Fill with NOPs` → 변경된 바이트 수가 원본 명령어 길이와 정확히 같은지 확인.

## 명령어/단축키
- x64dbg: 명령어 선택 후 우클릭 → `Binary` → `Fill with NOPs`, 또는 `Space`로 어셈블 다이얼로그를 열어 직접 `nop` 입력. 패치 결과는 `File` → `Patches`에서 목록 확인 후 저장 가능.
- IDA: 커서를 명령어 위에 놓고 `Edit` → `Patch Program` → `Assemble...` (또는 `Fill with NOPs`류 플러그인), 디스크 반영은 `Edit` → `Patch Program` → `Apply patches to input file`.
- GDB/Pwndbg: 런타임 메모리에 `set {char}addr = 0x90` 식으로 직접 바이트를 덮어써서 실행 중 패치 가능(디스크 파일에는 반영 안 됨, 프로세스 종료 시 사라짐).

## 출력 해석
- 헥스 덤프에서 `90`이 연속되면 그 개수가 곧 "무력화된 명령어의 원래 바이트 길이"의 강력한 단서다. 2바이트 = 짧은 Jcc, 5바이트 = CALL/JMP rel32, 6바이트 = 근접 조건부 점프(`Jcc rel32`, 0F 8x 계열).
- 디스어셈블러가 `nop word ptr [...]` 같은 형태를 보여줘도 실제로 그 메모리 주소를 읽지 않는다 — 오퍼랜드처럼 보이는 부분은 명령어 길이를 맞추기 위한 인코딩 트릭일 뿐이다.

## 흔한 실수
- **NOP 구간을 보자마자 "패치된 코드다"라고 단정**: 함수/루프 경계의 정렬 패딩일 수도 있다. 위치(경계인지 중간인지)와 정렬 여부를 먼저 확인해야 한다.
- **명령어 길이를 맞추지 않고 패치**: 어떤 명령어를 다른 명령어로 재어셈블할 때, 원본과 바이트 길이가 다른 인코딩을 쓰면(예: 짧은 인코딩으로 재어셈블) 그 뒤의 모든 명령어 주소가 밀리면서 함수 전체가 깨진다. 안전한 원칙은 **항상 원본과 정확히 같은 바이트 수만큼만 NOP으로 채우고, 중간에 바이트를 삽입/삭제하지 않는다**는 것이다.
- **CALL만 지우면 끝이라고 생각**: CALL을 NOP으로 지우면 그 함수의 반환값(EAX/RAX)이 계산되지 않은 채로 남아, 뒤따르는 비교/분기 로직이 예측 불가능하게 동작할 수 있다. 온전한 패치를 하려면 뒤따르는 `test`/`cmp`/`jcc`까지 함께 살펴봐야 한다.
- **메모리상의 패치가 디스크 파일에도 자동 저장된다고 착각**: IDA/x64dbg 모두 명시적으로 저장(예: IDA의 `Apply patches to input file`)하지 않으면 패치는 그 세션(또는 실행 중 프로세스)에만 적용된다.

## 막혔을 때 다음 체크
- NOP 구간이 정렬 패딩인지 패치 흔적인지 애매하면 → 원본/미패치 바이너리가 있는지, 또는 같은 함수의 다른 컴파일 버전과 바이트 diff를 떠서 비교해본다.
- NOP으로 무력화한 뒤 프로그램이 크래시하거나 이상하게 동작하면 → 지워진 CALL의 반환값에 의존하는 뒤쪽 로직이 있는지, 또는 명령어 길이가 원본과 정확히 일치했는지 다시 확인한다.
- `nop word ptr [...]` 형태가 실제 메모리 접근인지 궁금하면 → 디버거로 해당 주소에서 한 스텝 실행해보고 관련 메모리나 레지스터가 전혀 변하지 않는지 확인한다.

## 미니 예제

**예제 1 — 함수 앞 정렬 패딩**
```
; 바이트: 90 90 90 90 90 90
; 함수 sub_401240 시작 주소가 0x401240 (16의 배수)로 정렬됨
401230: c3                    ret
401231: 90 90 90 90 90 90     nop 6개  (정렬용 패딩, 실행 흐름과 무관)
401240: 55                    push rbp   ; 여기가 sub_401240 시작
```

**예제 2 — 짧은 조건부 점프 무력화 (전/후 바이트 비교)**
```
; 원본 (2바이트, JE rel8)
83 f8 00      cmp eax, 0
74 05         je  wrong_flag

; 패치 후 (정확히 2바이트만 교체)
83 f8 00      cmp eax, 0
90            nop
90            nop
```

**예제 3 — 멀티바이트 NOP (컴파일러가 생성한 정렬용)**
```
0f 1f 44 00 00    nop dword ptr [rax+rax*1+0x0]   ; 5바이트를 한 명령어로 처리
```

**예제 4 — CALL 무력화와 그 부작용 (연습용 예시)**
```c
// 원본 C 의도
if (check_password() == 0) fail();
```
```asm
; 원본 (5바이트 CALL)
e8 12 34 00 00    call check_password
85 c0              test eax, eax
74 08              jz   wrong_flag

; CALL만 NOP으로 지운 패치 (5바이트 교체)
90                 nop
90                 nop
90                 nop
90                 nop
90                 nop
85 c0              test eax, eax   ; eax는 check_password가 계산한 값이 아니라 이전 명령이 남긴 쓰레기 값!
74 08              jz   wrong_flag  ; 결과가 예측 불가능 — 온전한 패치가 아님
```
이 예제는 "CALL만 NOP으로 지우면 끝"이라는 흔한 오해를 보여준다. 실제로 크랙미를 안정적으로 통과시키려면 `test eax, eax` / `jz wrong_flag`까지 함께 NOP으로 지우거나, `jz`를 무조건 분기하지 않도록 바꾸는 등 뒤따르는 로직까지 함께 고려해야 한다.
