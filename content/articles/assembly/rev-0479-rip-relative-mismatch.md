## 한 줄 요약
x64의 RIP-relative 주소 지정에서 `[rip+disp32]`의 기준 주소는 **그 명령어의 시작 주소가 아니라, 그 명령어가 끝난 직후(다음 명령어가 시작되는) 주소**이며, 이걸 헷갈려서 명령어 시작 주소에 변위를 더하면 실제 IDA/Ghidra가 보여주는 주소와 어긋난다.

## 언제 검색해야 하나
- `lea rax, [rip+0x2ed5]` 같은 명령어를 손으로 직접 계산했는데 IDA가 보여주는 주석(`; "Hello"`)의 실제 주소와 다르게 나올 때
- IDA/Ghidra 없이 objdump나 raw 헥스덤프만으로 문자열/전역 변수 주소를 손으로 역산해야 할 때
- x86(32비트)과 x64에서 상대 주소 지정 방식이 왜 다른지 궁금할 때
- 디버거에서 실제 RIP 값과 정적 분석에서 계산한 주소가 안 맞아서 당황할 때

## 핵심 개념

### RIP-relative addressing이란
x64에서 새로 추가된 주소 지정 모드로, ModRM 바이트가 `mod=00, rm=101`인 경우 **RIP(다음 실행할 명령어의 주소) + 32비트 부호있는 변위(disp32)**를 유효 주소로 사용한다.
```
유효 주소 = RIP(현재 명령어가 끝난 직후 주소) + disp32
```
이 방식이 x64에 추가된 이유는 PIE(Position Independent Executable)와 ASLR을 지원하기 위해서다. 절대 주소를 코드에 하드코딩하지 않고 "현재 실행 위치 기준 상대 위치"로 데이터를 참조하면, 바이너리가 메모리 어디에 로드되든 코드를 수정할 필요 없이 항상 올바른 데이터를 가리킬 수 있다.

### 왜 "명령어 끝난 직후"가 기준인가
CPU가 명령어를 디코딩할 때 RIP는 이미 **다음 명령어를 가리키도록 미리 갱신**된다(파이프라인 구조상 그렇게 설계됨). 즉 `lea rax, [rip+0x2ed5]`라는 명령어가 실행되는 시점에는, "이 lea 명령어 자체가 몇 바이트인지" 계산이 끝난 뒤의 주소, 다시 말해 **다음 명령어의 시작 주소**가 RIP 값으로 쓰인다.

```
계산 공식: 목표 주소 = (이 명령어의 시작 주소 + 이 명령어의 전체 바이트 길이) + disp32
         = 다음 명령어의 시작 주소 + disp32
```

### 초보자가 자주 틀리는 계산
```
명령어: 48 8D 05 D5 2E 00 00      lea rax, [rip+0x2ed5]
이 명령어의 시작 주소: 0x401020
이 명령어의 길이: 7바이트 (REX 1 + opcode 1 + ModRM 1 + disp32 4)
```
틀린 계산(시작 주소 기준):
```
0x401020 + 0x2ed5 = 0x403EF5   ← 틀림
```
올바른 계산(다음 명령어 기준):
```
다음 명령어 시작 = 0x401020 + 7 = 0x401027
0x401027 + 0x2ed5 = 0x403EFC   ← 맞음
```
7바이트 차이가 최종 주소에도 그대로 7만큼 차이로 남는다. IDA/Ghidra는 이 계산을 자동으로 해서 `lea rax, [rip+0x2ED5]  ; "Hello, world"` 처럼 주석으로 실제 문자열/데이터까지 바로 보여주므로 평소엔 손으로 계산할 일이 거의 없지만, **raw 바이트만 주어진 문제**(패치, 쉘코드 분석, 수동 오프셋 계산)에서는 이 공식을 직접 써야 한다.

### x86(32비트)에는 RIP-relative가 없다
32비트 x86에는 RIP 상대 주소 지정 모드가 없다(EIP를 오퍼랜드로 직접 쓸 수 없음). 그래서 32비트 PIE 코드는 `call $+5; pop ebx` 같은 트릭으로 현재 EIP 값을 레지스터에 담은 뒤 거기에 오프셋을 더하는 방식을 쓴다. x64에서 RIP-relative가 표준으로 추가되면서 이런 트릭 없이 훨씬 짧고 빠른 코드로 위치 독립 코드를 만들 수 있게 됐다.

### CALL/JMP의 rel32와 헷갈리지 말 것
`call`/`jmp`의 상대 오프셋(rel32)도 "다음 명령어 기준"이라는 점은 RIP-relative 메모리 오퍼랜드와 동일한 원리다(REV-0478 참고). 차이는, CALL/JMP의 rel32는 **그 자체가 목표 실행 주소**가 되고, RIP-relative 메모리 오퍼랜드의 disp32는 **데이터/포인터의 주소**를 가리킨다는 점이다.

## 화면/코드에서 보이는 징후
- `lea rcx, [rip+0x1234]` — 흔히 문자열 리터럴, 전역 변수, vtable 등을 가리킴
- `mov eax, [rip+0x5678]` — 전역 변수 값을 읽음
- `call qword ptr [rip+0x2f10]` — IAT(Import Address Table)를 거친 임포트 함수 호출 (REV-0071 참고)
- IDA가 자동으로 `; "문자열내용"` 또는 `; dword_403020` 같은 주석을 붙여 실제 주소를 대신 알려줌 (직접 계산 불필요)

## 가장 먼저 할 것
1. IDA/Ghidra를 쓸 수 있다면 자동 주석을 그대로 신뢰한다 — 손 계산은 도구가 없을 때만 필요하다.
2. 손으로 계산해야 한다면 그 명령어의 **정확한 전체 바이트 길이**부터 구한다(REV-0477 참고, 프리픽스/ModRM/SIB/disp를 다 포함).
3. "명령어 시작 주소"가 아니라 "명령어 시작 주소 + 명령어 길이"를 기준으로 disp32를 더한다.

## 단계별 절차
**1) 명령어 길이 확정**

`objdump -d` 결과나 IDA 헥스뷰에서 해당 명령어가 몇 바이트인지 정확히 센다. RIP-relative를 쓰는 명령어는 보통 ModRM(1) + disp32(4)가 뒤에 붙으므로 opcode 부분만 잘 파악하면 된다.

**2) 다음 명령어 시작 주소 계산**

`다음 명령어 주소 = 이 명령어 시작 주소 + 이 명령어 전체 길이`

**3) disp32를 부호있는 32비트 정수로 해석해서 더하기**

disp32는 부호 있는 값이라 음수(0x80000000~0xFFFFFFFF 범위, 즉 최상위 비트가 1)일 수 있다. 음수면 실제로는 RIP보다 **앞쪽** 주소를 가리킨다. 예: `disp32 = 0xFFFFFF00`이면 이는 `-256`이므로 `다음 명령어 주소 - 256`이 목표 주소다.

**4) 결과를 IDA/objtool 출력과 대조**

계산 결과가 IDA 주석이나 `objdump -d`가 보여주는 해석 결과와 일치하는지 검증한다.

## 명령어/단축키
- objdump: `objdump -d -M intel <binary>`는 이미 상대 주소를 절대 주소로 환산해서 주석(`# 0x403efc`)을 붙여준다.
- IDA: 명령어 우클릭 없이 그냥 오퍼랜드에 마우스를 올리면 상태 표시줄에 실제 절대 주소가 나온다. `; "문자열"` 주석은 자동 생성.
- GDB: `x/i $rip` 실행 시 `# 0x403efc`처럼 계산된 절대 주소를 같이 보여준다.
- 계산기: 파이썬 인터프리터로 `hex(0x401027 + 0x2ed5)` 처럼 즉석 계산하는 것이 가장 빠르고 실수가 적다.

## 출력 해석
- objdump나 GDB가 `# 0x403efc <flag_string>`처럼 주석을 붙이면 그게 이미 정답(계산된 절대 주소)이다.
- 계산 결과가 매핑된 섹션 범위를 벗어나면(예: `.text`나 `.data` 범위 밖) 명령어 길이를 잘못 셌을 가능성이 크다 — 1단계로 돌아가 다시 센다.
- 음수 disp32를 양수로 착각해서 완전히 다른(더 큰) 주소를 계산했다면 최상위 비트를 다시 확인한다.

## 흔한 실수
- disp32를 "이 명령어가 시작하는 주소" 기준으로 더하는 것 — 항상 **다음 명령어 시작 주소** 기준이어야 한다.
- 명령어 길이를 opcode 1바이트만으로 대충 잡아서 disp32를 더할 기준 주소 자체를 잘못 구하는 것 — 프리픽스, ModRM, SIB까지 포함한 전체 길이를 정확히 세야 한다(REV-0477 참고).
- disp32를 부호 없는 값으로 착각해서 음수 오프셋(뒤쪽이 아니라 앞쪽 주소를 가리키는 경우)을 놓치는 것.
- x86(32비트) 코드에서도 RIP-relative가 있다고 착각하는 것 — 32비트에는 이 주소 지정 모드 자체가 없다.

## 막혔을 때 다음 체크
- 애초에 명령어 길이 계산이 헷갈리면 → REV-0477(명령어 길이가 이상하게 길게 잡힐 때)
- CALL의 rel32 상대 주소와 헷갈린다면 → REV-0478(CALL 명령인데 함수로 안 보이고 이상한 오프셋일 때)
- LEA 명령어 자체의 기본 동작이 궁금하면 → REV-0042(LEA: 주소 계산인데 왜 산술 연산처럼 보이는가)
- PIE/ASLR로 인해 실제 실행 주소가 계속 바뀌는 문제라면 → REV-0478의 ASLR 설명 참고

## 미니 예제
**예제 1 — 문자열 리터럴 참조 (LEA)**
```asm
0x401020:  48 8D 05 D5 2E 00 00     lea     rax, [rip+0x2ed5]
```
- 명령어 길이 7바이트 → 다음 명령어 주소 = `0x401020 + 7 = 0x401027`
- 목표 주소 = `0x401027 + 0x2ed5 = 0x403EFC`
- IDA라면 `lea rax, [rip+2ED5h] ; "Correct!"` 처럼 문자열까지 바로 보여준다.

**예제 2 — 전역 변수 읽기 (MOV)**
```asm
0x401030:  8B 05 CA 1F 00 00        mov     eax, [rip+0x1fca]
```
- 명령어 길이 6바이트 → 다음 명령어 주소 = `0x401030 + 6 = 0x401036`
- 목표 주소 = `0x401036 + 0x1fca = 0x403000` (전역 변수 위치)

**예제 3 — 음수 변위 (뒤쪽이 아니라 앞쪽 주소)**
```asm
0x401050:  48 8B 05 A0 FF FF FF     mov     rax, [rip-0x60]
```
- disp32 = `0xFFFFFFA0` = 부호있는 정수로 `-96`
- 명령어 길이 7바이트 → 다음 명령어 주소 = `0x401050 + 7 = 0x401057`
- 목표 주소 = `0x401057 - 96 = 0x401057 - 0x60 = 0x400FF7` (현재 명령어보다 앞쪽 주소)

## 관련 글
- REV-0042 — LEA: 주소 계산인데 왜 산술 연산처럼 보이는가
- REV-0477 — 명령어 길이가 이상하게 길게 잡힐 때
- REV-0478 — CALL 명령인데 함수로 안 보이고 이상한 오프셋일 때
- REV-0039 — MOV: 값 복사와 레지스터 메모리 이동

## 출처/검증
- RIP-relative addressing 정의(`mod=00, rm=101` 인코딩, disp32 기준점): Intel 64 and IA-32 Architectures Software Developer's Manual, Volume 2A, "Table 2-2, 2-3 32-bit / RIP-Relative Addressing" 및 Volume 1, "3.7.5 RIP-Relative Addressing" 기준.
- x86(32비트)에는 RIP-relative 모드가 없다는 점: 동일 매뉴얼에서 RIP-relative addressing이 64비트 모드 전용으로 명시됨(2026-09-08 확인).
