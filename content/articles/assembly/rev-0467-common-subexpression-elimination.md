## 한 줄 요약
Common Subexpression Elimination(CSE)은 컴파일러가 코드 안에서 **똑같은 계산이 반복되는 부분을 찾아 딱 한 번만 계산**하고 그 결과를 레지스터에 저장해 재사용하는 최적화로, 그 결과 어셈블리에서는 소스코드상 서로 다른 줄이었던 계산들이 하나의 명령어로 합쳐져 사라져 보인다.

## 언제 검색해야 하나
- 디컴파일 결과(C 코드)의 특정 변수 사용이 그 위 어디에서도 다시 계산되는 곳 없이 "이미 있던 값"을 그대로 쓰는 것처럼 보일 때
- 소스코드상 `a*b+c` 같은 식이 함수 안에서 두 번 나오는데, 실제 어셈블리에는 곱셈/덧셈 명령어가 한 번만 있을 때
- 어떤 레지스터 값이 코드 훨씬 위쪽에서 계산된 뒤 중간에 아무 재계산도 없이 한참 뒤에서 다시 쓰이는 걸 발견했을 때
- IDA 디컴파일에서 지역 변수 개수가 소스보다 적어 보이거나, 변수 하나가 여러 소스 표현식을 대표하는 것처럼 보일 때

## 핵심 개념

### CSE가 하는 일
"공통 부분식(common subexpression)"이란 같은 입력값에 대해 **결과가 항상 같은** 계산식이 코드 안에 두 번 이상 나타나는 것을 말한다. 컴파일러는 이런 식을 발견하면 딱 한 번만 계산해서 레지스터(또는 임시 슬롯)에 저장해두고, 나머지 등장 위치에서는 재계산 없이 그 레지스터 값을 그대로 읽어 쓰도록 코드를 바꾼다.

```c
int f(int a, int b, int c) {
    int x = a * b + c;
    ...
    int y = a * b + c;   // x와 완전히 같은 식
    return x + y;
}
```
`-O0`(최적화 없음)에서는 `a*b+c`가 두 번 그대로 계산되지만, `-O2`에서는 한 번만 계산한 뒤 그 값을 두 번 사용(`x`와 `y`가 사실상 같은 레지스터)하는 코드로 바뀐다. 극단적인 경우 `x + y`는 `x * 2`(즉 왼쪽 시프트 1)로까지 더 줄어들 수 있다.

### Value Numbering과의 관계
컴파일러 내부적으로 CSE는 보통 "값 번호 매기기(Value Numbering)"라는 기법으로 구현된다 — 같은 연산자와 같은 피연산자(레지스터/상수) 조합에는 같은 "값 번호"를 부여하고, 이미 같은 값 번호가 계산된 적이 있으면 재계산 대신 기존 결과를 재사용한다. 이 과정은 함수 전체(때로는 루프를 넘나들며) 범위에서 이뤄질 수 있다.

### 루프 불변 코드 이동(LICM)과의 차이
CSE와 자주 같이 언급되는 최적화로 **Loop Invariant Code Motion(LICM)**이 있다. CSE는 "같은 식이 여러 번 나오면 하나만 계산"하는 것이고, LICM은 "루프 안에서 매 반복마다 값이 절대 안 변하는 계산을 아예 루프 밖으로 끌어내는" 것이다.
```c
for (int i = 0; i < n; i++) {
    arr[i] = base * scale + offset;   // base*scale은 i와 무관 -> 루프 밖으로 이동 가능
}
```
`base * scale`이 루프 밖으로 나가면(LICM), 매 반복마다 곱셈을 반복하지 않고 곱셈 결과 하나를 레지스터에 담아 루프 안에서는 덧셈만 반복한다. 이 둘은 서로 다른 최적화지만 결과적으로 어셈블리에서 "소스에 있던 계산이 안 보이거나 예상 밖 위치에서 한 번만 등장"하게 만든다는 점에서 리버싱 관점에서는 비슷하게 다뤄진다.

### 왜 리버싱에서 헷갈리는가
디컴파일러(IDA Hex-Rays, Ghidra)는 최적화된 어셈블리를 최대한 다시 C처럼 보여주려고 하지만, CSE로 합쳐진 계산은 원본 소스의 "두 줄"이 아니라 "한 줄 + 재사용"으로 재구성된다. 그 결과:
- 디컴파일 코드의 변수 개수가 원본 소스보다 적어 보인다.
- 어떤 계산이 어느 소스 줄에서 왔는지 1:1로 대응시키기 어려워진다.
- 레지스터 하나가 코드 여러 곳에서 "재활용"되는 것처럼 보여서, 초보자는 "이 값이 왜 아직 안 지워지고 남아있지?"라고 헷갈리게 된다.

이건 버그가 아니라 정상적인 최적화의 결과이며, 소스코드가 아니라 **어셈블리가 실제로 실행되는 진실**이라는 점을 기억하면 된다 — 디컴파일된 C는 근사치일 뿐이다.

## 화면/코드에서 보이는 징후
```asm
; a*b+c 를 한 번만 계산해서 두 번 쓰는 패턴
imul    eax, edi, esi     ; eax = a * b
add     eax, edx          ; eax = a*b + c   (이게 x)
mov     ecx, eax          ; y도 같은 값을 그대로 복사(재계산 없음)
add     eax, ecx          ; return x + y  ->  사실상 eax*2
```
소스에는 곱셈과 덧셈이 각각 두 번씩 있어야 하는데, 어셈블리에는 `imul`이 딱 한 번만 있다는 점이 CSE가 일어났다는 신호다.

## 가장 먼저 할 것
1. 디컴파일 결과에서 변수 하나가 여러 소스 표현식을 대신하는 것처럼 보이면, 그 값이 정의된 지점(최초로 계산된 곳)을 먼저 찾는다.
2. 그 값을 재사용하는 모든 지점을 나열해서, 원래 소스에서는 몇 번의 계산이었을지 유추한다.
3. 값이 "왜 이렇게 오래 살아있는지" 궁금하면, 해당 레지스터가 함수 진입부터 끝까지 다른 목적으로 재사용(overwrite)되지 않는지 확인한다.

## 단계별 절차
**1) 반복되는 계산 패턴 찾기**
```asm
imul eax, edi, esi
add  eax, edx
```
같은 조합의 `imul`/`add`가 코드 안에 딱 한 번만 있는데 그 결과(`eax` 혹은 이를 복사한 레지스터)가 여러 곳에서 쓰인다면 CSE 후보다.

**2) 레지스터 생존 구간(liveness) 추적**
값이 계산된 지점부터, 그 레지스터가 다른 값으로 덮어써지기 직전까지를 "생존 구간"이라 한다. IDA에서 레지스터 이름을 더블클릭하면 같은 함수 안에서 그 레지스터가 쓰인 다른 줄들이 하이라이트되므로 생존 구간을 눈으로 바로 확인할 수 있다.

**3) LICM인지 단순 CSE인지 구분**
값이 루프 진입 직전(루프 헤더 바깥)에서 한 번만 계산되고 루프 내부에서는 그 값을 읽기만 한다면 LICM이다. 루프와 무관한 일반 코드 블록 안에서 반복 계산이 하나로 합쳐졌다면 단순 CSE다. 구분 자체가 분석에 필수는 아니지만, "왜 이 계산이 루프 밖에 있지?"라는 의문을 풀 때 도움이 된다.

## 명령어/단축키
- IDA: 레지스터/변수 더블클릭(같은 이름 하이라이트), `Ctrl+X`(사용처 나열, 디컴파일 창에서 변수 우클릭 → Jump to xref)
- Ghidra: `Decompile` 창에서 변수 클릭 시 해당 변수의 모든 사용처가 하이라이트됨
- GDB/x64dbg: 특정 레지스터 값이 언제 마지막으로 쓰였는지 확인하려면 해당 값에 하드웨어 워치포인트(`watch $eax` 유사 기능은 레지스터 자체엔 못 걸지만, 그 값을 저장하는 메모리 주소에는 걸 수 있다)를 고려

## 출력 해석
- 디컴파일 코드에서 변수 `v1`이 함수 초반에 계산되고 그 뒤로 재계산 없이 여러 번 쓰인다면, 원본 소스에서는 같은 식이 여러 번 등장했을 가능성이 높다는 뜻으로 해석하면 된다 — 실제 로직을 되짚어 원본 소스를 재구성할 때 유용한 단서다.
- `x + y`가 `x * 2`나 `x << 1`로 보이는 경우, CSE로 인해 `x`와 `y`가 동일한 값임이 컴파일러에게 이미 증명되어 곱셈/시프트로 더 단순화됐을 수 있다.

## 흔한 실수
- 어셈블리 명령어 개수가 소스코드 줄 수보다 적다고 "코드가 생략되거나 숨겨졌다"고 의심하는 것 — 대부분은 CSE/LICM 같은 정상 최적화 때문이다.
- 레지스터 값이 재사용되는 걸 보고 "이 레지스터가 전역 상태를 나타낸다"고 과도하게 해석하는 것 — 단순히 컴파일러가 재계산을 피한 임시 값일 수 있다.
- CSE로 합쳐진 코드를 보고 원본 소스에 계산이 한 번만 있었다고 단정하는 것 — 최적화 여부를 모르는 상태에서는 몇 번 계산됐는지 100% 복원할 수 없으니, 로직(결과)이 같다는 사실에 집중하는 게 낫다.

## 막혔을 때 다음 체크
- 값이 어디서 왔는지 계속 못 찾겠다면 → REV-0463(최적화로 사라진 변수를 디버거에서 복원하는 법)을 참고해 실행 중 실제 값을 확인한다.
- 루프 관련 코드에서 계산이 이상한 위치에 있다면 → REV-0457/REV-0458(for/while, do-while 루프 구분)을 먼저 참고해 루프 경계를 정확히 파악한 뒤 LICM 여부를 재확인한다.
- 최적화 여부 자체가 헷갈리면 → REV-0464(-O0과 -O2 비교)로 최적화 없는 버전과 비교한다.

## 미니 예제
**예제 1 — 기본 CSE**
```c
int f(int a, int b, int c) {
    int x = a * b + c;
    int y = a * b + c;
    return x + y;
}
```
```asm
imul    eax, edi, esi   ; a*b
add     eax, edx        ; a*b+c  (x == y, 값 번호가 같음)
add     eax, eax        ; return x+y == x*2
ret
```

**예제 2 — LICM으로 루프 밖으로 이동**
```c
int sum_scaled(int *arr, int n, int base, int scale) {
    int total = 0;
    for (int i = 0; i < n; i++)
        total += arr[i] + base * scale;
    return total;
}
```
```asm
imul    r8d, ecx, edx      ; base*scale, 루프 진입 전에 딱 한 번 계산
xor     eax, eax           ; total = 0
xor     r9d, r9d           ; i = 0
loop_top:
    add     eax, [rdi+r9*4]
    add     eax, r8d       ; 루프마다 재계산 없이 미리 계산된 값 재사용
    inc     r9d
    cmp     r9d, esi
    jl      loop_top
```
