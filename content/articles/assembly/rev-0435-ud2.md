## 한 줄 요약
`UD2`는 실행하면 항상 `#UD`(Invalid Opcode) 예외를 발생시키도록 Intel이 명시적으로 예약해 둔 "고의로 유효하지 않은" 명령으로, 컴파일러는 이를 "여기까지 오면 절대 안 되는 지점"(noreturn 함수 뒤, 도달 불가능한 코드)을 표시하는 안전장치로 쓰고, 일부 보호 기법은 예외 핸들러와 결합해 역공학 방해용 트랩으로도 활용한다.

## 언제 검색해야 하나
- `abort()`, `exit()` 같은 반환하지 않는(noreturn) 함수 호출 바로 뒤에 낯선 명령이나 `0F 0B` 바이트가 남아 있을 때
- Ghidra 디컴파일 결과에 `halt_baddata()`라는 처음 보는 함수가 나타났을 때
- 디버거로 실행하다가 갑자기 `Invalid Opcode` 예외로 프로그램이 죽었는데 크래시 버그인지 의도된 동작인지 판단해야 할 때
- 프로그램에 예외(SEH/VEH, signal handler)를 이용한 이상한 제어 흐름이 있어서 역공학이 방해받고 있다고 의심될 때

## 핵심 개념

### UD2가 실제로 하는 일
`UD2`는 오퍼랜드가 없고, 실행되면 **항상 예외 없이 넘어가는 법 없이 무조건** `#UD`(Invalid Opcode) 예외를 발생시킨다. 이름 자체가 "Undefined instruction 2"에서 왔으며, Intel SDM은 이 opcode(`0F 0B`)를 장래에도 절대 다른 명령으로 재사용하지 않고 "고의로 유효하지 않은 명령"의 자리로 영구히 예약해 두었다고 명시한다. 즉 다른 명령들이 실수로 잘못된 바이트를 만나 우연히 `#UD`를 내는 것과 달리, `UD2`는 **일부러** 예외를 내기 위해 존재하는 정식 명령이다.

### 오퍼랜드, 방향, 실행 후 흐름
```
UD2     ; 오퍼랜드 없음
```
실행되면 그 즉시 `#UD` 예외가 발생하고 제어가 예외 핸들러로 넘어가므로, **`UD2` 다음 명령은 정상적인 순차 실행으로는 절대 도달하지 않는다.** 이 명령 자체는 레지스터나 메모리를 바꾸지 않는다 — 예외를 일으키는 것 자체가 유일한 효과다.

### 플래그/스택/RIP 변화
`UD2` 자신은 어떤 범용 플래그도 직접 세팅하지 않는다. 다만 `#UD` 예외가 발생하는 과정에서 CPU는 일반적인 예외 처리 절차대로 현재 `RFLAGS`, `CS`, `RIP` 등을 커널 스택(또는 SEH 프레임)에 저장하고 등록된 예외 핸들러로 제어를 넘긴다 — 이는 `UD2`만의 특별한 동작이 아니라 모든 예외의 공통 처리 절차다. 유저 모드 애플리케이션 입장에서는 SEH(Windows)나 시그널 핸들러(`SIGILL`, Linux)가 등록되어 있지 않으면 프로세스가 즉시 종료된다.

### 컴파일러가 만드는 전형적 패턴
1. **noreturn 함수 뒤의 안전장치**: `abort()`, `std::terminate()`, `panic!()`(Rust) 같이 "절대 반환하지 않는다"고 컴파일러가 알고 있는 함수를 호출한 바로 뒤에, 혹시라도(이론상) 실행이 이어지면 즉시 멈추도록 `UD2`를 하나 심어둔다. 이는 실제로 실행될 것을 기대하는 코드가 아니라 순수한 안전망이다.
2. **`__builtin_trap()` / `__builtin_unreachable()`**: GCC/Clang에서 프로그래머가 명시적으로 "여기 도달하면 버그"라고 표시하면 `__builtin_trap()`은 `UD2`로, `__builtin_unreachable()`은 최적화 힌트로만 쓰이거나 디버그 빌드에서는 역시 `UD2`/`INT3`로 컴파일되곤 한다.
3. **어서션/컨트롤 플로우 가드 실패**: 스택 카나리 검사 실패, Control Flow Guard(CFG) 위반, 컴파일러가 삽입한 UB(정의되지 않은 동작) 탐지 코드가 실패 처리 함수를 호출한 뒤 안전망으로 `UD2`를 붙이는 경우가 있다.

### IDA/Ghidra 디컴파일에서 보이는 모습
Ghidra는 `UD2`(및 도달 불가능한 코드 영역)를 만나면 종종 `halt_baddata()`라는 의사(pseudo) 함수 호출로 표시한다 — 이는 "이 지점은 정상적인 데이터 흐름으로 도달할 수 없다"는 것을 나타내는 Ghidra의 관례적 표기다. IDA는 대개 `UD2`를 그대로 원문 니모닉으로 보여주며, 함수의 마지막 기본 블록이 `UD2`로 끝나면 그 함수를 noreturn으로 자동 추론하는 데 참고 정보로 활용하기도 한다.

### 리버싱에서의 의미
1. **죽은 코드(dead code) 식별**: `UD2`가 보이면 그 지점은 컴파일러가 "여기 실행될 리 없다"고 확신한 자리이므로, 그 이후를 분석하느라 시간을 쓸 필요가 없다는 강한 힌트다.
2. **함수가 noreturn인지 판단하는 단서**: 호출 직후 `UD2`가 붙어 있다면 그 호출 대상 함수가 반환하지 않는(예: `abort`, `exit`, `panic`) 성격일 가능성이 높다.
3. **예외 기반 난독화/안티디버깅 트릭**: 일부 패커/프로텍터는 코드 흐름 중간에 고의로 `UD2`(또는 그냥 raw `0F 0B` 바이트)를 심어두고, SEH/VEH 예외 핸들러를 등록해 그 예외를 가로챈 뒤 핸들러 안에서 실제 로직(복호화, 분기 결정 등)을 수행한다. 이렇게 하면 선형 디스어셈블리나 단순 정적 분석으로는 진짜 실행 흐름이 보이지 않고, 디버거로 예외를 직접 추적해야만 진짜 로직을 알 수 있다 — "예외 기반 난독화(SEH 오파크 제어 흐름)"라 불리는 기법의 한 형태다.

## 화면/코드에서 보이는 징후
- `call abort` 바로 다음 줄에 `ud2`
- Ghidra 디컴파일 결과에 `halt_baddata();`
- 함수의 마지막 basic block이 조건 분기 없이 그냥 `ud2`로 끝남
- 디버거에서 실행 중 갑자기 `EXCEPTION_ILLEGAL_INSTRUCTION`(Windows) / `SIGILL`(Linux)로 멈춤

## 가장 먼저 할 것
1. `ud2` 바로 위에서 어떤 함수가 호출됐는지 확인한다 — noreturn 함수(assert 실패, abort, panic 등)일 가능성이 높다.
2. `ud2` 근처에 예외 핸들러 등록 코드(SEH `try/except`, VEH `AddVectoredExceptionHandler`, Linux `sigaction(SIGILL, ...)`)가 있는지 확인한다 — 있다면 의도적 안티디버깅/난독화를 의심한다.

## 단계별 절차
**1) 단순 안전망(대부분의 경우) 판별**
```asm
call abort
ud2            ; abort()가 절대 반환하지 않으므로 도달 불가 — 그냥 안전망
```
→ 별도 분석 없이 넘어가도 된다.

**2) 예외 기반 난독화 의심 시 대응**
```asm
; 코드 중간에
ud2             ; 고의로 예외 유발
; 정상 실행 흐름은 여기서 끝난 것처럼 보이지만...
```
이런 경우 (a) 해당 모듈의 예외 핸들러 등록 위치(SEH 체인, VEH 목록)를 먼저 찾고, (b) 디버거에서 "예외 발생 시 자동으로 핸들러로 전달"하도록 설정(x64dbg: 옵션에서 예외 패스스루 활성화, 또는 예외 발생 시 Shift+F9/F9로 프로그램에 예외를 전달)한 뒤 핸들러 내부에서 실제로 무슨 일이 일어나는지 Step Into로 추적한다.

## 명령어/단축키
- IDA: `ud2`가 함수 끝에 있으면 자동으로 해당 함수를 noreturn으로 표시하는 경우가 있음(함수 속성에서 확인 가능)
- Ghidra: 디컴파일 창에서 `halt_baddata()`가 보이면 그 지점이 도달 불가능 코드임을 뜻함
- x64dbg: 예외 발생 시 "Pass exception to program"(Shift+F9)으로 등록된 핸들러에 예외를 넘겨서 흐름을 계속 추적
- GDB: `catch signal SIGILL`로 `#UD` 관련 시그널이 발생하는 지점에서 멈추도록 설정

## 출력 해석
- Windows에서 `UD2` 실행 시 디버거에 `Access violation` 대신 `Illegal Instruction`/`Invalid Opcode` 예외 코드(`0xC000001D`)가 뜬다.
- Linux에서는 `SIGILL` 시그널로 나타나며, 핸들러가 없으면 코어 덤프와 함께 프로세스가 종료된다.

## 흔한 실수
- `UD2`를 보고 "바이너리가 손상됐다" 또는 "디스어셈블리가 잘못됐다"고 성급히 결론짓는 것 — 대부분은 컴파일러가 의도적으로 심어둔 정상적인 안전망이다.
- `UD2`를 실행 가능한 일반 명령처럼 취급해서 그 다음 줄부터 계속 선형으로 디스어셈블리를 해석하려는 것 — `UD2` 이후 바이트는 코드가 아니라 정렬용 패딩이거나 다른 함수의 시작일 수 있다.
- 예외 핸들러를 놓치고 "`UD2`가 나오면 프로그램이 그냥 죽는다"고 단정하는 것 — 안티디버깅/난독화 목적이라면 핸들러가 예외를 잡아 다른 곳으로 흐름을 이어간다.
- `UD2`(고의로 예약된 opcode)와, 그냥 디스어셈블러가 잘못된 오프셋에서 시작해 우연히 `#UD`처럼 보이는 쓰레기 바이트를 혼동하는 것 — `0F 0B`라는 정확한 2바이트 시퀀스인지 직접 바이트를 확인해서 구분한다.

## 막혔을 때 다음 체크
- 이 함수가 정말 noreturn인지 확신이 안 서면 → 이 함수를 호출하는 모든 xref 지점에서 반환값을 실제로 사용하는 코드가 있는지 확인한다(있으면 noreturn이 아닐 수 있음).
- 예외 핸들러가 어디 있는지 못 찾겠다면 → Windows PE는 `.pdata`/SEH 체인, ELF는 시그널 핸들러 등록 함수(`sigaction`, `signal`) 호출부의 xref를 먼저 찾는다.
- 스택 카나리 실패 처리부와 함께 나온 것이라면 → 스택 카나리 체크 시퀀스 자체는 REV-0442(예정)에서 별도로 다룬다.

## 미니 예제
**예제 1 — noreturn 함수 뒤의 안전망**
```c
void fatal_error(const char *msg) {
    fprintf(stderr, "%s\n", msg);
    abort();
}
```
```asm
call fatal_error
ud2              ; fatal_error가 절대 반환하지 않으므로 이론상 도달 불가
; (이 함수의 나머지 코드는 이어지지 않음)
```

**예제 2 — assert 실패 처리 뒤의 UD2 (디버그 빌드 관용구)**
```c
assert(ptr != NULL);
```
```asm
test rax, rax
jnz  assert_ok
lea  rcx, [rip+assert_msg]
call __assert_fail    ; noreturn
ud2
assert_ok:
```

**예제 3 — 스위치문 default 케이스에서 컴파일러가 넣는 UD2 (도달 불가능 보장)**
```c
switch (state) {
    case 0: ... break;
    case 1: ... break;
    default: __builtin_unreachable();
}
```
```asm
; ... 점프 테이블 처리 ...
default_case:
ud2               ; 컴파일러가 "여기 올 리 없다"고 확신하고 심어둔 트랩
```

**예제 4 — 예외 핸들러와 결합된 난독화(개념적 예시)**
```asm
; 정상 흐름
mov  eax, 1
ud2              ; 고의로 #UD 유발 -> 등록된 VEH가 잡음
; 디스어셈블리상으로는 여기서 끝난 것처럼 보이지만
; VEH 핸들러 내부에서 RIP를 조작해 실제로는 다른 주소로 계속 실행됨
```
