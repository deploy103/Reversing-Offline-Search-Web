## 한 줄 요약
루프 언롤링은 반복문의 몸체를 여러 번(2/4/8회 등) 복사해서 한 번의 분기(branch)로 여러 원소를 처리하게 만드는 컴파일러 최적화로, 소스에는 `for` 한 줄이었던 코드가 어셈블리에서는 offset이 다른 여러 블록으로 "펼쳐져" 보인다.

## 언제 검색해야 하나
- 하나의 루프 안에 `[rax]`, `[rax+4]`, `[rax+8]`, `[rax+0xc]`처럼 오프셋만 다른 거의 똑같은 코드 블록이 여러 개 반복될 때
- 루프 카운터가 1이 아니라 4나 8씩 증가하는데 원본 소스에는 그런 스텝이 없었을 때
- 메인 루프 뒤에 카운터를 1씩 증가시키는 작은 루프가 하나 더 붙어 있어서 "루프가 두 개"처럼 보일 때(remainder/tail loop)
- 함수가 소스 코드보다 훨씬 길어 보여서 실제 로직보다 복잡하다고 착각하게 될 때

## 핵심 개념

### 왜 컴파일러가 루프를 펼치는가
루프 한 번을 돌 때마다 카운터 증가, 종료 조건 비교, 분기(`jmp`/`jl` 등)가 실행되는데, 이 오버헤드는 루프 몸체 자체가 짧을수록 상대적으로 비중이 커진다. 루프 언롤링은 몸체를 N번 복사해서 **분기 횟수를 1/N로 줄이고**, 동시에 CPU가 명령어를 더 잘 파이프라이닝/재배치할 수 있게 해서 성능을 높인다. `-O2`/`-O3`(GCC/Clang), MSVC `/O2` 등 최적화 옵션에서 자동으로 적용되며, GCC는 `-funroll-loops`로 더 적극적인 언롤링을 강제할 수도 있다.

### 완전 언롤(Full Unroll) vs 부분 언롤(Partial Unroll)
- **완전 언롤**: 반복 횟수가 컴파일 시점에 고정된 작은 상수라면(`for(i=0;i<4;i++)`), 컴파일러가 루프 구조 자체를 통째로 없애버리고 몸체를 4번 그대로 나열한다. 카운터도, 분기도 남지 않는다.
- **부분 언롤**: 반복 횟수가 실행 시점에야 정해지는 변수(`for(i=0;i<n;i++)`)라면, 루프 자체는 남지만 몸체를 k번(보통 4 또는 8) 겹쳐 넣고 카운터를 k씩 증가시킨다. 이때 `n`이 k의 배수가 아닐 수 있으므로, 메인 언롤 루프가 끝난 뒤 **나머지(remainder/tail) 루프**가 하나 더 붙어서 남은 `n % k`개를 1개씩 마저 처리한다.

### 전형적인 어셈블리 패턴 (부분 언롤, 4배)
```c
long sum = 0;
for (int i = 0; i < n; i++)
    sum += arr[i];
```
```asm
xor     eax, eax          ; sum = 0
xor     ecx, ecx          ; i = 0
mov     edx, n
and     edx, ~3           ; n을 4의 배수로 내림 (main_count = n & ~3)
test    edx, edx
je      .remainder_start

.main_loop:                        ; 4개씩 처리하는 메인 루프
    add     rax, [rdi+rcx*8]        ; sum += arr[i]
    add     rax, [rdi+rcx*8+8]      ; sum += arr[i+1]
    add     rax, [rdi+rcx*8+16]     ; sum += arr[i+2]
    add     rax, [rdi+rcx*8+24]     ; sum += arr[i+3]
    add     rcx, 4
    cmp     rcx, rdx
    jl      .main_loop

.remainder_start:
    mov     r8d, n
    and     r8d, 3                  ; 남은 개수 = n % 4
    test    r8d, r8d
    je      .done

.remainder_loop:                   ; 나머지 1개씩 처리하는 작은 루프
    add     rax, [rdi+rcx*8]
    inc     rcx
    dec     r8d
    jnz     .remainder_loop

.done:
    ; rax = sum
```
`.main_loop` 하나가 원소 4개(`i`, `i+1`, `i+2`, `i+3`)를 처리하고, `rcx`가 4씩 증가하며 분기(`jl`)가 반복 횟수의 1/4만 실행된다는 것이 핵심이다. 이후 `.remainder_loop`가 `n`이 4의 배수가 아닐 때 남는 부분을 처리한다 — 이 작은 루프를 놓치고 "메인 루프만 있다"고 오해하면, `n % 4 != 0`인 경우의 처리 로직을 빠뜨리게 된다.

### 완전 언롤 예시 (컴파일 시점 상수 반복 횟수)
```c
int sum = 0;
for (int i = 0; i < 4; i++)
    sum += arr[i];
```
```asm
mov     eax, [rdi]
add     eax, [rdi+4]
add     eax, [rdi+8]
add     eax, [rdi+0xc]
; 루프 구조, 카운터, 분기 자체가 완전히 사라짐
```

### SIMD와 결합된 언롤
언롤링은 REV-0447/REV-0448에서 다루는 SIMD 자동 벡터화(auto-vectorization)와 흔히 함께 나타난다. `movdqu`/`paddd` 같은 SIMD 명령이 한 번에 4개(32비트 정수 기준 128비트 레지스터) 또는 8개(256비트 YMM)를 처리하기 때문에, "SIMD 레지스터 폭만큼 자연스럽게 언롤된 것"으로 볼 수 있다. 이런 코드는 `add rax, [rdi+rcx*8]`류의 반복 대신 `paddd xmm0, [rdi+rcx*4]` 같은 벡터 명령이 한 블록에 여러 번(또는 그 자체로 4~8개를 한 번에) 나타난다.

### IDA/Ghidra 디컴파일에서 보이는 형태
Hex-Rays/Ghidra는 언롤된 루프를 두 가지 방식 중 하나로 보여준다.
1. **깔끔하게 복원**: 언롤 패턴을 인식해서 원래의 단순한 `for (i = 0; i < n; i++) sum += arr[i];` 형태로 되돌려 보여준다(비교적 자주 성공).
2. **펼쳐진 형태 그대로 노출**: 인식에 실패하면 `sum += arr[i]; sum += arr[i+1]; sum += arr[i+2]; sum += arr[i+3];`처럼 한 블록 안에 여러 줄로 된 로직과, 그 아래 별도의 "나머지 처리" `for`/`while` 루프가 따로 보이는 지저분한 형태로 나온다.

두 번째 형태를 만났을 때, 이것이 서로 다른 로직 4개가 아니라 "같은 몸체가 4번 반복된 것"임을 알아채는 것이 이 글의 핵심이다.

### 리버싱 관점에서의 의미
루프 언롤링은 함수를 소스 코드보다 훨씬 길고 복잡해 보이게 만드는 대표적인 원인이다. 반복되는 오프셋 패턴(`+0`, `+4`, `+8`, `+0xc` 또는 `+0`, `+8`, `+16`, `+24`)을 발견하면, "이건 새로운 로직이 아니라 루프 몸체 반복이다"라고 즉시 인식하고 하나의 몸체만 분석한 뒤 나머지는 건너뛸 수 있다. 또한 언롤링이 보인다는 것 자체가 `-O2` 이상의 최적화가 적용됐다는 강한 신호이므로, 다른 곳에서도 REV-0037류의 디컴파일 이상 현상(변수 소실, 인라이닝 등)이 함께 나타날 가능성을 미리 예상할 수 있다.

## 화면/코드에서 보이는 징후
- 한 루프 몸체 안에 오프셋만 `+0`, `+4`, `+8`, `+0xc`(또는 `+8`, `+16`, `+24`)로 다른 거의 동일한 명령 블록이 반복됨
- 루프 카운터가 `add rcx, 4`, `add rcx, 8`처럼 1이 아닌 수로 증가
- 메인 루프 바로 뒤에 카운터를 1씩 증가시키는 작고 단순한 두 번째 루프(remainder loop)가 이어짐
- `and reg, ~3`, `and reg, ~7`처럼 반복 횟수를 언롤 배수로 내림 처리하는 코드

## 가장 먼저 할 것
1. 루프 몸체 안에서 반복되는 블록들이 오프셋만 다른 동일 패턴인지 먼저 확인한다.
2. 카운터 증가 폭(1, 4, 8 등)을 확인해서 언롤 배수를 짐작한다.
3. 메인 루프 뒤에 작은 루프가 하나 더 있는지 확인해서, 그것이 remainder 처리인지 판단한다.

## 단계별 절차
1. 반복되는 코드 블록이 있는지, 그리고 그 블록이 조건 분기 없이 여러 번 연달아 나열되어 있는지 확인한다.
2. 인덱스가 매 블록마다 고정 값(1, 2, 3...)만큼 증가하는 패턴인지 확인한다 — 컴파일러가 루프를 펼친 흔적이다.
3. 블록 개수를 세어 원래 루프의 언롤 팩터(2배/4배/8배 등)를 추정한다.
4. 나머지 처리(remainder loop, 언롤 팩터로 안 나누어떨어지는 나머지 반복)를 위한 별도의 작은 루프가 뒤에 붙어 있는지 확인한다.

## 명령어/단축키
- IDA: F5로 디컴파일해서 언롤 인식에 성공했는지 먼저 확인 — 실패 시 그래프 뷰(스페이스바)에서 반복 블록 개수를 눈으로 센다.
- Ghidra: Decompile 창에서 유사하게 언롤 여부 확인, "Edit Function Signature"로 반복 변수 이름을 정리하면 가독성이 좋아진다.
- x64dbg/GDB: 루프 진입부에 브레이크포인트를 걸고 카운터 레지스터 값이 몇 씩 증가하는지 몇 번 반복해서 관찰(`p $rcx` 반복 조회).

## 흔한 실수
- 언롤된 4개(또는 8개)의 블록을 서로 다른 case/분기로 착각해서 각각 별도로 분석 노트를 작성하는 것 — 실제로는 완전히 동일한 로직이 인덱스만 다르게 반복된 것이다.
- 메인 언롤 루프만 보고 분석을 끝내서, 그 뒤에 붙은 나머지(remainder) 루프를 놓치는 것 — 배열 크기가 언롤 배수가 아닐 때만 실행되는 이 부분에 경계 조건 버그나 별도 처리 로직이 숨어 있을 수 있다.
- 컴파일 시점 상수 반복 횟수로 인해 루프 구조 자체가 사라진(완전 언롤) 코드를 보고 "이 함수엔 반복문이 없다"고 오판하는 것 — 소스 레벨에는 분명 루프가 있었지만 어셈블리에는 흔적이 안 남을 수 있다.
- SIMD 명령과 결합된 언롤을 보고 "복잡한 암호화 로직"으로 오인하는 것 — 실제로는 단순 반복 연산(합계, 복사, 비교 등)을 벡터화·언롤한 것일 뿐인 경우가 많다.

## 막혔을 때 다음 체크
- 반복되는 블록의 배열 접근 표기(`[base+idx*4]`)가 헷갈리면 → REV-0440, REV-0034.
- 이게 정말 언롤인지 아니면 다른 최적화 부작용인지 헷갈리면 → REV-0037에서 컴파일러 최적화 전반을 먼저 확인.
- SIMD 명령(`movdqu`, `paddd` 등)이 왜 나오는지 궁금하면 → REV-0447/REV-0448(memset/memcpy SIMD 패턴)에서 벡터화까지 이어서 확인.

## 미니 예제

**예제 1 — 부분 언롤(4배) + 나머지 루프**
```c
long sum = 0;
for (int i = 0; i < n; i++) sum += arr[i];
```
위 "전형적인 어셈블리 패턴" 절의 전체 코드 참고. 메인 루프가 4개씩, remainder 루프가 1개씩 처리한다.

**예제 2 — 완전 언롤 (컴파일 시점 상수)**
```c
for (int i = 0; i < 4; i++) sum += arr[i];
```
```asm
mov     eax, [rdi]
add     eax, [rdi+4]
add     eax, [rdi+8]
add     eax, [rdi+0xc]
```

**예제 3 — SIMD와 결합된 8배 언롤 힌트 (자동 벡터화)**
```asm
.loop:
    movdqu  xmm0, [rdi+rcx*4]       ; 4개씩 한 번에 로드
    paddd   xmm1, xmm0
    add     rcx, 4                  ; 카운터가 4씩 증가 → 언롤/벡터화 신호
    cmp     rcx, r8
    jl      .loop
```

**예제 4 — IDA 디컴파일이 언롤을 그대로 노출한 예**
```c
// Hex-Rays가 언롤 패턴 인식에 실패한 경우
for ( i = 0; i < main_count; i += 4 )
{
    sum += arr[i];
    sum += arr[i + 1];
    sum += arr[i + 2];
    sum += arr[i + 3];
}
for ( ; i < n; i++ )
    sum += arr[i];
```
이 형태를 보면 바로 "이건 언롤된 단일 합산 루프다"라고 판단하고 `sum += arr[i]`라는 원래 로직 한 줄로 압축해서 이해하면 된다.

## 출처/검증
- 루프 언롤링 개념과 GCC `-funroll-loops`/`-O2`/`-O3` 관계: GCC 공식 문서 "Options That Control Optimization" 기준 (2026-09-08 검증).

- SIMD 자동 벡터화와 언롤의 관계: Intel 64 and IA-32 Architectures Optimization Reference Manual, "Loop Unrolling and Vectorization" 관련 절 기준.
