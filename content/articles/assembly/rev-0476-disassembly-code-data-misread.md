## 한 줄 요약
디스어셈블러가 코드 영역 중간에 끼어 있는 데이터(문자열, 점프 테이블, 정렬 패딩)를 명령어로 잘못 해석하면, 그 지점부터 바이트 경계가 어긋나면서 이후 모든 명령어가 연쇄적으로 "말이 안 되는" 쓰레기 명령어로 보인다.

## 언제 검색해야 하나
- IDA/Ghidra에서 함수 중간부터 갑자기 처음 보는 이상한 니모닉이 잔뜩 나올 때
- 디스어셈블리 목록에 `db 0FFh` 처럼 바이트 단위로 정의되지 않은 구간이 섞여 있을 때
- 함수 하나인데 그래프 뷰(Graph view)가 이상하게 끊기거나 F5 디컴파일이 실패할 때
- x64dbg/GDB에서 특정 주소부터 명령어가 화면과 실제 실행 흐름이 다르게 보일 때

## 핵심 개념

### 왜 코드와 데이터가 섞이는가
x86/x64 실행 파일의 `.text` 섹션(코드 섹션)에는 실제로 실행되는 명령어만 있는 게 아니다. 컴파일러는 종종 코드 사이에 다음과 같은 **데이터**를 끼워 넣는다.
- `switch` 문의 점프 테이블(jump table) — 주소들의 배열
- 함수 다음의 정렬(alignment) 패딩 바이트 (0x00, 0xCC 등)
- 일부 컴파일러에서 코드 근처에 배치하는 상수 리터럴이나 문자열
- SIMD 명령어가 참조하는 정렬된 상수 블록

이 데이터 구간은 CPU가 실제로 실행하지 않으므로 "명령어"가 아니다. 하지만 디스어셈블러는 기본적으로 바이트 흐름을 순서대로 읽으면서 명령어로 해석을 시도하기 때문에, 데이터 구간을 코드로 착각하면 그 지점부터 바이트 하나씩 밀리거나 당겨져서 **완전히 다른 명령어들**로 디코딩된다.

### Linear Sweep vs Recursive Descent
디스어셈블 방식은 크게 두 가지다.
- **Linear sweep(선형 훑기)**: 주소 순서대로 처음부터 끝까지 무조건 명령어로 디코딩. 빠르지만 중간에 데이터가 섞이면 그대로 오인식한다.
- **Recursive descent(재귀 하강)**: 함수 진입점에서 시작해서 실제 실행 흐름(분기, 호출)을 따라가며 도달 가능한 지점만 코드로 인식. IDA와 Ghidra는 기본적으로 이 방식을 쓰기 때문에 대부분의 데이터 오인식을 피하지만, 완벽하지는 않다 — 특히 간접 점프 테이블(jump table)의 대상들을 자동으로 다 찾지 못하거나, 어떤 함수의 끝을 잘못 판단해서 다음에 오는 데이터를 "다음 함수"로 이어 붙여 읽는 경우가 있다.

### x86 명령어가 가변 길이라서 벌어지는 문제
x86/x64 명령어는 1바이트부터 최대 15바이트까지 길이가 다르다(REV-0477 참고). 그래서 데이터를 코드로 잘못 해석하기 시작하면, 그 데이터 값이 우연히 어떤 opcode 바이트처럼 보이는 경우 임의의 길이로 "명령어처럼 생긴" 것을 계속 만들어낸다. 이후 진짜 코드가 시작되는 위치까지도 **경계가 어긋난 채로** 계속 잘못 디코딩된다 — 마치 문장을 한 글자씩 밀려 읽는 것과 같다. 이 현상을 흔히 "디스어셈블리가 깨졌다(desync, misalignment)"라고 표현한다.

## 화면/코드에서 보이는 징후
- IDA에서 처음 보는 이상한 니모닉(`db`, 정의되지 않은 opcode)이나 `align` 지시어가 코드 사이에 섞여 나옴
- 함수 그래프가 갑자기 끊기거나, F5 디컴파일 시 "decompilation failed"류 에러(REV-0152 참고)
- 명령어 오퍼랜드가 말이 안 되는 레지스터 조합(예: 존재하지 않는 조합)으로 보임
- 같은 바이트열인데 어떤 주소에서 시작해서 읽느냐에 따라 완전히 다른 명령어들로 보임(오프셋 하나 차이로 전혀 다른 해석)

## 가장 먼저 할 것
1. 깨진 지점 바로 앞의 정상 코드가 `jmp`, `ret`, `int3` 등으로 끝나는지 확인한다 — 이 경우 그 뒤는 코드가 아니라 데이터(패딩, 점프 테이블)일 가능성이 높다.
2. 그 구간이 `switch`문에서 참조하는 점프 테이블 주소인지 xref로 확인한다.
3. IDA 기준으로 문제 구간을 선택하고 `U`(Undefine)로 일단 정의를 지운 뒤, 데이터인지 코드인지 다시 판단한다.

## 단계별 절차
**1) 깨진 구간 식별**

IDA에서 이상한 니모닉이 시작되는 첫 주소를 찾는다. 보통 바로 앞줄이 `jmp` 또는 `ret`으로 끝나 있으면 그 뒤는 실행되지 않는 데이터일 확률이 높다.

**2) Undefine으로 초기화**

문제 구간을 마우스로 드래그해서 선택 → `U` 키(Undefine) → 회색 `db` 바이트 나열 상태로 되돌린다.

**3) 데이터인지 코드인지 재판단**

- 4바이트/8바이트씩 규칙적으로 증가하는 주소값들이 보이면 점프 테이블이다. 이 구간은 `Array of offsets`(Ghidra는 "Data Type" 지정)로 정의해야지 코드로 만들면 안 된다.
- 반복되는 0x00, 0x90(NOP), 0xCC 값이면 정렬 패딩이다(REV-0473 참고). 그냥 데이터로 두거나 무시한다.
- 실제 실행되는 코드처럼 보이면(정상적인 명령어 패턴, 뒤에 `ret`으로 끝남) `C` 키(Code)로 다시 코드로 만든다.

**4) 코드로 재해석한 뒤 함수 경계 재설정**

코드로 판단했다면, 함수 시작 지점에서 `P`(Create function)를 눌러 함수를 다시 정의한다. 함수 경계가 깨졌던 경우(REV-0154) 이 단계에서 같이 고쳐진다.

**5) Ghidra에서 같은 작업**

문제 주소를 우클릭 → "Clear Code Bytes"로 기존 잘못된 디코딩을 지운 뒤, 데이터라면 우클릭 → "Data" → 적절한 타입 지정, 코드라면 우클릭 → "Disassemble"을 다시 실행한다.

## 명령어/단축키
- IDA: `U`(Undefine), `C`(코드로 만들기), `D`(데이터로 만들기), `P`(함수 생성), `Shift+F12`(문자열 확인), `X`(xref로 이 데이터를 누가 참조하는지 확인)
- Ghidra: 우클릭 → Clear Code Bytes, 우클릭 → Disassemble, 우클릭 → Data → (타입 선택)
- x64dbg/GDB: 실제 실행 시점에 그 주소에 브레이크포인트를 걸어(`bp <addr>` / `b *<addr>`) 그 지점이 정말 실행되는지 동적으로 확인하는 것이 가장 확실하다.

## 출력 해석
- 어떤 주소가 실제로 CPU에 의해 실행됐다면(디버거로 확인) 그 지점은 100% 코드다. 정적 분석 추측보다 이 동적 확인이 항상 우선한다.
- 점프 테이블로 재정의한 배열의 각 원소가 실제 함수 안의 주소들을 가리키면 재해석이 맞은 것이다.
- 재해석 후에도 여전히 이상한 명령어가 나오면 시작 오프셋을 1바이트씩 앞뒤로 옮겨가며 다시 시도한다 — 어긋남은 보통 1~수 바이트 단위다.

## 흔한 실수
- 이상한 명령어가 나오면 "이 바이너리가 난독화됐다"고 성급히 결론짓는 것 — 대부분은 단순한 코드/데이터 오인식이며 REV-0472(ifunc), REV-0473(NOP 패딩) 같은 정상적인 컴파일러 산출물이다.
- 점프 테이블 구간을 실수로 `C`(코드로 만들기)해서 더 심하게 꼬아버리는 것 — 먼저 규칙적인 4/8바이트 패턴인지 확인해야 한다.
- 함수 경계를 무시하고 무작정 전체를 Undefine 후 재분석(Reanalyze)만 반복하는 것 — 정확한 문제 지점을 좁혀서 국소적으로 고치는 게 훨씬 빠르다.

## 막혔을 때 다음 체크
- 함수 경계 자체가 잘못 잡힌 것 같다면 → REV-0154(IDA에서 함수 경계가 잘못 잡혔을 때)
- 명령어 길이가 예상보다 계속 길게 잡힌다면 → REV-0477(명령어 길이가 이상하게 길게 잡힐 때)
- F5 디컴파일이 계속 실패한다면 → REV-0152(IDA Decompiler Failed가 뜰 때)
- undefined bytes를 code/data로 재해석하는 상세 절차가 더 필요하면 → REV-0155(IDA에서 Undefined Bytes를 Code/Data로 재해석)

## 미니 예제
**예제 1 — 점프 테이블을 코드로 오인식한 경우**
```asm
; 정상: switch문의 점프 테이블은 데이터인데 코드로 잘못 해석됨
jmp     dword ptr [eax*4 + 0x403020]   ; 여기까지는 정상 코드
; 0x403020부터는 실제로 4바이트 주소 4개가 나열된 데이터인데
; 디스어셈블러가 이걸 계속 명령어로 읽으면 그 뒤로 쓰레기 명령어가 나온다
```
IDA에서 `0x403020`을 `U`로 되돌리고 "Array of 4 dwords"로 지정하면 정상적인 점프 테이블로 보인다.

**예제 2 — 정렬 패딩을 코드로 오인식한 경우**
```asm
prev_func:
    ret
; 여기 0xCC 0xCC 0xCC ... 가 다음 함수 시작 전 정렬용 패딩인데
; 디스어셈블러가 이를 int3(0xCC)를 반복 실행하는 명령어로 나열해버릴 수 있다
next_func:
    push    rbp
```
`ret` 바로 다음부터 다음 함수 시작 전까지의 `0xCC` 나열은 실행되지 않는 채움 바이트다 — REV-0473에서 더 자세히 다룬다.

**예제 3 — 오프셋 1바이트 차이로 완전히 다른 명령어가 되는 경우**
```
원본 바이트: 48 8B 45 F8 (올바른 시작점에서 읽으면)
→ mov rax, [rbp-8]

같은 바이트를 1바이트 밀려서 읽으면: 8B 45 F8 ...
→ mov eax, [rbp-8]  (다른 명령어, 그리고 그 다음 바이트도 전부 밀림)
```
이처럼 시작 오프셋 하나가 어긋나면 완전히 다른 명령어 스트림이 만들어진다.
