## 한 줄 요약
소스코드에는 분명히 여러 개의 함수 호출이 있는데 디스어셈블리를 보면 `CALL` 명령이 거의 또는 전혀 없는 경우, 이는 코드가 없어진 게 아니라 컴파일러가 **작은 함수들을 호출부에 통째로 복사해 넣는 인라이닝(inlining) 최적화**를 적용했기 때문이며, 여러 함수의 로직이 하나의 큰 함수 본문 안에 순서대로 펼쳐져 있다고 이해하면 된다.

## 언제 검색해야 하나
- `-O2`, `-O3`, MSVC `/O2` 같은 최적화 옵션으로 빌드된 바이너리에서 함수 하나가 유난히 길고 복잡한데 `CALL`이 거의 안 보일 때
- 소스코드(또는 심볼/디버그 정보)에는 분명 여러 헬퍼 함수가 있었는데 바이너리에는 그 함수 이름/경계가 안 보일 때
- `strlen`, `memcpy` 같은 잘 알려진 라이브러리 함수를 호출하는 코드일 텐데 Imports 목록에도, `CALL`로도 안 보일 때
- CTF 문제에서 "이 함수는 분명 검증 로직을 어딘가 호출할 텐데 CALL이 하나도 없다"고 헷갈릴 때

## 핵심 개념

### 인라이닝이란
함수 인라이닝(inlining)은 컴파일러가 **함수 호출 대신 그 함수의 본문 코드를 호출 지점에 그대로 복사해 넣는** 최적화다.
```c
static inline int square(int x) { return x * x; }

int compute(int a) {
    return square(a) + 1;
}
```
`-O2` 이상에서 컴파일하면 `square`를 부르는 `CALL` 명령이 아예 생성되지 않고, `compute`의 어셈블리 안에 `square`의 곱셈 로직이 그대로 펼쳐져 들어간다:
```asm
compute:
    imul    eax, edi, edi   ; square(a)가 통째로 인라인됨 - CALL 없음
    add     eax, 1
    ret
```

### 왜 컴파일러가 인라이닝을 하는가
- `CALL`/`RET` 자체의 오버헤드(스택 조작, 분기 예측 실패 가능성)를 없앨 수 있다.
- 함수 본문이 호출부에 펼쳐지면, 컴파일러가 호출자와 피호출자의 코드를 **함께 보고 추가 최적화**(상수 전파, 불필요한 코드 제거 등)를 할 기회가 생긴다.
- 특히 함수가 짧고(한두 줄), 자주 호출되면(루프 안 등) 인라이닝 이득이 크다.

### 인라이닝이 잘 일어나는 대표 사례
- `static`/`inline`/C++ 클래스 멤버 함수처럼 컴파일러가 함수 정의를 호출 지점과 같은 번역 단위(translation unit)에서 볼 수 있는 경우.
- 표준 라이브러리 함수 중 컴파일러가 "내장 지식"으로 알고 있는 것들 — `strlen`, `memcpy`, `memset`, `memcmp` 등은 GCC/Clang/MSVC가 아예 컴파일러 내장 함수(intrinsic/builtin)로 취급해서, 라이브러리 `CALL` 대신 인라인된 루프나 SIMD 코드(REV-0487, REV-0447~0449 참고)로 직접 바꿔치기하는 경우가 매우 흔하다.
- 게터/세터(getter/setter), 단순 래퍼(wrapper) 함수, 짧은 산술/비교 함수.
- C++의 연산자 오버로딩, 템플릿 함수, 람다 — 특히 STL 컨테이너(`std::vector`, `std::string`) 관련 코드는 인라이닝이 매우 공격적으로 적용되어 원래 함수 이름이 바이너리에 전혀 안 남는 경우가 많다.

### 인라이닝이 안 되는 경우
- 함수가 너무 크거나 복잡한 경우(컴파일러의 인라이닝 비용 임계값 초과).
- 함수가 재귀 호출을 하는 경우(무한정 펼칠 수 없으므로 보통 인라이닝 안 됨, 다만 재귀 깊이가 정적으로 정해진 특수한 경우는 예외).
- 함수 포인터로 간접 호출되는 경우(컴파일 시점에 어떤 함수가 불릴지 확정할 수 없으므로 인라이닝 불가능).
- 다른 번역 단위(다른 `.c`/`.cpp` 파일)에 정의되어 있고 LTO(Link-Time Optimization)가 꺼져 있는 경우 — 이런 함수는 컴파일 시점에 본문을 볼 수 없어 인라이닝이 불가능하고, 링크 시점에도 최적화가 없으면 그대로 `CALL`로 남는다.
- 함수 주소 자체가 필요한 경우(콜백 등록, `&func` 사용) — 함수의 실제 코드가 어딘가에는 남아있어야 하므로 완전히 사라지지 않는다.

### 디버그 빌드(-O0)와의 대조
`-O0`(최적화 없음)로 빌드된 바이너리는 인라이닝을 거의 하지 않으므로, 소스코드의 함수 구조가 어셈블리에도 거의 그대로 대응된다(함수마다 `CALL` 하나씩). 반대로 최적화가 강하게 걸린 릴리즈 빌드는 인라이닝, 함수 복제(REV-0466), 루프 언롤링(REV-0443) 등이 겹쳐서 원래 소스 구조를 거의 알아볼 수 없을 정도로 재구성되기도 한다. **`-O0`과 `-O2`를 나란히 비교하는 습관**(REV-0464 참고)이 이런 재구성 패턴에 익숙해지는 가장 좋은 방법이다.

### IDA/Ghidra에서 보이는 방식
- 인라인된 코드는 별도 함수로 분리되지 않고 호출자 함수의 일부로 그대로 디컴파일된다. 함수 하나의 디컴파일 결과가 유난히 길고, 여러 단계의 로직(예: 입력 검증 + 변환 + 비교)이 한 함수 안에 다 들어있다면 인라이닝을 의심한다.
- 디버그 심볼(PDB, DWARF)이 남아있는 바이너리라면 IDA/Ghidra가 라인 정보나 인라인 함수 이름을 주석으로 남겨주는 경우가 있다(컴파일러가 디버그 정보에 "이 코드는 원래 어느 함수의 몇 번째 줄이었다"는 정보를 심어둔 경우). 스트립된(strip) 릴리즈 바이너리는 이런 힌트가 전혀 없다.
- Ghidra는 함수 경계를 자동 인식하려 시도하지만, 인라인된 코드는 애초에 별도 함수 심볼이 없으므로 자동으로 다시 "이건 원래 함수였다"고 되살려주지는 못한다 — 이건 순수하게 사람이 코드 흐름을 읽고 논리적으로 재구성해야 하는 부분이다.

## 화면/코드에서 보이는 징후
```asm
; 소스: check_input() 함수가 validate_length(), validate_chars(), compute_hash() 세 함수를 호출
; 하지만 어셈블리에는 CALL이 하나도 없고 전부 한 함수 안에 펼쳐져 있음
check_input:
    ; validate_length()가 인라인됨
    mov     eax, [rdi+len_offset]
    cmp     eax, 20
    jne     fail
    ; validate_chars()가 인라인됨 (반복문으로 펼쳐짐)
    xor     ecx, ecx
loop_chars:
    movzx   edx, byte ptr [rdi+rcx]
    ; ... 문자 검증 로직 ...
    inc     ecx
    cmp     ecx, eax
    jl      loop_chars
    ; compute_hash()가 인라인됨
    ; ... 해시 계산 로직 ...
    ret
fail:
    xor     eax, eax
    ret
```

## 가장 먼저 할 것
`CALL`이 없는 긴 함수를 만나면, 그 함수를 "하나의 거대한 로직"으로 보지 말고 **논리적 블록 단위로 나눠서** 각 블록이 원래 어떤 역할(검증, 변환, 계산 등)을 했을지 추정한다. 블록 경계는 보통 조건 분기(`Jcc`)나 루프 시작/끝, 또는 완전히 다른 레지스터 집합을 쓰기 시작하는 지점에서 나뉜다.

## 단계별 절차
**1) 함수를 논리 블록으로 나누기**

IDA 그래프뷰(Space bar로 전환)로 보면 조건 분기에 따라 자연스럽게 블록이 나뉘어 보인다. 각 블록에 사람이 이해하기 쉬운 이름을 주석으로 달아둔다("여기까지 길이 검증", "여기부터 해시 계산" 등).

**2) 알려진 라이브러리 함수 패턴 인식**

`rep movsb`/`rep stosb`(REV-0080), SIMD 로드/저장 블록(REV-0487), `repne scasb`(길이 재기) 같은 패턴이 보이면 각각 `memcpy`/`memset`/`strlen`이 인라인된 것으로 즉시 인식하고 넘어간다.

**3) 상수/매직 넘버로 알고리즘 추정**

인라인된 해시/암호화 함수는 원래 이름이 사라졌어도 특징적인 상수(예: `0x9E3779B9`는 골든 비율 기반 해시, `0x811C9DC5`는 FNV 해시의 초기값)가 남아있는 경우가 많다. 이런 상수로 원래 알고리즘을 검색해서 역추적할 수 있다.

**4) 디버그 심볼이 있는지 확인**

PDB(Windows)나 스트립되지 않은 DWARF(Linux) 심볼이 있다면 IDA/Ghidra가 원래 함수 경계나 인라인 정보를 일부 복원해줄 수 있다. `file <바이너리>`(Linux) 또는 PDB 유무 확인으로 디버그 정보 존재 여부를 먼저 점검한다.

**5) -O0으로 재컴파일해서 비교 (소스가 있는 경우)**

만약 소스코드나 유사한 코드를 갖고 있다면, `-O0`으로 별도 컴파일해서 함수별로 분리된 어셈블리와 비교하면 어떤 부분이 어떤 원래 함수였는지 훨씬 쉽게 대응시킬 수 있다(REV-0464 참고).

## 명령어/단축키
- IDA: `Space`(그래프뷰/텍스트뷰 전환), `F5`(디컴파일 — 인라인된 로직도 하나의 큰 함수로 보여줌), 블록에 `;` 주석 달기
- Ghidra: `Function Graph` 뷰, 코드 영역 우클릭 → "Comment" 로 블록별 설명 추가
- 상수 검색: IDA `Alt+B`(바이너리 패턴 검색) 또는 Shift+F4(16진수 뷰에서 검색)로 특정 매직 넘버가 다른 곳에도 나오는지 확인
- `file <binary>`, `objdump --syms <binary>` (Linux): 심볼/디버그 정보 존재 여부 확인

## 출력 해석
- 함수가 매우 길고 `CALL`이 거의 없는데 여러 단계의 `Jcc` 분기와 반복 패턴이 섞여 있으면 → 여러 함수가 인라인되어 하나로 합쳐진 전형적인 모습이다.
- 반복 로직 안에 익숙한 상수(해시 초기값, 다항식 계수 등)가 보이면 → 그 알고리즘 자체를 검색해서 원래 함수 이름/용도를 추정할 수 있다.
- 함수 시작 부분과 끝부분에서 레지스터 용도가 완전히 바뀌면(다른 목적의 계산으로 전환) → 그 지점이 원래는 별개 함수였을 경계일 가능성이 크다.

## 흔한 실수
- `CALL`이 없다고 "이 함수는 아무것도 검증/계산하지 않는다"고 오해하는 것 — 오히려 그 반대로, 많은 로직이 그 함수 안에 압축되어 들어있을 가능성이 높다.
- 익숙한 라이브러리 함수(`strlen`, `memcpy` 등)가 안 보인다고 "이 프로그램은 표준 라이브러리를 안 쓴다"고 결론짓는 것 — 대부분 인라인되어 이름만 사라진 것이지 실제로는 그 로직이 그대로 실행된다.
- 인라인된 코드를 원래 함수 단위로 억지로 다시 쪼개려고 시간을 낭비하는 것 — 대부분의 리버싱 목적(취약점 찾기, 알고리즘 이해)에는 "이 블록이 논리적으로 무엇을 하는가"만 파악하면 충분하고, 원래 함수 경계를 정확히 복원할 필요는 거의 없다.
- 디버그 빌드(-O0)와 릴리즈 빌드(-O2/-O3)의 차이를 모른 채, 릴리즈 바이너리에서 소스코드와 1:1 대응을 기대하는 것.

## 막혔을 때 다음 체크
- 알고리즘이 뭔지 전혀 감이 안 잡히면 → 인라인된 블록에 나오는 상수를 검색 엔진이나 상수 데이터베이스에서 찾아본다(흔한 해시/암호 알고리즘의 매직 넘버일 수 있음).
- SIMD/REP 패턴이 섞여 있어서 더 헷갈리면 → REV-0487(SIMD), REV-0080(REP Prefix) 먼저 정리하고 돌아온다.
- 최적화로 인한 다른 재구성 패턴(함수 복제, 루프 언롤링 등)까지 겹쳐서 복잡하면 → REV-0443(루프 언롤링), REV-0466(함수 복제) 참고.
- 여전히 함수 경계 추정이 필요하면 → 디버그 심볼(PDB/DWARF)이 있는 버전이 따로 있는지, 또는 소스코드를 직접 비교 컴파일할 수 있는지 확인.

## 미니 예제

**예제 1 — 짧은 헬퍼 함수의 인라이닝**
```c
static inline int is_valid_char(char c) {
    return (c >= 'a' && c <= 'z');
}

int check(const char *s) {
    for (int i = 0; s[i]; i++) {
        if (!is_valid_char(s[i])) return 0;
    }
    return 1;
}
```
```asm
check:
    xor     eax, eax
loop_check:
    movzx   ecx, byte ptr [rdi+rax]
    test    cl, cl
    jz      valid
    cmp     cl, 'a'          ; is_valid_char()가 통째로 인라인됨 - CALL 없음
    jl      invalid
    cmp     cl, 'z'
    jg      invalid
    inc     rax
    jmp     loop_check
valid:
    mov     eax, 1
    ret
invalid:
    xor     eax, eax
    ret
```

**예제 2 — strlen이 인라인된 경우 (REP 계열로)**
```c
int len = strlen(buf);
```
```asm
lea     rdi, [buf]
xor     al, al
mov     rcx, -1
repne   scasb            ; strlen이 통째로 인라인됨 - call strlen 없음
not     rcx
dec     rcx
mov     len, ecx           ; RCX가 곧 문자열 길이
```

**예제 3 — 매직 넘버로 인라인된 해시 함수 추정**
```asm
; 함수 이름 없이 반복문 안에 이 상수가 보임
imul    eax, eax, 0x1000193   ; FNV prime (0x01000193) -> FNV-1a 해시 함수가 인라인된 것으로 추정 가능
xor     eax, ecx
```

**예제 4 — 인라인 안 되는 경우 (함수 포인터 간접 호출)**
```c
int (*validator)(char*) = pick_validator();
if (validator(input)) { ... }
```
```asm
call    pick_validator      ; 이건 인라인 안 됨 (반환값이 함수 포인터이므로 대상이 불확정)
mov     rbx, rax
lea     rdi, [input]
call    rbx                  ; 간접 호출도 컴파일 시점에 대상을 모르므로 인라인 불가능
```
이처럼 함수 포인터를 통한 간접 호출은 인라이닝의 예외이며, 여전히 `CALL`이 정상적으로 남는다.

## 출처/검증
- 함수 인라이닝의 원리와 컴파일러 판단 기준(비용 임계값, static/inline 힌트 등): GCC 공식 문서("Inline" 및 `-finline-functions` 옵션), Clang/LLVM 공식 문서(Inlining) 기준 (2026-09-08 검증).
- `strlen`/`memcpy`/`memset` 등이 컴파일러 내장 함수(builtin)로 처리되어 인라인/벡터화되는 관행: GCC 공식 문서("Other Builtins") 및 MSVC 문서(Intrinsics) 기준.
- LTO(Link-Time Optimization)와 번역 단위 간 인라이닝 제약: GCC 공식 문서("Link Time Optimization") 기준.
