## 한 줄 요약
`xor eax, eax`처럼 **같은 레지스터를 자기 자신과 XOR하는 것**은 항상 결과가 0이 되는 것을 이용한 "레지스터를 0으로 만드는" 관용구(idiom)일 뿐 어떤 암호화나 데이터 변환도 아니며, 오퍼랜드가 서로 다른 `xor eax, ecx` 같은 형태와는 완전히 다른 의미로 읽어야 한다.

## 언제 검색해야 하나
- `xor eax, eax`, `xor ecx, ecx`처럼 같은 레지스터가 두 번 나오는 코드를 보고 "이게 뭘 암호화/변환하는 거지?"라고 헷갈릴 때
- flag 복호화 루프를 분석하다가 `xor` 명령어를 만났는데 이게 진짜 키 XOR인지 단순 초기화인지 구분이 안 될 때
- `mov eax, 0`과 `xor eax, eax`가 왜 결과가 같은데 다른 인코딩으로 쓰이는지 궁금할 때
- 디스어셈블리에서 `xor`가 나올 때마다 무조건 "역산해야 할 암호화 단계"라고 오해하고 있을 때

## 핵심 개념

### XOR의 기본 동작 복습
`XOR dest, src`는 두 오퍼랜드를 비트 단위로 배타적 논리합(exclusive OR) 연산한 뒤 `dest`에 저장한다. 진리표는 다음과 같다.
```
0 XOR 0 = 0
0 XOR 1 = 1
1 XOR 0 = 1
1 XOR 1 = 0
```
어떤 값이든 **자기 자신과 XOR하면 모든 비트가 1 XOR 1 = 0 또는 0 XOR 0 = 0이 되어 결과는 항상 0**이다. 이건 그 레지스터에 실제로 어떤 값이 들어있었는지와 무관하게 항상 성립하는 수학적 성질이다.

### `xor eax, eax` = "eax를 0으로 만들어라"라는 뜻일 뿐
컴파일러는 레지스터를 0으로 초기화하고 싶을 때 두 가지 방법 중 하나를 선택할 수 있다.
```asm
mov  eax, 0     ; B8 00 00 00 00  -> 5바이트
xor  eax, eax   ; 31 C0           -> 2바이트
```
결과는 완전히 동일하게 `EAX = 0`이지만, `xor eax, eax`가 인코딩이 훨씬 짧고(2바이트 vs 5바이트), 최신 CPU에서는 이 패턴을 "제로화 관용구(zero idiom)"로 특별 인식해서 실행 유닛에 값이 전달되기를 기다릴 필요 없이(이전 값에 대한 의존성을 끊어서, false dependency 제거) 매우 빠르게 처리한다. 그래서 컴파일러는 거의 항상 `mov reg, 0` 대신 `xor reg, reg`를 선택한다 — 이것은 최적화의 결과물이지 어떤 비밀스러운 계산이 아니다.

### 진짜 XOR 기반 변환과 구분하는 법
CTF에서 문자열을 XOR로 인코딩/디코딩하는 진짜 로직은 **서로 다른 두 값**을 XOR한다.
```asm
xor  al, cl      ; AL과 CL이 다른 레지스터 -> 진짜 데이터 변환 (키로 XOR)
xor  byte ptr [rdi], 0x5A   ; 메모리 값과 상수 XOR -> 진짜 인코딩/디코딩
```
반면 `xor eax, eax`, `xor ecx, ecx`처럼 **오퍼랜드 두 개가 완전히 같은 레지스터**인 경우는 100% 제로화 관용구다. 구분 기준은 단 하나 — **두 오�레퍼랜드가 같은 레지스터인가, 다른가**이다.

### 플래그에 미치는 영향
`XOR`은 항상 다음 플래그를 결과에 맞춰 세팅한다(REV-0057 참고).
```
ZF = 1 (결과가 0이므로 항상 참)
SF = 0 (결과가 0이므로 음수 아님)
PF = 1 (0의 바이트 패리티는 짝수이므로 참)
CF = 0 (XOR은 항상 캐리를 0으로 클리어)
OF = 0 (XOR은 항상 오버플로우를 0으로 클리어)
```
그래서 `xor eax, eax` 직후에 `ZF`가 항상 1이 된다는 점을 이용해, 컴파일러가 이 명령어를 "0으로 초기화 + 제로 플래그 세팅"을 한 번에 하는 용도로도 종종 활용한다(바로 뒤에 `jz`가 이어지는 경우는 드물지만, `test`/`cmp` 없이 흐름을 이어가는 최적화에서 나타날 수 있다).

### 왜 XOR을 골랐는가 (다른 제로화 방법과 비교)
```asm
sub  eax, eax   ; 이것도 항상 0이 되지만 XOR보다 덜 쓰임
and  eax, 0     ; 이것도 항상 0이지만 즉치값이 필요해 인코딩이 더 김
xor  eax, eax   ; 가장 짧고, 대부분의 CPU에서 zero idiom으로 인식되어 가장 빠름
```
`XOR`이 사실상 업계 표준 관용구로 자리잡은 이유는 인코딩 크기와 실행 속도(디펜던시 제거) 양쪽에서 가장 유리하기 때문이다.

## 화면/코드에서 보이는 징후
- `xor eax, eax` 직후 `ret`이나 `mov [rbp-4], eax` — 함수의 반환값을 0으로 만들거나 지역 변수를 0으로 초기화하는 전형적인 패턴
- 함수 시작 부분(프롤로그 직후)에서 여러 개의 `xor reg, reg`가 연달아 나옴 — 여러 지역 변수/누산기를 한 번에 0으로 초기화
- 루프 시작 전 `xor ecx, ecx` — 카운터를 0부터 시작
- **혼동하지 말 것**: `xor al, [rdi+rcx]` 처럼 오퍼랜드가 다른 형태가 반복 루프 안에 있다면 이건 진짜 XOR 인코딩/디코딩 로직이다.

## 가장 먼저 할 것
1. `xor`의 두 오퍼랜드가 정확히 같은 레지스터인지부터 확인한다.
2. 같다면 그냥 "이 레지스터를 0으로 만든다"로 즉시 해석하고 넘어간다 — 더 깊이 분석할 필요가 없다.
3. 다르다면(레지스터-레지스터가 다르거나, 레지스터-메모리, 레지스터-상수) 진짜 데이터 변환일 가능성이 높으므로 REV-0057이나 관련 알고리즘 문서로 넘어가서 분석한다.

## 단계별 절차
**1) 오퍼랜드 동일성 확인**

`xor eax, eax`처럼 좌우가 같은 이름의 레지스터인지 눈으로 바로 확인한다. 다른 크기 표기(`xor eax, eax`는 되지만 `xor al, ah`처럼 다른 서브 레지스터인 경우는 진짜 값이 섞이므로 별개)까지 정확히 봐야 한다.

**2) 반복문 안인지 확인**

`xor` 명령어가 루프 안에서 인덱스가 바뀌는 메모리/레지스터를 대상으로 반복 실행된다면 이는 데이터 변환(암호화/디코딩) 루프일 가능성이 매우 높다. 함수 초입 한 번만 실행되는 `xor reg, reg`와는 문맥이 다르다.

**3) 디컴파일 결과와 대조**

IDA F5 결과에서 `xor eax, eax`는 보통 `v1 = 0;` 또는 `return 0;`처럼 아주 단순하게 표시된다. 만약 디컴파일 결과가 복잡한 계산식으로 나온다면 진짜 오퍼랜드를 다시 확인해야 한다.

## 명령어/단축키
- IDA: F5(디컴파일)로 `xor eax, eax`가 `v1 = 0`처럼 단순화되는지 확인
- x64dbg/GDB: 해당 명령어 실행 전후 레지스터 값을 비교(`p $eax` 전후)해서 실제로 0이 되는지, 그리고 그 전 값이 무엇이었는지(제로화이므로 사실 무의미) 확인
- objdump: `objdump -d` 결과에서 `31 c0`(2바이트) 인코딩이면 100% `xor eax, eax`류의 짧은 형태임을 바로 알 수 있음

## 출력 해석
- 실행 전 EAX 값이 무엇이었든 실행 후 항상 0이면 제로화 관용구가 맞다.
- ZF가 항상 1로 세팅되는 것도 정상이며, 별도의 "비교 성공/실패" 의미는 없다.
- 루프 안에서 매 반복마다 다른 결과가 나온다면(같은 레지스터 XOR인데도 값이 매번 다르다면) 그건 애초에 오퍼랜드를 잘못 읽은 것이니 다시 확인한다.

## 흔한 실수
- `xor`라는 이름만 보고 무조건 "이건 암호화/난독화 단계"라고 판단해서 불필요하게 역산을 시도하는 것 — 오퍼랜드가 같은 레지스터면 그냥 0을 만드는 것뿐이다.
- `xor eax, eax`를 `mov eax, 0`과 "기능은 같지만 다른 명령어"로 보고 굳이 둘의 차이를 분석하려 드는 것 — 결과·목적 모두 완전히 동일하며 인코딩 크기/속도 차이만 있을 뿐이다.
- 진짜 데이터 변환 XOR 루프(`xor al, [rdi+rcx]`, 키가 반복 적용되는 형태)를 발견했는데, 이걸 "그냥 초기화겠지"라고 대충 넘기는 것 — 오퍼랜드가 서로 다르면 반드시 값의 출처를 추적해야 한다.
- `xor eax, eax` 실행 후 플래그(ZF=1)를 보고 "방금 뭔가 비교가 성공했다"고 오해하는 것 — 이건 비교 결과가 아니라 XOR 연산 자체의 부수 효과일 뿐이다.

## 막혔을 때 다음 체크
- XOR 명령어 자체의 전체 문법/플래그를 다시 보고 싶으면 → REV-0057(XOR: XOR 연산과 XOR reg reg 제로화)
- 진짜 XOR 기반 flag 인코딩/디코딩을 역산하는 절차가 필요하면 → REV-0199(XOR 반복 변환 역산)를 참고
- 플래그가 왜 이렇게 세팅되는지 다시 확인하려면 → REV-0088(플래그 레지스터와 CF ZF SF OF PF를 Jcc와 연결해서 읽기)

## 미니 예제
**예제 1 — 반환값 0 초기화 (제로화 관용구)**
```c
// 원본 C
int get_zero(void) {
    return 0;
}
```
```asm
xor   eax, eax    ; EAX(반환값) = 0
ret
```

**예제 2 — 루프 카운터 초기화 (제로화 관용구)**
```asm
xor   ecx, ecx        ; i = 0
loop_start:
    cmp   ecx, 10
    jge   loop_end
    ; ... 루프 본문 ...
    inc   ecx
    jmp   loop_start
loop_end:
```

**예제 3 — 진짜 XOR 인코딩 루프 (혼동하면 안 되는 경우)**
```asm
xor   ecx, ecx           ; i = 0  (이건 제로화, 루프 카운터)
decode_loop:
    mov   al, [rsi+rcx]
    xor   al, 0x37        ; <- 이건 진짜 데이터 변환! 오퍼랜드가 다름(al과 상수 0x37)
    mov   [rdi+rcx], al
    inc   ecx
    cmp   ecx, r8d
    jl    decode_loop
```
같은 함수 안에 제로화 XOR(`xor ecx, ecx`)과 진짜 변환 XOR(`xor al, 0x37`)이 함께 있을 수 있다 — 오퍼랜드를 하나씩 확인해서 구분해야 한다.
