## 한 줄 요약
`LEA`(Load Effective Address)는 오퍼랜드에 `[...]` 형태의 대괄호가 있어도 **실제로 메모리를 읽지 않고, 그 안의 주소 계산식(더하기·상수배)만 계산해서 레지스터에 저장**하는 명령어이며, 이 성질을 이용해 컴파일러가 `LEA`를 순수한 정수 곱셈/덧셈 계산기로 즐겨 쓰기 때문에 "메모리를 다루는 명령어"라는 선입견으로 읽으면 잘못 해석하게 된다.

## 언제 검색해야 하나
- `lea eax, [eax+eax*2]` 같은 코드를 보고 "이게 메모리에서 뭔가를 읽어오는 거 아닌가?"라고 헷갈릴 때
- 어떤 함수에서 곱셈(`imul`)이 하나도 안 보이는데 결과가 곱셈처럼 동작하는 걸 발견했을 때
- `LEA` 다음에 플래그를 검사하는 `Jcc`가 이어지길 기대했는데 플래그가 전혀 안 바뀐 걸 확인했을 때
- 구조체 필드 접근(`lea rax, [rbx+rcx*8+0x10]`)과 순수 산술 계산용 `LEA`를 구분하고 싶을 때

## 핵심 개념

### LEA가 실제로 하는 일: 주소 "계산"이지 "접근"이 아니다
다른 대부분의 `[...]` 오퍼랜드를 쓰는 명령어(`MOV`, `ADD`, `CMP` 등)는 그 대괄호 안의 주소가 가리키는 **메모리 값을 실제로 읽거나 쓴다**. 하지만 `LEA`는 다르다. `LEA dest, [expr]`는 대괄호 안의 `expr`(베이스 레지스터 + 인덱스 레지스터 × 배율 + 변위)을 **주소 계산 유닛(AGU)으로 계산만 하고, 그 계산 결과값 자체를 dest에 저장**한다. 메모리 버스에 접근하는 로드(load) 동작이 아예 일어나지 않는다.

```asm
mov  eax, [rbx+8]    ; RBX+8 주소에서 메모리를 실제로 읽어서 EAX에 저장
lea  eax, [rbx+8]    ; RBX+8이라는 "숫자"를 계산해서 EAX에 저장 (메모리 접근 없음)
```

### 이 성질을 이용한 곱셈/덧셈 트릭
x86의 주소 계산식은 `베이스 + 인덱스*배율(1,2,4,8) + 변위`형태를 하드웨어가 한 사이클에 계산해준다. 컴파일러는 이걸 이용해서 **곱셈·덧셈 조합을 `IMUL`이나 `ADD` 여러 개 대신 `LEA` 한 줄로 압축**한다.

```asm
lea  eax, [rax+rax*2]   ; EAX = RAX + RAX*2 = RAX*3
lea  eax, [rax*4]        ; EAX = RAX*4
lea  eax, [rax+rax*4]    ; EAX = RAX*5
lea  eax, [rax*8+rax]    ; EAX = RAX*9
lea  eax, [rbx+rcx+4]    ; EAX = RBX + RCX + 4  (두 레지스터를 더하고 상수까지 더함)
```
이 배율은 인덱스 레지스터에만 적용 가능하고 1, 2, 4, 8만 지원되므로, 3, 5, 9배는 "자기 자신 + 자기 자신*배율" 형태로 표현하는 게 이 트릭의 핵심이다. `RAX*3`을 직접 표현하는 배율은 없지만 `RAX + RAX*2`로 우회하는 식이다.

### 플래그가 전혀 바뀌지 않는다
`ADD`, `IMUL` 등 진짜 산술 명령어는 플래그(CF, ZF, SF, OF 등)를 세팅하지만, **`LEA`는 산술처럼 보여도 플래그를 전혀 건드리지 않는다.** 이는 매우 중요한 구분점이다 — `LEA` 바로 다음에 오는 `Jcc`는 절대로 그 `LEA`의 결과를 보고 분기하는 게 아니다(플래그가 안 바뀌었으므로 더 이전의 `CMP`/`TEST` 결과를 그대로 참조하는 것). 초보자가 흔히 "LEA 다음에 조건 분기가 왜 이렇게 오지?"라고 헷갈리는 이유가 이것이다.

### 진짜 메모리 접근용 LEA와 산술용 LEA 구분
`LEA`는 원래 목적대로 **진짜 포인터/주소를 만드는 데에도** 똑같이 쓰인다.
```asm
lea  rax, [rbp-0x20]     ; 스택의 지역 변수 버퍼 주소를 구함 (포인터로 쓸 목적)
lea  rdi, [rbx+rcx*8]    ; 배열 rbx의 rcx번째 8바이트 원소 주소 (배열 인덱싱)
```
이런 경우는 다음 줄에서 그 결과가 `mov`나 함수 인자(REV-0071)로 쓰이며 "주소"로 취급된다. 반면 산술 트릭용 `LEA`는 그 결과가 바로 산술 계산에 이어지거나(`imul`, `add` 등 없이 곧장 다른 값과 연산) 정수 변수에 저장된다. **결과가 이후 코드에서 포인터로 역참조되는지(`[reg]` 형태로 다시 쓰이는지) 아니면 순수 숫자로 쓰이는지**를 보면 구분할 수 있다.

## 화면/코드에서 보이는 징후
- `lea eax, [eax+eax*2]`, `lea eax, [eax*4+eax]` 처럼 같은 레지스터가 베이스와 인덱스에 동시에 등장 — 곱셈 트릭일 확률이 매우 높음
- `lea` 결과가 바로 뒤에서 `[결과레지스터]` 형태로 다시 참조됨 — 진짜 주소(포인터)로 쓰이는 경우
- `lea` 다음에 플래그를 검사하지 않는 코드가 이어짐 — LEA는 플래그를 안 바꾸므로 당연한 것
- 함수 프롤로그 직후 `lea rax, [rbp-0x30]` — 지역 변수 버퍼의 시작 주소를 구하는 전형적 패턴

## 가장 먼저 할 것
1. `LEA` 대괄호 안의 표현식을 그대로 수식으로 옮겨 적어본다(`[rax+rax*2]` → `rax + rax*2`).
2. 그 결과가 이후 코드에서 `[결과]`처럼 다시 역참조되는지, 아니면 순수 숫자로 쓰이는지 확인한다.
3. 값으로 쓰인다면 배율(1,2,4,8)을 실제 정수로 환산해서 몇 곱하기 몇인지 계산해본다.

## 단계별 절차
**1) 대괄호 안 표현식을 산술식으로 변환**

`[base + index*scale + disp]` 형태를 그대로 `base + index*scale + disp`라는 정수 수식으로 옮긴다.

**2) base와 index가 같은 레지스터인지 확인**

같다면(`[rax+rax*2]`처럼) 이는 `rax * (1+2) = rax * 3` 형태의 곱셈 트릭이다. 서로 다른 레지스터면 두 값을 더하는 덧셈이거나 배열 인덱싱(진짜 주소 계산)이다.

**3) 결과 레지스터의 다음 쓰임새 추적**

결과가 담긴 레지스터가 이후 `mov [result], ...`나 `[result]` 형태로 역참조되면 주소(포인터)다. `add`, `cmp`, `imul` 등 순수 연산에 바로 쓰이거나 지역 변수에 정수로 저장되면 산술 계산이다.

**4) IDA 디컴파일과 대조**

IDA F5는 곱셈 트릭용 LEA를 대개 `v1 = v2 * 3;` 처럼 깔끔한 곱셈식으로 자동 복원해준다. 반대로 주소 계산용 LEA는 `&buffer[i]`나 포인터 연산 형태로 나타난다.

## 명령어/단축키
- IDA: F5 디컴파일 결과에서 LEA가 곱셈/덧셈 수식으로 정리되는지, 포인터 연산으로 정리되는지 확인
- x64dbg/GDB: `LEA` 실행 전후 플래그 레지스터 값을 비교해서 정말 안 바뀌는지 직접 확인(`p $eflags` 전후 비교)
- 계산기: 손으로 곱셈 트릭을 검증할 때는 파이썬으로 `base*(1+scale)` 형태를 바로 계산해보는 것이 빠르다.

## 출력 해석
- `LEA` 실행 전후 EFLAGS 값이 완전히 동일하면 정상이다(어떤 산술 명령어처럼 보여도 플래그 불변).
- 계산한 배수(3, 5, 9배 등)가 코드 전체 문맥(예: 구조체 크기, 배열 원소 크기)과 맞아떨어지면 그게 곱셈 트릭이 맞다는 강력한 근거다.
- 결과 레지스터를 역참조하는 코드가 뒤따르면 그건 산술이 아니라 주소 계산이었다는 뜻이니 앞선 판단을 정정한다.

## 흔한 실수
- 대괄호 `[...]`가 보이면 무조건 "메모리를 읽는다"고 반사적으로 판단하는 것 — LEA는 예외다.
- `LEA` 다음에 오는 `Jcc`가 그 LEA의 결과를 보고 분기한다고 착각하는 것 — LEA는 플래그를 바꾸지 않으므로 그 앞의 `CMP`/`TEST` 결과를 계속 참조하는 것이다.
- `lea eax, [eax+eax*2]`를 보고 실제로 무슨 곱셈인지 계산해보지 않고 그냥 "복잡한 주소 계산이겠거니" 하고 넘어가는 것 — 구조체 크기(예: 12바이트 원소 크기 = ×3)를 알아내는 중요한 단서를 놓치게 된다.
- LEA로 계산된 값이 항상 "포인터"라고 단정하는 것 — 정수 산술 결과일 수도 있다는 걸 항상 열어두고 다음 코드를 봐야 한다.

## 막혔을 때 다음 체크
- LEA의 기본 문법/오퍼랜드 형식을 더 자세히 보고 싶으면 → REV-0042(LEA: 주소 계산인데 왜 산술 연산처럼 보이는가)
- RIP 상대 주소를 계산하는 LEA(`lea rax, [rip+disp]`)가 헷갈리면 → REV-0479(상대 주소(RIP-relative)가 계산이 안 맞을 때)
- 곱셈이 시프트/덧셈으로 최적화되는 다른 패턴이 궁금하면 → REV-0454(나눗셈이 곱셈과 시프트로 최적화되는 패턴)를 참고
- 구조체 필드/배열 인덱싱 주소 계산 패턴을 더 보고 싶으면 → REV-0456(배열 경계 체크가 어셈블리에 나타나는 패턴)

## 미니 예제
**예제 1 — 3배 곱셈 트릭**
```c
int x3 = x * 3;
```
```asm
lea   eax, [rax+rax*2]   ; eax = rax + rax*2 = rax*3
```

**예제 2 — 구조체 배열 인덱싱 (진짜 주소 계산)**
```c
struct Item items[10];   // sizeof(Item) == 12
Item *p = &items[i];
```
```asm
lea   eax, [rax+rax*2]     ; i*3  (i를 3배로 만드는 중간 계산, sizeof=12=4*3이라 4바이트 단위로 3배)
lea   rax, [rbx+rax*4]     ; items 배열 시작(rbx) + i*12 바이트 위치 -> 진짜 포인터
mov   [rbp-8], rax          ; p = &items[i]
```

**예제 3 — 스택 지역 변수 버퍼 주소 (진짜 포인터, 산술 아님)**
```asm
lea   rdi, [rbp-0x40]     ; 지역 배열 버퍼의 시작 주소를 구함
call  memset               ; memset(buf, ...) 처럼 포인터로 바로 사용됨
```
이 경우는 곱셈 트릭이 아니라 순수하게 "이 지역 변수의 주소가 필요해서" 쓰인 LEA다.

## 관련 글
- REV-0042 — LEA: 주소 계산인데 왜 산술 연산처럼 보이는가
- REV-0479 — 상대 주소(RIP-relative)가 계산이 안 맞을 때
- REV-0047 — ADD: 덧셈과 플래그
- REV-0480 — 같은 니모닉인데 오퍼랜드 크기가 헷갈릴 때

## 출처/검증
- LEA가 메모리 접근 없이 유효 주소만 계산하고 플래그를 변경하지 않는다는 점: Intel 64 and IA-32 Architectures Software Developer's Manual, Volume 2A, "LEA—Load Effective Address" 섹션 기준.
- SIB(Scale-Index-Base) 인코딩의 배율(1,2,4,8) 제한: 동일 매뉴얼 Volume 2A, "2.1.5 Addressing-Mode Encoding of ModRM and SIB Bytes" 기준.
- 컴파일러가 곱셈을 LEA로 강도 감소(strength reduction)하는 관행: GCC/LLVM 최적화 관련 일반 문서 기준(2026-09-08 확인).
