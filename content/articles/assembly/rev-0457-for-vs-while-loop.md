## 한 줄 요약
같은 몸체를 가진 `for`문과 `while`문은 컴파일 후 사실상 동일한 어셈블리로 컴파일되므로, 최적화된 바이너리에서 "이게 for인지 while인지"를 어셈블리만 보고 확정하는 것은 대부분 불가능하며 애초에 그럴 필요도 없다 — 대신 초기화/조건/증가/몸체 네 요소를 각각 찾아내는 데 집중해야 한다.

## 언제 검색해야 하나
- 디스어셈블리나 IDA 그래프 뷰에서 반복 구조(백엣지, back edge)를 발견했는데 이게 소스에서 `for`였는지 `while`이었는지 궁금할 때
- 루프 진입부에 `jmp`로 조건 체크 블록으로 먼저 건너뛰는 코드가 있어서 왜 곧바로 몸체로 안 들어가는지 헷갈릴 때
- 디컴파일러(F5)가 `for (...)`나 `while (...)` 중 하나의 형태로만 보여줘서 원본과 다를까봐 의심될 때
- CTF 문제를 풀다가 반복문의 정확한 반복 횟수/종료 조건을 추적해야 할 때

## 핵심 개념

### 왜 구분이 안 되는가: 두 구문은 같은 것으로 컴파일된다
C 표준에서 아래 두 구문은 의미적으로 완전히 동일하다.
```c
for (init; cond; step) { body }
```
```c
init;
while (cond) { body; step; }
```
컴파일러 프론트엔드는 `for`문을 파싱하자마자 곧바로 "초기화 + while 형태"로 변환한 중간 표현(IR)을 만든다. 즉 백엔드가 기계어를 생성하는 시점에는 이미 원래 그것이 `for`였는지 `while`이었는지에 대한 정보 자체가 사라진 뒤다. 그래서 어셈블리만 보고 키워드를 알아내려는 시도는 애초에 컴파일러가 지워버린 정보를 복원하려는 것과 같다.

### -O0(비최적화)에서의 전형적인 모양
최적화가 꺼진 상태에서는 GCC/Clang/MSVC 모두 아래처럼 "조건을 맨 위가 아니라 맨 아래에 두고, 진입 시 조건 체크로 먼저 점프"하는 형태를 만든다.
```asm
; for (i = 0; i < n; i++) { body }
    mov   dword [i], 0        ; 초기화 (for 고유: 루프 시작 직전)
    jmp   L_cond               ; 조건 체크로 먼저 이동
L_body:
    ...body...
    mov   eax, [i]             ; 증가 (for 고유: 몸체 뒤 별도 블록)
    add   eax, 1
    mov   [i], eax
L_cond:
    mov   eax, [i]
    cmp   eax, [n]
    jl    L_body
```
```asm
; i = 0; while (i < n) { body; i++; }
    mov   dword [i], 0        ; 초기화가 루프 바깥, 하지만 for와 위치가 똑같음
    jmp   L_cond
L_body:
    ...body...
    mov   eax, [i]             ; 증가가 body 안에 있음 (source상 while 안의 문장)
    add   eax, 1
    mov   [i], eax
L_cond:
    mov   eax, [i]
    cmp   eax, [n]
    jl    L_body
```
두 어셈블리를 나란히 놓고 보면 **명령어 시퀀스가 완전히 동일**하다. 유일한 "단서"라고 부를 수 있는 것은 소스 레벨 디버그 정보(줄 번호 매핑)가 있을 때뿐이다 — 그 경우 `for`의 증가식은 `for (...)` 한 줄에, `while`의 증가식은 몸체 안의 별도 문장 줄에 매핑되어 줄 번호가 다르게 나타날 수 있다. 하지만 이는 디버그 정보가 남아있을 때만 가능한 이야기이고, 스트립된 릴리즈 바이너리에서는 이 단서조차 없다.

### -O2 이상에서의 루프 회전(Loop Rotation)
최적화가 켜지면 컴파일러는 "루프 가드 점프 + do-while 형태"로 한 번 더 정규화한다(자세한 이유는 REV-0458 참고). 이 형태에서도 for/while 구분은 여전히 불가능하며, 오히려 두 구문 모두 do-while 모양(조건이 몸체 끝에서 다시 체크되는 형태)으로 수렴해버린다.
```asm
    cmp   [n], 0        ; 가드: 0번 반복 가능성 처리
    jle   L_end
    xor   eax, eax       ; i = 0
L_body:
    ...body...
    inc   eax
    cmp   eax, [n]
    jl    L_body
L_end:
```

### 그럼 무엇을 봐야 하는가
어셈블리 레벨 리버싱에서 중요한 건 "키워드가 뭐였나"가 아니라 **루프의 네 요소를 정확히 식별하는 것**이다.
1. **초기화(init)**: 루프 진입 직전, 첫 조건 체크 이전에 한 번만 실행되는 값 설정
2. **조건(cond)**: 매 반복 시작/끝에서 평가되는 `cmp`+`jcc`
3. **몸체(body)**: 반복되는 실질 로직
4. **증가/갱신(step)**: 다음 반복 전에 반드시 실행되는 값 변경(반드시 `i++`류의 명시적 블록으로 분리되어 있지 않을 수도 있다 — while이나 for나 몸체 코드와 뒤섞여 있을 수 있음)

이 네 가지만 정확히 잡아내면, 디컴파일러가 최종적으로 `for(...)`로 보여주든 `while(...)`로 보여주든 실질적인 반복 로직 이해에는 전혀 차이가 없다.

### IDA 그래프 뷰에서의 모습
IDA Graph View(REV-0150 참고)에서 루프는 **백엣지(back edge)**로 나타난다 — 아래쪽 블록에서 위쪽 블록으로 되돌아가는 화살표다. 진입 노드에서 조건 체크 노드로 가는 간선, 몸체에서 조건 체크로 돌아가는 백엣지, 조건 체크에서 루프 밖(종료)으로 가는 간선을 식별하면 for/while 여부와 무관하게 루프 구조를 완전히 파악할 수 있다. Ghidra 디컴파일러(F5에 해당하는 자동 디컴파일)는 이 그래프 구조를 분석해서 관례적으로 `for` 또는 `while` 중 하나로 "재구성"해서 보여주지만, 이는 디컴파일러의 임의적 선택이지 원본 소스의 진실이 아니다.

## 화면/코드에서 보이는 징후
- 루프 진입 시 조건 체크 블록으로 곧장 건너뛰는 `jmp`가 있고, 그 조건 체크 블록 끝에서 몸체 시작으로 돌아가는 `jcc`가 있다 (-O0 스타일 "조건이 아래" 배치)
- 몸체 시작 전에 `cmp`+`jle`/`jge` 등으로 "0번 반복" 가능성을 미리 걸러내는 가드가 있다 (-O2 loop rotation)
- 증가식이 몸체의 마지막 문장과 물리적으로 붙어 있어서 구분이 안 된다
- 디컴파일러가 보여주는 `for`/`while` 키워드가 실행할 때마다(재분석마다) 달라질 수 있다 — 이는 버그가 아니라 원래 정보가 없기 때문에 발생하는 정상적 현상

## 가장 먼저 할 것
1. 반복 구조(백엣지)를 먼저 찾는다 — IDA 그래프 뷰나 Ghidra Function Graph에서 아래→위로 가는 화살표를 확인한다.
2. 조건 체크가 몸체 앞에 있는지 뒤에 있는지로 -O0/-O2 스타일을 짐작한다.
3. for/while 키워드 자체는 무시하고 초기화·조건·증가·몸체 네 블록을 각각 지목한다.

## 단계별 절차

**1) 백엣지 찾기**
루프 몸체의 마지막 명령이 몸체보다 낮은 주소로 되돌아가는 `jmp`/`jcc`인지 확인한다.

**2) 조건 위치로 -O0/-O2 스타일 구분**
```asm
; -O0 스타일: jmp로 조건 체크부터 먼저 감
    jmp   L_cond
L_body: ...
L_cond: cmp ...; jl L_body
```
```asm
; -O2 loop rotation 스타일: 가드 후 바로 do-while
    cmp ...; jcc L_end
L_body: ...; cmp ...; jl L_body
L_end:
```

**3) 초기화 지점 확인**
백엣지로 들어오지 않는(즉 루프 밖에서만 실행되는) 값 설정 명령을 찾는다. 이것이 초기화다.

**4) 증가/갱신 지점 확인**
몸체 마지막, 조건 재평가 직전에 실행되는 산술 연산(주로 `inc`, `add`)을 찾는다.

**5) 디컴파일러 결과와 교차검증**
IDA/Ghidra F5 결과에서 `for`/`while` 중 무엇으로 나오든, 위 1~4단계에서 직접 확인한 초기화/조건/증가/몸체와 일치하는지 검증한다. 불일치하면 디컴파일러 오류를 의심하고 원본 디스어셈블리를 신뢰한다.

## 명령어/단축키
- IDA: `Space`로 그래프 뷰/텍스트 뷰 전환, 그래프 뷰에서 화살표 색으로 분기 방향 확인(녹색=조건 참, 빨강=조건 거짓, 파랑=무조건), `F5` 디컴파일
- Ghidra: Function Graph 창(Window → Function Graph)에서 동일한 백엣지 시각화
- x64dbg/GDB: 조건 체크 주소에 브레이크포인트를 걸고 몇 번 반복되는지 직접 실행해서 확인(`bp` 반복 히트 카운트, GDB는 `ignore` 명령으로 N번째 히트까지 건너뛰기 가능)

## 출력 해석
- 디컴파일러가 `for (i = 0; i < n; i++)` 형태로 깔끔하게 보여준다면, 이는 초기화·조건·증가가 물리적으로 서로 떨어진 블록에 있어도 디컴파일러가 데이터 흐름을 분석해 재구성한 결과다.
- `while (true) { ... if (cond) break; ... }` 형태로 나온다면 루프 탈출 조건이 몸체 중간에 있는 경우(단순 for/while로 못 담아내는 형태)로, 원래 소스가 `while`이었을 가능성이 조금 더 높지만 여전히 확정할 수는 없다.

## 흔한 실수
- 어셈블리만 보고 "이건 for문이다/while문이다"라고 리포트나 문서에 단정적으로 적는 것 — 정보가 소실됐으므로 정확한 주장이 아니다. "루프 구조"라고 중립적으로 서술하는 것이 정확하다.
- 증가식이 몸체 뒤에 별도 블록으로 있으면 무조건 for라고 착각하는 것 — while 몸체 안에 `i++;`을 마지막 문장으로 직접 쓴 경우도 똑같은 모양이 나온다.
- -O0과 -O2의 "조건 위치가 다르다"는 것을 for/while 차이로 오해하는 것 — 이는 최적화 수준 차이지 소스 구문 차이가 아니다.
- 백엣지를 못 찾아서 루프인지도 모르고 순차 코드로 착각하는 것 — 그래프 뷰를 켜지 않고 텍스트 디스어셈블리만 위에서 아래로 읽으면 놓치기 쉽다.

## 막혔을 때 다음 체크
- 반복 횟수가 궁금하면 → 조건 비교 대상 값을 디버거로 확인하거나(REV-0176 참고 방식으로 반환값·레지스터 확인), 초기값과 종료 조건, 증가 폭을 계산해서 산술적으로 구한다.
- 루프가 여러 개 중첩되어 헷갈리면 → 그래프 뷰에서 백엣지를 하나씩 순서대로 따라가며 안쪽 루프부터 바깥쪽 루프 순으로 분리한다.
- 이 루프가 do-while처럼 보이는데 소스가 궁금하면 → REV-0458(do-while이 더 짧은 이유) 참고.

## 미니 예제

**예제 1 — for와 while이 동일하게 컴파일되는 경우**
```c
// (A) for
for (int i = 0; i < 5; i++) sum += arr[i];
// (B) while — (A)와 완전히 동일한 로직
int i = 0;
while (i < 5) { sum += arr[i]; i++; }
```
GCC/Clang `-O2`로 컴파일하면 (A)와 (B)는 바이트 단위로 동일한 어셈블리를 만든다(직접 `objdump -d`로 비교해보면 확인 가능 — REV-0464 참고).

**예제 2 — -O0 디스어셈블리 (전형적 for 스타일)**
```asm
mov   dword [rbp-4], 0      ; i = 0
jmp   .cond
.body:
mov   eax, [rbp-4]
add   eax, [rbp-8]           ; sum += arr[i] 계산의 일부
mov   [rbp-8], eax
add   dword [rbp-4], 1       ; i++
.cond:
cmp   dword [rbp-4], 4
jle   .body
```

**예제 3 — -O2 루프 회전 후 (for/while 구분 불가)**
```asm
test  ecx, ecx
jle   .end                  ; 0번 반복 가드
xor   eax, eax               ; i = 0
.body:
add   edx, [rdi+rax*4]       ; sum += arr[i]
add   rax, 1
cmp   rax, rcx
jl    .body
.end:
```
이 형태만 봐서는 원래 for였는지 while이었는지 절대 알 수 없다 — 오직 초기화/조건/증가/몸체 구조만 확인 가능하다.

## 출처/검증
- `for`문이 컴파일러 내부에서 `while` 형태 제어 흐름으로 정규화되는 것은 GCC/Clang(LLVM) 공식 문서의 제어 흐름 그래프(CFG) 생성 단계 설명 및 ISO C 표준(`for`문의 의미가 등가 `while` 형태로 정의됨, ISO/IEC 9899 6.8.5) 기준.
- IDA/Ghidra 그래프 뷰의 백엣지 시각화: Hex-Rays IDA 공식 문서(Graph View) 및 NSA Ghidra 공식 문서(Function Graph) 기준. (2026-09-08 검증)
