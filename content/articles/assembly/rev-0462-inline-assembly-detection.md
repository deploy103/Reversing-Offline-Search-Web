## 한 줄 요약
인라인 어셈블리(`__asm`, GCC `asm volatile`)는 컴파일된 뒤에는 문법적 표식이 전혀 남지 않지만, 컴파일러가 스스로는 잘 만들지 않는 특권/저수준 명령어(`rdtsc`, `cpuid`, `in`/`out`, `wrmsr` 등), 그 블록 앞뒤로 손으로 짠 듯한 레지스터 저장/복원, 디버그 정보상 한 줄에 몰린 명령어 개수, 디컴파일러의 번역 실패라는 네 가지 단서로 짐작할 수 있다.

## 언제 검색해야 하나
- IDA/Ghidra의 디컴파일 결과에 갑자기 원시 어셈블리 코멘트나 "decompilation failed"/"unable to decompile"류 경고가 뜨고, 그 위치의 명령어가 일반적인 C 코드에서 나올 법하지 않아 보일 때
- 함수 중간에 `rdtsc`, `cpuid`, `in al, dx`, `out dx, al`, `wrmsr`, `int 3` 같은 명령어가 특별한 이유 없이 나타날 때
- 암호화 루틴, 안티디버깅, CPU 기능 감지 코드처럼 손으로 최적화했을 법한 부분을 분석할 때
- 소스코드에 `__asm { ... }`나 `asm volatile(...)`가 있다는 걸 알고 있고, 컴파일된 바이너리에서 정확히 어느 부분인지 짚어내고 싶을 때

## 핵심 개념

### 왜 컴파일된 뒤에는 "인라인 어셈블리였다"는 표식이 없는가
컴파일러 프론트엔드는 인라인 어셈블리 블록을 만나면 그 안의 텍스트를 거의 그대로(어셈블러가 알아들을 수 있는 형태로) 최종 오브젝트 코드에 박아 넣는다. 컴파일러가 그 내용을 이해하고 재작성하는 게 아니라 "이 바이트들은 그대로 둬라"라는 식으로 취급하기 때문에, 최종 실행 파일 안에서는 그 명령어들이 컴파일러가 자동 생성한 코드와 물리적으로 전혀 구별되지 않는다. 그래서 "이건 인라인 어셈블리였다"를 100% 확신할 방법은 원칙적으로 없고, 아래 네 가지 정황 증거를 종합해서 강하게 추정하는 것이 현실적인 접근이다.

### 단서 1 — 컴파일러가 스스로 안 만드는(또는 거의 안 만드는) 명령어
일반적인 C/C++ 코드를 컴파일할 때 컴파일러가 자동으로 생성하지 않는, 혹은 매우 드물게만 생성하는 명령어들이 있다. 이런 것들이 특정 지점에 몰려있으면 인라인 어셈블리를 강하게 의심할 수 있다.
- **CPU 정보/타이밍**: `cpuid`(REV-0086), `rdtsc`(REV-0087) — C 표준 라이브러리 함수 호출 없이 직접 등장하면 인라인 어셈일 확률이 높다(컴파일러 intrinsic으로 생성되기도 하지만 intrinsic도 결국 소스에 명시적으로 `__cpuid()`/`__rdtsc()` 함수를 부른 결과이므로 넓게 보면 "저수준 코드를 의도적으로 쓴 지점"이라는 결론은 같다).
- **특권/포트 I/O 명령**: `in`, `out`, `wrmsr`, `rdmsr`, `hlt`, `cli`, `sti` — 일반 유저모드 애플리케이션 코드에서는 거의 나올 이유가 없다. 드라이버, 부트로더, 에뮬레이터, VM 코드에서 의도적으로 쓰인다.
- **동기화/저수준 힌트**: `pause`, `lfence`, `sfence`, `mfence` — 컴파일러가 `std::atomic`이나 인트린식을 통해 생성하기도 하지만, 락 구현이나 스핀락을 손으로 짠 코드에서 특히 자주 등장한다.
- **의도적 트랩/난독화**: `int3`, `ud2`, 비정상적인 프리픽스 조합 — 안티디버깅이나 자기수정코드(self-modifying code)에서 인라인 어셈으로 직접 심는 경우가 흔하다.

### 단서 2 — 부자연스러운 레지스터 저장/복원
인라인 어셈블리 블록이 특정 레지스터를 훼손(clobber)하는데 그 레지스터가 주변 C 코드에서도 필요하다면, 컴파일러는 블록 앞뒤에 `push`/`pop`으로 값을 보존하는 코드를 끼워 넣는다. 이 저장/복원 쌍이 컴파일러의 일반적인 함수 프롤로그/에필로그 패턴(REV-0031 참고)과 다른 위치, 즉 함수 중간에 국소적으로 나타난다면 그 사이가 인라인 어셈 블록일 가능성이 크다.
```asm
push  rbx                 ; 인라인 asm이 rbx를 건드리므로 미리 보존
push  rcx
; --- 인라인 asm 블록 (rbx, rcx를 자유롭게 사용) ---
cpuid
; ------------------------------------------------
pop   rcx
pop   rbx
```

### 단서 3 — 디버그 정보의 줄 번호 뭉침
디버그 심볼(PDB/DWARF)이 남아있는 바이너리라면, 정상적인 C 문장 하나는 보통 소수의 명령어(1~5개 정도)로 대응된다. 그런데 특정 구간의 명령어 10~20개 이상이 **전부 동일한 한 줄(line number)**에 매핑되어 있다면, 이는 "그 한 줄"이 사실 `__asm { ... }` 블록 전체(소스상으로는 한 개의 문장/블록으로 취급됨)였을 가능성을 시사한다. `objdump --dwarf=decodedline`이나 IDA/Ghidra가 로드한 라인 정보로 확인할 수 있다.

### 단서 4 — 디컴파일러의 번역 실패
IDA의 Hex-Rays나 Ghidra의 디컴파일러는 각 명령어를 자신이 아는 의미(semantics)로 변환해 C 유사 코드로 재구성한다. 그런데 아래 상황에서는 디컴파일러가 그 의미를 모델링하지 못해 실패하거나 원시 명령어를 그대로 노출한다.
- 특권 명령어, 문서화되지 않은 명령어, 디컴파일러가 지원하지 않는 SIMD/암호화 확장 명령
- 컴파일러가 절대 만들지 않는 순서로 배치된 스택 조작(디컴파일러의 스택 프레임 추정 로직이 깨짐)
- 자기수정코드나 계산된 점프처럼 정적 분석 자체가 어려운 제어 흐름

이럴 때 IDA는 종종 `Failed to decompile ...`류 에러를 띄우거나, 문제 구간을 그냥 원시 어셈블리 코멘트로 남긴 채 나머지만 디컴파일한다. Ghidra는 P-code로 변환이 안 되는 명령어를 만나면 `unimplemented` 경고를 달거나 해당 부분을 아예 비워둔 채로 진행한다.

### "핸드라이팅" 텍스처 알아보기
컴파일러가 생성한 코드는 일정한 "패턴"이 있다 — 지역 변수 접근은 항상 `[rbp+offset]`류로 통일되고, 주소 계산은 거의 항상 LEA(REV-0042)를 쓰며, 레지스터 재사용 규칙이 예측 가능하다. 반면 손으로 짠 인라인 어셈은 특정 레지스터를 고정해서 쓰거나(`__asm { mov eax, ...; cpuid; mov edi, ebx; ... }`), 컴파일러라면 절대 안 할 법한 비효율적/독특한 명령어 조합을 쓰는 경우가 많다. 여러 함수를 보고 "이 프로젝트의 컴파일러 스타일"에 익숙해지면, 이 텍스처 차이가 상당히 눈에 띄게 된다.

## 화면/코드에서 보이는 징후
- 함수 중간에 `cpuid`, `rdtsc`, `in`/`out`, `wrmsr`, `pause`, `int3` 등이 라이브러리 함수 호출 없이 직접 등장
- 그 앞뒤로 부자연스러운 위치에 `push`/`pop` 레지스터 저장/복원 쌍이 있음
- IDA/Ghidra 디컴파일 결과에 해당 구간만 실패 메시지나 원시 어셈블리가 그대로 노출됨
- 디버그 정보상 한 줄에 비정상적으로 많은 명령어가 매핑됨
- 주변 코드와 레지스터 사용 스타일이 확연히 다름(예: 함수 전체가 스택 지역 변수를 쓰는데 그 블록만 특정 레지스터를 고정적으로 재사용)

## 가장 먼저 할 것
1. 디컴파일이 실패하거나 이상하게 나온 지점을 먼저 원시 디스어셈블리로 전환해서 읽는다.
2. 그 구간에 특권/저수준 명령어가 있는지 확인한다.
3. 앞뒤로 레지스터 저장/복원이 국소적으로 있는지 확인해 블록의 시작/끝 경계를 짐작한다.

## 단계별 절차

**1) 디컴파일 실패 지점 식별**
IDA에서 `F5`를 눌렀을 때 특정 줄이 원시 어셈블리로 남아있거나 에러 메시지가 뜨면, 해당 주소로 이동해 그래프/텍스트 뷰에서 직접 읽는다.

**2) 특권/저수준 명령어 목록과 대조**
`cpuid`(REV-0086), `rdtsc`(REV-0087), `in`, `out`, `wrmsr`, `rdmsr`, `pause`, `lfence`/`sfence`/`mfence`, `int3`, `ud2`, `hlt` 등이 있는지 확인한다.

**3) 블록 경계 추정**
저장/복원 `push`/`pop` 쌍 사이, 또는 디버그 정보상 같은 줄로 매핑된 명령어들의 시작과 끝을 블록 경계로 잡는다.

**4) 목적 추정**
- `cpuid`+`rdtsc` 조합 → CPU 기능 감지 또는 타이밍 기반 안티디버깅(REV-0087 참고)
- `in`/`out` → 드라이버/에뮬레이터/저수준 하드웨어 접근
- `int3`/`ud2`가 정상 흐름에 있음(예외 처리 흔적이 아닌 경우) → 안티디버깅 트릭 또는 의도적 크래시

**5) 심볼/디버그 정보로 교차검증**
소스가 있다면 실제 `__asm`/`asm volatile` 블록과 대조하고, 없다면 문자열/함수명으로 목적(암호화 라이브러리 등)을 추정한다.

## 명령어/단축키
- IDA: 해당 주소에서 디컴파일 실패 시 `Space`로 그래프/텍스트 전환, 원시 명령어를 직접 확인. `Alt+T`로 특권 명령어 니모닉 텍스트 검색
- Ghidra: 디컴파일 창의 경고 아이콘 확인, Listing 뷰에서 원시 명령어 직접 확인
- objdump: `objdump --dwarf=decodedline <binary>`로 줄 번호-주소 매핑을 확인해 한 줄에 몰린 명령어 개수 파악
- x64dbg/GDB: 해당 블록에 브레이크포인트를 걸고 실제로 어떤 레지스터가 입출력으로 쓰이는지 실행하며 관찰

## 출력 해석
- 디컴파일러가 명확한 에러 없이도 어색한 원시 표현(`__asm { ... }` 유사 코멘트, 또는 의미 없는 임시변수 나열)을 낸다면, 그 부분의 의미를 디컴파일러가 정확히 모델링하지 못했다는 뜻이므로 신뢰하지 말고 원시 명령어를 직접 읽는다.
- `cpuid` 직후 `ebx`/`ecx`/`edx`를 조합해 문자열처럼 만드는 코드가 보이면(예: "GenuineIntel" 문자열 조립) 이는 CPU 벤더 식별 목적의 전형적인 인라인 어셈 패턴이다.

## 흔한 실수
- 디컴파일러가 보여주는 내용을 항상 신뢰하고 그대로 받아들이는 것 — 특권/미지원 명령어 구간에서는 디컴파일러의 번역이 부정확하거나 아예 없을 수 있으므로 반드시 원시 디스어셈블리로 확인해야 한다.
- 컴파일러 intrinsic(`__cpuid()`, `__rdtsc()` 같은 C 함수처럼 보이지만 실제로는 해당 명령어로 직접 치환되는 것)과 진짜 `__asm` 블록을 구분하지 않고 뭉뚱그리는 것 — 리버싱 관점에서는 둘 다 "개발자가 저수준 명령어를 의도적으로 썼다"는 점에서 결론은 비슷하지만, 소스 복원 시 문법이 다르다는 점은 알아두는 게 좋다.
- 특이한 명령어 하나만 보고 곧바로 "이건 인라인 어셈이다"라고 단정하는 것 — 컴파일러가 특정 인트린식이나 표준 라이브러리 함수(`memcpy`의 SIMD 인라인 등, REV-0448 참고)를 통해 자동으로 생성하는 경우도 있으므로, 문맥과 여러 단서를 함께 봐야 한다.
- 인라인 어셈 블록의 시작/끝 경계를 정확히 특정하지 않고 그 주변 코드까지 통째로 "이상한 코드"로 뭉뚱그려 분석을 포기하는 것 — 레지스터 저장/복원 쌍으로 경계를 좁히면 실제 블록은 생각보다 작은 경우가 많다.

## 막혔을 때 다음 체크
- 특권 명령어의 정확한 동작이 궁금하면 → Intel SDM 해당 명령어 절을 직접 찾아본다(리버싱 사전에는 자주 쓰이는 것만 개별 문서화되어 있을 수 있음).
- `cpuid`/`rdtsc`가 안티디버깅 목적인지 확신이 안 서면 → 그 결과값으로 어떤 분기를 타는지(값이 특정 임계치를 넘으면 디버거로 판단하는 패턴인지) 추적한다.
- 자기수정코드가 의심되면 → 실행 중 해당 메모리 영역이 쓰기 접근을 받는지 x64dbg/GDB의 메모리 접근 브레이크포인트로 확인한다.

## 미니 예제

**예제 1 — CPU 벤더 문자열 조립 (전형적 인라인 어셈)**
```c
char vendor[13];
__asm {
    mov eax, 0
    cpuid
    mov dword ptr [vendor], ebx
    mov dword ptr [vendor+4], edx
    mov dword ptr [vendor+8], ecx
}
```
```asm
mov   eax, 0
cpuid                       ; 일반 C 코드에서 함수 호출 없이 직접 등장 -> 강한 인라인 asm 단서
mov   [rbp-0x20], ebx
mov   [rbp-0x1c], edx
mov   [rbp-0x18], ecx
```

**예제 2 — 레지스터 보존이 필요한 인라인 asm**
```c
int result;
__asm__ volatile (
    "rdtsc"
    : "=a"(result)
    :
    : "edx"          // edx도 훼손됨을 컴파일러에 알림
);
```
```asm
push  rdx                  ; edx를 인라인 asm이 훼손하므로 보존
rdtsc
mov   [result], eax
pop   rdx
```

**예제 3 — 디컴파일 실패로 원시 어셈만 남는 경우 (개념 예시)**

// IDA F5 출력 예시(개념):
__int64 sub_401500()

  {

  }

## 출처/검증
- 인라인 어셈블리 문법과 클로버(clobber) 목록에 따른 레지스터 보존 규칙: GCC 공식 문서(Extended Asm) 및 MSVC 공식 문서(Inline Assembler) 기준.
- `CPUID`, `RDTSC`, 포트 I/O(`IN`/`OUT`), `WRMSR`/`RDMSR` 명령어의 정의와 권한 요구사항: Intel 64 and IA-32 Architectures Software Developer's Manual, Volume 2 해당 명령어 절 기준.
