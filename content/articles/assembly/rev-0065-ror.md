## 한 줄 요약
`ROR`(ROtate Right)는 목적 오퍼랜드의 비트를 오른쪽으로 지정한 횟수만큼 "회전"시키는 명령어다. `SHR`과 달리 밀려나는 비트를 버리지 않고 반대쪽(최상위 비트)으로 다시 채워 넣는다 — 즉 정보가 손실되지 않는다.

## 언제 검색해야 하나
- 어셈블리에 `ror eax, 1`, `ror ecx, cl`, `ror rax, 0Dh` 같은 코드가 반복문 안에 있을 때
- CTF crackme에서 플래그 문자열을 바이트마다 `ror`/`rol` + `xor`로 뒤섞는 루틴을 발견했을 때
- 쉘코드나 악성코드 분석 중 API 이름을 문자열 그대로 쓰지 않고 해시값으로 비교하는 루프(`ror` 기반 해시)를 볼 때
- IDA/Ghidra 디컴파일에서 `__ROR4__(x, n)` 같은 낯선 함수 호출이 보일 때

## 핵심 개념

### ROR이 실제로 하는 일
`ROR dest, count`는 `dest`의 모든 비트를 오른쪽으로 `count`번 민다. 이때 비트 0(최하위 비트, LSB)에서 밀려나가는 비트는 그냥 사라지는 게 아니라 **반대쪽 끝(최상위 비트)으로 다시 들어간다**. 그래서 "회전(rotate)"이라고 부른다.

예를 들어 8비트 값 `0b0000_0001`(=1)을 오른쪽으로 1번 회전하면:
```
회전 전: 0000 0001
회전 후: 1000 0000   (비트 0에 있던 1이 밀려나가면서 비트 7로 들어감)
```

### Intel 문법
```asm
ROR r/m8,  1
ROR r/m8,  CL
ROR r/m8,  imm8
ROR r/m16, 1 / CL / imm8
ROR r/m32, 1 / CL / imm8
ROR r/m64, 1 / CL / imm8      ; x64 전용
```
목적 오퍼랜드(`r/m`)는 레지스터 또는 메모리, 회전 횟수는 상수(`1` 또는 `imm8`) 또는 `CL` 레지스터로 준다. `SHL`/`SHR`과 오퍼랜드 형태가 완전히 동일하다.

**회전 횟수는 마스킹된다**: 32비트 오퍼랜드라면 실제 적용되는 횟수는 `count & 0x1F`(0~31), 64비트 오퍼랜드라면 `count & 0x3F`(0~63)다. 그래서 32비트 값을 32번 회전하면 `32 & 0x1F = 0`이 되어 아무 일도 일어나지 않은 것과 같다. 이 마스킹 규칙을 모르면 "왜 32만큼 돌렸는데 그대로지?" 하고 헷갈리기 쉽다.

### ROL과의 차이, SHR과의 차이
- **ROL(왼쪽 회전)** 은 방향만 반대다. `ror x, n`과 `rol x, (비트폭 - n)`은 결과가 완전히 같다 — 예를 들어 32비트 값을 오른쪽으로 5회전한 것은 왼쪽으로 27회전한 것과 동일하다. (ROL 자체는 REV-0064 참고)
- **SHR(논리 오른쪽 시프트)** 는 밀려나는 비트를 **버리고** 빈 자리를 0으로 채운다 — 정보가 손실된다. 반면 **ROR은 버리지 않고 반대쪽으로 순환**시키므로 정보가 보존된다. 이 차이 때문에 ROR은 "같은 횟수만큼 반대 방향(ROL)으로 다시 돌리면 원래 값으로 완전히 복원"할 수 있지만, SHR은 한 번 밀리면 그 비트를 되살릴 수 없다.

### 영향받지 않는 플래그 (중요)
ROR이 건드리는 플래그는 **CF와 OF 둘뿐**이다.
- **CF**: 회전으로 마지막에 밀려난 비트(= 회전 전 비트 0의 값)가 그대로 CF에 들어간다. 동시에 그 비트는 반대쪽 끝(최상위 비트)에도 들어간다.
- **OF**: 회전 횟수가 **정확히 1일 때만** 정의된다. 이때 OF는 "회전 후 결과의 최상위 비트 두 개를 XOR한 값"이다. 회전 횟수가 1이 아니면(0이거나 2 이상이면) **OF는 정의되지 않은(undefined) 값**이 되므로 읽고 판단해서는 안 된다.
- **ZF, SF, PF, AF는 전혀 변하지 않는다.** 이것이 `SHR`/`SAR`(이들은 ZF·SF·PF를 결과에 따라 갱신)과의 결정적 차이다. 즉 `ror eax, 1` 직후에 `jz`/`jnz`처럼 ZF를 검사하는 분기가 있다면, 그 ZF는 ROR이 아니라 **그 이전에 실행된 다른 명령**이 남긴 값이라는 뜻이니 주의해야 한다.

### 레지스터/메모리 효과
목적 오퍼랜드가 레지스터든 메모리든 그 자리에서 바로 값이 바뀐다(in-place). 스택이나 RIP에는 아무 영향이 없다 — ROR은 순수한 데이터 연산 명령이지 제어 흐름 명령이 아니다.

### 리버싱에서의 의미 — 해시/암호화 루틴의 신호
`ror`/`rol`은 CTF와 악성코드에서 다음과 같은 맥락으로 정말 자주 등장한다:
- **커스텀 해시/체크섬**: 문자열이나 버퍼를 한 바이트씩 읽으며 `ror hash, 7` 후 `xor hash, byte` 같은 패턴을 반복하는 루프. "정답 해시값"과 비교하는 crackme의 핵심 로직인 경우가 많다.
- **간단한 스트림 암호/난독화**: 플래그를 바이트 단위로 `ror`(또는 `rol`) + `xor`로 섞어 저장해두고, 실행 시 반대로 풀어서 비교하는 패턴.
- **API 해싱(ROR13 해시)**: 쉘코드나 패커가 임포트 테이블에서 함수 이름 문자열 대신 해시값으로 `GetProcAddress` 대상을 찾는 유명한 기법이다. 대표적으로 각 문자를 더한 뒤 `ror eax, 13`을 반복하는 "ROR13 해시"가 있다 — 이는 함수 이름 문자열이 바이너리에 그대로 남지 않게 해서 정적 분석(문자열 검색)을 어렵게 만드는 목적이다.

**결론적으로**: 반복문 안에서 `ror`/`rol`이 `xor`나 `add`와 함께 버퍼를 순회하고 있다면, 십중팔구 커스텀 해시/체크섬이거나 간단한 인코딩 루틴이다. 루프를 통째로 읽고 "무엇을 몇 번 회전시키는지, 어떤 값과 XOR/ADD 하는지"를 정리하면 Python으로 그대로 재현해서 반대로 풀 수 있다.

## 화면/코드에서 보이는 징후
- `ror eax, 1` — 상수 1칸 회전, OF가 의미 있게 정의됨
- `ror ecx, cl` — 회전 횟수가 런타임에 결정(다른 레지스터에서 계산된 값)
- `ror eax, 0Dh` — 13칸 회전, ROR13 해시의 전형적 모습
- 루프 안에서 `movzx`(바이트 읽기) → `xor`/`add` → `ror` 순서가 반복되는 패턴
- IDA 디컴파일에서 `__ROR4__(v, 0xD)` / `__ROR8__(...)` 같은 인트린식 함수 호출
- Ghidra 디컴파일에서 `(uVar1 >> 0xd | uVar1 << 0x13)`처럼 시프트 두 개를 OR로 합친 식 (컴파일러/디컴파일러가 회전을 시프트 조합으로 풀어서 표현하는 경우)

## 가장 먼저 할 것
1. 회전 대상 레지스터/메모리와 회전 횟수(상수인지 CL인지)를 확인한다.
2. 이 ROR이 반복문 안에 있는지 확인한다 — 반복문 안이면 해시/인코딩 루틴일 가능성이 높다.
3. 같은 루프 안에서 XOR, ADD 등 다른 연산이 어떤 값과 함께 쓰이는지 적어둔다.
4. 최종적으로 이 값이 무엇과 비교(`cmp`)되는지 찾는다 — 그게 "정답" 해시/체크섬이다.

## 단계별 절차

**1) 단순 회전 확인**
```asm
mov  eax, 0FFh
ror  eax, 4      ; eax = 0xF000000F
```
값을 손으로 계산하기 번거로우면 IDA/x64dbg의 레지스터 창에서 회전 전후 값을 직접 눈으로 비교한다.

**2) 반복문 안의 회전 — 해시 루프 의심**
```asm
xor  eax, eax
loop_start:
  movzx ecx, byte ptr [rsi]   ; 문자 1바이트 읽기
  add   eax, ecx
  ror   eax, 0Dh              ; 13칸 오른쪽 회전 (ROR13 스타일)
  inc   rsi
  cmp   byte ptr [rsi], 0
  jnz   loop_start
```
이 루프를 발견하면 파이썬으로 그대로 옮겨서 어떤 문자열이 어떤 해시값을 만드는지 브루트포스하거나, 반대로 목표 해시값에 맞는 문자열을 역산할 수 있는지 검토한다.

**3) CF로 원래 최하위 비트 확인**
```asm
ror  bl, 1
jc   was_odd     ; 회전 전 bl의 최하위 비트가 1이었으면 CF=1 → 홀수였다는 뜻
```

## 명령어/단축키
- IDA: 레지스터 창에서 회전 전/후 값을 직접 비교, `__ROR4__`/`__ROR8__` 인트린식 위에서 더블클릭하면 정의로 이동하지 않지만 이름 자체로 회전 폭(4=32비트, 8=64비트)을 알 수 있음
- x64dbg: 명령어 위에 커서를 놓으면 하단 상태바에 CF 변화가 표시됨, `F7`(Step Into)로 한 스텝씩 실행하며 레지스터 값 변화 관찰
- GDB/Pwndbg: `stepi`로 한 명령씩 실행 후 `info registers eax`(또는 `p/x $eax`)로 값 확인, `p/x $eflags`로 CF 비트 확인

## 출력 해석
- IDA에서 `__ROR4__(a1, 0xD)`가 보이면 "32비트 값 a1을 13칸 오른쪽 회전"이라는 뜻 — 4는 4바이트(32비트)를 의미하고, 8이면 8바이트(64비트) 버전이다.
- 디버거에서 CF가 회전 후 1로 바뀌었다면, 회전 전 그 값의 비트 0이 1이었다는 뜻이다(반대로 회전 전 최상위 비트를 알고 싶으면 ROL의 CF를 보면 된다).
- 루프를 다 읽고 나온 최종 `eax` 값이 이후 `cmp eax, 0DEADBEEFh` 같은 상수와 비교된다면, 그 상수가 바로 "이 문자열이 맞는지" 판별하는 목표 해시값이다.

## 흔한 실수
- ROR을 SHR과 같은 것으로 착각해서 "비트가 사라진다"고 오해하는 것 — ROR은 정보가 손실되지 않고 반대쪽으로 순환할 뿐이므로, 같은 횟수만큼 ROL로 돌리면 정확히 원상 복구된다. 디코드 루틴을 파이썬으로 재구현할 때 이 가역성을 이용하면 편하다.
- 회전 횟수가 오퍼랜드 크기보다 크다고 착각해서 계산을 잘못하는 것 — 실제로는 `count & 0x1F`(32비트) / `count & 0x3F`(64비트)로 마스킹된 값만 적용된다.
- ROR 직후 `jz`/`jnz` 같은 ZF 기반 분기가 나오면 "ROR이 ZF를 바꿨나?" 하고 헷갈리는 것 — ROR은 ZF를 절대 건드리지 않으므로, 그 ZF는 반드시 더 앞선 다른 명령(CMP, TEST, SUB 등)이 남긴 값이다.
- 회전 횟수가 1이 아닌데 OF를 신뢰해서 분기 조건을 해석하려는 것 — count != 1이면 OF는 undefined이므로 애초에 그 분기는 OF를 보는 게 아닐 가능성이 높다(다시 확인).

## 막혔을 때 다음 체크
- 루프의 회전 횟수나 XOR 상수가 계산식으로 되어 있어 손으로 풀기 힘들면 → 어셈블리를 그대로 Python으로 옮겨 스크립트로 재현한다.
- CF/OF가 이후 분기에 쓰이는지 애매하면 → 디버거로 브레이크포인트를 걸고 실제 플래그 값을 확인한다.
- 디컴파일러가 `__ROR4__` 대신 이상한 시프트 조합(`>>`, `<<`, `|`)으로 풀어서 보여준다면 → 그 식이 회전(rotate)의 표준 형태(`(x >> n) | (x << (32-n))`)인지 확인하고, 맞다면 정신적으로 "이건 그냥 ROR이다"라고 치환해서 읽는다.

## 미니 예제

**예제 1 — 상수 횟수 회전과 CF**
```asm
mov al, 0B4h      ; 0b1011_0100
ror al, 1         ; al = 0b0101_1010 = 0x5A, CF = 원래 비트0(0) → CF=0
```

**예제 2 — CL로 가변 횟수 회전**
```asm
mov cl, 4
ror eax, cl        ; eax를 4칸 오른쪽 회전
```

**예제 3 — API 해싱 스타일 루프 (개념 예시)**
```c
// 대략적인 원본 로직
unsigned int hash = 0;
for (char *p = name; *p; p++) {
    hash += (unsigned char)*p;
    hash = (hash >> 13) | (hash << (32 - 13));  // ror 13
}
```

xor  eax, eax
.loop:
