## 한 줄 요약
컴파일러는 데이터 의존성(어떤 명령어가 다른 명령어의 결과를 필요로 하는가)만 지키면 되는 한도 내에서, CPU 파이프라인 지연(latency)을 숨기려고 **소스코드 순서와 다르게 명령어를 재배치**할 수 있으며, 이를 명령어 스케줄링(Instruction Scheduling)이라 한다.

## 언제 검색해야 하나
- 디스어셈블리에서 서로 관련 없어 보이는 두 계산의 명령어가 번갈아 섞여 있어서 "이게 왜 여기 있지?"라는 의문이 들 때
- 소스코드에서는 A를 계산한 다음 B를 계산하는데, 어셈블리에서는 B에 해당하는 `mov`/`lea`가 A보다 먼저 나올 때
- `mov`로 메모리를 미리 읽어두는 명령어가 그 값을 실제로 쓰는 지점보다 한참 위에 있을 때
- CPU의 "비순차 실행(out-of-order execution)"과 컴파일러의 "명령어 스케줄링"이 같은 것인지 헷갈릴 때

## 핵심 개념

### 두 가지 서로 다른 "순서 재배치"를 구분하자
리버싱 초보자가 가장 헷갈리는 지점은 "명령어 순서가 바뀐다"는 현상이 사실 **완전히 다른 두 단계**에서 일어난다는 점이다.

1. **컴파일 시점 스케줄링(정적, static)**: 컴파일러가 코드를 생성할 때, 실행 결과가 바뀌지 않는 한도 내에서 명령어의 **텍스트 순서(바이너리에 실제로 저장된 순서)** 를 바꾼다. 이건 디스어셈블리에 그대로 보인다 — 우리가 IDA/Ghidra에서 보는 순서 자체가 이미 재배치된 결과다.
2. **CPU 실행 시점 재배치(동적, dynamic, 비순차 실행/OoO)**: 최신 x86 CPU(Intel Core, AMD Zen 계열 등)는 명령어를 프로그램 순서와 다르게 실행 엔진에 넣고, 준비된 것부터 먼저 실행한 뒤 결과만 프로그램 순서에 맞춰 정리(retire)한다. **이건 바이너리 파일 안의 바이트 순서에는 전혀 영향을 주지 않는다** — 디스어셈블리로는 절대 볼 수 없고, 오직 실제 실행 시점(하드웨어 내부)에서만 일어난다.

리버싱(정적 분석)에서 우리가 신경 써야 하는 것은 거의 항상 **1번(컴파일 시점 스케줄링)** 이다. CPU의 비순차 실행은 디스어셈블리를 읽는 데는 영향을 주지 않지만, 타이밍 기반 안티디버깅이나 사이드채널 분석을 다룰 때는 존재를 알아둘 필요가 있다.

### 왜 컴파일러가 순서를 바꾸는가
CPU 파이프라인에서 각 명령어는 실행에 걸리는 지연시간(latency)이 다르다. 예를 들어 메모리 로드(`mov eax, [rdi]`)는 캐시에 없으면 수십~수백 사이클이 걸릴 수 있지만, 레지스터끼리의 `add`는 1사이클이면 끝난다. 만약 로드 결과를 곧바로 다음 명령어에서 써야 한다면 CPU는 로드가 끝날 때까지 기다려야 한다(파이프라인 스톨). 컴파일러는 이걸 피하려고, **로드가 필요한 값을 실제로 쓰는 지점보다 미리 위쪽으로 옮겨서** 로드가 진행되는 동안 다른 독립적인 계산을 먼저 실행하도록 코드를 짠다.

```c
int compute(int *p, int a, int b) {
    int v = *p;      // 메모리 로드 - 느릴 수 있음
    int s = a + b;   // v와 무관한 계산
    return v + s;
}
```
`-O0`에서는 소스 순서 그대로 `mov`(로드) 다음에 `add`(a+b)가 나오지만, 최적화된 빌드에서는 로드를 더 일찍 실행하도록 배치되거나(이 경우는 이미 로드가 먼저라 순서가 안 바뀌지만), 더 복잡한 함수에서는 **뒤에 있는 독립적인 연산이 앞으로 당겨지는** 형태로 재배치가 흔히 일어난다.

### 데이터 의존성만은 항상 지켜진다
컴파일러가 아무리 순서를 바꿔도, "이 값을 쓰려면 반드시 그 전에 계산이 끝나 있어야 한다"는 규칙(데이터 의존성)은 절대 깨지 않는다. 즉 순서가 뒤섞여 보여도 각 레지스터/메모리 값의 정의(define)는 항상 그 사용(use)보다 어셈블리상 앞에 위치한다. 이 원칙 덕분에, 순서가 헷갈릴 때는 "이 레지스터가 마지막으로 쓰여진 곳이 어디인가"를 거슬러 올라가면 항상 답을 찾을 수 있다.

### CMP와 Jcc의 매크로 퓨전(참고)
스케줄링과 별개로, 최신 CPU는 `cmp`/`test` 바로 뒤에 오는 `jcc`를 하나의 내부 연산으로 합쳐 실행하는 매크로 퓨전(macro-op fusion)을 지원한다. 이 때문에 컴파일러는 `cmp`와 그 직후의 `jcc`를 웬만하면 떨어뜨리지 않고 붙여서 배치하는 경향이 있다 — 이는 스케줄링이 오히려 "순서를 지켜주는" 쪽으로 작동하는 예다. 자세한 마이크로옵 개념은 REV-0475를 참고.

## 화면/코드에서 보이는 징후
```asm
; 소스: v = *p; s = a+b; return v+s;
mov     eax, [rdi]     ; v = *p  (지연이 큰 로드를 먼저 실행)
lea     ecx, [rsi+rdx] ; s = a+b (로드가 진행되는 동안 독립적으로 계산 가능)
add     eax, ecx       ; v + s
```
```asm
; 소스 순서와 다르게, 뒤쪽 계산이 앞으로 당겨진 경우
mov     eax, [rbx+8]        ; (3) 사실 소스에서는 세 번째로 쓰이는 값이지만 먼저 로드됨
imul    ecx, edi, 10h
mov     edx, [rbx+4]        ; (2)
add     ecx, edx
add     ecx, eax            ; (1)+(2)+(3) 조합, 여기서 최종 사용
```

## 가장 먼저 할 것
1. 순서가 이상하다고 느껴지면 우선 각 레지스터가 **정의되는 곳**과 **쓰이는 곳**을 각각 표시해본다.
2. 정의가 사용보다 어셈블리상 앞에 있는지(항상 그래야 정상)를 확인한다 — 이게 깨져 보인다면 순서 착각이 아니라 다른 레지스터를 잘못 추적했을 가능성이 크다.
3. "왜 이 순서로 배치됐을까"는 대개 로드/느린 연산을 먼저 시작해서 지연을 숨기려는 목적이라고 이해하고 넘어가면 된다 — 로직 이해에는 순서 자체보다 의존성 그래프가 중요하다.

## 단계별 절차
**1) 데이터 의존성 그래프 그리기(머릿속 또는 종이에)**
각 명령어가 어떤 레지스터를 읽고(source) 어떤 레지스터를 쓰는지(dest) 나열한다. 화살표로 "이 값을 누가 만들고 누가 쓰는지" 연결하면 실제 실행 순서와 무관하게 논리적 순서가 드러난다.

**2) IDA 디컴파일(F5)로 재구성된 순서 확인**
Hex-Rays/Ghidra 디컴파일러는 데이터 의존성을 분석해서 대체로 사람이 이해하기 쉬운(소스에 가까운) 순서로 C 코드를 재구성해준다. 어셈블리 순서가 헷갈리면 먼저 F5부터 눌러 디컴파일 결과를 참고하는 것이 빠르다.

**3) 디버거로 실제 실행 순서 확인(필요시)**
디스어셈블리만으로 헷갈리면 x64dbg/GDB로 명령어 단위 스텝(`stepi`/F7)을 밟아가며 레지스터 값이 실제로 언제 채워지는지 직접 관찰한다.

## 명령어/단축키
- IDA: `F5`(디컴파일 — 의존성을 재구성해서 순서를 정리해줌), 레지스터 더블클릭(정의/사용 지점 하이라이트)
- x64dbg: `F7`(명령어 단위 스텝), Registers 창에서 각 스텝마다 값 변화 관찰
- GDB/Pwndbg: `stepi`(si), `info registers`, `x/5i $pc`(다음 5개 명령어 미리보기)

## 출력 해석
- 어셈블리 순서가 소스 순서와 다르더라도, 최종 결과값과 분기 조건은 항상 원본 로직과 동일하다 — 순서 자체에 의미를 부여하지 말고 "어떤 값이 어떤 값으로부터 계산됐는가"에 집중한다.
- 디컴파일러가 보여주는 C 코드 순서가 원본 소스와 100% 같다는 보장은 없다 — 디컴파일러도 나름의 재배치/정리를 거친 결과물이다.

## 흔한 실수
- 어셈블리 순서를 소스코드 실행 순서와 동일하다고 가정하고 위에서 아래로 그대로 번역하려는 것 — 최적화된 코드에서는 이 가정이 자주 깨진다.
- CPU의 비순차 실행(하드웨어, 실행 시점)과 컴파일러의 명령어 스케줄링(소프트웨어, 컴파일 시점)을 같은 현상으로 착각하는 것 — 디스어셈블리에서 실제로 관찰되는 재배치는 컴파일러가 만든 것이지, CPU가 실시간으로 바이너리를 바꾸는 게 아니다.
- 순서가 섞인 코드를 보고 "난독화 트릭"이라고 오판하는 것 — 대부분은 일반적인 최적화 스케줄링일 뿐 의도적인 방해 코드가 아니다(다만 실제 안티디스어셈블리 트릭도 존재하므로 문맥을 함께 봐야 한다).

## 막혔을 때 다음 체크
- 값의 출처를 못 찾겠다면 → REV-0467(CSE)이나 REV-0469(레지스터 할당)도 같이 의심해본다. 값이 재사용되거나 다른 레지스터로 옮겨졌을 수 있다.
- 디컴파일 결과가 더 헷갈린다면 → 어셈블리 원문으로 돌아가 레지스터별 정의/사용을 손으로 직접 추적한다.
- 진짜 안티디스어셈블리가 의심되면 → 명령어 경계 자체가 의심스러운지(REV-0476, REV-0477 계열 증상) 먼저 확인한다.

## 미니 예제
**예제 1 — 로드 지연 숨기기**
```c
int f(int *p, int a, int b) {
    int v = *p;
    int s = a + b;
    return v + s;
}
```
```asm
mov     eax, [rdi]   ; v = *p (지연 큰 로드를 최대한 먼저 시작)
lea     ecx, [rsi+rdx]
add     eax, ecx
ret
```

**예제 2 — 뒤쪽 계산이 앞으로 당겨진 경우**
```c
int g(int *arr, int i, int j, int k) {
    int a = arr[i];
    int b = arr[j];
    int c = k * 3;
    return a + b + c;
}
```
```asm
imul    r8d, ecx, 3        ; c = k*3 (독립적인 정수 연산, 로드보다 먼저 배치될 수 있음)
mov     eax, [rdi+rsi*4]   ; a = arr[i]
mov     edx, [rdi+rdx*4]   ; b = arr[j]
add     eax, edx
add     eax, r8d
ret
```

## 관련 글
- REV-0467 — Common Subexpression Elimination이 코드에 남기는 흔적
- REV-0469 — 레지스터 할당 차이로 같은 로직이 다르게 보이는 이유
- REV-0475 — 명령어 하나가 여러 마이크로옵으로 나뉜다는 개념(참고용)
- REV-0464 — -O0과 -O2 컴파일 결과를 나란히 비교하는 법
- REV-0060 — CMP: 값을 바꾸지 않는 SUB 비교

## 출처/검증
- 명령어 스케줄링과 파이프라인 지연 숨기기: 컴파일러 최적화 표준 교재 및 Agner Fog "Optimizing subroutines in assembly language" (x86 마이크로아키텍처 최적화 가이드) 기준.
- CPU 비순차 실행과 매크로 퓨전: Intel 64 and IA-32 Architectures Optimization Reference Manual 기준.
- 위 어셈블리 예제는 x86-64 `-O2` 최적화 결과를 단순화해 재구성한 예시다(2026-09-08 검증).
