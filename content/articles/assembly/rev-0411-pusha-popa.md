## 한 줄 요약
`PUSHA`는 16비트 범용 레지스터 8개(AX, CX, DX, BX, SP, BP, SI, DI)를 한 번에 스택에 밀어 넣고, `POPA`는 그 반대로 한 번에 꺼내 복원하는 레거시 명령어로, 64비트 모드에서는 아예 사용할 수 없다.

## 언제 검색해야 하나
- 16비트 DOS/부트로더/BIOS 코드나 CTF의 "레트로" 바이너리에서 `pusha`, `popa`를 만났을 때
- 레지스터 8개를 개별 `PUSH`/`POP` 없이 한 번에 저장/복원하는 이유가 궁금할 때
- 이 명령어가 x64 디스어셈블리에는 왜 전혀 안 보이는지 궁금할 때
- `POPA`가 실행돼도 SP 레지스터 값 자체는 스택에서 읽은 값으로 덮어써지지 않는 이유가 궁금할 때

## 핵심 개념

### Intel 문법과 오퍼랜드
```
PUSHA   ; 오퍼랜드 없음
POPA    ; 오퍼랜드 없음
```
둘 다 오퍼랜드를 받지 않는다 — "지금 있는 모든 범용 레지스터"를 대상으로 고정된 순서로 동작하기 때문이다.

### PUSHA가 실제로 하는 일 — 8개 레지스터를 정해진 순서로 PUSH
`PUSHA`는 16비트 레지스터 AX, CX, DX, BX, **원래(밀어넣기 시작 전) SP 값**, BP, SI, DI를 이 순서 그대로 스택에 하나씩 [PUSH](rev-0044-push.md)한다. 각 PUSH가 SP를 2씩 감소시키므로, 총 8워드(16바이트)만큼 SP가 줄어든다.
```
PUSHA 실행 순서 (각각 스택에 PUSH, SP -= 2씩):
  1. AX
  2. CX
  3. DX
  4. BX
  5. (원래) SP    <- PUSHA 시작 시점의 SP 값. 이후 PUSH들로 이미 변해버린 "현재" SP가 아니라 "시작 전" 값이라는 점이 중요!
  6. BP
  7. SI
  8. DI
```

### POPA가 실제로 하는 일 — 반대 순서로 POP, 단 SP 슬롯은 버림
`POPA`는 정확히 반대 순서로 [POP](rev-0045-pop.md)한다: DI, SI, BP, **(SP 슬롯 — 읽어서 버림, SP 레지스터에 로드하지 않음)**, BX, DX, CX, AX. SP 위치에 저장돼 있던 값은 스택에서 "읽기는 하지만 실제 SP 레지스터에 쓰지는 않는다" — 어차피 나머지 7개를 POP하고 나면 SP는 PUSHA 실행 전 값으로 자연스럽게 되돌아오기 때문에, 저장해둔 SP 값을 다시 로드할 필요가 없다(만약 로드해버리면 오히려 순환 참조처럼 값이 꼬인다).

### 플래그 변화
`PUSHA`/`POPA` 자체는 플래그를 전혀 건드리지 않는다 — 데이터를 옮기기만 할 뿐 계산을 하지 않기 때문이다.

### signed/unsigned 관점
해당 없음 — 레지스터 값을 그대로 옮기는 연산이다.

### 스택/SP 변화
```
PUSHA 실행 전: SP = S
PUSHA 실행 후: SP = S - 16   (8워드 = 16바이트)
POPA  실행 후: SP = S       (원래 값으로 정확히 복귀)
```

### 왜 64비트 모드에서는 쓸 수 없는가
`PUSHA`/`POPA`의 오피코드(`0x60`/`0x61`)는 **x64(64비트) 모드에서 아예 유효하지 않은 인코딩**이다. AMD64를 설계할 때 REX 접두사가 `0x40`~`0x4F` 범위를 차지하게 되면서, 오피코드 공간을 정리하는 과정에서 `0x60`/`0x61` 계열은 64비트 모드에서 되살리지 않기로 결정되었다. 그래서 64비트 코드에서 이 바이트를 만나면 `#UD`(잘못된 명령어) 예외가 발생하며, 컴파일러도 x64 타겟에는 절대 이 명령어를 생성하지 않는다. x64에는 `PUSHAQ`/`POPAQ` 같은 것도 존재하지 않는다.

### 왜 쓰였는가 — 레지스터 저장을 코드 한 줄로
16/32비트 시절에는 함수(인터럽트 핸들러 등)가 자신이 쓰는 레지스터를 개별적으로 `PUSH`/`POP`하는 대신, `PUSHA` 한 줄로 "일단 전부 저장"하고 `POPA` 한 줄로 "전부 복원"하는 것이 코드 크기 면에서 간결했다. 특히 DOS 인터럽트 핸들러, 부트로더, BIOS 콜백, 초기 16/32비트 셸코드에서 자주 쓰였다.

### 컴파일러 패턴
일반적인 C 컴파일러는 `PUSHA`/`POPA`를 자동으로 생성하지 않는다 — 컴파일러는 실제로 필요한(사용하는) 레지스터만 골라서 저장/복원하는 것이 더 효율적이기 때문이다. `PUSHA`/`POPA`는 손으로 작성된 어셈블리(인터럽트 서비스 루틴, 부트로더, 레거시 16/32비트 셸코드)에서만 볼 수 있다고 생각하면 된다.

### IDA/Ghidra 디컴파일에서 보이는 형태
IDA는 `pusha`/`popa`를 있는 그대로 어셈블리로 보여주며, Hex-Rays 디컴파일러는 이를 8개 레지스터의 개별 저장/복원으로 풀어서 표시하거나, 함수 프롤로그/에필로그의 일부로 뭉뚱그려 처리하는 경우가 많다. 순수 C 코드로 자연스럽게 역컴파일되는 대응물이 없다는 점을 기억해두면 된다.

### 리버싱 의미
`PUSHA`를 발견하면: (1) 16/32비트 레거시 코드이거나 (2) 손으로 작성된 어셈블리(셸코드, 부트로더, 인터럽트 핸들러)라는 강한 신호다. x64 바이너리에서는 절대 나타나지 않으므로, 이 명령어가 보인다면 파일이 32비트(또는 16비트) 대상이라는 것부터 다시 확인해야 한다.

## 화면/코드에서 보이는 징후
- `pusha` — 8개 16비트 레지스터 일괄 저장 (16비트 코드)
- `popa` — 8개 16비트 레지스터 일괄 복원
- 인터럽트 핸들러/부트로더 코드 초반의 `pusha`, 끝부분의 `popa`
- x64 바이너리에서는 절대 등장하지 않음 — 만약 디스어셈블러가 이 위치를 `pusha`로 표시한다면 코드/데이터 오분석을 의심해야 함

## 가장 먼저 할 것
1. 이 바이너리/코드 조각이 실제로 16비트 또는 32비트 모드인지 먼저 확인한다(x64면 애초에 나올 수 없는 명령어).
2. `pusha`와 짝을 이루는 `popa`가 어디 있는지 찾아 그 사이 블록 전체를 "레지스터 보존 구간"으로 묶어서 본다.
3. 그 구간 안의 코드가 실제로 무엇을 하는지(인터럽트 처리, 페이로드 실행 등) 분석한다.

## 단계별 절차

**1) 기본 저장/복원 인식**
```asm
pusha
; ... 레지스터를 자유롭게 쓰는 코드 ...
popa
; 이 지점에서 모든 레지스터가 pusha 실행 전 상태로 복원됨
```

**2) 인터럽트 핸들러에서의 전형적 사용**
```asm
int_handler:
    pusha              ; 호출자의 레지스터를 모두 보존
    ; ... 인터럽트 처리 로직 ...
    popa                ; 호출자의 레지스터 복원
    iret                 ; 인터럽트 반환 (REV-0415 참고)
```

**3) SP 슬롯이 버려지는 것 확인 (디버거)**
`pusha` 실행 직후 스택 메모리를 덤프해보면 5번째 워드 자리에 PUSHA 시작 전의 SP 값이 그대로 박혀 있는 것을 볼 수 있다. `popa` 실행 시 이 값은 읽히기만 하고 SP 레지스터에는 반영되지 않는다는 것을 레지스터 창에서 SP 값 변화로 확인할 수 있다.

## 명령어/단축키
- x64dbg/올리디버거류: 16/32비트 실행 파일을 열었을 때만 `pusha`/`popa`를 만날 수 있다 — 스택 창에서 8워드가 한 번에 쌓이는 것을 확인
- GDB: 16비트 real mode 디버깅(`gdb`+`qemu` 조합 등)에서 `x/8xh $sp`로 스택에 쌓인 8개 워드를 직접 확인 가능

## 출력 해석
- `pusha` 실행 후 SP가 정확히 16만큼 감소했는지 확인한다.
- `popa` 실행 후 SP가 `pusha` 실행 전 값으로 정확히 돌아왔는지 확인한다 — 안 돌아왔다면 그 사이에 스택을 직접 건드린(수동 `push`/`pop`을 짝 안 맞게 쓴) 코드가 있다는 뜻이다.

## 흔한 실수
- `PUSHA`가 x64에서도 동작한다고 가정하는 것 — 64비트 모드에서는 `#UD` 예외를 일으키는 유효하지 않은 인코딩이다.
- `POPA`가 스택에서 SP 값도 읽어서 SP 레지스터에 그대로 로드한다고 착각하는 것 — 그 슬롯은 읽지만 버려지고, SP는 나머지 7개 POP만으로 자연스럽게 원래 값으로 돌아온다.
- `PUSHA`로 저장되는 SP 값을 "PUSHA 실행 중간의 SP"라고 착각하는 것 — 정확히는 "PUSHA 시작 전"의 SP 값이 저장된다.
- `PUSHA`/`POPA`(16비트, 이 문서)와 `PUSHAD`/`POPAD`(32비트, REV-0412)를 같은 명령어로 혼동하는 것 — 오퍼랜드 크기와 스택 소비량(16바이트 vs 32바이트)이 다르다.

## 막혔을 때 다음 체크
- x64로 알고 있던 바이너리에서 `pusha`가 보이면 → 실제로는 32비트 서브시스템, WOW64 코드, 혹은 디스어셈블 위치 오분석(데이터를 코드로 잘못 해석)일 가능성을 의심한다.
- `pusha`/`popa` 사이 코드가 무슨 일을 하는지 모르겠으면 → 이 블록을 "레지스터가 보존되는 하나의 서브루틴"으로 보고, 진입 직전과 종료 직후의 레지스터 상태만 비교해서 순수 부작용(메모리 변경 등)을 찾는다.
- 스택이 예상과 다르게 어긋나면 → `pusha`와 `popa`가 정확히 짝을 이루는지, 그 사이에 균형이 안 맞는 수동 `push`/`pop`이 있는지 확인한다.

## 미니 예제

**예제 1 — 기본 저장/복원**
```asm
pusha
mov  ax, 1234h
mov  bx, 5678h
; ax, bx 등을 자유롭게 변경
popa
; 여기서부터 모든 레지스터는 pusha 이전 값
```

**예제 2 — 인터럽트 핸들러 (DOS/BIOS 스타일)**
```asm
my_int_handler:
    pusha
    push ds
    push es
    ; ... 인터럽트 처리 ...
    pop  es
    pop  ds
    popa
    iret
```

**예제 3 — 16비트 셸코드에서의 레지스터 보존**
```asm
start:
    pusha            ; 호출 환경의 레지스터를 모두 백업
    call payload      ; 페이로드 실행 (레지스터를 마음대로 사용)
    popa               ; 원래 레지스터 상태로 복원
    ; 원래 실행 흐름으로 안전하게 복귀
```
