## 한 줄 요약
`CALL` 바로 다음 위치에 있는 바이트가 정상적인 명령어처럼 안 보이거나 이상한 값으로 디스어셈블 되는 경우, 이는 컴파일러/작성자가 그 자리를 실행할 코드가 아니라 **데이터**(문자열, 점프 테이블 주소, 상수 등)로 의도적으로 배치했거나, 위치 독립 코드(PIC)/셸코드에서 `CALL`을 "현재 실행 주소(RIP)를 알아내는 트릭"으로 사용했기 때문이며, 디스어셈블러가 이걸 구분 못 하고 그냥 다음 바이트부터 기계적으로 디코딩하면서 깨져 보이는 것이다.

## 언제 검색해야 하나
- `call some_func` 바로 다음 줄이 말이 안 되는 명령어(정크처럼 보이는 옵코드)로 디스어셈블 될 때
- 셸코드나 PIC(Position-Independent Code) 분석 중 `call $+5`처럼 다음 명령을 그대로 호출하는 이상한 `CALL`을 만났을 때
- `call` 직후에 `pop rax`, `pop rsi` 같은 명령이 바로 이어지는 패턴을 봤을 때
- 스위치문 컴파일 결과에서 `call` 명령 다음에 정체불명의 오프셋 값 나열이 이어질 때

## 핵심 개념

### CALL의 본질을 이용한 트릭: "GetPC idiom"
REV-0071(CALL)에서 설명했듯, `CALL target`은 **다음 실행할 명령의 주소(반환 주소)를 스택에 PUSH**한 뒤 `target`으로 점프한다. 여기서 중요한 성질은, `CALL`이 그 자체로 항상 함수 호출을 의미하는 게 아니라 "현재 실행 위치(RIP)를 스택에 남기는 부수 효과"를 가진 명령이라는 점이다.

x86(32비트)에는 `RIP` 상대 주소 지정이 없기 때문에(x64에서만 `[rip+offset]`을 직접 쓸 수 있음), 위치 독립적으로 동작해야 하는 셸코드나 32비트 PIC 코드는 "지금 내가 메모리 몇 번지에서 실행되고 있는가"를 알아낼 방법이 필요했다. 그래서 다음과 같은 관용구(idiom)가 널리 쓰인다:

```asm
call    get_eip        ; "다음 명령의 주소"를 스택에 PUSH하고 get_eip로 점프
get_eip:
    pop     eax          ; 방금 스택에 쌓인 반환 주소(=이 pop 명령 자신의 주소)를 EAX로 회수
    ; 이제 EAX = get_eip 레이블의 실제 런타임 주소. 이걸 기준으로 다른 데이터/코드 위치를 상대 계산한다.
```

여기서 `CALL`은 사실상 함수 호출이 아니라 **"현재 주소를 레지스터로 꺼내는 한 줄짜리 트릭"**으로 쓰인 것이다. `RET`으로 돌아오지 않고 `POP`으로 반환 주소를 그냥 일반 데이터처럼 가져가 버리는 게 특징이다.

### 더 흔한 원인: CALL 뒤에 진짜 데이터가 온다
```asm
call    print_error
db      "Invalid input\n", 0    ; 이건 코드가 아니라 문자열 리터럴이다!
next_instruction:
    ...
```
`print_error` 함수가 "자신을 호출한 지점 바로 다음에 있는 데이터(문자열 주소 등)를 인자로 활용"하도록 설계된 경우, 컴파일러/어셈블리 작성자는 `CALL` 바로 뒤에 코드가 아니라 데이터를 배치한다. 함수 내부에서는 반환 주소(스택 맨 위)를 이용해 그 데이터 위치를 계산해서 읽은 뒤, **반환 주소를 데이터 길이만큼 보정해서 진짜 반환할 위치로 조정**한다. 이런 패턴은 옛날 컴파일러(특히 어셈블리로 직접 짠 에러 처리 루틴)나 일부 난독화 기법에서 나타난다.

디스어셈블러(IDA/Ghidra)는 기본적으로 `CALL` 다음 주소도 "당연히 코드겠지"라고 가정하고 계속 명령으로 디코딩을 시도한다. 그 자리가 실제로는 문자열/상수 데이터라면, 디코딩 결과는 의미 없는 옵코드 나열(정크처럼 보이는 명령들)이 된다.

### 점프 테이블 주소 배열도 비슷한 착시를 만든다
`switch`문이 점프 테이블로 컴파일되면, 테이블 자체(주소 값들의 배열)가 코드 섹션 안, 종종 관련 `CALL`이나 간접 `JMP` 근처에 바로 붙어 있는 경우가 있다. 이 역시 "명령어처럼 안 보이는 이상한 바이트 나열"로 보이지만 실제로는 4바이트/8바이트 단위의 순수 주소 데이터다. 자세한 내용은 REV-0441(Switch문 점프 테이블)에서 다룬다.

### IDA/Ghidra가 이걸 어떻게 처리하는가
- IDA는 함수 시그니처 분석이나 사용자의 수동 지정(`D`로 데이터 정의)을 통해 이런 인라인 데이터를 인식하면 자동으로 회색 처리하거나 `db`/문자열로 바꿔 보여준다. 하지만 자동 인식에 실패하면 코드처럼 잘못 디스어셈블된 채로 남는다.
- Ghidra도 마찬가지로, 함수 분석기가 이 패턴을 감지하지 못하면 데이터 영역을 코드로 오인해서 디스어셈블리를 깨뜨릴 수 있다.

## 화면/코드에서 보이는 징후
```asm
; GetPC idiom
call    0x401005          ; 다음 명령 주소로 그냥 점프하는 것처럼 보임(오프셋이 +5뿐)
0x401005: pop eax          ; call 직후 즉시 pop -> GetPC 트릭 신호
```
```asm
; 데이터가 뒤에 붙은 패턴
call    sub_401200
db 'E','r','r','o','r',0    ; IDA에서는 이 부분이 이상한 명령어들(정크)로 보일 수 있음
```

## 가장 먼저 할 것
`CALL` 바로 다음 코드가 이상해 보이면 먼저 두 가지 신호를 확인한다.
1. `CALL` 대상 위치의 **첫 명령이 `POP`인가?** → GetPC idiom 가능성이 매우 높다.
2. `CALL` 대상 함수가 반환 주소를 직접 조작(반환 주소에 어떤 값을 더하거나 그 위치의 데이터를 읽는 코드)하는가? → 데이터가 뒤에 붙은 패턴 가능성.

## 단계별 절차
**1) CALL 대상의 첫 명령 확인**

`call X`를 따라 `X`로 이동해서 첫 줄이 무엇인지 본다. `pop reg`라면 GetPC idiom이다 — 이 경우 그 함수는 사실상 반환하지 않거나(`RET`을 안 씀), 스택에서 반환 주소를 데이터로 꺼내 쓴다는 뜻이니 "이 함수가 뭘 호출하는지" 찾으려 하지 말고 "현재 위치를 구하는 트릭"으로 이해하고 넘어간다.

**2) 호출된 함수가 반환 주소를 어떻게 쓰는지 확인**

함수 내부에서 `[rsp]`(x64) 또는 `[esp]`(x86)를 직접 읽어서 그 주소 근처의 데이터를 참조하는 코드가 있다면, `CALL` 바로 뒤에 데이터가 붙어 있는 패턴이다. 이 함수는 보통 처리 후 반환 주소를 데이터 크기만큼 보정한 뒤 원래 호출자의 다음 코드로 점프한다.

**3) 깨진 디스어셈블리를 데이터로 재정의**

IDA에서 이상하게 디코딩된 영역을 선택하고 `U`(Undefine)를 누른 뒤, 실제 내용에 맞게 `A`(아스키 문자열로 정의) 또는 `D`(바이트/워드/드워드 데이터로 정의)를 적용한다. 그러면 그 뒤에 이어지는 진짜 코드도 올바른 오프셋부터 다시 디스어셈블된다.

**4) 스위치 점프 테이블인지 확인**

간접 `JMP`(`jmp [rax*4 + table]`) 근처에 있는 데이터라면 REV-0441을 참고해서 점프 테이블 패턴인지 확인한다.

## 명령어/단축키
- IDA: `U`(코드/데이터 정의 해제), `C`(코드로 재정의), `A`(아스키 문자열로 정의), `D`(바이트로 정의), `Alt+G`(구조체/배열로 데이터 재정의)
- Ghidra: 해당 영역 우클릭 → "Clear Code Bytes", 이후 우클릭 → "Data" 하위 메뉴에서 원하는 타입 지정
- x64dbg: 덤프 창에서 실제 메모리 바이트를 직접 확인(디스어셈블리와 별개로 raw hex를 보면 코드/데이터 구분에 도움)

## 출력 해석
- `call X` 다음에 `pop reg`가 바로 나오면 → 거의 항상 GetPC idiom. `reg`에 현재 실행 위치(대략 `call` 명령 직후 주소)가 담긴다.
- 정크처럼 보이는 명령 나열이 이어지다가 어느 지점부터 다시 말이 되는 코드로 돌아오면 → 그 사이 구간이 데이터였을 가능성이 매우 높다. 데이터 구간의 끝을 문자열 종료(`0x00`)나 고정 길이로 추정해서 재정의한다.
- Ghidra에서 함수가 이상하게 짧게 끝나거나 코드 흐름이 뚝 끊긴 것처럼 보이면 → 그 함수 뒤에 붙은 인라인 데이터를 함수 본문으로 착각해서 디스어셈블리가 오염됐을 가능성을 의심한다.

## 흔한 실수
- `CALL` 뒤에 오는 모든 바이트를 무조건 코드로 가정하고 디스어셈블리 결과를 그대로 믿는 것 — 특히 셸코드나 오래된 스타일의 에러 처리 루틴에서는 데이터가 섞여 있는 경우가 흔하다.
- GetPC idiom(`call` + `pop`)을 보고 "이 함수는 아무것도 안 하고 그냥 종료되나?"라고 오해하는 것 — 실제로는 RIP/EIP를 구하는 매우 실용적인 트릭이며, 이후 코드에서 그 레지스터를 기준으로 오프셋 계산을 한다.
- 데이터 구간을 코드로 착각해서 강제로 다시 디스어셈블하려다 진짜 코드 시작 위치를 못 찾고 계속 깨진 결과만 보는 것 — 먼저 데이터로 명시적으로 정의(U + A/D)한 뒤에 코드 영역을 다시 찾아야 한다.
- `CALL` 대상 함수가 반환하지 않는다는 걸 모르고 계속 그 함수의 `RET`을 찾으려 하는 것 — GetPC idiom 함수는 `RET` 없이 `POP` 후 `JMP`로 처리를 이어가는 경우가 많다.

## 막혔을 때 다음 체크
- `call` 뒤가 계속 이상하다면 → 대상 함수의 첫 줄이 `pop`인지부터 확인.
- 데이터인지 코드인지 애매하면 → 동적 디버거로 그 지점을 실제로 실행시켜 `RIP`가 그 데이터 구간을 건드리는지(즉 정말 실행되는지) 확인한다. 실행되지 않는다면 데이터가 맞다.
- 점프 테이블처럼 보이면 → REV-0441로 이동.
- 여전히 CALL의 기본 동작 자체가 헷갈리면 → REV-0071(CALL) 복습.

## 미니 예제

**예제 1 — 고전적인 GetPC idiom (32비트 셸코드)**
```asm
call    get_eip
get_eip:
    pop     ebx              ; ebx = get_eip의 실제 런타임 주소
    lea     eax, [ebx+msg-get_eip]  ; ebx를 기준으로 다른 데이터 위치 계산
msg:
    db "Hello", 0
```

**예제 2 — CALL 뒤에 문자열 데이터가 바로 붙은 패턴**
```asm
call    print_msg
db "Error: invalid input", 0
next_code:
    mov     eax, 1

print_msg:
    pop     rsi              ; 반환 주소 = 문자열 시작 주소
    ; rsi가 가리키는 문자열을 출력하는 로직...
    ; 문자열 길이만큼 반환 주소를 보정한 뒤 next_code로 점프(RET 대신 계산된 주소로 jmp)
```

**예제 3 — call $+5 (다음 명령으로 그냥 점프하는 최소 형태)**
```asm
call    $+5        ; 오프셋 0(다음 명령)으로 CALL -> 사실상 "현재 주소를 스택에 남기기"만을 위한 트릭
pop     eax          ; eax = call 다음 주소 = 이 pop 명령 자신의 주소
```

**예제 4 — IDA에서 깨진 디스어셈블리를 데이터로 재정의**
```text
1) 이상하게 디코딩된 바이트 범위를 마우스로 드래그해서 선택
2) 단축키 U (Undefine)
3) 단축키 A (문자열이라면 아스키로 정의) 또는 D (바이트/워드로 정의)
4) 데이터 뒤 실제 코드 시작 위치에 커서를 놓고 C (코드로 정의)
```

## 관련 글
- REV-0071 — CALL: 함수 호출, 반환 주소, 인자 추적
- REV-0072 — RET: 함수 반환과 스택 변화
- REV-0441 — Switch문 점프 테이블(Jump Table) 완전 분석
- REV-0490 — 명령어 하나를 건너뛰고 실행되는 것처럼 보일 때
