## 한 줄 요약
컴파일러의 레지스터 할당기(register allocator)는 각 변수를 어떤 물리 레지스터에 배정할지(또는 레지스터가 부족하면 스택으로 내보낼지)를 컴파일러/버전/최적화 옵션에 따라 다르게 결정하기 때문에, **완전히 같은 로직**이라도 어셈블리에서는 서로 다른 레지스터 이름과 다른 `push`/`pop` 목록으로 나타날 수 있다.

## 언제 검색해야 하나
- 동일한 함수를 다른 컴파일러(GCC vs Clang vs MSVC)나 다른 버전으로 빌드했을 때 로직은 같은데 레지스터 이름이 전부 달라 보일 때
- 함수 프롤로그에서 `push rbx`, `push r12` 처럼 그 함수 로직과 당장 관련 없어 보이는 레지스터를 저장하는 이유가 궁금할 때
- 두 함수(또는 두 버전의 같은 함수)를 diff 떠서 비교하고 싶은데 레지스터 이름 차이 때문에 "완전히 다른 함수"처럼 보일 때
- 지역 변수가 레지스터가 아니라 스택 메모리(`[rbp-0x14]`)에 저장되어 있어서 "왜 레지스터를 안 쓰지"라는 의문이 들 때

## 핵심 개념

### 레지스터 할당이 하는 일
소스코드의 지역 변수는 개수 제한이 없지만, CPU의 범용 레지스터는 x64에서도 16개(RAX, RBX, RCX, RDX, RSI, RDI, RBP, RSP, R8~R15)뿐이고 이 중 일부(RSP 등)는 특수 목적으로 예약되어 있다. 컴파일러는 **레지스터 할당(register allocation)** 단계에서 "어떤 변수를 어떤 물리 레지스터에 넣을지"를 결정한다. 대표적인 알고리즘으로 그래프 컬러링(graph coloring, GCC 계열이 전통적으로 사용)과 선형 스캔(linear scan, 빠른 컴파일이 필요한 JIT 등에서 흔함)이 있다. 어떤 변수를 어떤 레지스터에 배정하느냐는 **동시에 살아있는(live) 변수가 몇 개인지, 코드 순서, 컴파일러의 내부 휴리스틱**에 따라 결정되며, 논리적으로 "정답"이 하나만 있는 게 아니다.

### 왜 컴파일러/버전마다 다르게 보이는가
GCC, Clang, MSVC는 각자 다른 레지스터 할당 알고리즘과 휴리스틱을 쓴다. 같은 컴파일러라도 버전이 바뀌면 내부 휴리스틱이 조정되어 결과가 달라질 수 있다. 그 결과, **완전히 동일한 소스코드**를 세 컴파일러로 각각 빌드하면 세 개의 서로 다른(하지만 의미적으로 동등한) 어셈블리가 나온다 — 어떤 변수가 RAX에 들어가는지 RBX에 들어가는지, 어떤 임시값이 레지스터에 남는지 스택으로 밀려나는지가 전부 다를 수 있다.

### 레지스터가 부족하면: 스필(Spill)
동시에 살아있어야 하는 값의 개수가 사용 가능한 레지스터 개수보다 많으면, 컴파일러는 일부 값을 레지스터가 아니라 **스택 메모리**에 저장해뒀다가 필요할 때 다시 로드한다. 이를 스필(spill)이라 한다.
```asm
mov     [rbp-0x18], eax   ; 레지스터가 부족해서 값을 스택으로 내보냄(spill)
...                        ; 다른 계산들이 레지스터를 많이 씀
mov     eax, [rbp-0x18]   ; 다시 필요해져서 스택에서 로드(reload)
```
스필이 많을수록 코드가 느려지고 길어지므로, 최적화가 잘 된 코드(레지스터가 풍부한 x64에서는 특히)는 스필이 적은 경향이 있다. `-O0`(최적화 없음)에서는 거의 **모든 지역 변수를 스택에 저장**하고 매번 레지스터로 로드/스토어하는 극단적으로 비효율적인 코드가 나오는데, 이것도 크게 보면 "레지스터를 아예 할당하지 않는" 극단적 전략이라 볼 수 있다.

### Caller-saved vs Callee-saved 레지스터
함수 호출을 거치면서 레지스터 값이 보존되어야 하는지 여부는 호출 규약(calling convention)이 정한다.
- **Caller-saved(호출자 저장, volatile)**: 함수 호출 후 값이 바뀔 수 있다고 간주되는 레지스터. 호출자가 값을 유지하고 싶으면 CALL 전에 직접 저장해둬야 한다. x64 SysV/Microsoft 모두 RAX, RCX, RDX, RSI(SysV), RDI(SysV), R8~R11 등이 여기 해당한다(정확한 목록은 REV-0106, REV-0122 참고).
- **Callee-saved(피호출자 저장, non-volatile)**: 함수가 이 레지스터를 쓰려면 **진입 시 저장(push)하고 종료 전 복원(pop)** 해야 한다. RBX, RBP, RSP, R12~R15(SysV/MS 공통), RDI/RSI(Microsoft x64에서 추가로 callee-saved)가 대표적이다.

레지스터 할당기가 함수 안에서 오래 살아있는 변수(예: 루프 전체에서 쓰이는 카운터)를 callee-saved 레지스터에 배정하기로 결정하면, 그 함수는 진입부에서 `push rbx`, `push r12` 같은 코드를 갖게 된다. **이 함수 로직 자체와 rbx/r12가 의미적으로 관련이 있어서가 아니라, 단지 "오래 사는 값을 저장할 안전한 장소"로 그 레지스터를 골랐기 때문**이다.

### 리버싱에서 왜 중요한가
- **함수 diff/유사도 비교**: 두 함수(또는 패치 전후, 버전 전후)를 바이트 단위로 비교하면 레지스터 이름만 바뀌어도 완전히 다른 함수처럼 보인다. 이런 문제를 피하려면 레지스터 이름을 정규화(예: 첫 등장 순서대로 R1, R2, ...로 치환)한 뒤 비교하는 "구조적 diff"가 필요하다. BinDiff 같은 도구가 이런 정규화를 내부적으로 수행한다.
- **컴파일러/버전 지문(fingerprinting)**: 특정 레지스터 할당 패턴이나 프롤로그의 push 순서는 어떤 컴파일러/버전으로 빌드됐는지 추정하는 단서가 되기도 한다.
- **패턴 매칭 시그니처 작성**: YARA 룰이나 시그니처를 만들 때 레지스터 이름까지 고정하면 다른 빌드 옵션에서 매칭이 실패할 수 있다. 와일드카드로 레지스터 부분을 비워두는 게 안전하다.

## 화면/코드에서 보이는 징후
```asm
; 컴파일러 A (GCC -O2)
mov     eax, edi
imul    eax, esi
add     eax, edx
ret
```
```asm
; 컴파일러 B (Clang -O2) - 완전히 같은 소스, 다른 레지스터
mov     ecx, edi
imul    ecx, esi
lea     eax, [rcx+rdx]
ret
```
두 코드는 로직이 100% 동일하다(`a*b+c` 계산 후 반환). 하지만 레지스터 이름과 마지막 덧셈을 `add`로 하는지 `lea`로 하는지가 다르다.

```asm
; 오래 사는 값을 callee-saved 레지스터에 배정한 예
push    rbx                  ; 이 함수에서 rbx를 쓰겠다는 신호
push    r12
...
mov     rbx, rdi              ; 함수 인자를 rbx에 옮겨서 오래 보관
mov     r12, rsi
call    some_other_func       ; 호출 이후에도 rbx/r12 값은 보존됨
add     eax, ebx
...
pop     r12
pop     rbx
ret
```

## 가장 먼저 할 것
1. 함수 프롤로그에서 `push rbx`/`push r12` 같은 코드를 보면, "이 레지스터가 함수 끝까지 어떤 값을 보관하고 있겠구나"라고 예상하고 그 값의 최초 대입 지점을 찾는다.
2. 두 함수를 비교할 때 레지스터 이름이 다르다고 바로 "다른 로직"이라 단정하지 말고, 각 레지스터가 하는 **역할**(어떤 인자/계산 결과를 담고 있는지)을 먼저 맞춰본다.
3. 스택에 저장된 값(`[rbp-0x..]`)을 보면 "레지스터가 부족해서 스필된 값"일 수 있다는 걸 염두에 두고, 그 값이 로드되는 다른 지점도 함께 찾는다.

## 단계별 절차
**1) 함수 프롤로그의 push 목록으로 사용 레지스터 예상**
```asm
push rbp
push rbx
push r12
push r13
sub  rsp, 0x28
```
이 함수는 RBX, R12, R13을 로컬 변수 보관용으로 쓸 가능성이 높다는 걸 미리 알 수 있다. 에필로그에서 반드시 역순으로 `pop`되는지 확인해 균형이 맞는지도 체크한다(REV-0072 RET, REV-0151 스택 불균형 경고 참고).

**2) 레지스터를 "역할" 기준으로 재이름 붙이기**
IDA에서 레지스터 이름을 직접 바꿀 수는 없지만, 지역 변수로 변환(코멘트 또는 Hex-Rays의 변수 이름 변경 `N`)해서 "이 레지스터는 사실 `counter`다"처럼 표시해두면 로직을 따라가기 쉬워진다.

**3) 두 빌드 비교 시 구조적 특징에 집중**
레지스터 이름 대신 다음을 비교 기준으로 삼는다: 상수 값, 분기 개수와 방향, 호출하는 함수 이름, 메모리 접근 패턴(오프셋). 이런 요소가 같다면 레지스터 이름이 달라도 같은 로직일 가능성이 크다.

## 명령어/단축키
- IDA: 함수 프롤로그의 `push` 목록 확인, Hex-Rays 디컴파일 창에서 변수 우클릭 → Rename(`N`)으로 의미 있는 이름 부여
- Ghidra: Decompile 창에서 변수 더블클릭 → Rename Variable
- BinDiff류 도구: 레지스터 이름을 정규화한 구조적 diff를 제공(레지스터 이름 차이에 흔들리지 않는 비교)

## 출력 해석
- 프롤로그의 `push` 개수가 많을수록(레지스터를 많이 저장할수록) 그 함수가 상대적으로 지역 변수/오래 사는 값을 많이 다루는 "무거운" 함수일 가능성이 있다.
- 스택 접근(`[rbp-0x..]`, `[rsp+0x..]`)이 유난히 많다면 레지스터가 부족해서 스필이 많이 일어났다는 뜻이며, 종종 `-O0`이나 지역 변수가 매우 많은 함수에서 흔히 보인다.

## 흔한 실수
- 레지스터 이름이 다르다는 이유만으로 두 함수가 다른 로직이라고 단정하는 것 — 컴파일러/버전 차이만으로도 레지스터 배정은 얼마든지 달라진다.
- `push rbx`가 있는 걸 보고 그 함수가 특별히 `rbx`와 관련된 특수한 동작(예: 어떤 API 호출 규약)을 한다고 오해하는 것 — 대부분은 그냥 "빈 callee-saved 레지스터를 하나 빌려 쓴 것"뿐이다.
- 스택에 저장된 값(스필)을 전역 변수나 구조체 필드로 착각하는 것 — `[rbp-0x..]` 형태는 대개 지역 변수/임시값의 스택 슬롯이다.
- YARA/바이트 시그니처를 만들 때 레지스터 인코딩까지 고정해서, 컴파일러가 바뀌면(레지스터 할당이 달라지면) 매칭이 깨지는 취약한 룰을 작성하는 것.

## 막혔을 때 다음 체크
- 두 버전을 비교하고 싶은데 레지스터 차이 때문에 헷갈린다면 → REV-0464(-O0과 -O2 비교) 방법론을 적용해 먼저 최적화 없는 기준판과 비교한다.
- 값이 스필된 것 같은데 원래 어떤 변수였는지 모르겠다면 → REV-0463(최적화로 사라진 변수 복원)을 참고해 디버거로 실행 중 값을 직접 확인한다.
- 함수 시그니처(인자 개수)가 이상해 보인다면 → REV-0106/REV-0122(호출 규약)를 다시 확인해 어떤 레지스터가 인자용으로 고정되어 있는지 재확인한다.

## 미니 예제
**예제 1 — 같은 로직, 다른 레지스터(컴파일러 차이)**
```c
int f(int a, int b, int c) { return a * b + c; }
```
```asm
; GCC -O2
mov  eax, edi
imul eax, esi
add  eax, edx
ret
```
```asm
; Clang -O2
imul edi, esi
lea  eax, [rdi+rdx]
ret
```

**예제 2 — 오래 사는 값이 callee-saved 레지스터에 배정된 경우**
```c
int accumulate(int *arr, int n) {
    int total = 0;
    for (int i = 0; i < n; i++)
        total += heavy_call(arr[i]);   // 루프 안에서 함수 호출
    return total;
}
```
```asm
push    rbx                 ; total을 담을 레지스터를 보존용으로 미리 확보
push    r12                 ; arr 포인터도 호출 넘어 유지되어야 함
mov     r12, rdi
xor     ebx, ebx            ; total = 0
...
loop_top:
    mov     edi, [r12+rax*4]
    call    heavy_call       ; 호출 후에도 rbx(total), r12(arr)는 그대로 보존됨
    add     ebx, eax
    ...
pop     r12
pop     rbx
ret
```
루프 안에서 함수를 호출하면 caller-saved 레지스터(RAX 등)는 호출 후 값이 보장되지 않으므로, "호출을 넘어 계속 필요한 값"은 컴파일러가 callee-saved 레지스터(RBX, R12 등)에 배정하고 프롤로그/에필로그에서 저장/복원한다.

## 관련 글

- REV-0122 — Microsoft x64 Calling Convention
- REV-0467 — Common Subexpression Elimination이 코드에 남기는 흔적
- REV-0468 — 명령어 스케줄링 때문에 순서가 뒤바뀐 것처럼 보이는 코드
- REV-0464 — -O0과 -O2 컴파일 결과를 나란히 비교하는 법
