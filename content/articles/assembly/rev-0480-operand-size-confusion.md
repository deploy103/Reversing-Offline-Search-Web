## 한 줄 요약
`mov`, `add`, `cmp` 같은 니모닉은 이름이 같아도 실제로 몇 바이트를 다루는지는 **오퍼랜드로 쓰인 레지스터 이름**(`al/ax/eax/rax` 등)이나 **REX.W / 66h 프리픽스**에 의해 결정되며, 특히 x64에서는 "32비트 레지스터에 쓰면 64비트 상위가 자동으로 0으로 지워진다"는 규칙 때문에 초보자가 값을 잘못 추적하는 경우가 많다.

## 언제 검색해야 하나
- 같은 `mov` 명령어인데 어떤 줄은 `eax`, 어떤 줄은 `al`, 어떤 줄은 `rax`를 써서 뭐가 다른지 헷갈릴 때
- `mov eax, ...`를 실행했을 뿐인데 `rax`의 상위 32비트까지 0이 되는 게 이해가 안 될 때
- 오퍼랜드 크기 프리픽스(`66h`)나 REX 프리픽스(`48h` 등)가 붙었다 안 붙었다 하는 이유가 궁금할 때
- 디스어셈블리에서 레지스터 이름 끝 철자(`e` 접두, `r` 접두, `d`/`w`/`b` 접미) 차이를 못 외우겠을 때

## 핵심 개념

### 레지스터 이름과 크기 대응표
x86/x64에서 같은 물리 레지스터라도 몇 바이트를 쓰느냐에 따라 이름이 다르다. 예를 들어 RAX 계열은 다음과 같다.
```
RAX  - 64비트 전체 (8바이트)
EAX  - 하위 32비트 (4바이트)
AX   - 하위 16비트 (2바이트)
AL   - 하위 8비트  (1바이트, 최하위)
AH   - 상위 8비트 중 두 번째 바이트(비트 8~15), x64의 R8~R15 확장 레지스터에는 없음
```
R8~R15(x64에서 추가된 레지스터)는 접미사로 크기를 구분한다.
```
R8   - 64비트    R8D - 32비트    R8W - 16비트    R8B - 8비트
```
이 이름 규칙(REV-0022 참고)을 모르면 `mov eax, ebx`와 `mov rax, rbx`가 "같은 명령어의 다른 표기"가 아니라 **전혀 다른 크기를 다루는 별개의 명령어**라는 걸 놓치기 쉽다.

### 오퍼랜드 크기를 결정하는 3가지 요소
1. **레지스터 이름 자체**: `eax`를 쓰면 32비트 연산, `rax`를 쓰면 64비트 연산.
2. **REX.W 프리픽스**: x64에서 64비트 오퍼랜드를 쓰려면 opcode 앞에 REX 프리픽스(`0x40~0x4F`)의 W 비트가 1이어야 한다. 인코딩상 `48h`가 REX.W가 켜진 최소형이며, `mov rax, rbx`는 실제로 `48 89 D8`처럼 `48`(REX.W)이 붙는다.
3. **66h 오퍼랜드 크기 오버라이드 프리픽스**: 기본 32비트 오퍼랜드를 16비트로 바꾼다. `mov ax, bx`는 `66 89 D8`처럼 `66`이 붙는다.

기본값(프리픽스 없음)은 x64에서 **32비트**다. 그래서 `mov eax, ebx`는 REX 없이 `89 D8` 두 바이트로 끝나지만, `mov rax, rbx`는 REX.W가 필요해 `48 89 D8` 세 바이트가 된다.

### x64의 특수 규칙: 32비트 쓰기는 상위 32비트를 자동으로 지운다
이것이 가장 자주 헷갈리는 부분이다. **64비트 레지스터의 하위 32비트에 쓰기 연산을 하면(예: `mov eax, ...`, `add eax, ...`), 나머지 상위 32비트는 자동으로 0으로 초기화된다.** 이는 x86-64 아키텍처 자체의 규칙이다(8/16비트 쓰기에는 이 규칙이 적용되지 않는다 — `mov al, ...`이나 `mov ax, ...`는 상위 비트를 보존한다).

```asm
mov  rax, 0xFFFFFFFFFFFFFFFF   ; RAX 전체 = 모든 비트 1
mov  eax, 1                    ; EAX = 1을 쓰는 순간 RAX 전체 = 0x0000000000000001
                                ; (상위 32비트가 0으로 자동 클리어됨! 명시적으로 지운 게 아님)
```
반면:
```asm
mov  rax, 0xFFFFFFFFFFFFFFFF
mov  al, 1                     ; AL만 바뀜 -> RAX = 0xFFFFFFFFFFFFFF01 (상위 56비트 보존)
```
이 차이를 모르면 "왜 32비트로만 썼는데 64비트 레지스터 값이 완전히 리셋됐지?"라며 디버거 값을 잘못 해석하게 된다.

### 66h/67h 프리픽스: 오퍼랜드 크기 vs 주소 크기
- `66h`(오퍼랜드 크기 오버라이드): 데이터 크기를 바꾼다(32↔16비트).
- `67h`(주소 크기 오버라이드): 메모리 주소 계산에 쓰이는 레지스터 폭을 바꾼다(예: 64비트 모드에서 32비트 주소 지정 `[eax]` 형태를 쓰게 함). 이 둘은 서로 독립적이며 동시에 붙을 수도 있다.

### CMP/ADD/SUB 등 다른 니모닉에도 동일하게 적용
이 크기 규칙은 `MOV`뿐 아니라 거의 모든 산술/비교 명령어(`ADD`, `SUB`, `CMP`, `AND`, `OR`, `XOR`, `TEST` 등)에 동일하게 적용된다. `cmp eax, 10`과 `cmp al, 10`은 완전히 다른 비교이며, 후자는 하위 1바이트만 비교하므로 상위 바이트에 숨겨진 값 차이를 놓칠 수 있다.

## 화면/코드에서 보이는 징후
- 바로 위/아래 줄은 `eax`인데 어떤 줄만 `ax`나 `al`을 쓴 코드 (크기가 섞인 경우, 보통 구조체 필드나 문자 하나만 다루는 경우)
- `48` 바이트로 시작하는 opcode(REX.W 프리픽스)가 있는 줄과 없는 줄이 섞여 있음
- 디버거 레지스터 창에서 `EAX`를 바꿨는데 `RAX`의 상위 32비트가 0으로 변함
- IDA 디컴파일에서 `(int)`, `(char)`, `(short)` 같은 캐스트가 오퍼랜드 크기 차이를 반영해서 자동으로 붙음

## 가장 먼저 할 것
1. 문제가 되는 레지스터 이름의 접두/접미사를 정확히 읽고 몇 비트인지 REV-0022 표로 확인한다.
2. 32비트 레지스터에 값을 쓴 직후라면, 64비트 상위가 자동으로 지워졌다는 것을 전제로 다음 코드를 읽는다.
3. REX 프리픽스(`4x`로 시작하는 바이트)가 있는지 헥스뷰로 확인해서 64비트 연산인지 아닌지를 명확히 한다.

## 단계별 절차
**1) 레지스터 크기표로 이름 확인**

`al/ax/eax/rax`, `r8b/r8w/r8d/r8` 같은 이름 접두/접미사를 REV-0022(32비트와 64비트 레지스터 차이) 표와 대조한다.

**2) 32비트 쓰기의 자동 클리어 규칙 적용**

디버거로 값을 추적할 때, `mov eax, ...` 직후에는 반드시 `RAX` 상위 32비트가 0이 됐다고 가정하고 다음 로직을 읽는다.

**3) REX 프리픽스 유무로 진짜 크기 검증**

헥스뷰나 objdump로 원본 바이트를 보고 `48`(REX.W=1)이 있으면 64비트, 없으면(그리고 66h도 없으면) 32비트로 판단한다.

**4) 디컴파일 결과의 타입 캐스트와 교차 확인**

IDA F5 결과에서 변수가 `int`, `__int64`, `char`, `short` 등으로 나오면 이는 어셈블리의 레지스터 크기를 반영한 것이므로, 오퍼랜드 크기 판단이 맞았는지 검증하는 데 쓸 수 있다.

## 명령어/단축키
- IDA: 레지스터 위에 마우스를 올리면 툴팁으로 현재 크기/값 확인, `Alt+M` 등으로 헥스뷰 열어 원본 바이트 확인
- x64dbg: Registers 창에서 RAX를 우클릭 → "Show all"로 EAX/AX/AL 서브필드 값을 동시에 확인 가능
- GDB: `p/x $rax`, `p/x $eax` 각각 출력해서 크기별 값 비교, `info registers rax`
- objdump: `objdump -d -M intel <binary>` 원본 바이트 열에서 `48` 프리픽스 유무 확인

## 출력 해석
- `mov eax, 1` 실행 직후 `RAX`가 정확히 `0x0000000000000001`로 보이면 정상 동작(자동 상위 클리어)이다 — 버그가 아니다.
- `mov al, 1` 실행 직후 `RAX`의 나머지 바이트가 그대로 남아 있으면 이것도 정상이다(8/16비트 쓰기는 상위를 보존).
- REX.W가 있는데도 결과가 32비트처럼 보인다면 프리픽스 해석 자체를 잘못했을 가능성이 있다 — REV-0477 절차로 프리픽스를 다시 분해한다.

## 흔한 실수
- x64에서 `mov eax, ...`가 상위 32비트를 지운다는 규칙을 몰라서, 디버거에서 RAX 값이 "갑자기 줄어든 것"을 버그나 다른 명령어의 부작용으로 오해하는 것.
- 8/16비트 쓰기(`mov al, ...`, `mov ax, ...`)도 32비트와 똑같이 상위 비트를 지운다고 착각하는 것 — 이 규칙은 **오직 32비트 쓰기에만** 적용된다.
- REX 프리픽스가 없으면 무조건 "구식 32비트 코드"라고 단정하는 것 — x64 모드에서도 기본(REX 없음) 오퍼랜드 크기가 32비트일 뿐, 여전히 64비트 모드에서 실행되는 정상 코드다.
- 레지스터 이름의 접두사(`e`, `r`)와 접미사(`b`, `w`, `d`, 없음)를 혼동해서 R8D를 32비트가 아니라 64비트로 잘못 읽는 것.

## 막혔을 때 다음 체크
- 레지스터 이름/크기 전체 표가 다시 필요하면 → REV-0022(32비트와 64비트 레지스터 차이)
- 프리픽스 자체의 원리가 궁금하면 → REV-0474(명령어 프리픽스(REX, 66h, F2h/F3h)가 붙는 이유 개요)
- 명령어 바이트 길이 계산이 같이 헷갈리면 → REV-0477(명령어 길이가 이상하게 길게 잡힐 때)
- MOV 자체의 기본 동작을 다시 보고 싶으면 → REV-0039(MOV: 값 복사와 레지스터 메모리 이동)

## 미니 예제
**예제 1 — 32비트 쓰기의 자동 상위 클리어**
```asm
mov  rax, 0x1122334455667788   ; RAX = 0x1122334455667788
mov  eax, 0x9ABCDEF0           ; EAX만 썼을 뿐인데...
; 실행 후: RAX = 0x000000009ABCDEF0  (상위 32비트가 0으로 사라짐)
```
```c
// C에서 대략적인 느낌 (실제로는 CPU 레벨 규칙)
uint64_t rax = 0x1122334455667788ULL;
rax = (uint32_t)0x9ABCDEF0;   // 상위 32비트가 0으로 확장됨
```

**예제 2 — 8비트 쓰기는 상위를 보존**
```asm
mov  rax, 0x1122334455667788
mov  al, 0xFF
; 실행 후: RAX = 0x11223344556677FF  (하위 1바이트만 바뀜, 나머지는 그대로)
```

**예제 3 — REX.W 유무에 따른 인코딩 차이**
```asm
89 D8            ; mov eax, ebx      (REX 없음, 32비트)
48 89 D8         ; mov rax, rbx      (REX.W=1, 64비트)
66 89 D8         ; mov ax, bx        (66h 프리픽스, 16비트)
```
같은 ModRM 바이트(`D8`)를 공유하지만 프리픽스만으로 완전히 다른 크기의 연산이 된다.

## 관련 글
- REV-0022 — 32비트와 64비트 레지스터 차이
- REV-0474 — 명령어 프리픽스(REX, 66h, F2h/F3h)가 붙는 이유 개요
- REV-0477 — 명령어 길이가 이상하게 길게 잡힐 때
- REV-0039 — MOV: 값 복사와 레지스터 메모리 이동

## 출처/검증

- REX 프리픽스 인코딩과 W/R/X/B 비트: 동일 매뉴얼 Volume 2A, "2.2.1 REX Prefixes" 기준.
