## 한 줄 요약
드림핵 Silver 4 "Long Sleep"은 공개된 상세 write-up을 이번 조사에서 찾지 못했으므로, 이 글은 문제 이름과 Dreamhack 워게임에 실제로 존재하는 "긴 대기 시간을 패치로 우회해야 하는" 유형의 다른 문제들(예: 실제 시간 기준 대기를 요구하는 유형)에서 관찰되는 일반적 패턴을 근거로 한 추정 절차이며, 구체적인 검증 상수나 정답은 서술하지 않는다.

## 언제 검색해야 하나
- 프로그램을 실행하면 곧바로 응답이 멈추고, 실제로 몇 초~몇 분(혹은 그 이상)을 기다려야 다음 동작이 일어나는 것처럼 보일 때
- IDA/Ghidra에서 `Sleep`(Windows) 또는 `sleep`/`nanosleep`(Linux) 호출이 눈에 띄고, 그 값이 매우 큰 상수이거나 시간을 누적해서 검사하는 코드가 있을 때
- "그냥 실제로 기다리면 언젠가 플래그가 나오긴 하겠지만 그럴 수는 없다"는 상황이라 우회/패치가 필요하다고 느낄 때

## 핵심 개념

### Dreamhack 워게임에 존재하는 "긴 대기" 유형 문제의 일반적 구조
Dreamhack 워게임에는 실제로 "프로그램이 365일 같은 비현실적인 시간이 지나야 플래그를 출력하도록 만들어져 있고, 이를 패치해서 즉시 플래그를 받아내야 하는" 유형의 문제가 존재한다(예: "Simple Patch Me"). "Long Sleep"이라는 이름 역시 유사한 계열로, 프로그램이 한 번 또는 여러 번의 `sleep` 호출을 통해 현실적으로 기다릴 수 없는 시간을 만들어 놓고, 이 대기를 실제로 견디는 대신 코드/레지스터를 조작해서 우회하는 것이 목표일 가능성이 높다. 다만 실버 티어라는 점에서, 단순히 sleep 인자 하나를 줄이는 것보다 한 단계 더 나아간 장치(예: 실제 경과 시간을 별도로 검증하는 안티패치 체크, 또는 sleep을 여러 번 나눠서 호출하며 매번 검증하는 구조)가 있을 가능성을 열어두어야 한다.

### 단순 sleep 인자 패치가 막혀 있을 가능성
초급 문제라면 `sleep(매우 큰 수)`의 인자를 디버거에서 그냥 줄이거나, 호출 자체를 NOP 처리하면 끝나는 경우가 많다. 그러나 실버 티어에서는 프로그램이 `sleep` 전후로 `GetTickCount`/`QueryPerformanceCounter`(Windows) 또는 `time()`/`clock_gettime()`(Linux) 같은 함수로 실제 경과 시간을 다시 측정해서, "sleep을 건너뛰었는지"를 검증하는 안티치트성 코드가 추가돼 있을 수 있다. 이 경우 sleep 인자만 줄이면 경과 시간 검증에서 걸려 실패 처리될 수 있으므로, sleep 인자와 시간 측정 로직을 함께 찾아 둘 다 대응해야 한다.

### 우회 전략의 두 갈래
1. **인자/레지스터 패치**: `sleep`/`Sleep` 호출 직전에 인자를 줄이는 방식. 시간 재검증이 없다면 이것만으로 충분하다.
2. **시간 함수 자체를 후킹/패치**: 경과 시간 재검증이 있다면, `GetTickCount`/`time()` 같은 시간 조회 함수의 반환값을 디버거에서 조작하거나, 해당 호출 이후의 비교 분기를 강제로 "통과" 쪽으로 패치하는 방식이 필요하다. REV-0572(GetTickCount/QueryPerformanceCounter 안티디버그)에서 다루는 시간 측정 우회 기법이 그대로 적용될 수 있는 지점이다.

## 화면/코드에서 보이는 징후
- 실행 즉시 아무 출력도 없이 응답이 없는 상태가 이어진다.
- IDA Imports에 `Sleep`/`sleep`/`nanosleep`이 보이고, 호출 직전 인자가 큰 상수(예: 수만~수백만 밀리초)이거나 반복문 안에서 누적되는 형태다.
- `Sleep` 호출 전후로 시간 조회 함수(`GetTickCount`, `QueryPerformanceCounter`, `time`, `clock`)가 쌍으로 등장해 차이를 비교하는 코드가 있다.
- 여러 개의 `sleep` 호출이 반복문 안에 있어, 한 번만 우회해서는 전체 대기 시간이 줄지 않는 구조로 보인다.

## 가장 먼저 할 것
IDA/Ghidra에서 `Sleep`/`sleep` 계열 함수의 모든 호출부를 Xref로 찾아 몇 군데에서 호출되는지, 인자가 고정값인지 계산된 값인지 먼저 파악한다. 그다음 그 주변에 시간 측정 함수가 함께 있는지 확인해서, 이 문제가 "단순 인자 패치"로 끝나는 유형인지 "시간 재검증까지 있는" 더 복잡한 유형인지를 구분한다.

## 단계별 절차
1. `file`/`checksec`(ELF) 또는 PE-bear/DIE(Windows)로 플랫폼과 보호 기법을 먼저 확인한다.
2. IDA/Ghidra Imports에서 `Sleep`/`sleep`/`nanosleep`을 찾고 Xref로 모든 호출부를 나열한다.
3. 각 호출부의 인자가 상수인지, 변수(반복 누적)인지 확인한다.
4. 호출부 주변(전후 몇 줄)에서 시간 조회 함수 호출이 있는지 확인한다.
5. 시간 재검증이 없다면 x64dbg/GDB로 각 sleep 호출 직전에 브레이크포인트를 걸고 인자 레지스터 값을 작은 값으로 강제 변경한다.
6. 시간 재검증이 있다면 그 비교 로직(경과 시간이 기대치 이상인지 확인하는 `cmp`/`jl`/`jge` 등)을 찾아, REV-0572 절차를 참고해 시간 조회 함수의 반환값 또는 비교 분기 자체를 패치한다.
7. 모든 대기/검증 지점을 통과할 때까지 2~6단계를 반복하며, 최종적으로 플래그 출력 경로에 도달하는지 확인한다.

## 명령어/단축키
```bash
# Linux 예시
objdump -d ./long_sleep | grep -A3 "call.*sleep"
gdb ./long_sleep
(gdb) b sleep
(gdb) r
(gdb) p $rdi        # sleep 인자 확인
(gdb) set $rdi = 1
(gdb) c
```
```text
Windows 예시
x64dbg: Symbols 탭에서 Sleep 검색 → 호출부로 이동 → F2로 브레이크포인트 → F9 실행 → 레지스터 창에서 ECX/RCX(첫 인자) 확인 후 값 수정
```

## 출력 해석
- sleep 인자를 줄인 뒤에도 프로그램이 즉시 "시간이 부족하다"는 취지의 메시지를 낸다면, 별도의 시간 재검증 로직이 있다는 뜻이므로 시간 조회 함수 쪽을 추가로 봐야 한다.
- 여러 sleep 호출이 반복문 안에 있는데 한 번만 패치했다면, 전체 대기 시간의 일부만 줄어든 것이므로 반복문의 조건 자체(반복 횟수)를 확인해 조건을 만족시키거나 반복문을 빠져나오게 만드는 패치가 필요할 수 있다.
- 시간 조회 함수의 반환값을 조작했는데도 검증이 실패한다면, 프로그램이 두 번 이상 시간을 측정해서 서로 비교(예: 시작 시각과 끝 시각의 차이)하는 구조일 수 있으므로 두 측정 지점 모두를 일관되게 조작해야 한다.

## 흔한 실수
- sleep 인자 하나만 줄이고 시간 재검증 로직의 존재 가능성을 확인하지 않아 "패치했는데도 왜 안 되지"라며 헤매는 것.
- 실제로 프로그램을 오래 기다리게 두고 다른 작업을 하다가 디버깅 세션이 타임아웃되거나 시스템이 절전 모드로 들어가 프로세스가 멈추는 것을 놓치는 것.
- Windows `Sleep`(대문자, 밀리초 단위)과 Linux `sleep`(소문자, 초 단위)의 단위 차이를 혼동해 인자 값을 잘못 해석하는 것.
- 반복문 안에 있는 sleep 호출을 한 번만 우회하고 전체가 다 우회됐다고 착각하는 것.

## 막혔을 때 다음 체크
- 시간 측정 함수 자체가 안티디버깅 목적인지 확인이 필요하다면 → REV-0572 GetTickCount/QueryPerformanceCounter 안티디버그
- sleep 자체가 안티디버깅/안티샌드박스 용도로 쓰이는 전형적 패턴을 더 알고 싶다면 → REV-0573 Sleep 남용과 안티디버깅/안티샌드박스 기법
- 비슷하게 sleep을 다루지만 난수 비교까지 결합된 문제라면 → REV-1047 [Write-up] randzzz
- 패치 후 실행이 깨지는 문제를 겪는다면 → REV-0601 x64dbg 패치 후 저장했는데 실행하면 크래시 날 때

## 미니 예제
```c
// 긴 대기 + 재검증 구조 예시(추정 재구성, 실제 Long Sleep 코드 아님)
time_t start = time(NULL);
sleep(100000000);            // 비현실적으로 긴 대기(단순 패치 대상)
time_t end = time(NULL);
if (end - start < 100000000) {   // 대기를 건너뛰었는지 재검증
    puts("too fast, no flag");
    return 1;
}
puts("here is your flag...");
```
이런 "대기 + 경과시간 재검증" 이중 구조가 실제로 있다면, sleep 인자만 줄이는 패치로는 통과할 수 없고 `time()` 반환값 또는 비교 분기 자체를 조작해야 한다는 것이 이 글에서 제시하는 핵심 추정이다.

## 출처/검증
- "Long Sleep"이라는 정확한 제목의 write-up이나 공식 풀이는 이번 조사(WebSearch/WebFetch, 2026-09-10)에서 찾지 못했다. Dreamhack 워게임에 "Simple Patch Me"처럼 비현실적으로 긴 대기 시간을 패치로 우회해야 하는 문제가 실제로 존재한다는 점은 검색 결과로 확인했으나, 이는 Long Sleep과 별개의 문제다.
- 이 글의 내용은 문제 이름(Long Sleep)과 Dreamhack 워게임에 존재하는 "긴 대기 우회" 유형 문제들의 일반적 패턴에서 유추한 추정 절차이며, 실제 Long Sleep 바이너리를 분석한 결과가 아니다. 검증 상수, 정확한 시간 값, 플래그는 확인하지 못했고 지어내지 않았다.
