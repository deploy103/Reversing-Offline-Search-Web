## 한 줄 요약
rev-basic-5는 입력의 인접한 두 바이트를 더한 값(`input[i] + input[i+1]`)이 고정 배열 값과 같아야 하는 유형이라, 변수 하나씩 바로 구할 수 없는 대신 마지막 바이트가 널 바이트(0)라는 사실을 실마리로 삼아 배열 끝에서부터 역순으로 하나씩 값을 확정해 나가야 한다.

## 언제 검색해야 하나
- 드림핵 rev-basic-5 검증 함수에서 `*(a1+i+1) + *(a1+i) == byte_140003000[i]` 처럼 인접한 두 원소를 더하는 식을 만났는데, 미지수가 두 개씩 얽혀서 바로 하나씩 못 구할 때
- 앞의 XOR 문제(REV-1004)처럼 한 인덱스에 하나의 값만 걸려 있는 게 아니라서 "어디서부터 손을 대야 할지" 감이 안 잡힐 때
- 배열의 마지막 값이 왜 0으로 끝나는지, 그게 왜 실마리가 되는지 이해가 안 될 때

## 핵심 개념
지금까지의 문제들은 인덱스 `i` 하나에 대해 입력 바이트 하나만 결정하면 되는 식이었다. rev-basic-5는 다르다. 검증 함수는 `for (i = 0; i < 0x18; ++i)`(0x18 = 24) 루프를 돌며 `입력[i] + 입력[i+1] == byte_140003000[i]`인지 확인한다. 즉 하나의 식에 두 개의 미지수(`입력[i]`, `입력[i+1]`)가 동시에 들어 있어서, 이 식 하나만 봐서는 어느 쪽도 바로 결정할 수 없다.

이럴 때 쓰는 전략이 "경계 조건에서 시작해 역방향으로 확정해 나가는 것"이다. 입력 버퍼는 C 문자열이므로 실제 정답 길이 다음 바이트는 반드시 0(널 바이트)이어야 한다. 그리고 아스키 문자는 항상 0 이상의 값이다(음수가 될 수 없다). 이 두 가지 제약을 결합하면, 배열의 마지막 항 근처에서 "두 값을 더해서 특정 값이 되는데 한쪽이 반드시 0이어야 한다"는 조건이 성립하는 지점을 찾을 수 있고, 거기서부터 시작해 하나씩 이전 값을 역산해 나가면 전체 24바이트를 순서대로 채울 수 있다. 이는 REV-0218에서 다루는 "길이 검증부터 역추적하는" 접근과 REV-0200의 덧셈 기반 변환 역산을 함께 적용한 사례에 해당한다.

## 화면/코드에서 보이는 징후
- 실행 흐름은 이전 문제들과 동일: `Input : ` → 입력 → `Correct`/`Wrong`.
- 검증 함수 디컴파일 결과에 `if (*(a1 + i + 1) + *(a1 + i) != byte_140003000[i]) return 0;` 형태의 코드가 24회 반복된다.
- `byte_140003000` 배열의 마지막 값이 유난히 작은 수(예: 0에 가까운 값)로 끝나는 경우가 많다.

## 가장 먼저 할 것
DIE로 파일 확인 후 IDA에서 검증 함수를 F5로 디컴파일해 정확한 수식과 반복 횟수를 확인한다. 그다음 `byte_140003000` 배열 전체를 Hex View에서 순서대로 받아 적는다. 값을 다 받아 적었다면 곧바로 "마지막 값부터 역으로 풀 수 있는가"를 종이에 몇 개만 손으로 시도해보고, 규칙이 보이면 파이썬 스크립트로 자동화한다.

## 단계별 절차
1. DIE로 파일 확인, 실행해서 입출력 문구 확인.
2. IDA에서 검증 함수를 F5로 디컴파일, 정확한 인덱스 범위와 덧셈 식을 확인.
3. `byte_140003000` 배열 24개 값을 Hex View에서 순서대로 추출.
4. 아스키 문자는 음수가 될 수 없다는 제약과, 문자열이 널 바이트로 끝난다는 제약을 이용해 배열 끝 쪽 두 항의 관계부터 확정한다.
5. 확정된 값을 기준으로 그 앞의 식에 대입해 하나씩 역방향으로 풀어 나간다.
6. 24바이트를 모두 채웠으면 16진수 문자열로 조합해 CyberChef의 From Hex 기능이나 파이썬 `bytes.fromhex(...)`로 아스키 문자열로 변환한다.
7. 별도로 같은 역산 로직을 C나 Python으로 다시 구현해 앞쪽 식부터 순서대로 검증해보는 것도 실수를 줄이는 방법이다.
8. 도출한 문자열을 실제로 입력해 `Correct`가 나오는지 확인한다.

## 명령어/단축키
- IDA: `F5`(디컴파일), Hex View에서 배열 주소로 이동해 바이트 값 확인.
- CyberChef: "From Hex" 레시피로 16진수 문자열을 바로 아스키로 변환.
- Python: `bytes.fromhex('41 6c 6c...'.replace(' ', '')).decode()`.

## 출력 해석
`*(a1+i+1) + *(a1+i) != byte_140003000[i]`라는 조건에서 `!=`가 성립하면(즉 다르면) 즉시 0을 반환하고 함수가 끝난다. 배열 값 중 마지막 항이 예를 들어 `0x00`이라면, "입력의 마지막 두 바이트를 더한 값이 0이어야 한다"는 뜻이다. 아스키 문자가 음수일 수 없으므로 두 값 다 0보다 클 수 없고, 결국 두 값 모두 0(널 바이트)이라는 결론이 나온다. 이렇게 한쪽 끝을 확정하면, 그 값을 다음 식(한 인덱스 앞)에 대입해 나머지 미지수를 순서대로 풀 수 있다.

## 흔한 실수
- 미지수가 두 개씩 얽힌 식을 앞에서부터(인덱스 0부터) 풀려고 시도하다가 항상 정보가 부족해 막히는 것 — 경계 조건이 있는 쪽(배열 끝)부터 풀어야 한다.
- 아스키 문자가 음수일 수 없다는 제약을 놓쳐서, 두 값의 조합 후보를 지나치게 넓게 잡아 여러 경우의 수를 다 시도해야 하는 상황을 만드는 것.
- 16진수로 조합한 값을 문자열로 바꿀 때 바이트 순서를 거꾸로 넣어 전혀 다른 문자열이 나오는 것.
- 배열 크기(0x18 = 24)를 반복 횟수와 정답 길이 그대로 받아들이지 않고 1개 어긋나게 세어 마지막 문자를 놓치는 것.

## 막혔을 때 다음 체크
- 미지수 하나짜리 XOR 수식이 궁금하면 REV-1004(rev-basic-3)를 먼저 복습한다.
- "길이 검증부터 역추적"하는 일반적인 방법이 궁금하면 REV-0218을 참고한다.
- 다음 문제인 rev-basic-6의 치환 테이블 방식은 REV-1007을 참고한다.

## 미니 예제
```python
table = [...]  # byte_140003000에서 읽은 24개의 값
n = len(table)
buf = [0] * (n + 1)  # buf[n]은 항상 0(널 바이트)으로 가정

for i in range(n - 1, -1, -1):
    # table[i] == buf[i] + buf[i+1]
    buf[i] = table[i] - buf[i + 1]

flag = ''.join(chr(b) for b in buf[:-1])
print(flag)
```
`buf[n]`을 0으로 고정하고 배열 끝에서부터 거꾸로 `buf[i] = table[i] - buf[i+1]`을 적용하면, 인접한 두 미지수가 얽힌 식이라도 순서대로 하나씩 풀려나간다.
