## 한 줄 요약
"mix-compare"(Bronze 1)의 공개 write-up은 찾지 못했지만, 이름 자체가 "여러 비교 방식이 섞여 있다"는 것을 직접적으로 암시하므로, 하나의 검증 로직이 아니라 `strcmp`/`memcmp`/문자별 루프/산술 비교 등 서로 다른 비교 수단이 함께 쓰인 문제로 접근하는 것이 합리적인 출발점이다.

## 언제 검색해야 하나
- IDA/Ghidra로 `main`을 열었는데 비교 관련 함수(`strcmp`, `memcmp`)와 직접 짠 for 루프 비교가 동시에 보여서 어느 것부터 봐야 할지 헷갈릴 때
- Bronze 1이라 쉬울 거라 생각했는데 조건문이 예상보다 많이 섞여 있어서 전체 로직을 한 번에 이해하기 어려울 때
- "mix"라는 이름 때문에 무슨 암호화가 섞인 문제인지, 단순히 비교 방식이 여러 개인 문제인지 구분이 안 될 때

## 핵심 개념
검색 결과 "mix-compare"라는 정확한 이름의 드림핵 문제를 다룬 외부 write-up은 확인되지 않았다. 다만 드림핵 커뮤니티 포럼에는 "Breakpoint Oracle"과 "Compare Oracle" 취약점을 다루는 글이 존재하는데, 이는 검증 로직이 여러 단계로 나뉘어 있을 때 각 단계에서 브레이크포인트를 걸어 어디까지 맞았는지(Oracle) 알아낼 수 있다는 리버싱 문제 설계상의 약점을 설명하는 내용이다. "mix-compare"라는 이름과 방향성이 겹치는 주제이지만, 이 글이 "mix-compare" 문제 자체를 설명하는 것은 아니므로 직접적인 정답 정보로 사용할 수 없다.

이름에서 유추할 수 있는 합리적인 가정은 다음과 같다.

- "mix"는 여러 종류의 비교 연산(문자열 비교, 정수 비교, 비트 연산 비교 등)이 한 프로그램 안에 섞여 있다는 뜻으로 해석할 수 있다.
- "compare"는 그 자체로 조건 분기(`cmp`, `test` 이후 `jz`/`jnz`)가 핵심이라는 것을 알려준다.
- 이런 유형의 문제는 보통 입력 문자열의 각 부분(앞 4바이트는 `strcmp`, 뒤 4바이트는 산술 연산 등)을 다른 방식으로 검증하도록 짜여 있어서, 코드 전체를 한 번에 이해하려 하지 말고 비교가 일어나는 지점마다 하나씩 분리해서 분석하는 것이 효율적이다.
- 만약 검증 로직이 앞서 언급한 Breakpoint Oracle 취약점을 그대로 갖고 있다면, 정답을 몰라도 각 비교 지점에 브레이크포인트를 걸고 입력을 한 글자씩 바꿔가며 "다음 비교까지 도달하는지"를 관찰하는 것만으로 답을 한 글자씩 알아낼 수도 있다.

## 화면/코드에서 보이는 징후
- `main` 또는 검증 함수 내부에 `strcmp`/`memcmp` 호출과 직접 작성된 비교 루프(`for`+`cmp`)가 혼재
- 입력 문자열의 서로 다른 구간마다 다른 종류의 조건 분기가 나타남
- 조건을 하나 통과할 때마다 다음 비교로 넘어가는 것이 코드 흐름에서 뚜렷하게 보임(Breakpoint Oracle에 취약한 구조일 가능성)

## 가장 먼저 할 것
`main`(또는 진입점 근처의 검증 함수)에서 사용되는 모든 비교 관련 호출과 분기를 먼저 나열한다. 몇 종류의 비교가 있는지, 입력의 어느 구간을 대상으로 하는지부터 표로 정리하면 "mix"된 로직을 분리해서 볼 수 있다.

## 단계별 절차
1. IDA/Ghidra에서 `main`과 하위 함수의 모든 `cmp`/`test`/`strcmp`/`memcmp` 호출을 나열
2. 각 비교가 입력 문자열의 어느 바이트 구간을 대상으로 하는지 표로 정리
3. 가장 앞쪽 비교부터 x64dbg로 브레이크포인트를 걸고 입력을 바꿔가며 어디까지 통과하는지 관찰(Compare Oracle 방식)
4. 통과 조건을 하나씩 확정해가며 전체 입력을 재구성
5. 마지막 비교까지 통과하는 입력으로 최종 실행해 플래그 확인

## 명령어/단축키
```text
IDA: Alt+T(텍스트 검색)으로 cmp/test 인스트럭션 검색은 직접 지원 안 되므로 그래프 뷰(Space)로 분기 구조 확인
x64dbg: Ctrl+G(주소 이동) → F2(브레이크포인트) → F9(Run) → 레지스터/스택 창에서 비교 대상 확인
```

## 출력 해석
브레이크포인트를 각 비교 지점에 걸었을 때, 어떤 입력에서 다음 비교까지 도달하고 어떤 입력에서 그 자리에서 멈추는지를 기록해두면 정답을 한 조각씩 좁혀나갈 수 있다. 이것이 "Compare Oracle"이라 불리는 정보 노출 패턴이다.

## 흔한 실수
- 여러 비교 방식이 섞여 있다는 것을 모르고 첫 번째 비교(`strcmp`)만 통과시키면 끝이라고 생각하는 것
- Breakpoint Oracle 방식으로 답을 좁혀나가는 대신 무작정 완전한 로직 역산을 시도해 시간을 오래 쓰는 것
- 입력 구간별로 다른 검증이 적용된다는 것을 놓치고 하나의 통일된 알고리즘으로 착각하는 것

## 막혔을 때 다음 체크
- 비교 종류별 패턴 자체가 헷갈리면 → REV-0196 strcmp 기반 Flag 검증 패턴, REV-0197 memcmp 기반 Flag 검증 패턴, REV-0198 문자별 for 루프 검증 패턴
- 여러 알고리즘이 순서대로 이어지는 문제 전체 전략이 궁금하면 → REV-0911 여러 알고리즘이 순차적으로 합성된 문제 풀어내기
- x64dbg 브레이크포인트 조작이 서툴다면 → REV-0281 x64dbg 핵심 단축키와 명령 치트시트

## 미니 예제
```c
// 이름에서 유추한 예시 구조(실제 코드 아님)
if (strcmp(buf, "ABCD") != 0) fail();      // 앞 4바이트: 문자열 비교
if ((buf[4] ^ buf[5]) != 0x11) fail();     // 뒤쪽: 비트 연산 비교
if (atoi(buf + 6) != 1234) fail();         // 마지막: 정수 비교
```
이 예제는 "mix"라는 이름에서 유추한 가상의 구조이며, 실제 "mix-compare" 바이너리의 코드가 아니다.
