## 한 줄 요약
"legacyopt"는 이름 그대로 "오래된 최적화 기법"(Duff's Device로 추정되는 루프 언롤링)을 암호화 로직에 숨긴 문제이며, 암호화 알고리즘 자체를 정적으로 완전히 복원하지 않고도 "입력 한 글자를 바꾸면 출력의 그 위치부터만 값이 바뀐다"는 성질을 이용해 실행 파일을 오라클(oracle)처럼 두드려 플래그를 한 글자씩 복구할 수 있다.

## 언제 검색해야 하나
- 드림핵에서 "legacyopt"를 열었는데 output.txt(암호문 Hex)와 실행 파일만 주어지고 별다른 설명이 없을 때
- 입력 길이와 출력 Hex 문자열 길이 사이에 어떤 배수 관계가 있는지 확인하고 싶을 때
- 암호화 함수를 IDA로 열어봤는데 반복문이 이상하게 풀려있어서(언롤링) 로직을 눈으로 따라가기 힘들 때
- "정적으로 완전히 분석하지 않고도 풀 수 있는 방법이 있을까"를 찾고 있을 때

## 핵심 개념
이 문제는 원래 Dreamhack CTF Season 6 Round #8(Div2)의 reversing 카테고리 문제로 출제되었고(290점), 이후 상시 워게임(Bronze 2)으로 재등록된 것으로 보인다. 문제 설명에는 "Good ol' days of optimization..."라는 문구가 붙어 있고, 플래그 포맷은 `DH{...}` 형태다. 배포되는 파일은 실행 파일과, 미리 정해진 정답 플래그를 암호화해 둔 결과(output.txt, Hex 문자열)이다.

핵심 관찰은 두 가지다.
1. **길이 관계**: 입력 문자 수와 출력 Hex 문자열 길이 사이에 고정된 배수 관계가 있다. 참고한 풀이에서는 output.txt가 78자(Hex)였고, Hex 2글자가 원문 1바이트에 대응하므로 원래 평문(플래그)의 길이는 78 ÷ 2 = 39바이트로 추정할 수 있었다.
2. **선형/스트림 성질**: 암호화 함수가 입력의 앞부분만 바꿔도 출력의 뒷부분 전체가 요동치는 "블록 암호"라면 이 공격은 안 통한다. 그런데 이 문제는 앞의 몇 글자만 정답(`DH{`)과 일치시켜도 암호문의 앞부분 Hex가 그대로 일치하는 것을 확인할 수 있었다. 즉, i번째 출력 바이트는 i번째까지의 입력에만 의존하는 **스트림 암호형/순차 처리형** 구조라는 뜻이다. 이런 구조라면 한 글자씩 정답을 확정해나가는 오라클 공격이 가능하다.

문제 이름과 참고한 풀이에서 최종적으로 얻은 플래그 문구(`Duffs_Device_but_use_memcpy_instead`)로 볼 때, 내부적으로 Duff's Device(반복문을 여러 갈래로 나누어 언롤링하는 고전적인 최적화 기법, 원래는 `memcpy`류 반복 복사를 빠르게 하기 위해 쓰였다)를 응용해 바이트를 처리하는 것으로 추정된다. 다만 이 구조 자체를 IDA로 완전히 손으로 복원하지 않고도, 아래처럼 실행 파일을 반복 실행시켜 정답을 알아내는 방식이 훨씬 빠르다.

## 화면/코드에서 보이는 징후
- 실행 파일을 실행하면 표준입력으로 문자열을 받고, 표준출력(또는 파일)으로 Hex 문자열을 뱉는다.
- IDA에서 암호화 함수를 보면 `switch`문처럼 나뉜 여러 개의 유사한 코드 블록이 연속으로 나열되어 있다(Duff's Device의 전형적인 디컴파일 특징 — REV-0443 참고).
- 입력을 한 글자씩 바꿔가며 실행해보면, 바뀐 글자의 인덱스 이후부터만 출력 Hex가 달라지고 그 이전 부분은 그대로 유지된다.

## 가장 먼저 할 것
바이너리를 실행해서 아무 입력이나 넣어보고 출력 Hex 문자열의 길이를 잰다. 그 길이를 2로 나눠 플래그 바이트 길이를 추정한다. 그다음 같은 길이의 입력을 앞부분만 바꿔서 두세 번 더 실행해보고, 출력 Hex의 앞부분이 그대로 유지되는지(=스트림형 구조인지) 확인한다. 이 성질이 확인되면 암호화 알고리즘 내부를 완전히 분석하지 않고 오라클 브루트포스로 직행할 수 있다.

## 단계별 절차
1. 실행 파일과 output.txt(정답 플래그의 암호문 Hex)를 받는다.
2. output.txt의 Hex 문자열 길이를 2로 나눠 평문 길이(N)를 구한다(참고 풀이에서는 39).
3. Python(ptrlib 또는 pwntools의 `process`)으로 실행 파일을 반복 실행할 수 있게 스크립트를 짠다.
4. 길이 N짜리 입력을 전부 특정 문자(예: `"A"*N`)로 채워 한 번 실행하고 출력을 받아본다.
5. 인덱스 `i = 0`부터 시작해서, `string.printable`의 모든 문자를 `i`번째 자리에 대입해가며 실행하고, 출력 Hex의 앞 `(i+1)*2`글자가 output.txt와 일치하는지 비교한다.
6. 일치하는 문자를 찾으면 그 자리를 확정하고 `i`를 1 증가시켜 같은 과정을 반복한다.
7. `i`가 N에 도달하면 지금까지 확정한 문자열이 곧 플래그다.

## 명령어/단축키
```python
import string
from ptrlib import Process  # 또는 pwntools의 process

N = 39
target_hex = open("output.txt").read().strip()
flag = ["A"] * N

for i in range(N):
    for c in string.printable:
        flag[i] = c
        p = Process("./legacyopt")
        p.sendline("".join(flag))
        out = p.recvline().strip().decode()
        if out[: (i + 1) * 2] == target_hex[: (i + 1) * 2]:
            break
        p.close()
print("".join(flag))
```

## 출력 해석
스크립트가 진행되면서 `flag` 리스트의 앞부분이 점점 `DH{...`로 맞춰지는 것을 눈으로 확인할 수 있다. 앞부분이 실제 플래그 포맷(`DH{`)과 일치하기 시작하면 오라클 공격 방향이 맞다는 강한 확신을 가질 수 있다. 반대로 아무 문자를 넣어도 앞부분 Hex가 계속 바뀌기만 한다면, 이 문제가 스트림형이 아니라 블록 암호형일 가능성이 있으므로 이 접근법 대신 정적 분석으로 알고리즘을 완전히 복원해야 한다.

## 흔한 실수
- 길이 관계를 확인하지 않고 아무 길이의 문자열로 무작정 브루트포스를 시도하는 것 — 길이가 다르면 암호화 결과 전체가 흔들려 오라클이 성립하지 않는다.
- 암호화 함수가 스트림형인지 확인하지 않고 바로 오라클 공격을 시도하는 것 — 앞의 한두 글자만 바꿔보고 뒷부분 출력이 그대로인지 반드시 먼저 확인해야 한다.
- Duff's Device로 언롤링된 코드를 보고 "함수가 왜 이렇게 복잡하지"라고 겁먹어 정적 분석에만 매달리는 것 — 이런 구조는 오히려 오라클 공격으로 우회하기 좋은 신호다.
- 매 문자 시도마다 프로세스를 새로 실행하지 않고 이전 프로세스를 재사용해서 상태(내부 시드 등)가 오염되는 것.

## 막혔을 때 다음 체크
- 언롤링된 반복문 구조 자체가 헷갈리면 → REV-0443 루프 언롤링(Loop Unrolling) 알아보는 법
- 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 배경 지식이 필요하면 → REV-0037 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 이유
- 오래된/레거시 스타일 컴파일 문제 전반의 특징이 궁금하면 → REV-0324 오래된 대회 문제(레거시 컴파일러) 특징 알아보기
- 오라클 공격 대신 정적으로 완전히 알고리즘을 복원하는 절차가 필요하면 → REV-0017 recover-logic-before-solver(로직 복원 후 솔버 작성)

## 미니 예제
정상적인 스트림형 오라클의 동작을 단순화하면 다음과 같다.
```text
입력: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA (39자)
출력 Hex 앞부분: 3f 9a 2c ...

입력: DAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
출력 Hex 앞부분: 11 9a 2c ...   ← 첫 바이트만 바뀌고 나머지는 동일

입력: DHAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
출력 Hex 앞부분: 11 7d 2c ...   ← 두 번째 바이트까지만 바뀜
```
이렇게 한 글자씩 확정해 나가면, 최종적으로 참고한 풀이에서는 `DH{Duffs_Device_but_use_memcpy_instead}` 형태의 플래그를 얻었다고 밝히고 있다. 이 값은 참고 출처(satoki/ctf_writeups)에서 확인된 것으로, 실제 드림핵 상시 워게임판 legacyopt의 플래그와 완전히 동일한지는 별도로 검증되지 않았다.
