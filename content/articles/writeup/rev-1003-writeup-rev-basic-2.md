## 한 줄 요약
rev-basic-2는 정답 배열을 for 루프로 순회하며 입력값과 비교하는 유형인데, 디컴파일러가 정답 배열을 4바이트 단위(DWORD)로 읽어와 표시하는 반면 입력은 1바이트씩 읽기 때문에 접근 폭(stride) 차이를 못 알아채면 배열 크기와 정답 길이를 완전히 잘못 계산하게 된다.

## 언제 검색해야 하나
- 드림핵 rev-basic-2를 디컴파일했는데 `*(_DWORD*)&aC[4*i]` 같은 코드가 나와서 배열이 왜 4씩 건너뛰며 접근되는지 헷갈릴 때
- 정답 배열이 4바이트씩 읽히길래 정답 길이를 4배로 오해해서 계산이 계속 틀릴 때
- Hex View에서 실제 배열 값을 봤는데 디컴파일러가 보여주는 정수 값과 뭔가 안 맞는 느낌이 들 때

## 핵심 개념
이 문제도 겉보기 흐름은 앞선 두 문제와 같다: `Input : ` 출력 → `%256s`로 최대 256바이트 입력 → 검증 함수 호출 → `Correct`/`Wrong` 출력. 다만 검증 함수 내부가 `for (i = 0; i < 0x12; ++i)` 형태의 루프로 되어 있고, 루프 안에서 입력값의 `i`번째 바이트와 정답 배열 `aC`의 값을 비교한다.

여기서 함정은 컴파일러(또는 디컴파일러)가 이 비교를 `*(unsigned __int8*)(a1+i)`(입력 쪽, 1바이트 단위)와 `*(_DWORD*)&aC[4*i]`(정답 배열 쪽, 4바이트 단위)로 표시한다는 점이다. 실제 저장된 값 자체는 작은 정수(문자 하나의 아스키코드)이지만, 컴파일러가 정수 승격이나 배열 선언 방식에 따라 4바이트 폭으로 읽어오는 코드를 생성한 것이다. 겉모습만 보면 "정답 배열이 입력보다 4배 길다"고 오해하기 쉽지만, 실제로 의미 있는 값은 각 4바이트 블록의 하위 1바이트뿐이다. 이런 "선언과 실제 읽기 폭이 다르게 보이는" 상황은 배열/포인터 캐스팅을 다루는 문제에서 자주 나타나는 함정이며, Hex View로 원본 바이트를 직접 눈으로 확인하면 바로 정체가 드러난다.

## 화면/코드에서 보이는 징후
- 실행 결과는 이전 문제들과 동일하게 `Input : ` → `Correct`/`Wrong`.
- 검증 함수 디컴파일 결과에 `for (i = 0; i < 0x12; ++i)` 같은 루프와 `if (*(unsigned __int8 *)(a1 + i) != *(_DWORD *)&aC[4 * i]) return 0i64;` 형태의 비교문이 보인다.
- `aC`라는 이름의 전역 변수를 더블클릭하면 IDA가 데이터 세그먼트의 특정 주소로 이동하며, 그 자리에 바이트 배열이 저장되어 있다.

## 가장 먼저 할 것
DIE로 파일 확인 후 IDA에서 검증 함수를 F5로 디컴파일한다. 루프 조건(`0x12` = 18)을 먼저 확인해 "총 몇 바이트를 비교하는가"를 알아낸다. 그다음 비교식 양쪽의 타입 캐스팅(`unsigned __int8` vs `_DWORD`)을 반드시 같이 확인한다 — 이 캐스팅 차이를 놓치면 이후 모든 계산이 틀어진다.

## 단계별 절차
1. DIE로 파일 확인, 실행해서 입출력 문구 확인.
2. IDA에서 `main` → 검증 함수로 진입, F5로 디컴파일.
3. 루프 반복 횟수(`0x12` = 18진법 변환하면 10진수 18)를 확인해 정답 길이를 특정.
4. 비교식에서 입력 쪽은 1바이트(`__int8`)로, 배열 쪽은 4바이트(`_DWORD`)로 읽는다는 것을 확인 — 즉 배열의 각 원소는 4바이트 간격으로 떨어져 있지만 실제 값은 그 4바이트 중 하위 1바이트만 의미가 있다.
5. `aC`를 더블클릭해 데이터 위치로 이동, IDA의 Hex View(REV-0162)를 열어 `4*i` 간격으로 떨어진 실제 바이트 값 18개를 직접 읽는다.
6. 읽은 18개의 바이트 값을 순서대로 `chr()`로 변환해 문자열을 복원한다.
7. 복원한 문자열을 입력해 `Correct`가 나오는지 검증한다.

## 명령어/단축키
- IDA: `F5`(디컴파일), 데이터 이름 더블클릭(참조 위치로 이동), Hex View 창에서 주소로 바로 점프해 바이트 값 확인.
- 필요하면 배열 타입을 명시적으로 다시 지정할 때 `Y`(Set item type)를 사용해 4바이트가 아니라 1바이트 배열로 재해석할 수도 있다(REV-0148).
- Python: `''.join(chr(b) for b in byte_list)`로 최종 문자열 변환.

## 출력 해석
`*(_DWORD *)&aC[4 * i]`라는 표현은 "aC 배열의 `4*i`번째 바이트부터 4바이트를 정수로 읽는다"는 뜻이다. 만약 그 위치에 저장된 실제 바이트가 `43 00 00 00`(리틀 엔디안)이라면, 4바이트를 정수로 읽어도 그 값은 결국 `0x43`(67, 문자 `C`)과 같다. 즉 상위 3바이트가 전부 0이기 때문에 겉보기 표현만 다를 뿐 실제로 비교되는 값은 여전히 한 글자의 아스키코드다. 이 사실을 Hex View로 확인하고 나면 "4배 긴 배열"이라는 오해가 풀린다.

## 흔한 실수
- 배열 접근이 `4*i`로 되어 있다고 해서 배열 전체 크기를 `18*4=72`바이트로 오해하고 엉뚱하게 긴 문자열을 만들려는 것.
- Hex View를 확인하지 않고 디컴파일러가 보여주는 정수 값(예: 4바이트로 표시된 큰 수)을 그대로 문자로 변환해 이상한 문자가 나오는 것.
- 루프 조건의 `0x12`를 10진수 12로 잘못 읽어 정답 길이를 16진수/10진수 혼동으로 틀리는 것(0x12는 10진수 18이다).
- 입력 쪽과 배열 쪽의 캐스팅이 다르다는 것 자체를 눈치채지 못하고 타입 에러처럼 여겨 그냥 넘어가는 것.

## 막혔을 때 다음 체크
- 정답 배열 대신 하드코딩된 `if` 문 여러 개가 이어지는 형태라면 REV-1002(rev-basic-1)와 더 가깝다.
- 배열 비교가 XOR과 인덱스 연산까지 섞여 있다면 REV-1004(rev-basic-3)로 넘어가서 비교한다.
- 디컴파일 결과의 타입 캐스팅을 읽는 법 자체가 헷갈리면 REV-0162(Hex View 검증)와 REV-0148(타입 재지정)을 먼저 본다.

## 미니 예제
```c
int check(char *a1) {
    for (int i = 0; i < 0x12; ++i) {
        if (*(unsigned __int8 *)(a1 + i) != *(_DWORD *)&aC[4 * i])
            return 0;
    }
    return 1;
}
```
겉보기에는 `aC`가 72바이트짜리 배열처럼 보이지만, Hex View로 확인하면 각 4바이트 블록의 상위 3바이트는 모두 0이고 하위 1바이트만 실제 정답 문자다.
