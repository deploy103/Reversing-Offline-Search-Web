## 한 줄 요약
`flag` 파일 내용을 메모리에 올려두고 입력값과 비교하는 프로그램인데, 입력을 받는 `read()` 크기가 비교 대상 버퍼보다 커서 스택 버퍼 오버플로우가 나는 문제이며, "Correct/Failed" 같은 응답을 오라클로 활용해 플래그를 한 바이트씩 유출하는 사이드채널 방식으로 풀이한다.

## 언제 검색해야 하나
- checkflag 바이너리를 IDA로 열었는데 `fopen`으로 flag 파일을 읽어 어떤 버퍼에 저장한 뒤, 사용자 입력과 비교하는 구조가 보일 때
- `read()`나 `gets()` 같은 함수의 크기 인자가 목적지 버퍼보다 명백히 크게 설정되어 있어 "이거 오버플로우 아닌가?" 싶을 때
- 문제 카테고리가 pwnable과 reversing 양쪽에 걸쳐 있어서 익스플로잇과 분석을 같이 요구하는 느낌일 때

## 핵심 개념

### 두 버퍼가 스택에서 인접해 있다는 것의 의미
checkflag는 `flag` 파일의 내용을 읽어 들인 버퍼(코드상 v11)와 사용자 입력을 받는 버퍼(v10)를 스택에 인접하게 배치한다. 사용자 입력을 받을 때 `read()`에 지정된 크기가 입력 버퍼의 실제 크기(예: 64바이트)보다 큰 값(0xc8, 즉 200바이트)으로 설정되어 있어서, 입력을 충분히 길게 주면 입력 버퍼를 넘어 바로 옆에 있는 flag 버퍼까지 덮어쓸 수 있다. 이것이 전형적인 스택 기반 버퍼 오버플로우다.

### 성공/실패 메시지를 오라클로 쓰는 방식
프로그램은 입력이 flag 버퍼 내용과 일치하는지, 그리고 입력 길이가 flag보다 작거나 같은지를 확인해 "Correct"/"Failed" 계열 메시지를 출력한다. 오버플로우로 flag 버퍼의 일부를 자신이 원하는 값('a' 같은 채움 문자)으로 덮어쓰면서 "이 위치까지는 성공, 이 위치부터는 실패"라는 반응 차이를 관찰할 수 있다는 점이 핵심이다. 이런 방식을 오라클(oracle) 기반 사이드채널 공격이라 부른다 — 프로그램이 내부 값을 직접 보여주지는 않지만, 참/거짓 응답만으로도 내부 값을 한 조각씩 추론해낼 수 있다.

### 길이 추론과 바이트별 복구의 2단계
먼저 입력 버퍼와 flag 버퍼를 모두 같은 채움 문자로 덮어쓰는 오버플로우 양을 조금씩 줄여가며 시도한다. 어느 지점부터 "Failed"가 나오기 시작하면, 그 지점이 곧 flag의 실제 길이를 알려준다. 길이를 알아낸 다음에는 뒤쪽부터(또는 앞쪽부터) 한 글자씩, 이미 알아낸 부분은 그대로 채우고 아직 모르는 한 자리에 대해 출력 가능한 ASCII(0x20~0x7e) 전체를 하나씩 대입하며 "Correct" 응답이 나오는 문자를 찾는 과정을 flag 전체 길이만큼 반복한다.

## 화면/코드에서 보이는 징후
- `fopen("flag", "r")` 계열로 flag 파일을 여는 코드
- 사용자 입력을 받는 `read()`의 세 번째 인자(크기)가 목적지 버퍼 크기보다 명백히 큼
- "What's the flag?" 류의 프롬프트 출력 후 "Correct!"/"Failed" 두 갈래로만 결과가 나뉘는 구조

## 가장 먼저 할 것
IDA로 flag를 읽어들이는 버퍼와 사용자 입력 버퍼가 스택에서 서로 몇 바이트 떨어져 있는지(오프셋)부터 GDB로 실제 두 변수의 주소를 찍어보며 확인한다. 이 오프셋을 모르면 오버플로우 페이로드 길이를 정확히 설계할 수 없다.

## 단계별 절차
1. IDA에서 main(또는 검증 함수)을 열어 flag 버퍼와 입력 버퍼 각각의 스택 오프셋, `read()` 호출의 크기 인자를 확인한다.
2. GDB로 `read()` 호출 직후에 브레이크포인트를 걸고 두 버퍼의 실제 주소 차이를 재확인한다.
3. pwntools로 로컬 프로세스에 연결해, 채움 문자('a' 등)의 길이를 하나씩 줄여가며 전송해 "Failed"가 시작되는 지점(=flag 길이)을 찾는 스크립트를 작성한다.
4. 길이를 알아낸 뒤, 알려진 부분(이미 확인된 문자들)을 고정하고 미확인 위치에 0x20~0x7e를 순서대로 대입하는 반복문으로 한 글자씩 복구한다.
5. 전체 문자가 복구되면 `DH{...}` 형태로 이어붙여 최종 플래그를 완성한다.
6. 로컬에서 검증한 스크립트를 실제 원격 서버(nc 접속)에도 그대로 적용해 최종 플래그를 얻는다.

## 명령어/단축키
```python
from pwn import *
p = process("./checkflag")
p.sendlineafter(b"flag?", b"a" * length)
resp = p.recvline()
```
GDB: `break *read함수 호출 주소` 후 `x/64bx $rsp` 등으로 두 버퍼의 실제 메모리 배치를 눈으로 확인한다.

## 출력 해석
"Correct" 계열 메시지가 나오면 그 시점까지 시도한 바이트 값이 맞다는 뜻이고, "Failed"가 나오면 그 자리 값이 틀렸거나 길이 추정이 아직 안 맞았다는 뜻이다. 응답 문자열 하나하나가 곧 "예/아니오" 오라클 결과이므로, 스크립트에서 이 두 응답을 정확히 구분해서 분기하는 것이 브루트포스 자동화의 핵심이다.

## 흔한 실수
- flag 파일 끝의 개행 문자(0x0a)나 NULL 종료 방식을 고려하지 않아 마지막 한두 글자에서 계속 실패하는 것 — 로컬 실습 환경과 원격 서버의 flag 파일 저장 방식이 다를 수 있다는 점을 감안해야 한다.
- 오버플로우 채움 문자의 길이를 매 시도마다 다르게 계산하다가 오프셋이 하나씩 밀리는 실수.
- 로컬에서만 되는 방법(파일을 직접 읽는 등)에 의존하다가 원격 환경에서는 안 통하는 것을 뒤늦게 깨닫는 것.

## 막혔을 때 다음 체크
- 문자열 비교 기반 검증 함수의 일반적인 패턴이 헷갈리면 REV-0196 strcmp 기반 Flag 검증 패턴, REV-0197 memcmp 기반 Flag 검증 패턴을 본다.
- 무차별 대입이 현실적으로 가능한 범위인지 감이 안 잡히면 REV-0219 Brute Force가 가능한 입력 공간 계산을 본다.
- 입력과 출력만으로 내부 로직을 추정하는 블랙박스 전략 자체가 낯설면 REV-0829 블랙박스 방식으로 입력-출력 관계만 파악하는 전략을 본다.

## 미니 예제
```python
# 개념 예시: 길이를 알고 있다고 가정한 뒤 한 글자씩 복구하는 뼈대
known = b""
for pos in range(flag_len):
    for c in range(0x20, 0x7f):
        payload = known + bytes([c]) + b"a" * (flag_len - pos - 1)
        p = process("./checkflag")
        p.sendlineafter(b"flag?", payload)
        if b"Correct" in p.recvline():
            known += bytes([c])
            break
```
실제 문제의 오프셋과 길이 판별 조건은 이 글에서 재서술한 흐름을 참고해 직접 GDB로 확인해야 한다.
