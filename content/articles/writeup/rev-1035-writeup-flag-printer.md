## 한 줄 요약
"flag printer"라는 이름을 가진 리버싱 문제는 CTF 세계에 여러 대회(TMUCTF, AlpacaHack 등)에 같은 이름으로 존재하지만 드림핵 워게임 Bronze 2의 "flag printer"와는 별개의 문제이며, 드림핵 판의 상세 write-up은 찾지 못했다. 이름 그대로 "플래그를 출력하는 함수"를 찾아 그 함수가 실행되는 조건 또는 그 함수가 계산하는 값 자체를 역산하는 문제로 추정하고 접근하는 것이 합리적이다.

## 언제 검색해야 하나
- "flag printer"를 검색했는데 TMUCTF나 AlpacaHack 같은 다른 대회의 동명 문제 write-up만 나오고 드림핵 문제와는 맞지 않을 때
- 바이너리를 열어보니 `print_flag`, `show_flag` 같은 이름의 함수가 있는데 그 함수가 호출되는 조건을 못 찾겠을 때
- 함수 이름만 보고 "플래그 출력 함수만 실행하면 되겠네"라고 생각했지만 실행 흐름상 그 함수에 도달하지 못할 때

## 핵심 개념
검색 결과 "flag printer"라는 제목의 리버싱 문제는 TMUCTF 2021과 AlpacaHack(Daily Challenge, "Flag Printer 2100")에도 각각 존재한다. 이 두 문제는 드림핵과 무관한 별도 대회의 문제이므로 여기서 그대로 인용해 정답처럼 서술하는 것은 부적절하다. 다만 동일한 제목의 문제들이 공유하는 일반적인 설계 패턴은 참고할 가치가 있다.

다른 대회의 "flag printer"류 문제들에서 반복적으로 나타나는 설계는 다음과 같다.

- 프로그램이 시작하면 어떤 조건(타이머, 반복 연산, 특정 함수 호출) 뒤에 플래그를 출력하는 함수가 실행되도록 되어 있다.
- 그 조건이 지나치게 느리게 계산되도록 일부러 비효율적인 알고리즘(예: 메모이제이션 없는 재귀 피보나치 스타일 계산)으로 구현되어 있어서, 얼핏 보면 "그냥 기다리면 되는" 문제처럼 보이지만 사실상 현실적인 시간 안에 끝나지 않도록 설계된 경우가 있다.
- 이런 경우 해법은 프로그램을 그대로 기다리는 것이 아니라, 그 계산 로직을 코드로 재구현해 memoization(중복 계산 결과 캐싱)을 적용하거나, 타이머/조건 검사 지점을 디버거로 건너뛰는 패치를 하는 것이다.

드림핵의 "flag printer"(Bronze 2)가 정확히 이 구조인지는 확인되지 않았다. 다만 이름이 강하게 "플래그를 출력하는 로직 자체를 분석하라"는 것을 암시하므로, `print`/`show`/`flag` 등의 키워드로 문자열/함수 참조를 먼저 찾는 전략은 문제 구조와 무관하게 항상 유효한 첫걸음이다.

## 화면/코드에서 보이는 징후
- 실행 시 아무 것도 출력되지 않거나, 입력을 요구하지 않고 조용히 끝나거나 멈춰있는 것처럼 보임
- IDA/Ghidra에서 `flag`, `print`, `show` 등의 이름을 포함한 함수나 문자열이 존재함(strip 안 된 경우)
- 특정 함수가 호출되기까지 반복 루프나 재귀 호출이 과도하게 많아 실행 시간이 비정상적으로 길게 느껴짐

## 가장 먼저 할 것
Strings 창과 함수 목록에서 `flag`, `print`, `show`, `puts` 관련 이름을 모두 찾아 그 함수로의 xref(누가 호출하는지)를 추적한다. 호출하는 지점이 어떤 조건 뒤에 있는지 확인하는 것이 핵심이다.

## 단계별 절차
1. 실행해서 실제로 아무 반응이 없는지, 시간이 걸리는지, 입력을 요구하는지 관찰
2. IDA/Ghidra에서 플래그 관련 이름의 함수/문자열을 찾고 xref로 호출 지점 추적
3. 호출 지점 위쪽의 조건문(비교, 타이머, 반복 횟수 카운터)을 확인
4. 조건이 단순 비교라면 값을 맞춰 입력하고, 반복/재귀 연산이라면 그 알고리즘을 Python 등으로 재구현해 시간을 줄이거나 정확한 값을 미리 계산
5. x64dbg로 조건 통과 지점에 브레이크포인트를 걸어 우회 또는 값 확인으로 검증

## 명령어/단축키
```text
IDA: Shift+F12(Strings) → 더블클릭 xref, Shift+F4(문자열 참조된 함수 뷰)
x64dbg: 플래그 출력 함수 시작 주소에 F2 → EIP/RIP를 직접 그 주소로 이동(우회 시)
```

## 출력 해석
플래그 출력 함수 진입 직전에 항상 실패하고 있다면, 그 위쪽 조건이 무엇을 비교하는지가 핵심이다. 조건이 반복 연산 결과라면 결과를 눈으로 예측하기보다 동일한 로직을 스크립트로 재구현해 정확한 가능한 값을 얻는 편이 안전하다.

## 흔한 실수
- 이름이 같다는 이유로 다른 대회(TMUCTF, AlpacaHack)의 "flag printer" 풀이를 그대로 드림핵 문제에 대입해 시간을 낭비하는 것
- 반복/재귀 계산이 원인인데 그냥 프로그램을 오래 기다리기만 하다가 포기하는 것 — 현실적인 시간 안에 끝나지 않게 설계되었을 수 있음
- 플래그 함수 자체만 보고 그 함수를 호출하는 조건을 살펴보지 않는 것

## 막혔을 때 다음 체크
- 반복/재귀 연산이 원인인 것 같다면 → REV-0911 여러 알고리즘이 순차적으로 합성된 문제 풀어내기
- 같은 입력에도 결과가 다르거나 시간이 오래 걸리는 것처럼 보이면 → REV-0331 같은 입력인데 실행마다 다른 결과가 나올 때
- 특정 함수로의 진입 조건을 우회하는 패치 방법이 헷갈리면 → REV-0282 x64dbg 10분 실전 워크플로

## 미니 예제
```c
// 다른 대회의 "flag printer" 계열에서 흔히 보이는 설계를 일반화한 예시(실제 드림핵 코드 아님)
long long slow_calc(int n) {
    if (n <= 1) return n;
    return slow_calc(n - 1) + slow_calc(n - 2); // memoization 없는 재귀
}
if (slow_calc(input) == target) print_flag();
```
이 예제는 다른 CTF의 동명 문제에서 보이는 설계 원리를 일반화한 것으로, 드림핵의 "flag printer" 실제 코드가 확인된 것은 아니다.
