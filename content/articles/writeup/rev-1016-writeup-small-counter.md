## 한 줄 요약
Small Counter는 10부터 1까지 내려가는 단순 카운터 출력 루프처럼 보이지만, 루프가 끝난 뒤 특정 카운터 변수가 정확히 5였는지를 검사해 `flag_gen` 함수를 호출하는 숨은 분기가 있는 리눅스 ELF 문제로, GDB로 그 분기 직전에 멈춰서 메모리 값을 5로 직접 바꿔주면 플래그 생성 함수가 실행된다.

## 언제 검색해야 하나
- 프로그램을 실행하면 그냥 10, 9, 8 ... 1까지 숫자만 출력하고 끝나는 것처럼 보여서 "이게 왜 문제로 나왔지"라는 의문이 들 때
- IDA로 열었을 때 카운터 출력 루프는 있는데 루프가 끝난 직후에 `cmp`와 `jnz` 같은 분기가 하나 더 있고, 그 분기 안에서만 `flag_gen`이라는 함수가 호출되는 걸 발견했을 때
- 어떤 변수를 원하는 값으로 맞추고 싶은데 프로그램 로직상 자연스럽게는 그 값이 나오지 않아서 GDB로 강제로 값을 바꿔야 할 것 같을 때

## 핵심 개념
이 문제의 `main` 함수는 겉보기엔 매우 단순하다. 카운터 변수를 10에서 시작해 1이 될 때까지 1씩 줄이며 화면에 출력하는 평범한 반복문이 전부처럼 보인다. 그런데 공개된 풀이를 보면 이 루프 안에는 미끼가 하나 섞여 있다 — 카운터가 특정 값(3)일 때는 `strcpy`/`memcpy` 계열 함수로 어떤 문자열을 복사하는 코드가 실행되는데, 이는 실제 플래그 로직과는 무관한 더미(가짜) 동작이다. 진짜 핵심은 루프가 모두 끝난 시점(또는 특정 지점)에 스택에 저장된 카운터 관련 변수(`[rbp-0x4]`)를 `cmp` 명령으로 5와 비교하고, 같을 때만(`jnz`로 아니면 건너뜀) `flag_gen` 함수를 호출하도록 되어 있다는 점이다.

문제는 정상적인 카운터 흐름(10→1)만으로는 이 변수가 마지막에 5로 남지 않는다는 데 있다. 즉 프로그램을 있는 그대로 실행해서는 절대 `flag_gen`이 호출되는 경로에 들어갈 수 없고, 실행 중간에 디버거로 개입해 그 변수의 값을 강제로 5로 만들어줘야 한다. 이것이 "Small Counter"라는 문제 이름과 별개로, 실제로는 "메모리 값을 실행 중에 직접 조작하는 법"을 익히게 하려는 문제라는 뜻이다.

## 화면/코드에서 보이는 징후
- 실행 결과가 그냥 숫자 10부터 1까지 한 줄씩 출력되고 끝나며, "Wrong"이나 "Correct" 같은 판정 메시지가 전혀 없음
- IDA 그래프 뷰에서 카운터 루프를 빠져나온 직후에 `cmp DWORD PTR [rbp-0x4], 0x5`와 `jnz` 분기가 따로 존재함
- `jnz`가 건너뛰는 목적지 쪽에는 `flag_gen`으로 보이는 함수 호출이 없고, 분기를 타지 않았을 때만 `flag_gen` 호출로 이어짐
- 바이너리에 `puts@plt`, `printf@plt` 같은 PLT 심볼이 보여 리눅스 ELF 동적 링킹 바이너리임을 알 수 있음

## 가장 먼저 할 것
IDA 그래프 뷰에서 메인 루프를 빠져나오는 화살표를 따라가 `cmp`/`jnz` 분기 블록을 먼저 찾는다. 그 분기의 비교 대상 주소(스택 오프셋)와 비교값(5)을 정확히 적어두는 것이 이 문제의 시작점이다. 정상 실행으로는 이 조건을 만족시킬 수 없다는 것을 인지하고, 처음부터 "패치 또는 디버거 개입이 필요한 문제"로 접근 방향을 잡아야 한다.

## 단계별 절차
1. 바이너리를 그냥 실행해 10부터 1까지 출력되고 끝나는 동작을 확인한다.
2. IDA로 열어 `main`을 그래프 뷰로 보고, 카운터 루프 뒤에 이어지는 `cmp [rbp-0x4], 0x5` / `jnz` 분기의 정확한 주소를 확인한다.
3. GDB로 바이너리를 실행하고, 그 `cmp` 명령 주소에 브레이크포인트를 건다.
4. `run`으로 실행해 브레이크포인트에서 멈추면 `[rbp-0x4]`(또는 IDA가 보여준 정확한 스택 오프셋)의 현재 값을 확인한다.
5. 그 메모리 위치의 값을 5로 직접 덮어쓴다.
6. 실행을 이어가(`continue`) `flag_gen` 함수가 호출되는지, 그리고 플래그가 출력되는지 확인한다.

## 명령어/단축키
```bash
gdb ./chall
```
```text
(gdb) b *0x<cmp_instruction_address>
(gdb) run
(gdb) info registers rbp
(gdb) x/wx $rbp-0x4
(gdb) set {int}($rbp-0x4) = 5
(gdb) continue
```
`set {int}(주소) = 값` 구문이 GDB에서 실행 중 메모리를 직접 덮어쓰는 핵심 명령이다.

## 출력 해석
값을 5로 바꾼 뒤 실행을 이어가면 `flag_gen` 함수가 호출되어 알파벳을 특정 규칙(시프트 등)으로 치환하는 변환을 거친 플래그 문자열이 만들어지고, 이어서 표준출력으로 출력된다. 만약 여전히 `flag_gen`이 호출되지 않는다면 브레이크포인트를 건 주소가 실제 `cmp` 명령이 아니거나, 수정한 메모리 주소가 실제 비교에 쓰이는 변수와 다를 가능성이 크므로 IDA에서 오프셋을 다시 확인해야 한다.

## 흔한 실수
- 카운터가 3일 때 나오는 `strcpy`/`memcpy` 더미 코드를 진짜 핵심 로직으로 착각해서 그쪽을 분석하는 데 시간을 쓰는 것.
- `cmp` 명령 자체가 아니라 그보다 앞이나 뒤의 명령에 브레이크포인트를 걸어서 정작 비교가 일어나기 전에 값을 바꾸지 못하거나 이미 분기가 끝난 뒤에 바꾸는 것.
- GDB의 `set {int}(주소) = 값` 문법에서 자료형 크기를 잘못 지정해(예: `{char}`를 써야 하는데 `{int}`를 쓰는 등) 의도한 것보다 더 많은 바이트를 덮어써 버리는 것.
- 이 조작이 "한 번의 실행에서만" 유효하다는 것을 잊고, GDB를 재시작한 뒤에도 값이 유지되어 있을 거라 오해하는 것.

## 미니 예제
핵심 분기의 개념적 구조는 다음과 같다.
```c
int counter;
for (counter = 10; counter >= 1; counter--) {
    if (counter == 3) {
        // 더미 동작: strcpy/memcpy로 무관한 문자열 복사
    }
    printf("%d\n", counter);
}
if (counter == 5) {   // 정상 실행으로는 절대 참이 될 수 없는 조건
    flag_gen();
}
```
루프가 정상적으로 끝나면 `counter`는 0(또는 그와 유사한 값)으로 남기 때문에, 이 조건은 프로그램을 그대로 실행해서는 절대 만족될 수 없다. GDB로 실행 중 `counter`가 저장된 메모리를 5로 강제 조작하는 것이 이 문제의 유일한 실용적 해법이다.
