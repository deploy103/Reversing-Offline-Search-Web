## 한 줄 요약
문제 이름 "Recover"에서 "손상되었거나 의도적으로 지워진/변형된 데이터를 원래 형태로 복구하라"는 의도를 유추할 수 있는 브론즈 4 문제지만, 이 문제를 구체적으로 다룬 write-up을 찾지 못해 이 글은 이름에서 유추한 일반적 접근법만 절차 중심으로 정리한 것이며 실제 정답 로직으로 확정된 내용이 아니다.

## 언제 검색해야 하나
- 드림핵 Recover 문제를 열었는데 파일이 정상적으로 실행되지 않거나, 실행은 되지만 화면에 의도적으로 깨진 것처럼 보이는 데이터/이미지/문자열이 나올 때
- 바이너리 안에서 원본 데이터를 어떤 알고리즘으로 변형해서 저장해 둔 것 같은데 그 역함수를 찾아야 할 때
- "복구"라는 이름의 문제에서 무엇을 복구해야 하는지조차 감이 안 잡힐 때

## 핵심 개념

### "Recover" 계열 문제의 일반적인 두 갈래
드림핵을 포함한 여러 워게임에서 "Recover", "Restore", "Repair" 같은 이름을 가진 리버싱 문제는 대체로 다음 두 패턴 중 하나로 나타나는 경우가 많다(이 문제가 실제로 어느 쪽인지는 확인되지 않았다).

1. **파일 포맷 손상 복구형**: 실행 파일이나 첨부된 데이터 파일의 헤더/구조 일부가 의도적으로 손상되어 있어, 정상적인 도구(이미지 뷰어, 압축 해제기 등)로 열리지 않는다. 손상된 바이트를 원래 값으로 되돌리는 로직(체크섬, 매직 넘버, 오프셋 구조)을 분석해 파일을 되살리는 것이 목표다.
2. **인코딩/변형 복구형**: REV-1023 secret message처럼, 원본 데이터를 특정 알고리즘(런렝스 인코딩, XOR, 비트 셔플 등)으로 변형해 저장해 두고, 그 변형 알고리즘을 분석해 역함수를 구현하는 것이 목표다.

### 정적/동적 분석을 병행해야 하는 이유
어느 패턴이든 바이너리 안에 "무엇을 손상시켰는지"와 "어떻게 복구하는지"에 대한 힌트가 코드로 들어 있을 가능성이 높다. 실행 파일 하나만 있고 별도의 손상된 데이터 파일이 없다면, 바이너리 자체의 로직(예: 원본 값을 어떤 연산으로 바꿔 저장하는 함수)을 분석해서 그 연산의 역함수를 구현하는 흐름이 될 것으로 추정된다.

## 화면/코드에서 보이는 징후
- 실행 시 "파일이 깨졌다", "복구해야 한다" 류의 메시지 출력
- 첨부 파일이 표준 포맷 시그니처(매직 넘버)와 다르게 시작함
- 디컴파일 결과에 원본 값을 특정 연산으로 변형해 저장하는 함수가 보이고, 그 역연산을 구현해야 할 것으로 보이는 구조

## 가장 먼저 할 것
`file`(또는 Detect It Easy)로 제공된 실행 파일과 첨부 데이터 파일의 실제 포맷을 먼저 확인한다. 실행 파일이 어떤 언어/컴파일러로 만들어졌는지, 그리고 별도의 데이터 파일이 있다면 그 파일의 매직 넘버가 표준 포맷과 얼마나 다른지부터 살펴본다.

## 단계별 절차
1. 제공된 모든 파일에 대해 `file`과 Detect It Easy로 포맷을 확인한다.
2. 실행 파일을 IDA/Ghidra로 열어 "복구", "손상", "check" 등과 관련된 문자열 참조를 먼저 찾는다.
3. 데이터를 변형하는 함수(있다면)를 찾아 어떤 연산(비트 시프트, XOR, 치환 등)을 수행하는지 분석한다.
4. 분석한 변형 로직의 역함수를 Python 등으로 재구현한다.
5. 역함수를 실제 데이터에 적용해 정상적인 포맷(이미지, 텍스트, 실행 파일 등)으로 복구되는지 확인한다.
6. 복구된 결과 안에서 `DH{...}` 형식의 플래그를 찾는다.

## 명령어/단축키
```bash
file ./recover_data
xxd ./recover_data | head
```
IDA: Strings 창에서 "recover", "corrupt", "check" 등 키워드 검색 후 Xref로 호출 지점 추적.

## 출력 해석
`xxd`/`hexdump`로 파일 앞부분을 봤을 때 표준 포맷의 매직 넘버(예: PNG는 `89 50 4E 47`, ZIP은 `50 4B 03 04`)와 다른 값이 보인다면, 그 차이가 바로 "무엇이 손상/변형되었는가"에 대한 첫 번째 힌트가 된다.

## 흔한 실수
- 문제 이름만 보고 구체적인 변형 알고리즘을 지어내 그대로 정답이라 믿는 것 — 반드시 바이너리 분석으로 검증해야 한다.
- 첨부된 데이터 파일이 없는데도 어딘가에 파일이 있을 것이라 가정하고 헛되이 찾는 것 — 문제에 따라 변형 로직 자체가 실행 파일 안의 메모리 데이터에만 있을 수도 있다.
- 매직 넘버 몇 바이트만 보고 포맷을 단정하는 것 — 포맷 검증은 매직 넘버 이후 구조까지 같이 확인해야 확실하다.

## 막혔을 때 다음 체크
- 인코딩을 역으로 구현하는 유사한 실전 사례가 필요하면 REV-1023 [Write-up] secret message(런렝스 계열 인코딩을 분석해 역함수를 구현한 사례)를 참고한다.
- XOR 기반 변형일 가능성이 있다면 REV-0057 XOR: XOR 연산과 XOR reg reg 제로화, REV-0878 흔한 XOR 키 길이 탐지 팁 참조를 본다.
- 검증 로직을 파이썬으로 그대로 재현하는 일반적인 방법이 필요하면 REV-0222 검증 루틴을 Python으로 그대로 재현하기를 본다.

## 미니 예제
```python
# 변형 로직이 예: 각 바이트에 +1을 해서 저장했다고 가정한 경우의 복구 스크립트 예시
with open("corrupted.bin", "rb") as f:
    data = f.read()
recovered = bytes((b - 1) & 0xff for b in data)
with open("recovered.bin", "wb") as f:
    f.write(recovered)
```
이 예시는 "변형 연산의 역함수를 구현해 원본을 되살린다"는 일반적인 뼈대만 보여주는 것으로, Recover 문제의 실제 변형 알고리즘이 아니다.
