## 한 줄 요약
rev-basic-1은 `strcmp` 한 번이 아니라 `if (*a1 != 67) return 0;` 식으로 문자 하나하나를 하드코딩된 아스키 숫자와 순서대로 비교하는 유형이며, 그 숫자들을 순서대로 모아 `chr()`로 변환하면 정답이 나온다.

## 언제 검색해야 하나
- 드림핵 rev-basic-1을 열었는데 검증 함수 안에 `strcmp` 호출이 안 보이고 `if` 문이 여러 줄 이어져 있을 때
- 디컴파일 결과에 67, 111, 109 같은 숫자들이 각 `if` 문마다 하나씩 박혀 있는 걸 봤지만 이게 뭘 의미하는지 모를 때
- x64dbg로 문자열 참조를 따라갔는데 `call` 명령어 안으로 들어가야 진짜 비교 로직이 나온다는 걸 몰라서 막혔을 때

## 핵심 개념
rev-basic-0(REV-1001)과 겉보기 동작(입력 → Correct/Wrong)은 똑같지만, 내부 검증 방식이 다르다. 이 문제의 검증 함수는 정답 문자열 전체를 한 번에 비교하는 게 아니라, 입력 버퍼의 각 바이트를 인덱스 순서대로 하나씩 확인한다. 예를 들어 `if (*a1 != 67) return 0i64;` 는 "입력의 첫 번째 문자가 아스키코드 67(문자 `C`)이 아니면 즉시 실패"라는 뜻이고, 이런 `if` 문이 정답 길이만큼 연속으로 이어진다. 마지막에는 입력이 정확히 그 길이에서 끝나는지(널 바이트 검사)까지 확인하는 경우가 많다. 이는 REV-0198에서 다루는 "문자별 for/if 루프 검증 패턴"의 전형적인 예다. 결국 코드 안에 흩어진 숫자들을 순서대로 모아 아스키 문자로 바꾸면 그것이 곧 정답이다.

## 화면/코드에서 보이는 징후
- 실행하면 `Input : `이 출력되고 입력을 기다리며, 틀린 값을 넣으면 `Wrong`이 출력된다.
- IDA 디컴파일 결과에서 `sub_...1000` 같은 검증 함수 안에 `if (*(a1+n) != 숫자) return 0i64;` 형태의 코드가 정답 길이만큼 반복된다.
- x64dbg에서는 문자열 참조로 `Input : ` 출력 위치를 찾은 뒤, `Correct`/`Wrong` 분기 직전의 `call` 안으로 들어가면 각 바이트를 `cmp` 명령어로 하나씩 비교하는 코드가 보인다.

## 가장 먼저 할 것
DIE로 PE64/컴파일러를 확인한 뒤, 이번에는 정적 분석(IDA)과 동적 분석(x64dbg) 중 편한 쪽을 골라도 된다. 정적으로 먼저 시도한다면 IDA에서 검증 함수를 F5로 디컴파일해 `if` 문에 박힌 숫자들을 순서대로 받아 적는다. 동적으로 접근한다면 x64dbg에서 문자열 참조 검색으로 `Input : `을 찾아 그 주변의 `call` 명령어에 브레이크포인트를 걸고 내부로 들어간다.

## 단계별 절차
1. DIE로 파일 종류 확인, 실행해서 입출력 문구 확인.
2. (정적) IDA에서 `main` → 검증 함수로 진입해 F5로 디컴파일. `if (*(a1+i) != N)` 패턴의 `N` 값들을 인덱스 순서대로 나열.
3. (동적) x64dbg에서 마우스 우클릭 → Search for → Current Module → String references로 `Input : ` 찾기 → 더블클릭 진입.
4. `Correct`/`Wrong` 출력 분기 바로 앞의 `call` 명령어에 `F2`로 브레이크포인트를 걸고 `F9`로 실행, 내부로 진입해 각 바이트가 어떤 값과 `cmp`되는지 하나씩 확인.
5. 얻은 숫자 리스트를 파이썬 리스트로 만들고 `''.join(chr(n) for n in nums)`로 문자열 변환.
6. 변환한 문자열을 실행 파일에 입력해 `Correct`가 뜨는지 확인.

## 명령어/단축키
- x64dbg: 우클릭 → Search for → String references, `F2`(브레이크포인트 토글), `F9`(실행), `F7`/`F8`(Step Into/Over).
- IDA: `F5`(디컴파일), 숫자를 선택한 뒤 `R` 키를 누르면 그 자리에서 바로 아스키 문자로 표시가 바뀐다(숫자를 하나씩 문자로 확인하는 용도).
- Python: `chr(67)` → `'C'`.

## 출력 해석
`if (*a1 != 67) return 0i64;` 코드는 "입력 버퍼의 0번째 바이트가 67이 아니면 실패"라는 뜻이다. 67은 아스키코드 표에서 대문자 `C`에 해당한다. 이런 `if` 문이 예를 들어 20개 이어져 있다면 정답 길이가 20자라는 뜻이고, 마지막 `if`에서 0(널 바이트)을 확인한다면 그 다음에 문자가 더 없어야 한다는 뜻이다. IDA의 `R` 단축키를 숫자에 적용하면 매번 파이썬을 켜지 않고도 즉석에서 문자를 확인할 수 있어 빠르다.

## 흔한 실수
- 숫자들을 코드에 나온 순서 그대로 받아 적지 않고 뒤섞어서 정답 순서가 틀리는 것.
- `if (*(a1+i) != N) return 0;` 에서 인덱스 `i`가 0부터 시작하는지 1부터 시작하는지 헷갈려 한 글자를 놓치는 것.
- x64dbg에서 `Input :` 문자열 참조가 여러 개 나올 때 무작정 첫 번째만 보고 다른 함수로 들어가는 것.
- 아스키코드 변환 시 10진수와 16진수를 착각해서(IDA가 16진수로 표시하는 경우) 잘못된 문자로 변환하는 것.

## 막혔을 때 다음 체크
- 비교 대상이 상수 하나가 아니라 배열 원소이고, 배열 접근 폭이 입력과 다르게 보인다면 REV-1003(rev-basic-2)의 스트라이드 문제를 참고한다.
- `strcmp` 한 줄로 끝나는 훨씬 단순한 형태가 궁금하면 REV-1001(rev-basic-0)을 먼저 복습한다.
- x64dbg 브레이크포인트 자체가 익숙하지 않다면 REV-0178, REV-0179를 먼저 본다.

## 미니 예제
```c
int check(char *a1) {
    if (*(a1+0) != 67) return 0; // 'C'
    if (*(a1+1) != 111) return 0; // 'o'
    if (*(a1+2) != 109) return 0; // 'm'
    // ... 이후 인덱스도 동일한 패턴으로 계속됨
    return 1;
}
```
이런 형태를 보면 굳이 리버스 엔지니어링 도구로 자동화하지 않고, 숫자만 눈으로 옮겨 적어도 충분히 풀린다.
