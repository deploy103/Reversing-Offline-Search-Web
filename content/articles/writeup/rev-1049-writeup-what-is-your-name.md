## 한 줄 요약
드림핵 Silver 4 "What is your name?"에 대한 상세 write-up은 이번 조사에서 찾지 못했으므로, 이 글은 "이름을 입력받아 검증한다"는 문제 이름과 실버 티어가 브론즈보다 한 단계 더 복잡한 검증을 쓴다는 일반적 특성을 근거로, 이름 기반 입력 검증 문제에서 실제로 자주 쓰이는 검증 패턴들을 정리한 추정 절차이며 구체적인 정답 이름이나 상수는 다루지 않는다.

## 언제 검색해야 하나
- 프로그램이 "이름을 입력하세요" 같은 프롬프트를 띄우고, 입력한 이름에 따라 성공/실패 메시지가 달라질 때
- 디컴파일 결과에 입력 문자열을 한 글자씩 순회하며 XOR/덧셈/시프트 같은 연산을 누적하는 반복문이 보여서, 단순 `strcmp`(REV-0196)로는 설명이 안 될 때
- 브론즈 티어의 "Simple Crack Me" 계열 문제를 이미 풀어봤는데, 이번 문제는 그보다 검증 단계가 하나 더 있거나 연산이 더 복잡해 보일 때

## 핵심 개념

### 브론즈의 단순 비교와 실버의 차이(일반적 경향)
브론즈 티어의 이름/비밀번호 검증 문제는 대개 입력 문자열을 고정된 정답 문자열과 `strcmp`로 직접 비교하는 구조(REV-0196)이거나, 길이 체크 하나만 있는 경우가 많다. 실버 티어로 올라가면 다음과 같은 요소가 하나 이상 추가되는 경향이 있다.
- 입력 문자열 자체를 정답과 비교하는 게 아니라, 입력 문자열에 어떤 변환(체크섬, 간단한 해시, 문자별 XOR/회전)을 적용한 결과를 미리 정해둔 값과 비교.
- 이름의 길이나 특정 자리 문자에 대한 부가 조건(예: 첫 글자가 대문자여야 함, 특정 문자가 포함되면 안 됨)이 섞여 있는 다단계 검증.
- 검증 결과를 곧바로 참/거짓으로 쓰지 않고, 검증을 통과한 이름 자체를 키(key)로 써서 플래그의 나머지 부분을 복호화하는 구조(입력이 여러 개 가능하지만 "올바른" 이름 하나만 정확한 플래그를 만들어냄).

이 중 어떤 형태인지는 실제 바이너리를 봐야 확정할 수 있으므로, 이 글에서는 각 형태를 식별하는 절차를 제시하는 데 집중한다.

### 체크섬/해시 기반 검증을 식별하는 법
입력 문자열을 한 글자씩 반복문으로 순회하면서 누산 변수(accumulator)에 연산을 적용하는 패턴이 보이면, 이는 단순 비교가 아니라 체크섬/해시 기반 검증이다. 이런 구조에서는 여러 개의 다른 문자열이 같은 체크섬 값을 만들어낼 수 있으므로(충돌), 문제 제작자가 의도한 "그 이름"이 아니어도 검증을 통과하는 다른 문자열이 존재할 가능성이 있다는 점도 고려할 만하다. 다만 대회/워게임 문제는 보통 특정 정답 하나만 통과하도록 부가 조건을 더 걸어두는 경우가 많다.

### 이름이 복호화 키로 쓰이는 구조를 식별하는 법
검증 결과가 단순 참/거짓 출력으로 끝나지 않고, 검증 직후 바로 이어서 어떤 버퍼를 반복적으로 XOR/변환하는 코드가 나온다면, 입력한 이름이 플래그를 복호화하는 키로 재사용되고 있다는 신호다. 이 경우 "검증 통과"와 "플래그 복호화"가 사실상 같은 연산에 묶여 있으므로, 검증 로직의 상수를 그대로 키 후보로 추출해 복호화 루틴에 대입해보는 것이 효율적이다.

## 화면/코드에서 보이는 징후
- "What is your name?" 또는 유사한 문구로 이름 입력을 요구한다.
- 입력 문자열의 각 문자에 대해 반복문 안에서 `^=`, `+=`, `<<`/`>>` 연산이 누적되는 코드가 보인다.
- 최종 누산값을 하드코딩된 상수(4~8바이트 정수 또는 문자열)와 `cmp`/`memcmp`로 비교한다.
- 검증 성공 직후 별도의 버퍼(플래그로 추정되는 암호화된 데이터)에 대해 추가 연산을 수행하는 코드가 이어진다.

## 가장 먼저 할 것
IDA/Ghidra에서 입력 함수(`scanf`, `gets`, `fgets`, `cin>>` 등) 직후의 코드를 따라가며, 입력 문자열이 그대로 비교되는지 아니면 별도의 반복문에 들어가 변환되는지부터 확인한다. 변환 반복문이 있다면 그 안의 연산자와 상수를 먼저 기록한 뒤, 검증 성공 이후에 이어지는 코드까지 계속 따라가서 "검증만 하는지" "복호화까지 겸하는지"를 확인한다.

## 단계별 절차
1. 입력을 받는 함수 호출부를 찾아 입력 버퍼의 주소/크기를 확인한다.
2. 입력 버퍼를 사용하는 다음 함수(검증 함수로 추정)를 Xref로 따라간다.
3. 검증 함수 내부에 문자 단위 반복문이 있는지, 있다면 누산 연산자가 무엇인지 기록한다.
4. 반복문 종료 후 비교 대상 상수(또는 버퍼)를 확인한다.
5. 검증 성공 분기 이후에 추가 연산(복호화로 추정되는 코드)이 있는지 계속 따라간다.
6. 반복문 로직을 Python으로 그대로 옮겨 포팅하고, 알려진 상수와 일치하는 입력을 브루트포스(길이가 짧다면) 또는 역연산(XOR/덧셈처럼 역연산이 쉬운 경우)으로 구한다.
7. 구한 입력을 실제 프로그램에 넣어 검증 통과 및 플래그 출력(또는 복호화 결과)을 확인한다.

## 명령어/단축키
```python
# 체크섬 역연산 뼈대 예시(구조 설명용, 실제 문제의 정확한 연산은 직접 확인 필요)
target = 0x1234ABCD
# 만약 누산 연산이 XOR뿐이라면, 각 문자를 독립적으로 역산할 수 있는 경우도 있다.
# 덧셈/시프트가 섞여 있다면 순서를 거슬러 올라가는 역연산 함수를 직접 작성해야 한다.
```
IDA: `Alt+T`로 문자열 검색 창을 열어 "name"이 포함된 문자열을 찾아 그 Xref를 따라가면 검증 함수 진입점을 빠르게 찾을 수 있다.

## 출력 해석
- 반복문에서 사용하는 연산이 XOR뿐이라면, 각 문자 위치별로 독립적으로 역산이 가능해 정답 후보를 바로 계산할 수 있다.
- 덧셈이나 시프트가 섞여 있다면 이전 문자의 결과가 다음 문자 계산에 영향을 주므로, 마지막 문자부터 거슬러 올라가는 역순 계산이 필요하다.
- 검증 성공 이후 별도의 XOR 반복문이 다시 나온다면, 방금 입력한 이름이 키로 재사용된다는 뜻이므로 검증에 쓰인 것과 복호화에 쓰이는 것이 같은 문자열인지 다른 파생값인지 확인해야 한다.

## 흔한 실수
- 반복문을 보고 바로 "이건 표준 해시일 것"이라 단정하는 것 — 실제로는 문제 제작자가 즉석에서 만든 간단한 체크섬일 수 있으므로 REV-0876류 표준 상수와 먼저 대조해보고, 안 맞으면 커스텀 연산으로 간주해 직접 포팅해야 한다.
- 검증 통과 조건이 여러 개(길이+체크섬+특정 문자 포함 등)인데 하나만 만족시키고 나머지를 놓치는 것.
- 입력 버퍼 크기 제한(`scanf("%20s", ...)` 등)을 무시하고 너무 긴 후보 문자열을 시도해 검증 이전에 이미 잘려버리는 것.
- 검증과 복호화가 한 덩어리로 얽혀 있는데 이를 "검증만 통과하면 끝"이라 여기고 복호화 단계를 놓쳐 플래그를 못 얻는 것.

## 막혔을 때 다음 체크
- 단순 strcmp 검증과의 차이를 먼저 확실히 구분하고 싶다면 → REV-0196 strcmp 기반 Flag 검증 패턴
- 검증이 여러 단계로 나뉘어 있다고 판단되면 → REV-0314 다단계 검증(Stage 1/2/3)이 있는 문제 공략법
- 문자열 비교가 최적화로 여러 CMP로 풀려서 헷갈린다면 → REV-0470 문자열 비교가 여러 CMP로 풀리는 최적화 패턴
- 체크섬이 표준 해시 상수와 일치하는지 확인하려면 → REV-0876 해시 함수 매직 상수 빠른 참조(MD5/SHA1/SHA256 초기값)

## 미니 예제
```c
// 체크섬 검증 + 복호화 결합 구조 예시(추정 재구성, 실제 문제 코드 아님)
unsigned int chk = 0;
for (int i = 0; name[i]; i++) {
    chk = (chk << 3) ^ name[i];
}
if (chk == 0xDEADBEEF) {
    for (int i = 0; i < flag_len; i++) {
        flag_buf[i] ^= name[i % name_len];   // 검증 통과한 이름을 그대로 복호화 키로 재사용
    }
    puts(flag_buf);
}
```
이런 "검증에 쓰인 입력을 복호화 키로도 재사용"하는 구조가 실제로 있는지는 확인되지 않았지만, 실버 티어 이름 검증 문제에서 자주 나타나는 패턴이므로 검증 함수 이후의 코드를 반드시 계속 따라가 볼 필요가 있다.
