## 한 줄 요약
simple-operation은 "아모"라는 캐릭터가 미션을 주는 컨셉의 드림핵 워게임 문제로, `nc`로 원격 서버에 접속해 실행되는 바이너리를 로컬에서 정적/동적으로 먼저 분석한 뒤, 서버가 요구하는 연산 결과를 만족하는 입력값을 계산해 넣으면 서버가 `flag` 파일 내용을 그대로 출력해 주는 구조다.

## 언제 검색해야 하나
- 문제 페이지에서 파일을 받아 `nc <host> <port>`로 접속했는데 무엇을 입력해야 할지 감이 안 잡힐 때
- 로컬에서 GDB로 실행해 입력값을 계산해서 통과를 확인했는데, 막상 실제 원격 서버에 같은 값을 넣으면 "Input" 프롬프트 뒤로 응답이 없고 멈춰 있을 때
- x64dbg 같은 Windows GUI 디버거로 분석을 시작했다가, 받은 파일이 리눅스용이라는 것을 늦게 깨닫고 GDB로 전환해야 할 때

## 핵심 개념
문제 설명은 "우리의 친구 아모가 미션을 주었습니다. 내가 원하는 결과가 나오도록 값을 입력해 줘!"라는 컨셉으로, 실질적으로는 표준적인 "입력 → 연산 → 목표값과 비교" 구조의 리버싱 문제를 캐주얼한 스토리로 감싼 것이다. 배포되는 파일은 리눅스 ELF 바이너리이고, 실제 채점은 `nc`로 접속한 원격 서버 프로세스가 담당한다. 즉 로컬에 내려받은 파일은 분석용 사본이고, 정답을 계산해 넣을 대상은 별도로 떠 있는 서버 인스턴스라는 점이 이 문제의 구조적 핵심이다. 서버가 실제로 담고 있는 `flag` 파일은 로컬 사본에는 없기 때문에, 로컬에서 아무리 잘 분석해도 최종적으로는 반드시 `nc` 접속을 통해 정답을 제출해야 실제 플래그를 얻을 수 있다.

바이너리 내부 로직은 이름 그대로 "간단한 연산(simple operation)"이다. 사용자로부터 정수 또는 문자열 입력을 받아 더하기·곱하기·비트 연산 등 몇 단계의 산술을 수행한 뒤, 그 결과가 프로그램 내부에 정해진 목표값과 일치하는지를 검사하고, 일치하면 `flag` 파일을 열어 그 내용을 그대로 표준출력으로 내보내는 흐름을 갖는다. 드림핵 커뮤니티 Q&A에서도 실제로 이 문제를 처음 접한 사용자가 "GDB로 파일을 받아 어셈블리 코드를 한 줄씩 뜯어보고 있다"거나 "GUI 기반 x64dbg에서 CUI 기반 GDB로 바꾸는 게 힘들었다"는 경험을 남긴 것이 확인되는데, 이는 이 문제의 바이너리가 리눅스 ELF라는 사실을 놓치고 Windows 디버거로 접근을 시도했다가 도구를 바꿔야 했던 사례로 해석할 수 있다.

## 화면/코드에서 보이는 징후
- `file` 명령으로 확인하면 ELF 64-bit 실행 파일로 나옴(Windows PE가 아님)
- 실행하면 값 입력을 요구하는 프롬프트가 뜨고, 이후 산술 연산을 거쳐 조건 분기로 이어지는 구조가 디스어셈블리에 보임
- 조건을 만족하면 파일을 여는 시스템 콜(`open`/`fopen` 계열)과 그 내용을 출력하는 코드가 뒤따라옴(로컬 사본에는 실제 `flag` 파일이 없으므로 이 경로는 로컬에서는 실패하거나 빈 내용을 출력함)

## 가장 먼저 할 것
받은 파일을 `file ./chall`로 확인해 ELF인지, 몇 비트인지부터 확인한다. Windows 도구가 아니라 GDB, `objdump`, `readelf` 같은 리눅스 계열 분석 도구로 접근 방향을 바로 잡는 것이 이 문제에서 가장 먼저 해야 할 일이다. 그 다음 로컬에서 GDB로 실행해 입력을 받는 지점과 비교 지점을 먼저 파악한다.

## 단계별 절차
1. `file ./chall`, `checksec ./chall`로 ELF 여부와 보호 기법을 확인한다.
2. `objdump -d ./chall` 또는 GDB의 `disassemble main`으로 입력을 받는 함수와 연산이 이루어지는 위치를 찾는다.
3. GDB에서 비교 직전 지점에 브레이크포인트를 걸고 실제로 값을 넣어보며 레지스터/스택에 남는 중간 연산 결과를 관찰한다.
4. 목표값과 연산 규칙(더하기/곱하기/비트연산 등)을 파악해, 목표값을 만들어내는 입력값을 손으로 계산하거나 짧은 Python 스크립트로 역산한다.
5. 로컬 바이너리에 같은 값을 넣어 분기가 "성공" 경로로 들어가는지 GDB로 먼저 검증한다(로컬에는 실제 flag 파일이 없어 출력 내용 자체는 다를 수 있음에 유의).
6. 문제 페이지에 안내된 `nc <host> <port>` 명령으로 실제 서버에 접속한다.
7. 서버 프롬프트에 동일한 입력값을 넣어 서버가 `flag` 파일 내용을 그대로 출력하는지 확인한다.

## 명령어/단축키
```bash
file ./chall
checksec ./chall
objdump -d ./chall
gdb ./chall
nc <host> <port>
```
GDB 안에서는 `b *0x<주소>`로 비교 직전에 브레이크포인트를 걸고, `run`으로 실행한 뒤 `x/`, `info registers`로 중간값을 확인하는 흐름이 기본이다.

## 출력 해석
서버가 정답을 받아들이면 별도의 "Correct" 문구 없이 곧바로 `flag` 파일의 내용(보통 `DH{...}` 형식)을 화면에 출력한다. 반대로 값이 틀리면 서버는 별다른 메시지 없이 연결을 끊거나 다음 입력을 다시 기다리는 경우가 있으므로, 응답이 없다고 해서 무조건 서버 오류로 판단하지 말고 입력 형식(개행 문자 포함 여부, 정수인지 문자열인지)부터 다시 점검해야 한다.

## 흔한 실수
- Windows용 도구(x64dbg, PE-bear)로 리눅스 ELF 바이너리를 분석하려고 시도하는 것 — 반드시 GDB/objdump/readelf 계열로 전환해야 한다.
- 로컬에서 계산한 입력값이 로컬 사본에서 성공 경로로 들어가는 것만 확인하고, 실제 `nc` 서버에는 접속하지 않아 진짜 플래그를 받지 못하는 것.
- 입력 형식을 맞추지 않아서(예: 개행 없이 보내거나, 문자열인데 정수로 보내는 등) 서버가 입력을 아예 받아들이지 못하고 멈춰 있는 것을 "문제 서버가 다운됐다"고 오해하는 것.

## 막혔을 때 다음 체크
- 서버에 값을 보내는 자동화 스크립트를 만들고 싶다면 → REV-0266 pwntools로 프로세스 실행하고 입력 보내기
- GDB 사용법 자체가 헷갈리면 → REV-0642 GDB 명령어 심화 치트시트(watch/catch/tbreak)
- 검증 로직을 코드로 그대로 재현해서 계산하고 싶다면 → REV-0222 검증 루틴을 Python으로 그대로 재현하기
- 원격 디버깅/연결 자체가 안 될 때는 → REV-0847 원격 디버깅(gdbserver) 연결이 안 될 때

## 미니 예제
```python
from pwn import *

target_value = 0x1234  # 바이너리 분석으로 알아낸 목표값
# 목표값을 만들어내는 입력값을 연산 규칙의 역순으로 계산했다고 가정
answer = str(target_value - 100)  # 실제 연산 규칙에 맞게 수정 필요

conn = remote("host", 1234)
conn.recvuntil(b"Input")
conn.sendline(answer.encode())
print(conn.recvall())
```
정확한 목표값과 연산 규칙은 실제 바이너리를 GDB로 분석해야 확정되므로, 위 스크립트는 "값을 계산해서 넣고 결과를 받는" 흐름을 보여주는 뼈대로만 참고한다.

## 출처/검증
- 문제 설명("아모가 미션을 주었다", nc 접속 안내, flag 파일 형식 DH{...})은 드림핵 공식 챌린지 페이지(https://dreamhack.io/wargame/challenges/836)에서 확인했다.
- 사용자가 x64dbg에서 GDB로 전환하며 어려움을 겪었다는 경험, 로컬 계산값이 원격 서버에서는 응답이 없었다는 사례는 드림핵 커뮤니티 Q&A 게시판 검색 결과에서 확인한 내용을 재구성했다(구체적 게시글 원문은 로그인 후에만 전체 열람이 가능해 검색 스니펫 수준으로만 확인됨).
- 검증 로직의 정확한 연산식과 목표값은 공개된 상세 write-up을 찾지 못해 이 문서에서 구체적으로 확정하지 않았으며, "미니 예제"의 값은 예시일 뿐 실제 정답이 아니다.
