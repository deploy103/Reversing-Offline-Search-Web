## 한 줄 요약
분석 도구(x64dbg, 인젝션 DLL)나 분석 대상 크랙미가 다운로드/압축 해제 직후 조용히 사라지거나 Windows Defender가 "위협이 발견됨" 알림을 띄운다면, 리버싱 도구와 패킹된 샘플이 휴리스틱 탐지에 흔히 걸리기 때문이므로 격리된 분석 환경을 만들고 그 폴더만 실시간 검사에서 제외하는 것이 정석적인 해결책이다.

## 언제 검색해야 하나
- x64dbg나 크랙미 파일을 다운로드/압축 해제한 직후 파일이 갑자기 사라지고 Windows Security 알림이 뜰 때
- DLL 인젝션 도구를 실행했는데 아무 반응이 없거나 대상 프로세스가 즉시 종료될 때
- SmartScreen이 "Windows에서 PC를 보호했습니다"라며 실행 자체를 막을 때
- 방화벽이 분석 중인 샘플의 네트워크 통신을 막아서 C2 통신이나 네트워크 동작을 관찰할 수 없을 때

## 가장 먼저 할 것
분석 전용 폴더(예: `C:\Analysis\`)를 하나 만들고, Windows Security → 바이러스 및 위협 방지 → 설정 관리 → 제외 추가/제거에서 그 폴더 전체를 실시간 검사 예외로 등록한다. 절대 시스템 전체 실시간 보호를 끄지 않는다 — 특정 폴더만 예외 처리하는 것이 안전하다.

## 핵심 개념
Windows Defender를 비롯한 대부분의 백신은 두 가지 방식으로 리버싱 작업을 방해한다.

1. **도구 자체를 탐지**: x64dbg, Cheat Engine류 메모리 편집 도구, 일부 인젝터/후킹 라이브러리는 정상적인 리버싱/디버깅 도구임에도 "해킹 도구(PUA/HackTool)" 시그니처로 분류되는 경우가 흔하다. 서명되지 않은 실행 파일이거나, 프로세스 메모리 조작·코드 인젝션과 같은 동작 패턴 자체가 악성코드와 유사하기 때문이다.
2. **분석 대상을 탐지**: CTF 크랙미는 종종 UPX 등으로 패킹되어 있거나, 문자열이 암호화되어 있거나, 안티디버깅 코드가 들어 있다. 이런 특징은 실제 악성코드의 특징과 겹치기 때문에 휴리스틱/행위 기반 탐지에 걸리기 쉽다.

이 문제를 근본적으로 해결하는 방법은 실시간 보호를 끄는 것이 아니라, 분석 작업을 하나의 격리된 공간(전용 폴더 + 가급적 별도 VM)에 몰아넣고 그 공간만 예외로 지정하는 것이다. 이렇게 하면 시스템 나머지 부분의 보호는 유지하면서 분석 작업만 방해받지 않는다.

## 화면/코드에서 보이는 징후
- 압축을 푼 직후 파일 탐색기에서 파일이 눈앞에서 사라진다.
- Windows Security 센터에 "위협이 발견됨" 또는 "격리된 위협"이라는 알림이 뜬다(대표적으로 `HackTool:Win32/...`, `PUA:Win32/...` 같은 탐지명이 붙는다).
- 인터넷에서 받은 실행 파일 실행 시 "Windows에서 PC를 보호했습니다" 문구와 함께 SmartScreen이 실행을 막는다.
- 인젝션 DLL을 로드하려는 시도가 아무 오류 메시지 없이 조용히 실패한다(백신이 `WriteProcessMemory`/`CreateRemoteThread` 같은 행위를 가로채 차단).

## 단계별 절차
1. Windows Security(작업 표시줄 검색 → "Windows 보안") → 바이러스 및 위협 방지를 연다.
2. "바이러스 및 위협 방지 설정" → "설정 관리"로 들어간다.
3. "제외 항목" → "제외 추가 또는 제거" → "제외 추가" → "폴더"를 선택해 분석 전용 폴더 전체를 등록한다.
4. 도구/샘플을 그 폴더 안으로 이동한 뒤 다시 시도한다.
5. SmartScreen이 개별 실행 파일을 막는다면 그 파일 속성(우클릭 → 속성) 하단에 "차단 해제" 체크박스가 있는지 확인하고 체크한다.
6. 가능하다면 스냅샷을 되돌릴 수 있는 격리된 VM(네트워크는 호스트 전용/차단 모드)에서 실제 실행/동적 분석을 수행해, 호스트 시스템 자체를 감염 위험에 노출시키지 않는다.

## 명령어/단축키
- Windows Security 열기: 작업 표시줄 검색 → `Windows 보안` 입력
- 예외 등록 경로: 바이러스 및 위협 방지 → 설정 관리 → 제외 항목 → 제외 추가/제거
- PowerShell(관리자)로 폴더 예외 등록: `Add-MpPreference -ExclusionPath "C:\Analysis"`
- 파일 차단 해제: 파일 우클릭 → 속성 → 일반 탭 하단 "차단 해제" 체크

## 출력 해석
- Windows Security 알림에 탐지명이 `HackTool:` 또는 `PUA:`로 시작하면 도구 자체가 리버싱/해킹 유틸리티 패턴으로 분류된 것이며 실제 악성코드가 아닐 가능성이 높다(다만 출처가 불분명한 파일이라면 항상 의심을 유지해야 한다).
- 탐지명이 `Trojan:`, `Backdoor:`, `Ransom:` 등으로 시작한다면 실제 악성코드일 가능성도 있으므로, 신뢰할 수 있는 출처(공식 CTF 플랫폼, 공식 도구 배포처)의 파일인지 다시 한번 확인한다.
- 인젝션이 조용히 실패한다면 백신 로그(Windows Security → 보호 기록)에서 최근 차단 이벤트를 확인해 정말 백신이 개입했는지부터 검증한다.

## 흔한 실수
- 문제를 빨리 해결하려고 Windows Defender 실시간 보호 전체를 꺼버리는 것 — 분석 중 실제로 위험한 샘플을 다루게 되면 호스트 전체가 무방비 상태가 된다. 폴더 단위 예외로 범위를 좁혀야 한다.
- 출처가 불분명한 파일을 "리버싱 도구겠거니" 하고 예외 처리해서 실제 악성코드를 무방비로 실행하는 것 — CTF/신뢰할 수 있는 공식 출처의 샘플에만 이 절차를 적용한다.
- 네트워크로 통신하는 악성코드성 샘플을 호스트에서 직접 실행하며 인터넷에 연결된 상태로 관찰하는 것 — 격리 VM + 호스트 전용 네트워크에서 관찰해야 안전하다.
- 예외 등록 후에도 도구가 안 뜨는 이유가 사실은 관리자 권한 문제(REV-0598)인데 계속 백신만 의심하는 것.

## 막혔을 때 다음 체크
- 예외 등록 후에도 attach/실행이 안 된다면 → REV-0598(관리자 권한 없어서 디버깅 막힐 때)을 확인한다.
- 도구는 정상 실행되는데 분석 대상만 이상하게 종료된다면 → 안티디버깅 문제일 수 있으므로 패킹 카테고리의 디버거 종료 체크리스트를 확인한다.
- 인젝션한 코드가 여전히 안 보인다면 → REV-0602(CreateRemoteThread로 생성된 코드가 안 보일 때)를 확인한다.

## 미니 예제
`x64dbg` 최신 릴리스를 다운로드해 `C:\Users\me\Downloads`에 압축을 풀었더니 몇 초 후 Windows Security 알림에 "위협이 격리되었습니다 - HackTool:Win32/..." 문구가 떴고 `x64dbg.exe`가 사라져 있었다. `C:\Analysis\tools\x64dbg`라는 전용 폴더를 만들고 이를 제외 항목에 등록한 뒤 다시 압축을 풀자, 이번에는 파일이 삭제되지 않고 정상적으로 남아 실행할 수 있었다.

## 관련 글
- REV-0598 — 관리자 권한이 없어서 디버깅이 막힐 때
- REV-0602 — CreateRemoteThread로 생성된 코드가 안 보일 때
- REV-0603 — 프로세스가 여러 개 자식 프로세스를 만들어 분석이 꼬일 때

## 출처/검증
- Windows Security(Defender)의 제외 항목 설정 경로와 `HackTool`/`PUA` 탐지 분류 체계는 Microsoft 공식 문서 기준이다.
- 리버싱/디버깅 도구가 행위 기반 탐지에 흔히 걸리는 이유(서명되지 않은 실행 파일, 프로세스 메모리 조작 패턴)는 일반적인 백신 휴리스틱 탐지 원리 기준이다.
- 격리 VM에서 미확인 샘플을 실행하는 것이 안전하다는 권고는 일반적인 악성코드 분석 실무 관행 기준이다.
