## 한 줄 요약
x64dbg가 특정 API 호출 뒤로 "멈춘 것처럼" 보이는 가장 흔한 원인은 디버거 자체가 죽은 게 아니라, **대상 프로그램이 실제로 무언가를 기다리고 있거나(대기 API), 화면 밖/뒤쪽에 숨겨진 다이얼로그가 떠 있거나, 무한 루프(안티디버깅 포함)에 들어간 것**이다. 먼저 "Pause"를 눌러 지금 어디서 멈춰 있는지부터 확인하면 원인을 대부분 바로 구분할 수 있다.

## 언제 검색해야 하나
- `ReadFile`, `recv`, `WaitForSingleObject`, `GetMessage` 같은 API를 지나간 뒤 x64dbg가 아무 반응이 없을 때
- Run(F9)을 눌렀는데 CPU 창이 갱신되지 않고 몇 초~몇 분째 그대로일 때
- 대상 프로그램(디버기, debuggee)의 창이 응답 없음(꺼짐 없음, `(응답 없음)`) 상태로 보일 때
- 브레이크포인트를 걸어뒀는데도 걸리지 않고 진행이 안 될 때(이 경우는 REV-0622도 함께 확인)

## 핵심 개념
"멈췄다"는 증상은 크게 세 가지 서로 다른 상황을 뭉뚱그려 표현한 것이다. 구분하지 않고 무작정 재시작하면 같은 문제를 반복해서 겪는다.

1. **정상적인 대기(Waiting)**: `WaitForSingleObject(handle, INFINITE)`, `recv()`(블로킹 소켓), `GetMessage()`(메시지 루프), `Sleep(큰 값)`처럼 원래 그 지점에서 무언가(사용자 입력, 네트워크 데이터, 이벤트 시그널)를 기다리도록 설계된 코드에 도달한 것. 디버거는 죽지 않았고, 프로그램이 "정상적으로 대기 중"이다.
2. **숨겨진 UI**: `MessageBoxW`, `DialogBox` 등이 호출되어 모달 창이 떴는데, 이 창이 메인 창 뒤에 가려져 있거나 화면 밖(음수 좌표)에 그려져서 사용자 눈에 안 보이는 경우. 프로그램은 그 다이얼로그에서 사용자가 버튼을 누르길 기다리고 있다.
3. **진짜 무한 루프**: 안티디버깅 루틴이 디버거를 감지하고 의도적으로 무한 루프에 빠지게 하거나, 타이밍 체크(`RDTSC`, `GetTickCount`) 실패 후 종료 대신 루프를 도는 경우. 또는 단순히 분석 대상 코드 자체에 로직 버그로 인한 무한 루프가 있는 경우.

x64dbg 자체가 응답 없음 상태가 되는 경우(디버거 UI 자체의 버그)는 상대적으로 드물며, 대부분은 위 세 가지 중 하나로 "디버기(대상 프로세스)"가 멈춘 것이다.

## 화면/코드에서 보이는 징후
- x64dbg 상단 상태 표시줄에 "Running"이 계속 떠 있고 CPU 창의 현재 명령어 하이라이트가 갱신되지 않음
- 작업 표시줄이나 Alt+Tab 목록에 원래 없던 창(다이얼로그)이 추가로 떠 있음
- Threads 창에서 스레드 상태가 "Waiting"으로 표시됨(대기 API에 들어간 경우 x64dbg가 이렇게 표시해주기도 함)
- CPU 사용률(작업 관리자 기준)이 한 코어에서 100%로 계속 유지되면 진짜 무한 루프일 가능성이 높고, 0%에 가깝게 유지되면 대기 상태일 가능성이 높음

## 가장 먼저 할 것
x64dbg 툴바의 **Pause(일시정지)** 버튼을 누른다. Run이 아니라 이미 멈춰 보이는 상태라도 Pause를 누르면 "지금 실제로 실행 중인 명령어 위치"로 CPU 창이 이동한다. 이 위치가 무엇을 하고 있는지가 원인 판별의 핵심 단서다.

## 단계별 절차
1. **Pause 후 현재 위치 확인**: CPU 창에 표시된 주소가 어느 모듈(ntdll, kernel32, ws2_32, 또는 대상 바이너리 자체)에 속하는지 확인한다.
2. **`ntdll!NtWaitForSingleObject`, `ntdll!NtDelayExecution`, `ws2_32!recv` 근처에서 멈췄다면**: 정상적인 대기 상태다. Call Stack 창을 열어 어떤 함수가 이 대기를 호출했는지 상위 프레임을 확인하고, 무엇을 기다리는지(이벤트? 소켓 데이터? 타이머?) 판단한다. 필요하면 그 대기를 유발한 조건(예: 서버 응답, 사용자 입력)을 충족시켜준다.
3. **작업 표시줄/Alt+Tab으로 숨은 창 확인**: 대상 프로세스의 다른 창이 있는지 Alt+Tab으로 확인한다. Windows 작업 관리자에서 해당 프로세스를 우클릭해 "창 활성화"를 시도해볼 수도 있다. 다이얼로그를 찾았다면 필요한 버튼을 눌러 진행시키거나, x64dbg에서 `MessageBoxW`에 브레이크포인트를 걸고 반환값을 강제로 조작해 넘어간다.
4. **대상 바이너리 자체 코드에서 멈췄다면(무한 루프 의심)**: 같은 주소 근처를 여러 번 Pause해서 반복 확인한다. 매번 비슷한 좁은 범위(루프)에 머무른다면 무한 루프다. `RDTSC`, `GetTickCount`, `IsDebuggerPresent` 같은 안티디버깅 API 근처인지 확인한다(REV-0130, REV-0131, 그리고 REV-0240 디버거에서 갑자기 종료될 때 체크리스트도 함께 참고할 만한 안티디버깅 패턴 목록이다).
5. **강제로 흐름 바꾸기**: 무한 루프의 조건 분기(`jz`/`jnz` 등)를 NOP 처리하거나 레지스터 값을 강제로 바꿔서 루프를 빠져나가게 패치한 뒤 계속 진행할 수 있다(REV-0184 x64dbg 패칭 참고).
6. **그래도 안 풀리면 재시작**: 위 방법으로도 원인을 못 찾으면 x64dbg와 대상 프로세스를 모두 종료하고, 이번엔 문제가 된 API 호출 "직전"에 미리 브레이크포인트를 걸어 재시작한다. 무작정 Run으로 끝까지 보내지 말고, 의심 API 하나씩 Step Over(F8)로 넘기면서 어느 호출에서 실제로 멈추기 시작하는지 좁혀나간다.

## 명령어/단축키
- x64dbg: Pause 버튼(또는 F12), Run(F9), Step Over(F8)
- x64dbg: Call Stack 창, Threads 창, Log 창(마지막 로그 메시지 확인)
- x64dbg: `bp MessageBoxW`로 숨은 다이얼로그 탐지
- 작업 관리자: 프로세스 CPU 사용률로 대기 vs 무한 루프 구분

## 출력 해석
- Pause 직후 CPU 창 주소가 `ntdll.dll`이나 `KERNELBASE.dll`의 `Nt*`/`Wait*` 함수 내부면 정상 대기다. 급하게 종료하지 말고 원인 조건을 채워준다.
- 같은 좁은 주소 범위(예: 0x401200~0x401210)를 Pause할 때마다 반복해서 보게 되면 무한 루프이며, 그 루프 진입 직전의 비교/분기 코드가 조작해야 할 지점이다.
- CPU 사용률이 낮게 유지되면서 멈춰 있다면 거의 확실히 "대기"이지 "멈춤(hang)"이 아니다.

## 흔한 실수
- Run만 누르고 Pause를 눌러보지 않은 채 "디버거가 죽었다"고 단정하고 강제 종료하는 것. Pause는 언제나 안전하게 현재 상태를 볼 수 있는 첫 번째 수단이다.
- 숨겨진 `MessageBox`를 못 찾고 계속 기다리는 것. 특히 콘솔 프로그램인데 내부적으로 GUI 다이얼로그를 띄우는 경우 놓치기 쉽다.
- 네트워크 문제(서버 미응답)인데 클라이언트 코드에서 원인을 찾으려는 것. `recv`에서 멈췄다면 서버 쪽 상태도 함께 확인해야 한다.
- 무한 루프를 발견하고 무작정 패치부터 하는 것. 그 루프가 안티디버깅 루프인지, 원래 프로그램 로직(예: 폴링)인지 먼저 Call Stack과 주변 코드로 구분한 뒤 패치 여부를 결정해야 한다.

## 막혔을 때 다음 체크
- 무한 루프가 아니라 브레이크포인트 자체가 안 걸리는 것 같다면 → REV-0622(브레이크포인트를 걸었는데 한 번도 안 걸릴 때)를 확인한다.
- 패킹/안티디버깅으로 디버거가 아예 튕기는 것과는 다른 증상이니, 갑자기 종료되는 경우라면 → REV-0240(디버거에서 갑자기 종료될 때 체크리스트)을 확인한다.
- 멀티스레드 프로그램이라 어느 스레드가 멈췄는지 헷갈린다면 → REV-0617(실행마다 API 호출 순서가 달라 보일 때)을 참고한다.

## 미니 예제
콘솔 프로그램을 x64dbg로 실행하고 `bp recv`로 멈춘 뒤 Run을 눌렀는데 CPU 창이 몇 분째 갱신되지 않았다. Pause를 누르자 다음 위치에서 멈춰 있는 것이 확인됐다.

```text
ntdll.dll!NtDeviceIoControlFile
Call Stack:
  ws2_32.dll!recv
  target.exe!ReceiveLoop+0x23
```

Call Stack을 보니 `recv`가 커널 I/O 대기 중이었다. 이는 서버로부터 데이터가 오기를 기다리는 정상적인 블로킹 상태였고, 실제로는 서버 프로세스가 먼저 실행되지 않아 연결만 되고 응답이 없었던 것이 원인이었다. 서버를 먼저 기동한 뒤 재시도하니 `recv`가 정상적으로 반환됐다.

## 관련 글
- REV-0622 — 브레이크포인트를 걸었는데 한 번도 안 걸릴 때(x64dbg)
- REV-0240 — 디버거에서 갑자기 종료될 때 체크리스트
- REV-0617 — 실행마다 API 호출 순서가 달라 보일 때(멀티스레드)

## 출처/검증
- `WaitForSingleObject`, `recv`, `GetMessage`, `MessageBoxW`의 블로킹 동작과 시그니처는 Microsoft Win32 API 및 Winsock 공식 문서 기준이다.
- x64dbg의 Pause/Run 동작과 Call Stack/Threads 창 기능은 x64dbg 공식 문서 기준이다.
- 미니 예제의 구체적 상황과 주소값은 설명을 위해 구성한 예시다(2026-09-08 기준 서술).
