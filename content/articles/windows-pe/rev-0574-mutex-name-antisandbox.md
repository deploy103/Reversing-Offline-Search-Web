## 한 줄 요약
`CreateMutex`(또는 `CreateMutexEx`)로 특정 이름의 뮤텍스(mutex, 상호 배제 객체)를 만든 뒤 `GetLastError()`로 `ERROR_ALREADY_EXISTS`가 리턴되는지 확인하는 코드는, 정상적인 프로그램에서는 "같은 프로그램이 이미 실행 중이니 중복 실행을 막는다"는 흔한 용도로 쓰이지만, 악성코드에서는 자동 분석 샌드박스가 같은 샘플을 여러 번 재실행하며 행위를 관찰하는 것을 막거나, 특정 뮤텍스 이름의 존재 여부로 "이미 감염된 환경인지" 자가 판단하는 용도로도 쓰이며, 특이한 뮤텍스 이름 자체가 악성코드 패밀리를 식별하는 IOC(침해 지표)로 활용되기도 한다.

## 언제 검색해야 하나
- 코드에서 `CreateMutexA`/`CreateMutexW` 호출 직후 `GetLastError()`를 부르고 그 결과가 `ERROR_ALREADY_EXISTS`(값 183)인지 비교하는 패턴을 발견했을 때
- 악성코드 분석 리포트에서 특정 이름의 뮤텍스가 IOC로 기록된 것을 보고 그 뮤텍스가 코드에서 어떻게 쓰이는지 확인하고 싶을 때
- 같은 샘플을 두 번 실행했더니 두 번째부터는 아무 일도 안 일어나는 현상을 조사할 때
- 샘플이 실행 초반에 이상하게 생긴(무작위 문자열, 특정 캠페인 이름 등) 문자열을 뮤텍스 이름으로 쓰는 것을 발견했을 때

## 핵심 개념
`CreateMutex`는 원래 Windows 프로그래밍에서 여러 프로세스/스레드가 공유 자원에 동시에 접근하는 것을 막기 위한 동기화 객체를 만드는 API다. 그런데 이름이 있는(named) 뮤텍스는 시스템 전역(커널 오브젝트 네임스페이스)에 등록되므로, 이를 "이 프로그램의 인스턴스가 이미 실행 중인지 확인하는 용도"로 응용하는 것이 매우 흔한 패턴이다.

동작 원리:

```c
HANDLE hMutex = CreateMutexA(NULL, TRUE, "MyUniqueMutexName");
if (GetLastError() == ERROR_ALREADY_EXISTS) {
    // 이미 같은 이름의 뮤텍스가 존재 → 다른 인스턴스가 이미 실행 중
    ExitProcess(0);
}
```

`CreateMutex`는 이름이 같은 뮤텍스가 이미 시스템에 존재하면, **새로 만들지 않고 기존 뮤텍스에 대한 핸들을 그대로 리턴**하면서 `GetLastError()`가 `ERROR_ALREADY_EXISTS`(183)를 리턴하도록 설정한다. 이 리턴값 자체가 함수 성공/실패와는 별개의 신호이므로, 반환된 핸들이 `NULL`이 아니더라도 반드시 `GetLastError()`를 확인해야 "새로 만든 것"과 "기존 것을 재사용한 것"을 구분할 수 있다.

악성코드/샌드박스 회피 관점에서 이 패턴이 쓰이는 이유는 두 가지다.

1. **자동 분석 샌드박스 우회**: 많은 자동화 분석 시스템이 같은 샘플을 여러 설정(다른 시간, 다른 네트워크 조건 등)으로 반복 실행하며 행위를 수집한다. 이때 이전 실행에서 만든 뮤텍스가 아직 살아있는(또는 같은 이름을 재사용하는) 상황이면, 악성코드는 "이미 분석 중"으로 판단해 두 번째 실행부터는 페이로드를 실행하지 않고 조용히 종료할 수 있다. 다만 이 시나리오는 뮤텍스가 프로세스 종료 시 자동 해제되므로 완벽하지는 않고, 주로 "같은 세션에서 자기 자신의 중복 실행"을 막는 원래 목적과 "감염 표시(infection marker)"로서의 목적이 섞여 쓰인다.
2. **감염 마커(infection marker)**: 특정 고정된 이름의 뮤텍스가 시스템에 존재하는지를, 악성코드 자신이 "이 시스템은 이미 감염되어 있다"는 표시로 사용하는 경우도 있다. 이 경우 뮤텍스는 실행이 끝나도 사라지지 않도록 별도 프로세스가 유지하거나, 레지스트리 값과 함께 조합해서 쓰이기도 한다.

보안 분석/위협 인텔리전스 관점에서는 반대로 이 뮤텍스 이름이 매우 유용하게 쓰인다. 특정 악성코드 패밀리가 항상 같은(또는 규칙적인 패턴의) 뮤텍스 이름을 쓰는 경우, 그 이름 자체가 YARA 룰이나 IOC 목록에 올라가는 강력한 탐지 지표가 된다.

## 화면/코드에서 보이는 징후
- `call CreateMutexA`(또는 `CreateMutexW`) 직후 `call GetLastError`, 그 결과를 `0xB7`(183, `ERROR_ALREADY_EXISTS`)와 비교하는 `cmp`/`jz`
- `CreateMutexA`의 세 번째 인자(뮤텍스 이름 문자열)가 리소스나 암호화된 블록에서 복호화되어 나오는 경우 — 이름을 정적으로 숨기려는 시도
- 뮤텍스 이름이 GUID처럼 생겼거나, 특정 캠페인/버전 문자열이 포함된 경우(예: `Global\\XYZBotv2`)
- 프로그램을 두 번 연속 실행했을 때 두 번째 실행이 아무 동작 없이 즉시 종료됨

## 가장 먼저 할 것
1. `CreateMutexA`/`CreateMutexW` 호출을 찾아 세 번째 인자(뮤텍스 이름)를 확인한다. 문자열이 바로 안 보이면 리소스 섹션(REV-0141 참고)이나 문자열 복호화 루틴을 따라가 실제 값을 알아낸다.
2. 이 이름을 알려진 악성코드 IOC 데이터베이스(예: 공개 위협 인텔리전스 자료)와 대조해보면 샘플의 패밀리/캠페인을 특정하는 데 도움이 될 수 있다.

## 단계별 절차
**1) 뮤텍스 생성/확인 로직 위치 파악**
- IDA에서 `CreateMutexA`/`CreateMutexW`의 xref를 확인해 호출 지점으로 이동한다.
- 바로 다음에 `GetLastError` 호출과 `ERROR_ALREADY_EXISTS`(183, `0xB7`) 비교가 있는지 확인하고, 비교 결과에 따른 분기(정상 진행 vs 종료)를 표시해둔다.

**2) 뮤텍스 이름 문자열 확보**
- 이름 인자가 정적 문자열이면 IDA에서 바로 읽힌다.
- 동적으로 생성/복호화되는 경우, x64dbg로 `CreateMutexA` 호출 직전에 브레이크포인트를 걸고 세 번째 인자(x86: 스택 `[esp+8]`, x64: `R8`)가 가리키는 메모리를 `Follow in Dump`로 확인해 실제 문자열을 읽는다.

**3) 우회 방법 선택**
- **우회 방법 A(비교 분기 패치)**: `cmp eax, 0B7h` 다음의 조건 분기를 강제로 "정상 진행" 쪽으로 가도록 패치한다. 가장 확실한 방법이다.
- **우회 방법 B(사전 뮤텍스 미생성)**: 만약 반대 시나리오(뮤텍스가 이미 있어야 정상 동작하는 감염 마커형 로직)라면, 분석 전 미리 같은 이름의 뮤텍스를 직접 만들어두는 소형 도구를 작성해 실행한 뒤 샘플을 실행하는 방식으로 조건을 맞출 수 있다.

**4) 다른 실행 인스턴스와의 충돌 확인**
- 동일 샘플을 여러 번 실행하며 분석 중이라면, 이전 실행의 프로세스가 아직 살아있어 뮤텍스를 쥐고 있는 것은 아닌지 작업 관리자에서 확인한다. 이전 인스턴스를 완전히 종료해야 재분석 시 혼란을 피할 수 있다.

## 명령어/단축키
- IDA: `X`(교차 참조), `Shift+F12`(문자열 뷰에서 뮤텍스 이름 검색)
- x64dbg: `F2`(브레이크포인트), 인자 메모리 `Follow in Dump`, 비교 분기 명령어 우클릭 `Assemble`로 패치
- Sysinternals `Process Explorer`/`Process Hacker`의 Handle 뷰에서 `Mutant`(커널 오브젝트 타입) 목록을 확인하면 실행 중인 프로세스가 어떤 이름의 뮤텍스를 쥐고 있는지 직접 볼 수 있다.

## 출력 해석
- `GetLastError() == ERROR_ALREADY_EXISTS`(183)가 참이면 이 프로세스 실행 이전에 같은 이름의 뮤텍스를 만든 무언가(자기 자신의 이전 인스턴스, 또는 다른 악성코드 컴포넌트)가 아직 살아있다는 뜻이다.
- 프로세스가 종료되면 그 프로세스가 소유한 이름 있는 뮤텍스도 자동으로 해제되므로(핸들을 다른 프로세스가 열어두지 않은 이상), 재실행 시 다시 `ERROR_ALREADY_EXISTS`가 나온다면 뮤텍스를 쥔 다른 프로세스가 여전히 살아있다는 뜻이다.

## 흔한 실수
- `CreateMutex`의 리턴 핸들이 `NULL`이 아니라고 해서 "성공적으로 새로 만들어졌다"고 단정하는 것. 반드시 `GetLastError()`를 확인해야 새로 만든 것인지 기존 것을 재사용한 것인지 알 수 있다.
- 뮤텍스 이름만 보고 바로 "이 샘플은 특정 패밀리다"라고 단정하는 것. 이름이 재사용되거나 변형되는 경우도 많으므로 다른 IOC(파일 해시, C2 도메인 등)와 함께 교차 검증해야 한다.
- 분석 중 이전 실행 프로세스를 완전히 종료하지 않아 두 번째 실행이 "이미 실행 중"으로 오판되는 것을 "안티디버깅이 발동했다"고 착각하는 것.
- 뮤텍스 이름에 `Global\` 접두사가 붙어 있는 경우와 붙지 않은 경우(세션별 네임스페이스 vs 전역 네임스페이스)의 차이를 무시하는 것 — 원격 데스크톱/다중 세션 환경에서 동작이 달라질 수 있다.

## 막혔을 때 다음 체크
- 뮤텍스 체크와 함께 대기 시간도 확인한다면 → REV-0573(Sleep 남용과 안티디버깅/안티샌드박스 기법)을 함께 본다.
- 뮤텍스 이름 문자열이 암호화되어 있다면 → REV-0128(Windows 문자열 ASCII와 UTF-16 찾기)의 문자열 복호화 흔적 찾기 방법을 참고한다.
- 이 체크 외에도 실행 환경 자체를 탐지하는 코드가 더 있다면 → REV-0575(환경변수/사용자명으로 분석 환경을 탐지하는 기법)를 확인한다.

## 미니 예제
```c
HANDLE hMutex = CreateMutexA(NULL, TRUE, "Global\\a8f3e91c-...");
if (GetLastError() == ERROR_ALREADY_EXISTS) {
    CloseHandle(hMutex);
    ExitProcess(0);  // 이미 실행 중(또는 이미 분석 중) → 조용히 종료
}
// 여기부터 실제 악성 행위 시작
```
샌드박스가 같은 샘플을 짧은 간격으로 재실행하며 여러 각도(다른 인자, 다른 시간)로 관찰하려 할 때, 첫 실행이 뮤텍스를 쥔 채 아직 살아있으면 두 번째 실행은 이 검사에서 즉시 종료되어 아무 행위도 리포트에 남기지 않는다. 분석자는 `GetLastError() == ERROR_ALREADY_EXISTS` 비교 직후의 분기를 x64dbg에서 강제로 반대로 만들어(항상 "새로 생성됨"으로 처리) 우회하거나, 애초에 다른 이름의 뮤텍스를 쓰도록 실행 인자/환경을 바꿔 재현할 수 있다.

## 관련 글
- REV-0573 — Sleep 남용과 안티디버깅/안티샌드박스 기법
- REV-0575 — 환경변수/사용자명으로 분석 환경을 탐지하는 기법
- REV-0128 — Windows 문자열 ASCII와 UTF-16 찾기
- REV-0141 — Resource Section과 숨겨진 데이터 확인

## 출처/검증
- `CreateMutexA`/`CreateMutexW`의 시그니처, `ERROR_ALREADY_EXISTS`(183) 값과 리턴 동작은 Microsoft Learn Win32 API 공식 문서 기준이다.
- 뮤텍스 이름을 이용한 중복 실행 방지 및 샌드박스 회피 패턴은 다수의 공개 악성코드 분석 리포트와 위협 인텔리전스 자료에서 공통적으로 다루는 표준 기법이다(2026-09-08 기준 서술).
