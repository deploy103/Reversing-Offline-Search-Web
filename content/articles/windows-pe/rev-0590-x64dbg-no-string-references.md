## 한 줄 요약
x64dbg에서 우클릭 → `Search for` → `String references`를 실행했는데 목록이 텅 비는 가장 흔한 이유는, 그 스캔이 **지금 이 순간 메모리에 실제로 올라와 있는 바이트**만 훑기 때문이며, 패킹/암호화된 바이너리라면 아직 압축이 풀리거나 복호화되지 않은 시점에 스캔했기 때문이므로 압축 해제 루틴을 지난 뒤(OEP 근처)에 다시 스캔해야 한다.

## 언제 검색해야 하나
- x64dbg CPU 탭에서 우클릭 → `Search for → Current Module → String references`(또는 `All Modules`)를 실행했는데 결과 목록이 비어 있거나 의미 없는 잡음만 뜰 때
- IDA로 정적 분석할 때는 문자열이 분명히 보였는데, 같은 파일을 x64dbg로 열면 하나도 안 보일 때
- Detect It Easy로 확인해보니 UPX 등으로 패킹된 파일인데 x64dbg 문자열 검색 결과가 이상할 때

## 핵심 개념
x64dbg의 String references 기능은 지정한 범위(현재 모듈 또는 전체 모듈)의 **현재 커밋된 메모리 페이지**를 실제로 읽어서, ASCII/UTF-16 문자열처럼 보이는 바이트 패턴을 찾아 그 문자열을 참조하는 코드 위치와 함께 나열해주는 정적 스캔이다. 여기서 중요한 것은 이 스캔이 **스캔을 실행한 그 순간의 메모리 상태**만 본다는 점이다.

패커(UPX, Themida, VMProtect 등)로 압축된 실행 파일은 디스크상의 `.text`/`.rdata` 섹션에 원본 코드/문자열이 그대로 있지 않고, 대신 압축된 스텁 코드와 압축 데이터만 있다. 프로세스가 실행되면 스텁 코드가 먼저 실행되어 원본 코드/문자열을 압축 해제한 뒤에야 실제 OEP(Original Entry Point)로 점프한다. 만약 x64dbg가 파일을 로드한 직후, 즉 아직 스텁이 실행되기 전이나 실행 중인 시점에 문자열 검색을 돌리면 메모리에는 아직 압축된(사람이 읽을 수 없는) 바이트만 있으므로 검색 결과가 텅 비거나 의미 없는 잡음만 나온다.

암호화되지 않은 일반 바이너리인데도 결과가 비어 있다면, 검색 범위를 잘못 지정했거나(`Current Module`인데 실제 문자열이 다른 DLL에 있는 경우 등), 문자열이 너무 짧아 휴리스틱 최소 길이 기준(보통 3자 이상)에 못 미쳐 걸러졌을 가능성도 있다.

## 화면/코드에서 보이는 징후
- `Search for → String references` 실행 결과 창이 완전히 비어 있거나, 있어도 몇 개 안 되고 의미가 없어 보임
- Detect It Easy로 확인했을 때 "UPX", "Themida", "VMProtect" 등 패커 시그니처가 검출됨
- IDA 정적 분석(Strings 창, `Shift+F12`)에서는 문자열이 다수 보이는데, x64dbg 동적 분석에서는 같은 문자열이 안 보임
- x64dbg로 프로세스를 진입점 근처에서 멈춘 직후(패킹 스텁 실행 이전)에 검색을 시도한 상태

## 가장 먼저 할 것
Detect It Easy(REV-0126)로 대상 파일이 패킹되어 있는지부터 확인한다. 패킹되어 있다면 문자열 검색을 지금 시도할 게 아니라, 먼저 언패킹 스텁을 지나 OEP 근처까지 실행을 진행한 뒤 다시 검색해야 한다.

## 단계별 절차
**1) 패킹 여부 확인**
- Detect It Easy로 파일을 열어 상단 결과 창에 패커/컴파일러 시그니처가 뜨는지 확인한다.

**2) 언패킹 스텁을 지나 실행 진행**
- x64dbg에서 파일을 열고, 반복되는 압축 해제 루프를 눈으로 스텝하기보다는 실행 흐름이 급격히 다른 메모리 영역(원래 이미지 밖에 새로 할당된 영역이나 원본 섹션)으로 점프하는 지점을 찾는다. 흔한 방법은 `Memory Map` 탭에서 실행 가능(Execute) 권한이 새로 부여되는 페이지를 지켜보거나, 메모리 쓰기 브레이크포인트(하드웨어 브레이크포인트, `Memory Access` 조건)를 원본 코드 섹션에 걸어 그 섹션에 처음 쓰기가 끝나는 시점을 잡는 것이다.
- OEP로 추정되는 지점(원래 IDA에서 보던 함수들이 다시 보이기 시작하는 위치)에 도달하면 실행을 멈춘다.

**3) 그 시점에서 다시 문자열 검색**
- CPU 탭에서 우클릭 → `Search for → Current Module → String references`(또는 필요하면 `All Modules`)를 다시 실행한다. 이제 압축이 풀린 실제 코드/데이터가 메모리에 있으므로 원본 문자열이 정상적으로 나열된다.

**4) 필요하면 메모리를 덤프해서 정적 도구로 재분석**
- `Memory Map` 탭에서 원본 코드가 복원된 영역을 우클릭 → `Dump Memory to File`로 저장한 뒤, 그 덤프 파일을 IDA나 PE-bear로 다시 여는 방식이 반복 작업 없이 더 편할 수 있다.

## 명령어/단축키
```text
x64dbg: CPU 탭 우클릭 → Search for → Current Module/All Modules → String references
x64dbg: Memory Map 탭 → 우클릭 → Dump Memory to File
x64dbg: 하드웨어 브레이크포인트(Memory, Write) 설정으로 원본 섹션 복원 시점 포착
```

## 출력 해석
- 검색 결과 목록에 사람이 읽을 수 있는 실제 문자열(에러 메시지, 포맷 문자열, URL 등)과 그 문자열을 참조하는 명령어 주소가 함께 뜨면 정상적으로 원본 코드 영역을 스캔한 것이다.
- 여전히 결과가 이상하거나 깨진 문자만 나온다면, 아직 압축 해제가 완전히 끝나지 않은 더 이른 시점을 스캔했을 가능성이 크므로 실행을 조금 더 진행한 뒤 재시도한다.

## 흔한 실수
- 진입점에 도달하자마자(패킹 스텁 실행 전) 문자열 검색을 시도하고 "이 파일엔 문자열이 없다"고 결론짓는 것.
- `Current Module`로만 검색하고 실제 문자열이 다른 로드된 DLL이나 동적으로 할당된 힙 영역에 있는 경우를 놓치는 것 — 이럴 땐 `All Modules`나 특정 메모리 범위 지정 검색을 시도한다.
- 검색 결과가 나왔다고 그게 전부라고 믿는 것 — 문자열이 실행 중 특정 분기 이후에만 동적으로 조립(예: XOR 복호화)되는 경우, 그 분기를 지나기 전에는 여전히 안 보일 수 있다.

## 막혔을 때 다음 체크
- 이 파일이 패킹된 게 맞는지부터 확실히 하고 싶다면 → REV-0126(Detect It Easy로 컴파일러 패커 확인)을 먼저 실행한다.
- OEP를 못 찾겠다면 → REV-0585(Entry Point를 찾을 수 없다는 오류가 뜰 때)와 함께 하드웨어 브레이크포인트/메모리 접근 브레이크포인트 활용법을 익힌다.
- 문자열은 찾았는데 무슨 뜻인지 인코딩이 헷갈리면 → REV-0128(Windows 문자열 ASCII와 UTF-16 찾기)을 참고한다.

## 미니 예제
UPX로 패킹된 파일을 x64dbg로 열자마자 `Search for → String references`를 돌리면 결과가 거의 없거나 `UPX0`, `UPX1` 같은 섹션 이름만 스치듯 보인다. 대신 실행을 진행하며 `Memory Map`을 관찰하다가, 원래 `UPX1`이었던 영역에 실행 권한이 부여되고 코드가 채워지는 시점(전형적으로 `popad` 계열 명령 직후 큰 `jmp`가 원본 코드로 점프하는 지점)에서 실행을 멈춘 뒤 다시 문자열 검색을 하면, `"Enter password:"` 같은 원본 문자열들이 비로소 목록에 나타난다.

## 관련 글

- REV-0128 — Windows 문자열 ASCII와 UTF-16 찾기

- REV-0127 — x64dbg로 EXE 첫 분석 시작

## 출처/검증
- 패킹된 바이너리의 문자열/코드가 런타임에 메모리 상에서 복원된다는 동작 원리는 UPX 등 공개 패커의 공식 문서와 다수의 언패킹 튜토리얼에서 공통적으로 확인되는 사실이다.
- x64dbg `Search for → String references` 메뉴 경로와 스캔 범위 옵션은 x64dbg 공식 문서 및 실제 도구 사용 관찰 기준이며, 버전에 따라 메뉴 문구가 다를 수 있다(2026-09-08 기준 서술).
