## 한 줄 요약
`Sleep`을 비정상적으로 길게(수십 초~수 분) 호출하는 코드는 단순한 버그가 아니라, 자동화된 악성코드 분석 샌드박스가 보통 정해진 짧은 시간(수십 초~수 분)만 프로세스를 관찰하고 종료한다는 점을 노려 "샌드박스의 관찰 시간이 끝날 때까지 그냥 잠들어 있다가, 감시가 끝난 뒤에야 실제 페이로드를 실행"하는 회피 기법(Sleep-based sandbox evasion)일 가능성이 높으며, 여기에 더해 `Sleep` 호출 자체를 안티디버깅 타이밍 체크에 결합하는 변형도 흔하다.

## 언제 검색해야 하나
- 프로그램을 실행했는데 눈에 보이는 반응 없이 한참을 멈춰 있는 것처럼 보일 때
- 디스어셈블리에서 `Sleep(60000)`처럼 매우 큰 밀리초 값이 인자로 들어가는 호출을 발견했을 때
- 자동화 분석 샌드박스 리포트에는 "특별한 행위 없음"으로 나오는데, 실제로 몇 분 이상 실행해보면 악성 행위가 시작되는 샘플을 만났을 때
- `Sleep` 호출이 여러 번 나뉘어(짧은 구간을 반복) 있는 패턴을 봤을 때

## 핵심 개념
자동화 악성코드 분석 샌드박스(Cuckoo Sandbox류, 각종 상용 샌드박스)는 리소스와 시간 제약 때문에 보통 프로세스를 수십 초에서 길어야 몇 분 정도만 관찰하고 리포트를 생성한 뒤 종료시킨다. 공격자는 이 사실을 알고 있으므로, 진짜 악성 행위(C2 연결, 파일 암호화, 드롭퍼 실행 등)를 시작하기 전에 그 관찰 시간보다 긴 `Sleep`을 걸어 "아무 일도 안 일어나는 것처럼" 보이게 만든다. 관찰 시간이 끝나고 샌드박스가 분석을 종료한 뒤(또는 정상 사용자 환경에서 시간이 지난 뒤)에야 실제 코드가 실행되므로, 리포트에는 악성 행위가 전혀 기록되지 않는다.

주로 쓰이는 API/기법들:

- **`Sleep(DWORD dwMilliseconds)`**: 가장 기본적인 대기 함수. 인자로 밀리초 단위 시간을 받는다. `INFINITE`(0xFFFFFFFF)를 넘기면 무한 대기.
- **`SleepEx`**: `Sleep`과 유사하지만 alertable 대기(APC 큐 처리 가능)를 지원.
- **`NtDelayExecution`**: `Sleep`이 내부적으로 호출하는 더 낮은 레벨의 ntdll 네이티브 API. `Sleep` API 자체를 후킹해서 탐지/우회하는 보안 도구를 피하기 위해 이 네이티브 API를 직접 호출하는 악성코드도 있다.
- **누적/분할 Sleep**: 한 번에 큰 값을 `Sleep`하지 않고, 짧은 `Sleep`을 반복 호출하며 누적 시간을 계산하는 패턴. 일부 샌드박스가 "Sleep 호출 시 시간을 건너뛰는(time acceleration/skip)" 패치를 적용하는 것에 대응하기 위한 변형이다. 반복문 안에서 `Sleep(100)`을 수천 번 호출하며 매 반복마다 `GetTickCount`로 실제 경과 시간을 확인해, 시간이 "너무 빨리" 지났으면(즉 샌드박스가 Sleep을 가속시켰으면) 이상 환경으로 판단하는 결합 기법도 있다.
- **`WaitForSingleObject`를 이용한 위장 대기**: 실제로는 신호가 오지 않을 이벤트/뮤텍스 핸들에 긴 타임아웃을 걸어 사실상 `Sleep`과 같은 효과를 내면서 API 이름만 다르게 하는 변형.

## 화면/코드에서 보이는 징후
- `call Sleep`에 바로 앞서 `push`(x86) 또는 `mov ecx, N`(x64)로 매우 큰 상수(예: `0xEA60` = 60000ms = 60초, 또는 `0x927C0` = 600000ms = 10분)가 들어가는 코드
- 반복문 안에서 짧은 `Sleep` 호출과 카운터 증가가 함께 있고, 카운터가 특정 값에 도달해야 다음 단계로 넘어가는 구조
- `Sleep` 직후에 `GetTickCount`를 호출해 실제 경과 시간과 예상 시간을 비교하는 코드(REV-0572와 결합된 패턴)
- Import Table에 `Sleep`이 없고 대신 `ntdll.dll`의 `NtDelayExecution`을 동적으로(REV-0129 참고) 해결해서 쓰는 코드

## 가장 먼저 할 것
1. `Sleep`/`SleepEx`/`NtDelayExecution` 호출의 xref를 모두 나열해 인자로 들어가는 값이 얼마나 큰지 확인한다. 수 초 이내면 정상적인 UI 딜레이일 가능성이 크고, 수십 초 이상이면 샌드박스 회피를 의심한다.
2. 해당 `Sleep` 호출 직후에 실제로 어떤 코드가 실행되는지(단순 로직 계속 진행인지, 아니면 눈에 띄게 다른 동작—네트워크 연결, 파일 암호화 등—이 시작되는지) 확인한다.

## 단계별 절차
**1) 정적으로 대기 시간 규모 파악**
- IDA에서 `Sleep` 호출의 인자(밀리초)를 16진수에서 10진수로 변환해 실제 몇 초/몇 분인지 계산한다. 예: `0x493E0` = 300000ms = 5분.
- 반복 Sleep 패턴이면 `Sleep` 인자 × 반복 횟수로 총 대기 시간을 추정한다.

**2) x64dbg로 Sleep 호출을 가속/무력화**
- `kernel32!Sleep`(또는 `ntdll!NtDelayExecution`) 함수 시작 주소에 브레이크포인트를 걸고, 함수에 진입할 때마다 인자(x86은 스택 `[esp+4]`, x64는 `RCX`)를 강제로 작은 값(예: 10)으로 바꿔서 실제 대기 없이 바로 다음 코드로 넘어가게 만든다.
- x64dbg 스크립트(`Script` 탭 또는 조건부 브레이크포인트의 "Command on hit")로 이 레지스터/스택 조작을 자동화하면, 매번 수동 개입 없이 실행 내내 Sleep을 무력화할 수 있다.
- 또는 더 간단히, `call Sleep` 명령어 자체를 `nop`으로 패치해 호출 자체를 건너뛰는 방법도 있다(단, 리턴값이나 부수효과에 의존하는 코드가 없는지 먼저 확인).

**3) Sleep 이후 실제 행위 관찰**
- Sleep을 무력화한 뒤 실행을 계속하면서, `Sleep` 직후에 어떤 API들이 새로 호출되는지(네트워크, 파일, 레지스트리 API) 관찰한다. 이 시점부터가 진짜 분석해야 할 핵심 로직인 경우가 많다.

**4) 시간 가속 탐지 대응 코드가 있는 경우**
- `Sleep` 전후로 `GetTickCount` 비교가 함께 있다면(REV-0572 참고), `Sleep` 인자만 줄이지 말고 `GetTickCount`의 리턴값도 함께 일관되게 조작해야 "시간이 비정상적으로 안 흘렀다"는 탐지를 피할 수 있다. 두 조작을 따로따로 하면 서로 모순되는 값 때문에 탐지될 수 있다.

## 명령어/단축키
- IDA: `X`(교차 참조로 Sleep류 호출 지점 나열), 16진수 계산은 IDA 하단 상태바나 계산기 뷰(`Alt+Y`가 아니라 값 위에서 우클릭 후 `10진수로 보기`) 활용
- x64dbg: `F2`(브레이크포인트), 함수 진입 시 인자 레지스터/스택 값을 `수정`(Modify)으로 강제 변경, `Script` 탭에서 자동화 스크립트 작성
- x64dbg 명령창: `bp Sleep`(Sleep 함수에 브레이크포인트), `SetBPX ntdll.NtDelayExecution` 등 명령줄 방식도 가능

## 출력 해석
- `Sleep` 인자를 줄여 무력화한 뒤에도 프로그램이 여전히 눈에 띄는 동작을 안 하면, 진짜 로직은 다른 조건(사용자 입력 대기, 특정 날짜 도달 등)에 걸려 있을 수 있으므로 추가 확인이 필요하다.
- `Sleep` 무력화 직후 갑자기 CPU 사용률이 오르거나 네트워크 연결 시도가 관찰되면, 원래 그 시점 이후가 실제 페이로드 실행 구간이었다는 뜻이다.

## 흔한 실수
- `Sleep` 호출을 그냥 "UI 딜레이겠지"라고 넘겨짚고 인자 값을 확인하지 않는 것. 몇 초 정도의 짧은 Sleep은 정상일 수 있지만, 수십 초~수 분 단위는 반드시 의심해야 한다.
- `Sleep` 인자만 패치하고 `GetTickCount` 등 시간 검증 로직은 그대로 둬서, 프로그램이 "시간이 이상하게 빨리 지났다"고 자체적으로 탐지해버리는 것.
- 반복 Sleep 패턴에서 반복 횟수(카운터)까지 확인하지 않고 첫 번째 `Sleep` 인자만 보고 총 대기 시간을 과소평가하는 것.
- `Sleep`을 완전히 nop으로 지워서 부수효과(예: alertable 대기 중 APC 처리)에 의존하는 코드가 깨지는 것을 간과하는 것 — 가능하면 인자만 줄이는 방식이 더 안전하다.

## 막혔을 때 다음 체크
- Sleep과 함께 시간 비교 로직이 쓰인다면 → REV-0572(GetTickCount와 QueryPerformanceCounter 시간측정 안티디버깅)를 함께 확인한다.
- Sleep을 우회했는데도 여전히 실행 환경을 감지하는 것 같다면 → REV-0574(Mutex 이름으로 중복 실행 방지/샌드박스 회피 판단하기), REV-0575(환경변수/사용자명으로 분석 환경을 탐지하는 기법)를 참고한다.
- API가 동적으로 해결되어 Import Table에 안 보이는 경우 → REV-0569(API Hashing 개념) 또는 REV-0129(GetProcAddress LoadLibrary 동적 API 해석)를 확인한다.

## 미니 예제
```c
// 겉보기엔 단순한 초기화처럼 보이지만 실제로는 샌드박스 관찰 시간을 흘려보내는 코드
Sleep(600000);  // 10분 대기 — 대부분의 자동화 샌드박스 관찰 시간(보통 2~5분)을 넘김

// 여기서부터 진짜 페이로드
ConnectToC2Server();
DecryptAndExecutePayload();
```
자동화 샌드박스는 보통 프로세스를 몇 분만 관찰하고 리포트를 생성하므로, `Sleep(600000)` 구간에서 관찰이 끝나버려 `ConnectToC2Server`와 `DecryptAndExecutePayload`는 리포트에 전혀 기록되지 않는다. 반면 실제 피해자의 PC에서는(자동 종료가 없으므로) 10분 뒤 정확히 두 함수가 실행된다. 이 코드를 분석할 때는 `Sleep(600000)` 호출에 브레이크포인트를 걸고 인자를 `Sleep(10)` 수준으로 강제로 바꿔주면, 대기 없이 곧바로 `ConnectToC2Server` 이후의 진짜 로직을 관찰할 수 있다.

## 관련 글
- REV-0572 — GetTickCount와 QueryPerformanceCounter 시간측정 안티디버깅
- REV-0574 — Mutex 이름으로 중복 실행 방지/샌드박스 회피 판단하기
- REV-0575 — 환경변수/사용자명으로 분석 환경을 탐지하는 기법
- REV-0129 — GetProcAddress LoadLibrary 동적 API 해석
- REV-0569 — Import 함수를 런타임에 해시로 찾는 API Hashing 개념

## 출처/검증
- `Sleep`, `SleepEx`의 시그니처와 동작은 Microsoft Learn Win32 API 공식 문서 기준이다.
- `NtDelayExecution`은 공식 문서화가 제한적인 ntdll 네이티브 API로, `Sleep`이 내부적으로 이를 호출한다는 점은 다수의 Windows 내부 구조 레퍼런스에서 공통적으로 확인된다.
- Sleep 기반 샌드박스 회피(장기 대기로 자동 분석 시간을 넘기는 기법)는 다수의 공개 악성코드 분석 리포트와 보안 리서치 자료에서 표준적으로 다루는 회피 기법이다(2026-09-08 기준 서술).
