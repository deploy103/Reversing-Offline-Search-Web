## 한 줄 요약
API 호출 순서가 실행마다 뒤바뀌어 보이는 것은 버그도 아니고 분석 도구 문제도 아니라, 프로그램이 **여러 스레드**를 만들어 동시에 실행하고 OS 스케줄러가 그 스레드들을 매번 다른 순서/타이밍으로 CPU에 배정하기 때문이다. 해결책은 순서 자체를 "고정"시키려 하지 말고, 스레드별로(TID 기준으로) 분리해서 각 스레드가 하는 일을 따로따로 파악하는 것이다.

## 언제 검색해야 하나
- x64dbg나 Process Monitor로 API 호출 로그를 볼 때, 같은 바이너리를 다시 실행했는데 호출 순서가 바뀌어서 "이게 원래 로직이 맞나?" 헷갈릴 때
- 브레이크포인트를 걸어놨는데 예상한 순서와 다르게 걸려서 분석 흐름이 꼬일 때
- `CreateThread` 임포트가 여러 번 호출되는 것을 발견했을 때
- 디버깅 중 x64dbg Threads 창에 스레드가 2개 이상 떠 있는 것을 봤을 때

## 핵심 개념
Windows는 선점형 멀티태스킹 OS이며, 프로세스 안의 여러 스레드는 OS 스케줄러가 정하는 타임 슬라이스에 따라 번갈아 실행된다. 스레드 간 실행 순서는 CPU 코어 수, 시스템 부하, 캐시 상태 등 여러 외부 요인에 따라 매 실행마다 달라질 수 있다. 이것을 **비결정적(non-deterministic) 실행**이라고 부른다.

리버싱 관점에서 중요한 점은, 로그에 찍힌 API 호출들이 "하나의 순서 있는 이야기"가 아니라 **여러 스레드의 로그가 뒤섞여 있는 것**일 수 있다는 사실이다. 예를 들어 스레드 A가 파일을 읽고, 스레드 B가 동시에 네트워크 통신을 하고 있다면, 로그에는 두 스레드의 API 호출이 시간 순서대로 인터리빙(interleaving)되어 나타난다. 매 실행마다 A와 B 중 누가 먼저 CPU를 받는지가 달라지므로 겉보기 순서가 바뀐다.

이건 분석을 방해하려는 의도적 안티 디버깅 기법이 아니라(단, 일부러 여러 스레드에 로직을 흩어 분석을 어렵게 만드는 경우도 있긴 하다), 대부분은 그냥 프로그램이 실제로 멀티스레드 구조이기 때문에 생기는 자연스러운 현상이다.

## 화면/코드에서 보이는 징후
- Import 목록에 `CreateThread`, `_beginthreadex`, `CreateRemoteThread` 등이 있고 xref가 2개 이상
- x64dbg 왼쪽 하단 또는 상단 "Threads" 탭에 여러 개의 스레드 ID(TID)가 나열되어 있음
- Process Monitor에서 같은 프로세스인데 "Thread ID" 컬럼 값이 여러 개로 다름
- 같은 조건으로 재실행했는데 로그 파일의 줄 순서가 매번 바뀜(단, 각 스레드 "내부"의 상대적 순서는 보통 유지됨)

## 가장 먼저 할 것
로그나 브레이크포인트 히트 지점마다 **TID(스레드 ID)를 함께 기록**한다. x64dbg는 브레이크포인트가 걸릴 때 상단 상태 표시줄과 Threads 창에 현재 실행 중인 스레드 ID를 보여주므로, 이것부터 확인해서 "이 호출이 어느 스레드에서 왔는지" 구분한다.

## 단계별 절차
1. **스레드 생성 지점 찾기**: IDA에서 `CreateThread`(또는 `_beginthreadex`) 임포트에 `X`를 눌러 몇 개의 스레드가 어디서 생성되는지 먼저 파악한다. 각 호출의 `lpStartAddress` 인자(콜백 함수, REV-0616 참고)를 확인해 "이 스레드는 어떤 함수를 실행하는가"를 목록으로 정리한다.
2. **x64dbg Threads 창 활용**: 실행 중 Threads 탭을 열어두면 현재 떠 있는 모든 스레드의 TID, 시작 주소, 우선순위, 현재 상태(Running/Suspended/Waiting)를 볼 수 있다.
3. **스레드별로 분리해서 관찰**: Threads 탭에서 특정 스레드를 우클릭 → "Suspend"로 다른 스레드를 일시 정지시키고, 분석하려는 스레드 하나만 "Resume" 상태로 두면 그 스레드의 API 호출만 순서대로 관찰할 수 있다.
4. **조건부 브레이크포인트로 TID 필터링**: 특정 스레드의 동작만 보고 싶다면, 브레이크포인트 조건식에 `TID == 0x1234`처럼 스레드 ID 조건을 걸어 그 스레드가 그 지점을 지날 때만 멈추게 한다(REV-0183 조건부 브레이크포인트 참고).
5. **로그에는 항상 TID를 남긴다**: 직접 로깅 스크립트나 Process Monitor를 쓸 때도 TID 컬럼을 반드시 켜두고, 나중에 TID별로 정렬해서 "각 스레드 내부의 순서"를 먼저 재구성한 뒤, 스레드 간 상호작용(동기화 객체, 공유 변수)이 있는 지점만 별도로 분석한다.
6. **동기화 객체 확인**: 스레드들이 `WaitForSingleObject`, `EnterCriticalSection`, `CreateMutex` 등을 쓰고 있다면, 그 지점이 스레드 간 순서를 강제하는 "고정된 순서점"이므로 여기를 기준으로 삼으면 나머지 구간의 순서 뒤섞임은 신경 쓰지 않아도 되는 경우가 많다.

## 명령어/단축키
- x64dbg: Threads 탭에서 우클릭 → "Suspend"/"Resume"/"Switch to thread"
- x64dbg: 브레이크포인트 조건식에 `TID == <값>` 입력(조건부 브레이크포인트, REV-0183)
- IDA: Imports 창에서 `CreateThread` 더블클릭 후 `X`로 생성 지점 전부 나열
- Process Monitor(Sysinternals): 컬럼 편집에서 "Thread ID" 표시, 필터에 `Thread ID is <값>` 추가

## 출력 해석
- 같은 스레드(TID 동일) 내에서의 API 호출 순서는 재실행해도 항상 동일하다. 순서가 매번 바뀌는 것은 "서로 다른 스레드 사이"의 상대적 순서일 뿐이다.
- Threads 창에서 상태가 "Suspended"인 스레드는 아직 실행되지 않았거나 일시 정지된 것이고, "Running"은 스케줄러가 CPU를 배정한 상태다.
- `WaitForSingleObject`의 반환값이 `WAIT_OBJECT_0`(0)이면 대기 중이던 이벤트/뮤텍스가 시그널되어 정상적으로 깨어난 것이고, `WAIT_TIMEOUT`(0x102)이면 지정된 시간 내에 시그널되지 않아 타임아웃된 것이다.

## 흔한 실수
- 스레드 구분 없이 로그를 시간순으로만 나열하고 "이게 로직 순서다"라고 잘못 결론 내리는 것. 반드시 TID로 먼저 그룹화해야 한다.
- 재현이 안 된다고 생각해서 분석을 포기하는 것. 멀티스레드 프로그램은 재현성이 원래 낮으며, 이는 정상적인 특성이다. 대신 조건부 브레이크포인트나 스레드 Suspend로 관찰 가능한 조건을 인위적으로 만들면 된다.
- 스레드를 전부 Suspend한 채로 하나씩 Step만 실행하다가, 동기화 객체를 기다리는 다른 스레드가 영원히 깨어나지 못해 프로그램이 멈춘 것을 "버그"로 오해하는 것. 이 경우 필요한 스레드를 Resume해줘야 한다.

## 막혔을 때 다음 체크
- 특정 API 호출 이후 화면이 멈춘 것처럼 보인다면 → REV-0618(특정 API 호출 이후 x64dbg가 응답이 없을 때)을 확인한다.
- 스레드 시작 함수(콜백) 자체를 못 찾겠다면 → REV-0616(콜백 함수 주소만 있고 호출부가 안 보일 때)을 먼저 본다.
- 조건부 브레이크포인트 설정법이 헷갈린다면 → REV-0183(x64dbg 조건부 Breakpoint 기초)을 참고한다.

## 미니 예제
x64dbg Threads 탭에 스레드 두 개가 떠 있다고 하자.

```text
TID 0x1A04  시작 주소 0x00401500 (ThreadProc_Network)  상태: Running
TID 0x2A18  시작 주소 0x00401700 (ThreadProc_FileIO)   상태: Running
```

`ReadFile`에 브레이크포인트를 걸고 실행했더니 첫 실행에서는 `TID 0x1A04`가 먼저 걸리고, 재실행하면 `TID 0x2A18`이 먼저 걸린다. 겉보기엔 순서가 뒤바뀐 것 같지만, 브레이크포인트 조건에 `TID == 0x2A18`을 걸어 `ThreadProc_FileIO` 스레드만 따로 관찰해보면, 그 스레드 내부에서는 `CreateFileW → ReadFile → CloseHandle` 순서가 재실행해도 항상 동일하게 유지된다는 것을 확인할 수 있다.

## 관련 글
- REV-0616 — 콜백 함수 주소만 있고 호출부가 안 보일 때
- REV-0618 — 특정 API 호출 이후 x64dbg가 응답이 없을 때
- REV-0183 — x64dbg 조건부 Breakpoint 기초

## 출처/검증
- Windows 스레드 스케줄링이 선점형이며 매 실행마다 스레드 간 상대적 순서가 달라질 수 있다는 내용은 Windows 커널/스케줄러 관련 Microsoft 공식 문서 및 일반적인 운영체제 이론 기준이다.
- `CreateThread`, `WaitForSingleObject`, `EnterCriticalSection` 등의 시그니처와 반환값 의미는 Microsoft Win32 API 공식 문서 기준이다.
- x64dbg의 Threads 창, Suspend/Resume, 조건부 브레이크포인트 기능은 x64dbg 공식 문서 기준이며, 미니 예제의 구체적 TID/주소값은 설명을 위해 구성한 예시다(2026-09-08 기준 서술).
