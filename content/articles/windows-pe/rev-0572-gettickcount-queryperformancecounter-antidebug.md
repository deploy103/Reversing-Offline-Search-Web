## 한 줄 요약
타이밍 기반 안티디버깅은 코드 두 지점 사이의 경과 시간을 `GetTickCount`, `QueryPerformanceCounter`, `GetSystemTimeAsFileTime`, 또는 CPU 명령어 `rdtsc`로 직접 측정해서, 그 값이 비정상적으로 크면(디버거가 브레이크포인트에서 멈춰 있었거나 사용자가 한 줄씩 스텝하느라 시간이 오래 걸렸다는 뜻이므로) 디버깅 중이라고 판단하는 기법으로, 일반 실행 흐름을 방해하지 않으면서도 스테핑/브레이크포인트를 매우 민감하게 탐지할 수 있어 CTF와 실제 악성코드 양쪽에서 흔히 쓰인다.

## 언제 검색해야 하나
- 디스어셈블리에서 같은 API(`GetTickCount` 등)가 코드 앞뒤로 두 번 호출되고, 그 사이 리턴값을 빼서 어떤 상수와 비교하는 패턴을 봤을 때
- `rdtsc` 명령어가 두 번 나오고 그 사이 시간차를 계산하는 코드를 발견했을 때
- 프로그램을 그냥 실행(F9로 끝까지)하면 정상 동작하는데, 한 줄씩 스텝(F7/F8)하면서 분석하면 다르게 동작하거나 강제 종료될 때
- "타이밍 체크 안티디버깅"이라는 CTF 라이트업 문구를 보고 원리와 우회법이 궁금할 때

## 핵심 개념
디버거로 코드를 분석할 때는 브레이크포인트에서 멈춰 사용자가 레지스터/메모리를 확인하는 시간, 또는 한 줄씩 스텝하며 읽는 시간이 실제 CPU 실행 시간보다 압도적으로 길어진다. 정상적으로 그냥 실행되면 몇 개 안 되는 명령어 구간은 수 마이크로초~밀리초 단위로 끝나지만, 디버거로 스테핑하면 사람이 개입하는 수 초~수 분이 걸릴 수 있다. 이 차이를 이용하는 것이 타이밍 기반 안티디버깅의 핵심이다.

주로 쓰이는 시간 측정 방법들:

- **`GetTickCount`/`GetTickCount64`**: 시스템이 부팅된 이후 경과한 밀리초를 리턴하는 가장 단순한 API. 정밀도는 낮지만(보통 10~16ms 단위) 구현이 쉬워 흔히 쓰인다.
- **`QueryPerformanceCounter` + `QueryPerformanceFrequency`**: 고해상도 타이머 카운터 값을 얻어 `QueryPerformanceFrequency`가 알려주는 초당 틱 수로 나누면 훨씬 정밀한 경과 시간(마이크로초 단위)을 계산할 수 있다. CTF 문제에서 정교한 타이밍 체크에 자주 쓰인다.
- **`GetSystemTimeAsFileTime`/`GetSystemTimePreciseAsFileTime`**: 100나노초 단위의 시스템 시각을 얻어 두 시점의 차이를 계산.
- **`rdtsc`(Read Time-Stamp Counter)**: CPU 명령어로, 프로세서가 부팅 이후 실행한 클럭 사이클 수를 `EDX:EAX`(x64에서도 상위 32비트는 `EDX`, 하위는 `EAX`)에 담아 리턴한다. API 호출 없이 명령어 하나로 끝나기 때문에 후킹하기 훨씬 어렵고, 커널 디버거조차 완전히 숨기기 까다로운 대표적인 안티디버깅/안티에뮬레이션 기법이다.

동작 패턴은 대개 동일하다: (1) 측정 시작 시점 값을 저장 → (2) 보호하려는 코드 블록 실행(또는 아무 코드나 실행) → (3) 측정 종료 시점 값을 다시 읽음 → (4) 두 값의 차이를 계산 → (5) 그 차이가 미리 정한 임계값(threshold)보다 크면 "디버깅 중"으로 판단해 잘못된 결과를 리턴하거나, 조용히 종료하거나, 다른 실행 경로로 분기한다.

## 화면/코드에서 보이는 징후
- 같은 함수(`GetTickCount`, `QueryPerformanceCounter`, `rdtsc`)가 코드 상 가까운 거리에서 두 번 호출/실행됨
- 두 번째 호출 결과에서 첫 번째 호출 결과를 빼는 `sub` 연산 직후, 그 결과를 특정 상수(예: `100`, `1000`)와 비교하는 `cmp`/`jg`/`ja` 분기
- `rdtsc` 명령어 뒤에 `shl edx, 20h` (또는 `x64`의 경우 `shl rdx, 32`) 후 `or`로 `EDX:EAX`를 64비트 하나의 값으로 합치는 코드 — rdtsc의 전형적인 후처리 패턴
- 프로그램을 F9(그냥 실행)로 돌리면 정상, F7/F8(스텝)로 돌리면 다른 결과가 나오는 재현 가능한 차이

## 가장 먼저 할 것
1. 문제되는 함수/코드 블록의 시작과 끝에서 시간 측정 API 또는 `rdtsc`가 쌍으로 호출되는지 먼저 찾는다. `X`(교차 참조)로 이 API들의 모든 호출 지점을 나열해 짝을 맞춰본다.
2. 비교에 쓰이는 임계값 상수를 확인해, 얼마나 빠르게 실행돼야 "정상"으로 판정되는지 파악한다. 이 값이 우회 전략(패치 vs 하드웨어 브레이크포인트)을 결정한다.

## 단계별 절차
**1) 측정 지점과 비교 로직 특정**
- IDA에서 두 시간 측정 호출 사이의 코드 블록을 확인해, 이 구간이 보호하려는 실제 로직(예: 키 검증 알고리즘)을 포함하는지, 아니면 그냥 "디버거가 붙어 있는지"만 확인하는 독립적인 체크 블록인지 구분한다.
- 비교 결과에 따라 어디로 분기하는지(정상 경로 vs 탐지 시 경로) 확인한다.

**2) x64dbg에서 GetTickCount류 후킹/패치로 우회**
- `GetTickCount`, `QueryPerformanceCounter` 등 API 함수 시작 주소에 브레이크포인트를 걸고, 리턴 직전(`ret` 명령)에서 `EAX`(또는 x64 구조체 리턴이면 메모리 값)를 강제로 원하는 값으로 바꿔 두 번째 호출 시 첫 번째와 거의 같은 값이 나오도록 조작한다.
- 또는 비교 분기(`jg`/`ja` 등)를 찾아 조건 플래그를 항상 "정상" 쪽으로 가도록 NOP 처리하거나 분기 방향을 반대로 패치한다. 이 방법이 더 근본적이고 재발 가능성이 낮다.

**3) rdtsc 기반 체크 우회**
- `rdtsc`는 API가 아니라 CPU 명령어이므로 일반적인 API 후킹으로는 막을 수 없다. x64dbg에서 해당 명령어 주소에 브레이크포인트를 걸고, 실행 후 `EDX:EAX`(또는 합쳐진 64비트 값이 담긴 레지스터)를 원하는 값으로 강제 조작하는 방식을 쓴다.
- 더 근본적인 방법은 하드웨어 가상화 기반 디버거나 `rdtsc`를 트랩(intercept)할 수 있는 VM 환경(예: 하이퍼바이저 기반 안티안티디버깅 도구)을 쓰는 것이지만, 일반적인 CTF 환경에서는 비교 분기 자체를 패치하는 것이 가장 실용적이다.

**4) 스테핑 대신 브레이크포인트로 분석 습관 바꾸기**
- 타이밍 체크가 있는 구간은 한 줄씩 F7/F8로 스텝하지 말고, 체크 블록 전후에 브레이크포인트를 걸고 F9로 건너뛰어 실행 시간을 최소화하는 방식으로 분석한다.

## 명령어/단축키
- IDA: `X`(교차 참조로 시간 API/rdtsc 호출 지점 나열), `F5`(디컴파일해서 비교 로직 확인)
- x64dbg: `F2`(브레이크포인트), 함수 리턴 지점에서 `EAX` 우클릭 → `수정`(Modify)으로 리턴값 강제 변경, 조건 분기 명령어 우클릭 → `Assemble`로 `jg`를 `jmp`나 `nop`으로 패치
- x64dbg 스크립트: 조건부 브레이크포인트에 "명령 실행 후 조건 만족 시 자동으로 레지스터 수정" 스크립트를 걸어 매번 수동 조작하지 않고 자동화 가능

## 출력 해석
- 패치 전: 스텝 분석 시 두 시간 값의 차이가 임계값을 넘어 "디버깅 감지" 분기로 빠짐 → 프로그램이 조기 종료되거나 가짜 결과를 출력.
- 패치 후(비교 분기를 무력화): 시간 차이와 무관하게 항상 "정상" 경로로 진행 → 실제 로직을 끝까지 스텝으로 관찰 가능.
- rdtsc 두 값의 차이가 비정상적으로 클수록(수백만 사이클 이상) 디버거의 개입 시간이 길었다는 뜻이므로, 이 차이의 크기 자체가 "분석자가 얼마나 오래 멈춰 있었는지"를 역으로 알려주는 정보가 되기도 한다.

## 흔한 실수
- 타이밍 체크 분기를 못 찾고 계속 스텝으로만 분석하다가 매번 프로그램이 이상하게 종료되는 이유를 못 찾는 것. `GetTickCount`류 API의 xref부터 먼저 확인하는 습관이 필요하다.
- `GetTickCount`만 패치하고 같은 프로그램 안에 있는 `QueryPerformanceCounter`나 `rdtsc` 기반의 또 다른 체크를 놓치는 것 — 한 바이너리에 여러 종류의 타이밍 체크가 중첩되어 있는 경우가 흔하다.
- 임계값 비교 상수의 단위(밀리초 vs 마이크로초 vs CPU 사이클)를 헷갈려서 패치 방향을 잘못 잡는 것.
- 하드웨어 브레이크포인트(REV 관련 글 참고)를 안 쓰고 소프트웨어 브레이크포인트(`INT3`, `0xCC`)만 쓰면 코드 패치 자체가 타이밍에 영향을 줄 수 있다는 점을 간과하는 것.

## 막혔을 때 다음 체크
- 타이밍 체크와 별개로 `IsDebuggerPresent`류 API 체크도 같이 있는지 → REV-0130(IsDebuggerPresent 안티디버깅 식별), REV-0131(CheckRemoteDebuggerPresent 식별)을 확인한다.
- PEB 플래그 기반 체크도 같이 있는지 → REV-0132(PEB BeingDebugged 검사 이해)를 확인한다.
- 타이밍 체크가 `Sleep` 호출과 함께 쓰인다면 → REV-0573(Sleep 남용과 안티디버깅/안티샌드박스 기법)을 참고한다.

## 미니 예제
```c
DWORD t1 = GetTickCount();
// 보호하려는 실제 로직 (예: 키 검증 루프)
CheckSerialKey(input);
DWORD t2 = GetTickCount();

if ((t2 - t1) > 100) {   // 100ms 이상 걸리면 디버깅 중으로 판단
    ExitProcess(0);       // 조용히 종료
}
```
정상 실행 시 `CheckSerialKey` 내부 루프는 CPU에서 수 마이크로초 만에 끝나므로 `t2 - t1`은 거의 항상 0에 가깝다. 하지만 분석자가 `CheckSerialKey` 내부를 F7로 한 줄씩 스텝하며 몇 초 동안 관찰하면 `t2 - t1`이 수천(밀리초 단위)으로 커져 임계값 100을 넘고, 프로그램은 아무 에러 메시지도 없이 조용히 종료된다. 이 코드를 만난 분석자는 `if ((t2 - t1) > 100)` 비교의 `jg`(또는 `ja`) 분기를 찾아 항상 조건이 거짓이 되도록 패치하거나, `GetTickCount`의 두 번째 호출 리턴값을 강제로 `t1`과 같게 만들어 우회할 수 있다.

## 관련 글
- REV-0573 — Sleep 남용과 안티디버깅/안티샌드박스 기법
- REV-0130 — IsDebuggerPresent 안티디버깅 식별
- REV-0131 — CheckRemoteDebuggerPresent 식별
- REV-0132 — PEB BeingDebugged 검사 이해
- REV-0133 — TLS Callback과 main 이전 코드

## 출처/검증
- `GetTickCount`, `GetTickCount64`, `QueryPerformanceCounter`, `QueryPerformanceFrequency`, `GetSystemTimeAsFileTime`의 시그니처와 정밀도는 Microsoft Learn Win32 API 공식 문서 기준이다.
- `rdtsc` 명령어의 동작(`EDX:EAX`에 타임스탬프 카운터 반환)은 Intel 64 and IA-32 Architectures Software Developer's Manual 기준이다.
- 타이밍 기반 안티디버깅 패턴과 우회 전략은 다수의 공개 리버싱/악성코드 분석 레퍼런스에서 공통적으로 다루는 표준 기법이다(2026-09-08 기준 서술).
