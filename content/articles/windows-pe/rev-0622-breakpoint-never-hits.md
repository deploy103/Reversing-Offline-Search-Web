## 한 줄 요약
브레이크포인트가 안 걸리는 원인은 거의 항상 다음 중 하나다: **(1) ASLR로 모듈이 재배치되어 정적 분석에서 계산한 주소와 실제 런타임 주소가 다르거나, (2) 브레이크포인트가 비활성화(회색)되어 있거나, (3) 32비트/64비트 디버거를 잘못 선택했거나(x32dbg vs x64dbg), (4) 코드가 패킹/자체 수정되어 실제로 실행되는 바이트가 정적 분석 때와 다르거나, (5) 조건식이 맞지 않거나.** 절대 주소 대신 **심볼 이름으로 브레이크포인트를 걸면(`bp kernel32.CreateFileW`)** 대부분의 ASLR 문제가 자동으로 해결된다.

## 언제 검색해야 하나
- IDA에서 확인한 주소를 x64dbg에 그대로 입력해서 `bp 0x401500`처럼 걸었는데 실행해도 전혀 멈추지 않을 때
- 분명히 그 함수가 호출된다는 것을 다른 방법(로그, 결과물 변화)으로는 확인했는데 브레이크포인트만 안 걸릴 때
- Breakpoints 탭에서 브레이크포인트 항목이 회색으로 표시되어 있을 때
- DLL 안의 함수에 브레이크포인트를 걸었는데, 그 DLL이 로드되기 전에는 당연히 안 걸리다가 이후에도 계속 안 걸릴 때

## 핵심 개념
x64dbg는 기본적으로 **소프트웨어 브레이크포인트**를 사용한다. 이는 해당 주소의 첫 바이트를 `0xCC`(INT3 명령어)로 임시로 바꿔치기하고, CPU가 그 지점에 도달해 INT3 예외가 발생하면 디버거가 이를 가로채 원래 바이트로 복원한 뒤 사용자에게 멈춘 것처럼 보여주는 방식이다. 이 메커니즘이 깨지는 여러 경우가 있다.

- **ASLR(주소 공간 배치 난수화)**: 최신 Windows는 기본적으로 EXE/DLL을 매번 다른 베이스 주소에 로드한다. IDA에서 정적으로 계산한 주소(`ImageBase + RVA`)는 실제 런타임 베이스가 다르면 완전히 다른 곳을 가리킨다.
- **모듈 로드 시점**: DLL 내부 함수에 브레이크포인트를 걸 때, 그 DLL이 아직 메모리에 로드되지 않은 상태에서 절대 주소로 걸면 해당 주소에는 엉뚱한(혹은 매핑되지 않은) 내용이 있어 브레이크포인트가 무의미하다.
- **비활성화 상태**: Breakpoints 탭에서 브레이크포인트를 실수로 Disable(회색 점)한 채로 둔 경우.
- **비트수 불일치**: 32비트 PE는 x32dbg로, 64비트 PE는 x64dbg로 열어야 한다. 잘못된 비트수의 디버거로 붙이면 프로세스를 아예 열지 못하거나 엉뚱하게 동작한다.
- **자체 수정 코드/패킹**: 언패킹 스텁이 원본 코드 영역을 나중에 덮어쓰는 패커라면, 정적 분석 시점의 바이트와 실행 시점의 바이트가 다르므로 INT3 패치 지점 자체가 언패킹 과정에서 다시 원본 바이트로 덮여 사라질 수 있다.
- **조건식 불일치**: 조건부 브레이크포인트를 걸어놨는데 조건식이 실제로 절대 참이 되지 않는 잘못된 식이었을 경우.
- **하드웨어 브레이크포인트 슬롯 소진**: 하드웨어 브레이크포인트는 CPU 디버그 레지스터(DR0~DR3) 4개만 지원하므로, 이미 4개를 다 쓴 상태에서 5번째를 걸면 무시되거나 오류가 난다.

## 화면/코드에서 보이는 징후
- Breakpoints 탭의 해당 항목 앞 동그라미가 빨간색이 아니라 회색(비활성)
- 브레이크포인트를 건 주소로 Memory Map에서 이동해보면 그 모듈이 아예 리스트에 없거나(아직 로드 전), 다른 모듈이 그 주소를 차지하고 있음(ASLR로 다른 곳에 재배치)
- Log 창에 브레이크포인트 관련 메시지가 전혀 안 뜸(정상 히트라면 보통 로그가 남음)
- x32dbg로 64비트 PE를 열려고 하면 애초에 프로세스가 시작되지 않거나 즉시 오류가 남

## 가장 먼저 할 것
절대 주소 대신 **심볼/모듈 기준 브레이크포인트**로 다시 걸어본다. 시스템 API라면 `bp CreateFileW`, 특정 모듈 안이라면 `bp module.dll:1000`(RVA 기준) 형태로 걸면 x64dbg가 실제 로드된 베이스 주소를 자동으로 더해준다. 이것만으로 ASLR 문제의 대부분이 해결된다.

## 단계별 절차
1. **비트수부터 확인**: PE-bear나 DIE로 대상이 32비트(PE32)인지 64비트(PE32+)인지 먼저 확인하고, x32dbg/x64dbg 중 맞는 것으로 열었는지 확인한다.
2. **심볼 기반 브레이크포인트 사용**: 절대 주소 대신 함수 이름으로 건다.
   ```text
   bp CreateFileW
   bp target.exe:401500
   ```
   `모듈이름:오프셋` 형식은 파일 오프셋 기준 RVA로 해석되며, x64dbg가 현재 로드된 베이스 주소를 자동으로 계산해 더해준다.
3. **Breakpoints 탭에서 활성 상태 확인**: 항목이 회색이면 더블클릭하거나 우클릭 → Enable로 활성화한다.
4. **모듈 로드 여부 확인**: 대상 함수가 특정 DLL 안에 있다면, 먼저 그 DLL이 로드되는지 Memory Map이나 Log에서 확인한다. 아직 로드 전이라면 "Options → Break on new module load" 등을 활용해 로드 시점부터 잡거나, 지연 로드(REV-0620)일 수 있으니 먼저 그 DLL이 언제 로드되는지부터 확인한다.
5. **하드웨어 브레이크포인트로 전환**: 소프트웨어 브레이크포인트가 패킹/자체 수정 코드 때문에 씹히는 것 같다면, 해당 주소를 우클릭 → "Breakpoint" → "Hardware, Execute"로 걸어본다. 이는 INT3 바이트 패치가 아니라 CPU 디버그 레지스터를 사용하므로 코드 자체를 건드리지 않는다.
6. **조건식 재검토**: 조건부 브레이크포인트라면 Breakpoints 탭에서 조건식을 다시 확인하고, 일단 조건 없이 걸어서 애초에 그 지점에 도달은 하는지부터 확인한 뒤 조건을 하나씩 추가한다.
7. **ASLR 자체를 끄는 방법(최후 수단)**: 대상 EXE의 헤더에서 `IMAGE_DLLCHARACTERISTICS_DYNAMIC_BASE` 플래그를 끄면 항상 고정 베이스로 로드되게 만들 수 있지만, 이는 파일을 수정하는 것이므로 원본과 다르게 동작할 위험이 있어 최후의 수단으로만 쓴다.

## 명령어/단축키
- x64dbg: `bp <함수명>`, `bp <모듈>:<오프셋>`, Breakpoints 탭에서 Enable/Disable 토글
- x64dbg: 우클릭 대상 주소 → Breakpoint → Hardware, Execute(하드웨어 브레이크포인트)
- x64dbg: Memory Map(Alt+M)으로 모듈의 실제 로드 베이스 확인

## 출력 해석
- Memory Map에서 확인한 모듈의 실제 Base 주소가 IDA에서 가정한 `ImageBase`(기본값 예: `0x00400000` 또는 `0x140000000`)와 다르다면 ASLR로 재배치된 것이며, 차이(`실제 Base - ImageBase`)를 IDA 주소에 더해야 올바른 런타임 주소가 나온다.
- 하드웨어 브레이크포인트는 최대 4개까지만 동시에 걸 수 있으므로, 5개 이상 필요한 상황이면 우선순위를 정해 일부를 소프트웨어 브레이크포인트와 혼용해야 한다.

## 흔한 실수
- IDA 정적 주소를 그대로 x64dbg에 입력하고 ASLR을 고려하지 않는 것. 심볼 기반 브레이크포인트 사용이 훨씬 안전하다.
- 32비트 파일을 x64dbg로, 64비트 파일을 x32dbg로 잘못 열어놓고 다른 원인을 찾아 헤매는 것.
- Disable된 브레이크포인트를 놓치고 계속 "왜 안 걸리지" 고민하는 것.
- 하드웨어 브레이크포인트 슬롯이 이미 다 찼는지 확인하지 않고 계속 새로 거는 것.

## 막혔을 때 다음 체크
- 브레이크포인트는 걸리는데 그 이후 진행이 안 되는 것 같다면 → REV-0618(특정 API 호출 이후 x64dbg가 응답이 없을 때)을 확인한다.
- Step Over가 이상하게 동작한다면 → REV-0625(x64dbg Step Over가 CALL 내부로 계속 들어갈 때)를 확인한다.
- 기본 브레이크포인트 설정/삭제 방법 자체가 헷갈린다면 → REV-0178(x64dbg Breakpoint 설정과 삭제)을 먼저 본다.

## 미니 예제
IDA에서 `sub_401500`을 확인하고 x64dbg에 `bp 0x401500`으로 걸었는데 실행해도 멈추지 않았다. Memory Map(Alt+M)을 확인해보니 `target.exe`의 실제 로드 베이스가 `0x00460000`이었다(ImageBase는 `0x00400000`으로 가정했었음). 차이는 `0x60000`이므로 실제 주소는 `0x461500`이어야 했다. `bp target.exe:1500`(RVA 기준)으로 다시 걸자 정확히 멈췄다.

## 관련 글
- REV-0618 — 특정 API 호출 이후 x64dbg가 응답이 없을 때
- REV-0625 — x64dbg Step Over가 CALL 내부로 계속 들어갈 때
- REV-0178 — x64dbg Breakpoint 설정과 삭제

## 출처/검증
- 소프트웨어 브레이크포인트(INT3)와 하드웨어 브레이크포인트(디버그 레지스터 DR0~DR3)의 동작 방식은 Intel/AMD 아키텍처 매뉴얼 및 x64dbg 공식 문서 기준이다.
- ASLR(`IMAGE_DLLCHARACTERISTICS_DYNAMIC_BASE`)과 모듈 재배치 동작은 Microsoft PE/COFF 공식 문서 기준이다.
- 미니 예제의 구체적 주소값은 설명을 위해 구성한 예시다(2026-09-08 기준 서술).
