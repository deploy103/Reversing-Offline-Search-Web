## 한 줄 요약
PE 파일의 `.rsrc` 섹션은 아이콘, 버전 정보, 대화상자 같은 정상적인 부가 데이터를 담는 곳이지만, 패커나 악성코드는 이 섹션을 정상 리소스처럼 위장한 채 실제로는 암호화된 2단계 페이로드나 실행 파일 전체를 숨겨두는 경우가 많으므로, `.rsrc`의 트리 구조를 직접 펼쳐보고 각 리소스가 "이름표대로의 내용물"을 실제로 담고 있는지 확인하는 습관이 필요하다.

## 언제 검색해야 하나
- PE-bear나 IDA로 섹션 목록을 봤는데 `.rsrc` 섹션 크기가 코드 섹션(`.text`)보다도 훨씬 클 때
- 아이콘 하나 있는 평범한 GUI 프로그램인데 파일 크기가 몇 MB나 될 때
- Resource Hacker로 리소스를 열어봤는데 `RT_RCDATA`(순수 원시 데이터) 항목의 용량이 비정상적으로 클 때
- 문자열 창에는 별다른 게 없는데 임포트도 적고, 그런데도 뭔가 복잡한 동작을 하는 바이너리를 만났을 때(2단계 페이로드가 리소스에 숨어있을 가능성)

## 핵심 개념
`.rsrc` 섹션은 PE 파일 안에 아이콘, 커서, 비트맵, 대화상자 정의, 문자열 테이블, 버전 정보, 메니페스트(manifest) 등 실행에 직접 관여하지 않는 부가 데이터를 담는 표준 영역이다. 내부 구조는 **트리(계층) 형태**로 되어 있으며, 세 단계로 구성된다.

```text
Type (자원 종류)
  └─ Name/ID (자원 이름 또는 번호)
       └─ Language (언어, 예: 한국어/영어)
            └─ 실제 데이터
```

**Type**(첫 단계)에는 Windows가 미리 정의해둔 표준 리소스 종류들이 있다.
- `RT_ICON`(3) / `RT_GROUP_ICON`(14) — 아이콘
- `RT_BITMAP`(2) — 비트맵 이미지
- `RT_DIALOG`(5) — 대화상자 레이아웃 정의
- `RT_STRING`(6) — 문자열 테이블
- `RT_VERSION`(16) — 파일 버전 정보(회사명, 제품명, 버전 번호 등, "속성" 탭에서 보이는 정보)
- `RT_MANIFEST`(24) — 애플리케이션 매니페스트(권한 요구 수준 등 XML)
- `RT_RCDATA`(10) — **정해진 형식이 없는 순수 원시 바이너리 데이터**. 개발자가 임의의 목적으로 아무 데이터나 넣을 수 있는 자리다.

이 중 `RT_RCDATA`가 리버싱에서 특히 중요하다. 이름 그대로 "형식이 정해져 있지 않은 데이터"이기 때문에, 패커나 악성코드가 압축/암호화된 2단계 페이로드(실행 파일, 스크립트, 추가 DLL 등)를 통째로 집어넣기에 가장 자연스러운 자리다. 정상 프로그램이라면 설정 파일이나 임베디드 데이터베이스 같은 것을 넣지만, 악성 목적이라면 여기에 XOR/AES로 암호화된 두 번째 실행 파일을 넣어두고, 실행 시점에 이를 메모리로 읽어들여 복호화한 뒤 직접 실행(프로세스 할로잉 등)하는 방식이 흔하다.

더 교묘한 경우, `RT_ICON`이나 `RT_BITMAP`처럼 원래는 이미지 데이터가 들어가야 할 자리에 **타입 라벨만 이미지인 척하고 실제 바이트는 전혀 다른 데이터**(예: 암호화된 실행 파일)를 넣어두는 위장 기법도 쓰인다. 리소스 타입은 어디까지나 "이 데이터를 이렇게 해석해서 렌더링해달라"는 힌트일 뿐, 실제로 그 형식이어야 한다고 강제하는 검증 장치가 아니기 때문에 이런 위장이 가능하다. 그래서 "타입이 아이콘이라고 되어 있으니 진짜 아이콘이겠지"라고 안심하지 말고, 실제 바이트를 열어서 확인하는 습관이 중요하다.

## 화면/코드에서 보이는 징후
- PE-bear의 섹션 헤더 목록(`Sections`)에서 `.rsrc`의 `Raw Size`가 `.text`나 전체 파일 크기 대비 비정상적으로 큼
- Resource Hacker로 리소스 트리를 펼쳤을 때 `RT_ICON`인데 파일 크기가 일반적인 아이콘(수 KB) 대비 수백 KB~수 MB로 매우 큼
- `RT_RCDATA` 아래에 이름/번호만 있고 내용이 텍스트도 아니고 이미지도 아닌, 높은 엔트로피(무작위에 가까운 바이트 분포)의 데이터가 들어있음
- 리소스 데이터를 raw로 추출해서 첫 두 바이트를 확인했더니 `4D 5A`(`"MZ"`, PE 파일 시그니처)로 시작함 — 이는 리소스 안에 또 다른 실행 파일이 통째로 들어있다는 확실한 증거
- `RT_VERSION` 리소스인데 회사명/제품명 필드가 비어있거나 유명 소프트웨어를 사칭하는 값으로 채워져 있음(정상성 위장 목적)

## 가장 먼저 할 것
1. PE-bear나 CFF Explorer로 섹션 헤더를 확인해 `.rsrc` 섹션 크기가 비정상적으로 크지 않은지 먼저 확인한다.
2. Resource Hacker로 리소스 트리를 펼쳐서 각 항목의 Type/Name/Language와 실제 데이터 크기를 눈으로 훑어본다.
3. 크기가 유난히 큰 항목이나 `RT_RCDATA` 항목을 원시 바이너리로 추출해서 HxD 등으로 시작 바이트를 확인한다.

## 단계별 절차
**1) 리소스 트리 확인(Resource Hacker 또는 PE-bear)**
- Resource Hacker로 파일을 연다. 좌측 트리에서 `Icon`, `Bitmap`, `Dialog`, `String Table`, `Version Info`, `RCData` 등 카테고리별로 항목이 나열된다.
- 각 항목을 클릭하면 우측에 헤더 뷰(파싱된 형태) 또는 Hex 뷰로 실제 데이터를 볼 수 있다. 이미지 타입인데 이미지로 렌더링이 안 되고 깨져 보이거나 아예 렌더링 시도 자체가 실패한다면 의심해야 한다.

**2) 의심스러운 리소스 원시 추출**
- Resource Hacker에서 해당 항목을 우클릭 → "Save Resource As Binary File"(또는 "Save [항목] as a Binary File...")로 원본 바이트를 그대로 파일로 저장한다.
- 저장한 파일을 HxD로 열어 처음 몇 바이트를 확인한다. `MZ`(0x4D5A)로 시작하면 그 안에 또 다른 PE 파일(EXE/DLL)이 통째로 들어있는 것이다. `PK`(0x504B)로 시작하면 ZIP 계열 압축 파일일 수 있다.
- `file` 명령(Linux/WSL 환경이 있다면) 또는 Detect It Easy로 추출한 파일의 형식을 자동 판별해볼 수도 있다.

**3) 엔트로피로 암호화 여부 추정**
- 추출한 데이터가 특정 파일 시그니처로 시작하지 않고 바이트 분포가 매우 무작위해 보인다면 압축 또는 암호화되어 있을 가능성이 크다. PE-bear나 Detect It Easy의 엔트로피 분석 기능으로 수치를 확인하면(보통 7.5~8.0에 가까울수록 압축/암호화 가능성 높음) 판단에 도움이 된다.
- 이 경우, 바이너리 코드에서 이 리소스를 읽어오는 지점(`FindResource`/`LoadResource`/`LockResource` API 호출)을 IDA에서 찾아 그 이후 복호화 루프를 REV-0140(표준 API) 또는 알고리즘 카테고리(커스텀 XOR 등) 방식으로 추적한다.

**4) IDA로 리소스 사용 코드 찾기**
- 임포트 목록에서 `FindResourceW`, `LoadResource`, `LockResource`, `SizeofResource`를 찾는다. 이 네 함수가 함께 쓰이는 패턴이 "리소스에서 데이터를 꺼내 메모리로 가져오는" 전형적인 코드다.
- `FindResourceW`의 인자(리소스 타입, 이름/ID)를 확인하면 코드가 정확히 어떤 리소스를 대상으로 하는지 알 수 있다.

## 명령어/단축키
- Resource Hacker: 트리 항목 우클릭 → "Save Resource As Binary File" (원시 데이터 추출)
- PE-bear: `Sections` 탭(섹션 크기 비교), `Resources` 탭(트리 뷰)
- HxD: 추출한 파일을 열어 시작 바이트(`MZ`, `PK` 등) 확인
- IDA: 임포트에서 `FindResourceW`/`LoadResource`/`LockResource` 교차 참조(`X`) 확인

## 출력 해석
- 추출한 리소스 데이터가 `4D 5A 90 00`으로 시작하면 거의 확실히 내부에 완전한 PE 파일이 들어있다는 뜻이다. 이 추출 파일을 그대로 다시 PE-bear/IDA로 열어 2단계 분석을 진행하면 된다.
- `RT_VERSION` 리소스를 Resource Hacker로 열었을 때 `FileVersion`, `ProductName`, `CompanyName` 같은 필드가 정상적으로 파싱되어 보이면 진짜 버전 정보다. 파싱 자체가 깨지거나 이상한 바이트가 보이면 해당 항목이 버전 정보 형식을 흉내만 낸 것일 수 있다.
- 엔트로피가 낮고(예: 4.0 이하) 텍스트나 반복 패턴이 많이 보이면 암호화되지 않은 평문/설정 데이터일 가능성이 높다.

## 흔한 실수
- 리소스의 "Type" 라벨(`RT_ICON` 등)만 보고 내용도 당연히 그 형식일 거라고 믿어버리는 것. 반드시 실제 바이트를 눈으로 확인해야 한다.
- `.rsrc` 섹션 크기가 크면 무조건 의심하는 것도 과할 수 있다. 다국어 지원 프로그램은 언어별 문자열 테이블/대화상자가 많아 정상적으로도 `.rsrc`가 커질 수 있으므로, 크기만으로 판단하지 말고 개별 항목의 내용을 확인해야 한다.
- 리소스에서 페이로드를 추출한 뒤, 그 파일이 다시 통째로 실행 파일이라는 것을 알고도 "이건 그냥 첨부 파일이겠지"라며 더 이상 분석하지 않는 것. 2단계 페이로드야말로 진짜 핵심 로직인 경우가 흔하다.
- `FindResourceW`의 이름/ID 인자를 확인하지 않고 리소스 트리에서 눈에 띄는 아무 항목이나 추출해서 "이게 그 페이로드다"라고 단정하는 것. 반드시 코드가 실제로 참조하는 리소스인지 대조해야 한다.

## 막혔을 때 다음 체크
- 리소스에서 꺼낸 데이터가 표준 암호화 API로 복호화되는 것 같다면 → REV-0140(Crypt API BCrypt API 흔적 찾기)을 확인한다.
- 리소스를 읽어와서 파일로 다시 쓰는 코드가 있다면 → REV-0139(CreateFile ReadFile WriteFile 입력 데이터 추적)로 그 이후 흐름을 추적한다.
- 리소스 로딩 코드가 TLS 콜백이나 진입점 이전에 실행되는 것처럼 보인다면 → REV-0133(TLS Callback과 main 이전 코드)을 함께 확인한다.

## 미니 예제
Resource Hacker로 `sample.exe`를 열었더니 `RCData` 카테고리 아래에 `BINDATA`라는 이름의 항목이 하나 있었고, 크기가 1.2MB였다(전체 파일 크기는 1.3MB). 이 항목을 우클릭해서 "Save Resource As Binary File"로 `extracted.bin`으로 저장한 뒤 HxD로 열어보니 시작 바이트가 다음과 같았다.

```text
00000000  4D 5A 90 00 03 00 00 00  04 00 00 00 FF FF 00 00
```

`4D 5A`(`MZ`)로 시작하므로 이 리소스는 완전한 PE 파일을 통째로 담고 있는 것이다. `extracted.bin`의 확장자를 `.exe`로 바꿔 PE-bear로 다시 열어보니 정상적으로 PE 헤더가 파싱되었고, 이것이 바로 원본 프로그램이 실행 중에 몰래 풀어내는 2단계 페이로드였다. IDA에서 `sample.exe`의 코드를 보면 `FindResourceW(NULL, MAKEINTRESOURCE(101), L"RCDATA")` 형태의 호출로 이 리소스를 찾아 `LoadResource`/`LockResource`로 메모리에 매핑한 뒤, 별도 프로세스로 실행하거나 메모리에서 직접 매핑해 실행하는 코드가 이어질 가능성이 크다.

## 관련 글
- REV-0135 — DLL 문제 분석 시작하기
- REV-0139 — CreateFile ReadFile WriteFile 입력 데이터 추적
- REV-0140 — Crypt API BCrypt API 흔적 찾기

## 출처/검증
- `.rsrc` 섹션과 리소스 디렉터리 트리(Type/Name/Language) 구조는 Microsoft PE/COFF 형식 공식 문서 기준이다.
- 표준 리소스 타입 상수(`RT_ICON`, `RT_RCDATA`, `RT_VERSION`, `RT_MANIFEST` 등)는 Microsoft Win32 리소스 관련 공식 문서 기준이다.
- 리소스 섹션에 2단계 페이로드를 숨기는 기법은 다수의 악성코드 분석 레퍼런스 및 CTF 라이트업에서 반복적으로 확인되는 일반적인 패턴이다(2026-09-08 기준 서술).
