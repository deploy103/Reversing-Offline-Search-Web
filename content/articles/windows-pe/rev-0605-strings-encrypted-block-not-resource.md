## 한 줄 요약
IDA의 Strings 창(`Shift+F12`)이나 Resource Hacker/PE-bear의 리소스 뷰에서 flag나 의미 있는 문자열이 전혀 안 보인다면, 그 문자열은 평문 리소스가 아니라 `.data`/`.rdata`나 별도 섹션 안에 암호화/인코딩된 바이트 블록으로 들어 있다가 런타임에만 복호화되는 경우이므로, 정적으로 찾지 말고 복호화 루프의 출력 지점(루프가 끝난 직후, 또는 그 결과를 비교/출력하는 지점) 메모리를 x64dbg로 덤프해야 한다.

## 언제 검색해야 하나
- `Shift+F12`로 연 IDA Strings 창에 라이브러리 함수 이름이나 포맷 문자열 같은 잡음만 있고, 문제에서 기대하는 flag/메시지 문자열이 하나도 없을 때
- Resource Hacker나 PE-bear의 Resources 탭을 열어봤는데 String Table이나 RCDATA 리소스 자체가 없거나 비어 있을 때
- 문자열이 UTF-16으로 저장되어 있을 거라 생각해서 인코딩을 바꿔가며 찾아봐도 여전히 안 보일 때
- 프로그램을 실제로 실행하면 화면에 메시지가 뜨는데, 그 문자열이 파일 어디에도 그대로 존재하지 않을 때

## 가장 먼저 할 것
DIE(Detect It Easy)나 PE-bear로 각 섹션의 엔트로피를 확인한다. 일반 코드/문자열 섹션보다 눈에 띄게 높은 엔트로피(암호화되거나 압축된 데이터의 특징)를 가진 섹션이 있다면, 그 섹션이 암호화된 문자열/데이터 블록을 담고 있을 강력한 후보다.

## 핵심 개념
Windows PE에서 문자열이 저장되는 방식은 크게 두 갈래로 나뉜다.

1. **평문 저장**: 컴파일러가 그대로 `.rdata` 섹션에 ASCII/UTF-16 문자열 리터럴로 박아 넣거나, 리소스 컴파일러가 `.rsrc` 섹션 안에 String Table(`RT_STRING`) 또는 커스텀 `RT_RCDATA` 리소스로 넣는다. 이 경우 IDA Strings 창이나 Resource Hacker로 그대로 눈에 보인다(관련: REV-0128 Windows 문자열 인코딩, REV-0141 Resource Section).
2. **암호화/인코딩 저장**: 개발자(또는 크랙미 제작자)가 의도적으로 문자열을 XOR, 간단한 덧셈 암호, RC4, 혹은 Base64 등으로 인코딩한 바이트 배열로 바꿔서 `.data`/`.rdata` 또는 커스텀 이름의 섹션에 심어두고, 프로그램 시작 시(또는 필요한 시점에) 그 바이트 배열을 순회하며 복호화 루프를 실행해 힙이나 스택의 별도 버퍼에 평문을 만든다.

두 번째 경우가 이 글의 주제다. 정적 분석 도구는 원본 바이트가 사람이 읽을 수 있는 문자가 아니므로 애초에 "문자열"로 인식하지 못하고, 리소스 뷰어도 그 바이트가 표준 리소스 포맷(`RT_STRING`, `RT_RCDATA` 등)의 구조를 따르지 않으면 아무것도 보여주지 못한다.

이걸 찾아내는 실질적인 단서는 두 가지다.
- **엔트로피**: 암호화되거나 압축된 데이터는 바이트 값의 분포가 균일해 엔트로피가 높다(이론적 최댓값 8.0 bits/byte에 가까움). 반면 일반 코드나 평문 텍스트는 특정 바이트 값이 자주 반복되어 엔트로피가 상대적으로 낮다. DIE는 섹션별 엔트로피를 자동으로 계산해 보여준다.
- **디코드 루프 코드 패턴**: 정적으로 어셈블리를 훑어보면 고정 크기 버퍼를 순회하며 `xor`, `add`/`sub`, `rol`/`ror` 같은 연산을 반복하는 루프(전형적으로 `for`/`while` 형태로 컴파일된 코드)가 초기화 루틴이나 메인 함수 진입부 근처에 있는 경우가 많다.

## 화면/코드에서 보이는 징후
- IDA Strings 창에 `.rdata`의 라이브러리 관련 문자열(`msvcrt.dll`, 포맷 문자열 `%d`, `%s` 등)만 있고 문제 관련 문자열이 없다.
- Resource Hacker/PE-bear의 Resources 탭이 아이콘/버전 정보 정도만 있고 String Table이 비어 있거나 아예 리소스 섹션이 거의 없다.
- DIE의 섹션 정보에서 특정 섹션(흔히 `.data`)의 엔트로피 수치가 다른 섹션보다 눈에 띄게 높게 표시된다.
- 디스어셈블리에 고정 크기 배열을 인덱스로 순회하며 매 바이트마다 같은 상수와 `xor` 연산을 하는 루프가 보인다.

## 단계별 절차
1. DIE 또는 PE-bear로 섹션별 엔트로피를 확인해 의심 섹션을 좁힌다.
2. IDA에서 그 섹션의 데이터를 열어(View → Open subviews → Hex dump, 또는 해당 주소로 이동 후 `Shift+F12`가 아닌 hex view) 사람이 읽을 수 있는 문자가 아닌 바이트 나열인지 확인한다.
3. 이 데이터를 참조하는 코드를 찾기 위해 그 주소에 `X`(크로스 레퍼런스)를 걸어, 어떤 함수가 이 블록을 읽어들이는지 확인한다.
4. 그 함수 안에서 반복문(루프) 구조를 찾는다 — 인덱스 변수가 증가하며 배열 원소에 `xor`/`add`/`sub` 등을 적용하는 패턴이면 복호화 루프일 가능성이 높다.
5. x64dbg로 그 루프가 끝나는 지점(루프 탈출 직후, 다음 명령어)에 브레이크포인트를 건다.
6. 실행해서 브레이크포인트에 걸리면, 복호화된 결과가 저장되는 버퍼 주소(루프 안에서 쓰기 대상이었던 변수)를 Dump 창에서 확인한다. 이제 이 시점에는 평문이 채워져 있어야 한다.
7. 여러 문자열이 한 번에 복호화되는 구조라면, 이 시점에 전체 버퍼를 "Save To a File" 또는 그대로 눈으로 읽어 flag/메시지를 확인한다.

## 명령어/단축키
- DIE: 파일 열기 → 섹션별 엔트로피 확인(엔트로피 표시 옵션이 없으면 "Entropy" 플러그인/탭 활용)
- IDA: `X`(크로스 레퍼런스), 데이터 주소에서 우클릭 → "Jump in a new hex view"
- x64dbg: 복호화 루프 종료 직후 주소에 `F2`로 브레이크포인트, 결과 버퍼 우클릭 → "Follow in Dump"

## 출력 해석
- 엔트로피가 7.5 bits/byte 이상이면 암호화 또는 압축된 데이터일 가능성이 매우 높다(참고로 일반 x86/x64 코드 섹션은 대략 5.5~6.5 bits/byte 부근인 경우가 많다).
- 복호화 루프 종료 직후 덤프한 버퍼에 사람이 읽을 수 있는 ASCII 문자가 나타난다면 복호화가 성공적으로 끝난 시점을 정확히 찾은 것이다.
- 여전히 알아볼 수 없는 바이트라면, 아직 완전히 복호화되지 않은 중간 단계이거나(예: 다단계 인코딩) 잘못된 버퍼를 보고 있는 것이므로 루프를 한 단계 더 따라가야 한다.

## 흔한 실수
- 문자열이 UTF-16이라서 안 보이는 거라 생각하고 인코딩만 계속 바꿔보며 시간을 낭비하는 것 — 애초에 암호화된 바이트라면 인코딩을 바꿔도 의미 있는 문자열이 나오지 않는다.
- 리소스 섹션(`.rsrc`)만 확인하고 `.data`/`.rdata`에 있는 커스텀 암호화 블록은 확인하지 않는 것.
- 복호화 루프를 찾았는데 루프가 시작하기 전(아직 암호화된 상태)에 브레이크포인트를 걸어놓고 "왜 여전히 암호문이냐"고 헷갈리는 것 — 반드시 루프가 끝난 직후 지점에서 확인해야 한다.
- 문자열이 하나의 정적 배열이 아니라 필요할 때마다 하나씩 복호화되는 구조(지연 복호화)인데, 프로그램 시작 시점 한 번만 보고 "복호화되는 문자열이 없다"고 결론짓는 것 — 실제 입력을 넣어 해당 분기를 타야 복호화가 일어나는 경우도 많다.

## 막혔을 때 다음 체크
- 복호화에 표준 암호 API(`CryptDecrypt`, `BCryptDecrypt` 등)가 쓰인다면 → REV-0140(Crypt API BCrypt API 흔적 찾기)을 확인한다.
- 문자열이 원래 어떻게 저장되어야 정상인지 기준이 필요하다면 → REV-0128(Windows 문자열 ASCII와 UTF-16 찾기)과 REV-0141(Resource Section과 숨겨진 데이터 확인)을 참고한다.
- 복호화된 데이터가 사실 문자열이 아니라 코드/셸코드였다면 → REV-0602(CreateRemoteThread로 생성된 코드가 안 보일 때)의 버퍼 덤프 절차를 참고한다.

## 미니 예제
DIE로 `puzzle.exe`의 섹션 정보를 확인하니 `.data` 섹션의 엔트로피가 7.9로, 다른 섹션(5~6대)보다 눈에 띄게 높았다. 그 섹션의 바이트를 IDA hex view로 보니 사람이 읽을 수 없는 무작위처럼 보이는 32바이트 블록이 있었다. 이 블록을 참조하는 함수를 찾아보니 인덱스 0부터 31까지 순회하며 매 바이트에 상수 `0x5A`를 XOR하는 루프가 있었다. x64dbg에서 이 루프 다음 명령어에 브레이크포인트를 걸고 실행하자, 복호화 대상 버퍼에 `CTF{h1dd3n_1n_pl41n_byt3s}`라는 평문이 채워져 있는 것을 확인했다.

## 출처/검증
- 엔트로피를 이용한 암호화/압축 데이터 식별 방법은 Detect It Easy(DIE) 공식 문서 및 일반적인 정적 분석 실무 관행 기준이다.
- XOR 등 단순 인코딩을 이용한 런타임 문자열 복호화 패턴과 이를 x64dbg로 런타임에 가로채는 방법은 일반적인 리버스 엔지니어링/CTF 실무 관행 기준이다.
