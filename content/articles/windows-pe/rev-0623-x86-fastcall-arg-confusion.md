## 한 줄 요약
x86(32비트) `__fastcall`은 **정수/포인터 인자 중 앞 2개만** `ECX`, `EDX` 레지스터에 담기고, **3번째 인자부터는 스택**에 오른쪽에서 왼쪽 순서로 `push`된다. x64의 Microsoft 호출 규약(레지스터 4개, `RCX`/`RDX`/`R8`/`R9`)과 이름이 비슷해서 "레지스터 4개를 찾아야 한다"고 착각하기 쉬운데, x86 `__fastcall`은 완전히 다른 규약이며 레지스터는 딱 2개뿐이다.

## 언제 검색해야 하나
- IDA가 함수를 `__fastcall`로 자동 인식했는데(Functions 창이나 함수 시그니처에 표시됨) 어디까지가 레지스터 인자이고 어디부터가 스택 인자인지 헷갈릴 때
- x64dbg에서 함수 진입점에 멈췄는데 `ECX`, `EDX`에 뭔가 들어있어서 이게 인자인지 그냥 임시값인지 판단이 안 될 때
- 32비트 바이너리인데 x64 호출 규약(4개 레지스터)을 기준으로 인자를 찾다가 값이 안 맞아서 혼란스러울 때
- `__fastcall`과 `__thiscall`(C++ 멤버 함수)을 같은 것으로 착각해서 `this` 포인터 위치를 잘못 짚을 때

## 핵심 개념
x86(32비트) Windows에는 네 가지 주요 호출 규약이 있다(REV-0123 참고). 이 중 `__fastcall`의 규칙은 다음과 같다.

- **처음 두 개**의 `DWORD` 크기 이하(4바이트 이하) 정수/포인터 인자는 순서대로 `ECX`, `EDX`에 담긴다.
- **세 번째 인자부터**는 스택에 담기며, 호출자가 오른쪽 인자부터 왼쪽 순서로 `push`한다(다른 x86 규약과 동일한 스택 적재 순서).
- **부동소수점 인자**(`float`/`double`)는 크기와 상관없이 항상 스택으로 전달되며, 절대 `ECX`/`EDX`에 들어가지 않는다.
- **8바이트를 넘는 구조체**처럼 레지스터에 담기 어려운 큰 값도 스택으로 전달된다.
- **스택 정리는 호출된 함수(callee)가 담당**한다(`stdcall`, `thiscall`과 동일하게 callee-clean). 함수 끝에서 `retn N`(N은 스택 인자들의 총 바이트 수) 형태로 리턴하며 스택을 정리한다.

가장 흔한 혼동은 x64의 Microsoft 호출 규약과 헷갈리는 것이다. x64는 정수/포인터 인자 **4개**(`RCX`, `RDX`, `R8`, `R9`)를 레지스터로 전달하지만(REV-0122 참고), x86 `__fastcall`은 **2개**(`ECX`, `EDX`)뿐이다. 이름에 "fast"가 들어가 있어 x64와 같은 방식일 거라 착각하기 쉽지만, 아키텍처와 시대가 다른 별개의 규약이다.

또한 `__thiscall`(C++ 클래스의 비정적 멤버 함수 기본 규약, MSVC 기준)과도 헷갈리기 쉬운데, `__thiscall`은 `this` 포인터 **하나만** `ECX`에 담고 나머지 인자는 전부 스택으로 전달한다(즉 `EDX`는 쓰지 않는다). `__fastcall`은 `this` 개념이 없는 일반 함수에 쓰이며 2개까지 레지스터를 쓴다는 점이 다르다.

## 화면/코드에서 보이는 징후
- IDA 디컴파일(F5) 결과 함수 시그니처에 `__fastcall`이 명시되어 있고, `a1`, `a2` 같은 인자가 `@<ecx>`, `@<edx>` 표시와 함께 나옴(IDA 구버전 UI 기준 표기 방식은 다를 수 있음)
- 어셈블리에서 함수 호출 직전에 `mov ecx, ...` / `mov edx, ...`가 나온 뒤, 3번째 인자부터는 `push ...`가 이어지는 패턴
- 함수 끝부분이 `retn 8`, `retn 0Ch`처럼 0이 아닌 값으로 끝남(스택 인자 개수 × 4바이트만큼 callee가 정리)
- x64dbg에서 함수 진입 직후 `ECX`=포인터스러운 값, `EDX`=작은 정수 같은 값이 보이는 전형적인 2-레지스터 인자 패턴

## 가장 먼저 할 것
IDA에서 해당 함수의 호출 규약 표시(`__fastcall`인지 `__stdcall`/`__cdecl`/`__thiscall`인지)를 먼저 확인한다. `__fastcall`이 확실하면 **딱 2개까지만** 레지스터를 찾고, 3번째 인자부터는 즉시 스택으로 눈을 돌린다.

## 단계별 절차
1. **함수 시그니처 확인**: IDA `F5` 디컴파일 결과나 함수 프로토타입(`Y` 단축키로 타입 지정 시)에서 호출 규약을 확인한다.
2. **레지스터 인자 확인(1~2번째)**: 호출 직전 코드에서 `ECX`에 들어가는 값이 1번째 인자, `EDX`에 들어가는 값이 2번째 인자다. x64dbg로 함수 진입 시점에 브레이크포인트를 걸면 이 두 레지스터 값을 바로 확인할 수 있다.
3. **스택 인자 확인(3번째 이후)**: 함수 진입 직후(prologue 실행 전) 기준으로 `[esp]`가 리턴 주소, `[esp+4]`가 3번째 인자, `[esp+8]`이 4번째 인자... 순서로 이어진다. 이는 인자 번호만 1, 2번이 레지스터로 빠졌을 뿐, 스택 오프셋 계산 방식 자체는 일반 `stdcall`/`cdecl`과 동일하다.
4. **함수 끝의 `retn N` 확인**: N 값을 4로 나누면 "스택으로 전달된 인자 개수"를 역산할 수 있다. 예를 들어 `retn 8`이면 스택 인자가 2개이므로, 전체 인자는 레지스터 2개 + 스택 2개 = 총 4개임을 알 수 있다.
5. **`__thiscall`과 구분**: `EDX`를 전혀 안 쓰고 `ECX`만 쓴 채 나머지가 전부 스택이라면 `__thiscall`(C++ 멤버 함수, `ECX`=this)일 가능성이 높다. IDA가 클래스 메서드로 인식했다면 자동으로 `__thiscall`로 표시해준다.

## 명령어/단축키
- IDA: `Y`(변수/함수 타입 지정, 호출 규약 확인), `F5`(디컴파일)
- x64dbg(x32dbg): 함수 진입점에 `bp`, Registers 창에서 `ECX`/`EDX` 확인, Stack 창에서 `[esp+4]`부터 확인

## 출력 해석
- `ECX`, `EDX`에 담긴 값이 각각 1번째, 2번째 인자다. 순서를 절대 바꿔 읽지 않는다(`EDX`가 먼저, `ECX`가 나중이 아니다).
- `retn N`의 N이 0이면 스택 인자가 전혀 없다는 뜻이고, 이는 전체 인자가 2개(또는 그 이하) 뿐이거나 `void` 인자 함수라는 뜻이다.
- 부동소수점 인자를 쓰는 `__fastcall` 함수라면, 그 인자는 정수 인자 개수와 무관하게 항상 스택에서 찾아야 한다.

## 흔한 실수
- x64 호출 규약을 기준으로 "레지스터 4개(`ECX`, `EDX`, ??, ??)"를 찾으려 하는 것. x86에는 애초에 `R8`/`R9`에 대응하는 32비트 레지스터 개념이 없다(EAX/EBX/ESI/EDI 등은 fastcall 인자로 쓰이지 않는다).
- `__fastcall`과 `__thiscall`을 혼동해서 `EDX`에 값이 없는데도 계속 2번째 인자를 `EDX`에서 찾으려 하는 것.
- 함수 진입 후 프롤로그(`push ebp` 등)가 실행된 뒤의 `ESP` 기준으로 스택 인자 오프셋을 계산해서 오프셋이 틀어지는 것. 반드시 함수 진입 "직후, 프롤로그 실행 전" 기준으로 계산해야 한다.
- 부동소수점 인자가 섞여 있을 때 이것도 레지스터에 들어갈 것으로 착각하는 것. x86 `__fastcall`에서 부동소수점은 무조건 스택이다.

## 막혔을 때 다음 체크
- x64 호출 규약과 정확히 비교하고 싶다면 → REV-0122(Microsoft x64 Calling Convention)를 확인한다.
- 다른 x86 호출 규약(`stdcall`/`cdecl`/`thiscall`)까지 한 번에 정리하고 싶다면 → REV-0123(Windows x86 stdcall cdecl fastcall thiscall)을 먼저 읽는다.
- x64에서 비슷하게 헷갈리는 문제(섀도우 스페이스)가 궁금하다면 → REV-0624(Shadow Space를 안 챙겨서 인자 해석을 잘못했을 때)를 참고한다.

## 미니 예제
IDA에서 `__fastcall` 함수 `sub_401700`의 호출부를 봤더니 다음과 같았다.

```asm
push    10h             ; 4번째 인자
push    offset aData    ; 3번째 인자
mov     edx, 5          ; 2번째 인자
mov     ecx, [ebp+8]    ; 1번째 인자
call    sub_401700
```

`sub_401700` 내부 끝부분은 `retn 8`로 끝났다. 이는 3, 4번째 인자(스택으로 전달된 2개, 4바이트씩 총 8바이트)를 함수 자신이 정리했다는 뜻이며, 전체 인자는 `ECX`(1번), `EDX`(2번), 그리고 스택의 `aData`(3번), `0x10`(4번)까지 총 4개였다.

## 관련 글
- REV-0122 — Microsoft x64 Calling Convention
- REV-0123 — Windows x86 stdcall cdecl fastcall thiscall
- REV-0624 — Shadow Space를 안 챙겨서 인자 해석을 잘못했을 때

## 출처/검증
- x86 `__fastcall`의 `ECX`/`EDX` 2개 레지스터 인자 규칙, callee-clean 스택 정리, 부동소수점 예외 규칙은 Microsoft Visual C++ 공식 문서(Argument Passing and Naming Conventions) 기준이다.
- `__thiscall`의 `ECX`=this 규칙 역시 Microsoft Visual C++ 공식 문서 기준이다.
- 미니 예제의 구체적 어셈블리는 설명을 위해 구성한 예시다(2026-09-08 기준 서술).
