## 한 줄 요약
소프트웨어 브레이크포인트는 디버거가 원래 명령어의 첫 바이트를 `0xCC`(`INT3`)로 몰래 바꿔치기하는 방식이라, 코드 자신의 바이트를 실행 중에 다시 읽어서 원본과 비교하거나 체크섬(CRC 등)을 계산해 어긋나는지 확인하면 "누군가 내 코드 위에 브레이크포인트를 심어뒀다"는 사실을 잡아낼 수 있다.

## 언제 검색해야 하나
- x64dbg에서 `bp`(소프트웨어 브레이크포인트)로 특정 함수 시작 지점에 걸었을 때는 감지되는데, 같은 위치에 `ba`(하드웨어 브레이크포인트)로 걸면 감지되지 않는 상황을 마주쳤을 때
- 코드 섹션(`.text`)을 순회하며 각 바이트를 `0xCC`와 비교하는 루프, 또는 CRC32/체크섬을 계산하는 함수를 발견했을 때
- "이 프로그램은 self-checksumming을 한다"는 힌트가 있는 CTF 문제를 만났을 때
- 함수 시작 부분에 브레이크포인트를 걸면 코드가 정상 실행되다가 특정 시점에 갑자기 다른 결과가 나오는 것을 관찰했을 때

## 핵심 개념

### 소프트웨어 브레이크포인트의 원리
x64dbg, OllyDbg, WinDbg 등 대부분의 사용자 모드 디버거는 소프트웨어 브레이크포인트를 걸 때 CPU의 특별한 레지스터를 쓰는 게 아니라, **대상 주소의 원본 바이트 1개를 저장해두고 그 자리에 `0xCC`(`INT3` 명령어)를 덮어쓴다.** 실행이 그 주소에 도달하면 CPU가 `INT3` 예외를 발생시키고, 디버거가 이를 가로채 원본 바이트로 되돌려놓은 뒤 사용자에게 "여기서 멈췄다"고 보여준다. 이 방식은 하드웨어 브레이크포인트(REV-0536)와 달리 코드 메모리 자체를 수정하기 때문에, 코드를 다시 읽어보면 이 변조를 그대로 발견할 수 있다.

### 탐지 방법 1: 바이트 직접 비교
가장 단순한 방법은 함수 시작 지점(또는 검사하고 싶은 특정 위치)의 첫 바이트를 실행 중에 읽어서 `0xCC`인지 비교하는 것이다.
```c
BYTE* target = (BYTE*)SuspiciousFunction;
if (*target == 0xCC) {
    // 브레이크포인트가 걸려 있음
}
```
이 방법은 구현이 매우 간단하지만, 특정 주소 하나만 검사하므로 그 주소가 아닌 다른 곳에 걸린 브레이크포인트는 잡지 못한다.

### 탐지 방법 2: 코드 섹션 체크섬/CRC
더 촘촘한 방법은 코드 섹션 전체(또는 보호하려는 함수 범위) 바이트를 CRC32나 단순 합산 등으로 체크섬을 계산해서, 프로그램에 미리 박아둔(또는 다른 방식으로 계산한) 원본 체크섬과 비교하는 것이다. 이 방식은 `0xCC` 하나만 찾는 게 아니라 코드가 조금이라도 바뀌면(패치, 브레이크포인트, 후킹 등) 전부 걸리기 때문에 훨씬 강력하다. 다만 계산 비용이 있고, 프로그램 실행 흐름에 따라 여러 번 반복 계산해야 지속적인 방어가 된다.

### 왜 정적 분석만으로는 안 잡히나
디스어셈블리 상에서는 원본 코드가 그대로 보이므로(디버거가 붙지 않은 파일 자체는 `0xCC`로 패치되어 있지 않다), 이 검사 로직 자체는 정상적인 함수처럼 보인다. 오직 **디버거가 실제로 붙어서 브레이크포인트가 걸린 실행 시점**에만 검사 대상 바이트가 `0xCC`로 바뀌어 있으므로, 이 안티디버깅은 정적 분석으로는 존재 자체를 알아채기 쉽지 않고, 동적 분석(디버깅) 중에만 자기 발등을 찍는 역설적인 구조를 가진다.

### self-modifying code와의 관계
일부 프로텍터는 이 원리를 한 단계 더 발전시켜, 코드 섹션을 암호화해두고 실행 직전에 복호화하면서 동시에 체크섬도 검증하는 self-modifying + self-checksumming 조합을 쓴다. 이 경우 단순히 브레이크포인트 여부뿐 아니라 코드 자체가 온전한지(패치되지 않았는지)까지 함께 검사하게 된다.

## 화면/코드에서 보이는 징후
- 코드에 `.text` 섹션의 시작 주소와 크기를 상수로 들고 있는 루프가 있고, 그 안에서 각 바이트를 `cmp al, 0CCh` 형태로 비교.
```asm
mov  esi, offset func_start
mov  ecx, func_size
scan_loop:
    mov  al, [esi]
    cmp  al, 0CCh
    je   breakpoint_detected
    inc  esi
    loop scan_loop
```
- CRC32 계산 루프(다항식 상수 `0xEDB88320` 등이 코드나 데이터에 보임)와 그 결과를 특정 상수와 `cmp`하는 코드.
- x64dbg에서 `bp`로 함수 시작에 걸었을 때만 프로그램이 종료되거나 잘못된 값을 출력하고, 브레이크포인트를 지우면 정상 동작하는 경우.

## 가장 먼저 할 것
의심되는 검사 루프를 찾으면, 이 루프가 **어느 주소 범위**를 대상으로 하는지부터 확인한다(고정 함수 하나인지, `.text` 섹션 전체인지). 범위가 넓을수록(섹션 전체 체크섬) 우회가 까다로우므로, IDA에서 이 루프에 진입하는 조건과 빈도(한 번만 실행되는지, 반복적으로 실행되는지)를 먼저 파악해야 한다.

## 단계별 절차
**1) 검사 대상 범위 특정**

루프의 시작 포인터와 길이(또는 끝 주소) 값을 IDA에서 추적한다. `.text` 섹션 전체 범위(REV-0117 PE Section Table 읽기 참고)와 일치하면 전체 체크섬 방어이고, 특정 함수 하나의 크기와 일치하면 국소적 검사다.

**2) 비교 대상 파악**

체크섬 결과를 무엇과 비교하는지 확인한다. 코드에 하드코딩된 상수와 비교하면 그 상수를 역산해서 검사 자체를 이해할 수 있고, 다른 곳에서 동적으로 계산한 값과 비교하면(예: "패치되지 않은 다른 사본"을 파일에서 다시 읽어 비교) 더 정교한 방어다.

**3) x64dbg에서 실제로 관찰**

의심 함수 시작에 `bp`를 걸고 실행한 뒤, `bp`를 통과시키면서 이 검사 루프에 진입하는지, 그리고 그 결과가 검사에 걸리는지 스텝 실행(`F8`)으로 직접 눈으로 확인한다.

**4) 우회 아이디어 이해**

가장 흔한 우회는 문제의 주소에 소프트웨어 브레이크포인트 대신 **하드웨어 브레이크포인트**(REV-0536)를 쓰는 것이다. 하드웨어 브레이크포인트는 코드 바이트를 전혀 건드리지 않으므로 이 검사를 그대로 통과한다. 체크섬 검사 자체를 패치해서 항상 통과하도록 만드는 방법도 있지만, 이는 코드 자체를 수정하는 것이라 별도의 무결성 검사가 또 있다면 연쇄적으로 걸릴 수 있다.

## 명령어/단축키
- x64dbg: `bp <주소>`(소프트웨어 BP), `ba x 1 <주소>`(하드웨어 BP로 대체), `dump <주소>`로 실행 중 실제 메모리 바이트 확인
- IDA: 함수 시작에서 `Ctrl+E`(EA 목록)로 여러 함수 크기 비교, `Shift+F12`(Strings)로 체크섬 관련 상수 검색
- x64dbg: `Follow in Dump` 후 특정 주소가 실행 중 `0xCC`로 바뀌는지 실시간 관찰

## 출력 해석
- 실행 중 메모리 덤프에서 원래 명령어 자리에 `CC`가 보이면 그 위치에 소프트웨어 브레이크포인트가 걸려 있다는 직접적인 증거다.
- 체크섬 비교 결과가 "불일치"로 나오는 분기를 따라가면, 대개 종료(`ExitProcess`)나 잘못된 키/플래그 값 생성으로 이어진다 — 정상 흐름에서는 절대 도달하지 않는 코드처럼 보이므로 이 분기 자체가 좋은 단서가 된다.
- CRC 계산 결과가 특정 상수와 정확히 일치해야 통과하는 구조라면, 그 상수는 "원본(패치 안 된) 코드의 체크섬"이므로 코드를 조금이라도 패치하면 이 상수와 어긋나게 된다는 점을 항상 염두에 둬야 한다.

## 흔한 실수
- 하드웨어 브레이크포인트도 이 검사에 걸릴 것이라고 착각하는 것 — 이 기법은 오직 코드 바이트 변조(소프트웨어 BP)만 잡는다는 점을 구분해야 한다.
- 체크섬 검사 루프를 발견하고 바로 코드를 패치하는 것 — 패치 자체가 검사 대상 범위 안에 있으면 다음 검사에서 다시 걸린다. 검사 조건(비교 분기)을 패치하는 게 더 안전할 때가 많다.
- 검사가 한 번만 실행된다고 가정하는 것 — 실제로는 여러 함수 진입 시점마다 반복 호출되는 경우가 흔해서, 한 곳만 우회하고 안심하면 다른 지점에서 다시 걸린다.
- `INT3`(0xCC)와 `INT 3`(`0xCD 0x03`, 2바이트 형태)를 혼동하는 것 — 디버거가 자동으로 심는 것은 항상 1바이트 `0xCC`이고, 2바이트 `INT 3`은 컴파일러가 직접 넣는 경우에만 나타난다.

## 막혔을 때 다음 체크
- 하드웨어 브레이크포인트로 우회하는 원리를 더 자세히 보고 싶다면 → REV-0536 하드웨어 브레이크포인트(DR 레지스터) 탐지 기법
- 이 검사가 SEH/VEH와 결합된 형태라면 → REV-0539 SEH 기반 안티디버깅 심화 또는 REV-0540 VEH(Vectored Exception Handler) 기반 안티디버깅
- `.text` 섹션 범위를 정확히 특정하는 법이 궁금하다면 → REV-0117 PE Section Table 읽기
- 여러 안티디버깅 기법을 한눈에 정리한 표가 필요하다면 → REV-0529 — Windows 안티디버깅 기법 종류 빠른 참조표

## 미니 예제
```c
#include <windows.h>

BOOL CheckSoftwareBreakpoint(void* funcAddr) {
    BYTE first = *(BYTE*)funcAddr;
    return (first == 0xCC);
}

DWORD SimpleChecksum(BYTE* start, size_t len) {
    DWORD sum = 0;
    for (size_t i = 0; i < len; i++)
        sum += start[i];
    return sum;
}

int main(void) {
    if (CheckSoftwareBreakpoint((void*)main)) {
        ExitProcess(1);
    }
    if (SimpleChecksum((BYTE*)main, 0x50) != 0x1A2B3C4D) {
        ExitProcess(2);
    }
    printf("Enter flag: ");
    return 0;
}
```
디스어셈블리에서는 `main`(또는 보호 대상 함수)의 주소를 로드해서 첫 바이트를 읽고 `cmp al, 0CCh`로 비교하거나, 루프를 돌며 바이트 합산 후 고정 상수와 `cmp`하는 두 패턴이 함께 나타날 수 있다.

## 관련 글
- REV-0536 — 하드웨어 브레이크포인트(DR 레지스터) 탐지 기법
- REV-0539 — SEH 기반 안티디버깅 심화
- REV-0540 — VEH(Vectored Exception Handler) 기반 안티디버깅
- REV-0117 — PE Section Table 읽기
- REV-0529 — Windows 안티디버깅 기법 종류 빠른 참조표

## 출처/검증
- 소프트웨어 브레이크포인트가 대상 바이트를 `0xCC`(`INT3`)로 치환하는 방식으로 동작한다는 것은 Intel SDM Volume 2A의 `INT3` 명령어 설명 및 Microsoft 디버깅 관련 문서에서 공통적으로 확인되는 표준 동작이다.
- 코드 체크섬/self-checksumming 기반 안티디버깅·안티변조 기법은 다수의 공개 리버싱 레퍼런스(Check Point "Anti-Debug Tricks", Unprotect Project)에서 정리된 일반적인 패턴을 기준으로 서술했다(2026-09-08 확인).
