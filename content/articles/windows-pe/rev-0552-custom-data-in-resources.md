## 한 줄 요약
리소스 타입은 로더가 강제하는 형식 검증이 전혀 없는 "이름표"에 불과하기 때문에, 표준 `RT_RCDATA` 외에도 개발자가 임의로 정의한 문자열 타입 이름, 여러 개로 조각낸 소용량 리소스, 이미지/문자열 형식으로 위장한 데이터, 심지어 정상 리소스 데이터 뒤에 덧붙인 여분 바이트 등 다양한 방식으로 임의 데이터를 숨길 수 있으며, 각 리소스를 "선언된 타입이 요구하는 형식과 실제 바이트가 정말 일치하는지" 기준으로 검증하는 습관이 이런 은닉을 찾아내는 공통 열쇠다.

## 언제 검색해야 하나
- 리소스 트리에서 `RT_ICON`, `RT_VERSION`처럼 표준 상수가 아니라 따옴표로 된 문자열 타입 이름(`"DATA"`, `"CONFIG"` 등)을 발견했을 때
- 비슷한 이름의 작은 리소스가 수십~수백 개 나열되어 있어서 조각난 데이터가 아닌지 의심될 때
- `RT_STRING` 리소스에 사람이 읽을 수 있는 문구가 아니라 base64처럼 보이는 긴 문자열이 들어있을 때
- Detect It Easy나 PE-bear의 엔트로피 분석에서 특정 리소스만 유독 높은 엔트로피(7.5 이상)를 보일 때
- 이미 `RT_RCDATA` 위장 기법(REV-0141)은 확인했는데, 그보다 더 교묘한 은닉 방식이 있는지 궁금할 때

## 핵심 개념

### 왜 리소스는 은닉에 매력적인가
`.rsrc`는 `.text`(코드)나 `.data`(전역 변수)와 달리 "실행에 직접 관여하지 않는 부가 정보"로 인식되기 때문에, 초심자용 정적 분석 도구나 자동화 스캐너가 상대적으로 얕게 훑고 지나가는 경우가 많다. 또한 리소스 타입은 앞서 REV-0548에서 다룬 것처럼 `IMAGE_RESOURCE_DIRECTORY_ENTRY.Name`에 숫자든 임의 문자열이든 자유롭게 넣을 수 있고, 그 안의 데이터가 그 타입에 맞는 형식이어야 한다는 강제 검증도 로더 수준에서는 없다. 이 두 특성이 리소스를 은닉 장소로 매력적으로 만든다.

### 기법 1 — 커스텀(비표준) 타입 이름 사용
`.rc` 스크립트에서 `MYDATA CUSTOMTYPE "payload.bin"` 형태로 컴파일하면, 리소스 컴파일러는 `Type` 레벨의 `Name`을 표준 `RT_*` 숫자 상수가 아니라 `"CUSTOMTYPE"`이라는 문자열로 만든다(하이비트=1, REV-0548 참고). 대부분의 도구는 이런 커스텀 타입도 트리에 표시하지만, 사람이 훑어볼 때는 익숙한 `RT_ICON`/`RT_VERSION` 사이에서 낯선 이름 하나가 섞여 있으면 놓치기 쉽다.

### 기법 2 — 데이터 조각화(fragmentation)
페이로드를 하나의 큰 리소스로 넣으면 "리소스 하나가 유독 크다"는 게 눈에 띄기 쉽다. 이를 피하기 위해 페이로드를 수십~수백 개의 작은 조각으로 나눠 각각 별도의 리소스 ID로 저장하고, 실행 시점에 코드가 `FindResource`/`LoadResource`를 반복 호출해 순서대로 이어붙이는 방식이다. 개별 리소스는 작아서 크기 기반 휴리스틱을 통과하기 쉽지만, 리소스 개수가 유난히 많다는 것 자체가 단서가 된다.

### 기법 3 — 형식 위장(이미지/텍스트처럼 보이게)
`RT_BITMAP`이나 `RT_ICON` 자리에 유효한 헤더(`BITMAPINFOHEADER` 등)를 앞부분에 채워 넣어 "정상 이미지처럼 렌더링은 되지만" 그 뒤에 실제 페이로드를 덧붙이는 방식(REV-0551의 아이콘 트레일링 기법과 원리가 같다). 또는 `RT_STRING` 테이블에 사람이 읽는 문구 대신 base64/hex로 인코딩한 텍스트를 넣어두는 방식도 흔하다 — 문자열 리소스는 원래 UI 텍스트를 담는 곳이라 의심을 덜 받는다.

### 기법 4 — 여분 바이트 덧붙이기(트레일링)
`IMAGE_RESOURCE_DATA_ENTRY.Size`는 도구가 신뢰하는 값이지만, 만약 코드가 `FindResource`/`SizeofResource`로 얻은 크기를 쓰지 않고 자체적으로 계산한 오프셋과 길이로 데이터를 읽는다면, 공격자는 정상 형식 데이터 뒤에 원하는 만큼 바이트를 덧붙이고 자체 파싱 루틴에서만 그 여분을 읽어내는 방식도 가능하다. 이 경우 표준 리소스 뷰어는 앞부분(정상 형식)만 렌더링하고 여분은 그냥 무시한다.

### 기법 5 — 문자열 리소스와 매니페스트 여백 남용
`RT_STRING`은 원래 16개 문자열을 하나의 리소스 블록에 묶어 저장하는 특수한 구조(문자열마다 WORD 길이 접두 + UTF-16 문자, 16개 슬롯 중 실제로 안 쓰는 슬롯은 길이 0으로 남김)인데, 이 미사용 슬롯이나 특정 언어(Language) 리프 자체를 통째로 실제 UI에는 안 쓰이는 예비 슬롯으로 만들어 그 안에 인코딩된 데이터를 채워 넣는 방식도 관찰된다. 또한 `RT_MANIFEST`(REV-0550)처럼 사람이 읽는 XML 텍스트를 담는 리소스에 XML 주석(`<!-- ... -->`) 형태로 base64 데이터를 끼워 넣어, 매니페스트 파서는 정상적으로 무시하지만 별도 코드가 그 주석 텍스트를 직접 읽어 디코딩하는 방식도 이론적으로 가능하다. 두 방식 모두 "이 리소스 타입은 항상 이런 용도로만 쓰인다"는 관성적 가정을 역이용한다는 점에서 앞의 네 가지 기법과 본질이 같다.

## 화면/코드에서 보이는 징후
- 리소스 트리에서 `RT_*` 표준 상수가 아니라 따옴표 있는 문자열 타입 이름이 섞여 있음
- 비슷한 접두사(`CHUNK0`, `CHUNK1`, ... `CHUNK127`)를 가진 소용량 리소스가 대량으로 나열됨
- `RT_STRING` 테이블 항목이 자연어 문구가 아니라 `A0B1C2D3...` 같은 순수 16진수/base64 패턴처럼 보임
- Detect It Easy의 섹션/리소스별 엔트로피 분석에서 특정 항목만 7.5~8.0에 가까운 높은 값을 보임(압축/암호화 가능성)
- IDA 임포트 목록에 `FindResourceW`/`FindResourceExW`, `LoadResource`, `LockResource`, `SizeofResource`가 반복 호출되는 루프 패턴이 보임

## 가장 먼저 할 것
`.rsrc` 트리를 펼쳐 놓고 "이름이 익숙한가", "개수가 비정상적으로 많은가", "타입과 내용이 실제로 일치하는가" 세 가지 기준으로 빠르게 훑는다. 셋 중 하나라도 걸리면 해당 리소스(들)을 원시로 추출해 HxD/엔트로피 분석으로 넘어간다.

## 단계별 절차
**1) 리소스 트리 전체 목록화**
Resource Hacker나 PE-bear로 모든 Type/Name/Language 조합과 각 항목의 크기를 표로 뽑는다.

**2) 비표준 이름/과다 개수 스캔**
표준 `RT_*`가 아닌 타입 이름, 또는 유사한 이름 패턴이 반복되는 대량 항목이 있는지 확인한다.

**3) 형식 일치 여부 검증**
이미지/문자열 타입으로 선언된 항목의 실제 바이트가 그 형식의 헤더 규칙(예: 비트맵이면 `BITMAPINFOHEADER.biSizeImage`로 계산되는 예상 크기)과 일치하는지 계산해서 대조한다.

**4) 조각 리소스 이어붙이기**
조각화가 의심되면 각 리소스를 ID 순서대로 추출해 이어붙인 뒤(코드에서 어떤 순서로 이어붙이는지는 IDA에서 `FindResource` 호출 루프의 인덱스 계산을 봐야 정확히 알 수 있다) 파일 시그니처나 압축 헤더가 나타나는지 확인한다.

**5) IDA로 실제 사용 코드 확인**
임포트에서 `FindResourceW`/`FindResourceExW`를 교차 참조(`X`)해 호출 인자(타입, 이름/ID)를 확인하고, 그 뒤 `LockResource`로 얻은 포인터가 어떻게 쓰이는지(복호화 루프로 들어가는지, 다른 프로세스에 쓰이는지 등) 추적한다.

## 명령어/단축키
```text
Resource Hacker: 트리 전체를 펼쳐 Type/Name 목록 확인, 우클릭 → Save Resource As Binary File
Detect It Easy: 리소스/섹션별 엔트로피 분석 탭
IDA: 임포트에서 FindResourceW/FindResourceExW/LoadResource/LockResource 교차 참조(X)
HxD: 추출 파일에서 헤더 이후 오프셋으로 이동(Ctrl+G)해 여분 데이터 확인
```

## 출력 해석
- 커스텀 타입 이름의 데이터가 `MZ`/`PK`/`Rar!`/`7z` 등 알려진 파일 시그니처로 시작하면 페이로드가 거의 확실
- 조각들을 이어붙였을 때 유효한 압축/실행 파일 헤더가 나타나면 조각화 은닉이 맞음 — 순서가 틀리면 헤더가 깨지므로 여러 순서 조합(ID 오름차순, 이름 사전순 등)을 시도해봐야 할 수도 있음
- 엔트로피가 낮고(4.0 이하) 특정 패턴이 반복되면 단순 압축되지 않은 설정 데이터일 가능성이 더 높음
- 형식 위장 이미지에서 헤더가 요구하는 크기와 실제 크기 차이가 몇 바이트 수준이면 단순 정렬 패딩일 수 있으니, 차이가 최소 수백 바이트 이상으로 크게 나는 경우에 우선순위를 둬서 확인

## 흔한 실수
- 표준 `RT_*` 상수 목록에 없는 이름을 보자마자 무조건 악성으로 단정하는 것 — 정상적인 상용 소프트웨어도 자체 설정/에셋을 커스텀 리소스 타입으로 저장하는 경우가 흔하다. 반드시 내용을 확인해야 한다.
- 조각화된 리소스를 발견했지만 코드에서 실제로 이어붙이는 순서를 확인하지 않고 임의 순서로 이어붙여 "페이로드가 아니다"라고 성급히 결론짓는 것.
- `RT_STRING` 테이블의 이상한 텍스트를 보고도 그게 단순히 다국어 미번역 placeholder일 가능성을 배제하지 않는 것 — base64처럼 보여도 실제로는 다른 목적(라이선스 키 포맷 등)일 수 있으니 디코드해서 실제로 의미 있는 바이트가 나오는지 확인해야 한다.
- 리소스 데이터의 엔트로피만으로 압축/암호화 여부를 100% 확신하는 것 — 이미 압축된 이미지 포맷(PNG 등)도 원래 엔트로피가 높으므로, 반드시 선언된 형식과 실제 크기/헤더가 일치하는지 함께 확인해야 한다.

## 미니 예제
`launcher.exe`의 리소스 트리를 Resource Hacker로 펼쳐보니 표준 `RT_ICON`, `RT_VERSION` 사이에 `"NETRES"`라는 커스텀 타입 아래 `PART_0000`부터 `PART_0063`까지 64개의 작은 항목(각 약 8KB)이 있었다. IDA에서 임포트를 확인하니 `FindResourceW`가 루프 안에서 `L"PART_%04d"` 형태의 이름을 만들어 순서대로 호출하고, 각 결과를 `LockResource`로 읽어 하나의 버퍼에 이어붙이는 코드가 있었다. 64개를 ID 오름차순으로 모두 이어붙여 저장한 뒤 HxD로 확인하니 시작 바이트가 `4D 5A 90 00`(`MZ`)이었다. 개별 조각은 8KB 안팎이라 리소스 크기만 보고는 전혀 의심스럽지 않았지만, "비슷한 이름의 리소스가 64개"라는 개수 패턴 자체가 결정적인 단서였다.
