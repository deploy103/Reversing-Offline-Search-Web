## 한 줄 요약
CRC32, MD5, SHA-1, FNV, TEA/XTEA 같은 잘 알려진 알고리즘은 **표준으로 정해진 고유한 상수(매직 넘버)**를 코드 안에 그대로 갖고 있으므로, 그 상수를 IDA의 즉시값 검색(`Alt+I`)이나 Ghidra의 **Search → For Scalars**로 찾아내면 함수 이름이 `FUN_`이든 스트립되어 있든 상관없이 "이 함수가 어떤 알고리즘인지" 즉시 알아낼 수 있다.

## 언제 검색해야 하나
- 함수 안에 반복문과 XOR/시프트/덧셈이 뒤섞여 있는데 이게 표준 해시/암호 알고리즘인지 자체 제작 알고리즘인지 판단이 안 될 때
- `strcmp` 같은 명확한 문자열 비교가 안 보이고, 대신 정수 하나를 계산해서 비교하는 체크섬/해시 방식의 검증일 때(REV-0163, REV-0164로 해결이 안 될 때)
- 코드에 `0xEDB88320`, `0x67452301`, `0x9E3779B9` 같은 낯선 16진수 상수가 반복적으로 보일 때
- 알고리즘의 이름만 알아내면 인터넷 자료 없이도(오프라인 환경) 직접 구현을 재현해서 풀 수 있는 상황일 때

## 핵심 개념
CRC, 해시 함수, 일부 경량 암호 알고리즘은 표준 문서에 정의된 **고정된 초기값/다항식/라운드 상수**를 그대로 사용해야 정확히 같은 결과가 나온다. 이 값들은 알고리즘마다 유일하므로, 바이너리 안에서 이 상수를 발견하면 그 자체로 "이 코드는 이 알고리즘이다"라는 강력한 증거가 된다. 대표적인 값들:

| 알고리즘 | 대표 상수(16진수) | 의미 |
|---|---|---|
| CRC32(IEEE 802.3, zlib 등) | `0xEDB88320` | 반사된(reflected) 다항식 |
| MD5 | `0x67452301`, `0xEFCDAB89`, `0x98BADCFE`, `0x10325476` | 초기 해시 값(A, B, C, D) |
| SHA-1 | `0x67452301`, `0xEFCDAB89`, `0x98BADCFE`, `0x10325476`, `0xC3D2E1F0` | 초기 해시 값(H0~H4, MD5와 앞부분 유사) |
| SHA-256 | `0x6a09e667`, `0xbb67ae85`, `0x3c6ef372`, ... | 초기 해시 값(소수의 제곱근 소수부) |
| FNV-1/1a (32비트) | `2166136261`(`0x811C9DC5`, offset basis), `16777619`(`0x01000193`, prime) | 초기값과 곱셈 상수 |
| TEA/XTEA | `0x9E3779B9` | 델타(황금비 기반 상수) |
| Adler-32 | `65521`(`0xFFF1`) | 모듈러 연산 기준 소수 |
| Base64 인코딩 테이블 | 문자열 `"ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/"` | 인코딩 알파벳(문자열 검색으로도 찾을 수 있음) |

이 표에 없는 상수라도, 검증 로직 안에서 "왜 이 숫자를 쓰는지 설명이 안 되는 값"이 있다면 일단 검색엔진에 그 16진수/10진수 값을 그대로 검색해 보는 것도 유효한 전략이다(단, 이 documents 자체는 오프라인 환경을 가정하므로, 위 표처럼 자주 나오는 상수는 미리 외워두거나 이 문서를 오프라인으로 참고하는 것이 유용하다).

REV-0163(문자열)과 REV-0164(Imports)는 각각 "출력 메시지"와 "라이브러리 함수 호출"이라는 단서에 의존한다. 하지만 검증 로직이 **자체 구현한 해시/체크섬 함수**로 이루어져 있으면 이 두 단서가 모두 없을 수 있다. 이때 상수 검색이 세 번째 대안 경로가 된다.

## 화면/코드에서 보이는 징후
- 디컴파일 결과에 `for`/`while` 반복문 안에서 `<<`, `>>`, `^`, `+`, `*` 연산이 반복되는데 무슨 알고리즘인지 감이 안 잡힌다.
- 낯선 16진수 상수(8자리 이상)가 여러 개 나열되어 있거나, 배열 초기화 형태로 `0x67452301, 0xefcdab89, ...`처럼 4~5개가 연속으로 선언되어 있다.
- 함수 이름이 `FUN_` 그대로이고 문자열/Import 단서도 빈약한데, 결과값 하나를 계산해서 무언가와 비교하는 구조다.

## 가장 먼저 할 것
의심스러운 상수 하나를 정확히 적어두고(오탈자 주의, 16진수 대소문자와 자릿수를 그대로), 위 표와 대조해 본다. 표에 없으면 IDA는 `Alt+I`, Ghidra는 **Search → For Scalars**로 그 상수가 바이너리 다른 곳에서도 쓰이는지부터 확인한다.

## 단계별 절차

**1) 의심 상수 특정**

Decompile/디스어셈블리에서 설명이 안 되는 상수를 하나 고른다. 여러 개가 뭉쳐 있다면(초기화 배열 형태) 전부 기록해 둔다.

**2) 알려진 매직 넘버 표와 대조**

위 표(또는 이 문서를 기반으로 만든 개인 체크리스트)와 값을 비교한다. 정확히 일치하면 알고리즘이 확정된 것이다.

**3) 표에 없으면 즉시값/스칼라 검색으로 다른 사용처 확인**

- IDA: **Alt+I**(Search Immediate Value)를 누르고 값을 입력(10진수 또는 `0x` 접두사 16진수)해서 검색한다. `Ctrl+I`로 다음 일치 위치로 계속 이동할 수 있다.
- Ghidra: **Search → For Scalars...**를 열고 값을 입력한다(10진수 또는 `0x` 접두사). 결과가 테이블로 나열되며, 더블클릭하면 해당 위치로 이동한다.

**4) 같은 값이 배열/테이블 형태로 여러 개 붙어 있는지 확인**

특히 해시 함수는 초기값이 4~8개가 연속으로 붙어 있는 경우가 많다(MD5/SHA는 4~8워드). 하나를 찾았다면 그 주변 메모리를 Hex View(REV-0162)로 확인해서 나머지 상수들도 표와 맞는지 대조한다.

**5) 알고리즘이 확정되면 함수 경계와 흐름 정리**

이 상수를 사용하는 함수가 어디서 시작해서 어디서 끝나는지, 어떤 입력을 받아 어떤 출력을 내는지(리턴값, 아웃 파라미터)를 정리한다. 표준 알고리즘이라는 것을 알았으므로, 세부 구현 로직을 한 줄씩 다 이해하지 않아도 "표준 CRC32/MD5/FNV 구현"이라고 가정하고 넘어갈 수 있다.

**6) 오프라인 환경에서 알고리즘 재현**

표준 알고리즘임이 확정되면, Python 표준 라이브러리(`hashlib`, `zlib.crc32` 등) 또는 잘 알려진 순수 파이썬 구현으로 동일한 로직을 오프라인에서 재현할 수 있다. 이 부분은 REV-0168(정적 분석 결과를 Python 의사코드로 옮기기)에서 이어서 다룬다.

## 명령어/단축키
- IDA: 즉시값 검색 `Alt+I`, 다음 항목 `Ctrl+I`, 바이트 시퀀스 검색 `Alt+B`, 다음 항목 `Ctrl+B`
- Ghidra: **Search → For Scalars...**, 결과 테이블에서 더블클릭으로 이동, 바이트 시퀀스는 **Search → Memory...**
- 공통: 확정된 상수를 찾은 주소는 REV-0161 방식으로 이름을 붙여두면(`CRC32_TABLE`, `MD5_INIT` 등) 이후 다시 볼 때 바로 알아볼 수 있다.

## 출력 해석
- 즉시값 검색 결과가 하나도 없다면, 그 상수는 코드 안에 리터럴로 직접 박혀 있지 않고 계산으로 생성되거나(예: 런타임에 계산해서 만듦) 다른 진법/바이트 순서로 표현되어 있을 수 있다. 엔디안을 바꿔서(바이트 순서를 뒤집어서) 다시 검색해 본다.
- 검색 결과가 매우 많다면(수십~수백 개) 그 값은 흔한 스택 오프셋이나 작은 정수(0, 1, -1 등)처럼 알고리즘과 무관한 범용 상수일 가능성이 크다. 자릿수가 크고(8자리 16진수 이상) 특이한 패턴일수록 신뢰도가 높은 단서다.
- CRC32의 경우 값 자체(`0xEDB88320`)뿐 아니라, 이 값을 이용해 **256개 항목짜리 룩업 테이블**을 미리 계산해 둔 배열이 데이터 섹션에 통째로 박혀 있는 구현도 흔하다. 이 경우 코드에서 직접 다항식 상수가 안 보이고 큰 데이터 배열만 보일 수 있으니, 이런 배열을 만나면 "CRC32 lookup table일 가능성"을 의심하고 첫 몇 개 값을 표준 CRC32 테이블과 대조해본다.

## 흔한 실수
- 16진수 상수를 10진수로 착각하거나 반대로 착각해서 검색에 실패하는 것 — IDA/Ghidra 모두 `0x` 접두사로 16진수임을 명시해야 한다.
- 엔디안을 고려하지 않고 검색하는 것 — 검색 기능은 보통 "값"을 기준으로 검색해 내부적으로 엔디안을 처리해 주지만, Hex View에서 직접 바이트를 눈으로 찾을 때는 리틀 엔디안으로 뒤집힌 바이트 순서를 착각하기 쉽다(REV-0162 참고).
- 상수 하나만 일치한다고 알고리즘 전체를 성급히 확정하는 것 — 특히 MD5와 SHA-1은 초기값 4개가 겹치므로(`0x67452301` 등), 나머지 상수(SHA-1의 다섯 번째 초기값 `0xC3D2E1F0` 존재 여부, 라운드 상수 등)까지 확인해서 정확히 구분해야 한다.
- 자체 제작(커스텀) 알고리즘인데도 어떻게든 표준 알고리즘에 끼워 맞추려 하는 것 — 상수가 표와 정확히 일치하지 않으면 억지로 끼워 맞추지 말고, 그 자체로 "이 CTF만의 커스텀 변형 알고리즘"으로 보고 코드를 그대로 재현하는 방향으로 전환해야 한다.

## 막혔을 때 다음 체크
- 상수를 찾았는데 알고리즘 이름을 모르겠다면 → 이 문서의 표를 다시 확인하고, 자릿수와 값을 한 글자씩 재대조.
- 상수 근처 데이터가 실제로 무엇인지 확인하고 싶다면 → REV-0162(Hex View로 디컴파일 결과 검증하기).
- 이 상수를 쓰는 함수가 프로그램 전체에서 어디에 위치하는지 궁금하다면 → REV-0166(함수 Call Graph로 핵심 로직 좁히기).
- 알고리즘을 확정한 뒤 실제로 파이썬으로 재현해서 정답을 계산하고 싶다면 → REV-0168(정적 분석 결과를 Python 의사코드로 옮기기), 그리고 FNV 계열이라면 ../algorithms/rev-0208-fnv-16777619.md도 함께 참고.

## 미니 예제
어떤 함수의 디컴파일 결과가 다음과 같다고 하자.

```c
undefined4 FUN_00401700(char *param_1, int param_2) {
  uint hash;
  int i;
  hash = 2166136261;
  for (i = 0; i < param_2; i = i + 1) {
    hash = hash ^ (byte)param_1[i];
    hash = hash * 16777619;
  }
  return hash;
}
```

1. `2166136261`이라는 상수가 눈에 띈다. 위 표와 대조하면 `0x811C9DC5`, 즉 **FNV-1a 32비트의 offset basis**와 정확히 일치한다.
2. 곱셈에 쓰이는 `16777619`도 표와 대조하면 `0x01000193`, **FNV prime**과 일치한다.
3. 반복문 구조(XOR 먼저, 곱셈 나중)까지 보면 이는 표준 **FNV-1a** 알고리즘이라고 확정할 수 있다.
4. 알고리즘이 확정되었으므로, 이 함수를 처음부터 끝까지 해석하려 애쓰지 않아도 "입력 바이트 배열의 FNV-1a 해시를 계산하는 함수"라는 결론을 즉시 내릴 수 있다. 이후 목표 해시값과 비교하는 코드를 REV-0163/0164 방식으로 이어서 찾으면 된다.

FNV 해시 자체의 세부 계산 규칙과 파이썬 구현 예시는 ../algorithms/rev-0208-fnv-16777619.md 문서에 별도로 정리되어 있다.

## 관련 글
- REV-0162 — Hex View로 디컴파일 결과 검증하기
- REV-0163 — 문자열에서 검증 함수로 이동하는 정적 분석
- REV-0164 — Imports에서 검증 함수 후보 좁히기
- REV-0166 — 함수 Call Graph로 핵심 로직 좁히기
- REV-0168 — 정적 분석 결과를 Python 의사코드로 옮기기
- ../algorithms/rev-0208-fnv-16777619.md — FNV 해시(offset basis 2166136261, prime 16777619) 상세

## 출처/검증
- IDA 즉시값 검색(`Alt+I`/`Ctrl+I`)과 바이트 시퀀스 검색(`Alt+B`/`Ctrl+B`): Hex-Rays 공식 문서(Search 메뉴, Shortcuts 레퍼런스) 기준.
- Ghidra Search → For Scalars, Search → Memory: Ghidra 공식 Help 문서 및 Ghidra Beginner 교육 자료(Introduction to Ghidra) 기준.
- CRC32/MD5/SHA-1/SHA-256/TEA/Adler-32/FNV의 표준 초기값·다항식·상수는 각 알고리즘의 공개 표준 명세(RFC 1321(MD5), FIPS 180-4(SHA), RFC 1950(Adler-32/zlib), FNV 초안 명세, TEA 원 논문)에 정의된 값을 기준으로 정리했다.
- 이 문서는 라이브 IDA/Ghidra 화면을 직접 캡처해 재검증하지는 않았으며, 공식 문서와 표준 알고리즘 명세를 기준으로 작성되었다.
