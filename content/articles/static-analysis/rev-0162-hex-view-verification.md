## 한 줄 요약
디컴파일러(IDA F5, Ghidra Decompile 창)가 보여주는 C 유사 코드는 **추정 결과**이므로, 문자열/상수/구조체 레이아웃처럼 정답이 명확히 존재하는 값은 반드시 **Hex View(원본 바이트 그대로 보기)**로 열어 직접 눈으로 확인하는 습관이, 잘못된 가설로 시간을 낭비하지 않는 가장 확실한 방법이다.

## 언제 검색해야 하나
- Decompile 창에 `DAT_00403010`, `unk_403010` 같은 이름만 보이고 실제로 뭐가 들어있는지 궁금할 때
- 디컴파일러가 보여주는 상수값(예: `0x7fffffff`, `0x12345678`)이 진짜 그 값이 맞는지 의심될 때
- 문자열이 깨져 보이거나(예: 유니코드인데 ASCII로 잘못 해석됨) 이상한 문자가 섞여 나올 때
- 구조체 필드 레이아웃을 직접 정의하려는데, 실제 메모리에 그 필드들이 어떤 순서/간격으로 있는지 확인하고 싶을 때
- XOR 키, 룩업 테이블처럼 "바이트 배열 그 자체"가 알고리즘의 핵심인 경우

## 핵심 개념
디컴파일러는 어셈블리 명령어들을 패턴 매칭해서 C 문법으로 재구성하는 **번역기**다. 번역 과정에서 다음과 같은 왜곡이 생길 수 있다.

1. **타입 추정 오류**: 어떤 값이 `int`인지 `unsigned int`인지 디컴파일러가 문맥만으로 추정하다가 부호를 잘못 판단하면, 실제로는 양수인데 음수로(또는 반대로) 표시될 수 있다.
2. **문자열 인코딩 오추정**: 유니코드(UTF-16LE) 문자열을 ASCII로 잘못 해석하면 글자 사이에 `\x00`이 낀 이상한 문자열로 보이거나, 반대로 ASCII를 유니코드로 잘못 잡으면 절반만 보인다.
3. **구조체/배열 경계 오추정**: 디컴파일러가 스택이나 힙의 연속된 바이트를 어디까지를 한 변수로 볼지 잘못 나누면, 실제로는 하나의 배열인데 여러 개의 별개 변수(`local_28`, `local_24`, `local_20`...)로 쪼개져 표시될 수 있다.
4. **상수 표시 방식**: 같은 4바이트라도 리틀 엔디안 메모리 배열을 사람이 읽기 좋은 정수로 변환하는 과정에서, 실제 바이트 순서와 화면에 표시된 정수 표기가 직관과 다르게 느껴질 수 있다.

이런 왜곡들을 걸러내는 방법은 하나다 — **디컴파일러의 해석을 거치지 않은, 메모리에 실제로 저장된 바이트 값을 그대로 보는 것.** 이것이 Hex View(헥스 뷰)의 역할이다. Hex View는 해석 없이 각 바이트를 16진수 두 자리로, 그 옆에 프린터블 문자면 ASCII로 그대로 나열해서 보여준다. 디컴파일 결과와 Hex View를 나란히 대조하면 "디컴파일러의 해석"과 "실제 데이터"의 차이를 바로 알아챌 수 있다.

**IDA에서는**: 기본 화면 구성에 **Hex View-1** 탭이 포함되어 있다(없으면 View → Open subviews → Hex dump). 디스어셈블리 뷰나 Decompile 창에서 주소를 클릭하면, IDA는 여러 뷰가 같은 주소를 동기화해서 보여주는 구조이므로 Hex View-1 탭으로 전환만 해도 방금 보던 주소의 원본 바이트가 그대로 나온다. 특정 주소로 바로 이동하려면 Hex View 탭을 클릭한 상태에서 `G`(Jump to address)를 눌러 주소를 입력한다.

**Ghidra에서는**: **Window → Bytes**를 열면 Listing과 동기화되는 hex dump 패널이 뜬다(버전에 따라 기본으로 이미 열려 있을 수도 있다). Listing이나 Decompile 창에서 커서를 옮기면 Bytes 패널도 같은 주소로 따라 이동한다. Decompile 창에서 `DAT_00403010` 같은 이름을 더블클릭하면 Listing이 그 주소로 이동하고, Bytes 패널도 함께 그 위치의 원본 바이트를 보여준다.

## 화면/코드에서 보이는 징후
- Decompile 창에 이름만 있고 값이 안 보이는 전역 데이터(`DAT_`, `unk_`, `off_` 등)가 있다.
- 디컴파일러가 상수를 이상한 형태(음수, 매우 큰 16진수 등)로 보여주는데 문맥상 말이 안 되는 값 같다.
- 문자열이 한 글자씩 띄어져 있거나(`H.e.l.l.o.` 같은 패턴) 문자열 끝이 이상하게 잘려 있다.

## 가장 먼저 할 것
디컴파일 결과에서 의심스러운 이름/값을 하나 고른 뒤, 그 주소로 이동해서 Hex View(IDA는 Hex View-1 탭, Ghidra는 Bytes 패널)에 원본 바이트가 어떻게 찍혀 있는지 눈으로 직접 확인한다.

## 단계별 절차

**1) 의심 지점 특정**

Decompile/pseudocode에서 `DAT_XXXXXXXX`, `unk_XXXXXXXX`, 이상해 보이는 상수, 배열처럼 보이는 지역 변수 등을 하나 고른다.

**2) 해당 주소로 이동**

그 이름을 더블클릭(IDA/Ghidra 공통)하면 디스어셈블리/Listing 뷰가 그 주소로 이동한다.

**3) Hex View로 전환**

- IDA: **Hex View-1** 탭을 클릭한다. 탭이 안 보이면 View → Open subviews → Hex dump.
- Ghidra: **Window → Bytes**를 연다. 이미 열려 있다면 그냥 패널을 확인한다.

**4) 바이트를 있는 그대로 읽기**

Hex View는 왼쪽에 주소, 가운데에 16진수 바이트 나열, 오른쪽에 그 바이트들의 ASCII 표현(프린트 불가능한 바이트는 보통 `.`으로 표시)을 함께 보여준다. 이 세 부분을 함께 보면서 실제로 몇 바이트가 어떤 값인지 확인한다.

**5) 문자열이면 인코딩 확인**

바이트 사이사이에 `00`이 규칙적으로 끼어 있다면(예: `48 00 65 00 6c 00`) 이는 UTF-16LE(유니코드) 문자열이라는 뜻이다. `00`이 없이 바이트가 연속되어 있으면 일반 ASCII/UTF-8 문자열이다. 디스어셈블러가 이를 잘못 판단했다면, 해당 주소에서 우클릭 → 데이터 타입을 문자열로 다시 지정(IDA는 `Alt+A`로 ASCII String 스타일 변경, Ghidra는 우클릭 → Data → Unicode/String으로 재지정)해서 올바르게 렌더링되도록 고칠 수 있다.

**6) 상수/배열이면 바이트 단위로 직접 재구성**

여러 바이트로 이루어진 정수 상수는 리틀 엔디안 규칙(주소가 낮은 바이트가 값의 하위 바이트)에 따라 뒤에서부터 앞으로 읽어 값을 재구성한다. 예를 들어 Hex View에 `78 56 34 12`가 연속으로 있다면 이는 32비트 정수 `0x12345678`이다. 디컴파일러가 표시하는 정수와 이 계산 결과가 같은지 대조한다.

**7) 구조체 필드 오프셋 검증**

구조체를 정의하려는 경우, Hex View에서 값이 바뀌는 경계(예: 4바이트마다 의미 있는 값이 반복되는 패턴)를 직접 세어보고, 그 간격이 REV-0161에서 만든 구조체 정의의 필드 오프셋과 일치하는지 확인한다.

## 명령어/단축키
- IDA: Hex View-1 탭 클릭, 탭 안에서 `G`(Jump to address), 데이터 재정의 `Alt+A`(ASCII string), `D`(데이터로 변환 반복), `U`(Undefine)
- Ghidra: **Window → Bytes**, Bytes 패널에서도 Listing과 동일하게 `G`로 이동 가능, 데이터 재정의는 Listing에서 우클릭 → **Data → ...**
- 공통: 더블클릭으로 참조 주소 따라가기(REV-0160 XREF 개념과 함께 사용)

## 출력 해석
- Hex View의 오른쪽 ASCII 컬럼에 읽을 수 있는 문자가 연속으로 보이면 그 구간이 문자열일 가능성이 매우 높다. 프린트 불가능한 바이트(`.`으로 표시)가 섞여 있다면 문자열이 아니라 코드나 이진 데이터, 혹은 유니코드일 수 있다.
- 같은 패턴(예: 4바이트 단위)이 여러 번 반복되는 것이 보이면 배열이나 구조체 배열일 가능성이 크다.
- 값이 오름차순/규칙적인 증가 패턴을 보이면 룩업 테이블이나 점프 테이블일 수 있다.

## 흔한 실수
- 디컴파일 결과의 상수 표시를 그대로 믿고 Hex View 대조를 생략하는 것 — 특히 CTF 문제 풀이에서 정답 문자열이나 XOR 키처럼 정확도가 생명인 값은 반드시 원본 바이트로 재확인해야 한다.
- 엔디안을 고려하지 않고 Hex View에 보이는 바이트 순서를 그대로 정수로 읽는 것 — x86/x64는 리틀 엔디안이므로 바이트 나열 순서를 뒤집어야 실제 정수 값이 된다.
- 유니코드 문자열을 ASCII로 착각해서 절반만 읽고 "이상한 문자열"이라고 결론짓는 것 — `00`이 한 바이트씩 끼어 있는 패턴을 놓치지 않아야 한다.
- Hex View에서 값을 확인만 하고, 디스어셈블러/디컴파일러 쪽 데이터 타입을 고쳐주지 않아서 다음에 다시 볼 때 또 헷갈리는 것 — 확인했으면 REV-0161처럼 이름/타입을 정리해 두는 것이 좋다.

## 막혔을 때 다음 체크
- Hex View에서 본 값을 어떻게 이름 붙이고 정리할지 모르겠다면 → REV-0161(Ghidra Rename과 Data Type 수정).
- 이 데이터를 누가 참조하는지 더 넓게 보고 싶다면 → REV-0160(Ghidra XREF 따라가기).
- 이 상수/바이트 배열이 특정 알고리즘(체크섬, 암호화 등)의 일부인지 판단하고 싶다면 → REV-0165(상수 검색으로 알고리즘 찾기).
- 확인한 값을 실제로 파이썬으로 재현해서 풀이를 만들고 싶다면 → REV-0168(정적 분석 결과를 Python 의사코드로 옮기기).

## 미니 예제
Decompile 창에 다음과 같은 코드가 있다고 하자.

```c
int check(char *input) {
  int i;
  for (i = 0; i < 5; i = i + 1) {
    if ((input[i] ^ DAT_00403020[i]) != *(char *)(DAT_00403030 + i)) {
      return 0;
    }
  }
  return 1;
}
```

`DAT_00403020`(XOR 키로 추정)과 `DAT_00403030`(비교 대상 배열)이 실제로 무슨 바이트인지 디컴파일 창만으로는 알 수 없다. 이때:

1. `DAT_00403020`을 더블클릭 → Hex View(IDA)/Bytes(Ghidra)에서 해당 주소를 보니 `11 22 33 44 55`가 5바이트 연속으로 있는 것을 확인.
2. `DAT_00403030`도 같은 방법으로 확인하니 `5a 4b 5c 4d 5a` 5바이트가 있는 것을 확인.
3. 이제 두 배열의 실제 바이트 값을 알았으므로, REV-0168 방식으로 파이썬으로 `input[i] = key[i] ^ target[i]`를 계산해 정답 문자열 5바이트를 즉시 복원할 수 있다.

이 예제처럼, Hex View로 원본 바이트를 확인하는 순간부터 "가설"이 "확정된 사실"로 바뀌고, 그다음은 순수한 계산 문제가 된다.

## 출처/검증
- IDA Hex View-1 서브뷰와 디스어셈블리/디컴파일러 뷰 간 주소 동기화: Hex-Rays 공식 문서(IDA User Guide, View 구성 관련 topic) 기준.
- Ghidra Bytes 뷰(Window → Bytes)와 Listing 동기화: Ghidra 공식 Help 문서 기준.
- 리틀 엔디안 바이트 순서와 UTF-16LE 유니코드 문자열의 `00` 인터리브 패턴은 x86/x64 아키텍처 및 Windows 유니코드 문자열의 일반적 특성으로, 도구 문서가 아닌 아키텍처/인코딩 표준 자체에 근거한다.
- 이 문서는 라이브 IDA/Ghidra 화면을 직접 캡처해 재검증하지는 않았으며, 공식 문서와 널리 통용되는 UI 동작을 기준으로 작성되었다.
