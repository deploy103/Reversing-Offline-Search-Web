## 한 줄 요약
`.bss`/`.data`에 있는 전역 변수 하나를 기준으로 Data Xref(데이터 교차 참조)를 모두 나열하면, 그 변수를 읽기만 하는 곳과 값을 실제로 바꾸는(쓰기) 곳을 구분할 수 있어, 코드 전체를 순서대로 읽지 않고도 "이 상태값이 프로그램 전체에서 어떻게 변화하는지"를 지도처럼 재구성할 수 있다.

## 언제 검색해야 하나
- 디컴파일 결과에 `g_flag`, `dword_403000`처럼 이름 없는 전역 변수가 여러 함수에서 반복적으로 등장해, 어느 함수가 이 값을 실제로 바꾸는지 헷갈릴 때
- 게임/퍼즐형 CTF 문제에서 "현재 상태"나 "점수", "시도 횟수"를 담는 전역 변수를 찾았고, 이 값이 어디서 초기화되고 어디서 조건 검사에 쓰이는지 전체 그림이 필요할 때
- 전역 배열(룩업 테이블, 버퍼)의 각 인덱스가 어느 함수에서 채워지고 어느 함수에서 읽히는지 구분해야 할 때

## 핵심 개념
Data Xref는 REV-0757에서 다룬 Cross Reference Graph의 한 축으로, **특정 데이터 주소를 참조하는 코드 위치 전체**를 가리킨다. IDA/Ghidra는 참조를 단순히 "참조한다"고만 표시하지 않고, 명령어 종류에 따라 **읽기(read)**와 **쓰기(write)**를 구분해서 보여주는 경우가 많다.

- **쓰기 참조**: `mov [g_var], eax`처럼 이 주소에 값을 저장하는 명령어. 이 위치가 "누가 이 상태를 바꾸는가"에 대한 답이다.
- **읽기 참조**: `mov eax, [g_var]`, `cmp [g_var], 0`처럼 이 주소의 값을 가져오기만 하는 명령어. "누가 이 상태를 검사/사용하는가"에 대한 답이다.

이 구분이 중요한 이유는, 같은 xref 목록이라도 역할이 완전히 다르기 때문이다. 예를 들어 전역 변수 `g_attempts`(시도 횟수)에 대해:
- `main`에서 `g_attempts = 0`(쓰기, 초기화)
- `check_password` 실패 시 `g_attempts++`(읽기+쓰기, 갱신)
- `check_password` 시작 시 `if (g_attempts >= 3) exit()`(읽기, 조건 검사)

이 세 위치를 데이터 xref로 한 번에 나열하면, "시도 횟수 제한 로직이 정확히 어디서 초기화되고, 어디서 증가하고, 어디서 검사되는지"가 코드를 순서대로 읽지 않고도 정리된다.

**IDA에서 확인**: 전역 변수 심볼(또는 `.bss`/`.data` 상의 주소) 위에서 `X`를 눌러 Xrefs 목록을 연다. 목록의 각 항목 앞에 보통 `r`(read) 또는 `w`(write) 표시가 붙어 구분된다. View → Graphs → Xrefs to로 그래프 형태로도 볼 수 있다.

**Ghidra에서 확인**: 데이터 심볼 위에서 우클릭 → **Show References to**를 선택하면 참조 목록 창이 뜨고, 각 항목에 Read/Write 접근 종류가 표시된다. Listing 창에서도 해당 변수가 쓰이는 줄 옆에 이 정보가 함께 표시되는 경우가 많다.

**radare2에서 확인**: 데이터 주소로 `s`(seek) 이동 후 `axt`(REV-0751)로 참조 목록을 얻는다. radare2의 `axt` 결과는 참조 종류(코드 호출/데이터 접근)를 함께 표시하지만, read/write 세분화는 버전에 따라 표시 수준이 다를 수 있어 애매하면 해당 위치의 명령어(`mov [addr], reg` vs `mov reg, [addr]`)를 직접 눈으로 구분해야 한다.

## 화면/코드에서 보이는 징후
- 여러 함수의 디컴파일 결과에 같은 전역 변수 이름(또는 `dword_XXXXXX`)이 반복적으로 등장한다.
- 어떤 함수가 이 변수의 값을 실제로 바꾸는지, 아니면 그냥 읽어서 조건 검사만 하는지 코드를 여러 번 오가며 확인해야 해서 시간이 걸린다.
- 전역 배열의 특정 인덱스가 여러 곳에서 참조되는데, 초기화가 어디서 되는지 찾기 어렵다.

## 가장 먼저 할 것
전역 변수 심볼(또는 주소) 위에서 커서를 두고 IDA는 `X`, Ghidra는 우클릭 → Show References to, radare2는 `axt`를 실행해 전체 참조 목록부터 확보한다.

## 단계별 절차
1. 관심 있는 전역 변수의 주소/심볼을 확인한다(디컴파일 결과에서 변수명 클릭, 또는 Symbol Tree/Data 섹션에서 확인).
2. IDA `X` / Ghidra Show References to / radare2 `axt`로 전체 참조 목록을 뽑는다.
3. 각 참조 위치로 하나씩 이동해(더블클릭 또는 주소 복사 후 `s`) 실제 명령어가 읽기인지 쓰기인지 확인한다. 도구가 read/write를 자동 표시해주면 그대로 신뢰하되, 애매하면 명령어 형태(`mov [addr], X`가 쓰기, `mov X, [addr]`가 읽기)로 직접 재확인한다.
4. 쓰기 참조 위치들을 모아 "이 변수가 어떤 조건에서 어떤 값으로 바뀌는지" 표로 정리한다.
5. 읽기 참조 위치들을 모아 "이 값이 어떤 조건문/분기에 쓰이는지" 표로 정리한다.
6. 두 표를 합치면, 초기화 → 갱신 → 검사로 이어지는 이 변수의 전체 생애주기(lifecycle)가 완성된다.
7. 이 흐름이 문제 풀이에 중요한 상태 머신이라면 REV-0168 방식으로 파이썬으로 그대로 재현한다.

## 명령어/단축키
- IDA: 변수 위에서 `X`(Xrefs 목록, 앞에 r/w 표시), View → Graphs → Xrefs to
- Ghidra: 우클릭 → Show References to, Listing 창의 인라인 참조 표시
- radare2: 주소로 `s` 이동 후 `axt`, 필요시 `pdf`로 해당 위치 문맥 확인

## 출력 해석
- 쓰기 참조가 딱 한 곳뿐이라면 그 변수는 한 번만 설정되는(초기화 전용) 값일 가능성이 크다.
- 쓰기 참조가 여러 곳에 흩어져 있다면 여러 함수가 공유하는 가변 상태(mutable state)이며, 각 쓰기 위치의 조건을 모두 정리해야 값의 변화 규칙을 완전히 파악할 수 있다.
- 읽기 참조만 있고 쓰기 참조가 하나도 없다면, 그 변수는 프로그램 시작 전에 이미 값이 고정된 상수 데이터(룩업 테이블 등)일 가능성이 높다 — 이 경우 REV-0165/REV-0756의 상수 식별 전략으로 넘어가는 것이 더 적합할 수 있다.

## 흔한 실수
- 참조 목록에서 read/write 표시를 확인하지 않고 모든 참조를 "이 값을 바꾸는 곳"으로 오해하는 것 — 읽기와 쓰기를 반드시 구분해야 값의 변화 흐름을 제대로 재구성할 수 있다.
- 배열/구조체의 특정 필드만 참조를 확인하고, 같은 배열의 다른 인덱스나 다른 필드에 대한 참조는 놓치는 것 — 전역 배열 전체를 다룰 때는 인덱스별로 참조를 나눠 정리해야 한다.
- 참조가 많다고 그 변수를 즉시 핵심 로직으로 단정하는 것 — 로깅 카운터처럼 참조가 많아도 실제 문제 풀이와 무관한 변수일 수 있다(REV-0166/REV-0757의 흔한 실수와 동일한 함정).
- 정적 분석 결과만 믿고 실제 실행 중 값 변화를 확인하지 않는 것 — 애매하면 GDB/x64dbg로 그 주소에 watchpoint(`watch` 명령 등)를 걸어 실제로 언제 값이 바뀌는지 동적으로 확인하는 것이 가장 확실하다.

## 막혔을 때 다음 체크
- 코드+데이터 참조를 함께 보는 더 큰 그림이 필요하면 → REV-0757 Cross Reference Graph로 핵심 함수 찾기
- radare2 커맨드라인에서 같은 작업을 하고 싶다면 → REV-0751 radare2로 함수 목록과 XREF 확인하기(afl, axt)
- 참조된 데이터가 표준 알고리즘의 상수/테이블인지 의심되면 → REV-0165 상수 검색으로 알고리즘 찾기, REV-0756 문자열 상수 하나로 알고리즘 전체를 추정하는 실전 사례
- 정리한 흐름을 파이썬으로 재현하고 싶다면 → REV-0168 정적 분석 결과를 Python 의사코드로 옮기기

## 미니 예제
IDA에서 `dword_404050`이라는 전역 변수 위에서 `X`를 눌렀더니 다음 세 참조가 나왔다.
```
w  init      0x401120   mov [dword_404050], 0
w  check_pw  0x4011a5   inc dword_404050
r  check_pw  0x401190   cmp dword_404050, 3
```
`w`(쓰기) 표시가 붙은 두 곳(`init`에서 0으로 초기화, `check_pw`에서 증가)과 `r`(읽기) 표시가 붙은 한 곳(`check_pw`에서 3과 비교)을 정리하면, 이 변수는 "시도 횟수"이며 3번째 시도부터 어떤 분기로 빠지는 구조라는 것을 코드를 순서대로 읽지 않고도 xref 목록 세 줄만으로 파악할 수 있다.

## 관련 글

- REV-0165 — 상수 검색으로 알고리즘 찾기
- REV-0756 — 문자열 상수 하나로 알고리즘 전체를 추정하는 실전 사례

## 출처/검증
- 데이터 참조를 읽기/쓰기로 구분해 표시하는 기능: IDA 공식 문서(Cross-references, Xrefs 관련 topic) 및 Ghidra 공식 문서(Show References, Read/Write access kind) 기준.
- radare2 `axt`의 참조 표시 방식: radare2 공식 문서 "The Radare2 Book"의 xref 관련 chapter 기준.
- 이 문서는 실기 화면을 캡처해 재검증하지 않았으며, 버전에 따라 read/write 표시 방식(기호, 색상)이 다를 수 있다(2026-09-09 검증).
