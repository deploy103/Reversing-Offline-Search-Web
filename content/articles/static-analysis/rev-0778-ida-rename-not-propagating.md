## 한 줄 요약
`N`으로 이름을 바꿨는데 "다른 곳"에 반영이 안 된 것처럼 보인다면, 대부분은 IDA가 고장난 게 아니라 **바꾼 대상이 애초에 그 함수 안에서만 유효한 지역 변수/인자였거나(전역이 아님), 같은 이름이 이미 다른 곳에 존재해서 자동으로 `_0` 같은 접미사가 붙었거나, 같은 데이터베이스를 두 개의 IDA 창으로 동시에 열어놓고 헷갈리는 경우**이므로 대상의 유효 범위(scope)부터 확인해야 한다.

## 언제 검색해야 하나
- 함수 이름을 `N`으로 바꿨는데 다른 함수의 Pseudocode 안에서 그 함수를 호출하는 부분은 여전히 `sub_401000`으로 보일 때
- 지역 변수 이름을 바꿨는데 비슷한 로직을 가진 "다른 함수"의 같은 이름 변수(예: `var_4`)에는 반영이 안 될 때
- 원하는 이름을 입력했는데 저장된 이름 뒤에 `_0`, `_1` 같은 숫자가 자동으로 붙어 있을 때
- 같은 바이너리를 두 개의 IDA 창(또는 IDA와 별도로 열어둔 스냅샷)으로 열어두고 작업해서 어느 쪽에 반영됐는지 헷갈릴 때

## 핵심 개념
IDA에서 이름에는 크게 두 가지 유효 범위(scope)가 있다는 것을 알아야 이 문제를 이해할 수 있다.

- **전역(global) 이름**: 함수 이름, 전역 변수 이름, 문자열 라벨처럼 프로그램 전체에서 고유해야 하는 이름이다. 이런 이름을 바꾸면 데이터베이스 전체에서 그 주소를 참조하는 모든 곳(다른 함수의 디스어셈블리, Pseudocode의 호출부, Functions 창, Xrefs 목록)에 즉시 반영된다. 함수 이름을 바꿨는데 다른 곳에 반영이 안 됐다면, 대부분은 실제로는 바뀌었는데 그 화면을 아직 새로고침하지 않았거나(창을 닫았다 다시 열면 해결), 아예 다른 함수를 바꾼 것을 착각한 경우다.
- **지역(local) 이름**: 스택 변수(`var_4`, `arg_0`)나 Pseudocode 안의 지역 변수 이름은 **그 함수 하나에만 속하는 이름**이다. IDA는 기본적으로 스택 오프셋에 따라 `var_4`, `var_8`, `arg_0` 같은 이름을 자동으로 붙이는데, 이건 "이 함수 안에서 스택 프레임 어디에 있는가"를 나타내는 이름일 뿐 프로그램 전체에서 같은 의미를 갖는 게 아니다. 따라서 함수 A의 `var_4`를 `password_len`으로 바꿔도, 완전히 다른 함수 B에 있는 `var_4`는 전혀 다른 변수이므로 당연히 안 바뀐다 — 이건 버그가 아니라 애초에 서로 무관한 변수이기 때문이다.
- **이름 충돌과 자동 접미사**: 전역 이름은 프로그램 전체에서 고유해야 하므로, 이미 존재하는 이름을 다시 입력하면 IDA가 충돌을 피하기 위해 자동으로 `_0`, `_1` 같은 숫자를 뒤에 붙여 저장한다. 사용자가 입력한 이름 그대로 안 보이는 것을 "반영이 안 됐다"고 착각하기 쉽지만, 실제로는 저장은 됐고 다만 다른 이름으로 바뀐 것뿐이다.
- **같은 데이터베이스를 여러 창으로 열어둠**: IDA 데이터베이스(.idb/.i64) 파일을 실수로 두 개의 IDA 인스턴스에서 동시에 열어놓고 한쪽에서만 이름을 바꾸면, 당연히 다른 창에는 반영되지 않는다(파일 잠금 문제로 애초에 두 번째 인스턴스가 읽기 전용으로 열렸을 수도 있다). 또한 백업/스냅샷 파일을 열어놓고 원본은 그대로인 경우도 흔한 혼동 원인이다.

## 화면/코드에서 보이는 징후
- 함수 이름을 바꿨는데 Functions 창(Ctrl+P)에는 새 이름이 보이지만, 이미 열려 있던 다른 Pseudocode 탭은 예전 이름 그대로 표시됨(탭을 갱신 안 해서 그런 것일 수 있음).
- 지역 변수 이름을 바꾼 함수와 "비슷해 보이는" 다른 함수를 열어보면 여전히 `var_4`, `a1` 등 기본 이름 그대로임.
- Rename 대화상자에 원하는 이름을 입력했는데, 확인 후 창에는 `password_len_0`처럼 숫자가 붙어서 표시됨.
- 작업 표시줄이나 Alt+Tab 목록에 같은 파일명을 가진 IDA 창이 두 개 이상 떠 있음.

## 가장 먼저 할 것
바꾼 이름이 함수/전역 데이터의 이름인지, 아니면 특정 함수 안의 스택 변수/지역 변수 이름인지부터 구분한다. 후자라면 "다른 함수에 반영 안 되는 것"이 정상 동작이다.

## 단계별 절차
1. 반영이 안 됐다고 느끼는 두 위치가 정말 같은 주소/같은 변수를 가리키는지 확인한다. 함수라면 두 곳 모두 `Ctrl+P`(Functions 창)에서 검색해 실제로 같은 주소인지 대조한다.
2. 지역 변수(스택 변수) 이름이 다른 함수에 안 보이는 것이라면, 애초에 그 변수는 함수마다 독립적이라는 것을 이해하고, 각 함수에서 따로 이름을 붙여줘야 한다는 것을 받아들인다. 여러 함수에 걸쳐 같은 개념의 변수가 반복해서 나온다면, 함수마다 하나씩 직접 이름을 바꿔주는 수밖에 없다(자동 일괄 반영 기능은 없다).
3. 입력한 이름 뒤에 숫자가 자동으로 붙었다면, 그 이름이 이미 데이터베이스 어딘가(다른 함수, 전역 변수, 심지어 라이브러리 심볼)에 존재한다는 뜻이다. `Ctrl+P`나 `Alt+T`(텍스트 검색)로 그 이름을 검색해 원래 어디서 쓰이고 있었는지 확인하고, 필요하면 기존 것의 이름을 먼저 바꾸거나 새 이름에 구분되는 접두사(`chk_password_len`처럼)를 붙인다.
4. 여러 창/인스턴스를 헷갈리고 있는지 확인하려면, 운영체제의 창 목록(Alt+Tab, 작업 표시줄)에서 같은 데이터베이스 파일을 대상으로 하는 IDA 창이 몇 개인지 센다. 두 개 이상이라면 하나를 닫고 하나만 남겨서 작업한다.
5. 이름이 안 바뀐 게 아니라 "화면 갱신"이 안 된 것일 수도 있으므로, 의심되는 탭을 닫았다가 다시 열거나(`Ctrl+W` 후 재이동), 함수 위에서 `Esc`/다시 이동을 반복해 화면을 갱신해본다.
6. 여러 모듈/여러 개의 로컬 타입 라이브러리를 import한 상태에서 구조체 필드 이름을 바꾼 경우, 그 구조체가 실제로 다른 함수에서도 **같은 타입으로 지정**되어 있어야 필드 이름 변경이 그 함수의 Pseudocode에도 반영된다. 다른 함수의 변수가 아직 그 구조체 타입으로 지정되지 않았다면(단순 `int`나 미지정 상태라면), 구조체 필드 이름을 바꿔도 그 함수에는 당연히 안 보인다 — REV-0148의 타입 지정을 먼저 해야 한다.

## 명령어/단축키
- `N` : 이름 바꾸기(함수/변수/데이터 공통)
- `Ctrl+P` : Functions 창에서 실제 주소 대조
- `Alt+T` : 텍스트 검색(이름 충돌 여부 확인)
- `Ctrl+W` : 탭 닫기(화면 갱신 유도)
- `Y` : 타입 지정(구조체 필드 이름이 반영되려면 먼저 타입이 맞아야 함, REV-0148 참고)

## 출력 해석
- 이름 뒤에 자동으로 붙은 `_0`, `_1` 숫자는 "이 이름이 이미 다른 곳에서 쓰이고 있다"는 IDA의 충돌 방지 신호이지, 입력이 실패했다는 뜻이 아니다.
- 함수 이름이 Functions 창에는 바뀌어 보이는데 특정 탭에서만 예전 이름이면, 그 탭은 단순히 새로고침이 안 된 화면일 뿐 실제 데이터베이스에는 이미 반영되어 있다.
- 지역 변수 이름이 함수마다 따로 도는 것은 정상 동작이며, 이는 프로그램 전체 관점의 "네이밍 규칙 통일"이 필요할 뿐 오류가 아니다.

## 흔한 실수
- 스택 변수(`var_4`, `arg_0`) 이름이 함수마다 독립적이라는 사실을 모르고, 한 함수에서 바꾼 이름이 다른 함수에도 자동으로 퍼질 거라 기대하는 것.
- 이름 뒤에 숫자가 붙은 것을 "저장이 안 됐다"고 오해해서 같은 이름을 계속 다시 입력하며 시간을 낭비하는 것.
- 같은 데이터베이스 파일을 실수로 두 번 열어놓고 서로 다른 창에서 작업하다가 어느 쪽이 최신인지 헷갈리는 것.
- 구조체 필드 이름을 바꿨는데 다른 함수의 변수가 아직 그 구조체 타입으로 지정되지 않은 상태라서 "반영이 안 됐다"고 오해하는 것 — 타입 지정이 먼저다.

## 막혔을 때 다음 체크
- 이름 바꾸기 기본 사용법이 헷갈린다면 → REV-0147 IDA 함수 변수 이름 N으로 바꾸기
- 구조체/타입을 먼저 지정해야 하는 상황이라면 → REV-0148 IDA Y로 타입 지정하기
- 타입을 지정했더니 오히려 이상해졌다면 → REV-0780 IDA에서 타입 지정 후 디컴파일이 더 이상해질 때
- 데이터베이스 자체가 깨진 것 같다면 → REV-0779 IDA 데이터베이스(idb/i64)가 손상되어 안 열릴 때

## 미니 예제
`check_pw1`과 `check_pw2` 두 함수에서 각각 스택 변수 `var_4`를 `input_len`으로 바꿨는데, `check_pw2` 쪽 결과가 이상하다고 느낀 상황.

```text
1. check_pw1의 var_4를 input_len으로 변경 → 정상적으로 그 함수 안에서만 input_len으로 표시됨
2. check_pw2에도 같은 이름을 붙이려고 var_4 위에서 N → input_len 입력
3. 별문제 없이 각각 독립적으로 저장됨(원래 다른 변수이므로 이름 충돌 없음)
4. 착각의 원인은 두 함수의 var_4가 "같은 변수"라고 생각했던 것 — 실제로는 완전히 별개의 스택 위치였음을 오프셋(예: ebp-4 여부)을 다시 확인해 깨달음
```

## 관련 글
- REV-0147 — IDA 함수 변수 이름 N으로 바꾸기
- REV-0148 — IDA Y로 타입 지정하기
- REV-0780 — IDA에서 타입 지정 후 디컴파일이 더 이상해질 때
- REV-0779 — IDA 데이터베이스(idb/i64)가 손상되어 안 열릴 때

## 출처/검증
- 전역 이름과 지역(스택) 이름의 유효 범위 차이, 이름 충돌 시 자동 접미사 부여 동작: Hex-Rays 공식 사용자 가이드 "Renaming" 및 "Local variables" 섹션 기준.
- 동일 데이터베이스 파일을 여러 인스턴스에서 여는 경우의 파일 잠금/독립 세션 동작은 일반적으로 알려진 IDA 사용 관행에 기반한다.
