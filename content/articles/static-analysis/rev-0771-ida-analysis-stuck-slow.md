## 한 줄 요약
IDA 창 제목이나 상태 표시줄에 `please wait...`이 계속 떠 있고 진행률(progress bar)이 몇 분째 움직이지 않는다면, 대부분은 IDA가 "멈춘" 것이 아니라 **큰 바이너리의 auto-analysis(자동 분석)를 아직 백그라운드에서 계산 중**인 것이며, CPU 사용량이 실제로 높은지부터 확인해서 진짜 무한정지인지 정상적으로 느린 것인지 구분해야 한다.

## 언제 검색해야 하나
- 바이너리를 열었는데 IDA 창 제목이 계속 `IDA - please wait...` 상태로 몇 분 이상 유지될 때
- 큰 파일(수십~수백 MB, 특히 정적 링킹 바이너리)을 열었더니 화면이 하얗거나 회색인 채로 아무것도 안 뜰 때
- 이미 분석이 끝난 파일인데도 특정 조작(예: 대량 rename, 큰 구조체 적용) 후 IDA가 다시 몇 분씩 멈출 때
- 작업 관리자/`top`에서 IDA 프로세스가 CPU를 많이 먹는지 아닌지 구분해서 진짜 문제인지 판단하고 싶을 때

## 핵심 개념
IDA는 파일을 열면 곧바로 **auto-analysis**를 시작한다. 이 단계에서 IDA는 코드/데이터 경계를 추정하고, 함수를 인식하고, 각 명령어의 오퍼랜드를 해석하고, 문자열과 이름을 자동으로 붙이는 등 수많은 작업을 순차적으로 처리한다. 이 과정은 원래도 CPU를 많이 쓰는 작업이고, 다음과 같은 조건에서는 정상적으로도 몇 분에서 몇 십 분까지 걸릴 수 있다.

- 파일 크기가 크다(정적 링킹된 C++ 바이너리, 여러 서드파티 라이브러리가 통짜로 들어간 실행 파일 등).
- 함수 개수가 매우 많다(수만 개 단위) — IDA는 각 함수마다 스택 프레임, 타입, xref를 계산하므로 함수 수에 거의 비례해 시간이 늘어난다.
- `FLIRT` 시그니처 매칭(라이브러리 함수 자동 인식) 대상 라이브러리 목록이 많거나, 안티바이러스 실시간 검사 소프트웨어가 IDA의 임시 파일 접근을 매번 검사하며 I/O를 지연시키는 경우.
- 디스크가 네트워크 드라이브거나 외장 SSD인데 접근 지연이 큰 경우.

반대로 진짜 "멈춤"(hang)인 경우도 있다. 특정 난독화/패킹된 바이너리는 정상적인 코드처럼 보이지만 실제로는 함수 경계가 끝없이 겹치거나 재귀적으로 잘못된 코드 흐름을 만들어내서, auto-analysis 알고리즘이 사실상 끝나지 않는 루프에 가깝게 오래 걸리는 경우가 있다. 이때는 "느린 것"과 "멈춘 것"을 구분하는 게 핵심이고, 가장 확실한 구분법은 운영체제의 프로세스 관리자를 열어 IDA(정확히는 `ida64.exe`/`ida.exe` 또는 백그라운드 분석 스레드)가 실제로 CPU를 계속 소비하고 있는지 보는 것이다. CPU 사용률이 꾸준히 높다면 계산은 계속 진행 중이라는 뜻이고, CPU가 0%에 가깝게 떨어져 있는데도 창이 안 바뀐다면 진짜로 멈췄거나 다른 이유(예: 모달 대화상자가 화면 뒤에 숨어 있음)로 대기 중일 가능성이 높다.

## 화면/코드에서 보이는 징후
- IDA 창 제목 표시줄에 `please wait...` 또는 하단 상태 바에 `Analysing... (xx%)` 같은 진행률이 표시됨.
- 화면 중앙 또는 하단에 진행률 바(progress indicator)가 보이지만 오랫동안 퍼센트가 그대로임.
- Output window(메시지 로그)에 마지막 줄이 오래전에 멈춘 것처럼 보이고 새 줄이 추가되지 않음.
- 마우스로 IDA 창을 클릭해도 반응이 없고(Windows에서는 창 제목에 "(응답 없음)"이 붙기도 함), 메뉴가 열리지 않음.

## 가장 먼저 할 것
운영체제의 작업 관리자(Windows: Ctrl+Shift+Esc) 또는 `top`/`htop`(Linux)을 열어서 IDA 프로세스의 CPU 사용률을 확인한다. CPU를 계속 쓰고 있다면 그냥 기다리는 것이 정답이고, 섣불리 강제 종료하면 몇 분~몇 십 분 걸린 분석 결과를 통째로 날리게 된다.

## 단계별 절차
1. 작업 관리자/`top`에서 IDA 프로세스의 CPU 사용률을 확인한다. 지속적으로 몇 %라도 CPU를 쓰고 있다면 계산이 진행 중이므로 최소 몇 분 더 기다린다.
2. Output window(로그 창)를 확인한다. 창이 완전히 멈춘 것처럼 보여도, 그 아래 로그 창에는 `.....` 형태의 진행 점(dot)이 계속 찍히고 있을 수 있다 — 이는 auto-analysis가 살아있다는 증거다.
3. 화면 뒤에 숨은 모달 대화상자가 없는지 확인한다. 드물게 "Choose the file to load" 같은 선택창이나 예외 경고창이 다른 창 뒤에 가려져 있어서, 사용자가 답을 안 해서 멈춘 것처럼 보이는 경우가 있다. Alt+Tab(Windows) 또는 창 목록으로 다른 숨은 창이 있는지 확인한다.
4. 정말 오래 걸릴 것 같은 큰 파일이라면, 다음번부터는 파일을 열 때 뜨는 "Load a new file" 대화상자에서 **자동 분석 옵션을 조정**한다. 특히 옵션 창의 "Kernel options" / "Analysis options" 탭에서 `Create Function`, `Trace execution flow`처럼 무거운 옵션을 잠시 끄고, `Options → General → Analysis` 메뉴에서 `Reschedule background function analysis` 등을 조정해 필요한 부분부터 우선 분석하게 할 수 있다.
5. CPU 사용률이 0%에 가깝고 몇 분 동안도 전혀 변화가 없다면, 백업 없이 강제 종료하지 말고 먼저 **File → Produce file → Create IDC/Python script**나 스냅샷 저장이 가능한 상태인지(메뉴 반응 여부) 확인한다. 메뉴 자체가 전혀 안 열린다면 진짜 hang이므로, 마지막 수단으로 프로세스를 종료하고 다음에 열 때는 자동 분석을 잠시 끈 상태(`Options → General`에서 "Enable auto analysis" 체크 해제)로 파일을 로드한 뒤, 필요한 함수만 수동으로 `P`(Create function)로 분석 범위를 좁혀 나간다.
6. 같은 파일이 매번 오래 걸린다면, 다음 로드부터 무거운 원인을 미리 줄인다: 안티바이러스 실시간 검사 예외 목록에 IDA 작업 폴더 추가, 파일을 로컬 SSD로 복사한 뒤 열기, 불필요한 FLIRT 시그니처 로딩 생략.

## 명령어/단축키
- `Options → General → Analysis` : 자동 분석 관련 옵션(느린 옵션 끄기/켜기)
- 파일 로드 시 `Kernel options 1/2/3`, `Analysis options 1/2` 탭 : 무거운 개별 분석 항목 on/off
- Output window 스크롤 : 진행 중인 로그(점, 함수 이름) 실시간 확인
- 작업 관리자(Windows) `Ctrl+Shift+Esc` / `top`, `htop`(Linux) : 프로세스 CPU 사용률 확인

## 출력 해석
- Output window에 `....` 같은 점이 계속 이어서 찍힌다면 이는 IDA가 "아직 분석할 함수/블록이 남아 있다"는 뜻으로, 정상적으로 진행 중인 신호다.
- 진행률(progress bar)이 100%에 딱 붙어서 안 움직이는 경우, 마지막 단계(예: FLIRT 시그니처 최종 매칭이나 타입 정보 정리)가 유난히 오래 걸리는 경우가 많으므로 CPU 사용률만 살아있다면 계속 기다리는 것이 맞다.
- CPU 사용률이 0%로 완전히 떨어졌는데 창도 안 바뀌면, 대기 중인 다이얼로그나 데드락에 가까운 상태로 봐야 한다.

## 흔한 실수
- 진행률이 잠깐 멈춰 보인다고 바로 프로세스를 강제 종료하는 것 — 실제로는 계산 중인데 화면 갱신만 늦는 경우가 많고, 강제 종료하면 지금까지의 분석 결과(수십 분 걸린 것일 수도 있음)가 저장 안 된 상태로 사라진다.
- 대용량 파일을 열 때마다 기본 옵션 그대로 전체 분석을 돌려서 매번 오래 기다리는 것 — 실제로 봐야 할 함수가 몇 개 안 된다면 자동 분석을 최소화하고 수동으로 필요한 함수만 분석하는 편이 훨씬 빠르다.
- 네트워크 드라이브나 외장 HDD에서 파일을 직접 열어서 I/O 지연이 auto-analysis 지연으로 오인되는 것 — 로컬 SSD로 복사 후 여는 습관을 들이지 않는 것.
- 안티바이러스가 IDA의 임시 데이터베이스 파일(.id0, .id1 등)에 매번 실시간 검사를 걸어 느려지는 것을 모른 채 "IDA 자체가 느리다"고만 생각하는 것.

## 막혔을 때 다음 체크

- IDA 데이터베이스 파일 자체가 손상되어 다시 열리지 않는다면 → REV-0779
- 정적 링킹된 큰 바이너리라서 느린 것이라면 라이브러리 함수 인식 관련 → REV-0646 정적 링킹된(Statically Linked) ELF 분석 접근법
- Ghidra의 Auto Analysis 옵션과 비교해서 느린 이유를 판단하고 싶다면 → REV-0157 Ghidra Auto Analysis 옵션

## 미니 예제
정적 링킹된 300MB짜리 x64 ELF 바이너리를 IDA로 열었더니 창 제목에 `please wait...`이 뜨고 15분째 진행률이 92%에서 안 움직이는 상황을 가정하자.

```text
1. 작업 관리자(또는 top)에서 ida64 프로세스 확인 → CPU 20~40% 지속 사용 중 확인
2. Output window를 보니 "..........." 점이 계속 늘어나는 중 → 아직 계산 중이라는 뜻
3. FLIRT 시그니처 매칭 단계(라이브러리 함수 수천 개 대조)라서 오래 걸리는 것으로 판단
4. 강제 종료하지 않고 5분 더 대기 → 100%로 완료되고 정상적으로 화면 전환됨
```
CPU가 죽어있지 않다면 기다리는 것이 대부분 정답이며, 다음번엔 로드 전 FLIRT 옵션을 줄여서 시간을 아낄 수 있다.

## 출처/검증
- IDA auto-analysis 단계(코드/데이터 경계 추정, FLIRT 시그니처 매칭, 함수 재구성)의 일반적인 동작 방식: Hex-Rays 공식 사용자 가이드("Auto analysis") 기준.
- 분석 옵션(Kernel options, Analysis options) 위치와 역할: Hex-Rays 공식 문서의 "Load a new file" 대화상자 설명 기준.
- 정확한 메뉴 문구와 옵션 이름은 IDA 버전에 따라 달라질 수 있어, 실제 설치된 버전에서 재확인을 권장한다.
