## 한 줄 요약
IDA는 대부분의 함수 원형을 표준 호출 규약(`__cdecl`, `__stdcall`, `__fastcall` 등)을 기준으로 자동 추론하지만, 최적화된 코드나 손으로 짠 어셈블리처럼 인자가 비표준 레지스터·순서로 전달되는 경우에는 `__usercall`과 `@<레지스터명>` 표기를 이용한 **수동 프로토타입 편집**이 필요하며, 간접 호출(레지스터/메모리를 통한 CALL)의 원형은 별도의 "Set call type" 절차로 지정해야 한다.

## 언제 검색해야 하나
- REV-0148(Y로 타입 지정하기)에서 표준 호출 규약으로 함수 원형을 고쳤는데도 호출부의 인자 표시가 여전히 이상할 때
- 최적화 옵션(`-O2` 이상)으로 컴파일된 함수라서 인자가 예상 밖의 레지스터(예: x86-64에서 표준 SysV 순서를 따르지 않는 내부 헬퍼 함수)로 전달되는 것 같을 때
- `call eax`, `call [ebp-8]`처럼 레지스터/메모리를 통한 간접 호출인데, 그 호출의 인자/반환값이 Pseudocode에서 전혀 안 보이거나 잘못 보일 때
- 가변 인자 함수(`printf` 계열처럼 인자 개수가 호출마다 다른 함수)를 직접 만든 헬퍼 함수에 적용하고 싶을 때

## 핵심 개념

### 표준 호출 규약으로 충분한 경우
대부분의 x86/x64 함수는 `__cdecl`, `__stdcall`, `__fastcall`(x86) 또는 Windows x64/SysV x64의 표준 레지스터 순서(REV-0106, REV-0122, REV-0123 등에서 다루는 계산 규약)를 그대로 따른다. 이런 경우는 REV-0148에서 다룬 대로 `Y`를 눌러 표준 키워드가 포함된 C 선언 한 줄(`int __cdecl func(int a, char *b)`)만 입력하면 충분하다.

### 표준 규약으로 안 맞을 때 — `__usercall`
컴파일러가 특정 헬퍼 함수를 표준 계산 규약이 아니라 그때그때 가장 효율적인 레지스터 조합으로 인라인/최적화하면, IDA는 이를 `__usercall`이라는 특수 규약으로 표시한다. `__usercall`을 쓰는 함수 원형은 각 인자 뒤에 `@<레지스터명>`을 붙여 정확히 어떤 레지스터(또는 스택 오프셋)로 그 인자가 들어오는지 명시한다.

```c
int __usercall calc_hash@<eax>(int a1@<ecx>, int a2@<edx>);
```

이 예시는 반환값이 `eax`로, 첫 번째 인자가 `ecx`로, 두 번째 인자가 `edx`로 전달된다는 것을 명시적으로 지정한 것이다. 실제 어셈블리를 보고 각 인자/반환값이 어느 레지스터에 있는지 직접 확인한 뒤 이 표기로 옮겨 적어야 한다.

### 간접 호출의 원형 지정 — Set call type
`call eax`처럼 호출 대상이 레지스터/메모리에 담긴 함수 포인터인 경우, IDA는 그 호출이 정확히 어떤 원형의 함수를 부르는지 스스로 알 방법이 없어 인자를 전혀 인식하지 못하거나 매우 보수적으로 추정한다. 이럴 때는 해당 CALL 명령어 위에서 우클릭 → **Set call type...**(또는 Pseudocode에서 그 호출 표현식 위에 커서를 놓고 동일 메뉴)을 사용해, 그 호출이 어떤 원형을 따르는지 C 선언으로 직접 알려준다. 예를 들어 함수 포인터 배열(vtable, 콜백 테이블 등)을 통한 호출이라면, 그 테이블 항목들이 공통으로 따르는 원형을 이 방법으로 지정해줘야 REV-0152에서 다루는 `call analysis failed`류의 실패도 함께 해결되는 경우가 많다.

### 가변 인자 함수 원형
`printf`처럼 인자 개수가 고정되지 않은 함수는 C 문법 그대로 `int __cdecl my_log(const char *fmt, ...)`처럼 마지막에 `...`를 붙여 지정한다. IDA는 가변 인자 함수를 호출하는 지점마다 실제 넘겨지는 인자 개수를 스택/레지스터 사용 패턴으로 추정해서 보여주려 시도하지만, 완벽하지 않으므로 REV-0163/REV-0165처럼 포맷 문자열 자체를 보고 실제 인자 개수와 타입을 교차 검증하는 것이 안전하다.

### Functions 창에서 원형을 한눈에 보기
Functions 창(REV-0143)은 컬럼 설정에 따라 각 함수의 현재 원형(또는 최소한 인자 개수)을 요약해서 보여줄 수 있다. 여러 함수의 원형을 점검해야 할 때는 이 창에서 먼저 이상해 보이는 함수를 골라낸 뒤 하나씩 `Y`로 들어가 확인하는 순서가 효율적이다.

## 화면/코드에서 보이는 징후
- Pseudocode에서 함수를 호출하는 곳마다 인자가 실제 어셈블리의 레지스터 사용과 안 맞게 표시된다(너무 적거나 엉뚱한 값).
- 함수 원형에 `__usercall`이 이미 자동으로 붙어 있지만 `@<reg>` 표기가 실제 레지스터와 다르게 추론되어 있다.
- `call eax` 같은 간접 호출 다음 줄부터 반환값이 전혀 안 쓰이는 것처럼 보이거나, 인자 없이 호출되는 것처럼 보인다.
- 가변 인자 함수를 호출하는 곳마다 인자 개수가 제각각으로 추정되어 일관성이 없어 보인다.

## 가장 먼저 할 것
문제가 되는 CALL이 직접 호출(대상 주소가 고정)인지 간접 호출(레지스터/메모리를 통함)인지부터 구분한다. 직접 호출이면 그 함수 자체의 원형을 `Y`로 고치면 되고, 간접 호출이면 그 호출 지점에서 **Set call type**을 써야 한다.

## 단계별 절차
1. 디스어셈블리에서 문제되는 CALL의 실제 인자 전달 방식을 먼저 손으로 추적한다(어떤 레지스터/스택 위치에 무엇이 들어가는지, REV-0106/REV-0122/REV-0123의 표준 규약과 비교).
2. 직접 호출이면 대상 함수 이름 위에서 `Y`를 눌러 원형을 입력한다. 표준 규약과 다르면 `__usercall`과 `@<레지스터>` 표기를 사용한다.
3. 간접 호출이면 CALL 명령어(또는 Pseudocode의 해당 호출 표현식) 위에서 우클릭 → **Set call type...**을 선택하고 C 선언으로 원형을 입력한다.
4. 가변 인자 함수라면 원형 끝에 `...`를 추가한다.
5. 원형을 확정한 뒤 F5로 Pseudocode를 새로고침해서 호출부 인자 표시가 실제 어셈블리와 일치하는지 재확인한다.
6. 같은 원형을 따르는 호출이 여러 곳에 있다면(예: 같은 함수 포인터 테이블의 다른 항목들), 각 호출 지점마다 반복 적용하거나 공통 typedef를 Local Types(REV-0737)에 만들어 재사용한다.

## 명령어/단축키
- `Y`: 직접 호출 대상 함수의 원형 지정(REV-0148)
- 간접 호출(CALL) 위 우클릭 → **Set call type...**: 간접 호출의 원형 지정
- `__usercall`, `@<레지스터명>`: 비표준 레지스터 배치를 명시하는 C 선언 확장 표기
- `...`: 가변 인자 표시(표준 C 문법)
- 함수 위 우클릭 → **Reanalyze function**: 원형 변경 후 재분석

## 출력 해석
- 원형을 `__usercall` + `@<reg>`로 정확히 맞추면, 호출부에서 해당 레지스터에 들어있던 값이 인자 자리로 정확히 옮겨져 표시된다.
- Set call type 적용 후에도 여전히 인자가 안 보인다면, 애초에 그 간접 호출이 가리키는 실제 함수가 지정한 원형과 다르거나(다형적 콜백 테이블처럼 항목마다 원형이 다른 경우), 레지스터/스택 추적 자체가 다른 이유로 실패하고 있는 것이다.
- 색상 표시(사용자 지정 파란색 vs 추론된 회색)는 REV-0148과 동일하게 적용되며, `__usercall` 원형도 사용자가 확정하면 파란색으로 표시된다.

## 흔한 실수
- 표준 규약(`__cdecl` 등)으로만 계속 시도하다가, 실제로는 `__usercall`이 필요한 상황이라는 걸 눈치채지 못하고 시간을 낭비하는 것.
- `@<레지스터>` 표기에서 실제 어셈블리를 확인하지 않고 추측으로 레지스터를 적어 오히려 더 잘못된 정보를 확정해버리는 것.
- 간접 호출에 Set call type을 적용하지 않고, 직접 호출인 것처럼 대상 함수를 찾으려 xref를 뒤지며 헤매는 것 — 함수 포인터 테이블을 통한 호출은 REV-0145(Xrefs)만으로 대상이 안 보일 수 있다.
- 가변 인자 함수에 `...`를 빼먹고 고정 인자 개수로만 선언해서, 실제로는 더 많은 인자를 넘기는 호출부에서 인자가 잘려 보이는 것.

## 막혔을 때 다음 체크
- 표준 호출 규약 자체가 헷갈린다면 → REV-0106 SysV AMD64 Calling Convention, REV-0122 Microsoft x64 Calling Convention, REV-0123 Windows x86 stdcall cdecl fastcall thiscall
- 원형을 고쳤는데도 디컴파일이 실패한다면 → REV-0152 IDA Decompiler Failed가 뜰 때
- 원형에 쓸 구조체/타입 자체가 아직 없다면 → REV-0734 IDA에서 구조체를 직접 정의해서 디컴파일에 적용하기, REV-0737 IDA Local Types 창 활용하기
- 함수 원형 지정의 기본 조작법 자체가 헷갈린다면 → REV-0148 IDA Y로 타입 지정하기

## 미니 예제
최적화된 x86 코드에서 다음과 같이 표준 규약과 다른 레지스터로 인자가 전달되는 헬퍼 함수가 있다고 하자.

```asm
mov ecx, [ebp+8]
mov edx, [ebp+0Ch]
call sub_401700
```

`sub_401700` 내부를 보면 첫 인자를 `ecx`, 둘째 인자를 `edx`에서 읽고 결과를 `eax`에 담아 리턴한다. `sub_401700` 위에서 `Y`를 눌러 다음처럼 지정한다.

```c
int __usercall sub_401700@<eax>(int a1@<ecx>, int a2@<edx>);
```

이후 이름을 `calc_checksum`으로 바꾸면(REV-0147), 호출부도 다음처럼 정확하게 표시된다.

```c
result = calc_checksum(v1, v2);
```

## 출처/검증
- `__usercall` 규약과 `@<레지스터>` 표기로 비표준 인자 전달 위치를 명시하는 방식, 함수 원형 편집기에서 이 표기를 입력하는 절차: Hex-Rays 공식 문서(Calling conventions, Function signature) 기준.
- 간접 호출에 대해 별도로 "Set call type"을 지정해야 하는 동작과 이것이 콜백 테이블/함수 포인터 분석에서 자주 쓰이는 방법이라는 점: Hex-Rays 공식 문서 및 디컴파일러 관련 공식 블로그(Igor's tip of the week 시리즈) 기준.
- 이 문서는 2026-09-09 기준 공개된 Hex-Rays 공식 문서 검색 결과를 바탕으로 작성했으며, 정확한 메뉴 문구는 IDA 버전에 따라 다를 수 있으므로 실제 환경에서 재확인할 것을 권장한다.
