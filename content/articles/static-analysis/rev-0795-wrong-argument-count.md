## 한 줄 요약
디컴파일러는 함수 원형(prototype)이 명시적으로 없을 때 "호출 규약상 인자로 쓰일 수 있는 레지스터/스택 위치 중 실제로 값이 읽히는 것처럼 보이는 곳"을 역추적해 인자 개수를 **추측**하는데, 최적화된 코드·가변 인자·레지스터 재사용·인자를 안 쓰는 함수 등에서는 이 추측이 자주 틀리며, 결과적으로 실제로 없는 `a2`, `a3` 같은 가짜 인자가 보이거나 반대로 실제 인자가 하나 빠진 채로 디컴파일되므로, 함수 원형을 직접 `Y`(Set item type)나 Edit Function으로 수동 지정해서 고쳐야 한다.

## 언제 검색해야 하나
- Pseudocode에 `sub_401200(a1, a2, a3)`처럼 인자가 나오는데, 실제로 그 함수 본문 안에서는 `a2`나 `a3`가 전혀 쓰이지 않을 때
- 반대로 함수 본문에서는 분명히 4번째 인자로 보이는 값을 쓰는데 함수 시그니처에는 인자가 3개까지만 나올 때
- 함수를 호출하는 여러 곳에서 넘기는 인자 개수가 서로 다르게 보일 때(어떤 호출부는 3개, 어떤 곳은 4개)
- Decompilation failed 메시지 중 `call analysis failed`가 뜰 때(REV-0152 참고)

## 핵심 개념
디컴파일러는 함수 본문을 스캔하면서 "함수 진입 직후 어떤 레지스터/스택 슬롯이 **먼저 읽히는지**"를 보고 그것을 인자로 간주한다(x86-64 System V는 RDI, RSI, RDX, RCX, R8, R9 순서, Windows x64는 RCX, RDX, R8, R9 순서). 이 추론은 다음과 같은 상황에서 어긋난다.

1. **호출자가 인자를 넘기지만 함수가 쓰지 않음**: 함수가 특정 인자를 아예 무시하면, 디컴파일러가 그 레지스터를 "안 읽으니 인자가 아니다"라고 판단해 실제보다 인자를 적게 잡을 수 있다. 반대로 호출 규약상 해당 레지스터가 다른 용도로 우연히 값을 갖고 있다가 읽히는 것처럼 보이면, 실제로는 인자가 아닌데 인자로 착각되어 `a2` 같은 가짜 인자가 생긴다.
2. **가변 인자 함수(variadic, printf류)**: 컴파일러는 실제로 몇 개의 인자가 넘어올지 코드만 봐서는 알 수 없으므로, 형식 문자열(포맷 스트링)을 해석해야만 정확한 인자 개수를 알 수 있다. 디컴파일러가 형식 문자열을 분석하지 못하면 인자 개수를 과소/과대 추정한다.
3. **최적화된 레지스터 재사용**: 컴파일러가 인자로 받은 레지스터를 함수 안에서 바로 다른 값으로 덮어써 재사용하면, 그 레지스터가 인자였다는 흔적이 사라져 디컴파일러가 놓칠 수 있다.
4. **커스텀/비표준 호출 규약**: 어셈블리로 직접 짜인 함수나 특수 목적 함수(인터럽트 핸들러, 코루틴 트램폴린 등)는 표준 호출 규약을 따르지 않을 수 있어 자동 추론이 아예 의미가 없다.
5. **호출부마다 실제로 다른 함수를 가리키는 간접 호출**: 함수 포인터를 통해 서로 다른 서명의 함수가 같은 자리에서 불리면, 디컴파일러는 그중 하나의 관찰 결과만으로 원형을 확정해버려 다른 호출부와 안 맞을 수 있다.

## 화면/코드에서 보이는 징후
- `sub_401200(a1, a2, a3)`인데 함수 본문에 `a2`, `a3` 언급이 전혀 없음
- 호출부마다 실제로 넘기는 인자 개수(레지스터 준비 코드 개수)가 서로 다름
- `printf(fmt, a2)`처럼 포맷 문자열 안에 `%d %s` 등이 여러 개인데 인자는 하나만 잡힘
- Output window에 `call analysis failed`

## 가장 먼저 할 것
문제의 함수를 호출하는 **모든** 호출부를 Xref(Ctrl+X)로 모아서, 각 호출 직전에 어떤 레지스터/스택에 값을 채우는지 디스어셈블리로 직접 센다. 디컴파일러의 추측이 아니라 실제 어셈블리가 진짜 인자 개수의 근거다.

## 단계별 절차

**1) 호출부 전수 조사**
`Ctrl+X`로 모든 호출부를 나열하고, 각 CALL 직전 몇 개의 인자 레지스터(SysV: RDI/RSI/RDX/RCX/R8/R9, Windows x64: RCX/RDX/R8/R9)가 채워지는지 디스어셈블리에서 직접 확인한다. 스택으로 넘어가는 5번째 이후 인자도 놓치지 않는다.

**2) 함수 본문에서 실제 사용 여부 확인**
함수 진입 직후 각 인자 레지스터가 실제로 읽혀서 쓰이는지 확인한다. 읽히지 않는데도 디컴파일러가 인자로 표시했다면 그 인자는 삭제해도 되는 "노이즈"일 수 있다(다만 삭제 전에 모든 호출부가 그 값을 실제로 무시하는지 재확인).

**3) 가변 인자라면 형식 문자열부터 확정**
`printf` 계열이면 첫 인자(형식 문자열)를 REV-0163 방식으로 먼저 찾아 `%d`, `%s`, `%x` 개수를 세고, 그 개수만큼 정확히 인자를 지정한다.

**4) Y로 함수 원형 직접 지정**
함수 시작 주소에서 `Y`(Set item type)를 눌러 정확한 인자 개수/타입/호출 규약을 직접 타이핑한다. 예: `int __fastcall check(int a, char *buf, int len)`. Ghidra는 함수 서명 편집(우클릭 → Edit Function Signature)으로 동일하게 처리한다.

**5) 재분석 후 모든 호출부 재확인**
원형을 고친 뒤 F5로 다시 디컴파일하고, 다른 호출부들도 새 원형에 맞게 자연스럽게 보이는지 확인한다. 한 호출부만 보고 원형을 정했다가 다른 호출부에서 인자가 안 맞아 보이면, 애초에 그 위치가 서로 다른 함수를 가리키는 간접 호출일 수 있다(REV-0794).

## 명령어/단축키
- `Ctrl+X`: 호출부 전체 Xref 목록
- `Y`: 함수/변수 타입·원형 직접 지정
- Edit → Functions → Edit function: 원형, 호출 규약(calling convention) 편집
- Ghidra: 함수 위 우클릭 → Edit Function Signature

## 출력 해석
- 원형을 고친 뒤에도 `call analysis failed`가 계속 뜨면, 그 CALL이 사실은 함수 포인터를 통한 간접 호출이라 대상 자체가 불확실한 경우일 수 있다(REV-0794).
- 인자 타입을 실제보다 큰 타입(예: 실제 `char`인데 `int`로)으로 지정하면 상위 바이트에 쓰레기 값이 섞여 보일 수 있으니, 어셈블리에서 실제로 읽는 크기(byte/word/dword/qword 명령어 접미사나 레지스터 서브셋)를 함께 확인한다.

## 흔한 실수
- 딱 한 곳의 호출부만 보고 인자 개수를 확정하는 것 — 여러 호출부를 비교해야 진짜 원형이 보인다.
- 가변 인자 함수에서 형식 문자열을 확인하지 않고 디컴파일러가 잡아준 개수를 그대로 믿는 것.
- 인자를 삭제할 때 그 레지스터가 함수 내부에서 다른 목적으로(예: 임시 변수로) 재사용되고 있어서 실제로는 인자가 아니라 그냥 우연히 겹친 값이라는 것을 확인하지 않는 것.
- 표준 호출 규약을 따르지 않는 저수준 함수(직접 작성된 어셈블리 루틴)에 표준 규약 원형을 억지로 씌우는 것.

## 막혔을 때 다음 체크

- 원인이 함수 포인터를 통한 간접 호출/가상함수라면 → REV-0794
- 반환값 타입도 같이 이상하다면 → REV-0796
- 함수/변수 타입 지정 기본 사용법이 헷갈리면 → REV-0148

## 미니 예제
`sub_401300(a1, a2)`로 디컴파일됐는데, 실제 호출부 3곳 중 2곳은 인자를 2개만 채우고 1곳은 3개(RDI, RSI, RDX)를 채운다고 하자. 3개를 채우는 호출부를 자세히 보니 함수 본문에서도 RDX로 들어온 값(길이 인자로 추정)이 특정 분기에서만 조건부로 쓰이고 있었다. 이 경우 실제 원형은 `int check(char *buf, int flag, int len)`이며, `len`을 안 쓰는 것처럼 보였던 두 호출부는 사실 옵션 인자를 0으로 넘긴 것뿐이다. `Y`로 3개 인자 원형을 지정하면 세 호출부 모두 자연스럽게 정리된다.

## 출처/검증
- x86-64 호출 규약(SysV: RDI/RSI/RDX/RCX/R8/R9, Windows x64: RCX/RDX/R8/R9, 스택 오버플로 인자 규칙)은 System V ABI AMD64 문서 및 Microsoft x64 calling convention 공식 문서 기준.
- 디컴파일러가 인자 개수를 함수 본문의 레지스터 사용 패턴으로 추론한다는 점과, `call analysis failed` 실패 메시지는 Hex-Rays 공식 문서("Failures and troubleshooting") 기준.
- Ghidra의 Edit Function Signature 기능은 Ghidra 공식 문서(Functions 관련 챕터) 기준.
