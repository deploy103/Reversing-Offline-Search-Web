## 한 줄 요약
**마이크로코드(microcode)**는 Hex-Rays 디컴파일러가 어셈블리를 Pseudocode(C 비슷한 코드)로 바꾸는 과정에서 내부적으로 사용하는 중간 표현(IR, Intermediate Representation)으로, F5로 보는 최종 Pseudocode는 이 마이크로코드가 여러 단계(maturity level)를 거쳐 점점 더 고수준으로 다듬어진 최종 산출물일 뿐이며, 왜 디컴파일 결과가 원본 어셈블리와 다르게 보이는지 이해하거나 Hex-Rays 플러그인을 직접 만들려면 이 중간 단계 개념을 알아야 한다.

## 언제 검색해야 하나
- Pseudocode가 실제 어셈블리와 구조적으로 많이 달라 보여서 "디컴파일러가 정확히 어떤 과정을 거쳐 이렇게 재구성했는지" 궁금할 때
- Hex-Rays SDK를 이용해 나만의 디컴파일러 플러그인(자동 디옵퓨스케이션 등)을 만들어보고 싶어서 그 내부 구조를 알아야 할 때
- "microcode", "MMAT", "mba_t" 같은 용어를 Hex-Rays 관련 문서나 발표 자료에서 봤는데 뜻을 모를 때
- 최적화가 심한 코드에서 디컴파일 결과가 신뢰할 만한지 판단하기 위해 중간 단계의 존재를 이해하고 싶을 때

## 핵심 개념

### 마이크로코드란 무엇인가
IDA의 일반 디스어셈블리는 CPU 명령어(x86, ARM 등 아키텍처별 opcode)를 그대로 보여준다. 반면 Hex-Rays 디컴파일러는 이 아키텍처별 명령어를 먼저 **마이크로코드**라는 아키텍처 중립적인 중간 명령어 집합으로 변환한 뒤, 그 마이크로코드를 반복적으로 분석·단순화·재구성해서 최종적으로 C 비슷한 Pseudocode를 만들어낸다. 즉 F5를 눌렀을 때 나오는 결과는 "어셈블리 → 마이크로코드 → 여러 단계의 최적화/재구성 → Pseudocode"라는 파이프라인의 마지막 산출물이다.

### Maturity level(성숙도 단계)
Hex-Rays는 마이크로코드가 얼마나 정제되었는지를 여러 단계(maturity level)로 구분해서 관리한다. 대표적으로 다음과 같은 흐름을 거친다(공식 SDK 문서 상의 `MMAT_` 접두사 상수들로 표현됨).
- 갓 변환된 초기 마이크로코드(가장 저수준, 어셈블리에 가까움)
- 지역적인 단순화가 적용된 단계(불필요한 명령 제거, 간단한 산술 정리 등)
- 호출 규약(calling convention)이 반영되어 함수 인자/리턴 값이 정리되는 단계
- 전역적인 최적화(global optimization)가 반복 적용되는 단계들
- 지역 변수(local variable) 구조가 최종적으로 확정되는 단계(가장 고수준, Pseudocode 직전 단계)

각 단계를 거치며 중복 계산 제거, 상수 폴딩, 데드 코드 제거 같은 컴파일러스러운 최적화가 마이크로코드 위에서 반복 적용된다. 이 때문에 원본 어셈블리에 있던 명령어 몇 개가 Pseudocode에서는 아예 사라지거나 하나의 표현식으로 합쳐져 보이는 경우가 생긴다.

### 왜 이 개념이 리버싱에 중요한가
- **디컴파일 결과를 맹신하지 않는 습관**: Pseudocode는 여러 단계의 "추정과 재구성"을 거친 결과이므로, 특히 최적화가 많이 된 바이너리나 난독화된 코드에서는 중간 단계 어딘가에서 실제 의도와 다르게 단순화됐을 가능성이 있다. 이상하게 보이는 Pseudocode를 만나면 어셈블리(REV-0146)와 대조하는 습관이 필요한 이유가 바로 이 파이프라인 때문이다.
- **Hex-Rays 플러그인 개발의 기반**: 자동 디옵퓨스케이션, 커스텀 최적화, 특정 패턴 자동 인식 같은 고급 플러그인은 마이크로코드 단계에 직접 개입(마이크로코드 필터/옵티마이저 등록)해서 동작한다. 이런 플러그인을 이해하거나 만들려면 마이크로코드와 maturity level 개념이 출발점이 된다.
- **디컴파일 실패/이상 동작의 원인 추적**: REV-0152(Decompiler Failed)나 REV-0151(Positive SP Value)처럼 디컴파일이 실패하거나 이상해지는 문제도, 결국 이 파이프라인의 특정 단계(스택 분석, 호출 규약 추정 등)에서 잘못된 추정이 발생했기 때문인 경우가 많다.

### Microcode Explorer류 플러그인
Hex-Rays SDK에는 각 maturity level 단계의 마이크로코드를 텍스트로 덤프하거나 시각화해서 보여주는 예제 플러그인(마이크로코드 탐색기 성격의 도구)이 존재한다. 이런 플러그인을 활용하면 "이 단계에서는 이렇게 보였는데, 다음 단계에서 이렇게 바뀌었다"는 것을 직접 눈으로 비교하며 학습할 수 있다. 다만 이는 SDK 기반의 추가 플러그인 영역이라, 기본 IDA/Hex-Rays 설치만으로는 UI에 노출되지 않을 수 있다.

## 화면/코드에서 보이는 징후
Pseudocode에서 원본 어셈블리 명령어 수보다 훨씬 적은 줄로 로직이 표현되어 있거나, 여러 개의 개별 연산이 하나의 복잡한 식으로 뭉쳐 보이거나, 최적화가 심한 함수에서 지역 변수 개수가 실제 스택 사용량보다 적어 보이면 마이크로코드 단계의 최적화가 강하게 적용된 결과일 수 있다.

## 가장 먼저 할 것
Pseudocode 결과가 이상하게 재구성되어 보인다면, 우선 이것이 "버그"가 아니라 마이크로코드 파이프라인의 여러 최적화 단계를 거친 정상적인 재구성일 수 있다는 점을 전제하고, `Tab`으로 원본 어셈블리와 대조하는 것부터 시작한다.

## 단계별 절차

**1) Pseudocode와 어셈블리를 나란히 대조**

이상해 보이는 줄을 클릭하고 `Tab`으로 어셈블리(IDA View)로 전환해 실제 명령어들을 확인한다(REV-0146).

**2) 여러 명령어가 한 줄로 합쳐졌는지 확인**

어셈블리에서는 여러 줄이었는데 Pseudocode에서 한 줄의 복잡한 식으로 보인다면, 이는 마이크로코드 단계에서 산술 표현식이 합쳐진(folding) 결과일 가능성이 크다 — 로직 자체는 동일하다.

**3) 스택/타입 분석 실패 여부와 구분**

만약 단순히 최적화 때문이 아니라 아예 코드가 말이 안 되게 보인다면, REV-0151/REV-0153처럼 스택 포인터 분석 자체가 실패한 별개의 문제일 수 있으니 그쪽 체크리스트도 함께 확인한다.

**4) 더 깊이 파고들고 싶다면 SDK 문서로 이동**

특정 최적화가 왜 일어났는지 근본 원인까지 알고 싶다면, 이 문서 수준을 넘어 Hex-Rays SDK의 마이크로코드 관련 헤더/문서(`hexrays.hpp`의 microcode 관련 API, maturity level 상수 정의)를 직접 참고해야 한다.

## 명령어/단축키
마이크로코드 자체를 들여다보는 것은 기본 UI 단축키가 아니라 SDK/플러그인 영역이므로, 이 글에서는 개념 이해에 필요한 관련 항목만 정리한다.
- `F5` — Pseudocode 생성(마이크로코드 파이프라인의 최종 결과 확인, REV-0146)
- `Tab` — Pseudocode ↔ 어셈블리 전환(중간 단계 대조용)
- SDK의 `MMAT_*` 상수 — 마이크로코드 maturity level을 코드/플러그인에서 식별할 때 쓰는 이름 (UI 단축키 아님, SDK 참고용)

## 출력 해석
- Pseudocode 한 줄이 어셈블리 여러 줄에 대응해도 "잘못된 디컴파일"이 아니라 정상적인 표현식 결합인 경우가 대부분이다.
- 함수 상단에 자동 경고 주석(`positive sp value` 등)이 붙어 있다면 그것은 마이크로코드 최적화 문제가 아니라 더 앞 단계인 스택 분석 실패 문제이므로 REV-0151/REV-0153을 먼저 확인해야 한다.
- 디컴파일 자체가 완전히 실패(에러)하는 경우는 마이크로코드 개념과 별개로 REV-0152를 참고한다.

## 흔한 실수
- Pseudocode가 어셈블리와 다르게 보이는 것을 전부 "IDA 버그"로 오해하는 것 — 대부분은 마이크로코드 단계의 정상적인 최적화/재구성 결과다.
- 마이크로코드를 "또 다른 어셈블리 문법"으로 착각하는 것 — 실제로는 아키텍처 중립적인 별개의 중간 표현이며, x86이든 ARM이든 같은 마이크로코드 명령 집합으로 변환된다.
- 이 개념을 몰라도 되는 초보 단계에서 SDK 플러그인 개발까지 성급히 시도하다가 기초적인 Pseudocode 읽기(REV-0146)를 소홀히 하는 것.

## 막혔을 때 다음 체크
- 기본적인 F5/Pseudocode 읽기 자체가 아직 익숙하지 않다면 → REV-0146 IDA F5 디컴파일과 Pseudocode 읽기.
- 디컴파일 결과에 이상한 경고가 붙어 있다면 → REV-0151 IDA Positive SP Value Has Been Detected 경고, REV-0153 IDA Stack Pointer 분석이 틀렸을 때.
- 디컴파일이 아예 실패한다면 → REV-0152 IDA Decompiler Failed가 뜰 때.
- 변수/함수 타입을 더 정확히 지정해서 재구성 품질을 높이고 싶다면 → REV-0148 IDA Y로 타입 지정하기.

## 미니 예제
```text
어셈블리(개념 예시):
  mov  eax, [ebp-4]
  add  eax, [ebp-8]
  mov  [ebp-0Ch], eax
  mov  eax, [ebp-0Ch]
  imul eax, 2

Pseudocode 결과:
  v3 = (v1 + v2) * 2;
```
어셈블리 5줄이 Pseudocode 한 줄로 합쳐진 것은, 마이크로코드 단계에서 임시 저장(`[ebp-0Ch]`에 썼다가 바로 다시 읽는 패턴)이 불필요한 중간 단계로 판단되어 제거되고, 산술 연산이 하나의 표현식으로 정리되었기 때문이다. 로직은 동일하며, 이것이 마이크로코드 최적화가 실제로 하는 일의 축소판이다.

## 관련 글
- REV-0146 — IDA F5 디컴파일과 Pseudocode 읽기
- REV-0151 — IDA Positive SP Value Has Been Detected 경고
- REV-0152 — IDA Decompiler Failed가 뜰 때
- REV-0153 — IDA Stack Pointer 분석이 틀렸을 때

## 출처/검증
- 마이크로코드(microcode)와 maturity level(`MMAT_*`) 개념, 어셈블리 → 마이크로코드 → Pseudocode로 이어지는 디컴파일 파이프라인 구조는 Hex-Rays 공식 SDK 문서 및 공식 블로그의 디컴파일러 내부 구조 설명("Decompiler internals: microcode" 계열 자료)을 기준으로 개념 수준에서 정리했다(2026-09-09 검증).
- 이 문서는 "개념" 이해를 목표로 하며, 정확한 maturity level 이름·순서·API 시그니처는 버전에 따라 세부가 달라질 수 있으므로, 실제 플러그인 개발을 하려면 설치된 IDA SDK의 `hexrays.hpp` 및 공식 SDK 문서를 직접 참고해야 한다.
