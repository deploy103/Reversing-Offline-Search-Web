## 한 줄 요약
함수가 자기 자신(또는 A→B→A처럼 서로를 부르는 상호 재귀)을 호출하는 것을 발견했을 때, 디컴파일러는 그 호출을 "무한히 펼쳐서" 보여주지 않고 평범한 CALL 한 줄로만 표시하므로 pseudocode 자체가 실제로 무한히 길어지지는 않으며, 진짜 어려움은 "이 함수가 언제, 몇 번 자기를 부르는지, 각 호출마다 인자가 어떻게 바뀌는지"를 사람이 머릿속으로 여러 겹 쌓아 추적해야 한다는 데 있다 — base case(종료 조건)와 recursive case(재귀 호출 조건)를 분리해서 읽고, 필요하면 동적으로 실제 재귀 깊이/인자 변화를 관찰하는 편이 훨씬 빠르다.

## 언제 검색해야 하나
- 어떤 함수의 디스어셈블리/pseudocode 안에 자기 자신의 시작 주소로의 CALL이 보일 때
- 함수 A가 B를 부르고 B가 다시 A를 부르는 상호 재귀(mutual recursion) 구조를 발견했을 때
- 재귀 호출부의 인자가 매번 바뀌는데(예: `n-1`, 포인터+1칸 등) 그 변화 규칙을 한눈에 못 알아보겠을 때
- 재귀 함수인데도 CALL 없이 루프처럼 보여서 이게 진짜 재귀인지 컴파일러가 반복문으로 바꾼 것인지 헷갈릴 때(꼬리재귀 최적화)

## 핵심 개념
재귀 자체는 디컴파일러 입장에서 특별한 문제가 아니다. 함수 A 안에서 A를 부르는 CALL은 다른 함수를 부르는 CALL과 어셈블리 수준에서 완전히 동일하게 생겼다(대상 주소가 자기 자신일 뿐). 디컴파일러는 이걸 그대로 "A(...)"라는 한 줄의 재귀 호출 표현으로 보여주며, 실행을 시뮬레이션해서 여러 단계를 펼쳐 보여주지 않는다. 따라서 "디컴파일 결과 자체가 무한히 커지는 것"이 아니라, **사람이 그 한 줄의 호출을 몇 번이고 겹쳐서 상상해야 로직이 이해된다는 것**이 실제 어려움이다.

재귀 함수를 읽을 때 핵심은 다음 두 부분을 분리하는 것이다.

1. **base case(종료 조건)**: 더 이상 자기 자신을 부르지 않고 바로 값을 반환하는 분기. 이게 없으면 무한 재귀(스택 오버플로우)이므로 반드시 어딘가에 있어야 한다.
2. **recursive case(재귀 호출 조건)**: 자기 자신을 부르되, 인자를 반드시 "종료 조건에 가까워지는 방향"으로 바꿔서 넘기는 부분(예: `n`을 `n-1`로, 포인터를 다음 칸으로).

또한 컴파일러 최적화 중 **꼬리 재귀 최적화(tail-call optimization)**가 적용되면, `return f(n-1)`처럼 재귀 호출 결과를 그대로 리턴하는 패턴이 CALL/RET 없이 그냥 `jmp` + 레지스터 갱신으로 바뀐 **반복문(loop)** 형태로 컴파일될 수 있다. 이 경우 디스어셈블리에는 자기 자신을 부르는 CALL이 아예 안 보이고, 대신 함수 시작 주소로 되돌아가는 조건부 점프만 보인다 — 이는 원래 재귀 함수였지만 디스어셈블리 레벨에서는 반복문처럼 보이는 정상적인 결과다.

## 화면/코드에서 보이는 징후
- 함수 본문 안에 자기 함수 시작 주소로의 `call`이 있음
- 재귀 호출 직전에 인자를 계산하는 산술 연산(`sub`, `add`, 포인터 증감 등)이 있음
- 함수 시작 근처로 되돌아가는 조건부 `jmp`가 있는데 `call`/`ret` 페어가 안 보임(꼬리재귀가 반복문화된 경우)
- 스택 사용량이 재귀 깊이에 비례해서 커질 것으로 예상되는 구조(각 재귀 프레임마다 지역 변수를 스택에 저장)

## 가장 먼저 할 것
함수 안에서 **자기 자신을 부르는 CALL이 있는 분기**와 **부르지 않고 바로 리턴하는 분기**를 그래프 뷰(REV-0150)에서 시각적으로 분리해서 표시해둔다. 후자가 base case다.

## 단계별 절차

**1) base case 찾기**
그래프 뷰에서 자기 자신을 부르지 않고 종료하는 경로(리프 노드)를 찾는다. 이 경로에 도달하는 조건(예: `n == 0`, 포인터가 NULL)이 재귀가 멈추는 조건이다.

**2) recursive case에서 인자 변화 규칙 확인**
재귀 호출 직전 인자가 어떻게 계산되는지 확인한다(REV-0175 참고). 이 변화가 base case 조건 쪽으로 수렴하는지 확인하면 재귀가 실제로 끝나는 구조라는 것을 검증할 수 있다.

**3) 한 단계만 손으로 펼쳐보기**
전체를 무한히 펼치려 하지 말고, 딱 2~3단계만 손으로 직접 대입해서 시뮬레이션해본다(예: `f(3) → f(2) → f(1) → f(0)=base`). 대부분의 재귀 로직은 2~3단계만 봐도 패턴이 파악된다.

**4) 파이썬으로 그대로 옮겨 재귀 함수로 재현**
로직이 파악되면 원래 함수와 같은 구조(같은 base case, 같은 recursive case)를 가진 파이썬 재귀 함수로 옮겨 적어 직접 실행해본다(REV-0168). 손으로 여러 단계를 추적하는 것보다 훨씬 정확하고 빠르다.

**5) 꼬리재귀가 의심되면 반복문으로 재해석**
CALL 없이 함수 시작으로 되돌아가는 조건부 점프만 보인다면, 이는 꼬리재귀가 최적화되어 반복문이 된 것일 수 있다. 이 경우 "이 함수가 자기 자신을 부른다"고 생각하지 말고, 그냥 일반적인 `while`/`for` 루프로 읽으면 오히려 더 단순해진다.

**6) 정적 추적이 너무 어려우면 동적으로 깊이/인자 관찰**
재귀 인자 변화 규칙이 복잡하거나(단순 감소가 아니라 조건에 따라 여러 방향으로 갈라짐) 상호 재귀가 여러 함수에 걸쳐 있으면, 그 함수에 브레이크포인트를 걸고 몇 번 호출되는지, 매번 인자가 어떻게 바뀌는지 실제로 실행하며 로그를 남기는 편이 훨씬 빠르다(REV-0805 기준).

## 명령어/단축키
- `Space`: 그래프 뷰 전환(base case/recursive case 분기 시각화)
- `Ctrl+X`: 함수 자신을 부르는 CALL의 xref 확인(자기 참조 여부 확인)
- GDB `dprintf`(REV-0642): 멈추지 않고 재귀 호출마다 인자 값만 로그로 남기기

## 출력 해석
- 재귀 호출부의 인자 계산식이 base case 조건과 무관한 방향으로 변한다면, 실제로는 무한 재귀(버그) 코드이거나 애초에 재귀 조건을 잘못 파악한 것이다.
- 파이썬으로 재현한 재귀 함수가 원본과 다른 결과를 낸다면, base case 조건의 부등호 방향(`<` vs `<=`) 같은 경계값을 놓쳤을 가능성이 높다.

## 흔한 실수
- 재귀를 무한히 손으로 펼쳐서 이해하려다 시간을 낭비하는 것 — 2~3단계만 확인하고 파이썬으로 재현하는 것이 훨씬 효율적이다.
- 꼬리재귀 최적화로 반복문이 된 코드를 억지로 "재귀"라고 생각하며 CALL을 찾으려고 헤매는 것.
- base case를 찾지 않고 recursive case만 계속 따라가는 것 — 종료 조건을 먼저 확정해야 전체 구조가 이해된다.
- 상호 재귀(A↔B)에서 한 함수만 보고 판단하는 것 — 관련된 모든 함수를 함께 봐야 한다.

## 미니 예제
어떤 함수가 `if (a1 <= 1) return a1;` 형태의 즉시 리턴 분기와, `return sub_401200(a1-1) + sub_401200(a1-2);` 형태로 자기 자신을 두 번 부르는 분기를 가진다고 하자. base case는 `a1 <= 1`이고, recursive case는 인자를 `a1-1`, `a1-2`로 줄여가며 두 갈래로 재귀한다. 이는 전형적인 피보나치 수열 계산 패턴이다. 이를 파이썬으로 `def f(a1): return a1 if a1 <= 1 else f(a1-1) + f(a1-2)`로 그대로 옮기면, 손으로 트리를 그리지 않고도 어떤 입력에 대해 어떤 값이 나오는지 즉시 계산할 수 있다.

## 출처/검증
- 재귀 호출이 어셈블리 수준에서 일반 함수 호출과 동일하게 표현된다는 점과 디컴파일러가 이를 한 줄의 재귀 호출로만 표시한다는 원리는 컴파일러/디컴파일러 일반론(스택 프레임 기반 함수 호출 모델)에 근거한다.
- 꼬리 호출 최적화(tail-call optimization)가 CALL/RET 대신 JMP로 컴파일되어 반복문 형태가 된다는 것은 GCC/Clang 최적화 문서에서 일반적으로 설명되는 표준 최적화 기법이다.
