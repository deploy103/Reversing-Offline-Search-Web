## 한 줄 요약
함수에 XREF(교차 참조)가 하나도 안 잡히는 것은 그 함수가 실제로 안 쓰인다는 뜻이 아니라, 대부분 **함수 주소가 레지스터/메모리(함수 포인터, vtable, 콜백 테이블)를 통해 간접적으로 호출**되기 때문이며, 정적 분석 도구는 "이 주소가 상수로 어디 쓰였는지"는 추적할 수 있어도 "실행 시점에 레지스터에 무엇이 들어있는지"는 정적으로 완전히 계산하지 못하는 것이 근본 원인이다.

## 언제 검색해야 하나
- IDA/Ghidra에서 함수 위에 커서를 놓고 xref를 확인(`X`)했는데 목록이 비어 있을 때
- 콜백 함수, 이벤트 핸들러, C++ 가상 함수처럼 "누군가 분명히 호출할 것 같은" 함수인데 호출 지점이 안 보일 때
- 디스어셈블리에서 `call rax`, `call [rax+8]`, `call qword ptr [rdi+0x10]`처럼 레지스터나 메모리를 통한 호출을 발견했을 때
- 함수 포인터 테이블이나 vtable 구조를 다뤄야 하는 바이너리를 분석 중일 때

## 핵심 개념
정적 분석 도구의 XREF는 기본적으로 **코드에 상수로 박혀 있는 주소**를 추적하는 기능이다. `call 0x401230`처럼 대상 주소가 명령어 자체에 고정되어 있으면 도구가 즉시 "이 주소를 참조하는 곳"으로 XREF를 만들 수 있다. 하지만 다음과 같은 **간접 호출(indirect call)**은 대상 주소가 실행 시점에 레지스터나 메모리에서 계산되므로, 정적 분석만으로는 원본 함수 주소를 확정하기 어렵다.

1. **함수 포인터 변수**: `void (*handler)(void)` 같은 변수에 함수 주소를 담아두고 나중에 `call [handler]` 형태로 호출하는 패턴. 이 포인터에 어떤 함수 주소가 저장되는지는 그 변수에 값을 쓰는 다른 코드 위치를 찾아야 알 수 있다.
2. **vtable을 통한 가상 함수 호출**: C++의 가상 함수는 객체의 vtable 포인터를 읽고, 그 vtable 안의 특정 오프셋에 있는 함수 포인터를 읽어 호출한다(`call qword ptr [rax+0x18]` 형태). 실제 대상은 그 객체의 런타임 타입에 따라 달라질 수 있다.
3. **콜백/디스패치 테이블**: 이벤트 처리기, 명령 파서 등에서 함수 포인터 배열을 인덱스로 접근해 호출하는 패턴(`call [rbx + rax*8]`).
4. **레지스터 간접 호출(`call rax` 등)**: 이미 다른 계산으로 레지스터에 주소가 로드된 뒤 그 레지스터로 바로 호출하는 경우.
5. **동적 API 해석(GetProcAddress/dlsym)**: 런타임에 심볼을 찾아 함수 포인터를 얻은 뒤 호출하는 경우(REV-0129 참고), 정적으로는 대상 함수 이름조차 알 수 없다.

이런 경우에도 IDA/Ghidra는 종종 **데이터 흐름을 부분적으로 추적**해 가능한 대상 후보를 표시해 주기도 하지만(예: vtable 오프셋을 안다면), 완전히 자동으로 XREF가 채워지는 것을 기대할 수는 없다. 결국 사람이 "이 포인터/테이블에 무엇이 들어가는지"를 직접 추적해야 한다.

## 화면/코드에서 보이는 징후
- 함수 위에서 `X`(xrefs)를 눌러도 목록이 비어 있다.
- 그 함수의 이름이 Symbol Tree/Functions 목록에는 있지만 아무도 호출하지 않는 것처럼 보인다.
- 근처 코드에서 `call rax`, `call [rdi+0x20]`, `jmp [rbx+rcx*8]` 같은 레지스터/메모리 기반 호출 명령어가 보인다.
- 전역 변수나 구조체 필드에 함수 주소로 보이는 값이 대입되는 코드가 있다.

## 가장 먼저 할 것
XREF가 비어 있는 함수의 주소 자체가 **데이터 영역 어딘가에 상수로 저장되는지** 먼저 검색한다. 함수 주소가 데이터로 저장되는 지점을 찾으면, 그 데이터가 어떻게 읽혀서 호출되는지를 역으로 추적할 수 있다.

## 단계별 절차

**1) 함수 주소 자체를 상수 검색**

함수의 시작 주소 값을 상수 검색(constant search, REV-0165)으로 바이너리 전체에서 찾는다. 이 주소가 데이터 섹션의 어떤 테이블(함수 포인터 배열, vtable) 안에 들어 있다면, 그 테이블 시작 주소를 알아낼 수 있다.

**2) 테이블을 참조하는 코드 찾기**

찾은 테이블 주소에 대해 다시 XREF(`X`)를 확인한다. 이 테이블 자체는 상수 주소이므로 보통 정상적으로 참조 코드가 잡힌다. 그 참조 코드에서 인덱스 계산(`rax*8` 등)과 함께 `call [table + index*8]` 형태의 호출이 이루어지는 패턴을 확인한다.

**3) vtable 패턴이라면 클래스 구조로 접근**

C++ 가상 함수가 의심되면, 객체 생성자에서 vtable 포인터가 어떻게 설정되는지부터 찾는다. 생성자 안에서 `mov [rdi], offset vtable_XXX` 형태로 vtable 주소를 객체에 심는 코드를 찾으면, 그 vtable 데이터 안에 나열된 함수 포인터들이 각각 몇 번째 가상 함수인지 오프셋으로 알 수 있다(REV-0444 참고).

**4) 레지스터 간접 호출은 역방향으로 값 추적**

`call rax`처럼 레지스터로 바로 호출하는 경우, 그 레지스터에 값을 채워 넣은 직전 명령어들을 위쪽으로 거슬러 올라간다(`mov rax, [...]`, `lea rax, [...]` 등). IDA/Ghidra의 디컴파일 결과가 이 과정을 어느 정도 자동으로 정리해서 보여주기도 하므로, 의사코드를 함께 확인한다.

**5) 정적 추적이 한계에 부딪히면 동적으로 전환**

여러 단계의 간접 참조가 겹쳐 있어 정적으로 대상을 특정하기 어렵다면, 디버거로 그 `call` 명령어에 브레이크포인트를 걸고 실제 실행 시점에 레지스터 값(호출 대상 주소)을 직접 읽는다. 이 값이 바로 실제로 호출되는 함수의 주소다.

**6) 동적 API 해석이면 이름 자체가 실행 중에 결정됨을 인지**

`GetProcAddress`/`dlsym`으로 얻은 함수 포인터를 호출하는 경우라면, 정적 분석만으로는 애초에 어떤 함수인지 알 수 없는 것이 정상이다. 이때는 그 API에 전달되는 함수 이름 문자열을 먼저 찾거나, 디버거로 반환값을 확인해야 한다.

## 명령어/단축키
```text
IDA:    X (xrefs to), Alt+T / 상수 검색(REV-0165 절차), Ctrl+X(호출 대상 추적)
Ghidra: X (Cross-references), Search → For Scalars(상수 검색)
공통:   디버거 브레이크포인트 + 레지스터 값 확인(정적 한계 도달 시)
```

## 출력 해석
- 함수 주소가 데이터 섹션에서 상수로 발견되면, 그 데이터 위치의 XREF는 대개 정상적으로 채워져 있다 — "함수 자체의 XREF가 0"과 "그 함수 주소를 담은 테이블의 XREF가 0"은 서로 다른 상황이므로 반드시 구분해서 확인한다.
- 디컴파일 결과에 `(*func_ptr)(arg1, arg2)`처럼 함수 포인터 호출 형태로 표시되면, 도구가 이미 "이건 간접 호출"이라고 알려주고 있는 것이므로 XREF가 없는 것이 당연하다.
- 디버거로 확인한 실제 호출 대상 주소가 이미 알고 있는 함수와 일치하면, 그 지점에 수동으로 이름/주석을 남겨 정적 분석 결과를 보강할 수 있다(IDA/Ghidra 모두 간접 호출 지점에 사용자가 직접 참조 정보를 추가하는 기능을 제공한다).

## 흔한 실수
- XREF가 없다고 해서 그 함수가 죽은 코드(dead code)라고 성급히 결론 내리는 것 — 먼저 함수 포인터/vtable/콜백 가능성을 점검해야 한다.
- 함수 포인터를 담는 테이블 자체의 XREF를 확인하지 않고, 함수 자체의 XREF만 계속 들여다보는 것.
- vtable 구조를 모르는 상태에서 가상 함수 호출 패턴(`call [rax+N]`)을 일반 오류로 오해하는 것.
- 정적으로 100% 해결하려고 시간을 쏟다가, 디버거로 몇 초 만에 확인할 수 있는 것을 놓치는 것 — 정적 분석의 한계에 부딪히면 동적 분석으로 전환하는 판단이 필요하다(REV-0309 참고).

## 막혔을 때 다음 체크
- 상수 검색 자체의 절차가 궁금하면 → REV-0165.
- vtable/가상 함수 호출 패턴의 어셈블리 형태가 궁금하면 → REV-0444.
- 함수 포인터가 메모리에서 어떻게 보이는지 기초 개념이 필요하면 → REV-0348.
- 정적 분석에서 동적 분석으로 전환할 타이밍 판단이 필요하면 → REV-0309.
- Ghidra의 기본 XREF 사용법 자체가 헷갈리면 → REV-0160, IDA는 REV-0145.

## 미니 예제
`FUN_00401800`이라는 함수에 XREF가 하나도 없어서 죽은 코드로 의심했던 상황이다.

1. `FUN_00401800`의 주소 값(`0x00401800`)을 상수 검색으로 바이너리 전체에서 찾는다.
2. 데이터 섹션의 `dispatch_table`이라는 배열 안에서 이 주소가 발견된다.
3. `dispatch_table`에 대해 XREF를 확인하니 `handle_command` 함수 안에서 `call [dispatch_table + rax*8]` 형태로 참조되고 있음을 확인한다.
4. `handle_command` 함수를 읽어보니, 사용자 입력 명령어 번호를 인덱스로 써서 이 테이블을 통해 여러 핸들러 함수 중 하나를 호출하는 구조임을 알게 된다.
5. 이제 `FUN_00401800`이 "명령어 번호 N에 대응하는 핸들러"라는 역할을 정적으로 확정하고, `handle_cmd_N`처럼 의미 있는 이름을 붙인다.

## 출처/검증
- XREF가 코드에 상수로 박힌 주소 참조를 기준으로 만들어지며, 레지스터/메모리를 통한 간접 호출 대상은 정적으로 완전히 자동 계산되지 않는다는 한계: IDA(Hex-Rays) 및 Ghidra 공식 문서의 Cross-Reference/Data Flow 관련 설명, 그리고 두 도구의 상수 검색·데이터 흐름 추적 기능 설명 기준.
- vtable을 통한 C++ 가상 함수 호출 패턴(객체의 vtable 포인터를 읽고 오프셋으로 함수 포인터를 읽어 호출)은 Itanium C++ ABI(가상 함수 테이블 레이아웃 표준)에 근거한 통상적인 컴파일러 구현 방식 기준이다.
- 이 문서는 특정 바이너리로 직접 재현 검증하지 않았으며, 두 도구의 공식 문서와 C++ ABI 표준, 그리고 일반적으로 알려진 리버싱 실무 패턴을 바탕으로 정리했다.
