## 한 줄 요약
같은 x86 계열인데도 32비트 코드를 64비트로, 혹은 64비트 코드를 32비트로 잘못 로드하면 레지스터 이름 체계·포인터 크기·스택 정렬·호출 규약이 전부 어긋나서 코드가 말이 안 되는 것처럼 보이며, 이는 REV-0802(아예 다른 아키텍처로 로드)와 증상은 비슷하지만 원인은 "같은 계열 안에서 비트폭만" 잘못 고른 것이므로, `file`/`readelf`로 ELF Class(`ELF32`/`ELF64`)나 PE의 매직 넘버(`PE32`/`PE32+`)를 먼저 확인해서 정확한 비트폭으로 다시 열어야 한다.

## 언제 검색해야 하나
- 디스어셈블리에 `eax`, `ebx` 같은 32비트 레지스터가 나와야 할 것 같은데 `rax`, `rbx`가 나오거나 그 반대일 때
- 함수 인자 전달 방식이 이 저장소의 다른 x86/x64 문서에서 설명하는 규칙과 안 맞아 보일 때(레지스터로 넘어와야 할 인자가 스택에서 오는 것처럼 보이거나 그 반대)
- 포인터 값이 8바이트여야 할 것 같은데 4바이트로 잘려서 상위 주소가 날아간 것처럼 보일 때
- 스택 프레임 오프셋이 예상보다 정확히 2배 어긋나 보일 때

## 핵심 개념
x86과 x86-64(x64)는 같은 명령어 집합 계열에 속하지만, 세부적으로 다음이 다르다.

- **레지스터 이름과 폭**: 32비트는 `eax`/`ebx`/`ecx`/`edx`(4바이트), 64비트는 `rax`/`rbx`/`rcx`/`rdx`(8바이트)와 추가 레지스터(`r8`~`r15`)를 쓴다.
- **포인터 크기**: 32비트는 4바이트, 64비트는 8바이트. 이는 스택에 저장되는 반환 주소, 지역 변수 오프셋 계산에 전부 영향을 준다.
- **인자 전달 규칙**: 32비트는 대부분 스택으로 인자를 전달하는 관례(cdecl 등)가 흔하고, 64비트는 SysV(리눅스, RDI/RSI/RDX/RCX/R8/R9)나 Microsoft x64(RCX/RDX/R8/R9)처럼 레지스터로 앞쪽 인자를 전달하는 관례를 쓴다.
- **파일 헤더 표현**: ELF는 헤더의 `EI_CLASS` 필드가 `ELFCLASS32`/`ELFCLASS64`로 구분되고, PE는 옵셔널 헤더의 매직 넘버가 `0x10B`(PE32)/`0x20B`(PE32+)로 구분된다.

IDA/Ghidra가 파일 헤더를 정상적으로 읽었다면 자동으로 올바른 비트폭을 선택하지만, 헤더가 비정상이거나(레이어드/패킹된 파일) 사용자가 로드 옵션에서 수동으로 잘못된 비트폭을 강제 선택하면, 명령어 인코딩 해석 자체가 어긋난다. 이는 REV-0802(완전히 다른 CPU 아키텍처로 잘못 로드)와 원리는 같지만(잘못된 명령어 해석 규칙 적용), 증상의 미묘함이 다르다 — 완전히 다른 아키텍처는 즉시 알아볼 수 없는 명령어로 깨지지만, 32/64비트 혼동은 부분적으로는 그럴듯한 명령어가 나오는 것처럼 보여서 더 늦게 발견되는 경우가 많다.

## 화면/코드에서 보이는 징후
- 레지스터 이름 체계가 예상과 다름(32비트 이름만 나오거나 64비트 이름만 나옴)
- 함수 시작 프롤로그가 `push rbp` / `mov rbp, rsp`(64비트 스타일)와 `push ebp` / `mov ebp, esp`(32비트 스타일) 중 이 바이너리의 알려진 출처(예: 문제 설명에 "64비트 리눅스 바이너리"라고 명시됨)와 맞지 않음
- 포인터/주소 값이 8바이트가 되어야 하는 문맥에서 4바이트로 잘려 상위 비트가 사라진 것처럼 계산됨
- Import/함수 인자 분석 결과가 이 저장소의 다른 문서(REV-0021 x86 vs x64)에서 설명하는 전달 규칙과 다름

## 가장 먼저 할 것
IDA/Ghidra를 건드리기 전에 셸에서 파일의 진짜 Class/비트폭을 확인한다.

## 단계별 절차

**1) ELF Class 확인**
```bash
file chall
readelf -h chall | grep Class
```
`Class: ELF32` 또는 `ELF64`로 정확히 나온다. `file` 명령 출력에도 `ELF 32-bit`/`ELF 64-bit`가 그대로 표시된다.

**2) PE 매직 넘버 확인**
```bash
file chall.exe
```
`file`이 `PE32 executable`(32비트) 또는 `PE32+ executable`(64비트)로 구분해서 알려준다. 직접 확인하려면 옵셔널 헤더 시작 2바이트가 `0B 01`(PE32)인지 `0B 02`(PE32+)인지 hex로 봐도 된다.

**3) IDA에서 정확한 비트폭으로 재로드**
잘못 로드된 IDB는 폐기하고, File → Open 시 Processor type에서 아키텍처뿐 아니라 비트폭(예: "metapc"의 경우 로드 후 내부적으로 32/64가 파일 헤더로 결정되지만, raw 바이너리처럼 헤더가 불명확한 파일은 수동 선택이 필요할 수 있음)이 올바른지 확인한다.

**4) Ghidra에서 정확한 비트폭 Language 선택**
Import File의 Language 목록에서 `x86:LE:32:default`와 `x86:LE:64:default`(또는 `gcc`/`windows` 컴파일러 규격 포함)를 명확히 구분해서 고른다.

**5) 재로드 후 검증**
프롤로그 스타일, 레지스터 이름, 포인터 계산이 알고 있는 파일 출처(문제 설명, 실행 환경)와 일치하는지 확인한다.

## 명령어/단축키
```bash
file <binary>
readelf -h <binary> | grep -E "Class|Machine"
xxd -l 4 -s 0 <pe_optional_header_offset> <binary.exe>   # PE32/PE32+ 매직 직접 확인시
```
- IDA: File → Open 시 로드 옵션 재확인(잘못 로드된 IDB는 새로 생성해서 다시 시도)
- Ghidra: Import File의 Language 목록에서 비트폭 명시 선택

## 출력 해석
- `readelf -h`의 `Class` 필드가 실제 코드 스타일(레지스터 이름 등)과 다르면 잘못 로드된 것이 확정이다.
- 재로드 후 알려진 표준 프롤로그(`endbr64` 등 64비트 관련 명령, 혹은 32비트 전용 명령)가 정상적으로 보이면 문제가 해결된 것이다.

## 흔한 실수
- REV-0802(완전히 다른 아키텍처)와 이 문제를 혼동해서 엉뚱한 프로세서 모듈을 찾아 헤매는 것 — 이건 같은 x86 계열 안에서 비트폭만 잘못된 경우다.
- 파일 헤더를 확인하지 않고 "일단 64비트겠지"라고 추측만으로 로드하는 것.
- 32/64비트 차이가 레지스터 이름뿐이라고 생각해서 인자 전달 규칙(스택 vs 레지스터) 차이를 놓치고 잘못된 결론을 내리는 것.
- 레이어드/패킹된 파일에서 언패킹 후 실제 내부 코드의 비트폭이 겉 파일과 다를 수 있다는 것을 확인하지 않는 것.

## 막혔을 때 다음 체크
- 완전히 다른 CPU 아키텍처로 잘못 로드된 것 같다면 → REV-0802
- x86과 x64의 기본적인 차이(레지스터, 호출 규약)가 헷갈린다면 → REV-0021
- 올바른 비트폭으로 열었는데도 함수가 하나도 안 잡힌다면 → REV-0772

## 미니 예제
`file chall`이 `ELF 64-bit LSB executable, x86-64`라고 알려주는데, IDA에서 예전에 만들어둔 IDB(32비트로 잘못 열렸던 것)를 재사용해서 디스어셈블리를 보니 `push ebp`, `mov ebp, esp`처럼 32비트 스타일 프롤로그로 나오고 인자도 전부 스택에서 오는 것처럼 보였다. 이는 실제 파일과 로드된 비트폭이 다르다는 강한 신호다. 기존 IDB를 버리고 원본 파일을 새로 열되, 이번에는 로드 대화상자에서 파일 헤더가 자동으로 인식한 64비트 옵션을 그대로 받아들이면 `push rbp`, `mov rbp, rsp`와 SysV 레지스터 인자 전달(`rdi`, `rsi`...)이 정상적으로 보인다.

## 관련 글
- REV-0802 — IDA/Ghidra에서 잘못된 아키텍처로 로드되어 전부 깨질 때
- REV-0021 — x86와 x64를 구분하는 법
- REV-0772 — IDA에서 함수가 아예 하나도 안 잡힐 때

## 출처/검증
- ELF `EI_CLASS`(ELFCLASS32/ELFCLASS64) 필드는 System V ABI(ELF 스펙) 공식 문서 기준.
- PE 옵셔널 헤더의 매직 넘버(`0x10B`=PE32, `0x20B`=PE32+)는 Microsoft PE/COFF 공식 문서(PE Format 스펙) 기준.
- x86/x64 레지스터 이름 체계와 호출 규약 차이는 System V ABI AMD64 문서 및 Intel/AMD 아키텍처 매뉴얼 기준.
