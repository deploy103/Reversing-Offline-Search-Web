## 한 줄 요약
**FLIRT**(Fast Library Identification and Recognition Technology)는 정적으로 링크되어 심볼 이름이 사라진 라이브러리 함수(libc, 컴파일러 런타임 등)를, 함수 내부의 바이트 패턴을 미리 만들어둔 시그니처(`.sig`/`.pat` 파일)와 대조해서 원래 이름으로 자동 인식해주는 IDA 기능으로, 정적 링킹된 바이너리를 분석할 때 `sub_401230` 같은 이름 없는 함수 수백 개 중 어떤 것이 `malloc`, `strcpy` 같은 표준 함수인지 자동으로 알려준다.

## 언제 검색해야 하나
- 정적 링킹(static linking)된 바이너리라 함수 이름이 대부분 `sub_XXXXXX`로만 보일 때(REV-0646 참고)
- IDA가 처음 파일을 열 때 "표준 함수를 몇 개 인식했다"는 메시지를 봤는데 그게 무슨 뜻인지 궁금할 때
- 자체 static 라이브러리(직접 컴파일한 `.a`/`.lib`)를 여러 바이너리에서 반복해서 마주치는데, 매번 손으로 분석하지 않고 한 번만 시그니처를 만들어 재사용하고 싶을 때
- FLIRT로 인식된 함수 이름이 실제와 다르거나 충돌(false positive)나서 왜 그런지 이해하고 싶을 때

## 핵심 개념

### FLIRT가 해결하는 문제
동적 링킹된 바이너리는 `printf`, `malloc` 같은 함수를 임포트 테이블(PLT/IAT)로 호출하므로 IDA가 이름을 그대로 보여줄 수 있다. 하지만 **정적 링킹**된 바이너리는 그 라이브러리 함수의 실제 코드가 바이너리 안에 통째로 복사되어 들어가 있고, 컴파일 시 디버그 심볼이 제거(strip)되면 그 함수들의 원래 이름 정보가 전혀 남지 않는다. 이렇게 되면 IDA는 그 함수를 그냥 `sub_401230`처럼 주소 기반 이름으로만 표시할 수밖에 없다. FLIRT는 이 문제를 "이미 알려진 라이브러리 함수들의 바이트 패턴 데이터베이스"와 대조하는 방식으로 해결한다.

### 시그니처는 어떻게 만들어지는가 — 패턴 매칭 개념
FLIRT 시그니처는 함수의 처음 몇 바이트(주소가 바뀌어도 변하지 않는 부분은 그대로, 재배치(relocation)가 필요한 주소 부분은 와일드카드로 처리)를 정리한 패턴과, 체크섬 같은 보조 정보를 함께 담은 데이터베이스다. IDA는 분석 중인 바이너리의 함수 시작 바이트열을 이 데이터베이스의 패턴들과 비교해서 일치하는 것을 찾고, 일치하면 그 함수에 데이터베이스에 저장된 원래 이름(예: `malloc`, `_IO_printf`)을 자동으로 붙여준다. 컴파일러/라이브러리 버전, 최적화 옵션, 아키텍처가 다르면 바이트 패턴도 달라지므로, 시그니처는 보통 "특정 컴파일러+특정 라이브러리 버전+특정 아키텍처" 조합별로 따로 만들어진다.

### IDA가 기본 제공하는 시그니처
IDA는 자주 쓰이는 컴파일러/런타임(예: 여러 버전의 MSVC 런타임, glibc 계열 등) 조합에 대한 시그니처 파일을 기본 배포판에 함께 제공한다. 파일을 처음 열 때 IDA가 아키텍처/컴파일러를 추정해서 어울리는 시그니처를 자동으로 적용해보는 경우가 많고, 자동으로 안 됐다면 수동으로 불러올 수 있다.

### 직접 만들기 — FLAIR 도구 (`pelf`/`pcf`/`sigmake`)
Hex-Rays는 FLIRT 시그니처를 직접 만들 수 있는 별도 도구 모음(FLAIR, "Fast Library Acquisition for Identification and Recognition")을 함께 배포한다. 대표적인 도구는 다음과 같다.
- `pelf`(또는 `pcf` 등, 대상 라이브러리 파일 형식에 맞는 파서) — 정적 라이브러리(`.a`, `.lib`) 파일에서 각 함수의 패턴 정보를 추출해 `.pat`(텍스트 패턴) 파일로 만든다.
- `sigmake` — 여러 `.pat` 파일(패턴 텍스트)을 모아 실제 IDA가 로드할 수 있는 이진 형식 `.sig` 파일로 컴파일한다.
- `zipsig` — 만들어진 `.sig` 파일을 압축해 배포/보관하기 좋은 형태로 만든다.

이 도구들을 이용하면, CTF 문제에서 반복적으로 등장하는 자체 정적 라이브러리나 특정 프레임워크 코드에 대해 한 번만 시그니처를 만들어두고, 이후 같은 라이브러리가 포함된 다른 바이너리에서 계속 재사용할 수 있다.

## 화면/코드에서 보이는 징후
파일을 열었을 때 상태 메시지 창에 "library function(s) found"류의 로그가 보이거나, Functions 목록에서 일부 함수 이름이 밑줄이나 별도 표시(라이브러리 함수 표시 스타일)와 함께 실제 함수 이름으로 나와 있고, 반대로 인식이 안 된 나머지는 여전히 `sub_` 접두사로 남아 있다면 FLIRT가 이미 부분적으로 동작한 상태다.

## 가장 먼저 할 것
Output window(로그 창)에서 파일을 처음 열 때 나온 FLIRT 관련 메시지를 확인해, 어떤 시그니처가 자동 적용됐는지부터 파악한다.

## 단계별 절차

**1) 자동 인식 결과 확인**

파일을 열고 Output window 로그에서 "library function" 관련 메시지 유무를 확인한다. 이미 여러 함수가 인식되어 있다면 그 이름들을 참고해 분석을 시작한다.

**2) 수동으로 시그니처 적용**

자동으로 안 됐거나 다른 시그니처를 추가로 적용하고 싶다면 `File → Load file → FLIRT signature file` 메뉴에서 대상 아키텍처/컴파일러에 맞는 `.sig` 파일을 선택한다.

**3) 인식된 함수 검토**

FLIRT로 이름 붙은 함수라도 100% 확신할 수는 없으므로(특히 짧은 함수, 흔한 패턴), 실제 Pseudocode를 열어 그 이름과 동작이 실제로 일치하는지 한 번은 확인하는 것이 안전하다.

**4) 자체 라이브러리 시그니처 만들기(선택)**

같은 정적 라이브러리가 반복 등장하는 상황이라면, FLAIR 도구로 `.a`/`.lib`에서 `pelf`(또는 대상 형식에 맞는 도구)로 `.pat`를 뽑고, `sigmake`로 `.sig`를 만들어 이후 계속 재사용한다.

**5) 남은 함수는 수동 분석**

FLIRT로도 인식되지 않는 함수(자체 작성 코드, 매우 드문 라이브러리)는 결국 REV-0146 등 기본 정적 분석 절차로 직접 분석해야 한다.

## 명령어/단축키
| 메뉴/도구 | 동작 |
|---|---|
| `File → Load file → FLIRT signature file` | `.sig` 파일을 현재 IDB에 수동 적용 |
| Output window 로그 | 자동 적용된 FLIRT 시그니처와 인식된 함수 수 확인 |
| `pelf` / `pcf` (FLAIR 도구) | 정적 라이브러리(`.a`/`.lib`)에서 패턴(`.pat`) 추출 |
| `sigmake` (FLAIR 도구) | `.pat` 파일들을 이진 `.sig` 파일로 컴파일 |
| `zipsig` (FLAIR 도구) | 만든 `.sig` 파일 압축/정리 |

## 출력 해석
- FLIRT로 인식된 함수 이름은 대개 일반 사용자 지정 이름과 시각적으로 구분되는 스타일(예: 특정 색상이나 표시)로 나타나는 경우가 많다 — 이는 "IDA가 자동으로 추정한 이름"이라는 뜻이므로 100% 확신하지 말고 필요시 재검증한다.
- 같은 함수에 여러 시그니처 후보가 매칭되어 충돌하면 IDA가 후보 목록을 보여주거나 가장 가능성 높은 것을 자동 선택할 수 있다 — 이런 경우일수록 실제 코드와 대조 검증이 더 중요하다.
- 시그니처를 적용했는데도 함수 이름이 전혀 안 바뀐다면, 그 바이너리의 컴파일러/버전/최적화 옵션이 시그니처가 만들어진 조건과 달라 바이트 패턴이 안 맞는 것일 수 있다.

## 흔한 실수
- FLIRT가 인식한 이름을 100% 정답이라고 맹신하는 것 — 바이트 패턴 매칭 특성상 짧거나 흔한 함수는 오인식(false positive)될 수 있다.
- 정적 링킹 여부를 확인하지 않고 무작정 시그니처를 대량으로 불러와서 엉뚱한 매칭이 늘어나는 것 — 먼저 REV-0646으로 정적 링킹 여부와 사용된 라이브러리 종류를 파악하는 것이 순서상 유리하다.
- FLAIR로 시그니처를 만들 때 원본 정적 라이브러리가 아니라 이미 링크된 최종 바이너리에서 패턴을 뽑으려고 시도하는 것 — FLAIR 도구는 기본적으로 `.a`/`.lib` 같은 정적 라이브러리 아카이브를 입력으로 기대한다.
- 시그니처를 한 번 만들어두고 프로젝트/조직 차원에서 공유·재사용하지 않아, 같은 라이브러리를 볼 때마다 매번 새로 분석하는 것.

## 막혔을 때 다음 체크
- 정적 링킹된 바이너리 자체를 어떻게 다뤄야 할지 기초가 필요하면 → REV-0646 정적 링킹된(Statically Linked) ELF 분석 접근법.
- FLIRT로 인식되지 않은 함수를 직접 분석하는 기본기는 → REV-0146 IDA F5 디컴파일과 Pseudocode 읽기.
- 인식된 함수 이름을 더 정리하고 싶다면 → REV-0147 IDA 함수 변수 이름 N으로 바꾸기.
- glibc/musl 등 라이브러리별 차이를 함께 이해하고 싶다면 → REV-0647 musl libc와 glibc 차이가 리버싱에 미치는 영향.

## 미니 예제
```text
1. 정적 링킹된 strip 바이너리를 IDA로 열기
2. Output window: "104 library function(s) found" 로그 확인
3. Functions 창(Ctrl+P)에서 sub_ 접두사가 아니라 malloc, free, strcpy 등
   실제 이름이 붙은 함수들이 다수 보임
4. main처럼 인식 안 된 함수는 여전히 sub_401000 형태로 남아있어 직접 분석 필요
```

## 관련 글
- REV-0646 — 정적 링킹된(Statically Linked) ELF 분석 접근법
- REV-0647 — musl libc와 glibc 차이가 리버싱에 미치는 영향
- REV-0146 — IDA F5 디컴파일과 Pseudocode 읽기
- REV-0147 — IDA 함수 변수 이름 N으로 바꾸기

## 출처/검증
- FLIRT(Fast Library Identification and Recognition Technology)의 개념, 정적 링킹 함수 자동 인식 원리, `File → Load file → FLIRT signature file` 메뉴 경로는 Hex-Rays 공식 문서(docs.hex-rays.com)의 FLIRT 관련 설명을 기준으로 정리했다(2026-09-09 검증).
- FLAIR 도구 모음(`pelf`/`pcf`/`sigmake`/`zipsig`)의 역할은 Hex-Rays가 공개적으로 배포하는 FLAIR 패키지 설명 문서를 기준으로 정리했다. 정확한 실행 파일 이름/옵션은 배포판과 대상 파일 형식(ELF `.a` vs COFF `.lib` 등)에 따라 다를 수 있으므로 실제 사용 전 FLAIR 패키지에 포함된 README를 재확인할 것을 권장한다.
