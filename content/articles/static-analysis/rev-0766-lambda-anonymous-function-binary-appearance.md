## 한 줄 요약
C++ 람다(lambda)는 소스 코드에서는 이름이 없지만 컴파일되면 컴파일러가 자동으로 만든 **이름 없는 클로저 클래스**(캡처한 변수를 필드로 갖고 `operator()`를 멤버 함수로 갖는 구조체)가 되며, 캡처가 없으면 통째로 인라이닝되거나 평범한 함수 포인터로 사라지고, 캡처가 있으면 REV-0764의 클래스 구조 추정 방법을 그대로 적용할 수 있는 작은 객체로 남는다.

## 언제 검색해야 하나
- 데맹글된 함수 이름에 `lambda`라는 단어가 그대로 포함되어 있거나(`operator()`만 있고 클래스 이름이 이상한 형태) 이게 무슨 함수인지 감이 안 잡힐 때
- `std::function`, `std::for_each`, `std::sort`에 콜백을 넘기는 코드를 디컴파일했는데 실제 콜백 코드가 어디 있는지 안 보일 때
- 반복문 안에 함수 호출 없이 바로 코드가 인라인되어 있어서 원래 람다/콜백 구조였는지 짐작이 안 될 때
- C 코드인데도 짧은 익명 함수처럼 동작하는 코드(함수 포인터 배열, GCC 중첩 함수)를 만나서 C++ 람다와 구분이 안 될 때

## 핵심 개념

### 람다는 "이름 없는 클래스 + operator()"로 컴파일된다
C++ 표준은 람다 표현식(`[capture](params){...}`)을 컴파일러가 자동 생성하는 고유하고 이름 없는 클래스의 인스턴스로 정의한다. 이 클래스는:

- 캡처한 변수들을 멤버 필드로 갖는다(값 캡처는 값 복사본, 참조 캡처는 참조/포인터).
- 함수 호출 연산자 `operator()`를 멤버 함수로 갖고, 람다 본문이 바로 이 함수의 몸체가 된다.
- 캡처가 전혀 없는 람다(`[](int x){ return x+1; }`)는 암묵적으로 일반 함수 포인터로 변환 가능하며, 실제로 이런 경우 컴파일러가 별도의 클로저 객체 없이 그냥 평범한 정적 함수로 최적화해버리는 경우가 많다.

### 이름 맹글링에서 람다가 드러나는 형태
- **Itanium ABI(GCC/Clang)**: 람다의 클로저 타입은 "이름 없는 타입"이므로 `Ul<params>E_`(unnamed-type, lambda의 약자 `l`, 뒤에 매개변수 타입, 그리고 같은 스코프 내 몇 번째 람다인지 나타내는 순번 `_0`, `_1`...) 형태로 맹글링된다. 데맹글하면 보통 `main::{lambda(int)#1}::operator()(int) const` 같은 형태로 표시된다.
- **MSVC**: 컴파일러가 내부적으로 `<lambda_...>` 형태의 합성 이름을 붙이며, 데맹글 결과에 `` `anonymous namespace'::<lambda_1>::operator()`` 같은 표시가 나타난다.

두 경우 모두 핵심 특징은 같다 — **함수 이름 자체에 "lambda"라는 단어 또는 그에 준하는 표식(Itanium은 `Ul...E`, MSVC는 `<lambda_`)이 포함되고, 실제 호출 가능한 것은 `operator()`뿐**이라는 점이다.

### 캡처 없는 람다는 통째로 사라질 수 있다
캡처가 없고 함수가 짧으면, 컴파일러(특히 `-O2` 이상)는 클로저 객체를 아예 만들지 않고 그 자리에서 즉시 인라이닝해버리는 경우가 매우 흔하다. 이 경우 별도의 `operator()` 함수 자체가 바이너리에 남지 않을 수 있으며, 이는 REV-0495(인라인된 함수 때문에 CALL이 하나도 없는 함수를 만났을 때)에서 다루는 현상과 동일한 원리다. 이런 경우 "람다가 어디 갔지?"라고 함수를 찾아 헤매기보다는, 람다를 호출했을 자리(예: `std::sort`의 비교자 인자 위치)에 코드가 그대로 풀려 들어가 있는지부터 확인해야 한다.

### `std::function`을 통한 타입 소거(type erasure)
람다가 `std::function<void(int)>` 같은 타입으로 저장되면, 실제 호출은 내부에 저장된 **함수 포인터(또는 vtable과 유사한 내부 디스패치 구조)를 통한 간접 호출**로 나타난다. 이는 REV-0348(함수 포인터가 메모리에서 어떻게 보이는지)과 REV-0349(콜백 함수 패턴을 어셈블리에서 알아보는 법)에서 다루는 "콜백 패턴"과 정확히 동일한 형태로 디스어셈블리에 나타나며, 실제 호출 대상을 알아내려면 그 함수 포인터가 어디서 채워졌는지 역추적해야 한다.

### C 언어에는 람다가 없다 — 유사 패턴은 함수 포인터
C 코드에서는 언어 차원의 람다가 없으므로, 비슷한 역할은 평범한 정적 함수 + 함수 포인터 배열(콜백 테이블)로 구현된다. GCC의 비표준 확장인 중첩 함수(nested function)는 스택에 트램폴린 코드를 생성하는 드문 형태로 나타날 수 있지만 CTF 바이너리에서는 매우 드물다.

## 화면/코드에서 보이는 징후
- 데맹글된 이름에 `{lambda(...)#N}` 또는 `<lambda_N>`, `operator()`가 포함되어 있다.
- 아주 작은 클래스(필드 1~2개, 캡처 변수에 대응)에 생성자와 `operator()`만 존재하고 다른 메서드가 없다.
- `std::sort`, `std::for_each`, `std::function`을 호출하는 코드 주변에서 함수 포인터를 어딘가에서 읽어와 간접 호출(`call [rax]` 계열)하는 패턴이 보인다.
- 반복문 몸체 안에 별도 함수 호출 없이 계산 로직이 그대로 펼쳐져 있는데, 그 로직이 반복문 바깥 컨텍스트의 변수를 참조한다(캡처된 변수가 인라이닝되며 그대로 남은 흔적).

## 가장 먼저 할 것
데맹글된 이름에 `lambda`/`operator()` 표식이 있는지부터 확인한다. 있다면 REV-0764 방식으로 그 작은 클로저 "클래스"의 필드(캡처 변수)를 정리하고, `operator()`를 일반 메서드처럼 분석하면 된다. 표식이 없는데 콜백 패턴이 의심되면 인라이닝(REV-0495)을 먼저 의심한다.

## 단계별 절차
1. 함수 목록에서 `lambda`, `operator()`, `Ul`, `<lambda_` 표식을 검색해 후보를 모은다.
2. 후보로 찾은 클로저 클래스의 생성자(있다면)를 열어 어떤 변수를 캡처했는지(필드로 무엇을 저장하는지) REV-0764 방식으로 정리한다.
3. `operator()`를 열어 그 본문이 실제로 무슨 계산을 하는지 분석한다 — 첫 인자는 클로저 객체 자신(`this`)이고, 그다음부터가 람다의 실제 매개변수다.
4. 클로저 객체가 안 보이는데 `std::sort`/`std::for_each` 같은 템플릿 알고리즘 호출이 있다면, 그 호출 직전/직후에 인라이닝된 코드 블록이 있는지 REV-0166(Call Graph)과 함께 주변 코드를 넓게 살펴본다.
5. `std::function`을 통한 간접 호출이 보이면, REV-0348/0349 방식으로 함수 포인터가 저장된 위치를 역추적해 실제 대상 함수를 찾는다.
6. 최종적으로 "이 람다는 어떤 값을 캡처해서 어떤 계산을 하는가"를 한 문장으로 정리해 상위 함수 분석에 반영한다.

## 명령어/단축키
- IDA/Ghidra 공통: 함수 이름 필터에 `lambda`, `operator` 입력해 후보 검색
- IDA: 간접 호출 대상 추적은 해당 레지스터에서 역방향으로 데이터 흐름을 따라가며 `X`(Xref)를 반복 사용
- Ghidra: Decompile 창에서 함수 포인터 변수에 우클릭 → `References` 로 대입 위치 추적

## 출력 해석
- `operator()`가 상수만 반환하고 캡처 필드를 전혀 참조하지 않는다면, 이는 캡처 없는 람다이거나 단순 상태 없는 콜백이다.
- 클로저 클래스에 필드가 하나 있고 그 타입이 포인터라면 참조 캡처(`[&var]`)일 가능성이, 값 자체(정수/구조체)라면 값 캡처(`[var]`)일 가능성이 크다.
- 인라이닝되어 별도 함수가 없다면, 호출부 코드 안에서 반복되는 계산 패턴이 곧 람다 본문이라고 해석하면 된다.

## 흔한 실수
- `operator()`라는 이름만 보고 이것도 REV-0763에서 다룬 일반 연산자 오버로드(`operator==` 등)와 완전히 같은 것으로 취급해 클로저라는 특수성을 놓치는 것 — `operator()`는 함수 호출 연산자이므로 람다/함수 객체(functor)의 핵심 진입점이라는 점을 알아야 한다.
- 캡처 없는 람다가 인라이닝되어 안 보인다고 "이 프로그램엔 람다가 없다"고 단정하는 것 — 소스 레벨 구조와 바이너리 레벨 구조는 다를 수 있다.
- `std::function`의 내부 구현(작은 버퍼 최적화, 힙 할당 여부)을 완전히 이해하려고 시간을 쓰는 것 — 정적 분석 목적에서는 "결국 함수 포인터를 간접 호출한다"는 결론만 있으면 충분하다.

## 막혔을 때 다음 체크
- 클로저 클래스의 필드(캡처 변수) 구조를 정리하는 구체적 방법이 필요하면 → REV-0764(데맹글된 이름으로 클래스 구조 추정하기)
- 이름 자체가 `_Z`/`?`로 시작해서 해석이 안 된다면 → REV-0763(C++ 이름 맹글링 해석하기)
- 함수 호출인데 CALL 명령어가 안 보인다면 → ../assembly/rev-0495-no-call-due-to-inlining.md
- 함수 포인터/콜백 호출 패턴 자체가 처음이라면 → REV-0348(함수 포인터가 메모리에서 어떻게 보이는지), REV-0349(콜백 함수 패턴을 어셈블리에서 알아보는 법)

## 미니 예제
데맹글된 이름 목록에서 다음을 발견했다고 하자.

```
main::{lambda(int)#1}::operator()(int) const
```

이는 `main` 함수 안에서 정의된 첫 번째 람다(`#1`)의 호출 연산자다. 이 함수를 열어보니:

```c
int FUN_00401530(Lambda1 *this, int param_1) {
    return param_1 ^ *(int *)(this + 0);
}
```

`this+0`을 읽어 XOR하는 것으로 보아, 이 람다는 `main`의 지역 변수 하나를 **참조 또는 값으로 캡처**해서 XOR 키로 사용하는 형태다(`[key](int x){ return x ^ key; }`에 해당). `main` 함수에서 이 클로저 객체(`Lambda1` 인스턴스)가 생성되는 지점을 찾아 `this+0`에 어떤 값이 들어가는지 역추적하면 실제 XOR 키 값을 알아낼 수 있다.

## 출처/검증
- C++ 람다가 이름 없는 클로저 클래스와 `operator()`로 컴파일된다는 것, 캡처 없는 람다의 함수 포인터 변환 가능성은 ISO C++ 표준(람다 표현식 섹션)에 정의된 내용이다.
- Itanium C++ ABI의 람다 클로저 타입 맹글링 규칙(`Ul<params>E_`, unnamed-type-name)은 Itanium C++ ABI 공식 명세(Lambda 관련 확장 섹션) 기준.
- MSVC의 `<lambda_...>` 합성 이름 표기는 Visual C++ 디버그 정보 및 데맹글 도구(`undname`)의 실제 출력 관례에 기반했다.
- `std::function`의 타입 소거 기반 간접 호출 구조는 C++ 표준 라이브러리(`<functional>`) 명세와 주요 구현체(libstdc++/MSVC STL)의 공개된 설계 원리 기준이다.
