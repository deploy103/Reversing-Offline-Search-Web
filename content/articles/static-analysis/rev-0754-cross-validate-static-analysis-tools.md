## 한 줄 요약
IDA/Ghidra/radare2/Cutter 같은 디컴파일러는 모두 "추정"을 통해 사람이 읽기 좋은 코드를 만들어내는 도구이므로, 애매하거나 결과에 따라 문제 풀이 방향이 갈리는 지점에서는 한 도구의 결과만 믿지 말고 최소 하나의 다른 도구(또는 원본 디스어셈블리)와 대조해 일치 여부를 확인하는 습관이 필요하다.

## 언제 검색해야 하나
- IDA의 F5(REV-0146) 결과와 Ghidra의 Decompile 결과(REV-0158)가 같은 함수인데 구조나 조건문이 다르게 보일 때
- 디컴파일 결과의 특정 조건문이나 캐스팅이 이상하게 느껴지는데, 이게 실제 프로그램 로직인지 디컴파일러의 오역(誤譯)인지 판단이 안 될 때
- 문제 풀이의 성패가 걸린 핵심 조건(예: 정확히 몇 바이트를 비교하는지, 부호 있는 비교인지)이 도구 하나의 결과에만 의존하고 있을 때

## 핵심 개념
디컴파일러는 기계어를 그대로 보여주는 것이 아니라, 기계어 패턴을 보고 "이건 아마 이런 C 코드였을 것이다"라고 **추론**해서 pseudocode를 생성한다. 이 추론 과정에서 다음과 같은 이유로 도구마다 다른 결과가 나올 수 있다.

- **타입 추론 알고리즘 차이**: 같은 레지스터 사용 패턴을 보고도 IDA는 `int`로, Ghidra는 `uint`로 다르게 추정할 수 있다. 부호 있는/없는 비교(`jl` vs `jb` 등, REV-0113~계열)가 결과에 영향을 준다.
- **최적화 컴파일러가 만든 비직관적 코드 패턴**: `-O2` 최적화가 들어간 코드는 루프 언롤링, 강도 감소(strength reduction) 같은 변환이 적용되어 원래 소스와 형태가 크게 달라져 있다. 디컴파일러가 이를 되돌리는 정도가 도구마다 다르다.
- **시그니처/타입 데이터베이스의 차이**: FLIRT(IDA)와 Function ID(Ghidra, REV-0646)는 서로 다른 시그니처 DB를 사용하므로, 같은 라이브러리 함수라도 한쪽만 이름이 붙고 다른 쪽은 `sub_`/`FUN_`로 남을 수 있다.
- **버그 또는 특정 명령어 지원 미비**: 드물지만 특정 확장 명령어(SIMD, 새로운 아키텍처 명령 등)를 한 도구가 잘못 해석하거나 아예 지원하지 않아 pseudocode가 깨지는 경우가 있다.

이런 이유로, **결과가 문제 풀이에 결정적인 영향을 주는 지점**(비교 조건, 반복 횟수, 부호 여부 등)에서는 반드시 교차검증이 필요하다. 반대로 흐름이 명확하고 중요도가 낮은 부분까지 매번 두 도구로 확인하는 것은 비효율적이다 — 교차검증은 "의심스러운 지점"에 선택적으로 적용하는 전략이다.

## 화면/코드에서 보이는 징후
- 같은 함수를 IDA와 Ghidra 양쪽에서 열어봤는데, 조건문의 개수나 비교 연산자(`==` vs `!=`, `<` vs `<=`)가 다르게 표시된다.
- pseudocode에 나온 상수 값이 실제 hex view(REV-0162)의 바이트와 자릿수나 부호가 안 맞아 보인다.
- 한 도구에서는 반복문(`for`)으로 보이는 코드가 다른 도구에서는 `goto`가 섞인 형태로 보인다.

## 가장 먼저 할 것
문제 풀이에 직접적인 영향을 주는 조건문/상수/비교 연산 하나를 정확히 짚어두고, 그 지점만 원본 디스어셈블리(어셈블리 명령어 자체)로 내려가 재확인한다. 디컴파일 pseudocode끼리 비교하기 전에, 항상 "실제 기계어가 뭐라고 하는지"가 최종 기준이라는 점을 먼저 정한다.

## 단계별 절차
1. 의심 지점의 pseudocode 한 줄(조건문, 상수 비교 등)을 정확히 기록한다.
2. 같은 위치의 **원본 디스어셈블리**를 확인한다(IDA는 View → Disassembly, Ghidra는 Listing 창, radare2는 `pdf`). 어떤 어셈블리 명령(`cmp`, `jl`, `jb`, `movzx`, `movsx` 등)이 쓰였는지 REV-0113 계열 명령어 사전과 대조한다.
3. 가능하면 다른 도구(IDA↔Ghidra, 또는 radare2 native↔Cutter의 Ghidra 플러그인, REV-0753)로 같은 위치를 열어 pseudocode를 나란히 비교한다.
4. 두 도구의 pseudocode가 다르더라도, 원본 어셈블리 명령어 자체는 하나로 고정되어 있으므로 그 명령어의 정확한 의미(부호 있는 비교인지, 몇 바이트 비교인지)를 기준으로 최종 판단한다.
5. 그래도 애매하다면 실제로 실행해서 확인한다 — GDB/x64dbg로 해당 지점에 브레이크포인트를 걸고 레지스터/플래그 값을 직접 관찰하는 동적 검증이 가장 확실한 최종 수단이다.
6. 검증이 끝난 조건은 REV-0161 방식으로 이름/주석을 남겨, 같은 지점을 다시 의심하며 시간을 낭비하지 않도록 한다.

## 명령어/단축키
| 확인 대상 | IDA | Ghidra | radare2/Cutter |
|---|---|---|---|
| pseudocode | F5 | Decompile 창 | `pdg`(플러그인 필요) / Cutter Decompiler 패널 |
| 원본 디스어셈블리 | View → Disassembly | Listing 창 | `pdf` |
| xref 확인 | `X` 키 | 우클릭 → Show References | `axt`(REV-0751) |
| 실제 실행 값 확인(동적) | 디버거 연결 후 브레이크포인트 | 디버거 연결 후 브레이크포인트 | GDB/pwndbg 연결 |

## 출력 해석
- 두 도구의 pseudocode가 논리적으로 동치(예: `if (a == b)`와 `if (!(a != b))`)라면 표현만 다를 뿐 실제 문제는 없는 것이다 — 이 경우는 교차검증에서 "합격"으로 처리하고 넘어간다.
- 원본 어셈블리에서 `jl`(signed less than)이 쓰였는데 어느 한쪽 pseudocode가 `<`가 아니라 부호 없는 비교처럼 표현되어 있다면, 그 도구의 타입 추론이 틀렸을 가능성이 있다 — 이 경우 어셈블리 명령어를 최종 근거로 삼는다.
- 도구마다 상수 표시 진법(10진수/16진수)이 달라 착시가 생기는 경우도 있다. 값 자체를 16진수로 통일해서 비교하면 이런 착오를 줄일 수 있다.

## 흔한 실수
- 첫 번째로 연 도구의 결과를 별다른 의심 없이 그대로 정답으로 받아들이는 것 — 특히 대회 시간이 촉박할 때 이런 실수가 잦다.
- pseudocode끼리만 비교하고 원본 어셈블리 확인을 생략하는 것 — pseudocode는 두 도구 모두 "추정"의 결과이므로, 최종 근거는 항상 기계어 명령어여야 한다.
- 사소한 표현 차이(변수명, 괄호 위치)까지 전부 문제 삼아 교차검증에 과도한 시간을 쓰는 것 — 문제 풀이에 영향을 주는 지점에만 선택적으로 적용해야 한다.
- 정적 분석 결과만으로 끝까지 논쟁하며 실제 실행(동적 검증)으로 넘어가지 않는 것 — 애매함이 오래 지속되면 GDB/x64dbg로 직접 값을 찍어보는 것이 가장 빠른 해결책일 때가 많다.

## 막혔을 때 다음 체크
- IDA/Ghidra 각각의 디컴파일 창 자체를 다루는 법이 헷갈리면 → REV-0146 IDA F5 디컴파일, REV-0158 Ghidra Decompiler 창 읽기
- Cutter에서 native/Ghidra 두 디컴파일러를 전환하며 비교하는 구체적 방법은 → REV-0753 Cutter에서 Ghidra 디컴파일러 연동 확인하기
- radare2로 xref까지 함께 확인하고 싶다면 → REV-0751 radare2로 함수 목록과 XREF 확인하기(afl, axt)
- 그래도 판단이 안 서면 동적 분석으로 전환 → 디버거 브레이크포인트로 실제 레지스터/플래그 값 확인(동적 분석 카테고리 참고)

## 미니 예제
IDA에서 `check(int len)` 함수의 조건문이 `if (len > 16)`으로 표시되었는데, Ghidra에서는 같은 함수가 `if (len >= 17)`로 표시되었다고 하자. 두 표현은 정수 비교에서 논리적으로 완전히 동치이므로(`len > 16`과 `len >= 17`은 정수 범위에서 같은 조건), 이 경우는 실제 버그가 아니라 단순한 표현 차이다. 반면 IDA는 `len > 16`인데 Ghidra는 `(uint)len > 16`처럼 부호 없는 비교로 표시된다면, 원본 어셈블리에서 `jg`(signed)가 쓰였는지 `ja`(unsigned)가 쓰였는지를 직접 확인해 어느 쪽이 맞는 해석인지 가려야 한다.

## 출처/검증
- 디컴파일러가 타입/구조를 "추정"으로 재구성한다는 일반 원리와, 컴파일러 최적화가 디컴파일 결과에 영향을 준다는 설명: Hex-Rays IDA 공식 문서 및 Ghidra 공식 문서(Decompiler 관련 topic) 공통 기술 기준.
- FLIRT/Function ID 등 시그니처 DB 차이로 인한 결과 불일치는 각 도구 공식 문서에서 설명하는 시그니처 매칭 한계를 기준으로 정리했다.
- 이 문서는 여러 CTF 리버싱 사례에서 반복적으로 보고되는 "도구 간 디컴파일 결과 불일치" 패턴을 일반화해 작성했으며, 특정 바이너리를 직접 재현해 검증하지는 않았다(2026-09-09 검증).
