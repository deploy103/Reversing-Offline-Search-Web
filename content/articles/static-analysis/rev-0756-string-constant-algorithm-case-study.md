## 한 줄 요약
CRC/MD5 같은 알고리즘이 숫자 매직 넘버로 정체를 드러낸다면(REV-0165), Base64·Hex·커스텀 인코딩 계열 알고리즘은 **알파벳/문자셋 자체가 문자열 형태로 바이너리에 그대로 박혀 있는 경우**가 많으므로, 그 문자열 하나만 알아봐도 전체 인코딩/디코딩 로직을 처음부터 분석하지 않고 바로 표준 라이브러리로 재현할 수 있다.

## 언제 검색해야 하나
- 문자열 목록에 사람이 읽는 메시지가 아니라, 알파벳과 숫자가 규칙적으로 나열된 긴 문자열(길이 16, 32, 64 등)이 보일 때
- 함수 안에서 배열 인덱싱으로 문자를 하나씩 골라내는 패턴이 보이는데, 그 배열의 내용이 무슨 의미인지 감이 안 잡힐 때
- 출력 메시지 문자열(REV-0163)이나 매직 넘버(REV-0165) 둘 다 안 보이는데, 대신 문자로 된 테이블만 눈에 띌 때

## 핵심 개념
많은 인코딩/해시/암호 알고리즘은 계산에 쓰이는 "문자 집합" 또는 "치환 테이블"을 사람이 읽을 수 있는 문자열 형태로 데이터 섹션에 그대로 저장해 둔다. 이런 문자열은 CRC의 매직 넘버처럼 숫자가 아니라 **텍스트 자체가 서명(signature)** 역할을 한다.

### 대표적인 식별 패턴

| 알고리즘/포맷 | 특징적인 문자열 | 길이 |
|---|---|---|
| Base64 표준 알파벳 | `ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/` | 64자 |
| Base64 URL-safe 변형 | 위와 동일하되 마지막 두 글자가 `-_` | 64자 |
| Base32 | `ABCDEFGHIJKLMNOPQRSTUVWXYZ234567` | 32자 |
| Hex 인코딩(소문자) | `0123456789abcdef` | 16자 |
| Hex 인코딩(대문자) | `0123456789ABCDEF` | 16자 |
| 커스텀 XOR 치환/시저(Caesar) 계열 | 알파벳 순서가 뒤섞인 26~62자 문자열(표준과 순서가 다름) | 다양 |

이 표에서 표준 Base64/Base32/Hex 알파벳과 **정확히 일치**하면, 그 함수는 해당 표준 인코딩을 그대로 구현한 것이라고 거의 확신할 수 있다. 반대로 알파벳 개수는 같은데(예: 64자) 순서가 표준과 다르다면, "표준 Base64를 커스텀 알파벳으로 바꾼 변형"일 가능성이 크다 — 이 경우 원래 알고리즘 구조(비트 분할 방식 등)는 표준과 같으므로, 알파벳 매핑 테이블만 새로 만들어 그대로 재현하면 된다.

### 문자열 자체를 못 찾을 때
컴파일러가 이 테이블을 문자열 리터럴이 아니라 `char` 배열의 개별 바이트 초기화 형태로 넣는 경우, `strings` 명령으로는 못 찾고 데이터 섹션을 Hex View(REV-0162)로 직접 훑어야 보일 수 있다. 이 경우도 연속된 바이트가 인쇄 가능한 ASCII 범위(`0x20`~`0x7E`)에 몰려 있다면 여전히 사람 눈으로 식별 가능하다.

## 화면/코드에서 보이는 징후
- 문자열 목록에 길이가 정확히 64, 32, 16처럼 딱 떨어지고, 알파벳 대소문자+숫자+기호가 섞인 문자열이 보인다.
- 디컴파일 결과에 이 문자열을 가리키는 포인터가 있고, 함수 안에서 6비트 또는 4비트 단위로 인덱스를 계산해 이 배열에서 문자를 하나씩 꺼내는 패턴(`table[(value >> shift) & mask]`)이 보인다.
- `strings` 결과에 사람이 읽을 메시지가 전혀 없고, 대신 이런 규칙적인 문자열만 눈에 띈다.

## 가장 먼저 할 것
길이가 특이하게 딱 떨어지는(16/32/64자) 문자열을 발견하면, 위 표와 글자 하나하나를 순서대로 비교한다. 표준 Base64 알파벳과 완전히 일치하는지, 아니면 개수만 같고 순서가 다른지부터 구분한다.

## 단계별 절차
1. `strings ./chall` 또는 IDA/Ghidra의 Strings 창, radare2의 `iz`로 전체 문자열 목록을 확인한다.
2. 길이가 16/32/64자 근처이고 사람이 읽는 문장이 아닌 문자열을 후보로 표시한다.
3. 후보 문자열을 표준 Base64/Base32/Hex 알파벳과 한 글자씩 대조한다. 완전히 일치하면 표준 인코딩으로 확정한다.
4. 개수는 같은데 순서가 다르면, 그 문자열 자체를 "커스텀 알파벳 테이블"로 기록해 둔다.
5. 이 문자열을 참조하는 함수를 xref(REV-0160, `axt`)로 찾아가 실제로 인덱싱에 쓰이는지 확인한다.
6. 인덱싱 로직에서 몇 비트 단위로 인덱스를 뽑는지 확인한다 — 6비트(0~63) 단위면 Base64류, 5비트(0~31)면 Base32류, 4비트(0~15)면 Hex류라는 것이 코드 구조로도 재확인된다.
7. 표준 알고리즘으로 확정되면 Python `base64` 모듈이나 표준 라이브러리로 바로 재현하고, 커스텀 알파벳이면 표준 구현에 알파벳 매핑만 교체해서 재현한다(REV-0168).

## 명령어/단축키
```bash
strings ./chall | awk 'length==64'
strings ./chall | awk 'length==32'
strings ./chall | awk 'length==16'
```
IDA: Shift+F12(Strings window)에서 Length 열 기준 정렬.
Ghidra: Window → Defined Strings에서 필터/정렬.
radare2: `iz~64` 또는 `izz~64`(문자열 필터).

## 출력 해석
- 문자열이 표준 Base64 알파벳과 정확히 일치하면 인덱싱 비트 폭(6비트)과 패딩 문자(`=`) 유무만 추가 확인하면 표준 `base64.b64encode`/`b64decode`로 완전히 대체 가능하다.
- 순서가 뒤섞인 64자 문자열이면 표준 Base64 알고리즘 골격에 "이 문자열을 알파벳 테이블로 쓰는 변형"이라는 결론을 내릴 수 있다 — Python에서 `str.translate`로 표준 Base64 결과를 이 알파벳으로 재매핑하는 방식이 가장 빠르다.
- 문자열 길이가 애매하게 딱 떨어지지 않는다면(예: 37자) 표준 알고리즘이 아니라 완전한 커스텀 알고리즘일 가능성이 높으므로, 이 전략보다 REV-0165/REV-0168의 일반적인 로직 재현 접근이 더 적합하다.

## 흔한 실수
- 문자열 길이가 얼추 비슷하다고(예: 62자와 64자) 대충 Base64로 단정하는 것 — 패딩 문자나 특수 문자 두 개(`+/` 또는 `-_`)가 빠지거나 다르면 표준과 다른 변형일 수 있으므로 글자 수까지 정확히 세야 한다.
- 알파벳 테이블 문자열만 확인하고 실제 인덱싱 로직(비트 분할 방식)은 확인하지 않아, 같은 문자셋을 참조하지만 전혀 다른 방식으로 쓰는 커스텀 알고리즘을 표준 Base64로 착각하는 것.
- 문자열이 `char` 배열 형태로 나뉘어 있어 `strings` 결과에 안 보이는데, 그냥 "이 알고리즘엔 이런 문자열이 없다"고 결론짓고 넘어가는 것 — Hex View로 데이터 섹션을 직접 확인해야 한다.
- 커스텀 알파벳을 발견하고도 표준 알고리즘 골격을 재사용할 생각을 못 하고 전체 로직을 처음부터 다시 구현하려 드는 것 — 알파벳 매핑만 바꾸는 것으로 충분한 경우가 많다.

## 막혔을 때 다음 체크
- 숫자 형태의 매직 넘버(CRC/MD5/SHA 초기값 등)를 이용한 식별법이 궁금하면 → REV-0165 상수 검색으로 알고리즘 찾기
- 이 문자열을 참조하는 함수 자체를 못 찾겠다면 → REV-0163 문자열에서 검증 함수로 이동하는 정적 분석
- Hex View로 데이터 섹션을 직접 확인하는 방법이 필요하면 → REV-0162 Hex View로 디컴파일 결과 검증하기
- 알고리즘을 확정한 뒤 실제 파이썬 코드로 옮기고 싶다면 → REV-0168 정적 분석 결과를 Python 의사코드로 옮기기

## 미니 예제
어떤 문제의 문자열 목록에서 다음 64자 문자열을 발견했다고 하자.
```
ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/
```
표준 Base64 알파벳과 글자 하나하나가 완전히 일치한다. 이 문자열을 xref로 따라가니 어떤 함수가 3바이트씩 읽어 6비트 단위로 이 배열을 인덱싱하는 구조였다. 이 시점에서 함수 내부 로직을 한 줄씩 다 이해할 필요 없이 "표준 Base64 인코더"라는 결론을 내리고, Python에서는 `base64.b64encode(data).decode()` 한 줄로 동일한 결과를 재현할 수 있다. 만약 이 문자열의 마지막 두 글자가 `+/`가 아니라 `!@`처럼 다른 문자였다면, 표준 `base64` 모듈 결과에 `str.maketrans`로 마지막 두 문자만 교체하는 방식으로 커스텀 변형까지 재현할 수 있다.

## 관련 글
- REV-0165 — 상수 검색으로 알고리즘 찾기
- REV-0163 — 문자열에서 검증 함수로 이동하는 정적 분석
- REV-0162 — Hex View로 디컴파일 결과 검증하기
- REV-0168 — 정적 분석 결과를 Python 의사코드로 옮기기

## 출처/검증
- Base64/Base32 표준 알파벳: RFC 4648(The Base16, Base32, and Base64 Data Encodings) 명세 기준.
- Hex 인코딩 문자셋(`0-9a-f`, `0-9A-F`)은 일반적으로 통용되는 16진수 표기 규약 기준.
- 문자열 테이블을 이용한 알고리즘 식별 사례는 다수의 공개 CTF 리버싱 writeup에서 반복적으로 관찰되는 패턴을 일반화해 정리했으며, 특정 문제를 그대로 재현 검증한 것은 아니다(2026-09-09 검증).
