## 한 줄 요약
`Y`로 타입을 지정한 직후부터 디컴파일 결과가 이상해졌다면, 원인을 헤매기 전에 **가장 최근에 지정한 타입을 되돌려서(Undo) 정말 그 조작이 원인이었는지부터 확정**하는 것이 먼저이며, 확정되면 그 다음은 증상 종류(인자 개수/반환 타입/구조체 오프셋 중 무엇이 꼬였는지)에 따라 각각의 전용 심화 문서로 넘어가는 것이 가장 빠르다.

## 언제 검색해야 하나
- 함수 원형이나 구조체를 `Y`로 지정한 직후부터 Pseudocode가 이전보다 이상해졌는데, 정말 방금 한 조작 때문인지 확신이 안 설 때
- 구조체 타입 하나를 지정했는데 그 구조체를 쓰는 **다른 함수들**까지 줄줄이 이상해져서 어디서부터 손대야 할지 막막할 때
- 이미 `Reanalyze function`을 눌러버려서 되돌릴 수 없는 건 아닌지 불안할 때
- 앞으로 타입을 지정하기 전에 미리 검증해서 이런 상황 자체를 줄이고 싶을 때

## 핵심 개념
Hex-Rays 디컴파일러는 사용자가 `Y`로 명시적인 타입/원형을 지정하면 **그 정보를 절대적으로 신뢰**하고 그에 맞춰 마이크로코드를 재구성한다. 즉 방금 지정한 타입이 실제 동작과 다르면 결과가 이상해지는 것은 디컴파일러의 오류가 아니라 "사용자가 준 잘못된 정보를 성실하게 반영한 결과"다. 이 글은 개별 원인(인자 개수, 반환 타입, 구조체 오프셋)을 깊이 파고들기보다, **"방금 한 행동이 진짜 원인이 맞는지 확인하고, 안전하게 되돌리고, 올바른 다음 문서로 갈아타는" 절차 자체**에 집중한다. 세부 원인별 진단 방법은 이미 별도 문서로 정리되어 있다.

- **인자 개수/타입을 잘못 지정한 경우** → REV-0795(함수 인자 개수를 디컴파일러가 잘못 추론했을 때)에서 다루는 것과 같은 증상(가짜 `a2`, `a3` 변수, 사라진 인자)이 나타난다.
- **반환 타입을 잘못 지정한 경우** → REV-0796(반환 타입을 디컴파일러가 잘못 추론했을 때)과 같은 증상(있지도 않은 반환값 사용 코드, 반대로 무시됨)이 나타난다.
- **구조체 크기/오프셋을 잘못 지정한 경우** → REV-0797(구조체 크기를 잘못 추정해서 오프셋이 꼬일 때)과 같은 증상(`field_18`이 범위 밖으로 나가거나 서로 다른 필드가 겹쳐 보임)이 나타난다.

여기서 중요한 차이는, 저 세 문서는 **디컴파일러가 스스로 추론했다가 자동으로 틀린 경우**까지 포함해서 다루지만, 이 글은 **"방금 내가 직접 Y로 지정한 조작이 범인인지 아닌지조차 불확실한 상황"**을 정리하는 진단 절차라는 점이다. 특히 구조체처럼 **여러 함수가 공유하는 타입**을 잘못 지정하면, 그 타입을 참조하는 모든 함수가 동시에 영향을 받으므로 피해 범위를 파악하는 것 자체가 별도의 작업이 된다.

## 화면/코드에서 보이는 징후
- 타입을 지정한 함수 하나만 이상해진 게 아니라, 같은 구조체/타입을 쓰는 것으로 보이는 다른 함수들도 동시에 이상한 변수/필드 접근을 보이기 시작함.
- Pseudocode 창을 오가며 "이게 방금 내가 만든 문제인지, 원래 있던 문제인지" 스스로도 헷갈리는 상태.
- `Ctrl+Z`를 누르면 되돌아갈 것 같긴 한데, 이미 여러 단계(타입 지정 → Reanalyze → 이름 변경)를 거쳐서 정확히 몇 번 되돌려야 할지 불확실함.

## 가장 먼저 할 것
지금 열려 있는 함수에서 `Ctrl+Z`를 눌러 가장 최근 조작부터 하나씩 되돌리면서, 어느 시점에 결과가 "정상으로 보이는 상태"로 돌아오는지 확인한다. 이 한 단계만으로도 원인이 방금 한 타입 지정인지 아닌지가 바로 갈린다.

## 단계별 절차
1. 문제가 생긴 함수에서 `Ctrl+Z`를 눌러 한 단계씩 되돌린다. 되돌릴 때마다 Pseudocode를 확인해 "이상한 변수/필드"가 사라지는 시점을 찾는다.
2. 되돌렸을 때 정상으로 보인다면, 방금 지정한 타입이 원인이라는 것이 확정된 것이다. 이제 증상을 구체적으로 분류한다.
   - 인자 개수/타입이 문제였다면 → REV-0795의 절차대로 실제 호출부에서 레지스터/스택을 직접 세어 정확한 원형을 다시 만든다.
   - 반환값 사용 여부가 이상하다면 → REV-0796의 절차대로 호출자 쪽에서 `eax`/`rax`를 실제로 읽는지부터 확인한다.
   - 구조체 필드 접근이 이상하다면 → REV-0797의 절차대로 그 포인터에 대한 모든 오프셋 접근을 xref로 모아 실제 크기를 재구성한다.
3. 문제의 타입이 **여러 함수가 공유하는 구조체/타입**이었다면, 그 타입을 쓰는 다른 함수 목록부터 먼저 파악한다. Local Types 창(`Shift+F1`)에서 해당 구조체를 찾아 관련 정보를 확인하고, 그 타입으로 지정된 변수를 가진 함수들을 하나씩 열어 피해 범위를 확인한 뒤, REV-0797의 절차로 구조체를 다시 정의하고 나서 영향받은 함수들을 순서대로 `Reanalyze function` 한다.
4. 이미 `Reanalyze function`을 여러 번 눌러서 Undo 이력이 애매해졌다면, 최후의 수단으로 그 함수의 타입을 `Y`에서 지우고(원형을 기본/미지정 상태로) 처음부터 다시 자동 추론을 시켜본 뒤, 자동 추론 결과와 지금 결과를 비교해서 무엇이 달라졌는지 확인한다.
5. 다음번에 같은 상황을 줄이려면, 타입을 지정하기 전에 먼저 대상 함수를 호출하는 지점을 `X`로 찾아 실제 인자 개수/레지스터를 눈으로 확인하고, 구조체는 그 포인터에 대한 모든 접근 오프셋을 미리 나열해본 뒤 지정하는 "먼저 확인, 나중에 지정" 습관을 들인다.

## 명령어/단축키
- `Ctrl+Z` : 실행 취소(원인 확정용 진단 도구로 활용)
- `Y` : 타입/원형 재지정
- `Shift+F1` : Local Types 창(공유 구조체의 영향 범위 확인)
- `X` : 실제 호출부로 이동해 인자/반환값 사용 여부 확인
- 함수 시작 주소 우클릭 → `Reanalyze function`

## 출력 해석
- `Ctrl+Z`로 되돌렸을 때 문제가 사라진다면 원인이 확정된 것이므로, 이제 증상별 전용 문서(REV-0795/0796/0797)로 넘어가면 된다.
- 되돌려도 문제가 그대로라면, 원인은 방금 한 타입 지정이 아니라 다른 곳(예: 원래부터 있던 자동 추론 오류)에 있다는 뜻이므로 REV-0795/0796/0797을 먼저 훑어 자동 추론 오류 패턴과 비교해본다.
- 여러 함수가 동시에 이상해졌다면 공유 타입(구조체) 문제일 가능성이 매우 높다 — 함수 하나만 고치고 끝내면 나머지 함수에서 같은 문제가 재발한다.

## 흔한 실수
- 방금 한 조작이 원인인지 확인도 안 하고 곧바로 REV-0795/0796/0797의 세부 절차부터 따라 하다가 엉뚱한 곳을 고치는 것 — 먼저 Undo로 원인부터 확정해야 한다.
- 공유 구조체를 고쳤는데 그 구조체를 쓰는 다른 함수들을 재확인하지 않고 "이 함수 하나만 고치면 끝"이라고 생각하는 것.
- Undo 이력이 꼬였다고 포기하고 타입을 아예 기본 상태로 초기화하지 않은 채 계속 새로운 타입을 덧씌우며 문제를 키우는 것.
- 타입을 지정하기 전에 실제 호출부/오프셋을 확인하는 습관 없이 "일단 지정해보고 이상하면 그때 고치자"는 식으로 반복 시행착오만 하는 것.

## 막혔을 때 다음 체크
- 인자 개수/원형 자체가 문제라면 → REV-0795 함수 인자 개수를 디컴파일러가 잘못 추론했을 때
- 반환 타입이 문제라면 → REV-0796 반환 타입을 디컴파일러가 잘못 추론했을 때
- 구조체 오프셋이 문제라면 → REV-0797 구조체 크기를 잘못 추정해서 오프셋이 꼬일 때
- 타입 지정 기본 사용법이 헷갈린다면 → REV-0148 IDA Y로 타입 지정하기

## 미니 예제
공용 구조체 `PACKET`을 하나 정의해서 여러 함수의 인자 타입으로 지정했는데, 그중 `parse_header` 함수의 Pseudocode가 갑자기 이상해진 상황.

```text
1. parse_header에서 Ctrl+Z를 눌러 되돌려보니 PACKET 타입을 씌우기 전 상태에서는 정상적으로 보임 → 방금 한 구조체 지정이 원인으로 확정
2. Shift+F1(Local Types)에서 PACKET을 참조하는 다른 함수를 확인 → parse_body, parse_footer도 같은 구조체를 씀
3. parse_body를 열어보니 마찬가지로 필드 접근이 이상함을 확인(피해 범위가 이 구조체를 쓰는 함수 전체임을 확인)
4. REV-0797 절차대로 PACKET을 쓰는 모든 함수에서 오프셋 접근을 xref로 모아 실제 필드 크기를 재구성
5. PACKET 정의를 수정한 뒤 parse_header, parse_body, parse_footer를 순서대로 Reanalyze function
```

## 관련 글
- REV-0795 — 함수 인자 개수를 디컴파일러가 잘못 추론했을 때
- REV-0796 — 반환 타입을 디컴파일러가 잘못 추론했을 때
- REV-0797 — 구조체 크기를 잘못 추정해서 오프셋이 꼬일 때
- REV-0148 — IDA Y로 타입 지정하기

## 출처/검증
- Hex-Rays 디컴파일러가 사용자가 지정한 타입/원형을 그대로 신뢰하여 마이크로코드를 재구성한다는 동작 방식: Hex-Rays 공식 사용자 가이드 "Type information" 및 "Function signature" 섹션 기준.
- Local Types(공유 타입 라이브러리)가 여러 함수에 동시에 영향을 준다는 구조: Hex-Rays 공식 문서 "Local types" 섹션 기준.
