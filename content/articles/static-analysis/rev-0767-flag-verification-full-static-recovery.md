## 한 줄 요약
이 카테고리(`static-analysis`)에서 지금까지 다룬 개별 기법들(부트스트랩 걸러내기, 문자열/Import/상수 단서, Call Graph 좁히기, C++ 클래스/람다 해석, 스위치문 정리)을 실행 없이 처음부터 끝까지 순서대로 이어 붙이면, 대상 아키텍처를 실행할 수 없는 환경(오프라인, 아키텍처 불일치, 강력한 안티디버깅)에서도 Flag 검증 로직 전체를 복원하고 Python으로 정답을 계산해낼 수 있다.

## 언제 검색해야 하나
- 채점 서버 전용 아키텍처라 로컬에서 실행이 안 되거나, 에뮬레이터/디버거 설정이 오프라인 환경에서 여의치 않을 때
- 강력한 안티디버깅이 걸려 있어 동적 분석 시도 자체가 시간 낭비로 보일 때
- 지금까지 REV-0142~REV-0168, REV-0761~0766, REV-0769로 배운 개별 기법은 있는데, 실제 문제를 앞에 두고 "어떤 순서로 적용해야 하는지"가 헷갈릴 때
- 정적 분석 결과를 최종적으로 Python 스크립트 하나로 정리해서 Flag를 계산해내고 싶을 때

## 핵심 개념
이 문서는 새로운 기법을 소개하기보다, **이미 존재하는 정적 분석 기법들을 실전에서 적용하는 순서(파이프라인)**를 정리한 것이다. 전체 절차는 크게 5단계로 구성된다.

**1단계 — 트리아지 및 부트스트랩 제거**
파일 형식(PE/ELF), 아키텍처, 정적/동적 링킹, strip 여부를 확인하고, 진입점부터 `main`까지의 컴파일러 부트스트랩 체인(REV-0167)과 함수 내부에 흩어진 가드 함수(REV-0762)를 걸러내는 기준을 먼저 세운다. 이 단계를 건너뛰면 이후 모든 단계에서 무관한 코드를 계속 다시 걸러내야 하므로 시간이 배로 든다.

**2단계 — 검증 함수 후보 좁히기**
문자열(REV-0163), Import 함수(REV-0161/0164, REV-0761), 상수(REV-0165), Call Graph(REV-0166)를 교차 활용해 "이 함수가 입력을 받아 참/거짓을 반환하는 검증 로직"이라는 후보를 좁힌다. 후보가 하나로 좁혀지지 않으면, 각 후보에 "입력 → 출력" 한 줄 요약을 붙여 여러 개를 동시에 추적 대상으로 남겨둔다.

**3단계 — C++/객체지향 구조 해석 (해당하는 경우)**
바이너리가 C++로 작성되었다면 REV-0763(이름 맹글링)→REV-0764(클래스 구조)→REV-0765(상속)→REV-0766(람다) 순서로 클래스 계층을 복원한다. 이 순서를 지켜야 하는 이유는, 이름을 해석하지 않고는 클래스를 묶을 수 없고, 클래스 필드를 모르고는 상속 관계의 vtable 비교가 무의미하기 때문이다. C로 작성된 바이너리라면 이 단계는 생략한다.

**4단계 — 제어 흐름 정리**
검증 로직 안에 큰 스위치문(가상 머신 형태의 opcode 디스패치 등)이 있다면 REV-0769 방식으로 표로 정리하고, 여러 함수에 걸쳐 로직이 흩어져 있다면 REV-0770 방식으로 흐름 노트를 작성해 "전체 그림"을 하나의 문서로 통합한다. 이 단계가 끝나면 "입력 바이트가 어떤 순서로 어떤 변환을 거쳐 최종 비교에 도달하는지"를 처음부터 끝까지 말로 설명할 수 있어야 한다.

**5단계 — Python 의사코드 재현 및 역산**
REV-0168(정적 분석 결과를 Python 의사코드로 옮기기) 방식으로 지금까지 정리한 흐름을 Python 함수로 그대로 옮긴다. 이때 두 가지 경로가 있다.
- **순방향 재현**: 알고리즘을 그대로 옮겨 여러 입력 후보를 대입해 보며 검증(브루트포스가 가능한 짧은 입력일 때 유효).
- **역방향 계산**: XOR/덧셈처럼 가역 연산으로만 이루어진 변환이면, 목표 값(비교 대상 상수/파일)에서 역연산을 적용해 입력을 직접 계산(브루트포스보다 훨씬 빠르고 확실함).

어떤 경로를 택할지는 3단계에서 파악한 연산의 가역성에 달려 있으므로, 4단계에서 흐름을 정리할 때 각 연산이 가역인지(XOR, 덧셈/뺄셈, 비트 회전) 비가역인지(해시 함수, 곱셈 후 오버플로 버림)를 함께 표시해두면 이 단계가 훨씬 수월해진다.

## 화면/코드에서 보이는 징후
- 실행 파일의 아키텍처가 로컬 환경과 다르거나(예: ARM 바이너리인데 x64 환경만 있음), 배포된 파일에 실행에 필요한 라이브러리/환경이 빠져 있다.
- 안티디버깅 체크(`ptrace`, `IsDebuggerPresent`, 타이밍 체크)가 여러 겹으로 걸려 있어 동적 분석 셋업에 드는 시간이 정적 분석보다 오래 걸릴 것으로 예상된다.
- 검증 로직이 XOR/덧셈/시프트처럼 가역 연산 위주로 구성되어 있어, 실행해서 값을 관찰하기보다 수식으로 직접 역산하는 편이 더 빠르다.

## 가장 먼저 할 것
전체 절차를 시작하기 전에, REV-0770 방식의 빈 노트 파일을 하나 만들어두고 각 단계에서 알아낸 사실(함수 주소, 이름, 역할, 입출력)을 그 자리에서 바로바로 기록한다. 정적 분석은 여러 함수를 오가며 진행되므로, 기록 없이 머리로만 추적하면 중간에 맥락을 잃기 쉽다.

## 단계별 절차
1. 트리아지: `file`/`checksec`(ELF) 또는 PE 헤더 확인(REV-0524 계열), strip 여부 확인.
2. 부트스트랩/가드 함수 제거 기준 확립: REV-0167, REV-0762.
3. 검증 함수 후보 탐색: REV-0163(문자열) → REV-0164/REV-0761(Import) → REV-0165(상수) → REV-0166(Call Graph).
4. C++ 구조 해석(해당 시): REV-0763 → REV-0764 → REV-0765 → REV-0766.
5. 제어 흐름 정리: 스위치문은 REV-0769, 여러 함수에 걸친 흐름은 REV-0770.
6. 변수/타입 정리: REV-0147/REV-0161(이름 변경), REV-0148(타입 지정), REV-0162(Hex View 검증).
7. Python 의사코드 작성: REV-0168.
8. 각 연산의 가역성 판단 후 순방향 재현 또는 역방향 계산 선택, 오프라인 환경에서 Python으로 최종 값 계산.
9. 계산된 값을 원래 바이너리의 예상 입력 형식(문자열 인코딩, 구분자, 대소문자)에 맞춰 최종 Flag 형태로 정리.

## 명령어/단축키
이 문서 자체는 새 단축키를 소개하지 않으며, 앞서 언급한 각 REV 문서의 명령어/단축키 섹션을 순서대로 참고한다. 전체 절차를 관통하는 습관으로는 다음이 유용하다.
- IDA/Ghidra에서 분석 중인 데이터베이스(.i64/.gpr)를 각 단계가 끝날 때마다 저장(`Ctrl+S` 계열)해 중간 상태를 잃지 않도록 한다.
- Python 재현 스크립트는 처음부터 별도 `.py` 파일로 작성해, 정적 분석 중 새로운 사실을 알게 될 때마다 바로 업데이트한다.

## 출력 해석
- Python으로 재현한 알고리즘의 출력이 바이너리 안의 목표 상수/파일 내용과 일치하면, 정적 분석 결과가 정확했다는 강력한 증거다.
- 일치하지 않는다면, 십중팔구 (1) 어떤 단계에서 컴파일러 생성 코드(REV-0762)를 실제 로직으로 착각했거나, (2) 연산 순서(특히 반복문의 방향, 인덱스 증감 방향)를 반대로 옮겼거나, (3) 엔디안/부호 확장을 놓친 경우다.
- 부분적으로만 일치한다면(예: Flag 앞부분만 맞음), 검증 로직이 문자 단위로 순차 비교되는 구조일 가능성이 크므로 그 지점부터 다시 REV-0163/0165로 되짚어간다.

## 흔한 실수
- 5단계(Python 재현)로 성급히 넘어가서 실제로는 다 이해하지 못한 함수까지 대충 추측으로 코드를 옮기는 것 — 반드시 3~4단계에서 "이 함수가 무엇을 하는지 한 문장으로 설명 가능한" 상태를 만든 뒤에 옮겨야 한다.
- 동적 분석이 아예 불가능하다고 오해하고 지레 포기하는 것 — 이 문서는 "동적 분석이 여의치 않을 때의 대안 경로"를 위한 것이지, 동적 분석이 항상 불가능하다는 뜻은 아니다. 가능하다면 정적 분석 결과를 짧게라도 동적으로 교차 검증하는 것이 가장 안전하다.
- 가역 연산과 비가역 연산을 구분하지 않고 무조건 브루트포스부터 시도하는 것 — 입력 길이가 길면 브루트포스가 현실적으로 불가능하므로, 먼저 연산의 가역성을 판단하는 습관이 훨씬 효율적이다.
- 노트(REV-0770) 없이 진행하다가 중간에 어떤 함수가 무엇이었는지 잊어버려서 처음부터 다시 분석하는 것.

## 막혔을 때 다음 체크
- 부트스트랩/가드 함수 걸러내기가 아직 익숙하지 않다면 → REV-0167, REV-0762
- 검증 함수 자체를 못 찾겠다면 → REV-0163, REV-0164, REV-0165, REV-0166
- C++ 바이너리라 클래스/상속/람다 해석이 막혔다면 → REV-0763, REV-0764, REV-0765, REV-0766
- 큰 스위치문(가상 머신 형태)이 나와서 손으로 다 못 읽겠다면 → REV-0769
- 여러 함수에 걸친 로직을 정리하는 노트 형식이 필요하다면 → REV-0770
- Python으로 옮기는 구체적 방법이 필요하다면 → REV-0168

## 미니 예제
어떤 Linux ELF crackme가 CTF 채점 서버 전용 아키텍처(예: MIPS)로 빌드되어 로컬에서 실행할 수 없다고 하자. 이 경우 다음 순서로 진행한다.

1. `file ./chall`로 아키텍처와 링킹 방식 확인, `readelf -h`로 헤더 재확인.
2. 진입점부터 `main`까지 REV-0167 방식으로 부트스트랩을 걸러내고, `main` 안에서 REV-0762의 가드 함수 패턴을 제외한다.
3. `main`이 문자열 입력을 받아 `check(char *input)`을 호출하는 구조를 REV-0163/0166으로 확인.
4. `check` 내부가 `for` 반복문으로 각 문자를 `key[i]`와 XOR한 뒤 결과 배열과 비교하는 구조임을 REV-0165(상수: `key` 배열 값)로 확인.
5. XOR은 가역 연산이므로, 목표 비교 배열 값과 `key` 배열 값을 REV-0168 방식으로 Python에 그대로 옮기고 `flag[i] = target[i] ^ key[i]`로 직접 역산.
6. 실행 파일을 단 한 번도 실행하지 않고 Flag 전체를 계산.

## 관련 글
- REV-0167 — Compiler Generated Code와 실제 문제 로직 구분
- REV-0762 — 컴파일러가 생성한 헬퍼 함수(__security_check_cookie 등) 걸러내기
- REV-0166 — 함수 Call Graph로 핵심 로직 좁히기
- REV-0168 — 정적 분석 결과를 Python 의사코드로 옮기기
- REV-0769 — 큰 스위치문을 정적분석에서 표로 정리하는 법
- REV-0770 — 여러 함수에 걸친 로직을 하나의 흐름으로 정리하는 노트 작성법

## 출처/검증
- 이 문서는 이 저장소의 `static-analysis` 카테고리 내 개별 REV 문서들(REV-0142~REV-0168, REV-0761~0770)에서 이미 개별적으로 검증된 기법을 조합한 종합 워크플로우이며, 별도의 외부 1차 출처보다는 CTF/리버스 엔지니어링 커뮤니티에서 널리 통용되는 "정적 전용 분석" 방법론(문자열/Import/상수 기반 탐색 → 흐름 정리 → 스크립트 재현)을 기준으로 정리했다.
- 가역 연산(XOR, 덧셈/뺄셈, 회전)을 이용한 역방향 계산 접근은 CTF reverse 카테고리에서 일반적으로 통용되는 풀이 전략이다.
