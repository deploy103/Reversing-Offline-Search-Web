## 한 줄 요약
컴파일러 최적화(`-O2` 이상)는 짧고 자주 불리는 함수를 CALL/RET 오버헤드 없이 호출부 코드 안에 그대로 복사해 넣는 **인라이닝(inlining)**을 적용하며, 이 경우 그 헬퍼 함수는 아예 독립된 함수로 존재하지 않고(심볼도, CALL도 없음) 여러 호출부에 똑같거나 비슷한 코드 블록이 반복되어 나타나므로, "이 로직을 처리하는 함수를 찾자"는 접근 대신 반복되는 코드 패턴 자체를 식별해서 그 부분만 별도 로직으로 이해하는 방식으로 전환해야 한다 — 이는 REV-0154(함수 경계가 잘못 잡힘)와 달리 애초에 그 경계가 "존재하지 않는" 경우다.

## 언제 검색해야 하나
- 서로 다른 두 함수의 pseudocode 안에서 거의 동일한 코드 블록(예: 문자열 길이 계산, 간단한 체크섬 계산)이 CALL 없이 반복해서 나타날 때
- 소스에 분명히 있을 법한 짧은 헬퍼 함수(`is_valid_char`, `min`, `clamp` 등)의 이름이 Functions 창 어디에도 없을 때
- FLIRT/FunctionID로 라이브러리 함수를 찾으려 했는데(REV-0804) 매칭이 실패하는 이유가 애초에 그 함수가 통째로 인라인되어 독립된 코드 블록 자체가 없기 때문일 때
- 함수 경계 문제(REV-0154)의 해결 절차를 다 시도했는데도 "잘라낼 CALL도, 나눌 지점도" 안 보일 때

## 핵심 개념
컴파일러가 함수를 인라인하면, 그 함수의 코드(명령어들)는 호출자의 코드 흐름 안으로 그대로 복사되고, 원래의 CALL/RET 쌍은 사라진다. 이는 REV-0154에서 다루는 "함수 경계가 잘못 잡힌 것"과는 근본적으로 다르다 — 그쪽은 실제 함수 시작/끝이 존재하는데 디스어셈블러가 그 위치를 잘못 판단한 경우이고, 인라이닝은 **애초에 독립된 함수 경계 자체가 바이너리에 존재하지 않는** 경우다. 즉 "잘못 잡힌 경계를 바로잡는 것"이 아니라 "원래 없는 경계를 억지로 만들려고 하면 안 되는 것"이다.

인라이닝이 자주 일어나는 조건:
- 함수 본문이 매우 짧을 때(몇 줄 이내)
- 컴파일러가 자주 호출되는 함수라고 판단했을 때(핫패스 최적화)
- `static inline`으로 선언되었거나 헤더에 정의된 짧은 함수(C++ 클래스의 getter/setter, 연산자 오버로드 등)
- 링크 타임 최적화(LTO)가 켜져 있어 여러 파일에 걸친 인라이닝까지 가능한 경우(REV-0800과 연관)

인라인된 코드는 원래 함수 하나였다는 흔적(반복되는 명령어 시퀀스)은 남아 있지만, 심볼도 CALL도 없으므로 IDA/Ghidra의 Functions 창에는 절대 별도 항목으로 나타나지 않는다. FLIRT 시그니처도 "이 위치에서 이 크기만큼의 코드가 시작해서 끝난다"는 함수 단위 매칭을 전제로 하므로, 함수 경계 자체가 없는 인라인 코드에는 적용되지 않는다(REV-0804).

## 화면/코드에서 보이는 징후
- 서로 무관해 보이는 두 함수의 pseudocode 앞부분(또는 특정 구간)이 변수 이름만 다르고 로직 구조가 완전히 동일함
- 짧은 루프(예: 널 종료 문자열 길이를 세는 `while(*p) p++, len++;` 패턴)가 CALL 없이 여러 곳에 그대로 등장함
- 그 코드 블록 근처에 진입/탈출을 알리는 프롤로그/에필로그(스택 프레임 셋업)가 없음 — 인라인된 코드는 호출자의 스택 프레임을 그대로 씀

## 가장 먼저 할 것
반복되는 것으로 의심되는 코드 블록을 2~3곳에서 나란히 비교해서, 정말 동일한 로직인지(변수 이름/오프셋만 다를 뿐 명령어 구조가 같은지) 확인한다.

## 단계별 절차

**1) 반복 패턴 확인**
의심되는 코드 블록을 서로 다른 함수에서 최소 2곳 이상 찾아 나란히 놓고 비교한다. 명령어 종류와 순서, 분기 구조가 같다면 인라인된 동일 헬퍼 함수일 가능성이 높다.

**2) CALL/RET 유무로 인라이닝 여부 확정**
그 블록 진입/탈출 지점에 CALL이 없고, 그 블록 실행 전후로 스택 프레임이 별도로 생성되지 않는다면(호출자의 로컬 변수 영역을 그대로 공유한다면) 인라인된 것이 확실하다. CALL이 있다면 이는 REV-0154(함수 경계 문제) 쪽이지 인라이닝이 아니다.

**3) 억지로 함수로 분리하지 않기**
인라인된 코드는 실제로 독립된 함수가 아니므로, 무리하게 `P`(Create function)로 별도 함수를 만들려고 하면 오히려 스택 프레임 분석이 꼬인다. 대신 그 코드 블록 전체를 주석이나 그룹으로 묶어 "이 부분은 strlen 계산에 해당함"처럼 표시만 해둔다.

**4) 알려진 라이브러리 함수 패턴과 대조**
`strlen`, `memcpy`, `strcmp` 같은 흔한 함수는 컴파일러별로 잘 알려진 인라인 코드 패턴(이 저장소의 REV-0449 strlen 인라인 패턴 등)이 있다. 이런 패턴 목록과 대조하면 "이 블록이 사실은 strlen이다"처럼 정체를 빠르게 특정할 수 있다.

**5) 반복되는 각 위치에 동일한 주석/이름 규칙 적용**
같은 헬퍼가 여러 곳에 인라인되어 있다면, 각 위치에 일관된 주석("inlined: is_printable_char")을 남겨 다음에 다시 분석하지 않도록 한다.

**6) 함수 경계 문제와 계속 헷갈리면**
REV-0154의 진단 절차(진짜 경계 오류 vs 정상 구조 구분)를 먼저 다시 밟아, 이게 "잘못 잡힌 경계"가 아니라 "원래 없는 경계"임을 확정한다.

## 명령어/단축키
- 코드 비교: 두 pseudocode 창을 나란히 띄우고(Windows → New window) 수동 비교
- IDA: 우클릭 → Add comment 로 인라인 블록에 주석 남기기
- Ghidra: Function Comparison 창(Window → Function Comparison, 버전에 따라 위치 다름)으로 두 코드 블록의 유사도 시각적 비교

## 출력 해석
- 두 블록이 명령어 순서까지 완전히 동일하면 확실한 인라이닝이고, 일부만 비슷하면 컴파일러가 우연히 비슷한 코드를 생성한 것일 수 있으니 신중히 판단한다.
- FLIRT를 적용했는데도 흔한 라이브러리 함수 이름이 하나도 안 붙는다면, strip이 아니라 애초에 통째로 인라인되어 함수 단위 매칭 대상 자체가 없는 경우일 수 있다.

## 흔한 실수
- 인라인된 코드를 억지로 별도 함수로 쪼개려다 스택 프레임 분석을 망가뜨리는 것.
- 반복되는 코드 블록을 각각 독립적인 로직으로 착각해서 매번 처음부터 다시 분석하는 것 — 한 번 정체를 파악하면 나머지는 "같은 패턴"이라고 표시만 하면 된다.
- REV-0154(함수 경계 오류)와 이 문제를 혼동해서 "함수를 재생성"하는 절차만 반복 시도하는 것.
- 짧은 코드 블록이라고 무시하고 넘어갔다가, 사실 그 안에 핵심 검증 로직(인라인된 비교 함수)이 들어있는 것을 놓치는 것.

## 막혔을 때 다음 체크
- 실제로 함수 경계가 잘못 잡힌 것인지 먼저 구분하고 싶다면 → REV-0154
- 여러 컴파일 단위가 합쳐지는 LTO 환경이라 인라이닝 범위가 더 넓다면 → REV-0800
- FLIRT 매칭이 안 되는 이유가 이것 때문인지 확인하려면 → REV-0804
- strlen 인라인 패턴 같은 구체적 예시가 필요하면 → REV-0449

## 미니 예제
`check_flag`와 `check_password`라는 이름 있는 두 함수의 pseudocode 앞부분에, `for (i = 0; s[i]; i++);` 형태의 동일한 루프가 변수 이름만 다르게(`s`/`i` 대신 `buf`/`idx`) 반복되어 나온다고 하자. 두 함수 어디에도 `strlen` 호출은 없다. 이는 `strlen`이 컴파일러에 의해 두 곳 모두에 인라인되었기 때문이다. 이 경우 별도로 `strlen` 함수를 찾으려 하지 말고, 그 루프 블록에 "inlined strlen"이라는 주석만 남기고 각 함수의 나머지 진짜 로직(플래그 검증 부분)에 집중한다.

## 관련 글
- REV-0154 — IDA에서 함수 경계가 잘못 잡혔을 때
- REV-0800 — 여러 컴파일 단위가 하나로 합쳐져 함수가 너무 많을 때(LTO)
- REV-0804 — FLIRT 시그니처가 안 맞아서 라이브러리 함수를 놓칠 때
- REV-0449 — strlen이 인라인 최적화되는 패턴

## 출처/검증
- 함수 인라이닝(inline expansion)이 컴파일러 최적화 단계에서 CALL/RET 오버헤드를 제거하기 위해 적용된다는 것은 GCC/Clang/MSVC 공식 최적화 문서에서 공통적으로 설명하는 표준 최적화 기법이다.
- FLIRT가 함수 단위의 코드 패턴 매칭을 전제로 하며, 인라인되어 함수 경계가 사라진 코드에는 적용되지 않는다는 점은 Hex-Rays 공식 문서("FLIRT technology")의 동작 원리에 근거한 논리적 귀결이다.
