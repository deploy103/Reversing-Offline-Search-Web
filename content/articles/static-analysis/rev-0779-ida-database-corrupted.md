## 한 줄 요약
`.idb`/`.i64` 파일을 열려고 하는데 에러가 나거나 IDA가 열자마자 튕긴다면, 대부분은 **저장 도중 강제 종료(정전, 프로세스 킬, 디스크 꽉 참)로 파일이 불완전하게 쓰인 것**이 원인이므로, 먼저 자동 백업본(`.i64~`, 스냅샷)이 남아있는지부터 확인하고, 없다면 원본 바이너리에서 새로 분석을 시작해 이전 작업(주석, 이름)을 최대한 복구하는 방향으로 접근해야 한다.

## 언제 검색해야 하나
- `.idb`/`.i64` 파일을 더블클릭했는데 IDA가 아예 안 열리거나 에러 대화상자만 뜨고 종료될 때
- `database is corrupted`, `Failed to load database`, `unexpected end of file` 같은 메시지가 뜰 때
- IDA 작업 중 정전, 강제 종료(Task Manager로 kill), 디스크 용량 부족 등으로 비정상 종료된 직후부터 파일이 안 열릴 때
- 파일 탐색기에서 `.i64` 파일 크기가 0바이트이거나 비정상적으로 작을 때

## 핵심 개념
IDA 데이터베이스는 논리적으로는 하나의 파일(`.idb` 또는 최신 버전의 통합 포맷인 `.i64`)이지만, 내부적으로는 여러 개의 하위 저장소(예전 버전 기준으로 `.id0`—데이터베이스 본체, `.id1`—바이트별 플래그, `.nam`—이름 목록, `.til`—타입 정보 등)가 합쳐진 구조다. 저장(`Ctrl+S` 또는 자동 저장)은 이 여러 하위 구조를 순서대로 디스크에 써 내려가는 과정인데, 이 과정 중간에 프로세스가 강제로 죽거나 디스크 공간이 부족해지면 일부만 기록된 반쪽짜리 파일이 남는다. 이런 파일은 다음에 열 때 IDA가 내부 구조 일관성 검사에 실패해 손상으로 판단하고 로드를 거부한다.

IDA는 이런 상황에 대비해 몇 가지 안전장치를 기본으로 제공한다.

- **자동 백업/스냅샷**: IDA는 설정에 따라 일정 주기로 또는 종료 시점에 이전 상태를 별도 파일로 남겨두거나, 저장 시 이전 파일을 `.i64~` 같은 백업 확장자로 남기는 옵션을 제공한다.
- **`.til`(타입 라이브러리)과 로그 파일은 별개로 존재**: 데이터베이스 본체가 손상돼도, 같은 폴더에 남아있는 로그 파일(`.log`)이나 이전에 뽑아둔 IDC/Python 스크립트가 있다면 이름/주석 등 일부 정보를 다시 살릴 실마리가 된다.
- **원본 바이너리는 항상 안전함**: 데이터베이스가 통째로 날아가도, 분석 대상이었던 원본 실행 파일 자체는 별도로 보존되어 있으므로 최악의 경우 처음부터 다시 분석하면 된다. 이것이 "복구 불가능한 손실"이 되지 않도록 원본 바이너리와 데이터베이스 파일을 항상 분리해서 백업해두는 습관이 중요한 이유다.

## 화면/코드에서 보이는 징후
- 파일을 더블클릭하거나 IDA에서 `File → Open`으로 열었을 때 곧바로 에러 대화상자가 뜨고 메인 화면이 나타나지 않음.
- 에러 메시지에 `corrupted`, `bad file format`, `unexpected end of file`, `checksum` 등의 단어가 포함됨.
- 파일 탐색기/`ls -l`로 확인한 `.i64` 파일 크기가 이전에 저장했던 크기보다 훨씬 작거나 0바이트임.
- 같은 폴더에 `파일명.i64~` 같은 백업 확장자 파일이 남아 있음(자동 백업 옵션이 켜져 있었을 경우).

## 가장 먼저 할 것
손상된 파일을 건드리기 전에, 같은 폴더를 먼저 복사해서 별도 백업 폴더에 안전하게 보관한다. 그다음 같은 폴더 안에 `.i64~`나 날짜가 다른 백업 파일이 있는지부터 찾는다.

## 단계별 절차
1. 손상이 의심되는 폴더 전체를 다른 위치로 복사해 원본 상태를 보존한다(실수로 더 손상시키지 않기 위함).
2. 같은 폴더에서 파일명이 비슷한 백업 후보를 찾는다: `프로젝트명.i64~`, `프로젝트명_backup.i64`, 또는 IDA가 설정에 따라 만들어두는 스냅샷 폴더가 있는지 확인한다. 있다면 그 백업본을 먼저 열어본다.
3. 백업본도 없다면, 텍스트 에디터나 `file` 명령으로 손상된 `.i64` 파일의 헤더 일부라도 남아 있는지 확인한다(파일이 통째로 0바이트라면 복구 가능성은 거의 없다).
4. IDA를 다시 실행해 손상된 파일을 열어보되, 에러 메시지의 정확한 문구를 기록해둔다. 일부 손상은 IDA가 "일부 정보만 복구해서 열까요?" 같은 부분 복구 옵션을 제시하기도 하므로, 에러 대화상자의 선택지를 잘 읽는다.
5. 부분 복구도 안 된다면, 마지막 수단으로 원본 바이너리 파일(분석 대상이었던 실행 파일 자체)을 다시 IDA로 새로 열어 처음부터 분석을 시작한다. 이전에 작업했던 이름/주석은 사라지지만, auto-analysis는 다시 정상적으로 실행되므로 분석 자체를 못 하게 되는 것은 아니다.
6. 이전에 `File → Produce file → Create IDC/Python script`나 `Dump database to IDC file`로 뽑아둔 스크립트, 혹은 별도로 메모해둔 주석/이름 목록이 있다면, 새로 분석한 데이터베이스에 그 정보를 참고해서 다시 적용한다.
7. 앞으로 이런 손실을 줄이기 위해 재발 방지 조치를 한다: `File → Save`를 자주 눌러 스냅샷을 남기고, 큰 작업 전에는 `File → Produce file → ...`로 이름/주석만이라도 텍스트로 별도 백업하며, 저장이 자주 발생하는 위치를 디스크 공간이 넉넉한 로컬 드라이브로 옮긴다.

## 명령어/단축키
- `Ctrl+S` : 데이터베이스 저장(스냅샷 생성 옵션에 따라 백업본도 함께 생성될 수 있음)
- `File → Produce file → Create IDC/Python script` : 이름/주석 등을 텍스트로 별도 백업
- `File → Open` : 손상 의심 파일을 다시 열어 에러 문구 확인
- 파일 탐색기 또는 `ls -l` : 파일 크기/존재 여부 확인

## 출력 해석
- 에러 메시지에 `unexpected end of file`이 포함되면 저장이 끝까지 완료되지 못하고 중간에 끊겼다는 뜻으로, 강제 종료가 원인일 가능성이 매우 높다.
- 파일 크기가 정상 크기의 몇 분의 1로 작다면 저장 도중 디스크 공간 부족이나 강제 종료로 앞부분만 기록되고 끝난 것일 수 있다.
- 부분 복구 옵션을 제공하는 대화상자가 뜬다면, 완전한 손상이 아니라 일부 구조만 문제가 있는 것이므로 시도해볼 가치가 있다(단, 복구된 결과가 100% 정확하다는 보장은 없으므로 이후 재검증이 필요하다).

## 흔한 실수
- 손상된 파일을 백업 없이 계속 열었다 닫았다 하다가 자동 저장이 다시 덮어써서 복구 가능성이 있던 일부 데이터까지 날리는 것.
- 자동 백업 옵션이 꺼져 있는 줄 모르고 "IDA가 알아서 백업해줄 것"이라 방심하는 것 — 큰 작업 전에는 수동으로 파일을 복사해두는 습관이 필요하다.
- 데이터베이스가 손상됐다고 처음부터 다시 분석하는 것을 포기하는 것 — 원본 바이너리만 있으면 자동 분석은 다시 정상적으로 되므로, 이름/주석만 손실될 뿐 분석 자체가 불가능한 것은 아니다.
- 네트워크 드라이브나 외장 저장장치에서 직접 데이터베이스를 열고 저장하다가 연결이 끊겨 손상되는 경우 — 로컬 디스크에서 작업하고 완료 후 복사하는 편이 안전하다.

## 막혔을 때 다음 체크
- 재분석을 새로 시작하는데 파일을 처음 열었을 때 뭘 해야 할지 모르겠다면 → REV-0142 IDA에 바이너리 처음 열었을 때 해야 할 것
- 재분석 후 함수가 하나도 안 잡힌다면 → REV-0772 IDA에서 함수가 아예 하나도 안 잡힐 때
- 재분석이 너무 오래 걸리는 것 같다면 → REV-0771 IDA 분석이 멈춘 것처럼 매우 느릴 때
- 이름/주석 백업 스크립트 활용법이 더 필요하면 IDA 자동화/스크립팅 관련 문서를 참고한다.

## 미니 예제
장시간 분석하던 `.i64` 파일이 저장 도중 노트북 배터리가 꺼지면서 손상된 상황.

```text
1. 폴더 전체를 백업 폴더로 복사
2. 같은 폴더에서 challenge.i64~ 백업 확장자 파일 발견(자동 백업 옵션이 켜져 있었음)
3. challenge.i64~ 파일 확장자를 .i64로 바꿔 다시 열어보니 정상적으로 로드됨
4. 몇 분 전 저장 시점까지의 이름/주석이 대부분 복구됨을 확인
```
백업본이 없었다면 원본 실행 파일을 다시 IDA로 열어 처음부터 재분석했을 것이다.

## 관련 글
- REV-0142 — IDA에 바이너리 처음 열었을 때 해야 할 것
- REV-0772 — IDA에서 함수가 아예 하나도 안 잡힐 때
- REV-0771 — IDA 분석이 멈춘 것처럼 매우 느릴 때
- REV-0778 — IDA에서 이름을 바꿨는데 다른 곳에 반영이 안 될 때

## 출처/검증
- IDA 데이터베이스의 내부 다중 파일 구조(구버전 `.id0`/`.id1`/`.nam`/`.til` 및 최신 통합 `.i64` 포맷)와 저장/백업 동작: Hex-Rays 공식 문서 "Database description" 및 "Snapshots" 섹션 기준.
- 저장 도중 강제 종료 시 파일 손상 가능성은 파일 시스템 쓰기 도중 중단 시 발생하는 일반적인 소프트웨어 동작 원리에 기반한다.
- 정확한 백업 파일 확장자/옵션명은 IDA 버전에 따라 다를 수 있어 실제 설치 버전에서 재확인을 권장한다.
