## 한 줄 요약
LTO(Link Time Optimization, 링크 타임 최적화)/whole-program optimization이 적용된 바이너리는 컴파일러가 원래 여러 개의 `.c`/`.cpp` 파일(컴파일 단위)을 하나의 커다란 최적화 단위로 합쳐서 처리하기 때문에, 원래 파일 경계·`static` 함수 이름의 유일성·함수 배치 순서가 전부 사라지고 함수 개수만 비정상적으로 많아 보이거나 서로 무관해 보이던 로직이 한 함수에 섞여 보이는 경우가 흔하며, 이때는 "원래 소스 파일 구조를 복원하겠다"는 목표를 버리고 `main`에서 도달 가능한 호출 그래프만 따라가는 방식으로 분석 범위를 좁혀야 한다.

## 언제 검색해야 하나
- Functions 창의 함수 개수가 프로그램 규모에 비해 비정상적으로 많을 때(라이브러리까지 다 포함되어 정적 링킹된 경우와 함께 나타나기 쉬움)
- 같은 이름 계열(`helper`, `helper_0`, `helper_1`)의 `static` 함수가 여러 개 있어서 원래 소스에서 이름이 겹치던 여러 파일의 `static` 함수였음을 짐작할 수 있을 때
- 서로 관련 없어 보이는 기능(예: 입력 파싱과 암호화 로직)의 코드가 예상 밖으로 한 함수 근처에 나란히 배치되어 있을 때
- FLIRT/FunctionID 매칭이 평소보다 더 잘 안 통할 때(코드가 재배치/병합되어 시그니처 데이터베이스의 표준 패턴과 달라짐)

## 핵심 개념
일반적인(비-LTO) 컴파일은 각 `.c` 파일을 독립적으로 컴파일해서 오브젝트 파일(`.o`)을 만들고, 링커가 이들을 단순히 이어 붙인다. 이 경우 `static` 함수(그 파일 안에서만 보이는 함수)는 그 파일 하나의 문맥 안에서만 최적화되며, 서로 다른 파일의 `static` 함수끼리는 완전히 독립적이다.

LTO는 이 과정을 바꾼다. 컴파일러는 각 파일을 중간 표현(IR)으로만 컴파일해두고, **링크 시점에 모든 파일의 IR을 한꺼번에 모아** 프로그램 전체를 하나의 단위로 보고 최적화를 수행한다. 그 결과:

1. **컴파일 단위 경계가 사라짐** — 원래 어떤 함수가 어느 `.c` 파일에 있었는지 알려주는 정보(오브젝트 파일 경계, 소스 파일명)가 최종 바이너리에는 전혀 남지 않는다.
2. **static 함수의 이름 충돌 처리** — 서로 다른 파일에 있던 동일한 이름의 `static` 함수(예: 여러 파일에 각각 `static int helper(...)`가 있는 경우)가 하나로 합쳐지면서, 링커/컴파일러가 이름 뒤에 번호를 붙이거나(`helper.0`, `helper.1`) 심볼을 아예 지워버릴 수 있다.
3. **파일 간 인라이닝/함수 재배치** — LTO는 파일 경계를 넘어서까지 인라이닝(REV-0799)과 함수 재배치, 데드코드 제거를 수행하므로, 원래는 별개 파일의 서로 다른 목적을 가진 코드가 물리적으로 인접하게 배치되거나 하나로 합쳐질 수 있다.
4. **함수 개수 자체는 최적화로 오히려 줄어들 수도, 인라인 실패로 파편화되어 늘어날 수도 있음** — "함수가 너무 많다"는 인상은 실제로는 정적 링킹된 라이브러리 코드까지 전부 최적화 대상에 포함되어 한꺼번에 나타나기 때문인 경우가 많다.

즉 LTO 바이너리를 볼 때는 "원래 소스가 어떻게 나뉘어 있었는지"를 재구성하려는 시도 자체가 대부분 불가능하거나 비효율적이라는 점을 먼저 받아들여야 한다.

## 화면/코드에서 보이는 징후
- Functions 창 함수 개수가 프로그램 복잡도 대비 지나치게 많음(수백~수천)
- `helper`, `helper.0`, `helper.1`처럼 번호가 붙은 유사 이름의 `static` 함수 다수
- 소스 파일 정보(디버그 심볼이 남아있는 경우)를 보면 서로 다른 파일 출신 함수들이 주소상 인접해 있음
- 문자열/상수 클러스터(REV-0165)가 기대와 다르게 여러 기능 영역에 걸쳐 섞여 있음

## 가장 먼저 할 것
"모든 함수를 분류하겠다"는 목표를 버리고, `main`(또는 진입점)에서 실제로 호출되는 함수만 REV-0166(호출 그래프 좁히기) 방식으로 따라간다. LTO 여부와 무관하게, 실행되지 않는 코드까지 분석할 필요는 없다.

## 단계별 절차

**1) LTO 적용 여부 힌트 확인**
디버그 정보가 남아 있다면(stripped가 아니라면) 컴파일러가 남긴 메타데이터(예: ELF의 `.comment` 섹션, 빌드 관련 문자열)에서 LTO 관련 흔적을 확인할 수 있다. 없어도 위의 "화면/코드 징후"만으로 충분히 의심할 수 있다.

**2) main에서 시작하는 호출 그래프만 추림**
REV-0166 절차대로 `main`부터 실제로 호출되는 함수만 나열한다. 정적 링킹/LTO로 딸려온 라이브러리 내부 함수 대부분은 문제 로직과 무관하므로 무시한다.

**3) static 함수 번호 접미사는 원래 이름 충돌의 흔적으로만 이해**
`helper.0`, `helper.1`처럼 번호가 붙어 있다면, 이는 서로 다른 원본 파일에 있던 동명의 `static` 함수라는 뜻이지 실제로 연관된 로직이라는 뜻이 아니다. 번호가 다르면 별개 함수로 취급한다.

**4) 인접 배치를 곧이곧대로 "같은 파일/같은 기능"으로 해석하지 않기**
LTO는 원래 파일 순서를 무시하고 최적화상 유리한 순서로 함수를 재배치할 수 있다. 함수 주소가 가깝다고 기능적으로 연관됐다고 단정하지 않는다.

**5) 문자열/상수/호출 패턴으로 기능 클러스터 재구성**
파일 구조 대신, 문자열 참조(REV-0163)와 상수(REV-0165)를 기준으로 "이 함수들은 같은 기능(예: 입력 파싱)을 담당한다"는 논리적 클러스터를 직접 만든다. 이것이 원래 파일 구조보다 실제 분석에는 더 유용하다.

**6) 필요하면 문제 로직만 골라 파이썬으로 재현**
전체 구조를 이해하려 하지 말고, 실제로 검증 로직에 해당하는 함수 몇 개만 확정되면 그 부분만 REV-0168 절차로 재현해 문제를 해결한다.

## 명령어/단축키
- Functions 창 정렬(주소순/이름순 토글)로 번호 붙은 static 함수 그룹 확인
- `Ctrl+X`: 호출 그래프 추적
- `readelf -p .comment <binary>`: 컴파일러 버전/옵션 관련 문자열 확인(LTO 힌트가 남아 있을 수도 있음)

## 출력 해석
- `helper.0`/`helper.1`처럼 숫자 접미사가 있는 함수가 다수 보이면 LTO 병합 가능성이 매우 높다는 신호로 받아들인다.
- 호출 그래프로 좁힌 함수 집합이 원래 예상보다 훨씬 작다면, 나머지 수많은 함수는 대부분 딸려온 라이브러리/데드코드일 가능성이 높으므로 안심하고 무시해도 된다.

## 흔한 실수
- 원래 소스 파일 경계를 어떻게든 복원하려고 시간을 쓰는 것 — LTO로 병합된 정보는 대부분 복구 불가능하다.
- 번호가 붙은 동명 함수들을 같은 함수의 여러 버전이라고 착각해서 서로 비교하는 것 — 서로 다른 원본 파일의 별개 함수다.
- 함수가 너무 많다고 전체를 다 훑으려 하는 것 — 호출 그래프로 실행 경로만 추리는 것이 훨씬 빠르다.
- 인접한 함수들을 무조건 같은 기능으로 묶어서 분석하는 것.

## 막혔을 때 다음 체크
- 인라이닝 자체 때문에 함수 경계가 아예 안 보이는 문제라면 → REV-0799
- 정적 링킹된 라이브러리 코드가 섞여서 함수가 많아 보이는 것이라면 → REV-0646
- 호출 그래프로 후보를 좁히는 방법이 궁금하면 → REV-0166
- FLIRT 매칭이 이 때문에 잘 안 되는 것 같다면 → REV-0804

## 미니 예제
Functions 창에 `parse_input.0`, `parse_input.1`, `validate.0`, `validate.1`처럼 번호가 붙은 함수가 여러 쌍 보인다고 하자. 이는 원래 서로 다른 두 소스 파일에 각각 `static int parse_input(...)`, `static int validate(...)`가 정의되어 있었고 LTO 링크 과정에서 이름 충돌을 피하려 번호가 붙은 것이다. `main`에서 호출 그래프를 따라가 보니 실제로 문제 풀이에 필요한 것은 `validate.1`뿐이었고 `validate.0`은 전혀 호출되지 않는 죽은 코드였다. 이 경우 `validate.0`은 무시하고 `validate.1`에만 집중하면 된다.

## 관련 글
- REV-0799 — 인라인된 함수 때문에 원래 함수 경계를 못 찾을 때
- REV-0646 — 정적 링킹된(Statically Linked) ELF 분석 접근법
- REV-0166 — 함수 Call Graph로 핵심 로직 좁히기
- REV-0804 — FLIRT 시그니처가 안 맞아서 라이브러리 함수를 놓칠 때

## 출처/검증
- LTO(Link Time Optimization)/whole-program optimization이 컴파일 단위 경계를 넘어 함수를 재배치·병합·인라이닝한다는 원리는 GCC의 공식 문서(`-flto` 옵션 설명) 및 LLVM 공식 문서(LTO 관련 챕터)에서 설명하는 표준 동작이다.
- 동일 이름의 `static` 함수가 LTO 병합 시 번호 접미사(`.0`, `.1` 등)로 구분되는 방식은 GCC/LLVM 심볼 네이밍 관례에 근거한 일반적으로 관찰되는 현상이다.
