## 한 줄 요약
콜 그래프(REV-0166)에서 화살표가 자기 자신으로 돌아오거나(직접 재귀) 여러 함수를 거쳐 원래 함수로 되돌아오면(상호 재귀/사이클), 그 함수 묶음은 반복문이 아니라 **재귀 호출 구조**로 구현된 알고리즘일 가능성이 크므로, 스택 사용 패턴과 종료 조건(base case)을 중심으로 분석 전략을 바꿔야 한다.

## 언제 검색해야 하나
- 콜 그래프를 보다가 화살표가 같은 노드로 되돌아오는 형태(자기 자신을 가리키는 화살표, 또는 A→B→A 순환)를 발견했을 때
- 디스어셈블리에서 함수 안에 자기 자신의 주소로 향하는 `call`이 보여서 재귀 함수인지 확인이 필요할 때
- 스택 오버플로우가 나거나 함수 실행 중 스택이 예상보다 훨씬 깊어지는 이유를 콜 그래프로 확인하고 싶을 때
- 트리/그래프 순회, 분할정복, 피보나치류 알고리즘처럼 재귀로 구현되는 경우가 많은 로직을 식별하고 싶을 때

## 핵심 개념
콜 그래프에서 재귀는 두 가지 형태로 나타난다.

- **직접 재귀(direct recursion)**: 함수 A 노드에서 나가는 화살표가 다시 A 자신을 가리킨다. 디스어셈블리 레벨에서는 함수 내부에 자기 자신의 시작 주소로 향하는 `call`(또는 IDA/Ghidra가 `A`라는 이름으로 인식한 주소로의 호출)이 있다는 뜻이다.
- **상호 재귀/사이클(mutual recursion / cycle)**: A→B, B→A처럼 두 개 이상의 함수가 서로를 호출하며 순환하는 구조다. 콜 그래프에서는 여러 노드를 거쳐 원래 출발 노드로 돌아오는 닫힌 경로(cycle)로 나타난다.

두 형태 모두 실행 시점에는 **스택에 호출 프레임이 계속 쌓인다**는 공통 특징이 있다. 반복문(loop)은 같은 스택 프레임 안에서 점프만 반복하지만, 재귀는 매 호출마다 새로운 스택 프레임(리턴 주소, 지역 변수, 저장된 레지스터)이 쌓인다. 그래서 재귀 함수는 디스어셈블리에서 함수 프롤로그(`push rbp` / `sub rsp, N`)가 실행될 때마다 스택 포인터가 계속 낮아지는 패턴으로 확인할 수 있고, GDB/x64dbg로 실행 중 스택을 관찰하면(`bt`, Call Stack 창) 같은 함수 이름이 여러 번 반복해서 쌓여 있는 것이 보인다.

**IDA에서 사이클 찾기**: View → Graphs → Function calls로 전체 그래프를 그리면 화살표가 되돌아오는 지점이 시각적으로 드러난다. 특정 함수 하나만 확인하려면 그 함수에서 View → Graphs → Xrefs from을 열어, 나가는 참조 중 자기 자신이나 이미 지나온 노드가 다시 나타나는지 확인한다.

**Ghidra에서 사이클 찾기**: 함수 우클릭 → Function Call Graph로 열면 순환 경로가 화살표로 표시된다. Function Call Trees 패널(Ctrl+Alt+T)에서는 Outgoing Calls를 펼쳤을 때 이미 상위 트리에 나왔던 함수 이름이 다시 나타나면(트리 특성상 무한히 펼쳐지지 않도록 보통 한 번 더 펼치면 표시가 멈추거나 반복 표시됨) 재귀/사이클의 신호다.

**radare2에서 확인하기**: `axt`/`axf`(REV-0751)를 오가며 A의 outgoing에 A 자신 또는 이미 방문한 노드가 다시 나오는지 수동으로 추적하거나, `agf`로 그래프를 텍스트로 그려 화살표 순환을 확인한다.

## 화면/코드에서 보이는 징후
- 디스어셈블리에서 함수 내부에 자기 자신의 시작 주소로 향하는 `call` 명령이 보인다.
- 함수 A의 pdf/디컴파일 결과 안에 함수 B 호출이 있고, B의 코드 안에 다시 A 호출이 있다.
- 디버거로 실행하며 Call Stack을 보면 같은 함수 이름이 여러 프레임에 걸쳐 반복적으로 쌓여 있다.
- 입력 크기를 조금만 키워도 실행이 느려지거나 스택 오버플로우(Segmentation fault, Stack Overflow 예외)가 발생한다.

## 가장 먼저 할 것
콜 그래프에서 순환처럼 보이는 부분을 발견하면, 먼저 함수 하나를 기준으로 View → Graphs → Xrefs from(IDA) 또는 Function Call Graph(Ghidra)를 열어 실제로 자기 자신이나 이전 노드로 돌아오는 화살표가 있는지 직접 확인한다.

## 단계별 절차
1. 콜 그래프 전체 뷰(REV-0166)에서 화살표가 되돌아오는 것처럼 보이는 영역을 찾는다.
2. 의심되는 함수 하나를 기준으로 outgoing call(자신이 호출하는 함수) 목록을 확인한다 — IDA Xrefs from, Ghidra Function Call Trees Outgoing, radare2 `axf`.
3. 목록에 자기 자신의 이름/주소가 있으면 직접 재귀로 확정한다.
4. 자기 자신은 없지만 다른 함수 B가 있다면, B의 outgoing 목록도 같은 방식으로 확인해 A가 다시 나타나는지 본다 — 나타나면 A↔B 상호 재귀(사이클)다.
5. 재귀/사이클로 확정되면, 함수 내부에서 **재귀 호출 직전의 조건문(base case, 종료 조건)**을 찾는다. 이 조건이 재귀가 끝나는 지점이므로 알고리즘의 핵심 로직인 경우가 많다.
6. 실제 실행 스택을 GDB/x64dbg로 관찰해(`bt`, Call Stack 창) 재귀 깊이와 각 호출마다 전달되는 인자 변화를 추적하면, 정적 분석만으로 애매했던 재귀 구조를 확실히 검증할 수 있다.
7. 재귀 구조가 확정되면 Python으로 재현할 때도 굳이 반복문으로 바꾸지 않고 그대로 재귀 함수로 옮기는 것이 원본 로직을 실수 없이 재현하는 데 유리하다(단, 파이썬 기본 재귀 깊이 제한 `sys.setrecursionlimit()` 조정이 필요할 수 있다).

## 명령어/단축키
- IDA: View → Graphs → Function calls(전체), Xrefs from(개별 함수의 outgoing 확인)
- Ghidra: 함수 우클릭 → Function Call Graph, Window → Function Call Trees(`Ctrl+Alt+T`)의 Outgoing Calls 트리
- radare2: `axf`(outgoing 확인), `agf`(현재 함수 그래프 텍스트 출력)
- GDB/pwndbg: `bt`(backtrace로 현재 스택 프레임 나열), `info frame`
- x64dbg: Call Stack 창

## 출력 해석
- Outgoing 목록에 자기 자신이 나오면 100% 직접 재귀다.
- Outgoing을 따라가다 이미 지나온 함수로 되돌아오면 사이클(상호 재귀)이며, 이 경로에 포함된 모든 함수가 하나의 재귀 알고리즘 단위로 묶여 있다고 봐야 한다.
- 디버거의 Call Stack에서 같은 함수 이름이 N번 반복되어 있다면, 그 시점에 재귀가 N단계 깊이까지 진행되었다는 뜻이다. 이 값이 입력 크기와 비례해서 커진다면 입력 크기가 곧 재귀 깊이를 결정하는 알고리즘(예: 트리 순회, 분할정복)일 가능성이 크다.

## 흔한 실수
- 반복문(loop)과 재귀(recursion)를 혼동하는 것 — 반복문은 같은 스택 프레임에서 점프만 반복하므로 Call Stack에 새 프레임이 쌓이지 않는다. 반드시 실제 스택 프레임 증가 여부로 구분해야 한다.
- 콜 그래프에서 화살표가 되돌아오는 것처럼 보이지만 실제로는 서로 다른 두 함수가 우연히 같은 이름의 서로 다른 헬퍼를 호출하는 것을 사이클로 오인하는 것 — 정확히 같은 주소/심볼인지 반드시 확인해야 한다.
- 재귀 함수를 무리해서 파이썬 반복문으로 직접 변환하려다 종료 조건을 잘못 옮겨 결과가 미묘하게 틀리는 것 — 원본 구조를 최대한 그대로(재귀는 재귀로) 옮기는 것이 안전하다.
- 재귀 깊이 제한을 고려하지 않고 파이썬으로 그대로 재현했다가 `RecursionError`를 만나는 것 — `sys.setrecursionlimit()`로 미리 늘려야 한다.

## 막혔을 때 다음 체크
- 콜 그래프 전반의 조회 방법 자체가 궁금하면 → REV-0166 함수 Call Graph로 핵심 로직 좁히기
- radare2 커맨드라인으로 outgoing/incoming을 확인하는 구체적 명령이 필요하면 → REV-0751 radare2로 함수 목록과 XREF 확인하기(afl, axt)
- 코드+데이터 참조까지 넓혀서 확인하고 싶다면 → REV-0757 Cross Reference Graph로 핵심 함수 찾기
- 확정한 로직을 파이썬으로 옮기는 방법은 → REV-0168 정적 분석 결과를 Python 의사코드로 옮기기

## 미니 예제
Ghidra에서 `solve(int n)` 함수를 우클릭해 Function Call Graph를 열었더니, `solve` 노드에서 나간 화살표가 다시 `solve` 자신으로 돌아오는 것이 보였다. 디컴파일 결과를 확인하니 다음과 같은 형태였다.
```c
int solve(int n) {
  if (n <= 1) return n;
  return solve(n - 1) + solve(n - 2);
}
```
콜 그래프의 자기 참조 화살표 하나만으로 이 함수가 재귀 구조라는 것을 코드를 읽기 전에 먼저 알 수 있었고, `if (n <= 1) return n;`이 종료 조건(base case)이라는 것도 함께 확인해 전체가 피보나치 수열 계산 로직이라는 결론을 빠르게 내릴 수 있었다.

## 출처/검증
- 재귀 호출 시 매 호출마다 새 스택 프레임(리턴 주소, 저장 레지스터, 지역 변수)이 쌓인다는 설명은 x86-64 함수 호출 규약(calling convention)의 일반 원리 기준.
- IDA Function calls/Xrefs from, Ghidra Function Call Graph/Function Call Trees에서 순환 경로가 시각적으로 드러난다는 설명: 각 도구 공식 문서의 그래프 기능 topic 기준.
- 파이썬 `sys.setrecursionlimit()` 필요성은 파이썬 공식 문서(sys 모듈, recursion limit)에 명시된 기본 재귀 제한 동작 기준.
- 이 문서는 실기 화면을 직접 캡처해 검증하지는 않았다(2026-09-09 검증).
