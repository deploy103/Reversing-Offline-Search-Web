## 한 줄 요약
Case가 수십~수백 개에 달하는 큰 switch문(주로 커스텀 가상 머신의 opcode 디스패치 루프)은 코드를 위에서 아래로 읽는 방식이 아니라, "선택자 값 → 목표 주소 → 한 줄 동작 요약"으로 이뤄진 외부 표를 만들어 전수 조사하는 방식으로 접근해야 실수 없이 전체를 파악할 수 있다.

## 언제 검색해야 하나
- 반복문 안에서 `switch(opcode)` 형태로 수십~수백 개의 case를 처리하는 코드를 만나서, 이게 커스텀 가상 머신(VM)이나 인터프리터 구조로 보일 때
- REV-0441(Switch문 점프 테이블 완전 분석)로 어셈블리 레벨의 점프 테이블 구조 자체는 이해했는데, 실제 case가 너무 많아 하나씩 손으로 따라가기엔 시간이 부족할 때
- 디컴파일러가 `switch` 구문을 제대로 복원하지 못하고 원본 점프 테이블(주소 배열)만 데이터로 보여줄 때
- 여러 handler 함수가 거의 같은 모양이라 서로 구분이 안 되고, 전체를 한눈에 비교할 방법이 필요할 때

## 핵심 개념

### 왜 "표"로 접근해야 하는가
큰 switch문을 코드 순서대로(case 0, case 1, case 2, ...) 하나씩 읽으면, 이미 본 case와 아직 안 본 case를 계속 기억하고 있어야 하고, 비슷한 동작을 하는 case끼리 비교하기도 어렵다. 반면 각 case를 별도의 표 행(row)으로 만들면, (1) 아직 분석하지 않은 case를 빈 칸으로 바로 확인할 수 있고, (2) 비슷한 동작을 하는 case들을 표 안에서 정렬/그룹화해서 패턴(예: "0x00~0x0F는 전부 산술 연산, 0x10~0x1F는 전부 메모리 접근")을 찾기 쉬워진다. 이는 REV-0770에서 다루는 "여러 함수에 걸친 노트 작성법"의 스위치문 특화 버전이라고 볼 수 있다.

### 표에 포함해야 할 열(column)
최소한 다음 열을 갖춘 표를 만든다.

| case 값 | 핸들러 주소 | 스택/레지스터 영향 | 한 줄 동작 요약 | 확인 여부 |
|---|---|---|---|---|
| 0x00 | 0x401230 | 스택 top 2개 pop, 결과 push | ADD (덧셈) | 완료 |
| 0x01 | 0x401260 | 스택 top 2개 pop, 결과 push | SUB (뺄셈) | 완료 |
| 0x02 | 0x4012A0 | 메모리[reg] 읽기, push | LOAD | 진행중 |
| ... | ... | ... | ... | 미확인 |

"확인 여부" 열은 전체 case 개수 대비 진행 상황을 한눈에 보여주므로, 큰 규모의 VM opcode 분석에서 빠뜨린 case가 없는지 검증하는 체크리스트 역할도 겸한다.

### 점프 테이블에서 case 전체를 빠짐없이 뽑아내는 법
- **IDA**: switch문의 점프 테이블은 보통 `.rodata`/`.rdata`에 함수 포인터(또는 상대 오프셋) 배열로 존재한다. 배열 시작 주소에서 `Array`로 변환(`*` 또는 우클릭 `Data → Array`)한 뒤, 각 항목에 Xref(`X`)를 걸면 case 값(배열 인덱스)과 대상 주소의 대응 관계를 순서대로 확인할 수 있다.
- **Ghidra**: 디컴파일러가 `switch(x){ case 0: ...; case 1: ...; }` 형태로 이미 복원해주는 경우가 많다. 복원되지 않았다면 Listing에서 점프 테이블 데이터를 확인하고, 우클릭 `References → Show References to Address`로 각 항목의 대상을 확인한다.
- 두 도구 모두, 점프 테이블 항목 수를 세어보면 "이 switch문의 case가 정확히 몇 개인지"를 코드를 읽기 전에 먼저 알 수 있다(빠뜨림 방지에 유용).

### 선택자 변수에 enum을 지정해 가독성 높이기
case 값들의 의미를 어느 정도 파악했다면, IDA Local Types나 Ghidra Data Type Manager에 enum(예: `enum VmOpcode { OP_ADD = 0, OP_SUB = 1, ... }`)을 정의하고 switch의 선택자 변수 타입으로 지정한다. 이렇게 하면 디컴파일 결과가 `case 0:` 대신 `case OP_ADD:`처럼 표시되어, 표와 코드를 오가며 확인하는 부담이 크게 줄어든다.

## 화면/코드에서 보이는 징후
- 디컴파일 결과에 `case`가 수십 줄 이상 나열되어 있거나, `jtbl_...`, `switchdata_...` 같은 이름의 데이터 배열이 `.rodata`에 있다.
- 반복문이 "선택자 값을 읽고 → switch로 분기 → 다시 반복문 처음으로" 구조를 반복하는 인터프리터 루프 형태다(가상 머신 opcode 디스패치의 전형적 패턴).
- 여러 case의 핸들러 코드가 몇 줄짜리로 짧고 서로 비슷비슷해서 눈으로 구분하기 어렵다.

## 가장 먼저 할 것
점프 테이블(또는 case 개수)부터 세어서 표의 행 개수를 먼저 확정한다. "총 몇 개의 case가 있는지" 모른 채로 하나씩 읽기 시작하면 언제 다 봤는지 알 수 없다.

## 단계별 절차
1. switch문의 선택자 변수가 어디서 오는지 확인(입력 바이트, 바이트코드 배열의 현재 인덱스 등)해 REV-0441 방식으로 점프 테이블 위치를 특정한다.
2. 점프 테이블 항목 수를 세어 표의 전체 행 수를 정한다.
3. 표(스프레드시트 또는 마크다운 표)를 만들고 case 값·핸들러 주소 열부터 기계적으로 채운다(이 단계는 아직 코드를 읽지 않고도 가능).
4. 핸들러를 하나씩 열어 "스택/레지스터에 미치는 영향"과 "한 줄 동작 요약" 열을 채운다. 비슷한 핸들러는 복사해서 빠르게 채우되, 값(상수, 시프트 방향 등)의 미세한 차이를 반드시 재확인한다.
5. 유사한 case끼리 그룹을 지어(산술/메모리/분기/입출력 등) 표를 재정렬하면, 각 그룹의 대표 패턴만 자세히 읽고 나머지는 "같은 패턴, 상수만 다름"으로 빠르게 처리할 수 있다.
6. 전체 표가 채워지면, 이를 기반으로 enum을 정의해 IDA/Ghidra에 적용하고, REV-0168 방식으로 Python 인터프리터(같은 opcode 표를 그대로 Python 딕셔너리로 옮긴 것)를 작성해 실제 바이트코드를 해석/재현한다.

## 명령어/단축키
- IDA: 배열 변환은 데이터 선택 후 `*`(Array 변환 단축키, 버전에 따라 우클릭 메뉴 사용), Xref는 `X`, enum 정의는 Local Types 창에서 `Insert`
- Ghidra: 점프 테이블 데이터는 Listing에서 선택 후 우클릭 `Data → Create Array`, 참조 확인은 `Show References to Address`, enum은 Data Type Manager 우클릭 `New → Enum`
- 공통: 표는 마크다운 표 또는 CSV로 작성해 Python 스크립트(REV-0168)에서 그대로 파싱해 쓸 수 있게 하면 이중 작업을 줄일 수 있다

## 출력 해석
- 점프 테이블 항목 수와 표의 행 수가 안 맞으면, 일부 case가 `default`로 폴백되거나 여러 case가 같은 핸들러를 공유(fallthrough)하고 있다는 뜻이니 원본 소스코드의 `case 3: case 4: foo();` 같은 패턴을 의심한다.
- 어떤 case 핸들러의 "스택 영향"이 다른 case들과 전혀 다른 패턴(예: 대부분 2개 pop/1개 push인데 하나만 인자 없이 그냥 리턴)이면, 그 case가 `HALT`/`RETURN`류의 특수 opcode일 가능성이 크다.
- 문자열 출력이나 파일 I/O를 호출하는 case가 있다면(REV-0761 방식으로 CRT 함수 확인), 이는 이 VM이 단순 계산기가 아니라 부수 효과(side effect)를 갖는 완전한 인터프리터라는 뜻이다.

## 흔한 실수
- 표를 만들지 않고 코드만 읽다가 이미 분석한 case를 다시 분석하거나, 반대로 일부 case를 빠뜨리는 것.
- 비슷해 보이는 핸들러를 "같은 패턴이니 안 봐도 된다"고 넘겼다가, 실제로는 시프트 방향이나 부호 처리가 미묘하게 달라 전체 재현 결과가 틀리는 것 — 그룹화는 어디까지나 읽는 속도를 높이기 위한 것이지, 검증을 생략해도 된다는 뜻이 아니다.
- case 값과 핸들러 주소만 표에 적고 "동작 요약"을 비워둔 채 다음 단계(Python 재현)로 넘어가는 것 — 요약이 없으면 나중에 표만 보고는 다시 코드를 열어야 한다.
- enum을 정의하지 않고 숫자 그대로 코드를 계속 읽어, `case 23`이 무슨 의미인지 매번 표를 다시 찾아보는 비효율.

## 막혔을 때 다음 체크
- switch문의 어셈블리 레벨 점프 테이블 구조 자체가 아직 낯설다면 → REV-0441(Switch문 점프 테이블 완전 분석)
- 이 표를 더 큰 분석 노트 체계 안에 통합하고 싶다면 → REV-0770(여러 함수에 걸친 로직을 하나의 흐름으로 정리하는 노트 작성법)
- 표를 다 채운 뒤 실제로 Python 인터프리터로 재현하는 방법이 필요하다면 → REV-0168(정적 분석 결과를 Python 의사코드로 옮기기)
- 이 작업이 전체 Flag 복원 절차에서 어느 단계인지 궁금하다면 → REV-0767(정적분석만으로 Flag 검증 로직을 완전히 복원하는 절차)

## 미니 예제
어떤 crackme가 다음과 같은 바이트코드 인터프리터 루프를 갖고 있다고 하자.

```c
while (pc < len) {
    op = bytecode[pc++];
    switch (op) {
        case 0: stack[sp++] = stack[--sp] + stack[--sp]; break; // ADD
        case 1: stack[sp++] = stack[--sp] - stack[--sp]; break; // SUB
        case 2: stack[sp++] = input[bytecode[pc++]]; break;     // PUSH_INPUT
        ...
        case 47: return stack[--sp] == 0;                       // CMP_ZERO_RET
    }
}
```

점프 테이블을 세어보니 총 48개(0~47) case가 있다. 표를 만들어 하나씩 채우면:

| case | 요약 |
|---|---|
| 0 | ADD |
| 1 | SUB |
| 2 | PUSH_INPUT (입력 바이트 하나를 스택에 push) |
| ... | ... |
| 47 | 스택 top이 0이면 성공(반환값 결정) |

이렇게 48개를 전부 채운 뒤에는 이 표 자체가 곧 "이 VM의 명령어 집합 문서"가 되고, REV-0168 방식으로 Python 딕셔너리(`{0: lambda a,b: a+b, 1: lambda a,b: a-b, ...}`)로 그대로 옮겨 원본 바이트코드를 해석하는 인터프리터를 재현할 수 있다.

## 관련 글
- REV-0441 — Switch문 점프 테이블(Jump Table) 완전 분석

- REV-0770 — 여러 함수에 걸친 로직을 하나의 흐름으로 정리하는 노트 작성법
- REV-0767 — 정적분석만으로 Flag 검증 로직을 완전히 복원하는 절차

## 출처/검증
- switch문의 점프 테이블 컴파일 방식과 IDA/Ghidra의 배열 변환·Xref·enum 지정 기능은 각 도구의 공식 문서(Hex-Rays User Guide, Ghidra Help) 기준으로 정리했다.
- 커스텀 가상 머신(opcode 디스패치 루프) 구조 분석 방법론은 CTF reverse 카테고리에서 널리 통용되는 VM-crackme 분석 관행에 기반했다.
