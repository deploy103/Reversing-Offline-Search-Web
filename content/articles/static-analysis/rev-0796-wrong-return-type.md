## 한 줄 요약
디컴파일러는 함수 자체의 선언이 아니라 "호출한 쪽이 `eax`/`rax`(x86-64 반환 레지스터)를 실제로 읽어서 쓰는지"를 관찰해 반환 타입의 존재 여부와 크기를 추측하므로, 호출자가 반환값의 일부만 쓰거나(`al`만), 아예 무시하거나, 반대로 우연히 남아 있던 값을 잘못 읽으면 실제 함수 의미와 다른 반환 타입(`void`인데 `int`로, 혹은 그 반대로)이 붙을 수 있으며, 이때는 함수 원형을 `Y`나 Edit Function으로 직접 지정해서 고쳐야 한다.

## 언제 검색해야 하나
- Pseudocode에서 `v1 = sub_401200(...)`처럼 반환값을 받는 변수(`result`, `v1` 등)가 생기는데, 그 변수가 이후 어디에도 쓰이지 않을 때
- 함수가 명백히 `void`처럼 동작하는데(예: 화면 출력만 하는 함수) 디컴파일 결과에는 정수를 반환하는 것처럼 보일 때
- 반대로 함수가 분명히 성공/실패 값을 리턴하는데 호출부에서는 그 값을 아예 안 받아서, 반환 타입이 `void`로 잘못 잡혀 있을 때
- 함수 여러 종료 경로(return) 중 일부만 값을 설정하고 나머지는 설정하지 않는(uninitialized) 것처럼 보일 때

## 핵심 개념
x86-64에서 정수/포인터 반환값은 관례적으로 `rax`(또는 그 서브레지스터 `eax`/`ax`/`al`)에 담겨 돌아온다. 디컴파일러는 함수 정의 자체에 명시적 타입 정보가 없으면(원형이 지정 안 된 상태) 다음을 관찰해서 반환 타입을 추측한다: 함수가 끝나기 직전 `eax`에 의미 있는 값을 설정하는가, 그리고 호출한 쪽에서 그 `eax`를 실제로 읽어서 쓰는가. 이 추측은 다음과 같은 이유로 어긋난다.

1. **호출자가 반환값을 무시함**: 함수는 실제로 유의미한 값을 `eax`에 남기지만, 모든 호출부가 그 값을 안 쓰면 디컴파일러가 "반환값이 안 쓰이니 `void`나 다름없다"고 표시해버릴 수 있다(실제로는 값이 있는데 그냥 아무도 안 읽는 것뿐).
2. **부분 폭만 사용**: 함수가 사실은 1바이트(`bool`류 성공/실패)만 의미 있게 설정하는데, 호출자가 상위 비트까지 포함한 `eax` 전체를 정수로 취급해서 읽으면 쓰레기 상위 비트가 섞인 값으로 보일 수 있다. 반대로 함수가 `eax` 전체를 의미 있게 채우는데 호출자가 `al`(하위 1바이트)만 확인하면, 디컴파일러가 반환 타입을 실제보다 작게(`char`) 추정할 수 있다.
3. **일부 종료 경로에서만 반환값 설정**: 함수 안에 여러 `return`이 있는데, 어떤 경로는 `eax`를 명시적으로 설정하고 어떤 경로는 그냥 함수 끝(에필로그)으로 흘러가 `eax`에 이전 계산의 잔여값이 우연히 남아 있는 경우, 이 경로는 사실 "반환값 없음(void 의도)"인데 디컴파일러는 우연히 남은 값을 진짜 반환값처럼 취급할 수 있다.
4. **부동소수점 반환**: x86-64는 float/double을 `xmm0`으로 반환하는데, 함수가 실제로는 정수를 반환하면서 `xmm0`를 안 건드리면 디컴파일러가 반환 타입을 완전히 헷갈릴 수 있다.

## 화면/코드에서 보이는 징후
- 반환값을 받는 변수가 생성되지만 이후 전혀 사용되지 않음(죽은 코드처럼 보임)
- 함수가 여러 `return` 경로를 가지는데 그 중 일부에서만 `eax`가 명시적으로 설정됨
- 호출부에서 반환값의 하위 1바이트(`al`)만 `if` 조건으로 검사하는데, 함수 원형은 `int`(4바이트) 전체를 반환하는 것으로 나옴
- 함수 내부에 부동소수점 연산이 있는데 반환 타입은 정수로 표시됨

## 가장 먼저 할 것
문제 함수의 모든 종료 지점(`ret`)에서 실제로 `eax`/`al`/`xmm0` 중 무엇을 설정하는지 디스어셈블리로 직접 확인하고, 모든 호출부에서 그 반환값을 실제로 읽어서 조건/대입에 쓰는지 대조한다.

## 단계별 절차

**1) 함수의 모든 종료 지점 확인**
그래프 뷰(REV-0150)로 함수의 모든 `ret` 지점을 찾고, 각 지점 직전에 `eax`/`al`/`xmm0`를 설정하는 명령이 있는지 확인한다. 일부 경로만 설정한다면 그 함수의 진짜 의도가 "조건부로만 값을 리턴"인지, 아니면 사실 그 경로들도 뭔가 값을 리턴해야 하는데 컴파일러가 최적화로 생략한 것인지 판단한다.

**2) 호출부에서 실제 사용 여부와 폭 확인**
`Ctrl+X`로 호출부를 모아, 각 호출 직후 `eax`(4바이트), `al`(1바이트) 중 어느 크기로 읽는지, 아니면 아예 안 읽는지 확인한다.

**3) 원형 직접 지정**
함수 시작에서 `Y`를 눌러 정확한 반환 타입을 지정한다(`void`, `int`, `char`, `bool`, `double` 등). 부분폭만 의미 있다면 `char`나 `_BOOL1`처럼 작은 타입으로 지정해 상위 쓰레기 비트를 표시에서 제거한다.

**4) 재분석**
F5로 다시 디컴파일하고, 모든 호출부에서 반환값 사용이 자연스럽게 보이는지 재확인한다.

## 명령어/단축키
- `Y`: 함수/변수 타입·원형 지정(반환 타입 포함)
- `Ctrl+X`: 호출부 Xref 목록
- 그래프 뷰(Space): 함수의 모든 종료 경로(ret) 한눈에 보기
- Ghidra: 함수 우클릭 → Edit Function Signature에서 Return Type 필드 수정

## 출력 해석
- 반환 타입을 `void`로 바꿨는데도 호출부에서 `result` 변수가 계속 생긴다면, 그 호출부가 반환 레지스터를 실제로 읽는 코드가 남아 있다는 뜻이므로 그 부분을 다시 확인해야 한다.
- 타입을 `char`/`bool`로 좁혔더니 이전에 보이던 이상한 큰 값들이 사라지고 0/1만 남는다면, 원래 함수 의도가 성공/실패 플래그였다는 것이 확정된다.

## 흔한 실수
- 반환값을 아무도 안 쓴다고 해서 무조건 `void`로 단정하는 것 — 일부 호출부에서만 값을 쓸 수도 있으므로 모든 호출부를 다 확인해야 한다.
- `eax` 전체와 `al`을 구분하지 않고 아무 정수 타입이나 지정하는 것 — 실제 어셈블리가 몇 바이트를 다루는지 반드시 확인한다.
- 여러 return 경로 중 하나만 보고 반환 타입을 결정하는 것 — 다른 경로에서 다르게 동작할 수 있다.
- 부동소수점 반환(`xmm0`)을 놓치고 정수 레지스터(`eax`)만 확인하는 것.

## 미니 예제
`sub_401400`이 항상 `int` 반환으로 디컴파일되지만, 세 곳의 호출부를 모두 확인해보니 전부 `if ((sub_401400(...) & 0xFF) == 1)`처럼 하위 1바이트만 검사한다고 하자. 함수 본문을 그래프 뷰로 확인하니 모든 `ret` 직전에 `al`만 0 또는 1로 설정하고 상위 바이트는 건드리지 않는다. 이는 원래 `bool`(또는 1바이트 성공/실패 코드) 반환 함수였음을 의미하므로, `Y`로 반환 타입을 `_BOOL1`(또는 `char`)로 좁혀 지정하면 이후 상위 쓰레기 비트 없이 깔끔한 `if (sub_401400(...))` 형태로 정리된다.

## 출처/검증
- x86-64 반환값 레지스터 규칙(정수/포인터는 RAX, 부동소수점은 XMM0)은 System V ABI AMD64 문서 및 Microsoft x64 calling convention 공식 문서 기준.
- 디컴파일러가 반환 타입을 호출부의 실제 사용 패턴으로 추론한다는 원리는 Hex-Rays 공식 문서(디컴파일러 동작 원리 관련 챕터) 기준.
- Ghidra의 Edit Function Signature에서 Return Type을 수동 편집하는 절차는 Ghidra 공식 문서(Functions 관련 챕터) 기준.
