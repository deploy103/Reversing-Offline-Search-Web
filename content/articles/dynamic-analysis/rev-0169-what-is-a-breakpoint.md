## 한 줄 요약
Breakpoint(브레이크포인트, 중단점)는 "프로그램이 특정 주소나 조건에 도달하면 실행을 잠시 멈추라"고 디버거에게 지시하는 표시이며, 정적 분석만으로는 알 수 없는 실제 실행 시점의 값(레지스터, 메모리, 리턴값)을 확인하기 위한 동적 분석의 출발점이다.

## 언제 검색해야 하나
- 디버거를 처음 켜봤는데 그냥 F9(실행)를 누르면 프로그램이 끝까지 실행되거나 창이 닫혀버려서 뭘 봐야 할지 모를 때
- "브레이크포인트를 걸어라"라는 말은 들었는데 실제로 어느 주소에, 어떤 기준으로 걸어야 하는지 감이 안 잡힐 때
- x64dbg에서 F2를 눌렀는데 빨간 점이 안 생기거나, GDB에서 `break`를 쳤는데 실행이 멈추지 않을 때
- 특정 값이 특정 값이 될 때만 멈추고 싶은데(조건부 브레이크포인트) 어떻게 설정하는지 모를 때
- 소프트웨어 브레이크포인트와 하드웨어 브레이크포인트의 차이, 그리고 안티디버깅 코드가 왜 이걸 감지할 수 있는지 궁금할 때

## 핵심 개념

### Breakpoint란 무엇인가
Breakpoint는 실행 흐름 중 "여기서 멈춰라"라고 지정한 위치(주소) 또는 조건이다. 디버거가 프로그램을 실행시키다가 그 지점에 도달하면 CPU 실행을 일시 정지시키고, 그 순간의 레지스터/스택/메모리 상태를 그대로 사용자에게 보여준다. 정적 분석(IDA, Ghidra로 코드만 읽는 것)은 "이 시점에 이 레지스터에 어떤 값이 들어있을 것이다"를 추측만 할 수 있지만, 브레이크포인트로 실제 실행을 멈추면 그 값을 눈으로 직접 확인할 수 있다. 이것이 정적 분석과 동적 분석을 잇는 핵심 도구다.

### 소프트웨어 브레이크포인트 (Software Breakpoint)
가장 흔히 쓰는 방식이다. 디버거가 브레이크포인트를 걸 주소의 원본 바이트를 백업해 두고, 그 자리를 `INT3` 명령어(x86/x64 기계어로 `0xCC` 한 바이트)로 덮어쓴다. CPU가 실행 중 `0xCC`를 만나면 자동으로 예외(브레이크포인트 예외, INT 3)를 발생시키고, 디버거는 이 예외를 가로채서 실행을 멈춘 뒤 원래 바이트를 되돌려 놓는다.
- 장점: 개수 제한이 사실상 없다(원하는 만큼 여러 곳에 걸 수 있다).
- 단점: 코드 영역의 바이트를 실제로 수정하기 때문에, 프로그램이 자기 코드를 체크섬 검사하거나(코드 무결성 검사) 자기 자신을 읽어서 `0xCC`가 있는지 스캔하는 안티디버깅 기법에 걸릴 수 있다.

### 하드웨어 브레이크포인트 (Hardware Breakpoint)
CPU에 내장된 디버그 레지스터(x86/x64에서는 DR0~DR7)를 이용한다. 코드를 수정하지 않고, "이 주소에 접근하면(실행/읽기/쓰기) 멈춰라"는 조건을 CPU 레지스터에 직접 등록한다. CPU가 하드웨어 수준에서 감시하다가 조건이 맞으면 자동으로 멈춘다.
- 장점: 코드를 건드리지 않으므로 코드 무결성 검사를 우회한다. 또한 **메모리 읽기/쓰기**에도 걸 수 있다(소프트웨어 브레이크포인트는 실행에만 건다) — 이것이 워치포인트(watchpoint)다.
- 단점: 디버그 레지스터 개수가 보통 4개뿐이라(DR0~DR3) 동시에 4개까지만 걸 수 있다.

### 워치포인트(Watchpoint)란
특정 메모리 주소에 "값이 바뀌는 순간" 또는 "값을 읽는 순간" 멈추도록 거는 브레이크포인트의 한 종류다. 하드웨어 브레이크포인트 메커니즘을 사용하며, "이 변수가 도대체 어디서 바뀌는지 모르겠다" 같은 문제를 풀 때 매우 유용하다. x64dbg에서는 메모리 주소를 우클릭 → "Set Hardware Access/Write Breakpoint"로, GDB에서는 `watch <주소식>` 명령으로 건다.

### 조건부 브레이크포인트 (Conditional Breakpoint)
단순히 "이 주소에 도달하면 멈춰라"가 아니라 "이 주소에 도달했는데 특정 조건이 참일 때만 멈춰라"로 설정할 수 있다. 예를 들어 반복문 안의 CALL에 브레이크포인트를 걸었는데 100번 넘게 반복되는 루프라면, 매번 멈추는 대신 "카운터 변수가 50일 때만 멈춰라" 같은 조건을 걸어 원하는 순간만 빠르게 찾을 수 있다.

### 어디에 걸어야 하는가 — 실전 판단 기준
막연히 "여기쯤"이 아니라 목적에 따라 위치가 명확히 갈린다.
1. **입력이 처리되는 지점을 보고 싶다** → `scanf`, `fgets`, `read`, `gets` 같은 입력 함수의 **호출 직후**(CALL 다음 명령 주소)에 건다. 이 시점에는 입력 버퍼에 실제 사용자 입력이 채워져 있다(REV-0195 참고).
2. **함수 인자를 확인하고 싶다** → 목표 CALL 명령어의 **주소 자체**에 건다. 이 시점에는 아직 CALL이 실행되지 않았으므로 인자 레지스터(RDI/RSI/... 또는 RCX/RDX/...)에 세팅된 값을 그대로 볼 수 있다(REV-0175 참고).
3. **반환값을 확인하고 싶다** → CALL **다음 명령어** 주소에 건다. 이 시점에는 RAX/EAX에 반환값이 이미 들어가 있다(REV-0176 참고).
4. **분기 결과가 왜 그렇게 나오는지 보고 싶다** → 분기 명령(`je`, `jne`, `jg` 등) **직전의 `cmp`/`test`** 명령어 주소에 건다(REV-0174 참고).
5. **문자열이 언제 만들어지는지 모르겠다** → 그 문자열을 참조하는 코드 위치(IDA에서 문자열 더블클릭 → Xref로 찾은 주소)에 건다.
6. **특정 변수가 언제 바뀌는지 모르겠다** → 해당 메모리 주소에 워치포인트(하드웨어 접근/쓰기 브레이크포인트)를 건다.

핵심은 "무작정 시작 지점(entry point)에 걸고 F8을 수백 번 누르지 않는다"는 것이다. 먼저 정적 분석(IDA/Ghidra)으로 관심 있는 함수나 분기, CALL, 문자열 참조 위치를 특정한 다음, 그 주소에 정확히 브레이크포인트를 걸고 F9(또는 `continue`)로 단번에 그 지점까지 실행시키는 것이 훨씬 빠르다.

## 화면/코드에서 보이는 징후
- x64dbg에서 브레이크포인트가 걸린 줄은 디스어셈블리 창에서 **빨간 점 + 빨간 배경**으로 표시된다.
- x64dbg 하단 "Breakpoints" 탭에 걸어놓은 모든 브레이크포인트 목록(주소, 타입, 상태)이 나온다.
- GDB에서 `break`로 걸면 `Breakpoint 1 at 0x401234` 같은 메시지가 뜨고, `info breakpoints`로 전체 목록을 볼 수 있다.
- 실행이 브레이크포인트에서 멈추면 x64dbg는 해당 줄이 노란색 화살표로, GDB는 `Breakpoint 1, 0x0000000000401234 in main ()` 같은 메시지로 현재 위치를 알려준다.

## 가장 먼저 할 것
1. IDA/Ghidra 등 정적 분석 도구로 "어디를 봐야 하는지" 먼저 특정한다(문자열 Xref, 함수 이름, 분기 위치 등).
2. 디버거로 대상 바이너리를 로드한다(x64dbg: 파일 열기 또는 프로세스 attach / GDB: `gdb ./binary`).
3. 확정한 주소에 브레이크포인트를 건다.
4. F9(x64dbg) 또는 `run`/`continue`(GDB)로 실행해서 그 지점까지 단번에 도달시킨다.

## 단계별 절차

**x64dbg**
1. 디스어셈블리 창에서 브레이크포인트를 걸 명령어 줄을 클릭해서 선택한다.
2. `F2`를 누른다 — 해당 줄에 빨간 점이 생긴다(소프트웨어 브레이크포인트, `INT3` 삽입).
3. 다시 `F2`를 누르면 브레이크포인트가 해제된다(토글 방식).
4. 주소를 직접 입력해서 걸고 싶으면 명령창(Command bar)에 `bp 0x401234` 를 입력한다.
5. 조건부로 걸고 싶으면 브레이크포인트를 우클릭 → "Edit breakpoint"에서 조건식(예: `eax == 5`)을 입력한다.
6. 메모리 접근/쓰기를 감시하고 싶으면 Dump 창이나 Memory Map에서 주소를 우클릭 → "Breakpoint" → "Hardware, Access"/"Hardware, Write"를 선택한다(하드웨어 브레이크포인트).
7. `F9`를 눌러 실행하면 브레이크포인트에서 자동으로 멈춘다.

**GDB / Pwndbg**
1. 함수 이름이나 주소로 소프트웨어 브레이크포인트를 건다:
   ```
   break main
   break *0x401234
   ```
2. 하드웨어 실행 브레이크포인트가 필요하면(코드 무결성 검사를 우회하고 싶을 때):
   ```
   hbreak *0x401234
   ```
3. 메모리 값 변경/읽기를 감시하려면(워치포인트):
   ```
   watch *(int*)0x601020    ; 값이 바뀔 때 멈춤
   rwatch *(int*)0x601020   ; 값을 읽을 때 멈춤
   awatch *(int*)0x601020   ; 읽기/쓰기 모두 멈춤
   ```
4. 조건부 브레이크포인트:
   ```
   break *0x401234 if $eax == 5
   ```
5. 브레이크포인트 목록/삭제:
   ```
   info breakpoints
   delete 1
   ```
6. 실행/재개:
   ```
   run
   continue    (또는 c)
   ```

## 명령어/단축키
- x64dbg: `F2`(브레이크포인트 토글), `F9`(실행/계속), 명령창 `bp <주소>`, `bp <주소>,"<조건식>"`, Dump 우클릭 → Hardware Breakpoint
- GDB/Pwndbg: `break <함수/주소>`, `hbreak <주소>`(하드웨어), `watch <expr>`(쓰기 감시), `rwatch`(읽기 감시), `awatch`(읽기+쓰기), `tbreak <주소>`(한 번만 멈추는 임시 브레이크포인트), `delete <번호>`, `info breakpoints`, `run`, `continue`(`c`)

## 출력 해석
- x64dbg 상태 표시줄에 "Paused"가 뜨면 브레이크포인트에서 정지한 상태다. 이때 레지스터 창, 스택 창, Dump(메모리) 창의 값이 모두 그 순간의 실제 값으로 갱신된다.
- GDB에서 `Breakpoint 1, 0x0000000000401234 in target_func ()`가 출력되면, 어느 브레이크포인트(1번)에서 어느 함수 어느 주소에서 멈췄는지 알려주는 것이다.
- 브레이크포인트가 여러 번 걸리는 함수(반복 호출되는 함수)라면, 매번 같은 위치에서 다시 멈추므로 `continue`/`F9`를 반복해서 원하는 호출 차례까지 진행해야 한다. 이때 조건부 브레이크포인트를 쓰면 훨씬 빠르다.

## 흔한 실수
- 시작하자마자(entry point) 아무 조건 없이 F9만 계속 눌러서 프로그램이 그냥 끝나버리는 것 — 먼저 정적 분석으로 목표 주소를 정한다.
- 소프트웨어 브레이크포인트가 안티디버깅(자기 코드 체크섬 검사)에 걸려 프로그램이 이상 동작하는데 원인을 못 찾는 것 — 이런 경우 하드웨어 브레이크포인트(`hbreak`, x64dbg의 Hardware Breakpoint)로 바꿔본다.
- 라이브러리 함수 내부(예: `printf` 내부)에 브레이크포인트를 걸고 왜 소스가 안 보이냐고 헤매는 것 — 심볼이 없는 시스템 라이브러리는 디스어셈블리로만 보인다. 필요하면 해당 CALL 자체(호출 지점)에 거는 게 낫다.
- 브레이크포인트를 건 걸 잊고 다시 실행해서 예상치 못한 곳에서 멈추는 것 — `info breakpoints`(GDB)나 Breakpoints 탭(x64dbg)으로 항상 현재 걸려있는 목록을 확인하는 습관을 들인다.
- ASLR(주소 랜덤화)이 걸린 프로세스에서 절대 주소로 브레이크포인트를 걸어놓고 재실행할 때마다 안 멈춘다고 착각하는 것 — 실행할 때마다 베이스 주소가 바뀔 수 있으므로 함수 이름 기준(`break main`) 또는 모듈 베이스 기준 오프셋으로 걸어야 한다.

## 막혔을 때 다음 체크
- 브레이크포인트를 걸었는데 전혀 안 멈춘다면 → 그 코드 경로가 실제로 실행되는지(조건문에 의해 건너뛰어지는 건 아닌지) 먼저 의심한다.
- ASLR/PIE 바이너리인데 절대 주소로 걸었다면 → 모듈 베이스 주소를 확인하고(x64dbg Memory Map, GDB `info proc mappings`) 오프셋을 다시 계산하거나 함수 이름으로 건다.
- 소프트웨어 브레이크포인트를 걸었더니 프로그램이 크래시하거나 이상하게 동작한다면 → 안티디버깅/코드 체크섬 검사를 의심하고 하드웨어 브레이크포인트로 전환한다.
- 반복문 안이라 너무 자주 멈춘다면 → 조건부 브레이크포인트를 걸거나, 일단 브레이크포인트를 비활성화(disable)한 뒤 원하는 시점 근처에서 다시 활성화한다.

## 미니 예제

**x64dbg — CALL 직전에 브레이크포인트를 걸어 인자 확인**
```
; IDA에서 확인한 주소: 0x00401234에 call sub_401500 이 있다고 가정
```
1. x64dbg 디스어셈블리 창에서 `Ctrl+G`로 `0x00401234` 이동
2. 해당 줄 클릭 후 `F2`
3. `F9`로 실행 → 그 주소에서 정지
4. 레지스터 창에서 RCX/RDX(Windows x64) 또는 RDI/RSI(SysV) 값 확인

**GDB/Pwndbg — 조건부 브레이크포인트로 반복문 특정 회차만 멈추기**
```
break *0x401234 if $rdi == 50
run
```
→ 이 CALL이 여러 번 실행되더라도, RDI 값이 50일 때만 정확히 멈춘다.
