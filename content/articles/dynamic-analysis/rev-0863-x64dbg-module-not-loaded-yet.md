## 한 줄 요약
아직 프로세스 메모리에 로드되지 않은 DLL(또는 지연 로드 모듈) 안의 함수·주소에 x64dbg로 브레이크포인트를 걸려고 하면 그 주소가 아직 유효한 메모리로 존재하지 않아 브레이크포인트가 걸리지 않거나 무시되며, 이럴 때는 `bpdll`로 모듈 로드 이벤트 자체에 먼저 걸어 그 모듈이 뜨는 순간을 잡은 뒤 실제 목표 위치에 다시 브레이크포인트를 걸어야 한다.

## 언제 검색해야 하나
- 분석 대상 DLL 안의 함수 이름이나 주소로 `bp <모듈>.<함수>`를 걸었는데 x64dbg가 "이 심볼을 찾을 수 없습니다" 또는 걸리긴 했는데 실행해도 전혀 히트되지 않을 때
- 지연 로드(Delay-Load) DLL이라서 프로그램 시작 시점에는 그 모듈이 아직 메모리에 없는 경우(REV-0620 참고)
- 특정 플러그인/DLL이 `LoadLibrary`로 나중에 동적으로 로드되는 구조라서, 언제 로드되는지 미리 알 수 없을 때
- Memory Map(REV-0182 참고)에서 확인해보니 목표 모듈이 아예 목록에 없을 때

## 핵심 개념

### 왜 로드 전에는 브레이크포인트를 걸 수 없는가
소프트웨어 브레이크포인트는 목표 주소의 원본 바이트를 `INT3`(0xCC)로 덮어써서 동작한다(REV-0169 참고). 그런데 그 모듈이 아직 프로세스 주소 공간에 매핑되지 않았다면, 애초에 "덮어쓸 메모리"가 존재하지 않는다. 그래서 모듈이 로드되기 전에 그 안의 함수 주소나 심볼로 브레이크포인트를 걸면, x64dbg는 심볼을 해석하지 못하거나(이름 기반), 걸었더라도 실제로는 무효한 주소를 가리키고 있어 실행 중 아무 일도 일어나지 않는다.

### bpdll — 모듈 로드 시점 자체에 거는 브레이크포인트
x64dbg는 `bpdll <모듈이름>` 명령으로 "이 이름의 모듈이 로드되는 순간"에 자동으로 멈추는 특수한 브레이크포인트를 지원한다. 이는 목표 DLL 내부의 특정 주소가 아니라, Windows 로더가 그 DLL을 매핑하는 시점 자체를 잡는 것이라 모듈이 아직 로드되기 전이어도 걸 수 있다. 이 브레이크포인트가 히트되면, 그 시점에는 이미 대상 모듈이 메모리에 매핑되어 있으므로 그제서야 원하는 실제 함수/주소에 일반 브레이크포인트를 걸 수 있다.

### 심볼 이름 기반 브레이크포인트의 "pending" 동작
`bp <모듈>.<함수>` 형태로 아직 로드되지 않은 모듈의 심볼을 지정하면, 일부 상황에서는 x64dbg가 이를 대기(pending) 상태로 등록해 두었다가 나중에 해당 모듈이 로드되면 자동으로 실제 주소를 해석해 브레이크포인트를 활성화하기도 한다. 하지만 이는 항상 보장되는 동작이 아니므로, 확실하게 잡고 싶다면 `bpdll`로 로드 이벤트를 직접 거는 방식이 더 안정적이다.

### TLS 콜백과의 관계
DLL/EXE에 TLS 콜백이 있는 경우, `EntryPoint`보다도 먼저 실행되므로 "아직 로드 전"이라고 생각했던 시점에 이미 다른 코드가 실행되고 있을 수 있다. 원하는 모듈이 예상보다 훨씬 이른 시점에 로드될 수 있으므로 TLS 콜백 관련 문제(REV-0588)와 함께 고려해야 한다.

## 화면/코드에서 보이는 징후
- Memory Map(REV-0182)이나 Symbols 창에서 목표 DLL 이름이 아예 보이지 않는다.
- `bp 목표DLL.함수이름` 명령 실행 시 "지정한 모듈을 찾을 수 없습니다" 또는 유사한 오류/경고가 뜬다.
- Breakpoints 탭에는 등록되어 있는 것처럼 보이는데, 프로그램을 실행(`F9`)해도 전혀 멈추지 않는다.
- Log 창에 `DLL Loaded: <다른 모듈들>`만 계속 출력되고 목표 DLL의 로드 로그가 아직 안 보인다.

## 가장 먼저 할 것
1. Log 창을 열어 지금까지 어떤 모듈이 로드되었는지 확인한다(`DLL Loaded:` 로그).
2. 목표 모듈이 아직 로드되지 않았다면, 그 모듈을 로드시키는 API(`LoadLibrary`, 지연 로드 스텁 등)를 찾거나 `bpdll`로 로드 이벤트를 건다.
3. 로드된 이후 실제 목표 함수/주소에 다시 정상적으로 브레이크포인트를 건다.

## 단계별 절차
1. 명령창(Command bar)에 목표 DLL 이름으로 로드 이벤트 브레이크포인트를 건다.
   ```
   bpdll target.dll
   ```
2. `F9`로 실행한다. 목표 DLL이 로드되는 순간 자동으로 멈추고 Log 창에 `DLL Loaded: target.dll`이 표시된다.
3. 이 시점에 Memory Map(REV-0182)이나 Symbols 창을 새로고침하면 이제 `target.dll`이 목록에 나타난다.
4. 이제 정상적으로 원하는 함수/주소에 브레이크포인트를 건다.
   ```
   bp target.dll.ExportedFunc
   ```
   또는 Symbols 창에서 직접 더블클릭해 디스어셈블리로 이동한 뒤 `F2`로 건다.
5. 더 이상 필요 없다면 `bpdll` 브레이크포인트는 삭제하거나 비활성화한다.
6. 지연 로드(Delay-Load) DLL이라 언제 로드되는지 짐작이 안 된다면, 먼저 REV-0620을 참고해 지연 로드 임포트의 특징(처음엔 안 보이다가 특정 API 호출 시점에 로드됨)을 확인한다.

## 명령어/단축키
- `bpdll <모듈이름>` — 지정한 이름의 모듈이 로드되는 순간 멈추는 브레이크포인트
- `bp <모듈>.<함수>` — 모듈+함수 이름 기반 브레이크포인트(모듈이 로드된 이후에 사용해야 안정적)
- Log 창 — `DLL Loaded:` / `DLL Unloaded:` 이벤트 실시간 확인
- Memory Map(`Alt+M`류 단축키 또는 탭 클릭) — 현재 로드된 모듈 목록 확인

## 출력 해석
- Log 창에 `DLL Loaded: C:\...\target.dll`이 출력되면 이제부터 그 모듈 내부 주소는 유효한 메모리로 존재한다는 뜻이다.
- `bpdll` 브레이크포인트에서 멈춘 직후 디스어셈블리 창은 보통 Windows 로더 내부(`ntdll.dll`) 코드를 보여준다 — 이는 정상이며, 목표 DLL 자체의 코드를 보려면 이제 Symbols 창에서 해당 모듈로 다시 이동해야 한다.

## 흔한 실수
- 프로그램 시작 직후 곧바로 목표 DLL 내부 함수에 브레이크포인트부터 걸려고 시도해서 계속 실패하는 것 — 로드 여부를 먼저 확인해야 한다.
- `bpdll`을 걸어놓고 그 즉시 목표 함수까지 자동으로 멈출 거라 기대하는 것 — `bpdll`은 로드 시점에서 한 번 멈출 뿐이며, 실제 목표 지점에는 그 이후 별도로 브레이크포인트를 걸어야 한다.
- 지연 로드 DLL의 특성(REV-0620)을 모르고 "이 DLL은 임포트 테이블에 있으니 처음부터 로드되어 있겠지"라고 착각하는 것.

## 막혔을 때 다음 체크
- `bpdll`을 걸었는데도 전혀 히트되지 않는다면 → 모듈 이름 철자(대소문자, 확장자 포함 여부)를 다시 확인한다.
- 로드는 확인됐는데 그 안의 특정 함수에 브레이크포인트가 여전히 안 걸린다면 → Export가 이름 없이 Ordinal로만 되어 있지 않은지 확인한다(REV-0555 참고).
- TLS 콜백 때문에 예상보다 이른 시점에 다른 코드가 실행되는 것 같다면 → REV-0588을 참고한다.

## 미니 예제
```
(x64dbg 명령창) bpdll target.dll
F9 실행
[Log] DLL Loaded: C:\chall\target.dll
→ 자동으로 정지, 이 시점에 target.dll이 Memory Map에 나타남

(x64dbg 명령창) bp target.dll.CheckSerial
F9 실행
→ CheckSerial 함수 진입 시 정상적으로 멈춤
```

## 관련 글
- REV-0620 — Delay-Load Import가 처음엔 안 보여서 함수가 없다고 착각할 때
- REV-0588 — TLS 콜백 때문에 브레이크포인트가 먼저 안 걸릴 때
- REV-0182 — x64dbg Memory Map과 Module View
- REV-0169 — Breakpoint가 무엇이고 어디에 걸어야 하는가

## 출처/검증
- `bpdll` 명령과 모듈 로드 이벤트 브레이크포인트 동작: x64dbg 공식 문서(Commands, Breakpoints) 기준.
- 소프트웨어 브레이크포인트가 실제 매핑된 메모리에만 걸릴 수 있다는 제약: x64dbg 및 Windows 디버깅 일반 동작(INT3 삽입 방식) 기준.
