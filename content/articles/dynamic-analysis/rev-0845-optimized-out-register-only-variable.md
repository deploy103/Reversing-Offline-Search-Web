## 한 줄 요약
릴리즈/최적화 빌드(`-O2`, `/O2`)에서 GDB가 `<optimized out>`을, x64dbg의 Locals 창이 아예 빈 칸을 보여주는 것은 버그가 아니라 "지금 멈춘 지점에서는 그 변수가 레지스터에도 스택에도 대응하는 위치가 없다"는 정직한 보고이므로, 브레이크포인트 위치를 그 값이 살아있는 구간으로 옮기거나 디스어셈블리/디컴파일러로 직접 역추적해야 한다.

## 언제 검색해야 하나
- GDB `print 변수`에 `$1 = <optimized out>`이 뜰 때
- x64dbg Locals 창에 특정 변수가 아예 안 보이거나 회색으로 비활성화될 때
- 릴리즈 빌드를 디버깅하는데 변수 흐름을 따라가다가 계속 막힐 때
- 소스가 있는데도 재컴파일 없이 최적화된 바이너리에서 로컬 변수를 확인하고 싶을 때

## 핵심 개념

### 왜 이런 일이 생기는가(요약)
`-O0`(디버그 빌드)는 모든 지역 변수를 스택의 고정 위치에 저장해 함수 어디서 멈추든 항상 같은 곳에서 읽을 수 있다. 반면 `-O2`(릴리즈 빌드)는 변수가 실제로 필요한 구간에서만 레지스터에 잠깐 존재하다가, 그 구간이 끝나면 컴파일러가 즉시 그 레지스터를 재사용해버린다. 컴파일 타임에 값이 완전히 계산되어 상수로 접힌 경우는 애초에 런타임 위치 자체가 없다. 디버그 정보(DWARF `.debug_loc`, Windows PDB)는 이 변화를 "PC 구간별 위치 리스트"로 기록하며, 지금 멈춘 PC가 "위치 없음" 구간이면 GDB/x64dbg는 정직하게 값을 못 보여준다. 이 메커니즘 자체의 상세한 원리(위치 리스트 읽는 법, DWARF `.debug_loc` 덤프, Ghidra 정적 데이터 흐름으로 복원하는 법)는 REV-0463에서 깊이 다룬다. 이 글은 지금 이 상황에 부딪혔을 때 무엇부터 확인할지에 집중한다.

### 실전 체크리스트로 접근하기
1. 지금 멈춘 지점이 그 변수의 "살아있는 구간" 밖일 가능성이 가장 크다 — 브레이크포인트 위치를 바꾸는 것이 가장 빠른 해결책이다.
2. 소스 코드가 있다면 같은 소스를 디버깅 친화적인 옵션(`-Og`/`-O0`, Windows는 `/Od` 또는 Debug 구성)으로 재컴파일해서 먼저 로직을 이해한 뒤, 최적화된 바이너리로 대조하는 것이 가장 확실하다.
3. 소스가 없거나 재컴파일이 불가능하면(스트립된 릴리즈 바이너리), 디스어셈블리에서 그 값이 마지막으로 쓰인 지점을 역추적하거나, Ghidra/IDA의 디컴파일러가 재구성한 수식을 1차 근거로 삼는다.

## 화면/코드에서 보이는 징후
```gdb
(gdb) print sum
$1 = <optimized out>
```
x64dbg Locals 창에서 해당 변수 행 자체가 없거나 회색으로 표시됨. 같은 변수를 다른 브레이크포인트 위치에서 확인했더니 보였다 안 보였다 하는 것도 전형적이다.

## 가장 먼저 할 것
그 변수가 마지막으로 값이 정해지는 소스 라인(또는 그 근처 명령어)으로 브레이크포인트를 옮겨서 다시 확인한다. GDB라면 `info scope 함수이름`으로 그 변수가 유효한 PC 구간을 먼저 확인할 수 있다.

## 단계별 절차
1. `info scope 함수이름`(GDB)으로 변수의 유효 구간 정보를 확인한다.
2. 그 구간 안의 주소에 브레이크포인트를 다시 걸어 값이 사라지기 전에 확인한다.
3. 소스가 있다면 `-Og`/`/Od`로 재컴파일한 디버그 빌드에서 먼저 로직을 파악한다.
4. 소스가 없다면 디스어셈블리에서 현재 PC 위로 거슬러 올라가 그 레지스터/스택 슬롯에 마지막으로 값을 쓴 명령어를 찾는다.
5. Ghidra/IDA `F5` 디컴파일 결과의 수식을 확인하고, 그 수식의 입력 레지스터들을 디버거로 직접 읽어 손으로 계산한다.
6. 완전히 상수로 접힌 값이라면 디스어셈블리의 즉시값(immediate)을 그대로 정답으로 채택한다.

## 명령어/단축키
```gdb
info scope FUNC
info address VAR
print $eax
x/4xb ADDR
```
```bash
readelf --debug-dump=loc a.out
```
```text
x64dbg: CPU/Registers 창 직접 확인, Ctrl+G(주소 이동), IDA/Ghidra F5(디컴파일)
```

## 출력 해석
`<optimized out>`은 "현재 PC에서 유효한 위치 정보가 없다"는 뜻이지 "이 변수가 이 함수에서 안 쓰인다"는 뜻이 아니다. 다른 브레이크포인트 위치에서는 정상적으로 값이 보일 수 있다.

## 흔한 실수
- `<optimized out>`을 보고 바로 포기하거나 그 변수가 안 쓰인다고 오판하는 것.
- 최적화된 코드에서 소스 줄 단위로 정확히 한 줄씩 스텝할 수 있다고 기대하는 것 — 명령어 순서가 재배치/병합되어 소스 줄과 1:1 대응이 깨지는 경우가 흔하다.
- 디컴파일러가 보여주는 값을 "지금 이 순간의 실제 런타임 값"이라고 착각하는 것 — 디컴파일러는 수식을 보여줄 뿐이며 실제 값은 그 입력을 디버거로 읽어야 안다.
- 재컴파일이 가능한 상황인데도 시도해보지 않고 최적화된 바이너리와만 씨름하는 것.

## 막혔을 때 다음 체크
- 위치 리스트(DWARF `.debug_loc`)를 직접 읽는 법과 더 깊은 원리가 필요하다면 → REV-0463 최적화로 사라진 변수를 디버거에서 복원하는 법
- 최적화로 인한 다른 이상 현상(명령어 재배치, 분기 반전 등)이 궁금하다면 → REV-0037 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 이유
- 애초에 레지스터 값 자체를 수정해도 반영이 안 되는 문제라면 → REV-0843 레지스터 값을 수정했는데 프로그램이 무시하는 것처럼 보일 때

## 미니 예제
```c
int compute(int a, int b) {
    int sum = a + b;
    return sum * 2;
}
```
```asm
compute:
    lea   eax, [rdi+rsi]
    add   eax, eax
    ret
```
`return` 직전(`add eax, eax` 실행 후)에 멈춰 `print sum`을 하면 `sum`이 이미 `eax*2`로 소모되어 `<optimized out>`이 뜬다. `lea` 직후로 브레이크포인트를 옮기거나 `print $eax`로 직접 확인하면 값을 볼 수 있다.

## 관련 글
- REV-0463 — 최적화로 사라진 변수를 디버거에서 복원하는 법
- REV-0843 — 레지스터 값을 수정했는데 프로그램이 무시하는 것처럼 보일 때
- REV-0037 — 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 이유

## 출처/검증

- GDB의 `<optimized out>` 표시와 `info scope`/`info address`: GNU GDB 공식 매뉴얼 기준(2026-09-09 검증).
