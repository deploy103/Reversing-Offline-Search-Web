## 한 줄 요약
입력값의 메모리 위치를 어셈블리로 역산하기 어렵다면, **입력 함수(`scanf`/`fgets`/`read`/`recv` 등) 호출 직후 인자 레지스터를 직접 확인**하거나, **남들이 절대 안 쓸 고유한 패턴을 입력한 뒤 메모리 전체를 검색**하는 두 가지 방법으로 거의 항상 찾을 수 있다.

## 언제 검색해야 하나
- IDA/Ghidra 디스어셈블리에서 `lea`/오프셋 계산을 따라가려 했지만 스택 프레임이 복잡하거나 최적화되어 버퍼 주소 계산이 안 될 때
- 입력이 `malloc`으로 동적 할당된 힙 버퍼에 저장되어 스택 오프셋 같은 고정된 계산식이 없을 때
- 입력이 여러 번 복사되어(임시 버퍼 → 파싱 버퍼 → 최종 버퍼) 어느 버퍼를 봐야 할지 헷갈릴 때
- 함수 호출 규약이나 인자 순서 자체가 헷갈려서 "몇 번째 인자가 버퍼 주소인지" 확신이 안 설 때

## 핵심 개념

### 방법 1 — 입력 함수의 인자 레지스터에서 직접 읽기
버퍼 주소를 스택 오프셋으로 직접 계산할 필요 없이, 입력 함수가 호출되는 순간 그 함수의 인자 레지스터(또는 스택 인자)를 보면 버퍼 주소가 그대로 들어 있다. `fgets(buf, n, stream)`이면 첫 번째 인자, `read(fd, buf, count)`이면 두 번째 인자, `recv(sockfd, buf, len, flags)`이면 두 번째 인자가 버퍼 주소다. 이 값은 스택이든 힙이든 상관없이 항상 정확하다 — 계산이 아니라 "그 함수가 이미 계산해서 인자로 넘긴 값을 그대로 읽는" 것이기 때문이다.

### 방법 2 — 고유 패턴을 입력하고 메모리 전체 검색
버퍼가 어디 있는지 전혀 감이 안 잡히면, 프로그램 자체에 원래 나타나지 않을 독특한 문자열(예: `ZZZZYYYYXXXXWWWW` 같은 패턴, 또는 `AAAABBBBCCCCDDDD`처럼 구간을 구분할 수 있는 패턴)을 실제로 입력한 뒤, 디버거의 메모리 검색 기능으로 그 바이트열이 어디 있는지 프로세스 전체 메모리에서 찾는다. 이 방법은 코드를 전혀 안 읽고도 버퍼 위치를 알아낼 수 있어서, 난독화가 심하거나 인자 추적이 어려운 경우에 특히 유용하다.

### 여러 번 복사되는 경우 — 검색으로 모든 사본을 한 번에 찾기
입력이 한 곳에만 있지 않고 임시 버퍼에서 파싱 버퍼로, 다시 최종 검증 버퍼로 여러 번 복사되는 구조라면, 메모리 검색은 그 패턴이 존재하는 **모든 위치**를 한 번에 나열해준다. 각 위치에 접근 브레이크포인트(`watch`/메모리 브레이크포인트)를 걸면 어느 시점에 어디로 복사되는지 순서대로 추적할 수 있다.

## 화면/코드에서 보이는 징후
- 디스어셈블리에서 버퍼 주소 계산에 여러 단계의 포인터 연산(`mov rax, [rbp-8]`; `add rax, rcx` 등)이 얽혀 있어 손으로 따라가기 번거로움
- `malloc`/`HeapAlloc` 반환값을 바로 안 쓰고 다른 변수에 여러 번 대입/전달해서 최종 버퍼 포인터가 어느 레지스터에 있는지 헷갈림
- 입력 직후 바로 다른 함수(파싱 함수 등)로 포인터가 그대로 전달되어 원래 버퍼 위치를 잃어버린 느낌이 들 때

## 가장 먼저 할 것
입력 함수 이름을 정확히 알고 있다면(`scanf`, `fgets`, `read`, `recv`, `gets`) 그 함수에 브레이크포인트를 걸고 인자 레지스터/스택 인자를 확인하는 것부터 시도한다. 함수 이름조차 특정이 안 되면 바로 "고유 패턴 입력 후 메모리 검색"으로 넘어간다.

## 단계별 절차

**1) 입력 함수에 브레이크포인트를 걸고 인자에서 주소 확인 (GDB, x86-64 SysV)**
```gdb
(gdb) break fgets
(gdb) run
(gdb) print (char*)$rdi
$1 = 0x555555559260 ""
```
`fgets`의 1번째 인자(`$rdi`)가 버퍼 주소다. Windows x64 호출 규약이면 `$rcx`가 1번째 인자다.

**2) recv/read처럼 2번째 인자가 버퍼인 경우**
```gdb
(gdb) break recv
(gdb) run
(gdb) print (char*)$rsi
```

**3) 함수 이름을 특정할 수 없다면 고유 패턴을 입력하고 메모리 검색 (GDB)**
프로그램을 실행해 프롬프트가 뜨면 `ZZZZYYYYXXXXWWWW` 같은 문자열을 입력한다.
```gdb
(gdb) find /b 0x400000, 0x7fffffffffff, 'Z', 'Z', 'Z', 'Z', 'Y', 'Y', 'Y', 'Y'
0x7fffffffe410
```
`find` 명령이 해당 바이트열이 존재하는 모든 주소를 나열해준다. `/b`는 바이트 단위 비교를 뜻한다.

**4) x64dbg에서 동일한 접근 — Search for Pattern**
CPU/메모리 맵 창에서 우클릭 → Search for → Pattern(또는 Memory Map 전체 대상 검색)을 선택하고, 입력했던 패턴을 헥스(`5A 5A 5A 5A 59 59 59 59`) 또는 문자열로 검색한다. 검색 결과로 나온 모든 주소가 후보 버퍼 위치다.

**5) 후보 주소가 여러 개면 각각에 접근 브레이크포인트로 순서 추적**
```gdb
(gdb) watch *(char*)0x7fffffffe410
```
어느 시점에 그 주소에 값이 쓰이는지, 그리고 그 값이 다시 다른 주소로 복사되는지(다음 후보 주소에도 같은 패턴이 나타나는 시점) 순서대로 확인한다.

**6) 힙 버퍼라면 할당 함수 반환값도 함께 확인**
```gdb
(gdb) break malloc
(gdb) finish
Value returned is $1 = (void *) 0x5555555592a0
```
`malloc` 리턴 직후(REV-0852 참고) `$rax`(또는 x64dbg의 `EAX`/`RAX`)가 새로 할당된 버퍼 주소다. 이후 그 주소가 어디로 복사되어 쓰이는지 `watch`로 따라간다.

## 명령어/단축키
```gdb
(gdb) break fgets / break read / break recv / break malloc
(gdb) print (char*)$rdi   # SysV x64 1번째 인자
(gdb) print (char*)$rsi   # SysV x64 2번째 인자
(gdb) find /b START, END, 'p','a','t','t','e','r','n'
(gdb) watch *(char*)ADDR
(gdb) finish
```
```
x64dbg: 우클릭 → Search for → Pattern / String (전체 메모리 맵 대상)
x64dbg: bp fgets / bp recv, 인자 확인은 Registers 창
```

## 출력 해석
- `find` 명령이 여러 주소를 반환하면, 각각 스택/힙/데이터 영역 중 어디에 속하는지 `info proc mappings`로 대조해서 어느 영역의 사본인지 구분한다.
- `print (char*)$rdi`가 유효한 문자열로 보이면 그 주소가 맞는 버퍼다. 쓰레기 값이 보인다면 아직 함수 진입 직후(프롤로그 전)라 인자가 다른 위치에 있을 수 있으니 몇 명령어 더 진행 후 다시 확인한다.
- `malloc`의 `finish` 결과가 `Value returned is $1 = (void *) 0x0`이면 할당 실패이며, 이후 그 포인터를 그대로 쓰면 크래시가 나므로 이 자체가 분석 대상이 아니라 예외 상황일 수 있다.

## 흔한 실수
- 함수 인자 순서(어느 레지스터가 몇 번째 인자인지)를 Windows x64와 Linux SysV x64에서 헷갈리는 것 — 전자는 RCX/RDX/R8/R9, 후자는 RDI/RSI/RDX/RCX/R8/R9 순서다.
- 메모리 검색 패턴을 너무 짧게(2~3바이트) 잡아서 관련 없는 위치까지 대량으로 매칭되는 것 — 8바이트 이상의 고유한 패턴을 쓰는 것이 좋다.
- 검색은 성공했는데 그 주소가 "입력이 복사된 사본" 중 하나일 뿐, 프로그램이 실제로 비교에 쓰는 "최종" 버퍼가 아닌 걸 모르고 엉뚱한 곳만 계속 관찰하는 것 — 여러 사본이 나오면 각각에 watch를 걸어 최종적으로 비교 함수에 인자로 넘어가는 것이 어느 것인지 확인해야 한다.
- 힙 버퍼 주소는 ASLR/힙 레이아웃에 따라 실행마다 바뀔 수 있다는 것을 잊고 이전 실행에서 찾은 절대 주소를 그대로 재사용하는 것.

## 막혔을 때 다음 체크
- 버퍼 위치를 찾은 다음, 그 값이 실제로 변형되는 과정을 이어서 보고 싶다면 → REV-0195 디버거에서 입력 버퍼가 실제로 변하는 과정 추적.
- CALL 직전 인자 레지스터를 확인하는 기본기가 더 필요하다면 → REV-0175 CALL 직전 함수 인자 확인하는 법.
- 값이 스택이 아니라 레지스터에만 머물러서 못 찾는 상황이라면 → REV-0854 스택에서 원하는 값이 안 보일 때(레지스터에만 있을 때).

## 미니 예제
```gdb
(gdb) break scanf
(gdb) run
Enter value:
(gdb) continue
# 프로그램이 scanf에서 멈춤

(gdb) print (char*)$rsi
$1 = 0x7fffffffe3f0 ""
```
`scanf("%s", buf)`의 2번째 인자(`$rsi`)가 곧바로 버퍼 주소였다. 만약 이 방식으로도 어느 함수를 봐야 할지 모르겠다면:
```gdb
(gdb) continue
# 콘솔에 ZZZZYYYYXXXXWWWW 입력
(gdb) find /b 0x400000, 0x7ffffffff000, 'Z','Z','Z','Z'
0x7fffffffe3f0
```
같은 주소가 검색으로도 확인되어, 이 주소가 실제 입력 버퍼임을 다시 한번 확증했다.

## 관련 글
- REV-0195 — 디버거에서 입력 버퍼가 실제로 변하는 과정 추적
- REV-0175 — CALL 직전 함수 인자 확인하는 법
- REV-0852 — 함수 반환 직후로 브레이크포인트를 옮기고 싶은데 위치를 못 찾을 때

## 출처/검증
- x86-64 호출 규약별 인자 레지스터 순서(System V: RDI/RSI/RDX/RCX/R8/R9, Microsoft x64: RCX/RDX/R8/R9): System V AMD64 ABI 및 Microsoft x64 호출 규약 공식 문서 기준.
- GDB `find` 명령을 이용한 메모리 패턴 검색: GDB 공식 매뉴얼 "Searching Memory" 섹션 기준.
- x64dbg의 Search for Pattern/String 기능: x64dbg 공식 문서(Memory Map, Search) 기준 (2026-09-09 검증).
