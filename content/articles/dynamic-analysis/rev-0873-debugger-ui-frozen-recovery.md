## 한 줄 요약
디버거 UI가 멈추는 것은 대개 디버거 자체의 버그가 아니라 ①대상 프로세스의 모든 스레드가 실제로 멈춰서(브레이크포인트에 걸렸거나 데드락) 디버거가 응답을 기다리는 중이거나, ②로더 락(loader lock)처럼 Windows/Linux 내부 잠금 상태에서 API 호출이 걸려 멈춘 것이거나, ③디버거 자신의 무거운 분석 기능(심볼 로딩, 대용량 Trace)이 UI 스레드를 막고 있는 것이므로, 무작정 강제 종료하기 전에 어느 경우인지부터 구분하는 것이 좋다.

## 언제 검색해야 하나
- x64dbg 창 제목에 "(응답 없음)"이 뜨거나, 클릭해도 화면이 하얗게 변하고 아무 반응이 없을 때
- GDB에 명령을 쳐도 프롬프트가 안 돌아오고 계속 멈춰 있을 때
- 특정 API 호출(예: 락 관련 함수) 직후부터 디버거가 멈추기 시작할 때(REV-0618 참고)
- 강제로 꺼도 되는지, 아니면 좀 더 기다려야 하는지 판단이 안 설 때

## 핵심 개념

### 원인 ① 대상 프로세스가 진짜로 멈춰 있다
디버거 UI는 보통 대상 프로세스가 브레이크포인트에 걸리거나 사용자의 다음 명령을 기다리는 동안 "정지(Paused)" 상태를 유지하는 것이 정상이다. 이건 멈춘 것처럼 보여도 실제로는 정상 대기 상태다. 문제는 프로그램 자체가 데드락(여러 스레드가 서로의 락을 기다리며 영원히 진행 못 하는 상태)에 빠진 경우로, 이때는 아무리 기다려도 다시 움직이지 않는다.

### 원인 ② 로더 락(Loader Lock)과 관련된 멈춤
Windows에서 `LoadLibrary`, DLL의 `DllMain` 처리 등은 내부적으로 로더 락을 잡은 채로 실행된다. 디버거가 이 시점에 브레이크포인트로 특정 스레드를 멈추면, 다른 스레드가 같은 락을 기다리며 전체 프로세스가 사실상 멈춘 것처럼 보일 수 있다(REV-0618의 "특정 API 호출 이후 x64dbg가 응답이 없을 때"가 이 유형의 대표적인 예다). 이 경우는 그 특정 스레드만 재개시켜주면 풀리는 경우가 많다.

### 원인 ③ 디버거 자신의 무거운 작업
심볼(PDB/디버그 정보)을 다운로드하거나 파싱하는 작업, 큰 바이너리의 자동 분석, 대용량 Trace 로그 처리 등은 디버거의 UI 스레드를 장시간 점유할 수 있다. 이 경우는 실제로 "일을 하고 있는 중"이라 기다리면 끝나지만, 진행률 표시가 없으면 멈춘 것처럼 보인다.

### 무작정 강제 종료의 위험
디버거를 강제 종료(작업 관리자에서 "작업 끝내기", `kill -9`)하면 대상 프로세스까지 함께 죽거나, 저장하지 않은 브레이크포인트/주석 정보가 날아갈 수 있다(REV-0864 참고). 가능하면 먼저 원인을 구분해서 더 가벼운 복구 방법을 시도하는 것이 좋다.

## 화면/코드에서 보이는 징후
- Windows 작업 관리자에서 x64dbg 프로세스 상태가 "응답 없음"으로 표시된다.
- x64dbg 하단 상태 표시줄이 "Running"에서 멈춰 있고, 어떤 조작에도 반응이 없다.
- GDB 콘솔에 프롬프트(`(gdb)`)가 안 돌아오고 커서만 깜빡인다.
- 작업 관리자/`top`에서 대상 프로세스나 디버거 프로세스의 CPU 사용량이 0%에 가깝다(진짜 멈춤/데드락과 무거운 계산 중임을 구분하는 단서 — 계산 중이면 CPU를 쓰고 있어야 한다).

## 가장 먼저 할 것
1. 작업 관리자/`top`에서 CPU 사용량을 확인해, 디버거가 실제로 뭔가 계산 중인지(CPU 사용) 아니면 완전히 대기 중인지(CPU 0%) 구분한다.
2. 최근에 어떤 조작(브레이크포인트, API 호출 통과, 심볼 로드)을 했는지 되짚어 어느 시점부터 멈췄는지 확인한다.
3. 몇 분 정도는 강제 종료 전에 기다려본다(특히 심볼 로딩/Trace 작업 중이었다면).

## 단계별 절차

**Windows / x64dbg**
1. 작업 관리자에서 x64dbg와 대상 프로세스의 CPU 사용량을 각각 확인한다.
2. 멀티스레드 프로그램이라면, x64dbg의 Threads 창을 열어(다른 창이 반응한다면) 어떤 스레드가 멈춰 있고 어떤 스레드가 대기 중인지 확인한다.
3. 특정 스레드만 멈춰 있고 다른 스레드는 진행 가능해 보인다면, 그 스레드를 개별적으로 재개(Resume Thread)해본다.
4. 심볼 로딩 등 무거운 작업이 의심되면, 네트워크 연결을 끊어 온라인 심볼 서버 조회가 타임아웃되도록 유도하거나, 심볼 로딩 옵션을 꺼두고 재시도한다.
5. 위 방법으로도 안 풀리면 최후 수단으로 x64dbg 프로세스를 종료한다. 이 경우 REV-0864를 참고해 다음번엔 분석 정보가 저장되도록 설정을 미리 점검해둔다.

**Linux / GDB**
1. GDB가 멈춘 것처럼 보이면, `Ctrl+C`로 대상 프로세스에 인터럽트 시그널(SIGINT)을 보내 강제로 GDB의 제어권을 되찾아본다.
2. 그래도 반응이 없다면, 다른 터미널에서 대상 프로세스의 상태를 확인한다.
   ```
   ps -T -p <PID>
   cat /proc/<PID>/status | grep State
   ```
   `State: D`(uninterruptible sleep)라면 커널 I/O 대기 중이라 GDB 문제가 아니라 프로세스 자체가 멈춘 것이다.
3. 데드락이 의심되면 각 스레드의 스택을 확인한다.
   ```
   (gdb) thread apply all bt
   ```
   여러 스레드가 서로 다른 뮤텍스를 기다리는 스택이 보이면 데드락이 확정적이다.
4. 정말 복구 불가능하면 GDB만 별도로 종료하고(대상 프로세스는 그대로 둔 채) 새 GDB로 다시 attach를 시도하거나, 대상 프로세스까지 함께 종료한다.

## 명령어/단축키
- Windows: 작업 관리자(CPU 사용량 확인), x64dbg Threads 창(스레드별 상태/재개)
- Linux: `Ctrl+C`(SIGINT로 제어권 회수 시도), `ps -T -p <PID>`, `cat /proc/<PID>/status`, `(gdb) thread apply all bt`(전체 스레드 콜스택으로 데드락 확인)

## 출력 해석
- `thread apply all bt` 결과에서 두 스레드가 서로 다른 락 함수(`pthread_mutex_lock` 등) 안에 멈춰 있고, 그 락이 서로 맞물려 있다면 데드락으로 확정된다.
- `/proc/<PID>/status`의 `State: D`는 커널 I/O 대기이며, 디버거를 아무리 조작해도 그 자체로는 안 풀린다 — I/O 완료를 기다리거나 원인이 된 자원을 확인해야 한다.

## 흔한 실수
- CPU 사용량 확인 없이 바로 강제 종료해서, 사실은 무거운 분석 작업이 거의 끝나가던 것을 날려버리는 것.
- 멀티스레드 프로그램에서 한 스레드만 멈춘 것을 "전체가 멈췄다"고 오해하고, 다른 스레드를 재개해볼 생각을 못 하는 것.
- 데드락 상황을 디버거 버그로 오인해서 디버거를 재설치하거나 바꿔가며 시간을 낭비하는 것 — 실제로는 대상 프로그램의 문제인 경우가 많다.

## 막혔을 때 다음 체크
- 특정 API 호출 직후부터 항상 멈춘다면 → REV-0618(특정 API 호출 이후 x64dbg가 응답이 없을 때)을 먼저 참고한다.
- 강제 종료 후 분석 정보가 매번 날아간다면 → REV-0864(디버거 재시작할 때마다 설정이 초기화될 때)를 참고해 저장 설정을 점검한다.
- 여러 프로세스/스레드를 동시에 디버깅하는 구조라면 → 멀티스레드/프로세스 디버깅 관련 기초 개념을 함께 점검한다.

## 미니 예제
```
$ ps -T -p 4821
  PID   SPID TTY          TIME CMD
 4821   4821 pts/0    00:00:01 chall
 4821   4822 pts/0    00:00:00 chall
$ cat /proc/4821/status | grep State
State:  D (disk sleep)
```
프로세스 상태가 `D`(uninterruptible sleep)로 나온다면, 이는 GDB나 디버깅 조작과 무관하게 커널 I/O 완료를 기다리는 중이라는 뜻이며, 디버거를 아무리 조작해도 그 자체로는 풀리지 않는다.

## 관련 글
- REV-0618 — 특정 API 호출 이후 x64dbg가 응답이 없을 때
- REV-0864 — 디버거 재시작할 때마다 설정이 초기화될 때
- REV-0865 — 디버깅 중 CPU 사용량이 100%로 치솟을 때

## 출처/검증
- Windows 로더 락(Loader Lock)과 DLL 초기화 시 발생하는 데드락 가능성: Microsoft Learn "Dynamic-Link Library Best Practices" 문서 기준.
- GDB `thread apply all bt`로 전체 스레드 콜스택을 확인하는 방법: GNU GDB 공식 매뉴얼 "Threads" 섹션 기준.
- Linux 프로세스 상태(`D` uninterruptible sleep)의 의미: Linux `proc(5)` 매뉴얼 페이지 기준.
- 2026-09-09 검증.
