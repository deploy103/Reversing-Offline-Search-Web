## 한 줄 요약
디버거의 콜스택(x64dbg의 Call Stack 창, GDB의 `bt`)은 스택 프레임 포인터(RBP 체인)나 언와인드 정보를 이용해 역추적하는데, 최적화 빌드로 프레임 포인터가 생략되었거나(frame pointer omission), 버퍼 오버플로우로 리턴 주소/저장된 RBP가 실제로 깨졌거나, 심볼 정보가 없어서 디버거가 프레임 경계를 못 찾을 때 콜스택이 한두 줄만 나오거나 `??`, 이상한 주소로 끊겨 보인다.

## 언제 검색해야 하나
- x64dbg의 Call Stack 창에 현재 함수만 달랑 나오고 그 위 호출자들이 하나도 안 보일 때
- GDB `bt`(backtrace)를 쳤는데 `#1 0x0000000000000000 in ?? ()`처럼 의미 없는 값이 나오거나 중간에 끊길 때
- `Program terminated with signal SIGSEGV` 후 `bt`를 쳤더니 `No stack.`이라고 나올 때
- 최적화(`-O2` 등)로 컴파일된 바이너리를 분석할 때 콜스택이 디버그 빌드보다 훨씬 부실하게 나올 때

## 핵심 개념

### 콜스택은 어떻게 복원되는가
함수가 호출될 때마다 표준적인 프롤로그는 이전 RBP를 스택에 저장하고(`push rbp`) 현재 RSP를 새 RBP로 삼는다(`mov rbp, rsp`). 이렇게 저장된 RBP들이 사슬처럼 이어지기 때문에, 디버거는 현재 RBP에서 시작해 "이 프레임의 저장된 RBP → 그 위 프레임의 저장된 RBP → ..."로 계속 따라 올라가면서 각 프레임의 리턴 주소(저장된 RBP 바로 위 8바이트)를 읽어 콜스택을 재구성한다. 이것이 정상적으로 동작하려면 이 RBP 체인이 온전해야 하고, 심볼/디버그 정보가 있으면 그 리턴 주소를 함수 이름으로 바꿔서 보여준다.

### 원인 ① 프레임 포인터 생략(Frame Pointer Omission)
컴파일러 최적화 옵션(GCC/Clang `-fomit-frame-pointer`, MSVC `/Oy`)이 켜지면, RBP를 범용 레지스터로 재활용하고 프롤로그에서 `push rbp; mov rbp, rsp`를 아예 생략한다. 이 경우 디버거는 더 이상 RBP 체인을 따라갈 수 없고, 대신 CFI(Call Frame Information, DWARF의 `.eh_frame`)나 PDB의 언와인드 정보를 이용해야 하는데, 이런 정보가 없거나 디버거가 해석하지 못하면 콜스택이 한 프레임만 나오고 끊긴다. 릴리즈(최적화) 빌드에서 콜스택이 유독 부실한 가장 흔한 이유다.

### 원인 ② 스택 자체가 깨짐(진짜 오버플로우/오염)
버퍼 오버플로우 취약점이 있는 CTF 바이너리라면, 로컬 배열에 쓴 값이 저장된 RBP나 리턴 주소를 실제로 덮어써서 스택 구조 자체가 깨진 것일 수 있다. 이 경우 콜스택을 따라가다 보면 코드 영역이 아닌 이상한 주소(`??`)나 매핑되지 않은 주소가 나오는데, 이는 디버거 버그가 아니라 **오버플로우가 실제로 성공했다는 증거**일 수 있다(REV-0609, REV-0694 참고).

### 원인 ③ 심볼/디버그 정보 부족
스트립된 바이너리나 심볼이 없는 라이브러리 프레임을 지나갈 때는 리턴 주소는 정확히 읽혔더라도 함수 이름을 매길 수 없어 `?? ()`나 `<unknown>`으로 표시될 수 있다. 이는 스택이 실제로 깨진 것이 아니라 이름을 못 붙인 것뿐이다(REV-0695 참고).

## 화면/코드에서 보이는 징후
- x64dbg Call Stack 창에 현재 함수 한 줄만 있고 `Return to` 열이 비어있거나 이상한 주소를 가리킨다.
- GDB `bt` 결과가 `#0 ... in current_func ()` 다음에 바로 `(More stack frames follow...)` 없이 끊기거나, `#1 0x0000000000000000 in ?? ()`가 나온다.
- 최적화 빌드에서 `bt`가 정상 프레임 몇 개만 보여주고 나머지는 `??`로 채워진다.
- 명백히 버퍼 오버플로우를 유발한 직후 `bt`를 쳤더니 리턴 주소 자리에 사용자가 입력한 패턴(`AAAAAAAA` 같은)이 그대로 보인다.

## 가장 먼저 할 것
1. 이 콜스택 문제가 오버플로우로 인한 의도된 결과인지(취약점 성공의 증거), 아니면 단순히 최적화/심볼 부족 때문인지부터 구분한다.
2. 최적화 빌드인지 확인한다(디버그 정보 유무, `-O` 옵션 흔적).
3. 심볼이 없는 프레임인지, 아니면 리턴 주소 자체가 무효한 값인지 리턴 주소 값을 직접 눈으로 확인한다.

## 단계별 절차

**x64dbg**
1. Call Stack 창에서 각 행의 `Return to` 주소를 확인하고, 그 주소가 실제 코드 영역(모듈 매핑 범위) 안에 있는지 Memory Map(REV-0182)과 대조한다.
2. 매핑되지 않은/이상한 값이라면 스택이 실제로 오염된 것으로 보고, 그 값이 사용자가 넣은 입력 패턴과 일치하는지 확인한다.
3. 정상 범위인데 이름만 안 보인다면, 해당 모듈의 심볼을 다시 로드(우클릭 → Symbols, 또는 PDB 다운로드)해본다.

**GDB / Pwndbg**
1. 리턴 주소가 유효한 코드 영역인지 확인한다.
   ```
   (gdb) bt
   (gdb) info proc mappings
   ```
2. 프레임 포인터가 생략된 최적화 빌드가 의심되면, DWARF CFI 기반 언와인딩을 강제로 시도해본다(대부분 자동이지만 실패 시 `bt` 대신 레지스터/스택을 손으로 확인).
   ```
   (gdb) info frame
   (gdb) x/20gx $rsp
   ```
3. 오버플로우로 인한 오염이 의심되면, 스택 위쪽 메모리를 직접 덤프해서 저장된 리턴 주소 자리에 어떤 값이 들어있는지 눈으로 확인한다.
   ```
   (gdb) x/20gx $rbp
   ```
4. Pwndbg를 쓰고 있다면 `context` 화면 하단에 자동으로 표시되는 스택/백트레이스 요약을 함께 참고한다.

## 명령어/단축키
- x64dbg: Call Stack 창(자동 표시), Memory Map, Symbols(우클릭 메뉴)
- GDB/Pwndbg: `bt`(backtrace), `bt full`(지역 변수 포함), `frame <n>`, `info frame`, `x/Ngx $rsp`, `x/Ngx $rbp`, Pwndbg `context`

## 출력 해석
- `bt`에서 `#1 0x0000000000000000 in ?? ()`는 리턴 주소가 `0x0`으로 읽혔다는 뜻으로, 그 위치의 스택 메모리가 진짜로 0이거나 아예 접근 불가능했다는 신호다.
- 리턴 주소 자리에 `0x4141414141414141`처럼 사용자가 넣은 패턴이 그대로 보이면, 이는 버퍼 오버플로우로 리턴 주소를 성공적으로 덮어썼다는 확실한 증거다.
- x64dbg Call Stack에서 함수 이름 대신 `모듈명+오프셋` 형태로만 나오면 심볼이 없는 것뿐이며, 스택 자체는 정상일 수 있다.

## 흔한 실수
- 최적화 빌드에서 콜스택이 짧게 나오는 것을 무조건 "스택이 깨졌다"고 오해하는 것 — 실제로는 프레임 포인터 생략 때문일 수 있다.
- 오버플로우가 성공해서 콜스택이 깨진 것을 디버거 오류로 착각하고 다른 도구로 계속 바꿔가며 확인하는 것 — 오히려 이것이 취약점이 작동한다는 증거일 수 있다.
- 리턴 주소 값을 직접 확인하지 않고 콜스택 창의 표시만 보고 판단하는 것 — 항상 `Return to` 값이나 `bt`가 보여주는 주소 자체를 매핑 정보와 대조해야 한다.

## 막혔을 때 다음 체크
- GDB에서 `??`만 잔뜩 나온다면 → REV-0695(GDB backtrace가 ??로만 나올 때)를 참고한다.
- "corrupted stack frame" 같은 명시적 메시지가 뜬다면 → REV-0694를 참고한다.
- Windows에서 "Stack Corruption" 예외가 함께 뜬다면 → REV-0609를 참고한다.
- 함수 인자/리턴값 자체를 다시 추적하고 싶다면 → REV-0175, REV-0176을 참고한다.

## 미니 예제
```
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x4141414141414141 in ?? ()
(gdb) bt
#0  0x4141414141414141 in ?? ()
```
리턴 주소 자리가 통째로 `0x41`(문자 'A')로 채워진 것이 그대로 RIP까지 이어진 것을 보면, 콜스택이 "깨진 버그"가 아니라 버퍼 오버플로우로 리턴 주소를 완전히 장악했다는 뜻임을 알 수 있다.

## 관련 글
- REV-0695 — GDB backtrace가 ??로만 나와서 콜스택을 못 볼 때
- REV-0694 — GDB에서 스택 프레임이 corrupted stack frame이라고 나올 때
- REV-0609 — 스택이 깨졌다는 예외가 발생할 때(Stack Corruption)
- REV-0173 — 스택 값을 실행 중 추적하는 법

## 출처/검증
- 프레임 포인터 체인과 프레임 포인터 생략(`-fomit-frame-pointer`) 최적화가 스택 언와인딩에 미치는 영향: GCC 공식 문서(Optimize Options) 및 GNU GDB 매뉴얼 "Backtrace" 섹션 기준.
- GDB `bt`, `info frame`이 리턴 주소를 해석하는 방식: GNU GDB 공식 매뉴얼 "Examining the Stack" 챕터 기준.
- x64dbg Call Stack 창 동작: x64dbg 공식 문서(Debugging) 기준.
