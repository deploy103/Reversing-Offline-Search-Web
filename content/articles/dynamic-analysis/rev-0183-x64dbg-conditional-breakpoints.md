## 한 줄 요약
x64dbg의 조건부 브레이크포인트는 브레이크포인트를 우클릭해 `Edit breakpoint`를 열고 **Break condition**란에 `EAX==1`, `[rsp]==0xDEADBEEF` 같은 C와 비슷한 표현식을 입력하면, 그 조건이 참(0이 아닌 값)일 때만 실제로 실행을 멈추게 하는 기능이다.

## 언제 검색해야 하나
- 반복문(루프) 안에 있는 브레이크포인트가 수백 번씩 걸려서 F9를 계속 눌러야 할 때
- "이 변수 값이 특정 숫자가 됐을 때만" 멈추고 싶을 때
- 특정 스레드에서 실행될 때만, 또는 몇 번째 히트일 때만 멈추고 싶을 때
- 스택이나 메모리의 특정 값이 원하는 값과 일치할 때만 멈추고 싶을 때(예: `[rsp] == 0xDEADBEEF`)

## 핵심 개념
x64dbg의 모든 브레이크포인트는 세 가지 조건식을 가질 수 있다.

1. **Break condition(중단 조건)** — 이 조건이 참이어야 실제로 프로그램이 멈춘다. 기본값은 `1`(항상 참, 즉 항상 멈춤)이다.
2. **Log condition(로그 조건)** — 이 조건이 참일 때만 로그 텍스트를 Log 탭에 출력한다. 기본값은 `1`.
3. **Command condition(명령 조건)** — 이 조건이 참일 때만 지정한 명령(커맨드)을 실행한다. 기본값은 `1`.

이 세 조건 모두 x64dbg의 **표현식 문법(C와 비슷한 문법)**을 그대로 쓸 수 있다. 몇 가지 핵심 규칙이 있다.

- **숫자는 기본적으로 16진수로 해석된다.** 10진수를 쓰려면 앞에 `.`을 붙여야 한다(예: `.100`은 10진수 100, 그냥 `100`은 16진수 0x100=256).
- **레지스터는 이름 그대로 쓴다.** `EAX`, `RAX`, `ECX`, `RSP` 등.
- **메모리 값을 읽으려면 대괄호 `[ ]`로 감싼다.** `[rsp]`는 RSP가 가리키는 주소의 값(기본 크기)을 읽는다는 뜻이다. 예를 들어 `[rsp+8]`은 스택에서 RSP+8 위치의 값을 읽는다.
- **비교 연산자**: `==`(같다), `!=`(다르다), `<`, `>`, `<=`, `>=`는 조건이 참이면 1, 거짓이면 0을 돌려준다.
- **논리 연산자**: `&&`(그리고), `||`(또는)로 여러 조건을 묶을 수 있다.
- **함수 형태의 표현식**도 있다. 예를 들어 `mem.valid(EAX)`는 EAX 값이 유효한(매핑된) 메모리 주소인지 확인하고, `tid()`는 현재 스레드 ID를 돌려준다.

이런 문법을 조합하면 "EAX가 1이고 동시에 ECX도 1일 때만 멈춰라" 같은 조건을 `EAX==1 && ECX==1`로 정확히 표현할 수 있다.

## 화면/코드에서 보이는 징후
- 조건부 브레이크포인트가 설정된 줄도 화면에는 일반 브레이크포인트와 똑같이 빨간 원으로만 표시된다. 조건이 걸려 있는지는 겉모습만으로는 구분되지 않으므로, Breakpoints 탭에서 조건식 열을 확인해야 한다.
- F9로 실행했을 때 조건을 만족하지 않으면 프로그램은 멈추지 않고 계속 실행되며, Hit count(히트 횟수)만 계속 증가한다.
- 조건식 문법이 틀리면(예: 괄호가 안 맞음) x64dbg는 이 표현식을 "항상 참"으로 취급해서 매번 멈춰버린다. 즉, 조건을 걸었는데도 계속 멈춘다면 표현식 자체가 잘못됐을 가능성을 의심해야 한다.

## 가장 먼저 할 것
조건부 브레이크포인트를 걸기 전에, 먼저 일반 브레이크포인트(F2)로 한 번 멈춰서 그 지점의 레지스터/메모리 상태를 눈으로 확인한다. 여기서 "어떤 값이 어떤 조건일 때 내가 원하는 순간인지"를 구체적으로 정한 다음 조건식을 작성하는 것이 시행착오를 줄이는 방법이다.

## 단계별 절차

**1) 먼저 평범한 브레이크포인트 걸기**

원하는 위치에 F2로 소프트웨어 브레이크포인트를 건다(자세한 방법은 브레이크포인트 설정 문서 참고).

**2) Edit breakpoint 열기**

그 브레이크포인트가 걸린 줄을 우클릭 → `Breakpoint → Edit breakpoint`를 선택한다. 또는 `Breakpoints` 탭에서 해당 항목을 우클릭해도 같은 대화상자가 열린다.

**3) Break condition 입력하기**

대화상자의 Break condition 입력란에 원하는 조건식을 입력한다.

```text
EAX==1 && ECX==1
```

이 예시는 "EAX가 1이고 ECX도 1일 때만 실제로 멈춘다"는 뜻이다. 스택 값을 조건으로 쓰고 싶다면 다음처럼 대괄호로 메모리를 역참조한다.

```text
[rsp]==0xDEADBEEF
```

이건 "지금 RSP가 가리키는 스택 위치의 값이 0xDEADBEEF일 때만 멈춘다"는 뜻이다. CTF에서 특정 매직 넘버가 스택에 올라오는 순간을 잡을 때 자주 쓰는 패턴이다.

**4) 히트 횟수 기반 조건 쓰기**

몇 번째로 이 지점에 도달했을 때 멈추고 싶다면 `$breakpointcounter`라는 예약 변수를 쓴다.

```text
$breakpointcounter==3
```

이건 "이 브레이크포인트가 3번째로 실행될 때만 멈춘다"는 뜻이다. 매 3번째마다 멈추고 싶다면 `($breakpointcounter%3)==0`처럼 나머지 연산자 `%`를 활용한다.

**5) 특정 스레드에서만 멈추기**

멀티스레드 프로그램에서 특정 스레드에서 실행될 때만 멈추고 싶다면 `tid()` 함수를 쓴다.

```text
tid()==0x1C0
```

**6) 메모리 유효성/문자열 조건 활용**

`mem.valid(EAX)`는 EAX 값이 실제로 접근 가능한 메모리 주소인지 확인한다. 포인터 관련 조건을 걸 때 잘못된 주소에서 x64dbg가 평가 중 에러를 내지 않도록 미리 걸러주는 용도로 쓸 수 있다. 문자열 비교가 필요하면 `strstr(utf16(ECX), "foo")`처럼 메모리에서 유니코드 문자열을 읽어(`utf16(...)`) 특정 부분 문자열이 포함되어 있는지(`strstr`) 확인하는 조합도 가능하다.

**7) Log condition으로 멈추지 않고 관찰만 하기**

매번 멈추지 않고 그냥 로그만 남기고 싶다면 Break condition은 `0`(절대 멈추지 않음)으로 두고, Log condition과 Log text만 채운다. 이렇게 하면 프로그램은 끊김 없이 실행되면서 Log 탭에 원하는 시점마다 값이 기록된다.

## 명령어/단축키
- 브레이크포인트 우클릭 → `Edit breakpoint` : 조건식 편집 대화상자 열기
- Break condition 입력란 : 이 값이 참이어야 실제로 멈춘다(기본값 `1`)
- Log condition / Log text : 로그를 남길지 여부와 남길 내용
- Command condition / Command text : 조건 만족 시 자동 실행할 명령
- `$breakpointcounter` : 현재까지 이 브레이크포인트가 히트된 횟수
- `$breakpointexceptionaddress` : 브레이크포인트를 발생시킨 정확한 주소

## 출력 해석
- Breakpoints 탭에서 Hit count는 계속 늘어나는데 실제로 프로그램이 멈추지 않는다면, Break condition이 거짓으로 평가되고 있다는 뜻이다. 조건식이 의도한 대로인지 다시 확인한다.
- 반대로 조건을 걸었는데도 매번 멈춘다면, 표현식에 문법 오류가 있어서 x64dbg가 "항상 참"으로 처리하고 있을 가능성이 크다. 숫자 앞에 `.`을 빠뜨리지 않았는지, 괄호와 연산자가 올바른지 다시 확인한다.
- Log 탭에 조건부로 남긴 로그가 예상보다 훨씬 많이 쌓이면, Log condition이 너무 자주 참이 되고 있다는 뜻이므로 조건을 더 좁혀야 한다.

## 흔한 실수
- 10진수 값을 그대로 조건식에 넣었다가(`EAX==100`) 16진수로 해석되어(0x100=256) 의도한 값(10진수 100)과 다른 조건이 되는 경우 — 10진수를 쓰려면 반드시 `.100`처럼 마침표를 붙여야 한다.
- `[rsp]`처럼 메모리를 역참조하는 조건을 걸었는데, 그 시점에 RSP가 아직 유효하지 않은 스택 위치를 가리키고 있어서 평가 자체가 실패하는 경우 — 이런 상황을 막으려면 `mem.valid(rsp)` 같은 조건을 `&&`로 앞에 추가해 안전장치를 둔다.
- Break condition과 Log condition을 헷갈려서, 로그만 남기고 싶었는데 Break condition에 조건을 넣어 매번 프로그램이 멈춰버리는 경우.
- Command condition에 `run`처럼 실행 상태를 직접 바꾸는 명령을 넣었다가 x64dbg 내부 상태와 충돌하는 경우 — 공식 문서에서도 이런 상태 변경 명령 대신 `$breakpointcondition` 변수를 커맨드 텍스트 안에서 조작하는 방식을 권장한다.
- 조건식을 한 번에 복잡하게 작성하려다 오타를 내는 경우 — 간단한 조건(`EAX==1`)부터 걸어서 정상 동작을 확인한 뒤 조건을 점점 더 복잡하게 확장하는 것이 안전하다.

## 조건부 트레이싱과의 차이
x64dbg에는 조건부 브레이크포인트와 비슷하지만 다른 목적을 가진 **조건부 트레이싱(Conditional Tracing)** 기능도 있다. 조건부 브레이크포인트는 "조건이 참일 때 멈춘다"가 핵심이지만, 어디서 조건이 참이 되는지조차 감이 안 잡히는 경우에는 매번 멈춰서 확인하는 대신 트레이싱으로 조건이 참이 되는 지점들을 한 번에 기록하게 할 수 있다. 즉, "정확히 어디서 멈춰야 할지 알고 있다 → 조건부 브레이크포인트", "어디서 조건이 만족되는지 아직 모른다, 넓은 범위를 훑어야 한다 → 조건부 트레이싱"으로 구분해서 고르면 된다. 트레이싱 결과는 Trace 탭에 기록되며, 이 문서에서는 다루지 않지만 조건부 브레이크포인트와 표현식 문법을 그대로 공유하므로 여기서 배운 문법이 그대로 재사용된다.

## 미니 예제
루프 안에서 특정 인덱스에서만 멈추고 싶은 상황이다.

```text
1. 루프 본문 안의 특정 명령어 줄에 F2로 브레이크포인트
2. 그 줄 우클릭 → Breakpoint → Edit breakpoint
3. Break condition에 ECX==.10 입력 (10진수 10일 때만 멈추도록, 앞에 . 필수)
4. OK 후 F9로 실행
5. ECX가 0x0, 0x1, 0x2 ... 로 계속 바뀌며 지나가다가 정확히 10이 되는 순간에만 실제로 멈춤
6. Breakpoints 탭에서 Hit count를 보면 그 사이 몇 번이나 이 지점을 지나갔는지도 확인 가능
```

## 출처/검증
- Break condition/Log condition/Command condition 3분 구조, 표현식 문법(숫자 기본 16진수, 10진수는 `.` 접두, `==`/`!=`/`<`/`>` 등 비교 연산자, `&&`/`||` 논리 연산자), `$breakpointcounter`/`$breakpointexceptionaddress`/`$breakpointcondition` 예약 변수, `mem.valid()`/`tid()`/`strstr()`/`utf16()` 표현식 함수, 그리고 `EAX==1 && ECX==1`, `$breakpointcounter==3`, `tid()==1C0`, `strstr(utf16(ECX), "foo")` 예시는 공식 문서 help.x64dbg.com의 Conditional Breakpoints 페이지(introduction/ConditionalBreakpoint.html)와 Expressions 페이지에 근거했다(2026-09-08 조사, 원문 확인).
- `[rsp]==0xDEADBEEF` 형태의 메모리 역참조 조건은 대괄호가 메모리 접근/그룹핑에 쓰인다는 Expressions 문서의 문법 규칙에 근거한 정상적인 활용 예시이나, 이 구체적인 예문 자체가 공식 문서에 그대로 실려 있는 것은 아니므로 실습 환경에서 직접 테스트해볼 것을 권장한다.
