## 한 줄 요약
REV-0240의 카테고리별 체크리스트를 다 훑어도 원인을 못 찾았거나 여러 안티디버깅 기법이 겹쳐 있는 경우에는, "정상 실행"과 "디버거로 실행"이라는 두 실행을 나란히 놓고 **어느 지점에서 두 실행의 동작이 갈라지는지** API 호출 로그와 실행 흔적을 비교하며 이진 탐색하듯 좁혀나가는 실전 절차가 가장 확실하다.

## 언제 검색해야 하나
- REV-0240 체크리스트(IsDebuggerPresent, PEB, ptrace, RDTSC, CPUID, 예외 기반 등)를 순서대로 다 확인했는데도 뚜렷한 원인을 못 찾았을 때
- 여러 안티디버깅 기법이 동시에 겹쳐 있어서 하나를 우회해도 다른 곳에서 또 종료될 때
- "어디까지는 정상이고 어디서부터 달라지는지"를 정확한 명령어 단위로 짚어내고 싶을 때
- Import 목록에 뻔한 안티디버깅 API가 하나도 안 보이는데도 디버거에서만 다르게 동작할 때(직접 시스템 콜을 쓰거나 난독화된 경우)

## 핵심 개념

### 왜 카테고리 체크리스트만으로는 부족할 때가 있는가
REV-0240의 체크리스트는 "흔히 쓰이는 기법의 종류"를 기준으로 후보를 좁히는 방식이다. 하지만 상용 프로텍터나 공들여 만든 CTF 문제는 여러 체크를 조합하거나, API를 직접 호출하지 않고 시스템 콜을 수동으로 조립해서(REV-0533의 `NtQueryInformationProcess` 직접 호출 등) Import 목록에서 흔적을 감출 수 있다. 이럴 때는 "어떤 종류인가"보다 "정확히 어느 실행 지점에서 갈라지는가"를 실측으로 찾는 것이 더 확실하다.

### 차분 디버깅(differential debugging)의 기본 아이디어
같은 입력으로 프로그램을 두 가지 방식으로 실행한다.
1. 디버거 없이 그냥 실행(정상 실행)
2. 디버거로 실행(attach 또는 처음부터 로드)

두 실행의 관찰 가능한 흔적(호출한 API/시스템 콜 순서, 표준출력, 종료 코드, 실행 시간)을 나란히 기록해서 비교하면, 정확히 어느 API 호출 또는 어느 시점부터 둘의 흔적이 달라지는지 찾아낼 수 있다. 그 지점 직전의 코드가 바로 안티디버깅 체크가 있는 곳이다.

### 이진 탐색으로 실행 지점을 좁히기
프로그램 전체를 처음부터 끝까지 한 줄씩 비교하는 것은 비효율적이다. 대신 프로그램의 큰 흐름(초기화 → 입력 처리 → 검증 → 결과 출력) 중간 지점에 브레이크포인트를 걸어 그 시점까지는 정상 실행과 동일한 상태인지 확인하고, 같다면 뒷부분을, 다르다면 앞부분을 다시 반으로 나눠 확인하는 방식으로 원인 지점을 로그(log) 탐색 시간만큼 빠르게 좁힐 수 있다.

### 멈추지 않고 로그만 남기는 것이 핵심
비교를 위해 매번 멈춰서 눈으로 확인하면 느리고, 무엇보다 "디버거가 멈춰서 시간을 오래 끄는 것 자체"가 타이밍 기반 체크(REV-0872)를 유발할 수 있다. 따라서 `dprintf`(GDB, REV-0642 참고)나 로깅 전용 브레이크포인트("멈추지 않고 로그만 남기기" 옵션, x64dbg의 로그 브레이크포인트)로 값을 기록만 하고 계속 실행되게 하는 것이 안전하다.

## 화면/코드에서 보이는 징후
- 정상 실행 로그와 디버거 실행 로그를 나란히 diff했을 때, 특정 API 호출 이후부터 완전히 갈라진다.
- 종료 코드나 마지막 출력 메시지가 실행 방식에 따라 다르다.
- 브레이크포인트를 이분법으로 옮겨가며 확인했을 때, 어떤 지점까지는 레지스터/메모리 상태가 두 실행에서 동일하다가 특정 함수 이후로 달라진다.

## 가장 먼저 할 것
1. 정상 실행과 디버거 실행 각각의 로그(strace/ltrace 또는 API 후킹 로그)를 따로 남긴다.
2. 두 로그를 `diff`로 비교해 첫 번째로 달라지는 줄을 찾는다.
3. 그 줄 근처의 API/시스템 콜을 REV-0240 체크리스트와 대조해 어떤 범주인지 확인한다.

## 단계별 절차

**Linux / GDB**
1. 정상 실행 로그를 먼저 남긴다.
   ```
   strace -f -o normal.log ./chall
   ```
2. 디버거로 실행하며 같은 방식으로 로그를 남긴다(GDB 안에서 실행된 프로세스를 별도로 strace하기는 까다로우므로, 실전에서는 `gdb`가 자식 프로세스를 실행하기 전에 `catch syscall`로 시스템 콜 단위 로그를 남기거나, 별도 터미널에서 `strace -f -p <PID>`로 attach하는 방법을 쓴다).
   ```
   (gdb) catch syscall
   (gdb) run
   (gdb) continue
   ```
3. 두 로그를 비교한다.
   ```
   diff normal.log gdb.log | head -50
   ```
4. 첫 번째로 달라지는 시스템 콜(예: `ptrace`, `access`) 주변 코드를 정적 분석 도구로 확인한다.
5. 원인 함수가 확인되면 그 함수 진입 직전에 조건부 브레이크포인트나 `dprintf`를 걸어 세부 값을 계속 로그로 남기며 반복 검증한다.

**Windows / x64dbg**
1. Process Monitor 또는 API 후킹 도구로 정상 실행 시의 API 호출 순서를 기록해둔다.
2. x64dbg로 실행하며 같은 API들에 로그 브레이크포인트("Log message"만 남기고 자동으로 계속 실행)를 걸어 기록한다.
3. 두 기록을 비교해 첫 번째로 갈라지는 API 호출을 찾는다.
4. 그 API 호출 직후 반환값(REV-0176 참고)을 두 경우 각각 비교한다.
5. 반환값이 다르다면(예: `IsDebuggerPresent`가 정상에서는 0, 디버거에서는 1), 그 값을 사용하는 다음 분기(REV-0174 참고)를 찾아 원인을 확정한다.

## 명령어/단축키
- Linux: `strace -f -o <파일> <실행파일>`, GDB `catch syscall`, `dprintf LOCATION,"fmt",args`, `diff file1 file2`
- Windows: Process Monitor(별도 도구), x64dbg 로그 브레이크포인트(브레이크포인트 우클릭 → Edit → Log text 설정, "Break condition"을 비워두면 멈추지 않고 로그만 남김)

## 출력 해석
- `diff normal.log gdb.log`에서 처음 나오는 차이 줄이 곧 안티디버깅 체크가 관여하는 지점이다. 그 이전 줄들은 두 실행이 동일하므로 안심하고 건너뛸 수 있다.
- API 반환값이 정상 실행과 디버거 실행에서 다르게 나온다면(0 vs 1, 성공 vs 실패), 그 API가 바로 디버거 존재 여부를 확인하는 신호원이다.

## 흔한 실수
- 로그를 남기지 않고 매번 손으로 F8/Step을 눌러가며 두 실행을 눈으로 비교하려다 지쳐서 포기하는 것 — 처음부터 로그 기반 비교로 접근해야 훨씬 빠르다.
- 디버거로 실행할 때 멈춰서 오래 들여다보는 것 자체가 타이밍 기반 체크(REV-0872)를 유발할 수 있다는 것을 모르고, 매번 다른 결과가 나온다고 혼란스러워하는 것.
- 첫 번째로 발견한 차이점 하나만 우회하고 끝냈다가, 뒤에 또 다른 체크가 남아있어서 다시 종료되는 것 — 하나를 해결한 뒤에도 반드시 전체 로그 비교를 처음부터 다시 돌려 다음 차이점이 있는지 확인해야 한다.

## 막혔을 때 다음 체크
- 카테고리 자체를 아직 못 좁혔다면 → 먼저 REV-0240(디버거 갑자기 종료 체크리스트)의 8단계를 순서대로 다시 훑는다.
- attach하자마자 바로 죽는 특수 케이스라면 → REV-0858을 참고한다.
- Step 실행 중에만, 그것도 느리게 실행할 때만 죽는다면 → REV-0872(타이밍 기반 안티디버깅으로 스텝이 느려서 걸릴 때)를 참고한다.

## 미니 예제
```
$ strace -f -o normal.log ./chall
$ gdb ./chall
(gdb) catch syscall
(gdb) run
Catchpoint 1 (syscall), ptrace (PTRACE_TRACEME, ...)
...
(gdb) continue
...

$ diff normal.log gdb.log
< ptrace(PTRACE_TRACEME, 0, NULL, NULL) = 0
---
> ptrace(PTRACE_TRACEME, 0, NULL, NULL) = -1 EPERM (Operation not permitted)
```
`ptrace(PTRACE_TRACEME, ...)`의 반환값이 정상 실행에서는 `0`, 디버거 실행에서는 `-1`(이미 트레이싱 중이라 실패)로 갈라지는 지점을 정확히 찾아냈다. 이 결과를 REV-0234(ptrace 자가 트레이싱 안티디버깅)와 대조해 원인을 확정한다.

## 관련 글
- REV-0240 — 디버거에서 갑자기 종료될 때 체크리스트
- REV-0858 — 디버거가 붙자마자 프로그램이 종료될 때
- REV-0872 — 타이밍 기반 안티디버깅으로 스텝 실행이 너무 느려서 걸릴 때
- REV-0860 — 디버거 안에서 예외가 계속 발생해서 진행이 안 될 때
- REV-0174 — 조건 분기 직전에 무엇을 봐야 하는가

## 출처/검증
- `strace`/`ltrace`를 이용한 시스템 콜/라이브러리 호출 비교 기법: strace 공식 매뉴얼 페이지 및 REV-0111/REV-0112 기준.
- GDB `catch syscall`, `dprintf` 명령: GNU GDB 공식 매뉴얼 "Breakpoints" 챕터 기준.
- x64dbg 로그 전용 브레이크포인트("Log text"만 남기고 계속 실행) 동작: x64dbg 공식 문서(Breakpoints) 기준.
