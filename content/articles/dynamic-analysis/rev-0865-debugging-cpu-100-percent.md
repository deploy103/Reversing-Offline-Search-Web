## 한 줄 요약
디버깅 중 CPU 사용량이 갑자기 100%에 가깝게 치솟는 원인은 크게 세 가지, ①대상 프로그램 자체가 진짜로 CPU를 소모하는 무한/바쁜 루프(busy-loop, 안티디버깅일 수도 있음)를 돌고 있는 경우, ②디버거의 소프트웨어 워치포인트나 Trace/Run Trace 기능이 명령어 단위로 매번 멈춰서 검사하느라 원래 느린 경우, ③조건부 브레이크포인트의 조건식이 매우 자주 실행되는 지점(핫 루프)에 걸려 있어 매번 평가 비용이 누적되는 경우이며, 이 셋을 구분해야 올바르게 대응할 수 있다.

## 언제 검색해야 하나
- 디버거로 프로그램을 실행(`F9`/`continue`)했더니 CPU 사용량이 한 코어에서 100%로 튀고 응답이 느려질 때
- GDB에서 `watch` 명령을 걸었더니 실행 속도가 갑자기 몇 배로 느려지고 CPU 사용량이 치솟을 때
- x64dbg의 Trace Into(`Ctrl+F11`)나 Run Trace 기능을 켰더니 CPU와 디스크 사용량이 함께 급증할 때
- 반복문 안의 CALL에 조건부 브레이크포인트를 걸었는데 프로그램이 거의 멈춘 것처럼 느껴질 때

## 핵심 개념

### 원인 ① 대상 프로그램의 진짜 바쁜 루프
프로그램이 의도적으로(또는 버그로) CPU를 계속 소모하는 루프를 돌고 있을 수 있다. 특히 타이밍 기반 안티디버깅(REV-0872, REV-0538 참고)은 `RDTSC`나 `GetTickCount`/`QueryPerformanceCounter`를 반복 호출하며 짧은 시간 동안 매우 촘촘하게 루프를 도는 방식으로 구현되는 경우가 많아, 디버거가 붙어 있든 없든 그 구간에서는 CPU 사용량이 원래도 높게 나온다. 이 경우는 디버거 자체의 문제가 아니라 프로그램의 정상(혹은 의도된) 동작이다.

### 원인 ② 소프트웨어 워치포인트 — GDB의 흔한 함정
GDB의 `watch` 명령은 가능하면 CPU 디버그 레지스터를 이용한 하드웨어 워치포인트로 동작하지만, 대상 표현식이 너무 복잡하거나(레지스터/메모리 조합 표현식), 이미 하드웨어 워치포인트 슬롯을 다 썼거나, 원격 타깃이 하드웨어 워치포인트를 지원하지 않으면 GDB는 자동으로 **소프트웨어 워치포인트**로 전환한다. 소프트웨어 워치포인트는 사실상 "매 명령어마다 싱글스텝하며 값을 비교"하는 방식이라 실행 속도가 수십~수백 배 느려지고 그 시간 동안 GDB 프로세스(및 대상 프로세스)가 CPU를 거의 다 쓰게 된다.

### 원인 ③ x64dbg Trace Into / Run Trace
x64dbg의 Trace 계열 기능(`Ctrl+F11` Trace Into, Run Trace)은 수천~수백만 개의 명령어를 한 개씩 실행하면서 매번 레지스터/메모리 상태를 로그로 남긴다. 이는 기능이 무겁게 설계된 것이 정상이며, 큰 루프 안에서 이 기능을 켜면 CPU와 메모리(로그 저장) 사용량이 동시에 치솟는다. 필요한 범위에만 짧게 사용해야 한다.

### 원인 ④ 조건부 브레이크포인트의 반복 평가 비용
조건부 브레이크포인트(REV-0183, REV-0600 참고)는 그 주소에 도달할 때마다 디버거가 프로그램을 멈추고, 조건식을 평가하고, 거짓이면 다시 실행을 재개하는 과정을 반복한다. 이 주소가 초당 수만 번 실행되는 핫 루프 안에 있다면, 조건이 대부분 거짓이라 해도 "멈춤 → 평가 → 재개"라는 문맥 전환 비용이 누적되어 체감상 CPU 사용량이 치솟고 실행이 거의 멈춘 것처럼 느껴진다.

## 화면/코드에서 보이는 징후
- 작업 관리자/`top`에서 대상 프로세스 또는 디버거 프로세스(x64dbg.exe, gdb) CPU 사용량이 한 코어 기준 100%에 붙어 있다.
- GDB에서 `watch`를 걸 때 `Hardware watchpoints used exceed limit` 또는 소프트웨어 워치포인트로 전환됐다는 경고가 뜬 적이 있다.
- x64dbg Trace 관련 창(Trace Log)에 로그 줄 수가 매우 빠르게 늘어난다.
- 조건부 브레이크포인트를 건 이후로 `F9`를 눌러도 프로그램이 거의 반응하지 않는 것처럼 오래 걸린다.

## 가장 먼저 할 것
1. CPU를 많이 쓰는 것이 대상 프로세스인지, 디버거 프로세스인지부터 작업 관리자/`top`으로 구분한다.
2. 방금 건 워치포인트/Trace/조건부 브레이크포인트가 있다면 그것부터 끄고 다시 비교해본다.
3. 그래도 여전히 높다면, 프로그램 자체의 루프(안티디버깅 포함)를 의심하고 정적 분석으로 그 위치를 확인한다.

## 단계별 절차
1. 워치포인트를 걸어둔 상태라면 우선 삭제하거나 비활성화해서 CPU 사용량이 정상으로 돌아오는지 확인한다.
   ```
   (gdb) info watchpoints
   (gdb) delete <번호>
   ```
2. GDB가 소프트웨어 워치포인트로 전환됐는지 확인하려면 `watch` 실행 직후 메시지를 다시 살펴본다. 하드웨어 워치포인트를 명시적으로 강제하려면 대상 표현식을 단순화(레지스터 하나 또는 단일 메모리 주소)해서 다시 건다.
3. x64dbg Trace 기능을 켜둔 채로 큰 루프를 실행하고 있었다면, Trace를 끄고 필요한 구간에만 짧게(예: 한 번의 함수 호출 구간만) 다시 켠다.
4. 조건부 브레이크포인트가 핫 루프 안에 있다면, 조건을 더 이른 시점에 걸 수 있는 다른 지점(예: 루프 진입 직전, 또는 카운터 변수 자체에 대한 워치포인트)으로 옮기는 것을 고려한다.
5. 위 항목을 다 제거했는데도 CPU가 높다면, 그 구간의 코드를 정적으로 열어 실제로 무거운 루프(안티디버깅 타이밍 루프 등)가 있는지 확인한다(REV-0872 참고).

## 명령어/단축키
- GDB: `info watchpoints`, `delete <번호>`, `watch <expr>`(가능하면 단순 표현식으로)
- x64dbg: Trace Into(`Ctrl+F11`), Trace Over, Run Trace 관련 메뉴, Breakpoints 탭에서 조건부 브레이크포인트 임시 비활성화(체크 해제)
- 작업 관리자 / `top`, `htop` — CPU를 실제로 소비하는 프로세스 식별

## 출력 해석
- GDB에서 `watch` 걸 때 별다른 경고 없이 걸렸다면 하드웨어 워치포인트로 동작 중일 가능성이 높다(빠름). 반대로 "software watchpoint"라는 문구가 언급되면 명령어 단위 싱글스텝 방식이라 느릴 수밖에 없다.
- 작업 관리자에서 CPU를 많이 쓰는 쪽이 디버거 자신(x64dbg.exe, gdb)이라면 디버거의 분석 기능(Trace, 소프트웨어 워치포인트) 문제일 가능성이 크고, 대상 프로세스(target.exe) 자체라면 프로그램 로직(루프/안티디버깅) 문제일 가능성이 크다.

## 흔한 실수
- CPU 급증의 원인을 무작정 "안티디버깅이 걸렸다"고 단정하고 우회 기법부터 찾는 것 — 실제로는 자신이 걸어둔 워치포인트나 Trace 기능이 원인인 경우가 매우 흔하다.
- 소프트웨어 워치포인트로 전환된 것을 모른 채 "GDB가 원래 이렇게 느리다"고 오해하는 것 — 표현식을 단순화하면 하드웨어 워치포인트로 되돌아갈 수 있다.
- Trace 기능을 프로그램 전체 실행 동안 켜놓고 방치해서 로그가 수 GB로 불어나는 것 — 필요한 구간에서만 켜고 끄는 습관이 필요하다.

## 막혔을 때 다음 체크
- 타이밍 기반 안티디버깅이 의심된다면 → REV-0872를 참고해 스텝 실행 자체가 감지되는 상황인지 확인한다.
- CPU 문제와 별개로 디버거 UI 자체가 멈춘 것처럼 안 움직인다면 → REV-0873(디버거 UI 응답 없음 복구)을 참고한다.
- 워치포인트로 특정 값의 변경 지점을 찾으려던 것이었다면 → 하드웨어 워치포인트 슬롯 개수 제한(보통 4개)도 함께 고려한다(REV-0642 참고).

## 미니 예제
```
(gdb) watch *(int*)&g_complex_struct.field[i]
Watchpoint 2: *(int*)&g_complex_struct.field[i]
... (실행 속도 급격히 저하, CPU 100%)
(gdb) delete 2
(gdb) watch g_simple_flag
Hardware watchpoint 3: g_simple_flag
... (정상 속도로 복귀)
```
복잡한 표현식 대신 단순한 전역 변수 하나로 워치포인트를 바꾸자 하드웨어 워치포인트로 정상 동작하며 CPU 사용량이 즉시 정상으로 돌아왔다.

## 관련 글
- REV-0872 — 타이밍 기반 안티디버깅으로 스텝 실행이 너무 느려서 걸릴 때
- REV-0873 — 디버거 UI가 멈추거나 응답 없음일 때 복구 방법
- REV-0642 — GDB 명령어 심화 치트시트(watch/catch/tbreak)

## 출처/검증
- GDB 하드웨어/소프트웨어 워치포인트 선택 조건과 성능 차이: GNU GDB 공식 매뉴얼 "Setting Watchpoints" 섹션 기준.
- x64dbg Trace Into / Run Trace 기능 동작: x64dbg 공식 문서(Tracing) 기준.
- 타이밍 기반 안티디버깅에서 CPU를 소모하는 루프 패턴: 일반 리버싱/안티디버깅 참고 자료 기준.
