## 한 줄 요약
입력을 여러 단계(길이 체크 → 문자 집합 체크 → 부분 문자열 비교 → 해시/체크섬 비교 → 최종 XOR 등)에 걸쳐 검증하는 크랙미에서 "어디서 막히는지" 감이 안 잡힐 때는, 각 단계의 진입/통과/실패 지점에 로그 브레이크포인트를 걸어 "지금 몇 번째 단계까지 통과했는지"를 실행마다 자동으로 기록하고, 이 기록을 바탕으로 이진 탐색하듯 실패 단계를 좁혀가는 것이 이 카테고리(동적 분석) 전체에서 가장 실전적인 마무리 전략이다.

## 언제 검색해야 하나
- 정적 분석(REV-0767 참고)으로 검증 함수가 여러 개 체이닝되어 있는 것은 확인했는데, 실행 중 어느 함수에서 실제로 실패가 나는지 특정이 안 될 때
- 실패 메시지가 "Wrong!"처럼 뭉뚱그려 하나로만 나와서, 여러 단계 중 몇 번째에서 실패했는지 프로그램 출력만으로는 알 수 없을 때
- 단계 수가 많아서(5단계 이상) 하나씩 손으로 확인하기엔 너무 오래 걸릴 것 같을 때
- 여러 단계가 반복문/함수 포인터 테이블로 구현되어 있어 정적으로 순서를 파악하기 어려울 때

## 핵심 개념

### 이 문제는 이 카테고리에서 배운 모든 기법의 종합이다
다단계 검증을 정확히 추적하려면 지금까지 이 카테고리에서 다룬 기법들이 전부 조합되어야 한다.
- 어디에 멈춰야 하는지 판단하는 능력(REV-0169)
- 조건 분기 직전 값을 읽는 능력(REV-0174)
- 값이 예상과 다를 때 반복 회차/최적화를 의심하는 능력(REV-0867)
- 콜백/간접 호출로 숨겨진 단계를 찾는 능력(REV-0868)
- 안티디버깅이 섞여 있을 때 원인을 좁히는 능력(REV-0871)
- 값을 올바른 부호로 읽는 능력(REV-0870)

### "실패 지점 찾기"는 결국 이진 탐색이다
검증 단계가 `stage1 → stage2 → ... → stageN`처럼 순차적으로 이어진다면, 전체를 처음부터 하나씩 확인하는 대신 중간 단계에 먼저 브레이크포인트를 걸어 "여기까지는 통과했는가"를 확인하고, 통과했다면 뒷부분을, 실패했다면 앞부분을 다시 반으로 나누는 방식으로 로그 개수만큼 빠르게(단계 수가 N개면 약 log2(N)번의 확인만으로) 실패 단계를 좁힐 수 있다.

### "통과/실패"만 보지 말고 "그 단계에서의 입력 변형 상태"까지 기록한다
많은 검증 로직은 입력을 단계마다 변형(부분 XOR, 치환, 인덱스 재배열)하면서 넘긴다. 각 단계에서 단순히 "성공/실패" 불리언만 보면, 그 단계를 통과하기 위해 **정확히 어떤 값이 필요했는지**는 알 수 없다. 따라서 각 단계 직후에는 반드시 그 시점의 중간 버퍼/레지스터 값도 함께 로그로 남겨야, 나중에 그 단계를 만족시키는 입력을 역산할 수 있다.

## 화면/코드에서 보이는 징후
- 실행 결과로 "Wrong password" 한 줄만 나오고, 몇 번째 검증에서 실패했는지 알려주는 정보가 전혀 없다.
- 정적 분석에서 `check_len`, `check_charset`, `check_hash`, `check_final` 같은 이름(또는 이름 없는 여러 개의 유사한 함수)이 순서대로 호출되는 것이 보인다.
- 함수 포인터 배열이나 반복문으로 여러 검증 단계를 순회하는 구조라서, 정적으로는 몇 단계가 있는지 세기 어렵다.

## 가장 먼저 할 것
1. 정적 분석으로 검증 함수 후보를 최대한 나열하고, 대략적인 순서를 추정한다(REV-0767, REV-0805 참고).
2. 각 후보 함수의 시작/끝(또는 반환 직후)에 "멈추지 않고 로그만 남기는" 브레이크포인트를 건다.
3. 하나의 (틀린) 입력으로 한 번 실행해서, 어느 단계까지 로그가 남고 어디서부터 안 남는지 확인한다.

## 단계별 절차
1. 정적 분석으로 검증 함수 후보 목록을 만든다: `stage1_addr, stage2_addr, ..., stageN_addr`.
2. 각 함수의 반환 직후(REV-0176 참고)에 로그 전용 브레이크포인트를 건다.
   - GDB: `dprintf RET_ADDR, "stage%d return=%d\n", N, $eax`
   - x64dbg: 해당 주소에 브레이크포인트를 걸고 "Log text"에 `stageN return={eax}`를 설정한 뒤 "멈추지 않고 계속 실행"으로 설정
3. 아무 입력(예: 틀린 값 하나)으로 실행해서 로그를 끝까지 받는다.
4. 로그에서 마지막으로 성공(`return=1` 등)한 단계 번호를 확인한다 — 그 다음 단계가 실패 지점이다.
5. 단계 수가 매우 많다면(수십 개 이상), 처음부터 전부 로그를 걸지 않고 중간 지점 하나만 먼저 걸어 이진 탐색으로 범위를 좁힌 뒤, 좁혀진 범위 안에서만 세부 로그를 건다.
6. 실패 지점을 찾았다면, 그 단계 함수 내부에 다시 브레이크포인트를 걸어 REV-0174/REV-0867/REV-0870의 절차대로 그 안의 비교 로직과 값을 정밀하게 분석한다.
7. 그 단계를 통과시키는 값을 알아냈다면, 다음 단계로 넘어가 같은 과정을 반복한다. 이때 이전 단계에서 이미 확인한 로그는 그대로 남겨두고 새 단계만 추가하면, 매번 처음부터 전체를 다시 확인할 필요가 없다.

## 명령어/단축키
- GDB: `dprintf ADDR,"fmt",args`(멈추지 않는 로그), `break ADDR if EXPR`(조건부), `commands`+`continue`(로그 후 자동 재개)
- x64dbg: 브레이크포인트 "Log text" 설정(멈추지 않고 로그만), Log 창에서 실시간 확인
- 공통: 여러 번 실행 결과를 파일로 저장해 `diff`/텍스트 검색으로 비교

## 출력 해석
- 로그가 `stage1 return=1`, `stage2 return=1`, `stage3 return=0`까지만 찍히고 멈췄다면, 실패 지점은 정확히 3번째 단계다.
- 만약 `stage3` 로그 자체가 아예 안 찍힌다면, 2번째 단계에서 실패한 뒤 3번째 단계 함수 자체가 호출되지 않고 조기 종료됐다는 뜻이므로, 2번째 단계의 실패 처리 분기를 먼저 확인해야 한다.

## 흔한 실수
- 모든 단계에 한꺼번에 멈추는 브레이크포인트를 걸어서, 실행할 때마다 수십 번 `F9`/`continue`를 눌러야 하는 상황을 만드는 것 — 반드시 "멈추지 않는 로그"로 걸어야 한 번의 실행으로 전체 그림을 볼 수 있다.
- 성공/실패 불리언만 기록하고 중간 버퍼 값을 남기지 않아서, 실패 지점은 찾았는데 정작 그 단계를 통과할 값을 다시 처음부터 찾아야 하는 것.
- 단계 순서가 항상 고정이라고 가정하는 것 — 함수 포인터 테이블이나 조건에 따라 검증 순서 자체가 달라지는 구조도 있으므로, 여러 다른 입력으로도 순서가 같은지 확인해봐야 한다.
- 이 문제를 오직 하나의 원인으로만 접근하는 것 — 실제로는 안티디버깅(REV-0871)이 특정 단계에서만 섞여 있거나, 최적화로 두 단계가 하나로 합쳐져 보이는(REV-0867) 경우도 있으므로 이 카테고리의 다른 글들과 함께 접근해야 한다.

## 막혔을 때 다음 체크
- 로그를 걸었는데 특정 단계부터 아무 반응이 없다면 → 그 함수가 간접 호출/콜백으로 실행되는 건 아닌지 REV-0868을 참고해 확인한다.
- 단계별 값이 예상과 다르게 나온다면 → REV-0867(조건 분기 직전 값이 예상과 다를 때)의 확인 순서를 그대로 적용한다.
- 로그 도중 디버거가 이상하게 종료된다면 → REV-0871(안티디버깅 원인 좁히기)로 전환한다.
- 정적으로 전체 검증 로직을 이미 다 읽어낼 수 있을 것 같다면 → 굳이 동적 추적 없이 REV-0767(정적분석만으로 Flag 검증 로직을 완전히 복원하는 절차)로 되돌아가는 것도 고려한다.

## 미니 예제
```
(gdb) dprintf *0x401100+0x50,"stage1 return=%d\n",$eax
(gdb) dprintf *0x401200+0x40,"stage2 return=%d\n",$eax
(gdb) dprintf *0x401300+0x30,"stage3 return=%d\n",$eax
(gdb) run
stage1 return=1
stage2 return=1
stage3 return=0
[Inferior 1 (process 1234) exited with code 01]
```
로그 세 줄만으로 "1, 2단계는 통과했고 3단계에서 실패했다"는 것을 한 번의 실행으로 바로 확인했다. 이제 3단계 함수 내부만 집중적으로 분석하면 된다.

## 관련 글
- REV-0767 — 정적분석만으로 Flag 검증 로직을 완전히 복원하는 절차
- REV-0805 — 정적분석만으로 도저히 안 풀릴 때 동적으로 전환하는 기준
- REV-0871 — 안티디버깅 때문에 디버거에서 갑자기 종료될 때 원인 좁히기(실전)
- REV-0868 — 함수가 어디서 호출되는지 동적으로도 못 찾을 때(간접 호출/콜백)
- REV-0867 — 조건 분기 직전 값이 예상과 달라서 로직을 오해할 때
- REV-0169 — Breakpoint가 무엇이고 어디에 걸어야 하는가

## 출처/검증
- 로그 전용(멈추지 않는) 브레이크포인트를 이용한 실행 흐름 기록 기법: GNU GDB 공식 매뉴얼 "dprintf" 항목 및 x64dbg 공식 문서(Breakpoints, Log text) 기준.
- 이진 탐색 기반 문제 지점 좁히기는 일반적인 소프트웨어 디버깅 방법론(differential/bisection debugging)에 기반한 실전 절차다.
