## 한 줄 요약
x64dbg의 "New origin here"(우클릭 → 현재 명령어 포인터를 이 위치로 설정)와 GDB의 `jump *주소` / `set $rip = 주소` 명령을 쓰면, 실제로 명령어들을 한 줄씩 실행하지 않고도 RIP(EIP)를 원하는 주소로 강제로 옮겨 루프나 지루한 계산 구간을 건너뛸 수 있다.

## 언제 검색해야 하나
- 반복 횟수가 수만~수억 번인 루프(체크섬 계산, 무거운 해시 반복 등)를 한 스텝씩 넘기려면 너무 오래 걸려서, 루프가 끝난 지점으로 바로 건너뛰고 싶을 때
- 루프의 결과 자체보다 "루프 이후에 그 결과를 가지고 뭘 하는지"가 더 궁금할 때
- 루프 안에서 특정 조건이 되면 무한히 도는 것처럼 보이는 구간을 빠져나와 그 다음 코드를 먼저 확인하고 싶을 때
- 디버거로 실행하면 정상 실행보다 극단적으로 느려지는 구간(안티디버깅 타이밍 루프, 의도적 지연 등)을 우회하고 싶을 때

## 핵심 개념

### RIP를 옮긴다는 것의 의미
CPU는 항상 RIP(64비트) 또는 EIP(32비트)가 가리키는 주소의 명령어를 다음에 실행한다. 디버거가 멈춰 있는 동안 이 레지스터 값을 강제로 다른 주소로 바꾸면, 재개(Run/Continue) 시 CPU는 마치 그 주소로 `JMP`한 것처럼 그 지점부터 실행을 이어간다. 이는 실제 `JMP` 명령이 실행된 게 아니라 디버거가 CPU 컨텍스트를 직접 조작한 것이므로, 원래 프로그램 로직에는 없는 강제 개입이다.

### x64dbg — "New origin here"
디스어셈블리 창에서 원하는 목적지 줄(예: 루프가 끝난 직후 명령어)에 커서를 놓고 우클릭 → **New origin here**(단축키 없이 메뉴로 접근하는 경우가 많음, 버전에 따라 "Set RIP here"로 표기)를 선택하면 즉시 RIP가 그 주소로 바뀐다. Registers 패널에서도 RIP 값을 직접 더블클릭해 편집하는 것으로 동일한 효과를 낼 수 있다.

### GDB — `jump`와 `set $rip`
- `jump *0x401234`: 지정한 주소로 실행을 이어간다. 내부적으로 RIP를 그 주소로 설정한 뒤 실행을 재개하는 것과 거의 같지만, `jump`는 명령 자체가 "그 지점에 대한 새 브레이크포인트를 임시로 걸고 continue하는" 방식으로 동작하므로 곧바로 프로그램이 실행되기 시작한다는 점에 주의해야 한다(멈춘 상태를 유지하려면 목적지에 브레이크포인트를 미리 걸어둔다).
- `set $rip = 0x401234`: 레지스터 값만 바꾸고 프로그램은 실행되지 않는다. 이후 `continue`나 `stepi`로 직접 재개 시점을 조절할 수 있어 더 안전하다.

### 왜 이 방법이 "패치"보다 편한가
분기를 영구적으로 패치(REV-0184)하려면 바이너리 파일을 수정하고 저장해야 하지만, RIP 강제 이동은 지금 실행 중인 메모리 상태에서 즉시, 되돌릴 필요 없이 한 번만 시도해볼 수 있다. 다만 프로그램을 재시작하면 이 조작은 사라지므로, 매번 같은 위치를 건너뛰려면 반복해서 수행하거나 조건부 브레이크포인트(REV-0183, REV-0824)와 조합해 자동화해야 한다.

## 화면/코드에서 보이는 징후
- 디스어셈블리에 `loop_start:` 라벨 이후 `dec ecx` / `jnz loop_start` 형태의 카운터 루프가 있고, 카운터 초기값이 매우 큼(`mov ecx, 0x100000` 등)
- 브레이크포인트를 걸고 F8(Step Over)을 눌러도 루프 안에서 계속 같은 주소를 맴돌아, 실제로 몇 번을 눌러야 끝나는지 가늠이 안 됨
- x64dbg 상태 표시줄이나 GDB에서 CPU 사용률은 높은데 화면상 진행이 거의 안 되는 것처럼 보임(빠른 루프를 매 명령어 스텝으로 보고 있기 때문)

## 가장 먼저 할 것
루프를 건너뛰기 전에, 루프가 끝난 직후 정확히 어느 주소부터 코드가 이어지는지부터 디스어셈블리에서 확인한다(예: `jnz loop_start` 다음 줄). 또한 루프가 계산해서 레지스터/메모리에 남기는 결과 값이 있다면, 그 결과가 없는 상태로 건너뛰면 이후 로직이 깨질 수 있다는 점을 감안해 "결과 자체는 필요 없고 그 다음 흐름만 보고 싶은 경우"에 한해 이 방법을 쓴다.

## 단계별 절차
1. 루프의 시작과 끝 주소를 디스어셈블리에서 확인
2. 루프 끝 이후 첫 번째 명령어 주소를 정확히 기록
3. GDB는 그 주소에 임시 브레이크포인트를 걸어두거나 `set $rip = 주소`로 직접 이동, x64dbg는 그 줄에서 우클릭 → New origin here
4. 실행을 재개(GDB `continue`/`stepi`, x64dbg F9/F7)해서 실제로 원하는 지점부터 이어지는지 확인
5. 이후 로직이 루프 결과 값을 참조하는데 그 값이 비어있어 오동작한다면, REV-0825 방식으로 결과가 있어야 할 레지스터/메모리에 그럴듯한 값을 직접 채워 넣어 보정
6. 반복적으로 같은 루프를 건너뛰어야 한다면 루프 진입 지점에 조건부 브레이크포인트를 걸어 자동으로 이 과정을 반복하도록 구성(REV-0814 x64dbg 스크립트, 예정)

## 명령어/단축키
GDB(Linux):
```
disassemble loop_func
break *0x401260        # 루프 끝난 직후 주소
set $rip = 0x401260
continue
```
x64dbg(Windows):
```
디스어셈블리에서 목적지 줄 우클릭 → New origin here (Set RIP here)
Registers 패널에서 RIP 더블클릭 → 값 직접 입력
F9 (Run)
```

## 출력 해석
- x64dbg에서 New origin here를 실행하면 디스어셈블리 창의 화살표(현재 실행 위치 표시)가 즉시 그 줄로 이동한다. Registers 패널의 RIP 값도 동시에 바뀐 것을 확인할 수 있다.
- GDB `set $rip = 0x401260` 이후 `p/x $rip`을 찍어 실제로 원하는 주소로 바뀌었는지 재확인하는 습관이 좋다. `x/3i $rip`로 그 주소부터의 명령어 3줄을 미리 봐서 정말 원하는 코드가 맞는지 검증할 수 있다.
- 건너뛴 이후 프로그램이 곧바로 크래시하거나 이상한 값으로 분기한다면, 루프가 만들어야 했던 레지스터/스택/메모리 상태(예: 스택 정리, 카운터 초기화)를 건너뛰어서 그 이후 코드가 가정하는 전제조건이 깨졌을 가능성이 높다.

## 흔한 실수
- 루프 끝 주소를 잘못 짚어서(예: `jnz loop_start` 명령 자체의 주소로 이동해서 다시 루프에 갇힘) 원하는 효과를 못 얻는 것
- 루프가 계산한 값이 이후 로직에서 꼭 필요한 값인데도 그냥 건너뛰어서, 이후 코드가 초기화되지 않은 쓰레기 값을 가지고 동작하다 크래시하는 것
- GDB `jump` 명령을 썼는데 목적지에 브레이크포인트가 없어서 프로그램이 그대로 끝까지 실행되어 버려, 원하는 지점에서 다시 멈추지 못하는 것
- x64dbg에서 RIP만 옮기고 스택 포인터(RSP)는 그대로 둬서, 함수 내부의 스택 프레임 전제(로컬 변수 위치 등)가 깨져 있는데도 이를 인지하지 못하는 것

## 막혔을 때 다음 체크
- 분기 자체를 반대로 타게 하고 싶다면 RIP를 옮기는 것보다 → REV-0826 디버거에서 분기 조건을 강제로 바꿔서 실험하기(Flag 조작)가 더 안전한 대안일 수 있음
- 건너뛴 구간의 결과 값을 흉내 내야 한다면 → REV-0825 디버거에서 함수 인자를 실행 중 값으로 바꿔서 실험하기
- 이 조작을 반복 자동화하고 싶다면 → REV-0814 x64dbg 스크립트(Script) 탭으로 자동화하기 (예정)
- 이런 실험을 영구 패치로 확정하고 싶다면 → REV-0184 x64dbg CTF용 간단 패치와 저장
- "명령어를 건너뛴 것처럼 보이는" 관련 착시 현상이 궁금하면 → REV-0490 명령어 하나를 건너뛰고 실행되는 것처럼 보일 때

## 미니 예제
```
(gdb) disassemble
   0x0000000000401250 <+16>:  loop_start:
   0x0000000000401250 <+16>:  dec    ecx
   0x0000000000401253 <+19>:  jnz    0x401250 <loop_start>
   0x0000000000401255 <+21>:  mov    [rbp-0x4], eax   ; 루프 이후 첫 명령
(gdb) break *0x401255
(gdb) set $rip = 0x401255
(gdb) continue
Breakpoint 1, 0x0000000000401255 in compute_hash ()
```
`ecx`가 0이 될 때까지 수백만 번 돌아야 했을 루프를 건너뛰고, 바로 루프 이후 명령어에서 멈췄다. 다만 `eax`에 들어갈 계산 결과가 실제로는 만들어지지 않았으므로, 이후 로직이 이 값을 참조한다면 REV-0825 방식으로 적절한 값을 직접 채워 넣어야 한다.

## 출처/검증
- RIP/EIP가 다음 실행 명령어 주소를 가리키는 기본 동작: Intel 64 and IA-32 Architectures Software Developer's Manual Volume 1 기준.
- GDB `jump` 명령이 임시 브레이크포인트 기반으로 동작한다는 점과 `set $pc`(x86-64에서는 `$rip`) 사용법: GNU GDB 공식 매뉴얼("Continuing and Stepping" 절) 기준.
- x64dbg의 "New origin here"(RIP 강제 설정) 기능: x64dbg 공식 GitHub Wiki 문서 기준 (2026-09-09 검증).
