## 한 줄 요약
소프트웨어 브레이크포인트는 대상 주소의 원본 바이트를 `0xCC`(INT3)로 몰래 바꿔치기하는 방식이라, 프로그램이 실행 중 자기 코드를 다시 읽어 `0xCC`가 섞여 있는지 확인하거나 체크섬(CRC 등)을 계산해 원본과 비교하면 "누군가 내 코드를 건드렸다"는 사실을 잡아낼 수 있으며, Windows/Linux 모두 원리는 같고 하드웨어 브레이크포인트로 바꾸는 것이 가장 확실한 대응이다.

## 언제 검색해야 하나
- x64dbg에서 `bp`(소프트웨어)로 걸면 프로그램이 다르게 동작하는데, 같은 위치에 `ba`(하드웨어)로 걸면 정상 동작할 때
- GDB에서 그냥 `break`로 걸었을 때만 결과가 달라지고, 브레이크포인트 없이 실행하면 정상일 때
- 코드 섹션(`.text`) 바이트를 순회하며 `0xCC`와 비교하거나 CRC32를 계산하는 루프를 발견했을 때
- "self-checksumming" 힌트가 있는 CTF 문제를 만났을 때

## 핵심 개념

### 소프트웨어 브레이크포인트의 원리(플랫폼 공통)
x64dbg, GDB 모두 소프트웨어 브레이크포인트를 걸 때 대상 주소의 원본 바이트 1개를 저장해두고 그 자리를 `0xCC`(INT3)로 덮어쓴다. CPU가 그 지점에 도달하면 INT3 예외가 발생하고, 디버거가 이를 가로채 원래 바이트로 복원한 뒤 멈춘 것처럼 보여준다. 이 방식은 코드 메모리 자체를 수정하므로, 코드를 다시 읽어보면 이 변조가 그대로 드러난다.

### Windows에서의 탐지 — 바이트 비교/코드 체크섬
가장 단순한 방법은 함수 시작 바이트가 `0xCC`인지 직접 비교하는 것이고, 더 촘촘한 방법은 코드 섹션 전체 체크섬을 계산해 미리 저장해둔 값과 비교하는 것이다. 상세 구현 패턴과 우회 절차는 REV-0537에서 다룬다.

### Linux에서의 동등한 기법 — 자기 메모리 직접 읽기
Linux 바이너리도 원리는 동일하지만, 굳이 API 호출 없이 자기 자신의 코드 포인터를 그냥 역참조해서 바이트를 읽으면 된다(디버거가 붙어 있든 아니든 프로세스는 자기 자신의 코드 페이지를 읽기 권한으로 매핑하고 있다).
```c
unsigned char *p = (unsigned char *)&check_password;
if (p[0] == 0xCC) {
    _exit(1);
}
```
또는 `.text` 범위를 CRC32 등으로 체크섬화해서 링크 시점에 박아둔 값과 비교한다. `/proc/self/maps`로 `.text` 범위를 알아내 반복 검사하는 형태도 흔하다.

### 왜 정적 분석으로는 안 보이는가
디스크에 저장된 파일 자체는 `0xCC`로 패치되어 있지 않으므로, 이 검사 로직은 정적 분석 화면에서는 평범한 함수로 보인다. 오직 **디버거가 실제로 붙어 브레이크포인트가 걸린 실행 시점**에만 검사 대상 바이트가 바뀌어 있어 걸린다.

## 화면/코드에서 보이는 징후
```asm
mov  esi, offset func_start
mov  ecx, func_size
scan_loop:
    mov  al, [esi]
    cmp  al, 0CCh
    je   breakpoint_detected
    inc  esi
    loop scan_loop
```
- x64dbg에서 `bp`로 함수 시작에 걸었을 때만 프로그램이 종료되거나 잘못된 값을 출력하고, 브레이크포인트를 지우면 정상 동작
- CRC32 다항식 상수(`0xEDB88320` 등)를 계산하는 루프와 그 결과를 고정 상수와 비교하는 코드

## 가장 먼저 할 것
의심되는 검사 루프가 **어느 주소 범위**를 대상으로 하는지 먼저 확인한다(고정 함수 하나인지, `.text` 전체인지). 그 다음 문제의 주소에 소프트웨어 대신 하드웨어 브레이크포인트로 바꿔 걸어서 검사를 통과하는지 확인한다.

## 단계별 절차
1. 검사 루프의 시작 포인터/길이를 IDA나 Ghidra에서 추적해 대상 범위를 특정한다.
2. x64dbg: 문제 주소를 우클릭 → Breakpoint → Hardware, Execute로 바꿔 건다.
3. GDB: `break` 대신 `watch *(char*)0x주소`류의 하드웨어 워치포인트나, 아예 그 지점 대신 앞뒤 지점에 브레이크포인트를 걸어 우회한다.
4. 하드웨어 브레이크포인트로도 계속 걸린다면 REV-0842(하드웨어 브레이크포인트 탐지)로 원인을 넘겨서 확인한다.
5. 체크섬 비교 결과의 분기(`jz`/`jnz`)를 실제로 통과하는지 스텝 실행으로 직접 확인한다.

## 명령어/단축키
```text
x64dbg: bp <주소>(소프트웨어), 주소 우클릭 → Breakpoint → Hardware, Execute
```
```gdb
break FUNC
watch *(char*)0x주소
```

## 출력 해석
실행 중 메모리 덤프에서 원래 명령어 자리에 `CC`가 보이면 그 위치에 소프트웨어 브레이크포인트가 걸려 있다는 직접적 증거다. 체크섬 비교가 "불일치"로 나오는 분기를 따라가면 대개 종료나 잘못된 값 생성으로 이어진다.

## 흔한 실수
- 하드웨어 브레이크포인트도 이 검사에 걸릴 거라고 착각하는 것 — 이 기법은 오직 코드 바이트 변조(소프트웨어 BP)만 잡는다.
- 검사 루프가 한 번만 실행된다고 가정하는 것 — 여러 함수 진입 시점마다 반복 호출되는 경우가 흔하다.
- Linux에서는 이런 자체 검사가 없을 거라고 가정하는 것 — API 호출 없이 포인터 역참조만으로도 동일하게 구현 가능하다.
- 검사 로직을 발견하자마자 코드를 패치하는 것 — 패치 자체가 검사 대상 범위 안이면 다음 검사에서 다시 걸린다.

## 막혔을 때 다음 체크
- Windows 쪽 탐지 메커니즘을 더 자세히 보고 싶다면 → REV-0537 소프트웨어 브레이크포인트(0xCC) 탐지 기법
- 하드웨어 브레이크포인트로 바꿨는데도 계속 걸린다면 → REV-0842 하드웨어 브레이크포인트도 탐지당할 때
- 자기수정 코드와 결합된 경우라면 → REV-0230 Self-modifying Code 기초
- 애초에 브레이크포인트 자체가 안 걸리는 문제라면 → REV-0835 브레이크포인트가 안 걸릴 때 확인할 것들

## 미니 예제
```c
BOOL CheckSoftwareBreakpoint(void* funcAddr) {
    return (*(unsigned char*)funcAddr == 0xCC);
}
```
x64dbg에서 `bp main`을 걸고 실행하니 프로그램이 곧바로 종료됐다. 같은 위치에 하드웨어 브레이크포인트(`ba x 1 main` 상당)로 다시 걸자 정상적으로 멈췄고, 이후 분석은 하드웨어 브레이크포인트만으로 진행했다.

## 관련 글
- REV-0537 — 소프트웨어 브레이크포인트(0xCC) 탐지 기법
- REV-0842 — 하드웨어 브레이크포인트도 탐지당할 때
- REV-0230 — Self-modifying Code 기초
- REV-0835 — 브레이크포인트가 안 걸릴 때 확인할 것들

## 출처/검증
- 소프트웨어 브레이크포인트가 대상 바이트를 `0xCC`(INT3)로 치환하는 방식으로 동작한다는 것은 Intel 64 and IA-32 Architectures Software Developer's Manual의 `INT3` 설명 기준.
- 코드 체크섬/self-checksumming 기반 안티디버깅 기법은 다수의 공개 리버싱 레퍼런스(Check Point "Anti-Debug Tricks", Unprotect Project)에서 정리된 일반적인 패턴 기준(2026-09-09 확인).
