## 한 줄 요약
검증 함수 내부의 모든 명령을 다 이해하려 하지 않고, 함수 진입점과 반환 지점에 "멈추지 않고 값만 기록하는" 로그 브레이크포인트(x64dbg Log condition, GDB `dprintf`류 접근)를 걸어 여러 입력에 대한 인자·반환값 쌍을 빠르게 모으면, 내부 알고리즘을 몰라도 규칙을 귀납적으로 추론할 수 있다.

## 언제 검색해야 하나
- 검증 함수 내부가 인라인된 수학 연산, 여러 헬퍼 함수 호출로 뒤엉켜 있어 정적 분석으로 한 번에 이해하기 힘들 때
- "이 입력이면 이 반환값"이라는 데이터를 여러 개 쌓아서 패턴(예: 입력 길이와 반환값의 관계, 특정 바이트 위치의 영향)을 찾고 싶을 때
- 매번 브레이크포인트에 걸려서 수동으로 F9/`continue`를 누르는 게 아니라, 자동으로 로그만 남기고 계속 실행되게 하고 싶을 때
- REV-0829(완전 블랙박스 전략)까지 가기엔 아직 함수 위치를 알고 있고, 조금 더 세밀하게 "이 함수 하나"의 동작만 반복 관찰하고 싶을 때

## 핵심 개념

### "멈추는 브레이크포인트"와 "기록만 하는 브레이크포인트"의 차이
일반 브레이크포인트는 걸릴 때마다 실행을 멈추고 사람이 F9/`continue`를 눌러야 다음으로 넘어간다. 입력이 수십~수백 개라면 이 방식은 비효율적이다. 대신 "조건은 항상 참이지만 실제로 멈추지는 않고 로그만 남기는" 브레이크포인트를 쓰면, 프로그램이 알아서 끝까지 실행되는 동안 필요한 데이터만 자동으로 쌓인다.

- **x64dbg**: 브레이크포인트 Edit 창에서 **Break condition은 `0`**(항상 거짓 = 절대 안 멈춤)으로 두고, **Log condition은 `1`**(항상 참)로 두면서 **Log text**에 `{rdi} {rax}` 같은 표현식을 넣으면, 걸릴 때마다 실행은 멈추지 않고 Log 탭에 인자/반환값이 계속 쌓인다.
- **GDB**: `dprintf LOCATION, "format", args...` 명령이 정확히 이 역할을 한다. `dprintf validate_input, "arg=%s ret=?\n", buf`처럼 걸어두면 해당 위치를 지날 때마다 멈추지 않고 지정한 포맷으로 출력만 한다(반환값까지 한 줄에 찍으려면 진입점과 반환 지점 두 곳에 각각 `dprintf`를 걸어야 한다).

### 반환 지점에서 값을 잡는 법
함수 진입점에서는 인자를, 함수가 끝나는 시점(`ret` 직전 또는 호출부 복귀 직후)에서는 반환값(RAX/EAX)을 각각 로그로 남긴다. GDB는 `finish`를 자동화하기 어려우므로, 함수의 `ret` 명령 주소 자체에 `dprintf`를 걸어 `$rax`를 같이 찍는 방식이 실용적이다.

### 관찰 데이터를 어떻게 활용하는가
로그가 쌓이면 "입력 A → 반환 1", "입력 B → 반환 0"처럼 표를 만들 수 있다. 여러 입력을 체계적으로(예: 한 바이트씩 바꿔가며) 넣으면 어떤 바이트 위치가 결과에 영향을 주는지, 어떤 패턴이 성공 조건에 가까운지 귀납적으로 좁혀나갈 수 있다. 이는 REV-0832(런타임에서 발견한 상수를 정적분석과 대조)로 이어지는 실마리를 제공하기도 한다.

## 화면/코드에서 보이는 징후
- 같은 함수가 루프나 여러 호출 지점에서 서로 다른 인자로 계속 호출됨(예: 문자열의 각 문자마다 한 번씩 호출)
- 함수 내부에 헬퍼 함수 호출, 테이블 조회, 비트 연산이 뒤섞여 있어 의사코드만으로 규칙을 한눈에 알기 어려움
- 브레이크포인트를 걸어놓고 F9를 계속 눌러야 해서 "몇 번째 호출인지" 세는 것 자체가 번거로움

## 가장 먼저 할 것
함수의 진입점 주소와, 함수가 끝나는 지점(단일 `ret`이면 그 주소, 여러 `ret`이 있으면 전부)을 먼저 특정한다. 그 다음 calling convention에 따라 인자가 어느 레지스터/스택에 있는지(REV-0175), 반환값이 어느 레지스터에 담기는지(REV-0176) 확인해서 로그 표현식에 넣을 대상을 정한다.

## 단계별 절차
1. 대상 함수의 진입점과 `ret` 주소를 디스어셈블리에서 확인
2. x64dbg: 진입점에 브레이크포인트를 걸고 Edit breakpoint에서 Break condition `0`, Log condition `1`, Log text에 인자 레지스터 표현식 입력(예: `arg1={rcx} arg2={rdx}`)
3. x64dbg: `ret` 주소에도 같은 방식으로 Log text에 `{rax}` 입력
4. GDB: `dprintf 진입점주소, "in: rdi=%p\n", $rdi`
5. GDB: `dprintf ret주소, "out: rax=%d\n", $rax`
6. 프로그램을 여러 입력으로 반복 실행(가능하면 자동화 스크립트로 입력을 바꿔가며 여러 번 실행)
7. 쌓인 로그를 표로 정리해 입력별 반환값 패턴을 비교
8. 규칙이 보이면 REV-0832로 넘어가 발견한 상수/패턴을 정적 분석으로 재검증

## 명령어/단축키
GDB(Linux):
```
break validate_input
dprintf validate_input, "in: rdi=%p\n", $rdi
dprintf *0x4011f0, "out: rax=%d\n", $rax
run
```
x64dbg(Windows):
```
bp validate_input
Edit breakpoint → Break condition: 0, Log condition: 1
Log text: "in rcx={rcx} rdx={rdx}"
```

## 출력 해석
- GDB `dprintf` 로그는 일반 `printf`처럼 표준 출력에 그대로 섞여 나온다. 프로그램 자체의 출력과 헷갈리지 않도록 로그 문자열 앞에 `[TRACE]` 같은 접두어를 붙여두면 구분하기 쉽다.
- x64dbg Log 탭에 쌓인 줄들은 걸린 순서대로 시간순 기록이다. 같은 함수가 여러 번 호출됐다면 몇 번째 호출인지 줄 번호로 셀 수 있다.
- 반환값이 특정 입력 구간에서만 `1`(성공)로 바뀐다면, 그 구간에 해당하는 입력 특성(길이, 특정 바이트 값 등)이 검증 조건과 관련 있다는 강한 단서다.

## 흔한 실수
- Break condition을 `1`(기본값)로 그대로 둔 채 Log만 설정해서, 결국 매번 멈추는 일반 브레이크포인트와 다를 바 없어지는 것
- 함수에 `ret`이 여러 개(여러 개의 return 경로)인데 하나에만 로그를 걸어서 일부 호출의 반환값을 놓치는 것
- 로그가 너무 많이 쌓여서(수만 줄) 정작 어떤 패턴을 찾아야 하는지 못 찾고 로그 자체에 압도되는 것 — 처음부터 입력을 소규모로 체계적으로 바꿔가며 실행 횟수를 통제해야 함
- GDB `dprintf`의 포맷 문자열에 잘못된 타입 지정자를 써서(예: 포인터인데 `%d`) 엉뚱한 값이 찍히는 것을 알아채지 못하는 것

## 막혔을 때 다음 체크
- 함수 내부까지 아예 못 들어가고 프로그램 전체의 입출력만 봐야 하는 상황이면 → REV-0829 블랙박스 방식으로 입력-출력 관계만 파악하는 전략
- 인자/반환값 위치 자체가 헷갈리면 → REV-0175 CALL 직전 함수 인자 확인하는 법, REV-0176 CALL 직후 반환값 확인하는 법
- 이렇게 로그로 남긴 기록을 파일로 영구 보관하고 싶다면 → REV-0830 디버거 로그를 파일로 남겨서 나중에 분석하는 법
- 발견한 패턴/상수를 정적분석과 다시 맞춰보고 싶다면 → REV-0832 동적분석 중 발견한 상수를 정적분석과 다시 대조하는 법
- 메모리 값 변화를 관찰하려면 로그 브레이크포인트 대신 → REV-0191 GDB watchpoint 기초

## 미니 예제
```
(gdb) dprintf *0x4011a0, "in: buf=%s\n", (char*)$rdi
(gdb) dprintf *0x4011f0, "out: ret=%d\n", $rax
(gdb) run
in: buf=aaaa
out: ret=0
in: buf=bbbb
out: ret=0
in: buf=passw
out: ret=1
```
매 호출마다 멈추지 않고 입력 문자열과 반환값이 자동으로 로그로 남았다. `passw`를 넣었을 때만 `ret=1`이 나온 것을 보고, 입력의 어떤 특성이 성공과 연관되는지 추가 실험으로 좁혀갈 수 있다.
