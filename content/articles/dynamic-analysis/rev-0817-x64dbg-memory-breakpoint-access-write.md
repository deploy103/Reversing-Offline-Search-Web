## 한 줄 요약
x64dbg의 메모리 브레이크포인트(`bpm` 명령, 우클릭 메뉴의 `Breakpoint → Memory, Access/Write/Execute`)는 CPU 디버그 레지스터가 아니라 **Windows의 페이지 보호 속성(GUARD_PAGE)**을 이용해 특정 메모리 영역 전체(보통 4KB 페이지 단위)에 대한 읽기/쓰기/실행을 감시하는 방식으로, 개수 제한이 사실상 없고 버퍼처럼 넓은 범위를 한 번에 감시할 때 하드웨어 브레이크포인트보다 유리하다.

## 언제 검색해야 하나
- 감시해야 할 버퍼/구조체 크기가 하드웨어 브레이크포인트 한 번에 걸 수 있는 크기(보통 1/2/4/8바이트)보다 커서 전체를 한 번에 감시하고 싶을 때
- 하드웨어 브레이크포인트 슬롯(보통 4개)을 이미 다 써서 추가로 감시할 위치가 필요할 때
- 언패킹 문제에서 "압축 해제된 코드가 특정 메모리 영역에서 처음 실행되는 순간"을 잡고 싶을 때(OEP 찾기의 고전적 기법)
- `bpm`이라는 명령어를 어디선가 봤는데 하드웨어 브레이크포인트(`ba`)와 뭐가 다른지 궁금할 때
- 메모리 브레이크포인트를 걸었는데 의도한 곳이 아닌 다른 위치에서도 자꾸 걸릴 때

## 핵심 개념

### 동작 원리 — GUARD_PAGE 예외
메모리 브레이크포인트는 대상 주소가 속한 **메모리 페이지 전체**에 Windows의 `PAGE_GUARD` 보호 속성을 건다. 이 속성이 걸린 페이지에 어떤 방식으로든(읽기/쓰기/실행) 접근이 일어나면 CPU가 아니라 **운영체제 커널이 예외(`STATUS_GUARD_PAGE_VIOLATION`)를 발생**시키고, x64dbg가 이 예외를 가로채서 실행을 멈춘다. 하드웨어 브레이크포인트가 CPU의 `DR0`~`DR3` 디버그 레지스터를 직접 쓰는 것과는 전혀 다른 메커니즘이다.

이 방식의 특징:
- **개수 제한이 사실상 없다** — 디버그 레지스터 슬롯(4개)에 의존하지 않는다.
- **감시 단위가 페이지(보통 4KB)** — 지정한 주소가 속한 페이지 전체가 감시 대상이 되므로, 원하는 변수 바로 옆에 있는 무관한 데이터에 접근해도 예외가 발생해 멈출 수 있다(오탐 가능성).
- 예외 처리 왕복(커널 ↔ 디버거) 비용 때문에 **하드웨어 브레이크포인트보다 느리다.** 특히 그 페이지에 접근이 매우 잦으면 체감될 정도로 느려질 수 있다.

### 명령어 문법 — bpm(SetMemoryBPX)
```text
bpm arg1[, arg2[, arg3]]
```
- `arg1` — 감시할 메모리 영역 안의 아무 주소(그 주소가 속한 페이지 전체가 대상이 된다).
- `arg2`(선택) — 브레이크포인트가 걸린 뒤 자동으로 원래 보호 속성을 복원할지(`1`) 계속 유지할지(`0`) 여부. 이 값이 `0`/`1`이 아니면 이 인자가 곧 `arg3`(타입)로 취급된다. 즉 `bpm eax,r`은 `bpm eax,0,r`과 같다.
- `arg3`(선택) — 감시 타입: `a`(access, 읽기+쓰기+실행 전체 — 기본값), `r`(read), `w`(write), `x`(execute).

```text
bpm 00404060, 0, w      ; 00404060이 속한 페이지에 쓰기 감시
bpm eax, r               ; eax 주소가 속한 페이지에 읽기 감시
```

### 관련 명령들
- `bpmc`(`DeleteMemoryBPX`/`membpc`) — 메모리 브레이크포인트 삭제. 인자를 생략하면 모든 메모리 브레이크포인트를 삭제한다.
- `bpme`(`EnableMemoryBreakpoint`/`membpe`) — 비활성화된 메모리 브레이크포인트를 다시 활성화.
- `bpmrange`(`SetMemoryRangeBPX`/`memrangebp`) — 특정 주소 하나가 아니라 지정한 **범위** 전체에 대해 메모리 브레이크포인트를 건다. 감시하려는 버퍼가 여러 페이지에 걸쳐 있을 때 유용하다.
- `bpmcond`(`SetMemoryBreakpointCondition`) — 메모리 브레이크포인트에도 조건부 브레이크포인트(REV-0183)와 같은 방식으로 Break condition을 걸 수 있다. 조건이 `0`이 아닐 때만 실제로 멈춘다.
- `bpmlog`(`SetMemoryBreakpointLog`) — 메모리 브레이크포인트에 로그 텍스트를 지정해, 멈추지 않고 로그만 남기는 활용(REV-0816과 같은 발상)도 가능하다. 로그 조건을 지정하지 않으면 Break condition과 무관하게 항상 로그가 남는다.

### GUI로 걸기
Dump 창(메모리 덤프 뷰)에서 감시하려는 주소를 우클릭 → `Breakpoint → Memory, Access` / `Memory, Write` / `Memory, Execute`를 선택하면 `bpm` 명령을 직접 치지 않아도 동일한 효과를 낼 수 있다.

### 하드웨어 브레이크포인트, 소프트웨어 브레이크포인트와의 선택 기준
- **좁고 정확한 크기(1/2/4/8바이트)의 변수 하나를 빠르게 감시** → 하드웨어 브레이크포인트(REV-0818)가 더 빠르고 정밀하다.
- **버퍼/구조체처럼 넓은 범위를 통째로 감시하거나, 하드웨어 슬롯을 이미 다 썼을 때** → 메모리 브레이크포인트(`bpm`)가 적합하다.
- **코드 실행 지점 자체를 감시** → 소프트웨어 브레이크포인트(`bp`, REV-0178)가 기본이지만, 아직 디스어셈블되지 않은 데이터 영역(예: 언패킹 후 새로 생성된 코드)에 실행이 들어오는 순간을 잡고 싶다면 메모리 브레이크포인트의 `x`(execute) 타입이 유용하다 — 이게 바로 고전적인 "OEP 찾기" 기법 중 하나다.

## 화면/코드에서 보이는 징후
- 메모리 브레이크포인트가 걸린 페이지에 접근이 일어나면 프로그램이 멈추고, Log 탭에 `Guard page`(가드 페이지) 관련 예외 메시지가 남는다.
- Breakpoints 탭(또는 별도 Memory Breakpoints 목록)에서 타입(Access/Write/Execute)과 대상 페이지 범위를 확인할 수 있다.
- 감시하려는 변수와 무관해 보이는 코드에서도 멈춘다면, 같은 페이지 안의 다른 데이터에 접근이 일어난 것일 수 있다 — 페이지 단위 감시의 특성이다.
- 하드웨어 브레이크포인트와 달리 CPU 탭에 `DR7` 관련 표시는 나타나지 않는다(디버그 레지스터를 쓰지 않으므로).

## 가장 먼저 할 것
감시하려는 데이터의 정확한 주소와 크기를 먼저 확인한다(`dump 주소`로 Dump 창에 띄워보기). 크기가 몇 바이트에 불과하고 반복 접근이 매우 잦다면 하드웨어 브레이크포인트(REV-0818)부터 검토하고, 버퍼 전체거나 슬롯이 부족하면 메모리 브레이크포인트로 넘어간다.

## 단계별 절차

**1) 감시 대상 주소 확인**

Dump 창에서 `Ctrl+G`(Go to)로 원하는 주소로 이동하거나, 커맨드 바에서 `dump 주소`를 입력해 확인한다.

**2) GUI로 걸기**

Dump 창에서 해당 바이트 위치를 우클릭 → `Breakpoint → Memory, Write`(쓰기 감시 예시)를 선택한다.

**3) 명령어로 걸기(선택)**

```text
bpm 00404060, 0, w
```

**4) 실행하고 결과 확인**

`F9`로 실행한다. 그 페이지에 쓰기가 발생하면 자동으로 멈추고, CPU 탭에서 어느 명령어가 값을 바꿨는지 바로 확인할 수 있다.

**5) 오탐이 잦으면 조건/로그로 좁히기**

같은 페이지의 다른 데이터 때문에 너무 자주 멈춘다면 `bpmcond`로 조건을 걸어 원하는 조건일 때만 실제로 멈추게 하거나, `bpmlog`로 멈추지 않고 로그만 남기는 방식으로 바꾼다.

**6) 다 썼으면 정리**

```text
bpmc 00404060
```

## 명령어/단축키
```text
bpm 주소[, 자동복원(0/1)][, 타입(a/r/w/x)]   ; 메모리 브레이크포인트 설정 (SetMemoryBPX)
bpmc [주소]                                    ; 삭제, 인자 없으면 전체 삭제 (DeleteMemoryBPX)
bpme [주소]                                    ; 활성화, 인자 없으면 전체 활성화 (EnableMemoryBreakpoint)
bpmrange 시작주소, 끝주소[, 타입]              ; 범위 전체에 메모리 브레이크포인트 (SetMemoryRangeBPX)
bpmcond 주소, "조건식"                          ; 조건부로 만들기 (SetMemoryBreakpointCondition)
bpmlog 주소, "로그텍스트"                       ; 로그만 남기도록 설정 (SetMemoryBreakpointLog)
```
Dump 창 우클릭 → `Breakpoint → Memory, Access/Write/Execute` : GUI로 동일하게 설정.

## 출력 해석
- Log 탭에 가드 페이지 위반 관련 메시지와 함께 멈춘 주소가 나오면, CPU 탭에서 `x/i $rip`에 해당하는 현재 명령어를 확인해 정확히 어떤 명령(예: `mov`, `movsb`)이 그 접근을 유발했는지 본다.
- 하드웨어 브레이크포인트에 비해 멈추는 시점이 명령어 실행 "직후"인지 "직전"인지 미묘하게 다르게 느껴질 수 있는데, 이는 예외 기반 메커니즘 특성상 처리 시점 차이에서 비롯된다 — 정확한 값 확인이 필요하면 Stack/Dump 창을 함께 봐서 실제 값 변화가 반영됐는지 확인한다.
- 같은 페이지의 여러 변수에서 반복적으로 멈춘다면, 그 페이지 안의 다른 데이터 배치를 `dump 주소`로 확인해 진짜 관심 대상과 혼동되고 있는지 점검한다.

## 흔한 실수
- 감시하려는 변수 크기(예: 4바이트)만 정확히 감시된다고 착각하는 것 — 실제로는 그 변수가 속한 페이지(보통 4096바이트) 전체가 감시 대상이라서, 같은 페이지의 다른 데이터에 접근해도 멈춘다.
- 접근이 매우 잦은 페이지(예: 스택 상단)에 메모리 브레이크포인트를 걸어서 프로그램이 사실상 멈춘 것처럼 느려지는 것 — 예외 기반 방식이라 하드웨어 브레이크포인트보다 오버헤드가 크다.
- `bpm`의 두 번째 인자(자동 복원 여부)와 세 번째 인자(타입)의 순서를 헷갈려서 `bpm eax, w`처럼 쓰면 안 되고, 타입만 지정하고 싶다면 `bpm eax, w`가 실제로는 "자동복원=w"로 잘못 해석될 위험이 있다는 점(문서에 따르면 arg2가 0/1이 아니면 arg3로 간주되므로 `bpm eax,w`도 결과적으로 타입 `w`로 해석되지만, 명확성을 위해 `bpm eax,0,w`처럼 항상 세 인자를 다 채우는 습관이 안전하다).
- 메모리 브레이크포인트를 건 뒤 해당 페이지가 언패킹 과정에서 통째로 재할당/해제되는 경우를 고려하지 않아, 브레이크포인트가 조용히 무효화되는 것을 놓치는 경우.
- 하드웨어 브레이크포인트로 충분한 작은 변수 하나에도 습관적으로 메모리 브레이크포인트를 걸어 불필요하게 실행 속도를 떨어뜨리는 경우.

## 막혔을 때 다음 체크
- 좁은 범위(1~8바이트)를 더 빠르게 감시하고 싶다면 → REV-0818 x64dbg에서 하드웨어 브레이크포인트 활용하기를 참고한다.
- 감시 대상 자체를 조건으로 좁히거나 로그만 남기고 싶다면 → REV-0183 x64dbg 조건부 Breakpoint 기초, REV-0816 x64dbg Conditional Log Breakpoint 활용하기의 조건/로그 문법을 그대로 `bpmcond`/`bpmlog`에 적용한다.
- 기본적인 브레이크포인트 개념과 소프트웨어 브레이크포인트가 먼저 궁금하다면 → REV-0178 x64dbg Breakpoint 설정과 삭제를 본다.
- 감시 대상 주소를 아직 못 찾았다면 → REV-0182 x64dbg Memory Map과 Module View로 먼저 메모리 레이아웃을 확인한다.

## 미니 예제
언패킹된 코드가 힙에 새로 만들어진 뒤 처음 실행되는 순간(OEP 후보)을 잡는 상황이다.

```text
1. 압축 해제 루틴이 데이터를 써 넣는 힙 영역 주소를 Dump 창에서 확인 (예: 00650000)
2. 커맨드 바에 bpm 00650000, 0, x 입력 (해당 페이지에 실행 감시)
3. F9로 실행 — 압축 해제 루틴이 값을 쓰기만 할 때는 멈추지 않음(감시 타입이 x이므로)
4. 압축 해제가 끝나고 프로그램이 그 영역으로 점프해서 첫 명령어를 "실행"하는 순간 자동으로 멈춤
5. CPU 탭에서 현재 CIP가 바로 OEP 후보 주소 — 여기서부터 원본 코드 분석을 시작
```

## 관련 글
- REV-0818 — x64dbg에서 하드웨어 브레이크포인트 활용하기
- REV-0183 — x64dbg 조건부 Breakpoint 기초
- REV-0816 — x64dbg Conditional Log Breakpoint 활용하기
- REV-0178 — x64dbg Breakpoint 설정과 삭제
- REV-0182 — x64dbg Memory Map과 Module View

## 출처/검증
- `bpm`/`SetMemoryBPX` 명령의 인자 구조(`arg1` 주소, `arg2` 자동복원 0/1, `arg3` 타입 a/r/w/x)와 기본값(`a`): 공식 문서 help.x64dbg.com의 `commands/breakpoint-control/SetMemoryBPX.html` 기준(2026-09-09 조사).
- `bpmc`(`DeleteMemoryBPX`), `bpme`(`EnableMemoryBreakpoint`), `bpmrange`(`SetMemoryRangeBPX`), `bpmcond`(`SetMemoryBreakpointCondition`), `bpmlog`(`SetMemoryBreakpointLog`) 명령과 각 설명: 같은 공식 문서 사이트의 `commands/breakpoint-control/` 및 `commands/conditional-breakpoint-control/` 섹션 기준.
- 메모리 브레이크포인트가 GUARD_PAGE(페이지 보호 속성) 기반이며 하드웨어 브레이크포인트(디버그 레지스터 기반)와 메커니즘이 다르다는 설명: 공식 문서의 명령 설명("Set a memory breakpoint (GUARD_PAGE) on the whole memory region")에 근거했고, 페이지 단위 감시로 인한 오탐 가능성 및 속도 차이는 Windows `PAGE_GUARD` 보호 속성의 일반적으로 잘 알려진 동작 방식에 근거한 설명이므로 실습 환경에서 직접 검증을 권장한다.
