## 한 줄 요약
x64dbg에서 브레이크포인트는 디스어셈블리 줄에 커서를 두고 **F2**를 누르면 소프트웨어 브레이크포인트(빨간 원)로 설정/해제되며, 전체 목록은 **Breakpoints 탭**에서 관리하고, 명령어로는 `bp 주소`(설정)와 `bc 주소`(삭제)를 쓴다.

## 언제 검색해야 하나
- 특정 함수나 명령어에서 실행을 멈추고 값을 확인하고 싶을 때
- F2를 눌렀는데 브레이크포인트가 걸렸는지 안 걸렸는지 헷갈릴 때
- 브레이크포인트를 지웠다고 생각했는데 계속 거기서 멈출 때
- 코드 영역이 아니라 메모리 값이 바뀌거나 읽힐 때 멈추게 하고 싶을 때(하드웨어 브레이크포인트)
- 함수 이름(`CreateFileW` 등)만 알고 정확한 주소는 모를 때 브레이크포인트를 걸고 싶을 때

## 핵심 개념
x64dbg의 브레이크포인트는 크게 두 종류로 나뉜다.

1. **소프트웨어 브레이크포인트(Software Breakpoint)** — 대상 주소의 원래 바이트를 `INT3`(0xCC) 명령어로 임시로 바꿔치기해서, 그 지점에 실행이 도달하면 CPU가 예외를 일으키고 x64dbg가 이를 가로채 실행을 멈춘다. 코드 실행 지점에만 걸 수 있고, 개수 제한이 사실상 없다. F2로 거는 브레이크포인트가 바로 이것이다.
2. **하드웨어 브레이크포인트(Hardware Breakpoint)** — CPU의 디버그 레지스터(DR0~DR3)를 이용해서 특정 메모리 주소에 대한 **실행(Execute)**, **쓰기(Write)**, **읽기+쓰기(Access)**를 감시한다. 코드가 아니라 데이터 영역(변수, 버퍼 등)에 걸 수 있다는 점이 소프트웨어 브레이크포인트와 결정적으로 다르다. 단, CPU 디버그 레지스터 개수 제한 때문에 보통 동시에 최대 4개까지만 걸 수 있다.

이 외에 **메모리 브레이크포인트(Memory Breakpoint)** 도 있는데, 이건 페이지 단위로 메모리 접근 권한(보호 속성)을 바꿔서 그 페이지에 접근이 일어나면 예외를 발생시키는 방식이다. 특정 메모리 페이지 전체를 감시할 때 유용하다.

모든 브레이크포인트는 **Breakpoints 탭**(화면 위쪽 탭 목록)에서 한눈에 볼 수 있다. 여기에는 종류, 주소, 모듈, 활성화 여부, 히트 횟수(Hit count) 등이 표로 표시된다.

## 화면/코드에서 보이는 징후
- 소프트웨어 브레이크포인트가 걸린 줄은 디스어셈블리 창 왼쪽에 **빨간 원(●)**으로 표시된다.
- 비활성화(Disable)된 브레이크포인트는 빨간 원 대신 **회색/파란 테두리만 있는 원**으로 표시되어, 걸려 있지만 지금은 작동하지 않는다는 걸 구분해준다.
- 실행이 브레이크포인트에 걸려서 멈추면 상태 바가 "Paused"로 바뀌고, 자동으로 CPU 탭이 열리며 해당 줄이 노란색/회색으로 강조된다.
- Breakpoints 탭에는 각 브레이크포인트가 몇 번 히트됐는지(Hit count) 숫자로 표시되어, 특정 코드가 몇 번 실행됐는지 가늠할 수 있다.
- 명령어 입력창(하단 커맨드 바)에 `bp` 계열 명령을 입력하고 실행하면 Log 탭에 "Breakpoint at 주소 set!" 같은 메시지가 남는다.

## 가장 먼저 할 것
브레이크포인트를 걸기 전에, 지금 멈추고 싶은 지점이 **코드 실행 지점**인지 아니면 **메모리 값의 변화**인지부터 구분한다. "이 함수가 호출될 때 멈추고 싶다"면 소프트웨어 브레이크포인트(F2)면 충분하고, "이 변수 값이 언제 바뀌는지 모르겠다"면 하드웨어 브레이크포인트(쓰기 감시)가 필요하다.

## 단계별 절차

**1) 소프트웨어 브레이크포인트 걸기/해제하기 (F2)**

CPU 탭 디스어셈블리 창에서 원하는 줄을 마우스로 클릭해 커서를 놓고 **F2**를 누른다. 빨간 원이 생기면 브레이크포인트가 걸린 것이다. 같은 줄에서 F2를 한 번 더 누르면 브레이크포인트가 완전히 삭제된다(빨간 원이 사라짐).

**2) 우클릭 메뉴로 세밀하게 제어하기**

디스어셈블리에서 줄을 우클릭하면 `Breakpoint` 서브메뉴가 나온다. 여기서 다음을 고를 수 있다.
- `Toggle` — F2와 동일하게 설정/해제.
- `Set Hardware on Execution` — 이 주소에 실행이 도달하면 멈추는 하드웨어 브레이크포인트.
- `Remove` — 해당 브레이크포인트 삭제.
- `Edit breakpoint` — 조건/로그/실행 명령을 설정하는 대화상자를 연다(자세한 내용은 조건부 브레이크포인트 문서 참고).

레지스터 값이나 Dump 창에서 특정 메모리 주소를 우클릭하면 `Breakpoint → Hardware, Access/Write/Execute` 메뉴로 데이터 영역에 하드웨어 브레이크포인트를 걸 수 있다.

**3) 함수 이름으로 브레이크포인트 걸기 (명령어 사용)**

정확한 주소를 몰라도, 화면 하단의 명령어 입력창에 다음처럼 입력하면 함수 이름으로 바로 걸 수 있다.

```text
bp kernel32.CreateFileW
bp sample.MessageBoxA
```

`모듈이름.함수이름` 형태로 입력하면 x64dbg가 심볼/Export 테이블을 참고해 해당 주소를 찾아 브레이크포인트를 건다. 주소를 직접 안다면 `bp 00401234`처럼 주소로도 걸 수 있다.

**4) Breakpoints 탭에서 전체 관리하기**

화면 위쪽 `Breakpoints` 탭을 클릭하면 지금까지 걸어 둔 모든 브레이크포인트가 표로 나온다. 각 행을 우클릭하면 `Remove`(삭제), `Disable`(비활성화), `Enable`(다시 활성화)를 선택할 수 있다. 여러 개를 한꺼번에 정리할 때는 이 탭이 CPU 창에서 하나씩 F2를 누르는 것보다 훨씬 빠르다.

**5) 삭제/비활성화 구분해서 쓰기**

브레이크포인트를 잠깐만 꺼두고 싶다면(나중에 다시 켤 계획이면) **Disable**을, 아예 필요 없어졌다면 **Remove(삭제)**를 쓴다. Disable된 브레이크포인트는 화면에 빨간 원이 아니라 테두리만 있는 원으로 남아서 위치를 기억할 수 있다.

## 상황별로 어떤 브레이크포인트를 걸어야 할까
어떤 브레이크포인트를 걸지 고민될 때는 다음 기준으로 판단하면 대부분 해결된다.

- **"이 함수/이 명령어 줄이 실행되는 순간을 보고 싶다"** → 소프트웨어 브레이크포인트(F2)로 충분하다. 개수 제한도 사실상 없어서 CTF 실습에서 가장 많이 쓰는 방식이다.
- **"이 변수/버퍼 값이 언제 바뀌는지 코드를 안 봐도 알고 싶다"** → 그 메모리 주소에 하드웨어 브레이크포인트(Write)를 건다. 어떤 함수가 그 값을 바꾸는지 코드를 먼저 찾지 않아도, 값이 바뀌는 순간 자동으로 멈춰서 그 지점의 코드를 바로 확인할 수 있다.
- **"코드로 인식되지 않는 영역(패킹된 데이터 등)에 실행이 들어오는 순간을 잡고 싶다"** → 그 메모리 페이지 전체에 대한 메모리 브레이크포인트(Execute)가 적합하다. 소프트웨어 브레이크포인트는 코드로 인식된 위치에만 걸 수 있어서, 아직 디스어셈블되지 않은 데이터 영역에는 걸리지 않는 경우가 있기 때문이다.

또한 F2로 건 브레이크포인트를 일회성으로만 쓰고 싶다면, 원하는 줄에 커서를 두고 **F4(Run until Selection, 선택 지점까지 실행)**를 사용하는 방법도 있다. F4는 임시로 그 줄까지만 실행하고, 브레이크포인트 목록에 흔적을 남기지 않으므로 나중에 Breakpoints 탭을 정리할 필요가 없어 편리하다.

## 명령어/단축키
- `F2` : 커서 위치에 소프트웨어 브레이크포인트 토글(설정/해제)
- `F4` : Run until Selection(커서가 있는 줄까지만 임시로 실행, 브레이크포인트를 남기지 않음)
- `bp 주소` 또는 `bp 모듈.함수이름` : 소프트웨어 브레이크포인트 설정
- `bc 주소` : 해당 주소의 브레이크포인트 삭제(clear)
- `bd 주소` : 브레이크포인트 비활성화(disable)
- `be 주소` : 브레이크포인트 재활성화(enable)
- `ba <타입> <크기> 주소` : 하드웨어 브레이크포인트 설정(예: `ba w 4 0x401000`은 해당 주소 4바이트에 쓰기 감시)
- 우클릭 → `Breakpoint → Remove/Edit breakpoint` : 세부 관리

## 출력 해석
- 브레이크포인트에 걸려서 프로그램이 멈추면 Log 탭에 "Breakpoint at [주소]!" 형태의 메시지가 남는다. 이 로그로 몇 번째 히트에서 멈췄는지 시간순으로 되짚어볼 수 있다.
- Breakpoints 탭의 Hit count가 0이면 아직 한 번도 그 코드/메모리에 도달하지 않았다는 뜻이다. 예상한 흐름과 다르게 코드가 실행되고 있을 가능성을 의심해야 한다.
- `bp` 명령 실행 후 Log에 에러 메시지가 뜨면(예: "Invalid address") 함수 이름 철자가 틀렸거나 아직 해당 모듈이 로드되지 않은 시점일 수 있다. DLL 함수라면 그 DLL이 로드된 이후에 브레이크포인트를 걸어야 한다.

## 흔한 실수
- F2를 두 번 눌러서 브레이크포인트가 없어졌다고 착각하는 경우 — F2는 토글이라 한 번 더 누르면 다시 사라진다. 지금 상태가 헷갈리면 Breakpoints 탭에서 확인하는 것이 확실하다.
- 하드웨어 브레이크포인트를 4개 넘게 걸려고 시도해서 에러가 나는 경우 — CPU 디버그 레지스터 한계 때문에 보통 동시에 4개까지만 가능하다.
- DLL이 아직 로드되기 전에 `bp 모듈.함수`를 시도해서 "찾을 수 없음" 에러를 만나는 경우 — 해당 DLL을 로드하는 코드(예: `LoadLibrary` 호출) 이후 시점에 걸거나, 모듈 로드 이벤트에 브레이크포인트를 걸어야 한다.
- Disable과 Remove를 헷갈려서, Disable만 하고 "삭제했다"고 착각한 채 나중에 다시 그 지점에서 멈추지 않아 당황하는 경우(비활성화 상태이므로 당연히 안 멈춘다) — 반대로 Remove했다고 생각했는데 실은 Disable 상태로 남아 원이 계속 보이는 경우도 있다.
- 소프트웨어 브레이크포인트를 코드가 아닌 데이터 영역(자체 실행되지 않는 부분)에 걸어서 프로그램이 이상하게 죽는 경우 — 데이터 영역 감시는 반드시 하드웨어/메모리 브레이크포인트를 써야 한다.

## 미니 예제
CTF 크랙미에서 `MessageBoxA` 호출 직전에 멈춰서 인자를 확인하는 흐름이다.

```text
1. 명령어 입력창에 bp user32.MessageBoxA 입력 후 Enter
2. F9(Run)로 프로그램 실행
3. MessageBoxA 호출 직전에 자동으로 멈춤 (Breakpoints 탭에 Hit count 1로 표시)
4. Stack 창에서 인자(hWnd, lpText, lpCaption, uType) 확인
5. 확인이 끝나면 Breakpoints 탭에서 해당 항목 우클릭 → Remove로 정리
```

- 하드웨어 브레이크포인트 동시 개수 제한(통상 4개)은 x86/x64 CPU의 디버그 레지스터(DR0~DR3) 구조에 근거한 일반적으로 잘 알려진 사실이며, x64dbg 자체 문서에서 개수를 명시적으로 재확인하지는 못했으므로 실습 환경에서 직접 확인을 권장한다.
