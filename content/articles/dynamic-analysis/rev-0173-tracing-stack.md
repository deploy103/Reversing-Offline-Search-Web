## 한 줄 요약
디버거의 스택 창(x64dbg) 또는 `x/x $rsp`, `bt`(GDB/Pwndbg)로 RSP(스택 포인터) 주변 메모리를 직접 들여다보면, 지역 변수, 저장된 레지스터, 반환 주소, 함수 인자(스택으로 넘어간 경우)가 실제로 어떤 값으로 쌓여 있는지 확인할 수 있다 — 스택 오버플로우, 반환 주소 덮어쓰기, 지역 변수 추적 같은 문제에서 필수적인 기술이다.

## 언제 검색해야 하나
- 함수 안에서 `[rbp-0x20]` 같은 지역 변수의 실제 값이 뭔지 궁금할 때
- 스택 버퍼 오버플로우 문제를 풀면서 내가 넣은 입력이 실제로 스택 어디까지 덮어썼는지 확인하고 싶을 때
- 함수 호출 체인이 어떻게 쌓여 있는지(누가 누구를 불렀는지) 확인하고 싶을 때(콜스택)
- 반환 주소가 스택의 정확히 어느 위치에 있는지, 그리고 그 값이 내 입력으로 덮였는지 확인하고 싶을 때
- x64dbg의 스택 창에 나오는 여러 줄의 주소와 값이 뭘 의미하는지 모를 때
- GDB에서 `bt`(backtrace)를 쳤는데 나오는 스택 프레임 목록을 어떻게 읽어야 할지 모를 때

## 핵심 개념

### 스택이란 무엇을 담고 있는가 (복습)
스택은 함수 호출/지역 변수를 위해 쓰는 메모리 영역으로, 높은 주소에서 낮은 주소 방향으로 자란다(PUSH하면 RSP가 감소). 함수가 호출되면 그 안에 다음과 같은 것들이 순서대로 쌓인다(REV-0031 스택 프레임 참고).
1. `CALL` 실행 시 반환 주소가 PUSH됨
2. 함수 프롤로그에서 이전 RBP가 PUSH됨(`push rbp`)
3. `sub rsp, N`으로 지역 변수 공간이 확보됨
4. 그 공간에 지역 변수(버퍼, 카운터 등)가 저장됨

스택을 추적한다는 것은 이 메모리 영역을 실행 중 실제로 읽어서, "지금 이 순간 이 주소에 무슨 값이 들어있는가"를 확인하는 것이다.

### x64dbg 스택 창
x64dbg는 기본 레이아웃에 항상 "Stack" 창을 띄워둔다. 이 창은 RSP를 기준으로 위에서부터 순서대로 8바이트(x64)/4바이트(x86)씩 메모리 값을 보여주며, 각 줄 왼쪽에는 그 값이 저장된 실제 메모리 주소, 오른쪽에는 x64dbg가 자동으로 해석한 주석(예: 그 값이 반환 주소라면 어느 함수의 어느 줄로 돌아가는지, 문자열이면 그 내용)이 함께 표시된다. RSP가 가리키는 줄에는 화살표 표시가 있어 "지금 스택 맨 위"를 바로 알 수 있다.

### RSP vs RBP 기준
- **RSP(스택 포인터)**: 현재 스택의 맨 위(가장 낮은 주소)를 가리킨다. PUSH/POP, CALL/RET마다 계속 바뀐다.
- **RBP(베이스 포인터)**: 함수 진입 시점의 RSP 값을 고정해서 저장해 둔 것(표준 프롤로그 `push rbp; mov rbp, rsp` 사용 시). 함수 실행 중 RSP는 계속 움직이지만 RBP는 고정되어 있으므로, 지역 변수는 보통 `[rbp-0x14]`처럼 **RBP 기준 음수 오프셋**으로 표현된다. IDA/Ghidra 디스어셈블리에 나오는 `[rbp-0x20]` 같은 표현이 바로 이것이다.
- 최적화된 코드(프레임 포인터 생략, `-fomit-frame-pointer`)에서는 RBP를 범용 레지스터로 재활용하고 지역 변수를 전부 RSP 기준 오프셋으로 표현하기도 한다 — 이 경우 IDA가 스택 뷰(View → Open subviews → Stack frame)로 정리해서 보여준다.

### 콜스택(Call Stack)이란
스택에 쌓인 여러 개의 반환 주소를 순서대로 따라가면, 지금 실행 중인 함수가 "누구에게 불려서 여기까지 왔는지" 그 호출 경로 전체를 재구성할 수 있다. 이것이 콜스택(호출 스택)이다. x64dbg는 별도의 "Call Stack" 창에서 이를 자동으로 정리해 보여주고, GDB는 `bt`(backtrace) 명령으로 확인한다. 디버깅 중 "지금 내가 어느 함수 안의 어디에 있고, 여기까지 어떻게 왔는지" 감을 잃었을 때 가장 먼저 확인해야 할 창이다.

### 메모리를 직접 읽기 (임의 주소)
스택 창/콜스택 창이 자동으로 보여주는 범위를 벗어나 임의의 스택 주소를 직접 조회하고 싶을 수도 있다(예: 버퍼가 스택의 얼마나 깊은 곳까지 덮어쓰는지 확인). 이때는 x64dbg의 Dump 창에 주소를 입력하거나, GDB의 `x`(examine memory) 명령을 쓴다.

### 스택 추적이 특히 중요한 상황 — 버퍼 오버플로우
지역 변수 버퍼(예: `char buf[16]`)에 사용자 입력을 그대로 복사하는 코드(`strcpy`, `gets` 등)가 있으면, 입력이 16바이트를 넘을 때 그 뒤에 있는 스택 데이터(저장된 RBP, 반환 주소)까지 덮어쓸 수 있다. 실제로 이게 일어나는지 확인하려면, 입력 함수 호출 직후와 함수가 반환하기 직전(RET 실행 직전) 두 시점에 각각 브레이크포인트를 걸고 스택 창에서 버퍼 영역과 반환 주소 영역의 값이 실제로 어떻게 바뀌었는지 비교하면 된다.

## 화면/코드에서 보이는 징후
- x64dbg 스택 창에서 어떤 줄 오른쪽에 `return to main+0x1A` 같은 주석이 붙어 있으면, 그 값이 반환 주소이고 어디로 돌아가는지 자동 해석된 것이다.
- x64dbg에서 RSP가 가리키는 줄에 화살표(→)가 표시된다.
- GDB `bt` 출력에서 `#0`, `#1`, `#2` ... 번호가 매겨진 목록이 나오면, 각 번호가 하나의 스택 프레임(함수 호출 단계)이며 숫자가 작을수록 현재 실행 중인 곳에 가깝다.
- GDB `x/8xg $rsp` 같은 명령 출력에서 `0x7fffffffe420:  0x0000000000401235  0x0000000000000000` 처럼 나오면, 각 값이 8바이트(g=giant, quad word) 단위 메모리 내용이다.

## 가장 먼저 할 것
1. 지금 보고 싶은 것이 "지역 변수 값"인지 "반환 주소"인지 "콜스택 전체 경로"인지 먼저 명확히 한다.
2. 지역 변수라면 IDA/Ghidra에서 그 변수의 RBP(또는 RSP) 기준 오프셋을 먼저 확인한다.
3. 해당 함수 안 원하는 지점에 브레이크포인트를 건다.
4. 스택 창/`x` 명령으로 그 오프셋의 실제 값을 확인한다.

## 단계별 절차

**x64dbg**
1. 브레이크포인트를 걸고 `F9`로 원하는 지점까지 실행한다.
2. 화면의 "Stack" 창에서 RSP 기준 위에서부터 값들을 확인한다.
3. 특정 지역 변수(예: `[rbp-0x20]`)를 보고 싶다면, 레지스터 창에서 RBP 값을 확인한 뒤 Dump 창에 `RBP-20`(또는 실제 계산된 주소)을 입력해서 이동한다. 또는 디스어셈블리 창에서 `[rbp-0x20]`이 쓰인 줄을 우클릭 → "Follow in Dump"를 선택하면 자동으로 이동한다.
4. 콜스택 전체를 보려면 별도의 "Call Stack" 창을 확인한다(기본 레이아웃에 포함, 없으면 View 메뉴에서 활성화).
5. Dump 창에서 값을 우클릭하면 "Follow DWORD/QWORD in Dump"로 그 값이 가리키는 주소로 다시 이동할 수 있다(포인터 체인 추적).

**GDB / Pwndbg**
1. 브레이크포인트를 걸고 `run`으로 실행한다.
2. 스택 맨 위 근처 메모리를 직접 보려면:
   ```
   x/8xg $rsp      ; RSP부터 8바이트씩 8개(quad word) 16진수로 출력
   x/16xw $rsp      ; RSP부터 4바이트씩 16개(word) 16진수로 출력
   ```
3. 특정 지역 변수(RBP 기준 오프셋)를 직접 조회하려면:
   ```
   x/xg $rbp-0x20
   p *(long*)($rbp-0x20)
   ```
4. 콜스택(호출 경로) 전체를 보려면:
   ```
   bt
   backtrace
   ```
5. 현재 스택 프레임의 정보(인자, 저장된 레지스터 위치 등)를 자세히 보려면:
   ```
   info frame
   ```
6. Pwndbg를 쓰면 정지할 때마다 자동으로 스택 영역이 색상과 함께 정리되어 표시된다(`context` 화면의 STACK 섹션). 수동으로 다시 보고 싶다면:
   ```
   context
   ```
   Pwndbg는 스택 값이 다른 스택 주소를 가리키거나 알려진 문자열/함수를 가리키면 자동으로 화살표와 함께 풀어서 보여준다.

## 명령어/단축키
- x64dbg: Stack 창(기본 표시), Call Stack 창, Dump 창에 주소 입력(`Ctrl+G`), 값 우클릭 → "Follow DWORD/QWORD in Dump"(포인터 추적)
- GDB/Pwndbg: `x/Nxg <addr>`(g=8바이트 단위), `x/Nxw <addr>`(w=4바이트 단위), `bt`(backtrace), `info frame`, `p *(long*)(addr)`, Pwndbg `context`(자동 스택 정리 및 포인터 풀이)

## 출력 해석
- x64dbg 스택 창에서 어떤 줄의 값이 코드 영역 주소이고 주석에 함수 이름이 붙어 있으면, 그 줄은 반환 주소일 가능성이 매우 높다.
- GDB `bt` 결과 예: `#0 check_flag (input=...) at chal.c:12` / `#1 0x0000000000401235 in main () at chal.c:20` — `#0`이 현재 실행 중인 함수, `#1`이 그 함수를 호출한 곳(main의 0x401235 주소)이다.
- `x/8xg $rsp` 결과에서 값이 `0x0000000000401235`처럼 코드 영역(바이너리 로드 주소 범위) 안에 있다면 반환 주소일 가능성이 크고, `0x00007fffffffe4a0`처럼 스택 영역 자체를 가리키는 값이면 저장된 RBP(이전 프레임의 스택 포인터)일 가능성이 크다.

## 흔한 실수
- RBP 기준 오프셋(`[rbp-0x20]`)과 실제 메모리 주소를 혼동하는 것 — `[rbp-0x20]`은 "RBP 레지스터의 현재 값에서 0x20을 뺀 주소"이므로, 먼저 RBP의 실제 값을 확인한 뒤 그 값에서 계산해야 한다.
- 스택이 아래로 자란다는 것을 잊고 "버퍼 뒤"를 반대 방향(더 낮은 주소)에서 찾는 것 — 버퍼 오버플로우는 낮은 주소(버퍼 시작)에서 높은 주소(반환 주소가 있는 방향) 쪽으로 흘러넘친다.
- 최적화된 코드에서 RBP가 지역 변수 기준점으로 안 쓰이는 경우(프레임 포인터 생략)를 모르고 `[rbp-...]` 표현만 찾다가 못 찾는 것 — 이 경우 IDA의 Stack frame 뷰나 RSP 기준 오프셋을 확인해야 한다.
- 콜스택이 깨진 것처럼 보일 때(스택 오버플로우로 반환 주소가 손상된 경우) `bt`가 이상한 함수 이름이나 `??`를 출력하는 것을 디버거 오류로 착각하는 것 — 실제로 스택이 손상됐다는 중요한 신호일 수 있다.

## 막혔을 때 다음 체크
- 지역 변수 값이 이상하다면 → 정말 맞는 오프셋을 보고 있는지, RBP 값이 스텝 중간에 바뀌지 않았는지 확인한다.
- 콜스택이 이상하게 나온다면 → 스택이 손상됐거나(오버플로우) 프레임 포인터가 생략된 최적화 코드일 가능성을 의심한다.
- 반환 주소가 정확히 어디 있는지 못 찾겠다면 → 함수 진입 직후(프롤로그 실행 전) `[rsp]`가 바로 반환 주소이므로, 그 시점에 먼저 확인해두고 이후 RBP 기준으로 환산한다.
- 포인터가 가리키는 실제 데이터(문자열, 구조체)까지 보고 싶다면 → x64dbg "Follow in Dump" 또는 GDB `x/s <addr>`(문자열로 출력)를 쓴다.

## 미니 예제

**x64dbg — 지역 변수 버퍼 값 확인**
```asm
sub_401200:
    push    rbp
    mov     rbp, rsp
    sub     rsp, 0x30
    lea     rax, [rbp-0x20]   ; buf 주소
    ; ... scanf 등으로 buf에 입력을 채움
```
`lea` 다음 줄에 브레이크포인트를 걸고 `F9` → 정지 후 Dump 창에 `Ctrl+G`로 `rbp-20`을 입력하면 버퍼에 실제로 어떤 바이트가 들어있는지 확인할 수 있다.

**GDB/Pwndbg — 콜스택과 스택 메모리 함께 확인**
```
(gdb) break check_flag
(gdb) run
(gdb) bt
#0  check_flag (input=0x7fffffffe420 "flag{test}") at chal.c:12
#1  0x0000000000401235 in main () at chal.c:20
(gdb) x/4xg $rsp
0x7fffffffe3f0: 0x0000000000401235  0x0000000000000000
0x7fffffffe400: 0x00007ffff7dcfd90  0x0000000000000001
```
`x/4xg $rsp`의 첫 값(`0x401235`)이 `bt`의 `#1` 줄에 나온 반환 주소와 일치하는 것을 확인할 수 있다 — 이것이 실제로 스택에 저장된 반환 주소다.
