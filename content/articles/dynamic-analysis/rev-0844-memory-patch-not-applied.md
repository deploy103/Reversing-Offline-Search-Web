## 한 줄 요약
메모리 패치가 반영 안 되는 것처럼 보이는 원인은 편집 자체가 확정(commit)되지 않았거나, ASLR/PIE로 재배치된 엉뚱한 주소를 고쳤거나, 프로그램이 자기 코드/데이터 체크섬으로 변조를 감지해 스스로 원래 값으로 복원했거나, 디스크 파일만 고치고 이미 메모리에 로드된 옛 사본은 그대로 두고 재시작을 안 한 경우 중 하나다.

## 언제 검색해야 하나
- x64dbg Dump 창이나 GDB `set *(int*)addr = 값`으로 메모리를 고쳤는데 프로그램 동작이 바뀌지 않을 때
- 처음에는 패치가 적용된 것처럼 보였는데 몇 초/몇 번 실행 후 다시 원래 값으로 돌아와 있을 때
- 헥스에디터로 파일 자체를 고쳤는데 실행하면 여전히 예전 동작을 할 때
- 패치는 성공했다는데 그 다음 실행 흐름에는 영향이 전혀 없을 때

## 핵심 개념

### 원인 1 — 편집이 실제로 확정(commit)되지 않음
x64dbg의 Dump 창에서 헥스 값을 입력하고 Enter를 누르지 않거나 다른 곳을 클릭해버리면 편집이 취소된 것으로 처리될 수 있다. GDB의 `set *(int*)addr = 값`은 즉시 반영되지만, 자료형 크기(`int` vs `short` vs `char`)를 잘못 지정하면 의도한 바이트 범위와 다른 곳에 쓰여 마치 반영이 안 된 것처럼 보인다.

### 원인 2 — 정적 분석 주소와 실제 로드 주소가 다름(ASLR/PIE)
IDA에서 확인한 주소를 그대로 고쳤는데, ASLR/PIE로 실제 로드 베이스가 달라 엉뚱한 메모리를 고친 경우다. 이 문제의 근본 원리와 계산법은 REV-0840, REV-0194에서 다룬다.

### 원인 3 — 디스크 파일만 고치고 프로세스를 재시작하지 않음
이미 실행 중이거나 디버거가 이미 프로세스 이미지를 메모리에 매핑한 상태에서 헥스에디터로 디스크 파일만 고치면, 그 프로세스는 여전히 로드 당시의 옛 바이트를 메모리에 갖고 있다. 파일 패치는 반드시 **다음 실행부터** 반영된다는 점을 잊기 쉽다.

### 원인 4 — 자기수정 코드/무결성 검사가 스스로 복원함
프로그램이 코드/데이터 섹션의 체크섬을 주기적으로 검사해서 원본과 다르면 자동으로 원본 값을 다시 써넣는 "self-healing" 구조를 갖고 있으면, 패치 직후에는 값이 바뀌어 보이다가 다음 검사 시점에 조용히 되돌아간다. 이는 REV-0230(Self-modifying Code)과 REV-0537(코드 체크섬 탐지)에서 다루는 원리와 같은 메커니즘이 "패치 감지 + 복원" 방향으로 쓰인 경우다.

### 원인 5 — 쓰기 권한 문제(드묾)
`WriteProcessMemory`(Windows)나 `ptrace(PTRACE_POKEDATA, ...)`(Linux)는 대상 페이지가 `PAGE_GUARD`이거나 매핑 자체가 없는 등 예외적인 경우 실패를 반환하는데, 디버거 UI가 이 실패를 눈에 띄게 알려주지 않으면 "조용히 무시된 패치"처럼 보인다.

## 화면/코드에서 보이는 징후
- Dump 창에서 값을 바꾼 직후에는 반영된 것처럼 보이지만, 실행(F9/`continue`) 후 다시 그 주소를 조회하면 원래 값으로 돌아와 있음
- 패치한 파일을 실행했는데 디버거로 열어 다시 확인하면 패치 전 바이트 그대로임(파일 저장 자체가 안 된 경우)
- 같은 값을 여러 번 반복해서 패치해야만 실행이 끝까지 진행됨(주기적으로 복원하는 무결성 검사)

## 가장 먼저 할 것
패치 직후 **같은 주소를 다시 조회**해서 편집 자체가 확정됐는지부터 확인한다. 확정됐다면, 그 값이 다음 검사/재로드 전까지 유지되는지 한 스텝씩 실행하며 관찰한다.

## 단계별 절차
1. 패치 직후 바로 재조회해 편집이 실제로 적용됐는지 확인한다.
2. 대상 주소가 ASLR/PIE로 재배치된 실제 런타임 주소가 맞는지 Memory Map/`info proc mappings`로 재확인한다(REV-0840).
3. 파일을 고친 경우라면 실행 중이던 프로세스를 완전히 종료하고 새로 실행해서 확인한다.
4. 패치 후 몇 스텝 뒤에 값이 원래대로 돌아온다면, 그 사이에 실행된 코드에서 체크섬 검사/복원 루프가 있는지 역추적한다(REV-0230, REV-0537).
5. 근본적으로 값을 유지시키고 싶다면, 값 자체보다 그 값을 검사/복원하는 조건 분기를 패치하는 것이 더 안전하다.
6. x64dbg에서 디스크에 영구 반영하려면 Patches 창(Ctrl+P)에서 목록을 검토한 뒤 "Patch File..."로 저장한다.

## 명령어/단축키
```gdb
set *(int*)0x주소 = 값
x/4xb 0x주소
```
```text
x64dbg: Dump 창에서 헥스 편집 후 Enter, Ctrl+P(Patches 창), File → Patch File...
```

## 출력 해석
패치 직후 재조회에서 값이 그대로면 편집 자체가 실패한 것(주소/자료형 오류)이고, 처음엔 바뀌었다가 몇 스텝 뒤 되돌아오면 무결성 검사에 의한 복원이다. 두 경우의 대응이 다르므로 반드시 구분해야 한다.

## 흔한 실수
- 패치 직후 재조회 없이 "왜 실행 결과가 그대로냐"고 다음 문제로 넘어가는 것.
- ASLR/PIE 재배치를 고려하지 않고 정적 분석 주소를 그대로 패치하는 것.
- 디스크 파일만 고치고 이미 로드된 프로세스를 재시작하지 않는 것.
- 값 자체만 계속 다시 패치하고, 그 값을 되돌리는 검사/복원 루프를 찾지 않는 것.

## 막혔을 때 다음 체크
- 파일 오프셋과 실제 메모리 주소가 안 맞는 근본 원인이 궁금하다면 → REV-0840 브레이크포인트를 파일 오프셋으로 걸었는데 실제 메모리 주소랑 안 맞을 때
- 자기수정 코드/복호화 루프의 원리가 궁금하다면 → REV-0230 Self-modifying Code 기초
- 코드 체크섬 기반 탐지의 상세 구현이 궁금하다면 → REV-0537 소프트웨어 브레이크포인트(0xCC) 탐지 기법
- 패치 후 파일로 저장했는데 실행하면 크래시 난다면 → REV-0601 x64dbg 패치 후 저장했는데 실행하면 크래시 날 때

## 미니 예제
x64dbg Dump 창에서 검증 함수의 비교 상수를 `0x1234`에서 `0x0000`으로 바꿨다. F9로 실행을 이어가자 몇 스텝 뒤 그 주소를 다시 확인했더니 값이 `0x1234`로 돌아와 있었다. 역추적한 결과 별도의 스레드가 주기적으로 그 영역의 체크섬을 검사해 원본으로 복원하고 있었다. 값 대신 그 복원 루프의 진입 조건 분기를 패치하자 값이 유지됐다.

## 관련 글
- REV-0840 — 브레이크포인트를 파일 오프셋으로 걸었는데 실제 메모리 주소랑 안 맞을 때
- REV-0230 — Self-modifying Code 기초
- REV-0537 — 소프트웨어 브레이크포인트(0xCC) 탐지 기법
- REV-0601 — x64dbg 패치 후 저장했는데 실행하면 크래시 날 때

## 출처/검증
- `WriteProcessMemory`/`ptrace(PTRACE_POKEDATA, ...)`의 동작과 실패 조건: Microsoft Win32 API 공식 문서 및 `ptrace(2)` man page 기준.
- ASLR/PIE로 인한 런타임 재배치와 정적 분석 주소의 차이: System V ABI ELF 명세 및 Microsoft PE/COFF 문서 기준(2026-09-09 검증).
