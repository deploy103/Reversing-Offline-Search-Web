## 한 줄 요약
레지스터를 수정했는데 무시된 것처럼 보이는 가장 흔한 원인은 진짜로 안 바뀐 게 아니라 (1) 바로 다음 명령어가 그 레지스터를 다른 값으로 즉시 덮어써버렸거나, (2) 콜스택의 바깥쪽 프레임(GDB `frame N`)이나 엉뚱한 스레드에서 수정했거나, (3) 서브레지스터 폭을 착각한 경우이므로, "값이 실제로 바뀌었는지"와 "그 값이 다음에 쓰이는 지점까지 살아있는지"를 나눠서 확인해야 한다.

## 언제 검색해야 하나
- x64dbg Registers 창에서 값을 더블클릭해 바꿨는데 실행 결과(분기, 리턴값)가 그대로일 때
- GDB에서 `set $rax = 값`을 했는데 바로 `print $rax`를 해도 이전 값처럼 보일 때
- 콜스택 위쪽 프레임에서 레지스터를 바꿨는데 실제 프로그램 동작에는 아무 영향이 없을 때
- 멀티스레드 프로그램에서 레지스터를 바꿨는데 계속 이상하게 동작할 때

## 핵심 개념

### 가장 흔한 원인 — 바로 다음 명령어가 그 레지스터를 다시 쓴다
레지스터 편집은 항상 "지금 이 순간의 CPU 레지스터 값"만 바꾼다. 만약 다음에 실행될 명령이 `mov eax, [rbp-0x10]`처럼 그 레지스터를 메모리에서 다시 로드하는 명령이라면, 방금 바꾼 값은 명령어 하나만큼도 못 버티고 사라진다. 이는 x64dbg/GDB 어느 쪽이든 동일하게 발생하는, 도구와 무관한 현상이다. 지금 멈춰 있는 지점(`$pc`/EIP) 바로 다음 명령이 그 레지스터를 다시 쓰는지부터 확인해야 한다.

### GDB — 콜스택 프레임 선택 문제
`frame 1` 같은 바깥쪽 프레임을 보고 있는 상태에서 `set $rax = 값`을 하면, GDB는 경고 없이 받아주는 것처럼 보이지만 실제 CPU 레지스터(가장 안쪽 프레임 0의 값)에는 반영되지 않는 경우가 있다. 실행에 영향을 주려면 반드시 `frame 0`(가장 안쪽)으로 돌아온 상태에서 수정해야 한다. 자세한 사례와 스레드/서브레지스터 혼동까지 포함한 전체 목록은 REV-0713에서 다룬다.

### x64dbg — 스레드 선택 문제
멀티스레드 프로그램은 스레드마다 별도의 레지스터 세트를 가진다. Threads 창에서 지금 편집하려는 스레드가 실제로 다음에 실행될 스레드가 맞는지 확인하지 않으면, 엉뚱한(대기 중인) 스레드의 레지스터만 계속 바꾸게 된다.

### 서브레지스터 크기 혼동(플랫폼 공통)
`EAX`를 바꾸면 x86-64에서는 상위 32비트(`RAX`의 상위 절반)가 자동으로 0으로 클리어된다(제로 확장). `AL`(하위 8바이트)만 바꾸면 나머지 상위 바이트는 그대로 남는다. 어떤 폭을 바꿨는지와 어떤 폭으로 확인하는지가 다르면 "반영이 이상하다"고 오해하기 쉽다.

## 화면/코드에서 보이는 징후
```gdb
(gdb) frame 1
(gdb) set $rax = 0
(gdb) frame 0
(gdb) print $rax
$1 = 32          # frame 1에서 바꾼 값이 반영되지 않음
```
x64dbg에서는 Registers 창에서 값을 바꾸고 F8(Step Over)을 한 번 눌렀더니 그 값이 이미 다른 값으로 바뀌어 있는 경우가 전형적이다.

## 가장 먼저 할 것
값을 바꾼 직후 다시 한 번 조회해서(`print $rax` / Registers 창 갱신) 실제로 바뀌었는지부터 확인한다. 바뀌어 있다면 "무시된 것"이 아니라 "다음 명령이 곧바로 덮어쓴 것"이므로, 그 다음 명령어(`x/i $pc`)가 그 레지스터를 다시 로드하는지 확인한다.

## 단계별 절차
1. 값을 바꾼 직후 즉시 재조회해서 편집 자체가 성공했는지 확인한다.
2. `x/i $pc`(GDB) 또는 CPU 창의 다음 명령(x64dbg)을 확인해, 그 레지스터를 바로 다시 쓰는 명령인지 본다.
3. GDB라면 `bt`로 지금 몇 번째 프레임인지 확인하고, 실행에 영향을 주려면 `frame 0`으로 이동한다.
4. 멀티스레드라면 `info threads`(GDB)/Threads 창(x64dbg)으로 대상 스레드가 맞는지 확인한다.
5. 서브레지스터를 썼다면(`$eax`, `$al`) 폭이 맞는 이름으로 다시 확인한다.
6. 값을 진짜로 유지시키고 싶다면, 그 레지스터를 다시 로드하는 명령어 자체를 NOP 처리하거나 바로 그 지점 이후에 브레이크포인트를 걸어 다시 수정하는 방식으로 접근한다.

## 명령어/단축키
```gdb
print $rax
x/i $pc
bt
frame 0
info threads
thread N
set $rax = 값
```
```text
x64dbg: Registers 창 더블클릭 편집, Threads 탭, F8(Step Over) 후 재확인
```

## 출력 해석
값을 바꾼 직후 재조회했을 때 이미 이전 값으로 돌아와 있다면 편집 자체가 실패한 것(프레임/스레드 문제)이고, 바뀐 값이 보였다가 한 스텝 뒤에 사라진다면 다음 명령어가 덮어쓴 것이다. 이 둘을 구분하는 것이 원인 진단의 핵심이다.

## 흔한 실수
- 값을 바꾼 직후 재확인 없이 "반영이 안 됐다"고 단정하는 것.
- GDB에서 바깥쪽 프레임에 머문 채로 레지스터를 수정하고 `frame 0`으로 안 돌아온 것을 잊는 것.
- 멀티스레드 프로그램에서 `thread`/Threads 탭을 확인하지 않고 엉뚱한 스레드만 계속 편집하는 것.
- `$eax`로 바꿔놓고 `$rax`(64비트 전체)로 확인하면서 "왜 상위 비트가 이상하지"라고 헷갈리는 것 — 제로 확장은 정상 동작이다.

## 막혔을 때 다음 체크
- GDB 프레임/스레드 문제의 상세 사례가 필요하다면 → REV-0713 GDB에서 레지스터를 수정했는데 반영이 안 되는 것처럼 보일 때
- 메모리 값 패치도 비슷하게 반영이 안 된다면 → REV-0844 메모리 값을 패치했는데 반영이 안 될 때
- 브레이크포인트/워치포인트 타이밍 자체가 헷갈린다면 → REV-0708 GDB에서 tbreak/watch가 예상과 다른 시점에 걸릴 때

## 미니 예제
x64dbg에서 분기 직전 `EAX`를 `1`로 바꿨는데, F8을 한 번 누르고 나니 `EAX`가 다시 `0`이 되어 있었다. CPU 창에서 다음 명령을 보니 `mov eax, [ebp-0x8]`이었다 — 스택에서 다시 로드하는 명령이었기 때문에 레지스터 편집이 무의미했던 것이다. 대신 `[ebp-0x8]` 메모리 값 자체를 바꾸자 원하는 대로 반영됐다.

## 관련 글
- REV-0713 — GDB에서 레지스터를 수정했는데 반영이 안 되는 것처럼 보일 때
- REV-0844 — 메모리 값을 패치했는데 반영이 안 될 때
- REV-0708 — GDB에서 tbreak/watch가 예상과 다른 시점에 걸릴 때

## 출처/검증
- GDB의 프레임 선택과 언와인딩된 레지스터 값, `set $reg`/스레드별 컨텍스트: GDB 공식 매뉴얼("Selecting a Frame", "Registers", "Threads" 챕터) 기준.
- x86-64에서 32비트 레지스터 쓰기 시 상위 32비트가 자동 제로 확장되는 동작: Intel 64 and IA-32 Architectures Software Developer's Manual 기준(2026-09-09 검증).
