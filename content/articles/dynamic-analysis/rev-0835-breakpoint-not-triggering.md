## 한 줄 요약
브레이크포인트가 안 걸리는 원인은 x64dbg/GDB 어느 쪽이든 대부분 다섯 가지 범주(주소 계산 오류, 아직 로드 안 된 모듈, 비활성화 상태, 조건식/스코프 문제, 안티디버깅·자기수정 코드)로 좁혀지므로, 무작정 다시 걸어보기 전에 이 다섯 가지를 순서대로 소거하는 것이 가장 빠르다.

## 언제 검색해야 하나
- IDA/Ghidra에서 확인한 주소로 x64dbg에 `bp` 또는 GDB에 `break *0x주소`를 걸었는데 실행해도 전혀 멈추지 않을 때
- 어제까지는 잘 걸리던 브레이크포인트가 오늘 다시 실행하니 안 걸릴 때
- DLL/공유 라이브러리 안의 함수에 건 브레이크포인트가 계속 무시될 때
- 조건부 브레이크포인트를 걸었는데 조건이 한 번도 만족되지 않는 것 같을 때

## 핵심 개념

### 범주 1 — 주소가 실제 실행 위치와 다름(재배치)
Windows PE는 ASLR로, Linux PIE(ET_DYN) 실행 파일은 ASLR/PIE로 매 실행마다 로드 베이스가 바뀐다. 정적 분석에서 얻은 주소는 `ImageBase+RVA`(PE) 또는 오프셋(ELF PIE) 기준이라, 실제 런타임 베이스가 다르면 그 절대 주소는 전혀 다른 위치를 가리킨다. x64dbg 쪽 상세 사례는 REV-0622, GDB/PIE 쪽 상세 사례는 REV-0194, 파일 오프셋 자체가 VA와 안 맞는 근본 원리는 REV-0840에서 다룬다.

### 범주 2 — 대상 모듈/함수가 아직 메모리에 없음
DLL이나 `.so`가 지연 로드(delay-load)되거나 `dlopen`으로 나중에 로드되는 경우, 그 안의 함수에 절대 주소로 건 브레이크포인트는 로드 시점 전까지 의미 없는 메모리를 가리킨다. 이름 기반 브레이크포인트(`bp 모듈.dll:함수`, GDB `break 함수이름`)를 쓰면 대부분 자동 처리된다.

### 범주 3 — 비활성화/삭제/충돌 상태
x64dbg Breakpoints 탭에서 회색(Disable)으로 표시되어 있거나, GDB `info breakpoints`에서 이미 `tbreak`가 한 번 걸리고 자동 삭제된 경우(REV-0708 참고)가 흔하다. 하드웨어 브레이크포인트는 CPU 디버그 레지스터 슬롯이 보통 4개뿐이라 5번째부터는 무시되거나 소프트웨어로 자동 전환된다.

### 범주 4 — 조건식/스코프가 실제로 참이 되지 않음
조건부 브레이크포인트(x64dbg 조건식, GDB `condition`)의 표현식 자체가 논리적으로 참이 될 수 없는 경우, 또는 GDB에서 로컬 변수를 감시하다가 함수를 벗어나 워치포인트가 자동 삭제된 경우(REV-0708)도 "안 걸린다"로 오인되기 쉽다.

### 범주 5 — 안티디버깅/자기수정 코드가 방해함
프로그램이 코드 섹션 체크섬으로 소프트웨어 브레이크포인트(0xCC)를 탐지하거나(REV-0537, REV-0841), 패커/자기수정 코드가 실행 직전에 원본 바이트를 다시 덮어써서 INT3 패치 자체가 사라지는 경우(REV-0230)도 "브레이크포인트가 무효화된다"는 증상으로 나타난다.

## 화면/코드에서 보이는 징후
- x64dbg Breakpoints 탭 항목이 빨간 점이 아니라 회색이거나 목록에서 아예 사라짐
- GDB `info breakpoints`가 `No breakpoints or watchpoints.`를 출력
- Memory Map/`info proc mappings`에서 확인한 실제 로드 베이스가 정적 분석 때 가정한 베이스와 다름
- `run`/`continue`를 눌러도 프로그램이 끝까지 실행되거나 그냥 종료됨

## 가장 먼저 할 것
가능하면 절대 주소 대신 **심볼/함수 이름으로 다시 건다**(x64dbg `bp CreateFileW`, GDB `break main`). 이것만으로 재배치 관련 원인의 대부분이 즉시 해결된다.

## 단계별 절차
1. `info breakpoints`(GDB) 또는 Breakpoints 탭(x64dbg)으로 지금 걸려 있는 목록과 활성 상태를 확인한다.
2. 이름으로 다시 걸어본다. 안 되면 대상 모듈이 로드됐는지(Memory Map/`info proc mappings`) 확인한다.
3. PIE/ASLR 여부를 `checksec`(Linux)이나 PE-bear의 `DYNAMIC_BASE`(Windows)로 확인하고, 필요하면 로드 후 베이스+오프셋으로 재계산한다.
4. 조건부 브레이크포인트라면 조건 없이 먼저 걸어서 그 지점 자체에 도달하는지부터 확인한 뒤 조건을 하나씩 추가한다.
5. 위 네 가지를 모두 소거했는데도 안 걸리면, 코드 체크섬/자기수정 코드로 인한 무력화를 의심하고 하드웨어 브레이크포인트로 바꿔본다.

## 명령어/단축키
```text
x64dbg: bp <함수명|모듈:오프셋>, ba x 1 <주소>(하드웨어), Alt+M(Memory Map)
```
```gdb
info breakpoints
break FUNC
condition N EXPR
info proc mappings
```

## 출력 해석
Memory Map/`info proc mappings`의 실제 베이스와 정적 분석 때 가정한 베이스가 다르면 그 차이만큼 주소를 보정해야 한다. `info breakpoints`에서 항목 자체가 안 보이면 이미 삭제(`tbreak` 소진, 수동 `delete`)된 것이다.

## 흔한 실수
- 재배치 가능성을 고려하지 않고 절대 주소를 그대로 재사용하는 것.
- 하드웨어 브레이크포인트 슬롯(4개)이 이미 다 찼는지 확인하지 않고 계속 새로 거는 것.
- 조건부 브레이크포인트의 조건식만 의심하고, 애초에 그 지점에 도달하는지 자체를 확인하지 않는 것.
- "안 걸린다"를 무조건 안티디버깅으로 단정하고 다른 네 가지 범주를 먼저 소거하지 않는 것.

## 막혔을 때 다음 체크
- x64dbg에서 이 증상을 자세히 겪고 있다면 → REV-0622 브레이크포인트를 걸었는데 한 번도 안 걸릴 때(x64dbg)
- GDB에서 PIE 바이너리라서 주소가 매번 다르다면 → REV-0194 PIE 바이너리 GDB 브레이크포인트 잡기
- 파일 오프셋과 실제 메모리 주소가 근본적으로 왜 다른지 궁금하다면 → REV-0840 브레이크포인트를 파일 오프셋으로 걸었는데 실제 메모리 주소랑 안 맞을 때
- 안티디버깅이 확실히 의심된다면 → REV-0841 소프트웨어 브레이크포인트가 안티디버깅에 걸릴 때

## 미니 예제
IDA에서 `sub_401500`을 확인하고 x64dbg에 `bp 0x401500`을 걸었지만 실행해도 멈추지 않았다. Memory Map을 확인하니 실제 로드 베이스가 `0x00460000`(ImageBase는 `0x00400000`으로 가정)이어서 `0x60000`만큼 어긋나 있었다. `bp target.exe:1500`(모듈 기준 오프셋)으로 다시 걸자 정확히 멈췄다.

## 관련 글
- REV-0622 — 브레이크포인트를 걸었는데 한 번도 안 걸릴 때(x64dbg)
- REV-0194 — PIE 바이너리 GDB 브레이크포인트 잡기
- REV-0708 — GDB에서 tbreak/watch가 예상과 다른 시점에 걸릴 때
- REV-0840 — 브레이크포인트를 파일 오프셋으로 걸었는데 실제 메모리 주소랑 안 맞을 때
- REV-0841 — 소프트웨어 브레이크포인트가 안티디버깅에 걸릴 때

## 출처/검증
- 소프트웨어/하드웨어 브레이크포인트의 동작 방식(INT3 바이트 치환, CPU 디버그 레지스터)은 Intel 64 and IA-32 Architectures Software Developer's Manual 기준.
- x64dbg의 브레이크포인트 활성/비활성 및 심볼 기반 설정은 x64dbg 공식 문서 기준.
- GDB의 `break`/`condition`/`info breakpoints` 동작은 GDB 공식 매뉴얼("Breakpoints, Watchpoints, and Catchpoints" 챕터) 기준(2026-09-09 검증).
