## 한 줄 요약
"디버거에서만 다르게 동작한다"는 증상은 진짜 안티디버깅 체크 때문일 수도 있지만, 그보다 먼저 디버깅 환경 자체가 만드는 부수 효과(Windows 디버그 힙, 소프트웨어 브레이크포인트의 코드 변조, ASLR 고정, 표준출력 버퍼링 모드 변경, 작업 디렉터리/인자 차이)를 소거해야 하며, 두 원인을 구분하지 않으면 안티디버깅 우회 도구만 계속 시도하다 시간을 낭비하게 된다.

## 언제 검색해야 하나
- 같은 입력으로 더블클릭/터미널 직접 실행과 디버거 실행의 결과(성공/실패, 출력)가 다를 때
- `IsDebuggerPresent`나 `ptrace` 관련 임포트가 안 보이는데도 디버거에서만 다르게 동작할 때
- 브레이크포인트를 걸었을 때만 실패하고, 브레이크포인트 없이 그냥 실행하면 성공할 때
- 콘솔 프로그램인데 디버거 안에서는 출력이 한 줄씩, 밖에서는 뭉텅이로 나오는 등 타이밍 자체가 달라 보일 때

## 핵심 개념

### 진단 먼저: 진짜 체크인가, 환경의 부작용인가
브레이크포인트를 하나도 걸지 않고 그냥 실행(x64dbg F9 / GDB `run`)만 했을 때도 결과가 다르면 진짜 안티디버깅 체크(1번) 가능성이 높고, 브레이크포인트를 걸었을 때만 다르면 디버깅 환경의 부작용(2번) 가능성이 매우 높다. 이 대조 테스트가 원인 분류의 핵심이다.

### Windows — 디버그 힙과 소프트웨어 브레이크포인트 부작용
Windows는 디버거 하위에서 시작된 프로세스에 기본적으로 디버그 힙(할당 앞뒤 가드 바이트, 해제 메모리 패턴 채우기)을 활성화한다. 초기화되지 않은 메모리에 의존하는 코드는 디버거 유무에 따라 실제로 다른 값을 읽는다. 또한 소프트웨어 브레이크포인트(0xCC)는 코드 바이트를 바꾸므로, 자기 코드 체크섬을 검사하는 프로그램은 브레이크포인트 자체 때문에 실패한다. 자세한 진단은 REV-0584에서 다룬다.

### Linux — ASLR 고정과 TracerPid
GDB는 기본적으로 `disable-randomization on`이라 자신이 실행하는 자식 프로세스의 ASLR을 꺼버린다. 터미널에서 직접 실행할 때와 주소 관련 동작이 달라 보일 수 있으며 자세한 내용은 REV-0714에서 다룬다. 또한 `/proc/self/status`의 `TracerPid` 필드나 `ptrace(PTRACE_TRACEME, ...)`가 이미 실패하는지로 디버거 존재를 감지하는 코드가 있다면(REV-0234), 이는 진짜 안티디버깅이다.

### 표준입출력 버퍼링 모드 차이(플랫폼 공통)
C 표준 라이브러리는 출력이 터미널(tty)로 연결되어 있으면 줄 단위 버퍼링, 파이프나 리다이렉트로 연결되어 있으면 완전 버퍼링을 자동으로 선택한다. 디버거가 대상 프로세스의 표준출력을 자신의 내부 콘솔 창으로 연결하면 이 판단 결과가 원래 실행 방식과 달라져, "디버거에서만 출력 순서/타이밍이 이상하다"는 현상이 생길 수 있다 — 이는 안티디버깅이 아니라 단순한 버퍼링 방식 차이다.

### 작업 디렉터리/인자 차이(플랫폼 공통)
더블클릭/셸 실행과 디버거의 기본 시작 디렉터리·커맨드라인 인자가 다를 수 있다. 상대 경로로 파일을 여는 프로그램이라면 이 차이만으로 "파일을 못 찾음 → 에러 분기"로 갈 수 있다.

## 화면/코드에서 보이는 징후
- 특정 지역 변수(초기화 안 된 스택 값)가 디버거 유무에 따라 값이 달라 보임
- 소프트웨어 브레이크포인트를 지우고 다시 실행하면 정상으로 돌아옴
- 콘솔 출력이 디버거 안에서는 한 줄씩, 밖에서는 프로그램 종료 시점에 한꺼번에 나옴
- `GetModuleFileName`/`argv[0]` 기준 상대 경로 파일 열기가 디버거 세션에서만 실패함

## 가장 먼저 할 것
브레이크포인트 없이 그냥 실행만 해서 결과가 여전히 다른지부터 확인한다. 이 상태에서도 다르면 진짜 체크(1번), 브레이크포인트를 걸었을 때만 다르면 환경 부작용(2번)이다.

## 단계별 절차
1. 브레이크포인트 없이 F9/`run`만으로 대조 테스트를 한다.
2. Windows: 소프트웨어 브레이크포인트를 하드웨어 브레이크포인트로 바꿔서 재시도, `_NO_DEBUG_HEAP=1` 환경 변수로 디버그 힙 비활성화 후 재시도.
3. Linux: `set disable-randomization off`(GDB)로 ASLR을 실제 환경처럼 재현해서 재시도.
4. 출력 타이밍이 문제라면 대상 소스/빌드에 `setvbuf`/`stdbuf -o0` 같은 버퍼링 강제 옵션이 있는지 확인하거나, 리다이렉트 방식을 맞춰서 비교한다.
5. 위 항목을 모두 배제했는데도 다르면 `IsDebuggerPresent`/PEB(Windows), `TracerPid`/ptrace 자기attach(Linux) 같은 진짜 안티디버깅 코드를 찾는다.

## 명령어/단축키
```text
x64dbg: 하드웨어 브레이크포인트로 전환, Options → Preferences(작업 디렉터리/환경 변수)
set _NO_DEBUG_HEAP=1 && x64dbg.exe
```
```gdb
set disable-randomization off
cat /proc/$(pgrep 대상)/status | grep TracerPid
```

## 출력 해석
소프트웨어 브레이크포인트 제거 후 정상으로 돌아오면 코드 체크섬 검사가 원인이다. `_NO_DEBUG_HEAP=1` 적용 후 정상화되면 초기화 안 된 메모리 의존 로직이 원인이다. `TracerPid`가 0이 아니면 디버거가 실제로 붙어 있다는 뜻이며, 프로그램이 이 값을 스스로 읽고 있다면 진짜 탐지 코드다.

## 흔한 실수
- 브레이크포인트를 건 상태로만 테스트하고 대조군(브레이크포인트 없는 실행)을 생략하는 것.
- 디버그 힙/버퍼링 차이를 안티디버깅으로 오인해 우회 도구만 계속 켰다 끄는 것.
- 작업 디렉터리 차이로 인한 단순 파일 찾기 실패를 "디버거가 감지당했다"고 오해하는 것.
- Linux에서 `disable-randomization`이 GDB 기본값이라는 것을 모르고 "이 프로그램은 원래 주소가 고정이구나"라고 착각하는 것.

## 막혔을 때 다음 체크
- Windows 디버그 힙/브레이크포인트 부작용의 상세 절차가 필요하다면 → REV-0584 디버거에서 실행하면 다른 분기를 타는 것처럼 보일 때
- Linux에서 GDB와 셸 실행의 ASLR 차이가 궁금하다면 → REV-0714 동적분석 중 ASLR 때문에 라이브러리 베이스 주소가 계속 바뀔 때
- Linux ptrace 기반 자기탐지 코드의 원리가 궁금하다면 → REV-0234 ptrace PTRACE_TRACEME 안티디버깅
- 여러 안티디버깅 패턴을 한 번에 훑고 싶다면 → REV-0240 디버거에서 갑자기 종료될 때 체크리스트

## 미니 예제
Windows 콘솔 프로그램을 더블클릭하면 "Success"가, x64dbg로 실행하면 "Fail"이 나왔다. 브레이크포인트 없이 F9만 눌러도 여전히 "Fail"이 나와 2번(환경 부작용)이 아니라 1번(진짜 체크)로 판단했다. 분기 직전 값을 추적하니 `IsDebuggerPresent` 호출 직후였음을 확인해 안티디버깅으로 확정했다.

## 관련 글
- REV-0584 — 디버거에서 실행하면 다른 분기를 타는 것처럼 보일 때
- REV-0714 — 동적분석 중 ASLR 때문에 라이브러리 베이스 주소가 계속 바뀔 때
- REV-0234 — ptrace PTRACE_TRACEME 안티디버깅
- REV-0240 — 디버거에서 갑자기 종료될 때 체크리스트

## 출처/검증
- Windows 디버그 힙과 `_NO_DEBUG_HEAP` 환경 변수: 일반적으로 알려진 Windows 힙 관리자 동작 기준.
- GDB의 `disable-randomization` 기본값: GDB 공식 매뉴얼("Starting your Program" 챕터) 기준.
- `/proc/[pid]/status`의 `TracerPid` 필드: Linux 커널 문서(`Documentation/filesystems/proc.rst`) 기준.
- 표준입출력의 tty 여부에 따른 자동 버퍼링 모드 선택: C 표준 라이브러리(glibc/MSVCRT)의 일반적인 `stdio` 구현 동작 기준(2026-09-09 검증).
