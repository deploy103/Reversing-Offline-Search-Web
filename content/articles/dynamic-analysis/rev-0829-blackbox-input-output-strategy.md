## 한 줄 요약
디버거로 내부를 들여다볼 수 없거나 들여다보는 비용이 너무 클 때는, 프로그램 자체를 "입력을 넣으면 출력을 내놓는 하나의 함수"로 취급해 stdin/인자/네트워크 입력을 체계적으로 바꿔가며 stdout/종료 코드/응답의 변화만 비교하는 완전 블랙박스 전략을 쓸 수 있다.

## 언제 검색해야 하나
- 강한 패킹/난독화/안티디버깅으로 디버거를 붙이는 것 자체가 매우 어렵거나 결과가 왜곡될 때
- 내부 로직을 하나하나 리버싱하는 것보다, 일단 입력-출력 관계의 규칙성을 빠르게 파악해 문제 유형(예: 단순 XOR, 문자별 독립 검증, 체크섬 검증)을 짐작하고 싶을 때
- 서버형 문제(`nc` 접속)처럼 바이너리 자체가 없거나 로컬에서 디버거를 붙이기 어려운 환경일 때
- REV-0828의 "함수 단위 관찰"조차 어려운, 더 상위 수준(프로그램 전체)에서의 관찰이 필요할 때

## 핵심 개념

### 화이트박스 관찰(REV-0828)과 블랙박스 관찰(이 글)의 차이
REV-0828은 "특정 함수의 진입점과 반환 지점"에 로그를 걸어 그 함수 하나의 입출력을 관찰하는 방법으로, 함수 위치를 알고 있다는 전제가 있다. 이 글에서 다루는 블랙박스 전략은 그 함수 위치조차 몰라도, 혹은 알 필요 없이 "프로그램 전체"의 입력(표준입력, 커맨드라인 인자, 네트워크 페이로드)과 출력(표준출력, 종료 코드, 소요 시간, 네트워크 응답)만 비교한다. 디버거를 아예 쓰지 않고도 수행할 수 있는 것이 특징이다.

### 관찰 대상을 정의한다
블랙박스 실험에서 "출력"은 여러 형태로 정의할 수 있다.

- 표준출력 문자열(예: "Correct!" vs "Wrong!")
- 프로세스 종료 코드(`echo $?`, `$LASTEXITCODE`)
- 실행 소요 시간(타이밍 사이드채널 — 예: 첫 글자가 맞을 때만 비교 루프가 한 번 더 돌아 미세하게 느려지는 경우)
- 네트워크 응답 바이트열(서버형 문제)

이 중 하나라도 입력에 따라 달라진다면 그것이 관찰 신호가 된다.

### 체계적으로 입력을 바꾸는 것이 핵심
무작위로 아무 값이나 넣는 게 아니라, 한 번에 한 가지 변수만 바꾸는 것이 중요하다. 예를 들어 길이를 고정하고 한 바이트씩만 바꿔가며 출력이 바뀌는지 보면 "그 위치가 검증에 영향을 주는가"를 독립적으로 판단할 수 있다. 이 방식은 사실상 과학 실험의 "하나의 변인만 통제해서 바꾸기"와 동일하다.

### 자동화가 필수
사람이 손으로 값을 하나씩 바꿔 넣는 것은 비효율적이다. Python(`pwntools`의 `process`/`remote`)이나 셸 스크립트로 입력을 반복 생성하고 실행 결과를 자동으로 비교하는 것이 실전에서는 표준적인 접근이다. 예를 들어 `for i in range(256): send(bytes([i]) + rest); check_response()` 같은 루프로 한 바이트의 256가지 값을 모두 시도해보고 응답이 달라지는 값을 찾는다.

### 언제 블랙박스에서 다시 화이트박스로 전환하는가
블랙박스로 "대략 이런 규칙이 있다"는 가설(예: "각 바이트가 독립적으로 검증되는 것 같다", "타이밍 차이가 있다")을 세운 뒤에는, 가능하다면 그 가설을 디버거로 직접 확인하는 화이트박스 단계(REV-0828, 정적 분석)로 넘어가 정확한 알고리즘을 확정하는 것이 안전하다. 블랙박스만으로 확신하고 넘어가면 우연의 일치를 규칙으로 오해할 위험이 있다.

## 화면/코드에서 보이는 징후
- `strings`/`file`/`checksec` 결과 실행 파일이 UPX 등으로 패킹되어 있거나, 디버거로 열면 안티디버깅 체크로 바로 종료됨
- 서버 접속형 문제라 로컬에 분석할 바이너리 자체가 없고 `nc host port`로만 상호작용 가능
- 같은 입력을 여러 번 넣었는데 출력이 완전히 동일해서(결정론적) 재현 가능한 실험이 가능하다는 것이 확인됨
- 입력 길이를 바꾸면 응답이 오기까지 걸리는 시간이 눈에 띄게 달라짐

## 가장 먼저 할 것
가장 단순한 입력(빈 입력, 짧은 임의 문자열)부터 넣어보고 출력이 어떻게 나오는지 기준선(baseline)을 확보한다. 그 다음 입력을 아주 조금씩만 바꿔가며 출력이 바뀌는 지점을 찾는다. 자동화할 수 있으면 처음부터 스크립트로 실행 결과를 기록하도록 준비한다.

## 단계별 절차
1. 가장 단순한/무작위 입력으로 실행해 기준 출력(정답이 아님을 이미 아는 출력) 확보
2. 입력 길이만 바꿔가며 반응 차이가 있는지 확인(길이 검증이 있는지 짐작)
3. 길이를 고정하고 한 바이트(또는 한 필드)씩만 바꿔가며 나머지 조건 고정 상태로 반복 실행
4. 출력/종료코드/응답시간이 달라지는 값들을 표로 기록
5. 규칙(예: 특정 바이트에서만 반응이 다름 — 순차 검증 가능성 시사)을 가설로 세움
6. 가능하면 화이트박스(디버거, 정적 분석)로 전환해 가설을 확정
7. 확정되면 실제 정답 입력을 재구성

## 명령어/단축키
Linux 셸/파이썬(예시, pwntools):
```python
from pwn import *
for b in range(256):
    p = process('./chall')
    p.sendline(bytes([b]) + b'A' * 7)
    out = p.recvall(timeout=1)
    print(b, out)
    p.close()
```
셸 기준선 확인:
```bash
./chall <<< "test"
echo "exit code: $?"
```
GDB/x64dbg는 이 단계에서는 보조적으로만 사용(타이밍 확인, 크래시 여부 확인 등).

## 출력 해석
- 특정 바이트 값을 넣었을 때만 응답 문자열/종료 코드가 바뀐다면, 그 위치가 개별적으로 검증되는(순차 비교) 구조라는 강한 단서다.
- 모든 바이트를 바꿔도 반응이 균일하게 "전부 틀림"으로만 나온다면, 개별 바이트 검증이 아니라 전체를 한 번에 묶어서 검증하는(체크섬, 해시 비교) 구조일 가능성이 높다.
- 응답 시간이 입력에 따라 미세하게 달라진다면 타이밍 사이드채널 공격의 여지가 있다는 뜻이며, 여러 번 반복 측정으로 노이즈를 줄여 신뢰도를 높여야 한다.

## 흔한 실수
- 한 번에 여러 변수(길이와 내용 동시)를 바꿔서, 어떤 변화가 결과에 영향을 줬는지 구분하지 못하는 것
- 실행 결과가 매번 조금씩 다른(비결정론적, 예: 랜덤 시드, ASLR 관련 출력) 프로그램인데 이를 눈치채지 못하고 노이즈를 진짜 신호로 오해하는 것
- 자동화 스크립트 없이 수동으로 하나씩 테스트하다 지쳐서 충분한 샘플을 모으지 못한 채 성급히 결론 내리는 것
- 블랙박스로 세운 가설을 검증 없이 그대로 최종 답으로 사용해서, 실제로는 우연히 일치했을 뿐인 패턴을 정답 알고리즘으로 착각하는 것

## 막혔을 때 다음 체크
- 함수 위치는 알고 그 함수만 좁혀서 관찰하고 싶다면 → REV-0828 동적분석으로 검증 함수의 입출력만 계속 관찰하는 전략
- 서버 접속형 문제 특유의 접근 순서가 궁금하면 → REV-0303 서버 연결형 리버싱 문제(nc 접속) 접근 순서
- API 호출 순서만으로 동작을 재구성하는 좀 더 세밀한 관찰법은 → REV-0834 API 호출 순서만으로 프로그램 동작을 재구성하는 법
- 여러 단계로 나뉜 검증을 단계별로 추적하고 싶다면 → REV-0833 멀티스텝 검증 로직을 스텝별로 나눠서 동적으로 추적하는 법
- 시스템 콜 수준에서 힌트를 찾고 싶다면 → REV-0112 strace로 시스템 콜에서 힌트 찾기

## 미니 예제
```
$ ./chall <<< "AAAAAAAA"
Wrong!
$ ./chall <<< "PAAAAAAA"
Wrong!
$ ./chall <<< "AAAAAAAP"
Correct so far, next char?
```
길이를 고정하고 첫 바이트만 바꿨을 때는 반응이 그대로였지만, 마지막 바이트를 바꾸자 "Correct so far"라는 다른 메시지가 나왔다. 이는 검증이 문자열 뒤쪽부터, 혹은 특정 위치를 우선적으로 확인하는 구조일 수 있다는 단서이며, 다음 단계로 그 위치를 고정한 채 다른 위치를 마저 탐색하면 된다.

## 출처/검증

- pwntools `process`/`remote`를 이용한 반복 실행 자동화 패턴: pwntools 공식 문서 기준 (2026-09-09 검증).
