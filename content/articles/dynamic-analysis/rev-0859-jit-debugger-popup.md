## 한 줄 요약
분석 중인 프로그램이 처리하지 못한 예외(unhandled exception)를 던지면, 아직 아무 디버거도 붙어 있지 않은 상태에서 Windows가 레지스트리의 AeDebug(Application Error Debug) 설정을 보고 "이 프로그램을 디버그할 디버거를 선택하시겠습니까?"라는 Just-In-Time(JIT) 디버거 창을 띄우는 것이며, 이는 보통 버그(크래시)이지 침입 탐지가 아니므로 침착하게 디버거를 골라서 그 크래시 지점을 그대로 분석하면 된다.

## 언제 검색해야 하나
- 크랙미/CTF 바이너리를 그냥 더블클릭하거나 x64dbg 없이 실행했는데 갑자기 "프로그램이 작동을 멈췄습니다" 또는 "Just-In-Time debugging" 같은 제목의 창이 뜰 때
- 창에 "Debug" 버튼과 함께 Visual Studio, WinDbg 같은 디버거 목록이 나열되어 있는데 뭘 눌러야 할지 모를 때
- 이미 x64dbg로 붙여서 디버깅 중인데도 예외가 발생하는 순간 또 다른 JIT 디버거 창이 겹쳐서 뜰 때
- 이 팝업이 안티디버깅 탐지의 결과인지, 단순 크래시인지 구분하고 싶을 때

## 핵심 개념

### JIT 디버거가 뜨는 원리
Windows는 프로세스에서 처리되지 않은 예외(access violation, 0으로 나누기 등)가 발생하면 커널이 이를 감지하고, 현재 그 프로세스에 디버거가 붙어 있지 않다면 레지스트리 `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\AeDebug`(64비트 프로그램이면 `AeDebug`, WOW64 32비트 프로그램이면 `Wow6432Node\...\AeDebug`)에 등록된 "Debugger" 값을 실행해서 사후 디버거(post-mortem debugger)를 붙일 기회를 준다. 이때 여러 디버거가 설치되어 있으면 어떤 디버거를 쓸지 고르는 선택 창이 뜨는데, 이것이 바로 Just-In-Time 디버거 팝업이다. Windows 10/11에서는 이 기능이 기본적으로 WER(Windows Error Reporting)와 연동되어 "프로그램이 작동을 멈췄습니다" 창으로 먼저 보이는 경우도 많다.

### 왜 CTF/크랙미에서 자주 마주치는가
- 입력 검증 실패 시 의도적으로(또는 버그로) `NULL` 포인터 역참조, 배열 범위 초과 접근이 일어나도록 만든 바이너리가 많다.
- 안티디버깅 코드가 스스로 예외를 던져서 "디버거가 이 예외를 어떻게 처리하는지"로 디버거 존재를 확인하려 할 때도 예외가 표면화되면서 이 창이 뜰 수 있다.
- 즉 이 팝업 자체는 "탐지당했다"는 신호가 아니라 "처리되지 않은 예외가 있었다"는 신호일 뿐이다. 원인은 단순 버그일 수도, 의도된 안티디버깅일 수도 있으므로 크래시 지점을 봐야 판단할 수 있다.

### x64dbg를 JIT 디버거로 등록해두면 더 편하다
x64dbg는 설정에서 자기 자신을 시스템의 기본 JIT 디버거로 등록할 수 있다. 이렇게 해두면 이 팝업이 뜰 때 "Debug" 버튼만 누르면 바로 x64dbg가 크래시 지점(예외가 발생한 정확한 명령어)에 붙은 상태로 열리므로, 어떤 명령어에서 왜 죽었는지 바로 분석을 시작할 수 있다.

## 화면/코드에서 보이는 징후
- 창 제목이 "<프로그램 이름>이(가) 작동을 멈췄습니다" 또는 "Just-In-Time Debugging" 형태로 뜬다.
- 창 안에 "이 컴퓨터에 설치된 디버거"를 고르는 드롭다운/목록과 "Debug"/"디버그", "Close program"/"프로그램 닫기" 버튼이 있다.
- 이미 x64dbg로 프로세스를 실행 중이었다면, 예외가 발생한 순간 x64dbg 창이 노란 화살표로 예외 발생 지점을 가리키며 멈추고 상태 표시줄에 예외 코드(예: `ACCESS_VIOLATION`)가 표시된다 — 이 경우는 JIT 팝업이 따로 뜨지 않는 것이 정상이다.

## 가장 먼저 할 것
1. "Close program"으로 그냥 닫지 말고, 먼저 "Debug" 버튼을 눌러 목록에서 x64dbg(또는 WinDbg)를 선택해 실제로 붙여본다.
2. 붙은 직후 디스어셈블리 창에서 현재 명령어(크래시가 발생한 정확한 주소)와 예외 코드를 확인한다.
3. 이 크래시가 정상적인 버그인지, 안티디버깅이 의도적으로 만든 예외인지부터 판단한다(REV-0871 참고).

## 단계별 절차
1. 팝업이 뜨면 "Debug" 버튼을 누른다.
2. 디버거 선택 목록에 x64dbg가 없다면, x64dbg를 열고 `Options` → `Preferences` → `Attach`(또는 유사 메뉴)에서 "x64dbg를 기본 Just-In-Time 디버거로 등록"을 활성화한 뒤 다시 크래시를 재현한다.
3. x64dbg가 붙으면 상단 상태 표시줄과 로그 창에서 예외 코드(`0xC0000005` = ACCESS_VIOLATION 등)를 확인한다.
4. 디스어셈블리 창에서 현재 RIP/EIP가 가리키는 명령어를 확인하고, 콜스택(REV-0866 참고)을 함께 살펴 어느 함수 흐름에서 여기까지 왔는지 파악한다.
5. 크래시 원인이 사용자 입력 처리 버그인지, `IsDebuggerPresent`/예외 기반 안티디버깅인지 코드를 거슬러 올라가며 확인한다.
6. 필요하면 프로그램을 처음부터 x64dbg로 직접 열어서(팝업이 뜨기 전에 이미 디버거가 붙어 있는 상태로) 같은 지점까지 실행해, 이번엔 팝업 없이 그 자리에서 바로 멈추는지 비교한다.

## 명령어/단축키
- x64dbg: `File` → `Open`으로 대상 EXE를 직접 열어 처음부터 디버거를 붙인 상태로 실행(팝업을 아예 피하는 방법), `Options` → `Preferences` → JIT 디버거 등록 옵션
- WinDbg: `windbg -p <PID>`로 이미 뜬 프로세스에 붙거나, JIT 목록에서 WinDbg 선택 시 자동으로 크래시 지점에 붙어서 열림
- 레지스트리 확인(선택): `reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\AeDebug"`로 현재 등록된 JIT 디버거 확인

## 출력 해석
- 예외 코드 `0xC0000005`(ACCESS_VIOLATION)는 잘못된 메모리 주소 접근을 의미하며, 대상 주소가 `0x00000000` 근처면 NULL 포인터 역참조를 의심한다.
- 예외 코드 `0x80000003`(`STATUS_BREAKPOINT`)이 반복적으로 뜬다면 코드 안에 `INT3` 명령어가 직접 박혀 있거나(안티디버깅), 이미 다른 디버거가 소프트웨어 브레이크포인트를 심어놓은 상태일 수 있다(REV-0860 참고).
- 크래시 지점이 사용자 코드가 아니라 `ntdll.dll`이나 CRT 내부라면, 그 직전 콜스택에서 사용자 코드가 어떤 인자를 잘못 넘겼는지부터 확인해야 한다.

## 흔한 실수
- 당황해서 "Close program"만 누르고 정보를 다 날려버리는 것 — 이 창이 뜬 시점의 크래시 지점이 오히려 분석에 유용한 단서일 수 있다.
- JIT 팝업이 뜨는 것을 "디버거가 탐지당했다"는 신호로 오해해서 무작정 우회 기법부터 찾는 것 — 실제로는 단순 크래시인 경우가 훨씬 많다.
- x64dbg를 JIT 디버거로 등록해놓고 나중에 원래 상태로 되돌리는 것을 잊어서, 이후 다른 프로그램이 크래시할 때마다 x64dbg가 뜨는 것을 이상하게 여기는 것.
- 32비트 프로그램인데 64비트 WinDbg로 붙으려다 실패하는 것(REV-0861 참고) — WOW64 프로세스는 대응하는 비트수의 디버거로 붙어야 한다.

## 막혔을 때 다음 체크
- 이 창이 반복적으로, 특정 입력에서만 뜬다면 → 그 입력을 처리하는 함수 주변에 미리 브레이크포인트를 걸고(REV-0169) 예외가 뜨기 전 단계부터 추적한다.
- 예외가 안티디버깅 목적으로 의도된 것 같다면 → REV-0871에서 원인을 좁히는 절차를 따른다.
- 디버거가 붙은 후에도 예외가 계속 반복되며 진행이 안 된다면 → REV-0860을 참고해 예외를 프로그램에 전달할지 여부를 설정한다.

## 미니 예제
```text
[팝업] "chall.exe가 작동을 멈췄습니다."
디버거 선택: [x64dbg] [WinDbg] ...
→ [Debug] 클릭 → x64dbg 선택
```
x64dbg가 열리면 상태 표시줄에 `Access violation when reading [0000000000000000]` 같은 메시지가 뜨고, 디스어셈블리 창은 그 순간의 명령어를 노란 화살표로 가리킨다. 여기서 `bt`(콜스택 확인, REV-0866)와 레지스터 창을 함께 보면 어떤 함수가 NULL 포인터를 넘겼는지 바로 역추적할 수 있다.

## 관련 글
- REV-0860 — 디버거 안에서 예외가 계속 발생해서 진행이 안 될 때
- REV-0861 — 32비트 디버거로 64비트 프로세스를 못 열 때(또는 반대)
- REV-0871 — 안티디버깅 때문에 디버거에서 갑자기 종료될 때 원인 좁히기(실전)
- REV-0866 — 디버거에서 콜스택이 깨져서 안 보일 때
- REV-0169 — Breakpoint가 무엇이고 어디에 걸어야 하는가

## 출처/검증
- Just-In-Time(사후) 디버깅과 AeDebug 레지스트리 키의 동작 방식: Microsoft Learn "Enabling Postmortem Debugging" 문서 기준.
- x64dbg를 기본 디버거로 등록하는 기능: x64dbg 공식 문서(Preferences) 기준.
- 예외 코드(`ACCESS_VIOLATION`, `STATUS_BREAKPOINT`) 의미: Windows 예외 코드 관련 공식 문서 기준.
