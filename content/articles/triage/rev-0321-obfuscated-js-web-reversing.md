## 한 줄 요약
이 위키는 네이티브 바이너리(PE/ELF) 리버싱을 중심으로 다루지만, 가끔 "리버싱" 카테고리에 난독화된 JavaScript 문제가 섞여 나오는 경우가 있으며, 이때는 IDA/Ghidra가 아니라 브라우저 개발자도구와 코드 정렬(beautify) 도구로 최소한의 가독성을 확보한 뒤 "검증 함수를 찾아 거꾸로 추적한다"는 리버싱의 핵심 원칙을 그대로 적용하면 된다.

## 언제 검색해야 하나
- 첨부파일 확장자가 `.js`, `.html`이거나 IDA/Ghidra로 열리지 않고 텍스트 편집기로 열면 사람이 읽기 힘든 한 줄짜리 코드가 나올 때
- 변수명이 `_0x1a2b`, `_0x3c4d` 같은 패턴으로 전부 치환되어 있어 무엇을 하는 코드인지 감이 안 잡힐 때
- 문제를 풀려면 브라우저에서 버튼을 누르거나 콘솔에 값을 입력해야 하는 구조일 때
- 리버싱 대회인데 갑자기 웹 기반 문제가 섞여 나와서 어떤 도구를 써야 할지 모를 때

## 핵심 개념

### 네이티브 리버싱과 원칙은 같다
JavaScript도 결국 "입력값을 받아 어떤 로직으로 변환한 뒤 정답과 비교하는" 구조라는 점은 네이티브 바이너리의 `check_flag` 함수와 동일하다(REV-0006). 다만 도구가 다르다. IDA의 디컴파일러 대신 브라우저의 개발자도구(F12)가 있고, 어셈블리 대신 (난독화되었더라도) 원본과 같은 고급 언어인 JavaScript 코드를 그대로 읽는다는 점이 오히려 유리하다.

### 난독화 종류 파악
JS 난독화는 보통 다음 중 하나 또는 조합이다.
- **압축(minify)**: 줄바꿈과 들여쓰기를 제거해 한 줄로 만듦. 로직 자체는 안 바뀜.
- **변수명 치환**: 의미 있는 이름을 `_0x1a2b` 같은 무의미한 이름으로 바꿈. 로직 흐름은 그대로.
- **문자열 배열화**: 모든 문자열 리터럴을 하나의 배열에 몰아넣고 인덱스로 접근(예: `_0x4a2f[3]`). 실행 중 콘솔에서 그 배열을 출력해보면 원문이 그대로 보인다.
- **제어 흐름 평탄화(control flow flattening)**: `switch`문과 상태 변수로 원래 순서를 뒤섞음. 네이티브 바이너리의 REV-0231(제어 흐름 평탄화)과 개념이 동일하다.

### 최소 대응의 원칙
이 위키의 핵심 도구(IDA, Ghidra, x64dbg, GDB)는 JS에 적용되지 않는다. 하지만 오프라인 환경에서도 쓸 수 있는 최소한의 도구만으로 충분히 뚫을 수 있다.
- **브라우저 개발자도구(F12)**: 오프라인에서도 항상 사용 가능. Sources 탭에서 코드를 보고, 원하는 줄에 브레이크포인트를 걸어 실행을 멈추고 변수 값을 확인할 수 있다(네이티브 디버거의 `break`/`step`과 동일한 개념).
- **콘솔(Console) 탭**: `console.log`를 코드에 끼워 넣거나, 브레이크포인트가 걸린 상태에서 임의의 변수를 콘솔에 쳐서 즉시 값을 확인할 수 있다.
- **코드 정렬**: 개발자도구 Sources 탭 하단의 `{}` 아이콘(Pretty-print)을 누르면 한 줄로 압축된 코드가 자동으로 들여쓰기되어 최소한의 가독성이 생긴다. 별도 설치 없이 브라우저에 내장되어 있다.
- **Node.js**: 로컬에 Node가 설치되어 있다면 브라우저 없이 해당 스크립트 일부만 떼어내 직접 실행하고 중간 값을 출력해볼 수 있다.

## 화면/코드에서 보이는 징후
- 소스 코드가 세미콜론 하나 없이 수천 자짜리 한 줄로 되어 있음
- `var _0x4a2f = ['\x63\x68\x65\x63\x6b', ...]`처럼 문자열이 배열과 16진수 이스케이프로 뭉쳐 있음
- `while(true){ switch(_0x state){ case 1: ... } }` 형태의 상태 머신 구조
- 브라우저 콘솔에 `debugger;` 문이 반복 실행되어 개발자도구를 열면 계속 멈추는 안티 디버깅성 코드

## 가장 먼저 할 것
브라우저에서 파일을 열고 F12로 개발자도구를 켠 뒤 Sources 탭에서 Pretty-print(`{}`)로 정렬한다. 그 다음 페이지에서 "정답 확인" 버튼을 누르는 지점의 이벤트 리스너 코드부터 찾는다 — 네이티브 바이너리의 `main`에서 검증 함수로 가는 것과 같은 접근이다.

## 단계별 절차
1. 개발자도구(F12) → Sources 탭 → Pretty-print(`{}`)로 코드 정렬
2. Ctrl+F(Sources 탭 내 검색)로 `compare`, `check`, `flag`, `correct` 같은 키워드 검색 — REV-0163(문자열에서 검증 함수로 이동)과 같은 접근
3. 검증처럼 보이는 함수 시작 줄에 브레이크포인트(줄 번호 클릭)를 걸고 페이지에서 실제로 값을 입력해 실행 정지
4. 정지된 상태에서 Console 탭에 변수명을 직접 입력해 현재 값을 확인 (네이티브 디버거의 watch/print와 동일)
5. 문자열 배열화가 있다면 그 배열 변수를 콘솔에 출력해 원문 문자열을 한 번에 복원
6. 로직이 파악되면 Python이나 Node.js로 같은 로직을 재구현해 정답을 역산 (REV-0017과 동일한 절차)
7. `debugger;` 문이 반복 실행되어 방해되면 개발자도구 설정에서 "Disable breakpoints"를 잠깐 켜거나, 해당 줄에서 우클릭 → "Never pause here"로 무시

## 명령어/단축키
```text
F12                       개발자도구 열기
Ctrl+Shift+C               요소 선택 모드
{}                          Sources 탭 Pretty-print
Ctrl+F (Sources 내)         현재 파일 텍스트 검색
Ctrl+Shift+F                전체 스크립트 텍스트 검색
```
```bash
node script.js   # 오프라인에서 Node.js로 스크립트 조각 직접 실행
```

## 출력 해석
- Pretty-print 후에도 변수명이 `_0x`로 시작하면 이름 자체는 여전히 의미가 없다는 뜻이므로, 이름이 아니라 흐름(어떤 값이 어디서 비교되는지)으로 로직을 따라가야 한다.
- 콘솔에서 문자열 배열을 출력했을 때 사람이 읽을 수 있는 문장이 나오면 문자열 배열화 난독화가 전부이므로 로직 자체는 이미 거의 다 파악된 것이다.
- 브레이크포인트에서 변수 값이 계속 `undefined`로 보이면 스코프가 다른 위치에 브레이크포인트를 건 것이니 호출 스택(Call Stack 패널)을 보고 올바른 프레임을 선택했는지 확인한다.

## 흔한 실수
- JS 문제를 IDA/Ghidra로 열려고 시도하며 시간을 낭비하는 것 — 애초에 네이티브 실행 파일 포맷이 아니다.
- 변수명이 무의미하다고 코드 전체를 포기하는 것 — 원칙은 네이티브 리버싱과 같으므로 흐름과 비교 지점만 찾으면 된다.
- 문자열 배열화를 보고 "암호화됐다"고 오해하는 것 — 대부분 단순 배열 인덱싱이라 콘솔에서 그대로 출력하면 원문이 나온다.
- 온라인 JS 디옵퍼스케이터(webcrack, de4js 등)에 의존하려다 오프라인 환경이라 접속이 안 되는 것을 뒤늦게 깨닫는 것 — 브라우저 개발자도구만으로도 충분히 풀린다는 점을 먼저 시도한다.

## 막혔을 때 다음 체크
- 검증 함수를 찾는 접근 자체가 헷갈린다 → REV-0006 Flag 검증 함수 찾는 가장 흔한 경로(네이티브 기준이지만 원칙은 동일)
- 문자열에서 로직으로 접근하는 순서가 기억 안 난다 → REV-0163 문자열에서 검증 함수로 이동하는 정적 분석
- 제어 흐름이 뒤섞여 있어 순서를 못 따라가겠다 → REV-0231 Control Flow Flattening(네이티브 개념이지만 패턴 이해에 도움)
- 로직 복원 후 역산 설계가 막힌다 → REV-0017 솔버를 짜기 전에 직접 로직을 복원하는 순서

## 미니 예제
```javascript
var _0x4a2f = ['\x63\x6f\x72\x72\x65\x63\x74'];
function _0x1a2b(_0x3c4d) {
    return _0x3c4d === _0x4a2f[0];
}
```
개발자도구 콘솔에서 `_0x4a2f[0]`을 직접 입력하면 `"correct"`가 출력된다. 함수 이름과 변수명이 전부 난독화되어 있어도, 비교 대상 문자열은 배열에 그대로 남아 있으므로 콘솔 한 줄로 정답을 확인할 수 있다. 실제 대회 문제는 이보다 훨씬 복잡하지만, "비교 지점을 찾아 콘솔로 값을 확인한다"는 접근 자체는 동일하게 통한다.

## 관련 글
- REV-0006 — Flag 검증 함수 찾는 가장 흔한 경로
- REV-0163 — 문자열에서 검증 함수로 이동하는 정적 분석
- REV-0231 — Control Flow Flattening 기초
- REV-0017 — 솔버를 짜기 전에 직접 로직을 복원하는 순서
- REV-0319 — 리버싱과 Pwnable이 섞인 문제 구분하는 법

## 출처/검증
- Chrome DevTools Sources 패널의 Pretty-print, 브레이크포인트, Call Stack 기능: Chrome DevTools 공식 문서 기준.
- JS 난독화 유형(변수명 치환, 문자열 배열화, 제어 흐름 평탄화) 분류는 일반적으로 통용되는 JavaScript obfuscator 도구들의 옵션 명세 및 CTF web/리버싱 라이트업에서 공통적으로 확인되는 패턴 (2026-09-09 검증).
