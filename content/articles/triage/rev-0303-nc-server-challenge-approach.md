## 한 줄 요약
`nc host port`로 접속하는 서버형 리버싱 문제는 원격 서버가 하는 일을 **로컬에서 재현 가능한 바이너리로 먼저 확보**한 뒤 로컬에서 정적/동적 분석을 끝내고, 마지막 검증과 flag 획득만 원격 서버에 대해 수행하는 순서로 접근해야 한다.

## 언제 검색해야 하나
- 문제 설명에 `nc <host> <port>` 또는 `ncat`, `socat` 접속 명령이 적혀 있을 때
- 원격 서버에 연결하면 바이너리 없이 프롬프트만 나오는데 어떻게 분석해야 할지 막막할 때
- 로컬에 디버거를 못 붙이는 상황이라 원격 서버에서 직접 시행착오를 하려다 접속이 자주 끊겨서 비효율적일 때

## 핵심 개념
서버 연결형 문제는 두 가지 하위 유형으로 나뉜다.

1. **바이너리가 별도로 첨부된 경우** (가장 흔함): 문제 페이지에 실행파일이 함께 제공되고, `nc`는 그 바이너리를 실행 중인 서버에 연결하는 용도다. 이 경우 원격 서버는 사실상 "실행 환경"일 뿐이고, 실제 분석은 첨부된 바이너리로 전부 로컬에서 할 수 있다.
2. **바이너리가 첨부되지 않고 서버만 있는 경우**: 순수 프로토콜/서비스 분석 문제이거나, 블랙박스 방식으로 입출력만 보고 로직을 추측해야 하는 문제다. 이 경우 `nc`로 직접 상호작용하며 입출력 패턴을 관찰하는 것 자체가 유일한 정보 수집 수단이 된다.

리버싱 관점에서 핵심 원칙은 "**로컬로 가져올 수 있으면 반드시 로컬로 가져와서 분석한다**"이다. 원격 서버는 다음과 같은 제약이 있기 때문이다.
- 디버거(GDB, x64dbg)를 원격 프로세스에 직접 붙일 수 없다(서버 운영자가 gdbserver 등을 열어주지 않는 한).
- 연결이 타임아웃되거나, 동시 접속 수 제한, 요청 빈도 제한(rate limit)이 걸려 있을 수 있다.
- 시행착오(브루트포스, 반복 실행)를 원격에서 하면 네트워크 지연 때문에 로컬보다 수십~수백 배 느리다.
- 서버가 리셋되거나 시드값이 매 접속마다 달라질 수 있어(예: 랜덤 시드), 같은 입력을 넣어도 다른 결과가 나올 수 있다.

따라서 원격 서버는 "**최종 검증 및 flag 제출 창구**"로만 쓰고, 실제 분석/역산/브루트포스 로직 개발은 로컬 환경에서 끝내는 것이 정석이다.

## 화면/코드에서 보이는 징후
- 문제 설명에 `nc chal.example.com 31337` 형태의 접속 정보가 있다.
- 접속하면 배너 메시지 뒤에 `Enter your input: ` 같은 프롬프트가 뜬다.
- 첨부파일 목록에 실행 파일, 그리고 종종 `Dockerfile`이 함께 있다(로컬 재현을 위한 힌트).
- 몇 초 이상 응답이 없거나 잘못된 입력을 넣으면 즉시 연결이 끊긴다.

## 가장 먼저 할 것
첨부파일 목록에 실행 파일이 있는지부터 확인한다. 있다면 그 파일을 로컬에서 실행해 원격 서버와 동일한 프롬프트/배너가 나오는지 대조한다. 동일하면 이후 분석은 전부 로컬 바이너리로 진행하고, `nc` 접속은 최종 확인 단계에서만 사용한다.

## 단계별 절차

**1) 첨부 바이너리와 원격 서버 동일성 확인**
```bash
./chall
nc chal.example.com 31337
```
두 출력의 배너 문자열, 프롬프트 문구가 동일한지 비교한다. 동일하면 로컬 바이너리가 서버와 같은 코드임이 사실상 확정된다.

**2) `Dockerfile`/`docker-compose.yml`로 실행 환경 재현**
```bash
cat Dockerfile
docker build -t chall .
docker run -p 31337:31337 chall
```
Dockerfile이 제공되면 로컬에 동일한 환경을 통째로 띄울 수 있다. 이렇게 하면 서버가 리스닝 소켓을 여는 방식(예: `socat`, `xinetd`, 자체 fork 서버)까지 동일하게 재현되어, 진짜 서버와 100% 같은 조건에서 반복 테스트할 수 있다.

**3) 로컬에서 표준 정적/동적 분석 진행**
Docker 없이 바이너리만 있어도 대부분 충분하다. IDA/Ghidra로 정적 분석, 필요하면 로컬 프로세스로 실행 후 GDB/Pwndbg를 붙여 동적 분석한다(원격 서버에는 디버거를 붙일 수 없지만 로컬 사본에는 자유롭게 붙일 수 있다).

**4) 로컬에서 pwntools로 상호작용 스크립트 작성**
```python
from pwn import process, remote

LOCAL = True
if LOCAL:
    p = process('./chall')
else:
    p = remote('chal.example.com', 31337)

p.recvuntil(b'Enter your input: ')
p.sendline(b'test')
print(p.recvall(timeout=2))
```
`LOCAL` 플래그 하나로 로컬/원격을 즉시 전환할 수 있게 스크립트를 짜두면, 로컬에서 수백 번 반복 테스트한 뒤 마지막에 플래그 하나만 바꿔서 원격에 그대로 쏠 수 있다.

**5) 로컬에서 로직 복원 및 브루트포스/역산 검증 완료**
로컬 환경에서 반복 실행 속도가 빠르므로, 여기서 솔버를 충분히 검증한다. 성공률이 100%에 가까워질 때까지 로컬에서 반복한다.

**6) 마지막에만 원격 서버로 전환**
`LOCAL = False`로 바꾸고 실행해서 실제 flag를 획득한다. 원격 접속 횟수를 최소화하기 위해, 로컬 검증이 끝나기 전까지는 원격에 접속하지 않는다.

**7) 바이너리가 없는 순수 블랙박스 서버인 경우**
1~6단계를 쓸 수 없다. 이 경우 `nc`로 직접 접속해 다양한 입력(빈 입력, 매우 긴 입력, 특수문자, 예상 범위를 벗어난 숫자)을 넣어보며 응답 패턴 차이를 기록한다. 에러 메시지 차이(예: "Invalid format" vs "Wrong answer")는 검증 단계가 여러 개로 나뉘어 있다는 뜻이므로, 어느 단계에서 실패했는지 구분하는 단서가 된다.

## 명령어/단축키
```bash
nc chal.example.com 31337
ncat --ssl chal.example.com 31337   # TLS가 걸린 서버
cat Dockerfile
docker build -t chall . && docker run -p 31337:31337 chall
python3 solve.py            # LOCAL=True로 반복 검증
python3 solve.py --remote   # 최종 1회 실행(스크립트에 인자 분기 추가 시)
```
pwntools: `process()`, `remote()`, `recvuntil()`, `sendline()`, `recvall(timeout=2)`.

## 출력 해석
- 로컬 실행과 원격 접속의 배너가 다르면(예: 버전 문자열, flag 형식 안내 문구가 다름) 첨부된 바이너리가 서버의 것과 다른 버전일 수 있다는 경고 신호다. 이 경우 상수/오프셋을 다시 확인해야 한다.
- 원격 접속이 특정 입력 이후 즉시 끊기면(`recv` 결과가 빈 문자열) 서버 쪽에서 크래시가 났거나 타임아웃이 걸린 것이다. 로컬 재현 환경에서 같은 입력을 넣어 크래시 원인을 GDB로 확인한다.
- 응답 시간이 유난히 길면 서버가 의도적으로 지연을 넣어 브루트포스를 막고 있다는 신호일 수 있다(rate limiting). 이 경우 값을 한 번에 크게 좁힐 수 있는 역산 방법을 우선 찾아야 한다.

## 흔한 실수
- 첨부 바이너리가 있는데도 확인 없이 바로 `nc`로만 반복 시도해서, 네트워크 지연 때문에 시행착오가 매우 느려지는 것.
- 로컬 바이너리와 원격 서버가 실제로 동일한지 확인하지 않고 분석해서, 오프셋이나 상수가 미묘하게 다른 서버 버전(REV-0711과 유사하게 libc/바이너리 버전 불일치)에서 실패하는 것.
- pwntools 스크립트에서 로컬/원격 전환 스위치를 만들어두지 않아, 매번 코드를 손으로 고쳐 쓰다가 실수로 원격에 잘못된 입력을 대량으로 보내 rate limit에 걸리는 것.
- 서버 응답을 받을 때 타임아웃을 설정하지 않아(`recvall()`을 무한 대기로 호출) 스크립트가 멈춘 것처럼 보여 원인을 못 찾는 것.

## 막혔을 때 다음 체크
- 첨부 바이너리가 여러 개라 어디가 서버 로직인지 헷갈린다 → REV-0301 문제 파일이 여러 개일 때 우선순위 정하는 법
- 로컬 재현까지는 됐는데 정적 분석에서 막혔다 → REV-0018 대회장에서 리버싱 문제 하나를 끝까지 추적하는 실전 루틴
- 서버와 로컬 libc/바이너리 버전이 다른 것 같다 → REV-0711 서버 환경 glibc와 로컬 glibc가 달라 분석이 안 맞을 때

## 미니 예제
문제: "`nc chal.example.com 9999`로 접속해 숫자 맞추기 게임을 이기세요." 첨부파일: `guess`, `Dockerfile`.

1. `./guess` 로컬 실행 → `Guess a number between 1 and 100: ` 프롬프트 확인. `nc chal.example.com 9999` 접속 → 동일한 프롬프트 확인. 동일 바이너리로 확정.
2. IDA로 `guess` 정적 분석 → `srand(time(NULL))`로 시드를 매초 단위로 설정하고 있음을 발견 → 시드가 접속 시각에 의존하므로 접속 직후 서버 시각을 추정하면 재현 가능하다고 판단.
3. 로컬 `process()`로 100회 반복 실행하며 시드-정답 관계를 검증하는 스크립트 완성, 성공률 100% 확인.
4. `remote()`로 전환해 1회 실행 → flag 획득.

바이너리 확보 → 로컬 검증 → 원격 1회 실행이라는 순서를 지켰기 때문에 원격 접속은 딱 한 번으로 끝났다.
