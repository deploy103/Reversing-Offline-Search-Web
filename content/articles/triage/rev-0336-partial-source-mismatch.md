## 한 줄 요약
문제에서 일부 소스코드(헤더, 일부 함수, `main.c` 등)를 같이 줬는데 실제 바이너리와 안 맞아 보인다면, 대부분은 소스가 거짓이 아니라 **컴파일 옵션/버전 차이, 전처리기 조건부 컴파일, 혹은 소스가 "일부만" 제공되어 누락된 부분** 때문이므로, 직접 같은 옵션으로 재컴파일해서 바이트 단위로 비교하는 것이 가장 확실한 확인법이다.

## 언제 검색해야 하나
- 제공된 소스의 함수 이름/상수가 바이너리 안에서 검색해도 안 나올 때
- 소스에 있는 구조체 크기와 디컴파일러가 추정한 구조체 크기가 다를 때
- 소스를 그대로 컴파일해봤는데 결과 바이너리 크기/해시가 원본과 전혀 다를 때
- 소스는 단순한데 바이너리 디스어셈블리는 훨씬 복잡해 보일 때(혹은 그 반대)

## 핵심 개념
"소스와 바이너리가 안 맞는다"고 느낄 때 확인해야 할 원인 우선순위는 다음과 같다.

1. **컴파일러 최적화 차이** — 소스는 단순한 반복문인데 `-O2`로 컴파일되면 루프 언롤링, 인라이닝, 벡터화(SIMD)로 완전히 다른 모양의 어셈블리가 나온다(REV-0037, REV-0464 참고). 이건 소스가 틀린 게 아니라 "사람이 읽는 소스"와 "컴파일러가 최적화한 결과"의 정상적인 차이다.
2. **전처리기 조건부 컴파일(`#ifdef`)** — 제공된 소스에 `#ifdef DEBUG ... #endif`처럼 조건부 블록이 있는데, 실제 배포 바이너리는 다른 매크로 정의로 컴파일되어 그 블록이 통째로 빠지거나 다른 코드로 대체된 경우.
3. **소스가 "일부만" 제공됨** — 문제 출제자가 검증 로직 핵심 부분은 일부러 빼고 헤더나 보조 함수만 준 경우. 이 경우 "안 맞는" 게 아니라 애초에 안 줬을 뿐이며, 나머지는 바이너리에서 직접 분석해야 한다.
4. **컴파일러/버전 차이** — 소스를 준 시점과 배포 바이너리를 빌드한 컴파일러 버전(GCC 9 vs GCC 13, MSVC 버전 등)이 다르면, 같은 로직이라도 레지스터 할당, 스택 프레임 구성, 함수 순서가 달라질 수 있다.
5. **구조체 패딩/정렬 차이** — 컴파일 타겟의 비트폭(32/64비트)이나 `#pragma pack` 여부에 따라 구조체 크기와 필드 오프셋이 소스만 보고 예상한 것과 달라질 수 있다.
6. **소스가 의도적인 red herring(가짜 단서)** — CTF에서 드물지만, 제공된 소스가 실제 로직과 무관한 미끼일 수도 있다. 이 경우 문자열/상수 대조로 진위를 판단해야 한다.

## 화면/코드에서 보이는 징후
- `strings ./chall`에 소스에 있는 특정 문자열 리터럴이 안 보임
- 디스어셈블리의 CALL 순서/개수가 소스의 함수 호출 순서와 안 맞음
- 소스의 `struct`를 그대로 IDA에 타입으로 넣었는데 필드 오프셋이 어긋남(REV-0148 IDA Set Type 참고)

## 가장 먼저 할 것
제공된 소스에만 있는 **고유 문자열 리터럴**이나 **매직 상수**를 하나 골라, 바이너리에서 실제로 검색되는지부터 확인한다. 안 나오면 그 소스는 이 바이너리를 만드는 데 안 쓰였거나 다른 옵션으로 빌드된 것이다.

## 단계별 절차

**1) 소스의 고유 문자열/상수가 바이너리에 있는지 확인**
```bash
strings ./chall | grep "특정_문자열"
grep -n "0x1337BEEF" source.c
```
문자열이 바이너리에 없다면 이 소스가 그대로 컴파일된 게 아니거나, strip/난독화로 상수가 계산식으로 바뀌었을 가능성을 의심한다.

**2) 같은 컴파일러/옵션으로 직접 재컴파일해서 비교**
```bash
gcc -O2 -o my_build source.c
diff <(objdump -d my_build) <(objdump -d chall)
```
완전히 동일하지 않아도, 함수 순서/구조가 비슷하게 나온다면 최적화 옵션(`-O0`, `-O1`, `-O2`, `-Os`)을 바꿔가며 가장 비슷한 결과가 나오는 조합을 찾는다. 컴파일러 버전도 여러 개 있으면(`gcc-9`, `gcc-13` 등) 바꿔가며 시도한다.

**3) 전처리기 조건부 블록 확인**
```bash
gcc -E source.c | less
```
`-E` 옵션으로 전처리만 실행해 실제로 컴파일에 포함될 코드가 무엇인지 확인한다. `#ifdef`로 빠지는 블록이 있다면, 그 블록이 검증 로직의 핵심일 가능성을 의심한다.

**4) 구조체 크기/정렬 재확인**
```c
printf("%zu\n", sizeof(struct MyStruct));
```
소스에 있는 구조체를 직접 컴파일해 `sizeof`를 찍어보고, IDA/Ghidra가 추정한 구조체 크기와 비교한다. 32비트/64비트 빌드 차이나 `#pragma pack(1)` 여부를 의심한다.

**5) 소스가 일부만 제공된 것으로 결론 나면, 나머지는 바이너리 기준으로 분석**
소스에 없는 함수는 REV-0007(입력 함수부터 역추적하는 방법)의 방식대로 바이너리에서 직접 함수 경계와 로직을 재구성한다. 이미 확보한 소스는 구조체 정의나 상수 이름을 아는 데만 참고용으로 쓴다.

## 명령어/단축키
```bash
strings ./chall | grep "..."
gcc -O2 -o my_build source.c
gcc -E source.c
objdump -d my_build > a.asm
objdump -d chall > b.asm
diff a.asm b.asm
```

## 출력 해석
- `diff` 결과가 완전히 다른 함수 개수/순서를 보인다면 컴파일 옵션 차이가 크다는 뜻 — `-O0`부터 다시 시도한다.
- `gcc -E` 결과에 문제되는 함수 블록이 아예 없다면, 그 매크로가 실제 빌드에서 정의되지 않았다는 뜻이다. `-D<매크로명>`을 추가해서 다시 전처리해본다.
- 구조체 `sizeof`가 소스 기준 계산값과 다르면, 필드 사이에 컴파일러가 넣은 패딩 바이트가 있다는 뜻 — 필드를 하나씩 오프셋과 함께 다시 나열해 확인한다.

## 흔한 실수
- 소스와 바이너리가 100% 바이트 단위로 똑같아야 한다고 기대하는 것 — 컴파일러/버전/옵션 차이로 항상 완벽히 같을 수는 없다. "로직이 같은가"를 봐야지 "바이트가 같은가"를 보면 안 된다.
- `-O0`으로만 재컴파일해보고 안 맞는다고 포기하는 것 — 실제 배포 바이너리는 대부분 `-O2` 이상으로 빌드되므로 최적화 옵션을 반드시 바꿔가며 시도해야 한다.
- 소스에 없는 함수를 발견했을 때 "소스가 잘못됐다"고 의심하기보다 "이 소스는 일부만 제공된 것"이라는 훨씬 흔한 가능성을 먼저 배제하지 않는 것.
- 구조체 오프셋 불일치를 32/64비트 빌드 차이로 확인하지 않고 바로 "디컴파일러가 틀렸다"고 결론짓는 것.

## 막혔을 때 다음 체크
- 최적화로 인한 어셈블리 차이 자체가 낯설다면 → REV-0037 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 이유.
- `-O0`과 `-O2` 결과를 나란히 비교하는 구체적 방법이 필요하면 → REV-0464 -O0과 -O2 컴파일 결과를 나란히 비교하는 법.
- 소스 없이 함수를 처음부터 역추적해야 한다면 → REV-0007 입력 함수부터 역추적하는 방법.
- 컴파일러가 생성한 코드와 실제 문제 로직을 구분하는 기준이 필요하면 → REV-0167 Compiler Generated Code와 실제 문제 로직 구분.

## 미니 예제
```c
// 제공된 source.c 일부
#define KEY 0x1337

int check(int x) {
    return x ^ KEY;
}
```
```bash
$ strings chall | grep -i 1337
(아무 결과 없음)

$ objdump -d chall | grep -A3 "<check>:"
0000000000401136 <check>:
  401136: 8b 45 fc     mov eax,[rbp-0x4]
  401139: 35 ef 12 00 00  xor eax, 0x12ef
  40113e: c3           ret
```
소스에는 `KEY`가 `0x1337`로 정의되어 있는데, 실제 바이너리의 XOR 상수는 `0x12ef`다. `strings`로도 `1337`이 안 잡힌다. 이건 소스가 가짜라는 뜻이 아니라, 제공된 `source.c`가 실제 배포본과 다른 빌드(매크로 값이 다르게 정의된 버전)라는 뜻이므로, 상수는 소스가 아니라 바이너리에서 직접 뽑은 `0x12ef`를 써야 한다.

## 관련 글
- REV-0037 — 컴파일러 최적화가 디컴파일 결과를 이상하게 만드는 이유
- REV-0464 — -O0과 -O2 컴파일 결과를 나란히 비교하는 법
- REV-0007 — 입력 함수부터 역추적하는 방법
- REV-0167 — Compiler Generated Code와 실제 문제 로직 구분

## 출처/검증
- GCC 최적화 레벨별 코드 변형(인라이닝, 루프 언롤링, 벡터화): GNU GCC 공식 매뉴얼 "Options That Control Optimization" 섹션 기준 (2026-09-09 검증).
- 전처리기 조건부 컴파일과 `-E` 옵션 동작: GCC 공식 매뉴얼 "Preprocessor Options" 섹션 기준.
