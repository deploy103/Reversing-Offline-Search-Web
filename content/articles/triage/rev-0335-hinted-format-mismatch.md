## 한 줄 요약
문제 설명/카테고리/힌트가 "Windows PE"라거나 "32비트"라고 말해도 실제 파일을 직접 검사한 결과가 다르다면, **문제 설명을 그대로 믿지 말고 항상 파일 자체(`file`, 매직 바이트, 헤더 필드)를 근거로 재확인**해야 한다 — CTF에서는 의도적인 misdirection이거나 문제 출제자의 단순 오기일 수 있다.

## 언제 검색해야 하나
- 문제 카테고리가 "pwn"/"rev - Windows"라고 되어 있는데 실제로 받은 파일이 ELF일 때
- 문제 설명에 "32bit binary"라고 적혀 있는데 `file` 결과는 64비트일 때
- 힌트에 "UPX로 패킹되어 있다"고 했는데 DIE로 확인하니 패킹 시그니처가 없을 때
- 확장자가 `.exe`인데 실제로는 스크립트, .NET, 혹은 아예 다른 실행 형식일 때

## 핵심 개념
문제 설명과 실제 파일이 다른 경우는 원인에 따라 대응이 완전히 달라진다.

1. **의도된 misdirection(CTF 트릭)** — 출제자가 일부러 "이건 평범한 크래크미다"라고 설명해놓고 실제로는 패킹/난독화가 되어 있거나, 반대로 "매우 어려운 패킹 바이너리"처럼 보이게 해놓고 실제로는 단순한 문제인 경우. 힌트를 절반만 믿고 나머지는 직접 검증해야 한다.
2. **단순 오기/설명 미스** — 출제자가 문서를 여러 버전 관리하다가 설명 텍스트를 안 고친 경우. 실제로 흔하다.
3. **여러 파일이 섞여서 배포됨** — zip 안에 여러 바이너리(예: 서버용 ELF와 로컬 테스트용 PE)가 같이 들어있는데, 설명은 그중 하나만 기준으로 쓰여 있어서 다른 파일을 열어본 사람은 안 맞는 것처럼 느끼는 경우.
4. **버전/빌드 차이** — 문제 설명 작성 시점의 바이너리와 실제 배포된 바이너리가 다른 빌드(예: 최적화 옵션, 아키텍처 타겟)로 컴파일된 경우.
5. **아키텍처/비트폭에 대한 확인 없이 넘겨짚음** — "Windows 문제니까 32비트겠지"처럼 근거 없는 가정을 자기 스스로 세운 경우도 이 범주에 든다. 이건 힌트가 틀린 게 아니라 내가 확인을 안 한 것이므로, 항상 스스로도 재확인 습관을 들여야 한다.

원칙은 하나다: **문제 설명은 참고용이고, 최종 판단 근거는 항상 파일 자체다.**

## 화면/코드에서 보이는 징후
- 문제 설명: "This is a Windows executable." / 실제: `file chall` → `ELF 64-bit LSB executable`
- 문제 설명: "32-bit binary, statically linked." / 실제: `readelf -h`의 `Class:` 필드가 `ELF64`
- 힌트: "no protections" / 실제: `checksec` 결과 `Canary: Enabled`, `PIE: Enabled`

## 가장 먼저 할 것
문제 설명은 일단 접어두고, `file`과 헥스 에디터로 실제 매직 바이트/헤더 필드부터 직접 확인한다. 그 결과를 기준으로 분석 도구와 전략을 정한다.

## 단계별 절차

**1) 실제 파일 형식/비트폭/아키텍처를 독립적으로 확인**
```bash
file ./chall
readelf -h ./chall 2>/dev/null | grep -E "Class|Machine|Type"
```
Windows PE라면:
```bash
objdump -f ./chall.exe
```
`Class: ELF32` vs `ELF64`, `Machine: Advanced Micro Devices X86-64` 등 실제 값을 확인한다.

**2) 문제 설명과 실제 값을 나란히 표로 정리**
| 항목 | 문제 설명 | 실제 확인 |
|---|---|---|
| 형식 | Windows PE | ELF |
| 비트 | 32bit | 64bit |
| 보호기법 | 없음 | Canary+PIE |

표로 정리해두면 "설명이 틀린 부분"과 "설명이 맞는 부분"을 헷갈리지 않고 관리할 수 있다.

**3) 배포된 파일이 여러 개인지 재확인**
```bash
ls -la ./
file ./*
```
zip에 여러 바이너리가 섞여 있었다면, 문제 설명이 가리키는 게 어느 파일인지 다시 판단한다. 서버 실행용과 로컬 분석용 파일이 다를 수 있다(예: `chall`은 배포용 stripped, `chall_debug`는 심볼 포함).

**4) 그래도 판단이 안 서면 출제자/플랫폼 공지 확인**
CTF 플랫폼의 공지사항, 디스코드 채널 등에 정정 공지가 있는지 확인한다. 실전(대회)에서는 이런 정정이 흔히 올라온다.

**5) 힌트가 틀렸다는 게 확정되면, 힌트를 무시하고 실제 값을 기준으로 REV-0001(30초 트리아지)부터 다시 시작**
문제 설명에 의존한 가정(예: "32비트니까 레지스터는 EAX 기준")을 전부 실제 값(64비트면 RAX)으로 다시 세운다.

## 명령어/단축키
```bash
file ./chall
readelf -h ./chall | grep -E "Class|Machine|Type"
objdump -f ./chall.exe
checksec --file=./chall
```

## 출력 해석
- `readelf -h`의 `Class:` 필드가 `ELF32`면 32비트, `ELF64`면 64비트 — 문제 설명의 비트 수 언급과 반드시 대조한다.
- `file`이 `PE32+ executable`이라고 하면 64비트 PE(PE32+), `PE32 executable`이면 32비트 PE다. "+"의 유무가 비트폭을 가른다.
- `checksec` 결과가 문제 설명("보호기법 없음")과 다르게 `Canary: Enabled`, `PIE: Enabled`로 나온다면 힌트를 신뢰하지 말고 실제 보호기법 기준으로 분석 전략(오프셋 계산, 브레이크포인트 방식 등)을 짜야 한다.

## 흔한 실수
- 문제 설명만 보고 도구/전략(32비트용 IDA vs 64비트용, GDB 레지스터 이름 등)을 먼저 정해버려서, 나중에 실제 파일과 안 맞아 처음부터 다시 하는 것.
- "출제자가 실수할 리 없다"고 생각해서 명백한 실제 확인 결과보다 문제 설명을 우선시하는 것.
- zip 안의 여러 파일 중 엉뚱한 파일을 열어놓고 "설명이 틀렸다"고 오해하는 것 — 실제로는 파일을 잘못 골랐을 뿐인 경우가 많다.
- 힌트가 의도된 misdirection인 경우, 힌트를 완전히 무시하고 아무 단서로도 안 쓰는 것 — 오히려 "왜 이렇게 잘못 설명했을까"가 문제 풀이의 힌트일 수도 있다(예: 패킹된 걸 숨기려고 일부러 평범하다고 말한 경우).

## 막혔을 때 다음 체크
- 확장자 자체를 믿지 못하겠다면 → REV-0002 확장자를 믿으면 안 되는 이유와 실제 파일 형식 확인법.
- 파일이 아예 안 열리는 수준이라면 → REV-0332 문제 파일이 손상된 것처럼 안 열릴 때.
- 문제 설명/첨부파일에서 다른 단서를 더 찾고 싶다면 → REV-0012 문제 설명과 첨부파일에서 힌트 뽑는 방법.
- 확인 결과 패킹이 실제로 있다면 → REV-0224 패킹된 바이너리인지 의심하는 기준.

## 미니 예제
```text
문제 설명: "간단한 32bit Windows crackme입니다. 보호기법 없음."

$ file chall.exe
chall.exe: PE32+ executable (console) x86-64, for MS Windows

$ checksec --file=chall.exe
CANARY    : Enabled
```
문제 설명은 "32bit, 보호기법 없음"이라고 했지만 실제로는 `PE32+`(64비트)이고 스택 카나리도 활성화되어 있었다. 이 경우 32비트 기준 레지스터(EAX)로 분석 노트를 세우면 전부 다시 해야 하므로, 처음부터 64비트(RAX) 기준으로, 카나리 우회까지 고려해서 접근해야 한다.

## 관련 글
- REV-0002 — 확장자를 믿으면 안 되는 이유와 실제 파일 형식 확인법
- REV-0332 — 문제 파일이 손상된 것처럼 안 열릴 때
- REV-0012 — 문제 설명과 첨부파일에서 힌트 뽑는 방법
- REV-0224 — 패킹된 바이너리인지 의심하는 기준

## 출처/검증
- PE32 vs PE32+ 필드 구분(`Magic` 값 0x10b/0x20b): Microsoft PE/COFF Specification "Optional Header" 섹션 기준 (2026-09-09 검증).
- ELF `e_ident[EI_CLASS]` 필드로 32/64비트 판별: System V ABI ELF 사양 기준.
