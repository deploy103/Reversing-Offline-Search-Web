## 한 줄 요약
심하게 난독화된 코드는 "전체를 다 이해해야 한다"는 부담을 버리고 **입력에서 출력까지의 데이터 흐름 중 아주 작은 한 조각(변수 하나, 바이트 하나)만 추적하는 작업을 여러 번 반복해 쌓아가는 방식**으로 접근하면, 실제로는 명령어 하나하나를 다 읽지 않고도 검증 로직 전체를 복원할 수 있는 경우가 많다.

## 언제 검색해야 하나
- 디컴파일 코드나 어셈블리를 봤는데 변수/분기가 너무 많고 복잡해서 어디서부터 손대야 할지 막막할 때
- "이 코드 전체를 이해하기 전엔 한 발짝도 못 나간다"는 생각에 압도되어 아예 시작을 못 하고 있을 때
- 몇 번 시도했다가 복잡함에 질려서 문제를 덮어두고 다른 걸 하고 있을 때
- Control Flow Flattening, Opaque Predicate 등 알려진 난독화 기법(REV-0231, REV-0232)이 섞여 있어 코드 흐름 자체를 눈으로 따라가기 어려울 때

## 핵심 개념
이 글은 REV-0231(Control Flow Flattening), REV-0232(Opaque Predicate), REV-0233(문자열 난독화) 같은 **특정 난독화 기법을 기술적으로 해체하는 방법**을 다루지 않는다. 그런 기법들의 원리는 각 문서에서 따로 다룬다. 이 글이 다루는 것은 그보다 앞선 문제, 즉 **난독화가 여러 겹 겹쳐 있어서 심리적으로 압도당해 아예 분석을 시작하거나 계속하지 못하는 상태**를 어떻게 극복하느냐는 전략이다.

### "전부 이해해야 한다"는 착각 버리기
초보자가 난독화된 코드 앞에서 가장 먼저 하는 실수는 위에서부터 아래까지 모든 명령어의 의미를 순서대로 완벽히 이해하려는 것이다. 실제로 검증 로직을 복원하는 데 필요한 것은 **입력이 최종 비교 지점까지 어떻게 변환되는지에 대한 데이터 흐름**이지, 코드에 있는 모든 명령어의 의도를 아는 게 아니다. 난독화 기법 대부분(불투명 술어, 제어 흐름 평탄화, 죽은 코드 삽입)은 실제 데이터 흐름에는 영향을 주지 않으면서 코드 볼륨과 분기 복잡도만 늘리는 것이 목적이다. 즉 상당 부분은 애초에 "이해할 필요가 없는" 코드다.

### 쪼개서 접근하는 구체적 방법
1. **최종 비교 지점부터 거꾸로 시작한다**: 전체를 처음부터 읽지 말고, `strcmp`/`memcmp`나 최종 성공/실패 분기가 있는 지점을 먼저 찾는다(REV-0006, REV-0008). 그 지점에서 비교되는 값이 어디서 왔는지, 딱 한 단계만 거슬러 올라간다.
2. **변수 하나만 계속 추적한다**: 한 번에 전체 로직을 이해하려 하지 말고, 최종 비교값에 영향을 준 변수 하나를 정하고 그 변수가 어디서 만들어졌는지(대입문, 함수 호출 반환값)만 계속 거슬러 올라간다. IDA/Ghidra에서 변수 위에 커서를 놓고 우클릭 → Jump to xref, 또는 변수 이름 더블클릭으로 정의 위치를 빠르게 오갈 수 있다.
3. **동적으로 실제 값을 찍어본다**: 정적으로 눈으로 따라가는 게 너무 느리면, 그 변수가 쓰이는 지점에 브레이크포인트를 걸고 실제 실행 중 값이 어떻게 바뀌는지 관찰한다(REV-0005). 난독화된 코드라도 실제 실행 값은 난독화되지 않은 진짜 값이므로, 동적 관찰이 정적으로 코드를 읽는 것보다 훨씬 빠를 때가 많다.
4. **이해한 조각을 노트에 누적한다**: "변수 A는 입력의 3번째 바이트에서 왔고, 어떤 함수를 거쳐 변수 B가 됐다"처럼 작은 조각을 확인할 때마다 REV-0014 방식의 노트에 바로바로 적는다. 조각들이 쌓이면 어느 순간 전체 그림이 이어진다 — 처음부터 전체 그림을 그리려 하지 않는다.
5. **막힌 조각은 건너뛰고 다른 조각으로 옮긴다**: 하나의 변수 추적이 막히면(예: 함수가 재귀적이거나 너무 복잡함) 그 조각에 매몰되지 말고, 다른 조각(다른 변수, 다른 비교 지점)으로 옮겨서 진행률을 유지한다. 나중에 다른 조각에서 얻은 정보가 막혔던 조각을 이해하는 데 도움이 되는 경우가 많다.

### 심리적으로 포기하지 않는 방법
막막함은 대부분 "얼마나 더 해야 끝나는지 모르는 상태"에서 온다. 위 방식대로 작은 조각을 하나씩 확인하고 노트에 기록하면, 눈에 보이는 진행률(확인된 조각 개수)이 생기기 때문에 "전혀 진전이 없다"는 느낌 자체를 줄일 수 있다. 또한 REV-0310으로 애초에 "이 문제는 시간이 오래 걸린다"고 예상하고 시작했다면, 복잡한 코드를 보고 놀라는 대신 예상대로라고 받아들이기가 더 쉽다.

## 화면/코드에서 보이는 징후
- 함수 하나의 그래프 뷰(IDA Graph view)가 노드와 화살표로 가득 차서 한 화면에 안 들어온다.
- 같은 값을 여러 번 재대입하거나, 의미 없어 보이는 산술 연산(더했다가 다시 빼는 등)이 반복된다.
- 조건 분기가 실제로는 항상 같은 방향으로만 가는 것 같은데(불투명 술어 의심) 이유를 알 수 없다.
- 변수 이름이 전부 `v1`, `v2`, `v3`처럼 의미 없이 나열되어 있고 개수가 수십 개다.

## 가장 먼저 할 것
전체 코드를 위에서부터 읽으려는 시도를 멈춘다. 대신 최종 성공/실패 분기(`strcmp`, `memcmp`, 또는 flag 출력 직전 조건문)를 먼저 찾아서 그 지점부터 시작한다.

## 단계별 절차
1. 최종 비교/성공 분기 지점을 먼저 찾는다(REV-0006, REV-0008)
2. 그 지점에서 비교되는 변수 하나를 정한다
3. 그 변수가 어디서 정의됐는지 딱 한 단계만 거슬러 올라간다(정적으로 xref 확인 또는 동적으로 브레이크포인트)
4. 확인한 조각을 노트에 즉시 기록한다(REV-0014)
5. 다음 변수로 넘어가 같은 방식을 반복한다
6. 한 조각이 너무 오래 걸리면 표시만 해두고 다른 조각으로 넘어간다
7. 조각이 충분히 쌓이면(보통 전체 흐름의 60~70% 정도) 전체 그림을 다시 노트에서 정리해본다
8. 남은 빈 조각을 채우며 전체 로직을 완성한다

## 명령어/단축키
- IDA: 변수/함수 이름 위에서 `X`(xref 확인), 그래프 뷰에서 `Space`(그래프/텍스트 뷰 전환), `Ctrl+마우스휠`(그래프 확대/축소)
- GDB: 특정 지점에서 `watch 변수` 또는 `break *주소` 후 `print 변수`로 동적 값 확인
- 노트: 조각 단위 기록 템플릿 예시 — `[변수명] = [값/출처] (확인 방법: 정적/동적, 확실함/가설)`

## 출력 해석
- 동적으로 확인한 실제 값이 정적 코드에서 예상한 것과 다르다면, 정적으로 읽은 부분에 난독화 트릭(불투명 술어, 죽은 코드)이 섞여 있었다는 신호다 — 그 부분은 무시하고 실제 값 기준으로 계속 진행한다.
- 조각들을 이어봤는데 전체 흐름이 앞뒤가 안 맞으면, 중간에 놓친 조각(다른 함수를 거치는 경로)이 있다는 뜻이므로 그 구간만 다시 추적한다.

## 흔한 실수
- 여전히 전체 코드를 순서대로 다 이해하려고 시도하다가 같은 화면에서 몇 시간째 멈춰 있는 것.
- 막힌 조각 하나에 매몰되어 다른 쉬운 조각으로 옮기지 않는 것 — 진행률이 0으로 느껴져 포기하고 싶어지는 주된 원인이다.
- 확인한 조각을 노트에 기록하지 않아서, 나중에 이미 확인했던 걸 또 확인하는 것.
- 정적으로만 계속 씨름하고 동적 검증(실제 값 찍어보기)으로 전환하지 않는 것 — 난독화된 코드일수록 동적 관찰이 훨씬 빠른 지름길이 되는 경우가 많다.

## 막혔을 때 다음 체크
- 어떤 난독화 기법인지 구체적으로 알아야 다음을 진행할 수 있다 → REV-0231 Control Flow Flattening 기초, REV-0232 Opaque Predicate 기초, REV-0233 문자열 난독화가 보일 때
- 정적 분석 자체가 안 통해서 동적으로 전환해야 한다 → REV-0005 문제를 정적 분석부터 할지 동적 분석부터 할지 결정하는 법, REV-0241 패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환
- 노트 작성 방식 자체가 익숙하지 않다 → REV-0014 리버싱 노트 작성법: 함수 이름 바꾸기와 가설 기록
- 이 문제가 원래 시간이 오래 걸리는 게 맞는지 재확인하고 싶다 → REV-0310 리버싱 문제 난이도를 빠르게 가늠하는 체크포인트

## 미니 예제
그래프 뷰가 노드 80개로 가득 찬 함수를 마주쳤다. 전체를 읽는 대신 함수 끝의 `return v12 == 0x4C2A;` 한 줄만 찾아서 시작했다. `v12`가 어디서 왔는지 한 단계 거슬러 올라가니 `v12 = v9 ^ v3;`이었고, 다시 `v9`와 `v3`을 각각 추적했다. `v3`은 단순히 입력 버퍼의 2번째 바이트였고, `v9`는 또 다른 변수 세 개를 거쳐 계산된 값이었다. 이런 식으로 6번 정도 "한 단계씩 거슬러 올라가기"를 반복하니, 실제로 읽어야 했던 코드는 전체 80개 노드 중 12개 정도뿐이었다 — 나머지 68개는 그 변수들과 무관한 죽은 코드/불투명 술어였다.
