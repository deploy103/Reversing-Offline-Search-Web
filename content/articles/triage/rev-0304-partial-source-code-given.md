## 한 줄 요약
소스코드 일부가 제공되면 그 코드를 **컴파일된 바이너리와 1:1로 대조하는 지도**로 활용해서, 소스에 없는 나머지 부분(주로 검증 로직)을 훨씬 빠르게 좁혀 들어갈 수 있다.

## 언제 검색해야 하나
- 첨부파일에 바이너리와 함께 `.c`, `.py`, `.cpp` 소스 파일 일부가 같이 제공될 때
- 제공된 소스에 핵심 검증 함수 본문이 없고 함수 선언(프로토타입)이나 헤더만 있을 때
- 소스코드와 바이너리를 어떻게 연결해서 봐야 할지, 그냥 소스만 읽고 끝내도 되는 건지 헷갈릴 때

## 핵심 개념
CTF에서 소스코드 일부를 주는 이유는 대체로 두 가지다.

1. **문제 구조를 이해시키기 위해**: 입력 파싱, 자료구조 정의(`struct`), 메인 루프처럼 "이 프로그램이 무엇을 하는지"의 뼈대를 소스로 주고, 실제 검증 알고리즘이나 취약점이 있는 함수 하나만 비공개로 컴파일해 감춘다.
2. **빌드 방식/환경을 알려주기 위해**: `Makefile`, `CMakeLists.txt`, 컴파일 플래그(`-O2`, `-fno-stack-protector` 등)를 알려줘서 어떤 최적화가 적용됐는지, 어떤 보호 기법이 켜져 있는지 미리 알 수 있게 한다.

소스가 일부만 있어도 매우 유용한 이유는, 소스에 있는 **구조체 정의, 상수 이름(매크로/enum), 함수 시그니처(인자 개수와 타입)**를 그대로 IDA/Ghidra의 타입 정보로 가져다 쓸 수 있기 때문이다. 디컴파일러가 추측한 애매한 타입(`int64_t`, `void*`)보다 실제 소스의 타입(`struct Player { int hp; int level; }`)을 알고 보면 디컴파일 결과가 훨씬 명확해진다.

또한 소스에 있는 함수와 바이너리의 함수를 **이름/호출 순서/상수 리터럴**로 대조하면, strip된 바이너리에서도 어떤 함수가 소스의 어떤 함수에 대응하는지 빠르게 찾을 수 있다. 예를 들어 소스에 `check_password()`가 있고 그 안에 `0xDEADBEEF` 상수가 있다면, 바이너리에서 이 상수를 문자열/상수 검색으로 찾아 대응 함수 위치를 즉시 특정할 수 있다.

## 화면/코드에서 보이는 징후
- 첨부파일에 `main.c`는 있는데 `check.c`나 `verify.c`는 없고, `Makefile`에서만 그 파일 이름이 언급된다.
- 제공된 헤더 파일(`.h`)에 구조체나 매크로 정의는 있는데 함수 구현부(`.c`)는 없다.
- 소스에 있는 함수 이름이 컴파일된 바이너리의 심볼 테이블에도 그대로 남아 있어(strip 안 됨) 바로 대조가 가능하다.

## 가장 먼저 할 것
제공된 소스 전체를 한 번 읽으면서, 어떤 함수가 **정의(구현)**되어 있고 어떤 함수가 **선언(프로토타입)**만 있는지 표시한다. 선언만 있는 함수가 바로 바이너리 쪽에서 찾아야 할 대상이다.

## 단계별 절차

**1) 소스 읽고 구현 여부 표시**
```c
// main.c (제공됨)
int check_flag(const char *input);  // 선언만 있음 -> 구현은 바이너리에만 존재

int main(int argc, char **argv) {
    if (argc != 2) { puts("usage: ./chall <flag>"); return 1; }
    if (check_flag(argv[1])) puts("Correct!");
    else puts("Wrong!");
    return 0;
}
```
이 예시에서 `check_flag`가 실제로 분석해야 할 대상임이 소스만 읽어도 명확해진다.

**2) 구조체/매크로/상수를 IDA·Ghidra 타입으로 그대로 적용**
소스에 `struct Player { int hp; int level; char name[16]; };`가 있으면, IDA의 Local Types(Shift+F1 → Insert) 또는 Ghidra의 Data Type Manager에 동일한 구조체를 직접 만들어 등록한다. 이후 디컴파일 결과에서 해당 구조체 포인터에 이 타입을 적용(우클릭 → "Set type"/`Y` 단축키, Ghidra는 `Retype Variable`)하면 필드 접근이 `*(int*)(ptr+4)` 대신 `ptr->level`처럼 그대로 읽힌다.

**3) 상수 리터럴로 대응 함수 찾기**
소스에 있는 특이한 상수(매직 넘버, 배열 초기값)를 IDA의 상수 검색(Search → Immediate Value) 또는 `grep`으로 바이너리에서 찾는다.
```bash
objdump -d ./chall | grep -i "deadbeef"
```
매칭되는 위치가 바로 소스의 해당 함수가 컴파일된 지점이다.

**4) 호출 순서로 함수 매핑**
소스의 `main`에서 호출 순서(`parse_input()` → `check_flag()` → `print_result()`)를 그대로 바이너리 `main`의 호출 순서와 대조한다. strip된 바이너리라도 호출 순서와 인자 개수는 소스와 동일하므로, `sub_401200`, `sub_4013A0` 같은 이름 없는 함수들에 소스 이름 그대로 리네임(`N` 단축키)할 수 있다.

**5) 소스에 없는 부분만 집중 분석**
1~4단계로 매핑이 끝나면, 이제 소스에 구현이 없는 함수(`check_flag` 등)만 IDA/Ghidra F5 디컴파일로 집중 분석한다. 나머지 함수(`parse_input`, `print_result`)는 이미 소스를 봤으므로 다시 분석할 필요가 없다.

**6) 컴파일 플래그로 최적화/보호기법 미리 파악**
`Makefile`에 `-O2`가 있으면 디컴파일 결과에 루프 언롤링, 인라이닝이 많이 나타날 것을 미리 예상하고 접근한다. `-fstack-protector`가 있으면 스택 카나리 관련 코드가 섞여도 놀라지 않는다.

## 명령어/단축키
```bash
cat Makefile
grep -n "^[a-zA-Z].*(.*);" *.h        # 선언만 있는 함수 프로토타입 찾기
objdump -d ./chall | grep -i <상수값>
```
IDA: Shift+F1(Local Types 추가), `Y`(타입 지정), `N`(리네임), Search → Immediate Value(상수 검색).
Ghidra: Data Type Manager에서 구조체 생성, `Retype Variable`, Search → For Scalars(상수 검색).

## 출력 해석
- 소스의 구조체 크기와 바이너리에서 실제로 할당되는 메모리 크기(`malloc(sizeof(struct Player))` 호출의 인자값)가 일치하면 구조체 정의가 정확하다는 검증이 된다. 크기가 다르면 컴파일러가 패딩을 추가했거나 구조체 정의 자체가 문제와 다른 버전일 수 있다.
- 상수 검색으로 찾은 함수 주소가 소스에서 예상한 호출 순서와 다른 위치에 있다면, 컴파일러가 함수를 인라인했거나 순서를 재배치했을 가능성이 있다 — 이 경우 어셈블리 원문에서 직접 흐름을 재확인한다.

## 흔한 실수
- 제공된 소스만 읽고 "이해했다"고 착각한 뒤, 정작 바이너리에만 있는 핵심 함수(`check_flag`)를 분석하지 않고 넘어가는 것.
- 소스의 구조체 정의를 IDA/Ghidra에 등록하지 않고 디컴파일 결과의 raw 포인터 연산을 손으로 계속 환산하며 시간을 낭비하는 것.
- 소스와 바이너리의 컴파일러/최적화 버전이 다를 수 있다는 점을 무시하고, 소스 그대로의 라인 순서가 바이너리 어셈블리 순서와 완전히 같을 거라 가정하는 것.
- 헤더 파일에 있는 매크로 상수(`#define MAX_LEN 64`)를 무시하고 바이너리에서 나온 리터럴 상수를 다른 의미로 오해하는 것.

## 막혔을 때 다음 체크
- 소스와 바이너리 함수 이름이 대조가 안 될 정도로 다르다 → REV-0011 디컴파일 코드가 이상할 때 어셈블리로 돌아가는 기준에서 디컴파일 결과 자체를 재검증하는 절차 참고
- 소스만으로 이해했는데 정작 실행 흐름 추적이 막힌다 → REV-0007 입력 함수부터 역추적하는 방법
- 소스 없이 처음부터 리버싱해야 하는 상황과 헷갈린다 → REV-0018 대회장에서 리버싱 문제 하나를 끝까지 추적하는 실전 루틴

## 미니 예제
첨부파일: `chall`(바이너리, strip됨), `main.c`(일부 소스), `vm.h`(구조체 정의).

1. `main.c` 확인 → `int run_vm(struct VM *vm);` 선언만 있고 구현 없음. `vm.h`에 `struct VM { uint8_t *code; int pc; int regs[4]; };` 정의 발견.
2. Ghidra Data Type Manager에 동일한 `VM` 구조체 생성.
3. `main`에서 `run_vm(&vm)` 호출부를 strip된 바이너리에서 대조 → 호출되는 `FUN_00101450`이 `run_vm`에 대응한다고 확정, 리네임.
4. `FUN_00101450`의 첫 인자 포인터에 `VM*` 타입 적용 → 디컴파일 결과가 `vm->pc`, `vm->regs[i]`처럼 바로 읽히게 됨.
5. 이제 남은 작업은 `run_vm`(바이트코드 인터프리터) 로직만 분석하면 되므로, `main`과 입력 파싱 부분은 소스로 이미 끝났다고 보고 건너뛴다.

## 관련 글
- REV-0011 — 디컴파일 코드가 이상할 때 어셈블리로 돌아가는 기준
- REV-0007 — 입력 함수부터 역추적하는 방법
- REV-0018 — 대회장에서 리버싱 문제 하나를 끝까지 추적하는 실전 루틴
