## 한 줄 요약
`CTF{...}` 형식 자체는 맞는데 서버가 계속 오답 처리한다면, 눈에 보이는 형식이 아니라 **눈에 안 보이는 바이트**(끝의 개행/공백, 잘못 복사된 널바이트, 대소문자, 유니코드 유사 문자, 자릿수 하나의 오차) 중 하나가 원인일 확률이 매우 높으므로 "형식이 맞다"는 확신을 버리고 바이트 단위로 다시 검증해야 한다.

## 언제 검색해야 하나
- 리버싱으로 복원한 값을 `CTF{...}`로 감싸서 제출했는데 채점 서버가 계속 틀렸다고 할 때
- 로컬 바이너리를 직접 실행해서 복원한 flag를 넣었더니 `Correct!`가 나왔는데, 같은 값을 채점 서버 제출란에 넣으면 거부될 때
- 브루트포스/역산으로 flag 후보를 여러 개 얻었는데 어떤 게 진짜인지 판단이 안 설 때
- flag 문자열을 터미널에서 복사해서 붙여넣기(copy-paste)했는데 이상하게 안 먹힐 때

## 핵심 개념

### "형식이 맞다"와 "바이트가 정확히 같다"는 다르다
`CTF{some_flag_here}`처럼 겉보기 형식(중괄호, 접두사)이 맞아 보여도, 채점 서버는 **문자 하나하나를 정확히 비교**한다. 사람 눈에는 안 보이거나 무시하기 쉬운 다음과 같은 차이가 실제로는 전혀 다른 문자열을 만든다.

- **끝에 붙은 개행/공백**: `print(flag)`로 출력한 값을 터미널에서 그대로 드래그해서 복사하면 마지막에 개행 문자(`\n`)나 캐리지리턴(`\r`)이 함께 복사되는 경우가 있다. 화면상으로는 티가 안 난다.
- **파이썬 바이트 리터럴 표기 그대로 복사**: `print(flag_bytes)`의 출력이 `b'CTF{abc}'`처럼 나왔는데, 앞의 `b'`와 뒤의 `'`까지 통째로 복사해서 제출하는 실수. 반드시 `.decode()`하거나 `print(flag_bytes.decode())`로 순수 문자열만 뽑아야 한다.
- **널 바이트(`\x00`) 조기 종료**: C 문자열은 `\x00`을 만나면 그 지점에서 끝난 것으로 취급한다. 복원 로직이 8바이트를 계산했는데 그중 한 바이트가 우연히 `0x00`이면, 바이너리 자체는 그 지점까지만 비교하고 "Correct"를 내보낼 수 있지만, 채점 서버가 원본 평문 문자열과 완전히 일치하는지(널바이트 이후 내용까지) 별도로 확인하는 방식이라면 실패할 수 있다.
- **대소문자**: `ctf{...}`와 `CTF{...}`는 다른 문자열이다. XOR/시저 암호 계열 역산에서 알파벳 대소문자를 놓치기 쉽다.
- **유사 문자(look-alike characters)**: 대문자 `O`와 숫자 `0`, 소문자 `l`(엘)과 숫자 `1`과 대문자 `I`, 언더스코어(`_`)와 하이픈(`-`)을 폰트 상에서 구분 못 하고 잘못 옮겨 적는 경우. 특히 PDF로 된 문제 설명이나 스크린샷에서 값을 손으로 옮겨 적을 때 자주 발생한다.
- **복사-붙여넣기 중 유니코드 치환**: 일부 편집기/브라우저가 따옴표나 하이픈을 "스마트 문자"(예: 유니코드 `‘`, `’`, `—`)로 자동 변환해서 겉보기엔 똑같아 보이지만 실제 바이트는 다른 문자가 되는 경우.

### 해가 하나가 아닐 수 있다(역산의 비유일성)
XOR, 모듈러 연산, 정보 손실이 있는 압축/해시 기반 역산에서는 "그럴듯해 보이는" flag 후보가 여러 개 나올 수 있다. 예를 들어 키 길이를 잘못 가정하고 역산했는데 우연히 사람이 읽을 수 있는 문자열이 나왔다면, 그건 진짜 flag가 아니라 우연의 일치(false positive)일 수 있다. 이 경우 **로컬 바이너리로 직접 검증**하는 과정을 반드시 거쳐야 한다.

### 로컬 검증과 서버 제출은 다른 검사일 수 있다
일부 CTF 문제는 바이너리 자체의 `Correct!` 출력과, 채점 웹사이트가 flag를 인정하는 기준이 서로 다르게 구현되어 있을 수 있다(예: 채점 사이트가 대소문자를 구분하지 않게 만들어졌거나, 반대로 바이너리는 관대한데 채점 사이트는 엄격한 정규식을 쓰는 경우). 이 경우는 출제 실수(버그)일 가능성도 있으므로, 모든 자체 검증을 마쳤는데도 실패한다면 대회 운영진에게 문의하는 것도 정당한 다음 단계다.

## 화면/코드에서 보이는 징후
- 바이너리 직접 실행 시 `Correct!`가 나오는데 채점 서버는 거부.
- 복원한 값을 `print()`로 출력했을 때 눈으로 보기엔 문제없어 보임.
- flag 후보를 여러 번 다르게 만들어봤는데(브루트포스 키 길이 등을 바꿔가며) 매번 그럴듯한 문자열이 나옴 — 진짜인지 확신이 없음.
- 복사한 값을 터미널에 붙여넣었을 때 커서 위치가 예상과 다르게 움직이거나, `wc -c`로 길이를 재보면 예상 글자 수보다 1~2글자 더 많음.

## 가장 먼저 할 것
제출하기 전에 flag 후보를 **파일로 저장하고 `xxd`/`hexdump`로 바이트 단위로 확인**한다. 눈으로 읽는 문자열과 실제 바이트 열이 정확히 일치하는지, 끝에 개행이나 공백이 붙어있지 않은지부터 확인하는 것이 가장 빠르고 확실한 첫 단계다.

## 단계별 절차

**1) flag 후보를 파일로 저장 후 바이트 단위 확인**
```bash
printf '%s' 'CTF{recovered_flag_here}' > flag_candidate.txt
xxd flag_candidate.txt
```
`xxd` 결과 끝에 `0a`(개행)나 `20`(공백)이 의도치 않게 붙어있지 않은지 확인한다. `printf`는 `echo`와 달리 기본적으로 개행을 추가하지 않으므로 저장 시점부터 깨끗한 값을 만드는 데 유리하다.

**2) 파이썬에서 만든 값이면 repr()로 진짜 내용 확인**
```python
print(repr(flag))
```
`repr()`은 눈에 안 보이는 문자(`\n`, `\r`, `\x00`)까지 이스케이프해서 그대로 보여주므로, `print(flag)`만으로는 못 보는 문제를 여기서 바로 잡아낸다.

**3) 로컬 바이너리로 반드시 재검증**
```bash
python3 -c "print('CTF{recovered_flag_here}', end='')" | ./chall
```
`echo`가 아니라 `printf`/파이썬 `end=''`를 써서 개행을 추가하지 않고 정확히 그 바이트만 전달했을 때도 `Correct!`가 나오는지 확인한다. 만약 개행을 붙였을 때만 성공하고 안 붙이면 실패한다면(또는 반대라면), 서버 채점 방식이 개행 포함 여부에 민감하다는 뜻이니 그 형태 그대로 제출한다.

**4) 대소문자/유사 문자 하나하나 대조**
```bash
diff <(echo -n 'CTF{recovered_flag_here}') <(echo -n 'CTF{expected_something}')
```
확신이 서는 정답 후보가 여러 개라면 `diff`로 바이트 단위 차이를 명확히 뽑아본다.

**5) 채점 폼에 붙여넣기 전 최종 확인**
채점 폼(웹 입력창)에 붙여넣은 뒤 **제출 전에 다시 한 번 그 입력창의 내용을 전체 선택해서 복사, 로컬에서 `xxd`로 비교**한다. 브라우저나 입력창의 자동 완성/자동 수정 기능이 문자를 바꿔치기했을 가능성까지 배제하기 위함이다.

**6) 그래도 안 되면 역산 로직 자체를 재검토**
1~5단계를 다 거쳐도 계속 실패한다면, 복원 로직 자체가 우연히 그럴듯한 값을 만들어낸 것일 수 있다(비유일 해). 검증 로직을 처음부터 다시 손으로 계산해보거나, 다른 키 길이/다른 해석으로 역산을 재시도한다.

## 명령어/단축키
```bash
printf '%s' 'flag내용' > flag_candidate.txt
xxd flag_candidate.txt
wc -c flag_candidate.txt
diff <(printf '%s' 'A') <(printf '%s' 'B')
```
```python
print(repr(flag))          # 눈에 안 보이는 문자까지 표시
flag.decode()               # bytes를 순수 문자열로
flag.strip()                 # 앞뒤 공백/개행 제거 후 재검증(단, 이게 원인이었는지 먼저 확인)
```

## 출력 해석
- `xxd` 결과 마지막 바이트가 `0a`(`\n`)면 개행이 포함된 것이다. 채점 서버가 정확히 일치를 요구한다면 이 개행 유무가 성공/실패를 가른다.
- `wc -c`로 잰 길이가 눈으로 센 글자 수보다 많다면 숨은 문자(개행, 공백, 널바이트가 아닌 다른 바이트)가 끼어있다는 뜻이다.
- `repr()` 출력에 `\x00`이 보이면 널바이트가 문자열 중간에 있다는 뜻이며, C 문자열 비교 함수(`strcmp`)를 통과한 로컬 검증과 원본 바이트 비교를 하는 채점 서버 사이에 결과가 갈릴 수 있는 대표적 원인이다.

## 흔한 실수
- `print(flag_bytes)`의 파이썬 출력(`b'...'` 형태)을 그대로 복사해서 앞뒤 `b'`, `'`까지 제출하는 것.
- flag 후보가 "사람이 읽기에 그럴듯하다"는 이유만으로 검증 없이 곧바로 제출하는 것 — 반드시 로컬 바이너리로 먼저 확인한다.
- 대소문자 구분을 놓치고 알파벳을 전부 소문자/대문자로 통일해서 제출하는 것.
- 유사 문자(`O`/`0`, `l`/`1`/`I`, `_`/`-`)를 손으로 옮겨 적다가 잘못 옮기는 것 — 가능하면 항상 복사/붙여넣기나 스크립트 출력을 그대로 쓰고 손으로 재입력하지 않는다.
- 서버가 알람 타이머(REV-0338)로 이미 연결을 끊었는데 그 사실을 못 알아채고 "flag가 틀렸나?"라고 착각하는 것 — 응답 메시지를 정확히 읽어서 "오답"과 "연결 끊김"을 구분해야 한다.

## 막혔을 때 다음 체크
- 애초에 서버가 응답을 제대로 주는지조차 불확실하다면 → REV-0338(서버 문제에서 타임아웃이 계속 발생할 때)
- 로컬에서는 성공하는데 서버 자체가 다른 동작을 한다면 → REV-0340(로컬에서는 성공하는데 서버에서는 실패할 때)
- 역산 로직 자체가 맞는지 처음부터 재검토하려면 → REV-0017(솔버 작성 전 로직 복원)

## 미니 예제
```bash
$ python3 -c "print(repr('CTF{recovered_flag_here}\n'))"
'CTF{recovered_flag_here}\n'
```
`repr()`로 확인하니 끝에 `\n`이 포함되어 있었다. 원인은 `input()`으로 받은 값이 아니라, 파일에서 `readline()`으로 읽은 값을 그대로 flag로 썼기 때문이었다. `.strip()`으로 제거 후 재제출.
```bash
$ printf '%s' "$(python3 -c "print('CTF{recovered_flag_here}', end='')")" | ./chall
Correct!
```
개행 없이 정확한 바이트만 전달하자 로컬 바이너리도 `Correct!`를 반환했고, 같은 정제된 값을 채점 서버에 제출하니 정상적으로 인정되었다.

## 출처/검증
- C 문자열의 널바이트(`\x00`) 종료 규칙과 `strcmp` 계열 비교 동작: ISO C 표준(C11) 7.24 "String handling" 기준.
- 파이썬 `repr()`이 비출력 문자를 이스케이프해서 표시하는 동작: Python 공식 문서(docs.python.org) `repr()`/문자열 표현 섹션 기준.
- 유니코드 유사 문자(호모글리프) 및 스마트 따옴표 자동 치환으로 인한 텍스트 불일치 문제: Unicode Consortium의 호모글리프 관련 일반 설명 및 일반적인 텍스트 편집기 자동 수정 동작 기준 (2026-09-09 확인).
