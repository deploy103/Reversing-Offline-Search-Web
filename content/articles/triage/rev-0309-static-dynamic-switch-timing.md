## 한 줄 요약
정적분석과 동적분석은 처음에 한 번 선택하고 끝나는 것이 아니라 **분석 도중 특정 신호가 나타날 때마다 서로 전환해야 하는 반복 과정**이며, "값을 예측할 수 없어졌다"는 신호가 뜨면 동적으로, "너무 많은 지점을 일일이 실행해서 봐야 한다"는 신호가 뜨면 다시 정적으로 돌아가는 것이 기본 판단 기준이다.

## 언제 검색해야 하나
- 정적분석(IDA/Ghidra F5 디컴파일)만 계속 읽고 있는데 진전이 없어서 디버거를 켜야 할지 판단이 안 설 때
- 반대로 디버거로 브레이크포인트를 걸고 스텝을 반복하고 있는데 이게 맞는 방향인지, 다시 정적분석으로 돌아가야 하는지 헷갈릴 때
- REV-0005(처음에 정적/동적 중 무엇부터 할지)는 이미 알고 있지만, 분석 "도중에" 전환하는 타이밍을 구체적으로 알고 싶을 때

## 핵심 개념
REV-0005가 "문제를 처음 받았을 때 정적부터 할지 동적부터 할지"를 다룬다면, 이 문서는 **이미 한쪽으로 진행 중인 분석을 언제 다른 쪽으로 전환해야 하는가**를 다룬다. 실전 리버싱은 정적 → 동적 → 정적 → 동적을 여러 번 오가는 것이 정상이며, 전환 타이밍을 놓치면 한쪽 방법으로 무한정 시간을 쓰게 된다.

### 정적 → 동적 전환 신호
1. **값이 실행 시점에만 결정된다**: 난수(`rand`, `GetTickCount`), 시스템 시각, 사용자 입력, 환경변수, 네트워크 응답에 의존하는 변수가 비교에 쓰이면 정적으로는 그 값을 알 수 없다. 디컴파일 코드에서 "이 변수의 실제 값이 뭔지 소스만 봐서는 확정할 수 없다"고 느껴지면 전환 신호다.
2. **디컴파일 결과가 상식적으로 안 읽힌다**: SIMD 명령어(`__m128i`), 매크로 범벅(`HIDWORD`, `LOBYTE`), 인라인 어셈블리가 섞여 의사코드가 실제 로직보다 더 복잡해 보이면, 직접 실행해서 레지스터 값 변화를 관찰하는 게 더 빠를 수 있다.
3. **안티디버깅/자기수정 코드가 의심된다**: 코드가 실행 중 자기 자신을 변경하는 패턴(패커, 언패킹 스텁)이 보이면 정적 디스어셈블리 자체가 진짜 실행될 코드와 다를 수 있다. 이 경우 실행 후 메모리 덤프로 실제 코드를 봐야 한다.
4. **간접 호출/분기의 목적지를 정적으로 못 구한다**: `call rax`, `jmp [rbx+rcx*8]`처럼 레지스터/테이블 기반 간접 호출은 정적으로 목적지를 특정하기 어려운 경우가 많다(가상함수 테이블, 점프 테이블, VM 디스패치). 실행시켜 실제 목적지를 관찰하는 것이 빠르다.
5. **가설을 세운 지 오래됐는데 검증을 안 했다**: "아마 이 변수가 이 값이면 성공일 것"이라는 가설을 5분 이상 정적으로만 곱씹고 있다면, 그 시점이 디버거를 켜서 실제로 확인해볼 때다.

### 동적 → 정적 전환 신호
1. **스텝을 너무 많이 반복하고 있다**: F7/F8(스텝 인투/오버)을 수십 번 눌러도 끝이 안 보이는 루프(예: 긴 반복 암호화 루프, 대량 데이터 처리)에 갇혀 있다면, 스텝 대신 정적으로 루프 구조 전체를 한눈에 보는 게 낫다.
2. **전체 구조를 다시 봐야 할 필요가 생겼다**: 디버깅 중 새로운 함수 호출(이전에 정적분석에서 못 봤던 함수)을 발견하면, 그 함수의 전체 그림(다른 곳에서도 호출되는지, xref가 몇 개인지)은 정적분석 도구에서 보는 게 빠르다.
3. **값 하나는 확인했지만 "왜 그 값인지" 로직을 봐야 한다**: 디버거는 "지금 이 값이 무엇이다"는 보여주지만 "왜 그 계산 결과가 나왔는지" 전체 수식은 정적 디컴파일에서 한 번에 읽는 게 더 명확하다.
4. **반복 실행 비용이 커졌다**: 매번 프로그램을 처음부터 실행하고 여러 단계를 거쳐 관심 지점까지 도달해야 한다면(느린 초기화, 사용자 입력 여러 번 등), 그 지점까지의 로직을 정적으로 미리 파악해서 브레이크포인트 개수를 줄이는 게 효율적이다.

### 전환 판단을 빠르게 하는 요령
분석 중 스스로에게 "지금 내가 궁금한 것이 **구조(어떻게 연결되어 있는가)**인가 **값(지금 무엇인가)**인가"를 묻는다. 구조가 궁금하면 정적, 값이 궁금하면 동적이다. 이 질문 하나로 대부분의 전환 타이밍을 즉시 판단할 수 있다.

## 화면/코드에서 보이는 징후
- IDA/Ghidra 디컴파일 결과에 `time(NULL)`, `rand()`, `GetTickCount()` 같은 호출이 비교 로직 근처에 있다.
- 디스어셈블리에 `call rax`, `jmp qword ptr [rdx+rcx*8]` 같은 간접 호출/점프가 있고 정적으로 목적지를 못 구한다.
- x64dbg/GDB에서 같은 루프 안을 F8/`next`로 수십 번째 반복하고 있는데 아직 루프가 안 끝났다.
- 디버깅 중 브레이크포인트에 도달하려면 매번 3~4단계의 사용자 입력을 다시 해야 해서 반복 실행이 번거롭다.

## 가장 먼저 할 것
지금 하고 있는 작업이 "코드를 읽고 있는지"(정적) "실행시켜 보고 있는지"(동적) 스스로 인지한다. 그리고 위의 전환 신호 목록과 지금 상황을 1분 안에 대조해본다.

## 단계별 절차

**1) 현재 막힌 지점의 성격 파악**
"이 변수/분기의 실제 값을 모른다"인지 "이 코드 전체가 어떻게 연결되는지 모른다"인지 구분한다.

**2) 값을 모르는 경우 — 동적분석으로 전환**
해당 지점 직전에 브레이크포인트를 걸고(IDA+x64dbg는 REV-0306, Ghidra+GDB는 REV-0307 절차 참고), 실행해서 실제 값을 확인한다. 이때 전체 프로그램을 처음부터 다시 이해하려 하지 말고, **딱 그 값 하나**를 확인하는 데만 집중한다.

**3) 구조를 모르는 경우 — 정적분석으로 전환**
디버거를 잠시 멈추거나 종료하고, IDA/Ghidra에서 새로 발견한 함수의 xref, 콜그래프(IDA: View → Graphs → Function Calls, Ghidra: Function Call Graph)를 확인한다. 이 함수가 다른 곳에서도 호출되는지, 전체 프로그램에서 어떤 역할인지 지도를 다시 그린다.

**4) 루프에 갇혔을 때 — 조건부 브레이크포인트로 탈출**
동적분석 중 긴 루프에서 스텝을 반복하고 있다면, 무작정 F8을 누르지 말고 루프 종료 직후 지점에 브레이크포인트를 걸고 F9(실행)로 한 번에 건너뛴다. 특정 조건에서만 멈추고 싶다면 조건부 브레이크포인트(x64dbg: 브레이크포인트 우클릭 → Edit → Condition 설정, GDB: `break <위치> if <조건식>`)를 사용해서 반복 횟수를 줄인다.

**5) 자기수정 코드/패킹이 의심될 때 — 실행 후 메모리 덤프로 전환**
정적 디스어셈블리가 신뢰할 수 없다고 판단되면, 실제로 실행시켜 언패킹이 끝난 시점(예: OEP, Original Entry Point 도달)에서 메모리를 덤프하고 그 덤프를 다시 정적분석 도구로 연다. 이렇게 "동적으로 실제 코드를 확보한 뒤 다시 정적분석"하는 것도 흔한 전환 패턴이다.

**6) 매 전환마다 기록**
전환할 때마다 무엇을 확인했고 무엇이 남았는지 노트에 한 줄 남긴다. "정적에서 XOR 루프 구조 확인 완료 → 동적에서 key 값 확인 필요"처럼 남겨두면, 다시 전환하더라도 어디까지 했는지 헷갈리지 않는다.

## 명령어/단축키
```text
IDA: View -> Graphs -> Function Calls (콜그래프), X (xref)
Ghidra: Function Call Graph, Show References To
x64dbg: 브레이크포인트 우클릭 -> Edit -> Condition (조건부 브레이크)
GDB: break <위치> if <조건식>, watch <변수> (값이 바뀔 때만 정지)
```

## 출력 해석
- 콜그래프에서 어떤 함수가 여러 곳에서 호출되고 있다면(fan-in이 큼) 그 함수는 공용 유틸리티(예: 문자열 비교, 로깅)일 가능성이 높으므로 검증 로직의 핵심이 아닐 수 있다.
- 조건부 브레이크포인트로 루프를 건너뛰었는데도 원하는 시점에 안 멈추면, 조건식 자체(비교 연산자, 레지스터 이름)가 잘못됐을 가능성이 크므로 다시 정적분석으로 돌아가 정확한 변수/레지스터명을 재확인한다.
- 메모리 덤프 후 다시 연 정적분석 결과에서 원본 파일과 다른 코드가 나타나면, 원래 파일은 패킹되어 있었고 지금 보는 것이 실제 실행되는 언패킹된 코드라는 확증이다.

## 흔한 실수
- 값이 실행 시점에만 정해진다는 걸 알면서도 정적분석으로 계속 "추측"만 하다가 시간을 낭비하는 것.
- 반대로 구조 파악이 필요한 상황인데 디버거로 스텝만 반복하며 전체 그림 없이 국소적인 값만 계속 쌓아가는 것 — 나중에 조각들을 다시 맞추느라 이중 작업을 하게 된다.
- 조건부 브레이크포인트를 몰라서 긴 루프를 F8로 수백 번 누르며 시간을 낭비하는 것.
- 전환할 때마다 기록을 안 남겨서, 정적/동적을 오가는 동안 "내가 뭘 확인했었지"를 계속 다시 확인하는 것.

## 막혔을 때 다음 체크
- 애초에 문제를 처음 받았을 때 정적/동적 중 어디서 시작할지부터 모르겠다 → REV-0005 문제를 정적 분석부터 할지 동적 분석부터 할지 결정하는 법
- Windows PE에서 실제 전환 절차(주소 계산 포함)가 궁금하다 → REV-0306 IDA로 정적분석 후 x64dbg로 검증하는 워크플로
- Linux ELF에서 실제 전환 절차가 궁금하다 → REV-0307 Ghidra와 GDB를 같이 쓰는 워크플로

## 미니 예제
어떤 함수를 정적분석 중, `call [rax+rdx*8]`이라는 간접 호출을 발견했다.

1. 정적으로 `rax`, `rdx`가 어디서 오는지 xref로 몇 분간 역추적했지만 테이블 값 자체가 런타임에 채워지는 구조로 보여 특정이 어려움 → "값을 모른다" 신호로 판단, 동적분석으로 전환.
2. 이 `call` 명령 직전에 브레이크포인트를 걸고 실행, 도달 시 `rax`, `rdx` 레지스터 값을 확인 → 실제 목적지 주소를 계산.
3. 그 주소로 정적분석 도구에서 이동(Ctrl+G/Jump to Address)해서 함수 구조를 확인 → "구조를 봐야 한다" 신호이므로 다시 정적분석으로 전환.
4. 그 함수가 문자열 비교 유틸리티라는 걸 확인하고, 이 함수가 호출되는 다른 지점들도 콜그래프로 한 번에 확인 → 이 함수는 핵심 로직이 아니라 공용 유틸리티임을 파악하고 상위 호출자로 분석 대상을 옮김.

이 예제에서 정적 → 동적 → 정적으로 두 번 전환했고, 각 전환은 위에서 설명한 명확한 신호(간접 호출의 값을 모름 → 구조를 다시 봐야 함)에 따라 이루어졌다.

## 관련 글
- REV-0005 — 문제를 정적 분석부터 할지 동적 분석부터 할지 결정하는 법
- REV-0306 — IDA로 정적분석 후 x64dbg로 검증하는 워크플로
- REV-0307 — Ghidra와 GDB를 같이 쓰는 워크플로

## 출처/검증
- 정적/동적 분석 전환 판단 기준(간접 호출, 안티디버깅, 자기수정 코드): 일반적인 리버스 엔지니어링 방법론(다수의 공개 리버싱 교재 및 CTF writeup) 요약.
- 조건부 브레이크포인트(x64dbg Condition, GDB `break ... if`): x64dbg 공식 문서 및 GNU GDB 공식 문서 기준 (2026-09-09 검증).
