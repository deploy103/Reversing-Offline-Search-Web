## 한 줄 요약
프로그램 전체 로직이 이상하게 짧은 함수 하나에 몰려 있고 그 안에 "반복문 + 거대한 switch/점프 테이블 + 공통 카운터(프로그램 카운터 역할)" 구조가 보인다면 커스텀 가상머신(바이트코드 인터프리터) 문제일 가능성이 높으며, 이 경우 일반적인 함수별 분석 대신 **opcode 표부터 만드는 접근**으로 전략을 바꿔야 한다.

## 언제 검색해야 하나
- 프로그램의 핵심 로직이 하나의 큰 함수 안에서 반복문과 거대한 `switch`문으로만 이루어져 있어서 평소 방식(함수별로 나눠 분석)이 안 통할 때
- `.rodata`나 별도 섹션에 의미를 알 수 없는 바이트 배열이 있고, 그 배열의 각 바이트/워드가 코드처럼 하나씩 처리되는 것 같을 때
- 문자열에 "vm", "opcode", "bytecode", "interpreter" 같은 단어가 보일 때
- 디컴파일 결과에 `pc`, `ip`, `sp` 같은 변수명이 반복적으로 등장하고 이들이 배열 인덱스로 쓰일 때

## 핵심 개념
CTF에서 "커스텀 VM" 문제는 출제자가 직접 만든 가상의 명령어 집합(opcode)과 그 명령어를 해석해서 실행하는 인터프리터를 프로그램 안에 구현해 넣은 것이다. 실제 검증 로직은 x86 어셈블리로 직접 짜여 있는 게 아니라, 별도의 데이터 배열(바이트코드)로 저장되어 있고 인터프리터가 그 배열을 한 칸씩 읽어가며 해석·실행한다. 이 구조 때문에 IDA/Ghidra의 일반적인 "함수 단위 분석"이 거의 통하지 않는다 — 진짜 로직은 어셈블리가 아니라 데이터 배열 안에 있기 때문이다.

### 왜 이런 구조가 어려운가
일반적인 리버싱은 "이 함수가 무슨 일을 하는가"를 어셈블리/디컴파일 코드로 직접 읽는다. 하지만 VM 구조에서는 인터프리터 함수 자체는 항상 똑같은 fetch-decode-execute 루프만 반복할 뿐이고, 실제로 검증 로직이 무엇인지는 데이터 배열의 바이트 값에 달려 있다. 즉 "코드를 읽는" 문제가 아니라 "데이터를 코드처럼 해석하는" 문제로 바뀐다. 이 사실을 모르고 인터프리터 함수만 계속 정독하면 항상 같은 반복문만 보이고 진전이 없다고 느끼게 된다.

### 첫 징후를 알아보는 구체적 패턴
1. **fetch-decode-execute 루프**: `while(1) { op = bytecode[pc]; pc++; switch(op) { ... } }` 형태의 무한/긴 반복문. 디컴파일에서 `for` 또는 `while` 안에 거대한 `switch`문이 있고, `switch`의 각 `case`가 짧고(레지스터 값끼리 더하기/빼기/비교 같은 단순 연산) 서로 구조가 비슷하다면 각 `case`가 하나의 opcode 처리 루틴일 가능성이 높다.
2. **공통 상태 변수(레지스터 배열, 스택, PC)**: 코드 안에 크기가 고정된 배열(예: `int regs[8]`, `int stack[256]`)과, 그 배열을 가리키는 인덱스 변수(흔히 `pc`, `sp`, `ip`로 불리거나 이름 없이 `v4`, `v5` 등으로 나타남)가 반복해서 등장한다. 이 인덱스 변수가 반복문마다 증가하거나 조건에 따라 점프(그 자체가 재대입)하는 패턴이 보이면 VM의 프로그램 카운터일 가능성이 크다.
3. **바이트코드로 의심되는 데이터 배열**: `.rodata`나 전역 배열에 일반적인 문자열도 아니고 opcode처럼 반복적인 패턴(예: 특정 바이트 값이 자주 등장하고 그 뒤에 오퍼랜드로 보이는 바이트가 따라오는 구조)이 있는 바이트 시퀀스가 있다면 이것이 VM 프로그램(바이트코드) 자체일 수 있다.
4. **switch/점프 테이블 크기**: `case` 문이 수십 개(opcode 개수만큼) 있는 거대한 switch는 REV-0441(Switch문 점프 테이블)에서 다루는 일반적인 switch보다 훨씬 크고, 각 case의 코드가 서로 매우 비슷한 패턴(공통 헬퍼 호출 + 약간의 차이)을 반복한다.

### 확인되면 접근 전략을 바꾼다
커스텀 VM으로 확인되면, 더 이상 개별 함수를 하나씩 분석하는 방식이 아니라 다음 순서로 접근을 바꾼다.
1. 인터프리터의 fetch-decode-execute 루프를 찾아 **opcode 값과 그에 대응하는 case의 동작을 표(opcode 표)로 정리**한다. 예: `0x01 = ADD`, `0x02 = XOR`, `0x03 = JMP` 등.
2. 바이트코드 데이터를 추출해(GDB/x64dbg로 실행 중 메모리 덤프, 또는 정적으로 `.rodata`에서 추출) opcode 표를 기준으로 **바이트코드를 사람이 읽을 수 있는 니모닉으로 손으로 디스어셈블**한다.
3. 디스어셈블된 니모닉을 보면서 전체 검증 로직을 REV-0006~0009와 같은 방식으로 다시 읽어나간다 — 다만 대상이 x86 어셈블리가 아니라 VM 니모닉일 뿐 접근 방법 자체는 동일하다.

이 opcode 표 작성과 바이트코드 디스어셈블은 그 자체로 많은 시간이 걸리는 별도의 작업이므로, REV-0310 기준으로 VM 문제는 기본적으로 "1시간 이상짜리"로 분류하고 시간을 넉넉히 배정해야 한다. 구체적인 opcode 표 작성 절차와 바이트코드 완전 해석은 이 글의 범위를 넘는 심화 주제이므로, VM임을 알아채고 초기 대응(시간 배정, 접근 전략 전환)을 하는 것까지가 이 글의 목적이다.

## 화면/코드에서 보이는 징후
- 반복문 하나 안에 `case` 수십 개짜리 거대한 `switch`문이 있다.
- 코드 안에 크기가 고정된 정수 배열 여러 개(레지스터 배열, 스택 배열)와 그것을 가리키는 인덱스 변수가 반복적으로 조작된다.
- 함수 개수는 몇 개 안 되는데(인터프리터 본체 + 헬퍼 몇 개) 파일 크기나 문제 설명 대비 로직이 지나치게 단순해 보인다 — 실제 로직이 데이터에 있다는 신호다.
- 문자열/변수명에 vm, opcode, bytecode, interpreter, execute 등이 보인다.

## 가장 먼저 할 것
`switch`문이 있는 함수를 발견하면 그 함수를 정독하기 전에, 함수 크기와 `case` 개수, 그리고 함수 바깥의 반복문 존재 여부부터 확인한다. `case`가 10개 이상이고 각 case가 짧고 비슷한 구조라면, 바로 개별 case를 다 읽으려 하지 말고 "이건 VM일 수 있다"는 가설을 먼저 세운다.

## 단계별 절차
1. Functions 목록에서 크기가 유난히 큰 함수, 특히 `switch`가 있는 함수를 찾는다
2. 그 함수를 감싸는 반복문과 인덱스 변수(pc 역할)를 확인한다
3. `case`의 개수를 세고, 각 case가 공통 배열(레지스터/스택)을 조작하는 패턴인지 확인한다
4. `.rodata`나 전역 배열 중 바이트코드로 의심되는 데이터를 찾는다(문자열도 아니고 코드도 아닌 반복적 바이트 패턴)
5. VM으로 확신되면 REV-0310 기준으로 시간 배정을 재조정한다
6. 각 opcode 값과 case 동작을 매핑한 opcode 표를 만들기 시작한다
7. 바이트코드 데이터를 opcode 표로 니모닉화(수작업 디스어셈블)한다
8. 니모닉화된 로직을 REV-0006~0009 절차로 다시 분석한다

## 명령어/단축키
- IDA: 함수 위에서 `View → Graph view`로 전환하면 거대한 switch의 분기 구조가 한눈에 보임
- GDB: `break *인터프리터함수시작`, `x/64xb $바이트코드주소`로 바이트코드 데이터 덤프
- x64dbg: 덤프 창에서 바이트코드 배열 주소로 이동 후 바이트 단위로 관찰하며 인터프리터 실행과 함께 어떤 바이트가 읽히는지 대조

## 출력 해석
- 인터프리터 함수 실행 중 `pc`로 추정되는 변수를 감시(watch)했을 때 매 반복마다 일정하게 증가하다가 특정 조건에서 점프(비연속적으로 값이 바뀜)한다면, 그 변수가 VM의 프로그램 카운터임이 확정된다.
- 같은 opcode 값이 바이트코드 안에서 여러 번 반복해서 나타난다면, 그 opcode는 흔한 연산(예: 값 읽기, 더하기)일 가능성이 높고, 드물게 한두 번만 나타나는 opcode는 특수 연산(예: 최종 비교, 종료)일 가능성이 높다.

## 흔한 실수
- VM인 줄 모르고 인터프리터 함수의 어셈블리를 계속 반복해서 읽으며 "왜 이해가 안 되지"라고 시간을 낭비하는 것 — 반복문+거대 switch 패턴을 보면 빨리 VM 가설로 전환해야 한다.
- opcode 표를 만들지 않고 바이트코드를 눈으로만 훑어서 패턴을 외우려 하는 것 — 반드시 표로 기록해야 재현 가능하고 팀과 공유할 수 있다.
- VM임을 확인하고도 REV-0310 난이도 재평가를 안 해서 남은 시간 배분을 잘못하는 것.
- 일반 switch문(REV-0441, case 몇 개짜리)과 VM 인터프리터의 거대 switch(case 수십 개 + 공통 상태 배열)를 구분하지 못하고 모든 큰 switch를 VM으로 오판하는 것.

## 막혔을 때 다음 체크
- VM으로 확인했는데 opcode 표를 만드는 구체적 절차가 막막하다 → REV-0006 Flag 검증 함수 찾는 가장 흔한 경로(기본 절차를 VM 니모닉에도 동일하게 적용)
- 이 문제가 다단계 구조(Stage 3에서만 VM 등장) 안에 섞여 있다 → REV-0314 다단계 검증(Stage 1/2/3)이 있는 문제 공략법
- 시간이 많이 필요하다는 걸 알았는데 대회 시간이 부족하다 → REV-0312 시간이 부족할 때 부분점수를 노리는 전략
- 일반적인 컴파일러 switch/점프 테이블과 헷갈린다 → REV-0441 Switch문 점프 테이블(Jump Table) 완전 분석 (예정)

## 미니 예제
한 함수 안에 `while (pc < len) { op = code[pc++]; switch(op) { case 0x01: regs[a] += regs[b]; break; case 0x02: regs[a] ^= regs[b]; break; case 0x10: pc = target; break; ... } }` 형태의 코드가 있었다. `case`가 20개 가까이 있었고 모두 `regs[]` 배열을 조작하는 패턴이 반복됐다 — 전형적인 VM 인터프리터로 판단하고, `code[]` 배열을 GDB로 덤프한 뒤 `0x01=ADD`, `0x02=XOR`, `0x10=JMP`로 opcode 표를 만들어 전체 바이트코드를 니모닉으로 옮겨 적었다. 이후 일반 어셈블리 리버싱과 동일한 방식으로 그 니모닉 목록을 읽어 검증 로직을 복원할 수 있었다.

## 관련 글
- REV-0314 — 다단계 검증(Stage 1/2/3)이 있는 문제 공략법
- REV-0310 — 리버싱 문제 난이도를 빠르게 가늠하는 체크포인트
- REV-0312 — 시간이 부족할 때 부분점수를 노리는 전략
- REV-0006 — Flag 검증 함수 찾는 가장 흔한 경로
- REV-0441 — Switch문 점프 테이블(Jump Table) 완전 분석 (예정)
- REV-0231 — Control Flow Flattening 기초
