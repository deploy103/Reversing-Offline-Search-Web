## 한 줄 요약
바이너리를 열기 전에 **문제 제목, 설명 문장, 첨부된 모든 파일(바이너리 외 것 포함), 파일 이름·확장자, 카테고리 태그**를 먼저 읽으면 분석 방향과 시간 배분을 크게 절약할 수 있다.

## 언제 검색해야 하나
- 바이너리를 몇 시간째 분석했는데 알고 보니 문제 설명에 결정적인 힌트가 적혀 있었을 때(뒤늦게 깨달음)
- 첨부파일이 여러 개인데 실행파일만 열어보고 나머지는 무시하고 있을 때
- 문제가 안 풀려서 막막한데 다른 뭘 봐야 할지 모를 때

## 핵심 개념
CTF/워게임 문제는 출제자가 의도적으로 정보를 배치한 결과물이다. 바이너리 파일 자체가 분석 대상이라는 생각에 매몰되면, 정작 **문제 설명 텍스트, 함께 제공된 부가 파일, 파일 이름 자체**에 있는 힌트를 놓치기 쉽다. 초보자가 흔히 하는 실수는 문제 설명을 대충 읽고 바로 바이너리부터 여는 것이다. 하지만 실전에서 문제 설명과 첨부파일에는 다음과 같은 정보가 자주 숨어 있다.

1. **카테고리/난이도 태그**: "Reversing - Easy"처럼 표시되면 복잡한 암호 알고리즘보다는 단순 비교 로직일 가능성이 높다는 기대치를 잡을 수 있다.
2. **문제 설명 문장**: "이 프로그램은 특정 버전의 Windows에서만 동작합니다", "인자를 하나 받습니다" 같은 문장이 실행 방법 자체에 대한 힌트다. "제 친구가 만든 암호화 프로그램인데..."처럼 알고리즘 종류를 암시하는 경우도 흔하다.
3. **첨부된 부가 파일**: 실행파일 외에 `libc.so.6`, `Dockerfile`, `docker-compose.yml`, `README.txt`, 샘플 입출력 파일(`sample_input.txt`, `expected_output.txt`)이 같이 오는 경우가 많다. `libc.so.6`이 따로 있다면 로컬 시스템 libc와 버전이 다르다는 뜻이고, `Dockerfile`은 실행 환경(어떤 OS/라이브러리 버전)을 알려준다.
4. **파일 이름 자체**: `chall_xor.exe`, `rev_rsa`, `simple_vm`처럼 파일명에 알고리즘 종류가 그대로 적혀 있는 경우가 의외로 많다.
5. **문제 배점/제작자 코멘트**: 배점이 낮으면 대체로 단순한 문제, 높으면 리버싱 외에 암호학/알고리즘 지식이 추가로 필요한 경우가 많다.
6. **flag 형식(flag format)**: 대회마다 `FLAG{...}`, `CTF{...}` 같은 형식이 정해져 있다. 이 형식 자체가 "찾아야 할 문자열의 패턴"을 알려주므로, 바이너리 안에서 이 패턴과 일치하는 문자열/구조를 찾는 실마리가 된다.

## 화면/코드에서 보이는 징후
- 첨부파일 목록에 실행파일 하나만 있는 게 아니라 `.zip` 안에 여러 파일이 있다.
- 문제 설명에 "다음 값을 입력하면..." 같은 구체적 지시가 있는데 이를 놓치고 바로 리버싱을 시도해서 헛수고하고 있다.
- 실행 시 인자가 필요한 프로그램인데(`argv[1]`을 쓰는 `main`), 문제 설명에 "사용법: ./chall <파일>"이라고 적혀 있었던 걸 못 보고 그냥 실행해서 "왜 아무 반응이 없지"라며 헤매고 있다.

## 가장 먼저 할 것
바이너리를 열기 전에, 압축 파일을 풀었을 때 나온 **모든 파일 목록**을 `ls -la`(Linux) 또는 탐색기(Windows)로 확인한다. 실행파일이 아닌 파일들도 전부 열어서 내용을 읽는다.

## 단계별 절차

**1) 문제 설명 전문을 정독**
CTF 플랫폼(문제 페이지)의 설명 문장을 처음부터 끝까지 읽는다. 특히 다음 표현을 주의 깊게 본다.
- "실행 시 인자로", "특정 입력을 넣으면", "이 프로그램은 ~를 검증합니다" 같은 동작 설명.
- 버전 정보(예: "Ubuntu 22.04에서 컴파일됨").
- flag 형식 예시.

**2) 첨부파일 전체 목록 확인**
```bash
unzip -l challenge.zip
ls -la ./extracted/
```
실행파일 외에 다음이 있는지 확인한다.
- `libc.so.6`, `ld-linux-x86-64.so.2` → 특정 libc 버전에 의존. pwn 요소가 섞였을 가능성.
- `Dockerfile`, `docker-compose.yml` → 실행 환경(베이스 이미지, 설치 패키지)을 알려준다. `cat Dockerfile`로 열어보면 어떤 파일이 어디에 배치되는지, 어떤 포트를 여는지까지 나올 수 있다.
- `README.md`, `NOTE.txt` → 출제자가 직접 남긴 힌트일 수 있다.
- 샘플 입출력 파일 → 프로그램의 정확한 사용법과 기대 형식을 알려준다.

**3) 파일명/확장자 자체를 힌트로 활용**
파일명에 `vm`, `xor`, `rsa`, `custom_hash`, `opcode` 같은 단어가 있으면 해당 키워드로 먼저 접근 방식을 좁힌다. 예를 들어 `simple_vm`이라면 바이트코드 인터프리터(가상 머신) 패턴을 의심하고 시작하는 게 맞다.

**4) 실행 방법부터 재확인**
```bash
./chall --help
./chall
./chall < sample_input.txt
```
문제 설명에 언급된 실행 방법을 그대로 재현해서 정상적으로 실행되는지 먼저 확인한다. 인자가 필요한데 안 주면 프로그램이 조용히 종료되는 경우가 있어서, 이를 "안티디버깅 때문에 종료됐나?" 하고 오해하는 초보자가 많다.

**5) 위 정보를 노트에 요약**
읽은 정보를 리버싱 노트 맨 위에 적어둔다([rev-0014-reversing-notes.md](./rev-0014-reversing-notes.md) 참고). "이 문제는 인자를 하나 받고, libc 2.35가 첨부되어 있고, flag 형식은 `CTF{...}`이다" 처럼 정리해두면 나중에 분석하다가 방향을 잃었을 때 다시 참고할 수 있다.

## 명령어/단축키
```bash
unzip -l challenge.zip
unzip challenge.zip -d ./extracted
ls -la ./extracted
cat Dockerfile
cat README.md
file ./extracted/*
./chall --help
```

## 출력 해석
- `Dockerfile`에 `FROM ubuntu:22.04`가 보이면 대상 libc/커널 버전을 짐작할 수 있다.
- 첨부된 `libc.so.6`이 로컬 `/lib/x86_64-linux-gnu/libc.so.6`과 다르면, 이 문제를 풀 때는 반드시 첨부된 libc 기준으로 오프셋을 계산해야 한다(`ldd --version`으로 로컬 버전 확인 가능).
- 샘플 입출력 파일이 있는데 실제 실행 결과와 다르면, 프로그램 실행 조건(인자, 환경변수, 표준입력 방식)을 잘못 재현하고 있다는 신호다.

## 흔한 실수
- 문제 설명을 안 읽고 바로 바이너리부터 열어서, 이미 설명에 적혀 있던 실행 방법을 몰라 삽질하는 것.
- 첨부된 `libc.so.6`을 무시하고 로컬 libc 기준으로 분석해서 나중에 답이 안 맞는 것.
- 파일명에 이미 알고리즘 힌트(`xor`, `rsa` 등)가 있는데 못 보고 지나치는 것.
- 문제 배점/난이도를 무시하고 쉬운 문제에 너무 복잡한 암호 해석을 시도하며 시간을 낭비하는 것(반대로 어려운 문제를 너무 쉽게 보고 대충 접근하는 것도 마찬가지로 문제).

## 미니 예제
문제 설명: "제가 만든 간단한 코드입니다. 인자로 flag 후보를 넣어보세요. (Ubuntu 22.04)"
첨부파일: `chall`, `Dockerfile`

1. `Dockerfile` 확인 → `FROM ubuntu:22.04` → glibc 2.35 계열임을 짐작.
2. 실행 방법이 "인자로 넣으라"고 명시됨 → `argv[1]`을 쓰는 프로그램이라는 걸 미리 알고 시작.
3. `./chall test`로 실행해보니 `Wrong!`이 출력됨 → 정상 동작 확인, 이제 검증 로직을 찾으면 된다.
이 세 줄만 확인해도 "표준입력이 아니라 명령줄 인자를 받는다"는 걸 미리 알고 IDA에서 `argv`를 바로 찾아 들어갈 수 있어, `scanf`만 찾다가 헤매는 실수를 피할 수 있다.
