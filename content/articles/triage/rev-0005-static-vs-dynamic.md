## 한 줄 요약
"코드를 읽어서 이해되면 정적, 읽어도 값이 안 보이거나 안티디버깅/난독화가 있으면 동적"이 기본 원칙이며, 실전에서는 **정적으로 구조를 파악하고 동적으로 값을 확인하는 병행**이 가장 빠르다.

## 언제 검색해야 하나
- IDA/Ghidra를 켜야 할지 x64dbg/GDB를 켜야 할지 매번 헷갈릴 때
- 정적 분석으로 디컴파일까지는 봤는데 실제로 어떤 값이 어떻게 흘러가는지 감이 안 잡힐 때
- 안티디버깅이 걸려 있어서 디버거를 켜면 프로그램이 이상하게 종료될 때

## 핵심 개념
**정적 분석(static analysis)** 은 프로그램을 실행하지 않고 파일 자체(어셈블리, 디컴파일된 코드)를 읽어서 로직을 이해하는 방법이다. IDA, Ghidra가 대표 도구다. **동적 분석(dynamic analysis)** 은 실제로 프로그램을 실행시키면서 레지스터, 메모리, 함수 인자 값을 관찰하는 방법이다. x64dbg, GDB(+Pwndbg)가 대표 도구다.

둘은 경쟁 관계가 아니라 **상호 보완 관계**다. 실전에서 리버서는 이 둘을 계속 왔다갔다 한다:
- 정적 분석으로 "이 함수가 무엇을 하는 것 같다"는 **가설**을 세운다.
- 동적 분석으로 그 가설이 맞는지 **실제 값으로 검증**한다.

다만 시간이 제한된 CTF 환경에서는 "어느 쪽을 먼저, 얼마나" 할지 판단하는 감각이 중요하다. 판단 기준은 다음과 같다.

**정적 분석을 우선해야 하는 신호**
- 바이너리가 not stripped이고 함수/변수 이름이 그대로 남아있다.
- 디컴파일된 코드(IDA F5, Ghidra Decompile)가 상식적인 C 코드처럼 읽힌다 — `if (input == 0x1234)` 같은 명확한 비교문이 보인다.
- 문자열(`Correct`, `flag{` 등)이 평문으로 그대로 보인다.
- 알고리즘이 반복문 + 산술 연산 정도로 단순해 보인다.

**동적 분석을 우선해야 하는 신호**
- 코드에 `IsDebuggerPresent`, `ptrace(PTRACE_TRACEME, ...)` 같은 안티디버깅 호출이 있다 — 정적으로만 봐서는 실제 분기 결과를 알기 어렵다.
- 비교 대상 값이 런타임에 계산된다(예: 시간 기반 시드, 네트워크로 받은 값, 다른 함수의 리턴값을 그대로 씀).
- 코드가 패킹/난독화되어 있어서 정적으로는 의미 없는 코드만 보인다 — 언패킹 후 실제 코드가 메모리에 펼쳐지는 걸 봐야 한다.
- 자기수정코드(self-modifying code)나 JIT처럼 실행 중에 코드 자체가 바뀐다.
- 스택/레지스터에 값이 계속 쌓이는 복잡한 산술이라 손으로 계산하는 것보다 실제로 돌려서 결과값을 보는 게 압도적으로 빠르다.

**둘 다 필요한 가장 흔한 패턴**: 정적으로 검증 함수의 구조(반복문 개수, 비교 방식)를 파악한 뒤, 동적으로 그 함수에 브레이크포인트를 걸어서 각 반복에서 실제 비교되는 값이 무엇인지 확인한다. 이게 CTF 리버싱에서 가장 자주 쓰는 조합이다.

## 화면/코드에서 보이는 징후
- IDA F5 결과에 `sub_401200()`, `sub_401450()`처럼 이름 모를 함수 호출이 많고 반환값이 바로 조건문에 쓰인다 → 그 함수들을 다 정적으로 따라가느니 동적으로 브레이크포인트 걸고 리턴값만 보는 게 빠를 수 있다.
- 코드에 `rdtsc`, `GetTickCount`, `time(NULL)` 호출이 보인다 → 실행마다 값이 달라지는 요소이므로 정적 분석만으로는 최종 비교값을 알 수 없다.
- 디컴파일 결과가 반복문 안에서 배열 인덱스가 계속 바뀌는 복잡한 형태다 → 손으로 시뮬레이션하기보다 실행시켜서 몇 바퀴 도는지 직접 확인하는 게 빠르다.

## 가장 먼저 할 것
바이너리를 열면 일단 5~10분은 **정적 분석**으로 시작한다. 이유는 동적 분석은 "어디에 브레이크포인트를 걸어야 하는지"를 알아야 효율적인데, 그 정보 자체를 정적 분석(함수 목록, 문자열, xref)에서 얻기 때문이다. 아무 정보 없이 무작정 디버거로 F8만 누르며 한 줄씩 따라가는 것은 가장 비효율적인 방법이다.

## 단계별 절차

**1) 정적 분석으로 "지도"부터 그린다 (5~10분)**
- IDA/Ghidra로 열고 문자열(Shift+F12), 함수 목록(Ctrl+P)을 훑는다.
- 검증 함수로 보이는 후보를 찾는다([rev-0006-finding-check-function.md](./rev-0006-finding-check-function.md) 참고).
- 그 함수의 F5 디컴파일 결과를 읽어본다.

**2) 디컴파일 결과로 판단**
- 코드가 이해되고 비교 상수(`if (v1 == 0x539)`)가 바로 보인다 → 정적 분석 계속. 상수를 기록하고([rev-0013-record-constants-first.md](./rev-0013-record-constants-first.md)) 로직을 손으로 복원한다.
- 코드에 안티디버깅/시간 함수/반환값을 바로 못 믿을 함수 호출이 섞여 있다 → 동적 분석으로 전환.
- 디컴파일 자체가 이상하게 깨져 보인다(어셈블리랑 안 맞는 느낌) → [rev-0011-when-to-trust-asm.md](./rev-0011-when-to-trust-asm.md) 확인 후 어셈블리 원문을 본다.

**3) 동적 분석으로 전환할 때의 절차**
- 검증 함수 시작 주소에 브레이크포인트를 건다.
  - x64dbg: 함수를 더블클릭해서 이동한 뒤 **F2**.
  - GDB: `break *0x<주소>` 또는 심볼이 있으면 `break check_flag`.
- 실행(x64dbg **F9**, GDB `run` 또는 `r`)하고 입력을 넣는다.
- 브레이크포인트에 걸리면 레지스터/스택 값을 확인하며 **F8(스텝 오버)** 로 한 줄씩 진행, 궁금한 함수는 **F7(스텝 인투)** 로 들어간다.
- 조건 분기 직전에 실제 비교되는 값을 레지스터 창에서 직접 읽는다.

**4) 다시 정적으로 돌아가기**
동적 분석으로 특정 값(예: 배열에 담긴 상수들)을 확인했으면, 그 값을 들고 다시 정적 분석/코드 복원으로 돌아가서 전체 로직을 문서화한다. 최종적으로 솔버를 짜려면 이 문서화가 필요하다([rev-0017-recover-logic-before-solver.md](./rev-0017-recover-logic-before-solver.md)).

## 명령어/단축키
- IDA: `Shift+F12`(문자열), `Ctrl+P`(함수), `F5`(디컴파일), `X`(xref)
- x64dbg: `F2`(브레이크포인트), `F9`(실행), `F7`(스텝 인투), `F8`(스텝 오버), `Ctrl+F9`(현재 함수 끝까지 실행)
- GDB: `break <위치>`, `run`, `next`(스텝 오버), `step`(스텝 인투), `info registers`, `x/20xb $rsp`
- Pwndbg 추가: `context`(현재 상태 한눈에 보기), `vmmap`(메모리 맵)

## 출력 해석
- x64dbg에서 브레이크포인트에 걸린 뒤 우측 레지스터 창에 `EAX = 00001234`처럼 나오면 이게 방금 계산된 실제 값이다. 정적 분석에서 "이 값이 뭘까" 추측만 하던 걸 여기서 확정할 수 있다.
- GDB에서 `info registers rax`로 특정 레지스터만 확인 가능. `x/s $rsi`로 문자열 포인터가 가리키는 실제 문자열도 바로 볼 수 있다.

## 흔한 실수
- 아무 정보 없이 동적 분석부터 시작해서 F8을 수백 번 누르며 프로그램 전체를 한 줄씩 따라가는 것 — 정적으로 5분만 훑었어도 어디에 브레이크포인트를 걸어야 할지 알 수 있었다.
- 반대로, 안티디버깅이 명백히 있는데도 정적 분석만 고집하다가 값 하나를 알아내는 데 30분을 손 계산으로 낭비하는 것.
- 동적 분석 중 얻은 값을 기록하지 않고 디버거를 닫아버려서 다시 처음부터 반복하는 것 — 반드시 노트에 적는다([rev-0014-reversing-notes.md](./rev-0014-reversing-notes.md)).
- PIE/ASLR 켜진 상태에서 정적 분석에서 본 주소를 그대로 디버거에 입력해서 브레이크포인트가 안 걸리는 것.

## 미니 예제
디컴파일 결과가 다음과 같다고 하자.
```c
int v1 = transform(input);
if (v1 == key_value)
    puts("Correct!");
```
`key_value`가 전역 변수인데 초기화되는 곳을 찾아보니 `srand(time(NULL))` 뒤에 `rand()`로 채워지고 있다면, 이 값은 실행마다 달라지므로 정적으로는 알 수 없다. 이 시점이 바로 동적 분석으로 전환할 타이밍이다: `if (v1 == key_value)` 비교 직전 주소에 브레이크포인트를 걸고, 그 순간의 `key_value` 실제 메모리 값을 읽는다.

반대로 다음과 같다면:
```c
if (input == 0x1337 && input2 == 0xdead)
    puts("Correct!");
```
값이 이미 상수로 박혀 있으므로 디버거를 켤 필요 없이 그대로 정적으로 답을 구성하면 된다.
