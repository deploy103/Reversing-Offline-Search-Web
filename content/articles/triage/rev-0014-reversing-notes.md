## 한 줄 요약
분석 중인 함수/변수는 확실하지 않아도 **가설 이름(`maybe_xor`, `probably_check`)으로 즉시 리네임**하고, 별도 노트 파일에 "함수 목록 + 가설 + 확인 상태"를 표 형태로 유지하면 큰 바이너리에서 길을 잃지 않는다.

## 언제 검색해야 하나
- `sub_401200`, `sub_401450` 같은 이름이 너무 많아서 뭐가 뭔지 헷갈릴 때
- 어제 또는 몇 시간 전에 분석했던 함수인데 뭘 하는 함수였는지 기억이 안 날 때
- 큰 바이너리를 분석하다가 "내가 지금 어디까지 봤더라"를 스스로도 모를 때

## 핵심 개념
IDA/Ghidra가 자동 생성하는 `sub_401200` 같은 이름은 주소 기반이라 정확하지만 아무 의미도 없다. 함수가 5개면 그냥 다 열어봐도 되지만, 함수가 30개, 100개가 넘어가면 이름 없이는 "내가 이미 본 함수인지, 뭘 하는 함수인지"를 스스로 관리할 수 없게 된다.

리버싱은 본질적으로 **가설을 세우고 검증하는 과정의 반복**이다. 처음부터 함수의 정확한 역할을 알 수는 없다. 그래서 리네임은 "확신이 든 최종 이름"이 아니라 **"현재 시점의 가설"** 을 담아도 된다. 오히려 그렇게 하는 게 낫다:

- `sub_401200` → 처음 봤을 때 반복문 하나로 배열을 순회하는 게 보이면 → `maybe_loop_something`으로 리네임.
- 나중에 다시 봤을 때 XOR 연산이 보이면 → `maybe_xor_transform`으로 업데이트.
- 확신이 서면 → `xor_transform`으로 최종 확정.

이렇게 이름을 계속 갱신하면, Functions 창(Ctrl+P)만 봐도 "이 바이너리에서 내가 지금까지 뭘 알아냈는지"가 한눈에 요약된다. 이게 순수 텍스트 노트보다 강력한 이유는 **코드와 이름이 항상 같은 자리에 붙어있어서** 다시 그 함수를 열 때마다 자동으로 상기시켜주기 때문이다.

이와 별개로, IDA 자체 데이터베이스(.idb/.i64)에만 의존하면 안 되는 이유도 있다: 여러 바이너리를 왔다갔다 하거나, 전체 그림(어떤 함수가 어떤 함수를 호출하는지, 아직 못 본 게 뭔지)을 파악하려면 **외부 텍스트 노트**가 따로 필요하다.

## 화면/코드에서 보이는 징후
- Functions 창(Ctrl+P)에 `sub_`로 시작하는 이름이 20개 넘게 있다.
- 같은 함수를 두 번째 열었는데 예전에 봤다는 느낌만 있고 뭘 알아냈었는지 기억이 안 난다.
- 분석 노트가 아예 없어서 "내가 지금 검증 함수 안에 있는 건지, 아직 못 찾은 건지"조차 불확실하다.

## 가장 먼저 할 것
지금 보고 있는 함수를 클릭 한 번(또는 `N` 키)으로 리네임한다. 완벽한 이름이 아니어도 괜찮다 — `unknown1`, `maybe_check` 같은 임시 이름도 `sub_401200`보다 백배 낫다.

## 단계별 절차

**1) 함수를 볼 때마다 즉시 리네임**
- IDA: 함수 이름(Functions 창 또는 디스어셈블리의 함수 시작 줄)에 커서를 놓고 **N** 키 → 새 이름 입력. 한글은 IDA 이름 규칙상 안 되므로 영문/숫자/언더스코어로 작성한다(예: `maybe_xor_check`).
- Ghidra: 함수 이름 우클릭 → `Rename Function`(단축키 `L`).
- 확신 정도를 이름에 접두어로 표시하는 습관을 추천한다: `maybe_`(추측), `probably_`(꽤 확신), 접두어 없음(확정).

**2) 변수도 의미 있는 이름으로**
디컴파일 창에서 `v1`, `a1` 같은 변수도 **N**(IDA) 또는 더블클릭 후 이름 변경으로 바꾼다. 예: `v1` → `user_input`, `a2` → `key_len`.

**3) 함수 요약을 주석으로 남기기**
함수 시작 줄에서 **콜론(`:`)** 을 눌러 한 줄 요약을 적는다. 예: `입력을 8바이트씩 잘라서 각각 XOR 후 target과 비교`.

**4) 외부 노트 파일 유지**
IDA 안에서의 리네임/주석과 별개로, 프로젝트 폴더에 `notes.md` 하나를 만들어 다음 형식으로 관리한다.
```
# chall 분석 노트

## 파일 정보
- ELF 64bit, not stripped, PIE
- flag 형식: FLAG{...}

## 함수 목록 및 가설
| 주소       | 이름(리네임)        | 역할 가설                  | 확인 상태 |
|-----------|--------------------|----------------------------|-----------|
| 0x401136  | main               | 입력받고 check_flag 호출    | 확정      |
| 0x4011f0  | maybe_check_flag   | 8바이트씩 XOR 후 비교        | 진행중    |
| 0x401300  | maybe_print_banner | 배너 출력, 로직과 무관해 보임 | 확정(무관)|

## 상수
- key[8] @ check_flag+0x10: 01 03 03 07 0C 0A 0F 0E
- target[8] @ check_flag+0x40: (추출 필요)

## 다음 할 일
- target 배열 추출
- XOR 역산 스크립트 작성
```
이 표는 [rev-0013-record-constants-first.md](./rev-0013-record-constants-first.md)에서 기록한 상수를 그대로 이어서 정리하는 자리이기도 하다.

**5) 진행 상태 갱신**
분석이 진행될수록 "확인 상태" 칸을 `미확인 → 진행중 → 확정`으로 갱신한다. 이렇게 하면 나중에 "이 함수는 로직과 무관하니 다시 안 봐도 된다"는 판단을 스스로 신뢰할 수 있다 — 노트가 없으면 이미 무관하다고 판단했던 함수를 또 열어보게 된다.

## 명령어/단축키
- IDA: `N`(이름 바꾸기), `:`(주석), `Ctrl+P`(함수 목록에서 전체 이름 한눈에 보기)
- Ghidra: `L`(함수/변수 이름 바꾸기, 커서 위치에 따라 다름), 우클릭 `Rename`
- 노트 파일: 아무 텍스트 에디터(VS Code, 메모장)로 `notes.md` 유지, 표 형식은 마크다운으로 작성하면 나중에 읽기도 좋다.

## 출력 해석
- Functions 창에서 리네임된 함수들이 알파벳 순으로 섞여 보이므로, `maybe_` 접두어를 쓰면 정렬했을 때 관련 함수들이 몰려 보여 오히려 찾기 편해지는 부수 효과가 있다.
- 노트의 "확인 상태" 열이 전부 `진행중`이면 아직 확실한 결론에 도달한 함수가 없다는 뜻이므로, 다음에 뭘 해야 할지 판단하는 기준이 된다.

## 흔한 실수
- "나중에 한번에 이름 정리해야지"라며 미루다가 결국 안 하는 것 — 리네임은 발견 즉시, 1초도 안 걸리는 작업이다.
- 변수 이름은 안 바꾸고 함수 이름만 바꿔서, 정작 디컴파일 코드를 읽을 때 `v1`, `v2`, `a1`이 뒤섞여 여전히 헷갈리는 것.
- 노트 파일을 안 만들고 머릿속으로만 기억하려는 것 — 특히 중간에 쉬었다가 다시 분석을 재개할 때 노트가 없으면 처음부터 다시 훑어야 한다.
- 확신 없는 이름을 마치 확정된 것처럼(`maybe_` 접두어 없이) 지어서, 나중에 틀린 가설이었다는 걸 깨달아도 이름을 안 고치고 계속 쓰는 것 — 잘못된 이름은 잘못된 확신을 강화한다.

## 미니 예제
처음 열었을 때 `sub_401450`이 반복문 하나로 배열을 도는 게 보였다.
1. `N` → `maybe_loop_func`으로 리네임.
2. 콜론(`:`)으로 함수 시작 줄에 주석: `배열을 순회하며 뭔가 누적 - 체크섬 의심`.
3. 노트에 한 줄 추가: `| 0x401450 | maybe_loop_func | 체크섬 계산 의심 | 진행중 |`.
4. 나중에 다시 봤을 때 CRC32 상수 테이블(`0xEDB88320` 등)이 보임 → `crc32_calc`로 재리네임, 노트 상태를 `확정`으로 갱신.
