## 한 줄 요약
입력을 줘도 화면에 아무 반응이 없을 때는 프로그램이 진짜로 멈춘 게 아니라 **stdout 버퍼링 때문에 출력이 안 보이는 것**이거나, 프로그램이 기대하는 입력 형식과 실제로 준 입력이 달라서 **여전히 대기 중**인 경우가 대부분이며, 이 둘을 구분하는 것이 첫 단계다.

## 언제 검색해야 하나
- 프로그램을 실행해서 문자열을 입력하고 엔터를 쳤는데 아무 것도 출력되지 않을 때
- "Enter password:" 같은 프롬프트조차 안 뜨는데 커서만 깜빡이고 있을 때
- 파이프(`echo x | ./chall`)나 파일 리다이렉션으로 입력을 줬는데 출력이 하나도 안 나올 때
- 디버거로 멈춰서 확인하고 싶은데 어디서 멈췄는지조차 감이 안 잡힐 때

## 핵심 개념
"반응이 없다"는 현상은 실제로는 서로 다른 세 가지 상황을 뭉뚱그린 표현이다.

1. **출력 버퍼링(가장 흔한 원인)** — C 표준 라이브러리의 `stdout`은 터미널(tty)에 연결되어 있을 때는 줄 단위(line-buffered)로 자동 flush되지만, 파이프나 파일로 리다이렉션되면 **완전 버퍼링(fully-buffered)** 모드로 바뀐다. 이 경우 버퍼가 꽉 차거나 프로그램이 종료돼야 출력이 한꺼번에 나온다. 즉 "반응이 없다"고 느끼는 것은 사실 출력이 **커널로 아직 안 넘어간 것**뿐이다.
2. **입력 형식 불일치** — `scanf("%d", ...)`처럼 특정 형식을 기다리는데 문자열을 주면 입력 자체가 무시되거나 파싱이 실패해 무한정 다음 입력을 기다리는 상태가 될 수 있다. 프로그램은 죽지 않았고 여전히 `scanf`/`fgets` 안에서 블로킹 중이다.
3. **진짜로 멈춘 경우(데드락/무한 루프)** — 멀티스레드 프로그램에서 뮤텍스 데드락이 걸렸거나, 조건이 절대 만족되지 않는 `while(1)` 루프에 빠진 경우. 이 경우는 CPU 사용률(`top`)을 보면 100%로 치솟아 있어 구분 가능하다.

## 화면/코드에서 보이는 징후
- 파이프로 입력을 줄 때만 출력이 안 보이고, 인터랙티브 터미널에서 직접 타이핑하면 정상적으로 보임
- `strace`로 보면 `write()` 호출 자체가 없거나, 있는데도 터미널에는 안 보임(버퍼링)
- `top`/작업 관리자에서 CPU 사용률이 0%에 가까움(블로킹) vs 100%(무한 루프)

## 가장 먼저 할 것
`top` 또는 작업 관리자로 CPU 사용률부터 확인한다. 0%에 가까우면 뭔가를 "기다리는 중"(입력 대기, 버퍼링)이고, 100%면 진짜 루프에 빠진 것이다. 그다음 `stdbuf -o0`으로 버퍼링부터 강제로 꺼본다.

## 단계별 절차

**1) CPU 사용률로 대기 vs 루프 구분**
```bash
top -p $(pgrep chall)
```
0%대면 어딘가에서 블로킹 중(입력 대기 등), 100%면 무한 루프.

**2) 출력 버퍼링 의심 시 강제로 unbuffered 실행**
```bash
stdbuf -o0 ./chall
```
이렇게 실행했을 때 프롬프트가 바로 보인다면, 원래 문제는 버퍼링이었을 뿐 프로그램은 정상이었다. pwntools를 쓴다면 `process()`가 기본적으로 pty를 붙여주므로 이 문제를 피할 수 있는 경우가 많다.

**3) strace로 실제 write/read 호출 확인**
```bash
strace -f -e trace=read,write ./chall
```
`read(0, ...)`에서 멈춰 있다면 stdin을 기다리는 중이고, `write(1, ...)`가 이미 호출됐는데 화면에 안 보인다면 100% 버퍼링 문제다.

**4) 입력 형식이 프로그램 기대와 맞는지 소스/디스어셈블리로 확인**
정적 분석에서 `scanf`, `fgets`, `read` 호출부의 포맷 문자열(`"%d"`, `"%s"`, `"%20s"` 등)을 확인한다(REV-0109 참고). `%d`를 기대하는데 문자를 입력하면 `scanf`가 값을 읽지 못하고 입력 스트림에 그대로 남아 다음 호출까지 영향을 줄 수 있다.

**5) 디버거로 read/scanf 호출 지점에 브레이크포인트**
```gdb
break read
run
```
입력을 준 뒤 이 브레이크포인트가 실제로 걸리는지 확인한다. 걸리지 않으면 프로그램이 애초에 입력을 받을 지점까지 도달하지 못한 것 — 이전 단계(예: 초기화 루틴)에서 멈췄거나 크래시가 났을 가능성을 REV-0329 관점에서 다시 확인한다.

## 명령어/단축키
```bash
top -p $(pgrep chall)
stdbuf -o0 ./chall
strace -f -e trace=read,write ./chall
echo "test" | stdbuf -o0 ./chall
```
GDB: `break read`, `break scanf`, `run`, `continue`

## 출력 해석
- `read(0, "test\n", 1024) = 5` 이후 아무 `write`도 없다면, 프로그램이 입력은 받았지만 그 이후 로직에서 멈춘 것 — 다음 함수 호출을 추적해야 한다.
- `write` 호출 자체가 로그에 나타나는데 터미널에는 안 보인다면 100% 버퍼링 문제이며, `stdbuf -o0`이나 프로그램 종료 후 한꺼번에 보이는 출력으로 확인 가능하다.
- CPU 100%에서 `strace` 로그에 동일한 syscall이 반복된다면 무한 루프, 로그가 아예 안 늘어나면 시스템 콜 없는 순수 연산 루프(스핀락 등)다.

## 흔한 실수
- 버퍼링 때문에 안 보이는 것을 "프로그램이 죽었다"고 오해해서 강제 종료(Ctrl+C)해버리는 것 — 몇 초만 더 기다리거나 EOF를 주면 버퍼가 flush되며 출력이 한꺼번에 나올 수 있다.
- `scanf("%d")`에 문자열을 넣고 "왜 안 먹지"라며 계속 같은 입력을 반복하는 것 — 포맷 불일치면 입력을 100번 줘도 안 된다. 포맷을 먼저 맞춰야 한다.
- 파이프로 테스트할 때와 직접 타이핑할 때 동작이 다르다는 것을 알아채지 못하고 "환경이 이상하다"고만 생각하는 것.
- CPU 사용률을 확인하지 않고 무작정 코드부터 읽어서 시간을 낭비하는 것.

## 막혔을 때 다음 체크
- 입력 함수 자체를 못 찾겠다면 → REV-0007 입력 함수부터 역추적하는 방법.
- 입력 함수 호출부의 정확한 포맷/버퍼 크기를 봐야 한다면 → REV-0109 scanf fgets read 입력 추적.
- 디버거로 입력 버퍼가 실제로 어떻게 바뀌는지 보고 싶다면 → REV-0195 디버거에서 입력 버퍼가 실제로 변하는 과정 추적.
- 브레이크포인트 개념 자체가 헷갈린다면 → REV-0169 Breakpoint가 무엇이고 어디에 걸어야 하는가.

## 미니 예제
```bash
$ ./chall
Enter password:               <- 이건 실제로 바로 출력됨(터미널이라 line-buffered)


$ echo "1234" | ./chall
                               <- 아무것도 안 보임(파이프라 fully-buffered)

$ echo "1234" | stdbuf -o0 ./chall
Enter password:
Wrong password
```
같은 바이너리인데 터미널에서 직접 실행할 때는 프롬프트가 보이고, 파이프로 리다이렉션했을 때는 안 보였다가 `stdbuf -o0`을 붙이자 다시 보인 것으로, 원인이 로직이 아니라 버퍼링이었음을 확인할 수 있다.
