## 한 줄 요약
같은 바이너리의 같은 함수인데 IDA에서는 `sub_401000`, Ghidra에서는 `FUN_00401000`, GDB에서는 아예 이름 없이 주소만 보이는 것은 오류가 아니라, 각 도구가 **자동 이름 접두사 규칙**과 **심볼/디맹글링 처리 방식**을 서로 다르게 정의했기 때문이며, 실제 함수(주소, 코드)는 동일하다.

## 언제 검색해야 하나
- IDA로 찾은 함수를 Ghidra에서 찾으려는데 이름이 안 보여서 당황할 때
- 같은 심볼을 GDB에서 `break`로 걸었더니 IDA/Ghidra에 표시된 이름과 형태가 다를 때(맹글링된 이름 vs 디맹글된 이름)
- 정적 링킹된 바이너리에서 도구별로 인식하는 libc 함수 이름 개수가 다를 때
- C++ 바이너리에서 함수명이 `_ZN3Foo3barEv`처럼 보였다 `Foo::bar()`처럼 보였다 도구마다 다를 때

## 핵심 개념
심볼 이름이 도구마다 달라지는 원인은 크게 세 갈래다.

1. **자동 생성 이름의 접두사 규칙이 다름** — strip된 바이너리에서 이름 정보가 없을 때, IDA는 `sub_<주소>`, Ghidra는 `FUN_<주소>`라는 자체 규칙으로 임시 이름을 붙인다. 둘 다 "이름이 없다"는 사실을 표현하는 방식일 뿐, 실제 이 함수가 무엇인지에 대한 판단은 아니다.
2. **라이브러리 함수 시그니처 매칭(FLIRT 등) 결과가 다름** — IDA의 FLIRT 시그니처, Ghidra의 함수 ID 데이터베이스는 서로 다른 패턴 매칭 엔진과 시그니처 세트를 쓴다. 그래서 정적 링킹된 libc 함수를 IDA는 `malloc`으로 정확히 알아채는데 Ghidra는 `FUN_xxx`로 남겨두거나, 그 반대인 경우가 흔하다(REV-0668 참고).
3. **C++ 이름 맹글링(Name Mangling) 디맹글 결과 표기 차이** — 컴파일러는 `Foo::bar(int)`같은 함수를 `_ZN3Foo3barEi`(Itanium ABI, GCC/Clang)처럼 맹글링해서 심볼 테이블에 저장한다. IDA/Ghidra/GDB는 각자 내장된 디맹글러로 이를 사람이 읽기 좋은 형태로 복원하는데, 템플릿 인자 표기나 `const`/참조 표시 방식이 도구마다 미묘하게 다를 수 있다. 맹글된 원본 이름(`_ZN...`)은 항상 동일하다 — 사람이 보기 좋게 바꾼 결과만 다르다.
4. **분석 시점/버전 차이** — 같은 도구라도 버전이 다르거나 자동 분석을 다시 돌린 시점에 따라 리네임 규칙이 갱신되어 이름이 바뀔 수 있다.

핵심은: **주소가 같으면 같은 함수다.** 이름이 다르다고 해서 서로 다른 코드가 아니다.

## 화면/코드에서 보이는 징후
- IDA Functions 창: `sub_401136`
- Ghidra Symbol Tree: `FUN_00401136`
- `nm ./chall`: `0000000000401136 T main` (심볼이 남아있으면 실제 이름이 보임 — strip 여부에 따라 다름)
- C++ 바이너리에서 `_ZN3Foo3barEi` vs `Foo::bar(int)` vs `Foo::bar(int) const` 처럼 표기가 조금씩 다름

## 가장 먼저 할 것
이름이 아니라 **주소(offset)** 를 기준으로 같은 함수인지 먼저 확인한다. 두 도구에서 같은 오프셋을 열어봤을 때 디스어셈블리 바이트가 동일하면 100% 같은 함수다.

## 단계별 절차

**1) 주소 기준으로 동일 함수인지 확인**
IDA에서 `sub_401136`을 열어 시작 주소를 확인하고, 같은 주소를 Ghidra의 `Navigation > Go To`(단축키 `G`)로 이동해본다. 첫 몇 바이트(옵코드)가 동일하면 같은 함수다.

**2) 원본(맹글된) 심볼 이름으로 비교**
```bash
nm ./chall | c++filt
readelf -sW ./chall | grep FUNC
```
`nm`이 보여주는 원본 심볼 이름(맹글된 형태 포함)은 도구와 무관하게 항상 동일하다. IDA/Ghidra의 디맹글 표시가 헷갈리면 이 원본 이름을 기준으로 삼는다.

**3) FLIRT/함수 ID 매칭 결과 차이 확인**
정적 링킹 바이너리에서 한 도구는 `malloc`으로 인식하고 다른 도구는 `FUN_xxx`로 남아있다면, 인식에 실패한 도구 쪽에서 수동으로 시그니처를 적용하거나(IDA: `File > Load file > FLIRT signature`), 인식에 성공한 도구의 결과를 참고해서 다른 도구에 수동으로 이름을 옮겨 적는다.

**4) C++ 디맹글 표기 차이는 무시하고 원본 이름으로 노트 남기기**
분석 노트나 문서에는 화면에 보이는 디맹글된 표기 대신, `nm`/`readelf`로 뽑은 원본 맹글 이름을 같이 적어두면 도구를 바꿔도 헷갈리지 않는다.

**5) 여러 도구를 오가며 분석할 때는 리네임을 직접 통일**
IDA에서 분석해 `check_password`로 리네임했다면, Ghidra에서도 같은 주소의 함수를 동일하게 리네임(`L` 키)해서 두 도구의 이름을 맞춰준다. 자동으로 동기화되지 않으므로 수동 통일이 필요하다.

## 명령어/단축키
```bash
nm ./chall | c++filt
readelf -sW ./chall | grep FUNC
objdump -d ./chall | grep '<.*>:'
```
IDA: `Ctrl+P`(함수 목록), `N`(리네임)
Ghidra: `L`(리네임), `G`(Go To 주소)

## 출력 해석
- `nm | c++filt` 결과에 `T main`처럼 대문자 `T`가 있으면 `.text` 섹션에 정의된 전역(global) 함수라는 뜻이다.
- `_ZN3Foo3barEi`(맹글된 이름)와 `Foo::bar(int)`(디맹글된 이름)는 같은 함수를 가리키는 두 표기일 뿐이며, 어느 도구를 쓰든 `c++filt` 한 번이면 항상 같은 결과로 변환된다.
- IDA `sub_401136`과 Ghidra `FUN_00401136`이 같은 오프셋(`401136`)을 포함하고 있다면 100% 동일한 함수다.

## 흔한 실수
- 이름이 다르다는 이유만으로 "서로 다른 함수를 보고 있다"고 착각해서 분석을 두 배로 하는 것.
- 한 도구가 자동으로 알아낸 라이브러리 함수 이름(`malloc` 등)을 다른 도구에서도 당연히 알 거라고 기대하는 것 — FLIRT/함수 ID 매칭은 도구별로 독립적이다.
- C++ 디맹글 표기가 조금 다르다고(`const` 위치, 템플릿 괄호 표기 등) 다른 오버로드 함수라고 오해하는 것 — 원본 맹글 이름을 비교하면 바로 확인된다.
- 한 도구에서 리네임한 걸 다른 도구에도 자동 반영될 거라 착각하고 나중에 헷갈리는 것.

## 막혔을 때 다음 체크
- strip 여부 자체가 헷갈리면 → REV-0038 심볼이 있는 바이너리와 Stripped 바이너리 차이.
- 정적 링킹 바이너리에서 라이브러리 함수 인식이 도구별로 다르다면 → REV-0668 strip된 정적 바이너리에서 libc 함수 식별 개념(시그니처 매칭).
- IDA에서 함수 경계 자체가 이상하게 잡혔다면(이름 문제가 아니라 범위 문제) → REV-0154 IDA에서 함수 경계가 잘못 잡혔을 때.
- 함수 개수 자체가 적게 잡히는 문제라면 → REV-0328 함수 개수가 비정상적으로 적게 잡힐 때.

## 미니 예제
```
IDA Functions:     sub_401136
Ghidra Symbol Tree: FUN_00401136
GDB:                0x0000000000401136 in ?? ()

$ nm chall | c++filt | grep 401136
0000000000401136 t check_password
```
IDA와 Ghidra는 이름 없는 함수에 서로 다른 접두사(`sub_` vs `FUN_`)를 붙였을 뿐이고, `nm`으로 확인해보니 사실 심볼 테이블에는 `check_password`라는 이름이 남아있었다(소문자 `t`는 static/지역 함수). 이 경우 IDA/Ghidra가 심볼을 자동으로 안 읽어온 설정 문제일 수 있으니, 심볼 로드 옵션을 다시 확인해야 한다.

## 관련 글
- REV-0038 — 심볼이 있는 바이너리와 Stripped 바이너리 차이
- REV-0668 — strip된 정적 바이너리에서 libc 함수 식별 개념(시그니처 매칭)
- REV-0154 — IDA에서 함수 경계가 잘못 잡혔을 때
- REV-0328 — 함수 개수가 비정상적으로 적게 잡힐 때

## 출처/검증
- IDA/Ghidra의 자동 명명 규칙(`sub_`, `FUN_`) 및 FLIRT/함수 ID 개념: Hex-Rays IDA 공식 문서 및 Ghidra 공식 문서(Function ID 기능 설명) 기준 (2026-09-09 검증).
- Itanium C++ ABI 이름 맹글링 규칙: Itanium C++ ABI 공식 사양("Name Mangling" 섹션) 기준.
