## 한 줄 요약
확장자가 없거나 신뢰할 수 없는 여러 파일이 섞여 있을 때는 **매직 바이트(magic bytes)와 `file`/Detect It Easy 판정**을 기준으로 각 파일을 "실행 코드 / 라이브러리 / 데이터 / 스크립트 / 알 수 없음"의 다섯 범주로 분류한 뒤 범주별로 다른 분석 전략을 적용한다.

## 언제 검색해야 하나
- 첨부파일 여러 개의 확장자가 전부 지워져 있거나(`chall1`, `chall2`, `data1`처럼) 확장자가 실제 내용과 다를 때
- 파일이 10개 이상이라 하나씩 손으로 열어보기엔 비효율적일 때
- 이 파일이 실행 가능한 바이너리인지, 그냥 리소스/데이터 파일인지부터 판단이 안 설 때

## 핵심 개념
CTF 첨부파일은 종종 확장자가 제거되거나 의도적으로 위장되어 있다. 확장자만 보고 판단하면 안 되는 이유는, 확장자는 운영체제에게 "어떤 프로그램으로 열지"를 알려주는 힌트일 뿐 파일의 실제 내용을 보장하지 않기 때문이다(REV-0002에서 다루는 "확장자를 믿지 말라" 원칙과 동일한 이유). 실제 형식은 파일 맨 앞 몇 바이트, 즉 **매직 바이트(시그니처)**로 결정된다.

분류 기준이 되는 대표적인 매직 바이트:
- `4D 5A` (`MZ`) → Windows PE(EXE/DLL). 이후 PE 헤더까지 확인하면 32비트/64비트, EXE/DLL 구분 가능.
- `7F 45 4C 46` (`\x7fELF`) → Linux/Unix ELF. 이후 5번째 바이트로 32/64비트(`01`/`02`), 6번째 바이트로 엔디언 구분.
- `50 4B 03 04` (`PK\x03\x04`) → ZIP 계열(자체가 zip이거나, `.docx`/`.jar`/`.apk`도 내부적으로 zip).
- `89 50 4E 47` → PNG, `FF D8 FF` → JPEG 등 이미지 포맷. 이런 파일이 섞여 있으면 스테가노그래피 가능성도 열어둔다.
- `D0 CF 11 E0` → 구형 MS Office(OLE), `25 50 44 46` (`%PDF`) → PDF.
- 매직 바이트가 전혀 알려진 패턴과 안 맞으면(무작위처럼 보이는 바이트) 암호화/압축된 커스텀 포맷이거나, 커스텀 가상머신의 바이트코드 파일일 가능성이 있다.

이렇게 파일을 다섯 범주로 나눈다.
1. **실행 코드(PE/ELF)**: 직접 분석 대상. IDA/Ghidra로 연다.
2. **라이브러리(DLL/SO)**: REV-0301에서 다룬 것처럼 실행 코드의 보조 자료일 수 있다.
3. **데이터**: 실행 코드가 읽어들이는 입력, 설정, 암호화된 자료. 스트링/hex 덤프로 먼저 확인.
4. **스크립트/바이트코드**: 셰뱅(`#!`)으로 시작하는 텍스트 스크립트, 또는 커스텀 VM의 바이트코드로 추정되는 이진 파일.
5. **알 수 없음/암호화됨**: 매직 바이트가 없고 엔트로피가 높다(무작위처럼 보인다) — 별도 챌린지 파일이거나 암호화된 flag 파일.

## 화면/코드에서 보이는 징후
- 파일 탐색기/`ls`에서 확장자가 전부 없거나 `.bin`, `.dat`처럼 의미 없는 확장자로 통일되어 있다.
- 텍스트 에디터로 열었더니 깨진 문자가 나오는데, 이게 바이너리인지 그냥 인코딩 문제인지 구분이 안 된다.
- 어떤 파일은 실행하면 바로 종료되고 어떤 파일은 "command not found" 같은 오류가 나서 혼란스럽다.

## 가장 먼저 할 것
모든 파일에 대해 `file` 명령(또는 Windows에서는 HxD로 각 파일을 열어 첫 16바이트를 육안 확인, 또는 Detect It Easy에 일괄 드래그)을 돌려서 결과를 표로 만든다. 이 표가 이후 모든 분석 순서의 기준이 된다.

## 단계별 절차

**1) 일괄 매직 바이트 확인**
```bash
file * 2>/dev/null
```
Linux `file`이 없는 환경(순수 Windows)이라면 HxD로 각 파일을 열어 오프셋 0의 바이트를 직접 눈으로 비교하거나, PowerShell에서:
```powershell
Get-Content -Encoding Byte -TotalCount 4 .\unknown_file | ForEach-Object { '{0:X2}' -f $_ }
```

**2) 결과를 다섯 범주로 분류**
`file` 출력에 `PE32`, `ELF`, `Zip archive`, `ASCII text`, `data` 같은 키워드가 나온다. `data`로만 나오면 매직 바이트가 알려진 포맷과 안 맞는다는 뜻이므로 3단계로 넘어간다.

**3) `data`로 분류된 파일은 엔트로피/구조 재확인**
```bash
xxd unknown_file | head -20
strings unknown_file | head -20
```
- 앞부분에 읽을 수 있는 문자열(예: JSON 키, 알아볼 수 있는 헤더)이 보이면 커스텀 포맷 데이터 파일이다.
- 전혀 읽을 수 있는 문자열이 없고 바이트 분포가 균등해 보이면(0x00~0xFF가 골고루 나옴) 암호화되었거나 압축된 파일일 가능성이 높다. 이 경우 해당 파일을 읽는 실행 코드 쪽(1번 범주)을 먼저 분석해서 복호화/압축해제 로직을 찾아야 한다.

**4) 실행 코드로 분류된 파일 사이의 관계 확인**
PE/ELF로 분류된 파일이 여러 개면 REV-0301의 절차(Import/Export 관계 확인)로 우선순위를 매긴다.

**5) 분류표를 노트에 고정**
```text
chall       -> ELF 64bit, not stripped        [실행 코드, 메인]
libcheck.so -> ELF 64bit shared object        [라이브러리, 검증 로직 의심]
flag.enc    -> data (엔트로피 높음)            [암호화된 데이터, chall이 복호화 예상]
notes.txt   -> ASCII text                     [스크립트/텍스트, 힌트 확인 완료]
```
이 표를 `notes.md` 맨 위에 고정해두고, 이후 모든 분석 단계에서 참조한다.

## 명령어/단축키
```bash
file *
xxd <file> | head -20
strings <file> | head -30
readelf -h <file>   # ELF로 판정된 파일의 클래스/엔디언/타입 재확인
```
Windows: HxD(오프셋 0 바이트 확인), Detect It Easy(일괄 드래그로 포맷+컴파일러 자동 판정), 7-Zip으로 `PK` 시그니처 파일이 실제 zip인지 시험 삼아 열어보기.

## 출력 해석
- `file` 출력이 `data`인데 파일 크기가 정확히 문제 설명에 나온 flag 길이와 비슷하면 암호화된 flag 자체일 가능성이 높다.
- ELF인데 `readelf -h`의 `Type` 필드가 `DYN`이면 PIE 실행파일 또는 공유 라이브러리 둘 다 가능하므로, `readelf -d`의 `SONAME`/`NEEDED` 유무로 라이브러리인지 실행파일인지 추가 구분한다.
- `strings` 결과에 `import`, `struct`, JSON 키 같은 패턴이 보이면 커스텀 직렬화 포맷이므로, 이 구조체를 파싱하는 코드를 실행 파일에서 찾아야 정확한 필드 의미를 알 수 있다.

## 흔한 실수
- 확장자만 보고 스크립트 파일이라 판단해 무시했는데 실제로는 셰뱅만 붙은 바이너리인 경우.
- `file` 결과가 `data`로 나오면 "분석 불가"로 포기하는 것 — 오히려 이런 파일이 핵심 대상(암호화된 flag, 커스텀 VM 바이트코드)인 경우가 많다.
- 매직 바이트만 확인하고 실제 헤더 세부값(비트수, 엔디언, 서브타입)은 확인하지 않아 나중에 잘못된 아키텍처로 IDA/Ghidra를 열어 시간을 낭비하는 것.
- 여러 파일을 분류만 해두고 노트에 기록하지 않아, 나중에 어떤 파일이 무엇이었는지 다시 확인하러 왔다갔다 하는 것.

## 막혔을 때 다음 체크
- 분류는 끝났는데 어떤 파일부터 분석할지 순서를 못 정하겠다 → REV-0301 문제 파일이 여러 개일 때 우선순위 정하는 법
- 분류된 실행 파일이 서버에 접속해야 하는 형태다 → REV-0303 서버 연결형 리버싱 문제(nc 접속) 접근 순서
- 데이터 파일이 암호화된 것 같은데 어떻게 접근할지 모르겠다 → REV-0011 어셈블리 원문을 언제 믿어야 하는가(디컴파일 신뢰 판단)와 함께 해당 파일을 읽는 코드부터 추적

## 미니 예제
첨부파일 5개: `bin1`, `bin2`, `res.pak`, `README`, `x`

1. `file *` 실행 결과:
```
bin1: ELF 64-bit LSB pie executable, x86-64
bin2: ELF 64-bit LSB shared object, x86-64
res.pak: data
README: ASCII text
x: POSIX shell script, ASCII text executable
```
2. 분류: `bin1`(실행 코드, 메인), `bin2`(라이브러리), `res.pak`(데이터, 엔트로피 확인 필요), `README`(텍스트, 힌트), `x`(스크립트, 실행 절차 힌트).
3. `cat x` → `LD_LIBRARY_PATH=. ./bin1 res.pak`이라는 실행 스크립트임을 확인. 이로써 `bin1`이 `bin2`를 라이브러리로 쓰고, `res.pak`을 인자로 받는 구조라는 게 명확해졌다.
4. `strings res.pak | head` → 읽을 수 있는 문자열이 전혀 없음 → 암호화/압축된 데이터로 잠정 결론, `bin2`의 복호화 함수를 찾는 것을 다음 목표로 확정.

## 출처/검증
- 파일 매직 바이트(PE `MZ`, ELF `\x7fELF`, ZIP `PK\x03\x04` 등): 각 포맷 공식 스펙(Microsoft PE/COFF, System V ABI ELF, PKWARE ZIP 명세) 기준.
- `file` 명령의 매직 데이터베이스 동작 방식: GNU/`file` 프로젝트(`libmagic`) 공식 문서 기준 (2026-09-09 검증).
