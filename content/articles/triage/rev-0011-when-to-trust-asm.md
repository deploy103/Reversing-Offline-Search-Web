## 한 줄 요약
디컴파일러(F5)는 **추측 기반 도구**이므로, 최적화된 산술식·SIMD·인라인 함수·구조체 정렬·부동소수점·변수 타입이 얽힌 코드에서는 원문과 다르게 보일 수 있고, 이럴 때는 항상 **어셈블리 원문(그래프뷰/텍스트뷰)을 직접 읽어서 검증**해야 한다.

## 언제 검색해야 하나
- F5로 디컴파일한 코드가 앞뒤가 안 맞거나, 말도 안 되는 큰 상수·이상한 캐스팅이 보일 때
- 디컴파일 코드로 계산해서 나온 답이 실제로 안 먹힐 때("분명 로직대로 계산했는데 flag가 틀렸다고 나옴")
- SIMD 명령어(`xmm0`, `pxor`, `movaps` 등)가 디컴파일에서 이상한 함수 호출(`_mm_xor_si128` 등)로 뭉뚱그려질 때

## 핵심 개념
IDA의 F5(Hex-Rays 디컴파일러)나 Ghidra의 Decompile 창은 어셈블리를 사람이 읽기 좋은 C 스타일 코드로 **재구성**해주는 도구다. 이건 원본 소스 코드를 복원하는 게 아니라, 컴파일러가 만든 기계어를 역으로 "그럴듯한 C처럼 보이는 표현"으로 근사하는 것이다. 대부분의 경우 이 근사는 매우 정확하지만, 다음 상황에서는 오해를 일으킬 수 있다.

1. **컴파일러 최적화**: `-O2`, `-O3`로 컴파일된 코드는 루프 언롤링(loop unrolling), 상수 폴딩, 강도 감소(strength reduction, 예: 곱셈을 시프트+덧셈으로 바꿈) 등이 적용되어 있다. 디컴파일러는 이걸 원래 형태로 되돌리려 시도하지만 완벽하지 않다. 예를 들어 `x * 10`이 `(x << 3) + (x << 1)`로 컴파일된 걸 디컴파일러가 다시 `x * 10`처럼 보여줄 때도 있고, 그대로 시프트 연산으로 보여줄 때도 있다.
2. **SIMD/벡터 명령어**: `xmm`/`ymm` 레지스터를 쓰는 SSE/AVX 코드는 디컴파일러가 `__m128i`, 함수 호출 형태(`_mm_xor_si128(a, b)`)로 표현하는데, 이게 실제로 무슨 연산인지(바이트 단위 XOR인지 등) 직관적으로 안 와닿을 수 있다.
3. **타입 추론 오류**: 디컴파일러는 변수의 실제 타입(부호 있음/없음, 크기)을 스택 사용 패턴에서 추측한다. 이 추측이 틀리면 `unsigned int`인 값이 `int`로 잘못 표시되어 음수처럼 보이거나, 그 반대의 경우가 생긴다. 특히 비교/시프트 연산에서 부호 여부는 결과를 완전히 바꾼다.
4. **인라인된 함수**: 작은 함수는 컴파일러가 호출 없이 그 자리에 코드를 복사해 넣는다(인라이닝). 디컴파일 결과에 함수 호출이 안 보이고 코드가 길게 풀어져 있다면 인라인된 것이다 — 이게 오류는 아니지만, "이 로직이 어디 함수에 속한 건지" 헷갈릴 수 있다.
5. **디컴파일 실패/부분 실패**: 아주 드물게 디컴파일러가 특정 블록을 제대로 재구성 못 해서 `LOBYTE()`, `HIDWORD()`, `*(_DWORD *)(a1 + 4)` 같은 저수준 매크로가 잔뜩 섞인 코드를 보여준다. 이런 코드가 나오면 디컴파일러가 "자신 없어 하고 있다"는 신호다.

이럴 때는 F5 결과를 그대로 믿지 말고, **같은 함수를 어셈블리 뷰(그래프뷰/텍스트뷰)로 열어서 명령어 하나하나를 직접 해석**해야 한다. 어셈블리는 컴파일러가 만든 실제 기계어를 그대로 텍스트로 보여주는 것이라 "재구성"이 없다 — 유일하게 100% 신뢰 가능한 표현이다.

## 화면/코드에서 보이는 징후
- 디컴파일 코드에 `LOBYTE(v3)`, `HIDWORD(v5)`, `*(DWORD *)&v2` 같은 매크로/캐스팅이 반복적으로 보인다.
- 상수가 `0xCCCCCCCD` 같이 이상하게 큰 16진수로 보인다 — 이건 대부분 나눗셈을 곱셈+시프트로 바꾸는 최적화의 "매직 넘버"다(예: `/10`을 `* 0xCCCCCCCD >> 35`로 구현).
- 조건문에서 부호 있는 비교(`<`)와 부호 없는 비교(`<`, 실제로는 `jb`/`ja`)가 코드상 똑같이 `<`로 보이는데 실제 어셈블리는 다른 명령어(`jl` vs `jb`)일 수 있다.
- `__m128i`, `_mm_` 접두사 함수, `xmm0` 언급이 디컴파일에 보인다.

## 가장 먼저 할 것
의심스러운 줄에 커서를 놓고 IDA에서 **Space bar**를 눌러 그래프뷰/텍스트뷰 어셈블리로 전환한다(F5 창에서는 커서를 특정 줄에 두고 동기화된 어셈블리 라인이 우측/하단에 같이 보이도록 설정할 수도 있다: 디컴파일 창에서 한 줄을 클릭하면 대응하는 어셈블리 줄이 강조 표시된다).

## 단계별 절차

**1) 의심 지점을 어셈블리와 나란히 비교**
IDA 디컴파일 창에서 의심되는 줄을 클릭하면, 연동된 디스어셈블리 뷰(열려 있다면)에서 대응하는 명령어가 하이라이트된다. 창이 안 열려 있으면 F5 창 상단 메뉴 `View → Open subviews → Disassembly`로 새 창을 열고 나란히 배치한다.

**2) 실제 명령어와 플래그 확인**
비교/분기가 의심스러우면 `cmp`/`test` 다음에 오는 점프 명령어를 확인한다.
- `jl`, `jg`, `jle`, `jge` = **부호 있는(signed)** 비교.
- `jb`, `ja`, `jbe`, `jae` = **부호 없는(unsigned)** 비교.
디컴파일 코드에는 둘 다 그냥 `<` 또는 `>`로 보일 수 있어서, 값이 음수 근처일 때 결과가 완전히 달라질 수 있다. 이 차이는 [../assembly/rev-0071-call.md](../assembly/rev-0071-call.md) 같은 개별 명령어 문서나 CMP/Jcc 계열 문서에서 더 자세히 다룬다.

**3) 매직 넘버 나눗셈 인식**
`imul`/`mul` 뒤에 큰 시프트(`shr`, `sar`)가 이어지는 패턴이 보이면 나눗셈/나머지 연산의 최적화된 형태다. 이런 경우 디컴파일러가 이미 `/`, `%`로 변환해서 보여주는 경우가 많지만, 혹시 이상하게 보이면 원래 나눗셈으로 해석해도 크게 틀리지 않는다.

**4) SIMD 코드는 레지스터 단위로 손으로 풀기**
`pxor xmm0, xmm1`처럼 보이면 128비트(16바이트)를 한 번에 XOR한다는 뜻이다. 디컴파일 코드의 `_mm_xor_si128` 호출도 동일한 의미이므로, "16바이트 블록 단위로 XOR하는 연산"이라고 이해하고 넘어가면 된다. 세부 바이트 값이 궁금하면 동적 분석(x64dbg/GDB에서 xmm 레지스터 값 확인)이 훨씬 빠르다.

**5) 타입이 의심되면 변수를 강제로 재선언**
IDA 디컴파일 창에서 변수를 우클릭 → `Set lvalue type`(단축키 `Y`)으로 타입을 `unsigned int`, `signed int` 등으로 직접 바꿔볼 수 있다. 바꾼 뒤 코드가 더 상식적으로 보이면 원래 타입 추론이 틀렸던 것이다.

## 명령어/단축키
- IDA: `Space`(그래프뷰 ↔ 텍스트뷰), `F5`(디컴파일), `Y`(변수 타입 재정의), 디컴파일 창에서 줄 클릭 시 연동된 디스어셈블리 하이라이트
- Ghidra: Decompile 창과 Listing 창이 기본적으로 나란히 뜨고, 한쪽 클릭 시 다른 쪽도 동기화됨. 변수 타입 변경은 우클릭 → `Retype Variable`

## 출력 해석
- `Y`로 타입을 바꾼 뒤 코드가 훨씬 단순해지면(예: 이상한 마스킹 연산이 사라짐) 원래 타입 추론이 틀렸다는 확신을 가질 수 있다.
- 어셈블리에서 직접 계산해본 값과 디컴파일 코드로 계산한 값이 다르면, 어셈블리 쪽을 정답으로 취급한다.

## 흔한 실수
- 디컴파일 코드만 보고 손으로 계산해서 flag를 제출했는데 틀리는 경우, 원인을 못 찾고 로직 자체가 틀렸다고 오해하는 것 — 실제로는 부호 문제나 타입 추론 오류였던 경우가 많다.
- 어셈블리를 아예 안 읽어보고 "디컴파일이 이상하다"고만 생각하며 진전이 없는 것 — 이상하다고 느꼈다면 바로 어셈블리로 넘어가야 한다.
- SIMD 코드를 보고 지레 겁먹고 포기하는 것 — 대부분 단순 반복 연산(XOR, 덧셈)을 여러 바이트 한 번에 처리하는 것뿐이다.
- 매직 넘버 나눗셈 상수를 직접 손으로 해석하려고 애쓰는 것 — 디컴파일러가 이미 `/` `%`로 잘 바꿔준 경우가 대부분이니 우선 그 결과를 믿고, 이상할 때만 어셈블리로 확인한다.

## 막혔을 때 다음 체크

## 미니 예제
디컴파일 결과:
```c
if ( (unsigned int)(v1 - 5) > 0xA )
    goto fail;
```
언뜻 이상해 보이지만, 이는 컴파일러가 `if (v1 < 5 || v1 > 15)`를 최적화한 흔한 패턴이다(범위 체크를 뺄셈 후 unsigned 비교 하나로 압축하는 기법). 어셈블리를 보면:
```asm
lea eax, [rdi-5]
cmp eax, 0Ah
ja  fail
```
`ja`는 unsigned 비교이므로, `v1 - 5`가 `0`~`0xA`(10) 범위를 벗어나면(즉 unsigned 결과가 10보다 크면) fail로 간다는 뜻이다. 이는 `v1`이 5~15 범위 안에 있어야 통과한다는 의미와 동일하다. 디컴파일 코드만 봐서는 바로 이해하기 어렵지만, 어셈블리의 `ja`(unsigned above)를 보고 나면 왜 저렇게 표현됐는지 명확해진다.
