## 한 줄 요약
검증 함수가 여러 개 있는 문제는 각 함수를 무작정 순서대로 정독하지 말고, 먼저 **`main`(또는 호출부)에서 각 함수가 호출되는 순서와 인자를 표로 정리**해 "어느 함수가 어느 입력 필드를 검증하는지"부터 매핑한 뒤, 조건 분기가 가장 단순한 함수부터 공략하는 것이 빠르다.

## 언제 검색해야 하나
- 디컴파일 코드에 `check_username`, `check_password`, `check_serial`처럼 이름이 다른 검증 함수가 여러 개 보일 때
- strip된 바이너리라 이름은 없지만 `main`에서 비슷한 형태의 함수 호출이 여러 번 반복될 때
- 여러 입력 필드(아이디, 비밀번호, 시리얼 번호 등)를 받는 프로그램인데 각 필드가 어떤 함수에서 검증되는지 헷갈릴 때
- 검증 함수 하나를 다 풀었는데 프로그램이 여전히 실패 메시지를 낼 때(다른 함수가 더 있다는 신호)

## 핵심 개념
REV-0006에서 다룬 "검증 함수 찾기"는 검증 함수가 하나라고 가정한 경우다. 실제로는 입력 필드가 여러 개인 문제(로그인 폼, 시리얼 키 등록, 여러 옵션을 받는 CLI)에서 필드마다 별도의 검증 함수를 두는 경우가 흔하다. 이때는 "검증 함수 찾기"가 아니라 **"검증 함수들을 서로 구분하고 순서를 정하는 것"**이 과제가 된다.

### 함수 대 입력 매핑표 만들기
`main`(또는 메인 로직 함수)을 열어서, 입력을 받는 지점(`scanf`, `fgets`, `read`)부터 각 검증 함수 호출까지의 흐름을 표로 정리한다.

| 순서 | 호출 함수 | 인자로 들어가는 값 | 반환값 의미(추정) |
|---|---|---|---|
| 1 | `check_length` | 입력 문자열 전체 | 길이 통과 여부 |
| 2 | `check_username` | 입력의 앞부분(아이디 필드) | 아이디 일치 여부 |
| 3 | `check_password` | 입력의 뒷부분(비밀번호 필드) | 비밀번호 일치 여부 |

이 표를 만들면 각 함수가 **독립적으로 검증되는지**, 아니면 앞 함수의 결과가 뒤 함수의 입력에 영향을 주는지(REV-0314의 다단계 구조와 겹치는 부분)를 구분할 수 있다. 순수하게 여러 필드를 병렬로 검증하는 구조라면 이 문서의 범위이고, 한 필드를 순차적으로 여러 단계 거쳐 검증하는 구조라면 REV-0314를 같이 참고해야 한다.

### 공략 순서 정하는 기준
모든 검증 함수를 동시에 파고들 필요는 없다. 다음 기준으로 우선순위를 정한다.
1. **조건 분기가 적은 함수부터**: `if` 문 1~2개짜리 단순 비교 함수(예: 길이 체크)는 5분 안에 끝나므로 먼저 처리해 전체 진행률을 올린다.
2. **다른 함수의 입력이 되는 함수 먼저**: 예를 들어 `check_username`의 결과값이 `check_password`의 키로 쓰인다면, 반드시 `check_username`부터 풀어야 다음 단계로 넘어갈 수 있다. `main`의 호출 순서와 변수 의존 관계를 보고 이 종속성을 미리 파악한다.
3. **문자열 상수와 직접 비교하는 함수 먼저**: `strcmp(input, "admin")`처럼 정답이 바로 보이는 함수는 로직을 이해할 필요도 없이 즉시 값을 얻을 수 있다.
4. **복잡한 암호학적 변환이 있는 함수는 마지막**: TEA, AES, 커스텀 해시가 들어간 함수는 시간이 오래 걸리므로, 쉬운 함수들을 다 처리한 뒤 마지막에 집중해서 본다.

### 각 함수를 실제로 실행하는지 확인
정적으로 로직만 보고 넘어가지 말고, 각 함수에 브레이크포인트를 걸어 실제로 어떤 값이 인자로 들어오고 반환되는지 GDB/x64dbg로 확인한다. 특히 여러 필드 검증에서는 "이 함수가 실제로 이 필드를 검사하는 게 맞는지"에 대한 가정이 틀리는 경우가 많으므로(예: 두 함수의 인자가 뒤바뀐 것처럼 보였는데 실제로는 안 그런 경우), 동적으로 한 번은 검증해야 한다.

## 화면/코드에서 보이는 징후
- `main` 안에 `if (!check_a(input1)) fail(); if (!check_b(input2)) fail();` 형태로 검증 호출이 연달아 나온다.
- 여러 함수가 구조는 비슷한데(짧은 반복문 + 비교) 사용하는 상수만 다르다.
- strip된 바이너리에서 비슷한 크기의 함수가 2~4개 반복해서 호출된다.

## 가장 먼저 할 것
`main`을 열어 입력을 받는 지점부터 반환까지 전체 흐름을 한 번 쭉 훑으면서, 호출되는 검증 함수 이름(또는 주소)과 인자만 순서대로 받아 적는다. 이 단계에서는 각 함수 내부에 들어가지 않는다.

## 단계별 절차
1. `main`(또는 진입 로직)에서 입력 처리 직후부터 반환까지 호출되는 함수 목록을 순서대로 나열
2. 각 호출의 인자(어떤 변수/버퍼가 들어가는지)와 반환값 사용처(어떤 조건문에 쓰이는지)를 표로 정리
3. 함수 간 의존 관계(한 함수의 출력이 다른 함수의 입력이 되는지) 확인
4. 조건 분기 개수·크기 기준으로 쉬운 함수부터 순서 재배열
5. 가장 쉬운 함수부터 F5 디컴파일 정독 + 브레이크포인트로 실제 값 확인
6. 확정된 로직을 REV-0222 방식으로 Python에 옮겨 적음
7. 다음 함수로 이동, 전체 함수를 다 풀 때까지 반복
8. 모든 함수를 통과하는 입력을 조합해 실제 바이너리에 넣어 최종 검증

## 명령어/단축키
- IDA: 함수 이름 더블클릭으로 이동, `X`(xref) 키로 어디서 호출되는지 확인
- GDB: `break check_username`, `run`, `info args`, `finish`(반환값 확인)
- x64dbg: 함수 시작 주소에 브레이크포인트(F2), 실행(F9) 후 인자 레지스터/스택 확인

## 출력 해석
- 종속 관계 표에서 화살표가 한 방향으로만 흐르면(A → B → C) 이는 사실상 REV-0314의 순차적 다단계 구조와 유사하므로, 앞 단계부터 순서대로 풀어야만 다음 단계 값을 얻을 수 있다.
- 각 함수가 서로 다른 입력 버퍼만 참조하고 서로의 결과를 쓰지 않는다면, 함수들은 완전히 독립적이므로 순서와 무관하게 병렬로(팀이라면 REV-0311처럼 나눠서) 공략해도 된다.

## 흔한 실수
- 함수 이름만 보고 역할을 단정하는 것(예: `check_serial`이라는 이름이지만 실제로는 다른 필드를 검사할 수 있다) — 반드시 실제 인자를 GDB/x64dbg로 확인한다.
- 모든 함수를 처음부터 순서대로 똑같은 노력으로 정독하는 것 — 쉬운 함수부터 처리해 빠르게 진행률을 올려야 한다.
- 함수 간 의존 관계를 확인하지 않고 뒤쪽 함수부터 먼저 풀려다가, 앞쪽 함수의 결과값이 필요하다는 걸 뒤늦게 깨닫는 것.
- 한 함수를 완전히 이해했다고 착각하고 다음으로 넘어갔는데, 실제로는 그 함수가 다른 함수와 값을 주고받는 부분을 놓친 것.

## 막혔을 때 다음 체크
- 함수들이 순차적으로 하나의 흐름을 이루는 것 같다 → REV-0314 다단계 검증(Stage 1/2/3)이 있는 문제 공략법
- 애초에 어떤 함수가 검증 함수인지부터 확신이 안 선다 → REV-0006 Flag 검증 함수 찾는 가장 흔한 경로
- 팀으로 나눠서 함수별로 맡기고 싶다 → REV-0311 팀 대회에서 리버싱 문제를 분업하는 법
- 확정된 로직을 스크립트로 옮기는 방법이 필요하다 → REV-0222 검증 루틴을 Python으로 그대로 재현하기

## 미니 예제
`main`에서 `read_input(buf)` 이후 `check_len(buf)`, `check_prefix(buf)`, `check_hash(buf)`가 순서대로 호출되는 것을 확인했다. `check_len`은 `strlen(buf) == 20`만 확인하는 한 줄짜리 함수, `check_prefix`는 `memcmp(buf, "FLAG{", 5)`만 확인하는 함수였다 — 두 함수는 5분 안에 끝났다. 남은 시간을 전부 `check_hash`(SHA-256 유사 변환이 있는 함수)에 집중할 수 있었고, 이미 확정된 길이 20과 접두사 `FLAG{`라는 제약 조건 덕분에 `check_hash`의 브루트포스 범위도 줄일 수 있었다(REV-0016).

## 관련 글
- REV-0006 — Flag 검증 함수 찾는 가장 흔한 경로
- REV-0314 — 다단계 검증(Stage 1/2/3)이 있는 문제 공략법
- REV-0222 — 검증 루틴을 Python으로 그대로 재현하기
- REV-0016 — 브루트포스를 해도 되는 문제인지 판단하는 법
- REV-0311 — 팀 대회에서 리버싱 문제를 분업하는 법
- REV-0007 — 입력 함수부터 역추적하는 방법
