## 한 줄 요약
CTF 대회는 보통 시작 전에 flag 형식(`DH{...}`, `flag{...}` 등)을 공지하거나 서버 응답 예시로 노출하는데, 이 형식과 함께 결과물이 hex/base64/특정 길이의 해시라는 정보를 미리 알아두면 `strings`/`grep` 결과 수백~수천 줄 중 가능성 있는 후보를 정규식 하나로 즉시 걸러내고, 브루트포스나 해시 크래킹의 탐색 범위(문자셋·길이)도 처음부터 좁힐 수 있다.

## 언제 검색해야 하나
- `strings ./chall`이나 `strings ./chall | grep flag` 결과가 수백 줄 나와서 어떤 게 진짜 flag 후보인지 구분이 안 될 때
- 문제 설명이나 대회 공지에 flag 형식(예: `DH{...}`, `flag{...}`, `picoCTF{...}`)이 적혀 있는데 이걸 왜 활용해야 하는지 감이 안 올 때
- 코드에서 사용자 입력을 어떤 값과 비교하는데, 그 비교 대상이 16진수 문자열이거나 특정 길이의 문자열이라서 "이게 무슨 해시/인코딩인지" 자릿수로 짐작하고 싶을 때
- 브루트포스를 돌리려는데 몇 자리, 어떤 문자셋으로 시도해야 시간 안에 끝날지 감이 안 잡힐 때

## 핵심 개념

### flag 형식이 왜 탐색 범위를 좁혀주는가
CTF 문제는 최종적으로 `대회이름{내용}` 형태의 문자열을 제출하게 되어 있는 경우가 대부분이다(`DH{...}`, `flag{...}`, `picoCTF{...}` 등, 대회마다 다르지만 항상 공지된다). 이 형식을 알고 있으면 다음 두 가지를 즉시 할 수 있다.

1. **문자열 후보를 정규식으로 즉시 필터링**: `strings ./chall | grep -E '대회이름\{.*\}'`처럼 형식에 맞는 줄만 골라내면, 관계없는 라이브러리 문자열·디버그 심볼 수백 줄 중에서 실제 flag(또는 flag의 일부 조각, XOR/인코딩된 형태)가 있을 법한 위치를 바로 좁힐 수 있다.
2. **비교 대상 데이터의 정체를 자릿수로 추정**: 코드가 사용자 입력을 해시하거나 인코딩한 뒤 어떤 상수와 비교한다면, 그 상수의 길이와 문자셋만 보고도 어떤 알고리즘인지 상당 부분 추정할 수 있다(아래 참고표).

### 자주 쓰이는 길이/문자셋 단서 표
| 관찰되는 값 | 가능성 높은 정체 |
|---|---|
| 32자리 hex(`0-9a-f`) | MD5 해시(128비트 출력) |
| 40자리 hex | SHA-1 해시(160비트 출력) |
| 64자리 hex | SHA-256 해시(256비트 출력) |
| 8자리 hex, 값이 입력마다 크게 바뀜 | CRC32 체크섬(32비트 출력) |
| `A-Za-z0-9+/`로 구성되고 끝에 `=`/`==` 패딩 | 표준 Base64 인코딩 |
| `A-Za-z0-9-_`로 구성되고 패딩 없음 | URL-safe Base64(RFC 4648 §5) 변형 |
| `A-Z2-7`로만 구성 | Base32 인코딩 |
| 순수 대문자/숫자로만 된 고정 길이 문자열 | 커스텀 알파벳 인코딩(REV-0880 참고) 또는 UUID 유사 포맷 |

이 표는 "확정"이 아니라 "우선순위가 높은 가설"을 세우는 용도다. 예를 들어 비교 대상이 정확히 64자리 hex이고 코드 안에 `0x6a09e667` 같은 SHA-256 특유의 초기 해시값 상수가 보이면(REV-0895), 표에서 얻은 가설이 실제 상수 확인으로 바로 검증되는 식이다.

### 서버(nc) 문제에서 flag 형식이 주는 또 다른 힌트
`nc` 접속형 문제에서 서버가 실패 시 "Wrong flag format"과 성공 시 "Correct!" 같은 서로 다른 메시지를 준다면, 이 자체가 "서버가 형식 검사를 먼저 하고 값 검사를 나중에 한다"는 구조적 힌트다. 즉 아무 문자열이나 보내 형식 오류 메시지가 뜨는지, 정확한 형식(`대회이름{아무거나}`)을 보냈을 때 다른 오류 메시지로 바뀌는지 관찰하면, 형식 검사와 실제 값 검사가 분리된 두 단계라는 걸 알 수 있고 각 단계를 따로 공략할 수 있다.

### 브루트포스 범위를 좁히는 데도 그대로 적용된다
flag 내용부(`{}` 안쪽)의 길이가 코드에서 확인되거나(예: `strlen(input) != 20`으로 길이를 먼저 검사) 문제 설명에 "정답은 소문자와 숫자로만 구성됨" 같은 조건이 있다면, 브루트포스 문자셋과 길이를 그 조건에 맞게 고정해야 탐색 공간이 기하급수적으로 줄어든다. 예를 들어 길이 8자리에 문자셋이 `[a-z0-9]`(36가지)면 전체 경우의 수는 36^8 ≈ 2.8×10^12로 이미 매우 크지만, 문자셋을 대문자까지 포함한 62가지로 잘못 가정하면 62^8 ≈ 2.2×10^14로 100배 가까이 커진다. 형식을 정확히 좁히는 것 자체가 실현 가능성(REV-0219 브루트포스 실현 가능성 판단)을 바꾸는 요인이다.

## 화면/코드에서 보이는 징후
- 문제 설명/공지에 `Flag format: DH{...}` 같은 문구가 명시되어 있음
- `strings` 결과에 `{`, `}`가 포함된 짧은 문자열이 여러 개 섞여 있어서 어떤 게 진짜인지 헷갈림
- 코드에서 `strlen(input) == 32`, `strlen(input) == 64`처럼 고정 길이를 먼저 검사하는 분기가 있음
- 서버 응답이 "형식이 틀렸습니다"와 "값이 틀렸습니다"처럼 서로 다른 두 종류의 실패 메시지를 줌

## 가장 먼저 할 것
문제 설명, 대회 공지, 서버 배너/응답 메시지를 다시 한번 확인해 정확한 flag 형식 문자열을 확보한다. 형식을 못 찾았다면 `strings ./chall | grep -E '\{.*\}'`로 중괄호가 포함된 문자열부터 훑어 후보 형식을 추정한다.

## 단계별 절차
1. 문제 설명/공지에서 flag 형식(`대회이름{...}`)을 확인한다. 없으면 서버 접속(`nc host port`) 후 아무 값이나 보내 응답 메시지에 형식 힌트가 있는지 확인한다.
2. 확보한 형식을 정규식으로 만들어 `strings ./chall | grep -E '형식_정규식'`으로 바이너리 안의 문자열을 필터링한다.
3. 코드에서 사용자 입력을 비교하는 상수(하드코딩된 배열, 문자열)를 찾으면 그 길이를 정확히 센다(`len()`, 또는 IDA/Ghidra에서 배열 크기 확인).
4. 위 참고표를 기준으로 그 길이/문자셋에 해당하는 알고리즘 후보를 1~2개로 좁힌다.
5. 후보 알고리즘의 특징적인 상수(예: SHA-256의 `0x6a09e667`, REV-0895/REV-0896/REV-0897)가 코드에 있는지 대조해 가설을 검증한다.
6. 형식/길이 조건이 확정되면, 브루트포스나 자동 풀이 스크립트의 문자셋·길이 범위를 그 조건에 맞게 고정해 탐색 공간을 최소화한다.

## 명령어/단축키
```bash
# 대회 flag 형식이 DH{...}로 공지된 경우
strings ./chall | grep -E 'DH\{[^}]*\}'

# 형식을 모를 때 중괄호 포함 문자열부터 넓게 훑기
strings ./chall | grep -E '\{[^}]*\}'
```
```python
# 비교 대상 문자열의 길이/문자셋으로 후보 추정
target = "5d41402abc4b2a76b9719d911017c592"  # 예시
print(len(target))                            # 32 -> MD5 가능성
print(all(c in "0123456789abcdef" for c in target))  # hex 여부 확인
```

## 출력 해석
- `grep` 결과가 정확히 형식에 맞는 한두 줄로 줄어들면 그 문자열이 실제 flag(또는 인코딩된 flag)일 가능성이 매우 높다.
- 길이 32에 순수 hex 문자셋이면 MD5 해시 결과일 가능성이 높지만, "MD5로 해시된 값과 비교"인지 "MD5 자체가 flag"인지는 코드 흐름을 봐야 한다 — 참고표는 알고리즘 추정용이지 flag 자체를 알려주지 않는다.
- 서버가 형식 오류와 값 오류를 다른 메시지로 구분해준다면, 형식 검사를 통과시키는 것과 실제 값을 맞추는 것이 별개의 두 문제라는 뜻이므로 각각 다른 전략(형식은 규칙 맞추기, 값은 알고리즘 역산)을 세운다.

## 흔한 실수
- flag 형식 정규식에서 중괄호(`{`, `}`)를 이스케이프하지 않아 `grep -E`가 의도와 다르게 동작하는 것(`\{`, `\}`로 이스케이프 필요).
- 특정 길이의 hex 문자열을 보고 무조건 "이건 MD5다"라고 단정한 뒤, 실제로는 CRC32 두 개를 이어붙인 값이거나 커스텀 인코딩이라는 걸 나중에 알고 시간을 낭비하는 것 — 참고표는 가설이지 확정이 아니다.
- 브루트포스 문자셋을 실제 조건보다 넓게 잡아(예: 대소문자+숫자+특수문자를 다 포함) 탐색 공간을 불필요하게 키우는 것.
- 문제 설명에 이미 형식이 적혀 있는데 확인하지 않고 바로 무차별 문자열 검색부터 시작하는 것.

## 막혔을 때 다음 체크
- 알고리즘 자체를 코드 패턴으로 판별하는 체크리스트가 필요하면 → REV-0885 알고리즘 유형별 판별 체크리스트
- 해시별 매직 상수를 직접 대조하고 싶으면 → REV-0895 SHA-256 흔적을 상수로 알아보는 법, REV-0896 SHA-1 흔적을 상수로 알아보는 법, REV-0897 MD5 흔적을 상수로 알아보는 법
- Base64/Base32/URL-safe 변형 알파벳이 헷갈리면 → REV-0879 Base64/Base32/Base16 알파벳 빠른 참조, REV-0903 URL-safe Base64 변형 알아보기
- 브루트포스가 시간 안에 끝날지 판단하는 기준이 필요하면 → REV-0219 Brute Force가 가능한 입력 공간 계산, REV-0920 시간 복잡도로 브루트포스 가능 여부 판단하는 실전 기준
- 문제 설명/첨부파일에서 다른 종류의 힌트를 더 뽑고 싶으면 → REV-0012 문제 설명과 첨부파일에서 힌트 뽑는 방법

## 미니 예제
문제 공지에 `Flag format: DH{...}`가 적혀 있고, 바이너리 안에 여러 문자열이 섞여 있는 상황을 가정한다.
```bash
$ strings ./chall | grep -E 'DH\{[^}]*\}'
DH{this_is_a_decoy_string}
DH{n0t_th3_r3al_0ne}
```
두 후보 모두 형식은 맞지만 실제 실행 로직과 비교했을 때 둘 다 디코이(가짜)일 수 있다. 이 경우 형식 필터링으로 "검토해야 할 후보를 수백 줄에서 2줄로 줄였다"는 것 자체가 목적이며, 최종 판별은 코드가 실제로 어떤 문자열과 비교하는지(REV-0006 검증 함수 찾기) 추적해서 확정해야 한다.

또 다른 예로, 코드에서 다음과 같은 비교를 발견했다고 하자.
```c
if (strlen(input) != 64) return 0;
// ... input을 해시한 뒤 hex로 변환해 아래 상수와 비교
if (strcmp(hexdigest, "2c26b46b68ffc68ff99b453c1d30413413422d706483bfa0f98a5e886266e7ae") != 0) return 0;
```
비교 대상이 정확히 64자리이므로 참고표에 따라 SHA-256 해시일 가능성을 1순위 가설로 세우고, 코드 안에서 SHA-256 초기값 상수(`0x6a09e667` 등, REV-0895)가 실제로 쓰이는지 확인해 가설을 검증하면 된다.

## 관련 글
- REV-0885 — 알고리즘 유형별 판별 체크리스트
- REV-0895 — SHA-256 흔적을 상수로 알아보는 법
- REV-0879 — Base64/Base32/Base16 알파벳 빠른 참조
- REV-0219 — Brute Force가 가능한 입력 공간 계산
- REV-0012 — 문제 설명과 첨부파일에서 힌트 뽑는 방법

## 출처/검증
- MD5(128비트/32자리 hex), SHA-1(160비트/40자리 hex), SHA-256(256비트/64자리 hex), CRC32(32비트/8자리 hex) 출력 길이: 각 알고리즘의 표준 명세(RFC 1321, RFC 3174, FIPS 180-4, ISO 3309 계열)에 정의된 출력 비트 길이 기준 (2026-09-10 확인).
- 표준 Base64(RFC 4648 §4, `A-Za-z0-9+/`와 `=` 패딩) 및 URL-safe Base64(RFC 4648 §5, `A-Za-z0-9-_`) 문자셋 차이: RFC 4648 명세 기준 (2026-09-10 확인).
- CTF 대회에서 flag 형식을 사전 공지하고 서버가 형식 검사와 값 검사를 분리해 처리하는 관행: CTF 대회 운영 및 참가 경험에서 널리 통용되는 일반적 관행 (2026-09-10 검증).
