## 한 줄 요약
정적 분석(디스어셈블리/디컴파일)으로 읽은 로직과 디버거로 관찰한 실제 실행 흐름이 다르다면, 대부분은 도구가 틀린 게 아니라 **런타임에 코드/데이터가 바뀌거나(self-modifying), 정적으로는 계산 안 되는 값(간접 호출, 환경 의존 분기)이 실행 시점에 결정**되기 때문이므로, 어느 지점부터 어긋나는지부터 좁혀야 한다.

## 언제 검색해야 하나
- 디컴파일 pseudocode를 보고 예상한 분기와 실제 디버거에서 관찰한 분기가 다를 때
- 정적 분석에서는 존재하지 않던 코드가 디버거로 돌리면 메모리에 나타날 때
- 같은 주소인데 실행 전(파일)과 실행 후(메모리 덤프)의 바이트가 다를 때
- 패킹/난독화가 의심되는 바이너리를 정적 분석만으로 다 이해했다고 생각했는데 실제 동작이 안 맞을 때

## 핵심 개념
정적 분석은 "파일에 저장된 바이트"를 근거로 코드를 재구성하고, 동적 분석(디버거)은 "실제로 메모리에 올라와 실행되는 바이트"를 관찰한다. 이 둘이 다르다는 것은 **실행 중에 코드나 분기 조건이 바뀐다**는 뜻이며, 원인은 다음과 같다.

1. **Self-modifying code / 언패킹 스텁** — 프로그램이 실행 초반에 자기 자신의 코드 섹션을 복호화하거나 덮어쓴다. 파일 상태의 바이트와 실행 중 메모리의 바이트가 달라지므로, 파일만 정적 분석하면 실제로 실행되는 코드를 볼 수 없다(REV-0230 참고).
2. **간접 호출/점프(레지스터·메모리 기반)** — `call rax`, `jmp [rbx+rcx*8]`처럼 대상 주소가 컴파일 시점에 고정되지 않고 런타임에 계산되는 경우, 정적 분석 도구는 실제 호출 대상을 정확히 알 수 없어 표시를 못 하거나 잘못 추정할 수 있다.
3. **환경 의존 분기(안티디버깅/안티VM)** — `ptrace` 결과, `IsDebuggerPresent`, `CPUID` 결과 등에 따라 분기하는 코드가 있으면, 정적으로 읽을 때의 "이상적인" 코드 경로와 실제 실행 환경에서의 경로가 달라진다(REV-0238 CPUID VM 탐지 참고).
4. **디컴파일러의 최적화 코드 오독** — 컴파일러 최적화로 변형된 패턴(루프 언롤링, 인라이닝, 점프 테이블)을 디컴파일러가 잘못 해석해서, pseudocode가 실제 로직을 정확히 반영하지 못하는 경우도 있다(REV-0011, REV-0167 참고). 이 경우는 코드가 실제로 바뀌는 게 아니라 도구의 "번역"이 부정확한 것이다.
5. **멀티스레드/타이밍** — 여러 스레드가 동시에 값을 바꾸는 코드는 정적으로 순서를 예측할 수 없다.

## 화면/코드에서 보이는 징후
- 디버거의 메모리 덤프(예: x64dbg Dump 뷰, GDB `x/20i`)에서 본 opcode가 IDA 정적 디스어셈블리와 특정 주소부터 다름
- IDA/Ghidra 디컴파일에서는 단순해 보이는 `if` 문인데, 디버거로 스텝하면 예상과 다른 분기로 감
- 정적 분석에서 CALL 대상이 `call rax` 형태로만 보이고 실제 함수 이름을 알 수 없음

## 가장 먼저 할 것
문제되는 지점(예상과 다르게 동작한 분기/호출)의 주소를 정확히 특정한 뒤, 그 주소의 **파일 상 바이트**와 **실행 중 메모리 바이트**를 나란히 비교한다. 다르면 self-modifying, 같으면 값 의존적 분기다.

## 단계별 절차

**1) 문제 지점 주소 특정**
디컴파일 pseudocode에서 이상하다고 느낀 `if`문/호출부에 대응하는 실제 주소를 IDA/Ghidra에서 확인해둔다(pseudocode 줄을 클릭하면 우측 하단에 대응 주소가 나온다).

**2) 디버거로 그 주소 도달 전/후 바이트 비교**
```gdb
break *0x401234
run
x/16xb 0x401234        # 실행 도달 시점의 실제 바이트
```
파일에서 같은 오프셋의 바이트(`objdump -d` 결과 또는 헥스 에디터)와 다르면 self-modifying code가 확정이다.

**3) 간접 호출이라면 실행 시점 레지스터 값 확인**
```gdb
break *0x401234
run
print $rax
x/3i $rax
```
`call rax` 지점에서 멈춰 `$rax`가 실제로 가리키는 주소를 확인하고, 그 주소로 정적 분석 도구에서 다시 이동해 그 함수를 분석한다.

**4) 환경 의존 분기라면 조건에 영향을 주는 값 추적**
`ptrace`, `IsDebuggerPresent`, `CPUID` 등의 반환값을 저장하는 변수에 워치포인트(`watch`)를 걸어 그 값이 언제 어떻게 분기에 쓰이는지 확인한다(REV-0642 GDB watch 참고).

**5) 최적화로 인한 디컴파일 오독이 의심되면 어셈블리로 직접 검증**
디컴파일러의 pseudocode를 무조건 신뢰하지 말고, 의심되는 구간만 어셈블리로 내려가 직접 플래그 연산과 분기 조건을 손으로 재구성한다(REV-0011 참고).

## 명령어/단축키
```gdb
break *ADDR
x/16xb ADDR         # 실행 중 실제 바이트
x/3i $rax            # 레지스터가 가리키는 코드
watch VAR
```
IDA: pseudocode 줄에서 우클릭 `Sync with disassembly` 또는 `Jump to disassembly`(스페이스바 토글)
x64dbg: `Dump` 창에서 실행 중 메모리 바이트 확인, 파일 오프셋은 우클릭 `Follow in Disassembler` 대비

## 출력 해석
- `x/16xb 0x401234` 결과가 파일의 같은 오프셋 바이트와 다르면, 그 사이에 어떤 코드가 이 메모리를 덮어썼다는 뜻 — self-modifying code 확정. `watch *0x401234`를 걸어 언제 바뀌는지 역추적한다.
- `call rax`에서 `$rax`가 실행마다 다른 값을 가리키면 동적 디스패치(가상함수, 함수 포인터 테이블)이며, 정적 분석 시점에는 전체 후보를 다 알 수 없을 수 있다.
- 조건 분기 직전 `watch`한 변수의 `Old value`/`New value`가 안티디버깅/환경 체크 함수 호출 직후 바뀐다면, 그 분기는 실행 환경에 의존한다.

## 흔한 실수
- 디컴파일 결과를 실행 코드와 100% 동일하다고 맹신하는 것 — 특히 최적화가 강하게 들어간 바이너리에서는 디컴파일러도 실수할 수 있다.
- self-modifying code를 의심하지 않고 정적 분석 결과만으로 전체 로직을 재현하려다 몇 시간을 낭비하는 것.
- 간접 호출(`call rax` 등)을 보고 "분석 불가능"이라고 포기하는 것 — 디버거로 한 번만 실행해보면 실제 대상 주소를 바로 알 수 있다.
- 안티디버깅으로 분기가 바뀌는 걸 모르고 "왜 디버거에서는 다르게 동작하지"라고 반대로 헷갈리는 것(이 경우는 REV-0584, REV-0329도 함께 참고).

## 막혔을 때 다음 체크
- self-modifying code 자체 개념이 처음이라면 → REV-0230 Self-modifying Code 기초.
- 패킹/난독화 때문에 정적分석을 포기하고 동적으로 전환해야 하는 기준이 필요하면 → REV-0241 패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환.
- 디컴파일 코드 자체가 못 믿을 만큼 이상하다면 → REV-0011 디컴파일 코드가 이상할 때 어셈블리로 돌아가는 기준.
- 디버거에서만 분기가 다르게 보인다면(반대 상황) → REV-0584 디버거에서 실행하면 다른 분기를 타는 것처럼 보일 때.

## 미니 예제
```gdb
(gdb) break *0x401500
(gdb) run
(gdb) x/8xb 0x401500
0x401500: 0x48 0x89 0xe5 0x90 0x90 0x90 0x90 0x90
```
```bash
$ objdump -d chall | grep -A2 "401500:"
  401500:  90                      nop
  401501:  90                      nop
  401502:  90                      nop
```
파일 상 `0x401500`은 전부 `nop`(0x90)인데, 실제 실행 중 메모리에서는 `48 89 e5`(`mov rbp, rsp`)로 바뀌어 있다. 이는 실행 초반 어딘가에서 이 위치를 언패킹/복호화 루틴이 덮어썼다는 확실한 증거이며, 정적 분석만으로는 이 지점의 진짜 코드를 볼 수 없다.

## 관련 글
- REV-0230 — Self-modifying Code 기초
- REV-0241 — 패커와 난독화 때문에 디컴파일이 틀릴 때 정적/동적 전환
- REV-0011 — 디컴파일 코드가 이상할 때 어셈블리로 돌아가는 기준
- REV-0584 — 디버거에서 실행하면 다른 분기를 타는 것처럼 보일 때

## 출처/검증
- self-modifying code와 언패킹 스텁의 동작 원리: 일반 리버스 엔지니어링 교재 개념(패커/언패킹 관련 공개 자료) 기준 (2026-09-09 검증).
- GDB `x` 명령으로 실행 중 메모리 바이트를 확인하는 방법: GDB 공식 매뉴얼 "Examining Memory" 섹션 기준.
