## 한 줄 요약
문제를 열어서 5분 안에 파일 크기, 보호 기법 개수, 함수 개수, 문자열 힌트, solve 수(있다면) 다섯 가지만 확인하면 "지금 풀 것"과 "나중에 풀 것"을 대부분 구분할 수 있고, 이 판단을 빨리 할수록 대회 전체 점수가 올라간다.

## 언제 검색해야 하나
- 여러 문제 중 어떤 것부터 손대야 할지 정해야 할 때
- 겉보기엔 배점이 낮은데 막상 열어보니 복잡해 보여서 계속할지 넘어갈지 판단이 필요할 때
- 팀원에게 "이 문제 몇 시간짜리 같다"고 보고해야 할 때
- 이미 30분 넘게 붙잡고 있는데 원래 난이도 추정이 맞았는지 재확인하고 싶을 때

## 핵심 개념
CTF에서 문제 배점(포인트)은 난이도를 정확히 반영하지 않는 경우가 많다. 동적 배점 시스템(solve 수가 늘어날수록 점수가 낮아지는 방식)에서는 배점이 낮아 보여도 초반에는 고득점이었을 수 있고, 반대로 배점이 높아도 출제자가 단순히 시간이 오래 걸리는 노가다성 문제를 어렵다고 착각해서 배점을 높였을 수도 있다. 그래서 배점이 아니라 **직접 관찰 가능한 신호**로 난이도를 스스로 가늠하는 습관이 필요하다.

난이도를 가늠하는 다섯 가지 체크포인트는 다음과 같다.

**1) 파일 크기**: 수 KB~수십 KB의 작은 바이너리는 보통 로직이 단순하다. 수백 KB~수 MB는 정적 링킹(REV-0646)이거나 라이브러리가 포함된 경우다. 라이브러리 포함 자체는 난이도와 무관할 수 있지만, 사용자 코드가 아닌 부분(libc, C++ 런타임)까지 다 뒤져야 하면 체감 난이도가 올라간다.

**2) 보호 기법 개수**: `checksec` 결과에서 Canary, NX, PIE, RELRO 등이 몇 개나 켜져 있는지, DIE(Detect It Easy)로 패킹 여부를 확인한다(REV-0224 패킹된 바이너리인지 의심하는 기준). 순수 리버싱 문제(pwn이 아닌)에서는 이 항목들 자체보다 **안티디버깅 유무**(REV-0234~0240 계열)가 더 중요한 난이도 신호다. 안티디버깅이 여러 겹 걸려 있으면 동적 분석 자체에 시간이 든다.

**3) 함수 개수와 크기**: strip 여부와 무관하게, Functions 목록에서 사용자 정의로 보이는 함수가 몇 개인지, 그중 가장 큰 함수의 크기가 어느 정도인지 훑는다. 함수가 5개 이하면 대체로 짧은 문제, 수십 개 이상이면 로직이 여러 단계로 쪼개져 있을 가능성이 높다(REV-0313, REV-0314 참고).

**4) 문자열/문제 설명 힌트**: 문자열 창에 "Stage", "Level", "VM", "opcode" 같은 단어가 보이면 다단계나 커스텀 VM 문제일 가능성을 미리 의심할 수 있다(REV-0314, REV-0315). 문제 설명 자체에 "천천히 분석하세요", "brute force는 불가능합니다" 같은 문구가 있으면 출제자가 이미 난이도 힌트를 준 것이다(REV-0012).

**5) solve 수/순위표(있다면)**: 진행 중인 대회라면 스코어보드에서 해당 문제의 solve 수를 본다. 대회 시작 직후인데 이미 solve가 여러 건이면 생각보다 쉬운 문제일 가능성이 높고, 대회 막바지인데 solve가 0~1건이면 정말 어렵거나 버그가 있는 문제일 수 있다.

## 화면/코드에서 보이는 징후
- Functions 목록에 이름 없는 `sub_` 함수가 수십~수백 개 나열되어 있다.
- 문자열 창에 여러 단계를 암시하는 단어(Stage, Level, Round, Part)가 보인다.
- `checksec` 결과에 보호 기법이 전부 켜져 있거나(Full RELRO, Canary, PIE, NX 전부 Yes), 반대로 전부 꺼져 있다(연습용으로 단순화된 문제일 가능성).
- DIE 실행 시 엔트로피가 높게 나오고 알려진 패커 시그니처가 잡힌다.

## 가장 먼저 할 것
파일을 받으면 분석 도구를 열기 전에 `file`, `checksec`(또는 DIE), `strings`만 먼저 돌려서 위 다섯 체크포인트 중 1~4번을 2~3분 안에 훑는다. 이 단계에서 아직 어떤 함수도 자세히 읽지 않는다 — 목적은 로직 이해가 아니라 "이 문제에 얼마나 투자할지" 결정하는 것이다.

## 단계별 절차
1. `file ./chall`로 포맷과 정적/동적 링킹, strip 여부 확인
2. `checksec --file=./chall` 또는 DIE로 보호 기법과 패킹 여부 확인
3. `strings ./chall | less`로 훑으며 Stage/Level/VM/opcode 등 키워드 스캔
4. IDA/Ghidra로 열어 Functions 목록 개수와 가장 큰 함수 크기만 확인(아직 디컴파일 코드를 정독하지 않는다)
5. 진행 중인 대회면 스코어보드에서 solve 수 확인
6. 위 정보를 종합해 "5분짜리/30분짜리/1시간 이상짜리" 세 등급 중 하나로 잠정 분류
7. 분류 결과를 팀 노트나 개인 노트에 기록해두고(REV-0014), 실제로 풀어가면서 예상이 맞았는지 갱신

## 명령어/단축키
```bash
file ./chall
checksec --file=./chall
strings ./chall | grep -iE "stage|level|round|part|vm|opcode"
```
IDA/Ghidra: `Ctrl+P`(함수 목록 열기) 후 Size 열 기준 정렬로 가장 큰 함수 확인.

## 출력 해석
- `strings` 결과에서 "Stage 1", "Stage 2" 같은 문구가 실제로 나오면 REV-0314(다단계 검증)로 바로 넘어가는 게 낫다 — 처음부터 전체를 한 번에 풀려고 하지 않는다.
- Functions 목록에 함수가 극단적으로 적은데(1~3개) 파일 크기는 크다면, 정적 링킹으로 라이브러리 코드가 섞여 있어서 실제 사용자 로직은 그 몇 개 함수 안에 집중되어 있다는 뜻이다 — 오히려 분석 범위가 좁혀진 것으로 봐도 된다.
- 보호 기법이 전부 꺼져 있는 문제는 대체로 입문자용으로 설계된 것이므로, 다른 체크포인트가 애매해도 낮은 난이도로 잠정 분류해도 무방하다.

## 흔한 실수
- 배점만 보고 난이도를 판단해서, 실제로는 쉬운데 배점이 높다는 이유만으로 건너뛰거나 반대로 시간을 낭비하는 것.
- 함수 하나를 이미 열어서 코드를 읽기 시작해놓고 "일단 다섯 체크포인트부터"라며 되돌아가지 않는 것 — 순서를 지켜야 판단이 빠르다.
- 체크포인트 확인에 5분 이상 쓰는 것 — 이 단계는 어디까지나 빠른 감 잡기이지 분석이 아니다.
- 한 번 내린 난이도 판단을 절대적으로 믿고, 실제로 풀다가 예상과 다르다는 신호(REV-0015)가 나와도 재평가하지 않는 것.

## 막혔을 때 다음 체크
- 이미 시간을 많이 썼는데 난이도 예측이 틀렸던 것 같다 → REV-0015 막혔을 때 5분 체크리스트
- 여러 문제 중 우선순위를 정하는 기준이 더 필요하다 → REV-0301 문제 파일이 여러 개일 때 우선순위 정하는 법 (예정)
- 시간이 부족한 게 확실해졌다 → REV-0312 시간이 부족할 때 부분점수를 노리는 전략
- 팀으로 참가 중이라 분업 기준이 필요하다 → REV-0311 팀 대회에서 리버싱 문제를 분업하는 법

## 미니 예제
문제 A는 파일 크기 12KB, `checksec` 결과 보호 기법이 전부 꺼져 있고, Functions 목록에 함수 4개, 문자열에 "Enter password:"만 보인다 — 5분짜리로 잠정 분류. 문제 B는 파일 크기 2.1MB(정적 링킹), 보호 기법이 전부 켜져 있고, 문자열에 "Stage 1 passed, entering Stage 2..."가 보이며 Functions 목록에 사용자 함수로 추정되는 것이 30개 이상이다 — 다단계 구조가 확실하므로 1시간 이상짜리로 분류하고, REV-0314 절차를 참고해 스테이지 단위로 나눠서 접근하기로 계획을 세운다.

## 출처/검증

- `checksec`, DIE(Detect It Easy) 사용법: 각 도구 공식 문서 기준.
