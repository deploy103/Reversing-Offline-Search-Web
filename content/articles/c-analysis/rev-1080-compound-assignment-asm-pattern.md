## 한 줄 요약
`x += y` 같은 복합 대입 연산자는 항상 "현재 값을 읽고(Read) → 연산하고(Modify) → 다시 쓴다(Write)"는 세 단계로 컴파일되는데, 대상이 단순 지역 변수면 레지스터/스택 슬롯 하나로 짧게 끝나지만 대상이 포인터 역참조(`*p += y`)나 배열 원소(`arr[i] += y`)라면 주소 계산까지 매번 다시 해야 해서 명령어 수가 눈에 띄게 늘어난다.

## 언제 검색해야 하나
- 소스에는 `+=` 한 줄인데 어셈블리에는 `mov`(읽기) → 연산(`add`/`sub`/`imul` 등) → `mov`(쓰기)가 세 개 이상의 줄로 나뉘어 있어서 왜 이렇게 긴지 궁금할 때
- 포인터를 두 번 로드하는 것처럼 보이는 코드(`mov rax, [rbp-N]`이 연달아 두 번 나오는데 그 사이에 값 읽기/쓰기가 끼어 있는 형태)를 만났을 때
- `*counter += delta;` 같은 코드에서 그냥 `add`가 아니라 왜 포인터 역참조 로드가 앞뒤로 붙어 있는지 확인해야 할 때
- 같은 변수에 대해 여러 개의 복합 대입이 연달아 있을 때, 컴파일러가 중간값을 재사용하는지 매번 새로 읽는지 최적화 여부를 판단해야 할 때

## 핵심 개념
`x += y`는 의미상 `x = x + y`와 같지만, 대상 `x`가 메모리에 있는 경우(레지스터에만 있지 않은 경우) 반드시 그 메모리를 한 번 읽어서(Read) 값을 얻고, 연산을 수행해서(Modify) 새 값을 만들고, 다시 그 메모리에 써야(Write) 한다. 대상이 단순 변수면 이 3단계가 짧게 끝나지만, 대상이 포인터가 가리키는 곳이라면 "그 포인터가 가리키는 주소"를 계산하는 과정이 읽기 전과 쓰기 전에 각각 필요할 수 있어 코드가 늘어난다.

```c
void update(int *counter, int delta) {
    *counter += delta;   /* 포인터 대상 += : 주소 계산 + 읽기 + 연산 + 주소 계산 + 쓰기 */
    *counter *= 2;        /* 포인터 대상 *= : 동일한 4단계 반복 */
}
```

x86-64 SysV, `-O0`, Intel 문법:

```asm
update:
    push    rbp
    mov     rbp, rsp
    mov     [rbp-24], rdi     ; counter 저장 (포인터)
    mov     [rbp-28], esi     ; delta 저장
    mov     rax, [rbp-24]     ; rax = counter                (주소 계산: *counter 위치)
    mov     edx, [rax]        ; edx = *counter               (읽기, Read)
    mov     eax, [rbp-28]     ; eax = delta
    add     edx, eax          ; edx = *counter + delta        (연산, Modify)
    mov     rax, [rbp-24]     ; rax = counter                 (주소 계산을 다시 함: 쓰기 위해)
    mov     [rax], edx        ; *counter = edx                (쓰기, Write)
    mov     rax, [rbp-24]     ; rax = counter                 (다음 문장을 위한 주소 계산)
    mov     edx, [rax]        ; edx = *counter                (읽기)
    sal     edx, 1            ; edx = *counter << 1 = *counter * 2   (연산: *=2가 왼쪽 시프트로 컴파일됨)
    mov     rax, [rbp-24]     ; rax = counter                 (주소 계산)
    mov     [rax], edx        ; *counter = edx                (쓰기)
    pop     rbp
    ret
```

`*counter += delta;` 한 줄이 무려 6개의 명령어(주소 계산 2번, 읽기 1번, 연산 1번, 쓰기 1번, 그리고 delta 로드)로 풀린 것을 볼 수 있다. 특히 `mov rax, [rbp-24]`가 두 번 반복되는 것은 "포인터가 가리키는 주소"를 읽기 직전과 쓰기 직전에 각각 다시 계산했기 때문이다(`-O0`는 최적화를 하지 않아 값을 재사용하지 않고 매번 다시 로드한다). 만약 대상이 단순 지역 변수(`int x; x += delta;`)였다면 주소 계산 없이 `mov`(읽기)+`add`+`mov`(쓰기) 정도로 훨씬 짧게 끝난다.

## 화면/코드에서 보이는 징후
- 같은 포인터 변수를 읽는 `mov`가 짧은 구간 안에서 두 번 이상 반복되고, 그 사이에 역참조 읽기/쓰기가 끼어 있음
- `add`/`sub`/`imul`/`sal`/`sar`/`and`/`or`/`xor` 등의 연산 명령 앞뒤로 정확히 같은 주소를 향한 로드(읽기)와 스토어(쓰기)가 짝을 이룸
- `*=2`, `*=4`, `*=8` 같은 2의 거듭제곱 곱셈이 `imul` 대신 `sal`(shift left)로 나타남 — 시프트가 곱셈보다 빠르기 때문에 컴파일러가 자주 치환함
- 배열 원소에 대한 복합 대입(`arr[i] += y`)이라면 주소 계산 부분에 인덱스 곱셈(`i * 4` 등)까지 추가로 포함됨

## 가장 먼저 할 것
연산(`add`/`sub`/`imul` 등) 명령을 기준으로 그 직전에 읽기용 `mov`, 직후에 쓰기용 `mov`가 정확히 같은 주소를 대상으로 하는지 짝을 맞춰본다. 짝이 맞으면 그 셋을 하나의 복합 대입 연산자로 묶어서 해석하면 된다.

## 단계별 절차
1. 연산 명령어(`add`, `sub`, `imul`, `sal` 등)를 기준점으로 잡는다.
2. 그 직전에 있는 읽기(`mov reg, [주소]`)와 직후에 있는 쓰기(`mov [주소], reg`)가 같은 주소를 향하는지 확인한다.
3. 같은 주소라면 이것을 `*주소 = *주소 OP 값` 형태, 즉 원래 소스의 `대상 OP= 값`으로 재구성한다.
4. 대상이 단순 변수인지 포인터 역참조/배열 원소인지에 따라 주소 계산 명령어(포인터 로드, 인덱스 곱셈)가 앞뒤에 추가로 붙어 있는지 확인해 정확한 소스 형태(`*p += x`, `arr[i] += x`, `x += y`)를 구분한다.

## 명령어/단축키
- IDA: pseudocode(F5)에서 대개 `*counter += delta;` 형태로 이미 깔끔하게 복원되므로, 어셈블리와 대조해 "이 여러 줄이 한 문장이었구나"를 확인하는 용도로 사용
- Ghidra: Decompile 창에서 동일하게 복합 대입 형태 복원 확인
- GDB: 연산 명령 전후에 각각 브레이크포인트를 걸고 `x/dw 주소`로 읽기 전/쓰기 후 값을 비교해 Read-Modify-Write가 실제로 일어나는지 확인
- x64dbg: 메모리 감시식(watch)에 대상 주소를 등록해 명령어 스텝마다 값이 언제 바뀌는지 관찰

## 출력 해석
연산 명령 전후의 두 `mov`가 같은 주소를 대상으로 하고 있다면, 이는 하나의 복합 대입 연산자가 컴파일된 결과다. 특히 포인터 역참조 대상일 때 주소 로드(`mov rax, [rbp-24]`)가 읽기 전과 쓰기 전에 각각 나타난다면, 이는 최적화가 꺼져 있어(`-O0`) 컴파일러가 "포인터 값 자체는 바뀌지 않으니 한 번만 로드해도 된다"는 최적화를 적용하지 않았기 때문이다. 최적화를 켠 버전에서는 이 중복 로드가 사라지고 레지스터에 캐시된 주소를 재사용하는 경우가 많다.

## 흔한 실수
- 복합 대입 대상이 항상 `mov`+연산+`mov`의 정확히 3개 명령으로만 끝난다고 예상하는 것 — 포인터/배열 대상이면 주소 계산이 추가되어 5~7개 이상으로 늘어날 수 있다.
- `*=2`, `*=4` 등이 `imul`이 아니라 `sal`(시프트)로 나오는 것을 보고 곱셈이 아니라 다른 연산이라고 오해하는 것 — 2의 거듭제곱 곱셈은 시프트와 수학적으로 동일하며 컴파일러가 흔히 치환한다.
- 같은 주소에 대한 두 번의 로드(`mov rax, [rbp-24]`가 두 번)를 보고 "포인터 값이 바뀌는 게 아닌가"라고 의심하는 것 — 대부분의 경우 `-O0`의 비최적화 특성일 뿐, 포인터 자체 값은 두 로드 사이에 변하지 않는다(둘 다 같은 `[rbp-24]`에서 읽으므로 값은 동일).
- 비트필드/구조체 멤버에 대한 복합 대입(REV-1071의 `shr`/`and`/`shl`/`or` 패턴)과 일반 정수 변수의 복합 대입을 혼동해 "왜 이번엔 `and`가 더 있지?"라고 헷갈리는 것 — 비트필드는 읽기/쓰기 단계에 마스킹이 추가로 필요하다.

## 막혔을 때 다음 체크
- 복합 대입 대상이 비트필드 멤버라면 마스킹이 추가되는 이유가 → REV-1071 비트필드 구조체가 어셈블리에서 보이는 패턴
- 복합 대입의 오른쪽 값이 삼항 연산자 결과라면 → REV-1073 삼항 연산자(?:)가 CMOV 또는 분기로 컴파일되는 패턴
- 대상이 배열 원소(`arr[i] += y`)일 때 인덱스 계산 부분이 궁금하면 → REV-1058 1차원 배열 인덱싱이 어셈블리에서 보이는 패턴(예정)

## 미니 예제
전역 배열의 특정 원소에 값을 누적하는, 주소 계산이 포함된 복합 대입 예다.

```c
int scores[5];

void add_score(int idx, int points) {
    scores[idx] += points;   /* 배열 원소 대상 += : 인덱스 계산 + 읽기 + 연산 + 쓰기 */
}
```

```asm
add_score:
    push    rbp
    mov     rbp, rsp
    mov     [rbp-20], edi      ; idx 저장
    mov     [rbp-24], esi      ; points 저장
    mov     eax, [rbp-20]      ; eax = idx
    cdqe                       ; 64비트로 부호 확장
    lea     rdx, [rax*4]       ; rdx = idx * 4바이트  (원소 오프셋 계산)
    lea     rax, [rip+scores]  ; rax = scores 배열의 시작 주소
    add     rax, rdx           ; rax = &scores[idx]           (주소 계산 완료)
    mov     edx, [rax]         ; edx = scores[idx]             (읽기)
    mov     eax, [rbp-24]      ; eax = points
    add     edx, eax           ; edx = scores[idx] + points     (연산)
    lea     rax, [rip+scores]  ; rax = scores 시작 주소 (쓰기 위해 주소를 다시 계산)
    mov     ecx, [rbp-20]      ; ecx = idx (인덱스 다시 로드)
    movsxd  rcx, ecx
    lea     rax, [rax+rcx*4]   ; rax = &scores[idx]            (주소 계산 재수행)
    mov     [rax], edx         ; scores[idx] = edx              (쓰기)
    pop     rbp
    ret
```

단순 변수 대입과 비교하면 명령어 수가 두 배 이상 늘어난 것을 볼 수 있는데, 그 이유는 "몇 번째 원소인지" 계산하는 인덱스 연산(`idx * 4` + 배열 시작 주소)이 읽기 전과 쓰기 전에 각각 다시 이루어지기 때문이다. 이 패턴만 알아두면 아무리 길어 보이는 코드도 결국 "주소 계산 → 읽기 → 연산 → 주소 계산 → 쓰기"라는 5단계로 정리해서 읽을 수 있다.

## 관련 글
- REV-1071 — 비트필드 구조체가 어셈블리에서 보이는 패턴
- REV-1073 — 삼항 연산자(?:)가 CMOV 또는 분기로 컴파일되는 패턴
- REV-1058 — 1차원 배열 인덱싱이 어셈블리에서 보이는 패턴

## 출처/검증
- 복합 대입 연산자가 `x = x op y`와 동치이며 메모리 대상일 때 Read-Modify-Write 3단계로 컴파일된다는 규칙: C 표준(ISO/IEC 9899) 복합 대입 연산자 섹션 기준.
- 2의 거듭제곱 곱셈이 시프트 명령으로 대체(strength reduction)되는 컴파일러 최적화: 일반적인 컴파일러 최적화 기법 문서 및 실제 gcc/clang `-O0`/`-O1` 출력 비교로 반복 확인 (2026-09-10 검증).
