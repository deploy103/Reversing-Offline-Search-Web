## 한 줄 요약
전처리기 매크로(`#define`)는 컴파일 이전 텍스트 치환 단계에서 이미 호출 지점에 그대로 풀려서 들어가므로 애초에 함수라는 개념 자체가 존재하지 않고, `static inline` 함수는 컴파일러가 실제로 인라인을 적용하면 `call`/`push`/`pop`/`ret` 없이 그 함수의 본문이 호출 지점에 통째로 복사되어 나타난다 — 둘 다 최종 결과는 "함수처럼 보이던 코드가 CALL 명령 없이 사라진다"는 점에서 같다.

## 언제 검색해야 하나
- 소스코드에는 분명 함수/매크로 호출이 있는데 디스어셈블 결과에는 `call` 명령이 하나도 없어서 "이 함수가 사라졌나?" 의심될 때
- 똑같은 계산(예: 제곱, 최댓값)을 하는 짧은 코드 블록이 여러 함수 안에 반복해서 나타나는데, 소스에서는 한 번만 정의된 함수/매크로를 호출하고 있을 때
- IDA/Ghidra의 Functions 목록에 소스코드에서 정의한 짧은 헬퍼 함수 이름이 안 보여서 "빌드가 잘못됐나?" 의심될 때
- 매크로에 부작용이 있는 인자(`x++` 같은)가 들어갔을 때 왜 여러 번 증가하는지 원인을 어셈블리로 추적해야 할 때

## 핵심 개념
매크로와 인라인 함수는 "함수처럼 보이지만 실제로는 별도의 호출 가능한 코드 블록을 만들지 않는다"는 공통점이 있다. 매크로는 전처리기가 소스 텍스트 자체를 치환하므로 컴파일러는 매크로라는 것을 아예 모르고 이미 풀려있는 코드만 본다. `static inline` 함수는 실제로 함수로 정의되지만, 컴파일러가 호출부에 본문을 복사해 넣기로 결정하면(주로 `-O1` 이상, 함수가 짧을 때) 별도의 `call`이 생기지 않는다.

```c
#define SQUARE(x) ((x) * (x))

static inline int cube(int x) {
    return x * x * x;
}

int compute(int n) {
    return SQUARE(n) + cube(n);
}
```

x86-64 SysV, `-O1`, Intel 문법:

```asm
compute:
    imul    edx, edi, edi     ; edx = n*n            (SQUARE(n) 매크로가 이미 전처리 단계에서 (n)*(n)으로 치환된 결과, 호출 개념 자체가 없음)
    imul    eax, edx, edi     ; eax = edx*n = n*n*n   (cube(n) 인라인 함수 본문이 그대로 복사되어 전개된 결과, call 없음)
    add     eax, edx          ; eax = cube(n) + SQUARE(n)
    ret
```

전체 함수가 `imul` 두 번과 `add` 한 번, `ret` 하나로 끝난다. 소스에는 `SQUARE`라는 매크로와 `cube`라는 별도의 함수가 있었지만, 최종 어셈블리에는 그 어느 쪽도 독립된 코드 블록이나 `call` 명령으로 존재하지 않는다. `SQUARE(n)`은 전처리기가 `((n) * (n))`으로 그냥 텍스트를 바꿔버렸을 뿐이고, `cube(n)`은 컴파일러가 `n * n * n` 계산을 `compute` 함수 내부에 직접 풀어서 넣은 것이다.

## 화면/코드에서 보이는 징후
- 소스에서 이름이 붙은 함수인데 IDA/Ghidra Functions 목록, 또는 `nm`/`objdump` 심볼 목록에 그 이름이 안 보임(완전히 인라인되어 독립 함수로 남지 않음)
- 여러 다른 함수 안에서 똑같은 짧은 명령어 시퀀스(같은 연산 순서)가 반복해서 나타남 — 각각이 매크로/인라인 함수를 호출한 자리에 복사되어 들어간 것
- `call` 명령이 있어야 할 자리에 대신 몇 개의 산술/논리 명령어만 있고 `push`(인자 준비)/`pop`(정리)도 없음
- 컴파일러 최적화 리포트(`-Winline`, `-fopt-info-inline` 등)를 켜면 "inlined into"라는 메시지로 실제 인라인 여부를 컴파일 시점에 확인 가능

## 가장 먼저 할 것
사라진 것으로 보이는 함수 이름을 심볼 테이블(`nm`, IDA Functions 목록)에서 검색해 정말 독립된 함수로 존재하지 않는지 확인한다. 존재하지 않는다면, 그 함수를 호출했을 것으로 예상되는 다른 함수들의 본문 안에서 비슷한 연산 패턴이 반복되는지를 찾는다.

## 단계별 절차
1. 사라진 함수/매크로 이름을 심볼 테이블에서 검색해 독립 함수로 남아있는지 확인한다.
2. 없다면, 그 함수를 호출했을 상위 함수들의 디스어셈블을 열어 짧고 반복적인 연산 시퀀스를 찾는다.
3. 그 시퀀스가 매크로/인라인 함수의 원래 로직(제곱, 최댓값 등 단순 계산)과 일치하는지 소스와 대조한다.
4. 여러 호출 지점에서 같은 패턴이 복사되어 나타나는지 확인해, 이것이 인라인/매크로 전개의 결과임을 확정한다.

## 명령어/단축키
- IDA: Functions 창(`Shift+F3`)에서 이름 검색, 없으면 인라인/매크로로 사라졌을 가능성 우선 고려
- Ghidra: Symbol Tree에서 함수 검색, Decompile 결과에 원래 함수 호출 흔적이 없는지 확인
- GDB: `info functions 함수이름`으로 심볼 존재 여부 확인
- 컴파일 시점 확인(소스가 있을 때): gcc `-Winline`, `-fopt-info-inline-optimized` 로 실제 인라인된 함수 목록 출력

## 출력 해석
`call` 없이 산술 명령만 반복된다면, 그 코드는 매크로 전개 또는 성공적인 인라인화의 결과다. 반대로 짧은 함수인데도 여전히 `call`이 남아있다면, `-O0`로 컴파일되었거나(인라인은 대개 최적화가 있어야 실제로 적용됨) 컴파일러가 인라인하기엔 함수가 너무 크다고 판단했거나, `inline` 힌트만 주고 `static`을 빼서 별도 심볼이 유지된 경우일 수 있다.

## 흔한 실수
- `inline` 키워드가 있으면 무조건 인라인된다고 생각하는 것 — `inline`은 컴파일러에게 주는 힌트일 뿐이며, 실제 적용 여부는 컴파일러의 판단(함수 크기, 최적화 레벨)에 달려 있다.
- 매크로 인자에 부작용이 있는 표현식(`SQUARE(x++)`)을 넣었을 때 실제로 몇 번 평가되는지 어셈블리로 확인하지 않고 "함수처럼 한 번만 평가될 것"이라 가정하는 것 — 매크로는 텍스트 치환이므로 인자가 매크로 본문에서 여러 번 나타나면 그만큼 여러 번 평가된다.
- `-O0`로 빌드된 바이너리에서 `static inline` 함수를 찾다가 실제로는 `call`이 남아있는 걸 보고 "인라인이 안 됐으니 이 지식이 틀렸다"고 오해하는 것 — `-O0`에서는 최적화 자체가 거의 꺼져 있어 인라인도 잘 일어나지 않는 경우가 많다.
- 매크로 전개와 인라인 함수 전개를 구분하지 않고 뭉뚱그려 "둘 다 그냥 컴파일러가 알아서 한 것"이라고만 생각하는 것 — 매크로는 전처리기(컴파일 이전) 단계, 인라인은 컴파일러 최적화(컴파일 중) 단계로 서로 다른 시점에 일어난다.

## 막혔을 때 다음 체크
- 인라인으로 인해 함수 흐름이 어떻게 바뀌는지 더 배경지식이 필요하면 → REV-0357 함수 인라인이 코드 흐름에 미치는 영향
- CALL이 하나도 없는 함수를 실제로 만나서 원인을 찾는 실전 절차가 필요하면 → REV-0495 인라인된 함수 때문에 CALL이 하나도 없는 함수를 만났을 때
- 컴파일러가 인라인한 `memcpy`/`memset` 같은 표준 라이브러리 함수 패턴이 궁금하면 → REV-1070 컴파일러가 인라인한 memcpy/memset이 어셈블리에서 보이는 패턴(예정)

## 미니 예제
매크로 인자의 부작용이 여러 번 평가되는 것을 실제로 보여주는 예다.

```c
#define DOUBLE_IT(x) ((x) + (x))

int demo(int n) {
    return DOUBLE_IT(n++);   /* 위험한 사용: n++이 매크로 본문에서 두 번 나타남 */
}
```

```asm
demo:
    push    rbp
    mov     rbp, rsp
    mov     [rbp-4], edi      ; n 저장
    mov     eax, [rbp-4]      ; eax = n            (첫 번째 (x) 자리, 치환 결과 n)
    mov     edx, [rbp-4]      ; edx = n            (아직 증가 전 값)
    add     edx, 1
    mov     [rbp-4], edx      ; n = n + 1          (첫 번째 (x)에서 n++가 부작용으로 증가 실행)
    mov     ecx, [rbp-4]      ; ecx = n(이미 증가된 값!)   (두 번째 (x) 자리, 다시 n++로 치환되어 또 증가)
    add     ecx, 1
    mov     [rbp-4], ecx      ; n = n + 1          (두 번째 증가)
    add     eax, ecx          ; 결과 = 첫 evaluation 값 + 두 번째 evaluation 이후 값 (정의되지 않은/혼란스러운 결과)
    pop     rbp
    ret
```

`DOUBLE_IT(n++)`가 `((n++) + (n++))`로 그대로 텍스트 치환되기 때문에 `n++`이라는 부작용이 코드에 두 번 나타나고, 실제로 `n`이 두 번 증가한다. 이는 함수 호출이었다면 인자가 딱 한 번만 평가되어 절대 일어날 수 없는 현상으로, 매크로가 "함수처럼 보이지만 함수가 아니다"라는 것을 보여주는 대표적인 함정이다.

## 출처/검증
- 전처리기 매크로가 컴파일 이전 텍스트 치환 단계에서 처리되어 컴파일러가 함수 호출로 인식하지 않는다는 규칙: C 표준(ISO/IEC 9899) 전처리기(preprocessing) 섹션 기준.
- `inline`/`static inline` 키워드가 컴파일러에게 힌트일 뿐이며 실제 인라인 적용은 최적화 레벨과 함수 크기에 따라 컴파일러가 결정한다는 점: gcc/clang 공식 문서(inline 함수 처리) 및 실제 `-O0` vs `-O1` 출력 비교로 반복 확인 (2026-09-10 검증).
