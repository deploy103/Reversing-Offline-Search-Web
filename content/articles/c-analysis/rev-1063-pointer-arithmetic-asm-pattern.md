## 한 줄 요약
`p + n` 같은 포인터 산술은 실제로는 `n * sizeof(가리키는 타입)`만큼 주소를 이동시키는 연산이며, 어셈블리에서는 대부분 `LEA`(주소 계산) 명령 하나로, 크기가 1/2/4/8바이트인 경우 스케일 인덱스(`[reg + reg*4]`)로 압축되어 나타난다.

## 언제 검색해야 하나
- `p + 1`인데 어셈블리에서 4나 8이 더해져 있어서 "덧셈이 왜 이렇게 되나" 헷갈릴 때
- `lea rax, [rdi+rsi*4]`처럼 `*4`, `*8`이 붙은 `LEA`를 보고 뭘 계산하는지 모를 때
- 포인터를 반환하는 함수인데 실제로는 곱셈 명령이 안 보여서 산술 연산이 어디 있는지 못 찾을 때
- 포인터 산술과 배열 인덱싱(`p[i]`)이 결국 같은 코드로 컴파일되는 이유가 궁금할 때

## 핵심 개념
C에서 `int *p`에 대해 `p + 1`은 "1바이트 뒤"가 아니라 "`sizeof(int)`(보통 4바이트) 뒤"를 의미한다. 이는 언어 차원의 규칙이고, 컴파일러는 이 스케일링을 **컴파일 시점에 이미 곱해서** 어셈블리에 넣는다. 즉 런타임에 "곱셈 명령"이 보이지 않아도 이미 반영되어 있는 것이다.

두 가지 경우로 나뉜다.
- **상수만큼 이동** (`p + 1`, `p + 5` 등 컴파일 시점에 정해진 값): 그냥 상수를 곱한 값을 더한다. `lea rax, [rdi+4]`처럼 보인다.
- **변수만큼 이동** (`p + n`, n이 함수 인자나 변수): x86-64는 메모리 오퍼랜드에서 인덱스 레지스터에 1/2/4/8배의 스케일을 하드웨어가 직접 지원하므로(`[base + index*scale]`), `sizeof(타입)`이 1/2/4/8이면 `LEA` 한 줄로 끝난다. 8보다 크거나 1/2/4/8이 아니면(예: 12바이트 구조체) `imul`로 먼저 곱한 뒤 더해야 한다(REV-1064에서 다룸).

`LEA`는 실제로 메모리를 읽지 않고 **주소만 계산**하는 명령이라는 점이 핵심이다(REV-0042). 포인터 산술은 값을 읽는 게 아니라 새 주소를 만드는 것이므로 자연스럽게 `LEA`와 짝을 이룬다.

## 화면/코드에서 보이는 징후
- `lea rax, [rdi + rsi*4]` — `int*`(4바이트) 기준 `p + n` 계산. `*4`가 `sizeof(int)`를 반영
- `lea rax, [rdi + rsi*8]` — `long*`, `double*`, 포인터 배열(`sizeof(포인터)=8`) 기준
- `add rax, 4` 또는 `lea rax, [rax+4]` — 반복문에서 포인터를 1씩 전진(`p++`)시킬 때, 이미 4가 곱해져 더해짐
- Ghidra pseudocode에서 `p + n`이 그대로 유지되거나, 타입 정보가 없으면 `(int *)((char *)p + n * 4)`처럼 바이트 단위로 풀어서 보여줄 때도 있음

## 가장 먼저 할 것
`LEA` 또는 `ADD`에 곱해진 상수(스케일 또는 즉시값)를 보고 그 값을 4, 8 등으로 나눠본다. 나눈 값이 딱 맞아떨어지면 그것이 바로 원본 C 코드의 "포인터 이동 개수(n)"다. 예를 들어 `[rax+40]`이면 `40 / 4 = 10`, 즉 `int` 배열이라면 `p + 10` 또는 `p[10]`에 대응할 가능성이 높다.

## 단계별 절차
1. 함수가 포인터를 인자로 받는지 시그니처(첫 인자가 스택/레지스터에서 8바이트로 다뤄지는지)로 확인한다.
2. `LEA`나 `ADD rax, N` 형태로 그 포인터 레지스터에 값을 더하는 줄을 찾는다.
3. 더해지는 값이 상수(즉시값)인지, 스케일 인덱스(`*2/*4/*8`)가 붙은 레지스터인지 구분한다.
4. 상수라면 그 값을 원래 가리키는 타입 크기로 나눠서 "몇 개 앞/뒤로 이동했는지" 계산한다.
5. 결과 주소(`rax`)가 바로 역참조(`[rax]`)되는지 확인하면, 이 포인터 산술이 배열 인덱싱과 동일한 의도로 쓰였는지 알 수 있다(REV-1062, REV-0034).

## 명령어/단축키
- IDA/Ghidra: 포인터 변수에 정확한 타입(`int *` 등)을 지정하면 pseudocode가 바이트 오프셋 대신 `p[n]`, `p+n` 형태로 자동 정리됨
- GDB: `p p+1` (포인터 변수에 대해 GDB가 타입 크기를 반영해 계산해줌), `p (char*)p2 - (char*)p1` (두 포인터 차이를 바이트로 확인)
- x64dbg: 레지스터 계산기에서 `rdi + rsi*4` 직접 계산해보며 검증

## 출력 해석
```c
int *advance(int *p, long n) {
    return p + n;
}

int sum_first_three(int *p) {
    return p[0] + p[1] + p[2];
}
```

```asm
; advance, rdi = p, rsi = n
advance:
    push    rbp
    mov     rbp, rsp
    mov     [rbp-8], rdi
    mov     [rbp-16], rsi
    mov     rax, [rbp-8]      ; rax = p
    mov     rdx, [rbp-16]     ; rdx = n
    lea     rax, [rax+rdx*4]  ; rax = p + n*4바이트 = p + n (int 기준)
    leave
    ret

; sum_first_three, rdi = p
sum_first_three:
    push    rbp
    mov     rbp, rsp
    mov     [rbp-8], rdi
    mov     rax, [rbp-8]
    mov     edx, [rax]        ; p[0] = *(p+0)
    mov     rax, [rbp-8]
    mov     ecx, [rax+4]      ; p[1] = *(p+1), 오프셋 4 = 1*sizeof(int)
    add     edx, ecx
    mov     rax, [rbp-8]
    mov     eax, [rax+8]      ; p[2] = *(p+2), 오프셋 8 = 2*sizeof(int)
    add     eax, edx
    leave
    ret
```

`advance`의 `lea rax, [rax+rdx*4]`는 `p + n`을 계산만 하고 아직 역참조하지 않는다(`LEA`라서 메모리를 읽지 않음). 반면 `sum_first_three`에서는 `[rax+4]`, `[rax+8]`처럼 대괄호로 감싸 실제로 값을 읽으므로 역참조까지 포함된 배열 인덱싱이다. **포인터 산술만 하면 `LEA`, 산술 결과를 역참조하면 일반 `mov [reg+offset]`**이라는 것이 이 둘의 차이다.

## 흔한 실수
- `LEA`에 곱해진 스케일(`*4`, `*8`)을 보고 "곱셈 연산이 있다"고 착각해 `IMUL`을 찾아다니는 것 — 스케일 인덱스는 하드웨어가 무료로 처리하므로 별도 곱셈 명령이 없다.
- 포인터 산술 결과가 바로 새 포인터 값인지, 역참조된 데이터 값인지 대괄호 유무로 구분하지 않고 혼동하는 것.
- `char *` 기준 포인터 산술(스케일이 1이라 `LEA`에서 스케일 표기가 생략됨)을 보고 "덧셈이 안 맞다"고 오해하는 것 — `sizeof(char)==1`이라 `*1`은 그냥 표기되지 않는다.
- 구조체 크기가 4/8이 아닌 경우(예: 12바이트) `LEA` 스케일로 안 되고 `IMUL`이 별도로 나오는데, 이를 "포인터 산술이 아니다"라고 오판하는 것(REV-1064에서 다룸).

## 막혔을 때 다음 체크
- 구조체 크기가 4/8이 아니라 곱셈이 별도로 나오는 경우는 → REV-1064 구조체 배열 순회가 어셈블리에서 보이는 패턴
- `LEA`의 기본 문법과 왜 산술처럼 보이는지 원리는 → REV-0042 LEA: 주소 계산인데 왜 산술 연산처럼 보이는가
- 단순 배열 인덱싱 패턴 자체가 궁금하면 → REV-1058 1차원 배열 인덱싱이 어셈블리에서 보이는 패턴, REV-0034 배열 접근이 어셈블리로 변하는 방식
- 포인터 역참조 자체가 헷갈리면 → REV-1062 포인터 역참조가 어셈블리에서 보이는 패턴

## 미니 예제
스케일 값과 타입 크기의 대응표(자주 등장하는 4가지):
```
lea rax, [reg + idx*1]   ->  char*, unsigned char* (1바이트 타입)
lea rax, [reg + idx*2]   ->  short*  (2바이트 타입)
lea rax, [reg + idx*4]   ->  int*, float*  (4바이트 타입)
lea rax, [reg + idx*8]   ->  long*, double*, 포인터의 포인터(**p)  (8바이트 타입)
```
이 표만 외워두면 디컴파일러 없이 순수 어셈블리만 보고도 포인터가 가리키는 타입의 크기를 즉시 역추정할 수 있다.

## 출처/검증
- x86-64 메모리 오퍼랜드의 스케일 인덱스(`base + index*scale`, scale ∈ {1,2,4,8}) 하드웨어 지원: Intel 64 and IA-32 Architectures Software Developer's Manual 기준.
- C 표준상 포인터 산술이 가리키는 타입의 크기 단위로 이루어진다는 규칙: ISO C 표준(포인터 산술 절) 기준.
- gcc/clang이 포인터 산술을 `LEA` + 스케일 인덱스로 컴파일하는 패턴은 x86-64 리눅스/윈도우 환경에서 반복 확인되는 표준 패턴이다(2026-09-10 검증).
