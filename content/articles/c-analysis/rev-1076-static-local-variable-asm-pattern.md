## 한 줄 요약
함수 안에 `static`으로 선언된 지역 변수는 문법적으로는 그 함수 안에서만 이름을 쓸 수 있지만 메모리 상으로는 전역 변수와 똑같이 `.data`/`.bss`에 고정 위치를 가지므로, 어셈블리에서는 `[rbp-N]`이 아니라 전역 변수와 동일한 `[rip+심볼]`(x64) 고정 주소로 접근되며 함수를 몇 번 호출해도 그 위치와 값이 유지된다.

## 언제 검색해야 하나
- 함수 안에서 선언된 것 같은 변수인데 스택 프레임(`[rbp-N]`)이 아니라 `[rip+...]`나 고정 주소로 접근되어 "이거 지역 변수 맞나?" 싶을 때
- 같은 함수를 여러 번 호출했는데 그 안의 어떤 변수 값이 매번 리셋되지 않고 이전 호출의 값을 그대로 이어받는 것을 디버거에서 확인했을 때
- ID 생성기, 호출 횟수 카운터처럼 "함수 호출 간 상태를 유지"하는 로직을 어셈블리에서 먼저 발견하고 원래 C 코드가 어떤 모양이었을지 추론해야 할 때
- IDA/Ghidra가 함수 로컬 변수 목록에는 없는데 pseudocode 본문에 `dword_404050` 같은 전역풍 이름이 등장할 때

## 핵심 개념
`static` 지역 변수는 "그 이름이 보이는 범위(scope)는 함수 안"이지만 "그 변수가 사는 곳(storage)은 프로그램 전체 수명"이라는, 스코프와 저장 위치가 분리된 특수한 경우다. 컴파일러는 이런 변수를 지역 변수처럼 스택에 두면 함수가 끝날 때 사라지므로, 반드시 전역 변수와 동일한 방식으로 `.data`(0이 아닌 초깃값) 또는 `.bss`(0 또는 초깃값 없음) 섹션에 고정 배치한다.

```c
int next_id(void) {
    static int counter = 0;   /* static 지역변수: 함수 호출 간 값이 유지됨 */
    counter++;
    return counter;
}
```

x86-64, `-O0`, Intel 문법(PIE 환경):

```asm
next_id:
    push    rbp
    mov     rbp, rsp
    mov     eax, DWORD [rip+counter.0]  ; counter를 스택이 아니라 고정 위치에서 읽음 (전역과 동일한 방식)
    add     eax, 1                      ; counter++
    mov     DWORD [rip+counter.0], eax  ; 갱신된 값을 다시 같은 고정 위치에 저장
    mov     eax, DWORD [rip+counter.0]  ; return counter (다시 읽어서 반환값으로 사용)
    pop     rbp
    ret
```

주목할 점은 `push rbp`/`mov rbp, rsp`로 스택 프레임을 만들면서도, `counter`는 그 프레임 안 어디에도 등장하지 않는다는 것이다. `counter.0`(컴파일러가 이름 충돌을 피하려고 붙이는 접미사, 실제로는 `counter.2151` 같은 내부 식별자로 나타날 수 있음)이라는 심볼은 다른 전역 변수와 마찬가지로 `.data`(초깃값 `0`이라도 명시적으로 `= 0`이 아니면 컴파일러에 따라 `.bss`)에 위치하며, `next_id()`를 100번 호출하면 100번 모두 이 같은 위치를 누적해서 갱신한다.

## 화면/코드에서 보이는 징후
- 함수의 스택 프레임 크기(`sub rsp, N`)와 무관하게, 특정 변수가 계속 `[rip+심볼]`(또는 고정 리터럴 주소)로만 접근됨
- IDA/Ghidra가 해당 심볼을 함수 이름과 조합된 이름(`funcname_counter`, 또는 그냥 `dword_401050` 같은 순수 주소 이름)으로 표시함
- Xref(교차 참조)를 확인하면 그 심볼을 참조하는 함수가 딱 하나뿐임(전역 변수는 보통 여러 함수가 공유하지만, static 지역 변수는 선언된 함수 하나만 접근)
- `.bss`/`.data` 섹션 덤프에서 함수 이름과 관련된 듯한 위치에 정수 하나가 놓여 있고, 그 값이 프로그램 실행 동안 점점 증가/변화함

## 가장 먼저 할 것
그 변수를 참조하는 함수가 몇 개인지 Xref로 확인한다. 딱 하나의 함수만 참조한다면 static 지역 변수일 가능성이 매우 높고, 여러 함수가 공유한다면 그냥 평범한 전역 변수다(REV-1075).

## 단계별 절차
1. `[rip+심볼]`로 접근되는데 스택 프레임에는 대응하는 `[rbp-N]` 슬롯이 없는 변수를 찾는다.
2. 그 심볼의 Xref를 확인해 참조하는 함수가 하나뿐인지 검사한다.
3. 하나뿐이라면 IDA에서 그 심볼 이름을 `funcname_변수의미` 식으로 바꿔 static 지역 변수임을 표시해 둔다.
4. 프로그램을 여러 번 실행/호출해 그 값이 초기값에서 누적되는지 GDB/x64dbg로 실제로 확인해 "상태를 유지하는 변수"라는 가설을 검증한다.

## 명령어/단축키
- IDA: 심볼 위에서 `X`(Xref to)로 참조 함수 개수 확인, `N`으로 이름 변경
- Ghidra: References To로 참조 함수 확인, Data Type Manager에서 섹션(`.data`/`.bss`) 확인
- GDB: `b next_id`로 브레이크포인트, `p counter` 또는 `x/dw &counter`로 호출마다 값이 누적되는지 관찰(`c`로 재실행 후 값 비교)
- x64dbg: 메모리 맵에서 `.data`/`.bss` 섹션 확인, 해당 주소에 감시식(watch) 추가해 함수 재호출 시 값 변화 관찰

## 출력 해석
`next_id()`를 연속으로 세 번 호출하면 반환값이 `1, 2, 3`처럼 이어진다면, 이는 `counter`가 각 호출마다 초기화되지 않고 이전 값을 그대로 이어받는다는 뜻이며, 이것이 바로 static 지역 변수의 정의적 특징이다. 만약 매 호출마다 `1`만 반환된다면 그 변수는 static이 아니라 평범한 지역 변수(`int counter = 0;`)였을 가능성이 높다.

## 흔한 실수
- `[rip+...]`로 접근되는 모든 변수를 무조건 "평범한 전역 변수"로만 분류하고 static 지역 변수 가능성을 검토하지 않는 것.
- static 지역 변수의 초기화 코드(`counter = 0`)가 함수가 호출될 때마다 실행된다고 착각하는 것 — 실제로는 초기화가 프로그램 로드 시 딱 한 번만 이루어지고(`.data`/`.bss` 섹션 자체의 초깃값으로), 함수 본문에는 그 초기화 코드가 전혀 나타나지 않는다.
- 멀티스레드 환경에서 static 지역 변수가 스레드 간에도 공유된다는 것을 놓치고 "이 함수는 각자 독립적으로 카운트한다"고 오해하는 것(경쟁 상태/레이스 컨디션 가능성).
- 이름이 비슷하다는 이유로 서로 다른 함수의 서로 다른 static 변수를 같은 변수로 착각하는 것 — 컴파일러가 붙이는 내부 접미사(`.0`, `.2151` 등)로 구분해야 한다.

## 막혔을 때 다음 체크
- static이 아닌 일반 지역/전역 변수의 주소 구분 규칙이 헷갈리면 → REV-1075 전역 변수와 지역 변수가 어셈블리 주소로 구분되는 패턴
- 이 상태 유지 변수가 재귀 호출 안에서 쓰이고 있다면 스택 프레임과의 관계를 → REV-1066 재귀 함수가 어셈블리/스택에서 보이는 패턴(예정)에서 확인
- 더 상세한 전역/지역 구분 배경 지식은 → REV-0353 전역 변수와 지역 변수를 메모리 위치로 구분하는 법

## 미니 예제
호출될 때마다 다른 문자열을 반환하는 것처럼 보이지만 실제로는 static 배열 인덱스를 이용하는 패턴이다.

```c
int toggle(void) {
    static int state = 0;   /* 0 또는 1을 계속 뒤집으며 유지 */
    state = !state;
    return state;
}
```

```asm
toggle:
    push    rbp
    mov     rbp, rsp
    mov     eax, DWORD [rip+state.1]  ; 이전 상태 읽기
    test    eax, eax                 ; state가 0인지 검사
    sete    al                       ; state == 0 이면 al = 1, 아니면 al = 0  (!state 계산)
    movzx   eax, al                  ; 0/1 값을 32비트로 확장
    mov     DWORD [rip+state.1], eax ; 뒤집은 값을 같은 고정 위치에 다시 저장
    ret
```

`sete al`은 REV-0453에서 다루는 SETcc 패턴으로 `!state`(논리 NOT)를 0/1로 만든 것이고, 그 값을 다시 저장하는 대상이 스택이 아니라 `[rip+state.1]`이라는 고정 주소라는 점에서 이 변수가 static임이 확정된다.

## 출처/검증
- C 표준에서 `static` 지역 변수가 "블록 스코프이지만 정적 저장 기간(static storage duration)을 가진다"고 규정하는 부분: ISO/IEC 9899(C 표준) 저장 기간(storage duration) 섹션 기준.
- static 지역 변수가 실행 파일의 `.data`/`.bss` 섹션에 배치되고 전역 변수와 동일한 주소 방식으로 접근된다는 점: 실제 gcc/clang 컴파일 결과 및 ELF/PE 섹션 구조 비교로 반복 확인 (2026-09-10 검증).
