## 한 줄 요약
`strlen`을 손으로 구현한 코드(`while (*p) { p++; }` 또는 `for (i = 0; s[i]; i++)`)는 "포인터를 한 바이트씩 전진시키며 그 위치의 값이 0(널 문자)인지 검사"하는 루프로 컴파일되며, 이는 `CALL strlen`(REV-0071)처럼 라이브러리를 부르는 것과 달리 **함수 호출 없이 인라인된 반복문** 형태로 나타난다.

## 언제 검색해야 하나
- 루프 안에서 `cmp byte [rax], 0` 또는 `test al, al` 뒤에 조건 분기가 있고, 그 루프가 포인터를 1씩 증가시키는 것만 반복할 때
- `CALL strlen`이 안 보이는데도 문자열 길이를 재는 것 같은 동작이 코드에 있을 때(직접 구현했거나 컴파일러가 `strlen` 호출을 인라인한 경우)
- CTF 문제에서 비밀번호/플래그 길이를 검사하는 루프가 어디 있는지 찾아야 할 때
- Ghidra pseudocode에 `while (*param_1 != '\0')` 같은 패턴이 나와서 이게 왜 그렇게 보이는지 원본 어셈블리와 대조하고 싶을 때

## 핵심 개념
문자열은 C에서 "마지막에 널 바이트(`\0`, 값 0)가 붙은 문자 배열"이다. 따라서 "문자열이 어디서 끝나는지" 알아내려면 처음부터 한 바이트씩 읽으며 0을 만날 때까지 계속 전진하는 것 외에 방법이 없다. 이 루프는 항상 세 가지 요소로 구성된다.

1. **읽기**: 현재 포인터가 가리키는 1바이트를 읽는다(`mov al, [rax]` 또는 `cmp byte [rax], 0`).
2. **검사**: 그 값이 0인지 비교한다.
3. **전진**: 0이 아니면 포인터를 1 증가시키고(`inc rax` 또는 `add rax, 1`) 반복한다.

```c
int my_strlen(const char *s) {
    int len = 0;
    while (*s != '\0') {
        s++;
        len++;
    }
    return len;
}
```

이 루프는 겉모습이 REV-1067/1068에서 본 일반적인 `for`/`while` 루프와 똑같지만, **비교 대상이 항상 1바이트(`byte`) 크기이고 항상 상수 0과 비교**한다는 점, 그리고 갱신이 항상 "포인터 +1"이라는 점이 특징이다. 이 세 가지 특징이 함께 있으면 문자열 길이 검사 루프로 강하게 의심할 수 있다.

## 화면/코드에서 보이는 징후
- `movzx eax, byte [rax]` 또는 `cmp byte [rax], 0` — 1바이트 단위 읽기/비교
- 루프 갱신이 `add rax, 1` 또는 `inc rax`처럼 항상 1만큼 포인터를 전진(REV-1063과 달리 스케일 곱셈이 없음 — `char`는 크기가 1이라 곱셈 자체가 생략됨)
- 비교 상수가 항상 `0`(널 문자) — 다른 상수와 비교하면 이 패턴이 아님
- x86-64에서는 `REP` 계열 문자열 명령(`SCASB`, REV-0084)으로 컴파일되는 경우도 있음 — 이때는 루프 대신 `repne scasb` 한 줄로 보임
- 실제 `strlen` 라이브러리 호출은 대개 SIMD(SSE2/AVX) 최적화가 들어간 긴 코드로, 손으로 짠 위 패턴보다 훨씬 복잡하게 보인다 — 짧고 단순하면 인라인된 수동 구현일 가능성이 높음

## 가장 먼저 할 것
루프 안에서 "1바이트를 읽고, 0과 비교하고, 포인터를 1 증가시키는" 세 동작이 반복되는지 확인한다. 세 조건이 다 맞으면 이 루프의 목적은 "문자열 끝(널 바이트) 찾기"임을 바로 확정할 수 있다.

## 단계별 절차
1. 루프 조건 검사에서 비교 크기가 `byte`(1바이트)인지 확인한다 — `int`/`long` 비교라면 이 패턴이 아니다.
2. 비교 상수가 0인지 확인한다.
3. 루프 갱신부에서 포인터가 몇씩 증가하는지 본다 — 1이면 `char*` 순회다.
4. 루프가 끝난 뒤 그 결과(포인터 차이 또는 카운터 값)를 어떻게 쓰는지 본다 — 길이를 반환하거나 다른 함수(예: `strcmp` 스타일 비교, REV-0196)에 넘기는지 확인한다.
5. `REP`/`SCASB` 계열 명령이 대신 쓰였다면(REV-0084) 이 루프 대신 그 명령 한 줄이 통째로 같은 역할을 한다는 것을 확인한다.

## 명령어/단축키
- GDB: `x/s $rdi`로 함수 시작 시 문자열 내용을 바로 확인, `p (char*)$rax - (char*)$rdi`로 루프 종료 시 길이 계산 검증
- IDA/Ghidra: 루프에 우클릭 → 문자열 타입(`char *`)을 명확히 지정하면 pseudocode가 `while (*s)` 형태로 정리됨
- x64dbg: 메모리 덤프 창에서 포인터가 가리키는 위치를 따라가며 널 바이트 위치를 시각적으로 확인

## 출력 해석
```c
int my_strlen(const char *s) {
    int len = 0;
    while (*s != '\0') {
        s++;
        len++;
    }
    return len;
}
```

```asm
; my_strlen, rdi = s
my_strlen:
    push    rbp
    mov     rbp, rsp
    sub     rsp, 24
    mov     [rbp-24], rdi     ; s
    mov     dword [rbp-4], 0  ; len = 0
.L_cond:
    mov     rax, [rbp-24]
    movzx   eax, byte [rax]   ; eax = *s (1바이트 읽기, 0~255로 확장)
    test    al, al            ; *s == 0 ?  (TEST로 al 자체를 검사)
    je      .L_end            ; 0이면(널 문자) 루프 종료
    add     qword [rbp-24], 1 ; s++  (char라서 스케일 없이 그냥 +1)
    add     dword [rbp-4], 1  ; len++
    jmp     .L_cond
.L_end:
    mov     eax, [rbp-4]
    leave
    ret
```

`movzx eax, byte [rax]`가 "1바이트 읽기"이고, `test al, al` + `je .L_end`가 "0인지 검사"다. `add qword [rbp-24], 1`은 포인터를 정확히 1바이트 전진시키는데, `char`의 크기가 1이라서 REV-1063에서 본 스케일 곱셈이 아예 필요 없다. 이 세 요소(1바이트 읽기, 0 비교, +1 전진)가 한 세트로 반복되는 것이 이 패턴의 전형적인 모습이다.

## 흔한 실수
- 1바이트 비교(`cmp byte [...], 0`)를 int 비교와 똑같이 취급해서 실제로는 문자열 끝 검사인 루프를 "그냥 어떤 값이 0인지 확인하는 루프"로 뭉뚱그려 넘기는 것.
- `SCASB`/`REPNE SCASB`(REV-0084)로 압축된 코드를 보고 루프가 없다고 오해하는 것 — 한 명령어가 루프 전체를 대신한다.
- 문자열 길이를 재는 루프와 문자열 두 개를 비교하는 루프(REV-0196 strcmp 패턴, REV-0197 memcmp 패턴)를 구분하지 않고 섞어서 읽는 것 — strlen 스타일은 포인터 **하나**만 전진하고, strcmp 스타일은 포인터 **두 개**가 동시에 전진한다.
- SIMD 최적화가 들어간 실제 libc `strlen` 호출부(길고 복잡한 벡터 명령)를 보고 "이건 strlen이 아니다"라고 오판하는 것 — 최적화된 버전은 이 단순 패턴보다 훨씬 복잡하게 보일 수 있다.

## 막혔을 때 다음 체크
- 포인터 전진(1씩 증가)의 기본 원리가 궁금하면 → REV-1063 포인터 산술이 어셈블리에서 보이는 패턴
- 문자열 두 개를 비교하는 패턴과 구분하려면 → REV-0196 strcmp 기반 Flag 검증 패턴, REV-0197 memcmp 기반 Flag 검증 패턴
- SCAS 계열 명령으로 압축된 경우가 궁금하면 → REV-0084 SCAS와 문자열 검색 패턴
- 루프의 break/continue와 결합된 경우는 → REV-1067 break문이 있는 for 루프가 어셈블리에서 보이는 패턴

## 미니 예제
같은 로직을 `SCASB`로 최적화하면 루프 전체가 명령 한 줄로 압축된다(개념 예시):
```asm
mov     rdi, s
xor     al, al        ; al = 0 (찾을 값)
mov     rcx, -1        ; 최대 반복 횟수(사실상 무제한)
repne   scasb          ; rdi를 1씩 전진시키며 al(0)과 같은 바이트를 찾을 때까지 반복
; 루프 종료 후 rdi는 널 바이트 "다음" 위치, rcx는 남은 카운트의 보수
```
이 코드는 위에서 손으로 짠 6줄짜리 루프와 논리적으로 완전히 동일한 일을 하지만, 반복문 구조 없이 명령어 하나(`REP` 접두사가 붙은 `SCASB`)로 표현된다. 짧은 어셈블리에서 반복 흔적 없이 갑자기 문자열 길이가 나온다면 이 가능성을 의심해야 한다.

## 관련 글

- REV-1068 — continue문이 있는 for 루프가 어셈블리에서 보이는 패턴
- REV-0084 — SCAS와 문자열 검색 패턴
- REV-0196 — strcmp 기반 Flag 검증 패턴
- REV-0197 — memcmp 기반 Flag 검증 패턴

## 출처/검증
- C 문자열이 널 종료(`\0`) 규칙을 따른다는 것과 `strlen`의 표준 동작(첫 널 바이트까지의 길이 반환): ISO C 표준 라이브러리(`<string.h>`) 기준.
- gcc/clang `-O0`에서 수동 문자열 순회 루프가 1바이트 단위 읽기+비교+포인터 증가로 컴파일되는 패턴, 최적화 시 `REP SCASB`나 SIMD 코드로 대체될 수 있다는 점은 x86-64 리눅스/윈도우 환경에서 반복 확인되는 표준 패턴이다(2026-09-10 검증).
