## 한 줄 요약
구조체 안에 다른 구조체가 "값으로" 들어있으면 컴파일러는 바깥 구조체 오프셋과 안쪽 필드 오프셋을 미리 더해서 **한 번의 `mov`**로 접근하지만, 구조체 안에 다른 구조체를 가리키는 "포인터"가 들어있으면 두 번 연속 `mov`로 실제 메모리를 두 번 따라가야 한다.

## 언제 검색해야 하나
- `r->size.x` 같은 코드가 IDA/Ghidra에서 `*(int *)(r + 8)` 같은 이상한 포인터 캐스트로 보일 때
- 디컴파일 결과에 `[rax+8]`, `[rax+12]` 처럼 오프셋이 필드 이름과 안 맞아 보이는 숫자로 나올 때
- 구조체를 가리키는 포인터의 포인터를 따라가다가 몇 번 `mov`를 해야 하는지 헷갈릴 때
- 소스코드 없이 구조체 정의를 역으로 추정해야 하는데 어디까지가 "값"이고 어디부터가 "포인터"인지 구분이 안 될 때

## 핵심 개념
중첩 구조체는 두 가지 형태가 있고, 어셈블리에서 완전히 다르게 보인다.

**형태 1: 구조체가 값으로 포함(embedding)** — 안쪽 구조체가 바깥 구조체 메모리 안에 그대로 통째로 복사되어 있는 경우다. 이때는 "바깥 오프셋 + 안쪽 오프셋"을 컴파일 시점에 이미 계산해서 하나의 상수로 합쳐버리기 때문에 런타임에는 메모리 접근이 한 번만 일어난다.

**형태 2: 구조체를 가리키는 포인터로 포함** — 안쪽 구조체의 실제 데이터는 다른 메모리 위치에 있고, 바깥 구조체는 그 주소값(8바이트 포인터)만 들고 있는 경우다. 이때는 먼저 포인터 값을 읽어와야(1차 `mov`) 그 다음에 그 주소로 다시 접근(2차 `mov`)할 수 있다. `->`가 연속으로 두 번(`c->engine->hp`) 나오면 대부분 이 형태다.

## 화면/코드에서 보이는 징후
- 형태 1: `mov edx, [rax+8]` 처럼 레지스터 한 번 로드 후 오프셋 붙은 `mov`가 **한 번**만 등장
- 형태 2: `mov rax, [rax]` 다음에 다시 `mov eax, [rax]`처럼 **같은 레지스터를 재사용하며 mov가 두 번** 연속으로 등장
- Ghidra pseudocode에서 형태 2는 `*(int *)*(long *)(c)` 같은 이중 포인터 역참조 표현이 나옴
- IDA는 구조체 타입 정보가 있으면 `c->engine->hp`처럼 원본과 거의 같게 복원해주지만, 타입이 없으면 `*(_DWORD *)(*(_QWORD *)(a1))` 식으로 나옴

## 가장 먼저 할 것
문제의 `mov`가 몇 번 연속으로 "레지스터를 읽어서 그 레지스터로 다시 메모리를 읽는" 형태인지 센다. 한 번이면 값 임베딩(오프셋만 다름), 두 번 이상이면 포인터 체인이다. IDA에서는 변수에 우클릭 → `Convert to struct *`로 구조체 타입을 지정하면 오프셋 숫자가 실제 필드 이름으로 바뀌어 훨씬 읽기 쉬워진다.

## 단계별 절차
1. 함수 시작부에서 첫 인자가 저장되는 스택 슬롯(`[rbp-8]` 등)을 확인해 "이 함수가 받는 구조체 포인터가 무엇인지" 특정한다.
2. 그 슬롯에서 값을 읽는 첫 `mov rax, [rbp-8]`를 찾는다 — 이것이 구조체 포인터 자체를 레지스터에 올리는 동작이다.
3. 바로 다음 `mov`의 오프셋(`[rax+N]`)을 본다. 이 오프셋이 int/필드 크기라면 임베딩된 필드에 대한 직접 접근이다.
4. 만약 오프셋으로 읽은 결과(`rax`)를 다시 `[rax]` 형태로 한 번 더 읽는 `mov`가 있다면, 그건 포인터 멤버를 따라간 것이다.
5. GDB/x64dbg에서 실제 실행 중 해당 레지스터 값을 찍어보면(`print $rax` 또는 레지스터 창), 첫 mov 결과가 유효한 힙/스택 주소인지, 두 번째 mov 결과가 작은 정수(hp 값 등)인지 구분할 수 있어 형태 판별이 쉬워진다.

## 명령어/단축키
- IDA: 변수 우클릭 → `Convert to struct *` (구조체 타입 지정 후 오프셋이 필드명으로 표시됨)
- Ghidra: 변수 우클릭 → `Retype Variable` → 구조체 포인터 타입 지정
- GDB: `p *(struct Rect *)$rdi` 로 런타임에 구조체 전체를 필드 이름과 함께 출력
- x64dbg: 레지스터 값 우클릭 → `Follow in Dump`로 메모리 내용을 직접 확인

## 출력 해석
아래는 두 형태를 나란히 비교한 예제다.

```c
/* 형태 1: 구조체를 값으로 포함 */
struct Point { int x; int y; };
struct Rect  { struct Point origin; struct Point size; };

int get_area(struct Rect *r) {
    return r->size.x * r->size.y;
}
```

```asm
; get_area, x86-64 SysV, gcc -O0, Intel 문법
; rdi = r
get_area:
    push    rbp
    mov     rbp, rsp
    sub     rsp, 16
    mov     [rbp-8], rdi     ; r 저장
    mov     rax, [rbp-8]     ; rax = r  (1차: 구조체 포인터 자체 로드)
    mov     edx, [rax+8]     ; edx = r->size.x
                              ;   origin(8바이트) 다음이 size이므로
                              ;   size.x 오프셋 = 8(size 시작) + 0(x) = 8
    mov     rax, [rbp-8]
    mov     eax, [rax+12]    ; eax = r->size.y (8 + 4 = 12)
    imul    eax, edx
    leave
    ret
```

`r->size.x`와 `r->size.y`는 각각 메모리 접근이 **한 번**만 일어난다(`[rax+8]`, `[rax+12]`). 컴파일러가 `origin`(8바이트) + `size 안의 x 오프셋`(0) = 8을 이미 계산해 상수로 박아 넣었기 때문이다. Ghidra/IDA는 구조체 타입 정보가 있으면 이 두 줄을 그대로 `r->size.x`, `r->size.y`로 복원한다.

```c
/* 형태 2: 구조체를 포인터로 포함 */
struct Engine { int hp; };
struct Car    { struct Engine *engine; };

int get_hp(struct Car *c) {
    return c->engine->hp;
}
```

```asm
; get_hp, x86-64 SysV, gcc -O0, Intel 문법
; rdi = c
get_hp:
    push    rbp
    mov     rbp, rsp
    sub     rsp, 16
    mov     [rbp-8], rdi     ; c 저장
    mov     rax, [rbp-8]     ; rax = c
    mov     rax, [rax]       ; rax = c->engine  (1차 역참조: 포인터 값 로드)
    mov     eax, [rax]       ; eax = c->engine->hp (2차 역참조: 실제 데이터 로드)
    leave
    ret
```

여기서는 `mov`가 연속 두 번(`mov rax, [rax]` 다음 `mov eax, [rax]`) 등장한다. 첫 번째는 `engine` 포인터 값 자체를 읽은 것이고, 두 번째는 그 포인터가 가리키는 곳에서 `hp`를 읽은 것이다. 타입 정보가 없으면 Ghidra는 이를 `*(int *)*(long *)param_1` 같은 중첩 캐스트로 보여주는데, 바깥쪽 `*`가 두 번째 역참조, 안쪽 `*`가 첫 번째 역참조에 대응한다.

## 흔한 실수
- `[rax+8]` 같은 오프셋을 보고 무조건 "8바이트째에 있는 필드"라고 단정하는 것 — 실제로는 여러 필드의 오프셋이 합산된 값일 수 있어 구조체 전체 레이아웃(패딩 포함)을 먼저 복원해야 한다.
- 연속된 `mov rax, [rax]`를 단순 대입으로 오해하고 넘어가는 것 — 이는 포인터 체인을 한 단계 더 따라가는 동작이다.
- IDA에서 구조체 타입을 지정하지 않고 숫자 오프셋만 보고 필드 이름을 손으로 추측하다가 패딩 때문에 오프셋이 어긋나는 것(REV-1060, 패딩은 REV-0344 참고).

## 막혔을 때 다음 체크
- 구조체 필드 접근 자체의 기본 패턴이 헷갈리면 → REV-1060 구조체 필드 접근이 어셈블리에서 보이는 패턴, REV-0035 구조체 접근이 어셈블리로 변하는 방식
- 오프셋이 예상과 다르게 나오는 이유(패딩/정렬)가 궁금하면 → REV-0344 구조체 정렬/패딩이 미치는 영향, REV-0377 구조체 오프셋이 생각한 것과 다를 때
- 단순 포인터 역참조 자체의 기본 패턴은 → REV-1062 포인터 역참조가 어셈블리에서 보이는 패턴
- 구조체 배열을 순회하는 경우는 → REV-1064 구조체 배열 순회가 어셈블리에서 보이는 패턴

## 미니 예제
IDA에서 `struct Rect *` 타입을 지정하기 전과 후를 비교하면 차이가 명확하다.

```
타입 지정 전: return *(int *)(a1 + 8) * *(int *)(a1 + 0xC);
타입 지정 후: return a1->size.x * a1->size.y;
```

두 번째 형태(포인터 체인)는 타입을 지정해도 중간 구조체 이름까지는 자동으로 못 살리는 경우가 많으므로, `c->engine`이 가리키는 실제 타입을 별도로 `Car`, `Engine` 구조체로 등록해줘야 `c->engine->hp`처럼 완전히 복원된다.

## 출처/검증
- x86-64 SysV 호출 규약에서 구조체 포인터가 정수 레지스터(RDI 등)로 전달되는 방식: System V AMD64 ABI 문서 기준.
- gcc/clang `-O0` 기준 구조체 멤버 접근이 `mov reg, [base+offset]` 형태로 컴파일되고, 값 임베딩과 포인터 멤버가 역참조 횟수로 구분되는 패턴은 실제 x86-64 리눅스 환경에서 반복 확인되는 표준 패턴이다(2026-09-10 검증).
