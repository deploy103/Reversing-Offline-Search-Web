## 한 줄 요약
`&&`와 `||`는 왼쪽 조건의 결과만으로 전체 식의 값이 확정되면 오른쪽 조건을 평가하지 않는 "단축 평가(short-circuit evaluation)" 규칙이 있는데, 어셈블리에서는 이것이 왼쪽 조건을 `cmp`/`test`로 확인한 직후 곧바로 최종 결과 쪽으로 건너뛰는 조건 분기(`je`, `jne` 등)로 나타나며, 오른쪽 조건에 해당하는 명령어는 그 분기를 타지 않을 때만 실행된다.

## 언제 검색해야 하나
- `if (p != NULL && p->value > 0)` 같은 코드에서, 어셈블리를 보면 `p`가 NULL인지 확인하는 코드 다음에 `p->value`를 읽는 코드가 조건부로만 실행되고 있을 때
- 왜 어떤 비교 코드는 항상 실행되고 어떤 비교 코드는 특정 분기를 타야만 실행되는지 이해가 안 될 때
- 크래시 덤프를 보다가 `p->value` 역참조 지점에서 죽었는데 소스에는 분명 `p != NULL` 체크가 먼저 있는 걸 확인하고 "그럼 왜 NULL로 접근했지?"를 조사할 때(단축 평가가 깨진 게 아니라 다른 원인을 찾아야 함을 알기 위해)
- `||`로 연결된 여러 조건 중 하나라도 참이면 뒤를 검사하지 않는다는 것을 어셈블리 레벨에서 직접 확인하고 싶을 때

## 핵심 개념
`&&`는 왼쪽이 거짓이면 전체가 거짓으로 확정되므로 오른쪽을 평가할 필요가 없고, `||`는 왼쪽이 참이면 전체가 참으로 확정되므로 오른쪽을 평가할 필요가 없다. 컴파일러는 이 규칙을 "왼쪽 조건을 먼저 검사해서, 결과가 이미 정해지면 오른쪽 코드를 건너뛰고 최종 결과로 바로 점프"하는 분기 코드로 구현한다.

```c
int check(int *p, int n) {
    if (p != NULL && p[0] > n) {
        return 1;
    }
    return 0;
}
```

x86-64 SysV, `-O0`, Intel 문법:

```asm
check:
    push    rbp
    mov     rbp, rsp
    mov     [rbp-24], rdi    ; p 저장
    mov     [rbp-28], esi    ; n 저장
    mov     rax, [rbp-24]    ; rax = p
    test    rax, rax         ; p == NULL 인지 확인 (왼쪽 조건: p != NULL)
    je      .L_false         ; p == NULL 이면 && 전체가 거짓 확정 -> 오른쪽 p[0]>n은 검사 안 하고 바로 false로
    mov     rax, [rbp-24]    ; rax = p            (이 아래는 p != NULL 일 때만 실행됨)
    mov     eax, [rax]       ; eax = p[0]          (오른쪽 조건 평가 시작)
    cmp     eax, [rbp-28]    ; p[0]과 n 비교
    jle     .L_false         ; p[0] <= n 이면 && 전체가 거짓
    mov     eax, 1           ; 둘 다 참이었으므로 결과 = 1
    jmp     .L_end
.L_false:
    mov     eax, 0           ; 결과 = 0
.L_end:
    pop     rbp
    ret
```

핵심은 `je .L_false` 한 줄이다. `p == NULL`이면 이 명령이 바로 `.L_false`로 뛰어 버려서, 그 아래 있는 `mov eax, [rax]`(즉 `p[0]` 역참조)는 **절대 실행되지 않는다**. 이 덕분에 `&&`의 왼쪽이 안전 검사(널 체크)이고 오른쪽이 그 안전이 보장된 뒤에만 해도 되는 접근(역참조)일 때, 순서를 바꾸면 안 되는 이유가 어셈블리 레벨에서 그대로 보장된다.

## 화면/코드에서 보이는 징후
- 첫 번째 비교(`cmp`/`test`) 직후 조건 분기가 있고, 그 분기를 타면 두 번째 비교 코드를 완전히 건너뜀
- 분기 목적지가 최종 결과를 정하는 코드(예: `eax = 0` 설정 후 함수 끝)로 바로 연결됨 — 즉 "확정되면 더 볼 것 없이 결론으로 직행"하는 모양
- `||`의 경우 방향이 반대: 왼쪽이 참이면 바로 "결론=참"으로 건너뛰고, 왼쪽이 거짓일 때만 오른쪽 비교 코드가 실행됨

## 가장 먼저 할 것
분기 하나가 두 번째 비교/역참조 블록 전체를 건너뛰는 모양인지 확인한다. 건너뛰는 조건이 "이미 결과가 확정된 경우"라면(`&&`에서 왼쪽 거짓, `||`에서 왼쪽 참) 단축 평가 패턴이 맞다.

## 단계별 절차
1. `cmp`/`test` 뒤에 오는 조건 분기의 목적지를 확인한다.
2. 그 목적지가 "두 번째 조건 검사를 완전히 건너뛰고 결론으로 가는 지점"인지 확인한다.
3. `&&`라면 "왼쪽이 거짓일 때 건너뛰기(=false 확정)", `||`라면 "왼쪽이 참일 때 건너뛰기(=true 확정)" 방향인지 대조한다.
4. 건너뛰지 않는 경로에서만 두 번째 비교/역참조가 실행되는지 확인해, 소스의 `&&`/`||` 순서가 안전 검사 → 위험 접근 순서로 되어 있는지 재구성한다.

## 명령어/단축키
- IDA: pseudocode(F5)에서 `if (a && b)` 형태로 이미 복원되는지 확인, 그래프 뷰(스페이스바)로 분기 모양을 시각적으로 확인
- Ghidra: Decompile 창에서 동일하게 논리식 복원 확인, Graph View로 블록 연결 확인
- GDB: 첫 번째 비교 직후 분기에 브레이크포인트를 걸고 `p $zf`로 플래그 확인 후 실제로 어느 쪽으로 가는지 `si`(step instruction)로 추적
- x64dbg: 그래프 뷰(그래프 모드)로 조건 분기의 두 갈래를 시각적으로 비교

## 출력 해석
왼쪽 조건에서 이미 결과가 정해져 `.L_false`로 점프했다면, 그 실행 경로에서는 오른쪽 조건에 해당하는 명령어들이 CPU에 의해 아예 인출/실행되지 않는다. 즉 오른쪽 조건이 참인지 거짓인지는 이 실행에서는 계산되지 않은 채로 남는다 — 디버거에서 오른쪽 조건 변수 값을 확인해도 "이번 호출에서는 갱신되지 않았다"는 뜻일 수 있다.

## 흔한 실수
- `&&`/`||` 각각의 소스코드 줄 수만큼 항상 모든 비교가 실행된다고 가정하는 것 — 단축 평가로 인해 일부는 실행되지 않을 수 있다.
- 왼쪽 조건에 부작용(side effect, 예: 함수 호출 안에서 값 증가)이 있는 코드가 있는데, 오른쪽이 실행되지 않아도 왼쪽 부작용은 항상 일어난다는 걸 놓치는 것.
- `&&`의 분기 방향(거짓이면 건너뛰기)과 `||`의 분기 방향(참이면 건너뛰기)을 반대로 외워서 헷갈리는 것.
- 컴파일러가 최적화 시 단축 평가가 필요 없는 경우(부작용이 없고 두 조건 모두 계산해도 안전한 경우) `and`/`or` 비트 연산이나 `cmov`로 합쳐버려 분기 자체가 사라질 수 있다는 걸 모르고 항상 분기 형태만 찾는 것.

## 막혔을 때 다음 체크
- 이 조건의 결과가 삼항 연산자로 바로 이어진다면 → REV-1073 삼항 연산자(?:)가 CMOV 또는 분기로 컴파일되는 패턴
- 단순 if-else 하나만 있는 더 기본적인 분기 모양이 헷갈리면 → REV-1054 if-else가 어셈블리에서 보이는 패턴(예정)
- NULL 체크 이후 실제 포인터 역참조가 어떻게 명령어로 나오는지 더 보고 싶다면 → REV-1062 포인터 역참조가 어셈블리에서 보이는 패턴

## 미니 예제
`||`(단축 평가로 뒤 조건을 건너뛰는 방향이 반대인 경우)의 예다.

```c
int is_special(int x) {
    if (x == 0 || x == 100) {
        return 1;
    }
    return 0;
}
```

```asm
is_special:
    push    rbp
    mov     rbp, rsp
    mov     [rbp-4], edi     ; x 저장
    cmp     DWORD [rbp-4], 0
    je      .L_true          ; x == 0 이면 || 전체가 참 확정 -> 뒤의 x==100 비교는 볼 필요 없이 바로 true로
    cmp     DWORD [rbp-4], 100
    jne     .L_false         ; x != 0 이고 x != 100 이면 거짓
.L_true:
    mov     eax, 1
    jmp     .L_end
.L_false:
    mov     eax, 0
.L_end:
    pop     rbp
    ret
```

`&&`와 정반대로, `||`는 왼쪽이 **참**일 때(`je .L_true`) 바로 결론으로 건너뛴다. 왼쪽이 거짓일 때만 오른쪽 비교(`cmp ... 100`)가 실행된다.
