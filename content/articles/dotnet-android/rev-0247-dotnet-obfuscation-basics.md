## 한 줄 요약
.NET 난독화 도구(ConfuserEx 등)는 크게 **이름 맹글링(의미 없는 이름으로 교체), 제어 흐름 난독화(분기를 뒤섞고 불필요한 goto/스위치를 추가), 문자열 암호화(리터럴을 암호화해서 런타임에 복호화)** 세 가지를 조합해서 디컴파일 결과를 읽기 어렵게 만들지만, 이 세 가지 패턴 자체를 미리 알고 있으면 도구별 전용 디옵퓨스케이터 없이도 침착하게 원래 로직을 재구성할 수 있다.

## 언제 검색해야 하나
- ILSpy/dnSpyEx로 열었더니 클래스와 메서드 이름이 전부 `a`, `b`, `c`, `<Module>{GUID}` 같은 의미 없는 문자로 되어 있을 때
- 디컴파일러가 특정 메서드에서 "Could not decompile" 오류를 계속 내거나, 코드가 `goto IL_0042;` 같은 라벨 점프로 가득해서 논리 흐름을 눈으로 따라가기 힘들 때
- 문자열이 정상적인 텍스트가 아니라 바이트 배열이나 이상한 문자로 나와 있어서 실제 값을 알 수 없을 때
- ".NET 난독화가 대체 뭘 하는 건지" 전체 그림을 먼저 잡고 싶을 때

## 핵심 개념

### 왜 .NET은 유독 난독화가 절실한가
CIL은 메타데이터를 풍부하게 보존하기 때문에 디컴파일러가 원본 소스에 매우 가까운 코드를 복원해낸다는 것이 [REV-0242](./rev-0242-dotnet-identification.md)에서 다룬 .NET 리버싱의 큰 장점이었다. 하지만 이것은 배포자 입장에서는 정반대로 **소스코드를 거의 그대로 유출하는 것**과 같은 심각한 약점이 된다. 그래서 상용/CTF용 .NET 프로그램은 네이티브 C/C++ 프로그램보다 훨씬 적극적으로 난독화 도구를 적용하는 경향이 있다. 대표적인 오픈소스 도구가 `ConfuserEx`(및 그 포크들)이며, 상용 도구로는 `.NET Reactor`, `Eazfuscator.NET` 등이 있다. 이 글은 특정 도구의 역난독화 절차가 아니라, **어떤 도구를 쓰든 공통적으로 나타나는 패턴 세 가지**를 이해하는 데 집중한다.

### 패턴 1: 이름 맹글링(Name Mangling)
클래스, 메서드, 필드, 지역변수 이름을 `a`, `b`, `A`, `class1` 같은 짧고 의미 없는 이름으로 전부 바꿔치기하는 가장 기본적인 난독화다. IL 메타데이터에서 이름 자체는 원래 자유 문자열이라 컴파일러/런타임 동작에는 전혀 지장이 없고, 오직 사람이 읽었을 때 맥락을 잃게 만드는 것이 목적이다.
- **대응 전략**: 이름 대신 **동작(behavior)**으로 판단한다. 어떤 메서드가 `string.Equals`를 호출하고 결과에 따라 두 갈래로 분기한다면, 이름이 `a`든 `CheckPassword`든 "검증 함수"라는 사실은 똑같다. dnSpyEx/ILSpy에서 이런 함수를 찾으면 우클릭 → **Rename**(또는 IL 편집 후 Edit Method)으로 자기가 이해하기 쉬운 임시 이름을 붙여가며 분석하면 큰 프로그램에서도 길을 잃지 않는다.

### 패턴 2: 제어 흐름 난독화(Control Flow Obfuscation)
원래는 단순한 `if`/`else`나 `for` 루프였던 코드를, 실행 결과는 동일하게 유지하면서 **불필요한 분기, 상태 변수, `switch`문 기반의 흐름 뒤섞기(control flow flattening)**로 바꿔버리는 기법이다. 대표적인 형태가 하나의 정수 상태 변수(state variable)를 두고 `while(true) { switch(state) { case 1: ...; state = 3; break; case 2: ...; } }` 처럼, 원래 순차적이던 코드 블록들을 `switch`의 각 `case`로 흩어놓아서 순서를 뒤섞는 것이다. 디컴파일러는 이런 구조를 원래의 `if/else`로 복원하지 못하고 `goto`가 잔뜩 섞인 못생긴 코드를 그대로 보여주는 경우가 많다.
- **대응 전략**: goto/switch를 억지로 눈으로 따라가려 하지 말고, 상태 변수(state)가 어떤 값일 때 어떤 case로 가는지부터 표로 정리한다. 또는 [REV-0245](./rev-0245-cil-to-csharp.md)에서 다룬 IL 레벨로 내려가서 `br`/`brtrue`/`brfalse`의 목적지를 하나씩 따라가며 실제 실행 순서를 재구성하는 것이 오히려 더 명확할 때가 많다. dnSpyEx의 디버거로 실제 실행 중 브레이크포인트를 걸어 `state` 값이 어떻게 바뀌는지 관찰하는 동적 접근도 효과적이다.

### 패턴 3: 문자열 암호화(String Encryption)
`ldstr "flag{...}"`처럼 코드에 평문 문자열이 그대로 노출되면 [REV-0246](./rev-0246-dotnet-strings-resources.md)에서 다룬 검색만으로 바로 들킨다는 것을 알기 때문에, 많은 난독화 도구가 문자열 리터럴을 암호화된 바이트 배열로 바꾸고, 프로그램 시작 시(또는 각 사용 시점에) 복호화하는 별도 메서드를 자동 삽입한다. 이 경우 IL을 봐도 `ldstr` 대신 `ldc.i4` 상수 배열과 `call SomeDecryptMethod(...)` 호출만 보인다.
- **대응 전략**: 문자열이 쓰이는 지점에서 호출되는 복호화 메서드를 찾아 그 알고리즘(대개 XOR, 간단한 치환, 또는 AES 같은 표준 암호)을 파악한다. 알고리즘이 단순하면(XOR 등) 파이썬 등으로 동일 연산을 재현해서 모든 암호화된 문자열을 일괄 복호화할 수 있다. 많은 난독화 도구는 프로그램이 처음 실행될 때 문자열을 한꺼번에 복호화해서 어딘가에 캐싱해두므로, dnSpyEx로 그 초기화 루틴이 끝난 직후 브레이크포인트를 걸고 메모리 상의 복호화된 값을 직접 들여다보는 동적 방법이 정적으로 알고리즘을 역산하는 것보다 훨씬 빠를 때도 많다.

### 그 밖에 자주 보이는 보조 기법
- **어셈블리 병합/임베딩**: 여러 DLL을 하나의 exe 안에 리소스로 압축해 넣고 런타임에 로드하는 방식(예: `Costura.Fody`, `ILRepack`). 실제 로직을 담은 DLL이 메인 exe가 아니라 리소스 안에 있을 수 있으니 [REV-0246](./rev-0246-dotnet-strings-resources.md)의 리소스 확인을 함께 병행해야 한다.
- **안티 디버그/안티 덤프 체크**: `Debugger.IsAttached` 확인이나 자체 무결성 검사(자기 자신의 해시를 확인)를 추가해서 dnSpyEx 디버거 연결을 방해하려는 코드가 섞여 있을 수 있다.
- **가짜 메서드/죽은 코드 삽입**: 실제로는 호출되지 않는 더미 메서드를 잔뜩 끼워 넣어 분석 시간을 늘리는 기법.

## 화면/코드에서 보이는 징후
- 트리에 `a`, `b`, `c`, `<PrivateImplementationDetails>` 처럼 사람이 붙였다고 보기 힘든 이름이 대량으로 나열된다.
- 코드 안에 `int num = 0; while (true) { switch (num) { ... } }` 형태의 뼈대가 반복되고, 그 안에 `goto`가 여러 개 섞여 있다.
- `ldstr` 없이 `byte[]` 배열 초기화와 함께 낯선 이름의 static 메서드 호출이 문자열이 필요한 자리마다 반복적으로 나타난다.

## 가장 먼저 할 것
난독화된 프로그램을 만나면 전체를 한 번에 이해하려 하지 말고, **진입점(`Main`)에서부터 실제로 호출되는 메서드 몇 개만 골라 좁게 파고든다.** 이름이 아무리 깨져 있어도 `Main`은 대개 진입점이므로 `Go to Entry Point`로 여전히 찾을 수 있고, 거기서부터 호출 그래프를 하나씩 따라가면 어차피 분석해야 할 범위는 전체 어셈블리가 아니라 몇 개 메서드로 좁혀진다.

## 단계별 절차

**1) 난독화 여부와 종류 가늠하기**
트리의 이름 패턴(이름 맹글링), 특정 메서드를 열었을 때 디컴파일 실패 빈도(제어 흐름 난독화), 문자열 검색 결과가 거의 없는지(문자열 암호화) 세 가지를 빠르게 체크해서 어떤 조합이 적용됐는지 가늠한다.

**2) Main부터 호출 그래프 좁히기**
`Go to Entry Point`로 `Main`을 찾고, [REV-0244](./rev-0244-ilspy-basics.md)의 **Analyze(Uses/Used By)** 기능으로 실제로 호출되는 메서드만 추려낸다. 호출되지 않는 메서드(죽은 코드/더미)는 무시한다.

**3) 의심 메서드에 임시 이름 붙이기**
동작이 파악된 메서드는 dnSpyEx에서 우클릭 → Rename으로 `Check_Password`처럼 알아보기 쉬운 이름을 붙여 분석 진행 상황을 표시해 둔다(원본 파일이 아니라 사본에서 작업한다).

**4) 제어 흐름이 뒤섞인 메서드는 IL로 내려가서 분기 추적**
디컴파일 결과가 `goto` 범벅이면 [REV-0245](./rev-0245-cil-to-csharp.md)의 방법대로 IL 원문에서 `br`/`brtrue.s`/`brfalse.s`의 목적지를 하나씩 따라가며 실제 실행 순서를 종이에 재구성한다.

**5) 문자열 암호화는 동적으로 우회**
문자열이 암호화되어 있다면 dnSpyEx 디버거로 해당 문자열이 사용되는 지점(복호화 함수 호출 직후)에 브레이크포인트를 걸고 `Locals`/`Watch` 창에서 복호화된 실제 값을 직접 확인한다.

**6) 알고리즘이 단순하면 정적 재현**
복호화 로직이 단순 XOR/치환 수준이면 파이썬 스크립트로 동일 연산을 재현해서 모든 암호화 문자열을 한 번에 복호화하는 방법도 고려한다(반복 작업이 많을 때 특히 효율적).

## 명령어/단축키
```text
dnSpyEx: 어셈블리 우클릭 → Go to Entry Point   Main 찾기(이름이 깨져도 진입점 표시는 유지됨)
dnSpyEx: 메서드/변수 우클릭 → Rename            임시 이름 붙이기(분석용 메모)
ILSpy/dnSpyEx: 멤버 우클릭 → Analyze            Uses / Used By로 호출 그래프 좁히기
dnSpyEx: F9 브레이크포인트, F5 디버그 시작        복호화 후 실제 값 관찰
```

## 출력 해석
- `Analyze`의 **Used By**가 비어 있는 메서드가 대량으로 나온다면 죽은 코드/더미 삽입 난독화가 적용됐을 가능성이 높으니 분석 우선순위에서 제외한다.
- 브레이크포인트에서 확인한 복호화 후 문자열이 `flag{...}`나 URL, 파일 경로 형태로 사람이 읽을 수 있는 값이면 그 지점이 바로 찾던 목표에 해당한다.
- 같은 복호화 함수가 프로그램 전체에서 수십~수백 번 호출된다면, 그 함수가 문자열 암호화 도구가 자동 삽입한 공통 헬퍼일 가능성이 매우 높다.

## 흔한 실수
- 이름이 깨졌다고 곧바로 분석을 포기하는 것. 이름은 사람을 위한 라벨일 뿐 실행에는 아무 영향이 없으므로, 동작을 기준으로 판단하면 충분히 분석 가능하다.
- 제어 흐름 난독화가 걸린 메서드를 디컴파일된 C#만으로 눈으로 완벽히 이해하려고 시간을 쏟는 것. 오히려 IL이나 동적 디버깅이 더 빠를 때가 많다.
- 문자열 암호화 알고리즘을 처음부터 완벽하게 역산하려는 것. 실전에서는 알고리즘을 몰라도 실행 중 복호화된 값을 직접 훔쳐보는 동적 방법이 훨씬 빠른 경우가 많다.
- 특정 상용 난독화 도구 전용 자동 디옵퓨스케이터가 없다고 분석 자체가 불가능하다고 오해하는 것. 도구가 없어도 이 글에서 다룬 세 가지 기본 패턴만 이해하면 손으로도 충분히 진행할 수 있다(범위가 매우 큰 상용 난독화는 시간이 오래 걸릴 뿐 원리는 같다).

`ObfCrackme.exe`를 ILSpy로 열었더니 트리가 `a.b.c` 같은 이름으로 가득하다. `Go to Entry Point`로 `Main`(이 메서드만은 여전히 `Main`이라는 이름 그대로인 경우가 많다, 진입점 이름은 런타임이 찾아야 하므로 잘 안 바꾼다)을 찾아 들어가 보니, 안에서 호출하는 함수 하나가 `byte[]` 배열을 인자로 받아 무언가를 반환하는 짧은 static 메서드를 거쳐 `Console.WriteLine`에 그 결과를 넘긴다. 이 짧은 static 메서드가 바로 문자열 복호화 함수로 의심된다. dnSpyEx로 다시 열어 그 복호화 함수 호출 직후 줄에 브레이크포인트를 걸고 `F5`로 실행한 뒤 `Locals` 창을 보면, 반환값이 `"Welcome to the crackme!"` 같은 평문으로 나타나는 것을 확인할 수 있다. 이런 식으로 이름과 겉모습이 아무리 뒤섞여 있어도, 실행 흐름과 실제 값은 동적으로 관찰하면 그대로 드러난다.
