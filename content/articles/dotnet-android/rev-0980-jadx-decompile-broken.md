## 한 줄 요약
JADX 디컴파일 결과가 특정 메서드에서 `// Could not decompile` 주석만 남기거나 코드가 이상하게 뭉개져 보이는 이유는 대부분 해당 앱이 강한 난독화/최적화(R8/ProGuard의 코드 축소·인라인)를 거쳤거나, JADX가 아직 완벽히 지원하지 못하는 최신 코틀린 컴파일러 패턴이 쓰였거나, dex 최적화 과정에서 생긴 비표준 바이트코드 패턴을 만났기 때문이다.

## 언제 검색해야 하나
- 특정 메서드를 열었는데 코드 본문 대신 `// Could not decompile` 이나 텅 빈 화면만 보일 때
- 디컴파일된 코드에 `catch` 블록이 이상하게 중첩되어 있거나 변수 이름이 `var10000` 같은 자동 생성 이름뿐일 때
- 코드가 있긴 한데 논리가 원래 자바/코틀린 코드와 명백히 다르게 보일 때(최적화로 인한 재구성)
- JADX가 특정 클래스를 열 때 GUI가 멈추거나 매우 느려질 때

## 핵심 개념
JADX는 DEX 바이트코드를 정적 분석으로 재구성해서 사람이 읽을 만한 자바 코드로 되돌리는 디컴파일러다. 이 과정은 항상 100% 성공을 보장하지 않는다. 실패 또는 왜곡의 흔한 원인은 세 가지다.

첫째, **코드 축소/난독화 도구(R8, ProGuard)**가 죽은 코드 제거, 인라인, 제어 흐름 평탄화 같은 최적화를 적용하면 원본 소스와 대응 관계가 사라진 바이트코드가 생기고, JADX의 패턴 인식이 실패할 수 있다.

둘째, **코틀린 컴파일러가 생성하는 복잡한 상태 머신**(코루틴, 람다, 인라인 함수)이 최신 문법일수록 JADX 버전이 아직 대응하지 못한 패턴일 수 있다.

셋째, **dex 최적화 특유의 비표준 명령어 시퀀스**(레지스터 재사용, 예외 테이블의 비정상적 구조)가 JADX의 제어 흐름 복원 알고리즘을 헷갈리게 만들 수 있다.

이 문제들은 JADX 최신 버전으로 상당 부분 개선되지만, 완전히 사라지지는 않는다. 이럴 때는 JADX 자체가 제공하는 **Smali 보기**(로우레벨 원문 바이트코드)로 전환해서 원문을 직접 읽는 것이 가장 확실한 대안이다.

## 화면/코드에서 보이는 징후
- 메서드 본문에 `/* JADX: Could not decompile */` 또는 `// Could not decompile method`라는 회색 주석만 있다.
- 코드에 `int_1`, `var10000`, `switch (0)` 같은 비직관적인 자동 생성 표현이 많다.
- 트리 노드 이름이 유난히 `a`, `b`, `c` 처럼 한두 글자로만 되어 있는 클래스/메서드가 많다(난독화).
- JADX-GUI 설정(`Settings`)에 `Show inconsistent code` 같은 옵션이 켜져 있으면 이상한 코드도 강제로 보여준다.

## 가장 먼저 할 것
문제의 메서드를 우클릭하거나 상단 뷰 옵션에서 **Smali** 보기로 전환해서 원문 바이트코드가 실제로 존재하는지, 그리고 그 바이트코드 자체가 이상한 최적화 패턴인지부터 확인한다. Smali가 정상적으로 보인다면 디컴파일만 실패한 것이고, Smali 자체도 이상하면 dex 최적화/난독화가 원인일 가능성이 크다.

## 단계별 절차
1. 문제 메서드에서 **Smali** 보기로 전환해 원문 바이트코드를 확인한다.
2. JADX/JADX-GUI를 최신 버전으로 교체한 뒤 같은 파일을 다시 열어본다 — 디컴파일러 개선으로 해결되는 경우가 많다.
3. `Settings`에서 디컴파일 관련 옵션(예: 인라인 익명 클래스, 변수 이름 추론 등)을 조정해서 다시 시도한다.
4. 그래도 실패하면 apktool로 같은 APK를 디코딩해 smali를 텍스트로 직접 읽으며 로직을 손으로 재구성한다.
5. 코틀린 코루틴/람다 패턴이 의심되면, 원본 패턴(예: `Continuation`, `suspend` 관련 상태 머신)에 대한 배경 지식을 참고해서 재구성된 코드를 해석한다.
6. 특정 문자열/상수만 필요하다면 JADX의 Text Search로 해당 문자열이 정의된 다른(디컴파일 성공한) 위치를 찾아 우회한다.

## 명령어/단축키
```text
우클릭 클래스/메서드 → Smali 보기(또는 상단 뷰 전환)   원문 바이트코드 확인
Ctrl+Shift+F                                              전체 텍스트 검색으로 우회 단서 찾기
Settings → Decompile                                       디컴파일 옵션 조정
jadx -d output/ target.apk                                 CLI로 재시도(GUI와 다른 결과가 나올 수도 있음)
```

## 출력 해석
- `Could not decompile method`가 뜨는 메서드가 극소수(전체 앱 중 한둘)라면 정상 범주이며, Smali로 그 부분만 보완하면 충분하다.
- 앱 전체 대부분의 메서드가 이렇게 나온다면 심각한 난독화(상용 난독화 도구 적용)를 의심해야 하며, JADX 단독으로는 한계가 있다.
- Smali 보기에서도 명령어가 극단적으로 뒤섞여 있다면(레지스터 재사용이 심함) 최적화 강도가 높은 릴리즈 빌드라는 신호다.

## 흔한 실수
- Smali 보기를 시도해보지도 않고 "JADX가 고장났다"고 결론짓는 것.
- 이상하게 재구성된 코드를 그대로 원본 로직이라고 믿고 분석을 진행하는 것 — 특히 최적화된 조건문 순서는 원본과 다를 수 있다.
- 구버전 JADX를 계속 쓰면서 업데이트를 시도하지 않는 것.
- 난독화된 이름(`a`, `b`, `c`)을 보고 바로 포기하는 것 — 이름과 무관하게 동작(문자열 비교, 호출 순서)을 기준으로 로직을 따라가면 충분히 분석 가능한 경우가 많다.

## 막혔을 때 다음 체크
- Smali 문법 자체가 익숙하지 않다면 → REV-0252 smali 기초 문법
- apktool로 직접 디코딩해서 리소스/smali를 함께 봐야 한다면 → REV-0979 APK가 apktool로 디코드가 안 될 때
- 코드를 수정해서 재빌드까지 해야 한다면 → REV-0981 smali 코드를 수정 후 재빌드가 실패할 때

## 미니 예제
`Validator` 클래스의 `check` 메서드가 JADX-GUI에서 `// Could not decompile method: check`로만 나왔다. Smali 보기로 전환하니 `invoke-virtual`과 `move-result` 사이에 예외 테이블(`.catchall`)이 복잡하게 얽혀 있는 것을 확인했다. 이는 컴파일러가 try-finally 구조를 최적화 과정에서 재배치한 전형적인 패턴으로, JADX가 이 특정 형태를 완전히 재구성하지 못한 것이었다. Smali 코드를 한 줄씩 손으로 읽어 `p1.equals(v0)` 비교와 그 결과에 따른 분기를 직접 추적해 로직을 파악했다.
